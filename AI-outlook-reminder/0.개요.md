# AI Outlook Reminder 개요

> 2026-10-06 설계 회의록과 이후 사용자와의 요구사항 논의를 바탕으로 작성한 현재 시점의 개요다. 회의 당시 의견, 이후 구체화된 방향, 아직 검증되지 않은 구현 후보를 구분한다. 개발 완료나 실제 회사 계정의 API 연동 성공을 의미하지 않는다.

## 1. 추진 배경

회사는 SAP 전문 컨설팅 및 솔루션 회사이며, 경영관리본부는 여러 고객사와의 거래, 계약 및 관련 서류 절차를 담당한다. 이 과정에서 Outlook 이메일로 안내와 요청을 주고받으며 많은 메일을 처리하고 있다.

담당자가 이메일로 전달된 후속 처리를 놓쳐 회사가 받아야 할 대금을 받지 못하는 사례가 발생했다. 정확히 누락된 절차와 손실 규모는 추가 확인이 필요하지만, 핵심 문제는 이메일 속 업무 요청이 실제 처리로 이어지지 않았다는 것이다.

따라서 단순한 새 메일 알림을 넘어, 담당자가 **무엇을 해야 하는지 확인하고 미처리 업무를 계속 추적할 수 있는 기능**이 필요하다.

## 2. 목표와 현재 구상

**Outlook 이메일을 수집하고 LLM으로 내용을 요약·판단하여, 회신이나 후속 처리가 필요한 업무를 To-do list로 제공한다.**

회의 이후 사용자는 업무적 판단을 Outlook 기본 기능에 맡기지 않고 LLM으로 수행하겠다는 방향을 명확히 했다. 메일·작업 API는 데이터를 읽고 쓰는 역할을 맡고, LLM은 요청의 의미와 필요한 행동을 파악하는 역할을 맡는다.

현재 사용자가 명시한 구상은 다음과 같다.

1. 제공되는 API로 이메일 내용을 가져온다.
2. LLM이 내용을 요약하고 회신이 필요한지 판단한다.
3. 처리할 항목을 할 일 목록에 표시한다.
4. 담당자가 목록을 확인하고 업무를 처리한다.

원래 사고의 재발을 방지하려면, 회신뿐 아니라 **대금 청구, 서류 제출, 포털 등록, 승인 요청 등 메일 밖에서 수행하는 행동**도 판단 대상에 포함하는 것을 권장한다. 구체적인 업무 유형은 실제 사용자와 확인해야 한다.

### PoC 계정 조건 변경 — 2026-10-07

사용자 설명에 따르면 회사 관리자가 회사 계정의 Microsoft Graph 접근을 제한한 상태다. 따라서 **이번 구현·테스트는 회사 계정 대신 사용자의 개인 계정으로 로컬에서 진행한다.** 먼저 개인 Microsoft 계정의 Outlook.com 메일함, To Do, 개인 계정 로그인 지원 앱 등록·인증 가능 여부를 확인한다.

기본 시험 데이터는 업무 상황을 재현한 합성 메일로 준비한다. 회사 메일을 개인 계정으로 옮기는 것을 전제하지 않는다. 개인 계정 PoC에서 기술 흐름을 검증한 뒤 회사 적용 시 관리자 권한·정책과 실제 업무 환경을 별도로 검증한다.

구체적인 현재 실행 순서와 완료 기준은 [[1.목표·상태·상황 및 로컬 PoC 행동 플랜]]을 따른다. 아래의 전체 서비스 후보와 회사 도입 과제는 장기 검토 범위이며 이번 개인 계정 PoC의 필수 범위와 구분한다.

## 3. 현재 우리가 해야 하는 일

현재 단계는 **요구사항 구체화와 연동 가능성 검증**이다. 제품 전체를 바로 구현하기 전에 실제 대상 메일함에 접근할 수 있는지, 어떤 메일을 업무로 판단해야 하는지, 목록을 어디에 표시할지를 확인해야 한다.

| 구분 | 현재까지 파악된 내용 | 남은 작업 |
|---|---|---|
| 업무 문제 | 메일 후속 처리 누락으로 대금 미수령 사례 발생 | 실제 누락 사례와 정상 처리 절차 확인 |
| 판단 방식 | 사용자가 LLM을 이용한 요약·업무 판단을 원함 | 업무 유형, 판단 기준, 평가용 사례 정리 |
| 메일 환경 | 회사 계정 대신 개인 계정으로 PoC 진행하기로 함 | 개인 Microsoft 계정의 Outlook.com 메일함·To Do 사용 여부 확인. 회사 사서함 검증은 후속 단계 |
| API | 회사 계정의 Graph 접근 제한을 사용자 설명으로 파악함 | 개인 계정 로그인 지원 앱 준비 및 개인 메일 조회·작업 등록 시험 |
| 목록 화면 | To-do list와 완료 체크가 필요함 | Microsoft To Do 재사용 또는 자체 UI 결정 |
| 리마인더 | 주기적 상기 요청과 수동·실행 시 갱신 대안이 논의됨 | 수집 주기, 알림 시점, PC 종료 중 동작 요구 확인 |
| 구현 | Python이 후보로 언급됨 | 실행 환경, LLM 공급자·모델 및 비용 확인 |

## 4. 개발하거나 기존 기능으로 충족해야 할 기능

아래 항목은 현재 요구를 기능으로 정리한 것이다. 모든 기능을 새로 개발한다는 의미는 아니며, 목록·알림·완료 관리는 기존 제품을 재사용할 수 있다.

| 기능 | 필요한 동작 | 구현 시 확인할 점 |
|---|---|---|
| 메일 수집 | 허용된 사서함·폴더에서 대상 메일과 필요한 본문을 가져옴 | 과거 메일 범위, 자동 이동 폴더, 공유 사서함, 첨부 분석 여부 |
| 대화 맥락 확인 | 관련 수신·발신 메일과 기존 작업 상태를 함께 확인 | 이미 회신한 요청과 새로 발생한 요청을 구분 |
| LLM 요약 | 메일의 핵심 내용과 요청 사항을 짧게 정리 | 원문을 확인할 수 있도록 연결 유지 |
| LLM 업무 판단 | 필요한 행동, 회신 필요 여부, 기한 후보와 판단 근거 추출 | 기한이 없거나 판단이 불명확하면 임의 확정하지 않음 |
| 할 일 등록·표시 | 업무 제목, 요약, 해야 할 행동, 기한, 원문 링크를 목록으로 제공 | Microsoft To Do 또는 자체 화면 선택 |
| 상태 관리 | 사용자가 완료 여부를 확인하고 잘못된 판단을 수정 | 읽음·답장 발송과 실제 업무 완료를 구분 |
| 갱신·리마인더 | 새 업무를 반영하고 미처리 업무를 상기 | 실행 시·수동·주기 실행 및 반복 알림 정책 미정 |
| 누락·중복 관리 | 수집·분석 실패를 기록하고 재처리하며 동일 작업 중복 생성 방지 | 마지막 성공 시각, 실패 상태, 메일과 작업의 연결 기록 필요 |

### LLM 분석 결과의 예시

다음은 실제 메일이 아닌 출력 형태를 설명하기 위한 예시다.

| 항목 | 예시 |
|---|---|
| 요약 | 고객사가 이번 달 용역대금 청구 절차를 안내함 |
| 필요한 행동 | 청구서를 작성해 고객사 포털에 제출 |
| 업무 유형 | 대금 청구 |
| 회신 필요 여부 | 확인 필요 — 제출 이후 회신 요청은 불명확 |
| 기한 | 원문에 명시된 날짜. 없으면 미확인 |
| 판단 근거 | 기한과 제출 요청이 담긴 원문 문장 |
| 상태 | 사용자 확인 필요 또는 미완료 |
| 원문 | 해당 Outlook 메일 링크 |

### 누락 방지와 완료 처리 원칙 — 초기 구현 권장안

- 회신하지 않은 메일이 모두 할 일인 것은 아니며, 회신한 메일도 후속 업무가 남아 있을 수 있다.
- LLM 판단이 불확실하거나 분석이 실패한 메일은 조용히 제외하지 않고 확인 대상으로 남긴다.
- 초기에는 사용자 확인을 완료 기준으로 삼고, 읽음이나 회신 여부만으로 자동 완료하지 않는다.
- 동일 대화에도 여러 업무가 있을 수 있으므로, 대화가 같다는 이유만으로 모두 하나의 작업으로 합치지 않는다.
- 메일 수집 누락과 LLM 판단 누락을 구분해 점검한다. '절대 누락 없음'은 회의에서 강조된 목표이며 현재 보장된 성능이 아니다.
- 메일 본문은 분석 대상 데이터로 취급하며, 본문에 포함된 지시가 프로그램 권한이나 처리 규칙을 변경하지 않도록 한다.

## 5. 구현 후보와 우선 검토 방향

### 용어와 역할

| 구성 요소 | 역할 |
|---|---|
| Outlook | 직원이 메일을 읽고 보내는 앱·웹 화면 |
| Exchange Online | 회사 메일을 저장·송수신하는 Microsoft 클라우드 서비스 |
| Microsoft Graph | 프로그램이 메일과 작업 데이터에 접근하는 공식 API |
| LLM | 메일을 요약하고 필요한 업무를 판단하는 모델 |
| Microsoft To Do | 할 일 목록, 기한·리마인더 및 완료 상태를 관리하는 앱 |

To Do는 이미 등록된 작업을 관리하는 도구다. **회신하지 않은 메일을 찾아서 업무 필요성까지 판단하는 기능을 To Do만으로 해결하는 구상은 적합하지 않다.** 메일 수집과 LLM 판단을 별도로 구성해야 한다.

### 구현 후보

| 후보 | 장점 | 주요 조건 |
|---|---|---|
| Python + Graph + Microsoft To Do | 목록·알림·완료 UI를 재사용하여 개발량을 줄임 | 회사 API 권한과 To Do 사용 가능 여부 확인 |
| Python + Graph + 자체 데스크톱 UI | 메모장 형태와 업무별 표시를 자유롭게 구현 | UI·알림·상태 저장·배포를 추가 개발 |
| Power Automate + LLM + To Do | 클라우드에서 실행하여 PC 종료 중에도 처리 가능 | 라이선스·AI 연결 방식 및 누락·중복 보완 검토 |
| 클라우드 Python + Graph + To Do 또는 웹 UI | 상시 처리와 여러 직원으로 확대하기에 적합 | 클라우드 운영·인증·권한 관리 필요 |

**우선 검토 제안은 Python + Microsoft Graph + LLM + Microsoft To Do 조합이다.** 실제 사용자에게 To Do 화면이 충분한지 확인한 뒤 부족한 부분만 자체 UI로 보완한다. 이는 현재 권장안이며 확정된 아키텍처가 아니다.

```text
메일함(이번 PoC: 개인 Outlook.com 시험 메일함)
  → Microsoft Graph로 메일 및 관련 대화 조회
  → Python에서 수집 이력·기존 작업 확인
  → LLM 요약 및 업무·기한 후보 추출
  → 결과 검증·중복 확인
  → To-do list 등록·갱신
  → 담당자 확인·처리·완료 체크
```

로컬 Python 프로그램은 PC가 꺼져 있으면 새 메일 분석을 실행할 수 없다. PC 종료 중 처리까지 필요하면 Power Automate 또는 클라우드 실행 환경을 검토한다. 목록에 이미 등록된 작업의 알림과 새로운 메일을 수집·분석하는 과정은 별도로 확인한다.

## 6. 다음 작업 순서와 확인 기준

| 순서 | 작업 | 확인 기준 |
|---|---|---|
| 1 | 실제 사용자 요구사항 확인 | 대상 계정·폴더·업무 유형·완료 기준·알림 요구가 정리됨 |
| 2 | 계정·권한·데이터 처리 조건 확인 | Graph 접근 가능 여부, To Do 사용 가능 여부, 회사 메일을 처리할 수 있는 LLM 환경이 확인됨 |
| 3 | 최소 연동 검증 | 허용된 테스트 메일 조회와 테스트 작업 생성·완료·알림 동작을 실제 환경에서 확인 |
| 4 | 업무 판단 검증 | 실제 사례 또는 승인된 비식별 사례에서 요약·행동·기한 추출 결과를 담당자가 평가 |
| 5 | 수집부터 목록 표시까지 연결 | 중복 실행, 분석 실패, 재시작 이후에도 작업이 추적됨 |
| 6 | 대상 직원 시험 사용 | 잘못 등록된 업무와 놓친 업무를 확인하고 판단 기준·화면·알림을 조정 |

판단 검증에는 회신 필요 메일, 단순 안내, 이미 처리한 대화, 청구·서류 제출 요청, 기한이 불명확한 요청 등을 포함한다. 허용 가능한 누락률·오탐률과 알림 지연 기준은 담당자와 합의해야 하며, 현재 수치가 정해진 것은 아니다.

## 7. 아직 결정하지 않은 사항

- 대상 직원 수, 개인 사서함 또는 공유 사서함 여부.
- 메일 수집 대상·과거 조회 범위·첨부파일 분석 범위.
- 업무를 묶는 기준과 완료 후 새 요청이 온 경우의 처리 방식.
- Microsoft To Do 재사용 여부와 별도 바탕화면 UI 필요성.
- 주기적 갱신·알림 간격, 기한 초과 알림, PC 종료 중 처리 필요성.
- Python 최종 채택, LLM 공급자·모델, 비용 및 회사 데이터 처리 조건.
- 앱 등록·동의·권한 승인 담당자, 개발 담당자, 일정 및 예산.
