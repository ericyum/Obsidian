# 목표·상태·상황 및 로컬 PoC 행동 플랜

## 1. 세 문장으로 정의한 업무

- **목표:** 로컬 PC에서 개인 계정의 Outlook 시험용 이메일을 가져와 LLM으로 요약·업무 판단하고, 필요한 행동을 할 일 목록으로 제공하여 담당자가 확인·완료 처리하고 알림을 받을 수 있는 PoC를 실행·검증한다.
- **상태:** 회의록과 개요 작성, Microsoft Graph·To Do 기능 조사, LLM 활용 방향 정리까지 진행했으며, 실제 API 접근·모델 호출·연결 구현은 아직 미검증이다. 회사 계정은 관리자에 의해 Graph 접근이 제한되어 있으며, 개인 계정으로 구현·시험하기로 했다.
- **상황:** 경영관리본부는 Outlook으로 고객사 계약·청구·서류 업무를 처리하고 있으므로, 기존 메일과 작업 관리 기능을 활용하면서 사람이 놓칠 수 있는 후속 행동을 드러내야 하며, 이번 검증은 개인 계정과 합성 업무 메일을 이용한 로컬 PC 실행까지다. 회사 환경 적용은 후속 검증으로 분리한다.

### 2026-10-07 추가 조건: 개인 계정으로 PoC 진행

- 사용자 설명에 따르면 회사 관리자가 회사 계정의 Microsoft Graph 접근을 제한한 상태다. 구체적인 차단 정책·오류는 별도 진단하지 않았지만, 회사 계정을 이번 PoC의 선행 조건에서 제외한다.
- 구현·테스트는 사용자의 개인 계정으로 진행한다. 개인 Microsoft 계정인지, 실제 Outlook.com 메일함이 있는지, 같은 계정으로 To Do를 사용할 수 있는지는 먼저 확인한다. 다른 업체 이메일 주소로 만든 Microsoft 로그인 계정만 있다고 메일 API 사용 가능성을 확정하지 않는다.
- 개인 계정 로그인 지원 앱의 등록·사용 가능 여부와 사용자 위임 인증을 확인한다. 개인 계정으로 바꾸었다는 이유만으로 앱 등록과 API 접근이 이미 해결되었다고 간주하지 않는다.
- 기본 시험 데이터는 업무 상황을 재현한 합성 메일로 준비한다. 회사 메일의 개인 계정 복사·전달을 계획에 포함하지 않는다. 실제 회사 자료를 사용해야 한다면 별도로 허용된 처리 범위를 확인한다.
- 개인 계정에서 C1~C7을 충족하면 이번 로컬 PoC를 완료할 수 있다. 회사 계정 접근 제한 해제는 그 완료 조건이 아니다.
- 회사 도입 시에는 관리자 협의, 회사 계정 인증·권한, 실제 사서함·공유 사서함, 회사 데이터와 정책 적합성을 다시 검증한다. 개인 계정 PoC 성공은 회사 환경 검증 완료를 뜻하지 않는다.

## 2. 목표

### 최종 결과

개발자 또는 시험 사용자가 로컬 PC에서 프로그램을 실행하면, 개인 계정의 합성 시험용 메일을 수집하고 LLM이 요약·행동·기한 후보를 제시하여 할 일 목록에 표시한다. 사용자는 원문과 판단 근거를 확인하고 업무를 완료 처리할 수 있다. 프로그램을 다시 실행해도 같은 메일의 작업이 중복 생성되지 않고 기존 완료 상태가 유지되는지 확인한다.

**이 문서에서 로컬은 프로그램의 실행 위치를 뜻한다.** Microsoft Graph·LLM API·Microsoft To Do 같은 외부 서비스 호출은 사용할 수 있다는 계획상 가정이다. 완전 오프라인 실행이나 로컬 LLM만 사용한다는 뜻은 아니며, 외부 서비스 사용 가능 여부는 첫 단계에서 확인한다.

### 완료 기준

| ID | PoC 완료 시 확인할 결과 | 남길 증거 |
|---|---|---|
| C1 | 로컬 PC에서 실행 절차에 따라 프로그램이 시작되고 개인 계정의 시험용 Outlook 메일과 필요한 대화 맥락을 실제 Graph로 조회함 | 실행 안내, 계정·수집 범위, 조회 결과 |
| C2 | 실제 LLM 호출로 요약·필요 행동·회신 필요 여부·기한 후보·판단 근거가 생성되고 형식 오류를 감지함 | 시험 사례별 입력 식별자와 분석 결과 |
| C3 | 선택한 목록 화면에서 업무·기한·원문·확인 필요 상태를 확인하고 완료 처리할 수 있음 | 목록 화면 및 완료 전후 기록 |
| C4 | 동일 입력 재실행과 프로그램 재시작 후 중복 작업이 없고 기존 완료 상태가 유지됨 | 반복 실행 전후 작업 수·상태 비교 |
| C5 | 시험 작업에 지정한 알림이 선택한 방식으로 나타남 | 설정 시각·실제 표시 시각·클라이언트 실행 조건 |
| C6 | 수집 또는 분석 실패가 성공·업무 없음으로 처리되지 않고, 실패를 확인한 후 재시도할 수 있음 | 실패 사례·표시 결과·재시도 결과 |
| C7 | 사전에 정한 평가 사례와 기대 결과에 대조해 결과를 검토하고 누락·오탐·한계를 기록함 | 검증표, 수정 후 재검증 결과 |

초기 검증 기준 제안은 **평가 사례에 미리 지정한 핵심 청구·제출 요청이 아무 표시 없이 사라지는 경우가 없어야 한다**는 것이다. 불확실한 경우 확인 필요로 표시할 수 있으나, 모든 메일을 확인 필요로 보내는 방식은 유용성을 증명하지 못하므로 정확한 판단·불필요한 작업·확인 필요 비율도 함께 기록한다. 사례와 수용 기준은 구현 전에 정하며 운영 환경의 무누락 보장을 의미하지 않는다.

### 반드시 보존할 것

- 회신 여부와 실제 업무 완료 여부를 구분한다.
- 기한이 없거나 근거가 부족하면 임의로 확정하지 않는다.
- 분석 실패·판단 불확실성을 사용자가 볼 수 있게 남긴다.
- 원문과 생성된 업무의 연결을 유지한다.
- 메일 본문은 분석 데이터로 취급하고 프로그램에 대한 명령으로 실행하지 않는다.
- 본인 개인 계정과 사용 가능한 LLM 환경에서 합성 시험 데이터를 이용한다. 회사 데이터의 외부 이용은 별도 허용 범위에 따른다.

### 이번 범위 밖

- 클라우드 서버 배포, PC 종료 중 상시 수집, 운영 서비스 수준의 가용성 보장.
- 여러 직원에게 배포하는 설치 프로그램, 조직 전체 권한·관리 시스템.
- 자동 회신, 자동 청구, 외부 포털 제출 등 업무 실행 자동화.
- 모바일 전용 화면, Chrome 확장 프로그램, Outlook 추가 기능 개발.
- 모든 과거 메일·모든 첨부 형식의 분석과 완전 자동 업무 병합.
- 실제 업무 완료를 LLM만으로 확정하는 기능.

## 3. 상태 — 현재 어디까지 준비되었는가

### 이미 완료된 것

- 2026-10-06 회의 초반 회고와 이후 녹취를 통합한 회의록을 작성했다.
- [[0.개요]]에 배경, 필요한 기능, 구현 후보, 미확정 사항을 정리했다.
- 사용자는 LLM으로 메일 내용을 요약하고 회신 등 필요한 업무를 판단하겠다는 방향을 밝혔다.
- Microsoft Graph와 Microsoft To Do를 통한 메일 조회·작업 관리 가능성을 문서 수준에서 조사했다.
- 사용자의 회사 계정으로 Outlook 웹메일을 이용하는 화면을 확인했다. 이후 사용자 설명으로 회사 계정의 Graph 접근 제한을 파악했다. 개인 계정 API 접근은 아직 검증하지 않았다.

### 재사용할 자료

- 기존 회의록과 [[0.개요]]의 업무 배경·기능 목록.
- 앞선 조사에서 확인한 Microsoft 공식 API 자료.
- 기존 Outlook·To Do 화면과 계정 체계 — 실제 사용 권한 확인 후 재사용.

### 아직 확인하지 못한 것

- 사용할 개인 Microsoft 계정과 Outlook.com 메일함의 준비 상태, 시험 폴더와 메일 범위.
- 개인 Microsoft 계정 로그인을 지원하는 앱 등록·사용 가능 여부와 위임 인증·동의 조건.
- To Do 작업 생성·완료·알림의 실제 동작 및 사용 적합성.
- 사용할 LLM, 접근 권한, 합성 메일 처리 조건 및 호출 비용.
- 정상·누락 사례에 대한 업무 담당자의 기대 판단과 완료 기준.
- 개발 코드 위치, Python 실행 환경 및 재사용할 코드 존재 여부.

현재 문서 폴더에서 확인한 것은 개요 문서이며, 개발 저장소 전체를 확인한 것은 아니다. '구현이 전혀 없다'고 단정하지 않고 착수 시 기존 코드와 환경을 확인한다.

### 현재 정할 수 있는 범위

개인 계정으로 로컬 PoC까지 진행한다는 목표와 LLM을 활용하는 방향은 사용자 요청으로 정해졌다. Python, Graph, To Do는 우선 검토안이다. 계정 접근 정책이나 데이터 처리 허용 범위, 실제 업무 판단 기준을 개발자가 임의로 확정하지 않는다.

## 4. 상황 — 어떤 업무와 환경에 들어가는가

### 사용자 이용 방식

담당자는 다수 고객사의 계약·대금 청구·서류 업무를 이메일로 주고받는다. 메일을 읽었거나 답장했더라도 별도 신청·제출이 남아 있을 수 있다. 따라서 목록은 '읽지 않은 메일'이나 '답장하지 않은 메일'의 단순 모음이 아니라 **아직 해야 할 행동을 확인하는 도구**가 되어야 한다.

회의에서는 출근 후 또는 프로그램 실행 시 목록 확인, 체크박스 완료 처리, 주기적인 상기가 논의되었다. 정확한 화면 형태와 알림 주기는 미정이다. PoC에서는 수동 실행·갱신으로 전체 흐름을 검증하고 시험 알림 한 건의 동작을 확인하는 범위를 우선 제안한다.

### 기존 기능과 책임

| 기존 기반 | 재사용할 역할 | 별도로 필요한 역할 |
|---|---|---|
| Outlook·개인 계정 시험 메일함 | 메일 보관, 조회 화면, 원문 열기 | 수집할 범위와 관련 대화 선정 |
| Microsoft Graph | 허용된 메일 조회, 작업 데이터 접근 | 로그인·권한 처리와 수집 이력 관리 |
| LLM | 텍스트 요약·의미 판단 | 업무 기준, 입력 맥락, 결과 검증 |
| Microsoft To Do | 목록, 기한·알림, 완료 체크 | 업무 후보 생성과 원본 메일 연결 |
| 로컬 PC | PoC 프로그램 실행 | 재시작 후 상태 복원, 실패 표시 |

To Do는 메일에서 미회신 업무를 자동 판별하는 대체재가 아니다. 메일 수집과 LLM 판단을 담당하는 부분이 필요하다. To Do를 사용할 수 있다면 같은 목록·완료·알림 UI를 다시 만드는 일을 줄일 수 있다.

### 운영·보안·조직 제약

- 회사 계정은 관리자에 의해 Graph 접근이 제한된 상태이므로 이번 PoC에서는 사용하지 않는다. 개인 계정의 접근 가능 여부를 독립적으로 시험한다.
- 시험은 허용된 계정과 한정된 메일 범위에서 진행하고, 타 직원 사서함의 접근 권한을 추정하지 않는다.
- 이번 시험은 합성 메일을 사용한다. 회사 메일을 개인 계정이나 외부 LLM으로 옮기는 것을 전제하지 않는다.
- 인증 토큰·API 키는 문서·공유 폴더·소스 저장소에 넣지 않는다. 로컬 상태와 로그에 저장할 내용·위치·삭제 기준을 정한다.
- 로컬 실행이 멈추면 신규 수집·분석도 멈춘다. To Do 알림의 실제 표시 조건은 별도 시험한다.
- 일정·예산·담당 승인자는 아직 정해지지 않았다. 확인되지 않은 날짜나 담당자를 계획에 임의 배정하지 않는다.

## 5. 차이와 판단

### 현재 상태와 목표의 차이

| 차이 | 먼저 필요한 판단 | 해소 방법 |
|---|---|---|
| 회사 계정 접근 제한, 개인 계정 연동 미검증 | 개인 계정의 메일함·앱 인증을 준비할 수 있는가? | 개인 계정 메일 조회와 작업 생성의 작은 연동 시험 |
| 필요한 업무의 기준이 없음 | 어떤 요청을 할 일로 만들 것인가? | 사례와 정답·확인 필요 기준 작성 |
| LLM 분석 결과를 본 적이 없음 | 필요한 맥락과 출력이 충분한가? | 승인된 사례로 실제 모델 호출·대조 |
| 목록과 알림 방식 미정 | To Do가 요구를 충족하는가? | 사용자 흐름과 생성·완료·알림 시험 |
| 연결 구현 미검증 | 재실행·실패에도 일관적인가? | 수집부터 표시까지 연결 후 반복·실패 시험 |

### 상황을 기준으로 제한한 해결 방식

1. **Graph 접근이 가능하면** 이를 우선 사용해 개인 계정의 시험 사서함을 조회한다.
2. **To Do가 사용 가능하고 필요한 화면·상태·알림을 충족하면** 목록 기능으로 재사용한다.
3. **To Do가 불가능하거나 요구를 충족하지 못하면** 이유를 기록한 뒤 최소 로컬 목록·완료·알림 기능으로 대체한다. 두 UI를 동시에 만들지 않는다.
4. **Python을 우선 후보로 하되** 기존 코드·실행 환경을 확인한 뒤 필요한 최소 구성을 정한다. 에이전트 프레임워크 도입을 전제하지 않는다.
5. **실시간 webhook·클라우드 배포는 제외하고** 수동 실행 중심으로 검증한다. 누락 확인을 위한 수집 이력·중복 방지는 생략하지 않는다.

개인 계정의 Graph 준비가 완료되기 전에는 합성·승인된 파일 입력으로 LLM 분석과 화면 검증을 진행할 수 있다. 다만 이것은 부분 검증이며, **실제 Outlook 연동 기준 C1을 충족한 전체 PoC 완료로 표시하지 않는다.**

## 6. 행동 플랜

### 1단계. 시험할 사용자 흐름과 데이터 범위를 정한다

- **근거:** 목표는 업무 누락 방지이며, 현재 실제 업무 사례와 환경 범위가 미확인이다.
- **행동:** 개인 Microsoft 계정과 Outlook.com 메일함을 확인하고 시험 폴더·기간 및 관련 발신 메일 조회 범위를 정한다. 합성 메일로 시험 대화를 준비한다. 대표적인 회신 요청, 단순 안내, 청구·제출 요청, 이미 처리된 대화, 기한 불명확 사례를 모으고 기대 결과를 적는다. 첨부 없이는 판단할 수 없는 메일을 어떻게 표시할지도 정한다.
- **목적:** 기술적으로 실행되는 것과 업무에 맞게 판단하는 것을 구분한다.
- **산출물:** 시험 범위, 대표 사례·기대 결과, C7의 평가 기준, 외부 API를 이용하는 로컬 실행 가정의 확인 결과.
- **다음 단계 조건:** 무엇을 읽고 어떤 결과를 기대하는지 명시되어 있다.

### 2단계. 권한·실행 환경과 최소 연동을 확인한다

- **근거:** 기존 Microsoft 기능을 재사용하려면 개인 계정에서 실제 접근할 수 있어야 한다.
- **행동:** 기존 코드·Python 환경을 확인한다. 개인 Microsoft 계정 로그인 지원 앱의 등록·사용 가능 여부, 사용자 위임 인증 및 필요한 권한을 확인한 후 허용된 시험 메일 한 건 및 관련 대화를 조회한다. 허용된 LLM에 시험 입력을 보내 응답을 확인한다. To Do에 시험 작업을 생성해 원문 연결·완료·알림을 확인한다.
- **목적:** 접근 불가능한 서비스를 전제로 본 구현을 진행하지 않는다.
- **산출물:** 접근 가능·불가 표, 시험 결과, 필요한 권한·데이터 처리 조건, 개발 코드 위치.
- **다음 단계 조건:** 핵심 연동 가능 여부와 막힌 이유가 확인되어 있다. 회사 계정의 제한 해제를 기다리지 않고 개인 계정과 합성 데이터로 진행한다.

### 3단계. PoC의 처리 규칙과 구현 방식을 결정한다

- **근거:** 1단계의 업무 기준과 2단계의 기능·제약을 연결해야 한다.
- **행동:** To Do 재사용 또는 최소 로컬 목록 중 하나를 선택한다. LLM 입력 맥락과 출력 항목을 정하고, 메일·업무 연결 기준, 중복 판단, 완료 보존, 실패·불확실성 표시 규칙을 정한다. 수집 범위에서 벗어난 메일과 첨부는 검증 한계로 표시한다.
- **목적:** 각 역할을 기존 기능과 직접 구현할 부분에 배정한다.
- **산출물:** 결정 근거가 있는 구성도, 입력·출력 항목, 상태 처리 규칙, 검증 체크리스트.
- **다음 단계 조건:** 완료 기준 C1~C7을 각각 어떤 기능과 시험으로 확인할지 연결되어 있다.

### 4단계. 수집부터 할 일 표시까지 한 흐름을 구현한다

- **근거:** 목표는 개별 API 예제가 아닌 로컬에서 실행되는 전체 흐름이다.
- **행동:** 로컬 실행 → 메일 수집 → 관련 대화·기존 상태 조회 → LLM 요약·판단 → 결과 검증 → 작업 등록·갱신을 연결한다. 필요한 수집 이력과 메일·작업 연결을 저장한다. 원문 열기, 완료 처리, 시험 알림을 연결한다.
- **목적:** 사용자가 확인할 수 있는 결과를 만든다.
- **산출물:** 로컬 실행 코드, 설정 예시, 최소 상태 저장, 한 건의 전체 실행 결과.
- **다음 단계 조건:** 승인된 시험 입력으로 C1~C3과 C5의 기본 동작이 확인된다.

### 5단계. 재실행·실패·판단 오류를 검증하고 수정한다

- **근거:** 목록이 한 번 나타나는 것만으로 누락 방지 도구의 가능성을 입증할 수 없다.
- **행동:** 아래 검증표에 따라 반복 실행, 완료 후 재시작, 조회 실패, 모델 실패·형식 오류, 미확인 기한, 관련 후속 메일을 시험한다. 오탐·누락과 확인 필요 항목을 사례별로 기록하고 핵심 오류를 수정한다.
- **목적:** 수집·분석·등록의 실패와 업무 판단의 한계를 드러낸다.
- **산출물:** 재현 가능한 검사, 사례별 평가표, 수정·재검증 결과, 남은 제약.
- **다음 단계 조건:** 합의한 PoC 기준을 충족하고 실패 상태가 숨겨지지 않는다.

### 6단계. 로컬 시연과 재현 절차를 정리한다

- **근거:** 완료 여부는 목표에서 정한 사용자 흐름과 증거로 판단한다.
- **행동:** 준비된 PC에서 실행 절차를 따라 메일 분석, 작업 표시, 원문 확인, 완료 처리, 알림과 재실행을 시연한다. 사용한 계정 유형·모델·설정, 비용·처리 시간, 검증 범위와 미지원 범위를 정리한다.
- **목적:** 다른 사람이 같은 환경에서 결과를 재현하고 다음 단계 진행 여부를 판단할 수 있게 한다.
- **산출물:** 실행 안내, C1~C7 검증 결과, 시연 기록, 미해결 항목.
- **완료 조건:** C1~C7의 증거가 있고 합의한 평가 기준을 충족한다. 미충족 항목이 있으면 부분 완료로 기록한다.

## 7. 완료 기준에 직접 대응하는 검증표

| 시험 | 기대 결과 | 연결 기준 |
|---|---|---|
| 허용된 메일·관련 발신 메일 조회 | 정한 범위 내 메일을 가져오고 원문 식별 가능 | C1 |
| 회신 요청 / 단순 안내 / 청구·제출 요청 | 서로 다른 업무 필요성을 구분하고 행동·근거 표시 | C2, C7 |
| 기한 누락 / 맥락 부족 / 첨부 의존 | 날짜를 지어내지 않고 미확인·확인 필요 표시 | C2, C7 |
| 단순 확인 답장만 보낸 요청 | 답장이 있다는 이유만으로 청구·제출 완료로 확정하지 않음 | C2, C7 |
| 목록 확인·원문 열기·사용자 완료 | 사용자 행동이 가능하고 결과 상태를 확인할 수 있음 | C3 |
| 동일 입력 재실행 / 완료 후 재시작 | 작업 수가 불필요하게 늘지 않고 완료 상태가 유지됨 | C4 |
| 기존 대화에 새 요청 발생 | 새 입력을 감지하고 누락·잘못된 병합 여부를 확인 | C4, C7 |
| 시험 알림 시각 도달 | 정한 클라이언트 실행 조건에서 알림 확인 | C5 |
| API·모델 실패 / 잘못된 응답 형식 | 실패가 드러나고 재시도 후 결과 추적 가능 | C6 |
| 메일 안에 프로그램 지시 문구 포함 | 지시를 실행하지 않고 분석 데이터로만 취급 | C2, C6 |

## 8. 바로 착수할 첫 작업

**개인 Microsoft 계정에 Outlook.com 메일함과 To Do가 준비되어 있는지 확인하고, 개인 계정 로그인 지원 앱으로 Graph에서 합성 시험 메일 한 건을 읽는다.** 이 결과와 To Do·LLM의 최소 연결 시험을 근거로 구현 방식을 확정한다. 개인 계정의 앱 등록·인증 준비 중에는 합성 메일로 평가 사례와 기대 결과를 준비한다.

현재 문서는 행동 계획 수립의 결과이며, 위 연동 시험·구현·검증을 이미 수행했다는 기록은 아니다.
