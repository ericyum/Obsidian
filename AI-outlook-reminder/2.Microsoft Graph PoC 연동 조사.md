# Microsoft Graph PoC 연동 조사

## 1. 현재 결론

**필요한 메일 조회·변경분 조회·To Do 작업 관리 API는 개인 Microsoft 계정의 사용자 위임 권한을 지원한다. 개인 계정의 Graph 로그인·프로필 조회·메일 조회는 성공했다. 메일 조회는 `200 OK`, `value: []`로 응답했다. To Do 목록도 `Tasks.Read` 동의 후 `200 OK`로 기본 목록 1개를 반환했다. 개인 계정의 메일·To Do 읽기 연동을 Graph Explorer에서 확인했다.**

사용자가 제공한 로그인 식별자는 `ericyum9196@gmail.com`이다. 이 주소로 Outlook을 이용한다는 사실만으로 Gmail 메일함을 Graph로 읽을 수 있는 것은 아니다. 다음 세 가지를 구분해야 한다.

| 경우 | Graph 메일 API 적용 판단 |
|---|---|
| Gmail을 Outlook 앱에 연결해 Gmail 메일을 읽는 경우 | Outlook 앱에 표시되더라도 Google 메일함을 Graph 메일 API 대상으로 간주할 수 없음 |
| Gmail 주소를 개인 Microsoft 계정의 로그인 ID로 사용하는 경우 | 로그인 ID일 뿐이며, 별도의 Outlook.com 메일함 존재 여부 확인 필요 |
| 위 Microsoft 계정에 Outlook.com 메일함이 준비된 경우 | 해당 Microsoft 메일함은 개인 계정 지원 API의 연동 후보. 실제 인증·API 응답 확인 필요 |

Microsoft는 기존 계정에 새 Outlook.com 주소를 별칭으로 추가할 수 있다고 안내한다. 따라서 Gmail 로그인 주소만 보고 새 Microsoft 계정부터 만들 필요는 없다. 먼저 현재 계정의 메일함·별칭을 확인하고, 필요할 때 새 Outlook.com 주소 추가를 검토한다. 계정·별칭 변경은 이번 조사에서 수행하지 않았다.

근거: [Microsoft 계정 이메일 주소 추가](https://support.microsoft.com/en-us/accounts-billing/manage/how-to-add-an-email-address-or-phone-number-to-your-microsoft-account), [Google 계정과 Microsoft 계정의 관계](https://support.microsoft.com/en-us/accounts-billing/manage/link-your-google-account-and-microsoft-account), [Outlook에 Gmail 계정 추가](https://support.microsoft.com/en-gb/outlook/getstarted/add-a-gmail-account-to-outlook-for-windows?nochrome=true).

## 2. 실제 확인한 상태와 미검증 항목

2026-10-07 사용자가 개인 계정 로그인을 완료한 뒤 Graph Explorer에서 실제 조회를 실행했다.

| 확인 항목 | 결과 |
|---|---|
| Graph Explorer 로그인 | `Personal`, `ericyum9196@gmail.com`, `MSA` 확인 |
| `GET /me` | `200 OK`, 해당 개인 계정 프로필 반환 |
| `GET /me/messages` | 사용자 동의 후 `200 OK`, `value: []` (조회된 메일 0건) |
| 메일 권한 화면 | `Mail.Read`가 `Unconsent`로 표시되어 동의 반영 확인 |
| `GET /me/todo/lists` | `200 OK`, 기본 목록 1개 반환 (`wellknownListName: defaultList`, `isOwner: true`, `isShared: false`) |
| To Do 권한 화면 | `Tasks.Read` 동의 반영 확인. `Tasks.ReadWrite`는 미동의 |
| 개인 Microsoft 메일함 API 접근 | 성공. 응답의 messages 컨텍스트에서 Outlook.com 사서함 식별자 확인 |
| Graph 작업 생성·완료·알림 | 미실행 |

메일은 `Mail.Read` 동의 반영 후 접근에 성공했다. 빈 목록은 정상 응답이며 실제 메일 본문 조회·분석까지 검증한 것은 아니다. To Do도 `Tasks.Read` 동의 후 정상 조회됐으며 앞선 접근 오류는 재현되지 않았다. 조회 성공을 작업 생성·수정 권한 확보로 해석하지 않는다. 메일·작업 데이터를 변경하지 않았다.

직접 입력한 쿼리 주소와 실제 실행 결과가 일치하지 않는 UI 현상이 있어, 위 메일·To Do 검증은 공식 샘플 쿼리를 선택해 실행했다. 프로필 JSON을 메일 조회 성공으로 집계하지 않았다.

### 이전 시도 기록: 사용자 승인 후 권한 부여 (2026-10-07)

사용자가 `Mail.Read`와 `Tasks.Read` 부여 및 재조회를 승인했다. Graph Explorer의 해당 `Consent` 버튼으로 동의를 요청했으나 Microsoft 동의 팝업에는 로고·하단 링크만 나타나고 동의 본문과 승인 버튼이 표시되지 않았다. To Do 요청을 새로 열어도 같은 상태였고, 첫 팝업을 새로고침했을 때는 `invalid_request: The provided request must include a 'client_id' input parameter.`가 나타났다. 메일 권한 요청에서도 동의 본문을 확인할 수 없었다. 원인이 계정 설정인지 서비스·브라우저 문제인지는 아직 확정하지 않았다.

이전 시도 당시에는 권한 부여 완료가 확인되지 않았으며, API 재조회는 메일 `403 ErrorAccessDenied`, To Do `401 UnknownError`로 다시 실패했다. 이 결과는 권한 부여 성공 후의 실패가 아니라, 동의 흐름이 완료되지 않은 상태의 재시도다. 이후 사용자가 직접 동의를 완료했으며 최종 조회 결과는 아래 최신 확인에 반영했다.

### 최신 확인: 사용자 직접 수락 이후 (2026-10-07)

사용자가 권한을 수락했다고 알린 후 Graph Explorer에서 `Scope consent successful` 알림을 확인했다. 실제 재조회 결과 메일은 `200 OK`, `value: []`였으며 `Mail.Read` 동의 상태도 확인했다. 따라서 이 개인 Microsoft 계정의 Microsoft 메일함을 Graph로 조회할 수 있다. Gmail 원본 메일함 연동을 의미하지 않는다.

이어서 사용자가 To Do 읽기 권한도 직접 수락했다. `Tasks.Read`의 동의 상태와 성공 알림을 확인한 후 `GET /me/todo/lists`를 실행했고, `200 OK` 및 기본 목록 1개를 확인했다. 목록 이름은 `任务`, `wellknownListName`은 `defaultList`이며 본인 소유의 비공유 목록이다. `Tasks.ReadWrite` 권한은 부여하지 않았고 작업 생성·수정·완료·알림 시험은 수행하지 않았다.

## 3. 이번 PoC에 필요한 API

아래 경로의 기준 주소는 `https://graph.microsoft.com/v1.0`이며, 개인 계정으로 로그인한 사용자 위임 인증을 전제로 한다. 아래 표는 문서 조사 결과이지 실제 호출 기록이 아니다.

| 기능 | API | 이번 PoC 권한 | 사용할 정보·동작 |
|---|---|---|---|
| 받은 메일 조회 | `GET /me/mailFolders/inbox/messages` | `Mail.Read` | 제목, 본문, 발신자, 수신 시각, 원문 링크 |
| 보낸 메일 조회 | `GET /me/mailFolders/sentitems/messages` | `Mail.Read` | 답장과 후속 처리 맥락 확인 |
| 특정 메일 조회 | `GET /me/messages/{messageId}` | `Mail.Read` | 필요한 메일의 상세 내용 |
| 메일 변경분 조회 | `GET /me/mailFolders/{folderId}/messages/delta` | `Mail.Read` | 수집 이후 추가·수정·삭제 동기화 |
| To Do 목록 조회 | `GET /me/todo/lists` | 조회만 하면 `Tasks.Read`, 작업 생성까지 하면 `Tasks.ReadWrite` | 사용할 목록 ID |
| To Do 작업 생성 | `POST /me/todo/lists/{listId}/tasks` | `Tasks.ReadWrite` | 제목, 설명, 기한, 알림, 원문 연결 |
| To Do 작업 수정 | `PATCH /me/todo/lists/{listId}/tasks/{taskId}` | `Tasks.ReadWrite` | 완료 상태·기한·알림 갱신 |

개인 계정 지원은 [메일 조회](https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0), [메일 delta](https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0), [목록 조회](https://learn.microsoft.com/en-us/graph/api/todo-list-lists?view=graph-rest-1.0), [작업 생성](https://learn.microsoft.com/en-us/graph/api/todotasklist-post-tasks?view=graph-rest-1.0), [작업 수정](https://learn.microsoft.com/en-us/graph/api/todotask-update?view=graph-rest-1.0)의 Permissions 표에서 확인했다.

메일 기본 정보 조회에는 더 작은 `Mail.ReadBasic` 권한이 있지만 본문 분석에는 부족하므로 PoC에서는 `Mail.Read`를 검토한다. 원본 메일 수정과 메일 발송은 현재 필요하지 않아 `Mail.ReadWrite`, `Mail.Send`를 기본 요청 범위에 넣지 않는다. 근거: [권한 참조](https://learn.microsoft.com/en-us/graph/permissions-reference).

## 4. LLM에 전달할 데이터와 Graph가 하지 않는 일

수집 후보 필드는 `id`, `subject`, `body`, `from`, `toRecipients`, `receivedDateTime`, `sentDateTime`, `conversationId`, `internetMessageId`, `webLink`이다. 실제로 필요한 필드만 조회한다.

`conversationId`는 관련 대화를 묶는 단서지만 같은 대화에 여러 업무가 있을 수 있다. Graph에는 이번 업무 의미의 '회신해야 하지만 아직 처리하지 않은 요청'을 확정해 주는 전용 필드가 없다. 받은 메일·관련 보낸 메일·기존 작업 상태를 바탕으로 LLM이 필요한 행동을 제안하고 사용자가 완료를 확인하는 방식으로 처리한다.

근거: [message 구조](https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0).

To Do에는 `title`, `body`, `dueDateTime`, `isReminderOn`, `reminderDateTime`, `status`, `linkedResources` 등을 활용한다. 알림 설정이 API에 저장되었다는 사실과 사용자 화면에 실제 알림이 나타나는 것은 별도 검증 항목이다. 근거: [todoTask 구조](https://learn.microsoft.com/en-us/graph/api/resources/todotask?view=graph-rest-1.0).

## 5. 인증과 앱 준비

- 개인 Microsoft 계정을 지원하도록 등록된 앱과 사용자 위임 로그인을 사용한다.
- 로컬 앱이 쓰는 인증 토큰은 Outlook 앱의 로그인 상태와 별개다. Outlook에 로그인했다는 이유만으로 Python에서 Graph 호출이 허용되지 않는다.
- 자체 앱 등록은 Entra 디렉터리·등록 권한 등 별도 준비가 필요하다. 개인 계정을 보유한 것과 앱을 등록할 환경을 확보한 것은 다르므로 실제 이용 가능 여부부터 확인한다.
- 앱 등록의 지원 계정 유형에는 개인 계정 전용 또는 조직·개인 계정 모두 지원하는 선택지가 있다. 이번에는 회사 계정에 접근하지 않고 개인 계정 검증에 집중한다.
- 처음에는 Graph Explorer 같은 공식 시험 도구로 읽기 요청을 검증하는 경로를 검토한다. 도구 자체의 로그인·동의 조건을 확인하고, 샘플 데이터 응답을 사용자 계정의 성공 응답으로 착각하지 않는다.

근거: [앱 등록](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app), [Graph Explorer](https://learn.microsoft.com/en-us/graph/graph-explorer/graph-explorer-overview).

## 6. 실제 검증 순서

1. 개인 계정 로그인 및 `GET /me` 성공은 확인 완료했다.
2. 개인 Outlook 받은 편지함이 열리는지, Microsoft 메일함 주소가 무엇인지 확인한다. Gmail 앱 연결 화면인지도 구분한다.
3. Graph Explorer의 `Mail.Read`·`Tasks.Read` 동의와 메일·To Do 목록 접근은 확인 완료했다. 합성 시험 메일을 준비한 이후에는 아래와 같은 최소 필드 조회와 본문 조회를 순서대로 검증한다.

```http
GET https://graph.microsoft.com/v1.0/me/messages?$top=1&$select=id,subject
```

4. `200 OK`와 사용자 사서함 응답을 확인한다. `value: []`인 정상 응답은 빈 메일함일 수 있으며 오류로 단정하지 않는다. 본문 시험은 합성 메일을 준비한 뒤 수행한다.
5. `GET /me/todo/lists`의 기본 목록 조회는 완료했다. 작업 생성·수정에는 별도 `Tasks.ReadWrite` 동의가 필요하다. 쓰기 시험을 진행할 때 시험용 작업 한 건의 생성·완료·알림을 검증한다.
6. 자체 로컬 앱에서도 같은 흐름이 동작하는지 확인한다. 시험 도구에서의 성공만으로 Python 앱 인증 준비가 끝났다고 보지 않는다.

로그인 실패, 권한 부족, 메일함 미준비는 서로 다른 문제다. 오류가 발생하면 HTTP 상태와 오류 코드를 기록하되 토큰·인증 코드는 기록하지 않는다. 메일함 미준비 여부는 이메일 주소의 도메인만으로 단정하지 않는다.

## 7. 구현에서 빠뜨리지 않을 항목

- 목록 조회는 `@odata.nextLink`를 끝까지 따라가야 한다.
- delta 조회는 폴더 단위이며 받은 편지함 외 시험 대상 폴더도 별도로 고려한다.
- 메일 이동으로 인한 중복을 줄이기 위해 `Prefer: IdType="ImmutableId"` 사용을 검토한다. 같은 사서함 안의 이동에 적용되며 보관 사서함 이동 등에는 예외가 있다.
- 인증 실패·분석 실패·작업 생성 실패를 각각 구분하고 재시도 시 중복 등록을 방지한다.

근거: [메일 조회의 페이지 처리](https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0), [delta 조회](https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0), [Immutable ID](https://learn.microsoft.com/en-us/graph/outlook-immutable-id).

## 8. 판정

- **기능 적합성:** 개인 Microsoft 계정용 API가 있으므로 계획한 PoC는 문서상 구현 가능하다.
- **사용자 계정 적합성:** 개인 Microsoft 계정 인증과 Microsoft 메일함 API 접근은 성공했다. 현재 조회된 메일은 0건이며 합성 시험 메일 본문 조회는 후속 검증이 필요하다.
- **Gmail 원본 메일 조회:** Outlook에 Gmail이 표시된다는 이유로 Graph에서 Google 메일함을 읽을 수 있는 것은 아니다. 이 프로젝트의 Graph 검증에는 Microsoft가 제공하는 메일함을 사용하는 것이 적합하다.
- **실제 연동 성공:** Graph Explorer에서 프로필·메일 목록·To Do 목록 조회 성공. 실제 메일 본문 조회, Python 자체 앱 인증, LLM 분석, 작업 생성·완료·알림은 아직 미검증이다.
