# 테스트 및 검증 결과

> **2026-10-08까지의 저장소 검증 기록을 정리한 문서.** 이번 문서 작성 과정에서 테스트나 유료 API 호출을 다시 실행한 것은 아니다.

관련 문서: [[3.현재 구현 내용]] · [[5.최종 기능 및 사용 가이드]]

## 1. 결과 요약

| 검증 | 기록된 결과 | 해석 |
|---|---|---|
| 오프라인 pytest | **145개 통과** | 단위·통합·E2E 기본 범위, 외부 연결 차단 |
| 알림 관련 통합 테스트 재실행 | 32개 통과 | 전체 145개에 포함되는 일부 범위. 더해서 집계하지 않음 |
| JavaScript 알림 검사 | 통과 | 최초 표시·반복 조회·새로고침·데이터 출처 분리 |
| Codex LB 실제 LLM 합성 평가 | **5/5 사례 통과** | `gpt-6.1-sol`, 각 사례 1회 |
| 실제 메일 E2E | **수집 → 분석 → 업무 표시 성공** | 네이버 발송, Outlook 수신, Graph 및 실제 LLM 사용 |
| 실제 메일 알림 | 예약값 확인 | 예약 시각까지 기다려 실제 발생을 확인한 시험은 아님 |

이전 기록의 127·143·144개는 단계별 과거 총계다. 최신 총계 145개에 누적해서 더하지 않는다. 합성 평가 5건은 pytest 테스트 함수 **1개 안의 5개 사례**다.

## 2. 자동 검증 범위

| 영역 | 확인한 주요 동작 |
|---|---|
| 입력·분류 | Graph 형태 입력, 로그인 이메일 제거, 명확한 회신 요청과 불명확한 조건 구분 |
| 기한 | 날짜·시간·상대 날짜와 원문 근거 검증, 모호한 기한 처리 |
| 수집·복구 | 최초 기준 유지, 페이지 처리, 대기 저장·재시도, 중복 및 재실행 |
| 로컬 업무 | 업무 저장, 완료 처리, 후속 메일과 기한 변경 제안 |
| 알림 | 기본 하루 전 예약, 지정 시각, 해제, 완료 및 중복 표시 제어 |
| 프로바이더 | URL 검증, 키 보호·비노출, 저장·변경·삭제와 동시 실행 충돌 |
| 웹 API | 요청 검증, 로컬 출처 보호, 목업·실제 모드 상태 처리 |

테스트는 `tests/unit`, `tests/integration`, `tests/e2e`에 나뉜다. API 중심 자동 E2E와 실제 브라우저 수동 검증은 서로 다른 검증이다. pytest 통과만으로 모든 화면 조작을 실제 브라우저에서 시험했다는 뜻은 아니다.

프로바이더 개선 단계에서 구문·의존성 확인 기록도 있다. 독립 검토에서 목업 초기화의 트랜잭션 문제와 서비스 전환 중 설정 저장 충돌을 발견하여 재현 후 수정했다. 최종 분류 입력·프롬프트 변경의 읽기 전용 리뷰에서는 추가 조치 사항이 없었다.

## 3. 실제 LLM 합성 평가

저장된 Codex LB 설정과 `gpt-6.1-sol`로 다음 사례를 실제 호출했다.

| 합성 사례 | 기대 결과 | 결과 |
|---|---|---|
| 로그인 주소와 수신 별칭은 다르지만 명확한 요청 | 처리할 업무 + 확정 기한 | 통과 |
| 마감은 없지만 명확한 요청 | 처리할 업무 | 통과 |
| 다른 팀만 수행하고 사용자는 참조 | 제외 | 통과 |
| 승인 등 선행 조건 충족 여부가 불명확 | 확인 필요 | 통과 |
| 이미 완료된 요청 | 제외 | 통과 |

평가 파일은 `tests/live/test_inbox_prompt.py`, 결과 파일은 저장소의 `.artifacts/inbox-prompt-live.json`이다. **각 사례 1회 결과이므로 모델의 반복 안정성이나 전체 업무 메일 정확도를 보장하지 않는다.**

## 4. 실제 메일 E2E

사용자 승인에 따라 네이버에서 실제 Outlook 수신 주소로 가상의 청구 확인 메일을 보냈다. Microsoft 로그인에 쓰는 Gmail 주소와 Graph가 읽는 Outlook 사서함 주소를 구분하여 시험했다.

| 항목 | 확인 내용 |
|---|---|
| 메일 제목 | SAP 추가 구축대금 확인 요청 (SAP-2026-1008-B) |
| 요청 내용 | 부가세 포함 11,000,000원 청구금액과 세금계산서 발행 예정일 확인 후 회신 |
| 요청 기한 | 2026-10-09 18:00, 한국 시간 |
| 실행 | 웹의 ‘지금 가져와서 분석’ |
| 수집·분석 결과 | `processed=1`, `errors=[]` |
| 분류 | `decision=action`, `category=payment` |
| 생성 업무 | 청구금액 및 세금계산서 발행 예정일 확인 후 회신 |
| 기한 | `2026-10-09 18:00 Asia/Seoul`, 확정 |
| 알림 예약 | `2026-10-08 18:00+09:00` |
| 화면 | ‘처리할 업무’ 목록에서 확인 |

이전 프롬프트로 확인 필요가 된 두 건은 자동 재분석하지 않아 그대로 남았다. 새 결과의 성공과 과거 결과의 일괄 수정은 구분한다.

## 5. 발견한 문제와 수정 결과

| 문제 | 원인·조치 | 검증 |
|---|---|---|
| 명확한 요청이 확인 필요로 분류됨 | 로그인 이메일과 수신 별칭 비교를 제거하고, 사용자 사서함의 메일이라는 전제 및 행동·불확실성 구분을 강화 | 회귀 테스트, 실제 합성 5건, 새 메일 E2E |
| 키 인증은 되지만 실제 분석 HTTP 400 | LB의 JSON 모드 조건 문제. 사용자 JSON 입력에도 `output_format: json` 명시 | 실제 LLM 요청 및 메일 분석 성공 |
| ‘테스트이며 실제 청구 아님’ 메일 제외 | 해당 본문은 실제 업무 요청이 아니라는 의미이므로 제외 판단이 타당 | 사용자 승인 후 해당 문구 없는 새 메일로 재시험 |

## 6. 재현 방법

저장소에서 실행한다. 다음 기본 검증은 실제 API 키나 메일 전송이 필요 없다.

```powershell
cd C:\Users\염정운\project\AI-outlook-reminder
.\.venv\Scripts\python.exe -m pytest -q --basetemp=.artifacts/test-run
node tests/e2e/web_notification_check.cjs
```

Node.js는 JavaScript 검사에 필요하며 일반 앱 실행에는 필요 없다.

실제 LLM 합성 평가를 다시 실행하려면 웹에 프로바이더 설정이 저장되어 있어야 한다. **아래 명령은 외부 API 사용량과 비용이 발생할 수 있다.**

```powershell
$env:RUN_INBOX_PROMPT_LIVE = '1'
.\.venv\Scripts\python.exe -m pytest tests/live/test_inbox_prompt.py -q
Remove-Item Env:RUN_INBOX_PROMPT_LIVE
```

실제 메일 E2E는 모니터링 시작 후 Outlook 수신 주소로 새 메일을 보내고, 수동 수집 → 목록 → 상세 기한 → 알림 예약을 순서대로 확인한다. 이때 보내는 메일과 LLM 전송 내용은 시험 목적에 맞게 준비한다.

## 7. 미검증·후속 검증

- 회사 계정의 관리자 동의, 조건부 액세스 및 외부 LLM 전송 정책.
- 공동메일함·다중 사용자·대량 메일·장기간 연속 운영.
- 실제 예약 시각의 웹 알림 발생을 기다리는 장시간 시험.
- 다양한 실제 업무 표현에 대한 오분류·누락률과 모델별 반복 평가.
- 첨부파일 분석·데스크탑 알림 등 아직 구현하지 않은 기능.
