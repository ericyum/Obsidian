# Superpowers 사용 흐름

## 1. Superpowers의 정체

Superpowers는 Codex 자체를 교체하는 별도 Agent가 아니라 Codex에 설치되는 **Plugin**이다. Plugin 안에는 특정 작업을 반복 가능한 절차로 수행하도록 안내하는 여러 **Skills**가 들어 있다.

```text
Codex
└─ Superpowers Plugin
   ├─ brainstorming
   ├─ writing-plans
   ├─ executing-plans
   ├─ systematic-debugging
   ├─ test-driven-development
   ├─ verification-before-completion
   └─ 기타 Skills
```

## 2. 기본 개발 흐름

```mermaid
flowchart LR
    I[아이디어·요청] --> B[brainstorming]
    B --> S[승인된 spec]
    S --> W[writing-plans]
    W --> P[구현 plan]
    P --> E[executing-plans]
    E --> T[구현·테스트]
    T --> V[검증]
```

1. `brainstorming`: 무엇을 만들지 합의한다.
2. `writing-plans`: 합의한 설계를 구현 단계로 분해한다.
3. `executing-plans`: 계획을 읽고 단계별로 구현·검증한다.

모든 작업이 반드시 세 단계를 모두 거치는 것은 아니다. 단순 조사인 Spike는 조사 결과로 끝날 수 있고, 기존 코드의 작은 Bounded 변경은 짧은 설계 승인 뒤 곧바로 구현할 수 있다. 새로운 시스템이나 큰 구조 변경인 Architectural 작업은 spec과 plan을 남긴다.

## 3. 자동 적용과 명시적 선택

Codex는 요청이 Skill의 목적과 일치하면 자동으로 선택할 수 있다.

```text
회의록 Agent에 새로운 요약 기능을 추가하고 싶어.
```

반드시 특정 Skill을 사용하게 하려면 `$`로 명시한다.

```text
$brainstorming 회의록 Agent에 새로운 요약 기능을 추가하고 싶어.
```

앱의 `/` 목록에 활성 Skill이 보이면 `/brainstorming`으로 선택할 수도 있다. 공식적인 Codex의 명시적 Skill 멘션은 `$skill-name` 형태로 이해하면 된다.

## 4. Superpowers가 자동으로 하지 않는 것

- Plugin을 설치했다고 specs나 plans가 과거 작업에서 자동 생성되지는 않는다.
- 새 세션이 과거 대화 전체를 자동으로 기억하지 않는다.
- specs와 plans 폴더의 모든 문서를 언제나 자동으로 읽는다고 보장하지 않는다.
- Skill이 설치되었다고 브랜치, worktree, Commit과 PR이 무조건 생성되지는 않는다.
- 프로젝트의 `AGENTS.md`와 사용자의 명시적인 방침을 무시하지 않는다.

## 5. POC 프로젝트의 적용 예

```text
$brainstorming

AGENTS.md와 현재 회의록 Agent POC spec을 읽고,
새로운 기능의 요구사항과 설계를 먼저 정리해줘.
브랜치, worktree, Commit과 PR은 만들지 마.
```

이 요청에서 Superpowers는 설계 절차를 제공하고, `AGENTS.md`는 POC의 기술·보안·Git 경계를 제공한다.
