# writing-plans 사용 방법

## 1. 목적

`writing-plans`는 승인된 spec 또는 충분히 명확한 요구사항을 실제 구현자가 실행할 수 있는 작은 작업으로 분해하는 Skill이다. 코드를 수정하기 전에 어떤 파일을 만들고 바꾸며, 무엇을 테스트하고, 어떤 명령으로 성공을 확인할지 적는다.

## 2. 입력과 출력

| 구분 | 내용 |
|---|---|
| 입력 | 승인된 spec, 프로젝트 구조, `AGENTS.md`, 관련 코드·테스트 |
| 출력 | `docs/superpowers/plans/YYYY-MM-DD-<feature>.md` |
| 독자 | 코드베이스 맥락을 거의 모르는 구현자 또는 다음 Codex 세션 |
| 목표 | 추측 없이 단계별로 실행 가능한 계획 |

## 3. Plan의 기본 구조

```text
목표와 아키텍처
→ 기술 스택과 연결된 spec
→ 전역 제약
→ 파일 생성·수정 지도
→ Task 1
   ├─ 실패 테스트 작성
   ├─ 테스트 실패 확인
   ├─ 최소 구현
   └─ 테스트 통과 확인
→ Task 2 ...
→ 전체 검증
```

각 Task는 독립적으로 검토하고 테스트할 수 있는 크기여야 한다. `TODO`, “적절히 처리”, “위와 비슷하게 구현” 같은 Placeholder를 남기지 않고 정확한 파일, 인터페이스, 명령과 기대 결과를 적는다.

## 4. 호출 예시

```text
$writing-plans

docs/superpowers/specs/2026-08-31-example-design.md를 읽고
현재 코드 구조에 맞는 구현 계획을 작성해줘.
AGENTS.md에 따라 worktree, Commit과 PR 단계는 포함하지 마.
```

## 5. 프로젝트 방침에 따른 조정

Superpowers의 기본 Plan 예시는 자주 Commit하는 흐름을 포함할 수 있다. 그러나 다음 조건에서는 계획에서 제거하거나 사용자 승인 단계로 바꾼다.

- `AGENTS.md`가 자동 Commit을 금지함
- 사용자가 별도 브랜치나 worktree를 원하지 않음
- POC이므로 PR을 만들 필요가 없음

Skill의 Template보다 사용자의 직접 요청과 프로젝트 지침이 우선한다.

## 6. Plan 자체 점검

- spec의 모든 요구사항이 Task에 연결되는가?
- 정의되지 않은 함수·타입·파일을 참조하지 않는가?
- 테스트 명령과 기대 결과가 구체적인가?
- Placeholder나 모호한 문장이 없는가?
- 각 Task가 독립적으로 검증 가능한가?
