# specs 폴더의 개념과 사용 방법

## 1. 개념

`docs/superpowers/specs`는 `brainstorming` 과정에서 합의된 설계를 보존하는 기본 문서 공간이다. “무엇을 왜 만들며, 구성요소가 어떻게 연결되고, 어떤 조건을 만족해야 하는가”를 설명한다.

```text
docs/
└─ superpowers/
   ├─ specs/
   │  └─ YYYY-MM-DD-<topic>-design.md
   └─ plans/
      └─ YYYY-MM-DD-<feature>.md
```

specs는 규칙 파일인 `AGENTS.md`와 다르고, 실행 절차인 plans와도 다르다.

## 2. 세 문서의 차이

| 문서 | 답하는 질문 | 대표 내용 |
|---|---|---|
| `AGENTS.md` | 이 프로젝트에서 항상 무엇을 지켜야 하는가? | 보안·테스트·Git·코딩 규칙 |
| `specs/*.md` | 무엇을 왜 어떤 구조로 만들 것인가? | 요구사항·아키텍처·흐름·오류·검증 조건 |
| `plans/*.md` | 어떤 파일을 어떤 순서로 바꿀 것인가? | Task·테스트·코드 단계·명령 |

## 3. spec에 포함할 내용

- 배경과 해결하려는 문제
- 목표와 명시적인 범위 밖 항목
- 선택한 접근법과 대안의 Trade-off
- 아키텍처와 구성요소 책임
- 데이터·State·요청 흐름
- 외부 시스템과의 인터페이스
- 오류·보안·권한 처리
- 테스트 전략과 성공 기준
- 알려진 한계와 후속 이식 경계

## 4. 사전 설계와 회고형 As-built

spec은 두 가지 성격으로 작성할 수 있다.

### 사전 설계 명세

구현 전에 합의한 목표와 구조를 기록한다.

```text
아이디어 → brainstorming → 사용자 승인 → design spec → plan → 구현
```

### 회고형 As-built 명세

이미 구현된 시스템을 코드, 테스트와 기존 문서를 근거로 재구성한다. 이 경우 처음부터 존재했던 사전 명세인 것처럼 쓰지 않고 문서 성격을 명시한다.

```md
> 이 문서는 최초 구현 전에 작성된 사전 명세가 아니라,
> 현재 코드와 테스트를 기준으로 재구성한 회고형 As-built 명세다.
```

## 5. 파일명과 예시 구조

```text
docs/superpowers/specs/2026-08-31-meeting-agent-poc-as-built-design.md
```

```md
# 기능 또는 시스템 설계

## 1. 배경과 목적
## 2. 범위와 비범위
## 3. 선택한 접근법
## 4. 아키텍처
## 5. 구성요소와 책임
## 6. 데이터 흐름
## 7. 오류·보안 처리
## 8. 테스트 전략
## 9. 한계와 후속 작업
```

## 6. 새 세션에서 사용하는 방법

Codex가 `specs` 폴더의 모든 파일을 자동으로 읽는다고 가정하지 않는다. 관련 파일을 정확히 지정한다.

```text
AGENTS.md를 따르고,
docs/superpowers/specs/2026-08-31-meeting-agent-poc-as-built-design.md를 읽어줘.
이 설계를 기준으로 다음 변경을 검토해줘.
```

설계 변경이라면 `$brainstorming`으로 기존 spec을 갱신하고, 승인 후 `$writing-plans`로 구현 계획을 만든다.

## 7. 관리 원칙

- spec과 코드가 충돌하면 현재 실행 동작은 코드와 테스트로 확인한다.
- 의도와 구현의 차이는 결함 또는 변경 후보로 명시한다.
- 설계 계약이 바뀌면 관련 테스트와 spec을 함께 갱신한다.
- `TBD`, `TODO`와 해석이 갈리는 표현을 남기지 않는다.
- 한 spec이 독립된 여러 시스템을 다루면 더 작은 spec으로 분해한다.
- 비밀 값과 회의록 원문 같은 민감정보를 기록하지 않는다.
