# 3. 그렇다면 왜 Tool인가?

## Tool이라는 형태로 에이전트가 발전하게 된 계기

원래 에이전트는 명령어 기반으로 동작했다. 사람이 목표를 제시하면 에이전트가 다음과 같이 물어보고, 사용자가 승인하면 해당 명령어를 실행하는 구조였다.

> 이 명령어를 실행해도 될까요?

하지만 이러한 구조에는 다음과 같은 권한 문제가 있었다.

### 1. 권한 초과

에이전트가 `파일을 읽어라`라는 명령을 수행하다가 시스템의 중요 설정 파일이나 비밀번호 데이터베이스에 접근할 가능성이 있다.

### 2. 원격 코드 실행의 근본적인 취약점

악의적인 사용자가 프롬프트 인젝션 등을 이용하여 서버의 모든 파일을 삭제하는 것과 같은 파괴적인 명령을 내리면, 에이전트가 이를 그대로 수행할 위험이 있다.

### 3. 예측 불가능성

LLM이 어떤 명령어를 생성할지 완벽하게 통제하기 어렵다.

## 명령어를 Tool로 제한하기

따라서 특정 일을 수행하는 명령어와 로직을 개발자가 코드로 미리 지정하고, LLM은 그 코드를 Tool의 형태로 호출하도록 제한할 필요가 생겼다.

즉, 개발자가 허용한 일과 그 실행 방법을 미리 구현해 두고, LLM은 주어진 Tool 중에서 필요한 것을 선택하는 구조다.

```text
자유로운 명령어 생성
→ LLM이 어떤 명령을 만들지 예측하기 어려움

미리 구현된 Tool 호출
→ LLM은 허용된 Tool 중에서 필요한 행동을 선택함
```

이러한 방식으로 실행할 수 있는 행동을 제약하고, 명령어를 미리 구현해 둔 것이 Tool이다.

## 핵심 정리

> Tool은 LLM이 임의의 명령어를 만들어 실행하지 않도록, 수행 가능한 행동과 실행 로직을 개발자가 미리 정해 둔 것이다.
