# 4. Codex와 Claude Code 같은 범용 에이전트의 한계

다음과 같은 의문을 가질 수 있다.

> Codex나 Claude Code 같은 큰 에이전트가 있는데, 모든 일에 이것을 붙여서 해결하면 되지 않을까?

하지만 현실은 그렇지 않다. 그 이유를 이해하려면 다음 두 가지를 알아야 한다.

1. 범용 에이전트가 어떤 구조로 설계되어 있는가?
2. Loop가 반복될 때 LLM은 어떻게 이전 정보에 이어서 일을 진행하는가?

## 범용 에이전트의 설계 구조

범용 에이전트의 핵심적인 특징은 **사용자가 어떤 질문과 목표를 제시할지 미리 알 수 없다는 점**이다.

회의록 에이전트처럼 목표가 명확한 경우와 달리, 범용 에이전트의 사용자들은 매우 다양한 질문과 요구를 전달한다. 이런 여러 요구에 대응하기 위해 범용 에이전트에는 많은 종류의 Tool이 구축되어 있다.

따라서 다음과 같은 문제가 생길 수 있다.

- 할루시네이션이 발생하거나 사용자의 요구가 명확하지 않으면 목표와 크게 관련 없는 Tool을 호출할 수 있다.
- 어떤 난이도의 요청이 들어올지 모르기 때문에 우선 성능이 좋은 비싼 모델을 사용하게 될 수 있다.
- 많은 Tool 중에서 알맞은 Tool을 고르기 위한 과정에서도 추가 토큰이 사용된다.

## LLM은 어떻게 이전 작업을 기억하는가?

LLM은 입력된 프롬프트를 읽고 그에 따른 출력값을 내보낼 뿐이다. 즉, **LLM 자체에는 이전 실행을 기억하는 능력이 없다.**

그렇다면 다음과 같은 의문이 생긴다.

> 어떻게 직전까지의 과정을 기억하고 자연스럽게 다음 행동을 결정하는가?

그 대답은 **컨텍스트**다.

LLM이 받는 입력은 다음과 같은 여러 부분으로 구성된다.

- 시스템 프롬프트
- 사용자 역할의 메시지
- 사전 지식
- 출력 형식과 제약 조건
- 이전 대화와 Tool 실행 결과가 들어 있는 컨텍스트

이 컨텍스트에 이전 내용이 들어가기 때문에 우리 입장에서는 LLM이 마치 기억하고 있는 것처럼 느껴지는 것이다.

## 컨텍스트가 길어지는 문제

사용자가 Codex 같은 범용 에이전트에게 큰 업무를 부탁하면 여러 Tool이 실행되고 Loop가 계속 반복된다. 그 과정에서 컨텍스트에 들어가는 텍스트의 양도 계속 늘어난다.

작은 업무라면 감당할 수 있지만, 비즈니스의 한 Workflow 전체를 맡기면 많은 Loop가 발생한다. 나중에는 단 한 번의 Loop를 돌기 위해서도 LLM이 매우 많은 컨텍스트가 포함된 입력을 읽어야 한다.

최근에는 컨텍스트가 일정 수준 이상 길어지면 핵심만 요약하여 줄이는 `Compaction`을 사용할 수 있다. 하지만 이것도 컨텍스트 증가를 완화할 뿐, 처음부터 적은 컨텍스트만 생성하면서 일을 끝내게 하지는 못한다.

## 핵심 정리

범용 에이전트는 다양한 요구에 대응할 수 있지만, 그만큼 많은 Tool과 넓은 시스템 프롬프트가 필요하다. 큰 업무를 수행하는 동안 Loop가 반복되면 컨텍스트와 토큰 비용도 계속 늘어난다.

그렇다면 범용 에이전트의 이러한 한계를 어떻게 줄일 수 있을까?
