## 0. 한 줄 요약

> **에이전트의 품질은 결국 한 문장으로 귀결된다.**
>
> *"이 턴에 모델에게 무엇을, 어떤 순서로, 어떻게 보여줄 것인가."*

이 결정을 **"컨텍스트 조립"**이라 부른다.

회의록 에이전트 문서의 P4 단계는 이걸 정확히 한 노드로 표현한다.

```
AD  임시 Storage에서 회의록 원문 불러오기
 ↓
AE  시스템 지시 + 회의록 원문 + 현재 대화 기록  ── 조립
 ↓
AF  회의록을 바탕으로 답변
```

그리고 문서의 마지막 한 줄이 핵심 설계 결정을 내린다.

> 회의록 원문은 대화 기록에 계속 누적하지 않고 임시 Storage에 분리해 두었다가,
> 질문에 답할 때 현재 대화 기록과 조립한다.

**왜 이렇게 했는가.**

## 1. 왜 "조립"이 문제인가

### 1.1 에이전트 = 컨텍스트 조립기

LLM 에이전트는 본질적으로 이런 구조다.

- 모델 자체는 **상태가 없다(stateless)**.
- 매 호출마다 컨텍스트를 새로 조립해 **상태를 에뮬레이션**한다.
- 히스토리·메모리·툴 결과·검색 문서·시스템 지시가 전부 "이번 턴의 프롬프트"로 한 번에 들어간다.

이 조립 방식이 **품질·비용·지연·안정성**을 전부 결정한다.

→ 그래서 조립은 부가 기능이 아니라 **에이전트의 본체**다.

---

### 1.2 안 하면 생기는 일 — 회의록이 히스토리를 지배한다

회의록 에이전트에서 "원문을 히스토리에 계속 누적"하는 방식을 그냥 썼다고 치자.

- 멀티턴 질의응답 **20턴** 동안
- 회의록 원문 **약 30K 토큰**이 **매 턴마다 히스토리 어딘가에 다시 들어간다.**

#### 상황 — 턴별 프롬프트가 어떻게 쌓이는가

회의록 원문은 **한 번만 저장했으면 끝**일 것 같지만, stateless 모델은 매 턴 프롬프트를 처음부터 다시 조립한다. 그래서 원문이 **매 턴 통째로 재전송**된다.

```
[1턴]  시스템지시(2K) + 원문(30K) + 질문1
                         └── 32K ──┘

[2턴]  시스템지시(2K) + 원문(30K) + 질문1 + 답1 + 질문2
                         └──────── 30K 또 전송 ────────┘

[3턴]  시스템지시(2K) + 원문(30K) + 질문1·답1 + 질문2·답2 + 질문3
                         └──────── 30K 또 전송 ──────────────┘

  ⋮
[20턴] 시스템지시(2K) + 원문(30K) + [질문·답 × 19] + 질문20
                         └───────── 30K 또 전송 ─────────────────┘
```

> 원문 **30K**가 **20번** 다시 들어간다 → 원문만 **600K 토큰** 재전송.
> 원문은 **한 번도 안 변했는데** 매번 다시 보낸다. 이게 비용·캐시 문제의 출발점.

즉시 세 가지가 터진다.

| # | 현상 | 설명 |
|---|---|---|
| ① | **비용 폭발** | 원문이 매 턴 재전송. 20턴이면 원문만 **600K 토큰** |
| ② | **캐시 무효화** | 히스토리가 매 턴 변하면 프롬프트 앞부분(prefix)이 흔들린다. 캐시는 **정확한 prefix 일치**가 있어야 히트 → prefix가 흔들리면 매번 full 가격 |
| ③ | **회상 편향** | 거대한 원문이 계속 눈앞에 있으면, 모델은 원문에 끌려다니고 사용자의 실제 질문·대화 맥락이 **묻힌다** |

---

### 1.3 캐시 히트가 만드는 비용 차이 — 숫자로

> **프롬프트 캐시란?**
> 자주 바뀌지 않는 블록을 프롬프트 앞쪽에 고정하면, 그 블록은 재사용(캐시 히트)돼서 **싸진다.**
> 얼마나 싸지는지가 핵심이다.

> **prefix(접두부) — 캐시가 "앞에서부터" 작동하는 원리**
>
> 캐시는 프롬프트를 **맨 앞부터 차례로** 읽어, 이전 요청과 **바이트가 똑같은 구간**까지를 재사용한다. 이 앞부분을 **prefix**라 부른다.
>
> - **앞이 같아야 히트:** 처음부터 한 글자도 틀리지 않고 같아야 한다. **중간부터는 안 센다.**
> - **달라지는 지점부터 full:** 어디서든 처음으로 달라지면, **그 지점부터 끝까지 full 가격.**
> - **뒤가 달라도 OK:** 뒤(질문·대화기록)가 바뀌어도, 앞의 불변 블록이 prefix로 살아있으면 **그만큼은 히트.**
>
> → 그래서 **"불변 건을 앞으로, 변동 건을 뒤로"**가 그냥 미학이 아니라 **비용 공식**이다. 앞이 흔들리면 prefix가 깨져 매턴 full.

#### GPT-5.5 (1M 토큰당, 2026-04 출시)

| 항목 | 단가 | 비율 |
|---|---|---|
| 일반 입력(캐시 미힛) | $5.00 | 100% |
| **캐시 히트 입력** | **$0.50** | **90% 할인** |
| 출력 | $30.00 | — |

> ⚠️ **장문 할증 함정:** 입력이 **272K 초과**하면 세션 전체가 **입력 2배($10.00)·출력 1.5배**로 바뀐다.
> "다 때려넣어서" 컨텍스트가 272K를 넘는 순간 단가가 두 배로 뛴다 — 분리 조립이 더욱 유리해지는 이유.
> 출처: [OpenAI GPT-5.5](https://developers.openai.com/api/docs/models/gpt-5.5) · [Pricing](https://developers.openai.com/api/docs/pricing)

#### Claude (Sonnet 4.6 기준, 1M 토큰당)

| 항목 | 단가 | 배율 |
|---|---|---|
| 일반 입력 | $3.00 | 1.0x |
| 캐시 쓰기(5분 TTL) | $3.75 | 1.25x |
| 캐시 쓰기(1시간 TTL) | $6.00 | 2.0x |
| **캐시 히트(읽기)** | **$0.30** | **0.1x = 90% 할인** |
| 출력 | $15.00 | — |

> Claude는 캐시를 옵트인(`cache_control` 마커)해야 하고 쓰기에 프리미엄이 붙지만,
> **읽기는 90% 할인**. 캐시가 따뜻하게 유지될수록 절감율이 90%에 수렴한다.
> 출처: [Anthropic Prompt Caching](https://claude.com/blog/prompt-caching) · [TokenMix 분석](https://tokenmix.ai/blog/claude-api-cache-pricing)

> 📎 **참고 — SAP AI Core(Generative AI Hub) 경유 시 (실측 전, 문서 기준)**
>
> SAP AI Core를 거쳐 모델을 쓸 때 캐시 작동이 **모델별로 다르다**는 점에 주의.

| 모델 | 캐싱 | 코드 변경 |
|---|---|---|
| OpenAI GPT | **자동(implicit)** | ❌ 없음 |
| Google Gemini | **자동(implicit)** | ❌ 없음 |
| **Anthropic Claude** | **옵트인(explicit)** — `cache_control` 마커 직접 필요 | ✅ 필요 |

> SAP AI Core는 **통과(pass-through)**만 할 뿐 대신 캐시 마커를 넣어주지 않는다.
> 즉 Claude를 SAP AI Core로 쓸 때 `cache_control` 안 찍으면 **캐시 히트 0 → 매번 full 가격**, 90% 할인을 놓친다.
>
> **예시 — Claude 캐시 켜기 (간편, 권장)**
>
> ```python
> # 최상위에 cache_control 한 줄 → 시스템이 알아서 마지막 캐시 블록에 중단점
> response = client.messages.create(
>     model=MODEL,
>     max_tokens=300,
>     cache_control={"type": "ephemeral"},   # ← 이 한 줄
>     messages=[
>         {"role": "system", "content": "회의록을 바탕으로 답변하라..."},  # 불변
>         {"role": "user",   "content": 회의록_원문},                       # 준불변
>         {"role": "user",   "content": 사용자_질문},                       # 매턴 변화
>     ],
> )
> ```
>
> **검증 — 응답 usage로 히트 확인**
>
> ```python
> # Claude
> response.usage.cache_read_input_tokens        # 히트(0.1배로 청구)
> response.usage.cache_creation_input_tokens     # 캐시 쓰기(1.25배)
>
> # GPT (자동캐시라 마커 불필요, 결과만 확인)
> response.usage.prompt_tokens_details.cached_tokens
> ```
>
> 최소 캐시 길이: **Sonnet 1,024 / Opus·Haiku 4.5는 4,096 토큰**. 이보다 짧으면 캐시 자체가 안 된다.
>
> ⚠️ **이 내용은 공식 문서·SAP 커뮤니티 글 기준이지, 실제 환경에서 직접 검증한 게 아니다.**
> 발표·적용 전 SAP AI Core 실환경에서 `cache_control` 유무별 usage를 직접 찍어 확인해야 한다.
> 출처: [SAP 커뮤니티 - The Hidden Behavior of LLMs(캐싱·결정론)](https://community.sap.com/t5/technology-blog-posts-by-sap/the-hidden-behavior-of-llms-prompt-caching-and-determinism/ba-p/14285663) · [SAP Help - Prompt Caching](https://help.sap.com/docs/sap-ai-core/generative-ai/prompt-caching) · [Claude Prompt Caching Cookbook](https://platform.claude.com/cookbook/misc-prompt-caching)

### 1.4 시나리오로 보는 비용 비교

**조건**
- 회의록 원문 **30K 토큰** · 시스템 지시 2K · 멀티턴 질의응답 **20턴** · 1세션

#### ① 원문이 히스토리에 섞여 prefix가 흔들리는 경우

> 캐시 무효 → 매 턴 full 가격
> 원문 30K × 20턴 = **600K 토큰** 전송

| 모델 | 계산 | 비용 |
|---|---|---|
| GPT-5.5 | 600K × $5.00/1M | **$3.00** |
| Claude Sonnet 4.6 | 600K × $3.00/1M | **$1.80** |

#### ② 원문을 분리하고, system 지시 바로 뒤에 안정 prefix로 고정

> 1회 캐시 쓰기 + 19회 캐시 읽기

| 모델 | 계산 | 비용 | 절감 |
|---|---|---|---|
| GPT-5.5 | 30K×$5.00/1M(쓰기1) + 19×30K×$0.50/1M(읽기) | **$0.44** | **약 85%** |
| Claude Sonnet 4.6 | 30K×$3.75/1M(쓰기1) + 19×30K×$0.30/1M(읽기) | **$0.28** | **약 84%** |

> 💡 **2026년 프론티어는 양사 모두 90% 캐시 할인.** 구형(GPT-4o 50%) 시절엔 Claude가 압도적이었지만, 이제 GPT-5.5도 90% → 양사 다 **~85% 절감**.
>
> **"조립 방식 하나로 비용이 1/7로 줄고, 양사 공통으로 통한다."**

## 2. 컨텍스트는 무엇으로 구성되나

### 2.1 정석 4단 — 회의록 에이전트가 보여주는 본보기

P4의 AE 노드는 거의 교과서적인 4-블록 조립을 한다.

| 블록            | 회의록 에이전트에서               | 성질                            |
| ------------- | ------------------------ | ----------------------------- |
| ① **시스템 지시**  | "회의록을 바탕으로 답변하라" 등 역할/제약 | 턴 간 **불변** → 캐시 prefix 1순위    |
| ② **작업 컨텍스트** | 회의록 원문                   | 세션 단위 **준불변** → 캐시 prefix 2순위 |
| ③ **대화 기록**   | 지금까지의 Q&A                | **매 턴 변화** → prefix의 뒤쪽       |
| ④ **현재 질문**   | 이번 턴 사용자 입력              | **매 턴 변화** → 맨 뒤              |
|               |                          |                               |

> **순서가 핵심이다.**
>
> **변하지 않는 것을 앞으로, 변하는 것을 뒤로.**
>
> 이것만 지켜도 캐시 히트율이 달라진다.

```
[① 시스템 지시] → [② 회의록 원문] → [③ 대화 기록] → [④ 현재 질문]
   불변            준불변             매턴 변화         매턴 변화
 ◀──────────── 캐시 안정 영역 ───────────▶ ◀─ 변동 ─▶
```

---

### 2.2 추가로 들어갈 수 있는 것

에이전트가 커지면 컨텍스트는 이 4개에서 점점 늘어난다.
회의록 에이전트에는 없지만, 일반적으로 자주 끼워지는 블록:

| 블록 | 설명 | 캐시 관점 |
|---|---|---|
| **툴 정의 / 스키마** | 사용 가능한 툴의 시그니처 | OpenAI는 툴 정의 **순서**만 바뀌어도 캐시 터짐 |
| **검색 결과(RAG)** | 외부 지식 | 크면 조립 전에 검색으로 축소 |
| **퓨샷 예시(few-shot)** | 정답 형태를 가르치는 예시 | 불변 → prefix에 좋은 후보 |
| **스크래치패드 / 메모리** | 이전 세션 요약·장기 메모리 | — |
| **사용자 프로필 / 권한** | 이 사용자가 누구인지, 무엇을 볼 수 있는지 | — |
| **상태 변수** | `file_exists = true` 같은 세션 상태 | 회의록 문서 Z 노드가 정확히 이 케이스 |

> 출처: [OpenAI Prompt Caching Guide](https://developers.openai.com/api/docs/guides/prompt-caching)

> **핵심 원칙은 변하지 않는다.**
>
> **불변·준불변 블록은 앞으로, 변동 블록은 뒤로.**
>
> 들어가는 종류가 늘어도 이 순서 원칙 하나로 캐시·비용·회상이 정리된다.

---

### 2.3 조립은 "모으는" 게 아니라 "고르는" 것이다

툴 결과·검색 결과도 컨텍스트에 들어간다. 그런데 **툴이 돌려준 원본을 통째로 넣지 않는다** — 발췌하거나 요약하거나, 원본은 따로 두고 다이제스트만 넣는다. 회의록 원문을 임시 Storage에 분리한 것과 **같은 원리**: "큰 원본은 밖에 두고, 작게 고른 것만 들여보낸다."

> **핵심:** 조립은 "다 넣자"가 아니라 **"뺄 걸 고르는"** 일이다. 이걸 자세히 다루는 건 → **별도 발표 주제**

## 3. 안 하면 어떻게 되나 — 모델은 어디부터 머리가 나빠지나

> 이 절이 핵심이다.
> *"원문을 그냥 다 때려넣으면 안 되나?"* 에 대한 **답변.**

---

### 3.1 길어지면 못 읽는다 — 2026년 최신 모델의 한계

> "텍스트가 길어도 다 넣으면 모델이 다 읽지 않을까?" → **아니다.** 과제 종류에 따라 어디서부터 못 읽는지가 갈린다. 2026년 최신 모델 기준으로 보자.
>
> 먼저 용어 정리. 
> **바늘찾기** = 긴 텍스트 속에 숨긴 정답 하나를 찾는 테스트. 
> **싱글바늘** = 정답이 한 개, 
> **멀티홉** = 정답이 한 번에 안 보이고 여러 정보를 연결해야 찾는 과제.

#### ① 단순 검색(키워드 겹치는 정답 1개)은 1M에서 거의 해결 — 2026년 5월 연구

> **먼저 — "키워드가 겹친다"가 뭔 뜻?**
>
> 질문과 정답에 **같은 단어가 등장하면**, 모델은 추론할 필요 없이 그 단어만 찍어서 답을 가져올 수 있다.
>
> ```
> 질문: "예산은 얼마인가?"
> 원문: "...회의에서 예산은 500만 원으로 확정됐다..."
>           ↑↑↑  "예산"이라는 단어가 질문·원문에 같이 있음
> → 모델: "예산"만 매칭 → 답 500만 원 (검색이지 추론이 아님)
> ```
>
> 이런 "단어가 겹쳐서 바로 찾히는" 과제는 ①에서 보듯 2026년에 거의 해결됐다. **문제는 그 다음** — 정답이 한 번에 안 보이는 과제(②)가 무너진다.

[1M 토큰 회상·멀티홉 연구](https://arxiv.org/html/2605.02173) (Chow, HKU, 2026-05) — 정답이 키워드로 바로 찾히는 단순 검색은 1M(약 100만 토큰)에서 **전부 100%**.

| 모델 | 공식 윈도우 | 단순 검색 @1M |
|---|---|---|
| **Gemini 3.1 Pro** | ~1M | 100% |
| **Claude Opus 4.7** | ~1M | 100% |
| **GPT-5.5** | ~1.1M | 100% |

→ "키워드로 찾으면 되는 단순 검색"은 2026년에 와서 더 이상 변명거리가 아니다. 다 넣어도 찾는다 — **이 과제 한정**.

#### ② 그러나 "정답이 한 번에 안 보이는 과제"는 1M에서 무너진다

같은 연구에서 **멀티홉**(정답이 한 번에 안 보이고 여러 정보를 연결해야 찾는 과제)을 넣자 세 가지 양상이 드러난다.

| 모델 | 512K | 1M | 패턴 |
|---|---|---|---|
| **Gemini 3.1 Pro** | 4/5 | 4/5 | **안정** — 모든 구간 유지 |
| **Claude Opus 4.7** | ≥80% | 완만 하락 | **안정→완만** — 512K까지 견딤 |
| **GPT-5.5** | 4/5 | **2/5** | **급격 붕괴** — 1M에서 반토막 |

> 📉 **512K → 1M 구간이 최신 1M 모델들을 가른다.** GPT-5.5는 1M에서 **반토막**.
> "단순 검색 100%"가 곧 "긴 텍스트를 잘 읽는다"는 말이 아니라는 증거다.

> **예시 — 단어가 안 겹치면 "연결"이 필요하다 (싱글바늘 ≠ 멀티홉)**
>
> 질문: *"CFO는 누구인가?"*
> 원문: *"...재무담당 임원 김OO가 발표했다..."* — **'CFO'라는 단어가 원문에 안 겹친다.**
>
> → 모델이 'CFO = 재무담당 임원'을 **스스로 연결**해야 답에 도달 = **멀티홉**.
> → ①(단어 겹침)은 100%지만, 이런 "연결이 필요한" 과제는 **②에서 1M에 반토막**.
> "들어있다 ≠ 찾아낸다"가 바로 이 지점에서 발생한다.

#### ③ 에이전트 과제 — LOCA-bench (2026년 2월)

> **LOCA-bench란?** 에이전트가 긴 환경 설명(8K→256K) 속에서 **행동·탐색·도구 사용을 끝까지 제대로 수행하는지** 재는 벤치마크(HKUST, 2026-02). 단순 검색이 아니라 "상황을 읽고 행동하는" 능력을 평가한다.

검색이 아니라 **행동하는 에이전트**가 긴 환경 컨텍스트(8K→256K)를 다룰 때.

| 모델 | 8K | 256K | 하락 |
|---|---|---|---|
| **Claude-4.5-Opus** | 96% | **14.7%** | **−81점** |
| **GPT-5.2-Medium** | 72% | 21.3% | −51점 |
| **Gemini-3-Flash** | 64% | 17.3% | −47점 |

> 출처: [LOCA-bench](https://arxiv.org/html/2602.07962) (HKUST, 2026-02)
> 회의록 질의응답도 "주어진 텍스트에서 끌어오는 에이전트 과제"와 같은 부류. 256K에서 **Claude-4.5-Opus 14.7%** = 거의 안 읽는 수준.

**왜 이게 회의록 에이전트에 직결되는가.**

- 회의록 원문 30K + 멀티턴 누적이면 길이는 **쉽게 100K~256K를 넘긴다.**
- 싱글바늘(단어 겹침)은 100%지만, 회의록 질의응답은 **맥락을 연결하는 멀티홉/에이전트 과제** — ②③이 적용되는 영역.
- "다 때려넣으면 찾는다"는 **①의 환상**일 뿐, 실제 과제는 ②③에서 무너진다.

> **"들어있다" ≠ "찾아낸다." — 2026년엔 더 정확한 말: "싱글바늘은 찾지만, 진짜 회상은 못 찾는다."**

### 3.2 정답이 중간에 있으면 더 못 찾는다 — Lost in the Middle (TACL 2023)

> 참고: 단순 U자 곡선은 2026년 프론티어에서 **상당 부분 해소**됐다. 하지만 "정답이 한 곳에 몰려 있을 때" **분포 붕괴(Distributional Collapse)** 등 새로운 위치 함정이 2026년 연구로 드러났다 — 위치 설계는 여전히 유효하다.

[Lost in the Middle](https://arxiv.org/abs/2307.03172) (Liu et al., TACL 2023)은 **위치의 힘**을 보여준다.

```
정답 위치     회상 성능
─────────────────────────────
처음          ▰▰▰▰▰  좋음
  ↓
중간          ▰░░░░  최악   ← U자 곡선의 바닥
  ↓
끝            ▰▰▰▰▰  좋음
```

- 정답이 **처음·끝**에 있으면 잘 찾고, **중간**에 있으면 못 찾는다 — **U자 곡선.**
- 사람의 **계열 위치 효과**(처음·끝 기억, 중간 망각)와 같다.

#### 결정적인 예시

- GPT-3.5-Turbo는 정답이 중간에 있을 때,
  **문서를 아예 안 준 것(closed-book, 56.1%)보다 못한** 성적을 냈다.
  → "도움을 주려 넣은 문서가 방해가 됐다."
- 컨텍스트가 10 → 20 → 30 문서로 길어질수록 **계속 나빠진다.**
- GPT-4도 절대 점수는 높지만 **U자 곡선은 여전히** 나타난다.
- RAG 리더-리더 셋업에서 **20개 이상 검색 문서는 성능 향상을 거의 못 준다**(GPT-3.5 약 +1.5%).
  → 더 넣는 게 능사가 아니다.

> 출처: [TACL 논문](https://aclanthology.org/2024.tacl-1.9/)

> 회의록 원문을 "통째로 앞에" 두는 것도, "질문 바로 앞에" 두는 것도 **위치 설계**다.
> 원문 안에서 정답이 될 수 있는 부분이 어디에 놓일지 신경 쓰면 회상이 달라진다.

### 3.3 예시 — 조립 구조가 비용·회상을 바꾼다

#### 분리 + 안정 prefix (회의록 에이전트의 선택)

```
시스템 지시 → [원문·고정] → 대화 기록 → 질문
              ↑
       매 턴 같은 자리, 같은 내용
       → 캐시 히트 + "앞쪽"이라 회상에 유리
```

- **비용:** 원문이 매 턴 캐시 히트 → **절반 ~ 1/10** (1.4 참조).
- **회상:** 원문이 "앞쪽"에 고정 → Lost-in-the-Middle(중간 망각)을 피하고 앞쪽 배치 이점 확보.
- **히스토리:** 원문은 별도 Storage → 대화 기록엔 질의응답만 남아 맥락이 원문에 묻히지 않는다.

> 회의록 에이전트가 선택한 방식이 **정확히 이것**이다 — 비용·회상·히스토리 청결을 한 구조로 잡는다.

---

> **절 요약**
>
> "다 넣으면 되지"는 **비용**에서만 끝나는 게 아니라,
> **정확도**에서도 실패한다.
>
> 넣는 **순서·위치·캐시 안정성**까지 설계해야
> "들어간 것을 찾아낸다."

## 4. 보통 어떻게 하나 — 패턴

| # | 패턴 | 설명 |
|---|---|---|
| 1 | **분리 보관 → 호출 시 조립** | 이번 사례. 원문은 임시 Storage, 턴마다 히스토리와 조립. 히스토리 오염·세션 휘발·캐시 prefix 안정을 한꺼번에 해결 |
| 2 | **RAG** | 원문이 클 때 전부 넣지 않고 질문에 맞는 부분만 검색으로 축소. Lost-in-the-Middle이 "20개 이상 문서는 효과 미미" → 검색 결과는 **적게·관련도 높게** |
| 3 | **프롬프트 캐싱(prefix 고정)** | 불변 블록을 앞에 고정. 1.2~1.4의 전제가 되는 기법 |
| 4 | **컨텍스트 압축/요약** | 대화 기록이 길어지면 요약본으로 치환. ③ 대화 기록 블록이 비대해지는 걸 막음 |

> 실제로는 **1 + 3**이 거의 묶여서 쓰인다.
> 회의록 에이전트도 "분리 보관(1)" + "조립 시 원문을 안정 위치에(3의 전제)"의 **합성**.

> **주석 — "분리 보관"은 "안 보낸다"가 아니다 (이 사례의 핵심 함정)**
>
> 흔한 오해: *"Storage에 두었으니 매턴 프롬프트엔 안 넣고, 필요할 때 툴로 가져오겠지?"* → **이 사례는 아니다.**
>
> P4의 AD 노드("Storage에서 원문 불러오기")는 **백엔드 코드**가 매 턴 꺼내는 거지, **LLM이 툴 콜로 가져오는 게 아니다**. AE 노드("조립")처럼 매 턴 원문을 프롬프트에 **끼워넣는다(①)**. 다만 히스토리(대화기록)와 **분리 보관**하므로 캐시 prefix가 안정 → 매턴 재전송 비용을 **캐시 읽기(0.1배)**로 잡는다.
> "Storage에 분리"는 "히스토리에서 분리"일 뿐, "매턴 안 보낸다"가 아니다.
>
> **반대 설계 — ② on-demand 툴 호출**
>
> "Storage에서 **툴 콜**로 필요할 때만 원문(또는 일부)을 가져온다." = **다른 설계**. 원문이 너무 커서 매턴 전송이 부담일 때 RAG/검색으로 축소하는 방식 → `컨텍스트 선별` 발표에서 다룬다.

| | ① 매턴 조립 (이번 사례) | ② on-demand 툴 호출 |
|---|---|---|
| 원문 매턴 전송 | O — 캐시로 **0.1배** | X — 툴 결과로만 |
| 지연 | 없음 | 매턴 **툴 콜 라운드트립** |
| LLM 판단 의존 | 없음 (항상 원문 보임) | 있음 (언제 가져올지 LLM이 결정) |
| 적합한 조건 | 원문 중간 크기 · **전체가 잠재 근거** | 원문 **매우 큼** · 부분만 필요 |

> **왜 회의록(30K)은 ①인가:** 전체가 답의 근거가 될 수 있어 매번 다 봐야 한다. 30K면 캐시 전송(0.1배)이 툴 콜 지연+판단 실패 리스크보다 **싸고 안정적**. 원문이 **500K**쯤 되면 ②(RAG)로 넘어가야 ①의 비용/회상 부담을 피한다.

## 5. 노하우 + 기술 근거

> 왜 *"원문을 분리하고 조립 시점에 합친다"* 가 정답인가.
>
> **세 마리 토끼를 한 설계로 잡는다.**

| 목표 | 기술적 근거 | 이 사례에서 |
|---|---|---|
| 💰 **비용** | 캐시 읽기는 GPT-4o 50%·Claude 90% 할인. 불변 블록을 prefix에 고정하면 매 턴 히트 | 원문을 system 뒤에 고정 → 매 턴 캐시 히트 (1.4: **47~84% 절감**) |
| 🎯 **회상 정확도** | 싱글바늘은 1M에서 100%지만 멀티홉은 1M서 반토막, 에이전트 과제는 256K에서 14~21%로 추락(LOCA) | 원문을 히스토리에 누적하지 않아 컨텍스트가 부풀지 않음. Lost-in-the-Middle 위치 이점까지 확보 |
| 🧹 **히스토리 청결** | 원문이 히스토리에 섞이면 회상이 원문에 지배당함 (1.2) | 원문은 별도 Storage, 히스토리엔 질의응답만 |
| 🔒 **세션 안정성** | 원문을 히스토리에만 두면 세션 휘발 시 소실 | 임시 Storage + `file_exists` 상태로 복구 가능 |
| 🧱 **캐시 안정** | 히스토리가 매 턴 변하면 prefix가 흔들려 캐시 무효 | 원문은 변하지 않는 블록으로 분리 → prefix 안정 |

### 노하우의 영역

> *"정확히 몇 토큰부터 나빠지나"* — 이건 공식 스펙이 아니라 **실측 영역**이다.

2026년 실측 근거 — 과제 종류에 따라 다르다:

```
과제 종류               안전한 길이(실측)
──────────────────────────────────────────
싱글바늘(단어 겹침)     ~1M    (프론티어 해결)
멀티홉 추론             ~512K  (1M서 붕괴 시작)
에이전트 과제            ~8K~   (256K서 14~21%)
```

> 핵심 — **"공식 윈도우"가 아니라 "과제의 종류"가 유효 길이를 결정한다.**
> 회의록 질의응답은 싱글바늘이 아니라 **멀티홉/에이전트 과제**에 가깝다.

회의록 원문 크기 · 예상 턴 수 · 과제 종류 · 캐시 따뜻함을 재고 나서 고르는 선택지:

```
원문 작다 + 단순 검색  ──→ 통째로 조립
원문 중간 + 멀티홉     ──→ 분리 조립 + prefix 고정 (이번 사례)
원문 크다 / 턴 많음    ──→ RAG로 축소 후 조립
```

> **결론.**
>
> 공식 윈도우를 믿고 다 때려넣으면
> **비용(캐시+272K 할증)·정확도(멀티홉 붕괴) 양쪽에서 망한다.**
>
