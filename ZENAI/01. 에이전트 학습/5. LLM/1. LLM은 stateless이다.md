# LLM은 Stateless이다

## 1. State와 Stateless의 의미

상태 머신에서 **State**란 시스템이 특정 시점에 처해 있는 조건, 상황 또는 단계를 의미한다.

예를 들어 회의록 에이전트가 `recording`, `pause`, `stop` 중 어느 단계에 있는지는 다음 행동을 결정하는 State다. 이전에 어떤 일이 있었는지에 따라 현재 처리 방식이 달라진다.

**Stateless**는 시스템 전체에 State가 전혀 존재하지 않는다는 뜻이 아니다. 더 정확하게는 **각 요청을 처리하는 주체가 이전 요청의 상태를 자체적으로 기억하고 있다고 가정하지 않는 방식**이다. 따라서 현재 요청을 이해하고 처리하는 데 필요한 정보가 요청과 함께 전달되거나, 요청에 포함된 식별자를 이용해 외부 저장소에서 조회되어야 한다.

```text
Stateful 처리
이전 요청의 상태를 서버가 기억
→ 다음 요청이 그 상태에 의존

Stateless 처리
이전 요청을 서버가 기억한다고 가정하지 않음
→ 현재 요청만으로 의미를 파악할 수 있어야 함
```

HTTP 표준도 HTTP를 stateless 요청·응답 프로토콜로 정의한다. 각 요청 메시지의 의미를 독립적으로 이해할 수 있어야 하며, 이 특성은 프록시 연결 재사용과 여러 서버 사이의 동적 부하 분산에 유리하다.

## 2. Handshake와 Stateless는 서로 다른 개념이다

Handshake는 통신을 시작하기 전에 양쪽이 연결에 필요한 정보를 교환하고 조건을 맞추는 절차다. 반드시 “너는 누구인가?”처럼 상대의 사용자 신원을 확인하는 과정만을 뜻하지 않는다.

대표적으로 TCP의 3-way handshake는 양쪽이 연결을 수립하고 초기 순서 번호를 동기화하기 위한 절차다. TCP 연결은 `LISTEN`, `SYN-SENT`, `ESTABLISHED`처럼 명시적인 연결 State를 가진다.

```text
Client → Server: SYN
Client ← Server: SYN + ACK
Client → Server: ACK
→ TCP 연결 수립
```

여기서 주의할 점은 **통신 계층마다 State의 성격이 다를 수 있다는 것**이다. HTTP 요청은 stateless하게 설계되어 있어도 그 요청을 전달하는 하위 TCP 연결은 stateful할 수 있다. HTTPS 역시 연결 과정에서 암호화 조건을 협상하지만, 그것만으로 HTTP 애플리케이션이 클라이언트별 대화 상태를 서버에 보관해야 하는 것은 아니다.

따라서 “Handshake를 사용하면 stateful이고, 사용하지 않으면 stateless다”라고 단순화하면 안 된다.

API가 미리 정한 프로토콜, Endpoint와 입출력 Schema를 따른다는 것도 일반적으로 handshake와는 구분한다. 이는 클라이언트와 서버가 이해할 **통신 계약**을 사전에 합의한 것이다. 실제 요청마다 별도의 교섭 과정을 반드시 실행한다는 뜻은 아니다. 다만 인증 방식 협상이나 프로토콜 버전 협상처럼 일부 API·통신 기술이 별도의 handshake 절차를 둘 수는 있다.

## 3. Stateful 방식의 정확한 장단점

Stateful 서버는 사용자나 세션별 상태를 서버 측에 유지한다.

```text
사용자 A의 첫 요청
→ 서버가 A의 세션 상태 저장

사용자 A의 다음 요청
→ 저장해 둔 A의 상태를 이어서 처리
```

이 방식은 연속적인 상호작용을 구현하기 쉽지만 다음 비용이 발생할 수 있다.

- 세션 상태를 저장하기 위한 메모리와 저장소가 필요하다.
- 특정 서버에 상태가 묶이면 같은 사용자의 요청을 그 서버로 보내는 세션 고정이 필요할 수 있다.
- 여러 서버가 같은 상태를 사용하려면 공유 저장소나 동기화가 필요하다.
- 서버 장애가 발생했을 때 해당 서버에만 있던 상태를 잃을 수 있다.
- 서버 증설, 부하 분산과 장애 복구 구조가 복잡해질 수 있다.

다만 stateful 방식이 반드시 1:1 전용 서버를 요구하거나 병렬 처리를 불가능하게 만드는 것은 아니다. 여러 사용자와 요청을 병렬로 처리할 수 있지만, **클라이언트별 상태를 어디에 저장하고 여러 실행 주체가 어떻게 일관되게 공유할지**라는 추가 문제가 생긴다.

## 4. Stateless 요청 방식

Stateless 방식에서는 처리에 필요한 내용을 요청과 함께 전달한다.

```text
나는 누구인가
+ 무엇을 요청하는가
+ 어떤 대상에 대한 요청인가
+ 필요한 입력값과 인증 정보는 무엇인가
= 현재 요청을 처리하는 데 필요한 정보
```

이 정보가 반드시 하나의 본문에 모두 들어가는 것은 아니다. HTTP 요청에서는 다음과 같은 위치로 나뉠 수 있다.

- URI와 쿼리 매개변수
- HTTP 메서드
- Header의 인증 토큰과 메타데이터
- Body의 입력 데이터
- 외부 상태를 조회하기 위한 세션·대화·리소스 ID

서버는 요청을 받은 시점에 필요한 정보를 읽고 처리한다. 요청이 독립적으로 해석될 수 있으므로 가용한 여러 서버 중 하나로 전달하기 쉽고, 프록시·캐시·동적 부하 분산 같은 중간 계층을 사용하기도 쉬워진다.

하지만 stateless라고 해서 서버가 데이터베이스를 사용하지 않는 것은 아니다. 사용자 정보나 업무 데이터는 외부 저장소에 존재할 수 있다. 중요한 차이는 **요청 처리 서버가 이전 요청의 대화 상태를 자신의 로컬 메모리에 계속 가지고 있을 것이라고 가정하지 않는 것**이다.

## 5. LLM이 Stateless하다는 의미

LLM 모델은 독립적인 추론 요청 사이에서 사용자의 신원, 이전 대화, 의도와 업무 State를 스스로 기억하지 않는다. 새로운 호출을 받으면 모델은 그 호출에 제공된 컨텍스트와 학습된 모델 파라미터를 바탕으로 출력을 생성한다.

```text
첫 번째 호출
입력: "내 이름은 Eric이야"
→ 출력 생성

두 번째 독립 호출
입력: "내 이름이 뭐야?"
→ 첫 번째 호출 내용을 다시 전달하지 않았다면 알 수 없음
```

두 번째 호출에서도 이름을 답하게 하려면 애플리케이션이 이전 대화를 다시 포함해야 한다.

```text
System 지시
+ 이전 대화
+ 현재 사용자 요청
+ 필요한 문서와 Tool 결과
+ 현재 workflow_state
= LLM에 전달할 최종 컨텍스트
```

즉, 사용자가 느끼는 “대화의 기억”은 보통 LLM 자체의 기억이 아니라 애플리케이션이 다음 요소를 저장하고 다시 조립해 주기 때문에 만들어진다.

- 대화 기록
- 사용자·스레드 식별자
- Agent State와 Checkpoint
- Tool 또는 Skill 실행 결과
- 검색한 문서
- 장기 기억 저장소의 관련 정보

일부 API는 대화 ID나 이전 응답 ID를 받아 대화를 이어 주는 기능을 제공한다. 이것은 플랫폼이나 오케스트레이터가 저장된 대화 상태를 다시 모델 컨텍스트로 연결해 주는 기능이다. **상태 관리 기능이 있는 API를 사용하더라도 모델 자체가 독립 호출 사이의 기억을 자율적으로 보유한다는 뜻은 아니다.**

## 6. LLM 내부의 일시적 계산과 장기 기억을 구분한다

LLM이 한 번의 응답을 생성하는 동안에는 입력 토큰과 이미 생성한 토큰을 참고한다. 구현에 따라 계산 효율을 높이기 위한 KV cache도 사용할 수 있다. 그러나 이는 현재 추론 실행을 위한 일시적인 계산 상태이며, 별도의 다음 요청까지 사용자 기억으로 유지되는 Agent State와는 다르다.

또한 모델의 학습된 가중치는 지식과 생성 성향을 담고 있지만 특정 사용자의 직전 대화를 저장하는 세션 메모리는 아니다. 일반적인 추론 요청 한 번으로 모델 가중치가 갱신되는 것도 아니다.

따라서 다음 세 가지를 구분해야 한다.

| 구분 | 역할 | 대표 예시 |
|---|---|---|
| 모델 파라미터 | 학습으로 형성된 일반 지식과 패턴 | 모델 가중치 |
| 현재 호출의 컨텍스트 | 이번 출력 생성에 사용할 정보 | 시스템 지시, 대화, 문서, Tool 결과 |
| 외부 Agent State | 호출 사이에 업무 연속성을 유지 | `workflow_state`, Checkpoint, 대화 DB |

## 7. Agent 설계에서의 의미

LLM이 stateless이므로 Agent의 업무 상태를 LLM의 기억에 맡기면 안 된다.

```text
사용자 요청
→ 외부 State와 Checkpoint 조회
→ 필요한 대화·문서·실행 결과 조립
→ LLM 호출
→ Skill·Tool 실행
→ 확정적인 결과를 외부 State에 저장
```

LLM은 조립된 컨텍스트를 바탕으로 의도를 해석하고 답변을 생성한다. 반면 현재 업무 단계, 권한, 실행 성공 여부와 같은 결정적인 정보는 오케스트레이터와 백엔드가 관리해야 한다.

이 구조를 사용하면 다음 호출을 다른 모델 서버가 처리하더라도 같은 외부 State로 업무를 이어갈 수 있다. 또한 LLM이 잘못 기억하거나 이전 맥락을 누락하더라도 백엔드의 실제 상태와 저장된 Checkpoint를 기준으로 실행을 통제할 수 있다.

## 핵심 정리

> LLM이 stateless하다는 것은 모델이 독립적인 호출 사이에서 사용자와 이전 대화를 스스로 기억하지 않는다는 뜻이다. 따라서 애플리케이션과 Agent는 대화, State, Checkpoint, 문서와 실행 결과를 외부에 저장하고 매 호출마다 필요한 범위만 컨텍스트로 조립해야 한다. Handshake와 stateless는 서로 다른 계층의 개념이며, stateless 시스템도 연결 수립 절차와 외부 저장소를 사용할 수 있다.
