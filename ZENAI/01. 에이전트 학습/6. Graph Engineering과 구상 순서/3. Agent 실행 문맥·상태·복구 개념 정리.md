# Agent 실행 문맥·상태·복구 개념 정리

이 문서는 Agent를 설계할 때 자주 함께 언급되는 Trace, Scratchpad, Messages, State, Snapshot, Checkpoint, Interrupt의 의미를 구분한다. 특히 같은 데이터를 서로 다른 관점에서 부르거나, 구현 방식에 따라 용어의 경계가 흐려지는 경우를 정리하는 것이 목적이다.

## 1. Trace

Trace는 Agent가 실행되는 동안 발생한 사건을 관찰하고 추적하기 위한 **각종 실행 로그 기록**이다.

예를 들면 다음과 같은 내용이 Trace에 기록될 수 있다.

- 사용자 요청 수신
- LLM 호출과 응답
- Tool 호출과 Tool Action 결과
- Node와 Edge의 이동
- 오류와 재시도
- HITL 대기와 재개
- 토큰 사용량과 실행 시간

Trace의 주된 목적은 실행 과정의 관찰, 디버깅, 감사와 성능 분석이다. 따라서 Trace는 Agent가 다음 행동을 결정하기 위해 반드시 읽어야 하는 State나 Scratchpad와는 구분해야 한다.

## 2. Scratchpad

Scratchpad는 **LLM의 다음 판단에 사용되는 가변적인 작업 Context**다.

여기에서 가변적이라는 말은 Scratchpad의 모든 내용을 항상 LLM에게 보내는 것이 아니라, 현재 작업에 필요한 정보만 취사선택하여 LLM 입력 Context에 포함할 수 있다는 의미다.

예를 들어 회의록 검색 단계에서는 다음 정보를 포함할 수 있다.

- 사용자의 현재 요청
- 이전 Tool의 정제된 결과
- 현재까지의 작업 진행 내용
- 다음 판단에 필요한 회의 후보 정보

반면 다음 판단에 필요하지 않거나 보안상 노출하면 안 되는 정보는 제외할 수 있다. 회의록 원문도 특정 질문에 답하는 동안 일시적인 Context로 사용할 수 있지만, 항상 Scratchpad에 영속 저장해야 하는 것은 아니다.

### 2-1. 시스템 프롬프트와 Scratchpad의 차이

시스템 프롬프트는 Agent의 역할, 행동 원칙과 안전 정책처럼 **일반적으로 모든 LLM 호출에 공통으로 적용되는 비교적 불변적인 지시사항**이다. 따라서 일반적으로 Scratchpad에 포함하지 않는다.

반면 Scratchpad는 Tool 결과, 검색 결과와 작업 진행 내용처럼 실행 상황에 따라 추가·제외·교체되는 정보다.

LLM에 전달되는 전체 입력 Context를 개념적으로 나타내면 다음과 같다.

```text
LLM 입력 Context
├─ 시스템 프롬프트와 정책
├─ Messages에서 선택한 대화 이력
├─ 필요한 사전 지식과 외부 문서
└─ Scratchpad의 작업 Context
```

따라서 “시스템 프롬프트와 user role을 제외한 모든 것이 반드시 Scratchpad다”라고 단정하는 것보다는, **Scratchpad는 LLM 입력 가운데 현재 작업을 위해 가변적으로 구성하는 작업 영역**이라고 이해하는 편이 정확하다.

또한 `user`는 대화 참여자의 역할을 나타내는 메시지 메타데이터다. 실제 사용자의 발화 내용은 `user` 역할을 가진 Message로 관리한다.

## 3. Messages

Messages는 **사용자·Agent·Tool 사이에서 오간 내용을 역할과 발생 순서에 따라 표현한 LLM 입력용 대화 기록**이다.

일반적으로 다음과 같은 형태를 가진다.

```text
1. user: 지난주 프로젝트 회의 찾아줘.
2. assistant: 관련 회의를 검색하겠습니다.
3. tool: 회의 후보 3건을 찾았습니다.
4. assistant: 어느 회의를 확인할까요?
```

Messages와 Scratchpad의 중심 책임은 다음과 같이 다르다.

- Messages: 사용자·Agent·Tool 사이의 대화 이력을 관리한다.
- Scratchpad: LLM의 다음 판단에 필요한 작업 Context를 관리한다.

Messages의 일부는 다음 LLM 호출에 사용되므로 넓은 의미에서는 작업 Context가 될 수 있다. 그러나 실제 구현에서는 대화 이력과 그 밖의 작업 정보를 구분하기 위해 `messages`와 `scratchpad`를 별도 필드로 관리하는 편이 명확하다.

## 4. Graph Engineering의 State

Graph Engineering에서 State는 **Graph가 현재 어디까지 진행되었으며 다음 Node와 Edge를 결정하는 데 필요한 현재 실행 정보의 전체 집합**이다.

LangGraph에서는 이를 일반적으로 `Graph State`로 구현한다. TypeScript로 독립 Agent를 구현한다면 같은 역할의 객체를 `MeetingExecutionState`와 같이 직접 정의할 수 있다.

```text
Graph Engineering의 State
├─ LangGraph 구현: Graph State
└─ TypeScript 구현: MeetingExecutionState와 같은 실행 상태 객체
```

`search`, `question`, `none`과 같은 값은 State 전체가 아니다. 이 값들은 현재 작업 종류 또는 다음 Node를 정하기 위한 **라우팅 결과값**이다. 한 번의 실행 중에만 필요하다면 영속 State 필드가 아니라 하네스 내부의 일시적인 반환값으로 처리할 수도 있다.

## 5. State와 Scratchpad의 관계

Scratchpad는 State 전체를 대체하는 개념이 아니라, 일반적으로 State 안에 포함되는 작업 Context 영역이다.

예를 들어 회의록 Agent의 실행 상태는 다음과 같이 표현할 수 있다.

```ts
type MeetingExecutionState = {
  recordingModalStatus: RecordingModalStatus;
  authorizedMeetingIds: string[];
  pendingHitl?: PendingHitl;

  messages: Message[];

  scratchpad: {
    toolResults: ToolResult[];
    workingContext: WorkingContext[];
  };
};
```

각 영역의 책임은 다음과 같다.

- `recordingModalStatus`: 현재 녹화 상태의 기준값
- `authorizedMeetingIds`: 현재 허용된 회의록 ID의 기준값
- `pendingHitl`: 중단·재개에 필요한 HITL 대기 정보
- `messages`: 역할과 순서를 가진 대화 이력
- `scratchpad`: 이후 LLM 판단에 사용할 Tool 결과와 작업 Context

## 6. 모든 정보를 Scratchpad에 넣을 수 있는가

기술적으로는 가능하다. 다만 구현 형태에 따라 의미가 달라진다.

### 6-1. 구조화된 필드로 넣는 경우

```ts
const scratchpad = {
  recordingModalStatus: "recording",
  authorizedMeetingIds: ["meeting-123"],
  pendingHitl: null,
  messages: [],
  toolResults: [],
};
```

이 객체는 이름만 `scratchpad`일 뿐, 실질적으로 `MeetingExecutionState` 전체의 역할을 한다. 따라서 별도의 설계 방식이라기보다 **실행 State의 이름을 바꾼 것**에 가깝다.

### 6-2. 변경 이력을 계속 추가하는 경우

```text
- recordingModalStatus가 none에서 recording으로 변경됨
- meeting-123이 authorizedMeetingIds에 추가됨
- 사용자가 “지난 회의 찾아줘”라고 질문함
```

이 방식에서 Scratchpad는 모든 변경을 누적하는 **이벤트 로그**처럼 동작한다. 구현할 수는 있지만 다음과 같은 비효율성과 위험이 생긴다.

1. 현재 값을 알기 위해 과거 기록을 다시 탐색하거나 재생해야 한다.
2. 기록의 중복·누락·순서 오류가 현재 상태 판단에 영향을 준다.
3. LLM이 자연어 기록을 해석하여 상태를 판단하면 환각이나 해석 오류가 발생할 수 있다.
4. 누적 기록 전체를 LLM에게 전달하면 입력 Context와 토큰 사용량이 계속 증가한다.
5. 권한 ID나 녹화 상태처럼 정확해야 하는 값을 LLM의 자연어 해석에 의존하게 된다.
6. 대화 이력을 기존 채팅 저장소와 Scratchpad에 함께 저장하면 중복과 불일치가 발생할 수 있다.

예를 들어 현재 녹화 가능 여부만 확인하려고 해도 과거의 시작·일시정지·재개·종료·실패 기록을 순서대로 해석해야 한다. 구조화된 현재 값이 있다면 다음과 같이 즉시 확인할 수 있다.

```ts
state.recordingModalStatus === "none"
```

따라서 다음과 같이 역할을 분리하는 것이 적절하다.

- 현재 기준값: 구조화된 State 필드
- 사용자·Agent·Tool 대화: Messages
- 다음 LLM 판단에 필요한 작업 내용: Scratchpad
- 과거 실행과 변경 내역: Trace 또는 별도의 실행 로그

## 7. 변수값 변경과 Checkpoint

변수값이 변경되는 것 자체는 Checkpoint가 아니다.

```text
변수값 변경
→ 현재 값이 달라진다.

Checkpoint
→ 특정 시점의 실행 정보를 저장하여 이후 복구·재개에 사용할 수 있게 한다.
```

예를 들어 `recordingModalStatus`가 `recording`에서 `paused`로 바뀐 것만으로는 단순 변수값 변경이다. 변경된 변수값을 별도 저장소에 영속화하고, 중단 후 그 지점부터 복구할 수 있도록 했다면 그 저장 동작은 기술적인 의미의 Checkpoint가 될 수 있다.

이 때문에 사람에 따라 “변수값을 저장하는 로직도 Checkpoint다”라고 표현할 수 있다. 이 표현이 맞는지를 판단하려면 단순히 값이 바뀌었는지가 아니라 **그 상태를 저장하여 복구·재개에 사용하는지**를 확인해야 한다.

## 8. 기술 Checkpoint와 업무 Checkpoint

### 8-1. 기술적인 의미의 Checkpoint

Graph 실행 중 장애나 중단이 발생했을 때 특정 시점부터 복구·재개하기 위해 실행 상태를 저장하는 로직이다. 게임의 세이브 지점과 유사하다.

### 8-2. 업무적인 의미의 Checkpoint

정의된 업무 워크플로우가 완료되었다는 의미를 갖는 저장 지점이다. 예를 들면 “사용자 요청 하나에 대한 처리가 완료되었다”는 경계에 둘 수 있다.

### 8-3. 용어를 사용할 때의 주의점

Checkpoint는 말하는 사람의 관점과 목적에 따라 다른 범위를 가리킬 수 있다. 따라서 설계 문서에서는 다음 중 어느 의미인지 명시해야 한다.

- 장애 복구를 위한 기술 Checkpoint인지
- 업무 완료 경계를 나타내는 업무 Checkpoint인지
- 단순한 State 변경이나 저장을 Checkpoint라고 표현한 것인지

하나의 저장 지점이 기술 Checkpoint이면서 동시에 업무 Checkpoint일 수도 있다. 하지만 기술적으로 복구 가능한 모든 지점이 사용자 관점의 업무 완료 경계인 것은 아니다.

## 9. Snapshot

Snapshot은 **특정 시점의 State를 복사하거나 포착한 것**이다.

Snapshot을 영속 저장하고 중단된 실행의 복구·재개에 사용한다면, 그 Snapshot은 **기술 Checkpoint** 역할을 한다. 그러나 관찰, 디버깅이나 화면 표시만을 위해 일시적으로 복사한 Snapshot은 반드시 Checkpoint라고 할 수 없다.

```text
Snapshot
├─ 복구·재개에 사용함 → 기술 Checkpoint 역할
└─ 관찰·디버깅에만 사용함 → Checkpoint가 아닐 수 있음
```

또한 복구용 Snapshot이라 하더라도 사용자가 정의한 하나의 업무 완료 지점과 일치하지 않는다면 **업무 Checkpoint는 아닐 수 있다**.

## 10. LangGraph의 `interrupt()`와 Codex의 `interrupted`

두 용어는 이름이 비슷하지만 목적과 계층이 다르다.

### 10-1. LangGraph의 `interrupt()`

LangGraph의 `interrupt()`는 HITL을 위해 Graph 실행을 **의도적으로 중단하고 이후 입력을 받아 재개하기 위한 기능**이다. 재개하려면 중단 당시 실행 상태를 보존해야 하므로 Checkpointer와 State Snapshot을 함께 사용한다.

```text
Graph 실행
→ interrupt() 호출
→ 실행 상태 보존
→ 사용자 입력 대기
→ 보존된 상태에서 실행 재개
```

### 10-2. Codex의 `interrupted` 상태

Codex에서 `Ctrl+C` 등으로 표시되는 `interrupted`는 현재 Codex 작업이 외부 요청으로 중단되었다는 실행 상태를 의미한다. LangGraph의 HITL용 `interrupt()`를 호출했다는 뜻이 아니다.

따라서 다음처럼 구분해야 한다.

- LangGraph `interrupt()`: HITL을 위한 의도적 중단·상태 보존·재개 기능
- Codex `interrupted`: Codex 실행이 취소되거나 중단되었다는 상태 표시

## 11. 핵심 정리

```text
Trace
→ 실행 과정의 관찰·디버깅·감사를 위한 로그

Messages
→ 사용자·Agent·Tool 사이의 역할과 순서를 가진 대화 이력

Scratchpad
→ 다음 LLM 판단에 사용하도록 가변적으로 구성하는 작업 Context

State
→ 현재 Graph 실행과 다음 라우팅에 필요한 정보 전체

변수값 변경
→ 그 자체는 단순히 현재 값이 달라지는 것일 뿐이며 Checkpoint가 아님

Snapshot
→ 특정 시점의 State를 복사하거나 포착한 것

기술 Checkpoint
→ 복구·재개를 위해 실행 상태를 저장한 지점

업무 Checkpoint
→ 정의된 사용자 업무가 완료되었다는 의미를 갖는 저장 지점

LangGraph interrupt()
→ HITL을 위해 Graph를 의도적으로 멈추고 이후 재개하는 기능
```

가장 중요한 원칙은 현재 상태, 대화 이력, LLM 작업 Context와 실행 로그를 하나의 모호한 저장소에 섞지 않는 것이다. 구현상 하나의 객체나 데이터베이스를 사용하더라도 각 정보의 책임과 사용 목적은 명확하게 구분해야 한다.
