# 회의록 에이전트 POC 구조와 설계 대응

## 1. 전체 구조

```text
CLI · UI 대역
  ↓
MeetingAgentRuntime · 하네스
  ├─ Recording Workflow
  │    └─ SQLite 모달·Backend 대역
  └─ Agent Graph
       ├─ DeepSeekMeetingModel · 실제 LLM
       ├─ Search Subgraph
       ├─ Question Subgraph
       └─ SQLite Checkpointer
```

## 2. 파일별 역할

| 파일 | 역할 | 실제/대역 |
|---|---|---|
| `state.py` | Agent·Subgraph State와 Runtime Context | 실제 Graph 계약 |
| `agent_graph.py` | 최상위 Graph와 두 Subgraph | 실제 Graph 코드 |
| `recording_graph.py` | LLM 없는 녹화 실행 경계 | 실제 Workflow 코드 |
| `runtime.py` | Graph 조립, Checkpoint, Lock, HITL 재개 | 실제 하네스 |
| `model.py` | DeepSeek Adapter와 Model 계약 | DeepSeek 실제, RuleBased 대역 |
| `repository.py` | 권한·검색·원문·녹화 상태 | 제품 Backend의 SQLite 대역 |
| `cli.py` | 실행과 HITL 입력 | 프론트엔드 대역 |
| `tests/test_agent.py` | Graph와 State 불변 조건 | 실제 테스트 |
| `tests/test_recording.py` | 녹화 Workflow | 실제 테스트 |
| `tests/test_deepseek_model.py` | DeepSeek HTTP 계약 | HTTP Mock 테스트 |
| `tests/test_deepseek_integration.py` | 실제 LLM 전체 흐름 | 실제 외부 API 테스트 |

## 3. 최상위 Agent Graph

```text
START
→ receive_user_request
→ compact_scratchpad
→ llm_goal_condition
   ├─ search   → Search Subgraph
   ├─ question → Question Subgraph
   └─ direct   → 직접 답변 → END

Search / Question
→ LLM이 response + follow_up 반환
→ Graph Runtime이 State 반영·Checkpoint 저장
→ 고정 Condition
   ├─ follow_up=true  → llm_goal_condition 재진입
   └─ follow_up=false → END
```

DeepSeek의 최초 routing은 `search/question/direct`를 반환한다. Search·Question의 마지막 LLM은 응답과 `follow_up`을 함께 반환하고, 하네스의 고정 Condition이 다음 Edge를 선택한다. 최종 종료 확인만을 위한 별도 DeepSeek `none` 호출은 없으며 `done`도 사용하지 않는다.

## 4. Search Subgraph

```text
접근 가능한 후보 검색
→ S1에서 후보 수만 DeepSeek에 전달하여 경로 해석
→ 고정 Condition 분기
   ├─ 0개: 결과 없음
   ├─ 1개: 자동 선택 후 Backend 재검증
   └─ 여러 개: HITL 선택 후 Backend 재검증
→ 기존 ID가 있으면 추가·대체 HITL
→ authorized_meeting_ids 갱신
→ 검색 응답 생성
```

후보 결과의 `none/one/many` 경로는 원본 설계대로 DeepSeek이 구조화해 반환하고 실제 Edge는 코드가 선택한다. 검색 안내 문장은 `follow_up`과 함께 DeepSeek이 생성한다.

HITL 대기 중 후보 밖 ID나 `add/replace`가 아닌 값을 입력하면 오류 이유와 함께 같은 질문을 다시 표시한다. 일반 문장을 입력해도 새 Agent 요청을 시작하지 않고 기존 pending HITL을 유지한다. 선택 재검증의 권한·Backend 실패는 Graph 밖 예외가 아니라 구조화된 검색 실패 결과로 S3 안내 경로에 합류한다.

## 5. Question Subgraph

```text
authorized_meeting_ids 확인
→ 없으면 selection_required
→ Tool 2로 권한 재검증 및 원문 조회
→ Q2-A/B/C가 결과별 Model Context 조립
→ Q3가 DeepSeek response + follow_up 생성
→ 답변과 문서 메타데이터만 State에 저장
```

원문은 LangGraph의 `UntrackedValue` 메모리 채널로 Q1→Q2→Q3 실행 중에만 전달되며 기술 Snapshot과 Checkpoint에는 들어가지 않는다. `authorized_meeting_ids`와 후보 ID 목록은 LLM에 전달하지 않는다.

## 6. 녹화 Workflow

```text
START
→ recording_modal_and_backend
→ END
```

Graph는 고정 실행 경계이며 실제 상태 전이는 Repository 대역이 수행한다. Agent에는 모달 실행 가능 여부를 나타내는 `recording_modal_status`만 동기화한다.

설계도의 `none → recording ↔ pause → stop → none`은 모달 내부 상태 모델이다. POC LangGraph는 이를 Agent 쪽에 중복 구현하지 않고 Trigger를 모달 대역에 전달하는 단일 Node만 둔다.

## 7. Checkpoint 구분

- **기술 Snapshot:** LangGraph `SqliteSaver`의 Super-step State
- **업무 Checkpoint:** Search·Question 결과가 부모 State에 반영된 LangGraph Snapshot
- **HITL 중단:** `interrupt()`가 만든 재개 가능한 Snapshot

Checkpoint·Lock·HITL Context는 `(user_id, thread_id)`로 격리하며 다른 사용자는 같은 문자열의 Thread를 상속하거나 재개할 수 없다.
