# 발표용 로컬 Trace 시연 가이드

이 문서는 **발표 당일 Trace 화면의 시연 순서와 설명 포인트**만 다룬다. 개발 환경 구성, CLI 명령, 전체 단위 테스트와 실제 DeepSeek 통합 테스트 방법은 `3. POC 실행 및 테스트 방법`을 참고한다.

## 1. 발표 직전 점검

발표 전에 3번 문서의 오프라인 테스트와 실제 DeepSeek 통합 테스트를 한 번 실행한다. 이후 발표 전용 DB 파일명을 사용하면 기존 연습 상태와 섞이지 않는다.

```powershell
cd C:\Users\염정운\project\zen-ai-meeting-agent-test

.\.venv\Scripts\python.exe -m meeting_agent `
  --app-db data\presentation-app.db `
  --checkpoint-db data\presentation-checkpoints.db `
  --deepseek-key-file "C:\Users\염정운\OneDrive - (주)젠컨설팅\바탕 화면\API Key 및 Key 값\DeepSeek API Key.txt" `
  --deepseek-model "deepseek-v4-pro" `
  serve
```

- 기본 화면: `http://127.0.0.1:8765`
- 브라우저는 자동으로 열린다.
- 서버 종료: PowerShell에서 `Ctrl+C`

위 명령에는 `--model-provider rule-based`가 없으므로 기본 Provider인 실제 DeepSeek과 `deepseek-v4-pro`를 사용한다.

> **서버가 빠르게 켜지는 것만으로는 Model을 판별할 수 없다.** 서버 시작 단계에서는 API를 호출하지 않기 때문에 DeepSeek 모드도 즉시 기동된다. 실제 API 호출은 브라우저에서 회의록 질문을 입력한 순간 시작된다. 질문까지 거의 즉시 끝난다면 실행 명령에 `--model-provider rule-based`가 포함되어 있는지 확인한다.

## 2. 시연 1 — 결정적 녹화 Workflow

입력:

```text
/meeting-start
```

화면에서 짚을 부분:

```text
Recording Workflow
START
→ recording_modal_and_backend
→ END
```

- `previous_state: none`
- `current_state: recording`
- `recording_modal_status: healthy`
- LLM 목표 판단과 Search/Question Subgraph가 나타나지 않는다.

설명할 설계 의도:

> 녹화는 자연어 추론이 필요한 Agent 업무가 아니라 코드로 전이가 고정된 결정적 Workflow다.

## 3. 시연 2 — Search → Question 복합 목표

입력:

```text
meeting-001 회의록을 가져오고 결정 사항을 설명해줘
```

오른쪽 Trace에서 다음 순서를 설명한다.

```text
Agent Graph
receive_user_request
→ compact_scratchpad
→ llm_goal_condition: search

Search Subgraph
S1_candidate_search_and_judgment
→ S2B_one_candidate
→ S3_search_response_ready

Agent Graph
→ follow_up=true 고정 Condition
→ llm_goal_condition: question

Question Subgraph
Q1_tool_2_source_lookup
→ Q2B_build_source_context
→ Q3_question_response

Agent Graph
→ follow_up=false 고정 Condition
→ END
```

State에서 짚을 부분:

- `authorized_meeting_ids`에는 Backend가 검증한 `meeting-001`만 들어간다.
- `ScratchPad`에는 요청, LLM 판단과 검색·질문 응답이 중복 없이 쌓인다.
- `recording_modal_status`는 Agent가 모달 실행 가능 여부만 기억한다.
- 실제 녹화 상태 `recording_state`는 Agent State에 없다.
- 회의록 `transcript` 원문과 API 키는 Trace와 Checkpoint에 나타나지 않는다.

설명할 설계 의도:

> LLM은 검색·질문 응답과 후속 작업 여부를 함께 생성하지만 실제 Edge와 권한은 코드가 통제한다. Search의 `follow_up=true`를 고정 Condition이 읽어 Question 판단으로 복귀하고, Question의 `follow_up=false`에서 END로 이동한다.

## 4. 시연 3 — 복수 후보 HITL

입력:

```text
회의록 검색해줘
```

후보가 여러 개면 `S2C_multiple_candidates`에서 실행이 중단된다. 화면에 나온 후보를 다음처럼 선택한다.

```text
/select meeting-001
```

기존 허용 ID에 추가할지 대체할지 다시 묻는 경우:

```text
/merge add
```

또는:

```text
/merge replace
```

설명할 설계 의도:

> 여러 회의록 중 어떤 것을 사용할지는 모델이 임의로 확정하지 않고 사용자에게 되돌려 주는 HITL 경계다. 재개 시에도 Backend가 선택 ID를 다시 검증한다.

후보에 없는 ID나 잘못된 추가·대체 값을 입력하면 오류 이유가 포함된 같은 HITL 질문이 다시 나타난다. HITL 대기 중 일반 질문을 입력해도 새 요청으로 넘어가지 않고 현재 선택 질문을 유지한다.

## 5. 시연 4 — 녹화 마무리

```text
/meeting-pause
/meeting-resume
/meeting-stop
```

동일한 결정적 Node를 지나되 입력 명령에 따라 상태만 정해진 규칙으로 전이하는지 보여준다.

## 6. Trace가 실제 실행 로그인 근거

오른쪽 Trace는 발표용으로 임의 생성한 Node 목록이 아니다. 실제 LangGraph의 `stream_mode="debug"` 이벤트를 안전하게 가공한다.

| LangGraph 이벤트 | 화면 표현 |
|---|---|
| `task` | Node 시작 |
| `task_result` | Node 출력과 완료 |
| `checkpoint` | LangGraph 복구용 기술 State Snapshot과 다음 Edge |
| namespace | 상위 Agent Graph와 중첩 Subgraph 구분 |

보안상 회의록 원문 `transcript`와 API 키는 Trace 변환 단계에서 제외한다.

### 기술 Snapshot과 설계의 업무 Checkpoint 구분

LangGraph는 `SqliteSaver`로 실행을 복구하기 위해 **매 Super-step 뒤에 기술 Snapshot**을 저장한다. 이것은 설계도에 그린 업무 경계 Checkpoint Node가 아니다.

- **업무 경계 Checkpoint:** Search·Question 결과가 부모 Agent State에 반영된 LangGraph Snapshot
- **기술 State Snapshot:** LangGraph가 각 Node 실행 뒤 내부적으로 저장하는 복구 자료

화면은 발표 중 혼동을 막기 위해 기술 Snapshot을 기본적으로 숨긴다. 필요할 때만 오른쪽 상단의 `기술 State Snapshot 표시`를 체크한다.

현재 화면은 LangGraph debug event를 SSE로 즉시 전달한다. Node 시작, Tool 결과, Subgraph 진행과 다음 Edge가 발생하는 순서대로 바로 나타나며 요청 완료 후 인위적으로 재생하지 않는다.

## 7. 발표 당일 문제 대응

### DeepSeek 응답이 느릴 때

현재 POC는 `deepseek-v4-pro`를 실제 호출하지만 Graph의 구조화 JSON 계약에는 Thinking을 비활성화한다. 따라서 이전 기본 Thinking 실행보다 빨라질 수 있으며, 속도가 빠르다는 이유만으로 rule-based 대역이라고 판단하면 안 된다. `DeepSeek / Graph 실행 중…` 표시가 사라질 때까지 기다린다.

### 기본 Port가 사용 중일 때

```powershell
.\.venv\Scripts\python.exe -m meeting_agent serve --port 8766
```

브라우저에서 `http://127.0.0.1:8766`을 연다.

### API 또는 네트워크가 불안정할 때

```powershell
.\.venv\Scripts\python.exe -m meeting_agent `
  --model-provider rule-based `
  serve
```

Graph·Subgraph·Node·Edge·State 시연은 동일하다. 다만 발표 중 답변 Model만 테스트 대역으로 전환했다고 명시한다.

`--model-provider rule-based` 명령은 실제 DeepSeek을 사용하지 않는다. 따라서 질문이 즉시 끝나는 것이 정상이며, 실제 API 시연으로 설명하면 안 된다.

### 다시 처음부터 시연해야 할 때

서버를 종료하고 새로운 DB 파일명을 지정한다. 기존 DB를 발표 중 삭제하는 방식보다 안전하다.

```powershell
.\.venv\Scripts\python.exe -m meeting_agent `
  --app-db data\presentation-app-2.db `
  --checkpoint-db data\presentation-checkpoints-2.db `
  serve
```
