# Trace 구현 방식과 주요 개선 사항

최초 작성: 2026-09-23 · 갱신: 2026-09-28 · 구현 기준이며 운영 배포 상태와는 별개.

## 1. DB와 메모리의 역할

- **DB:** 서버를 재시작해도 유지해야 하는 대화·회의록·Agent State·Checkpoint·HITL 업무 상태를 보관한다.
- **RAM:** 실행 중인 서버가 데이터를 일시적으로 보관하는 메모리다. 브라우저에도 화면 표시용 임시 데이터가 있다.
- **이전 Trace:** 실시간 전달·화면 표시에는 메모리를, 과거 기록의 영속 보관·재조회에는 Trace 전용 DB 테이블을 사용했다.
- **현재 Trace:** 장기 보관의 필요성보다 구현·운영 단순화를 우선하여 **서버 프로세스 메모리에만 보관**한다. 외부 로그 제품·별도 저장 DB는 사용하지 않는다.
- 제거 대상은 `agent_trace_requests`, `agent_trace_events`와 전용 저장 로직이다. 기존 업무 DB와 실행 이력 `agent_run_spans`는 별개로 유지한다. 테이블 제거는 `0085` 적용 시 이루어진다.

## 2. 화면 표시와 재조회

- 서버가 Trace를 생성 → 메모리에 보관 → 호출자 브라우저에 SSE로 실시간 전달한다.
- 기존 별도 패널 대신 **스레드의 각 질문 아래, 최종 답변 앞에 접이식 ‘처리 과정’**을 표시한다.
- 이미 받은 내용을 펼칠 때는 통신이 필요하지 않을 수 있다. 새로고침·누락 보충 시에는 서버 메모리에서 다시 조회한다.
- 서버 재시작·재배포 시 과거 Trace는 유실된다. 대화·State·HITL은 DB에 남는다.
- 최대7일이며 용량 제한으로 더 일찍 제거될 수 있다. 단일 서버 프로세스 기준이고 다중 서버 공유는 지원하지 않는다.

## 3. 첫 실행에서 후속 상호작용까지 확장

- 첫 Run만 관측하고 후속 상호작용을 놓치던 사용 경험을 개선했다.
- 최초 질문·후속 질문·HITL 선택/재개·취소 등 **새 호출마다 해당 질문 아래 별도 Trace 묶음**을 만든다. 모든 일반 채팅 메시지에 생성하는 것은 아니다.
- 각 호출 중 새 단계가 발생하면 같은 묶음에 순서대로 추가한다. 기존 펼침 상태를 유지하고, 읽던 위치를 강제로 이동시키지 않는다.
- 사용자 선택 대기를 전체 완료와 구분하고, 재개·성공·실패·취소 상태를 연결한다.

## 4. 한국어 설명과 정보 보호

- 긴 내부 이벤트 이름 대신 ‘요청을 판단하고 있어요’, ‘검색 도구를 선택했어요’ 같은 고정 한국어 설명을 표시한다.
- 정형 실행 이벤트에는 실제 사용자·스레드·회의록 ID, 대화·회의록 본문, Tool 입출력 원문, 인증 키·원본 예외를 출력하지 않는다.
- **모델이 반환하는 추론 텍스트는 별도:** 질문·회의록 내용을 재언급할 수 있으므로, 모든 Trace가 민감정보를 포함하지 않는다고 보장하지 않는다. 안내 문구 제거는 정보 보호 보장을 의미하지 않는다.
- 호출자 본인만 조회한다. 같은 채널·스레드의 다른 사용자에게는 Trace를 보여주지 않는다.

## 5. Provider가 반환한 추론 텍스트 표시

- 기존의 안전한 처리 설명에 더해, **Provider가 API로 제공하는 추론 텍스트·요약**을 표시하도록 확장했다. 모델 내부의 전체 사고 과정을 복원하는 기능은 아니다.
- 정형 실행 단계는 한국어로, 추론 텍스트는 **번역하지 않고 원문 그대로** 표시한다. HTML·Markdown으로 해석하지 않아 `**`도 그대로 보인다.
- **오늘 표시 개선:** `공개 추론 요약` 제목과 고정 주의 문구를 제거하고, 원문 왼쪽에 `LLM 추론:`을 표시한다.

```text
LLM 추론: **Planning keyword-based search**
```

- 수신 조각은 약 50ms 단위 또는 2KB가 찼을 때 전달하고, 화면에서는 연속 조각을 합친다. 전체 답변 완료를 기다리지 않는다. 실제 첫 수신 시점은 Provider에 달려 있다.
- 추론 텍스트가 오지 않는 모델·응답에서는 해당 항목 없이 일반 실행 단계만 표시한다. 추론 강도 `high`가 텍스트 반환을 보장하지는 않는다.
- 추론 텍스트는 기존 메모리 기반 Trace 경로를 사용하고, 모델 실행 이력의 span에는 별도로 저장하지 않는다.

### 운영 연결 확인 결과

- 운영은 `chat-completions` 전제다. LiteLLM 표준 스트리밍 필드인 `choices[0].delta.reasoning_content` 문자열을 SDK가 읽고, `reasoning-delta` → `model.reasoning` → 화면으로 전달한다.
- `MEETING_MODEL_API=responses`는 별도 API 선택 설정이며, 추론 표시를 위해 운영에서 무조건 바꿔야 하는 값은 아니다.
- 설정 화면의 추론 강도 활성화는 zen-ai의 `MODELS` 카탈로그 설정에 따른다. 비활성화만으로 모델 자체가 추론을 지원하지 않는다고 판단할 수 없다.
- **미확인:** 운영 LiteLLM이 실제 추론 문자열을 반환하는지. 로컬 표준 응답 테스트 통과와 운영 실응답 검증은 구분한다.

## 6. 적용 범위와 검증

- 상세 계측은 회의 Builtin 중심이다. 일반 Agent·SAP의 내부 모델/Tool 상세 Trace는 향후 단계적으로 확장한다.
- 두 사용자 동시 브라우저에서 본인 Trace만 표시되고, 취소·재개가 서로 간섭하지 않으며 새로고침 후 복구되는 것을 확인했다.
- 기존 검증: 관련 추가 통합·UI 테스트51개 통과. 실제 마이크 녹음·전사는 검증 범위에서 제외했다.
- 오늘 수신·전달 경로 검사: 관련 84개 테스트 통과. DB 연계 조회·권한 테스트는 테스트용 역할 비밀번호 미설정으로 준비 단계에서 실패했다.
- 오늘 표시 변경 검증: 관련 13개 테스트, Prettier·ESLint·`git diff --check` 통과. 원문 보존·조각 병합·HTML 미실행을 확인했다.
- 전체 Vitest: **4,155개 통과 / 50개 실패 / 257개 건너뜀 / 미처리 오류 1건**. Windows 제약·DB 설정·Provider 테스트 오류 등이 있어 전체 회귀 통과로 보지 않는다. 이번 표시 변경에 대한 새 브라우저 E2E는 실행하지 않았다.
- 이번 표시 변경은 로컬 코드에 반영했으며 커밋·배포는 하지 않았다.

## 7. Tool 및 시간 초과 Trace 개선

- **Tool 이름:** 개별 도구마다 문구를 작성하는 대신 Tool 정의의 `title`을 우선 사용하고, 없으면 `name`을 사용한다.
- **입출력 구조:** 호출 시 입력, 반환 직후 출력의 필드 이름·자료형·배열 개수를 표시한다. 실제 값·회의록 ID·Tool 내부 로직은 표시하지 않는다.
- **시간 초과:** 일반 실패와 구분하여 `처리 시간 제한을 초과했어요 · 답변 생성 중 · 판단 2회 · 검색 1회`처럼 중단 단계와 횟수를 표시한다. 이 정보만으로 반복 검색이 잘못됐거나 모델이 내부에서 무엇을 추론했는지까지 단정하지 않는다.
