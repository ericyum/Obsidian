# LLM 추론 미표시 원인과 LiteLLM 호환성 개선

> 2026-09-29 기준 · 로컬 구현·검증 완료 / 운영 LiteLLM 반영 전

## 1. 발생한 문제

- 운영에서 회의록 검색·선택·최종 답변과 일반 Trace는 표시되지만, **LLM이 반환하는 추론 텍스트가 표시되지 않음**.
- 추론 강도를 높여도 해결되지 않아 `zen-ai → LiteLLM → SAP AI Core` 연결을 조사함.
- 단순한 화면 문제가 아니라 **LiteLLM 1.92.0의 SAP 어댑터 호환성과 모델별 API 경로 차이**가 핵심이었음.
- 운영 서버의 실제 설정 전체를 직접 확인한 결과와는 구분해야 함. 아래 원인·해결은 로컬에서 실제 SAP 호출과 설치된 변환 코드를 기준으로 확인함.

## 2. Claude와 GPT의 원인 차이

| 구분     | 확인한 원인                                                                     | 해결 방식                                                  |
| ------ | -------------------------------------------------------------------------- | ------------------------------------------------------ |
| Claude | LiteLLM SAP 어댑터의 지원 옵션에 `reasoning_effort`가 빠져 추론 옵션 전달 시 오류 발생            | 해당 옵션 전달을 허용하도록 호환 패치                                  |
| Claude | SAP 추론 블록은 배열인데, 앱의 OpenAI 호환 SDK가 받는 추론 텍스트는 문자열 형식을 기대함                  | 배열의 텍스트를 `reasoning_content` 문자열로 정규화하고 스트리밍 조각도 전달    |
| GPT    | 기존 SAP Orchestration의 Chat Completions 경로에서는 추론 강도를 높여도 공개 추론 텍스트가 관측되지 않음 | GPT별 foundation-models 배포를 만들고 native Responses 경로로 연결 |

- **“LiteLLM이 Responses API 자체를 지원하지 않는다”는 뜻은 아님.** 기존 LiteLLM Responses 기능에 SAP 배포별 주소·인증 연결을 추가한 것임.
- GPT의 결과를 SAP 모든 모델·버전의 영구적인 제약으로 일반화하지 않음. 이번에 확인한 경로와 모델 기준의 해결임.

## 3. 구현한 해결 구조

```text
회의록 Assistant → LiteLLM
                    ├─ Claude → SAP Orchestration → Chat Completions
                    └─ GPT    → 모델별 foundation-models 배포 → Responses
```

- 앱에 `MEETING_MODEL_API=sap-mixed` 선택 모드 추가.
  - GPT sol·terra·luna: Responses 사용, 공개 추론 요약 `auto` 요청.
  - Claude: 기존 Chat Completions 유지.
  - 미설정 시 기존 기본 동작 유지. 모델별 경로 전환을 자동으로 강제하지 않음.
- LiteLLM의 GPT 주소 매핑:
  - sol → `AICORE_GPT_SOL_DEPLOYMENT_URL`
  - terra → `AICORE_GPT_TERRA_DEPLOYMENT_URL`
  - luna → `AICORE_GPT_LUNA_DEPLOYMENT_URL`
- SAP OAuth 인증의 기존 토큰 캐시·갱신 기능 재사용. 인증키·배포 주소는 이미지가 아닌 환경변수로 전달.
- Claude 추론 원본 블록·서명은 별도 메타데이터에 보존하고, 화면에는 추론 텍스트만 전달. 원시 API의 Tool 왕복과 SDK의 메타데이터 보존 가능 범위는 구분함.
- Tool 스트림에서 발생하던 빈 `logprobs` 형식도 정규화.
- 공식 이미지의 버전·digest를 고정하고 호환 패치를 적용하는 **재현 가능한 Dockerfile**로 관리. DB 이미지를 수정한 것이 아님.

## 4. Trace 표시 원칙

- 모델/provider가 제공한 공개 추론 텍스트를 **`LLM 추론:` 뒤에 원문 그대로 표시**. 번역하거나 임의로 추론 내용을 만들지 않음.
- 모델 내부의 전체 사고 과정이 아니라, provider가 외부로 제공한 텍스트만 대상.
- 스트리밍으로 도착한 텍스트는 수신에 맞춰 추가함. provider가 늦게 보내면 화면도 늦게 표시됨.
- **매 요청마다 추론 텍스트가 나오는 것은 아님.** 높은 추론 강도도 요약 생성을 보장하지 않으며, 텍스트가 없는 정상 응답도 허용함.

## 5. 검증 결과

- 실제 SAP API: Claude 3종 15개, GPT Responses·Tool·기존 Chat bridge 9개 시나리오 통과.
- 브라우저 E2E: **sol·terra·luna·Sonnet·Opus·Haiku 6종** 모두 검색 → 선택 → 후속 질문 → 최종 답변 및 추론 표시 확인.
- Sonnet·Haiku는 답변 완료 전 추론 텍스트가 증가하는 장면까지 확인. 나머지 4종의 완료 전 표시 시점은 브라우저에서 포착하지 못했으므로 구분함.
- check·lint·knip 통과. 전체 회귀는 Windows·DB 테스트 환경 관련 실패가 남아 **전체 통과로 보지 않음**. GitHub Linux CI 확인 필요.
- 기존 재검색 반복 현상은 별도 프롬프트·대화 흐름 과제로 제외.

## 6. 운영 적용 시 남은 작업

- **커밋·머지만으로 운영 LiteLLM 이미지가 교체되지는 않음.** 현재 자동 배포는 이번 호환 이미지까지 연결되어 있지 않음.
- 읽기 전용 Ops 작업 `litellm-check`를 추가함. GitHub 반영 후 실행해 운영 이미지·모델 구성·환경변수 설정 여부 등을 확인할 예정이며, 아직 운영 조회를 수행한 것은 아님.
- 운영의 기존 모델 설정·콜백·LiteLLM 로그 DB를 보존하면서 호환 이미지 배포와 롤백을 연결해야 함.
- 운영 LiteLLM에 GPT 배포 주소 3개를 전달하고, 준비가 끝난 뒤 앱에 `sap-mixed` 적용. **앱 설정만 먼저 전환하지 않음.**
- 이후 운영에서 실제 호출·추론 표시를 최종 확인해야 완료됨.
