# LLM 추론 Trace 문제 조사와 운영 배포 중단까지의 기록

> **정리일: 2026-10-01**
> **범위:** 추론 텍스트 미표시 → 모델별 원인 규명 → 로컬 검증 → 운영 반영 시도 → 구성 해시 불일치.
> **현재 상태:** 로컬 호환성 개선과 운영 배포 완료는 별개다. 운영 전환 성공은 확인되지 않았으며, 배포 단순화 작업도 승인 전 중단한 상태다.

## 1. 핵심 요약

**처음에는 “Trace 화면에 추론 텍스트가 없다”는 문제였지만, 마지막에는 “수정한 LiteLLM을 운영에 안전하게 교체하지 못한다”는 문제로 바뀌었다.** 두 문제를 구분해야 진행 상황을 정확히 이해할 수 있다.

| 구분 | 핵심 문제 | 확인한 결과 |
| --- | --- | --- |
| **일반 Trace** | 요청·도구 호출·답변 작성 단계 표시 | 운영에서 정상 표시 |
| **Claude 추론 텍스트** | LiteLLM SAP 어댑터의 옵션·응답 형식 호환성 | 로컬 패치 및 실제 호출로 개선 확인 |
| **GPT 추론 텍스트** | 기존 Orchestration/Chat 경로에서 공개 추론 텍스트 미관측 | 모델별 foundation-models 배포 + Responses 경로로 로컬 확인 |
| **운영 반영** | 앱 코드 머지와 운영 LiteLLM 이미지 교체가 분리됨 | 별도 배포 연결이 필요했음 |
| **최종 중단 지점** | 실행 중 컨테이너와 Compose의 **구성 해시 불일치** | URL 적용 전 준비 단계에서 중단. 최종 원인은 미확정 |

**높은 추론 강도는 추론 텍스트 반환을 보장하지 않는다.** Trace는 provider가 실제로 제공한 공개 텍스트만 표시하며, 모델 내부의 전체 사고 과정을 추출하거나 없는 설명을 만들어 내는 기능이 아니다.

## 2. 전체 흐름 — 어디에서 문제가 달라졌나?

![[추론_텍스트_전달_경로.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/추론_텍스트_전달_경로.excalidraw)

**정형 Trace**는 코드가 실행 단계에 맞춰 만든 문장이다. “도구를 선택했어요”, “답변을 작성하고 있어요”가 보인다고 해서 모델의 추론 텍스트까지 도착했다는 뜻은 아니다.

**LLM 추론 Trace**는 모델 → SAP → LiteLLM → 앱 SDK → Trace 화면을 통과한 텍스트다. 중간 어느 지점에서든 텍스트가 없거나 형식 변환이 안 되면 일반 Trace와 최종 답변만 보일 수 있다.

| 표시 종류 | 원본 | 표시 방식 |
| --- | --- | --- |
| **처리 단계** | 앱이 발생시킨 정형 이벤트 | 한국어 문구 |
| **도구 입력·반환** | 호출 데이터의 구조 | 필드 이름·유형·배열 개수. 실제 값은 표시하지 않음 |
| **LLM 추론** | 모델/provider가 공개한 텍스트 | **`LLM 추론:` + 원문**, 번역하지 않음 |

## 3. 조사 과정 — 증상에서 모델별 원인까지

### 3-1. 화면 문제인지, 전달 경로 문제인지 분리

**최초 증상은 운영에서 검색·선택·최종 답변은 나오지만 추론 텍스트만 없다는 것**이었다. Claude와 GPT를 바꾸거나 GPT의 추론 강도를 높여도 표시되지 않았다.

그래서 **원시 API 응답 → SDK의 `reasoning-delta` → Trace 이벤트 → 화면** 순서로 확인할 필요가 있었다. 화면에 없다는 사실만으로 “모델이 추론을 안 한다” 또는 “UI가 고장 났다”고 결론 내릴 수는 없었다.

### 3-2. 로컬 Codex-LB와 운영 SAP·LiteLLM을 구분

**로컬에서 보였던 추론 표시가 운영에서도 그대로 된다는 보장은 없었다.** 로컬 Codex-LB 경로와 SAP·LiteLLM 경로는 주소·인증·API 방식이 달랐다.

특히 **`localhost:4000`은 해당 실행 환경의 로컬 주소**다. 로컬 PC에 LiteLLM을 설치하는 것과 운영 LiteLLM 컨테이너를 조회하거나 교체하는 것은 다른 일이다. `npm run dev` 실행만으로 별도 LiteLLM 서버가 생기는 것도 아니다.

**`LiteLLM_SpendLogs` 조회와 실제 응답 확인도 별개**다. DB 연결 정보와 기록 정책에 따라 조회 가능 범위가 달라지며, 로컬 이미지를 실행했다고 운영 로그 DB가 자동 연결되는 것은 아니다.

### 3-3. 로컬 LiteLLM을 구성하고 실제 SAP 호출 확인

**추측을 줄이기 위해 LiteLLM 1.92.0의 설치된 변환 코드와 실제 API 응답을 확인**했다. 초기 환경·인증 문제를 점검한 뒤 모델별 요청 옵션, 응답 형식, 스트리밍 전달을 분리해 조사했다.

이 과정에서 **Claude의 형식 호환성 문제**와 **GPT의 호출 경로 문제**가 서로 다르다는 점이 드러났다.

## 4. Claude와 GPT는 원인도 해결 방식도 달랐다

### 4-1. Claude — 옵션 전달과 추론 배열 변환

**LiteLLM 1.92.0의 SAP 어댑터에는 `reasoning_effort`가 기본 지원 옵션에 빠져 있었다.** 해당 옵션을 보내는 경로에서는 오류가 발생할 수 있어 전달 허용을 보완했다. 이것이 모든 미표시 상황의 단일 원인이라는 뜻은 아니다.

또한 **SAP 추론 블록은 배열**, 앱의 OpenAI 호환 경로에서 소비할 추론 텍스트는 **문자열**이었다. LiteLLM에서 일반 응답과 스트리밍 조각 모두에 변환을 적용했다.

| 보완 내용 | 목적 |
| --- | --- |
| **추론 옵션 전달 허용** | 요청 옵션이 어댑터에서 거부되지 않도록 함 |
| **배열 → 문자열 정규화** | 텍스트가 SDK와 Trace까지 전달되도록 함 |
| **원본 블록·서명 보존** | 표시용 문자열과 후속 호출용 정보를 구분 |
| **빈 `logprobs` 정규화** | 일부 Tool 스트림의 직렬화 호환성 보완 |

**수정한 대상은 DB 이미지가 아니라 LiteLLM 실행 이미지의 Python 어댑터 코드**다. 고정한 공식 이미지 위에 패치를 적용하는 Dockerfile로 재현 가능하게 만들었다.

### 4-2. GPT — 기존 Chat 경로와 native Responses 경로

**기존 SAP Orchestration의 Chat Completions 경로에서는 GPT의 공개 추론 텍스트가 관측되지 않았다.** 일반 답변 생성과 공개 추론 텍스트 제공은 별개의 기능이다.

해결을 위해 **sol·terra·luna의 foundation-models 배포**를 만들고, 모델별 주소로 **Responses 요청**을 보내도록 연결했다.

| 항목 | 기존 경로 | 로컬에서 검증한 변경 경로 |
| --- | --- | --- |
| **SAP 배포** | 공용 Orchestration deployment | GPT 모델별 foundation-models deployment |
| **API 방식** | Chat Completions | Responses |
| **LiteLLM 연결** | 기존 SAP provider | Responses의 SAP 인증·배포 주소 연결 보완 |
| **앱 설정** | 기본 `chat-completions` | `sap-mixed`: GPT는 Responses, Claude는 기존 Chat |
| **추론 표시** | 해당 GPT 경로에서 미관측 | 공개 요약을 반환한 요청에서 확인 |

**LiteLLM이 Responses API 자체를 지원하지 않았다는 뜻은 아니다.** 기존 기능에 이번 SAP native 배포의 인증·주소 연결을 보완한 것이다. Chat 요청 후 같은 질문을 Responses로 한 번 더 보내는 이중 호출 방식도 아니다.

**이번 결과를 SAP 전체의 영구적 제한으로 일반화하지 않는다.** 당시 모델·배포·설정에서 확인한 결과다.

## 5. 로컬에서는 어디까지 검증했나?

**아래는 기존 5번 문서와 저장소의 2026-09-29 검증 기록을 요약한 것이다.** 이번 문서 작성 중 API나 E2E를 다시 실행한 것은 아니다.

| 검증 | 기록된 결과 | 한계 |
| --- | --- | --- |
| **실제 API** | Claude 3종 15개, GPT Responses·Tool·Chat bridge 9개 시나리오 통과 | 운영 컨테이너 검증은 아님 |
| **브라우저 E2E** | 6종 모델의 검색·선택·후속 질문·최종 답변 및 추론 표시 확인 | 모든 요청이 텍스트를 보내는 것은 아님 |
| **완료 전 실시간 표시** | Sonnet·Haiku의 화면에서 텍스트 증가 확인 | 나머지 4종은 같은 시점 증거까지 확보하지 못함 |
| **check·lint·knip** | 통과 기록 | 전체 회귀 통과와 구분 |
| **전체 Vitest** | 4,404 통과 / 34 실패 / 25 skip / unhandled error 1 | Windows·실행 환경 관련 실패가 남아 전체 성공 아님 |

**로컬에서 해결됨 ≠ 운영에 적용됨.** 이 구분이 이후 배포 작업이 필요했던 이유다.

## 6. 왜 GitHub 머지만으로 끝나지 않았나?

**ZEN AI 앱 이미지와 LiteLLM 이미지는 별도로 실행**된다. 앱 코드를 머지해도 운영 LiteLLM이 기존 공식 이미지라면 어댑터 패치는 반영되지 않는다.

운영의 초기 읽기 전용 Ops 결과에서는 **LiteLLM 1.92.0**, GPT URL 3개 **UNSET**, 모델 provider **sap**, 앱 API **기본 chat-completions**가 관측되었다. 버전 번호만으로 패치 유무를 판정할 수는 없으므로 이미지 ID와 구성도 함께 봐야 한다.

**주소·인증정보는 이미지에 내장하지 않았다.** GitHub Secrets는 GPT URL 3개를 운영의 `.env.litellm`에 전달하기 위한 수단이었고, 기존 인증·DB·콜백은 서버 설정을 보존하는 방향이었다.

[편집 가능한 Excalidraw 원본](Excalidraw/운영_반영과_해시_중단_지점.excalidraw)

| 단계 | 목적 | 당시 상태 |
| --- | --- | --- |
| **운영 읽기** | 실제 이미지·모델·환경 설정 파악 | Ops/SSM으로 조회 |
| **URL 전달 준비** | GPT 배포 주소 3개를 GitHub Secrets에 등록 | 사용자 등록 진행 |
| **URL 적용 사전 검사** | 기존 실행 구성과 Compose 일치 확인 | **해시 불일치로 중단** |
| **URL 적용·재생성** | 운영 환경파일 반영 후 LiteLLM 재기동 | 마지막 실패 실행에서는 도달하지 않음 |
| **이미지·경로 전환** | 패치 이미지와 GPT Responses 구성 반영 | 성공 확인 없음 |
| **운영 호출 확인** | 실제 추론 표시 확인 | 최종 완료 판정 불가 |

## 7. 배포 작업과 진단이 늘어난 과정

**당초 이미지 교체에 GPT URL 등록·모델 경로 전환·환경 보존·복구가 결합되면서 작업 범위가 커졌다.** SSH 직접 접근 대신 기존 GitHub Actions의 AWS OIDC·SSM 경로를 이용했다.

| 기준 PR | 추가한 내용 | 이유 |
| --- | --- | --- |
| **#224** | 배포 확장 전 비교 기준 | 이후 기존 배포 복원 기준으로 지정 |
| **#225** | SAP 호환 이미지·모델 연결, 운영 조회 | 로컬 수정과 운영 상태 확인 |
| **#226** | 조건부 LiteLLM 자동 배포 연결 | 앱 머지와 별개인 이미지 교체 연결 |
| **#227** | SSM 기반 GPT URL 적용·복구 | 서버에 직접 로그인하지 않고 환경 반영 |
| **#228** | 실패 단계·오류 코드 표시 | 숨겨진 실패 지점 식별 |
| **#229** | 설정 항목별 불일치 진단 | 전체 해시 차이를 항목별로 좁힘 |
| **#230** | 환경변수별 비교 상태 | 어떤 설정 범주가 다른지 확인 |
| **#231** | Compose 달러 이스케이프 오탐 수정 | 인증키가 다르다는 진단의 표현 차이 보정 |

**반복 머지와 CI·배포 실행은 시간과 비용을 늘렸다.** 다만 각 진단 추가는 운영 적용 성공을 의미하지 않는다. 마지막까지 실패한 지점은 모델 호출이 아니라 **적용 전 구성 검사**였다.

## 8. “해시 값 충돌”의 정확한 의미

### 8-1. 충돌이 아니라 불일치

**해시 충돌**은 서로 다른 입력이 같은 해시가 되는 현상이다. 이번에는 아래 두 해시가 **달라서 중단**했으므로 정확한 표현은 **구성 해시 불일치(config drift)**다.

| 비교 대상 | 의미 |
| --- | --- |
| **Compose가 계산한 해시** | 지금 파일·환경을 읽어 계산한 LiteLLM 서비스 구성 |
| **컨테이너의 config-hash 라벨** | 실행 중 컨테이너를 만들 때 기록한 Compose 구성 해시 |

**검사의 의도는 이미지 외의 설정 변경을 함께 적용하지 않도록 막는 것**이었다. 기존 인증정보·명령·마운트 등이 달라진 상태에서 컨테이너를 재생성하면 예상하지 못한 변경이 섞일 수 있기 때문이다.

### 8-2. 인증키 불일치처럼 보인 오탐

**한때 `AICORE_CLIENT_SECRET`이 다르다고 표시되었지만, Compose JSON의 달러 기호 표현 차이가 진단을 왜곡할 수 있었다.**

예를 들어 비교용 JSON에서는 리터럴 `$`가 `$$`로 표현될 수 있다. 이를 실행 컨테이너 값과 그대로 비교하면 같은 의미의 값도 다르다고 판단할 수 있어, **Compose 비교값에서만 한 번 정규화**하도록 수정했다.

**실제 키나 환경파일의 따옴표·역슬래시를 임의로 삭제한 것은 아니다.** 파서와 `env_file: format: raw`의 규칙이 다르므로 “따옴표는 언제나 사라진다”는 식의 일반화도 피해야 한다.

### 8-3. 오탐 수정 후에도 남은 불일치

**#231 이후 마지막으로 제공된 실행 결과**에서는 다음과 같이 나타났다.

| 비교 항목 | 결과 |
| --- | --- |
| **Compose 버전** | same |
| **이미지** | same |
| **비교 대상 환경변수** | same |
| **command** | same |
| **entrypoint** | **unknown** |
| **비교 대상 마운트** | same |
| **최종 검사** | **LITELLM_CONFIG_DRIFT** |

**`unknown`은 다르다는 증거가 아니라 비교로 확정하지 못했다는 뜻**이다. 또한 이 진단은 전체 서비스 설정을 모두 비교하지 않는다. 따라서 표시된 항목이 같다고 해서 전체 해시까지 같아야 한다고 결론 내릴 수 없다.

**최종 원인은 미확정이다.** Compose의 표현·기본값·생성 시점 설정 등 추가 후보를 검토할 수 있지만, 어느 하나를 실제 원인으로 입증하지는 못했다. 로컬 합성 환경에서는 같은 불일치를 재현하지 못했다는 이전 조사 기록도 있다.

## 9. 마지막 상태와 방향 전환

**마지막 URL 적용 실패는 `prepare` 단계의 `compose_config` 검사에서 발생**했다. 그 실행에서는 URL 쓰기·LiteLLM 재시작·이미지 교체 단계로 넘어가지 않았다. 이를 “새 이미지가 올라갔는데 추론이 안 된다”로 해석하면 안 된다.

예산과 반복 배포 부담 때문에 이후 다음 방향을 제안했다.

- **GPT URL 등록·전환과 복잡한 배포 확장을 제거**
- **#224 기준의 기존 CI·Deploy·Ops를 최대한 복원**
- **Claude 호환 패치를 포함한 LiteLLM 이미지만 별도 수동 workflow로 배포**
- **다음 앱 배포에서 이미지가 되돌아가지 않도록 이미지 참조 유지**
- **기본 기동 확인·실패 시 이미지 복구는 유지**

**이 방향은 제안 상태다.** 사용자 피드백 수집 업무로 전환하면서 구현은 중단했으며, 복원·삭제·새 수동 배포가 완료됐다고 기록하지 않는다.

## 10. 이 기록에서 기억할 점

**첫째, “텍스트가 안 보인다”는 한 증상에도 여러 계층의 원인이 있다.** 모델의 제공 여부, API 경로, 어댑터 변환, SDK 이벤트, UI를 나눠서 확인해야 한다.

**둘째, 로컬 검증과 운영 적용은 별도의 완료 기준이다.** 수정 코드를 머지했다는 사실만으로 운영 컨테이너가 교체되지는 않는다.

**셋째, 진단 오탐을 고친 것과 배포 차단 원인을 해결한 것은 다르다.** 달러 기호 비교는 보정했지만 전체 구성 해시 불일치는 남았다.

**최종 결론:** 모델별 호환성 개선은 로컬에서 확인했으나, 운영 반영은 구성 해시 검사에서 막혔다. **운영 추론 표시까지 해결됐다고 볼 수 없는 상태에서 작업을 보류**했다.
