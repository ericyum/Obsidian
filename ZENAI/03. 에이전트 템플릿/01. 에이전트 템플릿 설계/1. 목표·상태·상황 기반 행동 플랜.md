# 에이전트 템플릿화 — 목표·상태·상황 기반 행동 플랜

> **우선순위 변경 · 2026-10-02:** 당장은 스킬·백그라운드 확장과 템플릿 구현을 보류한다. [[4. 회의 Builtin의 DB 업무 로직과 개선 범위]]를 기준으로 회의 Builtin의 DB/코드 책임 재배치에 대한 상세 구현 계획을 먼저 세우고, 로컬 회귀 검증 후 다음 기능을 재개한다. 아래는 장기 로드맵이며 이 우선순위가 앞선다.

갱신: **2026-10-01 · Builtin 선행 검증·스킬 저장 합의 반영**

> **범위:** 목표와 조사·설계·검증 순서를 정하는 행동 플랜이다. 바로 실행할 상세 구현 지시서는 아니다.
> 이전 문서와 충돌하면 **이번 회의 결과를 반영한 이 문서가 우선**한다. 2~4번 문서는 조사 근거로 남기되 과거 다중 Agent 관계·실행 설계 제안은 이번 범위에 적용하지 않는다. **4번 문서의 ‘기존 Builtin 유지·신규 템플릿부터 적용’ 순서는 이번 합의로 변경한다.** 책임 분리 원칙은 유지하되 회의 Builtin을 로컬에서 먼저 정리·검증한다.

## 1. 목표

**기존 고객사 기능을 보존하면서, 개별 Agent를 설정으로 생성하고 기존 실행 기반에 필요한 기능만 연결하는 템플릿을 만든다.**

- **기존 기능 보존:** 파마리서치의 Agent 생성·편집·호출·권한·대화·실행을 유지한다. 기존 데이터 일괄 전환을 강제하지 않는다.
- **개별 호출 유지:** 사용자가 원하는 Agent를 기존처럼 **@로 호출**한다. 별도 오케스트레이션 호출 대상으로 대체하지 않는다.
- **공통 기반 재사용:** 기존 정의·버전·모델·MCP·문맥·실행 큐를 우선 활용하고, Builtin에서 얻은 기능 중 부족한 것만 연결한다.
- **템플릿 설정:** 기본 모델·지침·Tool·실행 제한에 **백그라운드 허용 여부**와 **SKILL.md 기반 스킬 설정**을 포함한다.
- **실행 기능:** 필요한 HITL 대기·재개·취소, 실패·시간 초과, 일반 처리 Trace를 지원한다. 업무별 처리는 해당 Tool·업무 코드가 맡는다.
- **Builtin 선행 검증:** 회의 Builtin의 업무 로직을 적절한 코드로 옮기고 스킬을 적용해 검증한 뒤, 템플릿으로 생성한 Agent에서 다시 검증한다.
- **스킬 이해:** 구현 전에 스킬의 발견·선택·본문 로딩·실제 행동 반영 과정을 이해할 수 있는 학습 자료와 예시를 확보한다.

**완료 기준:** 신규 설정으로 만든 Agent가 정상 실행되고 기존 고객사 경로가 보존됨을 통합·브라우저 E2E로 확인한다. 스킬과 백그라운드 설정도 실제 실행 계약에 맞게 검증한다.

## 2. 상태

### 확인한 기반

- **저장:** 일반 Agent는 `agents`에 현재 정의, `agent_versions`에 버전별 정의를 저장한다. 사용 권한·MCP 연결·허용 모델·개인 설정은 분리되어 있다.
- **실행:** 일반 worker에 모델·Tool 조립, 문맥, `ask_user`, task/slice, 게시·종료 기능과 선택적 연결 지점이 있다. 실행 엔진 전체를 새로 만들 필요가 있다고 단정하지 않는다.
- **DB 경계:** 일부 업무 판단·문구·checkpoint 해석이 SQL 함수에 있다. 회의 Builtin부터 이전 대상을 확정해 판단을 코드에 두되 권한·잠금·CAS·원자적 저장 보장은 유지한다.
- **기존 조사:** 3번 현재 책임 조사와 4번 DB 이전 경계 문서는 재사용한다. 정적 조사이지 실제 이전 완료나 운영 검증 결과는 아니다.
- **관측:** 사용자 실시간 Trace는 메모리 기반이고 관리자 실행 이력은 별도 DB 저장이다. **LLM 추론 텍스트는 운영 미표시 상태로 보류**한다.
- **검증:** 이번 재작성에서 테스트를 실행하지 않았다. 과거 결과만으로 현재 전체 기능의 통과를 전제하지 않는다.

### 새 요구와 미확정 사항

| 항목 | 상태 |
| --- | --- |
| **백그라운드 허용 여부** | 별도 설정 테이블로 관리한다. 작업 실행·상태·완료 기능은 동료 구현과 연동하며 중복 개발하지 않는다. |
| **스킬 설정** | MD 파일은 별도 저장소에, 위치·버전·접근 범위는 DB에 둔다. Agent–스킬 연결로 선택을 관리한다. Builtin도 스킬을 사용한다. |
| **커맨드와 스킬** | `/meeting-start`는 커맨드다. 커맨드가 스킬을 시작하게 할 수는 있지만 둘은 같은 개념이 아니다. |
| **실행 방식 구분** | `execution_mode = NULL`이면 기존, `'harness'`이면 신규라는 안을 검토 중이다. 현재 구현된 컬럼은 아니다. |
| **조립 방식** | 기존 기반에 필요한 기능만 연결하는 방향이 유력하다. HITL·상태·종료 계약의 호환성을 확인해야 한다. |

## 3. 상황

### 고객사 호환성과 범위

- 기존 코드를 지우고 재구축하지 않는다. **신규 방식 선택이 기존 Agent 동작을 바꾸지 않아야 한다.**
- 생성 화면에서 기존/신규 방식을 구분하되, 화면 구분이 실행 엔진 전체 복제를 의미하지 않는다.
- 기존 `version`·`agent_versions` 기반을 우선한다. Builtin release·epoch를 그대로 이식하지 않는다.
- 적용된 migration을 수정·삭제하지 않는다. 필요하면 새 migration을 추가하고 구버전 서버·worker와의 호환성을 검토한다.
- Agent 간 관계·분기·결과 취합을 설정하는 오케스트레이터나 그래프 편집기는 만들지 않는다.
- **Subagent는 필요한 Tool이 외부에서 실행하도록 개발한다.** 템플릿 서버에 별도 subagent 실행기를 추가하지 않는다. Tool 내부 구현과 호출자가 받는 결과·상태 계약을 구분한다.
- Provider는 SAP에 고정하지 않는다. 기존 인증·MCP·사용자·community 권한 경계를 보존한다.

### 백그라운드 설정

- 템플릿에 **‘백그라운드 허용 여부’** 항목을 추가하고 **별도 설정 테이블**에 저장한다. 이 설정을 위해 기존 Agent 테이블에 boolean 컬럼을 추가하지 않는다.
- 기존 일반 실행 경로는 신규 설정 조회를 강제하지 않는다. 신규 템플릿의 설정 누락은 허용하지 않는 방향으로 설계하되, 기존 Builtin의 background 동작을 무심코 차단하지 않도록 적용 범위를 구분한다.
- 허용 설정과 실제 background 작업 기록은 별개다. Agent 정의 버전과의 연결, 실행 중 설정 변경의 의미를 정한다.
- 목표 UX는 Tool이 실제 작업을 시작했을 때 스레드에 **“현재 ○○ 작업이 백그라운드에서 실행 중입니다.”**와 같은 안내가 표시되는 것이다.
- Tool 정의의 설명은 기능 이해에 사용한다. **설명만 보고 실제 실행이 시작됐다고 단정하지 않는다.** 접수·상태·완료를 확인하는 응답이나 이벤트는 동료 구현과 맞춘다.
- **허용 설정은 실행 정책**, Tool의 background 특성은 기능 정보다. 둘을 구분한다.
- 현재는 항목·저장 방향을 계획에 반영한다. 신규 생성 기본값과 금지 시 Tool 노출·호출 처리는 동료 구현과 맞춘다. 별도 background 엔진을 만들지 않는다.

### 스킬 설정

- **스킬은 SKILL.md와 필요한 참조 문서·스크립트·자료로 구성되는 절차 지식**이다. Tool은 실제 작업 수단이고 커맨드는 요청을 시작하는 입력 방식이다.
- 파일이 있다고 모델이 저절로 읽거나 실행하지 않는다. 호스트가 사용 가능한 목록을 제공하고 필요한 본문·자료를 읽을 수 있게 해야 한다.
- 전형적인 흐름은 **목록 제공 → 관련 스킬 선택 → SKILL.md 읽기 → 필요한 참조 읽기 → 허용된 Tool로 절차 수행**이다. ZEN AI에 이미 이 흐름이 구현됐다는 뜻은 아니다.
- 스크립트를 포함한 스킬에도 자동 실행 권한을 부여하지 않는다. 기존 사용자·community·Tool 권한을 넘지 않게 한다.
- **재사용 스킬:** 미리 저장된 SKILL.md를 화면에서 체크해 연결한다. 선택할 때마다 파일을 복사하거나 Agent별 묶음을 새로 생성하지 않는다.
- **Agent 특화 스킬:** 직접 작성해 MD로 저장하고 같은 방식으로 연결한다. 공용/전용을 별도 시스템으로 나누지 않고 접근·공유 범위로 구분한다.
- **저장 구분:** 스킬 테이블은 이름·파일 위치·버전·접근 범위, 연결 테이블은 Agent와 선택한 스킬 버전을 관리한다. 정확한 테이블명·키는 조사 후 정한다.
- **Builtin 연결:** 일반 agents.id만 전제한 외래 키로 만들지 않는다. 기존 principal 구조 등 일반/Builtin 모두를 안전하게 식별할 방법과 각 정의 버전의 연결을 검토한다. Builtin release 체계를 일반 Agent에 복제하지 않는다.
- 파일은 서버·worker에서 접근 가능한 저장소에 둔다. 기존 버전을 덮어쓰지 않고 파일 생성 실패·DB 연결 실패·없는 파일 참조를 처리한다. 저장소 종류와 세부 로딩 방식은 아직 미정이다.
- 체크는 해당 스킬의 사용 가능 범위를 정하는 것이지 매 요청마다 모든 본문을 주입한다는 뜻이 아니다. 본문은 필요한 경우 읽고, Tool 권한은 별도로 확인한다.

## 4. 행동 플랜

**진행 순서:** 조사·계약 확정 → 회의 Builtin 리팩터링·스킬 적용 → 로컬 Builtin 검증 → 템플릿 조립·화면 구현 → 생성된 Agent 재검증.

**구현 공통 조건:** 각 구현 단계 전에 수용 기준과 기준↔테스트 매핑을 작성한다. src 동작 변경은 별도 우회 지시가 없다면 `intents/TEMPLATE.md`와 저장소 harness 절차를 따른다. 로컬 구현·검증과 운영 배포를 구분하며, 이 문서는 운영 변경이나 커밋·머지의 자동 실행 지시가 아니다.

### 1단계. 스킬을 학습하고 기존 구현·회귀 기준을 확인한다

- [ ] 커맨드·시스템 프롬프트·Tool·스킬의 차이를 예시로 설명한다.
- [ ] **목록 제공 → 선택 → SKILL.md 읽기 → 참조 읽기 → Tool 실행**에서 모델과 호스트 코드가 각각 하는 일을 보여 준다.
- [ ] `src/lib/agent-workspace/skills.ts` 등 기존 구현이 실제 파일 로딩인지 지침 문자열인지 확인한다.
- [ ] 회의 Builtin의 현재 SQL·코드 호출자를 3·4번 문서와 대조해 이전 대상을 갱신한다. 조사 전체를 처음부터 반복하지 않는다.
- [ ] 변경 전 로컬 테스트와 핵심 브라우저 시나리오의 기준 결과를 확보한다. 기존 실패와 새 회귀를 구분하고 실제 Provider/DB 테스트 대상이 로컬·시험 범위인지 확인한다.
- **산출물:** 스킬 학습 문서, 현재 구현 대비 부족한 기능, Builtin 이전 후보와 변경 전 검증 결과.

### 2단계. DB·코드·스킬 책임과 저장 계약을 확정한다

- [ ] 함수별로 **기존 SQL → 옮길 코드 파일/함수 → 유지할 DB 보장 → 대응 테스트**를 명시한다.
- [ ] 업무 판단·표시 문구·단계 해석은 코드로, 작업 절차 지침은 스킬로 나눈다. 권한·입력 검증·잠금·CAS·중복 방지·원자성은 지침 문장으로 대체하지 않는다.
- [ ] 스킬 파일 저장소·등록/수정·버전·공유 범위와 Agent–스킬 연결을 설계한다. 일반/Builtin 양쪽의 식별·버전 참조를 검증한다.
- [ ] 백그라운드 허용은 별도 설정 테이블로 설계하고 동료의 작업 기록 테이블·엔진을 재사용한다. 설명이 아닌 실제 접수 결과에 근거한 안내 계약을 맞춘다.
- [ ] 기존 Agent의 새 설정 미존재와 신규 템플릿의 설정 누락을 구별한다. 실행 중·HITL 대기 중 설정/스킬 변경과 권한 회수 정책을 정한다.
- [ ] 필요한 새 migration과 단계적 적용·롤백 조건을 정한다. 과거 migration을 수정·삭제하지 않는다.
- **산출물:** 파일별 책임 이전표, 스킬·background 저장 계약, Builtin 변경 의도와 검증 기준.

### 3단계. 회의 Builtin의 업무 로직을 코드로 옮기고 스킬을 적용한다

- [ ] 이전 대상별 회귀 테스트를 준비하고 검증 기준을 확인한 뒤 최소 변경한다.
- [ ] SQL의 업무 분기를 적절한 기존 adapter·engine·Tool 코드로 옮긴다. 새 파일은 책임 분리에 실제 필요한 경우만 만든다.
- [ ] 응답 게시·상태·checkpoint·종료의 원자성과 claim fencing을 보존한다. 종료 처리를 이중으로 수행하지 않는다.
- [ ] 회의 업무에 필요한 SKILL.md와 참조 자료를 작성한다. 모든 코드를 스킬 문장으로 치환하거나 장문의 지침을 중복 주입하지 않는다.
- [ ] Builtin에 사용 가능한 스킬 목록·본문 로딩을 연결하고 파일/권한 오류 처리를 구현한다. 커맨드 동작과 스킬 적용을 구분한다.
- [ ] 기존 Builtin release/config 검증을 보존하며 필요한 버전 변경을 정식 경로로 처리한다. 일반 Agent에 이 구조를 복제하지 않는다.
- **산출물:** 로컬에서 동작하는 리팩터링된 회의 Builtin과 실제 스킬 파일·연결. 템플릿 구현은 아직 진행하지 않는다.

### 4단계. 로컬 회의 Builtin을 먼저 검증한다

- [ ] 검색·선택·추가/대체·취소·후속 질문·최종 답변을 통합·브라우저 E2E로 확인한다.
- [ ] 스킬 목록 제공·본문 로딩·참조 이용을 관찰 가능한 근거로 확인한다. 답변이 그럴듯하다는 이유만으로 스킬 사용 성공으로 판단하지 않는다.
- [ ] 스킬 파일 누락·권한 거부·복수 스킬 충돌·버전 변경, HITL 재개·시간 초과·실패를 검증한다.
- [ ] 상태 경합·중복 요청·stale worker·권한 회수·게시 rollback과 기존 일반 Agent 회귀를 검증한다.
- [ ] 일반 처리 Trace와 Tool 구조 표시를 확인한다. 추론 텍스트 미표시는 실패 조건으로 두지 않는다.
- [ ] 녹음 제어와 전사 외부 연동을 구분한다. 로컬 전사 제약은 대역/실제 검증 범위를 따로 보고한다.
- [ ] 게이트 **check·lint·knip·vitest**와 통합·브라우저 결과를 기록한다.
- **다음 단계 조건:** 변경으로 생긴 회귀를 해결하고 미검증·기존 실패를 명시한다. Builtin 검증이 안 된 채 템플릿까지 동시에 바꾸지 않는다.

### 5단계. 검증된 기반으로 템플릿 조립·저장·화면을 확정한다

- [ ] `runAgentTurn`·`createWorkerDependencies`·`startAgentStream`에서 재사용 가능한 연결 지점을 선정한다.
- [ ] Builtin에서 검증한 기능 중 기존 일반 Agent에 없는 부분만 연결한다. `ask_user`·task/slice를 중복 구현하지 않고 회의 전용 상태도 범용으로 복사하지 않는다.
- [ ] 부족할 때만 좁은 신규 조립 진입점을 만든다. worker 전체 복제나 플러그인 프레임워크를 먼저 만들지 않는다.
- [ ] 기존 `agents`·`agent_versions` 기반을 검토한다. **NULL = 기존 / harness = 신규** 안은 background 설정 분리와 별개의 실행 식별 결정으로 검증한다. 채택 시 정의 버전에도 반영한다.
- [ ] 새 실행 식별·설정이 이전 worker에서 잘못 처리되지 않도록 호환 배포 순서를 정한다. 알 수 없는 값이나 신규 필수 정보 누락은 기존 방식으로 조용히 대체하지 않는다.
- [ ] 화면에 기본 설정·Tool·스킬 체크·특화 스킬 작성/연결·**백그라운드 허용 여부**를 반영한다.
- [ ] 2번 화면 시안의 과거 방향을 별도 작업으로 갱신한다. 이번 문서 수정에서 다른 문서를 자동 변경하지 않는다.
- **산출물:** 템플릿 조립 구조·저장/버전 계약·화면 시안·상세 구현 의도와 테스트 매핑.

### 6단계. 로컬 템플릿을 구현하고 화면에서 Agent를 생성한다

- [ ] 합의한 저장·조회·버전·분기·스킬 연결·화면을 구현한다. 기존 고객사 데이터나 실행 방식의 일괄 전환은 하지 않는다.
- [ ] 준비된 공용 스킬을 체크해 연결하고 Agent 특화 스킬을 작성해 저장한다. 기존 공용 파일을 Agent별로 복제하지 않는다.
- [ ] 화면에서 회의 업무용 Agent를 실제 생성한다. DB 수동 입력만으로 생성 검증을 대신하지 않는다.
- [ ] 동료 기능과 연결 가능한 범위에서 background 허용을 적용한다. 아직 미연결이면 설정 저장과 대역 검증까지만 완료로 표시한다.
- **산출물:** 템플릿으로 생성된 테스트 Agent와 설정·파일·버전 연결 증거.

### 7단계. 생성된 Agent로 동일 시나리오를 재검증한다

- [ ] 4단계의 회의 검색·선택·후속 질문·최종 답변 시나리오를 생성된 Agent로 다시 수행한다.
- [ ] Builtin과 신규 Agent가 같은 업무 요구를 충족하는지 비교한다. 내부 구현이나 모델 문구의 완전 일치가 기준은 아니다.
- [ ] 스킬 선택/미선택·본문 로딩·파일 누락·접근 거부·특화 스킬·버전 변경을 검증한다.
- [ ] background 허용/금지·접수 실패·실제 접수 후 안내·완료 연동을 검증한다. 대역과 실제 연동 결과는 구분한다.
- [ ] 기존 일반 Agent 생성·편집·@ 호출·개인 설정·MCP·응답을 다시 검증하고 사용자·community 격리와 동시 실행도 확인한다.
- [ ] 게이트 4종·통합·브라우저 E2E 결과를 정리한다. 테스트를 위해 기존 고객사 데이터나 운영 설정을 변경하지 않는다.
- **완료 조건:** Builtin 선행 검증과 템플릿 생성 후 검증을 각각 통과하고, 기존 고객사 기능 보존을 입증한다. 미검증 외부 연동은 완료에 포함하지 않는다.

**바로 다음 행동:** 스킬 학습·현재 구현·변경 전 회귀 기준을 확인하고, 회의 Builtin의 파일별 이전 계획을 확정한다. 이 문서 수정만으로 구현·migration·배포를 시작하지 않는다.
