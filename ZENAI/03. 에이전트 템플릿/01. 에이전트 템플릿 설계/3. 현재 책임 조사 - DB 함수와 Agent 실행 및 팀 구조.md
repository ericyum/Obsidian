# 1단계 조사 — DB 함수·일반 Agent·팀의 현재 책임

> **조사일:** 2026-10-01 · **기준 커밋:** `51e6eae999f409fade4a6f81bb63a2c4afa1a5da`
> **연결:** [[1. 목표·상태·상황 기반 행동 플랜]] · [[2. 에이전트 템플릿 방식 선택과 화면 시안]]
> **범위:** 저장소의 SQL 이력·호출 코드·테스트 소스에 대한 읽기 전용 조사.
> **한계:** 운영 DB의 실제 함수 정의·마이그레이션 적용 여부, 실제 모델 호출, 브라우저 E2E는 이번 조사에서 확인하지 않았다. 테스트는 **존재와 검증 의도**를 읽은 것이며 새로 통과시킨 결과가 아니다.

## 1. 결론부터

**새 템플릿은 빈 바닥에서 만들 필요가 없다.** 일반 Agent에는 이미 생성·버전·개인 설정·MCP·되묻기·작업 이어가기 경로가 있다. 회의 Builtin에는 별도의 claim·operation·checkpoint·HITL 보호 경계가 있다. 다만 **두 경로가 같은 범용 계약으로 완성되어 있지는 않다.**

| 핵심 발견 | 템플릿화에 주는 의미 |
| --- | --- |
| **DB 함수에 업무 규칙과 안전장치가 함께 들어 있다** | 업무 판단은 코드로 옮길 후보지만, 잠금·권한·원자적 저장까지 없애면 안 됨 |
| **일반 Agent에도 ask_user·작업 slice가 있다** | “HITL은 Builtin에만 있다”는 전제로 복제하지 않음 |
| **현재 팀은 멤버 묶음과 채널 초대 중심이다** | 순차·상하·병렬 그래프와 값 전달은 기존 기능으로 간주할 수 없음 |
| **사용자 Trace와 관리자 실행 이력이 다르다** | 사용자 Trace는 메모리, 관리자 span은 DB. 저장 정책을 혼동하지 않음 |
| **회의 engine·Tool 계약은 업무별로 고정되어 있다** | 파일 이름을 바꾸는 것만으로 범용 템플릿이 되지 않음 |
| **일반 Agent의 version 기반이 이미 존재한다** | Builtin release·epoch 체계를 신규 일반 Agent에 복제할 이유가 없음 |

**이번 단계의 산출물은 책임 지도와 이전 후보 목록**이다. 실행 엔진 전체 분리나 DB 함수 삭제를 결정·구현한 문서가 아니다. **LLM 추론 텍스트는 미표시 상태로 보류**하며 조사·구현의 선행 조건으로 삼지 않는다.

## 2. 현재 책임 지도

![[현재_에이전트_책임_지도.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/현재_에이전트_책임_지도.excalidraw)

**공통 사용자 접점은 채널 메시지이지만, 실행 경로는 분리되어 있다.**

- **일반 Agent:** 메시지 → 일반 run 생성 → 일반 worker → 모델·MCP·작업 공간 조립 → 응답/되묻기/후속 slice.
- **Builtin:** 메시지 → executor별 enqueue → Builtin claim → 등록된 업무 adapter → operation/step → 게시·checkpoint 확정.
- **팀:** Agent 목록을 구성하고 채널에 초대하는 관리 기능. 위 실행 흐름을 자동 그래프로 연결하는 계층은 현재 확인되지 않았다.

**그림의 Trace·관리자 이력 박스는 저장 책임을 구분한 것**이며, 모든 Agent가 같은 상세 실시간 이벤트를 이미 발생시킨다는 뜻은 아니다.

## 3. 조사표 A — DB 함수가 맡고 있는 책임

### 3-1. 조사 방법과 읽기 기준

**마이그레이션 파일 자체는 배포 시 실행되지만, 그 안에서 생성한 함수·트리거는 요청 처리 중에도 실행된다.** “migration에 있으니 초기 설정 코드뿐”이라고 보면 실제 실행 책임을 놓친다.

이 조사에서는 **CREATE / CREATE OR REPLACE / RENAME / DROP을 순서대로 추적**했다. 아래 “최신 정의”는 **저장소의 마이그레이션을 정상 적용한 경우**를 뜻한다. 운영 DB 카탈로그를 직접 확인한 결과는 아니다.

**예외적으로 이름만 검색하면 틀리는 부분:**

| 항목 | 올바른 해석 |
| --- | --- |
| `app_worker_sap_context` | 0047에서 기존 본문을 `app_worker_sap_base_context`로 바꾸고 wrapper 추가. base는 0056에서 갱신 |
| `app_worker_background_delivery_context` | 0091에서 기존 본문을 `..._base`로 바꾸고 최신 retry를 검사하는 wrapper 추가 |
| `app_trace_*` | 0085에서 사용자 Trace 함수 10개와 테이블 2개 삭제. 과거 정의를 현재 함수로 세면 안 됨 |
| `app_meeting_worker_claim_meeting` | 녹음·전사/회의록 재생성 worker용. 채팅 Agent의 Builtin claim과 다른 실행계 |

**이하 경로는 저장소 루트 기준**이다. SQL 파일은 번호로 축약했으며 전체 파일명은 마지막 근거 목록에 정리했다.

**일반 Agent의 동시성은 채널 전체가 아니라 thread 기준**이다. 0086의 canonical conversation key 트리거와 running partial unique index가 이를 보장한다. 따라서 신규 경로를 추가하면서 같은 thread에 두 실행이 겹치지 않는지도 검증해야 한다.

**HITL 전체가 DB 함수에 있는 것은 아니다.** 선택 문구, 번호 해석, 추가/대체 판단, 만료·취소·재개 흐름은 `meeting-tool.ts`와 `engine.ts`에도 있다.

현재 회의 HITL은 대략 **Tool 상태 저장 → 답변 게시와 실행 경계 확정 → 다음 사용자 메시지에서 새 run → 이전 checkpoint와 pending token으로 재개**한다. 실패 시 pending token을 미리 소비하지 않도록 지연 완료 처리도 있다.

**“그냥 메모리에 상태를 두면 된다”는 결론은 Trace에만 해당**한다. HITL·checkpoint·업무 상태는 실행 정확성을 위한 데이터이므로 Trace 메모리와 별개다.

### 3-7. 코드 이전 후보와 DB 보장 유지 — 2단계 입력자료

| 코드로 구현할 후보 | 함께 보존해야 할 DB 보장 |
| --- | --- |
| 표시 문구·회의 검색 조건·업무 phase 전이 | 권한을 통과한 데이터만 읽기 |
| HITL payload·checkpoint의 업무별 schema | expected version CAS, token·scope 검사 |
| 모델/Tool·재시도·스케줄 정책 계산 | snapshot 위조 차단·중복 방지·잠금 |
| 다음 단계 선택·출력 정규화 | checkpoint와 재큐잉의 원자성 |
| 응답 내용 생성 | 응답 event·run terminal·cursor의 원자성 |

**DB 보장 유지란 반드시 기존 함수 본문을 그대로 남기라는 뜻은 아니다.** 코드+transaction+제약조건으로 같은 성질을 보존할 수 있는지 검토하되, 현재 restricted worker 권한이 SECURITY DEFINER 함수를 통해서만 가능한 작업까지 단순 ORM 호출로 바꿀 수 있다고 가정하면 안 된다.

### 4-2. version은 무엇을 기록하나?

**agents.version과 agent_versions는 이미 정의 이력을 관리한다.** 생성 시 초기 정의를 저장하고, updateAgent는 row lock·expectedVersion 검사 후 버전을 증가시키고 snapshot을 추가한다.

**모든 저장을 한 종류로 보면 안 된다.**

- **관리자 정의 수정:** 일반 Agent의 version 이력.
- **개인 설정:** 별도 preference 및 preference version 경로.
- **활성화·보관 상태:** 전용 변경 경로. 정의 version 증가와 동일하게 취급하지 않음.
- **실행:** enqueue 시 선택한 정의와 실효 설정을 snapshot으로 고정하는 경로.

따라서 새 방식 선택자는 **명시적 정의/실행 계약으로 설계**해야 한다. UI 토글 값만 전달하고 실행 시마다 현재 화면 설정을 읽는 식은 안전하지 않다.

**주의할 버전 경계:** 같은 작업의 다음 slice는 설정 snapshot을 계승하지만, 사용자가 되묻기에 답해 만드는 **새 run까지 이전 agentVersion을 유지한다고 단정할 수 없다.** 새 메시지는 현재 실효 설정을 다시 읽는 경로가 있다. 또 MCP assignment와 서버 활성 상태는 실행 시점에 확인하며, **Tool 할당이 agent_versions에 함께 고정된다는 근거는 없다.** 템플릿 버전 계약에서 두 지점을 명시해야 한다.

### 4-3. 기존 기능과 Builtin의 차이

| 기능 | 일반 Agent | 회의 Builtin | 조사 결과 |
| --- | --- | --- | --- |
| **사용자 되묻기** | 작업 공간 설정 아래 ask_user, 질문 게시·waiting_user·후속 메시지 | 회의 선택/추가/대체와 pending token | 둘 다 있으나 동일한 HITL 계약은 아님 |
| **실행 이어가기** | 작업 task·slice·문맥/작업 파일 | 회의 state·checkpoint·새 run | 일반 경로를 먼저 재사용 검토 |
| **Tool** | MCP 발견·허용 Tool 조립·작업 공간 Tool | 검색·질문·녹음 등 업무 union/분기 | Builtin Tool 파일 통째 복제 금지 |
| **시간 제한** | RUN_TIMEOUT_MS 600,000, 작업 공간 soft slice 90,000 | executor operation 상한 60,000 등 별도 예산 | 하나의 timeout이라고 설명하지 않음 |
| **전체 작업 예산** | task 기준 30분·Tool 100회 등 코드 정책 | 회의 maxRounds 및 Builtin deadline/operation | 신규 의미·기본값은 후속 설계 |
| **Provider** | OPENAI_BASE_URL/KEY + 사용자 키 선택 경로 | 회의 모델 연결 별도 API 선택 | 특정 SAP provider로 고정된 템플릿이 아님 |
| **관측** | 관리자 실행 span·기존 progress | 상세 사용자용 trace + 관리자 span | 상세 실시간 Trace 연결은 별도 확장 필요 |

**회의 engine은 아직 범용 상태 머신 엔진이 아니다.** 검색/질문/녹음/회의 pending schema가 직접 들어 있다. 반대로 일반 worker에도 Jira read 전용 빠른 경로 등이 있어, 기존 조립부를 그대로 “범용 템플릿 완제품”이라고 부를 수도 없다.

### 4-4. MCP·Tool 연결에서 이미 있는 것

### 4-5. Trace는 두 시스템으로 나누어 봐야 한다

| 구분 | 사용자용 실시간 Trace | 관리자 실행 이력 |
| --- | --- | --- |
| **코드** | src/lib/agent-trace/** | src/lib/agent-history/** |
| **저장** | 프로세스 메모리 Map, 재시작·보존 한도에 따라 소실 | agent_run_spans DB |
| **내용/목적** | 처리 단계·Tool 구조·사용자 관찰 | model/tool/phase/memory span·사용량·입출력 등 운영 조사 |
| **조회 권한** | community + channel + 호출자 + 메시지 접근 재확인 | 커뮤니티 관리자 SQL 조회 경계 |
| **이번 템플릿 방향** | 일반 단계·Tool 구조를 확장 후보로 사용, 추론 텍스트 보류 | 기존 고객사 기록 기능 임의 삭제 금지 |

**메모리 Trace 조회도 권한·메시지 존재 확인에는 DB를 사용**한다. Trace 이벤트 본문을 DB에 저장하지 않는다는 말과 DB를 전혀 사용하지 않는다는 말은 다르다.

0085는 **agent_trace_requests / agent_trace_events만 제거**했으며 agent_run_spans는 의도적으로 유지했다. 일반 Agent 호출은 현재 상세 live Trace의 unsupported 경로를 사용하고, Builtin runtime에는 공통 이벤트와 adapter별 이벤트가 있다. **회의 수준의 상세 Trace가 모든 Agent에 자동 적용된 상태는 아니다.**

| 구분 | 후보 | 이유 |
| --- | --- | --- |
| **우선 재사용** | 일반 정의/version, 정책 검증, 사용자/커뮤니티 권한, 모델 연결, MCP 허용 목록·인증 | 이미 고객사 경로에서 쓰는 기반 |

**잠정 방향은 “공통 기반 재사용 + 필요한 조립 경계만 분리 검토”**다. 3단계의 A/B/C 비교·선정은 아직 남아 있으며 이 조사로 특정 구조를 확정하지 않는다.

## 5. 조사표 C — 현재 Agent 팀의 관계·전달·재개

### 5-1. 현재 팀이 저장하는 것

**agent_teams는 팀 이름·설명, agent_team_members는 Agent ID·position을 저장**한다. teams.ts 입력 계약은 **name / description / agentIds**다.

**position은 멤버 표시 순서**이지 “앞 Agent가 끝나면 뒤 Agent 실행”이라는 의존 관계가 아니다. team CRUD는 Agent grant를 자동 생성하지 않으며, 멤버 선택은 같은 커뮤니티의 일반 agents를 기준으로 한다.

| 요구사항 | 현재 조사 결과 | 다음에 필요한 것 |
| --- | --- | --- |
| **멤버 관리·정렬** | 지원 | 기존 CRUD 보존 |
| **채널에 팀 초대** | 멤버 Agent 초대 편의 기능 | 기존 초대 권한·부분 실패 처리 보존 |
| **상하 위임·결과 회수** | 팀 실행 계약에서 확인되지 않음 | 호출·반환·권한·취소 전파 계약 |
| **선후 실행** | position으로 실행하지 않음 | 명시적 의존 edge·완료 조건 |
| **병렬·결과 취합** | 일반 worker의 동시성과 팀 fan-out/join은 별개 | branch·join·실패 정책 |
| **A.output → B.input** | typed mapping 저장/실행 경로 없음 | schema·매핑·크기/참조 전달 계약 |
| **팀 버전 고정** | 팀 정의 snapshot/version 실행 계약 없음 | 팀 실행 시작 시 정의·멤버 version 고정 |
| **팀 HITL 재개** | 개별 Agent의 대기 기능과 별개 | 어느 노드/branch에서 재개할지 저장 |
| **팀 취소·재시도** | 팀 전체 실행 모델 없음 | 중복 부작용·부분 완료·재시도 경계 |
| **팀 Trace** | 부모/자식 실행 연결 완료로 볼 수 없음 | 팀 실행 ID·노드 실행 ID·사용자 관찰 권한 |

**채널 대화를 문맥으로 읽는 것은 명시적 데이터 전달이 아니다.** A가 게시한 문장을 B가 나중에 읽을 수 있는 경우에도, 타입 검증·호출 순서·완료 확인·정확한 입력 필드 매핑을 보장하지 않는다.

**실제 호출 예시:** 사용자가 A에게 질문 → A가 답변 → 사용자가 같은 스레드에서 B에게 “위 결과를 정리해줘”라고 질문하면 B는 앞선 답변을 문맥으로 받을 수 있다. 반면 **하나의 메시지에서 A·B를 동시에 멘션**하면 문맥은 각 trigger 시점까지로 제한되므로, A가 먼저 끝나도 그 새 결과가 B의 입력으로 자동 연결되지 않는다.

**현재 코드에 Agent 간 delegate/subagent 실행기는 확인되지 않았다.** channels/messages.ts는 actor가 user가 아니면 enqueue 전에 반환한다. Agent가 답변에 다른 Agent를 멘션해도 자동 위임 run을 만들지 않는다. 팀 position이 아닌 큐의 createdAt/id와 thread 동시성 정책이 실행 순서에 영향을 준다.

**근거:** src/lib/ui/agent-teams.ts의 deployTeamToChannel은 각 멤버를 기존 채널 members API로 초대하고 개별 성공·실패를 집계한다. 이 함수의 Promise.all은 초대 요청 병렬 처리이지 팀 업무 병렬 실행이 아니다.

### 5-2. Agent 간 권한은 전달값으로 확장되지 않는다

**상위 Agent가 읽을 수 있었던 자료라고 해서 하위 Agent도 자동으로 읽을 수 있는 것은 아니다.** 현재 커뮤니티·채널·사용자 MCP subject 경계를 그대로 지켜야 한다.

다음 단계에서 **원문 직접 전달 / 권한 검증 가능한 참조 전달**, **공유 데이터 / 개별 Agent State / Tool 내부 상태**를 나눠 결정해야 한다. 팀 이름을 만들었다는 이유로 모든 context를 공유하거나 사용자 인증을 다른 Agent에 넘기는 방식은 현재 코드의 보호 경계와 맞지 않는다.

### 5-3. 화면 시안과 현재 구현의 차이

**2번 문서의 관계·전달값 화면은 목표 시안이지 현재 기능이 아니다.** 팀 화면에 토글만 추가한다고 해당 실행 구조가 생기지 않는다. **단독 Agent 안정화 후 최소 순차 관계부터** 필요 범위를 확정하는 편이 기존 계획과 일치한다.

## 7. 다음 단계에 넘길 결정 항목

**1단계의 현재 책임 조사는 완료했고, 2단계부터는 설계 결정이 필요하다.**

1. **DB 로직 분류 확정:** 코드 이전 / DB 보장 유지 / 기존 업무 전용 유지로 함수별 범위를 합의한다.
2. **단독 Agent 실행 계약:** 일반 ask_user/task를 확장할지, 별도 pending/continuation 계약이 필요한지 결정한다.
3. **조립 경계 A/B/C 비교:** 일반 worker 재사용, 신규 조립 진입점, 전체 분리의 근거를 비교한다.
4. **방식·version snapshot:** UI 토글을 저장·실행 시 어떤 명시적 계약으로 고정할지 결정한다.
5. **관측 범위:** 사용자 메모리 Trace와 관리자 DB 이력을 유지하며 신규 경로에 연결한다. LLM 추론은 보류한다.
6. **팀은 후속:** 관계·값 전달·팀 버전·실패/재개 계약부터 정하고 UI를 연결한다.

**이번 조사로 제품 코드·DB·운영 설정은 변경하지 않았다.** 현재 DB 보장 때문에 코드 이전이 불가능하다고 결론 내린 것도 아니고, 반대로 SQL 함수를 모두 제거해도 안전하다고 결론 내린 것도 아니다.
