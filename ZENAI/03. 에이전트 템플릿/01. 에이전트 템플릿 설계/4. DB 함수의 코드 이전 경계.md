# 2단계 — DB 함수의 코드 이전 경계

> **작성일:** 2026-10-01 · **조사 기준:** `51e6eae999f409fade4a6f81bb63a2c4afa1a5da`
> **연결:** [[1. 목표·상태·상황 기반 행동 플랜]] · [[3. 현재 책임 조사 - DB 함수와 Agent 실행 및 팀 구조]]
> **문서 상태:** 신규 템플릿 설계를 위한 책임 배치안. **제품 코드·DB 변경은 하지 않았다.** 운영 DB의 실제 적용 상태와 실행 결과를 검증한 문서가 아니다.

## 1. 결론 — 판단은 코드, 안전한 확정은 DB

**신규 템플릿의 업무 판단·단계 선택·사용자 문구는 애플리케이션 코드에 둔다.** DB는 해당 판단을 안전하게 저장할 수 있는지 확인하고 **권한·중복 방지·동시성·원자성**을 보장한다.

이는 **DB 함수를 모두 없애거나 DB 저장을 메모리로 바꾼다는 뜻이 아니다.** 기존 Builtin은 현재 경로를 유지하고, 신규 템플릿에서 동일한 업무별 SQL을 복제하지 않는 것이 우선이다.

| 분류 | 결정 | 의미 |
| --- | --- | --- |
| **코드 이전** | 업무별 규칙은 코드가 소유 | 어떤 Tool을 쓸지, 무엇을 기다릴지, 다음 단계와 표시 문구 결정 |
| **DB 보장 유지** | 데이터 경계에서 강제 | 현재 권한, 실행 소유권, 충돌 검사, 중복 방지, 상태와 응답 동시 확정 |
| **기존 전용 유지** | 기존 Builtin과 고객사 경로 보존 | 회의·SAP 전용 함수와 release/epoch를 새 일반 Agent에 그대로 이식하지 않음 |
| **혼합 책임 분리** | 함수 내부 책임을 나누어 설계 | 업무 판단은 코드로 옮기되 저장 직전의 검증과 transaction은 유지 |

**왜 DB에 있었는가?** 현재 코드에서 확인되는 것은 업무 규칙과 보안·저장 경계가 하나의 `SECURITY DEFINER` 함수에 묶여 있다는 사실이다. 당시 작성 의도까지 확정할 수는 없지만, 제한된 worker가 정해진 작업만 수행하게 하는 역할은 분명하다. **DB에 있다는 사실 자체를 설계 오류로 단정하지 않는다.**

## 2. 이전이라는 말의 정확한 범위

**1차 대상은 신규 템플릿의 책임 배치다.** 기존 Builtin SQL을 즉시 지우는 작업이 아니다.

- **기존 일반 Agent:** 생성·실행·버전·권한 경로를 보존하고 재사용 가능 부분부터 사용한다.
- **기존 Builtin:** 현재 SQL과 adapter를 유지한다. 실제 리팩터링은 별도 변경 범위와 회귀 검증이 필요하다.
- **신규 템플릿:** 회의 선택·SAP phase 같은 업무 규칙을 새 SQL 함수에 복제하지 않는다.
- **마이그레이션:** 적용된 과거 파일을 고쳐 이력을 바꾸지 않는다. 실제 DB 변경이 필요하면 **새 migration**으로 추가한다.
- **일반 Agent 버전:** `version`·`agent_versions` 기반을 유지한다. Builtin의 release·epoch 체계는 가져오지 않는다.

**“코드 이전 완료”는 아직 아니다.** 여기서 결정하는 것은 소유 책임이며, 정확한 신규 파일·함수·테이블은 3단계의 실행 조립 방식 선정 후 확정한다.

## 3. 함수별 이전 경계

SQL 번호와 위치는 **저장소 기준**이며, 상세 파일명과 호출자는 3번 문서에 정리되어 있다.

| 현재 함수·근거 | 코드로 둘 책임 | DB에 유지할 보장 | 신규 코드의 담당 위치 |

**검색을 코드로 옮긴다고 모든 회의록을 읽어 메모리에서 필터링하지 않는다.** 검색 조건을 코드에서 조립하더라도 필터링·정렬·페이지 제한은 DB 쿼리로 수행할 수 있다. 옮기는 것은 **정책의 소유권**이다.

**schema 검증은 두 층으로 나눈다.** 업무별 상세 형식은 코드에서 검사하되, 저장 경계의 크기·소유자·버전·허용 상태 검사는 유지한다. 기존 SQL 검증을 없애면서 worker에게 광범위한 직접 쓰기 권한을 주는 방식은 채택하지 않는다.

**예시: SAP의 finish 함수는 현재 phase가 done이면 종료하고, decide/tool/review이면 다시 pending으로 보낸다.** 신규 템플릿에서는 코드가 **완료 / 계속 / 사용자 대기** 같은 실행 결정을 만들고, 저장 계층이 그 결정을 유효한 실행 상태에만 적용한다.

단, 이 세 종류를 지금 새 공통 프레임워크로 구현하겠다는 뜻은 아니다. **기존 일반 Agent의 ask_user·task·slice가 수용하는지 먼저 비교**한다.

**Background를 단독 템플릿 1차 구현에 자동 포함하지 않는다.** 다만 이후 이전 시 지켜야 할 경계를 남긴다.

## 4. 절대로 함께 제거하면 안 되는 보장

| 보장 | 잘못 옮겼을 때 발생하는 문제 | 유지 방식 |
| --- | --- | --- |
| **현재 권한 검사** | 대기 중 권한을 잃은 사용자가 원문을 다시 조회 | 읽기·쓰기 경계에서 scope와 권한 재검사 |
| **claim fencing** | 만료 worker가 새 worker 이후에 늦은 답변 게시 | token·slice·lease 조건을 저장 시점에도 검사 |
| **CAS** | 두 요청이 같은 상태를 읽고 서로 덮어쓰기 | expectedVersion 조건부 갱신, 충돌 시 명시적 처리 |
| **멱등성·unique** | 중복 요청·callback이 run이나 답변을 반복 생성 | DB unique/조건부 쓰기와 재시도 키 |
| **원자적 terminal** | 답변은 있지만 상태가 미완료, 또는 반대 | 응답·상태·cursor·checkpoint를 필요한 단위로 함께 commit |
| **원자적 continuation** | 상태는 저장됐지만 다음 실행이 없거나 중복 | checkpoint·재큐잉·claim 해제를 함께 commit |
| **최소 DB 권한** | 함수 제거 후 worker가 모든 테이블을 수정 | RLS·role·제한된 definer 경계 유지 또는 동등한 권한 설계 |

**함수 유지가 유일한 방법은 아니지만, 당장은 검증된 경계를 재사용한다.** ORM transaction으로 대체할 수 있는 부분도 있으나 **transaction만 추가한다고 RLS·role·fencing까지 대체되는 것은 아니다.**

또한 **LLM/MCP 호출 동안 DB transaction을 계속 열어 두지 않는다.** 짧은 transaction으로 준비 → 외부 호출 → 짧은 transaction으로 결과 확정한다. 중간 장애는 operation 상태와 멱등성으로 처리한다. 외부 부작용까지 DB가 자동 rollback해 주지는 않는다.

## 5. 이전 후 처리 예시 — 회의록 선택

**아래는 목표 책임 흐름이며 현재 구현 완료를 뜻하지 않는다.**

1. **Tool 코드:** 검색 조건을 만들고 권한이 적용된 조회를 요청한다.
2. **Tool 코드:** 후보가 여러 개면 선택 schema와 사용자 문구를 만든다.
3. **저장 경계:** 현재 권한·claim·expectedVersion을 확인해 대기 상태를 저장한다.
4. **실행 코드 + 저장 경계:** 사용자 대기 결정을 전달하고 응답·실행 종료·checkpoint를 일관되게 확정한다.
5. **다음 사용자 입력:** 코드가 번호·취소·추가/대체를 해석한다.
6. **재개 경계:** 해당 사용자·대화의 대기인지, 만료·권한 변경·중복 응답이 없는지 확인하고 실행한다.

**입력 문구나 선택 의미를 바꾸는 일은 코드 수정으로 처리**하고, 동시에 두 응답이 와도 상태가 깨지지 않게 하는 일은 DB 저장 경계가 책임진다.

일반 Agent의 새 run이 이전 Agent version을 자동 계승한다고 가정하지 않는다. **대기 중 정의가 바뀌었을 때의 재개 계약은 3단계에서 명시**해야 한다.

새 기능 테스트만으로 끝내지 않는다. **같은 입력의 기존 경로 회귀**, **다른 사용자·community 격리**, **강제 실패와 동시성**이 이전 완료의 기준이다.

사용자용 **메모리 Trace**는 실행 검증을 돕지만 상태 저장의 대체재가 아니다. 관리자 **agent_run_spans DB 이력**도 별개이므로 이번 범위에서 삭제하지 않는다. **LLM 추론 텍스트는 계속 보류**한다.

## 7. 적용 순서와 아직 결정하지 않은 것

**권장 적용 순서:**

1. 3단계에서 기존 일반 Agent의 조립 경로로 수용 가능한 범위를 비교한다.
2. 신규 템플릿의 업무 판단을 코드에 두고 기존 권한·모델·MCP·버전 기반을 재사용한다.
3. 부족한 저장 기능만 추가한다. SQL이 필요해도 업무별 분기 대신 **작고 제한된 저장 연산**으로 둔다.
4. 기존/신규 경로를 함께 검증한 뒤 신규 방식만 점진적으로 활성화한다.
5. 기존 Builtin 리팩터링·미사용 함수 제거는 필요할 때 별도 수행한다.

**현재 결정하지 않은 것:** 신규 파일명, 공통 checkpoint 저장소, 일반 ask_user/task와 Builtin HITL의 통합 방식, 대기 중 버전 변경 정책, AI SDK 조립 분리 방식. 이는 책임 분류가 불가능해서가 아니라 **3단계 실행 구조 선택에 종속되는 구현 결정**이다.

**최종 경계:** 에이전트가 “무엇을 할지”는 코드가 결정하고, 그 결정을 “누가·어떤 실행에서·한 번만·일관되게 확정할 수 있는지”는 저장 경계에서 강제한다.

## 8. 근거와 조사 한계

**직접 재확인한 주요 근거:**

- `drizzle/0087_meeting-timeout-message.sql`: 회의 전용 timeout 문구와 terminal 원자적 게시.
- `drizzle/0064_meeting-terminal-boundaries.sql`: pendingHitl 판정·성공 상태 갱신·실패 상태 보존.
- `drizzle/0062_meeting-builtin-agent.sql`: 회의 payload·checkpoint schema, 검색, 권한, CAS, prepare/finish.
- `drizzle/0057_builtin-invocation.sql`: research phase 판정과 checkpoint·재큐잉.

- `src/lib/meeting-agent/tools/state-repository.ts`: 이미 존재하는 Zod 상태 schema와 SQL 호출 경계.

**이 문서는 저장소 정적 조사와 설계 판단의 결과다.** 운영 DB 카탈로그 조회, DB migration 실행, 유료 모델 호출, 게이트·통합·브라우저 E2E는 수행하지 않았다. 제품 저장소 파일과 배포 설정은 변경하지 않았다.
