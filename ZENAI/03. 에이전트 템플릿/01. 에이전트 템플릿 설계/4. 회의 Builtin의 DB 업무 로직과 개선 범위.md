# 회의 Builtin의 DB 업무 로직 — 코드로 옮길 것과 남길 것

> **2026-10-02 · 다음 구현 계획을 위한 간단 정리**
> **이번 우선순위:** 회의 Builtin의 책임 재배치와 기존 동작 검증. **스킬·백그라운드 확장·템플릿 구현은 나중에 진행**한다.
> 이 문서는 문제 범위 설명이며 상세 implementation plan이나 이전 완료 보고가 아니다.

## 1. 무엇이 문제인가?

**회의 Builtin의 일부 업무 규칙이 애플리케이션 코드가 아니라 DB 함수·트리거 안에 들어 있다.**

예를 들어 시간 초과 안내 문구, 회의 선택 상태의 상세 형식, 대기 여부에 따른 실행 경계 해석이 SQL에 있다. 업무 규칙을 바꾸려면 코드뿐 아니라 migration까지 변경해야 하고, 이후 공통 실행 기능으로 재사용할 때 SQL의 업무 의존성이 따라온다.

다만 **DB에 있다는 이유만으로 전부 오류인 것은 아니다.** 현재 함수들은 업무 규칙과 함께 권한·동시성·안전한 저장도 책임진다. 이번 작업은 기능을 새로 만드는 것이 아니라 **기존 동작을 보존하면서 책임을 나누는 리팩터링**이다.

## 2. 실제로 확인한 사례

| 현재 위치 | DB에 들어 있는 내용 | 이전 검토 방향 | 반드시 유지할 것 |
| --- | --- | --- | --- |
| **app_append_builtin_terminal** · 0087 | 회의 Agent의 EXECUTION_TIMEOUT에 “처리 시간 제한을 초과했습니다.”를 지정 | 안내 문구 선택은 코드로 | 유효 claim 확인, 답변·cursor·run 종료의 원자적 저장 |
| **app_sync_meeting_state_and_checkpoint** · 0064 | pendingHitl이면 hitl_waiting으로 해석, 성공 시 usable state 갱신, 실패/취소 시 이전 상태 보존 | 업무 상태 해석의 코드 소유 여부를 검토 | 종료 경계 중복 방지, 실패 시 기존 상태 보존, 종료와 상태의 일관성 |
| **app_worker_save_meeting_state** · 0062 | selection/merge, 후보·선택 목록 등 회의 전용 payload 검사 | 업무별 schema를 코드와 정리·통합할 후보 | 현재 문서 권한, 크기·범위 제한, expectedVersion 기반 CAS |
| **app_worker_finish_meeting_run** · 0062 | scratchpad와 search_selection/search_merge 등 checkpoint 형식 검사 | 회의별 해석·검증과 저장 경계를 분리 검토 | operation 결과 일치, claim·권한 검증, checkpoint·게시 동시 확정 |
| **검색·문서 조회 함수** · 0062 | 회의 검색 조건과 접근 가능한 문서 조회 | 정책과 조회 책임을 구분하되 무조건 이전하지 않음 | DB 필터링·현재 접근권한·선택 범위 제한 |

**우선순위:** 문구처럼 분리가 분명한 부분부터 시작하고, checkpoint·schema는 호출자와 transaction 경계를 확인한 뒤 결정한다. 모든 후보를 한 번에 옮길 필요는 없다.

**schema 검증을 SQL에서 전부 삭제한다는 뜻은 아니다.** 제한된 worker의 권한 경계에서 필요한 검사는 DB에 남길 수 있다. 코드에 같은 검사가 있다는 사실만으로 DB 검증이 불필요해지는 것은 아니다.

## 3. 목표 책임

| 코드가 결정 | DB가 보장 |
| --- | --- |
| 어떤 문구를 표시할지 | 허용된 실행만 게시할 수 있는지 |
| 다음 단계가 완료·대기 중 무엇인지 | 상태·답변·실행 종료가 함께 확정되는지 |
| 회의 Tool의 업무별 입력·상태 의미 | 다른 사용자·대화·문서에 접근하지 못하는지 |
| 실패·취소를 어떻게 안내할지 | 이전 상태를 깨뜨리거나 중복 결과를 만들지 않는지 |

**“무엇을 할지”는 코드, “안전하게 확정할 수 있는지”는 저장 경계**가 맡는다. 실제 SQL은 계속 사용할 수 있으며 ORM으로 교체하는 것 자체가 목표가 아니다.

**원래 있어야 할 파일이 미리 확정되어 있는 것은 아니다.** 기존 `channel-adapter.ts`, `engine.ts`, `tools/state-repository.ts`, 공통 runtime의 실제 호출자를 따라 가장 작은 변경 위치를 선정한다. 공통 실패 처리에서 발생하는 timeout까지 확인해야 한다.

## 4. 이번 작업에 포함하지 않는 것

- SKILL.md 작성·등록·연결과 스킬 관리 UI.
- 백그라운드 허용 설정·새 실행 기능·동료 구현의 재작성.
- 신규 템플릿 생성 화면·저장 구조·실행 방식 전환.
- SAP 등 다른 Builtin 전체의 동시 리팩터링.
- LLM 추론 텍스트 표시 문제와 운영 LiteLLM 배포.

**기존 백그라운드·SAP 기능은 삭제하거나 비활성화하지 않는다.** 공통 함수가 바뀌면 이 기능들에 미치는 영향은 회귀 검증 대상이다. 신규 기능 개발을 보류하는 것과 기존 기능 보존은 별개다.

## 5. 다음 단계 — 상세 구현 계획을 세운다

**네, 다음은 writing-plans를 이용한 ‘회의 Builtin 책임 재배치’ 구현 계획 수립이다.** 아래 사항을 확정해야 실행 가능한 계획이 된다.

1. **현재 유효한 함수·트리거와 모든 호출자 재확인:** 과거 migration 하나만 보고 변경하지 않는다. 이후 재정의·공통 fallback·실패/취소 경로도 확인한다.
2. **최소 이전 범위 선정:** 각 규칙을 코드로 옮길지, DB 검증으로 남길지와 이유를 명시한다.
3. **파일·계약 확정:** 변경 파일, 함수 입력/출력, SQL 경계, 새 migration과 호환 적용 순서를 적는다. 과거 migration은 수정하지 않는다.
4. **수용 기준↔테스트 매핑:** 변경 전 행동을 기준으로 단위·DB 통합·브라우저 E2E에 나눠 연결한다.
5. **구현 순서:** 실패 테스트 확인 → 최소 변경 → 관련 테스트 → 게이트 4종 → 로컬 E2E 순으로 구성한다.
6. **실행 전 검토:** 사람과 의도를 확정하고 저장소의 intent/harness 절차를 따른다. 문서 작성만으로 구현·migration·운영 배포를 시작하지 않는다.

### 계획에 반드시 포함할 검증

- 검색·선택·추가/대체·취소·후속 질문·최종 답변이 이전과 동일하게 동작.
- timeout 문구와 실패·취소 후 재개 상태가 유지.
- 상태 충돌, 중복 요청, lease 만료 worker의 늦은 게시 차단.
- 권한 회수와 다른 사용자·community 접근 차단.
- 게시 실패 시 답변만 남거나 상태만 종료되지 않도록 rollback.
- 기존 일반 Agent와 공통 함수를 쓰는 Builtin 경로의 회귀.
- **check·lint·knip·vitest** 및 로컬 통합·브라우저 E2E. 기존 실패와 신규 회귀를 구분.
