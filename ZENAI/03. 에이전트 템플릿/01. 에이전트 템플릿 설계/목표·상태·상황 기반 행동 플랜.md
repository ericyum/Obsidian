# 에이전트 템플릿화 — 목표·상태·상황 기반 행동 플랜

작성: 2026-09-28

> 방향성과 조사 순서를 정하는 문서다. 아래 조사 대상의 현재 구현을 확인했다는 뜻은 아니며, 상세 구현 방식은 코드·DB 함수·테스트 조사 후 결정한다.

## 1. 목표

- **최종 결과:** 회의 Builtin에서 검증한 범용 실행 기능을 이용해, 고객사 기존 기능을 보존하면서 새로운 에이전트를 설정으로 만들고 실행할 수 있게 한다.
- **1차 완료 기준:** 새 생성 화면으로 만든 단독 Agent가 모델·Tool 호출, HITL 대기·재개·취소, 실패·시간 초과, Trace를 정상 처리한다.
- **2차 완료 기준:** 별도 팀 구성 화면에서 Agent 간 관계와 데이터 전달을 설정하고, 팀 실행·중단·재개를 검증한다.
- **보존:** 기존 고객사의 Agent·팀·설정·대화·권한·실행 동작. 신규 기능 선택을 강제하지 않는다.
- **범위 밖:** 실제 MCP 서버 구축, 기존 Agent 일괄 전환, Builtin release 체계의 템플릿 이식.

## 2. 상태

- 회의 Builtin에서 Tool 호출, HITL, 상태·Checkpoint, 실행 경계, Trace 등의 구현 경험과 테스트를 확보했다.
- 이 Builtin은 기능 검증의 출발점이다. 전용 코드·테이블·DB 함수를 새 템플릿에 그대로 복제하는 것이 목표가 아니다.
- Trace는 메모리 기반이며 호출자 전용이다. Tool 입출력 구조와 Provider가 반환하는 추론 텍스트 표시를 구현했다.
- 운영 추론 텍스트 전달은 아직 확인 중이며, 최근 전체 테스트도 실패가 남아 있다. 기존 구현 전체가 검증 완료됐다고 전제하지 않는다.
- **미확인:** DB 함수에 들어 있는 실행 책임, 일반 Agent의 조립·실행 확장 지점, 현재 팀의 관계 표현·데이터 전달·재개 방식.

## 3. 상황

- 기존 ‘에이전트 만들기’는 고객사가 사용 중이다. 관련 코드를 지우고 새로 만드는 방식은 불가하다.
- 생성 화면의 토글로 기존 방식과 신규 방식을 선택하는 방향이다. **화면 분리와 실행 엔진 전체 복제는 별개의 결정**이다.
- 회의 Agent에서 범용적으로 만든 HITL·Tool 호출 후 실행 경계 등의 기능은 신규 Agent의 기본 실행 기반 후보로 삼는다. 업무별 처리는 Tool에 둔다.
- 버전 관리는 기존 일반 Agent의 `version`·`agent_versions` 방식을 기반으로 한다. Builtin의 release·epoch 체계를 그대로 가져오지 않는다.
- Agent 간 상하·선후·병렬 관계는 개별 Agent의 `orchestrator` 항목이 아니라 **팀 구성에서 정의**한다. 팀에서도 기존 방식과 신규 방식을 분리하는 토글을 고려한다.
- 커뮤니티 경계 안에서 Agent·팀·채널을 사용한다는 제품 전제 아래, 실제 소유·공유·호출 권한 구현을 조사한다.
- **처음에는 단독 Agent 부분만 구현·검증하고, 안정화한 뒤 팀 기능을 추가·검증한다.** 단독 단계에서도 향후 팀에 필요한 최소 입출력 계약만 고려한다.
- Provider는 SAP에 고정하지 않는 방향이다. 주소·인증·모델 설정의 기존 경계를 조사하고, 비밀값 저장·접속 권한·임의 주소 접근 위험을 함께 검토한다.
- MCP 서버 구축은 훨씬 뒤에 논의한다. 현재는 서버가 존재한다고 가정한 Tool 계약과 테스트 대역으로 연결한다. Agent가 Tool 서버 내부 DB를 직접 읽지 않는다.

## 4. 차이와 판단

- **현재와 목표의 차이:** 특정 Builtin에서 동작하는 로직을, 설정으로 만든 여러 Agent가 안전하게 재사용할 수 있는 실행 계약으로 정리해야 한다.
- **확정된 방향:** 고객사 기존 기능 보존, 단독 Agent 우선, 팀에서 관계 구성, 일반 Agent 버전 체계 활용.
- **조사 후 결정:** AI SDK 조립 경로를 나눌 범위, 공통 실행 기반의 확장 지점, DB 함수의 코드 이전 범위, 팀 데이터 전달 방식.
- **피할 방식:** DB 함수 통째 복사, 기존 실행 엔진 통째 복제, 팀 관계를 Agent 정의에 고정, 모든 State·대화를 Agent 사이에 무조건 공유.

## 5. 행동 플랜

### 1단계. 현재 책임을 조사한다

| 조사 | 확인할 내용 | 산출물 |
|---|---|---|
| DB migration·함수 | 함수 생성·교체 이력과 현재 유효한 정의, 호출 코드·트리거·테스트를 역추적. 요청 접수, Run 생성·claim, HITL, 완료·실패·시간 초과, 응답 게시, 상태 저장, 권한 검증 중 실제 DB가 맡는 부분 확인 | 함수별 책임·호출자·읽기/쓰기·트랜잭션·이전 대상 대응표 |
| 일반 Agent 생성·실행 | 생성 → 설정/버전 저장 → 호출 → 모델·Tool 조립 → 실행 → 응답 흐름. Builtin과의 분기 및 공통 기반 확인 | 기존/신규 재사용·분리 지점 지도 |
| 기존 Agent 팀 | 멤버 구성, 실행 순서, 위임, 병렬 실행, 결과 취합, 값 전달, 권한, 버전 선택, 실패·HITL 재개가 현재 어떻게 구현됐는지 확인 | 지원 기능·부족 기능 목록 |

### 2단계. DB 함수의 코드 이전 경계를 결정한다

- 템플릿의 업무 판단·오케스트레이션은 애플리케이션 코드로 구현한다는 요구를 기준으로 이전 대상을 선정한다.
- **마이그레이션 SQL 파일과 그 안에서 생성한 런타임 DB 함수를 구분**한다. 과거 migration 파일을 수정·삭제하는 방식으로 이전하지 않는다.
- 권한·RLS·제약조건·원자적 claim 등 DB가 보장하던 성질을 명시한다. 코드 이전으로 중복 실행·경합·권한 우회가 생기지 않도록 트랜잭션과 조건부 갱신을 설계한다.
- 기존 고객사 경로가 사용하는 DB 함수는 유지한다. 신규 경로부터 적용하고 영향 범위를 확인한다.
- **산출물:** 로직별 ‘코드 이전 / DB 보장 유지 / 기존 전용 유지’ 대응표와 동시성 검증 항목.

### 3단계. 신규 생성 화면과 AI SDK 조립 방식을 비교·선정한다

- 후보 A: 화면은 분리하고 기존 실행 기반의 확장 지점을 사용한다.
- 후보 B: 기존/신규 AI SDK 조립 진입점을 분리하되 모델 연결·Tool 계약·Trace 등 검증된 공통 기능을 재사용한다.
- 후보 C: 실행 경로 전체를 분리한다. 기존 구조로 요구를 수용할 수 없다는 근거가 있을 때만 검토한다.
- 고객사 회귀 위험, 범용 HITL 수용 여부, 코드 중복, 테스트 격리, 유지보수 비용으로 비교한다. **‘두 개로 나눈다’를 미리 결론 내리지 않는다.**
- **산출물:** 선정 근거, 신규 Agent 식별·실행 분기, 설정/버전 저장 계약, 점진 활성화·롤백 방안.

### 4단계. 단독 Agent를 구현·검증한다

- 선정한 구조로 신규 생성·수정·호출과 범용 실행 기능을 연결한다. 임의 Harness 코드 작성 기능을 추가하는 것으로 확대하지 않는다.
- Tool 대역으로 정상 호출, 결과 사용, HITL 대기·재개·취소, 실패·시간 초과, 후속 질문, 중복 요청을 검증한다.
- 기존 생성 방식의 회귀, 커뮤니티·사용자 권한 격리, Trace 실시간 표시·호출자 전용 조회를 통합·브라우저 E2E로 확인한다.
- **완료 조건:** 새 화면에서 생성한 Agent가 동작하고 기존 고객사 경로가 보존됨을 증명한 뒤 팀 구현으로 넘어간다.

### 5단계. 팀의 관계·데이터 전달 계약을 확정한다

- ‘상하’는 위임·결과 회수, ‘좌우’는 선후 실행인지 병렬 실행인지 구체화한다. 화면 배치만으로 실행 의미를 결정하지 않는다.
- 팀 안의 Agent 배치와 실행 관계를 팀 정의에 저장한다. 같은 Agent를 다른 팀에서 다른 역할로 재사용할 수 있어야 한다.
- 각 단계의 입력·출력 스키마와 `이전 단계 출력 → 다음 단계 입력` 매핑을 정의한다. 전달값은 수신 Agent의 권한을 넓히지 않는다.
- 원문 직접 전달과 권한 검증 가능한 참조 전달을 비교한다. 팀 공유 데이터·개별 Agent State·Tool 내부 상태를 분리한다.
- 분기·병렬 결과 취합, 순환 제한, 실패 전파·재시도·취소, HITL 후 어느 단계부터 재개할지, 실행 중 버전 고정 방식을 정한다.
- **산출물:** 최소 팀 관계 모델, 데이터 매핑 예시, 상태·권한·실패 계약, 팀 Trace 연결 규칙.

### 6단계. 팀 기능을 추가하고 검증한다

- 기존 팀 기능을 보존한 신규 경로에 합의한 관계·전달 계약만 구현한다.
- 순차, 상위→하위 위임, 병렬→결과 취합, 입력 불일치, 하위 실패, HITL 재개, 취소·재시도 시 중복 부작용을 검증한다.
- 서로 다른 팀·사용자의 동시 실행과 권한 격리, Agent별 Trace 연결을 통합·브라우저 E2E로 확인한다.
- **산출물:** 구현·검증 결과, 기존 기능 보존 근거, 운영 제한과 단계적 적용 절차.
