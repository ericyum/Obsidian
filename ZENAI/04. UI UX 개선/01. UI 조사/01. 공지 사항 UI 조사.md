# 공지 사항 UI 조사

- 조사일: 2026-10-14 (한국 시간)
- 목적: 사내 직원이 ZENAI의 신규·업데이트 AI 에이전트를 발견하고, 자신에게 필요한 기능인지 판단한 뒤 실제 사용으로 이어지게 하는 공지 UI의 참고 자료
- 범위: **12개 업체의 공개 페이지 18개를 화면으로 조사**. ChatGPT는 공식 문서만 보조 참고
- 자료 위치: 이 문서와 같은 폴더 아래의 `공지사항 조사 자료/2026-10-14/`
- 상태: 외부 사례 조사. ZENAI의 최종 화면 설계나 구현 요구사항을 확정한 문서는 아님

> 가장 중요한 발견: 공지 화면은 **새 기능을 알게 하는 역할**, **과거 변경을 찾아보는 역할**, **사용 조건과 적용 상태를 이해하는 역할**을 함께 다룬다. 업체마다 이 세 역할을 한 페이지에 합치거나 별도 페이지로 나눈다. ZENAI에서는 직원이 공지를 읽은 뒤 “어떤 에이전트를 어디서 어떻게 쓸 수 있는가”까지 알아야 한다.

## 1. 조사 방법과 확인 범위

공식 제품·지원·커뮤니티 사이트를 직접 열어 화면 구성과 내용을 확인했다. 검색창, 필터 메뉴, 접기·펼치기 등은 가능한 범위에서 조작하고 해당 상태를 캡처했다. 웹 화면은 기본 **1440×1000**, 모바일 비교 화면은 **390×844**, 배율 1, 영어 UI 기준이다. 이미지들은 전체 페이지를 축소한 사진이 아니라 해당 위치의 브라우저 화면이다.

요청한 컴퓨터 사용 도구가 실행 환경 오류로 시작되지 않아, 설치된 Chrome의 별도 자동화 세션에서 공개 페이지를 열어 캡처했다. 기존 사용자 로그인 세션은 사용하지 않았다. 쿠키 창과 홍보 배너는 화면의 닫기·거절 버튼으로 가능한 경우 닫았다. 스크린샷의 웹페이지 내용을 합성하거나 수정하지 않았다.

이 문서에서 근거를 다음처럼 구분한다.

| 구분 | 의미 |
| --- | --- |
| 화면 확인 | 실제 렌더링 화면과 표시된 컨트롤을 확인 |
| 동작 확인 | 검색 입력, 필터 선택, 접기·펼치기 등을 실행한 결과 확인 |
| 공식 문서 확인 | 업체의 설명 문서를 읽음. 로그인한 실제 제품 화면을 조작했다는 뜻은 아님 |
| 해석·시사점 | 조사 결과를 ZENAI 상황에 연결한 판단. 업체의 주장이나 확정 설계가 아님 |

읽음 상태의 계정 간 동기화, 구독 후 전달, 관리자별 기능 노출, 접근성 전반, 모든 모바일 화면은 검증하지 않았다. 화면에 해당 기능이 보이지 않았다는 이유만으로 업체 전체에 그 기능이 없다고 판단하지 않는다.

### 3.1 Notion — 기능을 이해시키는 긴 업데이트 피드

확인 페이지: [Notion What’s New](https://www.notion.com/releases)

- **배치:** 상단에 큰 제목과 간단한 소개, 일러스트, 소셜 팔로우 링크. 아래는 왼쪽 날짜·버전, 오른쪽 제목·대표 이미지·본문의 2열 구성이다.
- **내용:** 하나의 릴리스 안에 여러 기능을 소제목으로 나눈다. 기능 설명과 실제 제품 화면을 번갈아 배치하고 연결·설정·도움말 링크를 붙인다.
- **탐색:** 최신 항목부터 스크롤해서 읽는 방식이며 과거 페이지로 이동하는 링크가 있다. 조사한 공개 화면에서 릴리스 전용 검색·제품 필터는 확인하지 못했다.
- **조건 안내:** 본문에서 관리 기능이나 연결 방법을 설명한다. 소개 이미지에 보이는 제품 UI와 실제 공지 페이지의 버튼을 구분해서 봐야 한다.
- **해석:** 새 에이전트의 쓰임새를 충분히 설명하기 좋다. 여러 작은 공지를 빠르게 찾는 데는 긴 피드가 부담이 될 수 있다.
- **ZENAI 참고:** 에이전트 공지의 첫 문장에서 해결하는 업무를 설명하고, 실제 화면과 사용 안내를 함께 보여주는 방식이 유용하다.

### 3.3 Linear — 큰 변경은 풍부하게, 작은 수정은 접어서

확인 페이지: [Linear Changelog](https://linear.app/changelog)

- **배치:** 회사 소식 영역 안에 변경 이력 탭을 둔다. 왼쪽 날짜와 세로선, 오른쪽 큰 제목·미디어·본문이 연결되는 타임라인이다.
- **정보량 조절:** 주요 기능은 길게 설명하고, 수정·개선·API 등 세부 항목은 접기·펼치기 그룹으로 분리한다. 펼친 수정 목록에는 관련 영역을 나타내는 작은 태그가 붙는다.
- **검색 동작:** 검색 버튼을 누르면 별도 모달이 열린다. `agent` 입력 시 관련 제목 목록이 표시됐고, `meeting` 입력 시 결과 없음 상태가 표시됐다. 본문 전체 검색인지 제목 중심 검색인지는 확정하지 않았다.
- **사용 안내:** 기능 설명에서 문서로 이어지는 링크와 이용 조건을 함께 제공한다.
- **해석:** 중요한 변경을 먼저 읽고 세부 수정은 필요할 때 펼쳐보는 구조다. 긴 글에서도 정보를 단계적으로 노출할 수 있다.
- **ZENAI 참고:** 직원 대상의 업무 변화와 관리·기술 세부 변경을 서로 다른 정보 깊이로 제공하는 사례다.

### 3.4 GitHub — 많은 변경을 빠르게 찾는 목록

확인 페이지: [GitHub Changelog](https://github.blog/changelog/), [개별 공지 예시](https://github.blog/changelog/2026-10-07-local-sandboxing-for-github-copilot-now-generally-available/)

- **배치:** 상단 제목 아래 RSS·소셜 링크, 변경 유형 탭, 필터 버튼이 있다. 본문은 월별 접기·펼치기 목록이다.
- **한 항목:** 날짜, 변경 유형, 짧은 제목, 제품·영역 태그를 보여준다. 첫 목록에서 긴 설명이나 큰 이미지를 반복하지 않는다.
- **필터:** 제품 태그 체크박스와 여러 조건 중 하나라도 일치·모두 일치하는 방식을 고르는 컨트롤이 있다. 초기화와 적용 버튼을 확인했다. 이번 조사에서는 필터 메뉴 구성을 확인했으며 적용 결과 캡처는 확보하지 못했다.
- **상세:** 개별 글로 이동하면 유형·게시일·읽는 시간·큰 제목·이미지·설명과 문서 링크를 제공한다.
- **재방문:** RSS와 소셜 링크가 있고 하단에는 별도 뉴스레터 신청 폼이 있다. 뉴스레터가 모든 변경 이력을 전달한다고 보지는 않는다.
- **해석:** 변경 수가 많고 관심 제품이 다른 사용자에게 적합하다.
- **ZENAI 참고:** 제목 목록에서 에이전트·변경 유형을 먼저 구별하는 방식이 참고할 만하다.

### 3.5 Vercel — 짧은 요약과 작성자를 보여주는 목록

확인 페이지: [Vercel Changelog](https://vercel.com/changelog), [개별 공지 예시](https://vercel.com/changelog/deployment-storage-pricing-expands-to-existing-teams)

- **배치:** 페이지 제목 아래 블로그 범주 탭, 검색창, RSS 아이콘을 둔다. 날짜를 왼쪽 세로선에 정렬하고 오른쪽에는 제목·짧은 요약·작성자 얼굴과 이름을 배치한다.
- **분류의 범위:** 상단 탭은 회사 블로그의 범주다. 에이전트나 제품별 필터와 같은 것으로 해석하면 안 된다.
- **상세:** 본문과 작성자 외에 게시일, 읽는 시간, 복사 메뉴를 제공한다. 정책 변경 글에서는 적용 대상·시점·영향·설정 안내를 함께 설명한다.
- **탐색:** 목록에 요약이 있어 상세 글을 열기 전에 관련성을 판단할 수 있다. 추가 항목을 불러오는 버튼도 있다.
- **해석:** 큰 대표 이미지를 매 항목에 넣지 않아 여러 변경을 훑기 쉽다. 작성자가 드러나 변경의 담당 영역을 이해하는 데 도움이 된다.

### 4.1 자주 보이는 기본 구조

조사 사례를 기능 목적에 따라 묶은 **분석상의 분류**다. 한 업체가 여러 형태를 동시에 사용한다.

| 목적         | 화면에서 보이는 방식     | 대표 사례                   | 장점에 대한 해석             | 부담에 대한 해석               |
| ---------- | --------------- | ----------------------- | --------------------- | ----------------------- |
| 새 기능을 발견   | 큰 제목·이미지·강조 카드  | Notion, Slack, Asana    | 직원의 관심과 사용 맥락을 만들기 좋음 | 첫 화면에서 많은 공지를 보기는 어려움   |
| 변경을 찾아보기   | 날짜순 목록·유형·제품 필터 | GitHub, Figma, Vercel   | 필요한 변경을 빠르게 비교하기 좋음   | 설명이 너무 짧으면 쓰임새를 모를 수 있음 |
| 기능을 실제로 사용 | 시작 방법·설정·도움말    | Cursor, Claude, ClickUp | 공지에서 행동으로 연결하기 좋음     | 조건이 긴 본문에 묻힐 수 있음       |
| 도입 영향을 검토  | 상태·영향도·예정일      | Atlassian, Microsoft    | 발표와 실제 제공을 구분하기 좋음    | 필터와 메타데이터가 많아짐          |

### 4.2 놓치기 쉬운 차이

1. **소개 페이지와 변경 이력은 같은 화면이 아닐 수 있다.** Slack·Asana·Cursor는 목적이 다른 페이지를 병행한다.
2. **검색의 범위를 확인해야 한다.** Linear·ClickUp은 공지 검색을 제공한다. 지원센터 검색이나 회사 블로그 검색은 더 넓은 범위일 수 있다.
3. **변경 유형과 배포 상태는 다른 정보다.** 신규·개선·수정은 무엇이 바뀌었는지, 예정·배포 중·제공 완료는 언제 쓸 수 있는지를 나타낸다.
4. **게시일과 실제 적용일도 다르다.** Microsoft·Atlassian처럼 일정 열이 있거나, 본문에서 단계적 배포를 설명하는 사례가 있다.
5. **RSS·소셜·뉴스레터와 앱 내 읽음 관리는 각각 다르다.** 외부 구독 수단의 존재가 사내 직원의 읽음 여부를 관리한다는 근거는 아니다.
6. **대표 이미지 속 버튼은 공지 페이지의 실행 버튼이 아닐 수 있다.** 제품 사용 예시 이미지와 실제 클릭할 수 있는 링크를 구별해야 한다.

## 5. 모바일 화면 비교

두 사이트만 좁은 브라우저 폭으로 추가 확인했다. 실제 휴대전화의 터치 조작·성능·모든 화면을 검증한 것은 아니다.

### 5.1 Notion

날짜·버전이 제목 위로 이동해 한 열로 쌓인다. 도입부 일러스트와 소개가 커서 실제 공지는 화면 아래에서 시작한다. **해석:** 사내 공지에서는 첫 화면에 필요한 정보를 얼마나 빨리 보여줄지가 중요하다. [원문](https://www.notion.com/releases)

![Notion 모바일 공지](<01-notion-mobile.png>)

### 5.2 GitHub

제품 태그는 제목 아래에 배치되고, 유형 탐색은 가로 이동 컨트롤을 사용한다. 필터 버튼이 별도 줄에 유지된다. **해석:** 작은 화면에서도 날짜·유형·제목·제품이라는 판단 정보가 유지되는지 참고할 수 있다. [원문](https://github.blog/changelog/)

## 6. 공지 전달과 읽음 관리 — 공식 문서로 보충한 내용

공개 공지 페이지의 디자인만으로 실제 제품 안의 전달 방식을 알 수 없어, 일부 업체의 공식 운영 문서를 추가 확인했다. **이 절은 로그인 제품 화면의 직접 조작 결과가 아니다.**

| 사례 | 공식 문서에서 확인한 내용 | 조사에서 구분할 점 |
| --- | --- | --- |
| Vercel 알림 | 대시보드의 알림 팝오버와 이메일 등으로 운영 이벤트를 전달. 안 읽은 알림 수를 표시하고 웹에서 본 알림은 팝오버를 닫을 때 읽음 처리 | 배포·도메인·사용량 같은 운영 알림이다. Changelog 전체가 이 경로로 전달된다고 확인한 것은 아님 |
| Microsoft Message center | 관리자용 변경 안내. 읽음/안 읽음·보관·즐겨찾기·서비스 필터·주간 이메일 등의 기능을 설명 | 공개 Roadmap과 조직에 실제 적용되는 변경 안내를 구분해야 함 |
| Atlassian 조직 변경 일정 | 관리자 화면에서 조직에 적용되는 변경과 배포 일정을 확인하는 절차를 제공 | 공개 커뮤니티 표의 일정과 특정 조직의 일정은 같은 수준의 정보가 아님 |

근거: [Vercel Notifications](https://vercel.com/docs/notifications), [Microsoft Message center](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/message-center?view=o365-worldwide), [Atlassian 조직별 변경 일정](https://support.atlassian.com/organization-administration/docs/find-out-when-your-organization-will-get-a-change/).

Microsoft 문서는 조직별 제공 상태가 **일부 기능 공지에만** 표시된다고 설명한다. 모든 공지가 개인·조직의 사용 가능 상태를 자동으로 보여준다고 일반화하면 안 된다. [공식 설명](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/message-center?view=o365-worldwide)

**ZENAI에 대한 해석:** 직원에게 필요한 것은 공지 페이지를 만들었다는 사실만이 아니다. 새 공지가 있다는 사실을 인지하는 경로, 자신과 관련 있는 변경을 찾는 경로, 다시 찾아보는 경로가 연결돼야 한다. 읽음은 내용을 봤다는 기록이고 실제로 에이전트를 사용했다는 기록과는 다르다.

## 7. ZENAI 상황에서 참고할 요소

이 절은 앞선 사례를 바탕으로 정리한 **검토 항목**이다. 외부 업체의 방식을 그대로 채택하거나 구현을 승인한 내용은 아니다.

### 7.1 직원이 공지를 읽을 때 필요한 판단 정보

| 직원이 알고 싶은 것 | 공지에서 검토할 정보 | 참고 사례 |
| --- | --- | --- |
| 무엇이 생겼나 | 대상 에이전트·짧은 제목·신규/개선/수정 구분 | GitHub, Figma, ClickUp |
| 내 업무에 왜 필요한가 | 해결하는 업무·기존 방식 대비 달라진 점·짧은 사용 예 | Slack, Asana, Notion |
| 지금 내가 쓸 수 있나 | 대상 직원/커뮤니티·사용 가능 여부·활성화 조건 | Cursor, Claude, Atlassian |
| 어디서 시작하나 | 해당 에이전트나 사용 안내로 이동하는 경로 | Cursor, Notion, ClickUp |
| 무엇을 입력하나 | 예시 요청·준비 자료·예상 결과 | 사례의 사용 안내를 ZENAI에 연결한 검토 항목 |
| 기존 사용에 영향이 있나 | 변경 전후·기존 사용자에게 필요한 조치·적용일 | Vercel, Atlassian |
| 나중에 어떻게 찾나 | 날짜·에이전트·업무 목적·검색·공유 링크 | GitHub, Figma, Linear |
| 궁금한 점은 어디에 묻나 | 담당자·가이드·질문 경로 | Vercel의 작성자, ClickUp의 피드백 연결 |

특히 ZENAI에서는 **플랫폼 전체의 신규 기능 공지**와 **특정 커뮤니티에서 해당 에이전트를 실제로 사용할 수 있는 상태**를 구분해서 검토할 필요가 있다. 전역 공지에 소개됐다는 이유만으로 현재 사용자의 권한이나 커뮤니티 활성화 상태를 추정하면 혼동을 만들 수 있다. 이는 ZENAI 구조를 고려한 해석이다.

### 7.2 목록과 상세에서 볼 정보의 차이

조사 사례에서 목록은 관련성을 판단하는 데, 상세는 기능과 조건을 이해하는 데 더 많은 공간을 사용한다. ZENAI 검토 시 다음 구분이 도움이 된다.

| 영역 | 검토할 정보 | 이유 |
| --- | --- | --- |
| 목록 | 제목·짧은 요약·대상 에이전트·유형·게시일 | 직원이 본인에게 필요한 공지인지 빠르게 판단 |
| 상세 | 사용 목적·변경점·화면/영상·시작 방법 | 기능을 이해하고 첫 사용을 준비 |
| 조건 | 적용 대상·시점·활성화/권한·필요한 준비 | 공지와 실제 화면의 차이를 설명 |
| 이후 탐색 | 검색·태그·과거 이력·개별 링크 | 시간이 지나도 공지를 다시 찾기 |
| 인지·읽음 | 새 공지 표시·읽음 처리의 기준 | 새로운 내용을 알아차리고 이미 본 내용을 구별 |

### 7.3 사용자 문제와 관련성이 높은 참고 조합

- **발견과 업무 맥락:** Slack·Asana의 주요 기능 소개. 새 에이전트가 해결하는 일을 보여주는 참고 자료다.
- **빠른 재탐색:** GitHub의 목록, Figma의 제품·업무 분류, Linear의 검색. 에이전트가 늘어날 때 필요한 공지를 다시 찾는 참고 자료다.
- **첫 사용 안내:** Cursor·Claude·ClickUp의 메뉴 위치와 조건 설명. 공지를 읽고 실제 기능을 시작하는 참고 자료다.
- **적용 상태와 영향:** Atlassian·Microsoft의 배포 상태·일정. 예정 기능과 사용 가능한 기능을 구분하는 참고 자료다.

### 7.4 적용 전에 정할 사항

이후 화면 설계를 진행할 때 다음 사항을 먼저 결정하면 참고 사례를 선택하기 쉽다.

1. 공지가 플랫폼 전체 대상인지, 커뮤니티별 대상인지, 둘 다인지.
2. 직원이 새 공지를 처음 발견하는 위치와 공지 목록으로 들어가는 위치.
3. 신규 에이전트·개선·수정·운영상 변경을 어떤 수준으로 구분할지.
4. 소개된 기능과 현재 사용 가능한 기능을 어떻게 구별할지.
5. 목록의 요약과 상세의 사용 안내를 어느 정도 길이로 제공할지.
6. 공지 작성·게시·정정의 담당자와 갱신 날짜를 어떻게 표시할지.
7. 읽음의 기준을 목록 노출·상세 열람 등 어디에 둘지.
8. 공지를 찾는 기준을 에이전트 이름 외에 업무 목적까지 제공할지.

## 8. 보조 사례와 조사 한계

### 8.1 ChatGPT — 공식 문서만 참고

[ChatGPT Release Notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)는 날짜별 변경과 대상 플랜·지역·플랫폼·단계적 제공 조건을 설명하는 공식 기록이다. 이번 브라우저 세션에서는 자동 접근 확인 화면이 표시돼 정상 공지 UI 캡처를 확보하지 못했다. 해당 확인 화면을 공지 페이지 스크린샷으로 제시하지 않았다.

따라서 ChatGPT는 12개 업체의 시각적 비교에 포함하지 않고 문헌 참고로만 다뤘다. 실제 앱 내 공지 노출, 읽음 저장, 구독 동작은 확인하지 않았다.

### 8.2 확인하지 않은 범위

- 로그인 후 개인별 알림함과 관리자 화면의 실제 동작.
- 읽음 상태가 서버에 저장되는지, 다른 기기와 동기화되는지.
- RSS·이메일을 구독한 뒤 실제 전달되는 내용과 빈도.
- 일부 제품에서만 적용되는 플랜·지역·권한 조건의 전체 목록.
- 반응·댓글·의견 작성 후 동작.
- 모든 공지의 빈 목록·오류·긴 제목·다국어 상태.
- 모바일 전체 화면과 접근성·성능의 종합 검증.

GitHub는 필터 메뉴를 열어 구성을 확인했지만 적용 결과 캡처는 확보하지 못했다. Figma는 실제 조건 적용 결과까지 확인했다. 이 차이를 비교표에서 기능 존재 여부와 동작 검증 여부로 혼동하지 않아야 한다.

## 9. 스크린샷 파일 안내

문서에 포함한 화면은 업체별 설명과 바로 함께 볼 수 있게 배치했다. 파일명 앞 번호는 조사 자료의 정렬용이며 업체 수나 순위가 아니다.

| 파일명 묶음 | 화면 내용 |
| --- | --- |
| `01-notion-*` | 첫 화면·본문·모바일 |
| `02-slack-*`, `03-slack-help-*` | 기능 소개·전체 업데이트·지원센터 |
| `04-linear-*` | 타임라인·수정 펼침·검색 결과 |
| `05-github-*` | 목록·필터 메뉴·별도 상세·모바일 |
| `06-vercel-*` | 요약 목록·상세 |
| `07-cursor-*`, `16-cursor-technical-*` | 기능 소개·시작 안내·기술 문서 |
| `08-figma-*` | 기본 목록·필터·조건 적용·본문 |
| `09-asana-*`, `10-asana-help-*` | 분기별 소개·업무 효과·지원 문서 |
| `11-atlassian-*` | 검색·상태 표·상태 필터 |
| `12-claude-*` | 월별 문서·조건 안내 |
| `14-microsoft-*` | 소개·로드맵·목록·상세 펼침 |
| `15-clickup-*` | 버전별 피드·필터·본문 |

폴더에는 일부 추가 스크롤 화면과 캡처 과정의 참고 이미지도 남아 있다. `13-chatgpt-*`는 접근 확인 화면이며 유효한 제품 UI 자료로 계산하지 않는다. 본문에 사용한 PNG의 출처·크기·저장 시각은 같은 자료 폴더의 `screenshot-manifest.csv`에 정리했다.
