# 에이전트 현황 대시보드 UI 조사

- 조사일: 2026-10-14
- 대상 사용자: ZENAI의 에이전트를 개발·관리하며 사용량과 실행 문제를 확인하는 개발자·커뮤니티 관리자
- 조사 목적: **어떤 에이전트가 얼마나 쓰이고, 어디에서 느려지거나 실패하며, 변경 후 무엇이 달라졌는지** 파악하는 화면의 요소 조사
- 자료: 사용자 제공 Claude Console 예시 6장 + 외부 서비스·도구 10종의 공개 화면·공식 UI 예시
- 자료 폴더: `에이전트 현황 대시보드 조사 자료/2026-10-14/`
- ZENAI 코드 기준: 현재 로컬 HEAD `7ef0c36132b2c7bc8de86dbee759ace72a25f1f6`
- 범위: UI 비교·항목별 필요성·지표 정의·현재 코드의 데이터 근거 조사. 구현이나 운영 배포 확인 결과는 아님.

> 첫 화면은 **전체 에이전트 비교와 이상 징후**, 다음 화면은 **선택한 에이전트의 추세·버전·사용자·도구**, 마지막 화면은 **문제 요청의 실행 이력**을 보여주는 구성이 유용하다. 제공된 Claude 화면의 세션 수·토큰·도구 사용량은 참고할 수 있으나, ZENAI의 요청·실행 조각·모델 호출을 같은 단위로 계산하면 사용 현황을 잘못 해석하게 된다.

## 1. 조사 방법과 판단 기준

### 1.1 증거의 구분

| 구분 | 의미 |
| --- | --- |
| 사용자 제공 화면 | 사용자가 문서에 넣은 원본을 직접 읽음. Claude 계정에 로그인하거나 버튼 동작을 검증한 것은 아님 |
| 공개 데모 직접 확인 | 별도 브라우저에서 화면·탭·기간 선택 등을 직접 확인. 데이터는 해당 서비스의 데모 자료 |
| 공식 문서 UI 예시 | 공식 문서가 제공하는 이미지·영상의 표시 화면을 브라우저에서 캡처. 제품 계정에서 조작한 화면과 구분 |
| 공식 제품 소개 UI | 제품 페이지에 표시된 예시·미리보기. 운영 계정의 실제 통계와 구분 |
| ZENAI 적용 해석 | 위 화면을 바탕으로 이번 목적에 맞게 제안한 배치·지표. 팀의 확정 요구사항이 아님 |
| 코드 확인 | 소스·스키마·마이그레이션의 정의를 확인. 운영 DB의 적용·실제 수집률·운영 UI 동작은 별도 검증 필요 |

기존 Chrome에 연결하는 도구는 앞선 조사에서 실행 오류가 있었다. 이번 공개 사례는 기존 로그인 프로필을 사용하지 않는 별도 Chrome 브라우저로 조사했다. 인증·404 화면은 대시보드 사례 이미지에 포함하지 않았다. Langfuse 공개 프로젝트 진입은 로그인 화면으로 이동해, 공식 대시보드 예시로 대체했다.

### 1.2 항목별 필요성의 기준

- **필수**: 사용량·신뢰성·문제 추적에 직접 필요.
- **조건부**: 비용 근거·버전·예약 실행·여러 에이전트 등의 전제가 있을 때 필요.
- **후순위**: 첫 대시보드 목적보다 설정·편집·운영 조치에 가까움.
- **제외**: ZENAI 모니터링과 관계없는 브라우저 UI 또는 의미 없는 장식.

필수라고 평가한 항목도 즉시 구현 가능하다는 뜻은 아니다. 각 지표의 수집 가능성은 4장에서 따로 구분했다.

### 1.3 먼저 통일해야 할 관측 단위

| 단위 | ZENAI에서 의미 | 주의 |
| --- | --- | --- |
| 사용자 메시지 | 사람이 보낸 한 메시지 | 에이전트 미호출 메시지를 사용량에 포함하지 않음 |
| 사용자 요청 | 특정 에이전트를 대상으로 한 업무 요청 | 한 메시지가 여러 에이전트를 부르면 에이전트별 요청과 플랫폼 메시지 수가 달라짐 |
| 실행 Run | 실행기로 전달되고 상태가 기록된 실행 | 한 요청이 여러 조각 Run으로 이어질 수 있음 |
| 실행 조각 Slice | 긴 작업을 나눠 처리하는 조각 | 조각 증가를 새로운 사용자의 요청 증가로 해석하지 않음 |
| 모델 호출 | 모델을 한 번 호출한 단계 | 하나의 요청 안에서 여러 번 발생 |
| 도구 호출 | 하나의 도구 실행 시도 | 스킬 조회·질문·업무 실행·외부 작업 접수를 구분 |
| 대화·세션 | 여러 요청을 묶는 대화 범위 | ZENAI에 Claude와 같은 세션 계약이 있다고 가정하지 않음. 채널·스레드·에이전트 축을 정의해야 함 |
| 업무 완료 | 원래 목표가 완료됐다는 증거 | Run의 done, HTTP 성공, 작업 접수와 구분 |

현재 소스의 custom Run 유일성은 `triggerEventId + agentId + sliceNo`다. 최초 조각은 0이며 후속 조각은 증가한다. Builtin은 principal·definition·background 작업과 별도 실행 방식이 있다. 사용자 요청 수의 후보 집계키와 Builtin 재개·백그라운드 연결 규칙을 함께 결정해야 한다.

## 2. 사용자 제공 예시 — Claude Console

**이 화면의 역할:** 현재 설정을 읽는 데 유용하다. 실제로 얼마나 쓰였는지, 최근 실패했는지, 사용자가 결과에 만족했는지는 이 화면만으로 알 수 없다. ZENAI에서는 읽기용 모니터링과 설정 편집 진입을 구분하는 것이 좋다.

## 3. 이 대시보드가 답해야 할 질문

| 개발자의 질문 | 필요한 UI | 알 수 있는 사실 | 이것만으로 알 수 없는 것 |
| --- | --- | --- | --- |
| 직원들이 어떤 에이전트를 쓰는가? | 에이전트별 요청·고유 호출자·사용 채널 비교 표 | 기간 내 사용 분포·사용 집중 | 직원 전체 대비 채택률은 이용 가능 대상자 분모가 있어야 계산 가능 |
| 새 에이전트가 실제로 사용되는가? | 첫 사용일·최근 사용일·일별 추세·이용 가능 상태 | 출시 후 호출 기록 | 공지를 못 봤는지, 필요가 없는지, 권한이 없는지의 원인 |
| 어떤 에이전트가 문제인가? | 최종 실패 수/비율·진행 중·오래된 대기 | 실패·정체가 집중된 대상 | 시스템 성공이 업무 성공인지는 별도 증거 필요 |
| 왜 느린가? | 큐 대기·처리 시간·모델·도구 waterfall | 지연이 집중된 단계 | 한 요청의 상관관계를 모든 요청의 원인으로 일반화 불가 |
| 비용이 왜 늘었는가? | 토큰 종류·모델·요청당 비용·상위 소비 요청 | 호출 증가와 요청당 소비 증가 분리 | 현재의 토큰 합만으로 실제 청구액 확정 불가 |

### 4.3 장기 집계와 실시간 Trace의 구분

| 종류 | 현재 근거 | 대시보드에서 역할 |
| --- | --- | --- |
| 영속 실행 이력 | agent_runs + agent_run_spans + usage_events + feedback. 관리자 범위로 조회 | 기간별 사용·실행 문제·버전 비교의 원천 후보 |
| 채팅 실시간 Trace | 프로세스 메모리. 기본 최대 168시간, 요청/이벤트/바이트 한도에 따라 더 일찍 제거 가능 | 본인 요청의 지금 진행·대기 관찰 |
| 상세 시간 로그 | agent.run_timing 구조화 로그 | 별도 수집·보존·검색 기반이 확인될 때 성능 분석 원천 |

실시간 Trace는 커뮤니티·채널·호출 사용자 범위를 검사한다. 프로세스 재시작·재배포로 사라지고 여러 인스턴스의 공유 원장으로 사용할 수 없다. **지난 30일 사용량을 메모리 Trace 목록에서 계산해서는 안 된다.**

반대로 DB Span이 있다고 모든 실행이 완전하게 기록됐다고 가정하지 않는다. 기존 이력 타입은 `captured / not_captured / partial`을 구분하고, Recorder에는 쓰기 실패·누락·flush timeout 처리가 있다. 대시보드에 “Trace 수집된 실행 x/y”, 미기록·부분 수집 수를 표시하면 데이터가 적은 에이전트가 정상처럼 보이는 문제를 줄일 수 있다.

근거: [Trace 메모리 한도](<C:/Users/ericy/github/zen-ai/src/lib/agent-trace/memory.ts>), [호출자별 Trace 접근](<C:/Users/ericy/github/zen-ai/src/lib/agent-trace/runtime.ts>), [이력 타입](<C:/Users/ericy/github/zen-ai/src/lib/agent-history/types.ts>), [DB Trace Recorder](<C:/Users/ericy/github/zen-ai/src/lib/agent-history/trace.ts>).

### 4.4 원문·오류·개인정보 표시

현재 코드의 Trace payload 처리는 알려진 비밀 키·토큰 등의 마스킹과 길이 제한을 수행한다. 하네스의 payload 생략과 root 요청 보존, 기존 경로의 내용 기록은 같지 않다. 삭제된 원본과 연결된 이력은 내용 숨김 투영이 있다. 따라서 “원본 보기”는 무조건 모든 Prompt·도구 결과를 보여주는 메뉴가 될 수 없다.

첫 대시보드는 합계·상태·종류·버전 중심으로 표시하고, 질문/응답·도구 상세는 기존 권한과 숨김 규칙을 유지한 실행 상세에서 확인한다. 마스킹이 모든 민감 데이터를 탐지한다는 보장은 하지 않는다.

근거: [payload 마스킹·제한](<C:/Users/ericy/github/zen-ai/src/lib/agent-history/trace-payload.ts>), [실행 이력 SQL의 내용 숨김](<C:/Users/ericy/github/zen-ai/drizzle/0070_community-agent-history.sql>).

## 6. ZENAI에 필요한 지표의 정의 제안

다음은 **구현 전에 합의할 계산식**이다. 현재 API가 아래 집계를 이미 제공한다는 뜻은 아니다.

| 지표 | 정의 제안 | 추천 UI | 확인에 도움이 되는 사실·제한 |
| --- | --- | --- | --- |
| 에이전트 요청 수 | 같은 사용자 요청의 후속 조각을 하나로 묶어 집계. custom은 triggerEventId+agentId가 출발점, Builtin 재개·후속 실행은 연결 규칙 별도 | 첫 카드·전체 비교 표·시간별 막대 | 어떤 에이전트가 쓰이는지. 플랫폼 메시지 수·Run 수와 구분 |
| 실행 Run/조각 수 | 원천 Run 수와 요청당 조각 분포 | 상세·정보 tooltip | 긴 작업의 실행 분할 규모. 새로운 요청 증가로 해석하지 않음 |
| 고유 호출자 | 기간·범위 내 식별 가능한 사용자 distinct. 자동 실행 별도 | 첫 카드·에이전트별 표 | 여러 직원이 사용하는지, 소수 사용자 집중인지 |
| 사용 채널 수 | 호출된 channelId distinct | 에이전트별 표·채널 탭 | 사용이 어느 협업 공간에 퍼졌는지 |
| 최근 사용일 | 범위 내 마지막 사용자 요청 시각 | 전체 표·미사용 목록 | 최근 사용 여부. 로그 수집 장애·접근 불가와 함께 해석 |
| 현재 대기/실행 중 | 지금 스냅샷의 pending/running 및 별도 작업 상태 | 상태 카드·오래된 대기 목록 | 현재 쌓인 작업. 선택 기간 생성 수와 다른 시간 기준을 라벨에 표시 |
| 최종 실행 실패율 | 요청 단위 최종 failed / (done+failed). 취소·진행·미확인 별도 수 | 실패 수와 분모를 병기한 카드·추세 | 종료된 관측 요청의 실행 신뢰성. 분모 0이면 N/A |
| 중간 도구 오류율 | 계측된 도구 실행 시도의 failed / 판정 가능한 종료 시도 | 도구 표 | 복구된 중간 오류도 볼 수 있음. 최종 요청 실패율과 별도 |
| 취소·대기·미확인 | 사용자 취소, HITL 대기, 외부 상태 unknown, 부분 수집을 분리 | 상태 분포·상세 timeline | 실패가 아닌 중단·결과 미확정의 규모 |
| 처리 지연 p50/p95 | 단위를 요청/Run/모델/도구로 구분하고 원 표본에서 계산 | 성능 탭·문제 실행 상위 목록 | 일반적인 속도와 느린 꼬리. 표본 수 병기 |
| 큐 대기 | 최초 접수→최초 claim, 조각 재대기·재시도는 별도 | 성능 분해 | 워커/용량 문제 후보. 최신 claimedAt만으로 최초 큐 대기를 복원하지 않음 |
| 사용자 경험 전체 시간 | 최초 요청 접수→사용자에게 최종 결과 전달. HITL/외부 작업 대기는 분리 | 상세 성능 | 사용자가 얼마나 기다렸는지. Run finishedAt만으로 전달 완료를 보증하지 않음 |
| 모델/도구 호출 수 | 계측된 단계 수, 시도·업무 효과 중복 기준 명시 | 호출 효율 표·분포 | 반복·복구·복잡도 후보. 도구 호출 횟수가 실제 업무 부작용 횟수와 같지는 않음 |
| 입력·출력 토큰 | 수집된 모델 usage의 각 합. DB Span과 usage fallback을 중복 합산하지 않음 | 첫 요약·상세 분포·모델별 비교 | 소비 변화. 미기록·캐시 구성·재시도 포함 범위 명시 |
| 추정 비용 | 사용 시점의 모델·토큰 종류·유효 단가로 계산, 미산정 비율 표시 | 비용 탭·상위 요청 | 고비용 요청과 원인 후보. “실제 청구액”과 별도 |
| 피드백 | up/down 수, 평가된 요청 수/전체 요청 수, 중복·수정 정책 명시 | 품질 탭·버전 비교 | 기록된 반응. 👍 비율을 전 직원 만족도로 표현하지 않음 |
| Trace/usage 수집률 | captured/partial/not_captured 및 토큰 관측 범위 | 카드 하단·데이터 상태 패널 | 숫자를 믿을 수 있는 범위 |
| 버전 비교 | 동일 기간·업무 유형·실행 종류별 표본 수와 지표 비교 | 버전 탭·변경 표시선 | 업데이트 전후 관측 차이. 인과 판정은 별도 |

### 6.1 숫자를 잘못 읽지 않기 위한 표시 예시

아래 값은 **UI 설명용 가상 예시**이며 ZENAI 실제 데이터가 아니다.

| 잘못 읽기 쉬운 표시 | 더 명확한 표시 제안 |
| --- | --- |
| 오류율 0% — 실행 0건 | 종료된 요청 0건 · 실패율 N/A |
| 성공률 99% | 최종 실행 완료 99/100 · 업무 품질 별도 |
| 도구 오류 8건 | 중간 도구 오류 8회 · 해당 요청 5건 · 최종 실패 1건 |
| 응답 시간 20초 | 처리 p95 20초 · n=120 · 큐/HITL/외부 대기 별도 |
| 토큰 0 | 미기록 / 수집된 0 / 비적용을 구분 |
| 비용 $0 | 산정 불가 · 모델 단가 미등록, 또는 검증된 사용량에 대한 추정 $0 |
| 피드백 90% 좋음 | 평가한 요청 20/500 · 그중 👍18 / 👎2 |
| 사용 0회 | 기간 내 호출 없음 · 활성/권한/수집 상태 함께 확인 |

**원천 손실도 확인해야 한다:** 현재 일반 실행의 usage 변환에는 provider가 반환하지 않은 토큰 값을 0으로 치환하는 경로가 있다. 이미 0으로 저장된 값에서 “실제로 0”과 “미반환”을 화면만으로 완벽히 복원할 수 없다. null/observed/source 같은 관측 여부를 새로 기록할지 조사해야 한다. 근거: [worker-runtime의 usage 변환·저장](<C:/Users/ericy/github/zen-ai/src/lib/agents/worker-runtime.ts>).

또한 custom `failRun`은 reason 인자를 받지만 Run 행에는 status/finishedAt만 갱신하며 reason을 직접 저장하지 않는다. 따라서 agent_runs만 집계해서 원인별 “중지 이유” 차트를 만든다고 주장할 수 없다. 관련 실패 이벤트·Span·Builtin terminal 정보를 정규화해 읽는 방식과 누락 상태가 필요하다. 근거: [runs.ts](<C:/Users/ericy/github/zen-ai/src/lib/agents/runs.ts>), [worker.ts의 agent.run_failed 기록](<C:/Users/ericy/github/zen-ai/src/lib/agents/worker.ts>).

## 7. 화면 구성 제안 — 전체 비교 → 에이전트 상세 → 실행 증거

### 7.1 전체 에이전트 대시보드

이 화면의 첫 질문은 **“어느 에이전트를 지금 살펴봐야 하는가?”**다.

| 위치 | 넣을 항목 | 개발자가 파악하는 사실 |
| --- | --- | --- |
| 상단 공통 조건 | 조회 권한이 있는 커뮤니티, 기간·시간대, 종류, 에이전트, 버전/모델 추가 필터 | 어떤 데이터 범위의 숫자인지 |
| 상단 오른쪽 | 마지막 집계 시각·수집 지연·새로고침 | 현재 상태를 얼마나 최근까지 반영했는지 |
| 요약 카드 | 요청 수, 고유 호출자, 최종 실패/분모, 지금 대기·실행 중, p50/p95, 입출력 토큰 | 사용·운영·속도·소비의 기본 상태 |
| 주요 비교 표 | 에이전트 이름/종류·이용 가능 상태, 요청 수, 고유 호출자, 최종 실패율, p95, 토큰, 최근 사용, 데이터 상태 | 사용 많은/적은 대상, 실패·느림·과소 수집 대상 |
| 이상 목록 | 오래된 대기, 실패 증가, 토큰 급증, 외부 작업 unknown | 우선 조사할 요청. 처음에는 정렬 기반 목록으로도 가능 |
| 기간별 추세 | 요청과 최종 실패 수. 상태별 색+숫자·단위 | 하루·시간 구간의 급변 |
| 미사용/이용 불가 구역 | 활성인데 호출 없는 대상, 비활성/권한 미충족 별도 | 사용 0의 비교 전제 |

여러 카드가 모두 긴 차트일 필요는 없다. 전체 비교 표를 중심으로 두고 “실패 많은 순·최근 사용 없는 순·p95 높은 순”으로 볼 수 있으면 개발자가 조사 대상을 빠르게 고를 수 있다.

**필터의 일관성:** 카드·차트·표가 같은 조건을 사용한다. “현재 실행 중”처럼 시간 기준이 다른 항목은 그 차이를 명시한다. 표에 보이는 최신 버전과 기간 안 실행된 버전도 구분한다.

### 7.2 선택한 에이전트 상세

| 탭 | 넣을 항목 | 목적 |
| --- | --- | --- |
| 개요 | 정체성·버전/모델, 요청/호출자/실패/토큰 추세, 최근 사용·데이터 상태 | 이 에이전트가 실제로 얼마나·어떻게 쓰이는가 |
| 실행 이력 | 상태·기간·버전·호출자·채널 필터, 요청 요약·ID·시간·토큰 | 이상 수치의 개별 실행 찾기 |
| 성능·도구 | p50/p95, 큐·모델·도구 시간, 도구별 호출·오류·관련 Run | 어디서 느려지고 어떤 의존 도구가 문제인가 |
| 품질 | up/down·평가 커버리지·근거 있는 업무 지표 | 실행 완료 후 결과의 유용성 |
| 버전·설정 | 실행 당시 버전, 모델/노력, 도구·스킬 제공/조회, 변경 시점 | 변경 전후와 설정 조건 |
| 비용 | 근거가 확보되면 모델/토큰 종류별 추정·고비용 요청 | 비용 증가 원인 |

초기에는 개요·실행 이력·성능/도구를 우선하고, 품질·비용·버전 고급 비교는 실제 데이터 근거에 따라 구성한다. 새 탭을 추가할지 기존 관리 화면에 요약을 붙일지는 사용자 동선·라우팅을 확인한 뒤 결정한다.

### 7.3 개별 실행 상세

기존 **대화 / 호출 흐름 / 실행 정보**를 이어 쓴다.

- 대화: 허용되는 질문/응답, 누락·삭제·잘림 상태.
- 호출 흐름: 모델·도구·phase/memory의 부모/자식과 소요, 도구 오류·복구, 수집 완전성.
- 실행 정보: Run/요청 연결, 종류·버전·모델·호출자·채널, 시각·조각·시도 의미.
- 추가 검토: HITL 대기와 외부 작업 접수/완료/결과 전달의 연결, 큐 시간과 실제 사용자 대기 시간.

조회 범위를 공유할 때 조건과 선택한 실행을 유지하면 문의·이슈 조사에 도움이 된다. 링크가 있다고 조회 권한이 생기지는 않는다.

### 7.4 지표를 눌렀을 때의 연결

| 클릭한 항목 | 이어지는 화면 | 유지할 조건 |
| --- | --- | --- |
| 에이전트 이름 | 해당 에이전트 개요 | 커뮤니티·기간 |
| 실패 수/실패 구간 | 실행 이력의 최종 실패 목록 | 에이전트·기간·버전·최종 실패 |
| p95/느린 요청 | 수집된 소요 시간 기준 정렬·상위 실행 | 지연 정의·표본·기간 |
| 도구 이름/오류 | 관련 도구 Span이 있는 실행 | 도구·상태·기간·계측 범위 |
| 토큰·비용 상위 대상 | 소비 큰 실행 목록 | 모델·버전·기간·비용 산정 원천 |
| 품질 하락 | 해당 피드백/평가 요청 | 평가자·기준·기간·커버리지 |

차트마다 독립 조건을 숨기지 않는다. 상세로 들어갔다가 돌아와도 기간·정렬·필터를 유지하는 것이 좋다.

### 7.5 빈 상태·접근·반응형

| 상황 | 보여줄 내용 |
| --- | --- |
| 아직 실행 기록 없음 | 처음 사용 전인지, 선택 기간 내 없는지와 기간 확대 경로 |
| 필터 결과 없음 | 적용 조건과 초기화 |
| 데이터 미수집/부분 수집 | 수집된 범위·지표 계산 불가·마지막 관측 시각 |
| 서버/API 조회 실패 | 오류·재시도, 이전 집계를 보여주면 갱신 시각 명시 |
| 접근권한 없음 | 허용된 조회 범위 안내. 권한 없는 통계·원문을 0으로 보여주지 않음 |
| 진행 중/사용자 대기/외부 unknown | 상태와 마지막 활동·관련 실행. 임의 timeout/실패 판정 금지 |
| 원본 삭제·내용 숨김 | 삭제/숨김 상태를 유지하고 원문 복원하지 않음 |
| 작은 화면 | 비교 열을 줄이고 상세로 전환, 필터 접기. 가로 스크롤에 장애 지표만 묻히지 않게 함 |

색상만으로 정상/오류/미확인을 구분하지 않는다. 상태 텍스트·아이콘·수치를 같이 제공하고, tooltip·탭·기간 선택은 키보드로 접근 가능해야 한다.

## 8. 초기 범위와 후속 조사 제안

### 8.1 먼저 가치가 큰 범위

1. 권한 범위가 분명한 **커뮤니티별 전체 에이전트 비교 표**.
2. 기간·상태·종류·에이전트 필터와 마지막 집계 시각.
3. 요청/실행 조각 단위 정의, 요청 수·호출자·최종 실패/분모·토큰·최근 사용.
4. 데이터가 있는 범위의 p50/p95와 Trace/usage 누락 표시.
5. 카드·표에서 기존 실행 이력과 상세로 연결.

여기서 “토큰·p95”는 필요한 원천을 검증한 범위부터 제공한다. 일단 숫자를 채우기 위해 누락을 0으로 만들지 않는다.

### 8.2 데이터 계약을 확인한 뒤 확장

- 도구별 오류/소요·중간 실패 복구·스킬 조회 분리.
- 긴 작업의 Slice·HITL·백그라운드 상태와 사용자 요청 연결.
- 버전 적용 시점·동일 조건 비교·피드백 커버리지.
- 캐시/모델별 비용 산정과 미산정 비율.
- 운영 임계치·표본·기간·중복 억제·담당자를 합의한 알림.
- 복잡한 하위 실행 관계의 Waterfall/Graph.

### 8.3 구현 전 확인할 항목

| 확인할 일 | 왜 필요한가 |
| --- | --- |
| “개발자”가 조회할 커뮤니티·에이전트·원문의 권한 | 코드 편집 권한과 운영 사용자 데이터 조회 권한은 다름 |
| custom/Builtin/채널/background의 요청 연결키 | 요청 수·최종 결과·사용자 수 중복 방지 |
| 모든 실행 경로의 usage·Span 수집 범위 | 값 없는 경로가 저비용/정상으로 보이지 않게 함 |
| 0070/0071 등 이력 관련 운영 마이그레이션과 실제 데이터 | 소스 정의가 운영 적용을 보증하지 않음 |
| 토큰 원천·null/0·캐시·단가·재시도 포함 정책 | 비용과 호출 효율 숫자의 정확한 의미 |
| 생성/시작/종료/결과 전달·HITL/외부 대기 시각 | 큐 대기와 사용자 경험 시간을 분리 |
| 실패 사유 이벤트의 영속성·종류별 정규화 | 중지 이유 차트를 실제 근거로 만들기 |
| 이력 페이지네이션과 집계 API/쿼리 범위 | 현재 목록 응답의 일부 행만 더해 전체 통계를 만들지 않기 |
| 기간·집계 주기·시간대·갱신 지연 | 비교와 장애 확인의 시간 기준 |
| 피드백·평가 커버리지와 업무 성공 기준 | done을 품질 성공률로 표현하지 않기 |
| 대규모 기간 조회의 집계·인덱스·성능 | 모든 실행/Span을 브라우저로 내려받아 합산하지 않기 |

앱 소스·DB·Harness·운영 설정은 변경하지 않았다. 이 문서를 바탕으로 화면과 데이터 계약을 확정하면 이후 구현 의도·수용 기준을 구체화할 수 있다.
