- 조사일: 2026-10-14
- 대상: ZENAI를 처음 사용하는 사내 직원의 온보딩·튜토리얼

- 자료: 사용자 제공 키안닷컴 예시 3장 + 외부 서비스·도구 13개의 사례 화면

> ZA-48의 목표는 **첫 에이전트 요청을 성공시키고, 같은 사용 패턴을 다른 에이전트에도 응용하도록 돕는 것**이다. 따라서 화면 위치를 알려주는 투어, 실제 행동을 안내하는 실습, 막혔을 때 찾아보는 도움말을 각각 어떤 역할로 사용할지 비교했다.

## 1. ZA-48에서 이해한 팀의 계획과 의도

### 1.1 목표와 사용자 경험

사용자가 플랫폼 용어와 구조를 모두 학습하기 전에, 안전한 예제로 에이전트 사용을 경험하도록 한다. 첫 실습에서는 안내를 제공하고, 두 번째 실습에서는 안내를 줄여 사용법의 전이를 확인한다.

| 단계 | 티켓의 1차 방향 | 이번 조사에서 볼 UI 요소 |
| --- | --- | --- |
| 최초 진입 | 첫 로그인 후 시작·건너뛰기 안내 | 시작 목적, 예상 분량, 자율 선택, 재방문 경로 |
| 따라 하기 | 허용된 예제 에이전트와 합성 자료로 찾기·추가(필요 시)·호출·결과 확인 | 한 번에 하나의 행동, 대상 강조, 실제 요청과 결과의 연결 |
| 응용 실습 | 다른 에이전트에 같은 방식으로 요청, 힌트 축소 | 과제 목표, 요청을 스스로 구성할 여지, 필요한 경우의 힌트 |
| 종료·재방문 | 다음 행동, FAQ, 중단·재개·재학습 | 현재 위치와 완료 결과, 다시 시작, 도움말 탐색 |

**혼합형인 첫 안내 + 실제 ZENAI 화면 실습을 우선 검토하는 가안**이다. 별도 전용 페이지와 실제 화면 위 가이드를 비교하는 단계이며 최종 방식은 확정되지 않았다.

3~5분은 초보자 관찰 전의 **가설 목표**다. 회의록 에이전트와 샘플 회의록도 후보이며, 대상 사용자·커뮤니티의 접근 가능성과 자료의 안전성을 확인한 뒤 결정한다. 모든 에이전트의 기능·권한·실행 방식이 같다고 설명해서는 안 된다는 원칙도 포함돼 있다.

### 1.2 역할 분리

아래는 티켓에 제시된 기능 계약 초안의 요약이다. 기존 구현의 재사용 가능성은 아직 확인되지 않았다.

| 영역 | 티켓에서 맡긴 책임 |
| --- | --- |
| UI | 첫 로그인 진입, 현재 단계·다음 행동, 실제 화면 안내, 이전·다시 하기·건너뛰기·재방문 |
| Harness | 단계 전이, 진행 위치와 완료 이력, 시도 구분, 가능한 실제 완료 검증, 권한·실행 경계 |
| 튜토리얼 에이전트·Prompt | 한 번에 하나의 행동 안내, 질문에 맞춘 설명 깊이, 막힌 원인에 맞춘 힌트, 두 번째 실습에서 개입 축소 |
| FAQ·상황별 도움말 | 최초 실습에 필요하지 않은 설치·권한·작업 지속·결과 저장·개념 설명 |

### 1.3 진행 위치와 성공 이력의 구분

티켓은 `currentStep`, `stepResults`, `attemptId`를 개념상 분리한다. 안내의 이전 단계로 돌아가거나 처음부터 다시 하더라도, 기존 성공 이력을 자동으로 지우거나 실제 채널 추가·메시지·에이전트 실행을 되돌리지 않는 방향이다.

또한 사용자의 “완료했어요”와 시스템이 확인한 성공을 구분한다. 확인할 수 없으면 미확인으로 기록한다. 권한 부족이나 실습 대상 부재는 대체 실습·안내로 처리하며, 튜토리얼에 새로운 관리 권한이나 우회 권한을 부여하지 않는다.

이 원칙 때문에 **다음 버튼을 누른 기록, 요청을 보낸 기록, 결과가 나온 기록, 결과를 확인한 기록을 같은 완료로 취급할 수 없다.** 외부 사례의 진행률도 무엇을 기준으로 계산하는지 구분해서 조사했다.

### 1.4 아직 확인·합의되지 않은 사항

- 실습 두 개의 대상 에이전트·합성 자료·전사 및 커뮤니티별 접근 가능성.
- 채널 참여·에이전트 추가·호출·응답 완료를 기존 API·이벤트·권한으로 관찰할 수 있는지.
- 첫 진입, 건너뛰기, 재방문, 재개를 기존 화면에서 제공하는 방식.
- 사용자별 상태·완료·재시도 저장, 복귀와 중복 실행 처리.
- 입력 자료 정책, 개인정보·사내 문서 허용 범위, 페이지 이탈과 장시간 작업의 실제 동작.
- 질문 분류, 실습 시나리오, MVP 범위, 검증 시나리오, 담당자와 후속 작업.

티켓의 검토 완료 조건도 구현 완료와 다르다. 실습 목적·행동·완료 증거·대체 경로 정의, 질문 분류 합의, 역할과 되돌리기 원칙 합의, 확인 사실과 미확정 사항 분리, 구현 범위·검증·담당자 결정이 필요하다.

### 1.5 근거의 범위

Chrome 연결 도구의 실행 오류로 열린 Jira 탭을 직접 읽지 못했다. 별도 브라우저 세션에서는 로그인 화면으로 이동했다. 이후 사용자가 제공한 티켓 본문을 읽어 위 맥락을 정리했다. **댓글·첨부·연결 이슈의 원문은 별도로 확인하지 않았다.**

이번 문서는 조사 결과이며, UI·DB·Harness 구현이나 샘플 데이터 공개·운영 적용을 승인하는 문서로 사용하지 않는다.

## 2. 제공된 예시 — 키안닷컴

원본 메모: **“마비노기 영웅전 사이트인 키안 닷컴”**. 제공된 3개 화면을 읽어 시작 → 영역 안내 → 종료 순으로 재배치했다. 출처 사이트는 [키안닷컴](https://키안.com)이다.

### 2.1 환영과 시작 선택

배경을 어둡게 하고 중앙 안내 카드를 띄운다. 캐릭터, 튜토리얼 범위, 환영 제목, 짧은 설명, 진행 점, 건너뛰기와 시작 버튼이 있다.

**해석:** 시작하기 전에 안내를 받을지 선택하게 한다. ZENAI의 첫 진입 안내에서 실습 목적·분량·시작·건너뛰기·나중에 찾는 위치를 검토할 때 참고할 수 있다.

### 2.2 실제 화면의 영역 강조

방송 카드에 밝은 테두리를 두고 주변을 어둡게 한다. 설명 카드가 대상 근처에 배치되며 캐릭터·설명·진행 점·이전/다음 버튼을 반복한다.

**해석:** 무엇을 설명하는지 화면 위치와 연결된다. ZENAI에서는 설명 대상뿐 아니라 사용자가 실제로 눌러야 할 대상과 입력 영역을 가리지 않는지도 중요하다. 이 사진만으로 강조한 카드의 클릭이 다음 단계 조건인지 판단할 수는 없다.

![키안닷컴 대상 영역 강조](<튜토리얼 조사 자료/2026-10-14/사용자 제공 예시/00-kian-spotlight-broadcast.png>)

### 2.3 완료와 다시 시작

종료 단계에서 상단 캐릭터 버튼을 강조하며 다시 튜토리얼을 시작할 수 있는 위치를 알려준다. 이전·완료 버튼과 진행 점이 있다. 본문은 페이지마다 튜토리얼을 제공할 계획도 설명한다.

**해석:** 끝난 뒤 다시 찾는 위치를 가르친다. 다만 재시작·완료 저장·페이지별 튜토리얼의 실제 동작은 제공된 이미지로 검증하지 않았다.

**응용 과제와 튜토리얼 에이전트의 구체적인 동작은 ZA-48의 목표를 기준으로 한 검토 항목**이다. 아래 모든 외부 서비스가 독립적인 전이 평가나 상황 진단형 튜토리얼 에이전트를 제공한다고 주장하는 것은 아니다.

## 4. 외부 서비스·도구별 조사

### 4.1 Driver.js — 대상 강조와 숫자 진행 표시

출처: [Driver.js 공개 데모](https://driverjs.com/)

- **직접 확인:** 안내를 시작하자 설명 대상만 밝게 보이고 그 아래 말풍선이 붙었다. 시작 안내에서 다음 단계로 이동하면 강조 대상과 설명이 바뀐다.
- **요소:** 제목·짧은 설명·이전/다음. 별도의 진행 표시 데모에서는 현재/전체 단계 숫자가 나온다.
- **의미:** 큰 카드 없이 필요한 요소 가까이에 안내를 둘 수 있다. 진행률 표시와 대상 강조 방식도 분리해 확인할 수 있다.

### 5.3 혼합형 가안을 검토할 때의 참고 관계

1. **시작 안내:** 키안닷컴·Intro.js처럼 짧게 실습 목적과 선택을 보여준다.
2. **첫 실습:** Driver.js·Shepherd의 필요한 영역 안내와 Svelte처럼 행동·결과를 연결하는 방식을 함께 검토한다.
3. **진행·재개:** Intercom·Appcues의 목록과 완료 조건을 참고하되, 실제 성공·미확인·재시도 이력을 구분한다.
4. **응용 실습:** 첫 실습의 안내를 그대로 반복하기보다 목표·자료를 제공하고 필요한 경우에 힌트를 받게 하는 방향을 검토한다.
5. **이후 사용:** Slack·Notion의 주제별 도움말과 키안닷컴의 재방문 안내를 참고한다.

예상 화면 수·실습 에이전트·문구·상태 저장 방식은 이 조사에서 결정하지 않았다.

## 7. UI 검토 시 확인할 항목

### 7.1 안내와 실제 조작의 관계

- 강조할 대상이 없거나 권한으로 숨겨진 경우의 대체 안내.
- 현재 설명·한 번의 다음 행동·실습 목적이 이해되는지.
- 카드가 입력창·전송 버튼·응답 결과를 가리지 않는지.
- 장시간 응답·오류·접근 불가·확인 불가를 구분하는지.
- 이전·다시 하기·처음부터·건너뛰기·재개가 각각 무엇을 바꾸는지.
- 같은 실습을 다시 시작할 때 실제 메시지·실행이 중복되지 않는지.
- 응용 실습의 힌트 사용과 수행 결과를 구분할 수 있는지.
- 처음부터 모든 FAQ·용어를 순서대로 읽지 않아도 되는지.

이는 구현 계약을 확정하기 위한 질문이며, 이번 조사에서 ZENAI의 동작을 검증한 결과는 아니다.

### 7.2 작은 화면과 키보드

Shepherd의 좁은 화면은 설명 카드가 화면 폭 대부분을 사용한다. 작은 창에서는 대상 요소·안내·다음 행동이 함께 보이는지 확인해야 한다.

환영 화면을 모달로 제공한다면 열릴 때 내부로 포커스를 이동하고, 키보드 탐색·닫기·닫은 뒤 복귀 위치를 검토해야 한다. 모달은 바깥 영역의 조작을 제한하므로, **실제 화면에서 직접 행동해야 하는 실습 안내와 모달의 관계**도 구분해야 한다. 이는 [W3C WAI 모달 대화상자 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)을 실습 상황에 연결한 해석이다.

업체의 접근성 지원 소개 문구를 개별 사이트 전체의 접근성 검증 결과로 사용하지 않았다.

### 7.3 초보자 관찰에서 볼 결과

티켓의 3~5분 가설을 검토할 때는 안내를 끝까지 읽었는지만 보지 않고 다음을 관찰하는 것이 목표와 연결된다.

| 관찰 항목 | 확인하려는 것 |
| --- | --- |
| 첫 요청까지 걸린 시간 | 실제 첫 행동의 장벽 |
| 첫 요청·결과 확인 성공 | 첫 실습 목적 달성 |
| 두 번째 실습의 수행 | 다른 에이전트로 사용법 전이 |
| 힌트 사용 지점과 내용 | 어디서 막혔는지 |
| 건너뛰기·중단·재개 | 안내의 부담과 복귀 가능성 |
| 접근 불가·대체 실습 | 사용자별 조건 차이 |
| FAQ 선택 | 초기 설명에서 빼도 되는 내용과 필요한 도움 |

측정값이나 기대 성공률을 제시한 것은 아니다. 실제 초보자 관찰과 팀 합의로 판단할 항목이다.

## 8. 조사 방법·출처·자료 관리

### 8.1 스크린샷의 성격

| 자료 유형 | 해당 사례 | 확인 범위 |
| --- | --- | --- |
| 사용자 제공 | 키안닷컴 3장 | 이미지에 보이는 시작·강조·종료 구조 |
| 공개 라이브 데모 직접 조작 | Driver.js, Intro.js, Shepherd | 시작·단계 이동·진행 표시·좁은 화면 |
| 녹화 기반 데모 직접 조작 | Arcade | 재생과 클릭 지점에 따른 구간 이동 |
| 공개 학습·도움말 직접 확인 | Slack, Asana, Figma, Notion | 목차·주제·실습·영상 구성, Slack 설명 탭 |
| 공개 실습 직접 조작 | Svelte | 정답 보기 후 코드와 결과 변경 |
| 공개 진입 화면 | Bolt, Duolingo | 첫 입력 안내, 선택·다음 환영 화면 |
| 공식 문서 속 제품 예시 | Intercom, Appcues | 설명과 제품 예시 이미지. 로그인 제품 직접 검증은 아님 |

새로 캡처한 기본 화면은 **1440×1000**, 좁은 화면은 **390×844**, 배율 1이다. 사용자 제공 원본은 본래 크기를 유지했다. 각 사진은 해당 위치의 브라우저 화면이며 전체 페이지를 축소한 이미지가 아니다.

컴퓨터 사용 도구가 실행되지 않아 공개 사이트는 설치된 Chrome의 별도 세션에서 확인했다. 기존 로그인 프로필·쿠키는 사용하지 않았다. 사이트 화면과 이미지 내용을 합성하거나 수정하지 않았다.

### 8.2 확인하지 못한 부분

- Jira의 열린 Chrome 탭, 댓글·첨부·연결 이슈 직접 열람. 기획 맥락은 사용자 제공 본문 기준.
- 키안닷컴의 현재 라이브 동작. 자동화 세션에서는 접근 제한 안내가 나와 제공된 이미지를 사용했다.
- 로그인 이후의 개인별 학습 상태 저장·기기 간 동기화·관리자 설정.
- Asana·Figma의 실제 계정 실습 완료와 전체 과정.
- Notion Academy 내부 과정. 공개 지원 허브와 조직 가이드로 보충했다.
- Navattic의 삽입 데모. 필요한 화면을 확보하지 못해 핵심 사례에 넣지 않았다.
- 모든 모바일·키보드·스크린리더 동작의 종합 검증.
- 기존 ZENAI API·이벤트·Harness의 재사용 가능성, 실제 정책·샘플 접근권한.
