# 회의록 Agent 이식 방향 재정립

## 1. 정정된 핵심

회의록 Agent는 일반 Agent의 AI SDK Tool Loop에 옵션 하나를 더한 Agent가 아니다. 그렇다고 채팅·Worker·Run 기반을 전부 새로 만드는 독립 서비스도 아니다.

정확한 위치는 다음과 같다.

```text
공통 Builtin Agent Platform
├─ definition·instance·mention·agent_runs
├─ claim·lease·operation·cancel·최종 message.posted
└─ Executor Registry
            ↓
회의록 전용 Executor
├─ 목표·상황 판단
├─ Search·Question·Recording 흐름
├─ HITL 중단·새 Run 재개
└─ 회의록 Tool·State 경계
```

## 2. 왜 Builtin Agent인가

- 시스템 프롬프트와 실행 로직을 제품 코드가 소유한다.
- 사용자가 임의 MCP Tool을 붙인 일반 Agent와 권한·감사 계약이 다르다.
- POC에서 확인한 상태 전이와 HITL 규칙을 코드로 강제해야 한다.
- 기존 Builtin Platform이 일반 Agent와 분리된 Manifest·Executor·Run authority를 이미 제공한다.

회의록 Agent의 모델·추론·Token·Context·Round 한도는 Builtin manifest와 instance config에서 확정한다. 회의록 전용 State를 일반 Agent DB 필드에 억지로 넣지 않는다.

## 3. Tool 로직 원칙

- 권한과 업무 정합성은 LLM이나 범용 Harness가 아니라 Tool/Repository 경계에서 검사한다.
- `authorizedMeetingIds`는 Tool 전용 상태이며 현재 Local Repository, 향후 MCP가 소유한다.
- Search·Question 결과 중 다음 판단에 필요한 값만 모델 Context로 보낸다.
- 회의록 원문과 인증정보는 영속 State·Checkpoint·Trace·감사에 남기지 않는다.
- Recording은 기존 UI·Backend에 명령만 전달하고 실제 상태를 Agent에 복제하지 않는다.

## 4. HITL 원칙

HITL 대기 때문에 Worker lease를 계속 잡지 않는다. 질문을 `message.posted`로 출력하고 현재 Run은 완료한다. 안전한 재개 위치와 Tool 토큰 참조는 `builtin_checkpoint`에 제한적으로 남기고, 후보·기존 허용 목록·추가/대체 상세는 Tool State Repository에 둔다.

다음 사용자 메시지는 새 Run이다. Executor가 같은 사용자·Agent·Channel·Thread Scope의 Pending HITL을 확인하고 Tool이 최신 권한·상태를 다시 검증한 뒤 재개한다. `/cancel`은 Pending 상태를 명시적으로 폐기한다.

## 5. 장기 확장과 현재 범위

장기적으로 사용자가 여러 커스텀 실행 로직을 선택하는 서비스가 목표이더라도, 이번 이식에서 일반 Agent Worker 전체를 미리 템플릿화하지 않는다. 먼저 기존 Builtin Executor 계약 안에서 회의록 실행 책임을 검증한다. 둘 이상의 Executor가 실제로 같은 Harness 구성 요소를 공유하게 되었을 때 검증된 부분만 공용 라이브러리로 추출한다.

현재 Local Search·Question Tool과 State Repository는 제품 검증용이다. 고객사 배포 단계에서는 같은 Tool·State 책임을 고객사 온프레미스 MCP로 함께 이동한다.
