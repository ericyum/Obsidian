# 캡슐화의 목적과 적용 방향

## 1. 캡슐화의 기준

파일을 많이 나누는 것이 목적이 아니다. 다음 셋 가운데 하나를 실제로 얻는 경우에만 경계를 둔다.

- **보안:** 신뢰할 수 없는 LLM·클라이언트가 권한·원문·상태 저장을 직접 결정하지 못하게 한다.
- **변경 격리:** Backend, 모델, Tool transport가 바뀌어도 목표 실행 흐름을 함께 수정하지 않는다.
- **검증:** 상태 전이와 데이터 투영을 외부 호출 없이 독립적으로 테스트한다.

## 2. 공통 Platform과 회의록 Executor

Builtin Runtime은 claim·lease·취소·operation·최종 `message.posted`만 안다. 회의록 Executor는 Search·Question·HITL·Recording 의미를 안다. 이 경계 덕분에 회의록 로직을 추가해도 Custom Agent Worker와 SAP Executor를 수정하지 않는다.

## 3. Engine과 Provider

- Engine: 다음 행동, Tool 결과에 따른 상태 전이, HITL 우선 처리
- Provider: AI SDK 모델 생성, Context 예산, 구조화 JSON 검증

모델 Provider를 분리하면 Engine 테스트에서 실제 API를 호출하지 않고, 모델·토큰 설정 변경이 상태 전이 코드를 흔들지 않는다.

## 4. Tool과 Repository

- Tool/Engine은 검색·질문이라는 업무 의도를 다룬다.
- Repository는 DB 질의, 사용자 권한 재검증, Local 상태 저장을 다룬다.

`authorizedMeetingIds`를 LLM이나 공통 Runtime이 직접 수정하지 못하게 하는 것이 핵심 보안 경계다. 현재 Repository는 Local 구현이고 향후 고객사 MCP Tool·State로 교체된다.

## 5. Context

같은 Thread의 `message.posted`와 현재 Run의 안전한 Tool 결과를 모델 예산 안에서 조립한다. Tool마다 다른 결과를 같은 의미로 재작성하려고 하지 않는다. 회의록 원문은 Question 호출에만 추가하고 저장 가능한 Checkpoint와 분리한다.

별도 `context.ts`가 실제로 여러 호출에서 공유되지 않는다면 Engine/Provider 안의 작은 함수로 시작한다. 규칙이 커지거나 독립 테스트가 필요해질 때만 파일로 추출한다.

## 6. HITL

공통 Runtime에는 공개 가능한 재개 메타데이터만 남긴다. 후보·기존 허용 목록·추가/대체 상세와 일회용 토큰의 소비는 Tool State Repository가 책임진다. 이 분리로 클라이언트나 LLM이 후보 ID를 조작해도 Tool의 최신 권한 검증을 우회하지 못한다.

## 7. Trace와 감사

- Realtime 진행 Event는 실행 관찰을 위한 best-effort 출력이다.
- Builtin operation receipt는 실행 결과를 남기는 공통 감사 원장이다.

별도 `trace.ts`나 `audit.ts`는 현재 구현이 한 파일의 작은 함수로 충분하면 만들지 않는다. 두 번째 Executor에서 동일한 규칙이 확인될 때 공용 Sink 또는 Adapter로 추출한다.

## 8. 결론

이번 이식은 기존 Platform과 회의록 도메인의 신뢰 경계를 분명히 하되, 아직 한 구현밖에 없는 인터페이스·Wrapper·폴더를 미래 재사용성만을 이유로 만들지 않는다.
