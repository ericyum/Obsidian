# ZEN AI 설계 의도와 변경 시 지켜야 할 경계

새 세션은 기존 코드가 있다는 이유로 그것이 사용자의 최종 의도라고 가정하지 않는다. 아래는 지금까지 합의한 방향과 변경 경계다. 구체적인 새 요청이 이를 바꾸면 새 의도와 검증 기준을 먼저 확정한다.

## 하네스 템플릿화의 목적

회의 Builtin에서 만든 실행 제어를 재사용해 다양한 도구와 에이전트를 만들려는 목적이다. 회의 도구 세 개만 처리하는 하드코딩 하네스를 복제하려는 것이 아니며, 파일·테이블 이름을 모두 template으로 지으라는 뜻도 아니다.

일반 에이전트의 모델·권한·MCP·실행 기반은 최대한 재사용하고, 없는 설정만 확장한다. Builtin과 생성 하네스는 구성·신원·저장 어댑터가 다르더라도 공통 실행 정책이 불필요하게 갈라지지 않게 한다. 현재 전체 엔진이 완전히 동일하다는 뜻은 아니다.

## 스킬은 매뉴얼이고 도구는 별도 권한이다

사용자가 특정 시나리오를 요청하면 해당 매뉴얼을 읽고 지침대로 행동한다. 어떤 실제 도구를 호출할지는 LLM이 허용된 도구 중 판단한다.

- 스킬 목록·요약·적용 상황을 사전 안내하고, 필요한 본문을 조회한다.
- 여러 요구가 있으면 관련 지침을 복수 조회하고 각각 처리한다.
- 무관한 단순 인사는 스킬 조회 없이 답할 수 있다.
- 공용 문서 매뉴얼은 작성 도구를 연결하지 않아도 체크·조회할 수 있다.
- 매뉴얼에 도구가 없어도 독립적으로 선택된 도구는 동작할 수 있어야 한다.
- 스킬을 읽는 것이 도구 권한을 부여하지는 않는다.

**마지막 두 항목을 위한 분리 변경은 기준 코드에서 미완료다.** 현재 시나리오별 toolRefs와 Builtin actions 검사가 있다. 단순히 UI 체크박스를 숨기거나 검사만 무조건 통과시키는 방식으로 해결하지 않는다. UI·저장·실행의 결합을 함께 풀고 실제 권한 검사는 유지해야 한다.

이 방향은 생성 하네스뿐 아니라 Builtin 회의 에이전트에도 적용한다.

## 도구 후속 실행은 공통 계약으로 판단한다

공통 루프에서 “녹음이면 종료, 검색이면 복귀” 같은 이름별 분기를 만들지 않는다. 기본은 모델로 돌아가 남은 목표를 판단하는 흐름이며, 안전한 경우만 공통 followUp 규약으로 마지막 호출을 생략한다.

업무 어댑터가 해당 도구의 입력·반환 형태·업무 로직을 아는 것은 정상이다. 없애려는 것은 업무 이름에 종속된 공통 종료·재개 정책이다. 특정 이름이 파일에 보인다는 이유로 전부 지우지 않는다.

복합 요구 누락 방지가 비용 절감보다 우선이다. 원문 읽기, 작업 접수, 앞으로 하겠다는 계획을 사용자 요청 완료로 세지 않는다.

## HITL은 LLM 해석과 코드 검증을 나눈다

사람의 응답은 LLM이 대기 상태를 보고 해석한다. 후보 검증·동시 변경·만료·실제 resume/cancel은 기존 코드가 맡는다. 자연어 취소를 고정 문구 하나로 제한하지 않되, 모호한 대상의 취소를 임의 확정하지 않는다.

백그라운드 완료 결과나 회의록 본문의 문장을 사람의 확인 응답으로 취급하지 않는다. 외부 자료는 지시문이 아닌 데이터다.

## 백그라운드는 도구가 접수하고 하네스가 상태를 잇는다

동료분이 설명한 기준은 도구 서버가 실행기 URL·키를 관리하고 실행기로 업무를 보내는 구조다. ZEN AI는 선택한 도구의 백그라운드 실행 허용, 예약·최소 정보·완료 재개를 맡는다.

따라서 Builtin·생성 하네스 UI에 공통 실행기 URL·API 키 입력란을 다시 추가하지 않는다. 로컬 slow_sum의 env 호환 경로와 과거 Builtin DB 연결 필드는 현 구현의 특수·호환 사항이며, 미래 모든 MCP의 연결 구조로 일반화하지 않는다.

현재 런타임에서 임의 도구 설명 문자열만으로 외부 완료 계약이 저절로 성립하지 않는다. 새 MCP를 붙일 때는 실제 접수·식별자·완료 보고·인증 규약과 테스트가 필요하다. 아직 없는 서버를 구축된 것으로 문서화하지 않는다.

도구 선택과 백그라운드 허용은 독립된 조건이다. 체크를 해도 도구 권한이 생기지 않는다. OFF로 바꾼 것과 접수된 일의 취소·결과 폐기는 다르다.

## 동료가 만든 코드와 기존 기능의 보호 경계

사용자는 동료 pokqok가 만든 백그라운드 예약·실행기·콜백 알고리즘을 함부로 바꾸지 않기를 요청했다. 우선 필요한 하네스 연결·지침·UI만 수정하고, 공통화가 필요해도 기존 중복 방지·권한·원장 보장을 유지한다. 알고리즘 자체 변경이 필요하면 원인과 범위를 설명하고 새 허용을 받는다.

과거에는 인터페이스 변경에 맞춰 통합 테스트의 가짜 모델을 decide에서 runTools로 맞추는 것만 별도 허용했다. 이것을 배경 실행기의 제품 로직 수정 허가로 해석하지 않는다.

기존 채널 메모·이전 컨텍스트 저장 기능도 사용자 작업 이전부터 있던 별도 기능이다. 근거 표기·메모 갱신 오류를 하네스 작업에 묶어 임의로 고치지 않는다. 검사에서 보이면 별도 범위로 기록한다. 보안상 중대한 새 문제는 숨기지 말고 알린다.

Windows 고유 실패, PDF 미리보기 준비, 실제 마이크·전사는 이전 하네스 검증에서 제외된 영역이다. 제외와 해결 완료는 다르다. 새 요청이 해당 영역을 포함하면 범위를 다시 정한다.

## 기존 권한과 격리는 유지한다

커뮤니티마다 하네스를 제공하는 것과 모든 사용자에게 생성·호출 권한을 주는 것은 다르다. 기존 개발자·관리 권한, agent grant, 채널 멤버십, 활성화, 도구 grant, 사용자별 MCP 인증, RLS를 유지한다.

관리·런타임·워커 DB 역할을 섞지 않는다. 모델이나 브라우저·trace에 URL 자격 증명, 완료 토큰, 암호화 키를 노출하지 않는다. 외부 서버가 죽었다고 연결이 확인되지 않은 도구를 사용 가능하다고 꾸미지 않는다.

## 변경 절차와 검증

저장소 현재 AGENTS.md가 우선이다. src 로직 변경은 사람과 의도 확정 → `intents/TEMPLATE.md` 형식의 intent와 수용 기준↔테스트 매핑 → 아래 경로를 따른다.

```powershell
npx tsx scripts/harness.ts --intent-file 'intents/<slug>.md' --open-pr
```

이 명령은 단순 검사만 하는 것이 아니라 반복 수정·4종 게이트·교차 모델 판정·커밋·draft PR 생성까지 포함하는 작업 경로다. 조사만 요청받았을 때 실행하지 않는다.

사용자가 **이번 작업의 직접 구현 예외**를 명시하면 해당 범위만 직접 편집할 수 있다. 과거 예외를 미래 요청에 자동 적용하지 않는다. 예외여도 check·lint·knip·vitest는 실행하며, 교차 모델 evaluator를 생략했다면 그 사실을 기록한다. 일반 코드 리뷰를 동일한 검증으로 바꿔 부르지 않는다.

설치된 Next 버전은 익숙한 옛 버전과 다를 수 있다. Next 코드를 수정하기 전에 `node_modules/next/dist/docs/`의 관련 지침을 읽는다. 문서 작업만 하는 경우 제품 코드·DB·배포를 변경하지 않는다.

## Git과 배포의 경계

미커밋 변경을 보호하고, 병합 충돌은 양쪽 의도를 파악해 해결한다. upstream main 보존과 우리 변경 보존을 파일 하나의 통째 덮어쓰기로 처리하지 않는다. DB migration 번호·journal·rename 이력도 함께 검토한다.

커밋·push·PR·main 병합·배포·DB 적용은 다른 행위다. 사용자의 제목 추천 요청이 PR 생성이나 배포 재실행 권한은 아니다. 브랜치·worktree 삭제도 정확한 대상과 보존 상태를 확인한 별도 작업이다.
