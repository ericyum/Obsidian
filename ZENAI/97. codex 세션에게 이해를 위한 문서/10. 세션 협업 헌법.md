원본은 이 문서 한 곳이다. 각 checkout의 `.context/session-rules.md`와 세션 인계는 원본을 가리킨다.

## 1. 시작·재개·새 세션의 필수 확인

1. 새 세션과 맥락이 부족한 세션은 이 폴더의 **00 → 05 → 06 → 담당 기능 문서**를 읽고 이 헌법을 읽는다. 에이전트 변경은 01·03·04, 로컬 실행은 02·04, 가격은 07도 확인한다.
2. 현재 checkout의 AGENTS.md·추가 지침·Git 상태·관련 실제 코드를 읽는다. 문서의 기준 SHA·시각과 현재 소스·실행 앱·DB·원격 main을 각각 대조한다. 과거 기록을 현재 완료로 해석하지 않는다.
3. 다른 세션의 최신 인계를 받은 뒤 목적, 자신의 담당, 보호할 기존 동작, 미완료, 공유 자원 소유자를 확인한다. 읽기나 접근이 불가능한 자료는 읽었다고 보고하지 않는다.
4. 오래된 worktree에서 과거 요청을 자동 재개하지 않는다. 이번 지정 상위 브랜치와 실제 작업 경로를 명시한다.

완료 기준: 담당 범위·base/head·worktree·현재 환경과 미완료를 설명할 수 있고, 다른 세션의 미커밋 변경을 보존한 상태다.

## 2. 변경 최소화와 동료 코드 보존

- PR은 합의한 사용자 목적만 다룬다. 독립 기능·환경 문제·정리를 끼워 넣지 않는다. 범위 확대가 필요하면 근거와 실제 영향부터 공유한다.
- 호출자·저장 경로·테스트를 먼저 조사한다. 기존 함수·컴포넌트·패턴을 재사용하고 요청을 완전히 해결하는 최소 변경을 택한다.
- 동료의 의도·권한검사·오류 처리·재시도·배포 SQL을 보존한다. 충돌 해결은 양쪽 변경의 의미를 확인하고 최신 main과 통합 전후 diff·조상 관계로 누락을 확인한다.
- 테스트는 기존 suite를 우선 확장하며 변경 동작과 위험 경계만 추가한다. 보안·데이터 무결성·필수 게이트는 유지한다. 새 변경·실패·미해결 위험 없이 같은 검사를 반복하지 않는다.
- 작업별 intent 하나에 계획·수용 기준·기준↔테스트 매핑을 모은다. 재시도마다 문서를 늘리지 않는다. src 변경은 저장소의 **intent → harness → 게이트 4종 → 교차 모델 판정** 경로를 따른다. 사용자의 명시적 예외만 예외다.
- 로그·스크린샷·일회성 검증 도구는 ignored `.context`에 둔다. 사용자가 요청한 Obsidian·Jira 근거만 해당 위치에 보강한다.
- 서식·줄바꿈·정렬을 보존하고 migration journal은 필요한 항목만 수정한다. 불필요한 추상화·설정·의존성을 추가하지 않는다.
- 커밋 전 모든 변경 파일의 필요성을 설명할 수 있어야 한다. 무관 변경·중복 문서·서식 소음을 제거한다. 파일 수·줄 수를 줄이려고 필요한 검증을 삭제하지 않는다.

### 조사·PoC 세션의 역할과 공유

- **담당:** 사용자가 추가·수정하고 싶은 내용의 구현 가능성, 공식 정책/API, 기존 코드와의 연결, 대안·제약을 조사한다. 필요하면 자기 소유의 분리된 임시 공간에서 가벼운 PoC를 수행하고 실험 조건·관측·한계를 남긴다.
- **구현 인계:** 제품 src 수정·정식 게이트/회귀/E2E·개발 하네스 실행은 구현/테스트 담당에게 넘긴다. 조사용 문서와 일회성 PoC를 제품 구현·최종 검증 완료로 보고하지 않는다. 사용자에게 이 역할을 바꾸라는 명시적 요청을 받으면 먼저 담당과 경계를 다시 공유한다.
- **착수 공지:** 사용자에게 조사 요청을 받으면 본격 조사 전에 기존 여섯 세션 모두에게 요청 목적·핵심 질문·범위·예정 산출물·관련 기존 기능과 공용 자원 사용 여부를 알린다. 이 세션의 사용자 요청과 ID를 승인 근거로 남긴다. 이는 현재 대화에서 직접 전송하는 절차이며 별도 예약 자동화나 상시 감시를 뜻하지 않는다.
- **결과 공지:** 구현 방향을 바꿀 중요한 발견과 조사/PoC 종료 때 공식 출처·확인 시점·ZEN AI의 실제 경로·확정 사실/추정/미확인·권고와 남은 검증을 여섯 세션에 공유한다. 긴 근거는 한 원본의 절대 경로로 인계하고 메시지에도 판단에 필요한 핵심 맥락을 담는다. 구현 중인 업무의 변경 여부는 조정자와 해당 담당이 결정한다.
- **수신·자원:** 다른 세션의 인계는 근거로 읽고 사용자 요청 범위 안에서 답한다. 인계만으로 제품 구현이나 권한 확대를 시작하지 않는다. 공용 문서·앱·DB·Chrome의 예약과 비밀값 보호는 이 헌법을 동일하게 적용한다. 송신 성공·상대 수신 확인·실제 반영 완료를 구분하고, 의미 없는 수신 확인 루프를 만들지 않는다.

## 4. 브랜치·파일·환경의 소유권

- 사용자 지정 통합 브랜치를 부모로 각 구현 담당이 별도 하위 브랜치·worktree에서 작업한다. 동일 checkout의 HEAD/index를 여러 세션이 동시에 바꾸지 않는다. 통합 checkout의 Git 변경은 조정자 한 곳에서 수행한다.
- 시작 전에 담당 파일과 공용 API/props 계약을 나눈다. 같은 파일 수정이 필요하면 소유자와 순서를 조정한다. migration 번호도 조정자가 배정한다.
- **3002 앱·기존 DB·Chrome·migration·공용 문서**는 소유자와 예약을 알린 뒤 사용한다. 다른 세션의 앱을 재시작하거나 DB·역할암호·.env를 바꾸지 않는다. Chrome 입력은 한 번에 한 세션만 한다.
- 기존 Docker **zen-ai-postgres-1 / zen-ai-litellm-local 두 개**를 사용한다. 새 컨테이너 추가가 필요하면 사용자와 먼저 범위를 합의한다. 전체 DB 검사에 role bootstrap이 필요하면 기존 PostgreSQL 컨테이너 안의 담당 전용 빈 클러스터를 사용한다. 같은 클러스터의 별도 DB는 역할 비밀번호를 격리하지 못한다.
- 임시 클러스터/포트/프로세스/fixture는 소유자·대상·생성 근거를 기록한다. 정리는 자신의 자원만, 절대 경로/DB 이름을 검증한 뒤 수행한다. 기존 사용자 자료와 타 세션 자원을 보존한다.

## 5. 테스트 준비·실행·복구 표준

이 절은 테스트를 시작할 조건과 실패 뒤 재개할 지점을 정한다. 현재 포트·PID·예약·fixture 명령은 담당자의 기존 시험 행렬과 예약 원장을 읽는다. 구체적인 과거 실패 근거는 같은 폴더의 **06. 현재 상태·미완료 작업·문제 해결**과 해당 작업의 ignored 로그를 참조한다.

### 5.1 실행 전 확인 — 대상·권한·환경을 먼저 맞춘다

1. **시험 대상:** 기존 intent의 수용 기준↔테스트 매핑에 사용자 흐름·역할·상태·경계를 적고, 이번 실행이 표적 회귀·공식 전체 게이트·읽기 리뷰·실제 Chrome 중 무엇인지 표시한다. worktree, branch/base/head, 미커밋 변경, 실행 명령, 기대 결과와 증거 경로를 고정한다. “모든 경우”는 이 유한한 행렬로 판단한다.
2. **런타임:** package.json에 맞는 실제 Node 실행 파일과 의존성을 확인한다. 앱과 같은 `scripts/load-env.ts` / `@next/env`로 환경을 해석하고, 대상 DB·포트·역할·인증 만료·모델/도구 가용성을 안전한 식별 정보로 대조한다. 비밀값 전체를 출력하거나 시험 편의를 위해 원본 `.env`를 고치지 않는다.
3. **실행 전 점검:** fixture·검증 도구는 먼저 구문 검사, 필요한 실제 모듈 export/alias 확인, 예약 누락 시 DB 연결 전에 거절되는지 확인한다. DB 없는 UI/mock 시험은 환경 파일과 DB/bootstrap 변수의 **실제 부재**를 자식 프로세스에서 확인한다. 빈 문자열은 부재가 아니다. 기존 Vitest config/globalSetup과 보호 검사를 유지한다.
4. **DB 격리 방식:** role bootstrap·암호 갱신이 있는 전체 검사는 §4의 빈 전용 클러스터로, 기존 역할을 재사용하는 브라우저 후보 DB는 정확한 예약과 역할 보존 조건으로 구분한다. 후자는 생성 전 기존 역할 속성·멤버십을 확인하고 migration/seed 뒤에도 같음을 대조한다. 조건이 다르면 준비 미완료로 중단하며 원본 DB로 전환하지 않는다.
5. **착수 조건:** 자원 소유자·예약과 현재 메모리를 확인한다. 예약 대기 중에는 DB 없는 준비·읽기 리뷰·문서를 진행한다. 승인된 기존 범위는 그대로 사용하고, 새 컨테이너·원본 역할 변경처럼 범위가 늘 때만 필요한 승인을 받는다.

완료 기준: 대상·기대 결과·환경·격리 방식·실행 권한·예약이 기존 시험 기록에 남아 있고 서로 일치한다. 계획이나 도구 구문 검사만으로 실제 DB/로그인/Chrome 준비 완료를 선언하지 않는다.

### 5.2 자원 예약 — 전체 하네스 수명과 실제 프로세스를 확인한다

- 이 PC에서는 **공식 전체 검사 1개, Vitest workers 최대 2**로 운영하며, 전체 검사 중 빌드·다른 DB 준비를 겹치지 않는다. 메모리가 부족하면 조정자가 실행 순서와 시점을 조정한다. 가벼운 정적 검사도 점유를 알리되 전체 DB 검사와 구분한다.
- 전체 하네스 예약은 코더·게이트·평가·다음 반복까지 포함한다. 한 게이트의 출력 종료나 클러스터 잠시 정지만으로 다음 담당에게 넘기지 않는다. 소유 전체 프로세스 종료와 최종 클러스터 STOP 영수증을 확인한 뒤 해제한다.
- 각 gate permit은 **실제 호스트의 PID·생성 시각·부모·cwd·intent/branch·슬롯/포트·새 nonce**, 요청의 waiting 상태와 기존 permit 부재를 대조해 한 번만 발급한다. granted→소비→admitted를 확인하고 다음 반복은 새 요청으로 확인한다. 종료된 PID/이전 nonce를 다시 승인하지 않는다.
- 재개 전 기존 session ID·실행 로그·요청·소유 프로세스를 조회한다. sandbox의 ProcessNotFound나 출력 정지는 호스트 프로세스 종료 근거가 아니다. 진행 중인 하네스·DB를 중복 시작하거나 다른 담당의 프로세스를 중단하지 않는다.
- 공식 검사 중 소스와 manifest를 고정한다. 수정은 같은 intent의 다음 코더 반복으로 넘기고, 달라진 소스를 이전 실행의 PASS와 연결하지 않는다.

### 5.3 검증과 fixture — 제품 실패를 정확히 재현한다

- **실제 RED**는 기대한 동작의 assertion 실패로 확인한다. DB 권한 거절·모듈 로드 실패·예약 guard 거절·테스트 0개 실행은 환경/준비 실패로 별도 기록한다. DB 변경 전 동작을 확인해야 하면 보존한 기존 소스와 새 테스트를 격리 복제에서 실행하고 원본 소스 일치를 검증한다.
- fixture는 고유 marker/DB와 정상 서비스·실제 runtime 권한을 우선 사용한다. 예상값과 실제 조회값을 분리하고 역할·멤버십·행 수·집계·상태를 대조해야 ready로 표시한다. immutable 날짜/append-only 원장은 필요한 값으로 최초 생성한다. 실제 실습 완료를 검증할 때 완료 proof/run/event/시간을 미리 만들어 성공을 대신하지 않는다.
- 잠금·늦은 응답·취소 검사는 실제 잠금 대기/commit·요청 취소·응답 순서를 관측해 재현한다. 임의 sleep·timeout 증가만으로 경합을 맞추지 않는다. 요청 종료 뒤 비동기 작업·연결·트랜잭션도 정리한다.
- 실패 사례와 영향 있는 기존 회귀부터 검사하고, 공식 게이트는 원래 범위로 실행한다. 실패를 없애려는 테스트 삭제·skip·보호 검사 해제·게이트 축소는 하지 않는다. 같은 소스의 같은 검사는 새 변경·실패·미해결 위험이 있을 때만 반복한다.

완료 기준: RED 원인과 GREEN 대상이 매핑되고, 필수 게이트·교차 모델 판정·skip 사유·소스 식별 근거를 원래 intent와 로그에서 확인할 수 있다. 저자 검사·독립 검사·전체 검사의 중복 수치를 합산하지 않는다.

### 5.4 실제 Chrome — DB 준비와 빌드의 순서를 지킨다

현재 통합 E2E의 실행 순서는 아래와 같다.

1. 최종 하네스 종료·ACCEPT·전용 클러스터 STOP → 통합 상위/빌드 child SHA와 제품 blob 일치·tracked clean 고정.
2. 최종 fixture 소스에서 정상 Builtin compile/생성물 확인 → 정확한 고유 DB 예약 → migration·fixture 준비 → 정상 runtime 서비스로 expected/observed 대조와 public ready 영수증.
3. 같은 candidate 환경으로 정식 빌드 → 실제 `BUILD_ID`, 앱·워커 PID/시작 시각·소스·DB·origin·cookie 설정 일치 확인.
4. 예약된 로그인 전환/원복 경로 확인 → Chrome **테스트1→테스트2→테스트3** 직접 조작 → 앱·워커·브라우저와 시험 데이터 원복.

**BUILD_ID는 DB prepare의 선행조건이 아니다.** fixture source SHA와 build child SHA가 다르면 제품 blob/생성물 일치 근거와 두 SHA를 구분해 기록한다. 준비·빌드·실행 중 대상이 바뀌면 영향을 받은 단계부터 정합성을 다시 확인한다.

후보 환경은 앱과 워커에 함께 전달하며 원본 `.env`에 저장하지 않는다. 합성 로그인은 승인된 독립 cookie와 로컬 Host/Origin/CSRF 검사를 사용하고 기존 인증 cookie를 추출하거나 덮지 않는다. 로그인 helper 시작만으로 로그인 완료라고 하지 않는다. 이전 화면의 스크린샷이나 실행 중인 오래된 앱은 새 소스의 E2E 근거가 아니다. React/JSDOM·API 검사와 실제 Next/Chrome 조작 결과를 구분한다.

### 5.5 막혔을 때 — 최초 원인에 맞춰 최소 복구한다

실패 명령·최초 오류·실제 대상·기대/관측·시도한 복구를 기존 로그 한 곳에 남긴다. 같은 명령을 반복하기 전에 아래 분류로 다음 조치를 정한다.

| 관측 | 다음 조치 |
| --- | --- |
| Node/env/모듈 불일치, 빈 bootstrap 변수 | 실제 자식 런타임·환경 로더·변수 부재를 대조하고 승인된 격리 환경에서 복구한다. 유효한 원본 암호나 설정을 바꾸지 않는다. |
| 공유 cache/Vite 임시 파일 EPERM | 원래 설정·suite를 유지하는 지원된 cache/loader 방식을 확인하고 변경점과 결과를 기록한다. 임의 config/globalSetup 우회로 성공을 만들지 않는다. |
| DB/RLS/fixture/immutable/FK 오류 | 대상 DB·실제 역할·생성 순서·트랜잭션 정리를 확인하고 본인 fixture/격리 환경만 고친다. 제품 결함이면 재현을 구현 담당에게 넘겨 같은 intent/harness로 수정한다. |
| 오래 걸리거나 출력이 없음 | 실행 session·실제 프로세스·최신 로그·예약 상태를 확인해 진행/정지/실패를 구분한다. 정상 실행을 중복 시작하지 않는다. |
| Chrome 연결/URL 확인 실패 | 확장·연결 상태 → 실제 브라우저/탭 재조회 → 같은 허용 브라우저의 탭 재선택/새 탭 → 허용된 진단 순서로 복구한다. URL 안전 확인을 다른 입력 수단으로 우회하지 않는다. |
| 도구 자동 승인 timeout/거절 | 프로세스 시작 전 실패인지, 일부 실행됐는지 영수증/상태로 먼저 확인한다. 기존 사용자 승인 근거와 허용된 재시도 범위를 확인하고, 해결되지 않는 권한은 정확한 차단 조치·이유·필요 범위만 사용자에게 요청한다. |
| 로그가 NUL·긴 manifest로 읽기 어려움 | 줄 길이 제한·필요한 구간/고정 패턴으로 읽는다. 비밀값·cookie·원본 env·운영 원문을 출력하거나 평가자에게 보내지 않는다. |

외부 모델 평가도 기존 승인된 제공자·전송 범위를 지킨다. 외부 승인·인증이 필요한 동안 독립적인 읽기 리뷰·문서는 계속하며, 해결되지 않은 전제와 다음 담당을 명시한다.

### 5.6 종료·재개 기록 — 테스트 결과와 복원을 함께 남긴다

- PowerShell의 native exit code는 명령 직후 `$LASTEXITCODE`로 보존한다. PostgreSQL `pg_isready`는 **no response=2**다. 명령 자체 실행 실패·다른 포트 응답과 구분하고, 소유 프로세스 종료/STOP 영수증과 함께 확인한 뒤 예약을 해제한다.
- 종료된 본인 소스 복제본이 lint에 중복 포함되면 절대 경로·소유·완료 상태를 검증해 ignored 보관 경로로 옮기고 이동 영수증을 남긴다. 실행 중 산출물과 gate/eval 원본 로그는 보존하며 lint 규칙을 바꾸지 않는다.
- 앱·워커를 원래 DSN/cookie 조건의 검증된 최신 빌드로 복원하고 브라우저의 선택 커뮤니티·경로·theme/viewport·시험 cookie를 되돌린다. 본인 후보 DB는 정확한 이름/marker·영수증·무접속을 확인해 정상 정리한다. 미정리 자원은 ID/소유자/이유를 기록해 인계한다.
- 최종 기록은 **소스 SHA/manifest·BUILD_ID·대상 DB/역할·명령·PASS/FAIL/SKIP/미실행/환경 실패·평가 판정·증거 경로·예약 해제/복원·남은 일과 담당**을 구분한다. DB/SQL 관측을 Chrome 통과로, child 통과를 최종 통합 통과로 확대하지 않는다. 수행하지 않은 모델·운영 배포·청구서 대사는 미검증으로 남긴다. 최종 원격 병합·배포 경계는 §6을 따른다.

## 6. 통합·PR·최종 병합의 경계

하위 브랜치 → 사용자 지정 통합 브랜치의 내부 통합은 사용자 요청 범위에서 리뷰·검증 후 진행할 수 있다. 통합 전에 최신 원격 main을 확인하고 이미 병합된 동료 변경이 조상/최종 diff에서 보존되는지 확인한다.

**원격 최종 PR의 병합, main 병합, 자동 병합 설정, 최종 배포는 반드시 사용자가 직접 한다.** 세션은 구현·테스트·내부 통합·커밋·푸시·PR 작성/갱신까지 진행하고 결과를 전달한다. 과거 요청의 머지 승인을 이번 최종 머지 권한으로 재사용하지 않는다. 머지 버튼·gh pr merge·merge API를 실행하지 않는다.

PR 제목·본문은 최종 실제 diff의 동작·검증·한계를 반영한다. push를 시작한 후 독립된 다음 작업을 계속하되 마지막에는 원격 SHA로 반영 여부를 확인한다. CI 성공, 소스 병합, 로컬 빌드, 운영 배포를 각각 구분해 보고한다.
