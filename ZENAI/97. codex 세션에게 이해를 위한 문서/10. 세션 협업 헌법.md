## 2. 변경 최소화와 동료 코드 보존

- PR은 합의한 사용자 목적만 다룬다. 독립 기능·환경 문제·정리를 끼워 넣지 않는다. 범위 확대가 필요하면 근거와 실제 영향부터 공유한다.
- 호출자·저장 경로·테스트를 먼저 조사한다. 기존 함수·컴포넌트·패턴을 재사용하고 요청을 완전히 해결하는 최소 변경을 택한다.
- 동료의 의도·권한검사·오류 처리·재시도·배포 SQL을 보존한다. 충돌 해결은 양쪽 변경의 의미를 확인하고 최신 main과 통합 전후 diff·조상 관계로 누락을 확인한다.
- 테스트는 기존 suite를 우선 확장하며 변경 동작과 위험 경계만 추가한다. 보안·데이터 무결성·필수 게이트는 유지한다. 새 변경·실패·미해결 위험 없이 같은 검사를 반복하지 않는다.
- 작업별 intent 하나에 계획·수용 기준·기준↔테스트 매핑을 모은다. 재시도마다 문서를 늘리지 않는다. src 변경은 저장소의 **intent → harness → 게이트 4종 → 교차 모델 판정** 경로를 따른다. 사용자의 명시적 예외만 예외다.
- 로그·스크린샷·일회성 검증 도구는 ignored `.context`에 둔다. 사용자가 요청한 Obsidian·Jira 근거만 해당 위치에 보강한다.
- 서식·줄바꿈·정렬을 보존하고 migration journal은 필요한 항목만 수정한다. 불필요한 추상화·설정·의존성을 추가하지 않는다.
- 커밋 전 모든 변경 파일의 필요성을 설명할 수 있어야 한다. 무관 변경·중복 문서·서식 소음을 제거한다. 파일 수·줄 수를 줄이려고 필요한 검증을 삭제하지 않는다.

### 2.0 커밋·푸시 전 main 최신화와 동료 변경 보존

**2026-10-31 사용자 추가 지시:** 다른 사람이 작성한 작업은 함부로 수정하지 않는다. 커밋·푸시 전에 아래 순서로 최신화와 침범 여부를 상세 검사한다.

1. 중앙 프로젝트의 실제 브랜치·HEAD·`git status`·staged/미추적 파일·진행 중 병합을 확인하고 작성자와 담당 범위를 구분한다. 기존 변경이 있으면 담당자와 보존·통합 순서를 맞춘 뒤 진행한다.
2. 사용자 지정 작업 브랜치에서 커밋·푸시 전에 **`git pull origin main`**으로 최신 main을 통합한다. 미커밋 작업은 먼저 파일·index·병합 상태와 복원 근거를 보존해 깨끗한 상태를 준비한다. pull 실패·충돌은 해결되지 않은 상태로 기록하고 커밋·푸시를 보류한다. 최종 main 병합·배포 권한은 여전히 사용자에게 있다.
3. 최신 main과 공통 조상·작업 HEAD, 동료의 관련 열린/병합된 PR·커밋·변경 파일을 대조한다. 열린 PR은 pull로 포함되지 않으므로 겹치는 기능·파일·migration 번호·공용 API를 별도로 조사하고 담당자와 조정한다. 소유자 동의 없이 열린 PR을 가져와 수정하거나 대체·폐기하지 않는다.
4. 통합 전후 diff에서 동료의 로직·권한·검증·오류 처리·설정·테스트가 삭제되거나 과거 값으로 돌아가지 않았는지 줄과 동작 단위로 상세 검사한다. 충돌이 없다는 사실이나 조상 포함만으로 보존 완료를 선언하지 않는다. 충돌 해결에는 양쪽 의도를 반영하고, 판단이 필요한 타인 변경은 소유자에게 확인한다.
5. 기준 main SHA·관련 PR/작성자·겹친 파일·보존 확인·충돌 해결·남은 차이를 기록한다. 최신화로 최종 소스가 달라졌으면 영향받은 게이트·회귀·최신 정식 빌드·E2E를 다시 검증한다. 푸시 직전 main이 다시 갱신됐으면 동기화·검사를 반복하고, 원격 이력을 강제 덮어써 동기화를 대신하지 않는다.

완료 기준: 최신 main을 반영한 소스와 실제 검증 대상이 일치하고, 동료 변경의 보존과 열린 PR 중복/충돌 검토 근거가 있으며, 미해결 침범·충돌이 없다.
### 2.1 사용자 업무 한 건의 책임과 대기 종료

- 사용자 업무 한 건마다 주 담당 구현 세션 하나가 의도·구현·결함 수정·검증 결과 취합·PR·정리까지 전체 완료를 책임진다. 검증 책임과 직접 실행 담당은 구분한다. 통합·E2E·로컬/운영 Chrome 검사는 지정 테스트 세션이 실행하고 구현 세션이 결과를 취합한다. 구현 중 필요한 단위·표적 검사와 저장소 필수 하네스 절차는 기존 지시를 따르며, 사용자 테스트 요청의 담당 배정은 §2.2를 따른다. 작업을 여러 구현 세션 사이에서 계속 왕복시키지 않는다.
- 다른 업무가 있으면 독립된 파일·자원으로 그 업무를 진행한다. 공용 시험 환경이 점유됐어도 DB 없는 준비·기존 근거 정리 등 실제로 필요한 독립 작업을 수행할 수 있다.
- 진행 가능한 일이 없으면 막힌 단계·필요한 자원·다음 담당·재개 조건·증거 경로를 한 번 인계하고 **현재 턴을 끝낸다**. 대기만을 위한 sleep·반복 상태 조회·메시지 수신 확인을 계속하지 않는다.
- 자원을 해제하거나 선행 결과를 만든 세션이 영향받는 담당에게 한 번 연락한다. 연락을 받은 세션은 소스·예약·프로세스 상태를 다시 확인한 뒤 그 지점부터 재개한다. 연락을 기다리기 위한 상시 실행은 두지 않는다.

### 2.2 테스트 요청은 테스트 세션으로 이관한다

**2026-11-02 사용자 지시:** 구현 세션이 테스트·재검사·남은 검사 진행 요청을 받으면 지정 테스트 세션으로 이관한다. 별도 명시 지시 없이 구현 세션이 직접 대신 수행하지 않는다. 이 역할 규칙은 과거 ‘구현 조정자가 전체/E2E를 주관한다’는 표현보다 우선한다.

1. 현재 운영 중인 지정 테스트 세션에 기존 채팅 도구로 한 번 전달한다. 새 세션·보조 에이전트나 중복 검사를 시작하지 않는다. 지정 담당이 없으면 담당을 조정한 뒤 실행한다.
2. 인계에는 최신 SHA/BUILD_ID·환경/계정·자원 소유권·실행 및 미완료 행렬·기존 결과/스크린샷/로그의 절대 경로·시험 중 바뀐 설정·복원 계획·정확한 재개 지점을 포함한다. 수행하지 않은 검사를 완료로 전달하지 않는다.
3. Chrome·앱·DB 조작은 테스트 담당 한 곳에 맡긴다. 구현 세션은 직접 조작을 멈추고 독립적인 구현/문서 업무나 결과 취합을 한다. 테스트 담당이 제어권을 반환해도 그것만으로 구현 세션이 테스트를 대신할 권한이 생기지 않는다.
4. Chrome 도구 문제는 테스트 담당이 §5.5.1로 직접 확인한다. 검색 목록만으로 부재를 단정하거나 Chrome 검사를 API 검사로 자동 대체하지 않는다. 직접 도구가 실제 제공되지 않거나 정책상 중단되면 구체적인 호출/제공 상태·증거·재개 조건을 인계하고 턴을 끝낸다. 상태 변화 없는 재시작 요청·담당 간 왕복·대기 감시는 하지 않는다.
5. 테스트에서 제품 결함을 발견하면 재현·실행 로그를 구현 담당에게 넘겨 같은 intent/harness로 수정한다. 수정 후 최신 후보를 테스트 담당에게 한 번 인계하여 영향받은 검사를 재개한다. 결과의 Chrome/API/단위 구분·PASS/FAIL/미실행·설정 복원 확인 뒤에만 전체 완료를 판단한다.

완료 기준: 테스트 담당에게 실제 전달됐고, 필수 맥락과 자원 소유권이 명시돼 있으며, 구현 세션의 중복 실행이 중단돼 있다. 메시지 송신 성공은 검사 완료를 뜻하지 않는다.

### 2.3 Jira 작성 원칙 — 기능과 해결 내용만 간결하게

**2026-11-03 사용자 지시:** Jira 본문·댓글·첨부 문서는 해당 기능·사안 자체를 설명한다. 이 절은 Jira에 상세 작업·검사 기록을 남기던 과거 관례보다 우선한다.

- 버그 카드는 증상, 확인된 원인, 해결 방법을 짧게 쓴다. 미확정 원인은 추정으로 표시한다.

- 상세 의도·검사 증거·진행 장애·인계는 기존 intent/ignored 기록과 Obsidian에 보관하고 Jira에 복제하지 않는다.

- 저장 전 본문·댓글·새 첨부가 이 원칙에 맞는지 확인한다. 기능/버그 요약과 Jira 업무 상태를 일치시키되 문서 정리만으로 상태를 변경하지 않는다.

## 4. 브랜치·파일·환경의 소유권

- 사용자 지정 통합 브랜치를 부모로 각 구현 담당이 별도 하위 브랜치·worktree에서 작업한다. 동일 checkout의 HEAD/index를 여러 세션이 동시에 바꾸지 않는다. 통합 checkout의 Git 변경은 조정자 한 곳에서 수행한다.
- 시작 전에 담당 파일과 공용 API/props 계약을 나눈다. 같은 파일 수정이 필요하면 소유자와 순서를 조정한다. migration 번호도 조정자가 배정한다.
- **3002 앱·기존 DB·Chrome·migration·공용 문서**는 소유자와 예약을 알린 뒤 사용한다. 다른 세션의 앱을 재시작하거나 DB·역할암호·.env를 바꾸지 않는다. Chrome 입력은 한 번에 한 세션만 한다.
- 기존 Docker **zen-ai-postgres-1 / zen-ai-litellm-local 두 개**를 사용한다. 새 컨테이너 추가가 필요하면 사용자와 먼저 범위를 합의한다. 전체 DB 검사에 role bootstrap이 필요하면 기존 PostgreSQL 컨테이너 안의 담당 전용 빈 클러스터를 사용한다. 같은 클러스터의 별도 DB는 역할 비밀번호를 격리하지 못한다.
- 임시 클러스터/포트/프로세스/fixture는 소유자·대상·생성 근거를 기록한다. 불필요한 본인 시험 프로세스만 신원을 확인해 종료하며, 로컬 시험 데이터는 §5.6에 따라 보존한다. 기존 사용자 자료와 타 세션 자원도 보존한다.

각 사용자 업무의 검증 기록에 아래 항목을 **모두 명기하고 실행**한다. 기존에 수행했던 검사 종류를 생략하지 않는다. 같은 최종 소스의 유효한 결과는 근거를 연결해 재사용하되, 제품 변경·실패·미해결 위험이 생기면 영향받은 검사를 다시 수행한다.

### 5.0.1 로컬·운영 각각의 세 에이전트 검증

**2026-10-30 사용자 추가 지시:** 로컬과 배포 후 운영 **각각**에서 ① Builtin 회의 에이전트(`meeting.assistant`), ② 만들어진 일반 에이전트, ③ 만들어진 하네스 에이전트를 **모두 별도로 검증**한다. 이 기준은 이번 `feat/gpt-sol-6.1-fix`에도 즉시 적용한다. 한 종류의 성공을 다른 종류의 통과로 기록하지 않는다.

- 각 환경의 세 종류마다 관리 화면의 모델 선택·설정 저장·새로고침 후 보존을 실제 클릭·입력으로 확인하고, 해당 에이전트를 채널에서 직접 호출해 실제 제공자의 최종 응답까지 확인한다. Builtin은 실행 release 상태/필요한 업그레이드까지, 일반·하네스는 생성된 에이전트의 설정/실행 버전과 하네스 도구·후속 호출 흐름까지 확인한다.
- 이번 수정의 제거 모델→유효 모델 재선택, 저장 오류 복구, 허용 목록·추론 설정·기존 설정 보존, Builtin 모델/release 전환을 해당 경로에서 검사한다. 실패·취소·권한·버전 충돌 등 관련 회귀도 원래 수용 기준과 연결한다. 운영에서 장애를 강제로 만들거나 업무 에이전트를 임의 변경하지 않고, 위험 경계 재현은 격리 환경에서 수행한다.
- 검증표에 **로컬×3종 / 운영×3종의 최소 여섯 칸**을 만들고 각 칸의 대상 ID·실행 버전·모델·소스/배포 SHA·실제 UI 조작·run/trace·최종 응답·PASS/FAIL/미실행·정리 상태를 따로 기록한다. 자동 E2E·API·직접 사용자 조작을 구분한다. 하나라도 미실행이면 전체 에이전트 검증 완료로 보고하지 않는다.

### 5.1 실행 전 확인 — 대상·권한·환경을 먼저 맞춘다

1. **시험 대상:** 기존 intent의 수용 기준↔테스트 매핑에 사용자 흐름·역할·상태·경계를 적고, 이번 실행이 표적 회귀·공식 전체 게이트·읽기 리뷰·실제 Chrome 중 무엇인지 표시한다. worktree, branch/base/head, 미커밋 변경, 실행 명령, 기대 결과와 증거 경로를 고정한다. “모든 경우”는 이 유한한 행렬로 판단한다.
2. **런타임:** package.json에 맞는 실제 Node 실행 파일과 의존성을 확인한다. 앱과 같은 `scripts/load-env.ts` / `@next/env`로 환경을 해석하고, 대상 DB·포트·역할·인증 만료·모델/도구 가용성을 안전한 식별 정보로 대조한다. 비밀값 전체를 출력하거나 시험 편의를 위해 원본 `.env`를 고치지 않는다.
3. **실행 전 점검:** fixture·검증 도구는 먼저 구문 검사, 필요한 실제 모듈 export/alias 확인, 예약 누락 시 DB 연결 전에 거절되는지 확인한다. DB 없는 UI/mock 시험은 환경 파일과 DB/bootstrap 변수의 **실제 부재**를 자식 프로세스에서 확인한다. 빈 문자열은 부재가 아니다. 기존 Vitest config/globalSetup과 보호 검사를 유지한다.
4. **DB 격리 방식:** role bootstrap·암호 갱신이 있는 전체 검사는 §4의 빈 전용 클러스터로, 기존 역할을 재사용하는 브라우저 후보 DB는 정확한 예약과 역할 보존 조건으로 구분한다. 후자는 생성 전 기존 역할 속성·멤버십을 확인하고 migration/seed 뒤에도 같음을 대조한다. 조건이 다르면 준비 미완료로 중단하며 원본 DB로 전환하지 않는다.
5. **착수 조건:** 자원 소유자·예약과 현재 메모리를 확인한다. 예약 대기 중에는 필요한 독립 준비·읽기 리뷰·문서를 진행하고, 진행할 일이 없으면 §2.1에 따라 재개 조건을 남기고 턴을 끝낸다. 승인된 기존 범위는 그대로 사용하고, 새 컨테이너·원본 역할 변경처럼 범위가 늘 때만 필요한 승인을 받는다.

완료 기준: 대상·기대 결과·환경·격리 방식·실행 권한·예약이 기존 시험 기록에 남아 있고 서로 일치한다. 계획이나 도구 구문 검사만으로 실제 DB/로그인/Chrome 준비 완료를 선언하지 않는다.

### 5.2 자원 예약 — 전체 하네스 수명과 실제 프로세스를 확인한다

- 이 PC에서는 **공식 전체 검사 1개, Vitest workers 최대 2**로 운영하며, 전체 검사 중 빌드·다른 DB 준비를 겹치지 않는다. 메모리가 부족하면 조정자가 실행 순서와 시점을 조정한다. 가벼운 정적 검사도 점유를 알리되 전체 DB 검사와 구분한다.
- 전체 하네스 예약은 코더·게이트·평가·다음 반복까지 포함한다. 한 게이트의 출력 종료나 클러스터 잠시 정지만으로 다음 담당에게 넘기지 않는다. 소유 전체 프로세스 종료와 최종 클러스터 STOP 영수증을 확인한 뒤 해제한다.
- 각 gate permit은 **실제 호스트의 PID·생성 시각·부모·cwd·intent/branch·슬롯/포트·새 nonce**, 요청의 waiting 상태와 기존 permit 부재를 대조해 한 번만 발급한다. granted→소비→admitted를 확인하고 다음 반복은 새 요청으로 확인한다. 종료된 PID/이전 nonce를 다시 승인하지 않는다.
- 재개 전 기존 session ID·실행 로그·요청·소유 프로세스를 조회한다. sandbox의 ProcessNotFound나 출력 정지는 호스트 프로세스 종료 근거가 아니다. 진행 중인 하네스·DB를 중복 시작하거나 다른 담당의 프로세스를 중단하지 않는다.
- 공식 검사 중 소스와 manifest를 고정한다. 수정은 같은 intent의 다음 코더 반복으로 넘기고, 달라진 소스를 이전 실행의 PASS와 연결하지 않는다.

### 5.3 검증과 fixture — 제품 실패를 정확히 재현한다

**검증 책임과 실행 담당:** §2.1의 구현 주 담당이 전체 검증의 누락 방지와 결과 취합을 책임지며, 실제 테스트 요청·통합/E2E 실행은 §2.2의 지정 테스트 세션으로 이관한다. 같은 최종 소스와 환경의 증거를 통합하고, 여러 업무를 합친 경우 최종 통합 소스를 고정해 전체 변경의 게이트·빌드·E2E·직접 조작을 확인한다. 단위/API 통과를 실제 UI·운영 검증으로 확대하지 않는다. 중복 실행을 줄이되 필수 검사 종류나 범위를 줄이지 않는다.

- **실제 RED**는 기대한 동작의 assertion 실패로 확인한다. DB 권한 거절·모듈 로드 실패·예약 guard 거절·테스트 0개 실행은 환경/준비 실패로 별도 기록한다. DB 변경 전 동작을 확인해야 하면 보존한 기존 소스와 새 테스트를 격리 복제에서 실행하고 원본 소스 일치를 검증한다.
- fixture는 고유 marker/DB와 정상 서비스·실제 runtime 권한을 우선 사용한다. 예상값과 실제 조회값을 분리하고 역할·멤버십·행 수·집계·상태를 대조해야 ready로 표시한다. immutable 날짜/append-only 원장은 필요한 값으로 최초 생성한다. 실제 실습 완료를 검증할 때 완료 proof/run/event/시간을 미리 만들어 성공을 대신하지 않는다.
- 잠금·늦은 응답·취소 검사는 실제 잠금 대기/commit·요청 취소·응답 순서를 관측해 재현한다. 임의 sleep·timeout 증가만으로 경합을 맞추지 않는다. 요청 종료 뒤 비동기 작업·연결·트랜잭션도 정리한다.
- 실패 사례와 영향 있는 기존 회귀부터 검사하고, 공식 게이트는 원래 범위로 실행한다. 실패를 없애려는 테스트 삭제·skip·보호 검사 해제·게이트 축소는 하지 않는다. 같은 소스의 같은 검사는 새 변경·실패·미해결 위험이 있을 때만 반복한다.

완료 기준: RED 원인과 GREEN 대상이 매핑되고, 필수 게이트·교차 모델 판정·skip 사유·소스 식별 근거를 원래 intent와 로그에서 확인할 수 있다. 저자 검사·독립 검사·전체 검사의 중복 수치를 합산하지 않는다.

### 5.4 실제 Chrome — DB 준비와 빌드의 순서를 지킨다

현재 통합 E2E의 실행 순서는 아래와 같다.

1. 최종 하네스 종료·ACCEPT·전용 클러스터 STOP → 통합 상위/빌드 child SHA와 제품 blob 일치·tracked clean 고정.
2. 최종 fixture 소스에서 정상 Builtin compile/생성물 확인 → 정확한 고유 DB 예약 → migration·fixture 준비 → 정상 runtime 서비스로 expected/observed 대조와 public ready 영수증.
3. 같은 candidate 환경으로 정식 빌드 → 실제 `BUILD_ID`, 앱·워커 PID/시작 시각·소스·DB·origin·cookie 설정 일치 확인.
4. 예약된 로그인 전환/원복 경로 확인 → 지정된 **최종 검증 주관 한 세션**이 Chrome 전체 통합 행렬 직접 조작(다른 테스트 세션은 준비·로그 분석 지원) → 앱·워커·브라우저의 임시 실행 설정 복원·로컬 시험 데이터 보존(§5.6).

**BUILD_ID는 DB prepare의 선행조건이 아니다.** fixture source SHA와 build child SHA가 다르면 제품 blob/생성물 일치 근거와 두 SHA를 구분해 기록한다. 준비·빌드·실행 중 대상이 바뀌면 영향을 받은 단계부터 정합성을 다시 확인한다.

후보 환경은 앱과 워커에 함께 전달하며 원본 `.env`에 저장하지 않는다. 합성 로그인은 승인된 독립 cookie와 로컬 Host/Origin/CSRF 검사를 사용하고 기존 인증 cookie를 추출하거나 덮지 않는다. 로그인 helper 시작만으로 로그인 완료라고 하지 않는다. 이전 화면의 스크린샷이나 실행 중인 오래된 앱은 새 소스의 E2E 근거가 아니다. React/JSDOM·API 검사와 실제 Next/Chrome 조작 결과를 구분한다.

외부 모델 평가도 기존 승인된 제공자·전송 범위를 지킨다. 외부 승인·인증이 필요한 동안 독립적인 읽기 리뷰·문서는 계속하며, 해결되지 않은 전제와 다음 담당을 명시한다.

### 5.5.1 실제 사용자 조작 연결의 진단과 재개

**2026-11-03 사용자 요청 반영:** 이번 테스트에서 실제 재개·완주한 절차를 기준으로 한다. 도구 연결, 앱 인증, 제품 동작을 각각 판정하고, 장애 내부 원인이 미확정인 부분은 미확정으로 남긴다. 이 절은 과거의 일괄 재시작 안내보다 우선한다.

#### 시작·재개 순서

1. **재개 지점 고정:** 기존 시험 행렬에서 마지막 완료 case와 다음 동작 하나를 확인한다. source SHA/BUILD_ID·앱/워커·DB/시험 계정·Chrome 소유자·browser/tab/URL·임시 설정과 복원 대상을 대조한다. 연결 복구만으로 이미 끝난 전체 검사를 다시 시작하지 않는다.
2. **직접 제공된 공식 도구 확인:** 이 대화의 `mcp__cua_repl.js`와 반환 문서를 따른다. `ALL_TOOLS`나 deferred 검색의 cua/browser 0건은 도구 부재의 근거가 아니다. 새 커널·reset 직후 첫 호출은 `await cua.getState();` 한 건만 제출한다. 맥락 요약 뒤 기존 커널을 이어 쓰면 도구 지침의 `cua.rewriteDocumentation()`으로 문서를 다시 확인한다.
3. **현재 탭 선택:** 반환 목록의 실제 Chrome browser ID·tab ID/URL로 선택한다. 이전 턴의 탭 ID나 AX 요소 번호는 다시 관측한다. stale tab/`Debugger unattached`는 같은 브라우저의 현재 탭 재조회 또는 문서가 허용한 새 시험 탭으로 확인한다. Chrome 입력은 지정 테스트 담당 한 곳만 수행한다.
4. **조작 후 관측:** 현재 URL과 페이지를 확인하고 클릭·입력 하나를 실행한 뒤 변경된 화면을 확인한다. 저장·전송 결과가 불명확하면 현재 화면과 읽기 전용 run/event 기록으로 반영 여부를 먼저 확인한다. 결과 확인 없이 같은 요청을 재전송하지 않는다.

완료 기준: 공식 Chrome의 현재 URL/화면 확인과 실제 조작 후 결과 재관측이 모두 성공했다. 그 뒤 해당 제품 case의 수용 기준을 검사한다. 도구 조회·로그인·API 성공은 제품 E2E 통과와 별도다.

| 관측 | 다음 조치와 판정 |
| --- | --- |
| Windows `sky.get_window_state`가 현재 URL 확인 실패 | Windows native 경로의 관측으로 기록한다. 공식 Chrome 확장의 연결 실패로 확대하지 않는다. 정책이 해당 턴 중단을 요구하면 즉시 따르고 같은 턴 다른 입력기로 우회하지 않는다. 별도 새 턴의 공식 Chrome 성공도 native 경로 복구를 뜻하지 않는다. |

### 5.5.2 테스트 막힘의 협업 피드백

§2.2의 담당 분리와 §3의 사용자 승인된 공유 범위를 따른다. 테스트 담당이 Chrome을 유지하고, 구현 담당은 로그·관련 코드·기존 정책을 읽어 원인 판별과 필요한 수정을 맡는다. 제어권 반환이나 상대의 조언만으로 구현 담당이 UI 검사를 대행하지 않는다.

1. **첫 의미 있는 막힘을 전달한다:** 기대/실제·재현 단계·SHA/BUILD_ID·계정 종류·run/event·마지막 call/output·시도한 복구·절대 증거 경로·현재 임시 변경·정확히 필요한 판별을 영향받는 담당에게 한 번 보낸다. 사용자가 승인한 기존 세션 간 공유만 사용한다.
2. **증거로 가설을 좁힌다:** 제공자 재시도 정책, HITL pending, redaction, 취소 wrapper 등 관측한 차이는 관련 소스/기준 main/실행 기록과 대조한다. 제품 결함·기존 계약·시험 도구/fixture 오류·제어 호출 오류를 구분한다. 이번 Builtin maxRetries=0, 취소 후 not_executed 반환, 기존 보안 fallback 사례처럼 표시나 span 이름만으로 회귀를 단정하지 않는다. 구현 담당의 코드 판독은 테스트 담당의 실제 UI 재현을 대신하지 않는다.
3. **한 원인에 한 조치를 적용한다:** 제품 수정은 같은 intent/harness 경로로 넘긴다. fixture 오류는 보호 장치를 보존한 정상 입력으로 교정하고 과거 실패를 남긴다. 연결/호출 문제는 §5.5.1을 따른다. 새 후보를 받으면 신원·빌드를 다시 맞춰 영향받은 case를 재검증한다.
4. **결과와 다음 담당을 닫는다:** 실제 재관측·PASS/FAIL/미실행·복원 상태와 남은 항목을 한 번 회신한다. 변경 없는 재시작/수신 확인/담당 왕복은 반복하지 않는다. 주 담당이 PR/Jira/Obsidian을 취합하고, 테스트 담당은 지정 증거 원장을 갱신해 중복 편집을 피한다.

완료 기준: 가설과 확인된 원인이 구분돼 있고, 조치 후 실제 재검증 또는 명확한 미완료/재개 조건이 기록돼 있으며, 임시 변경과 자원 소유권이 다음 담당에게 전달됐다. 메시지 송신 성공은 장애 해결이나 검사 완료가 아니다.

## 6. 통합·PR·최종 병합의 경계

하위 브랜치 → 사용자 지정 통합 브랜치의 내부 통합은 사용자 요청 범위에서 리뷰·검증 후 진행할 수 있다. 통합 전에 최신 원격 main을 확인하고 이미 병합된 동료 변경이 조상/최종 diff에서 보존되는지 확인한다.

**원격 최종 PR의 병합, main 병합, 자동 병합 설정, 최종 배포는 반드시 사용자가 직접 한다.** 세션은 구현·테스트·내부 통합·커밋·푸시·PR 작성/갱신까지 진행하고 결과를 전달한다. 과거 요청의 머지 승인을 이번 최종 머지 권한으로 재사용하지 않는다. 머지 버튼·gh pr merge·merge API를 실행하지 않는다.

### 6.1 PR 생성 계정 — ericyum

**2026-10-31 사용자 지시:** ZEN AI의 PR은 `ericyum` 계정으로 생성한다.

1. 생성에 사용할 인증 경로에서 GitHub의 현재 사용자(`/user` 또는 동등한 인증 사용자 조회)를 확인하고 login이 정확히 `ericyum`일 때만 PR을 생성한다. 로컬 `git user.name`·커밋 작성자·Chrome 로그인·다른 커넥터의 계정은 해당 경로의 인증 증거를 대신하지 않는다.
2. 계정이 다르면 그 경로의 PR 생성을 중단하고, 기존에 승인된 `ericyum` 인증 경로를 사용한다. 사용할 수 없으면 사용자가 계정을 연결하도록 안내한다. 토큰·암호를 로그·문서에 출력하거나 저장하지 않는다.
3. 생성 응답과 원격 PR을 다시 조회해 작성자가 `ericyum`이고 head 브랜치/SHA가 검증 대상과 일치함을 확인한다. PR URL·작성자·head SHA를 인계에 남긴다. 다른 계정으로 잘못 생성한 PR의 닫기/재생성은 사용자 지시에 따라 수행한다.

완료 기준: 원격 PR 작성자 `ericyum`, 지정 브랜치·검증 SHA 일치, 최종 병합·배포는 사용자 수행.
PR 제목·본문은 최종 실제 diff의 동작·검증·한계를 반영한다. push를 시작한 후 독립된 다음 작업을 계속하되 마지막에는 원격 SHA로 반영 여부를 확인한다. CI 성공, 소스 병합, 로컬 빌드, 운영 배포를 각각 구분해 보고한다.
