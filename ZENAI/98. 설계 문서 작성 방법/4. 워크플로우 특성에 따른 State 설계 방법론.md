# 워크플로우 특성에 따른 State 설계 방법론

이 문서는 에이전트 전체에 하나의 State 구조를 일괄 적용하지 않고, **각 워크플로우의 특성에 따라 적절한 State 관리 방식을 선택하는 방법론**을 정리한다.

> **State 설계 방식은 에이전트 단위가 아니라 워크플로우 단위로 선택한다.** 하나의 에이전트 안에서도 요청별 실행, 지속형 Workflow, 병렬 State, Actor, Reducer, Saga와 Event Sourcing을 목적에 따라 함께 사용할 수 있다.

## 1. 워크플로우를 업무 단위로 분리

먼저 에이전트가 수행할 일을 **독립적으로 시작·완료하고 성공·실패를 판정할 수 있는 업무 단위**로 나눈다.

```text
회의록 에이전트
├─ 회의 녹화
├─ 회의 제어
├─ 회의록 확정·공유
├─ 회의록 검색·선택
└─ 회의록 질의
```

분리할 때 확인할 핵심 질문은 다음과 같다.

- 어디서 **시작하고 끝나는가?**
- 독립적으로 **성공·실패를 판정**할 수 있는가?
- 다른 업무와 **동시에 실행**될 수 있는가?
- 어떤 실제 데이터나 리소스를 **조회·변경**하는가?

## 2. 워크플로우의 성격을 분류

각 워크플로우를 다음 기준으로 분류한다.

| 판단 기준 | 핵심 질문 |
|---|---|
| 실행 시간 | 한 요청으로 끝나는가, 장시간 지속되는가? |
| 사용자 입력 | 실행 중 승인·선택·추가 입력을 기다리는가? |
| 동시 실행 | 같은 종류의 업무가 여러 개 동시에 실행될 수 있는가? |
| 리소스 공유 | 다른 Workflow와 같은 데이터를 조회·수정하는가? |
| 결과 병합 | 여러 실행 결과를 안전하게 합칠 수 있는가? |
| 외부 효과 | DB 쓰기, 공유, 결재, 발주 같은 효과가 있는가? |
| 복구 | 실패 후 중간 지점부터 재개해야 하는가? |
| 감사 | 누가 언제 무엇을 변경했는지 보존해야 하는가? |

## 3. 실행 수명에 따라 기본 State 구조 선택

### 3-1. 요청 한 번으로 끝나는 짧은 업무

회의록 검색·질문처럼 한 요청을 처리하고 끝나는 업무는 **요청별 실행(Per-invocation Subgraph)**으로 구성한다.

```text
사용자 요청
→ 해당 업무의 작은 Graph와 임시 State 생성
→ 실행·결과 반환
→ 이번 Graph와 임시 State 종료
```

- 상위 에이전트의 전역 State를 `search`로 바꾸지 않는다.
- 검색어·후보·선택 단계는 **이번 실행의 임시 State**에서만 관리한다.
- 다음 요청에도 필요한 결과만 상위 State나 DB에 전달한다.

### 3-2. 여러 요청에 걸쳐 이어지는 업무

회의 녹화·결재처럼 오랫동안 이어지는 업무는 **지속형 Workflow Instance**로 관리한다.

```text
workflow_id = recording:meeting-123
State = recording → pause → recording → stop
```

- 고유한 `workflow_id`를 가진다.
- 독립적인 **State와 Checkpoint**를 유지한다.
- 이후 사용자 요청이 들어오면 기존 Workflow를 찾아 이어서 실행한다.

### 3-3. 하나의 대상에 고정된 여러 상태 영역이 존재하는 업무

녹화·업로드·전사처럼 하나의 대상에 여러 종류의 상태가 동시에 존재한다면 **병렬 Statechart**를 고려한다.

```text
Recording Region     = recording
Upload Region        = completed
Transcription Region = processing
```

한 영역의 변경이 다른 영역을 덮어쓰지 않는다. 단, 업무 종류나 동시 실행 개수가 계속 증가한다면 병렬 State를 계속 추가하지 않고 **독립 Workflow Instance**로 분리한다.

## 4. 같은 리소스를 사용하는 Workflow의 충돌 처리

Workflow State가 분리되어 있어도 같은 회의·회의록·SAP 문서를 동시에 수정하면 충돌할 수 있다.

| 작업 조합 | 기본 처리 |
|---|---|
| 읽기 + 읽기 | 병렬 실행 허용 |
| 읽기 + 쓰기 | 쓰기 직전 실제 상태·version 재검사 |
| 쓰기 + 쓰기 | 순차 처리 또는 version 충돌 검사 |

### 순차 처리

동일 리소스의 명령을 **하나씩 처리**한다.

```text
meeting-123 전용 처리 순서
일시정지 → 종료 → 확정·공유
```

기존 백엔드의 공통 Handler나 **Actor**가 이 역할을 맡을 수 있다.

### Version 검사

Workflow가 읽은 version과 실행 시점의 현재 version을 비교한다.

```text
expected_version = 7
current_version  = 8
→ 오래된 State를 기준으로 한 요청이므로 실행 거부
```

> **Workflow State 분리**는 실행 과정의 간섭을 막고, **순차 처리·version 검사**는 같은 실제 리소스의 충돌을 막는다.

## 5. 공통 State에 반영할 결과의 병합 가능성 판단

서로 다른 Workflow가 공통 State를 수정한다면 각 필드의 결과를 안전하게 합칠 수 있는지 판단한다.

### 안전하게 병합할 수 있는 값

- `messages`·로그의 **추가**
- 태그·ID의 **합집합**
- 사용량의 **합산**

이런 값은 확정적인 **Reducer**로 병합한다.

```text
기존 ID ∪ 새 ID
messages + 새 messages
기존 사용량 + 새 사용량
```

### 안전하게 병합할 수 없는 값

- ID 목록 **전체 대체**
- 회의의 `recording`, `pause`, `stop`
- 결재의 승인·반려
- 금액·권한 변경

이런 값은 Reducer로 억지로 합치지 않고 다음 방법을 사용한다.

- **순차 처리**
- **version 검사**
- **Human in the Loop**

```text
authorized_meeting_ids 추가
→ 합집합 Reducer 사용 가능

authorized_meeting_ids 대체
→ version 검사 또는 순차 처리 필요
```

## 6. 여러 Workflow가 하나의 큰 업무를 구성할 때

독립 Workflow들이 정해진 순서와 조건에 따라 하나의 업무를 완성한다면 **Process Manager**를 둔다.

```text
구매요청 Workflow 완료 Event
→ Process Manager
→ 예산검증 Workflow 시작 Command
```

Process Manager는 다음을 담당한다.

- 완료 Event를 보고 **다음 Workflow 시작**
- 전체 업무의 **현재 단계와 Workflow 참조값** 관리
- 실패 시 **재시도·중단·보상 여부** 결정

각 Workflow의 내부 State를 직접 가져와 수정하지 않는다.

### 외부 효과의 보상 — Saga

중간 실패 시 이미 실행된 외부 효과를 취소·정정해야 한다면 **Saga의 보상 작업**을 정의한다.

```text
예산 예약 성공
→ 관리자 결재 실패
→ 예산 예약 해제 실행
```

| 구분 | 역할 |
|---|---|
| Checkpoint 복구 | Workflow의 실행 State와 지점을 복원 |
| Saga 보상 | 이미 발생한 실제 백엔드·외부 효과를 취소·정정 |

되돌릴 수 없는 발주·지급·최종 공유는 실행 전에 **HITL과 권한 재검사**를 두고, 실행 후에는 삭제가 아니라 취소·정정 절차를 사용한다.

## 7. 감사·복원이 중요한 업무의 Event Sourcing 검토

현재 값뿐 아니라 **어떤 사건을 거쳐 현재 상태가 되었는지** 보존해야 한다면 Event Sourcing을 검토한다.

```text
MEETING_STARTED
MEETING_PAUSED
MEETING_RESUMED
MEETING_STOPPED
MINUTES_PUBLISHED
```

- 기존 Event를 덮어쓰거나 삭제하지 않고 새로운 Event를 추가한다.
- 현재 State는 Event를 순서대로 적용하거나 Projection으로 조회한다.
- Event Stream의 version으로 동시 쓰기 충돌을 감지할 수 있다.
- 잘못된 작업은 기존 Event 삭제가 아니라 **보상·정정 Event**로 처리한다.

Event Sourcing은 구현 비용이 크므로 다음 업무에 선택적으로 적용한다.

- 회의록 확정·공유
- 권한 변경
- SAP 구매요청·결재·발주·지급
- 취소·정정 이력이 필요한 업무

단순 검색·질문·요약과 임시 후보 생성은 일반 State·Checkpoint·실행 로그로 충분하다.

## State 설계 방식 선택표

| 워크플로우 특성 | 권장 방식 |
|---|---|
| 한 요청으로 끝나는 짧은 작업 | 요청별 실행 Subgraph |
| 여러 사용자 입력에 걸쳐 지속 | 지속형 Workflow Instance |
| 하나의 대상에 고정된 병렬 상태 영역 | 병렬 Statechart |
| 같은 리소스에 쓰기 요청이 많음 | Actor·순차 처리 |
| 같은 리소스의 충돌이 드묾 | Optimistic Version 검사 |
| 병렬 결과를 모두 보존할 수 있음 | Reducer·합집합·합산 |
| 병렬 결과 중 하나만 선택해야 함 | 순차 처리·Version·HITL |
| 여러 Workflow가 하나의 업무 구성 | Process Manager |
| 중간 실패 시 외부 효과 취소 필요 | Saga 보상 작업 |
| 감사·과거 상태 재구성이 중요 | Event Sourcing |

## 회의록 에이전트 적용 예

| 업무 | 특성 | 적합한 접근 |
|---|---|---|
| 회의 녹화 | 장시간 지속 | 지속형 Recording Workflow |
| 일시정지·재개·종료 | 같은 회의에 쓰기 | 공통 Handler의 순차 처리·version 검사 |
| 회의록 검색·질문 | 요청 한 번으로 종료 | 요청별 Subgraph와 임시 State |
| 후보 선택 | 실행 중 사용자 입력 대기 | 요청별 Subgraph의 HITL·Checkpoint |
| 선택 ID 추가 | 병합 가능 | 집합 Reducer |
| 선택 ID 대체 | 병합 불가능 | Version 검사·순차 처리 |
| 확정·공유 | 외부 쓰기·권한 필요 | 멱등성·실행 직전 권한과 version 재검사 |
| 확정·공유 이력 | 감사 필요 | 중요 Domain Event 저장 검토 |

## 핵심 정리

> 먼저 업무를 **독립 Workflow**로 나눈다. 이후 실행 시간, 동시성, 리소스 공유, 결과 병합 가능성, 복구와 감사 요구를 기준으로 **요청별 실행, 지속형 Workflow, 병렬 Statechart, Actor, Reducer, Process Manager, Saga, Event Sourcing**을 선택적으로 조합한다. LLM은 어떤 업무가 필요한지 판단하지만, State 병합·충돌 검사·권한·실제 리소스 변경은 오케스트레이터와 백엔드가 확정적으로 처리한다.
