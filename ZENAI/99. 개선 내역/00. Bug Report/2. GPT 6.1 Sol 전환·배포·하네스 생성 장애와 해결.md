# GPT 6.1 Sol 전환 중 발생한 문제와 해결 내역

작성일: 2026-11-02  
대상: 2026-10-30~31 GPT 5.6 Sol → GPT 6.1 Sol 전환 및 후속 배포·운영 복구  
상태: 관련 하위 티켓 ZA-100·ZA-101·ZA-102 해결 완료. 상위 ZA-6 전체의 완료를 뜻하지 않는다.

## 요약

세 번째는 GPT 6.1 모델의 응답 결함이 아니라, 전환 후 실제 운영 검증 중 드러난 배포 구성 문제다.

## 1. 새 모델을 골라도 설정이 저장되지 않음 — ZA-100

### 증상과 재현

에이전트 관리 화면에서 기존 일반·생성 하네스 에이전트를 편집하고 GPT 6.1 Sol을 선택해 저장하면 오류가 발생했다. Builtin 회의·SAP 에이전트에서는 모델 변경과 실행 버전 업그레이드가 서로 막히는 상황도 있었다.

기대 동작은 제거된 GPT 5.6 Sol 대신 현재 사용 가능한 모델을 명시적으로 선택해 저장하고, 해당 모델을 지원하는 실행 버전으로 정상 전환하는 것이었다.

### 원인

- 화면에 보이는 기본 모델을 바꿔도, 숨은 허용 모델 목록에 제거된 예전 모델 ID가 남아 서버 검증에서 거절됐다.
- Builtin의 현재 release와 최신 release가 지원하는 모델이 달랐다. 모델부터 바꾸면 현재 release와 맞지 않고, release부터 바꾸면 기존 모델과 맞지 않아 각각 따로 처리하는 방식으로는 복구가 막혔다.
- 고정 LiteLLM 검증기와 Chat→Responses 변환 경로에서도 신규 모델의 `reasoning_effort` 지원을 맞춰야 했다.

모델 목록의 표시 이름만 바꾸어서는 기존 저장값과 실행 버전의 호환성이 해결되지 않았던 것이다.

### 해결

- 일반·하네스 편집 및 복제에서 제거된 모델을 안내하고, 사용자가 대체 모델을 명시적으로 고르면 과거 ID가 저장 payload에 남지 않도록 했다.
- Builtin은 모델과 실행 release를 하나의 트랜잭션으로 전환하도록 했다.
- 이 과정에서도 권한 검사, 실행 중 run·HITL 보호, 버전 epoch 검사, 실패 시 rollback과 불변 이력을 유지했다.
- 활성 모델 참조를 배포 전에 검사하고, LiteLLM 추론 옵션 호환을 보완했다.
- 상급자가 먼저 수행한 운영 수동 복구와 기존 동료의 회의 에이전트 변경을 보존했다. 수동 복구와 재발 방지 코드 수정은 별도 단계다.

## 2. 미사용 옛 모델 정보 때문에 배포가 막힘 — ZA-101

### 증상

#335 이후 배포 실행의 prepare 단계에서 `DEPLOY_MODELS_UNKNOWN` 오류로 중단됐다.

### 원인과 확인 범위

배포 전 활성 모델 참조 검사가 사용하지 않는 retired GPT 5.6 Sol의 `MODELS` 메타데이터까지 활성 모델처럼 취급했다. 명시적인 GPT 6.1 설정과 옛 메타데이터가 함께 있는 조건에서 같은 거절을 재현했다.

당시 운영 원본의 정확한 불일치 항목은 직접 수집하지 않았다. 따라서 재현한 검사 결함과 운영 환경 원본값까지 확정한 주장은 구분한다.

### 해결

- 새 GPT 6.1 Sol 메타데이터와 제공자 지원이 명시된 경우에 한해, **실제로 사용하지 않는** retired 메타데이터만 검사 대상에서 제외했다.
- 일반·하네스·Builtin·실행이 실제 옛 Sol을 참조하면 계속 배포를 차단한다.
- 알 수 없는 모델, 다른 제공자 누락, 새 모델 명시 설정 누락에 대한 검증은 유지했다.
- 환경 예시와 배포 런북을 새 모델 기준으로 보완했다. 원본 `.env`·DB의 자동 이전이나 검증기 전체 우회로 해결하지 않았다.

## 3. 운영에서 하네스 에이전트만 생성 실패 — ZA-102

### 증상과 재현

운영 `/manage/agents`에서 일반 에이전트 생성은 성공했지만, 하네스 모드로 생성하면 서버 오류가 발생했다. 실제 생성 서비스와 runtime 역할로 스킬 저장 root가 없는 조건을 검사해 일반 성공·하네스 `SKILL_STORAGE_UNAVAILABLE`을 재현했다.

### 원인과 확인 범위

하네스는 생성 시 전용 스킬 매뉴얼 파일을 저장한다. 따라서 일반 생성과 달리 쓰기 가능한 스킬 파일 저장소가 필요했는데, 배포 구성에 전용 영속 경로와 볼륨이 준비되지 않았다.

당시 운영 실패의 원본 로그는 직접 확보하지 않았다. 동일 증상 재현과 배포 구성 결함, 수정 후 운영 생성 성공을 근거로 기록한다.

### 해결

- Dockerfile에 `/app/agent-skills`를 준비하고 비특권 `node` 소유, 권한 `0700`을 설정했다.
- production/EC2 Compose에 `AGENT_SKILL_ROOT`와 `agent-skills` named volume을 명시했다.
- 이미지 배포만으로 호스트 Compose까지 자동 갱신된다고 가정하지 않고 설정 동기화 절차를 문서화했다.
- 기존 저장소를 옮길 때 root·DB 백업과 상대 키·원문·digest 보존이 필요함을 런북에 명시했다.
- 일반·하네스 API, DB, `src/` 로직은 변경하지 않았다. 기존 파일·볼륨도 임의 삭제하지 않았다.

## 5. 재발 방지 시 확인할 사항

1. 모델 교체 시 UI 목록뿐 아니라 제공자 경로·MODELS·기본 모델·허용목록·Builtin 실행 release의 활성 참조를 함께 검사한다.
2. 제거 모델의 실제 사용은 차단하되, 사용하지 않는 과거 메타데이터와 불변 실행 이력은 구분한다.
3. Builtin의 모델과 release가 함께 바뀌어야 하는 경우 권한·실행 중 보호·충돌 검사·rollback을 유지한 원자적 전환을 사용한다.
4. 하네스 스킬 저장소와 작업 공간 마운트는 별개다. 저장 권한·영속 볼륨·호스트 Compose 반영·기존 자료 보존을 확인한다.
5. 정식 빌드 후 일반·하네스·Builtin을 각각 실제 호출한다. 설정 저장 성공, API 성공, 직접 Chrome 확인, 사용자 확인을 같은 증거로 취급하지 않는다.
