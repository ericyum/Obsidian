# 인프라 기초 강의 정리와 개념 보충

정리: **2026-11-13**

> [!info] 문서의 목적
> 사용자가 공유한 상급자의 **인프라 기초 강의**를 학습용으로 정리한다. 강의의 설명을 위한 가정과 실무에서 확인할 조건을 구분한다. 실제 ZEN AI 운영 구성이나 구현 완료를 기록한 문서는 아니다.

## 1. 강의의 전체 흐름

**인프라는 소프트웨어나 서비스를 안정적으로 구축·실행·운영하기 위해 필요한 기반 시설과 시스템의 총합**이다.

강의에서는 보안·OS·네트워크·하드웨어·애플리케이션·DB로 범위를 나눠 본 뒤, **애플리케이션과 DB 내부의 소프트웨어 문제는 제외하고 기초 실행 기반을 중심으로 설명한다.** 서비스 기반이 사용자 증가에 따라 어떻게 확장되는지가 전체 흐름이다.

| 순서 | 강의에서 다룬 내용 | 이해할 핵심 |
| --- | --- | --- |
| **1. 인프라의 범위** | 보안·OS·네트워크·하드웨어·애플리케이션·DB | 이번 기초 설명은 애플리케이션·DB 내부 로직을 제외하고 실행 기반을 중심으로 한다. |
| **2. 서버실 준비** | 공간·전원·LAN·항온항습·출입 관리 | 강의에서는 LAN을 팀의 직접 관리 영역으로, 다른 시설을 별도 관리 영역으로 가정한다. 실제 책임 분담은 조직에 따라 달라진다. |
| **3. 기본 서비스 연결** | 인터넷 회선·공인 IP·게이트웨이·WAS·DB | 사용자가 서버에 도달하는 경로와 요청 처리·자료 저장의 역할을 이해한다. |
| **4. 사용 증가와 병목 확인** | 작업 관리자의 CPU·메모리·네트워크 등 | 느려졌다는 증상만으로 증설하지 않고, 어떤 자원이 부족한지 확인한다. |
| **5. 증설 방법 선택** | Scale up·Scale out·DB/WAS 분리·로드밸런싱 | 자원 크기 증가, 역할 분리, 같은 역할의 서버 복제를 구분한다. |
| **6. 계속 운영하기** | 하트비트·모니터링·문제 통보·네트워크 경로 분리 | 사람이 계속 지켜보는 대신 상태를 관측하고, 공유 자원과 고장 영향 범위를 확인한다. |

이 흐름은 **모든 서비스가 같은 사용자 수에서 같은 순서로 확장해야 한다는 규칙은 아니다.** 회사의 목표·예산·실측 병목에 따라 구조가 달라진다.

온프레미스와 클라우드에서는 책임 경계도 다르다. AWS EC2를 쓰면 물리 기반은 AWS가, 게스트 OS·네트워크 접근·권한 등의 설정은 이용 조직이 관리한다.[^ec2-security]

### 1-1. 서버실을 만든다는 가정

기본 연결은 **사용자 → 인터넷 → 서버**로 단순화한다. 강의에서는 서버 측을 우리가 직접 작업할 수 있는 영역으로 두고, 서버실을 만든다고 가정한다.

| 필요한 요소 | 강의에서 가정한 관리 범위 |
| --- | --- |
| **공간** | 우리 팀의 직접 관할 밖 |
| **전기** | 일부 관련되지만 시설 관리팀이 담당한다고 가정 |
| **LAN 선** | 우리 팀의 직접 관할 |
| **항온항습** | 일부 관련되지만 시설 관리팀이 담당한다고 가정 |
| **출입 관리** | 우리 팀의 직접 관할 밖 |

이 설명에서는 **LAN 연결을 출발점**으로 삼는다. 조직 전체에서 관리할 필요가 없다는 뜻과 우리 팀이 직접 관리하지 않는다는 뜻은 구분한다.

### 1-2. 회선을 연결하고 기본 서비스를 만든다

- **가정집:** LAN 연결 → 공유기 → Wi-Fi 또는 유선 통신.
- **기업의 설명 예시:** 통신사 광회선 → 공인 IP 할당 → 외부와 내부를 잇는 게이트웨이 → 서버 구성 → WAS와 DB 역할 구분.

**WAS는 사용자 요청을 처리하고, DB는 자료를 저장·조회하는 역할**이다. 강의는 이를 2-tier 구조로 설명한다. 공인 IP·게이트웨이·포트 등 실제 접속 조건에 대한 보충은 아래 비교표에서 구분한다.

### 1-3. 사용자가 늘면 상태를 확인하고 구조를 확장한다

다음 숫자와 예산은 **강의의 설명을 위한 가정**이다.

1. **100명에서 101명으로 늘자 느려졌다고 가정한다.** 작업 관리자 같은 도구로 CPU·메모리·네트워크를 확인한다.
2. **CPU 사용이 크게 증가했다고 가정한다.** 더 좋은 CPU·추가 메모리 등으로 한 서버의 성능을 높이는 Scale up과, 서버 수를 늘리는 Scale out을 비교한다.
3. **예산 때문에 Scale up과 로드밸런서 도입을 당장 선택하지 못한다고 가정한다.** 서버를 추가하고 DB와 WAS의 역할을 나눠 자원 경합을 줄이는 방향으로 설명을 이어간다.
4. **예산과 사용자가 더 늘었다고 가정한다.** 가상화와 L4 로드밸런싱을 이용해 여러 서버로 트래픽을 나누는 구성을 설명한다.
5. **사람이 모든 서버를 계속 지켜보는 대신 모니터링을 도입한다.** 하트비트 등으로 상태를 확인하고, 문제가 감지되면 팀이 통보받도록 한다.
6. **대용량 파일 전송이 다른 통신에도 영향을 준다고 가정한다.** WAS와 DB가 같은 외부 경로를 공유하는 구성을 돌아보고, WAS에서 DB로 접근하는 내부 경로를 나누는 방향을 설명한다.

강의의 마지막 요지는 **이 기본 구조 위에서 회사의 상황·계획에 맞춰 서버와 연결 구조가 다르게 성장한다**는 것이다. 역할 분리와 수평 확장의 차이, 내부 경로 분리만으로 해결되지 않는 대역폭 문제는 다음 표에서 따로 보충한다.

## 2. 강의 개념과 실무에서 구분할 점

강의의 핵심은 **사용 증가 → 병목 관측 → 자원 보강·역할 분리·부하 분산 → 모니터링과 지속 개선**이다. 다만 다음 구분을 함께 기억해야 한다.

| 강의에서 이해한 개념 | 실무에서 함께 알아둘 구분 |
| --- | --- |
| 사용자 → 인터넷 → 서버 | 서버뿐 아니라 우리가 설정하는 DNS·TLS·보안그룹·라우팅도 관리 대상이다. 사용자 단말·통신사 문제도 영향은 확인하되 직접 제어 범위와 구분한다. |
| 광회선과 공인 IP를 받으면 외부 통신 가능 | 회선 품질은 계약과 구성에 따라 다르다. 공인 IP 외에도 경로·방화벽·서비스의 수신 설정이 맞아야 한다. AWS의 인터넷 게이트웨이와, 외부에서 먼저 접속할 수 없는 NAT 게이트웨이는 역할이 다르다.[^gateway] |
| DB + WAS의 2-tier | **역할이 두 층이라는 뜻과 물리 서버가 두 대라는 뜻은 다르다.** 한 서버의 컨테이너 두 개로도 나눌 수 있다. WAS는 요청을 처리하는 애플리케이션 서버다. |
| 100명은 괜찮고 101명부터 느려짐 | 설명을 위한 가정이다. 실제 한계는 가입자 수보다 **동시 요청·요청별 작업량·연결 지속 시간·실측 병목**으로 판단한다. |
| Scale up은 비싸고 Scale out은 저렴 | 더 큰 서버와 여러 서버 중 무엇이 유리한지는 다르다. 서버 비용뿐 아니라 저장소·통신·이중화·운영 복잡성까지 비교한다. |
| DB 서버와 WAS 서버를 분리 | 주로 **역할 분리로 자원 경합을 줄이는 조치**다. 여러 WAS 복제본으로 같은 종류의 요청을 나누는 수평 확장과 구분한다. |
| 가상화와 L4로 부하 분산 | 가상화가 로드밸런싱의 필수 조건은 아니다. L4는 TCP 등 연결 수준, L7은 HTTP 등 요청 수준의 분산이다. AWS NLB는 L4, ALB는 L7에 해당한다.[^load-balancer] |
| WAS 뒤에 DB를 연결하면 대역폭 문제 해결 | **외부 요청은 WAS로, DB 통신은 내부 경로로 분리**하는 방향은 타당하다. 하지만 같은 NIC·호스트·상위 회선·스토리지 한도를 공유하면 여전히 경합한다. 그림에서 선을 나누는 것만으로 대역폭이 보장되지는 않는다.[^bandwidth] |
