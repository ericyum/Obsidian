# 목표·상태·상황 기반 행동 플랜 수립 방법

## 1. 문서 목적

업무를 받자마자 구현 방법이나 산출물의 목차부터 정하면, 기술적으로 타당한 내용을 작성하더라도 실제 업무 방향과 어긋날 수 있다.

이를 방지하기 위해 설계·계획·구현에 들어가기 전에 반드시 다음 세 가지를 먼저 정리한다.

1. **목표:** 무엇을 달성해야 하는가?
2. **상태:** 나는 지금 어디까지 와 있는가?
3. **상황:** 결과물이 들어갈 환경은 어떻게 동작하고 있는가?

이 세 가지를 근거로 실제 행동 순서를 정리한 것이 이 문서에서 말하는 **행동 플랜**이다.

---

## 2. 왜 세 가지가 모두 필요한가

```text
목표만 알면
→ 어디로 가야 하는지는 알지만 출발점과 환경을 모른다.

목표와 상태만 알면
→ 현재와 목표의 차이는 알지만 주변 환경에 맞지 않는 방법을 선택할 수 있다.

목표·상태·상황을 모두 알면
→ 현재 위치에서 실제 환경을 이용해 목표에 도달하는 행동을 정할 수 있다.
```

따라서 행동 플랜은 단순한 작업 목록이 아니라 다음 관계를 설명해야 한다.

> **현재 상태에서 출발하여, 주어진 상황의 기능과 제약을 이용해 목표에 도달하는 방법**

---

## 3. 목표·상태·상황의 의미

### 3-1. 목표

목표는 최종적으로 만들어야 하는 결과 또는 해결해야 하는 문제다.

확인할 질문은 다음과 같다.

- 최종 결과물은 무엇인가?
- 완료되었다고 판단할 수 있는 기준은 무엇인가?
- 반드시 보존해야 하는 기능과 품질은 무엇인가?
- 이번 업무에서 하지 않아도 되는 것은 무엇인가?

목표는 가능한 한 한 문장으로 작성한다.

```text
예시: POC에서 검증한 회의록 Agent의 업무 로직을 zen-ai에서 실제로 사용할 수 있게 이식한다.
```

### 3-2. 상태

상태는 업무를 시작하는 시점에 이미 완료되었거나 확보된 것, 아직 부족한 것과 현재 준비 수준을 의미한다.

확인할 질문은 다음과 같다.

- 지금까지 무엇이 완료되었는가?
- 어떤 결과와 자료를 재사용할 수 있는가?
- 무엇이 아직 검증되지 않았는가?
- 현재 내가 결정할 수 있는 범위는 어디까지인가?

```text
예시: Python과 LangGraph POC를 완료하여 Search·Question, HITL, 권한 경계와 상태 흐름이 기술적으로 동작함을 검증했다.
```

### 3-3. 상황

상황은 결과물이 들어갈 제품·조직·사용자·기존 시스템의 실제 동작 방식과 제약을 의미한다. 단순한 폴더 구조나 사용 기술만 조사하는 것이 아니다.

확인할 질문은 다음과 같다.

- 사용자는 이 기능을 어떤 방식으로 사용하게 되는가?
- 기존 제품은 같은 목적을 어떤 기능으로 지원하고 있는가?
- 이미 구축되어 있는 책임과 재사용해야 하는 기반은 무엇인가?
- 새 결과물이 기존 기능과 어떤 관계를 맺어야 하는가?
- 운영·보안·일정·조직상 제약은 무엇인가?

```text
예시: zen-ai는 관리자나 사용자가 Prompt, 모델, Tool 등 각종 설정을 통해 원하는 Agent를 간편하게 생성하는 기능을 구현하고 있다.
```

### 3-4. 상태와 상황의 차이

| 구분 | 상태 | 상황 |
|---|---|---|
| 중심 | 현재 나와 작업의 준비 수준 | 결과물이 들어갈 외부 환경 |
| 질문 | 지금 어디까지 했는가? | 어디에, 어떻게 들어가야 하는가? |
| 예시 | POC를 완료했다 | zen-ai에 Agent 생성 기능이 있다 |
| 잘못 빠뜨렸을 때 | 이미 검증한 것을 다시 만들 수 있음 | 기존 제품과 맞지 않는 결과를 만들 수 있음 |

## 4. 행동 플랜을 만드는 순서

### 1단계. 세 문장으로 업무를 정의한다

구현 방법을 생각하기 전에 다음 세 문장을 먼저 작성한다.

```text
목표: 무엇을 달성해야 하는가?
상태: 현재 어디까지 완료되어 있는가?
상황: 결과물이 들어갈 환경은 어떻게 동작하는가?
```

### 2단계. 목표와 상태의 차이를 찾는다

현재 확보한 것만으로 목표를 달성할 수 있는지 확인하고, 추가로 필요한 조사·판단·구현을 찾는다.

### 3단계. 상황을 기준으로 해결 방법을 제한한다

가능한 모든 구현 방법을 나열하지 않는다. 기존 제품의 사용 방식과 기반 구조에 맞는 방법만 후보로 남긴다.

```text
기존 기능으로 해결 가능
→ 기존 기능 사용

전용 업무 로직이 필요
→ Tool 또는 해당 확장 지점에 구현

기존 기반이 지원하지 않음
→ 필요한 범위만 최소 확장
```

### 4단계. 판단이 필요한 일부터 순서를 정한다

아직 모르는 사실을 확인하기 전에 상세 구현 계획부터 작성하지 않는다.

```text
대상 기능 파악
→ 기존 기능과 요구 로직 대응
→ 구현 방식 결정
→ 구현
→ 완료 기준으로 검증
```

### 5단계. 각 행동에 목적과 산출물을 붙인다

각 단계는 단순한 동사가 아니라, 왜 하는지와 무엇이 남아야 하는지가 보여야 한다.

| 행동 | 목적 | 산출물 |
|---|---|---|
| POC 로직 정의 | 보존할 업무 계약 확정 | 로직·불변 조건 목록 |
| 제품 기능 파악 | 기존 기능의 수용 범위 확인 | 지원·부족 기능 목록 |
| 대응 방식 결정 | 구현 위치와 방법 확정 | 로직별 대응표 |
| 구현 및 검증 | 실제 목표 달성 확인 | 코드와 검증 결과 |

## 5. 이번 회의록 Agent 사례

### 목표

POC에서 기술적으로 검증한 회의록 Agent 로직을 zen-ai에 이식한다.

### 상태

Python과 LangGraph 기반 POC를 완료했으며, 원본 설계의 Node·Edge·State, Search·Question 처리, HITL, 권한 재검증과 원문 비영속성을 검증했다.

### 상황

zen-ai는 관리자나 사용자가 각종 설정을 통해 원하는 Agent를 생성하는 기능을 구현하고 있다. 따라서 회의록 Agent는 별도의 Agent Framework를 새로 만드는 방식이 아니라, 기존 Agent 생성 기능과 AI SDK Tool 구조를 이용해야 한다.

### 도출된 행동 플랜

```text
1. POC에서 이식할 핵심 로직과 설계 계약을 정의한다.
2. zen-ai의 Agent 생성 기능과 실제 사용자 흐름을 파악한다.
3. 각 로직을 기존 설정, AI SDK Tool, Framework 확장, 외부 기능 연결로 분류한다.
4. 결정한 방식으로 구현하고 POC의 계약을 다시 검증한다.
```

이 순서의 핵심은 POC의 코드를 어디에 복사할지 먼저 찾는 것이 아니다. **검증한 로직을 기존 제품의 기능으로 어떻게 실현할지 결정하는 것**이다.

---

## 6. 상황이 빠졌을 때 발생하는 문제

### 설계도 작성 사례

Node가 `input`, `state`, `output`으로 구성된다는 상황을 충분히 인식하지 못하면 Node와 State의 책임 경계가 없는 설계도가 만들어질 수 있다.

### zen-ai 이식 계획 사례

사용자가 설정으로 Agent를 생성하는 제품 기능을 파악하지 않으면, Prompt와 Tool을 기존 생성 기능에 연결하는 대신 모든 로직을 특정 코드 공간에 직접 넣는 방향으로 계획할 수 있다.

두 사례의 공통 원인은 기술 지식 부족만이 아니다.

> **결과물이 실제로 사용될 상황을 정의하지 않은 상태에서 구현 형태부터 결정한 것**

## 7. 실무 작성 템플릿

새 업무를 받으면 다음 양식을 먼저 작성한다.

```markdown
# 업무 행동 플랜

## 목표
- 최종 결과:
- 완료 기준:
- 반드시 보존할 것:
- 범위 밖:

## 상태
- 이미 완료된 것:
- 재사용할 결과와 자료:
- 아직 확인하지 못한 것:
- 현재 제약:

## 상황
- 사용자 이용 방식:
- 기존 제품·업무 기능:
- 재사용해야 하는 기반:
- 연결할 외부 기능:
- 운영·보안·일정 제약:

## 차이와 판단
- 현재 상태와 목표의 차이:
- 상황상 가능한 해결 방식:
- 먼저 확인해야 할 사실:

## 행동 플랜
1. 조사·확인:
2. 대응 방식 결정:
3. 구현:
4. 검증:
```

## 8. 계획 작성 전 최종 점검

- 목표가 구현 방법이 아니라 달성할 결과로 작성되었는가?
- 현재 완료된 것과 미완료된 것이 구분되어 있는가?
- 폴더와 코드뿐 아니라 사용자가 기능을 이용하는 방식까지 파악했는가?
- 기존 제품이 이미 제공하는 기능을 다시 만들고 있지 않은가?
- 상황을 확인하기 전에 상세 구현 위치를 확정하지 않았는가?
- 각 행동이 목표·상태·상황 중 어떤 근거에서 나왔는지 설명할 수 있는가?
- 마지막 검증이 처음 작성한 완료 기준을 직접 확인하는가?

## 핵심 원칙

> **업무를 받으면 구현 방법부터 정하지 않는다. 먼저 목표, 현재 상태와 실제 상황을 정의하고, 그 차이를 해소하는 순서로 행동 플랜을 만든다.**
