# 설계 문서 작성 방법

## 1. 설계 문서가 해결해야 하는 문제

설계 문서는 작성자가 알고 있는 내용을 모두 기록하는 문서가 아니라, 처음 보는 사람이 시스템의 전체 구조에서 세부 구현까지 길을 잃지 않고 내려갈 수 있게 만드는 문서다.

좋은 설계 문서는 다음 질문에 순서대로 답해야 한다.

1. 이 시스템은 무엇을 해결하는가?
2. 전체 업무는 어떤 큰 흐름으로 진행되는가?
3. 어떤 구성 요소가 각 흐름을 담당하는가?
4. State와 결과에 따라 어디에서 분기하거나 반복하는가?
5. 각 단계는 실제로 어떻게 실행되는가?
6. 권한, 실패, 저장과 같은 제약은 어디에서 강제하는가?

## 2. 전체에서 세부로 내려간다

처음에는 전체적인 구조를 한눈에 볼 수 있는 간단한 그림을 제시한다. 세부 예외와 구현 Node를 처음부터 모두 넣지 않는다.

```text
전체 간단한 워크플로우
→ 상위 업무별 Graph
→ 각 Graph의 세부 순서도
→ State·Skill·Tool·권한 등의 상세 정의
```

예를 들어 회의록 에이전트 문서는 다음 순서로 전개한다.

```text
회의 시작 → 회의 진행 → 회의록 확정·공유
          ⋯ 별도 사용자·세션 ⋯
관련 회의록 검색·선택 → 회의록 연속 질의응답

→ 회의 녹화 과정 Graph
→ 회의 시작·제어·공유 순서도
→ 회의록 기반 검색 과정 Graph
→ 검색·선택·질의응답 순서도
```

첫 그림의 목적은 전체 경로를 기억하게 만드는 것이다. 뒤의 Graph와 순서도는 그 경로 중 한 부분을 확대해 설명한다.

### 개요 문서와 상세 문서를 분리한다

하나의 문서가 비개발자용 업무 설명과 개발자용 실행 구조를 모두 자세히 다루면, 처음 보는 사람은 기술 용어 때문에 전체 업무를 파악하기 어렵고 개발자는 필요한 구현 정보를 찾기 어려워질 수 있다.

내용이 길어지면 다음과 같이 문서의 역할을 분리한다.

| 문서 | 주요 독자 | 먼저 답해야 하는 질문 |
|---|---|---|
| **업무 개요 문서** | 비개발자·기획자·처음 보는 사람 | 무엇을 위한 시스템이며, 누가 어떤 기능을 사용하는가? |
| **Graph 상세 문서** | 개발자·설계 검토자 | 어떤 Node·State·분기와 실행 절차로 구현되는가? |
| **상세 설계 문서** | 실제 구현 담당자 | State Schema, Tool 계약, 권한과 저장 구조는 무엇인가? |

업무 개요 문서에는 다음 내용만 우선 배치한다.

1. 시스템의 목적
2. 주요 사용자
3. 제공 기능
4. 한눈에 보는 전체 업무 흐름
5. 각 흐름의 간단한 사용 절차
6. 상세 문서로 이동하는 링크

State, Checkpoint, Condition, Skill, Tool과 같은 용어는 개요 문서의 첫 이해에 꼭 필요하지 않다면 상세 문서로 넘긴다.

### 용어와 표기법은 본문 진입을 막지 않게 배치한다

처음 보는 사람에게 State, Checkpoint, 오케스트레이터, Skill, Tool, HITL을 한꺼번에 설명하면 실제 업무 흐름보다 용어 학습이 먼저 시작될 수 있다.

상세 문서는 다음 순서로 구성한다.

```text
그림의 종류와 전체 기술 구조
→ State·Checkpoint의 핵심 적용 원칙
→ 용어·색상·도형을 설명하는 읽기 부록
→ 실제 업무별 Graph와 순서도
```

용어·표기 영역은 본문의 핵심 흐름과 구별되는 **읽기 부록**으로 표시한다. 각 업무 Graph 앞에는 해당 업무가 무엇을 다루는지 한두 줄로 설명하고, 생소한 용어의 상세 정의는 부록이나 별도 상세 설계 문서를 참조하게 한다.

## 3. 트리는 깊이 우선으로 전개한다

사람은 같은 내용이 문서 여러 위치에서 반복되는 것을 피로하게 느낀다. 따라서 설계 문서는 트리 구조로 전개하되, 한 가지를 설명하기 시작했으면 그 하위 내용을 끝까지 설명한 뒤 상위 단계로 돌아온다.

```text
나쁜 전개
A 개요 → B 개요 → A 상세 → C 개요 → B 상세 → A 예외

권장 전개
A 개요 → A 상세 → A 예외 → A 종료
→ B 개요 → B 상세 → B 예외 → B 종료
→ C
```

이를 **깊이 우선 전개**라고 볼 수 있다. 독자는 A에 대한 정보를 찾기 위해 문서 여러 곳을 오가지 않아도 된다.

단, 전체에서 공통으로 사용하는 표기 규칙이나 State 조건표처럼 어느 한 분기에만 속하지 않는 내용은 모든 세부 설명이 끝난 뒤 핵심 정리 직전에 공통 영역으로 둘 수 있다.

## 4. 한 개념에는 하나의 기준 위치를 둔다

같은 설명을 여러 절에 복사하면 수정할 때 일부만 바뀌어 문서가 서로 충돌한다. 개념마다 가장 상세하게 정의하는 기준 위치를 하나 정한다.

| 개념 | 기준 위치의 예 |
|---|---|
| 전체 업무 순서 | 전체 워크플로우 |
| State 사이의 이동 | 상위 Graph |
| 실제 Node 실행 순서 | 세부 순서도 |
| State 값의 의미 | State 정의 표 |
| Skill·Tool 허용 조건 | State 조건 표 |
| 권한의 최종 강제 위치 | 권한 및 실행 제약 |

다른 절에서는 같은 내용을 다시 길게 설명하지 않고 기준 위치를 참조한다. 다이어그램의 말풍선에는 조건의 핵심만 적고, 전체 조건표는 공통 요약이나 상세 설계 문서에 둔다.

## 5. 워크플로우·Graph·순서도의 역할을 구분한다

문서 안에서 그림의 역할을 명확히 나누면 같은 흐름을 반복해 그리는 문제를 줄일 수 있다.

| 구분 | 답하는 질문 | 포함할 내용 |
|---|---|---|
| 워크플로우 | 사용자의 업무가 전체적으로 어떻게 흘러가는가? | 핵심 업무 단계와 업무 사이의 관계 |
| Graph | State와 조건에 따라 어느 단계로 이동하는가? | State, 분기, 반복, 종료 |
| 순서도 | 한 업무가 실제로 어떤 순서로 실행되는가? | 사용자 입력, LLM, Skill, Tool, 백엔드, HITL, Checkpoint |

상세 순서도의 모든 Node를 다시 상위 Graph에 넣지 않는다. 상위 Graph는 상태 전이와 큰 분기만 보여주고, 구현 순서는 바로 아래 순서도에서 끝까지 설명한다.

### 본문과 그림은 같은 단위로 흐름을 나눈다

본문에서 업무가 두 줄기라고 설명하면서 바로 아래 그림에는 설명 없이 세 갈래가 나타나면, 독자는 어떤 기준으로 흐름을 나눈 것인지 혼동할 수 있다.

따라서 본문과 다이어그램은 다음 항목을 일치시킨다.

- 큰 흐름의 개수
- 각 흐름의 명칭
- 시작점과 복귀점
- 상위 업무와 하위 기능의 포함 관계
- 같은 단계에서 사용하는 추상화 수준

예를 들어 `회의 녹화`와 `공유 회의록 활용`을 두 개의 큰 업무로 정의했다면, `검색·선택`과 `질문·답변`은 별도의 동등한 업무처럼 나열하지 않고 `공유 회의록 활용`에 포함되는 하위 기능임을 글이나 묶음으로 표시한다.

반대로 검색과 질문이 입력 대기 상태에서 각각 독립적으로 실행되는 기능이라면, “두 줄기”라는 표현을 그대로 사용하지 않고 그림의 분기 구조에 맞게 설명한다.

## 6. 설계 의도와 실행 구조를 함께 기록한다

구조만 적으면 후임자가 이유를 모른 채 설계를 되돌릴 수 있다. 중요한 선택에는 짧은 설계 의도를 붙인다.

```text
결정
Skill·Tool의 백엔드에서 State 조건을 검사한다.

설계 의도
조건을 프롬프트에 모두 나열하지 않아 LLM 컨텍스트와 토큰 사용을 줄이고,
에이전트가 늘어날 때 조건 로직을 한곳에서 유지보수하기 위함이다.
```

설계 의도에는 다음을 포함하면 좋다.

- 해결하려는 문제
- 선택한 방법
- 포기한 대안 또는 감수한 비용
- 이 결정이 깨지는 조건

## 7. 책임 경계를 시각적으로 분리한다

LLM, 오케스트레이터, Skill, Tool, 백엔드와 사용자의 역할을 한 덩어리로 표현하지 않는다.

- **사용자**: 요청, Trigger, HITL 선택
- **LLM**: 의도 해석, Tool 사용 판단, 답변 생성
- **Skill**: 명시된 Trigger에 연결된 결정적 실행 진입점
- **Tool**: LLM이 선택할 수 있는 외부 기능 인터페이스
- **오케스트레이터**: Graph 이동, State 전달·갱신, 컨텍스트 조립
- **백엔드**: 권한, 실제 리소스 상태, 실행 조건과 성공 여부 강제

특히 “누가 판단하는가”와 “누가 최종적으로 강제하는가”를 구분한다. LLM이 Tool 호출을 제안할 수 있어도 권한과 State 조건은 백엔드가 최종적으로 검사한다.

## 8. State는 값뿐 아니라 변경 조건까지 적는다

State 표에는 이름과 설명만 적지 않고 다음 항목을 함께 기록한다.

- 어떤 이벤트로 진입하는가?
- 어떤 성공 결과가 있어야 변경되는가?
- 실패하면 기존 값을 유지하는가?
- 다음에 이동할 수 있는 State는 무엇인가?
- 어느 시점에 Checkpoint를 남기는가?

```text
/meeting-pause Trigger
→ 백엔드 일시정지 성공 이벤트
→ workflow_state = pause
→ 업무 경계 Checkpoint
```

Trigger가 발생한 시점과 실제 실행이 성공한 시점을 구분해야 한다. 버튼을 눌렀다는 이유만으로 성공 State를 먼저 기록하지 않는다.

## 9. 본문 근처에는 핵심 조건, 공통 영역에는 전체 조건을 둔다

세부 순서도에서는 Skill이나 Tool 옆의 말풍선으로 해당 단계의 핵심 State 조건을 바로 확인할 수 있게 한다. 모든 순서도가 끝난 뒤에는 Skill·Tool State 조건을 하나의 표로 다시 모아 전체 정책을 비교할 수 있게 한다.

이는 불필요한 반복이 아니라 서로 다른 읽기 목적을 위한 두 표현이다.

- 말풍선: 현재 순서도를 이해하기 위한 국소 정보
- 공통 조건표: 전체 기능의 조건을 비교·검토하기 위한 기준 정보

본문에는 핵심만 두고 상세 정의의 기준 위치를 명확히 하면 두 표현 사이의 불일치도 줄일 수 있다.

## 10. 정상 경로뿐 아니라 복귀·실패·종료를 그린다

설계 다이어그램에는 성공 경로만 그리지 않는다.

- 조건 거부 시 어디로 가는가?
- 실행 실패 시 State는 유지되는가?
- Human in the Loop 이후 어디에서 재개하는가?
- 반복 요청은 어느 State로 돌아가는가?
- 사용자가 업무를 끝내면 언제 `finish`가 되는가?
- 검색 결과가 없을 때 기존 선택을 보존하는가?

분기선에는 `성공`, `실패`, `있음`, `없음`, `추가`, `대체`처럼 판정 결과를 직접 적는다. 독자가 Condition 내부 구현을 읽지 않아도 다음 경로를 알 수 있어야 한다.

## 11. 가정·확정 사항·미결 사항을 분리한다

아직 구현되지 않은 내용을 확정된 사실처럼 쓰지 않는다.

| 구분 | 의미 |
|---|---|
| 가정 사항 | 현재 설계를 진행하기 위해 사실이라고 두는 전제 |
| 확정 사항 | 팀이 합의했거나 이미 구현된 구조 |
| 추후 결정 사항 | 구현 전에 추가 검토가 필요한 내용 |

예를 들어 이미 구축된 에이전트 초대와 전용 스레드 생성은 워크플로우에 새로 구현할 Node로 그리지 않고 가정 사항으로 명시한다. 반대로 이벤트 동기화 방식이 정해지지 않았다면 추후 결정 사항에 남긴다.

## 12. 문서 수정 시 일관성을 함께 검사한다

하나의 설계가 바뀌면 다음 위치를 함께 확인한다.

```text
용어 정의
→ 전체 워크플로우
→ 상위 Graph
→ 세부 순서도
→ State 표
→ Skill·Tool 목록과 번호
→ 권한·실행 조건
→ Human in the Loop와 Checkpoint
→ 핵심 정리
```

예를 들어 Tool을 Skill로 변경했다면 다이어그램의 Node만 바꾸는 것이 아니라 Tool 목록, State 변경 시점, 권한 검사 위치, 핵심 정리와 추후 결정 사항까지 확인해야 한다.

## 작성 전·후 점검표

### 처음 보는 사람의 이해도

- 첫 화면만 보고 시스템의 목적과 주요 사용자를 알 수 있는가?
- 전체 업무를 이해하기 전에 기술 용어부터 학습해야 하는 구조는 아닌가?
- 비개발자용 업무 개요와 개발자용 Graph 상세가 적절히 분리되어 있는가?
- 본문에서 설명한 큰 흐름의 개수와 다이어그램의 분기 구조가 일치하는가?
- 상위 업무와 하위 기능의 포함 관계가 명확한가?
- 각 Graph 앞에 해당 그림의 목적을 설명하는 짧은 정의가 있는가?
- 용어·색상·도형 설명이 별도의 읽기 부록으로 구분되어 있는가?
- 개요 문서와 상세 문서 사이를 이동할 수 있는 링크가 있는가?
- 첫 그림만 보고도 전체 업무 흐름을 설명할 수 있는가?

### 기술 설계의 일관성

- 상위 Graph에는 State와 큰 분기만 있는가?
- 각 분기의 세부 설명을 끝낸 뒤 다음 분기로 이동하는가?
- 같은 개념의 상세 정의가 여러 곳에 중복되어 있지 않은가?
- LLM과 확정적 백엔드의 책임이 분리되어 있는가?
- 모든 State 변경에 구체적인 성공 이벤트가 있는가?
- 실패·거부·재시도·복귀·종료 경로가 표시되어 있는가?
- Skill·Tool 번호와 명칭이 모든 문서에서 일치하는가?
- 가정과 미결 사항이 확정 설계와 구분되어 있는가?
- 핵심 정리만 읽어도 주요 설계 철학을 복원할 수 있는가?

## 핵심 정리

> 설계 문서는 전체 워크플로우에서 시작해 상위 Graph와 세부 순서도로 깊이 내려가며 작성한다. 하나의 분기를 설명하기 시작하면 예외와 종료까지 끝낸 뒤 다음 분기로 이동하고, 같은 개념의 상세 정의는 한 기준 위치에만 둔다. LLM·오케스트레이터·Skill·Tool·백엔드의 책임과 State 변경 조건을 명확히 분리하며, 정상 경로뿐 아니라 실패·복귀·반복·종료도 함께 기록한다.
