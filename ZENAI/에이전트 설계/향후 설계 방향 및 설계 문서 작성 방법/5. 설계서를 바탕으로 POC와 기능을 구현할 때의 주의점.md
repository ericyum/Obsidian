# 설계서를 바탕으로 POC와 기능을 구현할 때의 주의점

## 1. 문서 목적

설계서를 Codex와 같은 AI Coding Agent에게 전달했다고 해서 설계가 자동으로 동일하게 구현되는 것은 아니다.

AI는 요구사항을 빠르게 코드로 옮길 수 있지만, 작업 범위가 크고 여러 Graph·State·Tool·권한 경계가 한꺼번에 포함되면 다음과 같은 판단을 자체적으로 할 수 있다.

- 비슷해 보이는 Node를 합침
- 구현하기 편하도록 Node를 추가로 분리함
- 설계에 없는 공통 처리 Node를 추가함
- 종료·오류·재시도 흐름을 일반적인 패턴으로 보완함
- 기술 Framework의 동작을 업무 설계 개념으로 해석함

이러한 변경은 일반적인 개발에서는 개선일 수 있지만, **설계가 그대로 기술적으로 성립하는지 검증하는 POC**에서는 오히려 실패다.

> 설계 기반 구현에서는 “기능이 동작하는가?”뿐 아니라 “정해진 책임·Node·Edge·State·보안 경계를 그대로 거쳐 동작하는가?”를 확인해야 한다.

---

## 2. 핵심 원칙

설계서를 바탕으로 구현을 맡길 때는 다음 순서를 권장한다.

```text
설계의 목적과 변경 금지 조건 정의
→ 독립적으로 검증 가능한 책임 단위로 분해
→ Superpowers Writing Plans로 전체 계획 작성
→ 한 단계씩 테스트 우선 구현
→ 각 단계마다 설계 정합성 검토
→ 전체 연결과 회귀 테스트
→ 실제 Trace·State·저장 결과 확인
```

중요한 것은 “한 번에 전체를 만들어 달라”고 요청한 뒤 마지막에 결과를 검사하는 방식이 아니라, **전체 계획은 먼저 세우되 구현은 작은 검증 단위로 진행하는 것**이다.

---

## 3. 구현 전에 설계의 성격부터 고정한다

같은 설계서라도 구현 목적에 따라 허용되는 판단이 달라진다.

| 구현 목적 | AI에게 허용할 수 있는 판단 |
|---|---|
| 기술 탐색용 Prototype | 빠른 대안 선택, 일부 단순화 허용 |
| 설계 성립 검증 POC | 설계에 없는 Node·State·책임 변경 금지 |
| 제품 MVP | 기존 제품 구조에 맞춘 재설계 가능 |
| 운영 제품 구현 | 성능·보안·운영 요구까지 포함한 변경 필요 |

설계 성립 검증 POC라면 작업 시작 Prompt에 다음을 명시하는 것이 좋다.

```text
이 작업의 목적은 새로운 구조를 제안하는 것이 아니라
제공한 설계가 기술적으로 그대로 성립하는지 확인하는 것이다.

설계의 Node, Edge, State, Condition, Tool 책임을 임의로 합치거나 분리하지 않는다.
설계에 없는 Node나 상태가 필요하다고 판단되면 구현 전에 이유를 설명하고 승인을 받는다.
```

이 문장은 AI가 일반적인 Best Practice를 이유로 원본 설계를 재해석하는 것을 막는 기준이 된다.

## 4. 설계서를 독립적인 구현 단위로 나눈다

### 4-1. 전체를 한 번에 맡기지 않는다

Graph, LLM, Tool, HITL, Checkpoint, Trace, UI 대역을 한 요청에서 모두 구현하게 하면 AI가 동시에 너무 많은 관계를 유지해야 한다.

그 결과 전체 기능은 연결되더라도 세부 책임이 바뀌거나, 앞 단계의 임시 구현이 뒤 단계에서 규범처럼 굳어질 수 있다.

다음과 같이 독립적인 부위로 나누는 것이 좋다.

```text
1. State와 Runtime Context 계약
2. Repository와 권한 경계
3. Model Interface와 구조화 응답
4. Search Subgraph
5. Search HITL과 재개
6. Question Subgraph
7. 최상위 Agent Graph와 반복·종료 Condition
8. 녹화 Workflow
9. Checkpoint와 Thread 격리
10. Trace와 UI 대역
11. 전체 통합 시나리오
```

### 4-2. 파일이 아니라 책임 단위로 나눈다

“파일 하나씩 구현”은 항상 좋은 분해가 아니다. 하나의 업무 책임이 여러 파일에 걸쳐 있다면 테스트와 함께 하나의 단계로 묶어야 한다.

예를 들어 Search Subgraph 단계는 다음을 함께 포함할 수 있다.

- `agent_graph.py`의 Search Node와 Edge
- `repository.py`의 후보 검색 함수
- `model.py`의 후보 수 구조화 판단
- `tests/test_agent.py`의 Search 계약 테스트

반대로 같은 파일에 있더라도 Search와 Question은 서로 독립적으로 검토할 수 있으므로 다른 단계로 나누는 것이 좋다.

### 4-3. 좋은 작업 단위의 조건

하나의 작업 단계는 다음 조건을 만족해야 한다.

- 하나의 명확한 설계 책임을 구현한다.
- 입력과 출력 Interface를 설명할 수 있다.
- 해당 단계만 독립적으로 테스트할 수 있다.
- 리뷰어가 다른 단계와 별개로 승인 또는 반려할 수 있다.
- 완료 후 다음 단계가 의존할 결과가 명확하다.

너무 잘게 나눠 Setup, 빈 파일 생성, 타입 선언만 별도 단계로 만들 필요는 없다. **자체 테스트 주기를 가진 최소 책임 단위**가 적절하다.

## 5. Superpowers Writing Plans를 먼저 사용한다

Superpowers의 `writing-plans`는 설계서를 실제 구현 작업으로 번역하는 절차다.

Codex에서 명시적으로 사용하려면 설치된 버전에 따라 다음과 같이 호출할 수 있다.

```text
/Superpowers:WritingPlans
```

또는 일반 문장으로 다음처럼 요청할 수 있다.

```text
Superpowers Writing Plans를 사용해서 이 설계서를 구현 계획으로 분해해줘.
아직 코드는 수정하지 말고 설계의 모든 Node, State, Tool, 권한 경계가
어느 작업과 테스트에서 구현되는지 먼저 계획해줘.
```

명령 이름과 표기는 설치된 Plugin 버전과 화면에 표시되는 Skill 이름을 기준으로 확인한다.

### 5-1. Writing Plan에 반드시 들어갈 내용

계획서의 시작 부분에는 다음을 명시한다.

- **Goal:** 이번 구현이 완성할 결과 한 문장
- **Architecture:** 전체 구조와 책임 분리 방식
- **Tech Stack:** 사용할 언어, Framework, 저장소, 테스트 도구
- **Spec:** 기준이 되는 설계 문서 경로
- **Global Constraints:** 모든 단계가 지켜야 할 불변 조건

예시는 다음과 같다.

```markdown
# 회의록 Agent POC 구현 계획

**Goal:** 원본 회의록 Agent 설계의 Node·Edge·State와 보안 경계를
Python·LangGraph로 동일하게 구현하고 검증한다.

**Architecture:** 최상위 Agent Graph와 Search·Question Subgraph를 분리한다.
녹화는 별도의 결정적 Workflow로 두며 실제 제품 UI와 DB는 대역으로 처리한다.

**Tech Stack:** Python 3.11+, LangGraph, SQLite, unittest

**Spec:** C:\...\회의록 에이전트 설계\1-2. 회의록 에이전트 워크플로우 Graph 상세.md

## Global Constraints

- 설계의 Node와 State를 승인 없이 추가·삭제·통합·분리하지 않는다.
- 종료 상태는 `done`이 아니라 `none`이다.
- 회의록 원문과 API Key를 State·Checkpoint·Trace에 저장하지 않는다.
- 권한은 LLM이 아니라 Repository가 강제한다.
- Search·Question은 녹화 모달 State를 읽지 않는다.
```

### 5-2. 파일 구조부터 정한다

Task를 작성하기 전에 어느 파일이 어떤 책임을 가질지 먼저 정한다.

```text
src/meeting_agent/state.py
→ 영속 State와 비영속 Context 타입

src/meeting_agent/repository.py
→ 회의록 검색·조회와 권한 강제

src/meeting_agent/model.py
→ LLM Adapter와 구조화 응답 계약

src/meeting_agent/agent_graph.py
→ 최상위 Graph와 Search·Question Subgraph

src/meeting_agent/recording_graph.py
→ LLM 없는 녹화 Workflow
```

파일 구조는 코드 정리를 위한 장식이 아니라, 이후 작업 단위와 책임 경계를 고정하는 기준이다.

### 5-3. 각 Task에 Interface를 적는다

각 단계에는 다음 작업이 사용할 정확한 입력과 출력을 적는다.

```markdown
### Task 4: Search Subgraph

**Consumes**
- `Repository.search_meetings(user_id, request)`
- `MeetingModel.interpret_candidate_count(...)`

**Produces**
- `build_search_subgraph()`
- `authorized_meeting_ids` 갱신 결과
- 복수 후보일 때 `meeting_selection` HITL
```

Interface를 적지 않으면 서로 다른 Task에서 같은 값의 이름과 의미가 달라질 수 있다.

### 5-4. 설계 항목과 Task의 대응표를 만든다

계획을 작성한 뒤 설계의 각 항목이 어느 Task에서 구현되고 어느 테스트에서 검증되는지 확인한다.

| 설계 항목 | 구현 Task | 검증 테스트 |
|---|---|---|
| Search S1 | Task 4 | 후보 검색 및 LLM 판별 순서 |
| Search S2-A/B/C | Task 4 | 후보 0·1·복수 분기 |
| Search S3 | Task 5 | 선택과 추가·대체 HITL |
| Question Q1·Q2·Q3 | Task 6 | 원문 조회·Context·답변 책임 분리 |
| `follow_up` Condition | Task 7 | true 반복, false `none/END` |
| 녹화 Workflow | Task 8 | 실제 Graph Node·Edge Trace |

대응되지 않는 설계 항목이 있으면 계획이 불완전한 것이다.

## 6. 테스트를 구현 뒤의 확인 작업으로 미루지 않는다

각 Task는 다음 주기를 가져야 한다.

```text
설계 계약을 나타내는 실패 테스트 작성
→ 테스트가 예상한 이유로 실패하는지 확인
→ 최소 구현
→ 해당 테스트 통과
→ 관련 회귀 테스트
→ 설계도와 코드·Trace 비교
```

### 6-1. 기능 테스트와 설계 계약 테스트를 분리한다

```python
# 기능 테스트: 결과가 나오는가?
def test_search_returns_response():
    ...

# 설계 계약 테스트: 정해진 순서와 책임으로 결과가 나오는가?
def test_compound_request_uses_original_llm_role_order():
    ...
```

필요한 테스트 범주는 다음과 같다.

- 정상 결과 테스트
- Node·Edge·LLM 호출 순서 테스트
- State Schema 테스트
- HITL 중단·재개 테스트
- 사용자·Thread 격리 테스트
- 권한 거부·회수 테스트
- 원문·API Key 미노출 테스트
- Checkpoint·Trace 내용 테스트
- 실패·재시도·종료 경로 테스트

### 6-2. 각 단계가 끝날 때 확인할 것

한 단계가 완료되면 다음 단계로 넘어가기 전에 확인한다.

1. 이 단계의 Node가 설계와 같은 책임을 수행하는가?
2. 입력과 출력 State가 계획의 Interface와 일치하는가?
3. 설계에 없는 필드나 Node가 생기지 않았는가?
4. 실패와 HITL 이후의 Edge가 설계와 같은가?
5. 민감 정보가 State, 오류, Trace에 남지 않는가?

## 7. 단계별 구현을 Codex에 요청하는 방법

### 7-1. 전체 설계와 현재 Task를 함께 제공한다

AI에게 현재 단계만 던지면 전체 불변 조건을 잊을 수 있다. 반대로 전체 설계를 한 번에 구현하라고 하면 범위가 너무 커진다.

다음 세 가지를 함께 제공한다.

```text
1. 전체 설계 문서와 Global Constraints
2. 전체 Writing Plan
3. 이번에 구현할 Task 하나
```

예시는 다음과 같다.

```text
원본 설계 문서와 Writing Plan을 먼저 읽어줘.
이번에는 Task 4 Search Subgraph만 구현해.

S1, S2-A, S2-B, S2-C, S3의 책임을 합치거나 추가로 분리하지 말고,
해당 Task의 테스트까지만 통과시켜줘.
다른 Task의 코드는 Interface를 깨지 않는 범위 외에는 수정하지 마.
완료 후 설계 항목별 대응 결과와 실행한 테스트를 보고해줘.
```

### 7-2. 실행 방식

Writing Plan을 만든 뒤에는 상황에 따라 다음 방식을 사용한다.

- `subagent-driven-development`: 서로 독립적인 Task를 새 Agent가 구현하고 단계마다 검토할 때
- `executing-plans`: 한 세션에서 계획을 순서대로 실행하고 Checkpoint마다 검토할 때

어느 방식을 사용하든 Task 사이의 검토 단계를 생략하지 않는다.

### 7-3. Git 작업은 프로젝트 방침을 따른다

Superpowers의 일반적인 Plan 예시에는 Task마다 Commit하는 단계가 포함될 수 있다. 그러나 다음이 우선한다.

```text
사용자의 명시적인 요청
→ 저장소 AGENTS.md
→ 팀 Git 작업 방침
→ Skill의 일반 예시
```

별도 Branch, Worktree, Commit, PR이 필요 없다고 정한 POC에서는 해당 단계를 계획에서 제외하거나 검증 Checkpoint로 바꾼다.

## 8. AI가 임의로 바꾸지 못하게 할 항목

다음 항목은 계획의 Global Constraints와 각 Task의 테스트에 함께 넣는다.

### 구조 불변 조건

- Node를 임의로 추가·삭제·통합·분리하지 않는다.
- Subgraph의 시작점, 복귀점과 종료점을 변경하지 않는다.
- 공통 처리 로직을 설계에 없는 업무 Node로 만들지 않는다.
- 모달 내부 State와 Agent State를 혼합하지 않는다.

### 상태 불변 조건

- 영속 State와 Runtime Context를 구분한다.
- State 필드의 이름과 변경 조건을 설계와 일치시킨다.
- 초기·종료 상태 용어를 임의로 변경하지 않는다.
- Checkpoint에 저장할 수 없는 값을 명시한다.

### LLM·Tool 불변 조건

- LLM이 판단할 부분과 고정 코드가 판단할 부분을 바꾸지 않는다.
- Tool 입력에 전달하면 안 되는 서버 관리 State를 명시한다.
- 권한 판단을 Prompt에 위임하지 않는다.
- 구조화 출력의 허용 값과 검증 실패 처리를 정한다.

### HITL·실패 불변 조건

- 어떤 조건에서 중단하는지 명시한다.
- 잘못된 입력은 어디에서 재질문하는지 정한다.
- 사용자·Thread별 재개 Context의 키를 정한다.
- 거부, 재시도, 복구 불가능한 오류의 다음 Edge를 정한다.

## 9. 그렇게 하지 않으면 발생할 수 있는 문제

회의록 Agent POC에서는 전체 설계를 한꺼번에 구현하고 결과 중심으로 검토하면서 다음과 같은 문제가 실제로 발견되었다.

| 발생 문제 | 원인 | 예방 방법 |
|---|---|---|
| Search·Question Node가 임의로 합쳐지거나 분리됨 | Node 이름보다 최종 동작에 집중 | Task별 Node 책임과 호출 순서 테스트 |
| 설계에 없는 완료·Checkpoint Node 추가 | Framework 관행으로 설계를 보완 | 추가 구조는 구현 전 승인하도록 Constraint 명시 |
| `none` 대신 `done` 상태 등장 | 일반적인 종료 용어를 자동 적용 | State 허용값을 타입과 테스트로 고정 |
| Search·Question 뒤 불필요한 LLM 재호출 | 종료 판단 책임이 불명확 | `follow_up`과 고정 Condition Interface 명시 |
| 회의록 원문이 Checkpoint·Trace에 남을 위험 | State와 일시 Context 경계 미고정 | 금지 필드 검사와 민감 정보 회귀 테스트 |
| `authorized_meeting_ids`가 LLM에 전달됨 | 서버 State와 모델 Context 혼동 | Tool별 허용 입력과 금지 입력 명시 |
| 잘못된 HITL 입력이 예외 또는 Context 손상으로 이어짐 | 중단·재개를 후순위로 구현 | HITL을 별도 Task로 두고 오류 경로부터 테스트 |
| 사용자·Thread Context 충돌 가능성 | 식별 키 계약이 늦게 정해짐 | State 단계에서 Session Key를 먼저 확정 |
| 검색·질문이 녹화 상태를 읽음 | 공통 Runtime이 서로 다른 책임을 결합 | Subsystem별 State 소유자를 명시 |
| 녹화 Trace가 수동 표시로 구현됨 | UI 출력과 실제 Graph 증거를 구분하지 않음 | 실제 debug event 기반 Trace를 완료 조건으로 지정 |
| Trace가 실행 후 재생됨 | 발표 화면을 나중에 부가 기능으로 구현 | 관측성을 독립 Task로 계획하고 실시간성 테스트 |

이 문제들은 AI가 코드를 작성할 능력이 부족해서만 발생하는 것이 아니다. 전체 설계의 우선순위, 변경 금지 조건, Task 경계와 검증 방식이 구현 전에 충분히 고정되지 않으면 사람에게 맡겨도 비슷하게 발생할 수 있다.

## 10. 권장 Writing Plan 목차

설계 기반 POC에는 다음 목차를 사용할 수 있다.

```text
1. Goal과 POC의 성공 기준
2. 기준 설계 문서와 우선순위
3. 전체 Architecture
4. Global Constraints
5. 파일별 책임과 Interface
6. Task 1: State와 Context 계약
7. Task 2: Repository와 권한
8. Task 3: Model Interface
9. Task 4: 첫 번째 Subgraph
10. Task 5: HITL
11. Task 6: 두 번째 Subgraph
12. Task 7: 최상위 Graph
13. Task 8: 별도 결정적 Workflow
14. Task 9: Checkpoint와 Trace
15. Task 10: 전체 통합 테스트
16. 설계 항목·Task·테스트 대응표
17. 전체 검증 명령과 완료 조건
```

각 Task에는 최소한 다음을 포함한다.

```text
수정·생성할 정확한 파일
→ 입력 Interface
→ 출력 Interface
→ 먼저 작성할 실패 테스트
→ 최소 구현 내용
→ 실행할 정확한 테스트 명령
→ 기대 결과
→ 설계 정합성 검토 항목
```

## 11. 구현 전 점검표

### 설계 이해

- 이 구현이 Prototype, POC, MVP, 운영 제품 중 무엇인지 정의했는가?
- 설계 문서의 우선순위와 기준 문서를 정했는가?
- 변경하면 안 되는 Node·Edge·State·Tool 계약을 적었는가?
- 가정, 실제 구현, 대역을 구분했는가?

### 계획 분해

- 전체 설계를 독립적으로 테스트 가능한 책임 단위로 나눴는가?
- 각 Task의 입력과 출력 Interface가 명확한가?
- 설계의 모든 항목이 구현 Task와 테스트에 대응되는가?
- 서로 다른 Subsystem을 한 Task에 섞지 않았는가?

### 구현 요청

- 전체 설계, 전체 Plan과 현재 Task를 함께 제공했는가?
- 이번 단계 밖의 변경 범위를 제한했는가?
- 새 Node·State·의존성이 필요하면 먼저 승인받도록 했는가?
- 단계 완료 시 설계 대응 결과와 테스트 증거를 요구했는가?

### 검증

- 정상 응답뿐 아니라 Node·Edge·호출 순서를 검사하는가?
- HITL, 실패, 재시도와 종료 경로를 검사하는가?
- 사용자·Thread 격리를 검사하는가?
- 민감 정보의 State·Checkpoint·Trace·Log 미노출을 검사하는가?
- Trace가 수동 표시가 아닌 실제 실행 Event인지 확인하는가?

## 핵심 정리

> 설계 기반 구현을 AI에게 맡길 때는 전체 설계를 한 번에 구현하게 하지 않는다. 먼저 Superpowers Writing Plans로 목표, Architecture, 기준 설계, 전역 불변 조건과 파일 책임을 고정하고, 설계를 독립적으로 테스트 가능한 Task로 나눈다. 각 Task는 실패 테스트, 최소 구현, 설계 정합성 검토를 하나의 주기로 완료한다. 이렇게 하지 않으면 기능은 동작해도 Node 통합·분리, 임의 상태와 LLM 호출 추가, 원문 저장, HITL Context 손상, 수동 Trace처럼 설계와 다른 구현이 만들어질 수 있다.
