# ZEN AI 향후 설계 방향

## 1. 현재 단계와 장기 목표

현재 ZEN AI는 회의록 에이전트를 중심으로 Agent의 State, Skill, Tool, 권한, Human in the Loop와 Checkpoint 구조를 구체화하는 단계다.

장기적으로는 사용자가 각 전문 Agent를 직접 찾아 호출하지 않아도 되는 구조를 목표로 한다. 사용자는 하나의 **ZEN AI Main Agent**에게 요청하고, Main Agent가 여러 전문 Agent 중 적합한 하나 또는 여러 Agent에게 업무를 전달한다.

```text
사용자
→ ZEN AI Main Agent
   ├→ 회의록 Agent
   ├→ 문서 Agent
   ├→ 일정 Agent
   ├→ 검색 Agent
   └→ 향후 추가될 전문 Agent
→ 결과 통합
→ 사용자에게 하나의 응답으로 반환
```

회의록 에이전트는 이 장기 구조에서 첫 번째 전문 Agent이자, 이후 Agent를 양산하기 위한 기준 설계가 된다.

## 2. 사용자에게는 하나의 진입점만 제공한다

전문 Agent가 늘어날수록 사용자가 어느 Agent를 호출해야 하는지 직접 판단하게 해서는 안 된다. 사용자는 업무 목적만 설명하고, Main Agent가 다음을 담당한다.

1. 요청의 목적과 필요한 결과 해석
2. 요청을 하나 이상의 하위 업무로 분해
3. 각 업무에 적합한 전문 Agent 선택
4. Agent별 입력 컨텍스트와 권한 범위 구성
5. 실행 순서와 병렬 처리 여부 결정
6. 결과를 수집하고 충돌을 해결
7. 사용자에게 하나의 일관된 결과로 응답

사용자 경험은 다음과 같이 단순해진다.

```text
기존 방식
사용자가 Agent 탐색 → Agent 선택 → 각 Agent에 별도 요청 → 결과 직접 조합

목표 방식
사용자가 Main Agent에 한 번 요청
→ Main Agent가 선택·전달·통합
→ 하나의 결과 수신
```

## 3. Tool을 붙이는 구조에서 Agent를 붙이는 구조로 확장한다

사용자가 예로 든 `pi agent`처럼 일반적인 단일 Agent 제품은 하나의 Agent에 여러 Tool을 연결하고, Agent가 필요한 Tool을 선택하는 형태가 중심이 된다.

ZEN AI의 장기적인 차별점은 Main Agent에 단순 Tool만 추가하는 것이 아니라, **독립된 책임·State·Skill·Tool·권한과 전문 지식을 가진 여러 Agent를 연결하는 것**이다.

```text
Tool 중심 Agent
Agent → Tool A / Tool B / Tool C

ZEN AI 목표
Main Agent
→ 전문 Agent A → A의 Skill·Tool
→ 전문 Agent B → B의 Skill·Tool
→ 전문 Agent C → C의 Skill·Tool
```

Tool은 비교적 좁고 결정적인 기능을 실행한다. 전문 Agent는 하나의 업무 영역 안에서 여러 단계를 계획하고, 자체 State와 Tool을 사용하며, 정해진 결과 계약에 맞춰 업무 결과를 반환한다.

따라서 ZEN AI의 상품 방향은 다음과 같이 정의할 수 있다.

> 하나의 범용 Agent에 Tool을 계속 추가하는 제품이 아니라, 하나의 Main Agent에 지속적으로 전문 Agent를 연결하고 조합할 수 있는 Agent 플랫폼을 만든다.

## 4. Main Agent와 전문 Agent의 책임

### Main Agent

- 사용자의 단일 대화 창과 최종 응답 소유
- 사용자 의도 해석과 업무 분해
- 적합한 Agent 선택과 실행 계획 수립
- fan-out과 fan-in 제어
- Agent 사이의 의존 관계와 실행 순서 관리
- 결과 병합·충돌·중복 처리
- 전체 업무의 State, 진행 상태와 실패 정책 관리
- 사용자에게 추가 선택이 필요할 때 Human in the Loop 실행

### 전문 Agent

- 자신이 맡은 업무 영역 안에서만 판단하고 실행
- 자신의 Skill과 Tool 사용
- 자신의 세부 State와 Checkpoint 관리
- 백엔드 권한과 실제 리소스 상태 검사
- Main Agent가 요구한 결과 Schema에 맞춰 결과 반환
- 수행 근거, 변경 내용, 오류와 미완료 항목 함께 반환

Main Agent가 모든 전문 업무의 세부 규칙을 프롬프트로 알고 있어서는 안 된다. 전문 지식과 세부 실행 조건은 각 전문 Agent와 백엔드에 두고, Main Agent는 Agent의 능력과 입출력 계약만으로 오케스트레이션할 수 있어야 한다.

## 5. Agent Registry가 필요하다

Main Agent가 적합한 Agent를 선택하려면 Agent마다 기계가 읽을 수 있는 등록 정보가 필요하다.

```yaml
agent_id: meeting_agent
capabilities:
  - meeting_recording
  - meeting_minutes_search
  - meeting_minutes_qa
required_permissions:
  - meeting.read
  - meeting.write
input_schema: ...
output_schema: ...
supported_states: ...
side_effects: ...
```

Agent Registry에는 최소한 다음 정보가 포함되어야 한다.

- Agent 이름과 버전
- 담당 업무와 지원하지 않는 업무
- 입력·출력 Schema
- 필요한 권한
- 읽기·쓰기와 외부 부작용 여부
- 예상 비용과 지연 시간
- 병렬 실행 가능 여부
- 다른 Agent와의 선행·후행 의존 관계
- 실패 코드와 재시도 가능 여부

이 정보를 사용하면 Main Agent의 프롬프트에 모든 Agent 설명과 조건을 길게 나열하지 않고도 후보를 검색하고 선택할 수 있다.

## 6. Fan-out: 업무를 적합한 Agent들에게 분산한다

**Fan-out**은 하나의 사용자 요청을 여러 하위 업무로 나누고 적합한 Agent들에게 전달하는 과정이다.

```text
사용자 요청
“지난 회의의 결정 사항을 찾아 일정과 프로젝트 문서에 반영해 줘”

Main Agent 업무 분해
├→ 회의록 Agent: 관련 회의와 결정 사항 검색
├→ 일정 Agent: 결정된 일정 후보 검토
└→ 문서 Agent: 프로젝트 문서 수정안 준비
```

Fan-out 시에는 단순히 모든 Agent를 동시에 호출하지 않는다. 먼저 업무 사이의 의존 관계를 확인한다.

```text
회의록 검색 결과가 있어야 일정과 문서를 수정할 수 있음

1차 fan-out
→ 회의록 Agent

결과 수신 후 2차 fan-out
├→ 일정 Agent
└→ 문서 Agent
```

서로 독립적인 업무만 병렬로 실행하고, 선행 결과가 필요한 업무는 단계적으로 실행한다.

## 7. Fan-in: 여러 Agent의 결과를 하나로 모은다

**Fan-in**은 여러 Agent가 반환한 결과를 Main Agent가 수집해 하나의 결과나 다음 실행 State로 통합하는 과정이다.

Fan-in에서 중요한 것은 결과가 도착한 순서대로 무조건 붙이는 것이 아니라, 각 결과가 전체 결과의 어느 부분을 어떻게 변경해야 하는지 결정하는 것이다.

### 기본 병합 정책

| 정책 | 의미 | 적합한 상황 |
|---|---|---|
| 덮어쓰기 | 기존 값을 새 결과로 교체 | 최신 상태가 이전 상태를 완전히 대체할 때 |
| 이어쓰기 | 기존 결과 뒤에 새 결과를 추가 | 로그, 근거, 독립된 목록을 누적할 때 |
| 병합 | 객체나 목록의 서로 다른 필드를 합침 | Agent마다 담당 필드가 다를 때 |
| 중복 제거 병합 | 같은 항목을 제거하며 합침 | 회의록 ID, 태그, 후보 목록을 합칠 때 |
| 우선순위 선택 | 신뢰도·최신성·권한에 따라 하나를 선택 | 결과가 서로 충돌할 때 |
| Human in the Loop | 사용자가 최종 선택 | 자동 판단의 영향이 크거나 기준이 불명확할 때 |

덮어쓰기와 이어쓰기는 LLM이 결과 문장을 보고 즉흥적으로 선택하게 하기보다 결과 Schema에 병합 의도를 포함하는 것이 좋다.

```json
{
  "agent_id": "meeting_agent",
  "target": "project.decisions",
  "merge_policy": "append_deduplicate",
  "result": [...],
  "provenance": [...]
}
```

Main Agent의 fan-in reducer는 `target`과 `merge_policy`를 읽고 결정적으로 결과를 반영한다. 정책이 충돌하거나 데이터 손실 가능성이 있으면 자동 덮어쓰기 대신 Human in the Loop로 보낸다.

## 8. 결과에는 출처와 실행 정보를 함께 남긴다

여러 Agent의 결과를 합치면 어떤 결과가 어디에서 왔는지 알기 어려워진다. 각 결과에는 다음 메타데이터가 필요하다.

- 결과를 생성한 Agent와 버전
- 사용한 원본 리소스와 ID
- 실행 시각
- 성공·부분 성공·실패 상태
- 적용한 권한 범위
- 신뢰도 또는 검증 상태
- 적용해야 할 병합 정책
- 실제로 수행한 외부 변경과 제안만 한 변경의 구분

이 정보는 결과 충돌 해결, 감사, 오류 추적과 재실행에 사용한다.

## 9. State는 계층적으로 분리한다

Main Agent와 전문 Agent가 하나의 거대한 State 객체를 공동으로 수정하면 필드 충돌과 예상하지 못한 덮어쓰기가 발생한다. State를 다음과 같이 나누는 것이 좋다.

```text
Main Workflow State
├→ 사용자 요청과 전체 계획
├→ Agent 실행 목록과 의존 관계
├→ fan-in 결과와 전체 진행 상태
└→ Specialist State References
    ├→ meeting_agent state
    ├→ document_agent state
    └→ calendar_agent state
```

전문 Agent는 자신의 namespace만 수정하고, Main Agent에는 계약으로 정한 결과만 반환한다. Main Agent가 전문 Agent의 내부 `workflow_state`를 직접 조작하지 않도록 한다.

## 10. 권한은 전달하되 확대하지 않는다

Main Agent가 전문 Agent를 호출하더라도 사용자의 권한보다 넓은 권한을 부여해서는 안 된다.

```text
사용자 인증 정보
→ Main Agent가 현재 업무에 필요한 최소 범위 계산
→ 전문 Agent에 제한된 실행 컨텍스트 전달
→ 전문 Agent의 백엔드가 권한 재검사
```

Agent 선택과 권한 허용은 별개의 문제다. Main Agent가 어떤 Agent가 적합하다고 판단했더라도 실제 데이터 접근과 쓰기 권한은 각 백엔드가 최종적으로 강제한다.

쓰기 작업은 읽기보다 더 엄격하게 다룬다. 여러 Agent가 동시에 같은 리소스를 수정할 가능성이 있으면 버전 검사, 잠금, 멱등성 키, 승인 단계 또는 충돌 해결 정책이 필요하다.

## 11. 부분 실패를 기본 상황으로 본다

Fan-out 이후에는 일부 Agent만 성공할 수 있다. Main Agent는 전체를 무조건 실패시키거나 성공으로 포장하지 않고 결과를 구분해야 한다.

```text
전체 성공
부분 성공
재시도 가능 실패
사용자 입력 필요
권한 거부
복구 불가능 실패
```

부분 성공에서는 다음을 사용자에게 알려야 한다.

- 완료된 업무
- 실패하거나 실행하지 못한 업무
- 이미 발생한 외부 변경
- 재시도 가능한 항목
- 추가 권한이나 사용자 선택이 필요한 항목

쓰기 Agent가 성공한 뒤 다른 Agent가 실패했다고 해서 이미 실행된 외부 변경을 State만 되돌려 취소할 수는 없다. 필요하면 보상 동작을 별도 설계해야 한다.

## 12. Main Agent도 LLM의 기억에 의존하지 않는다

Main Agent가 여러 Agent를 조율하더라도 LLM 자체는 stateless다. 전체 계획, Agent 실행 결과, fan-in 대기 상태와 사용자 승인은 외부 State와 Checkpoint에 저장해야 한다.

```text
Main Agent 판단
→ 실행 계획을 State에 저장
→ 전문 Agent fan-out
→ 각 결과를 식별자와 함께 저장
→ fan-in reducer 실행
→ 다음 판단에 필요한 내용만 컨텍스트로 조립
```

모든 전문 Agent의 전체 대화와 결과를 Main Agent 컨텍스트에 계속 누적하지 않는다. 구조화된 결과, 요약, 필요한 근거만 전달하여 컨텍스트와 토큰 사용을 통제한다.

## 13. 운영을 위한 관찰과 평가가 필요하다

Agent가 많아지면 최종 답변만 보고 문제의 위치를 알기 어렵다. 다음 정보를 추적해야 한다.

- Main Agent의 업무 분해 결과
- 선택한 Agent와 선택 이유
- fan-out·fan-in 실행 순서
- Agent별 입력과 구조화된 결과
- State 전이와 Checkpoint
- Tool·Skill 실행 성공과 실패
- 권한 거부와 Human in the Loop 발생 지점
- 지연 시간과 토큰·비용
- 결과 병합 정책과 충돌 처리

평가 역시 개별 Agent의 정확도만 보지 않고 다음 계층으로 나눈다.

1. 올바른 Agent를 선택했는가?
2. 업무 의존 관계와 병렬 실행을 올바르게 계획했는가?
3. 각 전문 Agent가 자신의 업무를 정확히 수행했는가?
4. fan-in에서 결과를 손실하거나 잘못 덮어쓰지 않았는가?
5. 최종 응답이 사용자 요청을 완전히 충족했는가?

## 14. 단계별 발전 방향

### 1단계: 회의록 에이전트 기준 설계 확립

- State·Checkpoint 구조 확정
- Skill·Tool·백엔드 책임 분리
- 권한과 Human in the Loop 기준 확립
- 재사용 가능한 Agent 설계 문서 양식 정립

### 2단계: 전문 Agent 공통 계약 정의

- Agent Registry Schema
- 공통 입력·출력·오류 Schema
- 실행 상태와 결과 메타데이터
- 권한 전달과 최소 권한 원칙
- Agent별 State namespace

### 3단계: Main Agent의 단일 Agent 라우팅

- 사용자 요청에 가장 적합한 전문 Agent 하나 선택
- 요청 전달과 결과 반환
- 선택 실패와 사용자의 재선택 처리

### 4단계: Fan-out·Fan-in 도입

- 업무 분해와 의존 관계 Graph
- 독립 업무 병렬 실행
- 덮어쓰기·이어쓰기·병합 reducer
- 충돌 시 Human in the Loop
- 부분 실패와 재시도 처리

### 5단계: Agent 생태계와 상품화

- 새로운 전문 Agent의 등록·버전 관리
- 조직별 Agent 조합과 권한 정책
- Agent 품질 평가와 배포 기준
- 비용·지연 시간 기반 실행 최적화
- 감사 로그와 운영 대시보드

## 핵심 정리

> ZEN AI는 하나의 Agent에 Tool을 계속 붙이는 구조를 넘어, 하나의 Main Agent에 여러 전문 Agent를 연결하는 플랫폼을 목표로 한다. 사용자는 Main Agent에만 요청하고, Main Agent는 요청을 분해하여 적합한 Agent들에게 fan-out한 뒤 구조화된 결과를 fan-in한다. 결과를 통합할 때에는 덮어쓰기·이어쓰기·병합·중복 제거·Human in the Loop 정책을 명시적으로 설계해야 한다. 전문 Agent는 독립된 State와 실행 책임을 가지며, Main Agent는 선택·의존 관계·결과 통합과 사용자 경험을 소유한다.
