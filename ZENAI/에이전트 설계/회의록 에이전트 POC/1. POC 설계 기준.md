## 반영한 핵심 설계

- 회의록 검색·질문은 하나의 Agent Graph에서 Search·Question Subgraph로 실행한다.
- Search 결과 뒤에 남은 질문이 있으면 공통 처리 경계와 Checkpoint를 거쳐 LLM 판단 Node로 돌아간다.
- `search`, `question`, `none`은 Node와 Edge가 나타내는 개념적 State이며 같은 이름의 영속 변수는 만들지 않는다.
- 영속 Agent State는 `ScratchPad`, `authorized_meeting_ids`, `recording_modal_status` 세 필드만 사용한다.
- `user_id`, `thread_id`, 현재 사용자 요청은 비영속 `AgentContext`로 전달한다. 별도 `run_id`나 `request_id`는 사용하지 않는다.
- Tool 1은 접근 가능한 후보 검색, Tool 2는 허용 ID의 원문 조회만 담당한다.
- 후보 수 해석과 질문 응답은 Model 인터페이스를 거친다. POC에서는 API 없이 실행하기 위해 규칙 기반 모델을 사용한다.
- 복수 후보 선택과 기존 ID의 추가·대체는 LangGraph `interrupt()`로 처리한다.
- 원문은 Tool 2 실행 Node의 지역 변수에만 두고 State, ScratchPad, Checkpoint, 임시 저장소에 넣지 않는다.
- Search·Question·직접 답변은 모두 공통 Graph Runtime 처리로 합류해 결과 반영, 업무 Checkpoint 표시, 후속 작업 판단을 수행한다.
- 녹화는 LLM이나 Agent Tool을 사용하지 않는 독립적인 결정적 Workflow다.
- 실제 `recording_state`는 POC의 모달·백엔드 대역인 SQLite Repository가 소유한다. Agent에는 `recording_modal_status`만 동기화한다.
- 같은 스레드 요청은 런타임의 스레드별 잠금으로 프로세스 안에서 순차 처리한다.
- Tool 실행 실패는 두 번까지 시도하고 구조화된 오류 결과를 Model에 전달한다.
- `ScratchPad`가 POC 컨텍스트 예산의 50%에 도달하면 이전 실행 기록을 요약 이벤트로 Compact한다.

## POC에서의 대체 구현

실제 ZEN AI의 프론트엔드 모달, 인증 세션, 백엔드 API와 운영 DB는 포함하지 않는다. SQLite의 사용자·회의록·권한·녹화 테이블이 해당 경계를 재현한다.

실제 LLM 대신 `RuleBasedMeetingModel`이 의도 판단, 후보 수 해석, 후속 작업 판단과 답변 생성을 재현한다. Model Protocol은 시스템 지시, 현재 요청, ScratchPad, Tool 결과와 원문을 받을 수 있도록 구성되어 실제 모델 어댑터로 교체할 수 있다.

LangGraph SQLite Checkpointer는 기술적으로 각 Super-step의 복구 Snapshot을 저장한다. 설계 문서가 말하는 업무 완료 Checkpoint는 `business_checkpoint` 이벤트로 별도 표시하며, 상위 Agent Checkpoint의 State Schema는 세 필드로 제한한다.
