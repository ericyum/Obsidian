# 회의록 에이전트 POC 추진 배경과 설계 기준

## 1. POC를 작성하게 된 경위

회의록 에이전트는 최종적으로 실제 ZEN AI 서비스에 통합할 예정이다. 그러나 처음부터 서비스 안에서 구현하면 **설계 자체가 성립하는지**와 **서비스 통합이 올바른지**를 동시에 다루게 되어 문제의 원인을 분리하기 어렵다.

따라서 별도 저장소에서 설계 자체를 먼저 검증한다.

> PoC에서 확인해야 할 질문은 본질적으로 **“회의록 Agent 설계가 기술적으로 성립하는가?”**이다.

POC는 실제 제품을 당장 만드는 것이 아니라, 설계한 Graph·State·Tool·Checkpoint 경계만으로 **사용자 목표를 처음부터 끝까지 처리할 수 있는지 확인하는 독립 실험**이다.

## 2. POC에서 확인하려는 것

- 회의 녹화와 회의록 검색·질문을 독립된 실행 구조로 분리할 수 있는가?
- LLM 판단 업무와 코드로 고정할 결정적 Workflow가 올바르게 구분되는가?
- 하나의 요청에서 Search가 끝난 뒤 Question으로 이어지는가?
- `none/search/question`을 별도 영속 변수 없이 Node와 Edge로 표현할 수 있는가?
- `ScratchPad`, `authorized_meeting_ids`, `recording_modal_status`만으로 Agent 영속 State를 구성할 수 있는가?
- 권한과 선택 ID를 LLM이 아니라 Backend 계층이 검증하는가?
- 복수 후보와 추가·대체에서 HITL로 중단하고 같은 실행을 재개할 수 있는가?
- 원문을 Checkpoint에 저장하지 않고 Model Context에만 넣을 수 있는가?
- 실제 DeepSeek을 사용해도 코드가 정한 Graph 경계를 지키는가?

## 3. 검증 목적에 맞춘 구현 방식

### 3-1. Python·LangGraph 독립 프로젝트

POC는 `zen-ai` 저장소와 기술 구조에 종속시키지 않는다. Python과 LangGraph를 사용해 설계 문서의 Graph를 가장 직접적으로 실행하고 관찰한다.

```text
zen-ai/
└─ 향후 통합 대상인 실제 서비스

zen-ai-meeting-agent-test/
└─ 설계의 기술적 성립 여부를 검증하는 독립 POC
```

### 3-2. 설계 책임에 따른 파일 분리

```text
src/meeting_agent/
├─ state.py             State와 비영속 Runtime Context
├─ agent_graph.py       최상위 Graph와 Search·Question Subgraph
├─ recording_graph.py   LLM 없는 결정적 녹화 Workflow
├─ runtime.py           Checkpoint·Lock·HITL 재개 하네스
├─ model.py             실제 DeepSeek과 테스트 Model 경계
├─ repository.py        Backend·DB·녹화 모달 대역
└─ cli.py               실제 UI 대신 사용하는 실행 진입점
```

### 3-3. 실제 구현과 대역

| 구분 | 현재 POC | 의미 |
|---|---|---|
| Agent Graph·Subgraph | 실제 LangGraph | Node·Edge·Loop 검증 대상 |
| State·Checkpoint·HITL | LangGraph + SQLiteSaver | 저장·중단·재개 검증 대상 |
| LLM | 실제 `deepseek-v4-pro` | 실제 모델 판단 검증 |
| 테스트 LLM | `RuleBasedMeetingModel` | 빠른 오프라인 회귀 대역 |
| UI | CLI | ZEN AI 화면 대역 |
| 인증·권한·회의록 Backend | SQLite Repository | 책임과 Tool 계약 대역 |
| 녹화 모달·Backend | SQLite 녹화 Session | 상태 소유권 대역 |

DeepSeek이 실제라는 사실과 전체 POC가 운영 코드라는 사실은 다르다. UI·인증·운영 DB·실제 녹화 연결은 여전히 대역이다.

## 4. 설계 의도와 코드 반영

| 설계 의도                     | 구현 위치                                  |
| ------------------------- | -------------------------------------- |
| 녹화와 검색·질문의 독립 실행          | `recording_graph.py`, `agent_graph.py` |
| 녹화는 결정적 Workflow          | `build_recording_workflow()`           |
| Search·Question은 Subgraph | `build_agent_graph()`                  |
| 영속 State 세 필드             | `AgentState`                           |
| 사용자·Thread·요청은 비영속        | `AgentContext`                         |
| 권한은 Backend 코드가 강제        | `MeetingRepository`                    |
| 복수 후보·추가·대체 HITL          | LangGraph `interrupt()`                |
| 원문은 Model Context에서만 사용   | Checkpoint에 저장되지 않는 `UntrackedValue` 메모리 채널 |
| 후속 작업 재판단 Loop            | Runtime Checkpoint 이후 조건 Edge          |
| 실제 LLM 판단과 답변             | `DeepSeekMeetingModel`                 |

## 5. State 소유 기준

```text
Agent Checkpoint State
├─ ScratchPad
├─ authorized_meeting_ids
└─ recording_modal_status

Backend·모달 대역
└─ recording_state

현재 호출 Runtime Context
├─ user_id
├─ thread_id
└─ request
```

회의록 원문, DeepSeek API 키와 현재 요청은 Agent Checkpoint에 저장하지 않는다.

Checkpoint, 실행 Lock과 HITL 재개 Context는 `(user_id, thread_id)` 조합으로 격리한다. 회의록 ID 목록은 하네스가 관리하며 후보 수 판단에는 숫자만 LLM에 전달한다.

## 6. POC 이후

POC가 설계의 기술적 성립을 확인한 뒤에만 실제 `zen-ai` 구조에 맞춘 이식을 별도 작업으로 수행한다. 이식 전략은 `5. zen-ai 현행 구조와 향후 이식 전략` 문서에서 다룬다.
