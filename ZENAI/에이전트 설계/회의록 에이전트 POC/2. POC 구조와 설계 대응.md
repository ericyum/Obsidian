## 파일별 역할과 설계 대응

| 파일 | 핵심 역할 | 구현된 설계 |
|---|---|---|
| `src/meeting_agent/state.py` | State와 실행 Context 정의 | 영속 Agent State를 `ScratchPad`, `authorized_meeting_ids`, `recording_modal_status`로 제한한다. `AgentContext`에 사용자·스레드·현재 요청을 분리하고 `run_id`, `request_id`, 지속 `search/question` 변수를 두지 않는다. |
| `src/meeting_agent/agent_graph.py` | 최상위 Agent Graph와 Search·Question Subgraph | `none → search/question → none` 개념을 Node·Edge로 구현한다. 두 Subgraph가 공통 Runtime 처리로 합류하고 후속 작업이 있으면 LLM 판단으로 돌아간다. |
| `src/meeting_agent/recording_graph.py` | 녹화 명령의 결정적 Workflow | LLM과 Agent Tool 없이 고정 경로로 녹화 모달·백엔드 대역을 호출한다. 실행 오류는 `recording_modal_status=error`로 변환한다. |
| `src/meeting_agent/runtime.py` | Graph 컴파일, Checkpoint, 실행·재개, 순차화 | Agent Graph에만 SQLite Checkpointer를 연결한다. 녹화의 실제 State는 Checkpoint하지 않고 결과 상태만 Agent State에 동기화한다. 동일 스레드는 프로세스 내에서 순차 실행한다. |
| `src/meeting_agent/model.py` | LLM 교체 경계와 오프라인 규칙 모델 | 의도·후속 작업 판단, 후보 수 해석, 시스템 지시·ScratchPad·Tool 결과·원문을 이용한 답변 생성 계약을 정의한다. |
| `src/meeting_agent/repository.py` | SQLite 업무 데이터와 권한·녹화 백엔드 대역 | Tool 1 후보 권한 필터, 선택 ID 재검증, Tool 2 허용 원문 조회, 녹화 State 전이와 모달 상태 저장을 담당한다. |
| `src/meeting_agent/cli.py` | 실행 가능한 POC 명령 | 더미 데이터 생성, 단일 요청, 대화형 실행, HITL 재개, 녹화 명령과 Agent State 확인을 제공한다. |
| `tests/test_agent.py` | Agent 설계 검증 | Search→Question 반복, HITL, 권한, 최소 State, 원문 비저장, Model 경계, Tool 재시도·구조화 오류, Compact를 확인한다. |
| `tests/test_recording.py` | 녹화 설계 검증 | 정상 전이, 정상 거부의 `healthy` 유지, 실행 오류의 `error` 동기화와 Agent State 분리를 확인한다. |

## 주요 흐름

### Search Subgraph

```text
LLM 목표 판단
→ Tool 1 접근 가능 후보 검색
→ Model이 후보 수 해석
→ 0개 / 1개 / 복수 후보 분기
→ 필요 시 HITL 선택
→ 선택 ID 백엔드 재검증
→ 기존 ID에 추가 또는 대체
→ SEARCH_RESPONSE_READY
→ 공통 처리 경계
```

설계의 Tool 1 범위는 `repository.search_meetings()`가 담당한다. 후보 수 해석은 `MeetingModel.interpret_candidate_count()`가 담당하며, 최종 검증된 ID만 `authorized_meeting_ids`에 반영한다.

### Question Subgraph

```text
LLM 목표 판단
→ authorized_meeting_ids 확인
→ Tool 2 원문 조회
→ 시스템 지시 + 현재 요청 + ScratchPad + 원문 + Tool 결과 조립
→ Model 답변
→ QUESTION_RESPONSE_READY
→ 공통 처리 경계
```

Tool 2에서 가져온 `documents`는 Node 지역 변수다. State에는 답변과 ID·제목·상태 같은 구조화 메타데이터만 남는다.

### 공통 Graph Runtime 처리

Search, Question과 Tool 없는 직접 답변은 `graph_runtime_checkpoint`로 합류한다. 여기서 `business_checkpoint` 이벤트를 기록하고 `compact_scratchpad`를 거친 뒤 다시 목표 판단 Node로 이동한다. Model이 `done`을 반환할 때만 END가 확정된다.

### 녹화 Workflow

```text
start / pause / resume / stop
→ recording_graph.py의 고정 Node
→ Repository의 권한·State 전이 검사
→ recording_sessions 갱신
→ recording_modal_status만 Agent Checkpoint에 동기화
```

`recording_state`는 Agent State나 Agent Checkpoint에 들어가지 않는다. 정상적인 허용 State 거부는 `healthy`, 모달·연결 실행 예외만 `error`다.

## Checkpoint와 Runtime 데이터 구분

| 구분 | 값 |
|---|---|
| 영속 Agent State | `ScratchPad`, `authorized_meeting_ids`, `recording_modal_status` |
| 비영속 실행 Context | `user_id`, `thread_id`, 현재 `request` |
| Subgraph 내부 실행값 | 후보 목록, 선택 ID, Tool 상태와 구조화 오류 |
| 원문 | 현재 Tool 2·Model 호출의 지역 변수 |
| 업무 완료 표시 | `ScratchPad`의 `business_checkpoint` 이벤트 |

LangGraph의 기술 Snapshot과 설계상의 업무 완료 Checkpoint를 구분한다. 최종 상위 Agent State와 상위 Checkpoint State에는 설계의 세 필드 외 실행 제어 필드가 남지 않는다.
