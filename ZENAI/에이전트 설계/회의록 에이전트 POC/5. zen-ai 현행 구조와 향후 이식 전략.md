# zen-ai 현행 구조와 향후 회의록 Agent 이식 전략

## 1. 이 문서의 역할

1~4번 문서는 Python·LangGraph POC가 **설계의 기술적 성립 여부**를 어떻게 검증하는지 설명한다. 이 문서는 그 검증이 끝난 뒤, 결과물을 실제 `zen-ai`에 어떤 방식으로 번역해 이식할지를 별도로 정리한다.

> POC 구조와 제품 구조는 같을 필요가 없다. POC에서 검증한 책임·불변 조건·테스트 시나리오를 제품의 기존 실행 구조에 맞게 옮기는 것이 핵심이다.

## 2. 현재 zen-ai의 Agent 실행 구조

조사 결과 Agent 관련 공통 코드는 `src/lib/agents`를 중심으로 구성되어 있다. Agent별 독립 LangGraph 서버를 두기보다 다음 실행 골격을 공유한다.

```text
Agent 정의·Registry/DB
→ Run 생성과 Queue
→ 공통 worker.ts
→ worker-runtime.ts
→ AI Provider + 허용 Tool
→ Thread·Message 영속화와 UI Streaming
```

모델은 `src/lib/ai/provider.ts`의 OpenAI 호환 Provider를 통해 생성되며, 환경별 Base URL과 API Key로 공급자를 바꿀 수 있다.

## 3. 녹화 기능의 실제 구조

실제 녹화 상태는 Agent가 아니라 Meeting Recording Provider와 BackendAdapter가 소유한다.

```text
MeetingRecordingState.phase
├─ idle
├─ preparing
└─ recording
   └─ status
      ├─ recording
      ├─ paused
      ├─ silent
      ├─ disconnected
      └─ stopping
```

- 시작 명령: `@meeting 회의시작`
- 종료 요청: `paused`로 전환하고 확인 UI 표시
- 종료 확인: `stopping`
- 저장 성공 확인: `idle`
- 저장 실패: `paused` 복귀

따라서 POC의 녹화 Graph와 `recording_modal_status`를 제품에 그대로 복사하지 않는다. POC에서 확인한 **녹화는 LLM 자유 판단이 아닌 결정적 Workflow**라는 원칙만 유지하고, 실제 Provider/BackendAdapter 계약을 사용한다.

## 4. POC 개념의 이식 매핑

| POC에서 검증한 개념 | zen-ai 이식 위치/방식 |
|---|---|
| 최상위 Graph의 목표 판단 | 공통 Worker의 모델 실행과 Tool Calling Loop |
| Search Subgraph | 회의 검색 Tool |
| Question Subgraph | 권한 검증된 원문 조회 Tool + Prompt |
| `authorized_meeting_ids` | Thread 또는 Run에 연결된 제품 상태/메타데이터 |
| `ScratchPad` | 기존 Thread Message와 Run 이벤트 |
| LangGraph Checkpoint | Run·Message DB 상태와 Worker 재개 규칙 |
| `interrupt()` HITL | `waiting_for_user`에 해당하는 Run 상태와 UI 선택 이벤트 |
| SQLite Repository | 실제 인증·회의·공유 권한 Backend |
| DeepSeek Adapter | 기존 OpenAI 호환 AI Provider 설정 |
| 녹화 Graph | 기존 Recording Provider/BackendAdapter 명령 연결 |

## 5. 유지할 것과 다시 작성할 것

### 유지할 설계 자산

- System Prompt와 모델 판단 규칙
- Search/Question Tool의 입력·출력 계약
- 권한은 LLM이 아닌 Backend가 강제한다는 원칙
- 원문은 답변 Context에만 넣고 영속 Agent 상태에 저장하지 않는 원칙
- 복수 후보와 추가·대체의 사용자 선택 규칙
- Search → Question 복합 목표 테스트 시나리오
- Tool 실패, Retry, Compact와 Thread 격리의 불변 조건

### zen-ai 구조로 다시 작성할 부분

- Python `StateGraph`와 Node 함수
- `SqliteSaver` Checkpoint
- CLI와 프로세스 내부 Lock
- SQLite 더미 Repository
- POC의 가상 녹화 상태 저장소

## 6. 권장 이식 순서

```text
1. POC 테스트로 설계 성립 확정
2. 회의 검색·원문 조회 Tool 계약을 TypeScript schema로 번역
3. 실제 인증 Session과 회의 권한 Backend에 연결
4. 회의록 Agent 정의를 기존 Registry/DB 방식으로 등록
5. 공통 Worker에서 Tool Calling과 Prompt 연결
6. 복수 후보 선택을 Run 대기 상태와 UI 이벤트로 연결
7. 기존 Recording Provider에 시작·정지 명령 연결
8. POC의 핵심 시나리오를 제품 통합 테스트로 재작성
9. Streaming, Retry, 멱등성, 관측성과 보안 검증
```

## 7. 주의할 점

- Python POC를 TypeScript로 줄 단위 번역하지 않는다.
- LangGraph State를 제품 DB에 그대로 복제하지 않는다.
- 실제 녹화 상태를 Agent가 중복 소유하지 않는다.
- DeepSeek 키 파일 방식은 로컬 POC 편의 기능일 뿐 제품에서는 기존 비밀 관리 방식을 사용한다.
- 이식 작업은 별도 단계이며 현재 POC 저장소에서 `zen-ai` 커밋이나 Draft PR을 만들지 않는다.
