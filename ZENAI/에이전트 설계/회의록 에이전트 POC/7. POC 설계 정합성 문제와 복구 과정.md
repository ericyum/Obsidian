# POC 설계 정합성 문제와 복구 과정

## 1. 문서 목적

이 문서는 회의록 Agent 설계 문서를 바탕으로 POC 구현을 맡긴 뒤, 구현이 실제 설계와 달라진 부분을 발견하고 다시 원본 설계에 맞게 복구한 과정을 기록한다.

단순히 “버그를 고쳤다”는 작업 일지가 아니라 다음 질문에 답하기 위한 회고 문서다.

- 설계 문서를 제공했는데도 왜 구현이 설계와 달라졌는가?
- 어떤 부분이 임의로 합쳐지거나 분리되었는가?
- 보안, HITL, Checkpoint와 Trace에는 어떤 문제가 있었는가?
- 어떤 기준으로 원본 설계와 동일하게 복구했는가?
- 이후 설계 기반 구현에서 무엇을 확인해야 하는가?

> 이 문서는 대화 내용을 그대로 재현한 기록이 아니다. 원본 설계 문서, 현재 코드·테스트, `docs/superpowers/specs`와 Git 변경 기록에서 확인되는 사실을 기준으로 정리한 회고다.

---

## 2. 처음 의도했던 것

POC의 질문은 처음부터 다음과 같았다.

> **“설계한 회의록 Agent를 Python과 LangGraph로 구현했을 때, 설계한 책임·상태 전이·HITL·보안 경계가 기술적으로 온전하게 동작하는가?”**

따라서 POC는 새로운 설계를 만드는 작업이 아니었다. 이미 작성된 다음 원본 설계를 실행 가능한 코드로 옮기고 검증하는 작업이었다.

- 최상위 Agent Graph
- Search Subgraph의 S1, S2-A, S2-B, S2-C, S3
- Question Subgraph의 Q1, Q2, Q3
- `response.follow_up`과 고정 Condition을 이용한 반복·종료
- `none`을 초기·종료 상태로 사용하는 규칙
- `ScratchPad`, `authorized_meeting_ids`, `recording_modal_status`
- 복수 후보 선택과 ID 추가·대체 HITL
- Tool 1 검색과 Tool 2 원문 조회의 권한 경계
- Agent Graph와 녹화 모달 Workflow의 분리

성공 기준은 코드가 그럴듯하게 작동하는 것이 아니라, **설계도에 표시된 Node·Edge·State와 책임이 그대로 실행되는 것**이었다.

---

## 3. 왜 문제가 늦게 발견되었는가

초기 구현도 일반적인 요청에는 응답했고 테스트도 일부 통과했다. 그러나 “동작한다”와 “설계대로 동작한다”는 같은 의미가 아니었다.

```text
겉으로 확인하기 쉬운 것
사용자 요청 → 검색 또는 답변 → 결과 출력

실제로 검증해야 했던 것
정확한 Node 책임
→ 정확한 Edge와 Condition
→ State 저장 범위
→ HITL 중단·재개
→ 권한 재검증
→ 원문 비영속성
→ 실제 Graph Trace
```

초기에는 최종 응답이 나오는지에 집중하기 쉬웠고, 설계도의 각 Node가 코드에서 동일한 책임으로 존재하는지까지 계약 테스트로 고정하지 못했다. 그 결과 구현 과정에서 동작을 단순화하거나 보완하려고 넣은 판단이 원본 설계를 조금씩 변경했다.

---

## 4. 발생했던 주요 문제

### 4-1. 설계의 Node를 임의로 합치거나 다시 분리함

원본 설계는 Search Subgraph를 다음 경계로 나눈다.

```text
S1 후보 검색 및 판단
→ S2-A 후보 없음
→ S2-B 후보 1개
→ S2-C 후보 복수
→ S3 선택 및 authorized_meeting_ids 반영
```

그러나 구현 과정에서 LLM 후보 판별을 별도 Node처럼 분리하거나, 설계상의 S2-A·S2-B·S2-C 책임을 다른 형태로 합치는 변화가 있었다.

Question Subgraph에서도 원래 설계는 다음 세 책임을 분리했다.

```text
Q1 권한 검증된 회의록 원문 조회
→ Q2 Tool 결과별 일시적 Context 조립
→ Q3 LLM 답변 생성
```

초기 구현에서는 이 책임들이 충분히 분리되지 않아, Trace상 Node 이름은 있어도 실제 책임이 설계와 일치하지 않는 문제가 있었다.

#### 해결

- Search를 S1, S2-A, S2-B, S2-C, S3 경계로 재구성했다.
- 후보 수의 LLM 구조화 판단은 S1의 책임 안에 배치했다.
- Question을 Q1 조회, Q2 Context 조립, Q3 답변 생성으로 실제 코드 책임까지 분리했다.
- 테스트에서 설계 Node의 존재와 불필요한 별도 Node의 부재를 확인하도록 했다.

### 4-2. 설계에 없는 종료 판단과 Node가 추가됨

원본 설계에서는 Search 또는 Question LLM 응답이 `response + follow_up`을 반환하고, 고정 Condition이 다음 경로를 정한다.

```text
follow_up = true
→ LLM 목표 판단으로 복귀

follow_up = false
→ none
→ END
```

그러나 구현 과정에서 Search·Question 이후 `decide_next_action()`을 다시 호출해 최종 종료까지 LLM이 판단하는 흐름이 생겼다. 또한 `graph_runtime_checkpoint`, `request_finished`처럼 설계에 없는 별도 업무 Node가 추가되었다.

#### 문제점

- 원래 필요하지 않은 LLM API 호출이 늘었다.
- LLM 실행 순서가 설계도와 달라졌다.
- 고정 Condition의 책임이 LLM으로 이동했다.
- Trace에 설계도에 없는 Node가 표시됐다.

#### 해결

- Search·Question 응답에 `follow_up`을 포함하도록 복원했다.
- 하네스의 고정 Condition이 반복 또는 종료를 결정하게 했다.
- 최종 `none` 확인용 LLM 호출을 제거했다.
- `graph_runtime_checkpoint`, `request_finished` Node를 제거했다.

### 4-3. 설계에 없는 `done` 상태 사용

원본 설계의 목표 상태에는 별도 `done`이 없으며, 수행할 후속 업무가 없으면 `none`으로 돌아간다.

구현과 Trace 설명 과정에서 `done`이 종료 상태처럼 사용되면서 설계 용어와 코드 용어가 달라졌다.

#### 해결

- 목표 상태를 `search`, `question`, `direct`, `none`으로 통일했다.
- 업무 종료는 `follow_up=false → 고정 Condition → none/END`로 표현했다.
- Queue나 실행기의 기술적 완료 의미와 Agent 업무 상태의 `none`을 구분했다.

### 4-4. 회의록 원문이 State·Checkpoint·Trace에 남을 가능성

회의록 원문은 Tool 2 실행 중 LLM 답변을 만들기 위한 일시적 Context일 뿐, Agent State나 Checkpoint에 저장되어서는 안 된다.

초기 구조에서는 Tool 결과나 중간 Context가 State에 섞이면서 원문이 LangGraph Checkpoint나 Trace에 남을 위험이 있었다.

#### 해결

- Q1에서 조회한 원문을 비추적 Node 지역 Context로만 전달했다.
- Q2에서 필요한 Context를 조립하고 Q3 호출 후 폐기하도록 했다.
- 원문을 최종 State, Checkpoint, Trace, 오류 메시지에서 제거했다.
- 모델이 원문을 구조화 응답의 추가 필드로 되돌려도 State에 병합하지 않도록 검증했다.
- 테스트에서 실제 원문 문자열이 모든 Checkpoint와 Trace에 없는지 확인했다.

### 4-5. `authorized_meeting_ids`가 불필요하게 LLM에 전달됨

설계상 `authorized_meeting_ids`는 LLM이 권한을 판단하기 위한 자료가 아니다. 서버가 Tool 2의 조회 범위를 제한하기 위해 관리하는 State다.

회의록 ID가 LLM에 필요한 지점은 Tool 1의 검색 결과가 0개, 1개, 복수인지 해석하는 Search 과정뿐이다. Question과 일반 목표 판단 Prompt에는 전체 허용 ID 목록이 들어가면 안 된다.

#### 해결

- 목표 판단 Prompt에서 `authorized_meeting_ids`를 제거했다.
- Question LLM 호출에 ID 목록을 전달하지 않았다.
- Tool 2가 서버 State에서 허용 ID를 읽어 원문을 조회하게 했다.
- 조회 직전 Repository가 실제 사용자 권한을 다시 검증하게 했다.
- Spy Model 테스트로 허용 ID가 모델 입력에 들어가지 않는지 고정했다.

### 4-6. HITL 대기 Context와 입력 오류 처리 부족

복수 후보나 추가·대체 선택을 기다리는 동안 잘못된 형식의 값 또는 새로운 일반 문장이 들어오면 기존 대기 Context가 손상되거나 Graph 밖으로 예외가 전파될 수 있었다.

또한 사용자와 Thread를 충분히 조합하지 않은 키는 서로 다른 사용자의 Checkpoint, Lock 또는 HITL Context가 충돌할 가능성을 만들었다.

#### 해결

- HITL 대기 중 허용되지 않은 입력은 같은 질문을 다시 표시하게 했다.
- 잘못된 입력으로 Pending Context를 삭제하거나 덮어쓰지 않게 했다.
- 후보 목록에 없는 회의록 ID도 구조화된 재질문으로 처리했다.
- 사용자 ID와 Thread ID를 함께 사용해 Checkpoint, Lock, HITL Context를 격리했다.
- 단순 문자열 연결 대신 충돌하지 않는 구조화 키를 사용했다.
- 같은 Thread ID라도 사용자가 다르면 State가 공유되지 않는 테스트를 추가했다.

### 4-7. 동일 ID 반복 검색에도 불필요한 추가·대체 HITL 발생

이미 허용된 `meeting-001`을 다시 검색했을 때도 “추가할지 대체할지” 묻는 흐름이 발생했다.

#### 해결

새 선택 ID가 기존 허용 ID에 이미 포함되어 있으면 `unchanged`로 처리해 추가·대체 HITL을 생략했다.

```text
기존 허용 ID = [meeting-001]
새 선택 ID = [meeting-001]
→ 변경 없음
→ HITL 없이 검색 응답
```

### 4-8. Tool 실패와 권한 거부의 의미가 섞임

후보 재검증 실패, 권한 회수, 일반 Backend 장애가 같은 예외 형태로 Graph 밖까지 전파되면 LLM이나 사용자에게 적절한 안내를 만들기 어렵다. 내부 예외 문구에 원문이나 구현 정보가 포함될 위험도 있다.

#### 해결

- 권한 거부와 일반 Backend 장애를 구분한 구조화 실패 코드로 반환했다.
- 설계상 재시도 가능한 실패는 해당 단계에서 재시도하게 했다.
- 거부나 복구 불가능한 실패는 안전한 안내 응답으로 종료하게 했다.
- Tool, DeepSeek, 모달, Web 오류에서 내부 예외 문자열을 그대로 노출하지 않게 했다.

### 4-9. 검색·질문 흐름이 녹화 모달 상태를 읽음

검색·질문 Agent Graph와 녹화 Workflow는 서로 독립적이다. 검색·질문을 실행할 때 `recording_modal_status`를 다시 읽을 이유가 없지만, 공통 Runtime 처리 과정에서 녹화 상태를 함께 동기화하는 결합이 생겼다.

#### 해결

- 검색·질문 실행 경로에서 녹화 모달 상태 조회를 제거했다.
- `recording_modal_status`는 녹화 Trigger를 실행한 결과에 따라서만 갱신하게 했다.
- 녹화 모달 내부 `recording_state`는 Agent State가 아니라 모달 Repository가 소유하게 했다.
- Agent Checkpoint에는 설계된 세 필드만 남겼다.

```text
ScratchPad
authorized_meeting_ids
recording_modal_status
```

### 4-10. 녹화 Trace가 실제 Graph 실행이 아닌 수동 표시였음

녹화 화면에서 보이는 일부 Trace는 실제 LangGraph 실행 이벤트가 아니라, 녹화가 실행되었다는 내용을 수동으로 조립한 표시였다.

이 방식은 UI에서는 그럴듯하게 보여도 `recording_modal_and_backend` Node와 Edge를 실제로 통과했는지 증명하지 못한다.

#### 해결

- 녹화 Workflow도 실제 LangGraph debug stream에 연결했다.
- `START → recording_modal_and_backend → END` 실행을 실제 Node·Edge Trace로 표시했다.
- 실행 결과에 따른 `recording_modal_status`와 업무 Checkpoint 갱신을 별도로 표시했다.
- 녹화 다이어그램의 상세 상태는 Agent Graph State가 아니라 모달 내부 상태라는 경계를 유지했다.

### 4-11. Trace가 실시간이 아니라 실행 후 재생됨

브라우저 Trace가 Graph 실행 중 바로 전송되지 않고, 실행 완료 후 수집된 이벤트를 일정 간격으로 재생하는 형태였다.

#### 문제점

- 실제 실행 중 어디에서 시간이 걸리는지 알 수 없었다.
- LLM API 응답 대기와 사후 UI 지연을 구분할 수 없었다.
- 발표 화면이 실제 LangGraph 실행 순서를 증명하지 못했다.

#### 해결

- LangGraph debug event가 발생하면 SSE로 즉시 브라우저에 전달하게 했다.
- 인위적인 110ms 재생 지연을 제거했다.
- Parent Graph와 Search·Question Subgraph namespace를 구분했다.
- Node 완료 후 State와 Edge가 실제 실행 순서대로 나타나게 했다.

### 4-12. 업무 Checkpoint와 기술 Snapshot 혼동

LangGraph는 매 Super-step 뒤 기술 복구용 State Snapshot을 만든다. 이를 모두 `State Checkpoint`로 화면에 표시하면서 설계도에 없는 Checkpoint가 Node마다 추가된 것처럼 보였다.

#### 해결

- 설계상의 업무 경계를 `graph_runtime_checkpoint`라는 별도 Node로 만들지 않았다.
- 기술 Snapshot은 Trace 화면에서 기본적으로 숨겼다.
- 필요할 때만 기술 Snapshot 표시 옵션을 켤 수 있게 했다.
- 녹화 결과 반영과 같은 설계상의 업무 Checkpoint는 기술 Snapshot과 다른 이름과 의미로 표시했다.

### 4-13. ScratchPad Compact의 의미 손실 가능성

Context 크기를 줄이기 위해 ScratchPad를 단순 절단하면 이전 검색·선택·질문의 의미가 사라지거나 현재 요청까지 잘릴 수 있었다.

#### 해결

- 현재 요청의 의미를 우선 보존했다.
- 오래된 기록부터 줄이고 필요한 요약을 남기게 했다.
- Compact 이후 Context가 설정된 상한의 50% 이내인지 테스트했다.
- 여러 번 Compact해도 현재 업무 수행에 필요한 정보가 남는지 확인했다.

## 5. 복구할 때 사용한 기준

수정 과정에서는 “더 좋아 보이는 구현”보다 다음 우선순위를 사용했다.

```text
1. 원본 회의록 Agent 설계 문서
2. 특히 1-2 문서의 Graph와 세부 순서도
3. 설계자가 설명한 Node·State·Edge의 의미
4. 해당 의미를 고정하는 회귀 테스트
5. 코드 단순화와 구현 편의
```

설계도와 코드가 다를 때 코드에 맞춰 설계를 해석하지 않고, 설계의 의도를 먼저 확인한 뒤 코드를 수정했다.

다만 설계 문서가 표현한 개념과 LangGraph의 기술 동작은 구분했다.

- 설계의 공통 처리 로직을 억지로 별도 Node로 만들지 않는다.
- 업무 Checkpoint와 LangGraph 기술 Snapshot을 같은 개념으로 취급하지 않는다.
- 녹화 모달 내부 State를 Agent Graph State로 복제하지 않는다.
- 보안 불변 조건은 LLM Prompt가 아니라 Repository와 Runtime 코드로 강제한다.

## 6. 최종 구현 구조

### 6-1. 일반 회의록 요청 Agent Graph

```text
START
→ 초기 상태 none
→ LLM 목표 판단
→ Search 또는 Question Subgraph
→ response.follow_up Condition
   ├─ true  → LLM 목표 판단으로 복귀
   └─ false → none → END
```

Search와 Question은 녹화 모달 State를 읽거나 변경하지 않는다.

### 6-2. Search Subgraph

```text
S1 후보 검색 및 LLM 구조화 판별
├─ none → S2-A 안내
├─ one → S2-B 단일 후보 처리
└─ many → S2-C 사용자 선택 HITL
              ↓
         S3 허용 ID 반영
              ↓
     검색 응답 + follow_up
```

### 6-3. Question Subgraph

```text
Q1 authorized_meeting_ids를 이용한 권한 재검증 원문 조회
→ Q2 Node 지역의 일시적 Context 조립
→ Q3 LLM 답변 + follow_up
→ 원문 Context 폐기
```

`authorized_meeting_ids` 자체는 Question LLM에 전달하지 않는다.

### 6-4. 녹화 Workflow

```text
START
→ recording_modal_and_backend
→ END
```

Agent 쪽에서는 녹화 Trigger 실행과 `recording_modal_status` 갱신만 담당한다. 실제 `recording_state` 변화는 모달 대역이 소유한다.

## 7. 현재 보장하는 핵심 불변 조건

| 구분 | 현재 보장 내용 |
|---|---|
| Node | Search S1·S2-A/B/C·S3와 Question Q1·Q2·Q3 책임이 설계와 일치 |
| Edge | `follow_up`을 읽는 고정 Condition으로 반복 또는 END 결정 |
| 종료 상태 | 별도 `done` 없이 `none` 사용 |
| 영속 State | `ScratchPad`, `authorized_meeting_ids`, `recording_modal_status`만 유지 |
| 회의록 원문 | Node 지역 Context에서만 사용하고 State·Checkpoint·Trace에 저장하지 않음 |
| 권한 | Tool 1 검색 및 Tool 2 원문 조회 시 Repository가 검증 |
| LLM ID 노출 | Search 후보 수 판별 이외에는 허용 ID 목록을 직접 전달하지 않음 |
| HITL | 사용자·Thread별 격리, 잘못된 입력 재질문, 동일 ID의 불필요한 Merge 생략 |
| 녹화 | 일반 Agent Graph와 분리된 결정적 Workflow |
| Trace | 실제 LangGraph debug event를 SSE로 즉시 전달 |
| Checkpoint 표시 | 업무 경계와 기술 Snapshot을 구분하고 기술 Snapshot은 기본 숨김 |
| 오류 | 내부 예외와 원문을 사용자 응답·Trace에 노출하지 않음 |

## 9. 이번 작업에서 얻은 교훈

### 9-1. 설계 문서를 전달하는 것만으로는 충분하지 않다

AI나 개발자에게 설계도를 주더라도, 구현 과정에서는 단순화·추상화·오류 보완을 이유로 Node와 책임이 바뀔 수 있다. 따라서 각 Node의 이름뿐 아니라 **입력, 책임, 출력, 다음 Edge와 금지 사항**을 테스트 계약으로 고정해야 한다.

### 9-2. 동작 여부와 설계 정합성을 별도로 검증한다

응답이 정상 출력된다고 설계대로 구현된 것은 아니다.

```text
기능 테스트
“사용자 요청에 답하는가?”

설계 계약 테스트
“정해진 Node·Edge·State·권한 경계를 거쳐 답하는가?”
```

두 종류의 테스트가 모두 필요하다.

### 9-3. 설계에 없는 개선을 임의로 넣지 않는다

별도 완료 Node, 추가 LLM 판단, 공통 Checkpoint Node처럼 구현자가 좋아 보인다고 추가한 구조도 원본 설계의 책임을 바꿀 수 있다.

필요한 개선이 보이면 먼저 다음을 확인해야 한다.

1. 설계에 이미 같은 책임이 있는가?
2. 새 Node가 아니라 기존 Node 내부 처리인가?
3. 업무 개념인가, Framework의 기술 동작인가?
4. 설계 변경이 필요하다면 설계자와 먼저 합의했는가?

### 9-4. 보안 불변 조건은 출력 결과가 아니라 저장 경로까지 검사한다

원문이 화면에 보이지 않는 것만으로는 충분하지 않다. State, Checkpoint, Trace, Log, 오류와 Tool Audit까지 검사해야 한다.

### 9-5. Trace는 실제 실행의 증거여야 한다

Node 이름을 수동으로 그려서 보여주는 화면은 설명 자료일 뿐 실행 증거가 아니다. 실제 Graph event를 발생 즉시 전달해야 설계 경로, 지연 구간과 실패 위치를 확인할 수 있다.

## 10. 이후 작업 기준

회의록 Agent POC를 수정할 때는 다음 순서를 사용한다.

1. 원본 설계 문서와 1-2의 Graph를 먼저 확인한다.
2. 변경 대상 Node의 입력·책임·출력·Edge를 적는다.
3. 설계에 없는 Node 또는 State가 필요한지 먼저 검토한다.
4. 관련 계약 테스트를 먼저 추가하거나 수정한다.
5. 코드 변경 후 전체 오프라인 테스트를 실행한다.
6. 실제 Trace에서 Node·Edge·State와 Subgraph 경계를 확인한다.
7. 원문, 허용 ID, API Key가 저장·노출되지 않는지 검사한다.
8. 설계 계약이 바뀌었다면 원본 설계와 POC 문서를 함께 갱신한다.

## 핵심 정리

> 초기 POC는 사용자 요청에 응답할 수 있었지만, 일부 Node 책임과 LLM 실행 순서, 종료 State, HITL, 원문 저장 경계, 녹화 및 Trace가 원본 설계와 달랐다. 이후 원본 설계도를 규범으로 다시 고정하고 Search S1·S2-A/B/C·S3, Question Q1·Q2·Q3, `follow_up → none/END`, 서버 관리 허용 ID, 원문 비영속성, 사용자·Thread별 HITL, 독립 녹화 Workflow와 실제 LangGraph Trace를 코드와 회귀 테스트로 복구했다.
