# 회의록 에이전트 워크플로우 Graph 상세

이 문서는 회의록 에이전트의 **State, Checkpoint, 녹화 Trigger·모달, Tool과 세부 실행 Graph**를 정의하는 개발 상세 문서다.

서비스의 목적, 사용자와 전체 업무 흐름을 먼저 확인하려면 [[1-1. 회의록 에이전트 업무 개요]]를 참고한다.

> [!info] 권장 읽기 순서
> 처음 읽는 사람은 **그림의 계층 → State 표기 원칙 → 용어·색상 부록**을 먼저 확인한 뒤, 서로 독립된 녹화 Workflow Graph와 검색·질문 Agent Graph에서 필요한 상세 순서도로 내려가며 읽는다.

## 1. 기술 그림과 전체 구조

이 절은 문서의 중심이 되는 다이어그램을 읽기 전에, **업무 개요도에서 서로 독립된 Graph와 상세 순서도로 구체화되는 계층**과 회의록 시스템의 전체 기술 실행 구조를 설명한다.

### 1-1. 다이어그램의 계층과 역할

[[1-1. 회의록 에이전트 업무 개요]]의 그림은 전체 업무를 큰 단위로 나눈 **업무 개요도**다. 이 문서에서는 그 업무 단위를 실제 실행 단위로 바꾸고, 필요한 Node를 다시 내부 Graph로 펼친다.

```text
업무 개요도
├─ 독립된 회의 녹화 Workflow Graph → 녹화 Node 내부 순서도
└─ 회의록 검색·질문 Agent Graph → 검색·질문 상세 순서도
```

| 그림 | 답하려는 질문 | 이 문서의 예시 |
|---|---|---|
| **업무 개요도** | 전체 업무를 어떤 큰 단위로 나누는가? | 1-1 문서의 전체·하위 업무 흐름 |
| **독립 Workflow Graph** | LLM 없이 고정 규칙으로 실행되는 별도 Workflow의 Node와 Edge는 무엇인가? | 회의 녹화 Workflow Graph |
| **Agent Graph** | LLM 판단으로 이동하는 Agent의 Node와 Edge는 무엇인가? | 검색·질문 Agent Graph |
| **내부 순서도** | 하나의 Node 내부에서 무엇을 검사·실행하는가? | 회의 시작·제어, 검색·선택, 회의록 질의 상세 절차 |
| **State 전이도** | 특정 Graph 계층의 State가 어떻게 바뀌는가? | 모달의 `recording_state` 전이 |

복잡한 Node는 다시 내부 Graph로 나눌 수 있지만, 현재 검색·질문 설계에서는 그렇게 나누지 않고 **상위 State와 상세 순서도**만 표시한다.

State 전이도와 순서도는 같은 그림이 아니다. State 전이도는 **State 변화만**, 순서도는 **Node 내부 처리 순서와 조건**을 보여준다. 순서도에도 State 확인·변경이 표시될 수 있지만 사각형 전체가 State를 뜻하지는 않는다.

회의 녹화에는 LLM 판단이 없으므로 **독립된 결정적 Workflow Graph**로 표현한다. 회의록 검색·질문처럼 LLM이 Edge의 경로를 판단하는 과정은 **Agent Graph**로 표현한다. 두 Graph는 상위·하위 관계가 아니며 서로의 **Graph State**를 읽거나 변경하지 않는다. 다만 각각의 내부 업무를 Node·Edge·State로 구분하므로 두 그림 모두 Graph Engineering 방법론을 적용한다.

### 1-2. 전체 기술 구조

회의 녹화 명령과 회의록 검색·질문은 실행 진입 방식이 다르다.

```text
회의 시작·일시정지·재개·종료
→ 오케스트레이터의 고정 Trigger 코드
→ 회의 탭·상단바 버튼과 동일한 녹화 모달 로직
→ 기존 녹화 백엔드 메서드
→ 모달이 recording_state 갱신
→ 모달이 결과 신호 반환
→ 오케스트레이터가 recording_modal_status 반영

회의록 검색·질문
→ LLM이 의도와 Tool 호출 여부 판단
→ Tool 뒤의 백엔드가 권한·입력·리소스 상태 검사
→ authorized_meeting_ids 또는 답변 반영
```

녹화 명령은 LLM이나 Agent Tool이 판단하지 않는다. 권한과 실제 업무 상태도 LLM이 확정하지 않으며, 녹화 모달과 신뢰 가능한 백엔드가 검사한다.

## 2. State·Checkpoint 적용 원칙



### 2-1. State 적용 기준

이 문서에서 **State는 현재 Graph가 어느 실행 단계에 있는지를 나타내는 유한한 상태**다. 다이어그램 한쪽의 **State 정의표**에는 사용할 State의 뜻을 적고, 실제 값이 바뀌는 Edge에는 **State 변경 지점**을 명시한다.

```text
검색·질문 Agent Graph State
none / search / question
```

검색·질문 Graph에서는 `none`, `search`, `question`만 사용한다. 상세 순서도의 세부 실행 단계에는 별도의 State를 만들지 않는다. 이 State도 실제 코드에 같은 이름의 변수를 만들 필요는 없으며, 현재 실행 중인 Node와 선택된 Edge로 표현할 수 있다.

> [!warning] 코드의 `State = {}`와 구분
> 에이전트 코드에서 `State = {}`라고 부르는 객체는 Node 사이에 전달할 값을 모아 둔 **데이터 창고**다. 이 문서에서 말하는 Graph의 State와는 별개의 개념이다.

```python
State = {
    "messages": [...],
    "authorized_meeting_ids": ["meeting-123"],
    "recording_modal_status": "healthy",
}

RecordingModalState = {
    "recording_state": "recording",
}
```

- 코드의 `messages`, `authorized_meeting_ids`, `recording_modal_status`는 데이터 창고 안의 값이다.
- 모달의 `recording_state`는 `none`, `recording`, `pause`, `stop`이라는 유한한 값을 가지므로 Graph의 State를 코드로 직접 구현한 경우다.
- 검색·질문 State는 한 요청 안에서만 이동하므로 코드에 별도 지속 변수를 만들지 않는다.

`recording_modal_status`는 모달이 정상적으로 응답하고 동작하면 `healthy`, 모달 연결이나 실행 자체에 오류가 있으면 `error`다. 녹화 상태 조건에 따른 정상적인 거부는 모달 오류가 아니므로 `healthy`를 유지한다.

검색·질문은 모달의 `recording_state`를 변경하지 않으므로 회의 녹화 중에도 함께 처리할 수 있다.

### 2-2. Checkpoint 적용 기준

Checkpoint는 **워크플로우가 끝난 시점의 오케스트레이터 State와 실행 결과를 저장**한다.

- 녹화 Trigger 처리는 모달이 보낸 결과 신호가 `recording_modal_status`에 반영된 지점에 저장한다.
- 모달 내부의 `recording_state`는 Agent Checkpoint에 저장하지 않는다.
- 검색은 검증된 ID가 `authorized_meeting_ids`에 반영된 지점에 저장한다.
- 질문은 사용자 질문과 생성된 답변이 `messages`에 반영된 지점에 저장한다.
- 검색 후보가 여러 개여서 HITL로 기다릴 때는 같은 스레드의 런타임 내부 스냅샷으로 중단·재개하며, 업무 완료 Checkpoint와 구분한다.

Checkpoint는 **저장된 세이브 포인트**이며 자동 복구 기능 자체는 아니다. 오류가 발생하면 복구 로직이 마지막 정상 Checkpoint를 선택하고 해당 Agent 업무를 다시 실행해야 한다.

State와 Checkpoint의 구체적인 저장 구조는 [[2-1. 회의록 에이전트 현재 구현 상세 설계]]에서 다룬다.

## 3. 다이어그램을 읽기 위한 용어·표기 부록

> [!info] 이 절의 역할
> 이 절은 회의 녹화와 회의록 검색·질문의 본 흐름을 설명하는 부분이 아니라, 이후 다이어그램에 등장하는 **용어, 도형과 색상**을 해석하기 위한 부록이다. 익숙한 독자는 필요한 항목만 확인해도 된다.

| 용어                    | 이 문서에서의 의미                                                    |
| --------------------- | ------------------------------------------------------------- |
| **Agent**             | 사용자의 요청을 이해하고 필요한 Tool 호출이나 답변을 판단하는 AI                       |
| **LLM**               | 요청 해석, Tool 호출 여부와 답변을 생성하는 AI 모델                             |
| **코드의 `State = {}`**  | 오케스트레이터가 Node 사이에 전달하는 대화·검증 ID·모달 상태 정보의 데이터 창고              |
| **State**             | 현재 Graph 계층이 어느 실행 단계에 있는지 나타내는 유한한 상태                        |
| **저장 지점(Checkpoint)** | 정상적으로 완료된 업무 결과와 State를 저장한 지점                                |
| **실행 관리자(오케스트레이터)**   | Graph 이동, 실행 결과 반영과 Checkpoint 저장을 담당하는 구성요소                  |
| **녹화 모달 State**       | 임베디드 상단바 모달이 관리하는 실제 녹화 진행 상태                                 |
| **에이전트 호출 기능(Tool)**  | LLM이 백엔드 기능을 호출할 때 사용하는 이름·Description·Schema 기반 인터페이스        |
| **사용자 선택 대기(HITL)**   | AI가 임의로 결정하지 않고 사용자의 선택을 기다리는 구간                              |
| **Node**              | Graph에서 하나의 실행 책임을 담당하는 단계                                    |
| **Subgraph Node**     | 상위 Graph에서는 하나의 Node이지만 내부를 다시 Node·Edge·State로 펼칠 수 있는 실행 단위 |
| **Edge**              | 다음 실행 단계로 이어지는 경로                                             |
| **분기 조건(Condition)**  | 실행 결과에 따라 이동할 Edge를 선택하는 규칙                                   |

### 3-1. Trigger·모달·Tool·백엔드 구분

- **녹화 Trigger**: `회의 시작`, `/meeting-start`처럼 오케스트레이터의 고정 코드에 등록된 명령이다. LLM이나 Tool을 거치지 않고 기존 UI 버튼과 동일한 모달 로직을 실행한다.
- **녹화 임베디드 상단바 모달**: 실제 `recording_state`를 소유하고 시작·일시정지·재개·종료에 맞는 기존 백엔드 메서드를 호출한다.
- **Tool**: LLM이 이름·Description·Schema를 보고 호출하는 Agent의 실행 인터페이스다. 현재 Tool은 회의록 검색·선택과 원문 조회에만 사용한다.
- **오케스트레이터**: 고정 녹화 Trigger를 연결하고, 모달의 결과 신호를 받아 `recording_modal_status`를 갱신하며 Graph 이동과 Checkpoint 저장을 담당한다.
- **LLM**: 회의록 검색·질문의 Tool 호출 여부를 판단하고 실행 결과를 바탕으로 답변을 생성한다.
- **백엔드**: 인증·권한·실제 리소스 상태를 검사하고 기존 녹화·검색·조회 로직을 실행한다.

녹화 시작·일시정지·재개·종료는 Agent Tool이 아니다. Agent에 연결되는 Tool은 회의록 검색·선택과 원문 조회 두 개다.

### 3-2. 다이어그램 표기

| 요소               | 의미                                            | 표현                        |
| ---------------- | --------------------------------------------- | ------------------------- |
| Start·End        | Graph 실행의 시작, 이번 요청의 완료 또는 요청 대기 복귀 지점        | 타원형                       |
| Node             | 고정 Trigger 처리, 모달 실행, LLM 판단, Tool 호출, 백엔드 처리 | 사각형                       |
| Subgraph Node    | 내부에 별도의 Node·Edge 구조가 있는 상위 Node                 | `Subgraph Node` 라벨이 있는 사각형 |
| Subgraph Entry·Return | 상위 Graph와 하위 Subgraph가 연결되는 진입·반환 경계          | 타원형                       |
| Edge             | 다음 단계로 이동하는 실행 경로                             | 화살표                       |
| Edge 라벨          | Edge의 요청 종류, 전이 조건 또는 구조화된 실행 결과              | 화살표 위의 반투명 연회색 배경판과 글자    |
| Condition        | 실행 결과에 따라 다음 경로를 선택하는 단계                      | 마름모                       |
| State            | 현재 Graph 계층의 실행 상태                                  | State 정의표와 Edge의 State 변경 표기 |
| Node 범위          | 하나의 Node로 묶은 실행 책임의 시작과 끝                        | Graph별 강조색 점선 경계 박스           |
| State 정의표        | 해당 Graph 계층에서 사용하는 State와 의미                     | 다이어그램 한쪽의 Graph별 강조색 설명 박스 |
| State 범위          | 특정 State가 유지되는 Graph 구간의 시작과 끝                    | Graph별 강조색 실선 경계 박스           |
| State 변경 지점      | Node 결과에 따라 State 값이 실제로 달라지는 지점                 | Edge 가까이의 `State 변경 · A → B` 표기 |
| 업무 경계 Checkpoint | 완료된 요청의 코드 `State = {}` 데이터와 실행 결과를 저장하는 지점 | 원통형                       |
| 담당 영역            | LLM·오케스트레이터·Tool/백엔드의 책임 범위                   | 처리 구간별 반투명 영역 박스          |
| 규칙·설명 주석         | 실행 Node에 적용되는 규칙이나 책임 경계 설명                   | 연한 보라색 배경·보라색 점선 테두리와 연결선 |
| 국소 루프            | 같은 Node의 반복 또는 실패 이유 반환 후 재시도                 | 주황색의 작은 복귀 화살표            |
| 다음 요청 루프         | 이번 요청 완료 후 Agent 요청 대기로 복귀                    | 짙은 초록색 외곽 복귀 화살표          |
| Graph Runtime 공통 종료 처리 | 여러 실행 경로가 합류한 뒤 `messages` 반영·Checkpoint·END를 처리하는 런타임 경계 | 회색 점선 영역 또는 END 옆 주석 |

- **초록색 네모**: 사용자 입력·Trigger 또는 `Agent 요청 대기`, `recording_state=none`과 같은 입력·대기 경계
- **노란색 네모**: Human in the Loop
- **빨간색 네모·영역**: LLM 판단·생성과 LLM 담당 범위
- **파란색 네모·영역**: 결정적 Workflow 또는 오케스트레이터의 Tool 인터페이스·State 반영·Condition·컨텍스트 조립·Checkpoint
- **회색·흰색 네모·영역**: Tool 인터페이스 뒤에서 실행되는 백엔드 로직의 확정적 검사·실행
- **연한 보라색 네모**: 실행 요소가 아닌 규칙·설명 주석. 보라색 점선 테두리와 화살촉 없는 점선 연결선 사용
- **주황색 점선·실선·State 표기**: 회의록 검색·질문 Agent Graph의 Node 범위, State 범위와 변경 지점
- **하늘색 점선·실선·State 표기**: 별도로 실행되는 회의 녹화 Workflow의 Node 범위, `recording_state` 범위와 변경 지점
- **회색 화살표**: 정해진 단방향 진행
- **빨간색 화살표**: LLM 선택 또는 Condition 결과에 따라 갈라지는 분기
- **주황색 화살표**: 실패 후 재시도나 일시정지·재개 같은 국소 반복
- **짙은 초록색 화살표**: 업무 완료 후 다음 사용자 요청 대기로 복귀

화살표의 요청·조건·결과 문구는 대응하는 Edge의 경로 위에 고정하며, 선이 글자를 관통하지 않도록 **반투명 연회색 배경판**을 사용한다. 국소 반복은 해당 Node 가까이의 작은 주황색 복귀 화살표로 표시하고, 요청 전체가 끝난 뒤 다시 입력을 기다리는 반복은 다이어그램 외곽의 짙은 초록색 복귀 화살표로 구분한다.

점선 박스는 **Graph에서 하나의 Node로 보는 범위**이고, 실선 박스는 **State가 유지되는 범위**다. 검색·질문 Agent Graph는 주황색, 독립된 녹화 Workflow는 하늘색을 사용하여 두 State 체계가 연결되거나 공유되는 것으로 오해하지 않게 한다. `State 변경 · A → B` 표기는 앞 Node의 출력으로 State가 바뀌어 다음 Edge가 선택되는 정확한 지점을 보여준다. 검색·질문의 상세 순서도 자체에는 Node 경계나 별도 State를 중첩하지 않고, 각 상위 Node의 내부 구조는 순서도 바로 아래의 전용 Subgraph에서 따로 표현한다.

Graph Runtime의 공통 종료 처리는 독립 업무 Node가 아니다. 최종 실행 Node가 반환한 답변과 State 부분 업데이트를 런타임이 `messages`에 반영하고 Checkpoint를 저장한 뒤 END를 확정하는 공통 경계이므로, Node 사각형 대신 회색 점선 영역이나 END 옆 주석으로 나타낸다.

규칙·설명 주석은 실행 흐름에 포함되는 Node가 아니므로 **연한 보라색 배경과 보라색 점선 테두리**로 표시하고, 설명 대상과는 **화살촉 없는 보라색 점선**으로만 연결한다. Tool·백엔드 실행 요소는 회색·흰색 배경과 실선 테두리 및 실행 화살표를 사용하므로 주석과 구분된다.

> 권한과 실제 업무 상태는 LLM이나 Condition이 결정하지 않는다. 녹화 모달과 Tool 뒤의 백엔드가 검사하고, Condition은 구조화된 실행 결과에 따라 응답 경로만 선택한다.

## 4. 회의 녹화 과정

> [!summary] 회의 녹화 과정 한눈에 보기
> - **사용자:** 회의 생성자
> - **모달 시작 State:** `recording_state = none`
> - **주요 행동:** 시작, 일시정지, 재개, 종료
> - **종료:** 회의 종료 처리 후 `recording_state = none`
> - **특징:** 실제 녹화 State는 모달이 관리하고 Agent는 모달의 정상·오류 상태만 관리

> [!warning] Graph State와 코드 데이터를 구분해야 한다
> - **검색·질문 Agent Graph의 State:** `none`, `search`, `question`으로 구분되는 Agent 요청 단계
> - **독립된 녹화 Workflow의 State:** `none`, `recording`, `pause`, `stop`으로 구분되는 현재 녹화 단계
> - **코드 데이터 창고의 값:** `authorized_meeting_ids`, `recording_modal_status = healthy | error`
> - **내부 State의 실제 구현 위치:** 상단바 모달의 `recording_state = none | recording | pause | stop`
>
> 양쪽에서 사용하는 `none`은 이름만 같을 뿐 **서로 다른 소유자와 의미를 가진 별개의 State**다. Agent Graph의 `none`은 검색·질문 요청 대기이고, 녹화 Workflow의 `none`은 녹화 전·녹화 요청 대기다. 어느 한쪽의 State 변화도 다른 쪽 State에 영향을 주지 않는다. 오케스트레이터의 `State = {}` 객체 전체를 Graph State로 해석하지 않으며, 녹화 상태 전이와 허용 동작은 모달이 관리한다. 오케스트레이터는 모달이 정상적으로 동작하는지만 `recording_modal_status`로 관리한다.

> [!important] 회의 녹화는 Agent 판단 과정이 아니라 Workflow다
> 회의 녹화에서는 LLM이 사용자의 의도를 해석하거나 다음 기능을 선택하지 않는다. 오케스트레이터의 고정 Trigger 코드, 녹화 모달과 백엔드가 정해진 규칙에 따라 실행하는 **결정적 Workflow**다.

이 과정은 세 가지 관점으로 표현한다. **회의 녹화 Workflow Graph**는 녹화 단계별 Node와 Trigger에 따른 이동을, **State 전이도**는 모달 내부 `recording_state`의 허용 전이만을, 각 **순서도**는 Trigger 뒤에서 실행되는 모달·백엔드·결과 신호의 상세 절차를 보여준다.

**Node를 이렇게 나눈 이유**

- **요청 대기·회의 시작 Node (`none`)**: 녹화 전 상태에서 회의 시작 Trigger를 기다리고 시작 요청을 처리하는 업무 단위다.
- **녹화 Node (`recording`)**: 실제 녹화가 진행되는 동안 일시정지 또는 종료 Trigger를 받을 수 있는 업무 단위다.
- **일시정지 Node (`pause`)**: 녹화가 멈춘 동안 재개 또는 종료 Trigger를 받을 수 있는 업무 단위다.
- **종료 처리 Node (`stop`)**: 종료 백엔드와 모달 처리가 완료될 때까지 유지되는 업무 단위다. 종료 처리가 완료되면 `none`으로 바뀌고 END를 거쳐 다음 Trigger를 기다린다.

각 Node의 State는 **녹화 임베디드 상단바 모달이 실제 코드로 관리하는 `recording_state`**다. 고정 Trigger 판별, 모달 실행, 권한 검사와 백엔드 호출은 각 Node 사이의 전이를 성립시키기 위한 내부 실행이며, 더 이상 최상위 Node로 나누지 않는다.

#### 회의 녹화 단계별 State 변화

| 단계 | 실행 경로 | 모달의 `recording_state` | Agent의 `recording_modal_status` |
|---|---|---|---|
| 회의 시작 | 고정 Trigger → 모달 → 시작 백엔드 | `none → recording` | 정상 응답 시 `healthy` |
| 회의 일시정지 | 고정 Trigger → 모달 → 일시정지 백엔드 | `recording → pause` | 정상 응답 시 `healthy` |
| 회의 재개 | 고정 Trigger → 모달 → 재개 백엔드 | `pause → recording` | 정상 응답 시 `healthy` |
| 회의 종료 | 고정 Trigger → 모달 → 종료 백엔드 | `recording·pause → stop → none` | 정상 응답 시 `healthy` |
| 모달 연결·실행 오류 | 모달 결과 신호 | 기존 값 유지 | `error` |

`stop`은 녹화 종료 처리 시 거치는 모달 상태다. 종료 처리가 완료되면 모달은 `recording_state`를 바로 `none`으로 변경하고 Agent의 녹화 업무는 끝난다.

## 5. 회의록 검색·질문 과정

> [!summary] 회의록 활용 과정 한눈에 보기
> - **사용자:** 회의록을 공유받은 사용자
> - **시작:** Agent 요청 대기
> - **주요 행동:** 회의록 검색·선택 또는 원문 기반 질문
> - **종료:** 요청 처리 후 Agent 요청 대기
> - **남는 결과:** `authorized_meeting_ids` 또는 생성된 답변
> - **특징:** Graph에는 `none`, `search`, `question` State가 있지만 같은 이름의 지속 코드 변수는 만들지 않음

검색과 질문은 Graph에서 `none → search | question → none`으로 전환된다. `search`와 `question`은 해당 요청의 `END`까지 유지되고, **END 직후 입력 대기로 복귀하는 Edge에서 `none`으로 변경**된다. 이 State는 현재 실행 Node로 표현하며 별도 지속 코드 변수로 저장하지 않는다. 다음 질문에도 필요한 결과만 코드의 데이터 창고인 `messages`와 `authorized_meeting_ids`에 남긴다.

### 5-0. Graph Engineering 관점의 Agent Graph

#### Node·Edge·State 핵심 Graph

> **그림 유형: Node·Edge·State 핵심 Graph**  
> Agent의 내부 실행 요소를 제외하고 **Node, Edge, State만 남긴 최상위 개념도**다. `none`의 의도 판단 Node에서 `search` 또는 `question` Subgraph Node로 이동하고, 각 요청의 답변이 완료되면 `none`으로 돌아오는 구조만 먼저 파악한다.

#### 구현 요소를 포함한 상세 Graph

> **그림 유형: 최상위 Agent Graph**  
> LLM의 의도 판단 결과에 따라 `none`에서 `search` 또는 `question`으로 이동하는 가장 바깥 Graph다. 검색·선택과 질의는 내부 Subgraph를 가진 상위 Node이며, `search`와 `question`은 각 END까지 유지되고 END 직후 복귀 Edge에서 `none`으로 바뀐다. Tool 없는 직접 답변은 `none`을 유지한다. 주황색 점선은 세 상위 Node의 정확한 범위이며, Edge의 주황색 표기는 State가 바뀌는 지점이다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/09_Graph_Engineering_Agent_Graph_개선.svg]]

**Node를 이렇게 나눈 이유**

- **사용자 의도 판단 Node**: 현재 요청이 새 회의록 검색인지, 선택된 회의록을 이용한 질문인지 LLM이 판단한다.
- **회의록 검색·선택 Subgraph Node**: 검색 조건 추출부터 권한 필터, 후보 결과 판단, 검증된 ID 반영과 최종 LLM 안내까지가 한 번의 검색 요청이다. 내부 Node·Edge는 5-1의 Search Subgraph에서 펼친다.
- **회의록 질의 Subgraph Node**: 검증된 ID로 원문을 조회하고 컨텍스트를 조립해 LLM이 질문 한 번에 답변하는 단위다. 내부 Node·Edge는 5-2의 Question Subgraph에서 펼친다.

`END`는 에이전트 세션 종료가 아니라 **이번 요청의 처리가 완료된 경계**다. `search`와 `question`은 END까지 유지되며, END를 지난 복귀 Edge에서 `none`으로 변경되어 다음 입력을 기다린다.

### 5-0-1. Agent State·업무 연결도

> **그림 유형: Agent State·업무 연결도**  
> 최상위 Agent Graph의 `none`, `search`, `question` Node 범위를 유지하면서 검색·선택과 질의의 상세 실행 흐름을 함께 보여주는 그림이다. 별도의 내부 State는 추가하지 않고, 상위 State의 변경 지점만 Edge에 표시한다.

아래 그림은 `none`에서 사용자 입력을 받은 LLM이 **검색·선택, 원문 조회·답변 또는 Tool 없는 직접 답변** 중 하나를 판단하고, 각 업무의 END를 지난 뒤 다시 `none`으로 돌아오는 구조를 보여준다. Tool이 필요 없는 요청은 이 판단 Node에서 바로 답변을 생성하므로 별도의 직접 답변 Node를 두지 않는다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/10_Agent_오케스트레이터_State_갱신_흐름_개선.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/10_Agent_오케스트레이터_State_갱신_흐름.excalidraw)

검색·질의와 판단 Node에서 생성된 직접 답변은 **Graph Runtime 공통 종료 처리 경계**로 합류한다. 이 구간은 독립 업무 Node가 아니라, 진입 경로의 `search`, `question` 또는 `none`을 유지한 채 최종 답변과 State 부분 업데이트를 `messages`에 반영하고 Checkpoint를 저장한 뒤 END를 확정하는 런타임 처리다. END 직후 공통 복귀 Edge에서 `search/question → none`으로 정리하고, 직접 답변 경로는 `none`을 유지한다. 검색 결과 없음, ID 추가·대체·설정, 질의 대상 없음과 Tool 오류도 모두 정형화된 결과로 LLM에 전달되어 최종 사용자 응답이 생성된다. 이 과정에서 `recording_modal_status`와 모달의 `recording_state`는 변경하지 않는다.

### 5-1. 관련 회의록 검색·선택 상세 순서도

> **그림 유형: 검색·선택 상세 순서도**  
> 검색·선택 업무의 세부 처리 순서를 빠짐없이 보여주는 구현 순서도다. 이 순서도 자체에는 Node 경계를 중첩하지 않으며, 바로 아래의 Search Subgraph에서 같은 흐름을 내부 Node·Outcome Edge로 다시 묶는다. 내부 Node들은 별도의 State 값을 추가하지 않고 모두 상위 State인 `search`를 유지한다. LLM이 검색 경로를 결정하기 전까지는 `none`, 결정 직후부터 END까지는 `search`, END 직후 복귀 Edge부터 다시 `none`이다.

#### Search Node 내부 Subgraph

> **그림 유형: Search Node 내부 Subgraph**  
> 최상위 Agent Graph의 `회의록 검색·선택 Subgraph Node`를 펼친 그림이다. 내부 Node들은 모두 상위의 개념적 State인 `search`를 유지하며, 마지막 Node가 `SEARCH_RESPONSE_READY`를 반환한 뒤 Graph Runtime 공통 종료 처리에서 END가 확정된다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/14_Search_Node_내부_Subgraph_개선.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/14_Search_Node_내부_Subgraph.excalidraw)

Subgraph의 첫 번째 Node는 Tool 1 인터페이스 호출부터 백엔드 권한 필터·후보 검색, LLM의 후보 결과 해석까지를 한 책임으로 묶는다. LLM이 반환한 `NO_CANDIDATES`, `ONE_CANDIDATE`, `MULTIPLE_CANDIDATES` Outcome이 다음 Edge를 구분한다. 두 번째 Node는 Outcome에 따라 후보 없음, 자동 선택 또는 HITL을 처리하고 `authorized_meeting_ids`를 설정·추가·대체한 뒤 LLM 최종 답변을 생성한다. 세 Outcome 모두 최종적으로 같은 두 번째 Node로 들어가지만 전달하는 결과가 다르므로, 해당 Node 안에서 실행되는 결정적 경로가 달라진다.

두 번째 Node가 반환한 `SEARCH_RESPONSE_READY` 이후의 `messages` 반영·Checkpoint·END는 Search Subgraph의 세 번째 Node가 아니다. 여러 요청 경로가 공유하는 Graph Runtime 종료 처리이며, END 직후 복귀 Edge에서 `search → none`으로 바뀐다.

1. LLM이 검색 요청을 해석해 Tool 1 호출을 판단하고 검색 조건을 구성한다.
2. Tool 뒤의 백엔드가 접근 권한을 적용해 후보 검색 결과를 구조화하여 반환한다.
3. LLM은 반환된 후보 수를 해석해 0개, 1개 또는 2개 이상 경로를 선택한다.
4. 오케스트레이터는 필요한 HITL, 후보 ID 검증, 기존 ID 확인과 추가·대체를 진행하고 `authorized_meeting_ids`에 반영한다.
5. 오케스트레이터가 검색 결과 또는 State 갱신 결과를 정형화한 컨텍스트로 조립하면 LLM이 “결과 없음”, “추가 완료”, “대체 완료” 등에 맞는 최종 답변을 생성한다.
6. 오케스트레이터는 최종 답변을 `messages`에 반영하고 Checkpoint를 저장한 뒤 Agent 요청 대기로 돌아간다.
7. 검색 동안 `recording_modal_status`와 모달의 `recording_state`를 읽거나 변경하지 않으므로 녹화 중에도 검색할 수 있다.

### 5-2. 회의록 질의 상세 순서도

> **그림 유형: 질의 상세 순서도**  
> 회의록 질의 업무의 세부 처리 순서를 빠짐없이 보여주는 구현 순서도다. 이 순서도 자체에는 Node 경계를 중첩하지 않으며, 바로 아래의 Question Subgraph에서 같은 흐름을 내부 Node·Outcome Edge로 다시 묶는다. 내부 Node들은 별도의 State 값을 추가하지 않고 모두 상위 State인 `question`을 유지한다. LLM이 질문 경로를 결정하기 전까지는 `none`, 결정 직후부터 END까지는 `question`, END 직후 복귀 Edge부터 다시 `none`이다.

#### Question Node 내부 Subgraph

> **그림 유형: Question Node 내부 Subgraph**  
> 최상위 Agent Graph의 `회의록 질의 Subgraph Node`를 펼친 그림이다. 내부 Node들은 모두 상위의 개념적 State인 `question`을 유지하며, 마지막 Node가 `QUESTION_RESPONSE_READY`를 반환한 뒤 Graph Runtime 공통 종료 처리에서 END가 확정된다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/15_Question_Node_내부_Subgraph_개선.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/15_Question_Node_내부_Subgraph.excalidraw)

Subgraph의 첫 번째 Node는 허용 ID 확인, Tool 2 인터페이스 호출, 백엔드 원문 조회와 결과 정형화까지를 담당한다. 코드와 백엔드가 반환한 `SELECTION_REQUIRED`, `SOURCE_READY`, `SOURCE_DENIED_OR_FAILED` Outcome에 따라 다음 Edge가 구분된다. 두 번째 Node는 각 Outcome에 맞는 Model Context를 조립해 LLM에 전달하고, 원문 기반 답변·선택 필요 안내·실패 안내 중 하나를 최종 답변으로 생성한다.

두 번째 Node가 반환한 `QUESTION_RESPONSE_READY` 이후의 `messages` 반영·Checkpoint·END 역시 Question Subgraph 내부 Node가 아니라 Graph Runtime 공통 종료 처리다. END 직후 복귀 Edge에서 `question → none`으로 바뀌며, 조회한 원문은 State나 Checkpoint에 남기지 않는다.

1. 오케스트레이터가 사용자 질문을 `messages`에 반영하면 LLM이 원문 조회 Tool 2 호출을 판단한다.
2. Tool 2가 필요하지만 허용된 회의록 ID가 없으면 오케스트레이터가 선택 필요 결과를 정형화해 LLM에 전달하고, LLM이 사용자 안내를 생성한다.
3. 허용 ID가 있으면 Tool 뒤의 백엔드가 목록 포함 여부를 검사하고 원문을 조회한다. 거부·실패 결과도 정형화해 LLM에 전달한다.
4. 조회된 원문은 실행 중 문서 데이터로만 사용하고, 오케스트레이터가 시스템 지시·원문·`messages`를 최종 Model Context로 조립한다.
5. LLM은 원문, 선택 필요 또는 실패 결과에 맞는 최종 답변을 생성한다.
6. 오케스트레이터는 답변만 `messages`에 추가하고 Checkpoint를 저장한 뒤 Agent 요청 대기로 돌아간다. 원문은 State나 Checkpoint에 저장하지 않는다.



## 6. 녹화 Trigger·모달과 Agent Tool 조건 요약

| 실행 기능         | 위치와 역할                       | 실행 조건                                 | 성공 후 처리                                   |
| ------------- | ---------------------------- | ------------------------------------- | ----------------------------------------- |
| 회의 시작 Trigger | 오케스트레이터 고정 코드가 모달 시작 로직 연결   | 모달 `recording_state=none`·권한·실제 회의 상태 | 모달이 `recording` 반영, 오케스트레이터가 `healthy` 반영 |
| 일시정지 Trigger  | 오케스트레이터 고정 코드가 모달 일시정지 로직 연결 | 모달 `recording_state=recording`        | 모달이 `pause` 반영                            |
| 재개 Trigger    | 오케스트레이터 고정 코드가 모달 재개 로직 연결   | 모달 `recording_state=pause`            | 모달이 `recording` 반영                        |
| 종료 Trigger    | 오케스트레이터 고정 코드가 모달 종료 로직 연결   | 모달 `recording_state=recording·pause`  | 모달이 `stop → none` 반영                      |
| Tool 1. 검색·선택 | Agent가 호출하는 인터페이스            | 백엔드 권한 필터·선택 ID 검증                    | `authorized_meeting_ids` 반영               |
| Tool 2. 원문 조회 | Agent가 호출하는 인터페이스            | 요청 ID가 허용 목록에 포함                      | 원문을 호출 시점 컨텍스트에만 전달                       |

녹화 Trigger는 LLM이나 Agent Tool을 거치지 않는다. 모달의 `recording_state`는 모달이 관리하고, 오케스트레이터는 모달 결과 신호에 따라 `recording_modal_status`만 갱신한다.

## 핵심 정리

- 회의 시작·일시정지·재개·종료는 오케스트레이터의 고정 Trigger 코드가 기존 UI와 동일한 녹화 모달 로직에 연결한다.
- 회의 녹화는 LLM Agent가 판단하는 과정이 아니라 고정 Trigger·모달·백엔드가 실행하는 결정적 Workflow다.
- 실제 녹화 `recording_state`는 모달이 관리하고, Agent 오케스트레이터는 `recording_modal_status`와 `authorized_meeting_ids`를 관리한다.
- `recording_modal_status`는 모달의 정상 응답이면 `healthy`, 모달 연결·실행 오류이면 `error`다.
- 녹화 종료 처리가 완료되면 모달의 `recording_state`는 `stop → none`으로 바로 바뀐다.
- Agent Tool은 검색·선택 Tool 1과 원문 조회 Tool 2 두 개다.
- 검색·질문에는 요청 중 이동을 설명하는 개념적 Graph State가 있지만, 같은 이름의 지속 코드 변수나 `run_id`는 두지 않는다.
- 회의록 원문은 State·Checkpoint·임시 Storage에 저장하지 않고 LLM 호출 시점에만 조립한다.
