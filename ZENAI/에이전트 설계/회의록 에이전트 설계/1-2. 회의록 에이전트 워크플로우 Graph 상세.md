# 회의록 에이전트 워크플로우 Graph 상세

이 문서는 회의록 에이전트의 **State, Checkpoint, 녹화 Trigger·모달, Tool과 세부 실행 Graph**를 정의하는 개발 상세 문서다.

서비스의 목적, 사용자와 전체 업무 흐름을 먼저 확인하려면 [[1-1. 회의록 에이전트 업무 개요]]를 참고한다.

> [!info] 권장 읽기 순서
> 처음 읽는 사람은 **그림의 계층 → State 표기 원칙 → 용어·색상 부록**을 먼저 확인한 뒤, 서로 독립된 녹화 Workflow Graph와 검색·질문 Agent Graph에서 필요한 상세 순서도로 내려가며 읽는다.

## 1. 기술 그림과 전체 구조

이 절은 문서의 중심이 되는 다이어그램을 읽기 전에, **업무 개요도에서 서로 독립된 Graph와 상세 순서도로 구체화되는 계층**과 회의록 시스템의 전체 기술 실행 구조를 설명한다.

### 1-1. 다이어그램의 계층과 역할

[[1-1. 회의록 에이전트 업무 개요]]의 그림은 전체 업무를 큰 단위로 나눈 **업무 개요도**다. 이 문서에서는 그 업무 단위를 실제 실행 단위로 바꾸고, 필요한 Node를 다시 내부 Graph로 펼친다.

```text
업무 개요도
├─ 독립된 회의 녹화 Workflow Graph → 녹화 Node 내부 순서도
└─ 회의록 검색·질문 Agent Graph
   ├─ Search·Question Node 내부 Node·Edge·State 핵심 Graph
   ├─ 세부 Node 명칭이 표시된 내부 상세 순서도
   └─ 검색·질문 전체 상세 순서도
```

| 그림 | 답하려는 질문 | 이 문서의 예시 |
|---|---|---|
| **업무 개요도** | 전체 업무를 어떤 큰 단위로 나누는가? | 1-1 문서의 전체·하위 업무 흐름 |
| **독립 Workflow Graph** | LLM 없이 고정 규칙으로 실행되는 별도 Workflow의 Node와 Edge는 무엇인가? | 회의 녹화 Workflow Graph |
| **Agent Graph** | LLM 판단으로 이동하는 Agent의 Node와 Edge는 무엇인가? | 검색·질문 Agent Graph |
| **Node 내부 핵심 Graph** | 상위 Node를 어떤 내부 Node·Edge·State로 나누는가? | Search·Question Node 내부 핵심 Graph |
| **세부 Node 명칭 상세 순서도** | 내부 핵심 Graph의 각 Node가 실제 처리 단계 중 어디에 대응하는가? | S1·S2-A·Q1·Q2-A 등의 Node 명칭이 표시된 Search·Question 순서도 |
| **내부 순서도** | 하나의 Node 내부에서 무엇을 검사·실행하는가? | 회의 시작·제어, 검색·선택, 회의록 질의 상세 절차 |
| **State 전이도** | 특정 Graph 계층의 State가 어떻게 바뀌는가? | 모달의 `recording_state` 전이 |

검색·질문의 상위 Node는 내부에서 다시 판단과 분기가 발생하므로 **Node 내부 핵심 Graph**로 펼친다. 그다음 세부 Node 명칭 상세 순서도에서 내부 Node 명칭과 실제 처리 단계를 대응시키고, 전체 상세 순서도에서 담당 영역을 포함한 구현 순서를 확인한다.

State 전이도와 순서도는 같은 그림이 아니다. State 전이도는 **State 변화만**, 순서도는 **Node 내부 처리 순서와 조건**을 보여준다. 순서도에도 State 확인·변경이 표시될 수 있지만 사각형 전체가 State를 뜻하지는 않는다.

회의 녹화 명령은 Agent LLM이 하나의 **녹화 Tool**을 호출하고, Tool 내부에서 시작·일시정지·재개·종료 중 해당 Skill을 선택해 실행한다. 다만 4-0의 회의 녹화 Workflow Graph는 Tool 호출 여부가 아니라, Skill이 제어하는 녹화 모달 내부의 결정적인 State 전이를 표현한다. 검색·질문 Agent Graph와 녹화 모달 Workflow Graph는 서로의 **Graph State**를 읽거나 변경하지 않는다.

### 1-2. 전체 기술 구조

회의 녹화 명령과 회의록 검색·질문은 실행 진입 방식이 다르다.

```text
회의 시작·일시정지·재개·종료
→ Agent LLM이 녹화 Tool 호출
→ 녹화 Tool 내부에서 명령에 맞는 Skill 선택·실행
→ Skill이 회의 탭·상단바 버튼과 동일한 녹화 모달 제어 메서드 호출
→ 기존 녹화 백엔드 메서드
→ 모달이 recording_state 갱신
→ 모달·백엔드 결과가 Skill을 거쳐 녹화 Tool 실행 결과로 반환
→ 커스텀 하네스가 녹화 Tool 결과를 받아 recording_modal_status 반영
→ UI에 성공·거부·오류 결과 반환
→ END → 사용자 입력 대기

상단바 녹화 버튼
→ 녹화 Tool을 거치지 않고 동일한 녹화 모달 제어 메서드 직접 호출

회의록 검색·질문
→ LLM이 의도와 Tool 호출 여부 판단
→ Tool 뒤의 백엔드가 권한·입력·리소스 상태 검사
→ authorized_meeting_ids 또는 답변 반영
```

LLM은 사용자 녹화 명령에 따라 녹화 Tool과 입력 명령을 선택할 뿐, 실제 녹화 가능 여부와 권한을 판단하지 않는다. Tool 내부 Skill이 호출한 녹화 모달과 신뢰 가능한 백엔드가 현재 `recording_state`, 권한과 실제 업무 상태를 검사한다.

## 2. State·Checkpoint 적용 원칙



### 2-1. State 적용 기준

이 문서에서 **State는 현재 Graph가 어느 실행 단계에 있는지를 나타내는 유한한 상태**다. 다이어그램 한쪽의 **State 정의표**에는 사용할 State의 뜻을 적고, 실제 값이 바뀌는 Edge에는 **State 변경 지점**을 명시한다.

```text
검색·질문 Agent Graph State
none / search / question
```

최상위 검색·질문 Graph에서는 `none`, `search`, `question`만 사용한다. Search·Question Subgraph 내부에는 다음 Node와 Edge를 설명하는 더 세밀한 **개념적 제어 State**를 둘 수 있지만, 이를 별도의 지속 코드 변수로 만들지는 않는다. 상위 State와 내부 State 모두 현재 실행 중인 Node와 선택된 Edge로 표현할 수 있다.

> [!warning] 코드의 `State = {}`와 구분
> 에이전트 코드에서 `State = {}`라고 부르는 객체는 Node 사이에 전달할 값을 모아 둔 **데이터 창고**다. 이 문서에서 말하는 Graph의 State와는 별개의 개념이다.

```python
State = {
    "ScratchPad": [...],
    "authorized_meeting_ids": ["meeting-123"],
    "recording_modal_status": "healthy",
}

RecordingModalState = {
    "recording_state": "recording",
}
```

- 코드의 `ScratchPad`, `authorized_meeting_ids`, `recording_modal_status`는 데이터 창고 안의 값이다.
- 모달의 `recording_state`는 `none`, `recording`, `pause`, `stop`이라는 유한한 값을 가지므로 Graph의 State를 코드로 직접 구현한 경우다.
- 검색·질문 State는 한 요청 안에서만 이동하므로 코드에 별도 지속 변수를 만들지 않는다.

`recording_modal_status`는 모달이 정상적으로 응답하고 동작하면 `healthy`, 모달 연결이나 실행 자체에 오류가 있으면 `error`다. 녹화 상태 조건에 따른 정상적인 거부는 모달 오류가 아니므로 `healthy`를 유지한다.

검색·질문은 모달의 `recording_state`를 변경하지 않으므로 회의 녹화 중에도 함께 처리할 수 있다.

### 2-2. Checkpoint 적용 기준

Checkpoint는 **하나의 사용자 요청에 대한 최종 결과가 확정되어 UI에 반환되기 직전의 데이터와 실행 결과를 저장**한다. Search 다음 Question이 이어지더라도 각 Tool 실행 뒤에는 Checkpoint를 만들지 않고, 모든 재판단 루프가 끝난 뒤 한 번만 저장한다.

- 녹화 Tool 처리는 모달이 보낸 결과 신호가 `recording_modal_status`에 반영된 지점에 저장한다.
- 모달 내부의 `recording_state`는 Agent Checkpoint에 저장하지 않는다.
- 검색·질문 Tool의 중간 결과는 이후 LLM 호출에 사용할 컨텍스트에 포함할 뿐 Checkpoint를 만들지 않는다. Agent LLM의 최종 답변이 확정된 뒤 UI 출력 직전에 업무 Checkpoint를 저장한다.
- Tool 결과와 최종 답변을 구체적으로 어느 저장 공간에 어떤 수명으로 보관할지는 이후 구현 설계에서 결정한다. 조회한 회의록 원문은 저장하지 않는다.
- Search·Question Tool이 결과를 반환하면 커스텀 하네스가 이를 컨텍스트에 반영하고 같은 Agent LLM으로 돌려보낸다. Agent LLM은 다음 Tool 호출 또는 최종 답변을 판단한다.
- 검색 후보가 여러 개여서 HITL로 기다릴 때는 같은 스레드의 런타임 내부 스냅샷으로 중단·재개하며, 업무 완료 Checkpoint와 구분한다.

Checkpoint는 **저장된 세이브 포인트**이며 자동 복구 기능 자체는 아니다. 오류가 발생하면 복구 로직이 마지막 정상 Checkpoint를 선택하고 해당 Agent 업무를 다시 실행해야 한다.

State와 Checkpoint의 구체적인 저장 구조는 [[2-1. 회의록 에이전트 현재 구현 상세 설계]]에서 다룬다.

## 3. 다이어그램을 읽기 위한 용어·표기 부록

> [!info] 이 절의 역할
> 이 절은 회의 녹화와 회의록 검색·질문의 본 흐름을 설명하는 부분이 아니라, 이후 다이어그램에 등장하는 **용어, 도형과 색상**을 해석하기 위한 부록이다. 익숙한 독자는 필요한 항목만 확인해도 된다.

| 용어                    | 이 문서에서의 의미                                                    |
| --------------------- | ------------------------------------------------------------- |
| **Agent**             | 사용자의 요청을 이해하고 필요한 Tool 호출이나 답변을 판단하는 AI                       |
| **LLM**               | 요청 해석, Tool 호출 여부와 답변을 생성하는 AI 모델                             |
| **코드의 `State = {}`**  | 하네스가 Node 사이에 전달하는 대화·검증 ID·모달 상태 정보의 데이터 창고              |
| **State**             | 현재 Graph 계층이 어느 실행 단계에 있는지 나타내는 유한한 상태                        |
| **저장 지점(Checkpoint)** | 정상적으로 완료된 업무 결과와 State를 저장한 지점                                |
| **실행 관리자(하네스)**   | Graph 이동, 실행 결과 반영과 Checkpoint 저장을 담당하는 구성요소                  |
| **녹화 모달 State**       | 임베디드 상단바 모달이 관리하는 실제 녹화 진행 상태                                 |
| **에이전트 호출 기능(Tool)**  | LLM이 백엔드 기능을 호출할 때 사용하는 이름·Description·Schema 기반 인터페이스        |
| **사용자 선택 대기(HITL)**   | AI가 임의로 결정하지 않고 사용자의 선택을 기다리는 구간                              |
| **Node**              | Graph에서 하나의 실행 책임을 담당하는 단계                                    |
| **Subgraph Node**     | 상위 Graph에서는 하나의 Node이지만 내부를 다시 Node·Edge·State로 펼칠 수 있는 실행 단위 |
| **Edge**              | 다음 실행 단계로 이어지는 경로                                             |
| **분기 조건(Condition)**  | 실행 결과에 따라 이동할 Edge를 선택하는 규칙                                   |

### 3-1. Trigger·모달·Tool·백엔드 구분

- **녹화 명령**: `회의 시작`, `/meeting-start`처럼 Agent LLM이 녹화 Tool 호출로 해석하는 사용자 입력이다.
- **녹화 Tool**: 시작·일시정지·재개·종료 Skill을 하나의 Tool 안에 두고, 입력 명령에 맞는 Skill을 실행해 기존 UI 버튼과 동일한 녹화 모달 제어 메서드를 호출한다.
- **녹화 임베디드 상단바 모달**: 실제 `recording_state`를 소유하고 시작·일시정지·재개·종료에 맞는 기존 백엔드 메서드를 호출한다.
- **Tool**: LLM이 이름·Description·Schema를 보고 호출하는 Agent의 실행 인터페이스다. 현재 녹화 Tool, 회의록 검색·선택 Tool 1, 원문 조회 Tool 2를 사용한다.
- **하네스**: LLM 옆에서 실행을 보조하는 결정적 요소 전체를 뜻한다. Tool 인터페이스 호출, Tool 뒤 백엔드 로직 연결, State 반영, Graph 이동, 컨텍스트 조립과 Checkpoint 저장을 담당한다.
- **LLM**: 회의록 검색·질문의 Tool 호출 여부를 판단하고 실행 결과를 바탕으로 답변을 생성한다.
- **백엔드**: 인증·권한·실제 리소스 상태를 검사하고 기존 녹화·검색·조회 로직을 실행한다.

녹화 시작·일시정지·재개·종료는 각각 별도 Tool이 아니라 **하나의 녹화 Tool 내부 Skill**이다. Agent에는 녹화 Tool, 회의록 검색·선택 Tool 1과 원문 조회 Tool 2가 연결된다.

### 3-2. 다이어그램 표기

| 요소               | 의미                                            | 표현                        |
| ---------------- | --------------------------------------------- | ------------------------- |
| Start·End        | Graph 실행의 시작, 이번 요청의 완료 또는 요청 대기 복귀 지점        | 타원형                       |
| Node             | LLM 판단, Tool·Skill 실행, 모달 실행, 백엔드 처리 | 사각형                       |
| Subgraph Node    | 내부에 별도의 Node·Edge 구조가 있는 상위 Node                 | `Subgraph Node` 라벨이 있는 사각형 |
| Subgraph Entry·Return | 상위 Graph와 하위 Subgraph가 연결되는 진입·반환 경계          | 타원형                       |
| Edge             | 다음 단계로 이동하는 실행 경로                             | 화살표                       |
| Edge 라벨          | Edge의 요청 종류, 전이 조건 또는 구조화된 실행 결과              | 화살표 위의 반투명 연회색 배경판과 글자    |
| Condition        | 실행 결과에 따라 다음 경로를 선택하는 단계                      | 마름모                       |
| State            | 현재 Graph 계층의 실행 상태                                  | State 정의표와 Edge의 State 변경 표기 |
| Node 범위          | 하나의 Node로 묶은 실행 책임의 시작과 끝                        | Graph별 강조색 점선 경계 박스           |
| 세부 Node 명칭 상세 순서도 | 핵심 Graph의 각 Node를 실제 세부 단계의 명칭과 대응시킨 그림 | S1·S2-A·Q1·Q2-A 등의 주황색 Node명·내부 State 표기 |
| State 정의표        | 해당 Graph 계층에서 사용하는 State와 의미                     | 다이어그램 한쪽의 Graph별 강조색 설명 박스 |
| State 범위          | 특정 State가 유지되는 Graph 구간의 시작과 끝                    | Graph별 강조색 실선 경계 박스           |
| State 변경 지점      | Node 결과에 따라 State 값이 실제로 달라지는 지점                 | Edge 가까이의 `State 변경 · A → B` 표기 |
| 업무 경계 Checkpoint | 완료된 요청의 코드 `State = {}` 데이터와 실행 결과를 저장하는 지점 | 원통형                       |
| 담당 영역            | LLM과 이를 보조하는 하네스의 책임 범위                   | 처리 구간별 반투명 영역 박스          |
| 규칙·설명 주석         | 실행 Node에 적용되는 규칙이나 책임 경계 설명                   | 연한 보라색 배경·보라색 점선 테두리와 연결선 |
| 국소 루프            | 같은 Node의 반복 또는 실패 이유 반환 후 재시도                 | 주황색의 작은 복귀 화살표            |
| Agent 제어 루프        | Tool 결과를 컨텍스트에 반영한 뒤 같은 Agent LLM으로 복귀하는 경로       | 굵은 짙은 초록색 외곽 복귀 화살표       |
| 커스텀 Harness 연결 경계 | Tool 결과를 이후 LLM 호출에 사용할 컨텍스트에 포함하여 전달하는 Tool 바깥의 실행 경계 | 회색 점선 영역 또는 연결 주석 |

- **초록색 네모**: 사용자 입력·Trigger 또는 `Agent 요청 대기`, `recording_state=none`과 같은 입력·대기 경계
- **노란색 네모**: Human in the Loop
- **빨간색 네모·영역**: LLM 판단·생성과 LLM 담당 범위
- **파란색 네모·영역**: 결정적 Workflow 또는 하네스의 전체 담당 범위. Tool 인터페이스와 그 뒤의 백엔드 로직, State 반영·Condition·컨텍스트 조립·Checkpoint를 포함
- **회색·흰색 네모**: 파란색 하네스 담당 영역 안에서 Tool 인터페이스 뒤에 실행되는 백엔드의 확정적 검사·실행 단계
- **연한 보라색 네모**: 실행 요소가 아닌 규칙·설명 주석. 보라색 점선 테두리와 화살촉 없는 점선 연결선 사용
- **주황색 점선·실선·State 표기**: 회의록 검색·질문 Agent Graph의 Node 범위, State 범위와 변경 지점
- **하늘색 점선·실선·State 표기**: 별도로 실행되는 회의 녹화 Workflow의 Node 범위, `recording_state` 범위와 변경 지점
- **회색 화살표**: 정해진 단방향 진행
- **빨간색 화살표**: LLM 선택 또는 Condition 결과에 따라 갈라지는 분기
- **주황색 화살표**: 실패 후 재시도나 일시정지·재개 같은 국소 반복
- **굵은 짙은 초록색 화살표**: Tool 실행 결과를 컨텍스트에 반영한 뒤 같은 Agent LLM으로 돌아가 다음 Tool 호출 또는 최종 답변을 판단하는 Agent 제어 루프

화살표의 요청·조건·결과 문구는 대응하는 Edge의 경로 위에 고정하며, 선이 글자를 관통하지 않도록 **반투명 연회색 배경판**을 사용한다. 국소 반복은 해당 Node 가까이의 작은 주황색 복귀 화살표로 표시한다. Agent가 Tool 결과를 바탕으로 다시 판단하거나 요청 완료 후 입력 대기로 돌아가는 반복은 다른 박스·화살표와 겹치지 않는 **굵은 짙은 초록색 외곽 화살표**로 구분한다.

점선 박스는 사용된 그림에서 **Graph가 하나의 Node로 묶는 범위**를 보조적으로 나타내고, 실선 박스는 **State가 유지되는 범위**다. 검색·질문 Agent Graph는 주황색, 독립된 녹화 Workflow는 하늘색을 사용하여 두 State 체계가 연결되거나 공유되는 것으로 오해하지 않게 한다. `State 변경 · A → B` 표기는 앞 Node의 출력으로 State가 바뀌어 다음 Edge가 선택되는 정확한 지점을 보여준다. 검색·질문의 문서 전개에서는 먼저 내부 Node·Edge·State 핵심 Graph를 제시하고, 다음의 **세부 Node 명칭 상세 순서도**에서 S1·S2-A·Q1·Q2-A 등의 Node명을 실제 처리 단계에 대응시킨다. 이 순서도에는 내부 구획용 주황색 점선 박스를 반복해서 겹치지 않는다. 그 뒤의 전체 상세 순서도는 담당 영역과 전체 구현 순서에 집중한다.

커스텀 Harness 연결 경계는 Search·Question Tool 내부 Node가 아니다. Tool이 반환한 정형화된 결과를 이후 호출할 같은 Agent LLM의 컨텍스트에 포함하는 Tool 바깥의 공통 경계다. 최종 답변 또는 다음 Tool 호출은 이 Agent LLM이 판단하며, Checkpoint는 최종 답변이 확정된 뒤 UI 반환 직전에만 저장한다. 컨텍스트와 실행 결과의 구체적인 처리·저장 위치는 구현 설계에서 결정한다.

규칙·설명 주석은 실행 흐름에 포함되는 Node가 아니므로 **연한 보라색 배경과 보라색 점선 테두리**로 표시하고, 설명 대상과는 **화살촉 없는 보라색 점선**으로만 연결한다. Tool·백엔드 실행 요소는 파란색 하네스 담당 영역 안에서 회색·흰색 배경과 실선 테두리 및 실행 화살표를 사용하므로 주석과 구분된다.

> 권한과 실제 업무 상태는 LLM이나 Condition이 결정하지 않는다. 녹화 모달과 Tool 뒤의 백엔드가 검사하고, Condition은 구조화된 실행 결과에 따라 응답 경로만 선택한다.

## 4. 회의 녹화 과정

> [!summary] 회의 녹화 과정 한눈에 보기
> - **사용자:** 회의 생성자
> - **모달 시작 State:** `recording_state = none`
> - **주요 행동:** 시작, 일시정지, 재개, 종료
> - **종료:** 회의 종료 처리 후 `recording_state = none`
> - **특징:** 실제 녹화 State는 모달이 관리하고 Agent는 모달의 정상·오류 상태만 관리

> [!warning] Graph State와 코드 데이터를 구분해야 한다
> - **검색·질문 Agent Graph의 State:** `none`, `search`, `question`으로 구분되는 Agent 요청 단계
> - **독립된 녹화 Workflow의 State:** `none`, `recording`, `pause`, `stop`으로 구분되는 현재 녹화 단계
> - **코드 데이터 창고의 값:** `authorized_meeting_ids`, `recording_modal_status = healthy | error`
> - **내부 State의 실제 구현 위치:** 상단바 모달의 `recording_state = none | recording | pause | stop`
>
> 양쪽에서 사용하는 `none`은 이름만 같을 뿐 **서로 다른 소유자와 의미를 가진 별개의 State**다. Agent Graph의 `none`은 검색·질문 요청 대기이고, 녹화 Workflow의 `none`은 녹화 전·녹화 요청 대기다. 어느 한쪽의 State 변화도 다른 쪽 State에 영향을 주지 않는다. 하네스의 `State = {}` 객체 전체를 Graph State로 해석하지 않으며, 아래 녹화 다이어그램의 Node·State·Edge는 모달이 소유하는 `recording_state`와 그 전이를 나타낸다. Agent 내부 하네스는 모달의 녹화 State를 소유하거나 중복 갱신하지 않고, 모달 결과 신호에 따라 `recording_modal_status`만 갱신하여 Agent Checkpoint에 반영한다.

> [!important] Agent의 Tool 선택과 모달 Workflow를 구분한다
> 스레드의 녹화 명령은 LLM이 하나의 녹화 Tool을 호출하는 Agent 과정이다. Tool이 명령에 맞는 Skill을 실행한 뒤에는 녹화 모달과 백엔드가 정해진 규칙에 따라 동작하며, 실제 `recording_state` 전이는 결정적 Workflow로 처리된다.

이 과정은 세 가지 관점으로 표현한다. **회의 녹화 Workflow Graph**는 녹화 모달의 단계별 Node와 전이를, **State 전이도**는 모달 내부 `recording_state`의 허용 전이만을, 각 **순서도**는 LLM의 녹화 Tool 호출부터 Tool 내부 Skill, 모달·백엔드와 결과 신호까지의 상세 절차를 보여준다.

#### 구현 요소를 포함한 상세 Graph

> **그림 유형: 녹화 Workflow 내부 Graph**  
> Graph Engineering 방법론을 적용해 녹화 모달 Workflow를 **요청 대기·회의 시작, 녹화, 일시정지, 종료 처리** Node로 나눈 그림이다. 녹화 Tool 내부 Skill이 모달 제어 메서드를 호출하고 실행에 성공하면 모달의 `recording_state`가 바뀌어 다음 Node로 이동한다. 이 변화는 검색·질문 Agent Graph State에 영향을 주지 않는다.

> 이 그림은 독립된 녹화 시스템을 Graph Engineering 관점으로 모델링한 것이며, 검색·질문 Agent Graph 내부에 구현되는 Subgraph를 뜻하지 않는다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/05_회의_녹화_Workflow_Graph_개선.svg]]

**Node를 이렇게 나눈 이유**

- **요청 대기·회의 시작 Node (`none`)**: 녹화 전 상태에서 회의 시작 Skill의 모달 제어 요청을 받아 처리하는 업무 단위다.
- **녹화 Node (`recording`)**: 실제 녹화가 진행되는 동안 일시정지 또는 종료 Skill의 모달 제어 요청을 받을 수 있는 업무 단위다.
- **일시정지 Node (`pause`)**: 녹화가 멈춘 동안 재개 또는 종료 Skill의 모달 제어 요청을 받을 수 있는 업무 단위다.
- **종료 처리 Node (`stop`)**: 종료 백엔드와 모달 처리가 완료될 때까지 유지되는 업무 단위다. 종료 처리가 완료되면 `none`으로 바뀌고 END를 거쳐 다음 Trigger를 기다린다.

각 Node의 State는 **녹화 임베디드 상단바 모달이 실제 코드로 관리하는 `recording_state`**다. LLM의 녹화 Tool 호출과 Tool 내부 Skill 선택은 모달 Workflow의 진입 경로이며, 모달 실행·권한 검사와 백엔드 호출은 각 Node 사이의 전이를 성립시키는 내부 실행이다.

#### 회의 녹화 단계별 State 변화

| 단계 | 실행 경로 | 모달의 `recording_state` | Agent의 `recording_modal_status` |
|---|---|---|---|
| 회의 시작 | LLM → 녹화 Tool → 시작 Skill → 모달·백엔드 | `none → recording` | 정상 응답 시 `healthy` |
| 회의 일시정지 | LLM → 녹화 Tool → 일시정지 Skill → 모달·백엔드 | `recording → pause` | 정상 응답 시 `healthy` |
| 회의 재개 | LLM → 녹화 Tool → 재개 Skill → 모달·백엔드 | `pause → recording` | 정상 응답 시 `healthy` |
| 회의 종료 | LLM → 녹화 Tool → 종료 Skill → 모달·백엔드 | 종료 Skill: `recording·pause → stop` / Backend 후속 처리: `stop → none` | 정상 응답 시 `healthy` |
| 모달 연결·실행 오류 | 모달 결과 신호 | 기존 값 유지 | `error` |

`stop`은 녹화 종료 명령을 처리한 뒤 전사·요약이 진행되는 동안 유지되는 모달 상태다. 종료 Skill과 녹화 Tool의 책임은 `recording_state`를 `stop`으로 전환하는 데서 끝난다. 이후 기존 Backend가 전사·요약 후속 처리를 완료하면 `stop → none`으로 변경하며, 그때부터 새로운 녹화를 시작할 수 있다.

### 4-1. 회의 시작 순서도

> **그림 유형: 녹화 Workflow Node 내부 상세 순서도**  
> 녹화 Workflow Graph의 **요청 대기·회의 시작 Node**를 내부 로직까지 펼친 그림이다. 청록색 점선 경계는 이 Node의 전체 실행 범위이고, **보라색 점선 경계는 회의 시작 Skill이 담당하는 업무 로직 범위**다. State 실선 경계는 진입 `recording_state = none`이 유지되는 범위와 성공·거부·오류 결과에서 State가 달라지는 지점을 구분한다. 이 실행은 검색·질문 Agent Graph State를 읽거나 변경하지 않는다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/07_회의_시작_순서도_개선.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/07_회의_시작_순서도.excalidraw)

1. 사용자가 회의 시작 명령을 입력하면 Agent LLM이 하나의 녹화 Tool 호출을 판단한다.
2. 녹화 Tool은 입력 명령에 따라 내부의 회의 시작 Skill을 실행한다.
3. 회의 시작 Skill은 기존 회의 시작 버튼과 동일한 녹화 모달 제어 메서드를 호출한다.
4. 모달은 자신의 `recording_state`와 백엔드의 권한·실제 회의 상태를 기준으로 실행한다.
5. 성공하면 모달이 `recording_state`를 `recording`으로 갱신한다.
6. 모달이 보낸 정상·오류 신호에 따라 하네스는 `recording_modal_status`만 갱신하고 Checkpoint를 저장한다.
7. 하네스가 성공·거부·오류 결과를 UI에 반환하면 LLM으로 복귀하지 않고 END 후 사용자 입력 대기로 돌아간다.

### 4-2. 회의 일시정지·재개·종료 순서도

> **그림 유형: 녹화 Workflow 여러 Node의 공통 상세 순서도**  
> 녹화 Workflow Graph의 **녹화 Node와 일시정지 Node**에서 사용하는 공통 실행 로직을 펼친 그림이다. 스레드 명령은 LLM이 하나의 녹화 Tool을 호출하고 Tool 내부에서 일시정지·재개·종료 Skill 중 하나를 실행한다. **보라색 점선 경계는 선택된 Skill이 모달·Backend를 제어하고 실행 결과를 반환할 때까지 담당하는 업무 로직 범위**다. 상단바 버튼은 Tool을 거치지 않고 동일한 모달 제어 메서드로 합류한다. 종료 Skill은 `recording_state`를 `stop`으로 전환하는 데서 끝나며, 이후 기존 Backend가 전사·요약을 완료한 뒤 `stop → none`으로 전환한다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/08_회의_제어_순서도_개선.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/08_회의_제어_순서도.excalidraw)

스레드 녹화 명령은 `Agent LLM → 하나의 녹화 Tool → 명령별 Skill`을 거치고, 상단바 버튼은 직접 같은 모달 제어 메서드를 호출한다. 이후 모달이 실제 `recording_state`를 갱신하면 그 결과가 Skill을 거쳐 녹화 Tool 실행 결과로 반환된다. 커스텀 하네스는 `recording_modal_status`를 반영하고 성공·거부·오류를 UI에 반환한 뒤, LLM으로 되돌리지 않고 END 후 사용자 입력 대기로 이동한다.

## 5. 회의록 검색·질문 과정

> [!summary] 회의록 활용 과정 한눈에 보기
> - **사용자:** 회의록을 공유받은 사용자
> - **시작:** Agent 요청 대기
> - **주요 행동:** 회의록 검색·선택 또는 원문 기반 질문
> - **종료:** 현재 사용자 요청의 목표가 달성되어 남은 작업이 없을 때만 END 후 Agent 요청 대기
> - **남는 결과:** `authorized_meeting_ids` 또는 생성된 답변
> - **특징:** Graph에는 `none`, `search`, `question` State가 있지만 같은 이름의 지속 코드 변수는 만들지 않음

검색과 질문은 Graph에서 `none → search | question → none`으로 전환된다. 하나의 사용자 요청에 검색과 질문이 함께 포함되면, 첫 Subgraph의 결과를 반영한 뒤 **Agent 제어 루프가 LLM 판단 Node로 돌아가 다음 Tool 필요 여부를 다시 판단**한다. 더 수행할 작업이 없을 때만 END를 확정하고 입력 대기로 돌아간다. 다음 판단에 필요한 Tool 결과와 작업 기록은 `ScratchPad`에, 검증된 회의록 ID는 `authorized_meeting_ids`에 남긴다.

예를 들어 사용자가 “ID가 A, B인 회의록을 가져오고, 두 회의록 전반에서 특정 주제로 결정된 사항을 설명해줘”라고 요청하면 한 번의 Tool 호출로 끝나지 않는다.

1. LLM이 먼저 검색·선택이 필요하다고 판단한다.
2. Tool 1 결과를 통해 A, B를 검증하고 `authorized_meeting_ids`에 반영한다.
3. Tool 1은 검색·선택 실행 결과를 정형화하여 반환한다.
4. 커스텀 하네스가 Tool 1 결과를 이후 LLM 호출에 사용할 컨텍스트에 포함하고 같은 Agent LLM으로 되돌린다.
5. Agent LLM이 Tool 2를 선택하면 Tool 2가 허용된 회의록 원문을 조회해 정형화된 결과를 반환한다.
6. 커스텀 하네스가 Tool 2 결과를 컨텍스트에 반영하고 Agent LLM으로 전달하면, Agent LLM이 요청한 결정 사항을 답변하고 종료한다.

Tool이 전역적인 사용자 목표의 달성 여부를 단독으로 결정하는 것은 아니다. Tool은 성공·실패와 실행 결과를 구조화하여 반환하고, 커스텀 하네스는 이를 Agent 컨텍스트에 반영한다. 같은 Agent LLM이 원래 요청·`ScratchPad`·Tool 결과를 보고 **다음 Tool 호출 또는 최종 답변**을 판단한다.

### 5-0. Graph Engineering 관점의 Agent Graph

#### Node·Edge·State 핵심 Graph

> **그림 유형: Node·Edge·State 핵심 Graph**  
> Agent의 내부 실행 요소를 제외하고 **Node, Edge, State만 남긴 최상위 개념도**다. `none`의 의도 판단 Node에서 `search` 또는 `question` Subgraph Node로 이동하고, 각 요청의 답변이 완료되면 `none`으로 돌아오는 구조만 먼저 파악한다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/09A_검색_질문_Node_Edge_State_핵심_Graph_개선.svg]]

#### 구현 요소를 포함한 상세 Graph

> **그림 유형: 최상위 Agent Graph**  
> LLM의 의도 판단 결과에 따라 `none`에서 `search` 또는 `question`으로 이동하는 가장 바깥 Graph다. 검색·선택과 질의는 내부 Subgraph를 가진 Tool Node다. 각 Tool이 정형화된 결과를 반환하면 커스텀 하네스가 이를 컨텍스트에 반영하고 같은 Agent LLM으로 되돌린다. 이 연결 관계는 5-1-3·5-2-3 상세 순서도와 5-3 Agent 업무 흐름 순서도에서 펼친다. Tool 없는 직접 답변은 `none`을 유지한다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/09_Graph_Engineering_Agent_Graph_개선.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/09_Graph_Engineering_Agent_Graph.excalidraw)

**Node를 이렇게 나눈 이유**

- **사용자 의도 판단 Node**: 현재 요청이 새 회의록 검색인지, 선택된 회의록을 이용한 질문인지 LLM이 판단한다.
- **회의록 검색·선택 Subgraph Node(Tool 1)**: 검색 조건 추출부터 권한 필터, 후보 결과 판단, 검증된 ID 반영과 정형화된 결과 반환까지가 한 번의 Tool 실행이다. 내부 Node·Edge는 5-1의 Search Subgraph에서 펼친다.
- **회의록 질의 Subgraph Node(Tool 2)**: 검증된 ID로 원문을 조회하고 성공·선택 필요·거부·실패 결과를 정형화해 반환하는 단위다. 내부 Node·Edge는 5-2의 Question Subgraph에서 펼친다.

양쪽 `Subgraph END`는 에이전트 세션이나 전체 사용자 요청의 종료가 아니라 **해당 Search·Question Subgraph 실행이 끝난 경계**다. 이후의 초록색 Edge는 세부 Condition을 생략하고 상위 `none` Node로 복귀하는 뼈대만 나타낸다.

### 5-1. 관련 회의록 검색·선택 과정

#### 5-1-1. Search Node 내부 Node·Edge·State 핵심 Graph

> **그림 유형: Search Node 내부 Node·Edge·State 핵심 Graph**  
> 최상위 Agent Graph의 `회의록 검색·선택 Subgraph Node`를 내부 Node로 펼친 그림이다. 상위 State `search`는 전체에서 유지되지만, S1의 후보 판단 결과에 따라 내부 State가 `no_candidates`, `one_candidate`, `multiple_candidates`로 바뀌며 서로 다른 S2 Node를 선택한다. 각 분기가 완료되면 `response_ready`로 합류한다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/14_Search_Node_내부_Subgraph_개선.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/14_Search_Node_내부_Subgraph.excalidraw)

S1은 Tool 1 호출부터 권한 필터·후보 검색과 후보 수 판단까지를 담당한다. `NO_CANDIDATES`, `ONE_CANDIDATE`, `MULTIPLE_CANDIDATES` 결과가 각각 S2-A, S2-B, S2-C로 향하는 Edge를 선택한다. 각 Node는 결과 없음 처리, 단일 후보 자동 선택, 복수 후보 HITL과 ID 추가·대체를 담당한다. 세 경로가 완료되면 S3의 `tool_result_ready`로 합류하고 `SEARCH_TOOL_RESULT_READY`를 반환한다.

S3가 반환한 `SEARCH_TOOL_RESULT_READY`를 이후 LLM 호출의 컨텍스트에 포함하고 Agent LLM을 재호출하는 처리는 Search Tool 내부 Node가 아니다. Tool 바깥의 커스텀 하네스가 처리하며, 이 경계에서 상위 State가 `search → none`으로 정리된다. 이 중간 결과 뒤에는 Checkpoint를 만들지 않는다. 내부 State는 Edge와 Node 선택을 설명하는 **개념적 제어 State**이며, 별도의 영속 변수로 저장해야 한다는 뜻은 아니다.

#### 5-1-2. Search 세부 Node 명칭이 표시된 내부 상세 순서도

> **그림 유형: 세부 Node 명칭이 표시된 Search 내부 상세 순서도**
> 아래 그림은 5-1-3 전체 상세 순서도의 주황색 `search` 범위 내부를 그대로 복제한 것이다. 실제 처리 단계 가까이에 S1, S2-A, S2-B, S2-C, S3 명칭을 표시해 5-1-1 내부 핵심 Graph와 대응시킨다. 가독성을 위해 세부 Node마다 흐릿한 주황색 점선 구획을 반복하지 않으며, `SEARCH_TOOL_RESULT_READY` 이후의 Tool 바깥 커스텀 하네스 처리는 복제 범위에서 제외한다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/16_Search_Node_경계_상세_순서도_개선.svg]]

#### 5-1-3. 관련 회의록 검색·선택 전체 상세 순서도

> **그림 유형: 검색·선택 전체 상세 순서도**  
> 검색·선택 업무와 Tool 바깥 연결 과정을 펼친 그림이다. Agent LLM이 검색 경로를 결정하기 전까지는 `none`, 결정 직후부터 `SEARCH_TOOL_RESULT_READY`까지는 `search`다. Tool 1이 정형화된 결과를 반환하면 커스텀 하네스가 `search → none`으로 정리하고 결과를 컨텍스트에 반영한 뒤, 별도 조건 분기 없이 같은 Agent LLM으로 복귀시킨다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/11_관련_회의록_검색_선택_순서도_개선.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/11_관련_회의록_검색_선택_순서도.excalidraw)

1. LLM이 검색 요청을 해석해 Tool 1 호출을 판단하고 검색 조건을 구성한다.
2. 하네스가 Tool 인터페이스 호출부터 그 뒤의 백엔드 권한 필터·후보 검색까지 연결하고, 결과를 구조화하여 반환한다.
3. LLM은 반환된 후보 수를 해석해 0개, 1개 또는 2개 이상 경로를 선택한다.
4. 하네스는 필요한 HITL, 후보 ID 검증, 기존 ID 확인과 추가·대체를 진행하고 `authorized_meeting_ids`에 반영한다.
5. Tool 1은 결과 없음, ID 설정·추가·대체 또는 거부·실패를 구분한 정형화된 결과를 반환한다.
6. Tool 바깥의 커스텀 하네스는 Tool 1 결과를 이후 LLM 호출에 사용할 컨텍스트에 포함한다. 이 시점에는 Checkpoint를 저장하지 않는다.
7. 같은 Agent LLM이 반영된 Tool 1 결과를 보고 다음 Tool 호출 또는 최종 답변을 판단한다. Tool을 호출하지 않고 생성한 LLM 최종 답변은 이 Tool 결과 경로에 들어오지 않고 별도의 종료 경로로 이동한다.
8. 검색 동안 `recording_modal_status`와 모달의 `recording_state`를 읽거나 변경하지 않으므로 녹화 중에도 검색할 수 있다.

### 5-2. 회의록 질의 과정

#### 5-2-1. Question Node 내부 Node·Edge·State 핵심 Graph

> **그림 유형: Question Node 내부 Node·Edge·State 핵심 Graph**  
> 최상위 Agent Graph의 `회의록 질의 Subgraph Node`를 내부 Node로 펼친 그림이다. 상위 State `question`은 전체에서 유지되지만, Q1의 원문 조회 결과에 따라 내부 State가 `selection_required`, `source_ready`, `source_denied_or_failed`로 바뀌며 서로 다른 Q2 Node를 선택한다. 각 분기가 완료되면 `response_ready`로 합류한다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/15_Question_Node_내부_Subgraph_개선.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/15_Question_Node_내부_Subgraph.excalidraw)

Q1은 허용 ID 확인, Tool 2 호출, 백엔드 원문 조회와 결과 판단을 담당한다. `SELECTION_REQUIRED`, `SOURCE_READY`, `SOURCE_DENIED_OR_FAILED` 결과가 각각 Q2-A, Q2-B, Q2-C로 향하는 Edge를 선택한다. 각 Q2 Node는 회의록 선택 필요, 원문 조회 성공, 조회 거부·실패 결과를 구분해 Q3로 넘긴다. 세 경로가 완료되면 Q3가 결과를 정형화해 `QUESTION_TOOL_RESULT_READY`를 반환한다.

Q3가 반환한 `QUESTION_TOOL_RESULT_READY`를 이후 LLM 호출의 컨텍스트에 포함하고 Agent LLM을 재호출하는 처리는 Question Tool 내부 Node가 아니다. Tool 바깥의 커스텀 하네스가 처리하며, 이 경계에서 상위 State가 `question → none`으로 정리된다. 이 중간 결과 뒤에는 Checkpoint를 만들지 않으며, 조회한 원문은 State나 최종 Checkpoint에도 남기지 않는다.

> 회의록 질의 업무와 Tool 바깥 연결 과정을 펼친 그림이다. Agent LLM이 질문 경로를 결정하기 전까지는 `none`, 결정 직후부터 `QUESTION_TOOL_RESULT_READY`까지는 `question`이다. Tool 2가 정형화된 결과를 반환하면 커스텀 하네스가 `question → none`으로 정리하고 결과를 컨텍스트에 반영한 뒤, 별도 조건 분기 없이 같은 Agent LLM으로 복귀시킨다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/12_회의록_원문_조회_컨텍스트_답변_순서도_개선.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/12_회의록_원문_조회_컨텍스트_답변_순서도.excalidraw)

1. 하네스가 사용자 질문을 `ScratchPad`에 반영하면 LLM이 원문 조회 Tool 2 호출을 판단한다.
2. Tool 2가 필요하지만 허용된 회의록 ID가 없으면 Q2-A의 회의록 선택 필요 결과로 구분한다.
3. 허용 ID가 있으면 Tool 2가 백엔드의 허용 목록 검사와 원문 조회를 실행하고, Q2-B의 원문 조회 성공 또는 Q2-C의 거부·실패 결과로 구분한다.
4. 세 Q2 경로가 합류하면 Q3가 결과 유형에 맞는 정형화된 Tool 2 결과를 만들어 Tool 바깥 하네스에 반환한다. 조회된 원문은 Tool 실행 중 문서 데이터로만 사용한다.
5. 커스텀 하네스는 Tool 2 결과를 이후 LLM 호출에 사용할 컨텍스트에 포함한다. 이 시점에는 Checkpoint를 저장하지 않으며, 원문은 State나 최종 Checkpoint에도 저장하지 않는다.
6. 같은 Agent LLM이 반영된 Tool 2 결과를 보고 다음 Tool 호출 또는 최종 답변을 판단한다. Tool을 호출하지 않고 생성한 LLM 최종 답변은 이 Tool 결과 경로에 들어오지 않고 별도의 종료 경로로 이동한다.

### 5-3. Agent 업무 흐름 순서도

> **그림 유형: Agent 업무 흐름 순서도**  
> 이 그림은 위에서 아래로 검색·선택과 질의 업무가 이어지는 실행 순서를 종합해 보여주는 **순서도**다. Node·Edge·State 자체를 정의하는 Graph 설계도는 5-0, 5-1-1과 5-2-1의 핵심 Graph를 기준으로 한다.

아래 그림의 주황색 `search`, `question` 범위는 각각 **Tool 1과 Tool 2의 내부 업무 로직**이다. 각 Tool은 최종 답변을 생성하지 않고 정형화된 실행 결과만 반환한다. Tool 바깥의 커스텀 하네스가 결과를 이후 LLM 호출에 사용할 컨텍스트에 포함해 같은 Agent LLM으로 전달하며, Agent LLM이 다음 Tool 호출 또는 최종 답변을 판단한다.

![[ZENAI/에이전트 설계/회의록 에이전트 설계/Excalidraw/10_Agent_하네스_State_갱신_흐름_개선.svg]]

[편집 가능한 Excalidraw 원본](Excalidraw/10_Agent_하네스_State_갱신_흐름.excalidraw)

Tool Action 반환값과 LLM 반환값은 하네스가 서로 구분할 수 있는 형식으로 반환된다. Tool Action 반환값은 Tool 실행 결과이며, LLM 반환값은 Tool을 호출하지 않고 생성한 최종 답변이다.

두 반환값은 처음부터 서로 다른 경로로 처리한다.

- **Tool 1·2 반환값:** 두 Tool의 반환 경로만 합류한다. 하네스는 실행을 마친 Tool의 상위 State를 `search/question → none`으로 정리하고, 결과값을 이후 LLM 호출에 사용할 컨텍스트에 포함한다. 중간 Checkpoint 없이 같은 Agent LLM에 전달하여 다음 Tool 호출 또는 최종 답변을 다시 판단하게 한다.
- **LLM 최종 답변:** Tool을 호출하지 않고 생성한 답변이므로 Tool 반환 경로에 합류시키지 않는다. LLM이 반환한 사용자에게 보여줄 답변을 UI에 출력하며, 해당 요청의 모든 루프가 끝난 이 지점에서 업무 Checkpoint를 한 번 저장한다. 이후 END로 이동하여 사용자 입력 대기로 돌아간다. 실제 처리·저장 위치와 방식은 구현 설계에서 확정한다.

이 과정에서 `recording_modal_status`와 모달의 `recording_state`는 변경하지 않는다.



## 6. 녹화 Tool·모달과 Agent Tool 조건 요약

| 실행 기능         | 위치와 역할                       | 실행 조건                                 | 성공 후 처리                                   |
| ------------- | ---------------------------- | ------------------------------------- | ----------------------------------------- |
| 녹화 Tool | LLM이 스레드 녹화 명령에 따라 호출하는 단일 Tool. 내부에서 시작·일시정지·재개·종료 Skill 선택 | 사용자의 녹화 명령 | 선택된 Skill이 녹화 모달 제어 메서드 호출 |
| 상단바 녹화 버튼 | 녹화 Tool을 거치지 않고 동일한 모달 제어 메서드 호출 | 사용자의 UI 입력 | 모달·백엔드 실행 결과를 UI와 하네스에 반환 |
| Tool 1. 검색·선택 과정용 인터페이스 | Agent가 접근 가능한 후보 검색을 위해 호출하는 인터페이스 | 백엔드 접근 권한 필터 | 구조화된 후보 결과 반환. 이후 LLM과 하네스가 후보 해석·HITL·ID 재검증·`authorized_meeting_ids` 반영 |
| Tool 2. 원문 조회 | Agent가 호출하는 인터페이스            | 요청 ID가 허용 목록에 포함                      | 원문을 호출 시점 컨텍스트에만 전달                       |

스레드 녹화 명령은 LLM과 녹화 Tool을 거치지만 상단바 버튼은 동일한 모달 제어 메서드를 직접 호출한다. 두 진입 경로 모두 실제 상태·권한 판단은 모달과 백엔드에 맡기며, 하네스는 모달 결과 신호에 따라 `recording_modal_status`만 갱신한다.

녹화 Tool은 검색·질문 Tool 결과를 Agent LLM으로 되돌리는 재판단 경로에 들어가지 않는다. 커스텀 하네스가 Tool 결과를 `recording_modal_status`와 Checkpoint에 반영하고 UI에 반환한 뒤 요청을 종료한다.

## 핵심 정리

- 회의 시작·일시정지·재개·종료는 하나의 녹화 Tool 내부에 각각의 Skill로 구현한다.
- 스레드 녹화 명령은 Agent LLM이 녹화 Tool을 호출하고, Tool이 해당 Skill을 실행해 기존 UI와 동일한 녹화 모달 제어 메서드에 연결한다.
- LLM은 Tool과 명령만 선택하며 실제 녹화 State·권한·허용 동작은 모달과 백엔드가 결정적으로 처리한다.
- 실제 녹화 `recording_state`는 모달이 관리하고, Agent 하네스는 `recording_modal_status`와 `authorized_meeting_ids`를 관리한다.
- `recording_modal_status`는 모달의 정상 응답이면 `healthy`, 모달 연결·실행 오류이면 `error`다.
- 녹화 종료 처리가 완료되면 모달의 `recording_state`는 `stop → none`으로 바로 바뀐다.
- Agent Tool은 녹화 Tool, 검색·선택 Tool 1과 원문 조회 Tool 2다.
- Search·Question Tool은 결과를 커스텀 하네스가 컨텍스트에 반영해 같은 Agent LLM으로 되돌리지만, 녹화 Tool은 결과를 `recording_modal_status`에 반영하고 UI에 반환한 뒤 즉시 종료한다.
- 검색·질문에는 요청 중 이동을 설명하는 개념적 Graph State가 있지만, 같은 이름의 지속 코드 변수나 `run_id`는 두지 않는다.
- 회의록 원문은 State·Checkpoint·임시 Storage에 저장하지 않고 LLM 호출 시점에만 조립한다.
