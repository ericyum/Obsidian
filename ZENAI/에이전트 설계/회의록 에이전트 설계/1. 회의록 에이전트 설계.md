# 회의록 에이전트 설계

이 문서는 회의록 에이전트의 설계 가정, Tool의 역할, 권한과 실행 제약, State와 Checkpoint의 저장 범위를 정의한다.

회의록 업무 워크플로우와 각 단계의 Agent Graph는 [[4. 회의록 에이전트 워크플로우]]에서 별도로 다룬다.

## 1. 설계 시 가정 사항

### 1-1. 단일 에이전트로 구성

회의록 에이전트가 수행하는 작업과 Tool 흐름이 비교적 단순할 것으로 예상되므로 하나의 LLM이 여러 Tool을 선택하는 **단일 에이전트**로 구성한다.

여러 에이전트를 분리하지 않고 하나의 에이전트가 사용자의 요청, 현재 State와 Tool 결과를 보고 다음 행동을 결정한다.

### 1-2. 기존 ZEN AI 기능을 재사용

ZEN AI의 회의록 기능과 관련 백엔드 로직은 이미 구현되어 있다고 가정한다. 에이전트가 회의 생성·제어·확정·조회 로직을 새로 구현하는 것이 아니라, 기존 기능을 호출할 수 있도록 Tool 인터페이스를 제공한다.

특히 회의 제어에는 다음 두 백엔드 메서드가 존재한다고 가정한다.

- 회의 재생·일시정지 메서드
- 회의 종료 메서드

에이전트에는 두 메서드를 별도 Tool로 노출하지 않고, 하나의 회의 제어 Tool 내부에서 요청한 동작에 따라 알맞은 기존 메서드를 호출한다.

UI 버튼, Skill, 에이전트 요청처럼 진입점이 여러 개이더라도 실제 실행은 같은 기존 백엔드 로직을 사용한다.

### 1-3. State와 Checkpoint

현재 대화와 Agent Loop에 필요한 정보는 State의 `messages`에 저장한다고 가정한다.

```python
State = {
    "messages": [...],
}
```

`messages`에는 다음 정보가 들어갈 수 있다.

- 사용자의 요청
- LLM의 답변과 Tool 호출
- Tool 실행 결과
- Human in the Loop 이후 전달된 사용자 입력·선택 결과

Checkpoint는 State와 별개의 저장 공간이 아니라, 특정 시점의 State를 영속적으로 저장한 결과다. 다음과 같은 시점에 Checkpoint를 남긴다.

- 에이전트 세션을 생성한 직후
- Human in the Loop로 Graph를 중단하기 직전
- 사용자 입력을 받아 Graph를 재개한 뒤
- 주요 Tool 결과가 State에 반영된 뒤
- Compact로 `messages`가 갱신된 뒤

Checkpoint에는 State가 저장되므로 `messages`에 포함된 Tool 결과와 선택된 회의록 ID 결과는 저장될 수 있다. 반면 회의록 원문은 State에 넣지 않으므로 Checkpoint에도 복제하지 않는다.

### 1-4. Compact

LLM이 한 번에 처리할 수 있는 **컨텍스트 윈도우에는 한계가 있다.** 질문과 답변이 반복되면 State의 `messages`가 계속 길어지고, 결국 새로운 정보를 넣을 공간이 부족해지거나 LLM의 성능이 저하될 수 있다.

따라서 전체 컨텍스트 윈도우의 약 50%가 찼을 때를 기준으로 기존 대화 내용을 요약·정리하는 Compact를 실행한다. 이 기준은 사용하는 모델과 실제 토큰 사용량에 따라 조정할 수 있다.

```text
현재 컨텍스트 사용량 확인
→ 전체 컨텍스트 윈도우의 약 50% 미만: 그대로 진행
→ 전체 컨텍스트 윈도우의 약 50% 이상: Compact 실행
```

Compact의 대상은 State의 `messages`다. 회의록 원문은 `messages`에 저장하지 않으므로 Compact 대상에 포함되지 않는다.

### 1-5. 회의록 원문과 대화 기록의 분리

회의록 원문을 `messages`에 계속 누적하면 컨텍스트가 불필요하게 커지고, Compact 과정에서 원문 일부가 소실될 수 있다.

처음에는 사용자가 선택한 회의록 원문을 서버의 임시 Storage에 따로 저장하고, 질문할 때마다 임시 파일을 읽어오는 방법을 고려했다.

그러나 하나의 질문에 여러 회의록이 필요한 경우에는 선택된 회의록들을 임시 Storage에 일일이 저장하고 관리해야 한다. 질문에 따라 필요한 회의록 조합이 달라질 수도 있으므로 이 방식은 불필요하게 복잡해진다.

따라서 임시 Storage에 원문을 복사하지 않고 선택된 회의록의 ID만 확보한다. 회의록 내용이 필요한 시점마다 해당 ID를 이용해 원문을 가져와 최종 컨텍스트에 넣는다.

```text
회의록 원문을 messages에 누적
→ 컨텍스트가 불필요하게 커짐

회의록 원문을 임시 Storage에 저장
→ 여러 회의록이 필요하면 각각 저장·관리해야 함

선택된 회의록 ID만 확보
→ 필요한 시점에 ID로 원문 조회
→ 원문과 messages를 분리한 상태로 최종 컨텍스트 조립
```

회의록 원문은 LLM을 호출하는 동안에만 사용하는 실행 중 문서 데이터다. 원문은 State의 `messages`나 Checkpoint에 저장하지 않는다.

## 2. Tool 목록

### 모든 Tool에 대한 공통 원칙

1. 각 Tool의 입력 Schema와 Tool 결과가 LLM 컨텍스트에 돌아오는 형태를 정의해야 한다.
2. 입력 불일치와 실행 오류가 발생해도 에이전트가 다음 행동을 결정할 수 있도록 오류 결과를 구분해야 한다.
3. 같은 오류를 LLM에 반복해서 전달해 무한 루프가 생기지 않도록 재시도 횟수와 중단 기준을 정해야 한다.
4. LLM은 어떤 Tool을 어떤 입력으로 호출할지만 결정한다. 권한, 현재 상태 검증, 실제 메서드 선택과 실행은 Tool의 백엔드가 담당한다.
5. Tool은 가능한 한 기존 ZEN AI 백엔드 메서드를 감싼 얇은 실행 인터페이스로 구현한다.

### Tool 1. 회의 시작

기존 회의 정보 입력 모달과 회의 시작 로직을 호출하고, 사용자가 입력을 확정할 때까지 Graph를 중단한다.

```text
입력
- 현재 채널 정보

Human in the Loop
- 회의 정보 입력
- 회의 시작 확정

결과
- 기존 회의 시작 로직의 실행 결과
```

사용자가 회의 시작을 확정하기 전에는 실제 회의를 시작하지 않는다.

Tool이 수행하는 핵심 동작이 기존 모달을 표시하는 것이므로, `/meeting start`와 같은 Skill과 에이전트 요청이 동일한 진입 로직을 사용할 수 있다. 별도 Tool 형태가 반드시 필요한지는 실제 UI 연결 방식에 따라 결정한다.

### Tool 2. 회의 재생·일시정지·종료

하나의 `control_meeting` Tool로 구성한다.

```text
Tool
- control_meeting

입력
- meeting_id
- action: "pause" | "resume" | "end"
```

LLM은 사용자 요청을 바탕으로 `action`을 선택한다. Tool 내부 백엔드는 현재 사용자의 생성자 권한과 현재 회의 상태를 검사한 뒤 기존 메서드를 호출한다.

| `action` | 호출하는 기존 백엔드 메서드 |
|---|---|
| `pause` | 회의 재생·일시정지 메서드 |
| `resume` | 회의 재생·일시정지 메서드 |
| `end` | 회의 종료 메서드 |

회의가 이미 요청한 상태라면 같은 동작을 중복 실행하지 않고 현재 상태를 반환하도록 한다. 종료된 회의에 대한 재생·일시정지 요청처럼 허용되지 않는 상태 전이는 백엔드에서 거부한다.

일시정지 요청과 이후의 재생 요청은 하나의 Graph 실행이 계속 도는 것이 아니다. 각각 별도의 사용자 요청과 Agent 실행으로 같은 `control_meeting` Tool을 호출한다.

### Tool 3. 회의록 확정 및 공유

기존 회의록 확정·공유 백엔드 로직을 호출하여 작성된 회의록을 확정하고 지정된 채널에 공유한다.

실행 전에 백엔드에서 현재 사용자가 회의 생성자인지 검사한다. 권한이 없으면 확정과 공유를 모두 수행하지 않는다.

### Tool 4. 특정 주제와 연관된 회의록 가져오기

사용자의 질문에서 주제와 조건을 받아 관련 회의록 후보 목록을 조회한다.

조회 결과에는 사용자가 다음 중 하나에 해당하는 회의록만 포함한다.

- 회의 생성자
- 회의 참여자
- 회의록 공유 대상자

후보 수에 따른 동작은 다음과 같다.

| 조회 결과 | 동작 |
|---|---|
| 0개 | 관련 회의록이 없다고 응답 |
| 1개 | Human in the Loop 없이 해당 회의록을 바로 사용 |
| 2개 이상 | 후보 목록을 표시하고 Human in the Loop로 일시정지 |

후보가 2개 이상이면 사용자는 질문에 필요한 회의록을 하나 이상 선택할 수 있다.

### Tool 5. 선택한 회의록 ID 가져오기

4번 Tool의 검색 결과에서 최종적으로 사용할 회의록 하나 또는 여러 개의 ID를 가져온다.

```text
후보 1개
→ 해당 회의록 ID를 바로 가져옴

후보 2개 이상
→ 사용자가 하나 이상 선택
→ 선택된 회의록 ID들을 가져옴
```

Tool 결과로 반환된 회의록 ID는 State의 `messages`와 Checkpoint에 저장될 수 있다. 현재는 회의록 원문을 조회하는 기준값을 회의록 ID라고 가정하며, 실제 식별자와 조회 방식은 구현 단계에서 확정한다.

### Tool 6. 회의록 원문을 가져와 최종 컨텍스트에 추가

5번 Tool이 반환한 회의록 ID를 이용해 해당 회의록의 텍스트를 가져온다. 여러 ID가 전달되면 여러 회의록의 텍스트를 가져온다.

가져온 원문은 State의 `messages`에 추가하지 않는다. LLM 호출 직전에 별도의 문서 영역으로 넣고 현재 대화 기록과 조립한다.

```text
시스템 지시
+ 회의록 원문
+ 현재 messages
= LLM에 전달할 최종 컨텍스트
```

LLM이 생성한 답변만 `messages`에 추가하고, 회의록 원문은 실행이 끝나면 컨텍스트에서 제거한다.

#### 관련 회의록 자동 선별 방안 검토

여러 회의록 중 질문에 필요한 일부만 가져와야 하는 경우에는 어떤 회의록을 선택할지에 대한 기준이 필요하다.

현재 검토 중인 방안은 회의록 내용을 사전에 벡터화해 저장하고, 사용자 질문도 벡터화한 뒤 유사도가 일정 기준 이상인 회의록만 후보로 가져오는 방식이다. 이 방식은 아직 확정된 설계가 아니다.

## 3. 권한 및 실행 제약

### 3-1. 회의 제어

`control_meeting` Tool은 백엔드에서 다음 순서로 처리한다.

1. 인증된 사용자 확인
2. 해당 회의의 생성자와 비교
3. 현재 회의 상태 확인
4. `action` 값에 따라 기존 백엔드 메서드 선택
5. 실행 또는 거부 결과 반환

LLM이나 Agent State에 `authorized=true/false`를 저장해 권한을 판단하지 않는다. Tool이 반환한 결과는 Agent가 사용자 응답 경로를 선택하기 위한 정보일 뿐이며, 권한 자체는 백엔드가 강제한다.

### 3-2. 회의록 확정 및 공유

3번 Tool도 백엔드에서 현재 사용자가 회의 생성자인지 검사한다.

- 생성자이면 확정 및 공유 실행
- 생성자가 아니면 실행하지 않음

### 3-3. 관련 회의록 조회

4번 Tool의 백엔드는 현재 사용자가 생성자·참여자·공유 대상자인 회의록만 반환한다.

권한이 없는 회의록을 일단 LLM에 전달한 뒤 제거하는 방식은 사용하지 않는다. 권한 필터는 조회 단계에서 백엔드가 강제한다.

### 3-4. 후보 수에 따른 실행 제약

4번 Tool의 검색 결과가 없으면 5번과 6번 Tool을 실행하지 않는다.

```text
후보 0개
→ 관련 회의록 없음 응답
→ 실행 종료

후보 1개
→ Human in the Loop 생략
→ Tool 5 실행

후보 2개 이상
→ Human in the Loop로 사용자 선택 대기
→ 하나 이상의 회의록 선택 후 Tool 5 실행
```

### 3-5. 회의록 원문의 사용 범위

6번 Tool은 5번 Tool이 반환한 회의록 ID에 해당하는 원문만 가져온다.

회의록 원문은 답변 생성용 컨텍스트에만 포함하고 다음 위치에는 저장하지 않는다.

- State의 `messages`
- Checkpoint
- 별도의 임시 Storage

## 4. Human in the Loop와 Checkpoint

| 적용 기능 | Graph 중단 시점 | 사용자 행동 | 재개 후 동작 |
|---|---|---|---|
| 회의 시작 | 회의 정보 입력 모달 표시 후 | 정보 입력 후 `회의 시작` 확정 | 입력값으로 기존 회의 시작 로직 호출 |
| 관련 회의록 조회 | 접근 가능한 후보가 2개 이상일 때 | 회의록을 하나 이상 선택 | 선택 결과로 회의록 ID 가져오기 |

Human in the Loop를 실행하기 직전에 현재 State를 Checkpoint에 저장한다. 사용자가 입력하거나 선택하면 저장된 Checkpoint를 기준으로 Graph를 재개하고 사용자 결과를 State에 반영한다.

4번 Tool의 조회 결과가 0개이면 관련 회의록이 없다고 응답한다. 1개이면 Human in the Loop와 중단용 Checkpoint를 거치지 않고 바로 다음 단계로 진행한다.

## 5. 추후 결정 사항

- Tool 1을 별도 Tool로 유지할지, 기존 UI 또는 Skill 진입 로직으로 직접 연결할지
- 회의록 원문 조회에 사용할 실제 식별자와 조회 방식
- 벡터 유사도를 이용한 관련 회의록 자동 선별 방식의 적용 여부
- 사용하는 모델과 실제 토큰 사용량에 따른 Compact 실행 기준
- Tool별 입력 Schema, 결과 Schema, 오류 코드, 재시도 횟수와 중단 기준

## 핵심 정리

> 회의록 에이전트는 기존 ZEN AI 기능을 호출하는 단일 에이전트로 구성한다. 대화와 Tool 결과는 State의 `messages`에 저장하고 중요한 실행 지점의 State는 Checkpoint에 저장한다. 회의 제어는 하나의 `control_meeting` Tool이 `pause`, `resume`, `end`를 받아 기존 재생·일시정지 메서드와 종료 메서드 중 하나를 호출한다. 권한과 현재 상태는 Tool의 백엔드가 검사한다. 선택된 회의록 ID는 State에 남길 수 있지만 원문은 State·Checkpoint·임시 Storage에 저장하지 않고 필요한 시점에 조회해 최종 컨텍스트에만 넣는다.
