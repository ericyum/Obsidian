# 회의록 에이전트 현재 구현 상세 설계

## 1. 현재 설계 사항 요약본

| 항목 | 현재 설계 |
|---|---|
| Agent 구성 | 회의록 검색·질문에 두 Tool을 사용하는 단일 Agent |
| 실행 공간 | 사용자가 호출한 전용 스레드 |
| 동일 스레드 요청 | 기존 실행 큐에서 접수 순서대로 처리 |
| Agent 오케스트레이터 State | `ScratchPad`, `authorized_meeting_ids`, `recording_modal_status` |
| 녹화 모달 State | `recording_state = none, recording, pause, stop` |
| 녹화 제어 | 명시적 Trigger를 오케스트레이터의 고정 코드가 기존 UI와 동일한 모달 로직에 연결 |
| 녹화 과정의 성격 | LLM Agent 판단이 없는 결정적 Workflow |
| Agent Tool | Tool 1 검색·선택, Tool 2 원문 조회 |
| 권한 강제 | 모달과 Tool 뒤의 백엔드 로직에서 강제 |
| Human in the Loop | 후보 선택과 기존 ID의 추가·대체 여부에서 사용 |
| 실행 식별자 | 별도의 `actor`, `run_id`를 두지 않고 에이전트의 큐(queue)로 해결 |
| 컨텍스트 조립 | 회의록 원문을 State에 저장하지 않고 질문 시 조회·조립 |

> [!important] State 소유 기준
> 실제 녹화 진행 상태인 `recording_state`는 녹화 임베디드 상단바 모달이 관리·갱신한다. Agent 오케스트레이터는 모달이 반환하는 정상·오류 신호만 `recording_modal_status`의 `healthy` 또는 `error`로 관리한다. 검색·질문에 필요한 `authorized_meeting_ids`는 Agent 오케스트레이터 State에 유지한다.

## 2. 설계 가정

### 2-1. 단일 에이전트로 구성

회의록 에이전트가 수행하는 판단과 Tool 흐름이 비교적 단순할 것으로 예상되므로 하나의 LLM이 여러 Tool을 선택하는 **단일 에이전트**로 구성한다. 녹화 명시적 Trigger는 LLM 판단을 거치지 않고 오케스트레이터의 고정 코드에서 처리한다.

### 2-2. 사용자별 전용 스레드에서 독립적으로 실행

회의 생성·진행과 공유 회의록의 검색·질의는 하나의 Agent 실행으로 이어지는 과정이 아니다. 회의 생성자와 공유받은 사용자는 **각각 회의 에이전트를 호출해 생성된 자신의 전용 스레드에서 필요한 업무**를 시작한다.

#### 2-2-1. 동일 스레드의 요청은 순차 처리

전용 스레드는 해당 사용자의 회의록 Agent 실행 공간이다. 같은 사용자가 한 스레드에서 연속으로 보낸 Agent 요청은 기존 실행 큐(queue)에서 **접수된 순서대로 처리**된다고 가정한다. 따라서 현재 범위에서는 요청 순서를 구분하기 위한 별도의 `actor`나 `run_id`를 추가하지 않는다.

기존 `authorized_meeting_ids`와 무관한 별도의 회의록 집합과 대화 맥락을 사용하고 싶다면, 사용자가 자신의 채널에서 회의 에이전트를 다시 호출하여 **새 전용 스레드**에서 검색과 질문을 시작한다.

### 2-3. 두 종류의 실행 경로를 구분

회의록 업무에는 성격이 다른 두 실행 경로가 있다.

- **회의 녹화 과정**: 명시적 Trigger 또는 상단바 버튼이 기존 모달 로직을 실행하며, 실제 `recording_state`는 녹화 임베디드 상단바 모달이 지속 관리한다.
- **회의록 검색·질문 과정**: LLM이 현재 사용자 목표에 필요한 Tool을 선택한다. 하나의 요청 안에서 Search 다음 Question이 이어질 수 있으며, 각 Subgraph 결과를 반영한 뒤 후속 작업이 남았으면 LLM 판단으로 복귀한다. Graph에는 `none`, `search`, `question`이라는 개념적 State를 사용하지만 같은 이름의 지속 코드 변수는 만들지 않는다.

녹화 모달 State와 검색·질문 Agent Graph의 State는 **완전히 독립적**이다. 양쪽의 `none`도 이름만 같을 뿐, 녹화 Workflow에서는 녹화 전·요청 대기이고 Agent Graph에서는 검색·질문 요청 대기라는 서로 다른 값이다. 어느 한쪽도 다른 쪽 **Graph State**를 읽거나 변경하지 않으므로, 회의가 녹화 중이더라도 사용자는 기존 회의록을 검색하거나 이미 선택한 회의록을 바탕으로 질문할 수 있다.

### 2-4. 기존 ZEN AI 프론트엔드와 백엔드를 재사용

ZEN AI의 녹화 임베디드 상단바 모달, 회의록 기능과 백엔드 로직은 이미 구현되어 있다고 가정한다.

- 스레드의 녹화 Trigger는 오케스트레이터의 고정 코드가 회의 탭·상단바 버튼과 동일한 모달 로직에 연결한다.
- 모달은 자신의 `recording_state`에 따라 시작·일시정지·재개·종료 동작을 구분하고 기존 녹화 백엔드 메서드를 호출한다.
- 회의록 검색·선택과 원문 조회는 Agent Tool 인터페이스를 통해 기존 백엔드 로직을 호출한다.

```text
녹화 Trigger 또는 UI 버튼
→ 녹화 임베디드 상단바 모달
→ 기존 녹화 백엔드 메서드
→ 모달 recording_state 갱신
→ 모달 결과 신호
→ 오케스트레이터 recording_modal_status 갱신

LLM의 Tool 선택
→ 검색·선택 또는 원문 조회 Tool 인터페이스
→ Tool 뒤의 기존 백엔드 로직
→ 결과를 LLM 컨텍스트와 Agent State에 필요한 범위로 반영
```

## 3. 녹화 Trigger와 임베디드 상단바 모달

### 3-1. 녹화 State를 모달에서 관리하는 이유

이미 구축된 **녹화 임베디드 상단바 모달은 현재 녹화 상태에 따라 시작·일시정지·재개·종료 동작을 다르게 실행하도록 구성되어 있다.** 따라서 같은 녹화 State Machine을 Agent 오케스트레이터에 중복해서 구현하지 않고, 실제 `recording_state`는 모달이 관리·갱신하도록 한다.

회의 녹화는 LLM이 사용자 의도를 해석하거나 실행 기능을 선택하는 Agent 과정이 아니다. 명시적인 Trigger·UI 입력에 따라 모달과 백엔드가 정해진 경로를 실행하는 **결정적 Workflow**다.

Agent 오케스트레이터는 모달 내부의 녹화 상태를 직접 소유하지 않고, 모달이 반환하는 정상·오류 신호만 `recording_modal_status`의 `healthy` 또는 `error`로 관리하는 것이 더 단순하다.

이 구조에는 다음 효과가 있다.

- 사용자의 직접 UI 조작과 스레드 Trigger가 같은 모달 State를 사용한다.
- 모달과 Agent에 동일한 녹화 State를 중복 저장하지 않는다.
- 두 State를 별도로 동기화해야 하는 문제를 줄인다.
- Agent 오케스트레이터의 State와 분기 코드를 단순하게 유지한다.

### 3-2. 녹화 Trigger 매핑

| 사용자 입력 | 실행되는 기존 UI 로직 |
|---|---|
| `회의 시작`, `/meeting-start` | 회의 탭의 회의 시작 버튼과 동일한 로직 |
| `회의 일시정지`, `/meeting-pause` | 상단바의 일시정지 버튼과 동일한 로직 |
| `회의 재개`, `/meeting-resume` | 상단바의 재개 버튼과 동일한 로직 |
| `회의 종료`, `/meeting-stop` | 상단바의 종료 버튼과 동일한 로직 |

오케스트레이터는 위 명시적 Trigger를 고정 코드로 판별한다. 이 과정에는 LLM 판단이나 Agent Tool 호출이 없다.

### 3-3. 녹화 모달의 실행과 결과 신호

```text
명시적 Trigger 또는 상단바 버튼
→ 녹화 임베디드 상단바 모달
→ 모달의 현재 recording_state 검사
→ 인증·생성자 권한·실제 회의 상태 검사
→ 기존 녹화 백엔드 메서드 실행
→ 성공 시 모달이 recording_state 갱신
→ 모달이 정상·오류 결과 신호 반환
→ 오케스트레이터가 recording_modal_status 갱신
```

| 동작 | 모달의 허용 `recording_state` | 성공 후 모달 State |
|---|---|---|
| 회의 시작 | `none` | `recording` |
| 회의 일시정지 | `recording` | `pause` |
| 회의 재개 | `pause` | `recording` |
| 회의 종료 | `recording`, `pause` | `stop → none` |

모달이 정상적으로 응답하고 실행되면 오케스트레이터는 `recording_modal_status="healthy"`를 반영한다. 모달 연결이나 실행 자체에 오류가 있으면 `recording_modal_status="error"`를 반영한다. 현재 녹화 State상 허용되지 않는 요청을 모달이 정상적으로 거부한 경우는 모달 오류가 아니므로 `healthy`를 유지한다.

`stop`은 녹화 종료 처리 시 거치는 상태다. 종료 처리가 완료되면 모달의 `recording_state`는 바로 `none`으로 돌아간다.

## 4. Agent Tool 목록

### 4-1. 공통 원칙

Agent Tool은 LLM과 백엔드 로직 사이의 실행 인터페이스다. **녹화 제어에는 Agent Tool을 사용하지 않는다.**

1. Tool은 이름, Description, 입력·출력 Schema와 오류 형식을 가진다.
2. LLM은 어떤 Tool을 어떤 인자로 호출할지만 판단한다.
3. 인증, 권한, 입력 검증과 실제 비즈니스 로직은 Tool 뒤의 백엔드가 강제한다.
4. `authorized_meeting_ids`와 인증 정보는 LLM이 직접 생성하거나 수정하지 않는다.
5. 반환 오류 형식은 재시도, 사용자 확인, 다른 Tool 선택, 중단을 구분할 수 있도록 구조화한다.

| Tool | 핵심 기능 | 주요 사전 조건 | State 영향 | Human in the Loop |
|---|---|---|---|---|
| **Tool 1 — 검색·선택** | 접근 가능한 회의록을 검색하고 사용할 ID 확정 | 백엔드 접근 권한 필터 통과 | `authorized_meeting_ids` 추가·대체 | 후보 선택, 기존 ID 추가·대체 |
| **Tool 2 — 원문 조회** | 허용된 ID의 회의록 원문 조회 | ID가 `authorized_meeting_ids`에 포함 | 답변과 구조화된 결과만 `ScratchPad`에 추가 | 없음 |

### 4-2. Tool 1 — 관련 회의록 검색·선택

주제, 날짜 등의 조건으로 접근 가능한 회의록 후보를 검색하고 최종 ID를 확정하는 Search Subgraph에서 사용하는 Tool이다. Tool 1 인터페이스와 그 뒤의 백엔드는 권한 필터와 후보 검색을 담당하며, 후보 수 해석·HITL·ID 추가·대체와 최종 안내는 LLM과 오케스트레이터가 Search Subgraph 안에서 이어서 처리한다.

백엔드 로직상 사용자가 다음 중 하나에 해당하는 회의록만 후보로 반환하도록 강제한다.

- 회의 생성자
- 회의 참여자
- 회의록이 공유된 채널의 구성원

| 후보 수 | 처리 |
|---|---|
| 0개 | 관련 회의록 없음 반환, 기존 ID 유지 |
| 1개 | 해당 후보를 바로 검증·선택 |
| 2개 이상 | 같은 스레드에서 Human in the Loop로 하나 이상 선택 |

회의록 검색 이후 해당 회의록 ID들이 최초의 권한 필터링 후보 집합에 포함되는지 백엔드가 다시 확인한다. 그 후 기존 `authorized_meeting_ids`가 있으면 같은 스레드에서 **추가 또는 대체**를 선택하게 하고, 검증된 결과만 State에 반영하도록 반환한다.

Tool의 성공·실패 결과는 구조화하여 LLM에 전달한다. LLM은 접근 가능한 후보 수를 해석해 0개·1개·2개 이상 경로를 선택하고, 오케스트레이터는 필요한 HITL과 ID 추가·대체, `authorized_meeting_ids` 갱신을 수행한다. 그 결과를 정형화한 컨텍스트로 다시 받은 LLM은 “검색 결과 없음”, “기존 목록에 추가”, “새 목록으로 대체”와 같은 검색 응답과 **후속 작업 있음·없음**을 생성한다.

Search Subgraph 안에서는 상위 Graph State `search`와 내부 개념적 제어 State를 사용하지만 이를 지속 코드 변수로 저장하지 않는다. `SEARCH_RESPONSE_READY` 반환 뒤 Graph Runtime이 `search → none`으로 정리하고 결과를 `ScratchPad`에 반영한 뒤 Checkpoint를 저장한다. 후속 작업이 남았으면 LLM 판단 Node로 돌아가며, 남은 작업이 없을 때만 END를 거쳐 다음 입력을 기다린다.

### 4-3. Tool 2 — 회의록 원문 조회

사용자의 질문에 필요한 회의록 원문을 ID로 조회한다.

- 요청된 ID가 `authorized_meeting_ids`에 포함되어 있는지 서버에서 검사한다.
- 포함된 ID의 원문만 가져온다.
- 목록에 없는 ID이면 `UNAUTHORIZED_MEETING_ID`를 반환한다.
- 검색 단계의 채널 권한 전체를 반복 조회하지는 않되, 허용 목록 검증은 항상 수행한다.

가져온 원문은 State의 `ScratchPad`나 Checkpoint, 별도 임시 Storage에 저장하지 않는다.

```text
시스템 지시
+ 필요한 회의록 원문
+ 현재 ScratchPad
= LLM 최종 컨텍스트
```

LLM이 생성한 답변과 필요한 구조화된 Tool 결과만 `ScratchPad`에 추가하고 원문은 해당 호출이 끝나면 컨텍스트에서 제거한다.

허용 ID가 없거나 Tool 2가 거부·실패한 경우에도 구조화된 결과를 LLM에 전달해 회의록 선택 필요 또는 실패 이유를 최종 답변으로 생성한다. 사용자의 요청이 Tool 없이 답변 가능한 경우에는 LLM이 Tool 2를 호출하지 않고 `none`을 유지한 채 직접 답변한다. 어느 경로든 결과를 `ScratchPad`에 반영하고 Checkpoint를 저장한 뒤 같은 후속 작업 Condition으로 합류한다.

## 5. State Schema와 갱신 규칙

### 5-1. Agent 오케스트레이터 State

```python
RecordingModalStatus = Literal[
    "healthy",
    "error",
]

class MeetingAgentState(TypedDict):
    ScratchPad: list
    authorized_meeting_ids: list[str]
    recording_modal_status: RecordingModalStatus
```

| 필드 | 역할 |
|---|---|
| `ScratchPad` | 현재 사용자 목표, LLM 응답, Tool 결과, Human in the Loop 선택 결과와 후속 판단에 필요한 작업 기록 |
| `authorized_meeting_ids` | 검색 Tool에서 권한과 후보 검증을 거쳐 선택된 회의록 ID의 서버 관리 허용 목록 |
| `recording_modal_status` | 녹화 모달의 정상 동작 여부. 정상 응답은 `healthy`, 모달 연결·실행 오류는 `error` |

### 5-2. 녹화 임베디드 상단바 모달 State

```python
RecordingState = Literal[
    "none",
    "recording",
    "pause",
    "stop",
]
```

| 값 | 의미 | 설정 시점 |
|---|---|---|
| `none` | 진행 중인 녹화 과정이 없음 | 최초 모달 생성 또는 회의 종료 처리 완료 후 |
| `recording` | 회의 녹화 중 | 회의 시작 또는 재개 성공 후 |
| `pause` | 녹화 일시정지 | 일시정지 성공 후 |
| `stop` | 녹화 종료 처리 시 거치는 상태 | 종료 성공 후 |

대표 전이는 다음과 같다.

```text
none → recording ↔ pause → stop → none
```

### 5-3. State 소유권과 갱신 주체

| 값 | 소유·관리 위치 | 갱신 주체 | Agent Checkpoint |
|---|---|---|---|
| `ScratchPad` | Agent 오케스트레이터 | 오케스트레이터 | 포함 |
| `authorized_meeting_ids` | Agent 오케스트레이터 | 검증된 Tool 결과를 받은 오케스트레이터 | 포함 |
| `recording_modal_status` | Agent 오케스트레이터 | 모달 결과 신호를 받은 오케스트레이터 | 포함 |
| `recording_state` | 녹화 임베디드 상단바 모달 | 모달 | 포함하지 않음 |

LLM은 위 값을 임의로 생성하거나 수정하지 않는다. 모달의 실제 녹화 상태와 백엔드 리소스 상태는 모달과 백엔드가 관리하며, Agent 오케스트레이터는 이를 중복 저장하지 않는다.

### 5-4. `authorized_meeting_ids`

회의록 검색·선택 Tool은 백엔드 권한 필터를 통과한 후보 안에서 **최종 선택된 ID만 `authorized_meeting_ids`에 반영**하도록 결과를 반환한다. 실제 Agent State 갱신은 오케스트레이터가 담당한다.

기존 ID가 있는 상태에서 새 회의록을 검색하면 사용자가 같은 스레드에서 다음 중 하나를 선택한다.

- **추가**: 기존 ID와 새 ID를 중복 없이 병합
- **대체**: 기존 ID를 버리고 새 ID 집합으로 교체

검색 결과가 없거나 검색이 취소·실패하면 기존 목록을 유지한다.

## 6. Checkpoint

Checkpoint는 별도의 업무 상태가 아니라 **특정 시점의 Agent 오케스트레이터 State와 완료된 실행 결과를 저장한 세이브 포인트**다. 하나의 사용자 요청 안에서 Search 다음 Question이 이어지면 각 Subgraph 결과 뒤에 Checkpoint가 여러 번 생길 수 있다.

| 업무 단위 | Checkpoint에 반영되는 핵심 결과 |
|---|---|
| 녹화 Trigger 처리 1회 | 모달 결과 신호에 따른 `recording_modal_status` |
| 회의록 검색·선택 | 선택된 ID의 추가·대체 결과 또는 기존 ID 유지, 검색 응답·Tool 결과를 반영한 `ScratchPad` |
| 회의록 질문 1회 | 질문·답변·Tool 결과를 반영한 `ScratchPad`, 기존 `authorized_meeting_ids` 유지 |

모달 내부의 `recording_state`는 Agent Checkpoint에 저장하지 않는다. 검색과 질문의 개념적 Graph State를 지속 코드 변수로 만들지 않는다는 사실은 Checkpoint를 남기지 않는다는 뜻이 아니다. Graph Runtime은 `SEARCH_RESPONSE_READY` 또는 `QUESTION_RESPONSE_READY`를 받은 뒤 상위 State를 `search/question → none`으로 정리하고, 변경된 Agent State와 실행 결과를 Checkpoint에 저장한다.

검색·질문 Checkpoint 뒤에는 후속 작업 Condition을 실행한다. LLM은 원래 사용자 목표·`ScratchPad`·Tool 결과를 바탕으로 `후속 작업 있음/없음`을 구조화해 반환하고, 오케스트레이터의 고정 Condition은 그 값을 읽어 다음 Edge를 확정한다.

- 후속 작업이 있으면 END로 가지 않고 LLM 판단 Node로 복귀한다.
- 후속 작업이 없으면 현재 사용자 목표의 달성을 확정하고 END 후 Agent 요청 대기로 돌아간다.

업무 완료 지점의 Checkpoint와 사용자의 결정을 기다리는 `interrupt()` 기반 Human in the Loop는 구분한다. Checkpoint 자체는 자동 복구를 수행하지 않으므로, Tool 실행 오류가 발생하면 마지막 정상 Agent Checkpoint를 기준으로 해당 Agent 업무를 재시도하는 복구 오케스트레이션이 필요하다.

브라우저를 나갔다가 나중에 중단 지점부터 같은 Graph 실행을 복구하는 기능은 현재 범위에 포함하지 않는다.

## 7. 권한 및 실행 제약 상세 설명

각 실행 절에는 해당 기능을 이해하는 데 필요한 핵심 조건을 적고, 이 절에서는 **회의 녹화 과정**과 **회의록 검색·질문 과정**으로 나누어 전체 권한·실행 정책과 구성요소의 책임을 정리한다.

| 구성요소 | 회의 녹화 과정 | 회의록 검색·질문 과정 |
|---|---|---|
| **사용자·UI** | 명시적 Trigger 입력 또는 상단바 직접 조작 | 검색·질문 요청과 Human in the Loop 선택 |
| **LLM** | 사용하지 않음 | 검색·질문 의도 해석, Tool 1·2 선택과 답변 생성 |
| **오케스트레이터** | 고정 Trigger 연결, 모달 결과에 따른 `recording_modal_status` 갱신과 Checkpoint 저장 | 컨텍스트 조립, `authorized_meeting_ids` 갱신과 Checkpoint 저장 |
| **녹화 모달** | `recording_state` 검사·갱신과 기존 녹화 백엔드 메서드 호출 | 사용하지 않음 |
| **Agent Tool** | 사용하지 않음 | Tool 1·2를 통해 검색·선택과 원문 조회 백엔드 호출 |
| **백엔드** | 인증·생성자 권한·실제 회의 상태 검사와 녹화 로직 실행 | 접근 권한 필터, 선택 ID 검증과 허용된 원문 조회 |

### 7-1. 회의 녹화 과정

녹화 모달과 기존 백엔드는 다음을 검사한다.

1. 모달의 `recording_state`가 요청 동작의 허용 상태인지
2. 인증된 사용자인지
3. 해당 회의의 생성자인지
4. 백엔드의 실제 회의 상태가 동작 가능한 상태인지

성공한 경우에만 기존 녹화 메서드를 실행하고 모달이 `recording_state`를 갱신한다. LLM이나 Agent Tool에 녹화 상태와 권한 판단을 맡기지 않는다.

회의 종료 처리가 완료되면 모달의 `recording_state`는 `stop → none`으로 바로 바뀐다.

### 7-2. 회의록 검색·질문 과정

Tool 1은 조회 단계에서 사용자에게 접근 권한이 있는 회의록만 반환한다. 권한 없는 원문을 LLM에 전달한 뒤 제거하는 방식을 사용하지 않는다.

후보가 여러 개일 때의 선택과 기존 ID의 추가·대체는 같은 스레드의 Human in the Loop로 처리한다. 별도의 실행 식별자인 `run_id`는 두지 않는다.

Tool 2는 입력된 ID가 `authorized_meeting_ids`에 포함되어 있는지 백엔드에서 확인한다. 이 목록은 권한 자체를 LLM에 맡기는 값이 아니라, 앞선 검색·선택 과정에서 서버가 검증한 결과를 다음 조회에 전달하는 임시 허용 목록이다.

| 상황 | 사용자 행동 | 재개 후 처리 |
|---|---|---|
| 접근 가능한 후보가 2개 이상 | 필요한 회의록을 하나 이상 선택 | 후보 집합 포함 여부 재검증 |
| 기존 ID가 있는데 새 ID가 확정됨 | 기존 목록에 추가 또는 새 목록으로 대체 | 검증된 ID 목록 병합 또는 교체 |

사용자 선택을 기다리고 이후 실행을 재개하기 위해 `interrupt()` 등을 사용한다.

## 8. Compact

LLM의 컨텍스트 윈도우에는 한계가 있으므로 `ScratchPad`의 대화·작업 기록이 전체 **컨텍스트 윈도우의 약 50%에 도달하면 Compact를 실행**한다. 실제 기준은 모델과 토큰 사용량에 따라 조정한다.

이때 윈도우 용량 측정에 있어서 **회의록 원문은 `ScratchPad`에 누적하지 않으므로** Compact 대상으로 넣지 않으며, 원문은 질문 시점에 ID로 조회하여 최종 컨텍스트에만 임시로 조립한다. `authorized_meeting_ids`와 `recording_modal_status`도 Compact 대상이 아니다.

## 9. 추후 결정 사항

- 회의록 원문 조회에 사용할 실제 식별자와 조회 방식
- 여러 회의록 중 질문과 관련된 원문을 자동 선별할 방식
- 사용하는 모델과 실제 토큰 사용량에 따른 Compact 기준
- 녹화 임베디드 상단바 모달의 결과 신호와 `recording_modal_status` 사이의 구체적인 이벤트 동기화 방식
- **Tool별 입력·출력 Schema, 오류 코드, 재시도 횟수와 중단 기준** (Tool 설계)

## 핵심 정리

> 회의록 에이전트의 오케스트레이터는 `ScratchPad`, `authorized_meeting_ids`, `recording_modal_status`를 관리하고, 실제 녹화 `recording_state`는 이미 구축된 녹화 임베디드 상단바 모달이 관리한다. 회의 시작·일시정지·재개·종료는 명시적 Trigger를 오케스트레이터의 고정 코드가 기존 UI와 동일한 모달 로직에 연결하므로 LLM이나 Agent Tool을 사용하지 않는다. 회의 종료 처리가 완료되면 모달은 `stop → none`으로 바로 돌아간다. Agent에는 검색·선택 Tool 1과 원문 조회 Tool 2만 등록하며, 권한과 실제 실행 여부는 모달과 Tool 뒤의 백엔드가 강제한다.

회의 녹화는 결정적 Workflow이며, 회의록 검색·질문은 LLM이 Tool 필요 여부를 판단하는 반복적인 Agent 실행이다. 검색 결과, ID 갱신 결과, 질의 대상 없음과 Tool 오류는 정형화된 컨텍스트로 LLM에 전달된다. 결과를 `ScratchPad`에 반영하고 Checkpoint를 저장한 뒤 후속 작업이 있으면 LLM 판단으로 복귀하며, 현재 사용자 목표가 달성되었을 때만 END 후 다시 요청을 기다린다.
