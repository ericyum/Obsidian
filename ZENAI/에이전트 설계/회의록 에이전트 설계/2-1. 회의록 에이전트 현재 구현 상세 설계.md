# 회의록 에이전트 현재 구현 상세 설계

## 1. 현재 설계 사항 요약본

| 항목                | 현재 설계                                           |
| ----------------- | ----------------------------------------------- |
| Agent 구성          | 여러 Tool을 선택하는 단일 Agent                          |
| 실행 공간             | 사용자가 호출한 전용 스레드                                 |
| 동일 스레드 요청         | 기존 실행 큐에서 접수 순서대로 처리                            |
| 전역 State          | 회의 녹화 상태만 전역 State로 관리                          |
| 검색·질문             | 별도 업무 State 없이 요청 단위로 처리                        |
| Backend Skill     | 회의 시작·일시정지·재개·종료                                |
| Agent Tool        | 확정·공유, 검색·선택, 원문 조회                             |
| 권한 강제             | Skill·Tool 뒤의 백엔드 로직에서 강제                       |
| Human in the Loop | 후보 선택과 기존 ID의 추가·대체 여부에서 사용                     |
| 실행 식별자            | 별도의 `actor`, `run_id`를 두지 않고 에이전트의 큐(queue)로 해결 |
| 컨텍스트 조립           | 회의록 원문을 State에 저장하지 않고 질문 시 조회·조립               |
| State 갱신          | 현재 기준에서는 성공한 백엔드 결과를 받은 오케스트레이터가 반영             |

> [!important] 현재 State 갱신 기준
> 이 문서에서는 **Backend Skill과 Tool이 성공·실패 결과를 반환하고 오케스트레이터가 Agent State를 갱신하는 구조**를 현재 기준으로 사용한다. Tool 계층이 별도 저장소의 State를 직접 소유·갱신하는 구조는 검토안이며, 확정되기 전에는 현재 사양에 적용하지 않는다.

## 2. 설계 가정

### 2-1. 단일 에이전트로 구성

회의록 에이전트가 수행하는 판단과 Tool 흐름이 비교적 단순할 것으로 예상되므로 하나의 LLM이 여러 Tool을 선택하는 **단일 에이전트**로 구성한다.

### 2-2. 사용자별 전용 스레드에서 독립적으로 실행

회의 생성·진행·공유와 공유 회의록의 검색·질의는 하나의 Agent 실행으로 이어지는 과정이 아니다. 회의 생성자와 공유받은 사용자는 **각각 회의 에이전트를 호출해 생성된 자신의 전용 스레드에서 필요한 업무**를 시작한다.

#### 2-2-1. 동일 스레드의 요청은 순차 처리

동일한 전용 스레드에서 여러 사용자가 동시에 검색하거나 `authorized_meeting_ids`를 변경하더라도, Agent 요청은 기존 실행 큐(queue)에서 **접수된 순서대로 처리**된다고 가정한다. 따라서 요청 순서를 구분하기 위한 별도의 `actor`나 `run_id`는 추가하지 않는다.

공유된 `authorized_meeting_ids`와 무관하게 별도의 회의록 집합을 사용하고 싶다면, 사용자가 자신의 채널에서 회의 에이전트를 다시 호출하여 **새 전용 스레드**에서 검색과 질문을 시작한다.

### 2-3. 두 종류의 실행 경로를 구분

회의록 업무에는 성격이 다른 두 실행 경로가 있다.

- **회의 녹화 과정**: 일시정지·재개·종료처럼 다음 행동의 허용 여부가 이전 상태에 의존하므로 **`state`로 지속 관리**한다.
- **회의록 검색·질문 과정**: 검색 한 번 또는 질문 한 번을 처리하면 끝나는 일회성 실행이다. **별도의 `state`를 만들지 않는다**.

두 경로는 하나의 전역 업무 State를 차지하기 위해 경쟁하지 않는 구조이며 따라서 회의가 녹화 중이더라도 사용자가 기존 회의록을 검색하거나, 이미 선택한 회의록을 바탕으로 질문할 수 있다.

## 3. 구성요소와 책임 경계

| 구성요소 | 현재 책임 |
|---|---|
| 사용자·UI | Trigger 입력, 녹화 조작, Human in the Loop 선택 |
| LLM | 사용자 의도 해석, Agent Tool 선택, 답변 생성 |
| 오케스트레이터 | Graph 실행, 컨텍스트 조립, 성공 결과에 따른 Agent State 갱신 |
| Backend Skill | 녹화 상태·인증·권한·실제 회의 상태 검사 후 녹화 메서드 실행 |
| Agent Tool | LLM이 백엔드 기능을 호출하기 위한 이름·Description·Schema·오류 계약 제공 |
| Tool 뒤의 백엔드 | 입력·권한·실제 리소스 상태 검사와 비즈니스 로직 실행 |

### 3-1. 기존 ZEN AI 백엔드를 재사용

ZEN AI의 회의록 기능과 백엔드 로직은 이미 구현되어 있다고 가정한다.

- 회의 시작·일시정지·재개·종료는 **녹화 Skill에 해당하는 백엔드 로직**이 수행한다.
- 회의록 확정·공유, 검색·선택, 원문 조회는 **Agent Tool 인터페이스**를 통해 기존 백엔드 로직을 호출한다.

녹화 Skill과 Agent Tool은 모두 실제 비즈니스 로직을 백엔드에서 실행하지만, 에이전트와의 관계가 다르다.

```text
녹화 Trigger·UI
→ 녹화 Skill에 해당하는 백엔드 로직 직접 실행
→ 성공 결과를 받은 오케스트레이터가 state 갱신

LLM의 Tool 선택
→ Agent에 등록된 Tool 인터페이스 호출
→ Tool 뒤의 백엔드 로직 실행
→ 결과를 LLM 컨텍스트와 State에 필요한 범위로 반영
```

녹화 Skill은 Agent 내부에 코딩되어 LLM이 선택하는 Tool이 아니다. Tool 역시 비즈니스 로직 그 자체가 아니라, LLM이 백엔드 기능을 안전하게 호출할 수 있도록 이름·Description·입출력 Schema·오류 형식을 제공하는 **실행 인터페이스**다.

## 4. State Schema와 갱신 규칙

### 4-1. State 구성

```python
RecordingState = Literal[
    "none", "recording", "pause", "stop", "share",
]

class MeetingAgentState(TypedDict):
    messages: list
    authorized_meeting_ids: list[str]
    state: RecordingState
```

| 필드 | 역할 |
|---|---|
| `messages` | 사용자 요청, LLM 응답, Tool 결과, Human in the Loop 선택 결과 등 대화 기록 |
| `authorized_meeting_ids` | 검색 Tool에서 권한과 후보 검증을 거쳐 선택된 회의록 ID의 서버 관리 허용 목록 |
| `state` | 현재 회의 녹화 과정의 지속 상태 |

`state`는 다음 의미를 가진다.

| 값 | 의미 | 설정 시점 |
|---|---|---|
| `none` | 진행 중인 녹화 과정이 없음 | 최초 State 생성 시 또는 확정·공유가 끝난 뒤 |
| `recording` | 회의 녹화 중 | 회의 시작 또는 재개 백엔드 성공 후 |
| `pause` | 녹화 일시정지 | 일시정지 백엔드 성공 후 |
| `stop` | 녹화 종료, 확정·공유 대기 | 종료 백엔드 성공 후 |
| `share` | 회의록 확정·공유 성공 | 확정·공유 성공 결과를 반영하는 시점 |

대표 전이는 다음과 같다.

```text
none → recording ↔ pause → stop → share → none
```

`none`은 에이전트가 꺼진 상태가 아니라 **진행 중인 녹화가 없는 상태**다. 회의록 검색과 질문은 `state`를 변경하지 않는다.

### 4-2. State 갱신 주체

녹화 Skill이나 Tool이 State를 직접 수정하지 않는다. 백엔드가 성공 또는 실패 결과를 반환하면 **오케스트레이터가 결과를 검증하고 State를 갱신**한다.

```text
백엔드 실행 성공
→ 정규화된 성공 결과 반환
→ 오케스트레이터가 State 갱신
→ 필요할 때 결과를 LLM 컨텍스트에 추가

백엔드 실행 거부·실패
→ 기존 State 유지
→ 구조화된 오류 결과 반환
```

LLM은 State 값을 임의로 생성하거나 수정하지 않는다. 실제 녹화 상태와 권한의 최종 진실의 원천은 백엔드이며, `state`는 성공(또는 실패)한 백엔드 결과를 Agent 실행에 반영한 값이다.

### 4-3. `authorized_meeting_ids`

회의록 검색·선택 Tool은 백엔드 권한 필터를 통과한 후보 안에서 **최종 선택된 ID만 `authorized_meeting_ids`에 반영**하도록 결과를 반환한다. 실제 State 갱신은 오케스트레이터가 담당한다.

```python
State = {
    "messages": [...],
    "authorized_meeting_ids": ["meeting-123", "meeting-456"],
    "state": "recording",
}
```

이 예시처럼 녹화 중에도 기존 회의록 ID가 유지될 수 있다. 검색·질문과 녹화 상태는 서로 다른 관심사이므로 한쪽이 다른 쪽을 막지 않는다.

`authorized_meeting_ids`는 LLM이나 사용자가 직접 수정할 수 없다. 원문 조회 Tool은 요청된 `meeting_id`가 이 목록에 포함된 경우에만 원문을 조회한다.

기존 ID가 있는 상태에서 새 회의록을 검색하면 사용자가 같은 스레드에서 다음 중 하나를 선택한다.

- **추가**: 기존 ID와 새 ID를 중복 없이 병합
- **대체**: 기존 ID를 버리고 새 ID 집합으로 교체

검색 결과가 없거나 검색이 취소·실패하면 기존 목록을 유지한다.

## 5. 녹화 Skill에 해당하는 백엔드 로직

### 5-1. 공통 원칙

회의 시작·일시정지·재개·종료 Skill은 에이전트가 보유한 Tool이 아니다. 전용 스레드의 명령 Trigger나 임베디드 녹화 바가 직접 호출하는 **백엔드 로직**이다.

각 Skill은 Runtime이 전달한 신뢰 가능한 현재 `state`를 매개변수 또는 실행 컨텍스트로 받고 다음을 수행한다.

```text
Trigger 또는 UI 요청
→ 녹화 Skill 백엔드 호출
→ 전달받은 state가 허용 상태인지 검사
→ 인증·생성자 권한·실제 회의 상태 검사
→ 기존 녹화 메서드 실행
→ 성공 또는 구조화된 거부·실패 결과 반환
→ 성공한 경우에만 오케스트레이터가 state 갱신
```

| 백엔드 Skill | 허용 `state` | 성공 후 State |
|---|---|---|
| 회의 시작 | `none` | `recording` |
| 회의 일시정지 | `recording` | `pause` |
| 회의 재개 | `pause` | `recording` |
| 회의 종료 | `recording`, `pause` | `stop` |

State 조건을 통과해도 인증·생성자 권한과 백엔드의 실제 회의 상태를 다시 검사한다. Agent State만으로 보안이나 실제 리소스 상태를 확정하지 않는다.

예시 성공 결과는 다음처럼 정규화할 수 있다.

```json
{
  "event": "MEETING_PAUSED",
  "status": "success",
  "next_state": "pause",
  "meeting_id": "meeting-123"
}
```

오케스트레이터는 이 결과를 받은 뒤에만 State를 변경한다. 사용자에게 자연어 안내가 필요할 때는 결과를 컨텍스트에 넣어 LLM이 응답하게 하고, 고정 UI 안내만 필요하면 LLM 호출을 생략할 수 있다.

## 6. Agent Tool 목록

### 6-1. 공통 원칙

Agent Tool은 LLM과 백엔드 로직 사이의 실행 인터페이스다.

1. Tool은 이름, Description, 입력·출력 Schema와 오류 형식을 가진다.
2. LLM은 어떤 Tool을 어떤 인자로 호출할지만 판단한다.
3. 인증, 권한, 입력 검증과 실제 비즈니스 로직은 Tool 뒤의 백엔드가 강제한다.
4. `state`와 인증 정보는 LLM이 인자로 만들지 않고 오케스트레이터가 정해진 형식으로 전달.
5. 오류는 재시도, 사용자 확인, 다른 Tool 선택, 중단을 구분할 수 있도록 구조화한다.
6. 쓰기 Tool에는 중복 실행 방지를 위한 멱등성 장치를 둔다.

세 Tool의 현재 역할과 실행 제약은 다음과 같다.

| Tool | 핵심 기능 | 주요 사전 조건 | State 영향 | Human in the Loop |
|---|---|---|---|---|
| **Tool 1 — 확정·공유** | 회의록을 확정하고 지정 채널에 공유 | `state="stop"`, 회의 생성자 | 성공 시 `share → none`, 실패 시 `stop` 유지 | 없음 |
| **Tool 2 — 검색·선택** | 접근 가능한 회의록을 검색하고 사용할 ID 확정 | 백엔드 접근 권한 필터 통과 | `authorized_meeting_ids` 추가·대체, `state` 변경 없음 | 후보 선택, 기존 ID 추가·대체 |
| **Tool 3 — 원문 조회** | 허용된 ID의 회의록 원문 조회 | ID가 `authorized_meeting_ids`에 포함 | 답변만 `messages`에 추가, `state` 변경 없음 | 없음 |

### 6-2. Tool 1 — 회의록 확정 및 공유

기존 회의록 확정·공유 백엔드 로직을 호출해 회의록을 확정하고 지정된 채널에 공유한다.

- `state="stop"`일 때만 실행한다.
- 백엔드에서 현재 사용자가 회의 생성자인지 검사한다.
- 성공하면 오케스트레이터가 `share`를 반영한 뒤 녹화 과정을 마치며 `none`으로 변경한다.
- 실패하면 `stop`을 유지하고 구조화된 오류를 반환한다.

### 6-3. Tool 2 — 관련 회의록 검색·선택

주제, 날짜 등의 조건으로 접근 가능한 회의록 후보를 검색하고 최종 ID 선택까지 하나의 Tool 흐름에서 처리한다. 별도의 ‘ID 가져오기 Tool’로 분리하지 않는다.

백엔드는 사용자가 다음 중 하나에 해당하는 회의록만 후보로 반환한다.

- 회의 생성자
- 회의 참여자
- 회의록이 공유된 채널의 구성원

| 후보 수 | 처리 |
|---|---|
| 0개 | 관련 회의록 없음 반환, 기존 ID 유지 |
| 1개 | 해당 후보를 바로 검증·선택 |
| 2개 이상 | 같은 스레드에서 Human in the Loop로 하나 이상 선택 |

선택된 ID가 최초의 권한 필터링 후보 집합에 포함되는지 백엔드가 다시 확인한다. 기존 `authorized_meeting_ids`가 있으면 같은 스레드에서 **추가 또는 대체**를 선택하게 하고, 검증된 결과만 State에 반영하도록 반환한다.

이 검색 흐름에는 지속적인 `search` State, `run_id`, 별도 검색 Subgraph가 필요하지 않다. 한 번의 요청 안에서 검색·선택·검증을 끝내고 Agent는 다음 입력을 기다린다. 검색은 `state`를 변경하거나 녹화 과정을 차단하지 않는다.

### 6-4. Tool 3 — 회의록 원문 조회

사용자의 질문에 필요한 회의록 원문을 ID로 조회한다.

- 요청된 ID가 `authorized_meeting_ids`에 포함되어 있는지 서버에서 검사한다.
- 포함된 ID의 원문만 가져온다.
- 목록에 없는 ID이면 `UNAUTHORIZED_MEETING_ID`를 반환한다.
- 검색 단계의 채널 권한 전체를 반복 조회하지는 않되, 허용 목록 검증은 항상 수행한다.

가져온 원문은 State의 `messages`나 Checkpoint, 별도 임시 Storage에 저장하지 않는다.

```text
시스템 지시
+ 필요한 회의록 원문
+ 현재 messages
= LLM 최종 컨텍스트
```

LLM이 생성한 답변만 `messages`에 추가하고 원문은 해당 호출이 끝나면 컨텍스트에서 제거한다. 이 질문 실행도 `state`를 변경하지 않는다.

## 7. 권한 및 실행 제약

각 Backend Skill과 Agent Tool 절에는 해당 기능을 이해하는 데 필요한 핵심 조건을 적고, 이 절에서는 전체 기능에 적용되는 **권한·실행 정책의 기준 정보**를 정리한다.

### 7-1. 녹화 제어

녹화 Skill 백엔드는 다음을 검사한다.

1. 전달받은 `state`가 요청 동작의 허용 상태인지
2. 인증된 사용자인지
3. 해당 회의의 생성자인지
4. 백엔드의 실제 회의 상태가 동작 가능한 상태인지

성공한 경우에만 녹화 메서드를 실행하고 성공 결과를 반환한다. LLM이나 `authorized=true/false` 같은 Agent State에 권한 판단을 맡기지 않는다.

### 7-2. 확정·공유

Tool 1은 `state="stop"`과 회의 생성자 권한을 백엔드에서 검사한다. 둘 중 하나라도 충족하지 않으면 확정·공유를 실행하지 않는다.

### 7-3. 검색·선택

Tool 2는 조회 단계에서 사용자에게 접근 권한이 있는 회의록만 반환한다. 권한 없는 원문을 LLM에 전달한 뒤 제거하는 방식을 사용하지 않는다.

후보가 여러 개일 때의 선택과 기존 ID의 추가·대체는 같은 스레드의 Human in the Loop로 처리한다. 별도의 실행 식별자인 `run_id`는 두지 않는다.

### 7-4. 원문 조회

Tool 3은 입력된 ID가 `authorized_meeting_ids`에 포함되어 있는지 백엔드에서 확인한다. 이 목록은 권한 자체를 LLM에 맡기는 값이 아니라, 앞선 검색·선택 과정에서 서버가 검증한 결과를 다음 조회에 전달하는 임시 허용 목록이다.

### 7-5. Human in the Loop

Human in the Loop는 관련 회의록 검색·선택 Tool 안에서만 사용한다.

| 상황 | 사용자 행동 | 재개 후 처리 |
|---|---|---|
| 접근 가능한 후보가 2개 이상 | 필요한 회의록을 하나 이상 선택 | 후보 집합 포함 여부 재검증 |
| 기존 ID가 있는데 새 ID가 확정됨 | 기존 목록에 추가 또는 새 목록으로 대체 | 검증된 ID 목록 병합 또는 교체 |

사용자 선택을 기다리는 동안 같은 실행을 재개하기 위해 런타임 내부 스냅샷은 필요할 수 있다. 그러나 별도의 `run_id`나 지속적인 검색 State는 만들지 않는다.

## 8. Checkpoint와 Compact

### 8-1. Checkpoint

Checkpoint는 별도의 업무 상태가 아니라 **특정 시점의 Agent State를 저장한 스냅샷**이다.

설계 다이어그램에서는 각 업무 단위가 끝나 최종 결과와 State 변경이 반영된 지점에 **업무 경계 Checkpoint**를 표시한다.

| 업무 단위 | Checkpoint에 반영되는 핵심 결과 |
|---|---|
| 회의 시작 | 성공 시 `recording`, 실패 시 기존 상태 |
| 녹화 제어 1회 | `pause`, `recording`, `stop` 또는 실패 전 상태 |
| 회의록 확정·공유 | 성공 시 `share → none`, 실패 시 `stop` |
| 회의록 검색·선택 | 선택된 ID의 추가·대체 결과 또는 기존 ID 유지 |
| 회의록 질문 1회 | 질문과 답변, 기존 `authorized_meeting_ids` 유지 |

검색과 질문에 별도의 지속 State가 없다는 사실은 Checkpoint를 남기지 않는다는 뜻이 아니다. 요청이 끝난 뒤 변경된 `messages`와 `authorized_meeting_ids`를 기존 Agent State에 반영할 수 있다.

Human in the Loop로 사용자 선택을 기다릴 때는 LangGraph checkpointer의 **런타임 내부 스냅샷**이 필요할 수 있다. 이는 업무 완료 지점에 표시하는 업무 경계 Checkpoint와 구분한다.

Tool 실행 중 오류가 발생하면 마지막 정상 업무 경계 Checkpoint를 기준으로 해당 업무를 재시도할 수 있도록 복구 오케스트레이션을 구현한다. Checkpoint 자체가 자동 복구를 수행하지는 않는다.

```text
오류 감지
→ 오류 유형과 재시도 가능 여부 판단
→ 마지막 정상 Checkpoint 선택
→ State 복원
→ 실패한 업무 단위 재실행
```

쓰기 작업은 State만 되돌려도 이미 실행된 백엔드 작업이 취소되지 않으므로 멱등성 키나 버전 검증 등 중복 실행 방지 장치가 필요하다.

브라우저를 나갔다가 나중에 중단 지점부터 같은 Graph 실행을 복구하는 기능은 현재 범위에 포함하지 않는다. 사용자는 필요할 때 에이전트를 다시 호출해 검색하거나 질문할 수 있다.

### 8-2. Compact

LLM의 컨텍스트 윈도우에는 한계가 있으므로 `messages`가 전체 컨텍스트 윈도우의 약 50%에 도달하면 Compact를 실행한다. 실제 기준은 모델과 토큰 사용량에 따라 조정한다.

회의록 원문은 `messages`에 누적하지 않으므로 Compact 대상이 아니다. 원문은 질문 시점에 ID로 조회하여 최종 컨텍스트에만 임시로 조립한다.

## 9. 추후 결정 사항

- 회의록 원문 조회에 사용할 실제 식별자와 조회 방식
- 여러 회의록 중 질문과 관련된 원문을 자동 선별할 방식
- 사용하는 모델과 실제 토큰 사용량에 따른 Compact 기준
- 임베디드 녹화 바와 Agent State 사이의 구체적인 이벤트 동기화 방식
- Tool별 입력·출력 Schema, 오류 코드, 재시도 횟수와 중단 기준

## 핵심 정리

> 회의록 에이전트는 `messages`, `authorized_meeting_ids`, `state`를 가진 단일 에이전트다. **회의 녹화만 지속 State로 관리**하고, 회의록 검색과 질문은 요청 시 Tool을 실행한 뒤 끝나는 일회성 업무로 처리한다. 회의 시작·일시정지·재개·종료 Skill은 Agent 내부 Tool이 아니라 State·권한·실제 회의 상태를 검사하고 기존 녹화 메서드를 실행하는 백엔드 로직이며, 성공 결과를 받은 오케스트레이터가 `state`를 갱신한다. Agent에는 확정·공유, 검색·선택, 원문 조회의 세 Tool 인터페이스만 등록한다. 검색 후보가 여러 개이거나 기존 ID의 추가·대체가 필요하면 같은 스레드에서 Human in the Loop로 처리하며 `run_id`는 사용하지 않는다. 권한과 실제 실행 여부는 항상 백엔드가 강제하고, 회의록 원문은 호출 시점의 최종 컨텍스트에만 조립한다.
