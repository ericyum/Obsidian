# Tool 계층 확장 및 State 관리 검토안

이 문서는 현재 회의록 에이전트에서 **Tool 기능 영역의 지속 데이터 소유와 저장 책임을 Agent 하네스에서 분리하는 방안**을 검토한다. Main Agent와 여러 전문 Agent를 연결하는 구조는 장기 확장 가능성으로만 구분해 다룬다.

> [!warning] 문서 상태 — 제안·검토 단계
> 이 문서의 내용, 특히 **Tool 계층이 별도 저장소의 State를 직접 조회·검사·갱신하는 구조는 아직 확정된 사안이 아니다.**
>
> 현재 구현 기준은 [[2-1. 회의록 에이전트 현재 구현 상세 설계]]를 따른다. 실제 녹화 `recording_state`는 이미 구축된 녹화 임베디드 상단바 모달이 소유하며 이 검토안의 Tool State 분리 대상이 아니다. 이 검토안이 팀 결정으로 확정되면 현재 구현 문서의 `authorized_meeting_ids` 소유권과 책임 경계를 함께 개정한다.

> [!important] 이 문서에서 말하는 Tool State
> 이 문서의 `Tool State`, `MeetingToolState`와 State Repository는 `authorized_meeting_ids`처럼 Tool 계층이 다음 실행에도 사용해야 하는 **지속 데이터와 그 저장 계약**을 뜻한다. 검색·질문 Agent Graph의 개념적 State인 `none`, `search`, `question`이나 Search·Question Subgraph 내부의 제어 State를 Repository에 저장하자는 의미가 아니다.

## 1. Tool State 분리를 검토하는 이유

현재 회의록 에이전트는 단일 Agent 서버에서 LLM·Graph·하네스와 Tool을 함께 운영한다. 이 단계에서 검토하는 핵심은 Main Agent 구현이 아니라, Tool 1과 Tool 2가 함께 사용하는 `authorized_meeting_ids`의 조회·검증·갱신 책임을 어디에 둘 것인가다.

Agent 하네스가 Tool별 지속 데이터의 의미와 모든 검사·갱신 규칙까지 직접 알게 되면 Tool이 늘어날수록 중앙의 조건·분기 코드가 복잡해진다. 이를 줄이기 위해 Tool은 자신의 기능에 필요한 **지속 데이터 검사·권한 검사·백엔드 메서드 실행**을 Tool 계층의 책임 경계 안에서 처리하고, Agent 하네스에는 구조화된 결과만 반환하는 방향을 검토한다.

```text
회의록 Agent의 LLM
→ Tool 이름·Description·Schema를 보고 호출 결정

회의록 Agent의 하네스
→ 선택된 Tool 인터페이스 실행

Tool 계층
→ Tool 전용 State 조회·검사·갱신
→ 권한과 실제 리소스 상태 검사
→ 백엔드 메서드 실행
→ 구조화된 결과 반환
```

장기적으로 Main Agent와 여러 전문 Agent를 연결하게 되면 같은 책임 경계를 재사용할 수 있다. 이 경우 Tool 내부에서 전문 Agent에 업무를 위임하는 구조도 고려할 수 있지만, 이는 **현재 회의록 Agent의 확정 구현이 아니라 향후 확장 예시**다.

> **핵심 설계 의도:** 현재 검토 대상은 회의록 Agent의 Tool State 분리다. Main Agent·전문 Agent 위임은 이 경계를 장기적으로 재사용할 수 있다는 확장 가능성으로만 다룬다.

## 2. 전역 State 최소화 원칙

Tool이 추가될 때마다 각 Tool의 처리 단계를 전역 State에 저장하면 여러 State가 서로의 실행 조건과 갱신 방식에 영향을 주게 된다. 그 결과 **State 조합과 의존 관계**가 늘어나 Condition, Reducer, Checkpoint와 동시 실행 제어의 유지보수가 복잡해진다.

따라서 전역 State에는 **다음 요청에서도 유지되어야 하며 이후 행동의 허용 여부에 영향을 주는 값만 저장**한다. Tool 실행 중에만 필요한 후보 목록과 중간 결과는 Tool 내부의 지역·임시 데이터로 관리하고, 원문이나 데이터는 백엔드나 별도의 DB에 둔다.

현재 구현 기준은 다음과 같다.

```text
Agent 하네스
├─ ScratchPad
├─ authorized_meeting_ids
└─ recording_modal_status

녹화 임베디드 상단바 모달
└─ recording_state
```

검색·질문에는 `none`, `search`, `question`이라는 개념적 Graph State가 있지만 같은 이름의 지속 코드 변수는 두지 않는다. 실제 녹화 `recording_state`도 Agent 전역 State에 중복 저장하지 않고 모달이 관리한다.

> **핵심:** 전역 State의 필드 수를 무조건 줄이는 것이 아니라, **지속성과 Agent 실행에 반드시 필요한 값만 남겨 회의록 Agent의 하네스를 가볍게 유지**한다.

## 3. Tool 기능 영역의 State 소유 제안

현재 구현에서는 `ScratchPad`, `authorized_meeting_ids`, `recording_modal_status`를 Agent 하네스가 관리한다. 이 가운데 회의록 검색·조회 Tool이 함께 사용하는 `authorized_meeting_ids`를 Tool 계층의 별도 저장소로 분리하는 방안이 제안되었다.

실제 녹화 `recording_state`는 이미 녹화 임베디드 상단바 모달이 소유하므로 Tool State Repository로 옮길 대상에서 제외한다. `recording_modal_status`는 모달이 보낸 정상·오류 신호를 Agent가 보관하는 값이므로, 계속 Agent State에 저장할지 요청 시 모달 상태를 조회할지는 별도로 검토한다.

회의 녹화는 LLM Agent가 기능을 판단하는 과정이 아니라 고정 Trigger·모달·백엔드가 실행하는 결정적 Workflow이므로, 이 문서의 Tool 계층 확장 대상에도 포함하지 않는다.

여기서 지속 데이터를 분리한다는 것은 저장 위치만 옮기는 것이 아니다. **Tool 계층이 `authorized_meeting_ids`의 의미와 검증·갱신 규칙까지 소유하고, Agent 하네스에는 구조화된 실행 결과만 반환**해야 한다.

```text
회의록 Agent 하네스
├─ ScratchPad
├─ recording_modal_status
└─ 사용자 의도에 따라 Tool 호출

Tool 계층
→ 전용 영속 저장소에서 authorized_meeting_ids 조회
→ 권한·선택 ID·실제 리소스 상태 검사
→ 검색 또는 원문 조회 실행
→ 성공 시 authorized_meeting_ids 갱신
→ 구조화된 결과만 Agent에 반환

녹화 임베디드 상단바 모달
→ recording_state를 별도로 관리·갱신
```

## 4. 방안 1 — Agent 서버와 MCP Tool·State 서버 분리

기존의 단일 Agent 서버에서 `tools.py`와 Tool 전용 State 관리 부분을 분리하여 별도의 MCP 서버로 운영한다.

```text
회의록 Agent 서버
├─ LLM
├─ Graph·하네스
├─ ScratchPad
└─ recording_modal_status
        │
        ▼
MCP Tool·State 서버
├─ tools.py
├─ authorized_meeting_ids Schema
├─ 권한·선택 ID 검사와 백엔드 실행
└─ 영속 저장소 Read·Write

녹화 임베디드 상단바 모달
└─ recording_state
```

**장점**

- Agent 하네스와 Tool·State 실행 책임이 프로세스 수준에서 명확히 분리된다.
- Tool 코드에서는 `authorized_meeting_ids`와 같은 논리적 변수명으로 State를 조회·갱신할 수 있다.
- Tool과 State 규칙을 Agent 서버와 독립적으로 수정·배포·확장할 수 있다.
- Agent 서버에는 Tool 전용 저장소의 직접 접근 권한을 부여하지 않아도 된다.
- 향후 다른 Agent가 같은 Tool 계층을 사용해야 할 때 재사용하기 쉽다.

**한계**

- Agent 서버 외에 MCP 서버를 추가로 배포·운영해야 한다.
- Tool 호출마다 네트워크 통신이 발생한다.
- MCP 서버 장애가 모든 Tool 실행에 영향을 줄 수 있다.
- 인증, 버전 호환성, 로그·모니터링과 장애 복구 대상을 별도로 관리해야 한다.

**적합한 상황**

- Tool과 Agent를 서로 독립적으로 배포하거나 확장해야 할 때
- Tool 계층을 여러 Agent가 공통으로 사용할 가능성이 클 때
- 프로세스 수준의 강한 책임·권한 격리가 필요할 때
- 별도 서버의 운영 비용보다 장기적인 재사용성과 독립성이 중요할 때

## 5. 방안 2 — 단일 Agent 서버와 명시적 State Schema·Repository

Agent 서버 하나를 유지하되, 배포 과정에서 `tools.py`의 소스 위치를 탐색하여 State 변수를 자동 추출하지 않는다. 대신 State Schema와 저장소 접근 계약을 명시적으로 정의하고, Tool은 Repository 인터페이스를 통해 별도 영속 저장소에 접근한다.

```python
class MeetingToolState:
    authorized_meeting_ids: list[str]

class MeetingStateRepository:
    def load(self, user_id, thread_id): ...
    def save(self, user_id, thread_id, meeting_state): ...
```

```text
회의록 Agent 서버 하나
├─ LLM·Graph·하네스
├─ ScratchPad
├─ recording_modal_status
└─ tools.py
   ├─ MeetingToolState
   ├─ 권한·선택 ID 검사와 백엔드 실행
   └─ MeetingStateRepository
              │
              ▼
       별도 영속 저장소

녹화 임베디드 상단바 모달
└─ recording_state
```

Repository는 DB 테이블, Redis Key와 저장 위치를 Tool 코드에서 감추며, Tool은 `meeting_state.authorized_meeting_ids`처럼 논리적인 변수명으로 State를 사용한다.

**장점**

- 별도의 MCP 서버 없이 Agent 서버 하나만 운영한다.
- 네트워크를 통한 MCP 호출이 없어 현재 구조가 단순하다.
- 소스 파일 위치를 찾아 State 변수를 추출하는 방식보다 변수 변경과 파일 이동에 안전하다.
- Tool은 저장소의 물리적 위치가 아니라 명시적인 State 객체와 변수명으로 작업한다.
- Repository를 교체하거나 테스트용 구현으로 바꾸기 쉽다.
- 나중에 Tool 계층을 MCP 서버로 분리하더라도 State Schema와 Repository 계약을 재사용할 수 있다.

**한계**

- Agent 서버와 Tool 계층의 배포 수명주기가 여전히 결합되어 있다.
- Tool 코드나 State 규칙을 변경하면 Agent 서버를 다시 배포해야 한다.
- 여러 Agent 서버에서 같은 Tool을 사용하면 코드와 State 규칙이 복제될 수 있다.
- 프로세스 수준의 장애·권한 격리는 MCP 분리 방식보다 약하다.
- Repository, State Schema와 저장소 마이그레이션을 명시적으로 관리해야 한다.

**적합한 상황**

- 현재처럼 회의록 Agent 하나가 Tool을 전용으로 사용하는 단계
- Tool을 독립적으로 확장할 필요보다 빠른 구현과 단순한 운영이 중요한 단계
- 별도 MCP 서버 운영 비용을 아직 감수할 필요가 없을 때
- 향후 MCP 분리를 고려하되 현재는 단일 서버로 시작하려 할 때

## 6. 방안 비교와 현재 권고안

| 판단 기준 | 방안 1. MCP 서버 분리 | 방안 2 개선형. 단일 서버 + Repository |
|---|---|---|
| 운영 서버 수 | 2개 | 1개 |
| Tool 호출 | 네트워크 호출 | 같은 서버 내부 호출 |
| Agent·Tool 독립 배포 | 용이 | 어려움 |
| 프로세스·권한 격리 | 강함 | 상대적으로 약함 |
| 현재 구현 난이도 | 높음 | 낮음 |
| 여러 Agent의 Tool 재사용 | 유리 | 코드 복제 가능 |

현재 회의록 Agent 하나를 빠르게 구현하는 단계에서는 **방안 2 개선형**이 적합하다. 명시적인 `MeetingToolState`와 `MeetingStateRepository`를 사용하면 별도 서버 없이도 Tool이 `authorized_meeting_ids`의 조회·검증·갱신 책임을 맡고, 저장 위치를 직접 찾는 문제도 피할 수 있다.

향후 Tool 계층을 독립적으로 배포·확장하거나 여러 Agent가 함께 사용해야 한다면 **방안 1**로 전환한다. 이때 방안 2에서 정의한 State Schema와 Repository 계약을 MCP 서버로 이동하면 되므로 처음부터 두 방식의 계약을 동일하게 유지하는 것이 좋다.

> [!note] 검토 단계의 권고
> **현재 권고안:** 현재는 방안 2 개선형을 우선 검토하고, 독립 배포·재사용·강한 격리의 필요가 커지는 시점에 방안 1로 전환한다. 어느 방식을 선택하더라도 Tool Repository가 소유하기로 확정된 지속 데이터만 DB·Redis 같은 영속 저장소에 보관한다. `authorized_meeting_ids`는 사용자·스레드 키로 허용 ID 집합을 격리하고, 개념적 Graph State는 같은 이름의 영속 필드로 만들지 않는다. Agent 하네스는 Tool Repository 내부 데이터를 직접 판단하거나 수정하지 않고 구조화된 Tool 결과와 Repository 참조·버전을 사용한다. 이 방안을 확정하면 [[2-1. 회의록 에이전트 현재 구현 상세 설계]]의 `authorized_meeting_ids` 소유권과 갱신 주체를 함께 변경해야 한다.

### 6-1. 제안 채택 시 Repository와 Agent Checkpoint의 일관성

> [!warning] 적용 조건
> 이 절은 방안 1 또는 방안 2 개선형을 실제로 채택해 `authorized_meeting_ids`를 Tool Repository로 옮길 때만 적용한다. 현재 [[2-1. 회의록 에이전트 현재 구현 상세 설계]]에는 적용하지 않는다.

제안이 채택되면 Tool Repository의 `authorized_meeting_ids`와 Agent의 `ScratchPad`·Checkpoint가 서로 다른 저장 경계에 놓인다. 따라서 저장 위치만 옮기는 것으로 끝내지 않고 다음 정책을 함께 정해야 한다.

- Tool Repository의 ID 갱신이 성공한 뒤에만 Search Subgraph가 다음 응답 생성 단계로 진행하며, S3가 `SEARCH_RESPONSE_READY`를 반환한다.
- Agent Checkpoint에는 Tool Repository의 사용자·스레드 키와 State 버전 또는 스냅샷 참조를 기록한다.
- 동일 요청을 재시도해도 ID 추가·대체가 중복 반영되지 않도록 멱등성 키나 요청 버전을 사용한다.
- Repository 저장은 성공했지만 Agent Checkpoint 저장이 실패한 경우의 재조회·재적용·보상 규칙을 정의한다.
- Checkpoint 복구 시 기록된 Repository 버전과 현재 버전이 다르면 자동 덮어쓰기하지 않고 충돌 처리 규칙을 적용한다.

이 구조가 확정되면 1-2·2-1·3·4 문서에서 `authorized_meeting_ids`를 Agent Checkpoint에 직접 포함한다고 설명한 부분도 Repository 참조·버전 기반 설명으로 함께 변경해야 한다.

## 7. 확정 전에 함께 결정할 사항

- `authorized_meeting_ids`의 실제 저장소와 사용자·스레드별 격리 키
- 같은 ID 목록을 동시에 추가·대체할 때의 잠금·버전·멱등성 정책
- Agent Tool 1과 Tool 2가 같은 허용 ID 목록을 공유하는 방법
- Agent 하네스와 Tool 계층 사이의 결과 Schema
- Tool Repository와 Agent Checkpoint 사이의 커밋 순서·버전·멱등성·복구 정책
- `recording_modal_status`를 Agent State에 저장할지 실행 시 모달에서 조회할지
- MCP 서버로 분리해야 하는 구체적인 전환 조건
- 현재 `authorized_meeting_ids`를 새 저장 구조로 옮기는 마이그레이션 방식

## 핵심 정리

> 이 문서의 핵심은 현재 구조를 즉시 변경하는 것이 아니라, 기능과 Agent가 늘어날 때 **중앙 하네스에 Tool별 지속 데이터 규칙과 하위 실행 순서를 집중시키지 않는 확장 방향**을 검토하는 것이다. 실제 녹화 `recording_state`는 모달이 계속 소유하며, 검토 대상은 주로 `authorized_meeting_ids`의 Tool 계층 분리와 `recording_modal_status`의 저장 방식이다. 현재 단계에서는 단일 서버와 명시적 State Schema·Repository 방식이 권고안이지만 확정 사항은 아니다.
