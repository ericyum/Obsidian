# 회의록 에이전트 상세 설계

이 문서는 회의록 에이전트의 설계 가정과 **녹화 Skill·Agent Tool의 구분**, State, Checkpoint, 권한 및 실행 제약을 정의한다.

전체 업무 워크플로우와 세부 Graph는 [[1. 회의록 에이전트 워크플로우 graph 정의]]에서 다룬다.

## 1. 설계 시 가정 사항

### 1-1. 단일 에이전트로 구성

회의록 에이전트가 수행하는 판단과 Tool 흐름이 비교적 단순할 것으로 예상되므로 하나의 LLM이 여러 Tool을 선택하는 **단일 에이전트**로 구성한다.

### 1-2. 사용자별 전용 스레드에서 독립적으로 실행

회의 생성·진행·공유와 공유 회의록의 검색·질의는 하나의 Agent 실행으로 이어지는 과정이 아니다. 회의 생성자와 공유받은 사용자는 각각 회의 에이전트를 호출해 생성된 자신의 전용 스레드에서 필요한 업무를 시작한다.

### 1-3. 두 종류의 실행 경로를 구분

회의록 업무에는 성격이 다른 두 실행 경로가 있다.

- **회의 녹화 과정**: 일시정지·재개·종료처럼 다음 행동의 허용 여부가 이전 상태에 의존하므로 `recording_state`로 지속 관리한다.
- **회의록 검색·질문 과정**: 검색 한 번 또는 질문 한 번을 처리하면 끝나는 일회성 실행이다. 별도의 `search`, `question` State를 만들지 않는다.

두 경로는 하나의 전역 업무 State를 차지하기 위해 경쟁하지 않는다. 따라서 회의가 녹화 중이더라도 사용자가 기존 회의록을 검색하거나, 이미 선택한 회의록을 바탕으로 질문할 수 있다.

### 1-4. 기존 ZEN AI 백엔드를 재사용

ZEN AI의 회의록 기능과 백엔드 로직은 이미 구현되어 있다고 가정한다.

- 회의 시작·일시정지·재개·종료는 **녹화 Skill에 해당하는 백엔드 로직**이 수행한다.
- 회의록 확정·공유, 검색·선택, 원문 조회는 **Agent Tool 인터페이스**를 통해 기존 백엔드 로직을 호출한다.

녹화 Skill과 Agent Tool은 모두 실제 비즈니스 로직을 백엔드에서 실행하지만, 에이전트와의 관계가 다르다.

```text
녹화 Trigger·UI
→ 녹화 Skill에 해당하는 백엔드 로직 직접 실행
→ 성공 결과를 받은 오케스트레이터가 recording_state 갱신

LLM의 Tool 선택
→ Agent에 등록된 Tool 인터페이스 호출
→ Tool 뒤의 백엔드 로직 실행
→ 결과를 LLM 컨텍스트와 State에 필요한 범위로 반영
```

녹화 Skill은 Agent 내부에 코딩되어 LLM이 선택하는 Tool이 아니다. Tool 역시 비즈니스 로직 그 자체가 아니라, LLM이 백엔드 기능을 안전하게 호출할 수 있도록 이름·Description·입출력 Schema·오류 형식을 제공하는 **실행 인터페이스**다.

### 1-5. 다중 에이전트 확장을 고려한 Tool 내부 위임 구조

현재 회의록 에이전트는 단일 에이전트로 구성하지만, 장기적으로는 **Main Agent를 중심으로 여러 전문 Agent를 연결하는 구조**로 확장하는 것을 고려한다.

모든 Tool의 실행 순서와 Agent 간 전달 과정을 Main Agent의 오케스트레이터에 직접 작성하면, Agent와 Tool이 늘어날수록 중앙의 조건·분기 코드가 복잡해진다. 중앙 오케스트레이터가 하위 Agent들의 세부 실행 순서까지 모두 알아야 하므로 기능 추가와 변경이 다른 흐름에도 영향을 주어 유지보수가 어려워질 수 있다.

이를 줄이기 위해 각 Tool은 자신의 기능에 필요한 **State 검사·권한 검사·백엔드 메서드 실행을 Tool 뒤의 백엔드 로직에 캡슐화**한다. 향후 전문 Agent의 판단이 필요한 기능은 같은 경계 안에서 해당 Agent를 호출하고 결과를 Tool의 출력 Schema로 반환하는 **Tool 내부 위임 구조**로 확장한다.

```text
Main Agent의 LLM
→ Tool 이름·Description·Schema를 보고 호출 결정

Main Agent의 오케스트레이터
→ 선택된 Tool 인터페이스 실행

Tool 뒤의 백엔드 로직
→ State·권한 검사
→ 실제 메서드 실행
→ 필요하면 전문 Agent의 LLM에 업무 위임
→ 전문 Agent가 자신의 Tool을 이용해 처리
→ 최종 결과를 최초 Tool의 결과로 반환
```

이 구조에서는 Main Agent의 오케스트레이터가 Tool의 **기능과 입출력 계약**만 알면 된다. Tool 내부에서 어떤 전문 Agent와 하위 Tool이 실행되는지, 그 세부 순서가 무엇인지는 알 필요가 없다. 따라서 중앙 오케스트레이터에 모든 업무 순서를 집중시키지 않고 각 기능의 책임 경계 안으로 분산할 수 있다.

> **핵심 설계 의도:** 현재는 회의록 단일 에이전트로 시작하되, Tool을 단순 메서드 호출이 아닌 확장 가능한 실행 경계로 설계한다. 장기적으로는 Tool 내부에서 전문 Agent에 업무를 위임하고 그 결과를 반환하게 하여, Main Agent의 오케스트레이터를 변경하지 않고도 다중 에이전트 기능을 추가할 수 있도록 한다.

#### 1-5-1. 전역 State 최소화

Tool이 추가될 때마다 각 Tool의 처리 단계를 전역 State에 저장하면 여러 State가 서로의 실행 조건과 갱신 방식에 영향을 주게 된다. 그 결과 **State 조합과 의존 관계**가 늘어나 Condition, Reducer, Checkpoint와 동시 실행 제어의 유지보수가 복잡해진다.

따라서 전역 State에는 **다음 요청에서도 유지되어야 하며 이후 행동의 허용 여부에 영향을 주는 값만 저장**한다. Tool 실행 중에만 필요한 후보 목록, 중간 결과와 처리 단계는 **Tool 내부의 지역·임시 데이터**로 관리하고, 원문이나 대용량 데이터는 백엔드에 두며 State에는 필요한 ID만 저장한다.

현재 회의록 에이전트는 이러한 기준에 따라 `messages`, `authorized_meeting_ids`, `recording_state`만 전역 State로 관리하고, `search`와 `question` 같은 단발성 처리 상태는 두지 않는다.

> **핵심:** 전역 State의 필드 수를 무조건 줄이는 것이 아니라, **지속성과 라우팅에 반드시 필요한 값만 남겨 Main Agent의 오케스트레이터를 가볍게 유지**한다.

#### 1-5-2. Tool 전용 State 분리 방안 검토

장기적으로 Agent와 Tool이 늘어나는 상황에 대비해, Main Agent의 공유 State에는 `messages`만 두고 `authorized_meeting_ids`, `recording_state`처럼 특정 기능에 종속된 값은 **각 Agent 또는 Tool의 전용 공간으로 분리**하는 방안을 검토한다.

`messages`는 오케스트레이터가 시스템 지시와 대화 기록을 조립해 LLM에 전달하는 핵심 값이므로 Main Agent가 관리한다. 반면 회의록 기능에서만 사용하는 값은 회의록 Tool 뒤의 백엔드가 직접 읽고 쓰게 하여 Main Agent의 오케스트레이터가 하위 기능의 세부 State를 알지 않도록 한다.

```python
MainAgentState = {
    "messages": [...],
}

MeetingToolState = {
    "authorized_meeting_ids": ["meeting-123"],
    "recording_state": "recording",
}
```

```text
Main Agent
→ messages를 이용해 Tool 호출 판단
→ 회의록 Tool 호출

회의록 Tool 뒤의 백엔드
→ 자신의 전용 State 조회
→ State·권한 검사와 실제 메서드 실행
→ 전용 State 갱신
→ 필요한 결과만 Main Agent에 반환
```

이 구조를 구현하기 위해 다음 두 방안이 제기되었다.

**방안 1. Tool별 MCP 서버를 통한 Read·Write**

`tools.py`에 해당하는 MCP 서버를 두고, Tool이 전용 State를 조회·갱신하는 인터페이스를 제공한다.

```text
Main Agent
→ MCP Tool 호출
→ MCP 서버가 Tool 전용 State Read·Write
→ 검사·실행 결과 반환
```

- Agent와 Tool의 실행 경계를 분리할 수 있다.
- 여러 Agent가 동일한 Tool 기능을 재사용하기 쉽다.
- 인증, 사용자·스레드별 격리와 Read·Write Schema를 서버에서 강제할 수 있다.
- MCP 서버의 메모리 변수만 사용하면 재시작 시 State가 사라지므로, 실제 운영에서는 DB·Redis 등의 영속 저장소와 연결해야 한다.

**방안 2. 배포 시 Tool 정의를 정적 파일로 포함**

Agent 서버를 배포할 때 `tools.py`, TXT 또는 `config.py`를 함께 복사하여 Tool의 정의와 처리 규칙을 로컬에 포함하는 방식이다.

- Tool Description, Schema, 고정 정책과 기본 설정처럼 **실행 중 변경되지 않는 정보**를 배포하기에 적합하다.
- 별도의 Tool 서버 없이 Agent 서버 안에서 바로 읽을 수 있어 구조가 단순하다.
- `recording_state`와 `authorized_meeting_ids`처럼 실행 중 계속 바뀌는 값은 정적 설정과 구분해야 한다.
- 변경되는 State를 파일이나 `tools.py`의 전역 변수에 직접 저장하면 다중 서버 간 값 불일치, 동시 쓰기 충돌과 서버 재시작 시 유실 문제가 발생할 수 있으므로 운영 환경에서는 별도의 영속 저장소가 필요하다.

| 구분 | 정적 파일에 적합 | 전용 State 저장소에 적합 |
|---|---|---|
| Tool Description·Schema | O | 선택 사항 |
| 고정 정책·기본 설정 | O | 선택 사항 |
| `recording_state` | X | O |
| `authorized_meeting_ids` | X | O |
| 사용자·스레드별 실행 값 | X | O |

> **검토 결론:** Tool 전용 State를 Main Agent의 공유 State에서 분리한다는 방향은 타당하다. 다만 정적 파일은 Tool 정의와 고정 설정을 배포하는 용도로 사용하고, 실행 중 변경되는 State는 MCP 서버 또는 Tool 백엔드가 DB·Redis 같은 영속 저장소를 통해 Read·Write하도록 구성하는 것이 안전하다. 이 방안을 채택하면 아래의 Agent State 정의와 `recording_state` 갱신 주체도 함께 변경해야 하므로 현재는 확정안이 아닌 검토안으로 둔다.

## 2. State 설계

### 2-1. State 구성

```python
RecordingState = Literal[
    "none", "recording", "pause", "stop", "share",
]

class MeetingAgentState(TypedDict):
    messages: list
    authorized_meeting_ids: list[str]
    recording_state: RecordingState
```

| 필드 | 역할 |
|---|---|
| `messages` | 사용자 요청, LLM 응답, Tool 결과, Human in the Loop 선택 결과 등 대화 기록 |
| `authorized_meeting_ids` | 검색 Tool에서 권한과 후보 검증을 거쳐 선택된 회의록 ID의 서버 관리 허용 목록 |
| `recording_state` | 현재 회의 녹화 과정의 지속 상태 |

`recording_state`는 다음 의미를 가진다.

| 값 | 의미 | 설정 시점 |
|---|---|---|
| `none` | 진행 중인 녹화 과정이 없음 | 최초 State 생성 시 또는 확정·공유가 끝난 뒤 |
| `recording` | 회의 녹화 중 | 회의 시작 또는 재개 백엔드 성공 후 |
| `pause` | 녹화 일시정지 | 일시정지 백엔드 성공 후 |
| `stop` | 녹화 종료, 확정·공유 대기 | 종료 백엔드 성공 후 |
| `share` | 회의록 확정·공유 성공 | 확정·공유 성공 결과를 반영하는 시점 |

대표 전이는 다음과 같다.

```text
none → recording ↔ pause → stop → share → none
```

`none`은 에이전트가 꺼진 상태가 아니라 **진행 중인 녹화가 없는 상태**다. 회의록 검색과 질문은 `recording_state`를 변경하지 않는다.

### 2-2. State 갱신 주체

녹화 Skill이나 Tool이 State를 직접 수정하지 않는다. 백엔드가 성공 또는 실패 결과를 반환하면 **오케스트레이터가 결과를 검증하고 State를 갱신**한다.

```text
백엔드 실행 성공
→ 정규화된 성공 결과 반환
→ 오케스트레이터가 State 갱신
→ 필요할 때 결과를 LLM 컨텍스트에 추가

백엔드 실행 거부·실패
→ 기존 State 유지
→ 구조화된 오류 결과 반환
```

LLM은 State 값을 임의로 생성하거나 수정하지 않는다. 실제 녹화 상태와 권한의 최종 진실의 원천은 백엔드이며, `recording_state`는 성공한 백엔드 결과를 Agent 실행에 반영한 값이다.

### 2-3. `authorized_meeting_ids`

회의록 검색·선택 Tool은 백엔드 권한 필터를 통과한 후보 안에서 최종 선택된 ID만 `authorized_meeting_ids`에 반영하도록 결과를 반환한다. 실제 State 갱신은 오케스트레이터가 담당한다.

```python
State = {
    "messages": [...],
    "authorized_meeting_ids": ["meeting-123", "meeting-456"],
    "recording_state": "recording",
}
```

이 예시처럼 녹화 중에도 기존 회의록 ID가 유지될 수 있다. 검색·질문과 녹화 상태는 서로 다른 관심사이므로 한쪽이 다른 쪽을 막지 않는다.

`authorized_meeting_ids`는 LLM이나 사용자가 직접 수정할 수 없다. 원문 조회 Tool은 요청된 `meeting_id`가 이 목록에 포함된 경우에만 원문을 조회한다.

기존 ID가 있는 상태에서 새 회의록을 검색하면 사용자가 같은 스레드에서 다음 중 하나를 선택한다.

- **추가**: 기존 ID와 새 ID를 중복 없이 병합
- **대체**: 기존 ID를 버리고 새 ID 집합으로 교체

검색 결과가 없거나 검색이 취소·실패하면 기존 목록을 유지한다.

## 3. Checkpoint와 Compact

### 3-1. Checkpoint

Checkpoint는 별도의 업무 상태가 아니라 **특정 시점의 Agent State를 저장한 스냅샷**이다.

설계 다이어그램에서는 각 업무 단위가 끝나 최종 결과와 State 변경이 반영된 지점에 **업무 경계 Checkpoint**를 표시한다.

| 업무 단위 | Checkpoint에 반영되는 핵심 결과 |
|---|---|
| 회의 시작 | 성공 시 `recording`, 실패 시 기존 상태 |
| 녹화 제어 1회 | `pause`, `recording`, `stop` 또는 실패 전 상태 |
| 회의록 확정·공유 | 성공 시 `share → none`, 실패 시 `stop` |
| 회의록 검색·선택 | 선택된 ID의 추가·대체 결과 또는 기존 ID 유지 |
| 회의록 질문 1회 | 질문과 답변, 기존 `authorized_meeting_ids` 유지 |

검색과 질문에 별도의 지속 State가 없다는 사실은 Checkpoint를 남기지 않는다는 뜻이 아니다. 요청이 끝난 뒤 변경된 `messages`와 `authorized_meeting_ids`를 기존 Agent State에 반영할 수 있다.

Human in the Loop로 사용자 선택을 기다릴 때는 LangGraph checkpointer의 **런타임 내부 스냅샷**이 필요할 수 있다. 이는 업무 완료 지점에 표시하는 업무 경계 Checkpoint와 구분한다.

Tool 실행 중 오류가 발생하면 마지막 정상 업무 경계 Checkpoint를 기준으로 해당 업무를 재시도할 수 있도록 복구 오케스트레이션을 구현한다. Checkpoint 자체가 자동 복구를 수행하지는 않는다.

```text
오류 감지
→ 오류 유형과 재시도 가능 여부 판단
→ 마지막 정상 Checkpoint 선택
→ State 복원
→ 실패한 업무 단위 재실행
```

쓰기 작업은 State만 되돌려도 이미 실행된 백엔드 작업이 취소되지 않으므로 멱등성 키나 버전 검증 등 중복 실행 방지 장치가 필요하다.

브라우저를 나갔다가 나중에 중단 지점부터 같은 Graph 실행을 복구하는 기능은 현재 범위에 포함하지 않는다. 사용자는 필요할 때 에이전트를 다시 호출해 검색하거나 질문할 수 있다.

### 3-2. Compact

LLM의 컨텍스트 윈도우에는 한계가 있으므로 `messages`가 전체 컨텍스트 윈도우의 약 50%에 도달하면 Compact를 실행한다. 실제 기준은 모델과 토큰 사용량에 따라 조정한다.

회의록 원문은 `messages`에 누적하지 않으므로 Compact 대상이 아니다. 원문은 질문 시점에 ID로 조회하여 최종 컨텍스트에만 임시로 조립한다.

## 4. 녹화 Skill에 해당하는 백엔드 로직

### 4-1. 공통 원칙

회의 시작·일시정지·재개·종료 Skill은 에이전트가 보유한 Tool이 아니다. 전용 스레드의 명령 Trigger나 임베디드 녹화 바가 직접 호출하는 **백엔드 로직**이다.

각 Skill은 Runtime이 전달한 신뢰 가능한 현재 `recording_state`를 매개변수 또는 실행 컨텍스트로 받고 다음을 수행한다.

```text
Trigger 또는 UI 요청
→ 녹화 Skill 백엔드 호출
→ 전달받은 recording_state가 허용 상태인지 검사
→ 인증·생성자 권한·실제 회의 상태 검사
→ 기존 녹화 메서드 실행
→ 성공 또는 구조화된 거부·실패 결과 반환
→ 성공한 경우에만 오케스트레이터가 recording_state 갱신
```

| 백엔드 Skill | 허용 `recording_state` | 성공 후 State |
|---|---|---|
| 회의 시작 | `none` | `recording` |
| 회의 일시정지 | `recording` | `pause` |
| 회의 재개 | `pause` | `recording` |
| 회의 종료 | `recording`, `pause` | `stop` |

State 조건을 통과해도 인증·생성자 권한과 백엔드의 실제 회의 상태를 다시 검사한다. Agent State만으로 보안이나 실제 리소스 상태를 확정하지 않는다.

예시 성공 결과는 다음처럼 정규화할 수 있다.

```json
{
  "event": "MEETING_PAUSED",
  "status": "success",
  "next_recording_state": "pause",
  "meeting_id": "meeting-123"
}
```

오케스트레이터는 이 결과를 받은 뒤에만 State를 변경한다. 사용자에게 자연어 안내가 필요할 때는 결과를 컨텍스트에 넣어 LLM이 응답하게 하고, 고정 UI 안내만 필요하면 LLM 호출을 생략할 수 있다.

## 5. Agent Tool 목록

### 5-1. 공통 원칙

Agent Tool은 LLM과 백엔드 로직 사이의 실행 인터페이스다.

1. Tool은 이름, Description, 입력·출력 Schema와 오류 형식을 가진다.
2. LLM은 어떤 Tool을 어떤 인자로 호출할지만 판단한다.
3. 인증, 권한, 입력 검증과 실제 비즈니스 로직은 Tool 뒤의 백엔드가 강제한다.
4. `recording_state`와 인증 정보는 LLM이 인자로 만들지 않고 Runtime이 신뢰된 컨텍스트로 전달한다.
5. 오류는 재시도, 사용자 확인, 다른 Tool 선택, 중단을 구분할 수 있도록 구조화한다.
6. 쓰기 Tool에는 중복 실행 방지를 위한 멱등성 장치를 둔다.

### 5-2. Tool 1 — 회의록 확정 및 공유

기존 회의록 확정·공유 백엔드 로직을 호출해 회의록을 확정하고 지정된 채널에 공유한다.

- `recording_state="stop"`일 때만 실행한다.
- 백엔드에서 현재 사용자가 회의 생성자인지 검사한다.
- 성공하면 오케스트레이터가 `share`를 반영한 뒤 녹화 과정을 마치며 `none`으로 변경한다.
- 실패하면 `stop`을 유지하고 구조화된 오류를 반환한다.

### 5-3. Tool 2 — 관련 회의록 검색·선택

주제, 날짜 등의 조건으로 접근 가능한 회의록 후보를 검색하고 최종 ID 선택까지 하나의 Tool 흐름에서 처리한다. 별도의 ‘ID 가져오기 Tool’로 분리하지 않는다.

백엔드는 사용자가 다음 중 하나에 해당하는 회의록만 후보로 반환한다.

- 회의 생성자
- 회의 참여자
- 회의록이 공유된 채널의 구성원

| 후보 수 | 처리 |
|---|---|
| 0개 | 관련 회의록 없음 반환, 기존 ID 유지 |
| 1개 | 해당 후보를 바로 검증·선택 |
| 2개 이상 | 같은 스레드에서 Human in the Loop로 하나 이상 선택 |

선택된 ID가 최초의 권한 필터링 후보 집합에 포함되는지 백엔드가 다시 확인한다. 기존 `authorized_meeting_ids`가 있으면 같은 스레드에서 **추가 또는 대체**를 선택하게 하고, 검증된 결과만 State에 반영하도록 반환한다.

이 검색 흐름에는 지속적인 `search` State, `run_id`, 별도 검색 Subgraph가 필요하지 않다. 한 번의 요청 안에서 검색·선택·검증을 끝내고 Agent는 다음 입력을 기다린다. 검색은 `recording_state`를 변경하거나 녹화 과정을 차단하지 않는다.

### 5-4. Tool 3 — 회의록 원문 조회

사용자의 질문에 필요한 회의록 원문을 ID로 조회한다.

- 요청된 ID가 `authorized_meeting_ids`에 포함되어 있는지 서버에서 검사한다.
- 포함된 ID의 원문만 가져온다.
- 목록에 없는 ID이면 `UNAUTHORIZED_MEETING_ID`를 반환한다.
- 검색 단계의 채널 권한 전체를 반복 조회하지는 않되, 허용 목록 검증은 항상 수행한다.

가져온 원문은 State의 `messages`나 Checkpoint, 별도 임시 Storage에 저장하지 않는다.

```text
시스템 지시
+ 필요한 회의록 원문
+ 현재 messages
= LLM 최종 컨텍스트
```

LLM이 생성한 답변만 `messages`에 추가하고 원문은 해당 호출이 끝나면 컨텍스트에서 제거한다. 이 질문 실행도 `recording_state`를 변경하지 않는다.

## 6. 권한 및 실행 제약

### 6-1. 녹화 제어

녹화 Skill 백엔드는 다음을 검사한다.

1. 전달받은 `recording_state`가 요청 동작의 허용 상태인지
2. 인증된 사용자인지
3. 해당 회의의 생성자인지
4. 백엔드의 실제 회의 상태가 동작 가능한 상태인지

성공한 경우에만 녹화 메서드를 실행하고 성공 결과를 반환한다. LLM이나 `authorized=true/false` 같은 Agent State에 권한 판단을 맡기지 않는다.

### 6-2. 확정·공유

Tool 1은 `recording_state="stop"`과 회의 생성자 권한을 백엔드에서 검사한다. 둘 중 하나라도 충족하지 않으면 확정·공유를 실행하지 않는다.

### 6-3. 검색·선택

Tool 2는 조회 단계에서 사용자에게 접근 권한이 있는 회의록만 반환한다. 권한 없는 원문을 LLM에 전달한 뒤 제거하는 방식을 사용하지 않는다.

후보가 여러 개일 때의 선택과 기존 ID의 추가·대체는 같은 스레드의 Human in the Loop로 처리한다. 별도의 실행 식별자인 `run_id`는 두지 않는다.

### 6-4. 원문 조회

Tool 3은 입력된 ID가 `authorized_meeting_ids`에 포함되어 있는지 백엔드에서 확인한다. 이 목록은 권한 자체를 LLM에 맡기는 값이 아니라, 앞선 검색·선택 과정에서 서버가 검증한 결과를 다음 조회에 전달하는 임시 허용 목록이다.

## 7. Human in the Loop

Human in the Loop는 관련 회의록 검색·선택 Tool 안에서만 사용한다.

| 상황 | 사용자 행동 | 재개 후 처리 |
|---|---|---|
| 접근 가능한 후보가 2개 이상 | 필요한 회의록을 하나 이상 선택 | 후보 집합 포함 여부 재검증 |
| 기존 ID가 있는데 새 ID가 확정됨 | 기존 목록에 추가 또는 새 목록으로 대체 | 검증된 ID 목록 병합 또는 교체 |

사용자 선택을 기다리는 동안 같은 실행을 재개하기 위해 런타임 내부 스냅샷은 필요할 수 있다. 그러나 별도의 `run_id`나 지속적인 검색 State는 만들지 않는다.

## 8. 추후 결정 사항

- 회의록 원문 조회에 사용할 실제 식별자와 조회 방식
- 여러 회의록 중 질문과 관련된 원문을 자동 선별할 방식
- 사용하는 모델과 실제 토큰 사용량에 따른 Compact 기준
- 임베디드 녹화 바와 Agent State 사이의 구체적인 이벤트 동기화 방식
- Tool별 입력·출력 Schema, 오류 코드, 재시도 횟수와 중단 기준

## 핵심 정리

> 회의록 에이전트는 `messages`, `authorized_meeting_ids`, `recording_state`를 가진 단일 에이전트다. **회의 녹화만 지속 State로 관리**하고, 회의록 검색과 질문은 요청 시 Tool을 실행한 뒤 끝나는 일회성 업무로 처리한다. 회의 시작·일시정지·재개·종료 Skill은 Agent 내부 Tool이 아니라 State·권한·실제 회의 상태를 검사하고 기존 녹화 메서드를 실행하는 백엔드 로직이며, 성공 결과를 받은 오케스트레이터가 `recording_state`를 갱신한다. Agent에는 확정·공유, 검색·선택, 원문 조회의 세 Tool 인터페이스만 등록한다. 검색 후보가 여러 개이거나 기존 ID의 추가·대체가 필요하면 같은 스레드에서 Human in the Loop로 처리하며 `run_id`는 사용하지 않는다. 권한과 실제 실행 여부는 항상 백엔드가 강제하고, 회의록 원문은 호출 시점의 최종 컨텍스트에만 조립한다.
