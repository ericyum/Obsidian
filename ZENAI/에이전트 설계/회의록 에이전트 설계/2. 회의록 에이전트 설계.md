# 회의록 에이전트 설계

이 문서는 회의록 에이전트의 설계 가정, Skill과 Tool의 역할, 권한과 실행 제약, State와 Checkpoint의 저장 범위를 정의한다.

회의록의 전체 업무 워크플로우, 회의 녹화·회의록 기반 검색의 두 Agent Graph와 각 단계의 세부 순서도는 [[1. 회의록 에이전트 워크플로우 graph 정의]]에서 별도로 다룬다.

## 1. 설계 시 가정 사항

### 1-1. 단일 에이전트로 구성

회의록 에이전트가 수행하는 작업과 Tool 흐름이 비교적 단순할 것으로 예상되므로 하나의 LLM이 여러 Tool을 선택하는 **단일 에이전트**로 구성한다.

여러 에이전트를 분리하지 않고 하나의 에이전트가 사용자의 요청, 현재 State와 Tool 결과를 보고 다음 행동을 결정한다.

### 1-2. 사용자별 전용 스레드에서 독립적으로 실행

회의 생성·진행·공유와 공유 회의록의 검색·질의는 하나의 Agent 실행으로 이어지지 않는다. 회의 생성자와 공유받은 사용자는 각각 회의 에이전트를 호출해 생성된 자신의 전용 스레드에서 필요한 업무를 시작한다.

### 1-3. 기존 ZEN AI 기능을 재사용

ZEN AI의 회의록 기능과 관련 백엔드 로직은 이미 구현되어 있다고 가정한다. 에이전트가 회의 생성·제어·확정·조회 로직을 새로 구현하는 것이 아니라, 회의 녹화 제어는 Skill과 임베디드 바가, 확정·공유와 회의록 검색·조회는 Tool이 기존 기능을 호출한다.

특히 회의 제어에는 다음 세 백엔드 메서드가 존재한다고 가정한다.

- 회의 시작 메서드
- 회의 재생·일시정지 메서드
- 회의 종료 메서드

에이전트에는 세 메서드를 Tool로 노출하지 않는다. 회의 시작 메서드는 `/meeting-start` Skill이 호출하고, 재생·일시정지와 종료 메서드는 `/meeting-pause`, `/meeting-resume`, `/meeting-stop` Skill 및 상단 임베디드 녹화 바의 각 버튼이 동일한 공통 회의 제어 백엔드 Handler를 통해 호출한다.

전용 스레드에서 전달되는 에이전트 명령도 실제 실행 단계에서는 기존 ZEN AI 백엔드 로직을 사용한다.

### 1-4. State와 Checkpoint

#### State의 구성

State에는 대화와 실행 결과를 관리하는 `messages`, 현재 업무 단계를 나타내는 `workflow_state`, 검증된 회의록 ID 목록인 `authorized_meeting_ids`를 둔다.

```python
WorkflowState = Literal[
    "none", "recording", "pause", "stop",
    "share", "search",
]

class MeetingAgentState(TypedDict):
    messages: list
    workflow_state: WorkflowState
    authorized_meeting_ids: list[str]
```

`messages`에는 다음 정보가 들어갈 수 있다.

- 사용자의 요청
- LLM의 답변과 Tool 호출
- Tool 실행 결과
- Human in the Loop 이후 전달된 사용자 입력·선택 결과

`authorized_meeting_ids`는 Tool 2의 권한 필터를 통과하고 Tool 3에서 최종 선택된 회의록 ID를 보관하는 서버 관리 임시 허용 목록이다.

```python
State = {
    "messages": [...],
    "workflow_state": "none",
    "authorized_meeting_ids": ["meeting-123", "meeting-456"],
}
```

이 필드는 LLM이나 사용자가 직접 생성·수정하지 않는다. Tool 2와 Tool 3의 검증된 서버 코드만 갱신하며, Tool 4는 이 목록에 포함된 회의록만 조회할 수 있다. 재검색을 시작해도 기존 목록은 즉시 비우지 않는다. 새 ID가 확정된 뒤 Human in the Loop에서 선택한 결과에 따라 기존 목록과 중복 없이 병합하거나 새 ID 집합으로 교체한다.

`workflow_state`의 값과 변경 시점은 다음과 같다.

| 값 | 의미 | 값이 설정되는 시점 |
|---|---|---|
| `none` | 검색이나 녹화 제어 같은 일시적인 업무 단계가 진행 중이지 않은 초기·사용자 입력 대기 상태 | 사용자의 요청으로 Agent Graph 실행이 처음 시작된 직후 또는 선택한 업무 실행이 끝난 직후 |
| `recording` | 회의 녹음이 진행 중인 상태 | 회의 시작 또는 녹음 재개 백엔드가 성공 이벤트를 반환한 직후 |
| `pause` | 회의 녹음이 일시정지된 상태 | 일시정지 백엔드가 성공 이벤트를 반환한 직후 |
| `stop` | 회의가 종료된 상태 | 회의 종료 백엔드가 성공 이벤트를 반환한 직후 |
| `share` | 회의록이 확정·공유된 상태 | 확정·공유가 성공한 직후 |
| `search` | 관련 회의록을 검색하고 있는 상태 | Tool 2의 State 조건을 통과하고 후보 검색을 시작하는 시점 |

`none`은 에이전트가 호출되기 전의 꺼진 상태를 뜻하지 않는다. 호출 전에는 Agent Graph와 그 실행 State가 존재하지 않는다. 사용자의 최초 요청으로 State가 생성될 때와, 회의 녹화 과정 또는 회의록 검색 실행이 끝나 다음 요청을 기다릴 때 `none`을 사용한다. `authorized_meeting_ids`가 저장되어 있어도 현재 검색이나 녹화 제어가 실행 중이 아니라면 `workflow_state`는 `none`일 수 있다. 회의록 질문과 답변도 별도의 State로 전환하지 않고 `none`을 유지한 채 처리한다.

대표적인 상태 전이는 다음과 같다.

```text
회의 생성자
none → recording ↔ pause → stop → share → none

공유받은 사용자
검색: none → search → none
질문·답변: none → none
재검색: none → search → none
```

`workflow_state`는 Agent Graph의 진행과 라우팅을 돕는 값이다. 실제 녹음 상태와 권한의 최종 기준은 백엔드에 있으며, State 값만으로 실제 회의 상태나 실행 권한을 확정하지 않는다.

Skill 또는 Tool이 호출하는 백엔드 실행이 성공한 뒤에만 다음 상태로 변경한다. 단순한 명령 인식, Skill 호출 또는 임베디드 바 버튼 클릭만으로 성공 상태를 미리 기록하지 않는다. 실행이 거부되거나 실패하면 기존 `workflow_state`를 유지하고 오류 결과를 `messages`에 기록한다.

녹화 제어의 실제 상태는 공통 백엔드가 진실의 원천이며, Agent State는 성공 결과를 반영하는 영속적인 사본으로 본다. Skill과 임베디드 바는 모두 같은 Handler를 호출하고, 성공 이벤트를 받은 오케스트레이터가 State를 갱신한 뒤 업무 경계 Checkpoint를 남긴다. 스레드에 자연어 안내가 필요할 때만 정규화한 성공 이벤트를 컨텍스트에 추가하여 LLM을 호출한다. UI 표시 갱신이나 고정 안내만 필요하면 LLM 호출은 생략할 수 있다.

`share`는 회의록이 실제로 확정·공유되었음을 나타내는 상태이며, 성공 결과를 State에 반영한 뒤 회의 녹화 과정 전체를 마무리하고 `none`으로 돌아간다. 관련 회의록 검색은 후보 검색·선택, ID 검증·저장과 기존 ID의 추가·대체를 모두 `search` 안에서 처리한 뒤 `none`으로 돌아간다. 검색 결과가 0개이거나 검색이 취소·실패한 경우에도 기존 `authorized_meeting_ids`를 지우지 않고 `none`으로 돌아간다. 질문 한 번에 대한 답변을 반환한 뒤에도 `authorized_meeting_ids`와 `workflow_state="none"`을 유지하며, 에이전트는 다음 질문이나 요청을 계속 기다린다.

#### 두 업무 과정의 진입 제약

회의록 에이전트의 업무는 다음 두 과정으로 분리한다.

- **회의 녹화 과정**: `recording`, `pause`, `stop`, `share`
- **회의록 기반 검색 과정**: `search`

회의 녹화 과정에 진입하면 과정이 완료되어 `none`으로 돌아가기 전까지 새 회의를 시작하거나 회의록 기반 검색 과정으로 이동할 수 없다. 예를 들어 `recording` 또는 `pause` 상태에서 사용자가 지난 회의록을 검색해 달라고 요청하더라도 Tool 2는 검색을 실행하지 않는다. 현재 회의 녹화 과정을 먼저 마쳐야 한다는 구조화된 반려 이유를 반환한다.

회의록 질문은 `none`에서 처리하며, 사용자가 회의록을 추가하거나 대체하려 하면 `none`에서 Tool 2를 다시 실행해 `search`로 진입한다. 기존 ID 목록은 검색 중에도 유지하고, 새 ID가 확정되면 기존 목록에 추가할지 완전히 대체할지를 Human in the Loop로 선택한다. 검색 처리가 끝나면 다시 `none`으로 돌아가 질문을 계속 받을 수 있다.

```text
workflow_state = recording
사용자 요청 = "지난 회의 내용을 검색해 줘"
→ Tool 2 내부 State 검사 실패
→ STATE_CONFLICT
→ "현재 회의 녹화 과정이 끝나지 않았습니다" 반환

workflow_state = none
사용자 요청 = "지난 회의 내용을 검색해 줘"
→ Tool 2 실행 허용
→ workflow_state = search
```

`none`은 현재 검색이나 녹화 제어 같은 일시적인 업무 단계가 실행 중이지 않아 에이전트가 다음 요청을 기다리는 상태다. 이후 새로운 요청이 들어오면 `/meeting-start` Skill 또는 Tool 2가 새로운 업무 실행을 시작하거나, Tool 4가 저장된 `authorized_meeting_ids`를 이용해 질문 한 번을 처리할 수 있다.

State의 범위는 전용 스레드별로 분리한다. 회의를 생성·진행한 사용자의 스레드 State를 공유받은 사용자의 회의록 조회 스레드가 이어받지 않는다. 공유받은 사용자의 에이전트는 자신의 새 스레드에서 `workflow_state="none"`으로 시작하고, 백엔드의 권한 필터를 통과한 회의록을 ID로 조회한다.

#### Checkpoint의 의미와 적용 기준

Checkpoint는 State와 별개의 저장 공간이 아니라, 특정 시점의 State를 영속적으로 저장한 결과다. 다음과 같은 시점에 Checkpoint를 남긴다.

- 하나의 업무 워크플로우가 끝난 시점
- 해당 워크플로우의 최종 Tool 결과와 State 변경이 모두 반영된 시점
- 사용자에게 최종 결과를 반환하기 직전

설계 다이어그램에서는 이를 **업무 경계 Checkpoint**라고 표현하고, 각 Graph의 종료 지점에 한 번만 표시한다.

| 워크플로우 | 종료 시 대표 `workflow_state` | Checkpoint에 남는 결과 |
|---|---|---|
| 회의 시작 | 성공 시 `recording`, 실패 시 `none` | 회의 시작 결과 |
| 회의 제어 요청 1회 | `pause`, `recording`, `stop` 또는 실패 전 기존 값 | 일시정지·재개·종료 결과 |
| 회의록 확정·공유 | 성공 시 `none`, 실패 시 `stop` | 확정·공유 결과와 회의 녹화 과정 완료 여부 |
| 관련 회의록 검색·선택 | `none` | 검색 결과와 추가·대체가 반영된 회의록 ID 또는 기존 ID 유지 결과 |
| 회의록 질문 1회 | `none` | 사용자 질문과 생성된 답변; 기존 회의록 ID 유지 |

LangGraph 구현에서는 checkpointer를 Graph에 연결하면 각 super-step과 `interrupt()` 시점의 State 스냅샷이 런타임 내부에 저장될 수 있다. 이 저장은 현재 실행 중인 Human in the Loop를 재개하기 위한 **런타임 내부 스냅샷**이며, 문서의 업무 경계 Checkpoint와 구분한다.

따라서 설계 다이어그램에는 업무 워크플로우가 완료되는 지점만 Checkpoint로 표시한다. 다만 Human in the Loop를 실제로 중단·재개하려면 중단 시점의 내부 스냅샷은 기술적으로 필요하다.

Checkpoint에는 State가 저장되므로 `messages`에 포함된 Tool 결과와 선택된 회의록 ID 결과는 저장될 수 있다. 반면 회의록 원문은 State에 넣지 않으므로 Checkpoint에도 복제하지 않는다.

Compact는 안전한 업무 경계에서 실행하고, 정리된 `messages`를 해당 워크플로우의 마지막 Checkpoint에 함께 반영한다. Compact만을 위한 별도의 업무 Checkpoint는 두지 않는다.

브라우저를 나갔다가 나중에 기존 Graph의 중단 지점부터 실행을 복구하는 기능은 현재 범위에 포함하지 않는다. 사용자가 다음 날 다시 회의록에 대해 질문하려면 회의 에이전트를 새로 호출하고, Tool 2로 관련 회의록을 검색한 뒤 Tool 3으로 ID를 확정하고 Tool 4로 원문을 조회한다.

현재 단계에서는 Tool 실행 중 오류가 발생했을 때 이전 Checkpoint로 돌아가는 오케스트레이션 로직도 구현 범위에 포함하지 않는다. Checkpoint는 이전 State를 저장한 결과일 뿐이므로, 오류가 발생했다고 자동으로 이전 시점으로 돌아가지는 않는다.

향후 실행 중 오류 복구가 필요해지면 다음 로직을 별도로 구축해야 한다.

```text
Tool 오류 감지
→ 재시도 또는 중단 여부 판단
→ 마지막으로 정상 완료된 Checkpoint 선택
→ 해당 State와 실행 지점을 기준으로 Graph 재실행
```

쓰기 Tool이 일부 작업을 수행한 뒤 실패한 경우에는 Checkpoint로 State를 되돌려도 이미 실행된 백엔드 작업이 자동으로 취소되지 않는다. 따라서 재실행을 도입할 때는 중복 실행을 막는 멱등성 처리도 함께 고려해야 한다.

### 1-5. Skill·Tool 백엔드 내부 State 조건

State에 따른 Skill·Tool 허용·금지 조합을 시스템 프롬프트, 사전 지식 또는 Description에 모두 나열하지 않는다. 에이전트와 기능이 늘어날수록 LLM이 읽어야 할 조건 텍스트와 토큰 사용량이 커지고, 같은 조건이 여러 위치에 중복되어 유지보수가 어려워질 수 있기 때문이다.

각 Skill과 Tool이 호출하는 신뢰된 서버 코드가 Runtime 또는 Graph 실행 컨텍스트에서 현재 `workflow_state`를 전달받아 자신의 실행 조건을 결정적으로 검사한다.

```text
if current_state in allowed_states:
    권한·리소스 상태 검사
    기존 백엔드 기능 실행
else:
    기존 백엔드 기능 실행하지 않음
    STATE_CONFLICT와 반려 이유 반환
```

Skill과 Tool의 기본 State 조건은 다음과 같다.

| 실행 기능 | 실행이 허용되는 `workflow_state` | 허용되지 않을 때의 처리 |
|---|---|---|
| `/meeting-start` Skill | `none` | 진행 중인 과정을 먼저 마쳐야 한다는 이유 반환 |
| `/meeting-pause` Skill 또는 일시정지 버튼 | `recording` | 현재 녹음 중이 아니라는 이유 반환 |
| `/meeting-resume` Skill 또는 재개 버튼 | `pause` | 현재 일시정지 상태가 아니라는 이유 반환 |
| `/meeting-stop` Skill 또는 정지 버튼 | `recording`, `pause` | 종료할 수 있는 회의 상태가 아니라는 이유 반환 |
| Tool 1. 확정·공유 | `stop` | 회의를 먼저 종료해야 한다는 이유 반환 |
| Tool 2. 관련 회의록 검색 | `none` | 녹화 과정이 진행 중이면 먼저 마쳐야 한다는 이유 반환 |
| Tool 3. 회의록 ID 확정 | `search` | 유효한 검색 후보가 없다는 이유 반환 |
| Tool 4. 회의록 원문 조회 | `none` | 질의 대상 회의록이 확정되지 않았거나 다른 업무 단계가 진행 중이라는 이유 반환 |

Tool 4는 State 조건 외에도 요청된 ID가 `authorized_meeting_ids`에 포함되어 있는지 함께 검사한다.

State 조건을 통과하지 못한 Tool 결과는 최소한 다음 정보를 구분할 수 있어야 한다.

```json
{
  "status": "rejected",
  "error_code": "STATE_CONFLICT",
  "current_state": "recording",
  "allowed_states": ["none"],
  "reason": "현재 회의 녹화 과정이 끝나지 않아 회의록 검색을 시작할 수 없습니다.",
  "retryable": false
}
```

LLM은 모든 State 조건을 직접 판단하지 않고 Skill 또는 Tool 백엔드가 반환한 반려 이유를 사용자에게 설명한다. Graph 이동과 State 전달·갱신은 계속 오케스트레이터가 담당하며, 각 실행 기능은 자신의 실행 조건만 검사한다. 권한과 실제 회의 상태는 `workflow_state`만 신뢰하지 않고 기존 백엔드에서 별도로 검증한다.

### 1-6. Compact

LLM이 한 번에 처리할 수 있는 **컨텍스트 윈도우에는 한계가 있다.** 질문과 답변이 반복되면 State의 `messages`가 계속 길어지고, 결국 새로운 정보를 넣을 공간이 부족해지거나 LLM의 성능이 저하될 수 있다.

따라서 전체 컨텍스트 윈도우의 약 50%가 찼을 때를 기준으로 기존 대화 내용을 요약·정리하는 Compact를 실행한다. 이 기준은 사용하는 모델과 실제 토큰 사용량에 따라 조정할 수 있다.

```text
현재 컨텍스트 사용량 확인
→ 전체 컨텍스트 윈도우의 약 50% 미만: 그대로 진행
→ 전체 컨텍스트 윈도우의 약 50% 이상: Compact 실행
```

Compact의 대상은 State의 `messages`다. 회의록 원문은 `messages`에 저장하지 않으므로 Compact 대상에 포함되지 않는다.
## 2. Skill 목록

### 모든 녹화 Skill에 대한 공통 원칙

회의 녹화의 시작·일시정지·재개·종료는 LLM이 선택하는 Tool이 아니라 전용 스레드의 Trigger에 연결된 Skill로 실행한다. 사용자가 자연어 Trigger를 입력하면 시스템이 대응하는 명령 Skill로 라우팅하며, 녹화 중 표시되는 상단 임베디드 바의 버튼도 같은 공통 백엔드 Handler를 호출한다.

| 사용자 입력·UI Trigger | 실행 Skill 또는 공통 동작 |
|---|---|
| 스레드의 `회의 시작` 또는 `/meeting-start` | `/meeting-start` Skill |
| 스레드의 `회의 일시정지` 또는 `/meeting-pause` | `/meeting-pause` Skill |
| 스레드의 `회의 재개` 또는 `/meeting-resume` | `/meeting-resume` Skill |
| 스레드의 `회의 완료`·`회의 종료` 또는 `/meeting-stop` | `/meeting-stop` Skill |
| 임베디드 바의 일시정지·재개·정지 버튼 | 각 Skill과 동일한 공통 백엔드 Handler |

Skill 호출이나 버튼 클릭은 실행 요청일 뿐 성공 결과가 아니다. 공통 Handler가 다음 순서로 처리한다.

```text
Trigger 또는 버튼 클릭
→ 현재 workflow_state 검사
→ 인증 사용자·생성자 권한 검사
→ 백엔드의 실제 녹화 상태 검사
→ 기존 녹화 백엔드 메서드 실행
→ 성공 이벤트 또는 구조화된 거부·실패 결과 반환
→ 성공 이벤트일 때만 오케스트레이터가 State 갱신
→ 업무 경계 Checkpoint 저장
→ 대화 응답이 필요할 때만 LLM 호출
```

Skill과 임베디드 바가 State를 직접 수정하지 않는다. 백엔드가 반환한 성공 이벤트를 State reducer가 반영한다. 실패하거나 거부되면 기존 State를 유지하며, LLM을 호출하는 경우에는 성공·실패 결과와 사용자에게 필요한 설명만 정규화해 컨텍스트에 넣는다.

```json
{
  "event": "MEETING_PAUSED",
  "status": "success",
  "workflow_state": "pause",
  "meeting_id": "meeting-123",
  "occurred_at": "2026-08-21T14:30:00+09:00"
}
```

LLM 응답 생성이 실패하더라도 이미 성공한 녹화 동작과 State 갱신을 되돌리지 않는다. 임베디드 바에서 Graph 바깥으로 발생한 성공 이벤트도 해당 스레드의 State에 동기화하며, 다음 Agent 실행 시 필요하면 백엔드 실제 상태와 State를 대조한다.

### Skill 1. `/meeting-start`

전용 스레드에서 `회의 시작` 또는 `/meeting-start` Trigger가 감지되면 실행한다. 현재 `workflow_state`가 `none`일 때만 허용한다.

조건을 통과하면 기존 회의 시작 백엔드 메서드를 실행한다. 시작 성공 이벤트가 반환되면 오케스트레이터가 `workflow_state`를 `none`에서 `recording`으로 바로 변경한다. State 조건이 거부되거나 시작 백엔드가 실패하면 `none`을 유지하고 구조화된 반려·실패 결과를 반환한다. 자연어 안내가 필요할 때만 이 결과를 LLM 컨텍스트에 넣어 사용자에게 회의 시작 결과를 안내한다.

### Skill 2. `/meeting-pause`

스레드의 `회의 일시정지`·`/meeting-pause` Trigger 또는 임베디드 바 일시정지 버튼에서 같은 Handler를 호출한다. `workflow_state="recording"`일 때만 허용하며, 실제 일시정지 성공 이벤트를 받은 직후 `pause`로 변경한다.

### Skill 3. `/meeting-resume`

스레드의 `회의 재개`·`/meeting-resume` Trigger 또는 임베디드 바 재개 버튼에서 같은 Handler를 호출한다. `workflow_state="pause"`일 때만 허용하며, 실제 재개 성공 이벤트를 받은 직후 `recording`으로 변경한다.

### Skill 4. `/meeting-stop`

스레드의 `회의 완료`·`회의 종료`·`/meeting-stop` Trigger 또는 임베디드 바 정지 버튼에서 같은 Handler를 호출한다. `workflow_state`가 `recording` 또는 `pause`일 때만 허용하며, 실제 종료 성공 이벤트를 받은 직후 `stop`으로 변경한다. `stop`은 녹화가 끝난 상태일 뿐 전체 회의 녹화 과정의 완료 상태가 아니므로, 이후 Tool 1로 회의록 확정·공유를 마쳐야 `none`으로 돌아간다.

## 3. Tool 목록

### 모든 Tool에 대한 공통 원칙

1. 각 Tool의 입력 Schema와 Tool 결과가 LLM 컨텍스트에 돌아오는 형태를 정의해야 한다.
2. 입력 불일치와 실행 오류가 발생해도 에이전트가 다음 행동을 결정할 수 있도록 오류 결과를 구분해야 한다.
3. 같은 오류를 LLM에 반복해서 전달해 무한 루프가 생기지 않도록 재시도 횟수와 중단 기준을 정해야 한다.
4. LLM은 어떤 Tool을 어떤 입력으로 호출할지만 결정한다. 권한, 현재 상태 검증, 실제 메서드 선택과 실행은 Tool의 백엔드가 담당한다.
5. Tool은 가능한 한 기존 ZEN AI 백엔드 메서드를 감싼 얇은 실행 인터페이스로 구현한다.
6. 각 Tool은 실행 전에 현재 `workflow_state`가 자신의 허용 상태에 포함되는지 내부 코드로 검사하고, 조건이 맞지 않으면 `STATE_CONFLICT`와 구체적인 반려 이유를 반환한다.
7. `workflow_state`, 인증 사용자와 권한 정보는 LLM이 Tool 인자로 생성하지 않으며, 오케스트레이터 또는 서버 Runtime이 신뢰된 실행 컨텍스트로 전달한다.

### Tool 1. 회의록 확정 및 공유

기존 회의록 확정·공유 백엔드 로직을 호출하여 작성된 회의록을 확정하고 지정된 채널에 공유한다.

실행 전에 백엔드에서 현재 사용자가 회의 생성자인지 검사한다. 권한이 없으면 확정과 공유를 모두 수행하지 않는다.

현재 `workflow_state`가 `stop`일 때만 실행한다. 확정·공유가 성공하면 `share`를 거쳐 회의 녹화 과정을 마치고 `none`으로 돌아간다. State 조건, 권한 검사 또는 실행이 실패하면 `stop`을 유지하고 반려·오류 이유를 반환한다.

### Tool 2. 특정 주제와 연관된 회의록 가져오기

사용자가 회의 에이전트를 호출해 생성한 자신의 전용 스레드에서 전달한 질문으로부터 주제와 조건을 받아 관련 회의록 후보 목록을 조회한다.

현재 `workflow_state`가 `none`일 때 검색을 허용하고, 후보 검색을 시작하면 `search`로 변경한다. 기존 `authorized_meeting_ids`가 있어도 목록을 유지한 채 재검색할 수 있다. 회의 녹화 과정이 진행 중이면 검색을 실행하지 않고 `STATE_CONFLICT`와 해당 과정을 먼저 마쳐야 한다는 이유를 반환한다.

조회 결과에는 사용자가 다음 중 하나에 해당하는 회의록만 포함한다.

- 회의 생성자
- 회의 참여자
- 회의록 공유 대상자

후보 수에 따른 동작은 다음과 같다.

| 조회 결과 | 동작 |
|---|---|
| 0개 | 관련 회의록이 없다고 응답 |
| 1개 | Human in the Loop 없이 해당 회의록을 바로 사용 |
| 2개 이상 | 후보 목록을 표시하고 Human in the Loop로 일시정지 |

후보가 2개 이상이면 사용자는 질문에 필요한 회의록을 하나 이상 선택할 수 있다.

검색 결과가 0개이면 결과 없음 메시지를 기록하고 `workflow_state`를 `none`으로 변경한다. 기존 `authorized_meeting_ids`가 있으면 해당 목록을 지우지 않고 유지하며, 기존 ID가 없어도 결과 없음만 반환한 뒤 `none`으로 돌아간다.

### Tool 3. 선택한 회의록 ID 가져오기

Tool 2의 검색 결과에서 최종적으로 사용할 회의록 하나 또는 여러 개의 ID를 가져온다.

현재 `workflow_state`가 `search`일 때만 실행한다. 다른 상태이면 유효한 검색 후보가 없다는 `STATE_CONFLICT` 결과를 반환한다.

```text
후보 1개
→ 해당 회의록 ID를 바로 가져옴

후보 2개 이상
→ 사용자가 하나 이상 선택
→ 선택된 회의록 ID들을 가져옴
```

Tool 결과로 반환된 회의록 ID는 State의 `messages`와 Checkpoint에 저장될 수 있다. 현재는 회의록 원문을 조회하는 기준값을 회의록 ID라고 가정하며, 실제 식별자와 조회 방식은 구현 단계에서 확정한다.

Tool 3은 최종 선택된 ID가 Tool 2에서 반환한 접근 가능한 후보 집합에 포함되는지 서버에서 확인한다. 검증된 기존 ID가 없다면 새 ID 집합을 바로 저장한다. 기존 ID가 있다면 Human in the Loop로 다음 중 하나를 선택한 뒤 서버 코드가 목록을 갱신한다.

- **추가**: 기존 ID와 새 ID를 중복 없이 병합
- **대체**: 기존 ID를 버리고 새 ID 집합으로 교체

검증된 ID가 하나 이상 확정되면 `authorized_meeting_ids`에 반영하고 `workflow_state`를 `search`에서 `none`으로 변경한다. 이후 에이전트는 확정된 ID를 이용한 질문이나 다른 사용자 입력을 기다린다.

### Tool 4. 회의록 원문을 가져와 최종 컨텍스트에 추가

Tool 3이 반환한 회의록 ID를 이용해 해당 회의록의 텍스트를 가져온다. 여러 ID가 전달되면 여러 회의록의 텍스트를 가져온다.

Tool 4는 채널 권한 전체를 다시 조회하지 않는다. 대신 입력된 ID가 State의 `authorized_meeting_ids`에 포함되어 있는지 서버에서 확인하고, 포함된 ID의 원문만 가져온다. 목록에 없는 ID가 입력되면 원문을 조회하지 않고 `UNAUTHORIZED_MEETING_ID` 오류를 반환한다.

현재 `workflow_state`가 `none`이고 요청된 ID가 `authorized_meeting_ids`에 포함되어 있을 때만 원문 조회를 허용한다. 다른 업무 State이면 현재 진행 중인 업무를 먼저 마쳐야 한다는 `STATE_CONFLICT` 결과를 반환하고, 허용 목록에 없는 ID이면 `UNAUTHORIZED_MEETING_ID`를 반환한다. 질문과 답변을 처리하는 동안에도 `workflow_state="none"`과 기존 `authorized_meeting_ids`를 유지한다. 답변을 반환하면 이번 질문의 Graph 실행만 끝나며, 에이전트는 같은 ID 목록을 바탕으로 다음 질문을 계속 기다린다.

가져온 원문은 State의 `messages`에 추가하지 않는다. LLM 호출 직전에 별도의 문서 영역으로 넣고 현재 대화 기록과 조립한다.

```text
시스템 지시
+ 회의록 원문
+ 현재 messages
= LLM에 전달할 최종 컨텍스트
```

LLM이 생성한 답변만 `messages`에 추가하고, 회의록 원문은 실행이 끝나면 컨텍스트에서 제거한다.

#### 관련 회의록 자동 선별 방안 검토

여러 회의록 중 질문에 필요한 일부만 가져와야 하는 경우에는 어떤 회의록을 선택할지에 대한 기준이 필요하다.

현재 검토 중인 방안은 회의록 내용을 사전에 벡터화해 저장하고, 사용자 질문도 벡터화한 뒤 유사도가 일정 기준 이상인 회의록만 후보로 가져오는 방식이다. 이 방식은 아직 확정된 설계가 아니다.

## 4. 권한 및 실행 제약

### 4-1. 회의 제어

각 녹화 Skill과 임베디드 바 버튼이 공유하는 공통 백엔드 Handler는 다음 순서로 처리한다.

1. 요청된 동작과 현재 `workflow_state` 조합이 허용되는지 검사
2. 인증된 사용자 확인
3. 해당 회의의 생성자와 비교
4. 실제 현재 회의 상태 확인
5. Skill 또는 버튼 동작에 따라 기존 백엔드 메서드 선택
6. 성공 이벤트 또는 구조화된 거부·실패 결과 반환
7. 성공 이벤트이면 오케스트레이터가 State를 갱신하고 Checkpoint 저장

LLM이나 Agent State에 `authorized=true/false`를 저장해 권한을 판단하지 않는다. Skill 또는 UI에서 시작된 요청의 결과는 Agent가 사용자 응답 경로를 선택하기 위한 정보일 뿐이며, 권한과 실제 녹화 상태는 백엔드가 강제한다. Skill 호출과 UI 버튼 클릭은 State 변경 시점이 아니며, 실제 동작의 성공 이벤트가 State 변경의 기준이다.

### 4-2. 회의록 확정 및 공유

Tool 1도 백엔드에서 현재 사용자가 회의 생성자인지 검사한다.

- `workflow_state="stop"`이고 생성자이면 확정 및 공유 실행
- State 조건이 맞지 않거나 생성자가 아니면 실행하지 않음
- 성공하면 `share → none`으로 전환하고, 실패하면 `stop` 유지

### 4-3. 관련 회의록 조회

Tool 2는 `workflow_state`가 `none`인지 먼저 검사하고, 조건을 통과하면 백엔드에서 현재 사용자가 생성자·참여자·공유 대상자인 회의록만 반환한다. 기존 `authorized_meeting_ids`가 있는 상태에서 재검색하더라도 해당 목록은 새 ID의 추가·대체가 확정될 때까지 보존한다.

권한이 없는 회의록을 일단 LLM에 전달한 뒤 제거하는 방식은 사용하지 않는다. 권한 필터는 조회 단계에서 백엔드가 강제한다.

### 4-4. 후보 수에 따른 실행 제약

Tool 2의 검색 결과가 없으면 Tool 3과 Tool 4를 실행하지 않는다.

```text
후보 0개
→ 관련 회의록 없음 응답
→ 기존 authorized_meeting_ids 없음: workflow_state = none, 실행 종료
→ 기존 authorized_meeting_ids 있음: 기존 ID 유지, workflow_state = none

후보 1개
→ Human in the Loop 생략
→ Tool 3 실행

후보 2개 이상
→ Human in the Loop로 사용자 선택 대기
→ 하나 이상의 회의록 선택 후 Tool 3 실행

기존 ID 있음
→ Human in the Loop로 추가 또는 대체 선택
→ 추가: 기존 ID와 새 ID를 중복 없이 병합
→ 대체: 새 ID 집합으로 교체
```

### 4-5. 회의록 원문 조회와 임시 허용 목록

Tool 4는 `workflow_state`가 `none`인 경우에만, Tool 3이 반환하고 `authorized_meeting_ids`에 저장된 회의록 ID에 해당하는 원문을 가져온다. 질문과 답변이 끝난 뒤에도 `none`과 기존 ID 목록을 유지한다.

```text
Tool 2
→ 채널 권한 필터를 통과한 후보 반환

Tool 3
→ 선택된 ID가 후보 집합에 포함되는지 확인
→ 기존 ID가 있으면 추가·대체 선택 반영
→ authorized_meeting_ids에 저장

Tool 4
→ 요청된 ID가 authorized_meeting_ids에 포함되는지 확인
→ 포함되면 원문 조회
→ 포함되지 않으면 조회 거부
```

`authorized_meeting_ids`는 권한을 LLM에 맡기기 위한 State가 아니다. 서버가 이미 검증한 결과를 Tool 4에 전달하기 위한 임시 허용 목록이며, LLM은 이 값을 직접 수정할 수 없다.

회의록 원문은 답변 생성용 컨텍스트에만 포함하고 다음 위치에는 저장하지 않는다.

- State의 `messages`
- Checkpoint
- 별도의 임시 Storage

## 5. Human in the Loop와 Checkpoint

| 적용 기능 | Graph 중단 시점 | 사용자 행동 | 재개 후 동작 |
|---|---|---|---|
| 관련 회의록 조회 | 접근 가능한 후보가 2개 이상일 때 | 회의록을 하나 이상 선택 | 선택 결과로 회의록 ID 가져오기 |
| 회의록 ID 추가·대체 | 새 ID가 확정되었고 기존 ID가 있을 때 | 기존 ID에 추가 또는 새 ID로 대체 선택 | 검증된 ID 목록을 병합하거나 교체 |

Human in the Loop에서 Graph를 재개하려면 중단 시점의 State가 보존되어야 한다. LangGraph checkpointer가 만드는 런타임 내부 스냅샷을 이용해 사용자 입력을 기다렸다가 같은 실행을 재개한다.

이 중단 지점은 별도의 업무 경계 Checkpoint로 간주하지 않는다. 회의록 검색·선택 업무 전체가 완료된 뒤에 최종 State를 업무 경계 Checkpoint에 반영한다.

Tool 2의 조회 결과가 0개이면 관련 회의록이 없다고 응답하고 `none`으로 돌아간다. 기존 ID가 있으면 해당 목록을 유지한 채 `none`으로 돌아간다. 후보가 1개이면 후보 선택을 위한 Human in the Loop는 생략하지만, 기존 ID가 있다면 추가·대체 선택은 수행한다.

## 6. 추후 결정 사항

- 회의록 원문 조회에 사용할 실제 식별자와 조회 방식
- 벡터 유사도를 이용한 관련 회의록 자동 선별 방식의 적용 여부
- 사용하는 모델과 실제 토큰 사용량에 따른 Compact 실행 기준
- 임베디드 바에서 Graph 바깥으로 발생한 성공 이벤트의 구체적인 동기화 방식
- Tool별 입력 Schema, 결과 Schema, 오류 코드, 재시도 횟수와 중단 기준

## 핵심 정리

> 회의록 에이전트는 상위 시스템이 생성한 사용자별 전용 스레드에서 Trigger와 요청을 받아 기존 ZEN AI 기능을 호출하는 단일 에이전트로 구성한다. 회의 시작·일시정지·재개·종료는 네 개의 녹화 Skill과 임베디드 바가 같은 공통 백엔드 Handler를 사용하며, 실제 동작의 성공 이벤트가 반환된 뒤에만 오케스트레이터가 State를 갱신한다. 대화 안내가 필요할 때만 이 결과를 컨텍스트에 넣어 LLM을 호출한다. 회의 녹화 과정은 완료되어 `none`으로 돌아가기 전까지 다른 과정으로 이동할 수 없다. 회의록 검색은 `none → search → none`으로 처리하고, 후보 검색·선택, ID 검증·저장과 기존 ID의 추가·대체를 모두 `search` 안에서 마친다. 회의록 질문과 답변은 `none`을 유지하며 처리하고, 답변 뒤에도 기존 `authorized_meeting_ids`를 유지한 채 다음 입력을 기다린다. Tool 1은 확정·공유, Tool 2는 권한이 필터링된 후보 검색, Tool 3은 검증된 ID 목록 갱신, Tool 4는 허용 목록에 포함된 회의록 원문 조회를 담당한다. Skill과 Tool의 백엔드는 허용 State와 권한을 결정적으로 검사하고, 조건이 맞지 않으면 `STATE_CONFLICT`와 반려 이유를 반환한다. 업무 경계 Checkpoint는 각 업무 워크플로우의 종료 지점에 두며, 회의록 원문은 State·Checkpoint·임시 Storage에 저장하지 않고 필요한 시점의 최종 컨텍스트에만 넣는다.
