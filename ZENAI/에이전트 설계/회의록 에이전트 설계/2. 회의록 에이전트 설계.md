# 회의록 에이전트 설계

이 문서는 회의록 에이전트의 설계 가정, Tool의 역할, 권한과 실행 제약, State와 Checkpoint의 저장 범위를 정의한다.

회의록 업무 워크플로우와 각 단계의 Agent Graph는 [[1. 회의록 에이전트 워크플로우 graph 정의]]에서 별도로 다룬다.

## 1. 설계 시 가정 사항

### 1-1. 단일 에이전트로 구성

회의록 에이전트가 수행하는 작업과 Tool 흐름이 비교적 단순할 것으로 예상되므로 하나의 LLM이 여러 Tool을 선택하는 **단일 에이전트**로 구성한다.

여러 에이전트를 분리하지 않고 하나의 에이전트가 사용자의 요청, 현재 State와 Tool 결과를 보고 다음 행동을 결정한다.

### 1-2. 사용자별 전용 스레드에서 독립적으로 실행

회의 생성·진행·공유와 공유 회의록의 검색·질의는 하나의 Agent 실행으로 이어지지 않는다. 회의 생성자와 공유받은 사용자는 각각 회의 에이전트를 호출해 생성된 자신의 전용 스레드에서 필요한 업무를 시작한다.

### 1-3. 기존 ZEN AI 기능을 재사용

ZEN AI의 회의록 기능과 관련 백엔드 로직은 이미 구현되어 있다고 가정한다. 에이전트가 회의 생성·제어·확정·조회 로직을 새로 구현하는 것이 아니라, 기존 기능을 호출할 수 있도록 Tool 인터페이스를 제공한다.

특히 회의 제어에는 다음 두 백엔드 메서드가 존재한다고 가정한다.

- 회의 재생·일시정지 메서드
- 회의 종료 메서드

에이전트에는 두 메서드를 별도 Tool로 노출하지 않고, 하나의 회의 제어 Tool 내부에서 요청한 동작에 따라 알맞은 기존 메서드를 호출한다.

전용 스레드에서 전달되는 에이전트 명령도 실제 실행 단계에서는 기존 ZEN AI 백엔드 로직을 사용한다.

### 1-4. State와 Checkpoint

#### State의 구성

State에는 대화와 Tool 결과를 관리하는 `messages`와 현재 에이전트 업무 단계를 나타내는 `workflow_state`를 둔다.

```python
WorkflowState = Literal[
    "none", "start", "recording", "pause", "stop",
    "share", "search", "get_ID", "question",
]

class MeetingAgentState(TypedDict):
    messages: list
    workflow_state: WorkflowState
    authorized_meeting_ids: list[str]
```

`messages`에는 다음 정보가 들어갈 수 있다.

- 사용자의 요청
- LLM의 답변과 Tool 호출
- Tool 실행 결과
- Human in the Loop 이후 전달된 사용자 입력·선택 결과

`authorized_meeting_ids`는 Tool 4의 권한 필터를 통과하고 Tool 5에서 최종 선택된 회의록 ID를 보관하는 서버 관리 임시 허용 목록이다.

```python
State = {
    "messages": [...],
    "workflow_state": "get_ID",
    "authorized_meeting_ids": ["meeting-123", "meeting-456"],
}
```

이 필드는 LLM이나 사용자가 직접 생성·수정하지 않는다. Tool 4와 Tool 5의 검증된 서버 코드만 갱신하며, Tool 6은 이 목록에 포함된 회의록만 조회할 수 있다. 새로운 회의록 검색을 시작하면 기존 목록을 비우고 이번 검색에서 선택된 ID로 교체한다.

`workflow_state`의 값과 변경 시점은 다음과 같다.

| 값 | 의미 | 값이 설정되는 시점 |
|---|---|---|
| `none` | 에이전트가 호출되어 아직 구체적인 업무 상태로 전환되기 전의 초기 상태 | 사용자의 요청으로 Agent Graph 실행이 시작된 직후 |
| `start` | 회의 시작 모달이 표시되어 사용자 확정을 기다리는 상태 | 회의 정보 모달을 표시한 직후 |
| `recording` | 회의 녹음이 진행 중인 상태 | 회의 시작 또는 녹음 재개가 성공한 직후 |
| `pause` | 회의 녹음이 일시정지된 상태 | 일시정지가 성공한 직후 |
| `stop` | 회의가 종료된 상태 | 회의 종료가 성공한 직후 |
| `share` | 회의록이 확정·공유된 상태 | 확정·공유가 성공한 직후 |
| `search` | 관련 회의록을 검색하고 있는 상태 | 검색 요청을 해석하고 Tool 4를 호출하는 시점 |
| `get_ID` | 질의에 사용할 회의록 ID가 확정된 상태 | Tool 5가 선택된 회의록 ID를 반환한 직후 |
| `question` | 확정된 회의록을 바탕으로 질의응답을 진행하는 상태 | 사용자의 회의록 질문을 받은 시점 |

`none`은 에이전트가 호출되기 전의 꺼진 상태를 뜻하지 않는다. 호출 전에는 Agent Graph와 그 실행 State가 존재하지 않으며, 사용자의 요청으로 Graph가 시작된 직후 생성되는 초기 State 값이 `none`이다.

대표적인 상태 전이는 다음과 같다.

```text
회의 생성자
none → start → recording ↔ pause → stop → share

공유받은 사용자
none → search → get_ID → question → question …
```

`workflow_state`는 Agent Graph의 진행과 라우팅을 돕는 값이다. 실제 녹음 상태와 권한의 최종 기준은 백엔드에 있으며, State 값만으로 실제 회의 상태나 실행 권한을 확정하지 않는다.

Tool의 백엔드 실행이 성공한 뒤에만 다음 상태로 변경한다. 실행이 거부되거나 실패하면 기존 `workflow_state`를 유지하고 오류 결과를 `messages`에 기록한다.

State의 범위는 전용 스레드별로 분리한다. 회의를 생성·진행한 사용자의 스레드 State를 공유받은 사용자의 회의록 조회 스레드가 이어받지 않는다. 공유받은 사용자의 에이전트는 자신의 새 스레드에서 `workflow_state="none"`으로 시작하고, 백엔드의 권한 필터를 통과한 회의록을 ID로 조회한다.

#### Checkpoint의 의미와 적용 기준

Checkpoint는 State와 별개의 저장 공간이 아니라, 특정 시점의 State를 영속적으로 저장한 결과다. 다음과 같은 시점에 Checkpoint를 남긴다.

- 하나의 업무 워크플로우가 끝난 시점
- 해당 워크플로우의 최종 Tool 결과와 State 변경이 모두 반영된 시점
- 사용자에게 최종 결과를 반환하기 직전

설계 다이어그램에서는 이를 **업무 경계 Checkpoint**라고 표현하고, 각 Graph의 종료 지점에 한 번만 표시한다.

| 워크플로우 | 종료 시 대표 `workflow_state` | Checkpoint에 남는 결과 |
|---|---|---|
| 회의 시작 | `recording` 또는 실패 시 `start` | 회의 시작 결과 |
| 회의 제어 요청 1회 | `pause`, `recording`, `stop` 또는 실패 전 기존 값 | 일시정지·재개·종료 결과 |
| 회의록 확정·공유 | `share` 또는 실패 전 기존 값 | 확정·공유 결과 |
| 관련 회의록 검색·선택 | `get_ID` 또는 검색 결과가 없으면 `search` | 검색 결과와 선택된 회의록 ID |
| 회의록 질문 1회 | `question` | 사용자 질문과 생성된 답변 |

LangGraph 구현에서는 checkpointer를 Graph에 연결하면 각 super-step과 `interrupt()` 시점의 State 스냅샷이 런타임 내부에 저장될 수 있다. 이 저장은 현재 실행 중인 Human in the Loop를 재개하기 위한 **런타임 내부 스냅샷**이며, 문서의 업무 경계 Checkpoint와 구분한다.

따라서 설계 다이어그램에는 업무 워크플로우가 완료되는 지점만 Checkpoint로 표시한다. 다만 Human in the Loop를 실제로 중단·재개하려면 중단 시점의 내부 스냅샷은 기술적으로 필요하다.

Checkpoint에는 State가 저장되므로 `messages`에 포함된 Tool 결과와 선택된 회의록 ID 결과는 저장될 수 있다. 반면 회의록 원문은 State에 넣지 않으므로 Checkpoint에도 복제하지 않는다.

Compact는 안전한 업무 경계에서 실행하고, 정리된 `messages`를 해당 워크플로우의 마지막 Checkpoint에 함께 반영한다. Compact만을 위한 별도의 업무 Checkpoint는 두지 않는다.

브라우저를 나갔다가 나중에 기존 Graph의 중단 지점부터 실행을 복구하는 기능은 현재 범위에 포함하지 않는다. 사용자가 다음 날 다시 회의록에 대해 질문하려면 회의 에이전트를 새로 호출하고, Tool 4로 관련 회의록을 검색한 뒤 Tool 5로 ID를 확정하고 Tool 6으로 원문을 조회한다.

현재 단계에서는 Tool 실행 중 오류가 발생했을 때 이전 Checkpoint로 돌아가는 오케스트레이션 로직도 구현 범위에 포함하지 않는다. Checkpoint는 이전 State를 저장한 결과일 뿐이므로, 오류가 발생했다고 자동으로 이전 시점으로 돌아가지는 않는다.

향후 실행 중 오류 복구가 필요해지면 다음 로직을 별도로 구축해야 한다.

```text
Tool 오류 감지
→ 재시도 또는 중단 여부 판단
→ 마지막으로 정상 완료된 Checkpoint 선택
→ 해당 State와 실행 지점을 기준으로 Graph 재실행
```

쓰기 Tool이 일부 작업을 수행한 뒤 실패한 경우에는 Checkpoint로 State를 되돌려도 이미 실행된 백엔드 작업이 자동으로 취소되지 않는다. 따라서 재실행을 도입할 때는 중복 실행을 막는 멱등성 처리도 함께 고려해야 한다.

### 1-5. Compact

LLM이 한 번에 처리할 수 있는 **컨텍스트 윈도우에는 한계가 있다.** 질문과 답변이 반복되면 State의 `messages`가 계속 길어지고, 결국 새로운 정보를 넣을 공간이 부족해지거나 LLM의 성능이 저하될 수 있다.

따라서 전체 컨텍스트 윈도우의 약 50%가 찼을 때를 기준으로 기존 대화 내용을 요약·정리하는 Compact를 실행한다. 이 기준은 사용하는 모델과 실제 토큰 사용량에 따라 조정할 수 있다.

```text
현재 컨텍스트 사용량 확인
→ 전체 컨텍스트 윈도우의 약 50% 미만: 그대로 진행
→ 전체 컨텍스트 윈도우의 약 50% 이상: Compact 실행
```

Compact의 대상은 State의 `messages`다. 회의록 원문은 `messages`에 저장하지 않으므로 Compact 대상에 포함되지 않는다.
## 2. Tool 목록

### 모든 Tool에 대한 공통 원칙

1. 각 Tool의 입력 Schema와 Tool 결과가 LLM 컨텍스트에 돌아오는 형태를 정의해야 한다.
2. 입력 불일치와 실행 오류가 발생해도 에이전트가 다음 행동을 결정할 수 있도록 오류 결과를 구분해야 한다.
3. 같은 오류를 LLM에 반복해서 전달해 무한 루프가 생기지 않도록 재시도 횟수와 중단 기준을 정해야 한다.
4. LLM은 어떤 Tool을 어떤 입력으로 호출할지만 결정한다. 권한, 현재 상태 검증, 실제 메서드 선택과 실행은 Tool의 백엔드가 담당한다.
5. Tool은 가능한 한 기존 ZEN AI 백엔드 메서드를 감싼 얇은 실행 인터페이스로 구현한다.

### Tool 1. 회의 시작

회의 에이전트 전용 스레드에서 사용자가 입력한 `@회의 시작`을 Trigger로 기존 회의 정보 입력 모달과 회의 시작 로직을 호출하고, 사용자가 입력을 확정할 때까지 Graph를 중단한다.

```text
입력
- 현재 채널 정보

Human in the Loop
- 회의 정보 입력
- 회의 시작 확정

결과
- 기존 회의 시작 로직의 실행 결과
```

사용자가 회의 시작을 확정하기 전에는 실제 회의를 시작하지 않는다.

사용자 진입점은 전용 스레드의 `@회의 시작` 명령으로 확정한다. 다만 기존 모달을 표시하는 단계를 LLM이 선택하는 Tool로 둘지, Trigger 이후 실행되는 결정적 Node로 둘지는 구현 단계에서 결정한다.

### Tool 2. 회의 재생·일시정지·종료

하나의 `control_meeting` Tool로 구성한다.

```text
Tool
- control_meeting

입력
- meeting_id
- action: "pause" | "resume" | "end"
```

LLM은 사용자 요청을 바탕으로 `action`을 선택한다. Tool 내부 백엔드는 현재 사용자의 생성자 권한과 현재 회의 상태를 검사한 뒤 기존 메서드를 호출한다.

| `action` | 호출하는 기존 백엔드 메서드 |
|---|---|
| `pause` | 회의 재생·일시정지 메서드 |
| `resume` | 회의 재생·일시정지 메서드 |
| `end` | 회의 종료 메서드 |

회의가 이미 요청한 상태라면 같은 동작을 중복 실행하지 않고 현재 상태를 반환하도록 한다. 종료된 회의에 대한 재생·일시정지 요청처럼 허용되지 않는 상태 전이는 백엔드에서 거부한다.

일시정지 요청과 이후의 재생 요청은 하나의 Graph 실행이 계속 도는 것이 아니다. 각각 별도의 사용자 요청과 Agent 실행으로 같은 `control_meeting` Tool을 호출한다.

### Tool 3. 회의록 확정 및 공유

기존 회의록 확정·공유 백엔드 로직을 호출하여 작성된 회의록을 확정하고 지정된 채널에 공유한다.

실행 전에 백엔드에서 현재 사용자가 회의 생성자인지 검사한다. 권한이 없으면 확정과 공유를 모두 수행하지 않는다.

### Tool 4. 특정 주제와 연관된 회의록 가져오기

사용자가 회의 에이전트를 호출해 생성한 자신의 전용 스레드에서 전달한 질문으로부터 주제와 조건을 받아 관련 회의록 후보 목록을 조회한다.

조회 결과에는 사용자가 다음 중 하나에 해당하는 회의록만 포함한다.

- 회의 생성자
- 회의 참여자
- 회의록 공유 대상자

후보 수에 따른 동작은 다음과 같다.

| 조회 결과 | 동작 |
|---|---|
| 0개 | 관련 회의록이 없다고 응답 |
| 1개 | Human in the Loop 없이 해당 회의록을 바로 사용 |
| 2개 이상 | 후보 목록을 표시하고 Human in the Loop로 일시정지 |

후보가 2개 이상이면 사용자는 질문에 필요한 회의록을 하나 이상 선택할 수 있다.

### Tool 5. 선택한 회의록 ID 가져오기

4번 Tool의 검색 결과에서 최종적으로 사용할 회의록 하나 또는 여러 개의 ID를 가져온다.

```text
후보 1개
→ 해당 회의록 ID를 바로 가져옴

후보 2개 이상
→ 사용자가 하나 이상 선택
→ 선택된 회의록 ID들을 가져옴
```

Tool 결과로 반환된 회의록 ID는 State의 `messages`와 Checkpoint에 저장될 수 있다. 현재는 회의록 원문을 조회하는 기준값을 회의록 ID라고 가정하며, 실제 식별자와 조회 방식은 구현 단계에서 확정한다.

Tool 5는 최종 선택된 ID가 Tool 4에서 반환한 접근 가능한 후보 집합에 포함되는지 서버에서 확인한다. 검증을 통과한 ID만 State의 `authorized_meeting_ids`에 저장한다.

### Tool 6. 회의록 원문을 가져와 최종 컨텍스트에 추가

5번 Tool이 반환한 회의록 ID를 이용해 해당 회의록의 텍스트를 가져온다. 여러 ID가 전달되면 여러 회의록의 텍스트를 가져온다.

Tool 6은 채널 권한 전체를 다시 조회하지 않는다. 대신 입력된 ID가 State의 `authorized_meeting_ids`에 포함되어 있는지 서버에서 확인하고, 포함된 ID의 원문만 가져온다. 목록에 없는 ID가 입력되면 원문을 조회하지 않고 `UNAUTHORIZED_MEETING_ID` 오류를 반환한다.

가져온 원문은 State의 `messages`에 추가하지 않는다. LLM 호출 직전에 별도의 문서 영역으로 넣고 현재 대화 기록과 조립한다.

```text
시스템 지시
+ 회의록 원문
+ 현재 messages
= LLM에 전달할 최종 컨텍스트
```

LLM이 생성한 답변만 `messages`에 추가하고, 회의록 원문은 실행이 끝나면 컨텍스트에서 제거한다.

#### 관련 회의록 자동 선별 방안 검토

여러 회의록 중 질문에 필요한 일부만 가져와야 하는 경우에는 어떤 회의록을 선택할지에 대한 기준이 필요하다.

현재 검토 중인 방안은 회의록 내용을 사전에 벡터화해 저장하고, 사용자 질문도 벡터화한 뒤 유사도가 일정 기준 이상인 회의록만 후보로 가져오는 방식이다. 이 방식은 아직 확정된 설계가 아니다.

## 3. 권한 및 실행 제약

### 3-1. 회의 제어

`control_meeting` Tool은 백엔드에서 다음 순서로 처리한다.

1. 인증된 사용자 확인
2. 해당 회의의 생성자와 비교
3. 현재 회의 상태 확인
4. `action` 값에 따라 기존 백엔드 메서드 선택
5. 실행 또는 거부 결과 반환

LLM이나 Agent State에 `authorized=true/false`를 저장해 권한을 판단하지 않는다. Tool이 반환한 결과는 Agent가 사용자 응답 경로를 선택하기 위한 정보일 뿐이며, 권한 자체는 백엔드가 강제한다.

### 3-2. 회의록 확정 및 공유

3번 Tool도 백엔드에서 현재 사용자가 회의 생성자인지 검사한다.

- 생성자이면 확정 및 공유 실행
- 생성자가 아니면 실행하지 않음

### 3-3. 관련 회의록 조회

4번 Tool의 백엔드는 현재 사용자가 생성자·참여자·공유 대상자인 회의록만 반환한다.

권한이 없는 회의록을 일단 LLM에 전달한 뒤 제거하는 방식은 사용하지 않는다. 권한 필터는 조회 단계에서 백엔드가 강제한다.

### 3-4. 후보 수에 따른 실행 제약

4번 Tool의 검색 결과가 없으면 5번과 6번 Tool을 실행하지 않는다.

```text
후보 0개
→ 관련 회의록 없음 응답
→ 실행 종료

후보 1개
→ Human in the Loop 생략
→ Tool 5 실행

후보 2개 이상
→ Human in the Loop로 사용자 선택 대기
→ 하나 이상의 회의록 선택 후 Tool 5 실행
```

### 3-5. 회의록 원문 조회와 임시 허용 목록

6번 Tool은 5번 Tool이 반환하고 `authorized_meeting_ids`에 저장된 회의록 ID에 해당하는 원문만 가져온다.

```text
Tool 4
→ 채널 권한 필터를 통과한 후보 반환

Tool 5
→ 선택된 ID가 후보 집합에 포함되는지 확인
→ authorized_meeting_ids에 저장

Tool 6
→ 요청된 ID가 authorized_meeting_ids에 포함되는지 확인
→ 포함되면 원문 조회
→ 포함되지 않으면 조회 거부
```

`authorized_meeting_ids`는 권한을 LLM에 맡기기 위한 State가 아니다. 서버가 이미 검증한 결과를 Tool 6에 전달하기 위한 임시 허용 목록이며, LLM은 이 값을 직접 수정할 수 없다.

회의록 원문은 답변 생성용 컨텍스트에만 포함하고 다음 위치에는 저장하지 않는다.

- State의 `messages`
- Checkpoint
- 별도의 임시 Storage

## 4. Human in the Loop와 Checkpoint

| 적용 기능 | Graph 중단 시점 | 사용자 행동 | 재개 후 동작 |
|---|---|---|---|
| 회의 시작 | 회의 정보 입력 모달 표시 후 | 정보 입력 후 `회의 시작` 확정 | 입력값으로 기존 회의 시작 로직 호출 |
| 관련 회의록 조회 | 접근 가능한 후보가 2개 이상일 때 | 회의록을 하나 이상 선택 | 선택 결과로 회의록 ID 가져오기 |

Human in the Loop에서 Graph를 재개하려면 중단 시점의 State가 보존되어야 한다. LangGraph checkpointer가 만드는 런타임 내부 스냅샷을 이용해 사용자 입력을 기다렸다가 같은 실행을 재개한다.

이 중단 지점은 별도의 업무 경계 Checkpoint로 간주하지 않는다. 회의 시작 또는 회의록 검색·선택 업무 전체가 완료된 뒤에 최종 State를 업무 경계 Checkpoint에 반영한다.

4번 Tool의 조회 결과가 0개이면 관련 회의록이 없다고 응답한다. 1개이면 Human in the Loop를 거치지 않고 바로 다음 단계로 진행한다.

## 5. 추후 결정 사항

- `@회의 시작` Trigger 이후 모달 표시 단계를 Tool과 결정적 Node 중 어느 방식으로 구현할지
- 회의록 원문 조회에 사용할 실제 식별자와 조회 방식
- 벡터 유사도를 이용한 관련 회의록 자동 선별 방식의 적용 여부
- 사용하는 모델과 실제 토큰 사용량에 따른 Compact 실행 기준
- Tool별 입력 Schema, 결과 Schema, 오류 코드, 재시도 횟수와 중단 기준

## 핵심 정리

> 회의록 에이전트는 이미 상위 시스템이 생성한 사용자별 전용 스레드에서 명령과 요청을 받아 기존 ZEN AI 기능을 호출하는 단일 에이전트로 구성한다. State는 `messages`, `workflow_state`, 서버가 관리하는 `authorized_meeting_ids`로 구성한다. Tool 4가 채널 권한을 필터링하고 Tool 5가 선택된 ID를 임시 허용 목록에 저장하며, Tool 6은 목록에 포함된 ID의 원문만 조회한다. 설계상 Checkpoint는 각 업무 워크플로우의 종료 지점에 두고, Human in the Loop 재개용 런타임 내부 스냅샷과 구분한다. 회의 제어는 하나의 `control_meeting` Tool이 `pause`, `resume`, `end`를 받아 기존 메서드를 호출하며, 권한과 실제 회의 상태는 Tool의 백엔드가 검사한다. 회의록 원문은 State·Checkpoint·임시 Storage에 저장하지 않고 필요한 시점에 조회해 최종 컨텍스트에만 넣는다.
