# 회의록 에이전트의 컨텍스트 구조

이 문서는 [[1-1. 회의록 에이전트 업무 개요]], [[1-2. 회의록 에이전트 워크플로우 Graph 상세]], [[2-1. 회의록 에이전트 현재 구현 상세 설계]]를 기준으로, 대화 기록과 선택된 회의록 원문을 LLM에 어떤 방식으로 전달할지를 정의한다.

Tool 계층의 State 소유를 장기적으로 분리하는 방안은 [[2-2. Tool 계층 확장 및 State 관리 검토안]]에서 다룬다. 대화 기록을 Compact하는 세부 방법론은 [[1. 대화 컨텍스트 Compact 방법론 조사]]에서, Tool 결과와 Model Context 조립 방법론은 [[2. Tool 결과와 Model Context 조립 방법론 조사]]에서 다룬다.

## 1. 이 구조가 필요한 이유

회의록 질문이 들어올 때마다 전체 원문을 Agent State의 `ScratchPad`에 추가하면 같은 문서가 반복해서 누적된다.

```text
질문할 때마다 회의록 전체를 ScratchPad에 추가
→ 같은 문서의 중복 저장
→ 대화 토큰과 Checkpoint 크기 증가
→ Compact 대상에 원문까지 섞임
```

따라서 다음 세 데이터를 분리한다.

```text
전용 스레드의 Agent State와 대화 기록
≠ 기존 백엔드에서 조회한 회의록 원문
≠ 한 번의 LLM 호출에 전달하는 최종 Model Context
```

LangChain은 지속적으로 관리되는 State와 한 번의 모델 호출에 사용하는 Model Context를 구분한다. Model Context는 State를 변경하지 않고 호출마다 다르게 조립할 수 있는 일시적인 입력이다.

- [LangChain Context Engineering](https://docs.langchain.com/oss/python/langchain/context-engineering)
- [LangChain Context 개요](https://docs.langchain.com/oss/python/concepts/context)

## 2. 컨텍스트를 구성하는 네 영역

| 영역 | 관리하는 내용 | 유지 범위 | LLM이 직접 보는가? |
|---|---|---|---|
| Agent State | `ScratchPad`, `authorized_meeting_ids`, `recording_modal_status` | 사용자별 전용 스레드 | Model Context에 조립한 값만 봄 |
| Runtime Context | 인증 사용자, 전용 스레드, 기존 백엔드·DB 접근 수단 | 현재 실행 | 자동으로 보지 못함 |
| 실행 중 문서 데이터 | Tool 2가 허용 ID로 조회한 회의록 원문 하나 이상 | 현재 질문 처리 | Model Context에 넣을 때만 봄 |
| Model Context | 시스템 지시, 필요한 원문, 현재 `ScratchPad`와 구조화된 실행 결과를 조립한 최종 입력 | LLM 호출 1회 | 실제 모델 입력 |

핵심은 회의록 원문을 State나 별도의 임시 Storage에 복사하지 않는 것이다. 검증된 ID만 `authorized_meeting_ids`에 유지하고, 원문은 질문할 때 기존 백엔드에서 다시 조회한다.

실제 녹화 진행 상태인 `recording_state`는 녹화 임베디드 상단바 모달이 소유한다. Agent 질문 컨텍스트에 녹화 상태를 누적하거나 회의록 검색을 위해 변경하지 않는다.

## 3. Model Context에 사용하는 `ScratchPad`

`ScratchPad`에는 다음 판단에 필요한 대화와 작업 기록이 들어간다.

- 사용자의 요청과 질문
- LLM의 답변
- LLM이 생성한 Tool 1·2 호출
- 사용자에게 필요한 구조화된 Tool 결과
- Human in the Loop의 후보 선택과 추가·대체 선택 결과
- 검색·선택과 원문 조회의 성공·거부·실패 메타데이터

회의록 원문 전체는 `ScratchPad`에 저장하지 않는다. Tool 1의 검색·권한 필터·후보 검증을 거쳐 확정된 ID는 별도 필드인 `authorized_meeting_ids`에 반영하고, `ScratchPad`에는 사용자에게 보여줄 선택 결과와 다음 판단에 필요한 메타데이터만 남긴다.

Tool 2가 조회한 원문도 ToolMessage나 작업 기록으로 누적하지 않는다. LLM 답변을 만드는 현재 호출에만 사용하고, 호출 후에는 답변과 필요한 구조화된 Tool 결과만 `ScratchPad`에 추가한다.

현재 설계에서는 `ScratchPad`의 대화·작업 항목을 Reducer로 누적하는 구조를 전제로 한다. `ScratchPad`는 단순 채팅 로그가 아니라 원래 사용자 목표, 완료된 Subgraph 결과와 아직 남은 작업을 다음 LLM 판단에 전달하는 실행 기록이다.

- [LangGraph Graph API의 State와 Reducer](https://docs.langchain.com/oss/python/langgraph/graph-api)

## 4. Runtime Context의 역할

Runtime Context는 LLM이 생성하는 값이 아니라 서버가 실행 시 제공하는 정보다.

- 인증된 사용자 ID
- 현재 전용 스레드 ID
- 기존 ZEN AI 백엔드 호출 수단
- DB 연결
- 서버에서 확인한 요청 범위

```text
LLM이 생성하는 Tool 인자
→ 검색 주제·날짜 조건, 조회할 meeting_id 등

서버가 Runtime Context로 제공하는 값
→ 인증 사용자, 전용 스레드, 백엔드·DB 접근 수단
```

Runtime Context는 자동으로 LLM 프롬프트에 들어가지 않는다. Tool과 백엔드는 이를 사용해 권한과 리소스 상태를 검사하고, 모델 답변에 필요한 구조화된 결과만 반환한다.

- [LangChain Runtime](https://docs.langchain.com/oss/python/langchain/runtime)
- [LangChain Tools와 ToolRuntime](https://docs.langchain.com/oss/python/langchain/tools)

## 5. `authorized_meeting_ids`의 역할

Tool 1은 주제·날짜 조건으로 접근 가능한 회의록을 검색하고, 권한 필터·후보 선택·ID 검증을 한 흐름에서 처리한다. 검증된 최종 ID만 Agent State의 `authorized_meeting_ids`에 반영한다.

```text
Tool 1 검색·권한 필터
→ 후보 선택과 필요 시 HITL
→ 후보 집합 포함 여부 재검증
→ 새 ID 설정 또는 기존 ID에 추가·대체
→ authorized_meeting_ids 반영
```

이 필드는 원문 저장소가 아니라 다음 질문에서 Tool 2가 조회를 허용할 ID를 전달하는 서버 관리 참조값이다. LLM은 값을 임의로 만들거나 수정하지 않는다.

현재 구현에서는 검증된 Tool 1 결과를 받은 오케스트레이터가 `authorized_meeting_ids`를 갱신한다. 향후 Tool 계층이 별도 Repository에서 조회·검증·갱신 책임까지 소유하는 방안은 [[2-2. Tool 계층 확장 및 State 관리 검토안]]의 검토 대상이다.

## 6. Tool 2와 실행 중 문서 데이터

Tool 2는 질문에 필요한 회의록 ID가 `authorized_meeting_ids`에 포함되어 있는지 백엔드에서 검사한 뒤 기존 ZEN AI 백엔드에서 원문 하나 이상을 조회한다.

```text
authorized_meeting_ids
→ Tool 2가 요청 ID의 허용 목록 포함 여부 검사
→ 기존 백엔드에서 원문 조회
→ 실행 중 문서 데이터로 전달
→ Model Context 조립에 사용
```

회의록 원문은 다음 위치에 저장하지 않는다.

- Agent State의 `ScratchPad`
- Agent Checkpoint
- 별도의 임시 Storage

Tool 2의 영속적인 결과에는 조회 성공 여부, 사용한 회의록 ID, 문서 수와 같은 메타데이터만 남길 수 있다. 원문 본문은 오케스트레이터의 컨텍스트 조립 단계에 일시적으로 전달하고 LLM 호출이 끝나면 버린다.

허용 ID가 없거나 Tool 2가 거부·실패한 경우에도 구조화된 결과를 LLM에 전달한다. LLM은 회의록 선택 필요 또는 실패 이유를 사용자에게 답변한다.

## 7. Model Context 조립

회의록 질문에서는 다음 정보를 한 번의 Model Context로 조립한다.

```text
시스템 지시
+ Tool 2가 조회한 회의록 원문 하나 이상
+ 현재 전용 스레드의 ScratchPad
+ 구조화된 Tool 결과
= LLM 최종 Model Context
```

```text
LLM 호출 전
→ 사용자 질문을 ScratchPad에 반영
→ LLM이 Tool 2 필요 여부 판단
→ Tool 2가 허용 ID의 원문 조회
→ 시스템 지시·원문·ScratchPad·구조화된 Tool 결과 조립

LLM 호출
→ 조립된 컨텍스트로 답변 생성

LLM 호출 후
→ 답변과 필요한 Tool 결과만 ScratchPad에 추가
→ 원문은 State와 Checkpoint에 추가하지 않음
```

사용자의 요청이 원문 없이 답할 수 있다면 LLM은 Tool 2를 호출하지 않고 직접 답변한다.

## 9. 하나의 사용자 목표가 처리되는 순서

1. 사용자가 전용 스레드에서 회의록 내용에 관해 질문하거나 검색과 질문을 함께 요청한다.
2. 오케스트레이터가 원래 사용자 목표를 `ScratchPad`에 반영한다.
3. LLM이 Search, Question 또는 Tool 없는 직접 답변 중 다음 실행 경로를 판단한다.
4. Question이 선택되면 Tool 2가 `authorized_meeting_ids` 포함 여부를 검사하고 필요한 원문을 조회한다.
5. 원문은 실행 중 문서 데이터로만 유지한다.
6. 시스템 지시, 필요한 원문, 현재 `ScratchPad`와 구조화된 Tool 결과를 조립해 LLM을 호출한다.
7. LLM은 질의 응답과 `후속 작업 있음/없음`을 구조화하여 반환한다.
8. 오케스트레이터는 답변과 필요한 Tool 결과를 `ScratchPad`에 추가하고 Agent 업무 경계 Checkpoint를 저장한다.
9. Graph Runtime의 Condition은 후속 작업이 있으면 LLM 판단 Node로 돌아가고, 없으면 END를 확정한 뒤 Agent 요청 대기로 돌아간다.

예를 들어 “ID A와 B를 가져오고 두 회의록의 결정 사항을 설명해줘”라는 요청은 다음과 같이 이어진다.

```text
원래 사용자 목표를 ScratchPad에 기록
→ Search Subgraph에서 A·B 검증과 authorized_meeting_ids 반영
→ 검색 결과를 ScratchPad에 반영하고 Checkpoint
→ 후속 작업 있음
→ LLM 판단으로 복귀
→ Question Subgraph에서 A·B 원문 조회와 답변 생성
→ 답변을 ScratchPad에 반영하고 Checkpoint
→ 후속 작업 없음
→ END → Agent 요청 대기
```

## 10. Compact와의 관계

Compact의 대상은 `ScratchPad` 안의 대화·작업 기록이다. 회의록 원문은 State에 저장하지 않으므로 Compact 대상에 포함되지 않는다.

```text
컨텍스트 사용량이 전체 윈도우의 약 50% 미만
→ 현재 ScratchPad 유지

컨텍스트 사용량이 전체 윈도우의 약 50% 이상
→ ScratchPad의 대화·작업 기록 Compact
→ 정리된 ScratchPad를 State에 반영
→ 다음 질문에서 authorized_meeting_ids로 원문 재조회
```

`authorized_meeting_ids`와 `recording_modal_status`는 `ScratchPad`와 별도 필드이므로 Compact의 영향을 받지 않는다. Tool 1의 선택 결과를 설명하는 작업 기록만 요약 대상이 될 수 있다.

- [LangChain Short-term Memory와 Summarization](https://docs.langchain.com/oss/python/langchain/short-term-memory)

## 11. 토큰 예산

회의록 원문을 `ScratchPad`와 분리하더라도 LLM 호출 시 포함한 원문의 토큰은 사용된다.

```text
최종 입력 토큰
= 시스템 지시
+ Tool 2가 조회한 회의록 원문
+ Compact된 ScratchPad
+ 답변 생성을 위한 여유 공간
```

이 구조는 원문이 `ScratchPad`에 반복 누적되는 문제를 해결하지만 긴 회의록 자체가 모델의 컨텍스트 한도를 초과하는 문제까지 해결하지는 않는다. 이후 다음 방식을 비교해야 한다.

- 전체 원문 사용
- 질문과 관련된 구간만 검색
- 청크 단위 조회
- 부분 요약과 원문 구간 병행

## 12. 권한 정보와 Model Context의 분리

권한 정보 자체를 Model Context에 넣어 LLM이 접근 가능 여부를 판단하게 하지 않는다.

```text
후보 접근 권한 필터와 선택 ID 검증
→ Tool 1 뒤의 백엔드

요청 ID의 허용 목록 포함 여부와 원문 조회
→ Tool 2 뒤의 백엔드

Model Context에 포함하는 회의록
→ 백엔드 검사를 통과한 원문만 포함
```

`authorized_meeting_ids`도 LLM이 권한을 추론하기 위한 프롬프트 문장이 아니라, 서버가 검증한 결과를 Tool 2에 전달하기 위한 구조화된 State다.

## 13. 컨텍스트 구조에서 결정할 항목

- Tool 2가 원문을 컨텍스트 조립 단계에 전달하는 구체적인 구현 방식
- Tool 2의 영속적인 결과에 남길 메타데이터 Schema
- 긴 회의록을 전체로 넣을지 관련 구간만 넣을지
- 조립한 원문을 어떤 Message 역할과 형식으로 모델에 전달할지
- 사용하는 모델과 실제 토큰 사용량에 따른 Compact 기준

## 핵심 정리

> Tool 1은 접근 가능한 회의록의 검색·선택·검증을 처리하고, 확정된 ID는 `authorized_meeting_ids`에 원문 재조회를 위한 참조값으로 유지한다. 질문이 들어오면 Tool 2가 허용 ID의 원문을 조회하고, LLM 호출 시점에만 `시스템 지시 + 회의록 원문 + ScratchPad + 구조화된 Tool 결과`를 조립한다. 호출 후에는 답변과 필요한 Tool 결과만 `ScratchPad`에 추가하며 원문은 State·Checkpoint·임시 Storage에 저장하지 않는다. Checkpoint 뒤에 후속 작업이 남아 있으면 LLM 판단으로 복귀하고, 사용자 목표가 달성되었을 때만 END 후 입력 대기로 돌아간다.
