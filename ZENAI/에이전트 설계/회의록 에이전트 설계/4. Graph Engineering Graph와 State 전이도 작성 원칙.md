# Graph Engineering Graph와 State 전이도 작성 원칙

이 문서는 회의록 에이전트 설계에서 사용하는 그림을 **최신 Graph Engineering 관점의 실행 Graph**와 **State 전이도**로 구분하고, 두 그림을 일관되게 작성하기 위한 기준을 정의한다.

Graph Engineering은 2026년에 빠르게 확산된 신생 용어이므로 하나의 공식 표준으로 고정되어 있지는 않다. 이 문서에서는 LangGraph의 실행 모델과 최근 Agent Workflow 연구에서 공통적으로 확인되는 원칙만 사용한다.

## 1. 두 그림을 구분하는 이유

두 그림은 서로 다른 질문에 답한다.

| 구분 | 답하려는 질문 |
|---|---|
| Graph Engineering 관점의 Agent Graph | 어떤 작업 단위가 실행되고, 어떤 결과가 다음 작업을 허용하는가? |
| State 전이도 | 업무 진행에 따라 `workflow_state` 값이 어떻게 바뀌는가? |

하나의 그림에 Agent, Tool, State 값, State 갱신, Checkpoint와 세부 백엔드 메서드를 모두 넣으면 실행 구조와 상태 변화가 섞여 읽기 어려워진다. 따라서 상위 실행 구조와 State 수명주기를 별도 그림으로 관리한다.

## 2. Graph Engineering 관점의 Agent Graph

### 2-1. 핵심 철학

Graph Engineering 관점의 Agent Graph는 **작업의 토폴로지**를 그린다.

- Node는 독립적으로 실행·검증·재시도할 수 있는 작업 단위다.
- Node는 LLM Agent뿐 아니라 Skill, 일반 프로그램, 검증기 또는 Human gate가 될 수 있다.
- Edge는 단순한 연결선이 아니라 다음 Node 실행을 허용하는 구조화된 Outcome과 의존 관계다.
- Loop는 없애는 대상이 아니라 Node 내부 또는 Node 사이에 명시적으로 배치하는 실행 구조다.
- 실패·재시도·중단 조건을 Edge로 드러내어 실행 경로를 관찰하고 테스트할 수 있어야 한다.
- Context는 전체 Graph에 계속 누적하기보다 현재 Node가 필요한 정보만 조립해 전달한다.

### 2-2. Node 선정 기준

다음 중 하나 이상에 해당할 때 독립 Node로 분리한다.

- 별도로 실행할 수 있다.
- 입력과 출력 Schema를 정의할 수 있다.
- 성공·실패 여부를 독립적으로 검증할 수 있다.
- 실패 시 해당 지점부터 재시도할 필요가 있다.
- 사람의 승인이나 선택이 필요한 Gate다.
- 다른 실행 주체나 권한 경계를 가진다.

다음과 같은 런타임 내부 처리는 그 자체가 독립 업무가 아니라면 상위 Agent Graph의 Node로 만들지 않는다.

- State 읽기·갱신
- `messages`에 결과 추가
- Context 조립
- Reducer 적용
- Checkpoint 저장
- 단순 성공·실패 판별

이러한 처리는 실행 Node가 반환하는 결과 또는 세부 LangGraph 순서도에서 표현한다.

### 2-3. Edge 작성 기준

Edge에는 다음 Node로 이동할 수 있는 이유를 적는다.

```text
업무상 의미
+ 구조화된 Outcome 코드
```

예시는 다음과 같다.

```text
시작 성공
MEETING_STARTED

ID 확정
IDS_CONFIRMED

회의록 추가·대체
SEARCH_MORE · REPLACE_IDS
```

Outcome은 가능하면 자유 텍스트가 아니라 enum 형태로 정의한다. 이를 통해 라우팅, 추적, 재시도와 테스트에서 동일한 값을 사용할 수 있다.

### 2-4. State와 Checkpoint 표현

LangGraph에서 State는 현재 실행의 공유 스냅샷이며, Node는 State를 입력받아 부분 업데이트를 반환한다. 따라서 State는 Graph 실행에 반드시 존재할 수 있지만, **State 값이나 State 갱신을 항상 독립 Node로 그려야 한다는 뜻은 아니다.**

상위 Agent Graph에서는 다음과 같이 처리한다.

```text
작업 Node 실행
→ Outcome + State update 반환
→ 오케스트레이터와 Reducer가 반영
→ 런타임이 필요한 Checkpoint 저장
→ Outcome Edge를 따라 다음 Node 실행
```

Checkpoint 저장도 런타임의 공통 동작이면 별도 Node로 그리지 않는다. 사용자가 저장 자체를 명령하거나 저장 성공이 별도의 업무 결과가 되는 경우에만 독립 Node를 고려한다.

### 2-5. 시각 표현 규칙

- 빨간색 네모: LLM Agent 또는 LLM 판단이 핵심인 작업 Node
- 파란색 네모: Skill, Tool, 백엔드 프로그램 등 결정적 실행 Node
- 노란색 네모: Human in the Loop 또는 사용자 결정 Gate
- 회색 실선: 정상 완료 후 다음 작업으로 진행하는 Edge
- 빨간 실선: 조건에 따라 이전 작업으로 돌아가거나 대안 경로로 이동하는 Edge
- 빨간 점선: 실패 후 재시도 Edge
- Edge 라벨: `업무 의미 + Outcome 코드`

정상 경로는 위에서 아래로 읽히게 두고, 재시도와 되돌아가기는 측면의 곡선 Edge로 분리한다. 하나의 Node에서 나오는 Edge가 많다면 Outcome을 묶거나 하위 Graph로 분리한다.

## 3. State 전이도

### 3-1. 핵심 철학

State 전이도는 **업무 상태의 수명주기**를 그린다.

- Node는 `none`, `recording`, `pause`와 같은 State 값이다.
- Edge는 State를 바꾸는 성공 이벤트나 사용자 행동이다.
- Tool, LLM, 백엔드 Handler의 내부 과정은 State 변경 원인이 필요한 경우에만 Edge 라벨로 간단히 표시한다.
- State가 바뀌지 않는 실패는 자기 순환 또는 기존 State 유지 주석으로 표현한다.
- 실제 권한과 리소스 상태의 진실의 원천은 백엔드이며, State 전이도는 이를 대신하지 않는다.

State 전이도에는 State가 없어야 하는 것이 아니라, 반대로 **State 값이 중심 Node여야 한다.**

### 3-2. State 선정 기준

State는 다음 Node의 실행 가능 여부나 사용자에게 보이는 업무 상태를 실제로 구분할 때만 추가한다.

- 다른 Skill·Tool의 허용 여부가 달라진다.
- 오류 복구나 재개 기준이 달라진다.
- UI에 표시해야 하는 의미 있는 업무 상태다.
- 일정 시간 유지되며 이후 요청의 판단 기준이 된다.

아주 짧은 내부 처리 단계는 별도 State로 만들지 않는다. 예를 들어 회의 시작 메서드가 성공하는 즉시 녹화 중이 된다면 `start`를 두지 않고 `none → recording`으로 전이한다.

### 3-3. Edge 작성 기준

State 전이 Edge에는 State 변경을 확정하는 사건을 적는다.

```text
none -- MEETING_STARTED --> recording
recording -- MEETING_PAUSED --> pause
pause -- MEETING_RESUMED --> recording
recording -- MEETING_STOPPED --> stop
```

사용자 요청이나 버튼 클릭만으로 State를 먼저 바꾸지 않는다. 백엔드가 실제 동작의 성공 이벤트를 반환한 뒤에만 전이한다.

### 3-4. 시각 표현 규칙

- State 값: 동일한 모양의 파란색 또는 대기 상태용 초록색 네모
- 정상 State 전이: 회색 실선
- 조건에 따른 복귀·실패 유지: 빨간 화살표
- Condition: 분기가 꼭 필요한 경우에만 마름모 사용
- Tool·LLM·Checkpoint: State 전이도에는 원칙적으로 독립 Node로 넣지 않음

## 4. 두 그림의 연결 방법

두 그림은 서로 대체하지 않고 같은 설계를 다른 관점에서 검증한다.

| Agent Graph | 반환 Outcome | State 전이도 |
|---|---|---|
| 회의 시작 실행 Node | `MEETING_STARTED` | `none → recording` |
| 회의 진행 Node | `MEETING_PAUSED` | `recording → pause` |
| 회의 진행 Node | `MEETING_RESUMED` | `pause → recording` |
| 회의 진행 Node | `MEETING_STOPPED` | `recording·pause → stop` |
| 회의록 확정·공유 Node | `MINUTES_PUBLISHED` | `stop → share → none` |
| 회의록 검색 Node | `CANDIDATES_FOUND` | `none·get_ID·question → search` |
| 회의록 선택 Gate | `IDS_CONFIRMED` | `search → get_ID` |
| 회의록 질의 Node | `FOLLOW_UP_QUESTION` | `get_ID·question → question` |

Agent Graph의 모든 Outcome이 반드시 State를 변경할 필요는 없다. 예를 들어 후속 질문은 `question` State를 유지하면서 같은 질의 Node를 다시 실행할 수 있다.

## 5. 작성 순서

1. 먼저 실제 업무를 독립적으로 실행·검증할 수 있는 작업 단위로 나눈다.
2. 각 작업의 입력, 성공·실패 Outcome과 다음 작업을 정의한다.
3. 이를 Node와 Outcome Edge로 연결해 Agent Graph를 작성한다.
4. 다음 작업의 허용 여부를 바꾸는 지속적인 업무 상태만 추려 State Schema를 정의한다.
5. 성공 이벤트를 기준으로 State 전이도를 별도로 작성한다.
6. Agent Graph의 Outcome과 State 전이가 서로 일치하는지 표로 검증한다.
7. 세부 구현이 필요하면 각 작업 Node를 LangGraph 순서도로 확장한다.

## 6. 피해야 할 작성 방식

- Agent Graph의 모든 작은 코드 줄을 Node로 만드는 것
- State 값과 State 갱신 작업을 같은 수준의 Node로 섞는 것
- LLM이 자연어를 해석한 결과만으로 권한이나 실제 업무 State를 확정하는 것
- 실패 Edge가 어디로 가는지 표시하지 않는 것
- 재시도 횟수와 중단 조건이 없는 무한 자기 순환
- 하나의 그림에 상위 업무 구조와 모든 백엔드 세부 구현을 동시에 넣는 것
