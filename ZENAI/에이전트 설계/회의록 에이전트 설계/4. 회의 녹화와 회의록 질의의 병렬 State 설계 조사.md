# 회의 녹화와 회의록 질의의 병렬 State 설계 조사

이 문서는 회의 녹화 중에도 과거 회의록을 검색하고 질문할 수 있도록, 서로 다른 업무가 하나의 전역 State를 덮어쓰지 않는 구조를 비교한다.

일반적인 State 설계 선택 기준은 [[4. 워크플로우 특성에 따른 State 설계 방법론]]에서 다루며, 이 문서에서는 현재 회의록 에이전트에 필요한 수준으로 단순화한다.

## 1. 문제 정의

기존 설계는 녹화와 검색에 하나의 `workflow_state`를 사용했다.

```text
회의 녹화
none → recording ↔ pause → stop → share → none

회의록 검색
none → search → none
```

이 구조에서는 녹화 중 검색을 허용하기 어렵다.

```text
workflow_state = recording
→ 검색을 위해 search로 변경
→ 일시정지·재개·종료가 녹화 상태를 확인할 수 없음
```

그러나 두 업무의 성격은 다르다.

- **회의 녹화**는 시작 후 일시정지·재개·종료·확정 및 공유까지 여러 요청에 걸쳐 이어진다.
- **회의록 검색·질문**은 요청이 들어올 때 Tool과 LLM을 실행하고 결과를 반환하면 끝난다.

따라서 검색을 녹화와 같은 지속 State Machine으로 관리할 필요가 있는지 검토해야 한다.

## 2. 1안 — State 필드를 두 개로 분리

### 구조

```python
State = {
    "recording_state": "recording",
    "retrieval_state": "searching",
}
```

### 장점

- 녹화와 검색 State가 서로의 값을 **덮어쓰지 않는다.**
- `recording_state=recording`인 동안 `retrieval_state=searching`을 함께 표현할 수 있다.
- 녹화 로직과 검색 로직이 자신이 담당하는 필드만 검사하므로 **State 소유권이 비교적 명확하다.**
- 기존 단일 State를 두 필드로 나누는 방식이므로 초기 구현이 단순하다.
- 녹화와 검색이라는 고정된 두 영역만 존재한다면 전체 상태를 한 State 객체에서 확인하기 쉽다.

### 한계

- 검색은 요청이 끝나면 더 이상 유지할 상태가 없는데도 `retrieval_state=idle` 같은 값을 계속 보관한다.
- 한 개의 `retrieval_state`로는 검색 요청 여러 개를 동시에 구분하기 어렵다.
- 전사·요약·결재·SAP 업무가 추가될 때마다 전역 State에 필드를 계속 추가해야 한다.

```text
recording_state
retrieval_state
transcription_state
approval_state
purchase_state
...
```

- 모든 필드가 하나의 Checkpoint에 저장되면 한 업무의 복구 범위에 다른 업무의 State까지 포함될 수 있다.
- `messages`와 `authorized_meeting_ids` 같은 공통 필드의 동시 갱신에는 별도의 Reducer·version 규칙이 필요하다.

### 적합한 경우

- 병렬 업무 영역이 적고 고정되어 있는 경우
- 각 영역의 상태가 실제로 여러 요청에 걸쳐 지속되는 경우
- 각 영역에서 동시에 하나의 실행만 존재하는 경우

현재 검색·질문은 요청 한 번으로 끝나므로 별도의 지속 `retrieval_state`를 두는 것은 필요 이상으로 무겁다.

## 3. 2안 — 여러 상태를 하나의 조합 값으로 저장

### 구조

```text
workflow_state = recording/searching
workflow_state = pause/selecting
workflow_state = stop/idle
```

### 장점

- 기존의 단일 `workflow_state` 필드를 유지할 수 있다.
- 로그나 화면에서 두 업무 상태를 한 줄로 표시할 수 있다.
- 허용할 조합을 enum으로 모두 정의하면 정의되지 않은 조합을 Schema 단계에서 거부할 수 있다.

### 한계

- 상태 수가 늘어날수록 가능한 조합이 곱셈으로 증가한다.

```text
녹화 상태 5개 × 검색 상태 4개 = 20개 조합
전사 상태 4개 추가 = 80개 조합
```

- 녹화 상태 하나만 변경해도 검색 상태를 포함한 전체 값을 다시 저장해야 한다.
- 녹화와 검색이 동시에 저장하면 마지막 쓰기가 다른 쪽 변경을 덮어쓸 수 있다.
- 각 백엔드 로직이 조합 문자열을 해석해 자신에게 필요한 부분을 꺼내야 한다.
- 새로운 업무가 추가될 때 기존 enum, 파싱 코드, 허용 조합과 다이어그램을 모두 수정해야 한다.
- 실제로 독립적인 업무들을 하나의 값으로 강하게 결합한다.

### 적합한 경우

실제 State보다는 화면·로그의 **표시용 계산값**에 적합하다.

```text
실제 저장
recording_state = recording

현재 검색 Tool 실행 여부 = true

표시용
recording/searching
```

회의록 에이전트의 기본 State 구조로는 권장하지 않는다.

## 4. 3안 — 녹화 State만 지속하고 검색·질문은 요청 시 실행

### 핵심 판단

State는 단순히 실행 중 잠깐 거치는 모든 단계를 기록하기 위한 값이 아니다. **다음 사용자 요청에서도 기억해야 하며 이후 실행 가능 여부나 경로에 영향을 주는 정보**를 보관한다.

회의 녹화는 여러 요청에 걸쳐 이어지고 현재 상태에 따라 다음 동작이 달라진다.

```text
recording
→ 일시정지·종료 가능

pause
→ 재개·종료 가능

stop
→ 확정·공유 가능
```

따라서 녹화에는 별도의 지속 `recording_state`가 필요하다.

반면 검색과 질문은 요청 한 번 안에서 처리하고 끝난다.

```text
검색 요청
→ 검색 Tool 실행
→ 후보 검색·선택
→ authorized_meeting_ids 갱신
→ 종료

회의록 질문
→ 원문 조회 Tool 실행
→ 컨텍스트 조립
→ LLM 답변
→ 종료
```

검색 후보 수에 따른 분기는 존재하지만, 검색이 끝난 뒤 `searching`이나 `selecting`을 다음 요청까지 유지할 필요는 없다. 후보가 여러 개이면 같은 스레드에서 Human in the Loop로 사용자가 선택하고 제출하도록 하며, 별도의 `run_id`나 지속 검색 State를 두지 않는다.

### Agent State

```python
AgentState = {
    "messages": [...],
    "authorized_meeting_ids": ["meeting-123", "meeting-456"],
    "recording_state": "recording",
}
```

| 필드 | 역할 |
|---|---|
| `messages` | 사용자 요청, LLM 답변과 필요한 Tool 결과 |
| `authorized_meeting_ids` | 검색·선택·검증이 끝난 회의록 ID |
| `recording_state` | 녹화·일시정지·재개·종료·확정 및 공유 과정의 지속 상태 |

검색어, 후보 목록과 현재 선택 단계는 검색 요청 내부에서만 사용한다. 이후 질문에 필요한 최종 ID만 `authorized_meeting_ids`에 반영한다.

### Backend Skill과 Agent Tool의 구분

회의 녹화 제어에 사용하는 Skill은 Agent에 연결된 Tool이 아니라 **Trigger 또는 UI가 호출하는 백엔드 로직**이다.

```text
회의 시작·일시정지·재개·종료 Trigger 또는 UI
→ 해당 Backend Skill 호출
→ 전달받은 recording_state 검사
→ 인증·생성자 권한·실제 회의 상태 검사
→ 기존 백엔드 동작 실행
→ 성공 또는 구조화된 반려·실패 결과 반환
→ 성공 결과를 받은 오케스트레이터가 recording_state 변경
```

Skill이 State를 직접 수정하지 않으며, LLM이 Skill을 Tool Calling으로 선택하는 구조도 아니다.

Agent에 연결되는 것은 다음 **Tool 인터페이스**다.

| Tool | Agent에서 보이는 역할 | 실제 실행 |
|---|---|---|
| 회의록 확정·공유 Tool | 확정·공유 요청 | Tool 인터페이스 뒤의 백엔드가 State·권한 검사 후 실행 |
| 회의록 검색 Tool | 검색 조건으로 접근 가능한 회의록 검색·선택 | Tool 인터페이스 뒤의 백엔드 검색·권한 필터와 같은 스레드 HITL |
| 회의록 원문 조회 Tool | 검증된 ID로 원문 조회 | Tool 인터페이스 뒤의 백엔드가 허용 ID 검사 후 조회 |

Tool은 실제 로직 자체가 아니라 **LLM과 백엔드 실행 로직 사이의 인터페이스**다. LLM은 Tool 이름·Description·Schema를 보고 호출을 결정하고, 실제 권한·State 검사와 실행은 백엔드가 담당한다.

### 실행 관계

```text
Main Agent
├─ State
│  ├─ messages
│  ├─ authorized_meeting_ids
│  └─ recording_state
│
└─ Tool 인터페이스
   ├─ 회의록 확정·공유 Tool
   ├─ 회의록 검색 Tool
   └─ 회의록 원문 조회 Tool

Trigger·UI
└─ Backend Skill
   ├─ 회의 시작
   ├─ 회의 일시정지
   ├─ 회의 재개
   └─ 회의 종료

Tool과 Skill 뒤의 실제 업무 로직
└─ 기존 ZEN AI 백엔드
```

### `workflow_id`와 `run_id`

현재 범위에서는 별도의 `workflow_id`를 두지 않는다.

- 한 전용 스레드에서 동시에 하나의 현재 회의만 녹화한다.
- 실제 회의는 기존 `meeting_id`와 전용 스레드로 식별할 수 있다.
- 같은 스레드에서 여러 녹화 Workflow를 동시에 실행하지 않는다.

검색에도 별도의 `run_id`를 두지 않는다.

- 검색 요청과 HITL 선택은 같은 스레드에서 하나씩 처리한다.
- 후보가 여러 개이면 사용자가 같은 스레드의 선택 UI에서 제출한다.
- 검색 결과가 비동기로 여러 개 돌아오거나 여러 선택창이 동시에 열리는 구조가 아니다.

향후 한 스레드에서 같은 종류의 장기 업무나 비동기 검색을 여러 개 동시에 실행해야 할 때만 식별자 도입을 다시 검토한다.

### 장점

- 녹화 중에도 검색·질문을 실행할 수 있고 `recording_state`를 덮어쓰지 않는다.
- 사용하지 않는 `retrieval_state`, `search`, `question` State를 유지하지 않는다.
- 별도의 Subgraph, `workflow_id`, `run_id` 없이 현재 요구사항을 충족한다.
- 녹화 State, 대화 기록과 검증된 ID의 역할이 명확하다.
- Skill·Tool·백엔드·오케스트레이터의 책임을 분리할 수 있다.
- 새로운 단발성 검색·질문 기능은 필요할 때 Tool과 LLM 실행으로 추가할 수 있다.

### 한계

- 같은 스레드에서 여러 검색·HITL을 동시에 실행하는 구조로 확장되면 실행 식별자가 필요할 수 있다.
- `authorized_meeting_ids` 추가와 대체가 동시에 발생하면 Reducer 또는 version 검사가 필요하다.
- 향후 여러 장기 업무가 동시에 지속된다면 녹화 외에도 해당 업무만의 별도 State를 추가해야 한다.
- 복잡한 장기 업무가 서로 의존하면 Process Manager·Saga 같은 추가 설계가 필요할 수 있다.

## 5. 세 방안 비교

| 방안 | 구조 | 현재 적합성 | 핵심 한계 |
|---|---|---:|---|
| 1안. State 필드 두 개 | 녹화 State + 검색 State | 보통 | 단발성 검색 State를 불필요하게 유지 |
| 2안. 조합 State | 녹화·검색을 하나의 값으로 결합 | 낮음 | 조합 폭발과 동시 갱신 충돌 |
| 3안. 녹화 State만 지속 | 녹화만 State 관리, 검색·질문은 요청 시 실행 | 높음 | 향후 같은 업무의 동시 실행 시 식별 구조 재검토 필요 |

## 6. 현재 회의록 에이전트에 대한 권고

현재 회의록 에이전트에는 **3안**을 권고한다.

### 이유

1. **녹화는 지속 업무**이므로 다음 요청의 실행 가능 여부를 판단할 State가 필요하다.
2. **검색과 질문은 단발성 업무**이므로 요청 내부에서 Tool과 LLM을 실행하고 끝내면 된다.
3. 검색 때문에 녹화 State를 `search`로 바꾸지 않으므로 **녹화 중 검색·질문을 허용**할 수 있다.
4. 현재는 한 스레드에서 검색·HITL을 하나씩 처리하므로 별도의 `run_id`가 필요하지 않다.
5. 한 대표 사용자가 하나의 현재 회의를 녹화하므로 `thread_id`와 `meeting_id` 외에 별도의 `workflow_id`가 필요하지 않다.
6. Agent에는 Tool 인터페이스만 연결하고, Skill과 Tool 뒤의 State·권한·실제 실행 로직은 기존 백엔드에서 강제할 수 있다.

> **최종 권고:** Agent State에는 `messages`, `authorized_meeting_ids`, `recording_state`를 둔다. 녹화 제어 Backend Skill은 전달받은 `recording_state`와 실제 회의 상태를 검사해 동작한 뒤 결과를 반환하고, 성공 결과를 받은 오케스트레이터가 State를 변경한다. 회의록 검색과 질문에는 별도의 지속 State·Subgraph·`workflow_id`·`run_id`를 두지 않고, Agent가 검색 Tool 또는 원문 조회 Tool을 호출해 요청 한 번을 처리한다.
