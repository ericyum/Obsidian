# 회의 녹화와 회의록 질의의 병렬 State 설계 조사

이 문서는 회의 녹화 중에도 과거 회의록을 검색하고 질문할 수 있도록, 서로 독립적인 업무의 State를 어떻게 분리할지 비교하고 현재 채택 구조를 정리한다.

현재 구현 기준은 [[1-2. 회의록 에이전트 워크플로우 Graph 상세]]과 [[2-1. 회의록 에이전트 현재 구현 상세 설계]]을 따른다. Tool 계층의 State 소유를 별도 서버나 Repository로 분리하는 장기 검토안은 [[2-2. Tool 계층 확장 및 State 관리 검토안]]에서 다룬다.

## 1. 문제 정의

녹화와 검색·질문을 하나의 `workflow_state`로 표현하면 두 업무가 같은 값을 덮어쓴다.

```text
단일 workflow_state = recording
→ 과거 회의록 검색을 위해 searching으로 변경
→ 녹화 일시정지·재개·종료가 현재 녹화 상태를 확인할 수 없음
```

그러나 두 업무의 성격은 다르다.

- **회의 녹화**는 여러 사용자 동작에 걸쳐 이어지며 현재 상태에 따라 다음 허용 동작이 달라지는 결정적 Workflow다.
- **회의록 검색·질문**은 하나의 사용자 목표 안에서 LLM과 Search·Question Subgraph를 반복 실행할 수 있는 Agent 업무다. 각 Subgraph가 끝나면 결과를 저장하고 후속 작업 여부에 따라 LLM 판단으로 복귀하거나 요청을 완료한다.

현재 녹화 상태 전이는 다음과 같다.

```text
none → recording ↔ pause → stop → none
```

`stop`은 종료 처리 중 거치는 모달 상태이며, 종료가 완료되면 바로 `none`으로 돌아간다. 별도의 `share` State는 사용하지 않는다.

## 2. 1안 — 두 지속 State 필드를 하나의 Agent State에 둔다

### 구조

```python
AgentState = {
    "recording_state": "recording",
    "retrieval_state": "searching",
}
```

### 장점

- 녹화와 검색 State가 서로의 값을 덮어쓰지 않는다.
- 한 객체에서 두 업무의 현재 상태를 확인할 수 있다.
- 두 업무가 모두 여러 요청에 걸쳐 지속된다면 각 필드의 소유권을 나누기 쉽다.

### 한계

- 현재 검색·질문은 요청이 끝나면 유지할 실행 상태가 없는데도 `idle`, `searching`, `selecting` 같은 값을 계속 저장하게 된다.
- 실제 녹화 `recording_state`를 이미 모달이 소유하는데 Agent에도 중복 저장하면 동기화 문제가 생긴다.
- 장기 업무가 늘어날 때마다 전역 Agent State 필드가 계속 증가한다.
- 서로 다른 업무의 State가 하나의 Checkpoint에 묶여 복구 범위가 불필요하게 커질 수 있다.

### 적합한 경우

- 두 업무가 모두 여러 요청에 걸쳐 실제로 지속되는 경우
- 두 상태를 같은 오케스트레이터가 반드시 소유해야 하는 경우

현재 구조에는 적합하지 않다. 검색·질문은 지속 업무 State가 아니며 실제 녹화 상태의 소유자는 Agent가 아니라 녹화 모달이다.

## 3. 2안 — 여러 상태를 하나의 조합 값으로 저장한다

### 구조

```text
workflow_state = recording/searching
workflow_state = pause/selecting
workflow_state = stop/idle
```

### 장점

- 화면이나 로그에서 두 업무 상태를 한 줄로 표시할 수 있다.
- 허용 조합을 모두 정의하면 Schema 단계에서 정의되지 않은 조합을 거부할 수 있다.

### 한계

- 독립적인 상태 수가 늘어날수록 가능한 조합이 곱셈으로 증가한다.
- 한쪽 상태만 바뀌어도 다른 쪽 상태를 포함한 전체 값을 다시 저장해야 한다.
- 동시 갱신 시 마지막 쓰기가 다른 업무의 변경을 덮어쓸 수 있다.
- 모달이 소유하는 녹화 상태와 Agent의 요청 단계를 하나의 값으로 강하게 결합한다.
- 새로운 업무가 추가될 때 enum, 파싱 코드, 허용 조합과 다이어그램을 모두 수정해야 한다.

### 적합한 경우

실제 저장 State보다는 화면·로그의 **표시용 계산값**에 적합하다.

```text
실제 값
모달 recording_state = recording
현재 검색 요청 실행 여부 = true

표시용 계산값
recording/searching
```

회의록 에이전트의 저장 구조로는 권장하지 않는다.

## 4. 3안 — 소유 영역을 분리하고 검색·질문은 요청 시 실행한다

### 핵심 판단

지속 코드 State의 데이터 필드에는 다음 요청에서도 기억해야 하며 이후 실행 경로나 허용 동작에 영향을 주는 정보만 둔다. 반면 Graph의 `none`, `search`, `question`은 현재 실행 중인 Node와 선택된 Edge를 설명하는 개념적 State이므로 같은 이름의 지속 데이터 필드가 없어도 사용할 수 있다.

회의 녹화는 현재 상태에 따라 다음 동작이 달라지므로 지속 상태가 필요하지만, 그 상태는 이미 녹화 임베디드 상단바 모달이 소유한다.

```text
recording
→ 일시정지·종료 가능

pause
→ 재개·종료 가능

stop
→ 종료 처리 완료 후 none
```

검색과 질문의 각 Subgraph 실행은 하나의 업무 경계를 이루지만, 하나의 사용자 목표 안에서 연속될 수 있다.

```text
검색 요청
→ Tool 1 검색·권한 필터·후보 선택·ID 검증
→ authorized_meeting_ids 반영
→ 검색 응답·Tool 결과를 ScratchPad에 반영
→ Checkpoint
→ 후속 작업이 있으면 LLM 판단으로 복귀

회의록 질문
→ Tool 2 허용 ID 검사·원문 조회
→ 컨텍스트 조립
→ LLM 답변
→ 답변·Tool 결과를 ScratchPad에 반영
→ Checkpoint
→ 후속 작업이 없을 때 END 후 Agent 요청 대기
```

검색 후보가 여러 개이면 같은 스레드에서 Human in the Loop로 선택하고 실행을 재개한다. 검색·질문 Agent Graph에는 `none`, `search`, `question`과 Subgraph 내부의 개념적 제어 State가 있지만, 이를 같은 이름의 지속 코드 변수로 저장하지 않는다. Search 또는 Question 결과가 Graph Runtime에 진입하면 상위 State를 `search/question → none`으로 정리하고 다음 Edge를 선택한다.

### State 소유 구조

```python
RecordingModalState = {
    "recording_state": "recording",
}

AgentState = {
    "ScratchPad": [...],
    "authorized_meeting_ids": ["meeting-123"],
    "recording_modal_status": "healthy",
}
```

| 값 | 현재 소유 위치 | 역할 |
|---|---|---|
| `recording_state` | 녹화 임베디드 상단바 모달 | 실제 녹화 진행 상태와 허용 동작 판단 |
| `recording_modal_status` | Agent 오케스트레이터 | 모달 정상 응답은 `healthy`, 연결·실행 오류는 `error` |
| `ScratchPad` | Agent 오케스트레이터 | 사용자 목표, LLM 답변, Tool 결과와 후속 판단에 필요한 작업 기록 |
| `authorized_meeting_ids` | 현재는 Agent 오케스트레이터 | Tool 1 검증을 통과한 회의록 ID 허용 목록 |

모달 내부의 `recording_state`는 Agent Checkpoint에 저장하지 않는다. Agent는 모달이 보낸 결과 신호를 `recording_modal_status`에 반영할 뿐 실제 녹화 상태를 중복 저장하거나 변경하지 않는다.

`authorized_meeting_ids`의 조회·검증·갱신 책임을 향후 Tool 계층의 Repository로 옮기는 방안은 검토 중이며, 확정 전까지는 [[2-1. 회의록 에이전트 현재 구현 상세 설계]]의 Agent State 소유 기준을 따른다.

### 녹화 Trigger·모달과 Agent Tool의 구분

회의 시작·일시정지·재개·종료는 Agent Tool이 아니다.

```text
명시적 녹화 Trigger 또는 상단바 버튼
→ 오케스트레이터의 고정 Trigger 코드
→ 기존 UI와 동일한 녹화 모달 로직
→ 모달의 recording_state 검사
→ 백엔드 인증·생성자 권한·실제 회의 상태 검사와 실행
→ 성공 시 모달이 recording_state 갱신
→ 모달 결과 신호
→ 오케스트레이터가 recording_modal_status만 갱신
```

이 과정은 LLM이 기능을 선택하는 Agent 과정이 아니라 **결정적 Workflow**다.

Agent에 연결되는 Tool은 두 개다.

| Tool | Agent에서 보이는 역할 | 실제 실행 |
|---|---|---|
| **Tool 1 — 검색·선택** | 관련 회의록을 검색하고 사용할 ID 확정 | 백엔드 권한 필터·후보 검색·ID 검증, 필요한 HITL과 추가·대체 |
| **Tool 2 — 원문 조회** | 허용된 ID의 회의록 원문 조회 | 백엔드가 `authorized_meeting_ids` 포함 여부를 검사하고 원문 조회 |

회의록 확정·공유 Tool은 사용하지 않는다. 녹화 종료는 모달의 `recording_state`가 `stop → none`으로 전이되면서 완료된다.

### 실행 관계

```text
회의록 Agent 서버
├─ LLM
├─ Graph·오케스트레이터
├─ Agent State
│  ├─ ScratchPad
│  ├─ authorized_meeting_ids
│  └─ recording_modal_status
└─ Agent Tool
   ├─ Tool 1 · 검색·선택
   └─ Tool 2 · 원문 조회

녹화 임베디드 상단바 모달
└─ recording_state

녹화 Trigger·UI
→ 모달
→ 기존 녹화 백엔드

Agent Tool
→ Tool 뒤의 검색·조회 백엔드
```

두 영역은 서로의 State를 변경하지 않는다.

- 녹화 Trigger·모달은 `authorized_meeting_ids`를 읽거나 변경하지 않는다.
- 검색·질문은 모달의 `recording_state`와 Agent의 `recording_modal_status`를 변경하지 않는다.
- 따라서 녹화가 `recording` 또는 `pause`여도 과거 회의록 검색·질문을 처리할 수 있다.

검색·질문 Agent Graph 안의 `none`, `search`, `question`은 현재 실행 중인 Node와 Edge를 설명하는 State이며 모달의 `recording_state`와 별개다. Agent가 Search·Question 사이를 반복하더라도 녹화 Workflow State에는 영향을 주지 않는다.

### 동일 스레드의 실행 순서

현재는 동일한 전용 스레드의 Agent 요청을 기존 실행 큐에서 접수 순서대로 처리한다고 가정한다. 따라서 검색·HITL을 구분하기 위한 별도의 `run_id`를 두지 않는다.

- 검색 요청과 후보 선택은 같은 스레드에서 하나씩 처리한다.
- `authorized_meeting_ids` 추가·대체도 큐 순서대로 반영한다.
- 별도 회의록 집합을 사용하려면 새 전용 스레드에서 회의 에이전트를 다시 호출한다.

한 스레드에서 같은 종류의 비동기 장기 업무를 여러 개 동시에 실행해야 할 때만 `run_id`나 별도 실행 식별자를 다시 검토한다.

### 장점

- 녹화 중에도 검색·질문을 실행할 수 있으며 어느 쪽도 다른 쪽의 State를 덮어쓰지 않는다.
- 모달과 Agent에 실제 녹화 상태를 중복 저장하지 않는다.
- `retrieval_state`와 `share`는 사용하지 않는다. `search`, `question`은 Graph 모델의 개념적 State로 사용하되 같은 이름의 **지속 코드 변수**는 만들지 않는다.
- 녹화 Workflow와 LLM Agent 업무의 책임 경계가 명확하다.
- Agent Tool을 검색·선택과 원문 조회 두 개로 단순하게 유지한다.
- 별도의 Subgraph·`workflow_id`·`run_id` 없이 현재 요구사항을 충족한다.

### 한계

- 모달 결과 신호와 `recording_modal_status` 사이의 이벤트 동기화 규칙이 필요하다.
- 같은 스레드에서 검색·HITL을 실제로 병렬 실행하게 되면 실행 식별자와 동시성 제어가 필요하다.
- `authorized_meeting_ids`를 동시에 추가·대체하는 구조로 확장되면 version·잠금·멱등성 정책이 필요하다.
- 향후 다른 장기 업무가 추가되면 그 업무의 실제 소유 영역에 별도 State를 둘지 다시 판단해야 한다.

## 5. 세 방안 비교

| 방안 | 구조 | 현재 적합성 | 핵심 한계 |
|---|---|---:|---|
| 1안. Agent에 지속 State 두 개 | Agent가 녹화 State와 검색 State 모두 소유 | 낮음 | 모달 State 중복과 불필요한 검색 State |
| 2안. 조합 State | 녹화·검색을 하나의 값으로 결합 | 낮음 | 조합 폭발과 독립 업무의 강한 결합 |
| 3안. 소유 영역 분리 | 모달은 녹화 State, Agent는 `ScratchPad`·검증 ID·모달 상태만 관리 | 높음 | 향후 실제 병렬 실행 시 동시성 설계 필요 |

## 6. 현재 채택 구조

현재 회의록 에이전트는 **3안**을 채택한다.

1. 실제 `recording_state`는 녹화 임베디드 상단바 모달이 소유한다.
2. Agent 오케스트레이터는 `ScratchPad`, `authorized_meeting_ids`, `recording_modal_status`를 관리한다.
3. 회의 녹화는 고정 Trigger·모달·백엔드가 실행하는 결정적 Workflow다.
4. 검색·질문에는 `none`, `search`, `question`이라는 개념적 Graph State를 사용하지만 같은 이름의 지속 코드 변수는 두지 않는다.
5. Agent Tool은 Tool 1 검색·선택과 Tool 2 원문 조회 두 개만 사용한다.
6. 녹화 종료는 `stop → none`이며 `share` State나 확정·공유 Tool을 사용하지 않는다.
7. 동일 스레드의 Agent 요청은 큐에서 순차 처리하며 현재는 별도의 `workflow_id`와 `run_id`를 두지 않는다.
8. 각 Search·Question 결과를 `ScratchPad`에 반영하고 Checkpoint를 저장한 뒤, 후속 작업이 있으면 LLM 판단으로 복귀하고 사용자 목표가 달성되었을 때만 END를 확정한다.

> **결론:** 병렬성을 하나의 복합 State로 표현하지 않는다. 실제 녹화 상태는 모달에, `ScratchPad`와 검증된 회의록 ID는 Agent에 둔다. 검색·질문의 `none`, `search`, `question`은 Graph 실행 경로를 설명하되 지속 코드 변수로 저장하지 않는다. 각 Subgraph 뒤에는 Checkpoint와 후속 작업 Condition을 거쳐 Agent 제어 루프를 계속하거나 END를 확정한다. 서로 다른 소유 영역이 상대방의 State를 읽거나 변경하지 않게 함으로써 녹화와 과거 회의록 활용을 함께 허용한다.
