# 회의 녹화와 회의록 질의의 병렬 State 설계 조사

## 1. 조사 배경

기존 회의록 에이전트 설계에서는 다음 두 업무 과정을 서로 엄격하게 분리했다.

- 회의 녹화 과정
- 기존 회의록을 검색하고 질문하는 과정

단일 `workflow_state`를 사용하여 회의 녹화 과정에 진입하면 녹화가 끝날 때까지 회의록 검색 과정으로 이동하지 못하게 했다. 이 구조는 두 과정이 서로의 진행 상태를 침범하지 못하게 한다는 장점이 있지만, 다음과 같은 정상적인 사용자 요청도 막는다.

```text
현재 회의를 녹화하는 중
→ 사용자가 완전히 다른 과거 회의록에 관해 질문
→ 녹화 과정이 진행 중이므로 검색 Tool이 실행을 거부
```

이를 해결하기 위해 `none`을 공통 질문 입력 지점으로 사용하는 방안도 생각할 수 있다. 그러나 질문을 받기 위해 녹화 중인 `workflow_state`를 `none`으로 바꾸면 이후 일시정지·재개·종료 Skill이 현재 상태를 `recording`으로 인식하지 못한다.

```text
recording
→ 과거 회의록 질문을 받기 위해 none으로 변경
→ 사용자가 회의 일시정지 요청
→ /meeting-pause는 recording만 허용
→ STATE_CONFLICT 발생
```

즉, 문제의 원인은 `none`의 전이 규칙이라기보다 **서로 독립적으로 진행될 수 있는 두 업무 상태를 하나의 `workflow_state`에 넣었다는 것**에 있다.

이 문서는 다음 대안을 비교하고, 회의 녹화와 기존 회의록 질의를 서로 간섭시키지 않으면서 동시에 진행하기 위한 구조를 제안한다.

1. State를 두 개로 나누는 방법
2. `recording/searching`처럼 두 상태를 하나의 문자열로 조합하는 방법
3. 병렬·직교 State 영역과 업무별 Subgraph를 사용하는 방법

## 2. 상태 머신 이론에서의 해석

회의 녹화 상태와 회의록 질의 상태는 어느 하나가 다른 하나의 하위 단계가 아니다.

```text
회의 녹화 상태
idle → recording ↔ paused → stopped → publishing → idle

회의록 질의 상태
idle → searching → selecting → ready ↔ answering → idle
```

두 과정은 서로 다른 사건에 반응하고, 한쪽의 상태가 바뀌어도 다른 쪽의 상태는 유지될 수 있다.

```text
회의 녹화 중 과거 회의록 질문
recording 상태 유지
질의 상태만 idle → searching → ready → answering

질문 도중 회의 일시정지
질의 상태 유지
녹화 상태만 recording → paused
```

상태 머신 이론에서는 이와 같이 여러 상태 영역이 동시에 활성화되는 구조를 **병렬 상태(Parallel States)** 또는 **직교 영역(Orthogonal Regions)**이라고 한다.

W3C SCXML은 병렬 상태에 진입하면 모든 자식 상태 영역이 함께 활성화되며, 하나의 이벤트에 대해 각 영역이 독립적으로 전이하거나 해당 이벤트를 무시할 수 있다고 정의한다. 여기서 병렬은 반드시 여러 OS Thread가 물리적으로 동시에 실행된다는 뜻이 아니다. 여러 상태가 같은 시점에 유효하며, 이벤트 처리는 정해진 순서로 수행할 수도 있다.

- [W3C SCXML - Parallel States](https://www.w3.org/TR/scxml/)
- [XState - Final, History and Parallel States](https://stately.ai/docs/xstate/v6/final-history-parallel)

현재 회의록 에이전트의 두 과정은 이러한 직교 상태 영역으로 해석하는 것이 자연스럽다.

## 3. `none`을 통합 입력 지점으로 사용하면 안 되는 이유

`none`과 같은 업무 State는 에이전트가 사용자 입력을 받을 수 있는지를 나타내는 값이 아니다. `none`은 특정 상태 영역에서 현재 진행 중인 업무가 없다는 뜻이어야 한다.

사용자 입력은 State와 별도로 상위 입력 Router가 항상 받을 수 있어야 한다.

```text
사용자 입력·UI 이벤트
→ 상위 입력 Router
→ 녹화 명령이면 Recording 영역으로 전달
→ 회의록 검색·질문이면 Retrieval 영역으로 전달
→ 복합 요청이면 여러 이벤트로 분해하여 실행
```

따라서 회의 녹화 도중 과거 회의록 질문을 받더라도 녹화 State를 `none`으로 변경하지 않는다.

```text
recording_state = recording
retrieval_state = answering
```

이 상태에서 일시정지 이벤트가 들어오면 다음처럼 녹화 영역만 변경한다.

```text
recording_state: recording → paused
retrieval_state: answering 유지
```

결론적으로 **입력을 받을 수 있는가**와 **각 업무가 어느 단계인가**는 분리해야 한다.

## 4. 대안 1 — State를 두 개로 분리

### 4-1. 기본 구조

단순한 `state_1`, `state_2`보다는 각 상태의 책임이 드러나는 이름을 사용한다.

```python
class MeetingAgentState(TypedDict):
    messages: list

    recording_state: Literal[
        "idle",
        "recording",
        "paused",
        "stopped",
        "publishing",
    ]

    retrieval_state: Literal[
        "idle",
        "searching",
        "selecting",
        "ready",
        "answering",
    ]

    authorized_meeting_ids: list[str]
    search_return_state: Literal["ready", "answering"] | None
```

초기값은 다음과 같다.

```text
recording_state = idle
retrieval_state = idle
```

### 4-2. 장점

- 회의 녹화와 회의록 질의가 서로의 State를 덮어쓰지 않는다.
- 두 과정이 동시에 활성화될 수 있다.
- 녹화 Skill은 `recording_state`만 검사할 수 있다.
- 검색 Tool은 `retrieval_state`만 검사할 수 있다.
- 각 상태 영역의 State 전이도를 독립적으로 작성하고 검증할 수 있다.
- 새로운 업무 영역이 추가될 때 별도의 State 필드를 추가할 수 있다.
- 어떤 Skill·Tool이 어느 업무 영역에 의존하는지 명확해진다.
- Node가 자신이 담당하는 State 키의 부분 업데이트만 반환할 수 있다.

LangGraph의 State는 여러 개의 키로 구성할 수 있으며, Node가 반환한 부분 업데이트는 각 키의 reducer 규칙에 따라 적용된다. 따라서 녹화 Node는 `recording_state`만, 검색 Node는 `retrieval_state`만 갱신하는 구조를 만들 수 있다.

- [LangGraph Graph API - State와 Reducer](https://docs.langchain.com/oss/python/langgraph/graph-api)

### 4-3. 한계점

- 전체 시스템 상태는 두 상태 영역의 조합으로 표현된다.
- 양쪽 과정이 `messages`와 같은 공유 필드를 동시에 수정하면 갱신 규칙이 필요하다.
- Tool이 어떤 상태 영역을 읽고 수정할 수 있는지 정하지 않으면 결합도가 다시 높아질 수 있다.
- Checkpoint에서 전체 State를 복구할지 한쪽 영역만 복구할지 구분해야 한다.
- 이름 없이 `state_1`, `state_2`로 만들면 시간이 지나면서 책임이 모호해진다.

이러한 한계는 State를 분리해서 생기는 본질적인 문제라기보다 **공유 데이터의 소유권과 갱신 규칙이 없을 때 발생하는 문제**다.

## 5. 대안 2 — `recording/searching` 형식의 조합 State

### 5-1. 기본 구조

두 상태를 하나의 문자열이나 enum 값으로 표현한다.

```text
idle/idle
recording/idle
recording/searching
paused/answering
stopped/ready
```

### 5-2. 장점

- 현재 두 상태를 한 줄로 표시하기 쉽다.
- 로그나 UI에서 전체 상태 조합을 빠르게 확인할 수 있다.
- 모든 허용 조합을 하나의 enum으로 정의하면 존재해서는 안 되는 조합을 차단할 수 있다.

### 5-3. 한계점

#### 상태 조합 폭발

```text
녹화 상태 5개 × 검색 상태 5개
= 총 25개 조합

세 번째 업무 영역에 상태가 4개 추가
5 × 5 × 4
= 총 100개 조합
```

업무 영역과 상태가 늘어날수록 관리해야 할 조합이 곱셈으로 증가한다.

#### 문자열 파싱 의존

```python
recording_state, retrieval_state = workflow_state.split("/")
```

- Tool마다 파싱 로직이 중복될 수 있다.
- 문자열의 순서와 형식에 의존한다.
- 일부 Tool은 앞부분만, 다른 Tool은 뒷부분만 검사하게 된다.
- 오타나 잘못된 조합이 실행 전 검증되지 않을 수 있다.
- 새로운 업무 영역을 추가하면 기존 파싱 코드가 영향을 받는다.
- 한쪽 상태만 갱신하려 해도 전체 문자열을 교체해야 한다.
- 동시 갱신 시 한쪽 변경이 다른 쪽 변경을 덮어쓸 수 있다.

### 5-4. 적절한 사용 범위

슬래시 형식은 실제 State의 원본보다는 로그·UI·다이어그램을 위한 **파생 표시 값**으로 사용하는 것이 적절하다.

```text
실제 저장
recording_state = recording
retrieval_state = searching

표시용 문자열
recording/searching
```

## 6. 권장 구조 — 이름 있는 직교 State와 업무별 Subgraph

두 대안 중에서는 State를 분리하는 1안이 적합하다. 다만 단순히 State 필드만 두 개 만드는 데서 끝내지 않고, 다음과 같이 Root Graph와 두 업무 Subgraph로 구성하는 것을 권장한다.

```text
회의록 에이전트 Root Graph
├─ 입력 Router
├─ Recording Subgraph
│  └─ recording 영역 소유
├─ Retrieval Subgraph
│  └─ retrieval 영역 소유
└─ 공통 응답·messages 조립
```

권장 State 구조는 다음과 같다.

```python
class RecordingState(TypedDict):
    status: Literal[
        "idle", "recording", "paused", "stopped", "publishing"
    ]
    active_meeting_id: str | None


class RetrievalState(TypedDict):
    status: Literal[
        "idle", "searching", "selecting", "ready", "answering"
    ]
    authorized_meeting_ids: list[str]
    search_return_state: Literal["ready", "answering"] | None


class RootState(TypedDict):
    messages: list
    recording: RecordingState
    retrieval: RetrievalState
```

이 구조는 두 개의 완전히 무관한 시스템을 만든다는 뜻이 아니다.

- Root State와 사용자 스레드는 하나로 유지할 수 있다.
- Root Checkpoint에 두 상태 영역을 함께 저장할 수 있다.
- 내부에는 독립된 두 상태 머신이 동시에 활성화된다.
- 각 Skill·Tool은 자신에게 필요한 상태 영역만 읽는다.
- 입력 Router가 이벤트를 어느 영역에 전달할지 결정한다.

LangGraph의 Subgraph는 독립된 Graph를 부모 Graph의 Node로 사용할 수 있다. 부모와 Subgraph가 다른 State Schema를 사용할 때는 Wrapper가 부모 State를 Subgraph 입력으로 변환하고 결과를 다시 부모 State로 매핑할 수 있다. 이 방식은 각 업무의 사적인 State와 공유 State의 경계를 명시하는 데 적합하다.

- [LangGraph Subgraphs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)

## 7. 모든 Tool이 두 State를 검사해야 하는가

모든 Tool이 양쪽 State를 검사할 필요는 없다. 오히려 모든 Tool이 두 상태를 읽으면 분리한 상태 영역이 다시 강하게 결합된다.

각 Skill·Tool은 실제 실행에 필요한 상태 영역만 검사해야 한다.

| 실행 기능 | 주로 검사할 상태 |
|---|---|
| `/meeting-start` | `recording.status` |
| `/meeting-pause` | `recording.status` |
| `/meeting-resume` | `recording.status` |
| `/meeting-stop` | `recording.status` |
| 회의록 확정·공유 | `recording.status` |
| 회의록 후보 검색 | `retrieval.status` |
| 회의록 ID 확정 | `retrieval.status` |
| 회의록 원문 조회 | `retrieval.status`, `authorized_meeting_ids` |
| 단순 메시지 포맷 변환 | 업무 State 검사가 필요하지 않을 수 있음 |
| 두 과정의 데이터를 함께 사용하는 기능 | 실제로 필요한 두 상태 모두 검사 |

예를 들어 회의록 검색 Tool은 녹화 상태와 무관하게 검색할 수 있어야 하므로 `retrieval.status`만 검사한다.

```python
if retrieval.status in {"idle", "ready", "answering"}:
    execute_search()
else:
    reject("이미 다른 검색·선택 작업이 진행 중입니다.")
```

따라서 다음 상태 조합은 오류가 아니라 정상 상태다.

```text
recording.status = recording
retrieval.status = searching
```

State Machine의 Guard는 전이를 허용할지를 판단하는 결정적인 조건이다. 여러 상태 영역의 조건이 실제로 필요할 때만 `and`, `or`, `not`과 같은 조합 조건을 사용한다.

- [XState Guards](https://stately.ai/docs/guards)

## 8. Tool 내부 State 조건의 중복을 줄이는 방법

기존 설계의 다음 원칙은 유지한다.

> State 조건과 권한은 LLM이 아니라 Skill·Tool이 호출하는 신뢰된 백엔드가 검사한다.

다만 모든 Tool 구현에 비슷한 `if`문을 복사하지 않고 공통 Guard 또는 Policy 모듈을 두는 것이 좋다.

```python
TOOL_POLICIES = {
    "meeting_pause": {
        "recording.status": {"recording"},
    },
    "meeting_stop": {
        "recording.status": {"recording", "paused"},
    },
    "minutes_search": {
        "retrieval.status": {"idle", "ready", "answering"},
    },
    "minutes_fetch": {
        "retrieval.status": {"ready", "answering"},
        "requires_authorized_id": True,
    },
}
```

각 Tool의 백엔드는 공통 검사기를 호출한다.

```python
guard_result = enforce_tool_policy(
    tool_name="minutes_search",
    state=state,
)

if guard_result.rejected:
    return guard_result

return execute_search()
```

이 구조에는 다음 장점이 있다.

- State 조건을 백엔드가 결정적으로 강제한다.
- LLM 프롬프트와 Tool Description에 조건을 반복하지 않는다.
- Tool마다 긴 조건문을 복사하지 않는다.
- 각 Tool이 어느 상태 영역에 의존하는지 명시할 수 있다.
- 정책 표를 이용해 자동 테스트를 생성할 수 있다.
- 반려 코드와 반려 결과 Schema를 통일할 수 있다.

## 9. 양쪽 과정이 사용하는 공유 Tool 처리

공유 Tool이라고 해서 반드시 두 상태 영역을 모두 검사하는 것은 아니다. 실제 의존성에 따라 다음 세 종류로 구분한다.

### 9-1. 업무 State와 무관한 Tool

예시는 시간 조회, 단순 포맷 변환, 고정 안내 데이터 생성 등이다.

```text
업무 State 검사 불필요
```

### 9-2. 한쪽 업무 상태만 필요한 Tool

예를 들어 회의록 원문 조회가 기존 회의록 질의에만 사용된다면 `retrieval` 영역만 검사한다. 같은 스레드에서 녹화가 진행 중인지 여부는 이 Tool의 실행 조건이 아니다.

### 9-3. 두 업무 상태가 실제로 필요한 Tool

예를 들어 현재 녹화 중인 회의와 과거 회의록을 함께 비교하는 기능은 양쪽 상태와 데이터가 모두 필요할 수 있다.

```python
requires:
    recording.status in {"recording", "paused"}
    retrieval.status in {"ready", "answering"}
```

이러한 기능만 두 상태를 모두 검사한다.

### 9-4. 백엔드는 공유하지만 업무 조건이 다른 경우

공통 백엔드 기능을 여러 과정에서 사용하지만 허용 State와 입출력 계약이 다르면 업무별 Adapter를 둔다.

```text
공통 백엔드 기능
├─ Recording Tool Adapter
│  └─ recording Guard
└─ Retrieval Tool Adapter
   └─ retrieval Guard
```

백엔드 구현은 재사용하되 Tool 계약과 Guard는 업무별로 분리하는 방식이다.

## 10. Tool 호환성을 위한 계약

각 Skill·Tool에 자신이 읽고 쓰는 State 영역을 선언하는 것이 좋다.

```yaml
name: minutes_search
reads:
  - retrieval.status
  - authenticated_user
writes:
  - retrieval.status
  - retrieval.candidate_ids
allowed_states:
  retrieval.status:
    - idle
    - ready
    - answering
outcomes:
  - CANDIDATES_FOUND
  - NO_CANDIDATES
  - STATE_CONFLICT
```

이 계약을 사용하면 다음 문제를 줄일 수 있다.

- 녹화 Tool이 실수로 `retrieval`을 수정하는 문제
- 검색 Tool이 실수로 `recording`을 수정하는 문제
- 두 Tool이 같은 필드를 서로 다른 방식으로 덮어쓰는 문제
- 공유 필드의 reducer 정책이 정의되지 않은 문제
- 어떤 Tool 조합을 병렬 실행할 수 있는지 알 수 없는 문제

특히 `reads`, `writes`, `allowed_states`, `outcomes`를 기준으로 Tool 단위 테스트와 Tool 조합 테스트를 만들 수 있다.

## 11. 동시 실행과 이벤트 처리

두 상태 영역이 동시에 활성화되어도 모든 백엔드 작업을 물리적으로 동시에 실행할 필요는 없다. 한 사용자 스레드에서 발생한 이벤트를 결정적인 순서로 직렬 처리하면 Race Condition을 줄일 수 있다.

```text
이벤트 큐
→ 이벤트 하나 선택
→ 관련 State 영역 검사
→ 백엔드 실행
→ 해당 영역만 State 갱신
→ Checkpoint
→ 다음 이벤트 처리
```

사용자가 질문을 보내는 순간 임베디드 바에서 일시정지를 누른 경우 다음처럼 처리할 수 있다.

```text
1. MEETING_PAUSED 처리
   recording.status만 갱신

2. MINUTES_QUESTION 처리
   retrieval.status와 messages 갱신
```

두 이벤트는 서로 다른 상태 영역을 수정하므로 업무 State 충돌이 발생하지 않는다.

다만 두 영역이 모두 `messages`를 수정한다면 다음 규칙이 필요하다.

- 메시지마다 고유 ID 부여
- 이벤트 발생 순서 또는 서버 수신 순서 기록
- append와 overwrite 기준 정의
- 동일 메시지의 중복 반영 방지
- 병렬 Node 결과를 합치는 reducer 정의

LangGraph에서는 State의 각 키에 독립적인 reducer를 지정할 수 있으며, 병렬 Branch의 결과를 누적하거나 특정 메시지를 ID 기준으로 갱신할 수 있다.

- [LangGraph Graph API - Reducers](https://docs.langchain.com/oss/python/langgraph/graph-api)
- [LangGraph Graph API - Parallel Branches](https://docs.langchain.com/oss/python/langgraph/use-graph-api)

## 12. Checkpoint와 복구 시 주의점

Root Checkpoint에는 두 상태 영역을 함께 저장할 수 있다.

```json
{
  "recording": {
    "status": "recording",
    "active_meeting_id": "meeting-current"
  },
  "retrieval": {
    "status": "answering",
    "authorized_meeting_ids": ["meeting-old"]
  }
}
```

문제는 한쪽 과정이 실패했을 때 전체 Checkpoint를 과거 시점으로 되돌리는 경우다.

```text
과거 회의록 검색 실패
→ 전체 State를 이전 Checkpoint로 복구
→ 이미 성공한 녹화 일시정지까지 되돌아갈 위험
```

따라서 복구와 재시도는 업무 영역 단위로 수행해야 한다.

```text
검색 Tool 실패
→ retrieval 영역의 실패 Node만 재시도
→ recording 영역은 현재 상태 유지
```

권장 원칙은 다음과 같다.

- Checkpoint는 Root State 전체의 일관된 Snapshot을 저장한다.
- 실패한 업무의 Node와 State 영역만 재시도한다.
- 다른 영역의 성공한 State 업데이트는 유지한다.
- 외부 부수 효과를 가진 Skill·Tool은 멱등성 키를 사용한다.
- 전체 State를 과거로 되돌리는 기능은 사용자 승인이나 명시적 복구 정책이 있을 때만 사용한다.

LangGraph의 Checkpointer는 Thread별 StateSnapshot을 저장하며, 실패 후 특정 단계부터 재실행하거나 Subgraph State를 확인할 수 있다. 다만 실제 복구 범위와 외부 부수 효과의 취소는 별도 설계가 필요하다.

- [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

## 13. Graph와 State 전이도 작성 방법

병렬 상태 구조를 적용하면 Agent Graph와 State 전이도를 다음처럼 분리한다.

### 13-1. Root Agent Graph

Root Agent Graph에는 상위 입력과 업무 라우팅 관계를 표시한다.

```text
사용자 입력·UI 이벤트
→ 입력 Router
├→ Recording Subgraph
└→ Retrieval Subgraph
```

### 13-2. Recording State 전이도

```text
idle
→ recording
↔ paused
→ stopped
→ publishing
→ idle
```

### 13-3. Retrieval State 전이도

```text
idle
→ searching
→ selecting
→ ready
→ answering
↔ searching
→ idle
```

### 13-4. 동시 상태 예시

다이어그램이나 표에서는 두 상태를 조합하여 현재 전체 상태를 예시로 보여줄 수 있다.

```text
(recording, idle)
(recording, searching)
(paused, answering)
(stopped, ready)
```

이 조합은 별도의 단일 State 값이 아니라 두 직교 상태 영역의 현재 Snapshot이다.

## 14. 설계 결정 권고안

1. 기존 단일 `workflow_state`를 두 개의 직교 상태 영역으로 분리한다.
2. 필드 이름은 `state_1`, `state_2`가 아니라 `recording`, `retrieval`처럼 책임을 드러내게 한다.
3. 각 영역의 초기·대기 상태는 각각 `idle`로 둔다.
4. `none`을 통합 질문 입력 지점으로 사용하지 않는다.
5. Root Agent의 입력 Router는 어느 업무 State에서도 사용자 입력을 받을 수 있게 한다.
6. 녹화 Skill과 확정·공유 Tool은 `recording` 영역만 검사한다.
7. 검색·ID 확정·원문 조회 Tool은 `retrieval` 영역만 검사한다.
8. 두 과정의 데이터가 실제로 필요한 Tool만 두 상태 영역을 모두 검사한다.
9. Tool 내부에서는 공통 Policy Guard를 호출하여 조건 중복을 줄인다.
10. 각 Tool은 `reads`, `writes`, `allowed_states`, `outcomes` 계약을 선언한다.
11. Recording과 Retrieval을 별도의 Subgraph로 구성하고 Root Graph가 입력을 라우팅한다.
12. `recording/searching`과 같은 슬래시 표현은 로그와 다이어그램 표시용으로만 사용한다.
13. Checkpoint는 두 상태를 함께 저장하되 재시도·복구는 업무 영역 단위로 수행한다.
14. `messages`와 같이 공유되는 필드에는 reducer와 순서 정책을 별도로 정의한다.

## 핵심 정리

> 회의 녹화 과정과 기존 회의록 질의 과정은 어느 하나가 다른 하나를 대체하는 단일 상태 흐름이 아니라, 동시에 활성화될 수 있는 두 개의 직교 상태 영역이다. 따라서 하나의 `workflow_state`를 번갈아 변경하거나 `recording/searching` 같은 조합 문자열을 원본 State로 저장하기보다, 하나의 Root State 안에 `recording`과 `retrieval`이라는 이름 있는 상태 영역을 따로 두는 것이 적합하다. 사용자 입력은 `none` State가 아니라 상위 입력 Router가 항상 받고, 각 Skill·Tool은 자신이 실제로 의존하는 상태 영역만 검사해야 한다. 공통 Policy Guard와 Tool의 `reads`·`writes` 계약을 사용하면 Tool별 조건 중복과 호환성 문제를 줄일 수 있으며, Checkpoint는 전체 Snapshot을 저장하되 실패한 업무 영역만 재시도해야 한다.
