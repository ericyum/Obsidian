# 회의 녹화와 회의록 질의의 병렬 State 설계 조사

## 문제

회의를 녹화하는 도중에도 사용자는 과거 회의록을 검색하고 질문할 수 있어야 한다. 검색을 위해 녹화 State를 `none`으로 바꾸면 이후 일시정지·재개·종료가 실패하므로, 두 과정이 서로의 진행 상태를 덮어쓰지 않는 구조가 필요하다.

검토할 방안은 다음 세 가지다.

1. State를 두 개로 분리
2. 두 상태를 하나의 조합 문자열로 저장
3. 녹화만 지속 State로 두고 검색·질의는 요청마다 독립 실행

---

## 1안 — State를 두 개로 분리

### 구조

녹화와 검색·질의의 현재 상태를 별도 필드에 저장한다.

```text
recording_state = recording
retrieval_state = searching
```

### 장점

- 녹화와 검색이 동시에 진행될 수 있다.
- 검색이 시작되어도 녹화 State가 유지되므로 일시정지·재개·종료가 정상 작동한다.
- 녹화 Skill은 `recording_state`, 검색 Tool은 `retrieval_state`만 검사할 수 있다.
- 한쪽 작업의 실패와 재시도가 다른 쪽 상태에 영향을 주지 않게 설계할 수 있다.
- 두 과정이 모두 장시간 이어지는 업무라면 각각의 진행 단계를 명확히 추적할 수 있다.

### 한계

- 두 State를 항상 유지하고 Checkpoint에 함께 저장해야 한다.
- `messages`처럼 양쪽이 함께 수정하는 데이터에는 병합·순서 규칙이 필요하다.
- 각 Tool이 어느 State를 읽고 수정하는지 소유권을 명확히 정해야 한다.
- 검색·질의가 실제로는 짧은 일회성 작업이라면 불필요한 전역 State를 계속 유지하게 된다.
- 검색 요청을 여러 개 동시에 처리하려면 하나의 `retrieval_state`만으로는 각 요청을 구분하기 어렵다.

### 적합한 경우

녹화와 검색·질의가 모두 여러 사용자 입력에 걸쳐 오래 지속되고, 각각의 현재 단계를 계속 복구해야 할 때 적합하다.

## 2안 — `recording/searching` 조합 State

### 구조

두 상태를 하나의 문자열이나 enum 값으로 저장한다.

```text
workflow_state = recording/searching
workflow_state = paused/answering
```

### 장점

- 현재 두 과정의 상태를 한 줄로 확인할 수 있다.
- 기존의 단일 `workflow_state` 필드를 유지하기 쉽다.
- 로그, 화면, 다이어그램에서 전체 상태를 간단하게 표시할 수 있다.
- 허용할 조합을 미리 열거하면 잘못된 조합을 차단할 수 있다.

### 한계

- Tool마다 문자열을 분리해서 필요한 부분을 검사해야 한다.
- 한쪽 상태만 바꿔도 전체 문자열을 다시 만들어야 한다.
- 녹화와 검색이 동시에 상태를 갱신하면 마지막 저장이 다른 쪽 변경을 덮어쓸 수 있다.
- 상태 수가 늘수록 가능한 조합이 곱셈으로 증가한다.

```text
녹화 상태 5개 × 검색 상태 5개 = 25개 조합
```

- 세 번째 업무 영역이 추가되면 기존 문자열 형식과 모든 파싱 코드를 수정해야 한다.
- Tool마다 앞부분, 뒷부분 또는 전체 조합을 서로 다르게 검사하면 호환성과 유지보수가 나빠진다.

### 적합한 경우

업무 영역과 상태 수가 매우 적고 앞으로 거의 늘어나지 않을 때만 실제 State로 사용할 수 있다. 일반적으로는 실제 저장 방식보다 다음과 같은 **표시용 값**으로 사용하는 편이 안전하다.

```text
실제 저장: recording_state, retrieval_state
표시용: recording/searching
```

## 3안 — 지속형 녹화 State + 요청형 Retrieval Run

### 구조

두 과정을 같은 종류의 State Machine으로 취급하지 않는다.

- 회의 녹화는 장시간 이어지므로 지속 State Machine으로 관리한다.
- 회의록 검색·질의는 사용자 요청마다 독립된 `Retrieval Run`을 생성한다.
- Retrieval Run이 끝나면 실행 상태는 종료하고, 계속 필요한 ID와 답변만 저장한다.

```text
Main Agent
├─ recording_status           지속 State
├─ authorized_meeting_ids     계속 사용할 데이터
└─ retrieval_run_ID           요청할 때만 생성되는 임시 실행
```

회의 녹화 중 질문이 들어오면 다음처럼 처리한다.

```text
recording_status = recording

retrieval_run_123
검색 → 회의록 선택 → 답변 → 실행 종료
```

후보가 여러 개라면 해당 Retrieval Run만 Human in the Loop에서 대기하고, 녹화 State는 그대로 유지한다.

### 장점

- 전역 `retrieval_state`를 계속 유지할 필요가 없다.
- 검색이나 질문이 녹화 State를 덮어쓸 수 없다.
- 검색·질의 요청마다 `run_id`가 있으므로 여러 요청을 서로 구분할 수 있다.
- 검색 실패와 재시도가 녹화 Checkpoint에 영향을 주지 않는다.
- 각 질의가 끝나면 임시 실행 상태를 정리하므로 전체 State가 단순해진다.
- 향후 Main Agent가 여러 전문 Agent에게 요청 단위로 일을 전달하는 구조와 잘 맞는다.

### 한계

- 요청마다 `run_id`를 생성하고 결과·Human in the Loop 응답을 올바른 실행에 연결해야 한다.
- 여러 실행이 동시에 답변하면 `messages`의 순서와 병합 규칙이 필요하다.
- 임시 후보 ID와 확정된 `authorized_meeting_ids`를 구분해야 한다.
- 질의 자체가 여러 사용자 입력에 걸친 장기 업무로 발전하면 해당 Retrieval Run에 별도의 지속 State가 필요하다.
- 녹화와 질의 양쪽 데이터를 함께 사용하는 기능은 Main Agent가 두 실행 결과를 조정해야 한다.

### 적합한 경우

녹화는 오래 지속되지만 검색·질의는 요청마다 짧게 실행되고 끝나는 현재 회의록 에이전트와 가장 잘 맞는다.

## 세 방안 핵심 비교

| 방안 | 실제 저장 구조 | 가장 큰 장점 | 가장 큰 한계 |
|---|---|---|---|
| 1안. State 두 개 | `recording_state` + `retrieval_state` | 두 장기 과정을 독립적으로 추적 | 짧은 질의에도 전역 State를 계속 유지 |
| 2안. 조합 State | `recording/searching` | 한 줄로 전체 상태 표시 | 조합 폭발과 동시 갱신 시 덮어쓰기 |
| 3안. 지속 State + 요청형 Run | 녹화 State + 요청별 Retrieval Run | 녹화와 개별 질의를 가장 강하게 격리 | Run ID와 결과 연결 구조가 필요 |

## 현재 설계에 대한 권고

현재 회의록 에이전트에는 **3안**을 우선 권고한다.

회의 녹화는 시작부터 종료·확정·공유까지 이어지는 장기 과정이지만, 과거 회의록 검색과 질문은 사용자 요청마다 실행되고 답변 후 끝나는 성격이 강하다. 두 과정을 똑같은 전역 State Machine으로 만들기보다 다음처럼 비대칭적으로 관리하는 편이 자연스럽다.

```text
회의 녹화: 지속 State Machine
회의록 검색·질의: 요청 단위 Retrieval Run
```

다만 회의록 질의가 향후 여러 사용자 입력에 걸쳐 장시간 이어지고 반드시 중간 상태를 복구해야 하는 업무로 바뀐다면, 그때는 1안처럼 `retrieval_state`를 별도의 지속 State로 승격할 수 있다.
