# 회의록 Agent 이식 방향 계획서

## 1. 목적

Python·LangGraph POC에서 확인한 회의록 검색, 질문, HITL, 녹화 시작과 보안 규칙을 실제 `zen-ai` 제품 구조에 맞게 옮긴다. POC의 파일과 Graph 구현을 줄 단위로 복사하는 것이 아니라 책임과 상태 전이를 번역한다.

## 2. 제품에서 사용할 실행 기반

회의록 Agent는 사용자가 시스템 프롬프트와 MCP Tool을 조합해 만드는 일반 Custom Agent가 아니라, 저장소가 코드를 소유하는 **Builtin Agent**다.

```text
agents/meeting/assistant/manifest.json + system-prompt.md
→ Builtin definition compiler
→ builtin_agent_instances
→ 채널 초대와 @MENTION
→ builtin agent_runs
→ Builtin Worker
→ meeting-agent-v1 Executor
→ 공통 operation ledger와 message.posted Finalizer
```

따라서 다음을 새로 만들지 않는다.

- 일반 Agent Worker를 복제한 `standard-runner.ts` / `custom/runner.ts`
- Runner 공통화를 위한 새 `runner-contract.ts`
- 모든 State를 모으는 별도 Python `server.py`
- 회의록 Agent를 일반 `agents` 테이블의 특수 행으로 등록하는 방식

Builtin Runtime이 이미 claim, lease, timeout, 취소, operation receipt, Executor Registry와 최종 답변 저장 계약을 제공하므로 이를 재사용한다.

## 3. 회의록 전용 구현

```text
src/lib/meeting-agent/
├─ engine.ts                 목표 판단과 Search·Question·Recording 흐름
├─ provider.ts               AI SDK 모델 호출과 구조화 응답 검증
├─ channel-adapter.ts        Builtin Runtime과 회의록 Executor 연결
├─ thread-context.ts         같은 Thread의 안전한 대화 Context
└─ tools/
   ├─ repository.ts         회의록 Backend·권한 조회
   └─ state-repository.ts   authorizedMeetingIds와 Tool HITL 상태
```

폴더명은 책임을 설명하기 위한 기준이며, 실제 구현에서 한 파일로 충분한 책임은 불필요하게 쪼개지 않는다.

## 4. State 소유권

| 정보 | 소유 위치 |
|---|---|
| 사용자·Agent 최종 대화 | 기존 `message.posted` |
| Run claim·lease·완료·operation 감사 | 기존 Builtin Runtime과 `agent_runs` |
| 안전한 Scratchpad 요약·Pending HITL 재개 메타데이터 | Builtin Run의 제한된 `builtin_checkpoint` |
| `authorizedMeetingIds`, 후보·추가·대체 상세와 일회용 토큰 | 현재 Local Meeting Tool State Repository, 향후 고객사 MCP |
| 회의록 원문 | 현재 Question Model 호출 메모리에서만 사용 |
| 실제 녹화 상태 | 기존 Meeting Recording Provider와 Backend |
| 화면 편의 캐시 | 필요하면 Local Storage·IndexedDB 등 사용자 클라이언트 |

`recordingModalStatus`는 Agent State에 저장하지 않는다. Agent의 Recording Tool 성공은 실제 녹화 완료가 아니라 요청자의 브라우저에 녹화 시작 요청을 전달했다는 뜻이다.

## 5. Search·Question

Search Tool은 호출 사용자가 현재 접근 가능한 회의만 검색한다. 후보가 하나면 자동 선택·검증하고, 여러 개이면 Tool State Repository에 상세 후보 Snapshot을 저장한 뒤 HITL을 만든다. 사용자의 다음 메시지는 새 `agent_runs` 행을 생성한다. Executor는 Agent State/Workflow Checkpoint의 최소 참조만 사용해 `tools.resume()`을 호출하며, 상세 Snapshot 조회·입력 검증·선택 처리는 Tool 내부에서 수행된다. 유효하면 Tool은 중단된 Search 내부의 다음 단계로 진행한다. 기존 `authorizedMeetingIds`가 있으면 그때 별도의 add/replace HITL이 발생할 수 있고, 이는 Search Tool만의 순차 업무 단계다. Tool 처리가 끝난 뒤 Engine은 검색 응답을 만들고 사용자 요청에 따라 Question Tool 호출 여부를 다시 판단한다.

Question Tool은 저장된 `authorizedMeetingIds`를 그대로 신뢰하지 않고 원문을 읽을 때마다 현재 사용자 권한을 다시 확인한다. 원문은 LLM 입력으로만 전달하고 Checkpoint·Trace·감사·최종 메시지의 내부 데이터로 저장하지 않는다.

## 6. Recording

`@meeting 회의시작` 명령은 이미 Composer가 기존 Recording Provider를 직접 호출한다. 회의록 Agent가 녹화 시작을 판단한 경우에는 같은 Provider를 호출하는 요청자 전용 휘발성 제어 Event를 사용한다. 녹화 상태 머신을 Agent에 복제하지 않는다.

## 7. 최종 방향

회의록 Agent만의 실행 판단과 Tool 상태는 독립적으로 두되, 채팅·멘션·Builtin Run·Worker·Realtime 진행·operation 감사·최종 `message.posted`는 제품 공통 기반을 사용한다. 현재 Local Tool 경계는 향후 고객사 온프레미스 MCP로 이동할 수 있도록 사용자·Agent·Channel·Thread Scope와 표준 결과 계약을 유지한다.

## 8. Builtin Agent 등록·호출 수명주기

### 8.1 컴파일과 Release publish

`manifest.json`은 `definitionKey`, `executorId`, handle, 허용 모델, 실행 상한을 정의하고 `system-prompt.md`는 시스템 프롬프트 본문을 제공한다. Compiler는 두 파일을 읽어 컴파일된 Builtin Registry를 만든다. `npm run dev`·`build`·`test`의 사전 단계에서는 이 컴파일이 자동 실행되지만, 컴파일 결과가 곧 DB 저장을 의미하지는 않는다.

배포·migration 단계의 Release Publisher가 Registry의 검증된 실행 메타데이터를 `builtin_definition_releases`에 기록한다. Release에는 `executorId`, `allowedModels`, `maxOutputTokens`, `maxRounds`, `contentDigest` 등이 저장된다. 프롬프트 본문은 컴파일된 Registry에 있고 digest로 DB Release와 일치 여부를 검증한다.

### 8.2 커뮤니티 등록

관리자가 특정 커뮤니티에 Agent를 등록하면 `agent_principals(kind = builtin)`을 만들고, 이를 참조하는 `builtin_agent_instances`와 `builtin_instance_config_versions`를 생성한다. Principal은 `@MEETING` 같은 신원을, Instance는 해당 커뮤니티에 설치된 사실을, Instance Config는 허용 범위 내 커뮤니티별 모델·제한을 나타낸다.

### 8.3 사용자 호출과 실행

사용자가 `@MEETING`을 입력하면 채널 Runtime은 Principal을 찾아 `kind = builtin`인지 확인하고 Instance·현재 Release·Config를 검증한다. 그 결과로 `run_kind = builtin`, `definitionKey`, `executorId`, 유효 모델·토큰·라운드가 포함된 `agent_runs` 행을 만든다. 공통 Builtin Worker가 이를 claim/lease한 뒤 Executor Registry에서 코드로 등록된 `meeting-agent-v1`을 찾아 호출한다. `channel-adapter.ts`는 Runtime 입력을 회의록 Engine 입력으로 변환하고, Engine이 Provider·Tool·State Repository를 사용해 실제 업무를 수행한다.

이 네 저장소를 물리적으로 순서대로 네 번 조회한다는 뜻은 아니다. JOIN·DB 함수로 함께 읽을 수 있지만, Identity·Release·Community Installation·Effective Configuration의 책임과 수명을 분리하는 것이 핵심이다.
