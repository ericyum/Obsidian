# 회의록 Agent 이식 방향 계획서

## 1. 목적

POC에서 검증한 회의록 업무 로직을 zen-ai에 이식하되, 기존 Agent 생성·실행 Framework와 AI SDK의 공통 Tool Calling 구조를 변경하지 않는 것을 원칙으로 한다.

이 문서는 구현 코드보다 **이식 방향과 책임 경계**를 먼저 확정한다. 구체적인 파일별 코드와 구현 순서는 다음 단계에서 작성한다.

## 2. zen-ai의 기존 Agent 생성·실행 흐름

zen-ai의 일반적인 Agent 실행 흐름은 다음과 같다.

```text
채팅창에서 @Agent 호출 감지
→ Agent Run 생성
→ 호출 문자와 일치하는 Agent DB 행 조회
→ 시스템 프롬프트·모델·실행 정책·Tool 정보 로드
→ Runtime과 AI SDK가 Agent 조립
→ 사용자 요청 처리
```

회의록 Agent도 이 기본 흐름을 벗어나지 않는다. 모든 사용자가 사용할 수 있는 **내장 시스템 Agent**이지만, 별도의 독립 실행 Framework를 새로 만들지는 않는다.

## 3. Agent 정보는 DB에 등록

기존 Framework를 최대한 유지하기 위해 회의록 Agent의 정의 정보는 Agent DB에 등록한다.

- Agent ID와 이름
- 호출 문자 또는 슬러그
- 설명과 시스템 프롬프트
- 모델 및 추론 정책
- 출력·컨텍스트·라운드 한도
- 사용할 Tool 정보
- 모든 사용자가 사용할 수 있다는 부여 정책

따라서 별도의 `agent_definition.ts`를 두지 않는다. 회의록 Agent는 코드에만 존재하는 예외 객체가 아니라, 기존 실행 과정에서 조회하고 식별할 수 있는 Agent 행을 가진다.

## 4. Tool 로직은 내부 전용 공간에 구현

회의록 Agent의 Tool은 우선 외부 MCP 서버가 아니라 zen-ai 내부의 전용 공간에 구현한다.

```text
src/lib/agents/meetings/
├─ search-tool.ts
├─ question-tool.ts
├─ recording-tool.ts
├─ recording.ts
├─ session-data.ts
└─ hitl.ts
```

- `search-tool.ts`: 회의록 검색과 선택·권한 처리
- `question-tool.ts`: 허용된 회의록 원문 조회와 질문 처리
- `recording-tool.ts`: 녹화 요청을 Tool 형태로 노출
- `recording.ts`: 기존 녹화 모달·Backend를 호출하는 실제 Skill 로직
- `session-data.ts`: `authorized_meeting_ids`, `recording_modal_status` 변수값 관리
- `hitl.ts`: Tool 실행 중 필요한 HITL 대기·재개 정보 관리

Agent DB에는 회의록 Agent가 사용할 Tool 정보가 등록되고, 실제 `execute` 로직은 위 내부 파일에 연결한다. Tool 호출 라우팅은 AI SDK의 기존 Tool 실행 방식에 맡기며, Runtime에 Tool별 수동 분기문을 추가하지 않는다.

## 5. 변수값 관리 방향

`session-data.ts`에는 회의록 Agent 전용 변수값만 둔다.

- `authorized_meeting_ids`
- `recording_modal_status`

HITL 정보는 성격이 다르므로 `hitl.ts`에서 별도로 관리한다. 현 단계에서는 이 변수값들을 위한 별도 DB를 새로 설계하지 않는다.

## 6. Search·Question 처리 구조

Search Tool과 Question Tool 내부에는 별도의 LLM 호출을 넣지 않는다. Tool은 업무 로직을 실행한 뒤 **Tool Action 결과값만 반환**한다.

```text
사용자 질문
→ Agent LLM 판단
→ Search Tool Action
→ 기존 AI SDK Harness가 결과를 Context에 추가
→ Agent LLM 재판단
→ Question Tool Action
→ 기존 AI SDK Harness가 결과를 Context에 추가
→ Agent LLM 재판단
→ 최종 답변 및 종료
```

Tool 실행 결과를 다시 LLM에 전달하고 목표 달성 시 종료하는 과정은 AI SDK로 조립된 Agent의 공통 구조다. 따라서 회의록 Agent만을 위한 `공통 결과 처리 로직`, 별도 Handler 또는 Runtime 특수 분기를 만들지 않는다.

## 7. 기존 설계도 해석 수정

기존 설계 문서에서 Search·Question Tool 내부에 Context 조립과 LLM 재호출까지 포함된 것처럼 보이는 표현은 수정이 필요하다.

정확한 책임 경계는 다음과 같다.

- Tool 내부: 검색·조회·권한 확인·HITL 등 업무 로직을 실행하고 결과 반환
- 공통 Agent Harness: Tool 결과를 대화 Context에 조립
- Agent LLM: 다음 Tool 호출 또는 최종 답변을 판단

따라서 `5-3. Agent State·업무 연결도`는 구현 Graph 명세가 아니라 전체 업무 진행을 설명하는 **순서도**로 해석한다. 실제 구현은 AI SDK의 표준 Tool Calling Loop를 그대로 따른다.

## 8. 녹화 기능도 Tool로 구성

`/meeting-start` 같은 녹화 명령을 Runtime이 직접 가로채는 별도 Harness는 만들지 않는다. 녹화 기능도 세 번째 Tool로 등록한다.

```text
녹화 명령 입력
→ Agent LLM이 시스템 프롬프트와 Tool 설명에 따라 Recording Tool 선택
→ Recording Tool이 recording.ts 실행
→ 기존 녹화 모달·Backend 연결
→ 실행 결과에 따라 recording_modal_status 갱신
→ Tool 결과를 기존 AI SDK Harness가 Agent LLM에 전달
→ 안내 답변 및 종료
```

이 방식은 특정 명령을 위한 Runtime 예외 분기를 만들지 않으면서, zen-ai가 지향하는 Tool 기반 Agent 구성 방식을 유지한다.

## 9. 최종 방향

회의록 Agent 이식의 핵심은 새로운 Agent Framework를 만드는 것이 아니다.

1. Agent 정의와 정책은 기존 Agent DB에 등록한다.
2. Search·Question·Recording을 내부 Local Tool로 구현한다.
3. 전용 변수값과 HITL 정보만 회의록 Agent 내부 공간에서 관리한다.
4. Tool 선택, 결과 Context 조립, LLM 재호출과 종료는 기존 Runtime·AI SDK Harness를 재사용한다.
5. 회의록 Agent 전용 Runtime 분기와 별도 공통 처리 로직은 추가하지 않는다.

다음 단계에서는 이 방향을 기준으로 실제 zen-ai 코드의 연결 지점을 확인하고, DB 등록 항목·Local Tool 등록 방식·변수값 저장 방식·녹화 모달 연동 방식을 구체화한다.
