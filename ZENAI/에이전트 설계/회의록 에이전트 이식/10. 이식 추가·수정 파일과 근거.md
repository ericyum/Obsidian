## 1. 변경 범위를 먼저 구분한다

기존 파일 24개 수정과 새 파일 2개, 총 26개가 검증 종료 시점의 목록이다. 전날 이식 커밋 전체의 파일 목록이 아니라 그 이후 검증 작업의 변경 목록이다. 이번 Obsidian 통합 문서와 보관 ZIP은 이 26개에 포함하지 않는다.

- 실제 처리 로직: engine.ts의 null 처리, registry-source.ts의 Windows 비교, compile.ts의 Windows 재시도, 새 DB migration.
- 실행 의존성: Next 등 패키지 버전과 lockfile. 직접 앱 코드를 고치지 않아도 실행에 영향을 줄 수 있다.
- 테스트: 실제 상태·권한 검증 보강과 실행 환경 호환성.
- 검사 설정·포맷: 검사 대상과 줄바꿈·표현 정리.
- 로컬 생성물: .context, .next 등. 제품 구조에 추가한 실행 의존성이 아니다.

따라서 “테스트 통과 조건만 조금 바꾼 작업”은 아니다. 공통 Worker/Builtin/Realtime/operation 구조는 유지하면서 발견된 오류를 수정했다.

## 2. 실제 동작 변경의 원인과 효과

### Engine의 null 판정

새 저장소의 pendingHitl:null은 “사용자 선택 대기 없음”인데 parser가 손상된 체크포인트로 거부해 후속 질문이 실패했다. null/undefined를 정상적인 대기 없음으로 처리한다. 잘못된 non-null 데이터는 계속 거부한다.

### Windows 파일 검사와 출력 교체

registry-source.ts는 읽는 동안 정의 파일이 바뀌었는지 검사한다. Windows의 조회별 메타데이터 차이를 실제 교체로 오판해 DEFINITION_PATH_CHANGED: registry.json이 발생했다. Windows 비교 항목을 조정하고 Linux inode/device 검사는 유지했다. .env 누락 문제가 아니었다.

compile.ts는 완성된 임시 출력 파일을 최종 이름으로 교체한다. Windows 동시 실행 중 일시적 점유로 rename EPERM이 재현됐다. Windows의 EPERM/EACCES/EBUSY에만 최대 5회, 10/20/40/80/160ms 대기 재시도를 추가했다. 최종 파일을 먼저 삭제하지 않으며 그 외 오류와 Linux는 즉시 실패 동작을 유지한다.

### DB 종료 경계 기록

기존 0059 트리거는 checkpoint=null이면 기록을 건너뛰었다. 새 0060 migration은 종료 전 상태에서 done/failed/cancelled로 전이하는 회의 Run의 경계를 남긴다.

- 성공하고 유효한 체크포인트가 있으면 누적 Agent State를 갱신한다.
- 실패·취소는 종료 경계를 남기고 마지막 정상 Agent State를 보존한다.
- JSON null pending HITL을 정규화하고 객체인 경우 대기 상태로 처리한다.

기존 migration을 덮어쓰거나 DB를 새로 만드는 작업이 아니다. 기존 트리거 함수의 처리를 보완하는 후속 migration이며 대상 DB에 적용해야 효력이 있다.

검증은 audit 0건뿐 아니라 npm ls 정합성, Linux npm ci, 전체 테스트·빌드·실제 UI까지 수행했다. Drizzle schema export는 업데이트 전후 줄바꿈 정규화 후 동일했고, 이 export 비교를 위해 사용자 DB에 접속하거나 migration을 생성하지 않았다.

core.autocrlf=true인 Windows에서 CRLF 때문에 대량 포맷 오류가 발생했다. endOfLine:auto로 줄바꿈 차이를 구분하고 실제 서식 불일치만 정리했다. .prettierignore는 Git 추적 설정이 아니다. .gitignore와 전역 Git 설정은 이번 검증에서 수정하지 않았다.

## 부록. 향후 회의 Tool MCP 전환 계약

현재 구현을 변경하지 않고, 향후 Local Tool을 MCP transport로 옮길 때 유지할 경계를 정의한다. 현재의 `MeetingAgentTools`는 TypeScript 판별 유니언을 반환하며, 아래 공통 envelope는 아직 구현된 MCP API가 아니다.

### 호출과 결과

인증된 서버가 community, principal, user, conversation, run, operation 범위를 결정한다. 모델이나 클라이언트가 보낸 scope를 권한 근거로 쓰지 않는다. 각 논리적 Tool 호출은 안정적인 `toolCallId`를 가진다. 재전송은 동일 ID와 입력 digest로 중복 실행을 방지하고, 같은 ID에 다른 입력이면 거부한다.

| 필드 | 계약 |
| --- | --- |
| `toolCallId` | 논리 호출 식별자. 기존 operation receipt와 연결한다. |
| `toolName` | `search`, `question`, `recording` 중 하나. resume/cancel은 Search의 HITL 재개 동작이다. |
| `status` | `success`, `hitl_required`, `failed`, `cancelled` 중 하나. |
| `output` | 성공 시에만 필요한 최소 결과. Question 원문은 해당 답변 모델 호출에서만 일시적으로 사용한다. |
| `hitl` | HITL일 때만 `{ tool, pendingToken, resumePoint }`. 후보 목록과 검증 Snapshot은 포함하지 않는다. |
| `errorCode` | 실패 시 안정적인 허용 목록 코드. exception, 접속 문자열, 토큰 원문을 넣지 않는다. |

Search의 empty/selected는 success로, hitl은 hitl_required로 매핑한다. Question의 selection_required는 사용자에게 재선택을 안내하는 도메인 결과이며 원문 조회를 시도하지 않는다. Recording success는 대상 사용자의 연결에 시작 이벤트가 전달됐다는 뜻이다. 실제 녹화 완료나 저장 완료를 의미하지 않는다.

### HITL와 저장소

Tool State Repository가 token 생성·만료·scope·선택 입력·현재 접근 권한·상태 버전을 검증한다. 무효 입력은 동일 token과 Snapshot을 유지한다. 유효 입력은 Snapshot 소비와 선택 목록 갱신을 원자적으로 처리한다. 만료, 권한 철회, 중복 resume, stale version은 구분 가능한 결과로 처리하고 임의 재승인하지 않는다.

Engine에는 Scratchpad와 최소 HITL 참조만 반환한다. 상세 후보, selected IDs와 원본 요청 Snapshot은 Tool 저장소에 둔다. Agent State는 누적 요약 상태이고 Workflow Checkpoint는 한 Run의 경계 상태다. transport 전환이 두 저장소의 책임을 합치거나 별도 Engine `select()` 단계를 만들면 안 된다.

### 메시지·감사·Trace

최종 사용자 응답만 기존 terminal 경로를 통해 `message.posted`에 저장한다. MCP Tool 응답 전체를 채팅 이벤트로 복사하지 않는다. 감사에는 기존 Builtin operation receipt/evidence와 호출 식별자, 상태, 코드, 사용량을 사용한다. 별도 감사 저장소를 만들지 않는다.

진행 상태는 기존 Realtime Hub의 `agent-delta`로 보낸다. run ID, 순번, Tool 이름과 허용된 상태만 담고 API 키, 원문, pending token, Snapshot을 보내지 않는다. 전체 MCP 요청/응답을 무조건 로깅하지 않는다. 오류 문자열과 모델 응답도 로그 직렬화 전에 동일 기준으로 제한한다.

### 전환 수용 기준

Local과 MCP 구현에 같은 계약 테스트를 적용한다. empty/single/multi Search, 잘못된 선택 유지, 유효 resume, 만료·취소·권한 철회, 중복 전송, Recording 이벤트 전달 실패, 연결 끊김 후 재시도, 순서가 뒤바뀐 Trace를 검증한다. Agent State·Checkpoint·감사·Trace에 원문과 token/Snapshot이 새어나오지 않는 것을 별도로 검사한다. MCP transport의 실제 구현·배포는 이번 검수 범위에 포함되지 않는다.
