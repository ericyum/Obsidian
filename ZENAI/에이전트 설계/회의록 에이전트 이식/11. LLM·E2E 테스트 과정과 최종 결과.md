# LLM·E2E 테스트 과정과 최종 결과

기록 기준: 2026-09-15

## 1. 목적

회의록 Builtin Agent를 실제 사용 흐름에 가깝게 검증했다. 단순한 LLM 응답 확인이 아니라 Provider, Engine, Search Tool, Recording Tool, HITL, PostgreSQL 상태 저장, Workflow Checkpoint, 브라우저 Realtime 이벤트를 각각 확인했다.

## 2. 환경과 준비

- Zen AI 로컬 서버: localhost:3002
- PostgreSQL: 로컬 Docker 컨테이너
- LLM: Codex-LB 로컬 Gateway
- 테스트 모델: gpt-5.6-sol 및 Gateway에 노출된 모델
- 테스트 사용자와 커뮤니티에 회의록 접근 권한을 일부 부여
- 검색 결과가 0건, 1건, 복수 건이 되도록 테스트 회의록을 준비

API 키는 소스, 문서, Git 추적 파일에 기록하지 않고 실행 프로세스의 환경변수로만 주입했다.

## 3. LLM Provider 테스트

decide, searchResponse, answerQuestion, directResponse를 실제 Gateway에 연결했다.

- 검색 요청이 search와 유효한 검색 조건을 반환하는지 확인
- Search Tool이 확정한 후보와 권한을 Provider가 다시 판단하지 않는지 확인
- 회의록 원문에 근거한 질문 답변이 생성되는지 확인
- 일반 인사 요청이 Tool 없이 처리되는지 확인
- JSON 앞뒤 설명, 코드블록, 누락 필드에 대한 보정과 재검증 확인

초기에는 일부 모델에서 strict JSON 위반과 60초 timeout이 발생했다. 회의록 Provider에 JSON 객체 추출, 누락 필드 보완, 1회 보정 호출, Zod 재검증을 적용했다.

## 4. 검색과 HITL 테스트

### 4.1 검색 결과별 동작

- 0건: LLM 추가 호출 없이 접근 가능한 회의록이 없다는 결정적 문구 반환
- 1건: 해당 회의록 자동 선택 및 제목 안내
- 복수 건: Search Tool이 후보와 pending token을 저장하고 waiting_for_input으로 run 종료

검색 후보와 권한 판단은 Engine이 아니라 Search Tool과 PostgreSQL 경계가 담당한다.

### 4.2 선택, 추가, 대체, 취소

- 번호 또는 meeting ID 선택
- 기존 허용 목록이 없을 때 set
- 기존 허용 목록이 있을 때 추가 또는 대체
- 잘못된 번호와 잘못된 merge 명령
- cancel 명령
- 동일 회의록 재선택 시 불필요한 HITL을 만들지 않는지 확인

추가는 기존 authorized_meeting_ids와 새 선택 ID를 합친다. 대체는 새 선택 목록만 유지하므로 이전 회의록을 질문할 수 없는 것이 정상이다.

## 5. HITL 재개와 후속 질문

최초 HITL run은 최소 pendingHitl checkpoint만 남기고 종료한다. 사용자가 선택을 입력하면 Tool State의 상세 snapshot을 읽고 유효성을 검증한다.

수정 전에는 선택 ID를 저장한 직후 snapshot을 삭제했다. 그 다음 Provider 호출이 실패하면 상태는 갱신됐지만 재시도할 token이 없어 missing이 되었다.

수정 후 순서는 다음과 같다.

1. 유효한 선택을 Tool State에 반영한다.
2. 후속 searchResponse가 성공할 때까지 snapshot을 유지한다.
3. 후속 응답 성공 후 completeResume으로 snapshot을 삭제한다.
4. followUp이 true이면 Question Tool로 계속 진행한다.

실제 스레드에서 추가 후 authorized_meeting_ids가 기존 ID와 새 ID의 합집합으로 저장되었고, 이후 두 회의록을 대상으로 질문 답변이 성공했다. 일부 질문의 60초 timeout은 Codex-LB 응답 지연이었으며 재시도 시 정상 답변되어 권한이나 상태 저장 결함과 구분했다.

## 6. Recording Tool과 녹음 E2E

녹음 제어는 검색·질문과 분리된 세 번째 Recording Tool로 구현했다.

Agent 호출 예시:

@MEETING 회의 녹화를 시작해줘
@MEETING 회의를 일시정지해줘
@MEETING 회의를 재개해줘
@MEETING 회의를 종료해줘

Recording Tool이 요청을 start, pause, resume, stop Skill 중 하나로 분류하고 브라우저 Realtime control event를 전달한다. Tool 결과가 반환되면 Engine은 다시 LLM으로 돌아가지 않고 run을 종료한다. stop은 기존 종료 확인 절차를 거친다.

슬래시 명령도 지원한다.

/meeting-start
/meeting-pause
/meeting-resume
/meeting-stop

## 7. 발견한 문제와 해결

| 문제 | 원인 | 해결 |
| --- | --- | --- |
| 모델 JSON 계약 위반 | 모델별 출력 형식 편차 | JSON 추출·보정·Zod 재검증 |
| 추가 후 재시도 missing | 후속 Provider 호출 전에 snapshot 삭제 | 성공 후 삭제하는 2단계 완료 |
| merge 안내에 후보 전체 표시 | candidates 전체를 사용 | selected candidates만 표시 |
| 원인 불명 generic 실패 | channel-adapter가 원래 예외를 버림 | 안전한 오류 로그 추가 |
| Agent 호출로 pause/resume/stop 불가 | start 직접 분기만 존재 | Recording Tool과 네 Skill 추가 |
| Gateway 60초 timeout | 외부 모델 응답 지연 | 재시도 가능 상태와 진단 로그 유지 |
## 8. 최종 판정

- 검색 0건, 1건, 복수 건: 통과
- HITL 선택, 추가, 대체, 취소: 통과
- 추가 후 기존 및 새 회의록 질문: 통과
- 대체 후 기존 회의록을 답하지 않음: 정상
- Recording Tool의 start, pause, resume, stop 분기: 통과
- 네 가지 슬래시 명령: 통과
- Agent State, Tool State, Workflow Checkpoint 분리: 유지
- 관련 단위 테스트, 타입 검사, 포맷 검사: 통과

DB 통합 테스트는 소유 테스트 클러스터 환경에서만 실행되도록 제한되어 일반 로컬에서는 자동 skip된다. 따라서 단위 테스트, 실제 Provider 테스트, 브라우저 수동 테스트, DB 소유 클러스터 테스트를 서로 다른 증거로 기록해야 한다.

## 9. 재현 절차

1. PostgreSQL Docker와 Codex-LB를 실행한다.
2. Codex-LB 주소와 키를 현재 PowerShell 세션에만 임시 설정한다.
3. npm run dev로 서버를 시작한다.
4. 테스트 커뮤니티에 로그인하고 회의록 Agent를 등록한다.
5. 검색 0건, 복수 후보, 번호 선택, 추가, 기존 회의록 질문을 순서대로 실행한다.
6. Agent 호출로 녹음 시작, 일시정지, 재개, 종료를 실행한다.
7. 채널 메시지, agent_runs, Agent State, Tool State, Workflow Checkpoint, Realtime 이벤트를 함께 대조한다.
