# 회의록 Agent 이식 방향 재정립

## 1. 문서 목적

이 문서는 회의록 Agent 이식 계획을 수립하기 전에, 발표와 피드백을 통해 새롭게 확인된 **현재 상황과 방향성**을 정리한다.

구현 위치, 파일 구조, DB 저장 방식과 세부 개발 순서는 아직 확정하지 않는다.

## 2. 발표 당시의 이해

발표에서는 다음과 같은 방향을 설명했다.

- 회의록 Agent도 기존 Agent 생성·실행 구조를 최대한 유지한다.
- 기존 Framework에 맞춰 Agent 정보와 Tool을 연결한다.

기존 구조를 파악하고 구성 요소의 대응 방향을 설명한 점은 유효했다. 다만 **내장 Agent의 의미**를 기존 Agent 생성 템플릿 형태에 맞춰서 미리 등록된 Agent로 잘못 이해했다.

## 3. 내장 회의록 Agent의 정확한 의미

이번 회의록 Agent에서 말하는 **내장 Agent**는 기존 Agent 생성 템플릿으로 만드는 Agent가 아니다.

zen-ai 내부의 **별도 공간에 다음 요소를 포함한 독립적인 Agent**를 구축한다.

- 회의록 Agent 커스텀 Harness 로직
- 각 Tool의 내부 로직
- 회의록 Agent에서 사용되는 변수값(`modal_status`, `meeting_ids`)
- 회의록 Agent에서 사용되는 `Human in the Loop`와 `Checkpoint` 구현

따라서 기존의 공통 Agent Harness에 회의록 Agent를 그대로 끼워 넣는 것이 목표가 아니다. POC와 설계 문서에서 정의한 커스텀 Harness를 제품 환경에 맞게 실제로 구현하고 검증하는 것이 목표다.

## 4. 독립 Agent로 구현하는 이유

회의록 Agent는 Graph Engineering을 바탕으로 업무 흐름을 `Node·State·Edge`로 설계했다.

기존 Agent 생성 템플릿을 사용해서 구현하면 설계한 커스텀 Harness의 제어 흐름을 온전히 구현하기 어렵다. 그렇게 되면 설계도를 작성하고 POC로 검증한 의미가 줄어든다.

예시를 들자면 녹화 워크 플로우의 경우에는 에이전트가 Tool을 호출한 후 다시 LLM으로 돌아가는 구조(`Tool Action`)가 아니라 그대로 끝나버리는 구조(`Tool Calling`)인데 Agent 생성 템플릿으로는 이것을 구현하기가 불가능하다.

따라서 이번 작업은 다음을 확인하기 위한 실험적 구현이다.

> 설계한 커스텀 Harness를 zen-ai 내부의 독립된 Agent로 구축했을 때 실제 제품 환경에서도 정상적으로 동작하는가?

## 5. 향후 확장 방향

회의록 Agent는 단일 기능을 위한 일회성 예외 구현에 그치지 않는다.

이번 구현으로 커스텀 Harness가 정상 작동하는 것을 확인한 뒤, Harness의 공통 요소와 선택 가능한 제어 로직을 점차 정리한다. 장기적으로는 사용자가 필요한 Harness 로직을 선택하여 Agent를 만들 수 있는 확장된 Agent 템플릿으로 발전시키는 것을 목표로 한다.

즉, 회의록 Agent는 **커스텀 Harness 기반 Agent를 템플릿화하기 위한 첫 번째 실험작**이다.

## 6. Tool 로직의 핵심 원칙

Tool 내부 로직은 단순히 현재 회의록 Agent에서만 동작하도록 작성하지 않고, 책임을 명확히 분리하고 캡슐화해야 한다.

캡슐화의 목적은 다음과 같다.

- Tool의 내부 구현을 외부 실행 흐름과 분리한다.
- 입력과 출력의 경계를 명확하게 만든다.
- **비슷한 기능이 필요한 다른 Agent에서도 동일 로직을 재사용**할 수 있게 한다.
- 내부 구현을 변경하더라도 호출하는 쪽의 영향을 최소화한다.
- 독립적인 테스트와 유지보수가 가능하게 한다.

따라서 각 Tool의 내부 코드는 **외부에서 세부 구현을 알지 못해도 사용할 수 있도록** 캡슐화하고, **비슷한 기능이 필요한 다른 Agent에서도 다시 사용할 수 있는 단위로 구성**한다. 이것이 이번 피드백에서 말한 **로직을 잘 다듬는 것**과 **재사용성 증대**의 의미다.

## 7. 현재 확정된 방향

현재 단계에서 확정된 사항은 다음과 같다.

1. 회의록 Agent는 기존 Agent 생성 템플릿으로 만드는 Agent가 아니다.
2. zen-ai 내부의 별도 공간에 독립된 내장 Agent로 구축한다.
3. POC에서 검증한 커스텀 Harness와 Graph 설계를 제품 환경에 맞게 구현한다.
4. Tool 내부 로직은 책임별로 캡슐화하여 **재사용 가능**하게 만든다.
5. 이번 구현 결과를 기반으로 향후 커스텀 Harness 선택형 Agent 템플릿으로 확장한다.

## 8. 아직 결정하지 않는 사항

이 문서는 현황과 방향성을 정리하는 문서이므로 다음 내용은 아직 결정하지 않는다.

- 실제 소스 폴더와 파일 구조
- 공통 채팅 기반과 독립 회의록 Agent 사이의 연결 방식 확립
- `Human in the Loop`와 `Checkpoint` 구현 방식
- 회의록 Agent 변수값과 HITL 대기 정보의 저장 위치·수명
- 각 Tool의 입력 Schema·정형화된 반환값·오류 계약
- 독립 회의록 Agent의 호출·식별을 위해 DB에 등록할 최소 정보
- 단계별 구현 및 테스트 순서

이 항목들은 zen-ai의 실제 연결 지점을 다시 확인한 뒤 별도의 구현 계획에서 결정한다.
