# 회의록 Agent 이식을 위한 행동 플랜

## 현재 상태와 목표

- **현재 상태:** Python과 LangGraph로 회의록 Agent POC를 완료했다.
- **목표:** POC에서 검증한 로직을 zen-ai의 기존 Agent Framework에 맞게 이식한다.
- **zen-ai의 일반적인 상황:** 일반 Agent는 관리자나 사용자가 Agent 생성 기능에서 설정과 MCP Tool을 선택해 만든다.
- **회의록 Agent의 특수한 상황:** 회의록 Agent는 사용자가 생성하는 일반 Agent가 아니라, zen-ai에 처음부터 포함되는 내장 시스템 Agent로 구현한다. 따라서 Agent 생성 모달을 통한 구성 방식은 사용하지 않는다.

## 행동 플랜

### 1. POC에서 이식할 핵심 로직 정의

Search, Question, HITL, 권한 검증, 상태 관리, 녹화 Trigger 등 POC에서 검증한 업무 로직과 반드시 보존해야 할 조건을 확정한다.

### 2. zen-ai의 내장 시스템 Agent 구조 파악

시스템 Agent가 어디에 등록되고 사용자의 요청에서 어떻게 선택·호출되는지 확인한다. Prompt·모델·Tool, 사용자·Thread별 실행 상태, HITL, Streaming과 실행 기록이 기존 Runtime에서 어떻게 처리되는지도 파악한다.

### 3. POC 로직의 대응 방식 결정

각 POC 로직을 내장 시스템 Agent 구조에서 어디서 처리할지 결정한다.

- 기존 시스템 Agent Runtime이 담당할 기능
- 회의록 전용 Tool이 담당할 기능
- 권한·원문 조회 등 Backend가 담당할 기능
- 상태와 HITL을 위해 기존 Framework를 최소한으로 확장할 부분
- 기존 녹화 모달 및 Backend와 연결할 부분

### 4. 구현 및 검증

결정한 대응 방식에 따라 회의록 Agent를 zen-ai의 내장 시스템 Agent로 구현한다. 이후 POC에서 사용한 시나리오를 다시 실행하여 Tool 호출 순서, HITL, 권한 재검증, 상태 유지와 회의록 원문 비영속성이 동일하게 보장되는지 확인한다.

## 핵심 방향

> **POC의 Python·LangGraph 코드 구조를 그대로 옮기는 것이 아니라, POC로 검증한 업무 로직과 설계 계약을 zen-ai의 기존 실행 기반을 사용하는 내장 회의록 시스템 Agent로 구현한다.**

```text
POC에서 이식할 로직 정의
→ zen-ai의 내장 시스템 Agent 구조 파악
→ 각 로직을 시스템 Agent 구조에 대응
→ 내장 시스템 Agent로 구현 및 검증
```
