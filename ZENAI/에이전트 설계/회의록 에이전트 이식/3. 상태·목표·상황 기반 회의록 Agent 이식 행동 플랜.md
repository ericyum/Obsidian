# 상태·목표·상황 기반 회의록 Agent 이식 행동 플랜

## 1. 문서 목적

이 문서는 [[2. 회의록 Agent 이식 방향 재정립]]에서 확인한 상황을 바탕으로, POC 이후 실제 zen-ai 이식까지 수행할 행동을 순서대로 정리한다.

회의록 Agent를 기존 Agent 생성 Template이나 공통 Agent Harness에 끼워 넣지 않는다. **공통 채팅 기능은 활용하되, 커스텀 Harness를 포함한 독립 내장 Agent로 구현하고 검증**한다.

## 2. 상태·목표·상황

### 상태

- Python과 LangGraph POC를 통해 설계한 업무 흐름이 기술적으로 성립하는지 확인했다.
- Search·Question·Recording Tool, HITL, 권한 검증, 변수값, Checkpoint와 녹화 모달 State의 책임을 설계했다.
- Search·Question은 Tool 결과를 Harness가 반영한 뒤 Agent LLM이 다시 판단한다.
- Recording은 하나의 Tool 내부에서 시작·일시정지·재개·종료 Skill을 실행하고, 결과를 LLM에 다시 넣지 않고 UI에 반환한 뒤 종료한다.

### 목표

POC에서 검증한 책임과 실행 계약을 zen-ai의 제품 환경에 맞게 구현하여, **커스텀 Harness를 가진 독립 회의록 Agent가 실제 채팅 환경에서 정상적으로 작동하는지 확인**한다.

### 상황

- 일반 Agent는 Agent 생성 기능과 공통 실행 구조를 통해 만들어진다.
- 회의록 Agent는 일반 Template으로 만드는 Agent가 아니라 zen-ai 내부에 별도로 구축하는 시스템 Agent다.
- 다만 멘션 감지, 전용 Thread 생성, 사용자 입력 전달과 응답 표시 같은 공통 채팅 기반까지 새로 만들 필요는 없다.
- 독립 회의록 Agent는 공통 채팅 기반과 연결하되 전용 LLM 실행부, 커스텀 Harness, Tool, 변수값, HITL과 Checkpoint를 독립적으로 가진다.
- 이번 구현은 향후 커스텀 Harness를 선택 가능한 Agent Template으로 발전시키기 위한 첫 번째 실험이다.
- Tool과 Harness 내부 로직은 안전성·변경 격리·재사용성을 위해 책임별로 캡슐화해야 한다.

## 3. 핵심 행동 원칙

> POC 코드를 그대로 복사하지 않는다. POC에서 검증한 책임·흐름·입출력 계약을 추출하여 zen-ai에 독립 회의록 Agent로 다시 구현한다.

다음 원칙을 함께 지킨다.

- 공통 채팅 기반과 독립 Agent 실행부의 책임을 구분한다.
- 기존 공통 Agent Runtime이나 AI SDK Harness의 재사용을 미리 전제하지 않는다.
- 외부에는 명확한 입력과 출력만 제공하고 권한·보안 정책은 캡슐 내부에서 강제한다.
- 단순 연결 코드까지 무조건 추상화하지 않고 실제로 안전성, 변경 격리 또는 재사용성의 효과가 있는 책임 단위를 분리한다.
- 구현 편의를 위해 설계한 Tool 실행 순서와 종료 조건을 변경하지 않는다.

## 4. 단계별 행동 플랜

### 1단계. 이식한 로직 확정

POC와 최신 설계 문서를 비교하여 제품에 옮길 실행 계약을 먼저 고정한다.

- Agent LLM, 커스텀 Harness와 Tool 사이의 책임 경계
- Search·Question·Recording Tool의 입력과 정형화된 반환값
- Tool 결과를 이후 LLM 호출의 Context에 포함하고 재판단으로 연결하며, LLM이 반환한 최종 답변은 UI에 출력하는 규칙
- `authorized_meeting_ids`, `recording_modal_status` 등 변수값의 소유권과 생명주기
- HITL 중단·재개와 Checkpoint의 업무 경계
- 회의록 원문과 인증정보를 Agent State, Checkpoint와 Trace에 남기지 않는 보안 조건
- Recording Tool 결과는 LLM에 재투입하지 않고 `recording_modal_status` 갱신과 UI 반환 후 종료하는 예외 흐름

**완료 기준:** 구현자가 POC 코드를 보지 않아도 각 구성요소의 입력·출력·책임과 다음 실행 경로를 설명할 수 있다.

### 2단계. 공통 채팅 기반과 독립 Agent의 접점 조사

zen-ai 코드에서 다음 기능의 실제 진입점과 데이터 계약을 확인한다.

- `@회의록 Agent` 멘션을 감지하는 지점
- 호출 메시지를 루트로 전용 Thread를 생성하는 지점
- Thread의 사용자 입력과 인증된 사용자 정보를 Agent에 전달하는 지점
- 독립 회의록 Agent 실행부를 호출할 수 있는 라우팅·Adapter 경계
- 응답, Streaming, HITL, Trace와 오류를 Thread UI에 표시하는 이벤트 경계
- 회의록 Agent의 호출·실행·답변 작성자를 식별하기 위해 DB에 필요한 최소 정보
- 기존 회의록 조회·권한 Backend와 녹화 모달 제어 메서드의 호출 경계

이 단계에서는 공통 Agent Runtime이나 AI SDK Harness 전체를 그대로 사용한다고 가정하지 않는다. 공통 채팅 기능에서 **독립 회의록 Agent의 실행 진입점으로 요청을 전달하고 결과를 돌려받는 최소 연결 지점**을 찾는다.

**완료 기준:** 추측한 파일명 대신 실제 코드의 함수, 호출 관계, 입력·출력과 DB 요구사항을 근거로 연결도를 작성한다.

### 3단계. 독립 회의록 Agent 구조 설계

확인한 연결 지점을 바탕으로 독립 Agent의 내부 구조와 외부 Adapter를 설계한다.

```text
공통 채팅 기반
├─ 멘션 감지
├─ 전용 Thread 생성
├─ 사용자 입력·인증 정보 전달
└─ 응답·HITL·Trace 표시
        ↓
회의록 Agent 연결 Adapter
        ↓
독립 회의록 Agent
├─ 전용 Agent LLM 실행부
├─ 커스텀 Harness
├─ Search Tool
├─ Question Tool
├─ Recording Tool
│  ├─ 시작 Skill
│  ├─ 일시정지 Skill
│  ├─ 재개 Skill
│  └─ 종료 Skill
├─ 변수값 관리
├─ HITL 대기·재개
└─ Checkpoint·Trace
        ↓
기존 권한·회의록·녹화 Backend
```

이 단계에서 다음 세부 계약을 결정한다.

- 각 Tool의 입력 Schema, 정형화된 반환값과 오류 계약
- 변수값과 HITL 대기 정보의 저장 위치, 수명과 사용자·Thread 격리 키
- 설계상의 업무 Checkpoint 저장 시점과 이를 구현할 저장 기술 결정
- 호출·식별을 위해 DB에 등록할 최소 정보와 코드에 둘 독립 Agent 구성의 경계
- 공통 채팅의 사용자 입력을 독립 Agent에 전달하고, Agent의 답변·HITL·Trace·오류를 채팅 UI에 표시하는 연결 방식
- 권한 확인, 입력 검증, 데이터 접근, 결과 정형화 등 캡슐화할 내부 로직

특히 `authorized_meeting_ids`, `recording_modal_status`와 같은 변수값의 관리 방식은 **독립 회의록 Agent 구조 설계 과정에서 추가로 조사하여 확정해야 한다.** 별도 DB에 저장하는 방식, 전용 파일이나 Python 모듈을 별도 서버로 실행하여 관리하는 방식 등 선택지가 다양하며, 서버 재시작·다중 인스턴스·동시 요청·사용자와 Thread 간 격리까지 고려해야 하므로 설계 난도가 있는 영역이다. 이 문서에서는 특정 방식을 미리 확정하지 않고, zen-ai의 실제 실행 환경과 기존 저장 구조를 확인한 뒤 적합한 방식을 선택한다.

**완료 기준:** 각 구성요소가 하나의 명확한 책임과 입출력 계약을 가지며, 독립적으로 테스트할 수 있고 의존 방향이 한 방향으로 정리되어 있다.

### 4단계. 캡슐화 경계와 공통 로직 설계

3단계에서 정한 구조를 바탕으로 Tool과 커스텀 Harness 내부에서 캡슐화할 책임 단위를 결정한다. 이 단계에서는 범용 Framework를 미리 만들지 않고, 실제로 안전성·변경 격리·재사용성의 효과가 있는 로직만을 분석하고 따로 분류를 한다.

- Search·Question Tool의 권한 검증, 입력 검증, 데이터 접근과 결과 정형화 책임 분리
- Recording Tool 내부의 시작·일시정지·재개·종료 Skill과 녹화 Backend 제어 책임 분리
- Harness 내부의 Tool 결과 Context 구성, LLM 재판단과 최종 답변 UI 출력 책임 분리
- HITL 중단·재개와 Checkpoint를 Harness 내부의 독립적인 제어 로직으로 캡슐화
- 각 캡슐화 단위의 입력, 출력, 오류와 의존성 계약 정의
- 권한·보안 정책을 UI나 LLM이 우회하지 못하도록 내부에서 강제할 위치 결정
- 둘 이상의 Tool·Agent·Harness에서 실제로 활용할 가능성이 있는 로직을 공용 후보로 선정

한 곳에서만 사용하는 단순 연결 코드까지 억지로 분리하지 않는다. 현재 책임과 계약을 명확히 만드는 것을 우선하고, 실제 공통 사용 사례가 확인된 로직만 공용 영역으로 확장한다.

**완료 기준:** 각 캡슐화 단위가 하나의 책임과 명확한 입출력 계약을 가지며, 호출부가 내부 구현을 몰라도 사용할 수 있고 독립적으로 테스트할 수 있다.

### 5단계. 기능 단위 구현

전체 Agent를 한꺼번에 만들지 않고 제품에서 끝까지 실행 가능한 흐름을 순서대로 구현한다.

1. 공통 채팅 기반에서 독립 회의록 Agent로 진입하고 응답을 돌려주는 최소 연결
2. Recording Tool과 네 개 Skill, 모달 제어, 상태 갱신과 즉시 UI 반환
3. Search Tool의 권한 필터, 후보 처리, HITL과 허용 ID 반영
4. Question Tool의 허용 ID 재검증, 원문 조회와 정형화된 결과 반환
5. Search·Question 결과를 이후 호출의 Context에 포함하고 Agent LLM 재판단
6. LLM 최종 답변의 UI 출력 직전 Checkpoint, 오류 처리, Streaming과 Trace 연결

실행 규칙은 다음과 같이 구분한다.

```text
Search·Question Tool
→ Tool 실행 결과 반환
→ 커스텀 Harness가 Tool 결과를 이후 LLM 호출의 Context에 포함
→ Agent LLM 재판단
→ 추가 Tool 호출 또는 최종 답변 반환
→ 사용자에게 보여줄 최종 답변을 UI에 출력

Recording Tool
→ 해당 Recording Skill 실행
→ 녹화 Backend 결과 반환
→ 커스텀 Harness가 recording_modal_status 갱신
→ UI 결과 반환
→ END
```

Tool 결과, LLM Context와 최종 답변을 실제로 어느 공간에서 처리하거나 저장할지는 3단계의 독립 회의록 Agent 구조 설계에서 확정한다. 이 행동 플랜은 특정 저장 구조를 전제하지 않는다.

두 흐름을 구현 편의를 위해 하나의 공통 종료 규칙으로 합치지 않는다.

**완료 기준:** 각 단계가 실제 zen-ai 화면 또는 통합 테스트에서 독립적으로 시연 가능하다.

## 6. 한 문장으로 정리

> **POC에서 검증한 로직을 확정하고, 공통 채팅 기반과 독립 회의록 Agent의 최소 연결 지점을 확인한 뒤, 캡슐화 경계와 계약을 설계하여 Tool과 커스텀 Harness를 기능 단위로 구현한다.**
