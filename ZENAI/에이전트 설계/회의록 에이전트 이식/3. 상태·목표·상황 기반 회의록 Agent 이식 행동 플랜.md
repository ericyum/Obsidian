# 상태·목표·상황 기반 회의록 Agent 이식 행동 플랜

## 1. 이 문서의 기준

이 문서는 [[2. 회의록 Agent 이식 방향 재정립]]에서 확인한 현재 상황을 바탕으로, POC 이후 실제 zen-ai 이식까지 무엇을 어떤 순서로 해야 하는지 정리한 행동 플랜이다.

기존 Agent 생성 Template에 회의록 Agent를 끼워 넣는 계획이 아니다. 회의록 Agent는 **커스텀 Harness를 포함한 독립 내장 Agent**로 먼저 구현하고, 검증된 구조를 향후 Agent Template 고도화에 활용한다.

## 2. 상태·목표·상황

### 상태

- Python과 LangGraph POC를 통해 핵심 업무 흐름의 기술적 성립 가능성을 확인했다.
- Search·Question Tool, HITL, 권한 검증, 변수값, Checkpoint와 녹화 모달 State의 책임 경계를 설계했다.
- 최신 설계에서는 녹화 명령도 하나의 녹화 Tool로 진입하고, Tool 내부에서 시작·일시정지·재개·종료 Skill을 선택하도록 정리했다.

### 목표

POC에서 검증한 업무 로직과 최신 설계의 커스텀 Harness를 zen-ai 안의 독립된 회의록 Agent로 이식하여 실제 제품 환경에서 동작하게 한다.

### 상황

- 일반 Agent는 사용자가 Agent 생성 기능으로 설정하고 공통 Runtime·AI SDK Harness에서 실행한다.
- 회의록 Agent는 일반 Template으로 생성하는 Agent가 아니라 zen-ai에 처음부터 포함되는 시스템 Agent다.
- 이번 구현의 목적은 설계한 커스텀 Harness가 제품 환경에서도 성립하는지 확인하는 것이다.
- Tool 내부 업무 로직은 이후 다른 Agent에서도 재사용할 수 있도록 캡슐화해야 한다.
- 장기적으로는 이번 결과를 바탕으로 커스텀 Harness의 일부를 선택 가능한 Agent Template 기능으로 발전시킨다.

## 3. 핵심 행동 원칙

> POC 코드를 그대로 복사하지 않는다. POC에서 검증한 **책임, 흐름과 계약**을 추출하고, zen-ai의 실제 연결 지점에 맞춰 독립 내장 Agent로 다시 구현한다.

## 4. 단계별 행동 플랜

### 1단계. 이식 기준 확정

POC와 최신 설계 문서를 비교하여 제품으로 옮길 계약을 먼저 고정한다.

- 커스텀 Harness의 Node·Edge·분기 책임
- Search·Question·Recording Tool의 입력과 정형화된 반환값
- `authorized_meeting_ids`, `recording_modal_status`의 소유권과 생명주기
- Search Tool의 HITL 중단·재개 규칙
- 회의록 원문을 State·Checkpoint·Trace에 저장하지 않는 보안 경계
- 녹화 Tool은 결과를 LLM에 재투입하지 않고 UI 반환 후 종료한다는 예외 흐름

**완료 기준:** 구현자가 POC 내부 코드를 보지 않아도 각 구성요소의 입력·출력·책임과 다음 실행 경로를 설명할 수 있다.

### 2단계. zen-ai 연결 지점 확인

독립 내장 Agent가 제품에서 호출되고 결과를 반환하기 위해 필요한 실제 연결 지점을 확인한다.

- `@회의록 Agent` 호출 감지와 전용 Thread 생성 지점
- 시스템 Agent 등록·식별 방식
- Agent Runtime과 AI SDK Streaming 진입점
- 커스텀 Harness를 실행할 수 있는 확장 경계
- Local Tool 등록과 `execute` 연결 방식
- 사용자·Thread별 변수값과 HITL 임시 정보의 저장 위치
- 녹화 모달 제어 메서드와 기존 녹화 Backend 호출 경계
- UI에 Tool 진행·HITL·성공·거부·오류를 전달하는 이벤트 형식

**완료 기준:** 추측한 파일명이 아니라 실제 코드의 진입 함수, 호출 관계와 데이터 계약을 근거로 연결도를 작성한다.

### 3단계. 독립 회의록 Agent 구조 설계

확인한 연결 지점 위에 회의록 Agent 전용 영역과 외부 Adapter의 경계를 정한다.

```text
zen-ai 호출·Thread·Streaming 경계
→ 회의록 Agent 전용 진입 Adapter
→ 커스텀 Harness
   ├─ Search Tool
   ├─ Question Tool
   └─ Recording Tool
      ├─ 시작 Skill
      ├─ 일시정지 Skill
      ├─ 재개 Skill
      └─ 종료 Skill
→ 기존 권한·회의록·녹화 Backend 및 UI
```

- Harness는 Agent 전체 실행 순서와 분기를 담당한다.
- Tool은 업무별 입력·출력 계약만 외부에 노출한다.
- 검색, 원문 조회, 권한 검사와 녹화 제어 로직은 Tool에서 분리 가능한 내부 서비스로 캡슐화한다.
- zen-ai 고유 API, DB와 UI 이벤트 형식은 Adapter가 담당하여 핵심 업무 로직에 직접 퍼지지 않게 한다.

**완료 기준:** 각 모듈의 책임과 의존 방향이 한 방향이며, Tool 내부 로직을 독립적으로 테스트할 수 있다.

### 4단계. 기능 단위로 구현

한꺼번에 전체 Agent를 구현하지 않고, 제품에서 끝까지 실행 가능한 단위로 순차 구현한다.

1. 시스템 Agent 호출·전용 Thread·독립 Harness 진입
2. Recording Tool과 네 개 Skill·모달 제어·즉시 UI 반환 경로
3. Search Tool의 권한 필터·후보 처리·HITL·허용 ID 반영
4. Question Tool의 허용 ID 재검증·원문 조회·정형화된 결과 반환
5. Search·Question 결과의 ScratchPad·Context 반영과 Agent LLM 재판단
6. Checkpoint, 오류 처리, Streaming과 Trace 연결

Recording Tool은 `Tool 결과 → recording_modal_status 반영 → UI 반환 → END`로 끝낸다. Search·Question Tool은 `Tool 결과 → 커스텀 Harness → Agent LLM 재판단`으로 돌아간다. 두 종료 규칙을 하나의 공통 분기로 억지로 합치지 않는다.

**완료 기준:** 각 단계가 실제 zen-ai 화면 또는 통합 테스트에서 독립적으로 시연 가능하다.

### 5단계. 설계 기준으로 통합 검증

구현 편의가 아니라 설계 문서의 사용자 흐름을 기준으로 검증한다.

- 회의 시작·일시정지·재개·종료 성공과 정상 거부·오류
- 녹화 Tool 결과가 LLM으로 돌아가지 않고 UI 반환 후 종료되는지 확인
- 검색 후보 0개·1개·복수 후보와 HITL 재개
- 기존 허용 ID의 추가·대체와 재검증
- 선택된 회의록 원문 조회와 질문 답변
- 하나의 요청에서 Search 다음 Question으로 이어지는 Harness Loop
- 사용자·Thread 간 변수값과 HITL 격리
- API Key와 회의록 원문이 State·Checkpoint·Trace에 남지 않는지 확인

**완료 기준:** 핵심 시나리오가 설계 다이어그램과 같은 순서로 실행되고, 보안·권한·데이터 보존 조건을 모두 만족한다.

## 5. 구현 이후의 다음 판단

회의록 Agent가 독립 구조로 안정적으로 동작한 뒤에만 다음을 검토한다.

- 커스텀 Harness에서 여러 Agent가 재사용할 수 있는 공통 부분
- Agent 생성 기능에서 선택 가능한 Harness 정책
- Tool 내부 서비스의 공용 모듈 승격 범위
- 변수값과 HITL의 영속 저장소 고도화

처음부터 범용 Framework를 만들지 않는다. 회의록 Agent에서 실제로 검증된 경계만 추출해 점진적으로 Template화한다.

## 6. 한 문장으로 정리

> **POC에서 검증한 업무 계약을 확정하고, zen-ai의 실제 연결 지점을 확인한 뒤, 커스텀 Harness와 캡슐화된 Tool을 가진 독립 내장 회의록 Agent를 기능 단위로 구현하고 설계 시나리오로 검증한다.**
