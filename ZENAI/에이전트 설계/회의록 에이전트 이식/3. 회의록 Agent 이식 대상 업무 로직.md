# 회의록 Agent 이식 대상 업무 로직

## 1. 문서 목적

이 문서는 POC에서 기술적으로 검증한 내용 중 **zen-ai에 이식해야 할 업무 로직과 보존 조건**을 정의한다. 구체적인 구현 위치와 방식은 zen-ai의 Agent 생성 기능을 파악한 뒤 결정한다.

---

## 2. 전체 업무 흐름

일반 회의록 요청은 하나의 Agent가 사용자 요구를 판단하여 Search 또는 Question 기능을 선택하는 구조다.

```text
사용자 요청
→ Agent 목표 판단
   ├─ Search
   ├─ Question
   └─ Tool 없는 직접 응답

Search·Question 결과
→ 공통 Condition
   ├─ follow_up = true  → Agent 목표 판단 반복
   └─ follow_up = false → 응답 후 종료
```

Search와 Question은 각각 하나의 Tool 역할을 하며, zen-ai 이식 시 내장 회의록 시스템 Agent가 사용하는 두 Tool로 구현한다. 구체적인 등록·호출 방식은 시스템 Agent 구조를 확인한 뒤 결정한다.

---

## 3. Search 업무 로직

Search는 사용자 요청에 맞는 회의록을 찾고, 이후 Question에서 사용할 수 있는 회의록 ID를 확정한다.

1. 사용자 요청에서 검색 조건을 구성한다.
2. 사용자가 접근할 수 있는 회의록 범위에서만 후보를 검색한다.
3. 후보를 0개, 1개, 복수로 판별한다.
4. 후보가 없으면 안내하고, 1개면 해당 회의록을 선택한다.
5. 복수 후보이면 HITL로 사용자 선택을 받는다.
6. 사용자가 선택한 ID의 후보 포함 여부와 접근 권한을 다시 검증한다.
7. 기존 허용 ID가 있으면 필요한 경우 추가·대체 여부를 HITL로 확인한다.
8. 확정된 ID를 `authorized_meeting_ids`에 반영한다.
9. 검색 응답과 `follow_up`을 반환한다.

예외 처리 로직은 다음을 포함한다.

- 후보 밖 ID 또는 잘못된 HITL 입력은 같은 질문으로 재입력 요청
- 이미 허용된 동일 ID를 다시 선택하면 불필요한 추가·대체 HITL 생략
- 권한 거부와 Backend 장애를 구분한 안전한 실패 응답
- Tool 실패 재시도 후 구조화된 결과 반환

---

## 4. Question 업무 로직

Question은 Search에서 확정한 회의록을 근거로 사용자의 질문에 답한다.

1. `authorized_meeting_ids`가 없으면 먼저 회의록을 검색하도록 안내한다.
2. 서버가 `authorized_meeting_ids`를 이용해 조회 범위를 정한다.
3. 원문 조회 직전에 현재 사용자의 접근 권한을 다시 검증한다.
4. 권한이 유효한 회의록 원문을 일시적으로 조회한다.
5. Tool 결과와 원문으로 답변 Context를 구성한다.
6. LLM이 사용자 질문에 대한 답변과 `follow_up`을 생성한다.
7. 답변 생성 후 회의록 원문 Context를 폐기한다.

`authorized_meeting_ids`는 서버가 Tool의 조회 범위를 제한하는 변수이며 Question LLM에 직접 전달하지 않는다.

---

## 5. 공통 결과 처리 로직

Search와 Question은 모두 `response + follow_up` 형식의 결과를 반환한다.

- `follow_up = true`: 현재 요청에 남은 업무가 있으므로 Agent가 다음 Tool을 판단한다.
- `follow_up = false`: 사용자에게 응답하고 `none` 상태로 종료한다.

반복·종료는 별도 LLM 판단이 아니라 공통 고정 Condition이 결정한다.

---

## 6. 녹화 업무 로직

`/meeting-start`, 회의 시작 등 녹화 명령은 일반 회의록 Agent의 자유 판단 대상이 아니다.

```text
녹화 Trigger
→ 기존 녹화 모달과 Backend 실행
→ 실행 결과에 따라 recording_modal_status 갱신
```

실제 녹화 단계별 상태는 녹화 모달이 소유한다. Agent는 Trigger 실행과 결과 동기화만 담당하며 Search·Question은 녹화 상태를 읽거나 변경하지 않는다.

---

## 7. 관리해야 할 값

- `ScratchPad`: Agent 판단, Tool 사용 결과와 응답 이력을 기록하는 공간
- `authorized_meeting_ids`: 현재 Thread에서 사용할 수 있도록 권한 검증이 완료된 회의록 ID 변수
- `recording_modal_status`: 녹화 Trigger 실행 결과를 동기화하는 변수
- `user_id`, `thread_id`, 현재 요청: 실행 시 전달하는 Runtime Context

위 값들은 `search`, `question`, `none`과 같은 Graph State와 구분한다.

---

## 8. 반드시 보존할 조건

- 회의록 접근 권한은 LLM이 아니라 서버와 Repository 경계에서 검증한다.
- 회의록 원문은 답변 생성 중에만 사용하고 State, Checkpoint, Trace와 Log에 저장하지 않는다.
- `authorized_meeting_ids`는 Search 후보 판별에 필요한 경우를 제외하고 LLM에 직접 전달하지 않는다.
- 사용자와 Thread별로 허용 ID, 실행 상태와 HITL Context를 격리한다.
- HITL의 잘못된 입력은 진행 정보를 잃지 않고 같은 질문으로 다시 요청한다.
- Search·Question과 녹화 Workflow의 책임을 섞지 않는다.
- 종료를 위한 별도 `done` 상태나 불필요한 LLM 호출을 추가하지 않는다.
- 내부 오류와 민감정보를 사용자 응답 및 추적 데이터에 노출하지 않는다.

## 핵심 정의

> **이식 대상은 POC의 Python·LangGraph 코드가 아니라, 단일 Agent의 Search·Question Tool 선택과 반복, HITL, 권한 검증, 안전한 원문 사용 및 녹화 Trigger로 구성된 업무 로직과 설계 계약이다.**
