# zen-ai 내장 시스템 Agent 실행 기반 파악

## 1. 문서 목적

이 문서는 회의록 Agent 이식 행동 플랜의 2단계에 따라, **zen-ai에 내장 회의록 시스템 Agent를 추가할 때 재사용할 실행 기반과 확장할 경계**를 정리한다. **에이전트를 호출하면 스레드가 생겨고 그 스레드에서 에이전트를 사용하는 그 기초 기반은 유지해야하기 때문.**

일반 Agent 생성 기능은 관리자가 Prompt·모델·MCP Tool 등을 설정하여 Agent를 만드는 기능이다. 회의록 Agent는 이 기능으로 생성하지 않고, 모든 사용자가 처음부터 호출할 수 있는 내장 시스템 Agent로 구현한다.

---

## 2. 조사 결과

현재 zen-ai에는 내장 AI 기능은 존재하지만, 회의록 Agent가 그대로 따를 수 있는 별도의 **내장 시스템 Agent 유형이나 등록 구조**는 확인되지 않았다.

- 일반 Agent는 DB에 저장된 Agent·정책 버전·허용 Tool 정보를 Runtime이 읽어 실행한다.
- 메시지에서 Agent가 호출되면 실행 작업이 생성되고 Worker가 이를 처리한다.
- Worker는 대화 Context, System Prompt, 모델과 Tool을 준비해 AI SDK의 `streamText()`를 실행한다.
- AI SDK는 같은 실행 안에서 LLM의 Tool 호출, Tool 실행 결과의 재전달과 다음 LLM 호출을 반복한다.
- 최종 Agent 답변은 채팅 메시지로 저장되지만 Tool 결과 원문은 다음 요청의 대화 Context로 저장되지 않는다.
- Tool 감사 기록에는 호출한 Tool 이름과 출처 정보만 남는다.

따라서 새로운 Agent 실행 Framework를 만들 필요는 없다. 기존 Runtime과 AI SDK 실행 구조를 재사용하면서, **DB에서 일반 Agent 정의를 읽는 경로와 나란히 코드에 내장된 회의록 Agent 정의를 읽는 경로**를 추가하면 된다.

---

## 3. 기존 일반 Agent 실행 흐름

```text
사용자 메시지에서 Agent 호출
→ Agent 실행 작업 생성
→ DB에서 Agent 정책 버전 로드
→ 대화 Context 로드
→ 모델·System Prompt·허용 MCP Tool 준비
→ AI SDK streamText() 실행
→ LLM ↔ Tool 반복
→ 최종 답변 Streaming 및 메시지 저장
```

이 구조에서 다음 기능은 회의록 Agent도 그대로 재사용한다.

- 사용자·Thread의 채팅 Context 구성
- 모델 Provider 연결
- AI SDK Streaming
- 동일 실행 안의 LLM·Tool 반복과 Tool 결과 재전달
- 최대 출력 Token, Context 한도와 최대 Round
- 최종 답변 저장 및 화면 전달
- Tool 호출 감사와 사용량 기록

## 4. 회의록 시스템 Agent를 위해 추가할 경계

회의록 Agent 호출 시에는 일반 Agent처럼 DB의 사용자 설정을 읽지 않고 코드에 고정된 정의를 읽는다.

```text
Agent 호출 확인
├─ 일반 Agent
│  → DB의 Agent 정의·정책·허용 Tool 로드
└─ 회의록 시스템 Agent
   → src/lib/agents/meetings/agent_definition.ts 로드

공통 단계
→ 기존 Runtime과 AI SDK로 실행
```

Runtime에는 다음과 같은 최소 확장이 필요하다.

1. 회의록 시스템 Agent의 고정 호출 주소와 식별자를 등록한다.
2. 회의록 Agent를 모든 사용자가 호출할 수 있도록 일반 Agent 부여 절차와 구분한다.
3. 회의록 Agent일 때 `agent_definition.ts`에서 System Prompt, 모델 정책과 Tool 정의를 읽는다.
4. 코드로 정의된 Search·Question Tool을 AI SDK의 Tool 목록에 연결한다.
5. 회의록 Agent의 녹화 명령은 LLM에 전달하지 않고 `recording.ts`로 보낸다.
6. Search·Question 결과의 `response + follow_up`을 설계의 공통 Condition에 맞게 처리한다.

---

## 5. 대화 및 Tool 실행 이력

기존 AI SDK는 같은 실행 안에서 다음 내용을 실행 문맥에 누적하여 다음 LLM 호출에 전달한다.

- 사용자 입력
- LLM의 Tool 호출
- Tool 실행 결과
- 이후 LLM 호출과 최종 답변

따라서 POC의 ScratchPad 역할을 위해 별도의 `scratchpad.ts`를 만들 필요는 없다. 기존 AI SDK 실행 문맥과 Runtime의 Thread 대화 Context를 재사용한다.

다만 Tool 결과는 실행이 끝난 뒤 다음 사용자 요청의 대화 Context로 복원되지 않는다. 회의록 Agent에서 실행을 넘어 유지해야 하는 값은 ScratchPad가 아니라 다음 두 영역으로 분리한다.

- `session-data.ts`: 사용자·Thread별 `authorized_meeting_ids`, `recording_modal_status`
- `hitl.ts`: HITL 중단 후 Tool 실행을 재개하는 데 필요한 최소 정보

회의록 원문은 Tool 2 실행 중 AI SDK Context에서만 사용하고, 채팅 메시지·Session Data·HITL 정보·Log·Audit에 저장하지 않는다.

## 6. 녹화 명령 처리 기반

녹화 명령은 일반적인 LLM Tool Calling 대상이 아니다. Runtime이 회의록 시스템 Agent의 입력을 받을 때 먼저 결정적으로 검사한다.

```text
회의록 시스템 Agent 입력
→ 녹화 명령인가?
   ├─ 예: LLM에 전달하지 않음
   │      → recording.ts
   │      → 기존 녹화 모달·Backend 연결
   │      → 결과에 따라 recording_modal_status 갱신
   └─ 아니요: 기존 AI SDK 실행 경로
```

모달 내부의 상세 녹화 State는 기존 녹화 기능이 소유한다. 회의록 Agent는 명령 전달과 최종 상태 동기화만 담당한다.

---

## 7. HITL 처리 기반

AI SDK의 일반 Tool 반복은 한 번의 실행 안에서 끝난다. 반면 HITL은 사용자 입력을 기다렸다가 Tool 실행을 이어가야 하므로 별도의 중단·재개 정보가 필요하다.

개념적으로는 Search Tool이 아직 실행 중인 상태이며, 구현에서는 Worker를 계속 점유하지 않도록 실행을 중단하고 다음 입력에서 복원한다.

```text
Search Tool 실행
→ 사용자 선택 필요
→ hitl.ts가 사용자·Thread별 Pending HITL 최소 정보 저장
→ UI 스레드에 질문 출력
→ 사용자 입력 검증
→ 같은 Search Tool 처리 재개
```

`hitl.ts`에는 회의록 원문이나 전체 대화 이력을 저장하지 않는다. HITL 종류, 후보 ID, 허용 입력과 재개 위치 등 최소 정보만 관리한다.

---

## 핵심 정리

> **zen-ai에는 회의록 Agent가 그대로 따를 기존 내장 시스템 Agent 유형은 없지만, 일반 Agent를 실행하는 Runtime과 AI SDK 기반은 이미 구축되어 있다. 회의록 Agent는 `src/lib/agents/meetings`의 코드 정의를 Runtime이 선택적으로 불러오도록 최소 확장하고, 기존 Streaming·대화 Context·LLM/Tool 반복 실행은 그대로 재사용한다.**
