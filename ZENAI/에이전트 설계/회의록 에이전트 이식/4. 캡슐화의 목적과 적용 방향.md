# 캡슐화의 목적과 적용 방향

## 캡슐화란

> **캡슐화는 외부에는 입력값과 출력값만 보여주고, 밖에서는 내부 로직을 알거나 직접 건드리지 못하게 하는 것이다.**

호출하는 쪽은 정해진 입력을 전달하고 결과만 받는다. 구체적인 처리 과정과 권한·보안 검증은 캡슐 내부가 책임진다.

## 1. 핵심 목적

회의록 Agent에서 캡슐화를 적용하는 목적은 내부 로직을 명확한 입출력 계약 뒤에 두고 다음 세 가지 효과를 얻는 것이다.

1. **안전성·보안 정책의 내부 강제**
2. **내부 변경이 외부에 미치는 영향 최소화**
3. **Tool과 커스텀 Harness 내부 로직의 재사용성 증대**

단순히 파일을 여러 개로 나누거나 내부 구현을 외부에 보이지 않게 만드는 것만으로는 충분하지 않다. 외부에는 필요한 기능과 제한된 입출력 형식만 제공하고, 권한 확인·입력 검증·민감정보 보호 같은 정책을 캡슐 내부에서 일관되게 강제해야 한다.

## 2. 안전성·보안

UI와 LLM은 내부 업무 로직을 직접 조작하지 않고 정해진 인터페이스를 통해서만 기능을 요청해야 한다. 캡슐 내부에서는 입력값을 신뢰하지 않고 권한과 안전정책을 다시 검증한다.

회의록 Agent에서는 다음과 같은 로직이 이 경계에 해당한다.

- 사용자별 회의록 접근 권한 검증
- `authorized_meeting_ids`에 포함된 회의록만 조회하도록 제한
- Tool 입력값의 형식과 허용 범위 검증
- 회의록 원문과 인증정보가 State, Checkpoint, Trace에 남지 않도록 차단
- 녹화 제어 요청이 허용된 상태 전이인지 검증
- HITL 결과가 허용된 선택지인지 검증

이러한 검증을 UI나 시스템 프롬프트에만 의존하면 UI 또는 모델의 잘못된 요청으로 정책이 우회될 수 있다. 따라서 실제 데이터와 기능을 다루는 내부 로직이 최종적인 보안 경계가 되어야 한다.

## 3. 변경 영향 최소화

호출하는 쪽은 내부 구현이 아니라 입력과 출력의 계약에만 의존해야 한다. 이 계약을 유지하면 내부 구현이 변경되어도 UI, 모델, Tool 또는 다른 Agent를 함께 수정할 필요가 줄어든다.

예를 들면 다음과 같다.

- 회의록 저장소가 변경되어도 Search Tool의 검색 요청·응답 형식은 유지한다.
- 권한 확인 방식이 변경되어도 Tool은 동일한 권한 검증 인터페이스를 호출한다.
- 녹화 Backend가 변경되어도 Recording Tool은 동일한 녹화 제어 결과를 받는다.
- HITL 저장 방식이 변경되어도 Tool과 UI 사이의 대기·재개 계약은 유지한다.

즉, 외부에 공개된 계약과 내부 구현을 분리하여 변경 범위를 캡슐 내부로 제한한다.

## 4. Tool 내부 로직의 재사용성

zen-ai Agent 프로젝트는 **Tool 중심의 Agent**를 기조로 하며, 앞으로 다양한 Tool을 계속 추가하는 방향으로 발전한다.

Tool 하나에 모든 코드를 직접 작성하면 비슷한 Tool을 추가할 때마다 같은 로직을 다시 구현해야 한다. 반대로 공통 기능을 책임 단위로 분리해 캡슐화하면 새로운 Tool은 검증된 로직을 조합하고 Tool 고유의 부분만 구현할 수 있다.

```text
Tool 인터페이스
→ 필요한 내부 로직을 import
→ Tool에 필요한 조합과 고유 로직만 구현

재사용 가능한 내부 로직
→ 하나의 명확한 책임으로 분리
→ lib 등의 공용 영역에 캡슐화
```

권한 확인, 입력 검증, 데이터 조회, 결과 정형화처럼 여러 Tool에서 반복될 수 있는 로직이 대표적인 대상이다. 이를 통해 중복 구현을 줄이고 새로운 Tool을 더 빠르고 일관되게 추가할 수 있다.

## 5. 커스텀 Harness 로직의 재사용성

회의록 Agent는 기존 Agent 생성 Template에 단순히 끼워 넣는 Agent가 아니다. 별도 공간에 커스텀 Harness를 포함한 독립 Agent를 구현하고, 설계한 제어 흐름이 실제 제품 환경에서도 작동하는지 확인하는 첫 사례다.

회의록 Agent의 커스텀 Harness가 정상적으로 동작하면 향후 Agent 생성 기능에서 Harness 제어 방식을 선택할 수 있도록 Template화하는 기반으로 활용할 수 있다.

```text
커스텀 Harness
→ 실행·분기 책임에 따라 작은 로직으로 분리
→ 재사용 가능한 로직은 캡슐화
→ 필요한 제어 로직을 조합하여 새로운 Harness 구성
```

Tool 결과 반영, Checkpoint, HITL 중단·재개, 즉시 종료와 LLM 재판단 같은 제어 로직을 합당한 책임 단위로 나누면 다른 Agent의 Harness를 만들 때 검증된 로직을 다시 조합할 수 있다.

## 6. 캡슐화 대상을 판단하는 기준

다음 조건 중 하나 이상에 해당하는 로직은 Tool이나 Harness에서 분리하여 재사용 가능한 단위로 캡슐화할 가치가 있다.

- 둘 이상의 Tool이나 Agent에서 반복될 가능성이 있는가
- 독립적인 입력과 출력으로 표현할 수 있는가
- 하나의 명확한 책임을 가지는가
- 외부에서 내부 구현을 몰라도 호출할 수 있는가
- 보안·권한 정책을 반드시 동일하게 적용해야 하는가
- 내부 구현이 바뀌어도 호출부의 변경을 막아야 하는가
- 독립적으로 테스트할 가치가 있는가

반대로 한 곳에서만 사용하는 단순한 연결 코드까지 억지로 분리하지 않는다. 분리했을 때 **보안 정책의 일관성**, **변경 영향의 격리**, **재사용성** 중 하나 이상의 실질적인 이점이 있어야 한다.

또한 재사용 가능성이 불확실한 로직을 미리 과도하게 일반화하지 않는다. 현재 책임과 입출력 계약을 명확하게 만드는 것을 우선하고, 실제로 공통 사용 사례가 확인되면 공용 영역으로 확장한다.

## 7. 적용 대상과 기대 효과

| 대상 | 캡슐화하는 내용 | 안전성·보안 | 변경 영향 최소화 | 재사용성 |
|---|---|---|---|---|
| Tool 내부 로직 | 권한 확인, 입력 검증, 데이터 접근, 결과 정형화 | UI·LLM의 정책 우회와 민감정보 노출 차단 | 저장소와 검증 방식의 변경을 Tool 외부와 격리 | 새로운 Tool에서 검증된 로직 재사용 |
| 커스텀 Harness | Tool 결과 반영, 분기, HITL, Checkpoint, 종료 방식 | 허용된 실행 흐름과 사용자 개입 경계 강제 | 제어 방식의 변경을 UI와 Tool에서 격리 | 다른 Agent의 Harness 구성에 재사용 |
| Recording Skill | 시작, 일시정지, 재개, 종료의 녹화 제어 | 허용되지 않은 상태 전이와 직접 Backend 조작 차단 | 녹화 Backend 변경을 Recording Tool에서 격리 | 다른 녹화 기능에서 제어 로직 재사용 |

## 8. 결론

회의록 Agent에서 캡슐화는 단순한 코드 정리 기법이 아니다. 권한과 안전정책을 내부에서 강제하고, 내부 구현 변경의 파급 범위를 줄이며, Tool과 커스텀 Harness를 반복적으로 확장할 수 있게 만드는 설계 원칙이다.

따라서 각 로직은 외부에 명확한 입력과 출력 계약을 제공하고, 보안 검증과 구체적인 구현은 캡슐 내부에 둔다. 다만 재사용 가능성이 없는 단순 로직까지 무조건 분리하지 않고 실제 효과가 있는 책임 단위를 기준으로 캡슐화한다.
