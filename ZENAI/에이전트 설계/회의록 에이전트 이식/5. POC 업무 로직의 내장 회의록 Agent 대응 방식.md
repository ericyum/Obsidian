# POC 업무 로직의 내장 회의록 Agent 대응 방식

## 1. 문서 목적

이 문서는 POC에서 검증한 회의록 Agent의 업무 로직을 zen-ai의 **내장 회의록 시스템 Agent**로 구현할 때 각 책임을 어디에 둘지 정의한다.

핵심 방향은 다음과 같다.

> **회의록 Agent 전용 실행 Framework를 새로 만들지 않는다. 회의록 전용 정의와 업무 로직은 `src/lib/agents/meetings`에 두고, 모델 실행·Streaming·대화 Context와 LLM/Tool 반복은 기존 Runtime과 AI SDK를 재사용한다.**

---

## 2. 목표 폴더 구조

```text
src/lib/agents/meetings/
├─ agent_definition.ts  # System Prompt, 모델 정책, Tool 이름·설명·등록 정보
├─ search-tool.ts       # Tool 1: Search 업무 로직
├─ question-tool.ts     # Tool 2: Question 업무 로직
├─ recording.ts         # 녹화 명령과 기존 모달·Backend 연결
├─ session-data.ts      # authorized_meeting_ids, recording_modal_status 관리
└─ hitl.ts              # HITL 중단·입력 검증·재개 정보 관리
```

다음 파일은 별도로 만들지 않는다.

- `scratchpad.ts`: 기존 AI SDK 실행 문맥과 Thread 대화 Context를 재사용한다.
- `types.ts`: 공통 사용이 실제로 생기기 전까지 각 파일 안에 필요한 Type을 정의한다.
- `handler.ts`: 별도 실행 계층을 추가하지 않고 Runtime의 회의록 Agent 전용 분기에서 처리한다.

---

## 3. 전체 실행 흐름

```text
사용자가 회의록 시스템 Agent 호출
→ Runtime이 회의록 Agent 전용 정의를 코드에서 로드
→ Agent 실행 환경 준비
   ├─ System Prompt 등록
   ├─ Search Tool 등록 → search-tool.ts 실행 함수 연결
   └─ Question Tool 등록 → question-tool.ts 실행 함수 연결
→ 입력이 녹화 명령인지 먼저 확인
   ├─ 녹화 명령
   │  → LLM에 전달하지 않음
   │  → recording.ts 실행
   │  → recording_modal_status 갱신
   └─ 일반 요청
      → 준비된 회의록 Agent에 사용자 입력 전달
      → LLM이 직접 답변하거나 등록된 Tool 선택
      → 선택된 Tool의 실행 함수 호출
      → Tool 결과에 대한 공통 Condition 처리
      → 반복 또는 최종 응답
```

---

## 4. 파일별 책임

### 4.1 `agent_definition.ts`

회의록 시스템 Agent를 AI SDK로 조립하는 데 필요한 고정 정의를 제공한다.

- Agent 이름과 고정 호출 식별자
- System Prompt
- 기본 모델과 기존 Runtime 기본값을 사용하는 추론·출력·Context·Round 정책
- Search·Question Tool의 이름, Description과 실행 함수 연결 정보

별도로 정하지 않은 실행 정책은 다음 값을 명시하여 기존 Runtime 기본 동작을 사용한다.

```ts
defaultReasoningEffort: null,
maxOutputTokens: null,
contextLimitTokens: null,
maxRounds: 0,
```

- `null`: 별도 제한이나 Override를 두지 않고 기존 모델·Provider·Runtime 기본값을 사용한다.
- `maxRounds: 0`: LLM이 실행을 끝낼 때까지 별도의 Round 상한을 두지 않는다.

Runtime은 회의록 Agent가 호출되었을 때에만 이 파일의 정의를 읽는다. 이 파일은 별도의 Graph나 LLM 반복문을 구현하지 않는다.

`agent_definition.ts`는 Search·Question Tool 객체를 AI SDK의 `tools`에 직접 등록한다. 각 Tool 객체에는 실행할 `execute()` 함수가 포함되므로, LLM이 Tool 이름을 선택하면 AI SDK가 연결된 실행 함수를 자동으로 호출한다. 따라서 Runtime에 Tool 이름별로 `search-tool.ts` 또는 `question-tool.ts`를 찾아 실행하는 별도의 분기 로직은 추가하지 않는다.

### 4.2 `search-tool.ts`

POC의 Search Subgraph 전체를 하나의 Tool 내부 로직으로 구현한다.

- 검색 조건 구성
- 접근 가능한 회의록 후보 검색
- 후보 0개·1개·복수 판별
- 복수 후보 선택 HITL
- 선택 ID의 후보 포함 여부와 권한 재검증
- 기존 허용 ID의 추가·대체 HITL
- `authorized_meeting_ids` 갱신
- `response + follow_up` 반환

### 4.3 `question-tool.ts`

POC의 Question Subgraph 전체를 하나의 Tool 내부 로직으로 구현한다.

- 사용자·Thread의 `authorized_meeting_ids` 확인
- 원문 조회 직전 현재 접근 권한 재검증
- 허용된 회의록 원문 임시 조회
- 질문 답변에 필요한 Context 구성
- 답변과 `follow_up` 생성
- 처리 완료 후 원문 Context 폐기

`authorized_meeting_ids`는 서버가 조회 범위를 제한하는 데 사용하며 Question LLM에 직접 전달하지 않는다.

### 4.4 `session-data.ts`

회의록 Agent가 사용자·Thread별로 유지해야 하는 변수값을 관리한다.

- `authorized_meeting_ids`
- `recording_modal_status`

이 값들은 `search`, `question`, `none`과 같은 Graph Engineering의 State가 아니다. Tool과 녹화 로직이 사용하는 관리 변수값이다.

### 4.5 `hitl.ts`

Search Tool 실행 중 사용자 선택이 필요할 때 중단과 재개를 관리한다.

- Pending HITL 저장과 조회
- 사용자·Thread별 격리
- 허용 입력 검증
- 잘못된 입력에 같은 질문 재요청
- 같은 Search Tool 처리 지점 재개
- 완료 또는 취소 시 Pending 정보 제거

회의록 원문과 전체 ScratchPad는 저장하지 않는다.

### 4.6 `recording.ts`

녹화 명령을 기존 녹화 모달·Backend와 연결한다.

- 녹화 명령을 구조화된 명령으로 변환
- Frontend 녹화 모달에 실행 요청 전달
- 기존 Backend 처리 결과 수신
- 결과에 따라 `recording_modal_status` 갱신
- 사용자에게 성공·실패 안내

모달의 내부 녹화 단계별 State는 이 파일이나 Agent가 소유하지 않는다.

## 5. Runtime에서 변경할 부분

Runtime은 일반 Agent 실행 구조를 유지하면서 회의록 시스템 Agent에 필요한 분기만 추가한다.

### 5.1 시스템 Agent 호출과 정의 로드

```text
일반 Agent 호출
→ DB의 Agent 정의와 정책 로드

회의록 시스템 Agent 호출
→ src/lib/agents/meetings/agent_definition.ts 로드
```

회의록 Agent는 Agent 생성 모달, 사용자별 부여와 MCP Tool 선택을 사용하지 않는다. 고정 시스템 Agent로 등록하며 모든 사용자가 호출할 수 있게 한다.

### 5.2 녹화 명령 선처리

회의록 Agent 입력이 녹화 명령이면 AI SDK에 전달하지 않고 `recording.ts`를 실행한다. 이 분기는 회의록 Agent가 호출된 경우에만 동작하므로 다른 Agent의 입력에는 영향을 주지 않는다.

### 5.3 회의록 Agent 실행 환경 준비와 일반 요청 처리

Runtime은 회의록 Agent 실행 환경을 준비할 때 `agent_definition.ts`에서 다음 정보를 읽어 기존 AI SDK 입력 위치에 등록한다.

```text
System Prompt → AI SDK의 System Instructions
Tool 이름·Description·입력 Schema·실행 함수 → AI SDK Tools
모델·추론·실행 정책 → 기존 모델 실행 옵션
```

그 이후 일반 요청이 들어오면 이미 준비된 회의록 Agent에 사용자 입력을 전달한다. LLM은 System Prompt와 등록된 Tool 정보를 보고 직접 답변하거나 필요한 Tool을 선택한다.

```text
LLM이 Search Tool 선택
→ search-tool.ts의 실행 함수 호출

LLM이 Question Tool 선택
→ question-tool.ts의 실행 함수 호출
```

사용자 입력, 기존 Thread Context, Tool 호출 결과의 다음 LLM 전달과 Streaming은 기존 Runtime이 담당한다.

### 5.4 공통 결과 처리

Search와 Question은 공통으로 `response + follow_up`을 반환한다.

```text
follow_up = true
→ Tool 결과를 AI SDK 실행 문맥에 추가
→ LLM이 다음 목표와 Tool을 판단

follow_up = false
→ response를 최종 사용자 응답으로 전달
→ 추가 LLM 호출 없이 실행 종료
```

기존 AI SDK는 Tool 결과를 다음 LLM 호출에 자동 전달하므로 `follow_up = true` 경로를 재사용할 수 있다. `follow_up = false`일 때 Tool의 `response`를 바로 최종 출력하도록 회의록 Agent 전용 종료 조건을 Runtime의 Tool 결과 처리 지점에 추가한다.

---

## 6. ScratchPad 대응

별도의 `scratchpad.ts`를 만들지 않는다.

```text
같은 실행 안의 사용자 입력·Tool 호출·Tool 결과
→ AI SDK 실행 문맥이 누적하고 다음 LLM 호출에 전달

실행을 넘어 유지되는 사용자·Agent 대화
→ 기존 Thread 메시지 Context 사용
```

HITL 재개 정보와 회의록 Agent 변수값은 ScratchPad와 구분하여 각각 `hitl.ts`, `session-data.ts`에서 관리한다.

---

## 7. HITL 처리

HITL은 Search Tool 내부의 업무 흐름이다. Agent 입장에서는 Search Tool 호출이 아직 완료되지 않은 상태다.

```text
Search Tool
→ 사용자 선택 필요
→ 실행 중단 및 Pending HITL 저장
→ UI 스레드에 질문
→ 사용자 입력
→ 입력 검증
→ Search Tool 처리 재개
→ 최종 Tool 결과 반환
```

Worker의 열린 실행을 계속 유지하지 않고, `hitl.ts`가 재개에 필요한 최소 정보를 저장한 뒤 다음 사용자 입력에서 복원한다. 이를 통해 Runtime Timeout이나 프로세스 재시작에도 대응할 수 있어야 한다.

## 8. 보안과 데이터 경계

- 회의록 Agent 사용 권한과 개별 회의록 접근 권한을 구분한다.
- 모든 사용자가 시스템 Agent를 호출할 수 있어도 Search와 Question의 Backend 권한 검증은 생략하지 않는다.
- Tool 1 검색과 Tool 2 원문 조회에서 사용자 권한을 검증하고, Tool 2는 조회 직전에 다시 검증한다.
- `authorized_meeting_ids`와 Pending HITL은 사용자·Thread별로 격리한다.
- 회의록 원문은 Question Tool과 LLM 답변 생성 중에만 메모리에서 사용한다.
- 원문은 채팅 메시지, Session Data, Pending HITL, Log, Trace와 Tool Audit에 저장하지 않는다.
- Tool Audit에는 Tool 이름과 안전한 실행 Metadata만 기록한다.
- 내부 오류는 민감정보가 제거된 구조화 결과로 변환한다.

## 9. POC 설계와 zen-ai 구현 대응표

| POC 설계 요소 | zen-ai 구현 위치 |
|---|---|
| 단일 회의록 Agent와 목표 판단 | `agent_definition.ts`의 System Prompt + 기존 LLM Runtime |
| Search Node/Subgraph | `search-tool.ts` |
| Question Node/Subgraph | `question-tool.ts` |
| Search·Question Tool 선택 | 기존 AI SDK Tool Calling |
| `response + follow_up` 공통 Condition | Runtime의 회의록 Agent 전용 Tool 결과 처리 |
| Tool 결과 후 Agent 재진입 | 기존 AI SDK 실행 문맥과 다음 LLM 호출 |
| 최종 응답 후 `none` | `follow_up = false` 처리 후 Runtime 실행 종료 |
| ScratchPad | 기존 AI SDK 실행 문맥과 Thread 대화 Context |
| `authorized_meeting_ids` | `session-data.ts` |
| `recording_modal_status` | `session-data.ts` |
| Search Tool 내부 HITL | `hitl.ts` + 기존 채팅 UI |
| 녹화 Trigger | Runtime의 명령 선처리 + `recording.ts` |
| 권한 검증과 원문 조회 | Search·Question Tool이 호출하는 기존 Meeting Backend |

## 핵심 정리

> **회의록 Agent는 사용자 설정으로 생성하는 일반 Agent가 아니라 코드에 내장된 시스템 Agent다. `agent_definition.ts`와 두 Tool을 기존 Runtime·AI SDK에 연결하고, 녹화 명령·공통 `follow_up` Condition·HITL·Session Data만 회의록 전용 경계로 추가한다.**
