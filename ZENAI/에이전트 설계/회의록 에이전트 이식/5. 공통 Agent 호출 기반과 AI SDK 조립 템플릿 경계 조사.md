# Agent 호출·구동 순서와 독립 실행부 경계 조사

## 1. 조사 목적과 결론

이 문서는 `zen-ai`에서 Agent가 호출되고 답변을 남기기까지의 전체 흐름을 간략히 정리하고, 그 안에서 **공통 제품 기반과 Agent별로 다르게 진행되는 부분 사이의 경계**를 확인한다.

회의록 Agent 이식의 기본 방향은 다음과 같다.

```text
공통 호출·실행 준비 재사용
→ Agent별 Runner 선택
→ 독립 회의록 Agent 실행
→ 공통 결과 처리 재사용
```

즉 채팅, 멘션, 실행을 위한 DB접속과 Worker를 새로 만드는 것까지의 **회의 에이전트도 사용하는 부분은 굳이 건드릴 이유가 없다**. 기존 제품 기반은 유지하고, 일반 AI SDK Tool Loop가 담당하던 중간의 **에이전트가 조립되고 실행되는 부분만 회의록 에이전트의 커스텀 로직으로 교체**하는 것이다.

다만 현재 코드는 이 경계를 독립된 인터페이스로 완전히 분리해 두지 않았다. `runAgentTurn()` 이라는 메서드가 AI SDK를 이용해 일반 Agent들을 조립하고 실행하는 부분이지만, 동시에 **바깥의 worker에 알맞는 반환값으로 만들어저 반환하는 공통 마무리 책임**이 함께 있는 것이다. 아래의 경계 A와 B는 현재 코드에서 분석한 **공통 부분과 에이전트 조립/실행 사이의 경계**이자 앞으로 **책임 경계에 따라 추가로 분리해야 할 지점**이다.

## 2. 최초 호출부터 답변 완료까지 요약

사용자가 채팅창에 다음과 같이 입력했다고 가정한다.

```text
@회의 에이전트 지난 회의를 찾아줘
```

전체 과정은 다음과 같다.

```text
① Channel Handler와 Channel Runtime이 요청 접수·검증
→ ② 사용자 메시지를 message.posted Event로 저장
→ ③ @멘션을 해석하여 회의록 Agent의 agentId 식별
→ ④ Agent DB에서 권한·버전·모델·실행 한도 조회
→ ⑤ agent_runs에 pending 실행 작업 생성
→ ⑥ Worker가 작업을 claim

──── 경계 A: 공통 준비 완료, Agent별 실행부 선택 ────

→ ⑦ 일반 Agent Runner 또는 Meeting Agent Runner 실행
→ ⑧ LLM·Tool·Harness가 이번 요청의 최종 결과 확정

──── 경계 B: Agent별 실행 완료, 공통 처리로 복귀 ────

→ ⑨ Realtime Text와 진행 Event를 UI에 전송
→ ⑩ 최종 답변을 message.posted로 같은 Thread에 저장
→ ⑪ 사용량·Tool 감사 기록 및 agent_runs 완료·실패 처리
```

**최초 호출 메시지는 별도의 Thread 행을 생성하지 않고, 해당 메시지가 Thread 루트**가 된다. 그리고 Agent 답변은 그 메시지의 ID를 `parentEventId`로 사용하여 자동으로 그 아래로 연결된다.

같은 Thread의 **후속 질문도 새로운 `agent_runs` 작업**을 만든다. 새 멘션이 없으면 기존에 호출된 Agent를 상속하고, **Worker는 Thread의 이전 `message.posted` Event를 다시 읽어 이번 Turn의 대화 Context로 구성**한다. 또한 Worker 안에 조립된 Agent가 계속 살아서 다음 질문을 기다리는 구조가 아니라 그때 그때 요청마다 worker가 실행되어 에이전트가 조립이되는 구조인 것이다.

## 3. 경계 A: 공통 준비에서 Agent별 Runner로 넘어가는 지점

경계 A는 **Worker가 `agent_runs`(현재 어떤 사용자 요청이 들어왔고 진행 중인지를 저장하는 DB) 에 있는 작업을 읽고, 실제 Agent 조립/실행을 시작하기 직전**이다.

이 지점까지는 모든 Agent가 다음 제품 기반을 함께 사용한다.

- Channel 메시지 접수와 인증·입력 검증
- `message.posted` 저장과 Thread 루트 지정
- `@` 멘션 해석과 회의록 Agent의 agentId 식별
- 후속 Thread에서 Agent 답변이 Thread 루트에 따라 그 아래로 연결되도록 설정
- Agent 활성 상태와 사용자 권한 확인 및 버전·모델·추론 설정·실행 한도 확정
- `agent_runs` DB 행 생성, Worker가 접수 후 에이전트 조립/실행 요청, worker에 대한 lease(특정 요청의 소유권을 일정 기간 동안 독점적으로 확보하는 설정)와 timeout 설정

이후에는 안정적인 **Agent 유형 식별값을 기준으로 조립/실행을 하는 로직(Runner)를 선택하는 구조**가 필요하다.

```text
Worker가 에이전트 조립/실행 요청
→ Agent 실행 유형 확인
   ├─ 일반 Agent → Standard Agent Runner
   └─ 회의록 Agent → Meeting Agent Runner
```

단순 에이전트 이름이나 변경 가능한 slug을 이용하는 것 보다는 특정 안정적인 식별값을 사용하는 편이 안전할 것이다. 식별값을 어떻게 구현하며 별도의 DB에 넣을지는 구조 설계 단계에서 확정한다.

경계 A에서 어떤 Runner로 갈지 구분하기 위해 제공해야 할 최소 정보는 다음과 같다.

| 입력                                | 용도                    |
| --------------------------------- | --------------------- |
| Run ID와 claim 정보                  | 실행 완료·실패·중복 방지        |
| `agentId`, Agent 유형·버전            | 실행할 Runner와 정책 식별     |
| `triggerEventId`, `triggerUserId` | 현재 요청과 사용자 식별         |
| `channelId`, Thread 루트            | 대화 조회와 결과 전송 위치       |
| 확정된 실행 설정                         | 모델·추론·Token·Round 한도  |
| `AbortSignal`                     | lease 상실·timeout 시 중단 |

## 4. Agent별 실행부의 경계

### 4-1. 일반 Agent Runner

현재 일반 Agent는 Agent DB에서 가져온 시스템 프롬프트·모델·Tool·이전 대화를 AI SDK 코드 안의 `streamText()`메서드에 전달되어 자동조립을 하는 구조이다. 이후 AI SDK의 Tool Loop가 LLM 판단, Tool 실행, Tool 결과 재입력과 최종 답변 생성을 처리한다.

```text
Agent 설정 + Messages + MCP Tool
→ AI SDK streamText()
→ 일반 Tool Loop
→ 최종 답변
```

### 4-2. Meeting Agent Runner

회의록 Agent는 독립 공간의 커스텀 Harness를 실행해야 한다. 일반 Agent와 다른 핵심 책임은 다음과 같다.

- Search·Question Tool 결과를 다음 LLM Context에 포함하고 목표를 재판단
- 복수 후보 선택과 허용 ID 추가·대체를 위한 HITL 중단·재개 로직(이 과정에서 worker의 상태를 건드리지 않고 UI에 출력 및 대기 상태로 있어야 함)
- 사용자·Thread별로 별도의 회의록 Agent 내부 변수값(modal_status, meeting_ids)을 사용
- 최종 사용자 답변 직전의 업무 Checkpoint
- Recording Tool 성공 여부를 반영해 녹화 상태 변수값(modal_status)를 갱신하고, LLM으로 돌아가지 않은 채 UI 결과를 확정하는 종료 규칙(tool calling)
- 회의록 기반 질문시 회의록 접근 권한 재검증과 회의록 원문이 기록등에 남지 않도록 하는 처리
- 회의록 Agent 설계에 맞춘 안전한 Trace

```text
1. Meeting Agent 기초 설정(시스템 프롬프트 등)
2. Messages(기본적으로 worker에서 message.posted로 저장을 해줌) + 에이전트 State 클래스(Messages 외의 변수값, ScratchPad 등의 설정)
3. 커스텀 Harness
4. Search·Question·Recording Tool과 내부의 HITL 특수 로직
```

따라서 회의록 Agent를 기존 `streamText()` Tool Loop의 설정값만 바꾼 일반 Agent로 취급해서는 안 된다. 기존 호출 기반과 연결이 되어있는 것일 뿐, 내부 실행 방식은 독립적이어야 한다.

## 5. 경계 B: Agent별 결과를 공통 처리로 돌려주는 지점

경계 B는 Runner가 사용자에게 보여줄 최종 결과를 확정한 뒤, 공통 UI·DB 처리로 돌아오는 지점이다.

일반 Agent와 회의록 Agent가 내부에서 서로 다른 방식으로 실행되더라도 **이후 worker의 공통 후속 처리 부분 입장에서 동일한 형태**여야 한다.

개념적인 결과에는 다음 내용이 필요하다.

- 실행 결과: 완료·실패·중단(HITL 대기 상태에서 중단되는 경우를 후속 처리 코드에서 추가할 지는 나중에 고민)
- 사용자에게 보여줄 최종 답변
- Token 사용량
- Tool 감사에 사용할 민감한 값이 없는 Metadata
- 답변을 보여주기 위한 Channel 및 Thread정보(어디에 최종 답변을 출력할지)

### Streaming

에이전트 Runner가 끝난 뒤 지정된 형태로 반환하는 로직 말고도, 에이전트 실행 중 발생하는 Tool호출 현황 같은 **실시간 진행 상황을 worker쪽 공통 Realtime 처리 로직으로 전달**할 수 있도록 Streaming 기능용 출력 형식도 동일한 형태 여야 한다.(callback 또는 event sink 등의 형식이라고 함) 

```text
Agent별 Runner
├─ 실행 중: 공통 Realtime 출력 경계로 Text·진행 Event 전달
└─ 실행 종료: 표준화된 최종 결과 반환
                    ↓
               공통 Finalizer(Worker)
```

## 6. 공통 결과 처리로 재사용할 영역

경계 B 이후에는 가능한 한 다음 기존 제품 기능을 재사용한다.

- Realtime Text와 진행 Event 전송(worker에 지정된 형태의 실시간 진행 사항을 전달하는 Streaming 기능)
- 최종 Agent 답변을 `message.posted`로 저장(worker에서 `message.posted`라는 공간으로 사용자과 에이전트 사이의 대화가 저장(Messages), 그 후 이를 토대로 UI가 출력하는 구조)
- 호출 메시지의 Thread 루트에 답변 연결
- Token 사용량과 Tool 호출 감사 기록
- `agent_runs` 성공·실패·중단 처리
- claim·lease(에이전트 호출 및 worker 하나가 점유하고 있는 것을 보장하는 로직)가 올바르게 이루어졌는지 확인 및 중복 완료 방지 로직

현재는 **이 기능들이 독립된 Finalizer로 분리되어 있지 않고 `runAgentTurn()` 내부에 일반 AI SDK 실행 코드와 함께** 있다. 따라서 Meeting Agent Runner를 추가할 때는 공통 코드를 복사하는 것이 아니라, 일반·회의록 Runner가 함께 사용할 **Realtime 출력 부분과 최종 답변 처리 부분를 따로 추출**하는 방향이 적절하다.

## 7. "State 클래스"에 Messages는 필요 없다.

### 7-1. Messages

기존 worker에 있는 `message.posted` Event가 대화 이력이다. Worker는 새 Run을 시작할 때 현재 Thread의 Event를 읽어 `ModelMessage[]`로 변환한다.

```text
기존 message.posted Event
→ Worker가 Thread 대화 조회
→ ModelMessage[] 구성
→ Meeting Agent Runner 등 조립된 에이전트에 입력
```

따라서 회의록 Agent 내부에 별도의 Messages를 둬서 동일한 대화 이력을 다시 저장할 필요는 없다. 그저 에이전트가 호출이 되면 Worker가 생성한 Messages(`ModelMessage[]`)를 조립된 에이전트에 입력만 하도록 하면 된다.

### 7-2. "State 클래스"와 Scratchpad

Messages와는 다르게 회의록 Agent에만 있는 고유 값들은 공통 `message.posted` 처리로 대체되지 않는다.

```ts
type MeetingExecutionState = {
  authorizedMeetingIds: string[];
  recordingModalStatus: RecordingModalStatus;
  pendingHitl?: PendingHitl;

  scratchpad: {
    toolResults: ToolResult[];
    workingContext: WorkingContext[];
  };
};
```

- 이전 대화 이력(Messages): worker의 `message.posted`에서 가져다 씀 -> **"State 클래스"에는 없음**
- 권한·녹화·HITL 현재 상태값: `MeetingExecutionState` 내부의 각 변수 값들
- 다음 LLM 판단에 필요한 가변적인 context: `scratchpad`

**저 "State 클래스"인 'MeetingExecutionState'가 GraphEngineering에서의 State이다.**

#### Trace

과거 실행 내역을 로그의 형태로 기록을 한다면 Trace로직도 추가하는 것을 고려해야 한다. Trace는 실행 로그이지 Scratchpad와는 다르다. 그리고 Trace를 구현하려면 Meeting Agent Runner가 별도로 관리해야 하며 구체적으로 어떻게 관리를 할 지는 향후 '독립 회의록 Agent 구조 설계' 단계에서 확정해야 한다.

## 8. 현재 코드에서 확인한 위치

| 책임                           | 현재 코드 위치                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------ |
| 메시지 API·검증                   | `src/app/api/channels/[channelId]/messages/route.ts`, `src/lib/channels/handlers.ts` |
| 메시지 저장·멘션·Run 생성             | `src/lib/channels/messages.ts`                                                       |
| Agent 권한·실행 설정 확정            | `src/lib/agents/effective-config.ts`                                                 |
| `agent_runs` 생성·claim        | `src/lib/agents/runs.ts`, `src/lib/agents/worker-runtime.ts`                         |
| Thread Messages와 Agent 설정 조회 | `src/lib/agents/worker-runtime.ts`                                                   |
| AI SDK 조립·일반 Tool Loop       | `src/lib/agents/worker-runtime.ts`의 `startAgentStream()`                             |
| 현재 Turn 조정과 공통 마무리           | `src/lib/agents/worker.ts`의 `runAgentTurn()`                                         |
| Agent 관리 API                 | `src/lib/agents/runtime.ts`                                                          |

`src/lib/agents/runtime.ts`는 Agent 생성·수정·활성화와 같은 관리 API의 Runtime이다. Worker가 Agent Turn을 실행하고 AI SDK를 조립하는 Runtime과 혼동하면 안 된다.

## 9. 최종 정리

회의록 Agent는 **기존 제품의 채팅과 실행 기반을 사용하되, 독립된 회의 에이전트 실행 로직를 가져**야 한다.

```text
[공통]
메시지 접수 → message.posted → 멘션·Agent DB → agent_runs → Worker claim

[경계 A]
Agent 유형에 따라 Runner 선택

[독립]
Meeting Agent State → 커스텀 Harness → Tool·HITL·Checkpoint → 결과 확정

[경계 B]
실시간 Streaming Event와 표준화된 최종 결과 전달

[공통]
UI 전송 → message.posted → Thread 연결 → 사용량·감사 → Run 완료
```

핵심 경계는 두 곳이다.

1. **경계 A:** Worker가 Run을 claim한 뒤 Standard Agent Runner와 Meeting Agent Runner를 선택하는 지점
2. **경계 B:** Agent별 실행 결과를 worker의 공통 Realtime(실시간 Streaming 기능)·메시지 저장·사용량·감사·Run 완료 처리 로직으로 넘기는 지점

회의록 Agent의 독립성은 제품의 공통 호출 기반을 버린다는 뜻이 아니다. **공통 기반은 재사용하되, 설계를 통해 만든 커스텀 Harness가 있는 독립된 회의 에이전트 부분만 독립되게 따로 만드는 것**이 이식 방향이다.
