# Agent 호출·구동 순서와 독립 실행부 경계 조사

## 1. 조사 목적과 결론

이 문서는 `zen-ai`에서 Agent가 호출되고 답변을 남기기까지의 전체 흐름을 간략히 정리하고, 그 안에서 **공통 제품 기반과 Agent별로 다르게 진행되는 부분 사이의 경계**를 확인한다.

회의록 Agent 이식의 기본 방향은 다음과 같다.

```text
공통 호출·실행 준비 재사용
→ Agent별 Runner 선택
→ 독립 회의록 Agent 실행
→ 공통 결과 처리 재사용
```

즉 채팅, 멘션, 실행을 위한 DB접속과 Worker를 새로 만드는 것까지의 **회의 에이전트도 사용하는 부분은 굳이 건드릴 이유가 없다**. 기존 제품 기반은 유지하고, 일반 AI SDK Tool Loop가 담당하던 중간의 **에이전트가 조립되고 실행되는 부분만 회의록 에이전트의 커스텀 로직으로 교체**하는 것이다.

다만 현재 코드는 이 경계를 독립된 인터페이스로 완전히 분리해 두지 않았다. 현재 `runAgentTurn()`은 일반 Agent의 조립·실행뿐 아니라 Streaming, 최종 답변 저장, 사용량·감사 기록과 `agent_runs` 완료·실패 처리까지 내부에서 직접 수행한 뒤 `Promise<void>`로 끝난다. 즉 현재는 Agent별 Runner가 결과 객체를 바깥 Worker에 반환하는 구조가 아니다.

향후에는 Agent별 Runner가 표준화된 결과를 반환하고 공통 Finalizer가 후속 처리를 담당하도록 분리해야 한다. 아래의 경계 A와 B는 현재 코드에서 분석한 **공통 부분과 에이전트 조립·실행 사이의 책임 경계**이자 앞으로 추가로 분리해야 할 지점이다.

## 2. 최초 호출부터 답변 완료까지 요약

사용자가 채팅창에 다음과 같이 입력했다고 가정한다.

```text
@회의 에이전트 지난 회의를 찾아줘
```

전체 과정은 다음과 같다.

```text
① Channel Handler와 Channel Runtime이 요청 접수·검증
→ ② 사용자 메시지를 message.posted Event로 저장
→ ③ @멘션을 해석하여 회의록 Agent의 agentId 식별
→ ④ Agent DB에서 호출 권한을 확인하고, 이번 Run에 사용할 Agent 버전·모델·추론·Token·Context·Round 한도를 확정
→ ⑤ agent_runs에 pending 실행 작업 생성
→ ⑥ Worker가 작업을 claim

──── 경계 A: 공통 준비 완료, Agent별 실행부 선택 ────

→ ⑦ Standard Runner 또는 Custom Runner 실행
   └─ 실행 중 Realtime Text와 진행 Event를 공통 출력 경계로 전송
→ ⑧ LLM·Tool·Harness가 이번 요청의 최종 결과 확정

──── 경계 B: Agent별 실행 완료, 공통 처리로 복귀 ────

→ ⑨ 최종 답변을 message.posted로 같은 Thread에 저장
→ ⑩ 사용량 기록 및 agent_runs 완료·실패 처리
```

**최초 호출 메시지는 별도의 Thread 행을 생성하지 않고, 해당 메시지가 Thread 루트**가 된다. 그리고 Agent 답변은 그 메시지의 ID를 `parentEventId`로 사용하여 자동으로 그 아래로 연결된다.

같은 Thread의 **후속 질문도 새로운 `agent_runs` 작업**을 만든다. 새 멘션이 없으면 기존에 호출된 Agent를 상속하고, **Worker는 Thread의 이전 `message.posted` Event를 다시 읽어 이번 Turn의 대화 Context로 구성**한다. 또한 Worker 안에 조립된 Agent가 계속 살아서 다음 질문을 기다리는 구조가 아니라 그때 그때 요청마다 worker가 실행되어 에이전트가 조립이되는 구조인 것이다.

## 3. 경계 A: 공통 준비에서 Agent별 Runner로 넘어가는 지점

경계 A는 **Worker가 `agent_runs`(현재 어떤 사용자 요청이 들어왔고 진행 중인지를 저장하는 DB) 에 있는 작업을 읽고, 실제 Agent 조립/실행을 시작하기 직전**이다.

이 지점까지는 모든 Agent가 다음 제품 기반을 함께 사용한다.

- Channel 메시지 접수와 인증·입력 검증
- `message.posted` 저장과 Thread 루트 지정
- `@` 멘션 해석과 회의록 Agent의 agentId 식별
- Agent 활성 상태와 사용자 권한 확인 및 버전·모델·추론 설정·실행 한도 확정
- `agent_runs` DB 행 생성, Worker claim, worker에 대한 lease(특정 요청의 소유권을 일정 기간 동안 독점적으로 확보하는 설정)와 timeout 설정

이후에는 안정적인 **Agent 유형 식별값을 기준으로 조립/실행을 하는 로직(Runner)를 선택하는 구조**가 필요하다.

```text
Worker가 Run claim 완료
→ Agent 실행 유형 확인
   ├─ 일반 Agent → Standard Agent Runner
   └─ 선택형 커스텀 Agent → Custom Runner
```

단순 에이전트 이름이나 변경 가능한 slug을 이용하는 것보다는 특정 안정적인 식별값을 사용하는 편이 안전할 것이다. 위의 Standard Runner와 Custom Runner는 현재 코드에 완전히 분리된 모듈이 아니라, 향후 `runAgentTurn()`의 책임을 분리할 때 사용할 실행부다. Agent DB에는 선택한 커스텀 실행 로직과 버전을 저장하고, 구체적인 조합 규칙은 구조 설계 단계에서 확정한다.

경계 A에서 어떤 Runner로 갈지 구분하기 위해 제공해야 할 최소 정보는 다음과 같다.

| 입력                                | 용도                    |
| --------------------------------- | --------------------- |
| Run ID와 claim 정보                  | 실행 완료·실패·중복 방지        |
| `agentId`, Agent 유형·버전            | 실행할 Runner와 정책 식별     |
| `triggerEventId`, `triggerUserId` | 현재 요청과 사용자 식별         |
| `channelId`, Thread 루트            | 대화 조회와 결과 전송 위치       |
| 확정된 실행 설정                         | 모델·추론·Token·Round 한도  |
| `AbortSignal`                     | lease 상실·timeout 시 중단 |

## 4. Agent별 실행부의 경계

### 4-1. 일반 Agent Runner

현재 일반 Agent는 Agent DB에서 가져온 시스템 프롬프트·모델·Tool·이전 대화를 AI SDK 코드 안의 `streamText()`메서드에 전달되어 자동조립을 하는 구조이다. 이후 AI SDK의 Tool Loop가 LLM 판단, Tool 실행, Tool 결과 재입력과 최종 답변 생성을 처리한다.

```text
Agent 설정 + Messages + MCP Tool
→ AI SDK streamText()
→ 일반 Tool Loop
→ 최종 답변
```

### 4-2. Custom Runner에서 실행하는 회의록 구성

회의록 Agent는 선택형 Custom Runner와 범용 Harness를 사용하되, 회의록 전용 업무 상태는 Tool 쪽에 둔다.

- Search·Question Tool 결과를 다음 LLM Context에 포함하고 목표를 재판단
- 복수 후보 선택과 허용 ID 추가·대체를 위한 HITL 중단·재개
- 공통 실행 State는 `scratchpad`, `pendingHitl` 정도로 제한
- `authorizedMeetingIds`는 Search·Question Tool이 전용 저장 영역에서 직접 조회·갱신
- Recording Tool은 녹화 Skill 트리거 전달 후 LLM으로 돌아가지 않고 Run 종료
- 회의록 접근 권한 재검증과 원문 비영속 처리
- 안전한 Trace Event 발생

```text
1. Agent DB에서 확정한 시스템 프롬프트·모델·실행 한도
2. Worker가 message.posted에서 복원한 Messages
3. Runner가 State 저장소에서 읽은 공통 Custom State
4. 범용 Harness와 등록된 Search·Question·Recording Tool
```

HITL이 발생하면 공통 State 저장소의 Pending HITL 영역에 대기 정보·재개 위치·안전한 State Snapshot을 함께 저장하고 HITL 질문을 UI에 출력한 뒤 **현재 Run은 `done`으로 종료**한다. 다음 사용자 입력은 기존 방식대로 **새로운 Run**을 만들며, Custom Runner는 진입 시 Pending HITL을 먼저 조회하여 일반 요청인지 HITL 응답인지 구분한다. 별도의 `waiting_for_input` 상태나 `agent_runs.pendingHitlId` 컬럼은 두지 않는다.

따라서 회의록 Agent를 기존 `streamText()` Tool Loop의 설정값만 바꾼 일반 Agent로 취급해서는 안 된다. 기존 호출 기반과 연결이 되어있는 것일 뿐, 내부 실행 방식은 독립적이어야 한다.

### 4-3. Tool 결과와 실행 후 흐름의 경계

Tool의 실행 결과와 Harness의 다음 행동은 구분한다.

```ts
type ToolResult = {
  toolCallId: string;
  toolName: string;
  status: "success" | "failed" | "hitl_required";
  output?: unknown;
  hitl?: HitlRequest;
  errorCode?: string;
};
```

- Tool 전용 상태는 Tool이 직접 저장하므로 `stateUpdates`는 반환하지 않는다.
- LLM이 알아야 하는 Search·Question 결과만 `output`으로 반환한다.
- HITL 정보는 `hitl`로 반환하여 `pending-hitl.ts`가 처리한다.
- Recording Tool의 성공은 실제 녹화 완료가 아니라 **Skill 트리거 전달 성공**을 뜻한다.

Tool 실행 후 `return_to_llm` 또는 `end_run`으로 갈지는 결과값이 아니라 Tool 등록 정보의 `afterExecution` 정책으로 정한다. 현재는 로컬 `tools/*.ts`가 실행 함수와 정책을 함께 제공하고, 향후에는 온프레미스 MCP Tool의 사용자 정의 metadata 또는 Tool manifest에서 함께 읽는다. Harness는 Tool 이름별 예외를 하드코딩하지 않고 Tool Resolver가 정규화한 정책을 따른다. 단, `hitl_required`는 `afterExecution`보다 우선한다.

## 5. 경계 B: Agent별 결과를 공통 처리로 돌려주는 지점

경계 B는 Runner가 사용자에게 보여줄 최종 결과를 확정한 뒤, 공통 UI·DB 처리로 돌아오는 지점이다.

일반 Agent와 회의록 Agent가 내부에서 서로 다른 방식으로 실행되더라도 **이후 worker의 공통 후속 처리 부분 입장에서 동일한 형태**여야 한다.

개념적인 결과에는 다음 내용이 필요하다.

- 실행 결과: 완료·HITL 질문 출력·실패·중단
- 사용자에게 보여줄 최종 답변 또는 HITL 질문
- Token 사용량
- 답변을 보여주기 위한 Channel 및 Thread 정보(어디에 최종 답변을 출력할지)

### Streaming

에이전트 Runner가 끝난 뒤 지정된 형태로 반환하는 로직 말고도, 에이전트 실행 중 발생하는 Tool호출 현황 같은 **실시간 진행 상황을 worker쪽 공통 Realtime 처리 로직으로 전달**할 수 있도록 Streaming 기능용 출력 형식도 동일한 형태 여야 한다.(callback 또는 event sink 등의 형식이라고 함) 

```text
Agent별 Runner
├─ 실행 중: 공통 Realtime 출력 경계로 Text·진행 Event 전달
└─ 실행 종료: 표준화된 최종 결과 반환
                    ↓
               공통 Finalizer(Worker)
```

## 6. 공통 결과 처리로 재사용할 영역

경계 B 이후에는 가능한 한 다음 기존 제품 기능을 재사용한다.

- Runner 실행 중 Realtime Text와 진행 Event를 전달할 공통 출력 경계
- 최종 Agent 답변을 `message.posted` Event로 저장하고 UI에 표시
- 호출 메시지의 Thread 루트에 답변 연결
- Token 사용량 기록
- 일반 Agent의 기존 MCP Tool 감사 기록
- `agent_runs` 성공·실패 처리
- claim·lease(에이전트 호출 및 worker 하나가 점유하고 있는 것을 보장하는 로직)가 올바르게 이루어졌는지 확인 및 중복 완료 방지 로직

현재는 **이 기능들이 독립된 Finalizer로 분리되어 있지 않고 `runAgentTurn()` 내부에 일반 AI SDK 실행 코드와 함께** 있다. 따라서 Custom Runner를 추가할 때는 공통 코드를 복사하는 것이 아니라, Standard·Custom Runner가 함께 사용할 **Realtime 출력 부분과 최종 답변 처리 부분을 따로 추출**하는 방향이 적절하다.

현재 로컬 Search·Question·Recording Tool은 MCP Tool이 아니므로 `mcp_audit_events`에 `mcp_tool.called`로 기록하지 않는다. `custom/runner.ts`가 민감정보를 제거한 Tool 감사 항목을 Run 메모리에 모으고, 최종 완료·HITL 질문 출력·실패 등으로 Run이 종료되기 직전에 회의록 Agent 전용 감사 저장소에 기록한다. 별도의 `audit.ts`나 감사 Adapter는 지금 만들지 않고, 여러 Agent에서 재사용할 근거가 생길 때만 공용 구조로 추출한다.

## 7. 영속 "State 클래스"에 Messages를 중복 저장할 필요는 없다.

### 7-1. Messages

기존 `message.posted` Event가 영속 대화 이력의 원본이다. 사용자 메시지는 Channel 메시지 처리 과정에서 저장되고 Agent의 최종 답변은 현재 `runAgentTurn()` 내부에서 저장된다. Worker는 새 Run을 시작할 때 현재 Thread의 Event를 읽어 `ModelMessage[]`로 변환한다.

```text
기존 message.posted Event
→ Worker가 Thread 대화 조회
→ ModelMessage[] 구성
→ Standard 또는 Custom Runner에 입력
```

따라서 Custom Agent의 영속 State에 별도의 Messages를 두어 동일한 대화 이력을 다시 저장할 필요는 없다. Worker가 복원한 Messages(`ModelMessage[]`)를 Runner의 실행 입력으로 전달하면 된다. 한 Run 안에서만 필요한 임시 Messages를 실행 객체에 둘 수는 있지만, 기존 채팅 이력을 별도 State 저장소에 중복 영속화하지 않는다.

### 7-2. 공통 Custom State와 Tool 전용 상태

Runner가 Run 시작 시 불러와 Harness에 전달하는 공통 State는 다음처럼 최소화한다.

```ts
type CustomAgentState = {
  scratchpad: Scratchpad;
  pendingHitl?: PendingHitl;
};
```

- 이전 대화 이력: `message.posted`에서 `ModelMessage[]`로 복원하므로 State에 중복 저장하지 않음
- `scratchpad`: 다음 LLM 판단에 필요한 가변적인 작업 Context
- `pendingHitl`: HITL을 사용하는 경우에만 존재하며, 사용하지 않으면 빈 레코드도 만들지 않음

Runner는 Run 시작 시 이 State를 한 번 읽고 Harness는 Run 동안 메모리 객체를 사용한다. 일반 완료 직전에는 변경된 공통 State를 저장하고, HITL 발생 시에는 질문 출력과 Run 종료 전에 Pending HITL·재개 위치·안전한 Snapshot을 먼저 저장한다.

`authorizedMeetingIds`는 Search·Question Tool만 사용하는 회의록 업무 상태이므로 공통 State에 넣지 않는다. Tool이 동일한 사용자·Agent·Channel·Thread 격리 키의 Meeting 전용 영역을 직접 조회·갱신한다. `recordingModalStatus`는 Agent State에 저장하지 않으며 실제 녹화 상태는 녹화 Backend가 소유한다.

### 7-3. Pending HITL 저장소와 기술 Checkpoint

`agent_runs`는 기존처럼 사용자 메시지마다 새로 생성하고 `pending → running → done/failed` 상태를 유지한다. HITL 대기 상태는 공통 State 저장소의 Pending HITL 영역에서 사용자·Agent·Channel·Thread 단위로 관리한다.

이 저장소에는 대기 정보뿐 아니라 `resumePoint`와 `stateSnapshot`도 함께 보관한다. 따라서 중단된 실행을 복구·재개할 수 있게 하는 **기술적인 의미의 Checkpoint 역할도 한다.** 별도의 Checkpoint 저장소나 `agent_runs`의 `pendingHitlId` 컬럼은 현재 단계에서 두지 않는다.

Custom Runner는 시작할 때 Pending HITL을 먼저 조회한다. Pending HITL이 있으면 현재 입력을 HITL 응답으로 검증하고, 유효하면 Snapshot을 복원해 재개한다. 유효하지 않으면 기존 HITL을 다시 안내한다. Pending HITL이 없다면 일반 질문·요구로 새 실행을 시작한다.

향후에는 `/cancel`처럼 현재 Pending HITL을 명시적으로 취소하고 새로운 일반 질문을 시작할 수 있는 기능 추가도 고려한다.

### 7-4. Trace

Trace는 Tool 감사 기록보다 넓은 범위에서 Graph·Node·Edge·LLM·Tool·HITL·Checkpoint의 실행 과정을 관찰하는 기록이며 Scratchpad와는 다르다. Harness에는 범용 `TraceSink.emit()` 호출 지점을 두고, 초기 Sink 구현체는 안전한 서버 로그를 출력한다. 향후 Realtime Trace UI나 별도 Trace 저장소로 교체할 수 있다.

Trace Sink는 실행 중 실시간·best-effort로 동작하고, Tool 감사 기록은 `custom/runner.ts`가 Run 종료 직전에 영속 저장한다. 두 기능은 목적·시점·저장 경로가 다른 별도 로직이다. Trace에는 회의록 원문, API 키·인증정보, 내부 오류 원문과 전체 권한 ID를 포함하지 않는다.

## 9. 최종 정리

회의록 Agent는 **기존 제품의 채팅과 실행 기반을 사용하되, 독립된 회의 에이전트 실행 로직를 가져**야 한다.

```text
[공통]
메시지 접수 → message.posted → 멘션·Agent DB → agent_runs → Worker claim

[경계 A]
Agent 실행 유형에 따라 Standard 또는 Custom Runner 선택

[독립]
Custom Runner 진입 → Pending HITL·공통 Custom State 조회
→ 범용 Harness → Tool·HITL·실행 후 정책
├─ Search·Question: output을 Context에 넣고 LLM 재판단
├─ Recording: Skill 트리거 전달 후 end_run
├─ 실행 중: 공통 Realtime 출력 경계와 Trace Sink 사용
└─ Run 종료 직전: runner.ts가 전용 감사 기록 저장
→ 결과 확정

[경계 B]
표준화된 최종 결과 전달

[공통]
message.posted → UI 출력·Thread 연결 → 사용량 기록 → Run 완료
```

핵심 경계는 두 곳이다.

1. **경계 A:** Worker가 Run을 claim한 뒤 Standard Runner와 Custom Runner를 선택하는 지점
2. **경계 B:** Agent별 실행 결과를 worker의 공통 메시지 저장·사용량·Run 완료 처리 로직으로 넘기는 지점. Realtime Streaming은 Runner 실행 중 공통 출력 경계를 통해 전달한다.

회의록 Agent의 독립성은 제품의 공통 호출 기반을 버린다는 뜻이 아니다. **공통 기반은 재사용하되, 설계를 통해 만든 커스텀 Harness가 있는 독립된 회의 에이전트 부분만 독립되게 따로 만드는 것**이 이식 방향이다.
