# 공통 Agent 호출 기반과 회의록 Executor 경계 조사

## 1. 결론

실제 `zen-ai`에는 이미 Custom Agent와 분리된 Builtin Agent Platform이 있다. 회의록 Agent는 일반 Agent의 `runAgentTurn()`을 Standard/Custom Runner로 분해해 넣는 것이 아니라 **새 Builtin definition과 Executor로 등록**하는 것이 맞다.

```text
공통 Builtin Platform 재사용
→ Executor Registry에서 meeting-agent-v1 선택
→ 회의록 전용 실행
→ 공통 operation·message.posted 완료 처리
```

이 결정으로 이전 문서가 제안했던 `src/lib/agents/worker/runner-contract.ts`, `standard-runner.ts`, `custom/runner.ts`와 공통 Finalizer 추출은 이번 이식 범위에서 제거한다. 기존 Builtin Runtime의 계약이 이미 그 역할을 한다.

## 2. 최초 호출부터 완료까지

```text
① Channel Runtime이 사용자 메시지 검증
→ ② message.posted 저장
→ ③ builtinMentions에서 회의록 principal 식별
→ ④ compiled definition과 instance config에서 executor·model·reasoning·Token·Context·Round 한도 확정
→ ⑤ builtin agent_runs 생성
→ ⑥ Builtin Worker가 claim·lease 획득

──── 경계 A: 공통 Platform → 회의록 Executor ────

→ ⑦ Meeting channel adapter가 Thread Context와 안전한 이전 Checkpoint 조회
→ ⑧ Meeting Engine이 Search·Question·Recording·direct 처리
→ ⑨ 실행 중 공통 Realtime 경계로 안전한 진행 Event 출력
→ ⑩ 표준 ExecutorResult와 안전한 Checkpoint 반환

──── 경계 B: 회의록 Executor → 공통 Platform ────

→ ⑪ operation receipt 확정
→ ⑫ 최종 답변을 같은 Thread의 message.posted로 저장
→ ⑬ agent_runs done/failed/cancelled 확정
```

최초 호출 메시지가 Thread 루트다. 별도 Thread 행을 만들지 않는다. 후속 메시지는 각각 새 Run을 만들고, Worker가 같은 Thread의 이전 `message.posted`를 다시 조회한다.

## 3. 경계 A: 공통 준비와 회의록 실행

공통 Platform이 회의록 Executor에 제공하는 값은 기존 `RuntimeSnapshot`과 `BuiltinRun` 계약을 따른다.

- Run ID, claim token, claim slice와 deadline
- principal·trigger user·channel·conversation key
- definition과 executor ID
- model·reasoning·Token·Context·Round 한도
- AbortSignal

회의록 전용 코드는 다음만 소유한다.

- 목표와 다음 행동 판단
- Search·Question·Recording 상태 전이
- Tool 실행과 HITL
- 안전한 Context 조립
- 회의록 전용 State Repository와 권한 재검증

회의록 Executor는 Custom Agent의 prompt, preference, generic grant를 fallback으로 읽지 않는다.

## 4. AI SDK의 역할

AI SDK는 Worker가 Messages를 저장하는 기능이 아니다. 제품에서 역할은 모델 호출과 현재 호출 안의 입력·출력 처리를 돕는 것이다.

```text
message.posted 대화 + system prompt + 안전한 Scratchpad/Tool 결과
→ Meeting Provider가 AI SDK generateText() 호출
→ 구조화된 목표·답변 결과 검증
→ Engine이 다음 Tool 또는 종료 결정
```

Builtin 회의록 Executor는 일반 Agent의 `streamText()` 자동 Tool Loop에 실행 제어를 맡기지 않는다. HITL과 `afterExecution=end_run`처럼 코드가 보장해야 하는 전이는 Meeting Engine이 처리한다. AI SDK가 DB의 `message.posted`나 `authorizedMeetingIds`를 자동으로 갱신하지 않는다.

Tool 결과의 내부 형태는 Tool마다 달라도 되지만, Engine에 들어오는 최소 결과는 다음처럼 제한한다.

```ts
type MeetingToolResult = {
  status: "success" | "failed" | "hitl_required";
  output?: unknown;
  hitl?: { prompt: string; pendingToken: string };
  errorCode?: string;
};
```

- `toolCallId`와 Tool Message 자동 누적은 일반 AI SDK Tool Loop의 설명이며, 이번 회의록 Executor가 반드시 같은 내부 형식을 사용할 필요는 없다.
- Search·Question의 다음 판단에 필요한 값만 현재 모델 Context에 넣는다.
- Tool 내부 저장용 변수는 `output`에 되돌리지 않는다.
- 원문은 Question 답변 호출 직후 버린다.

## 5. 경계 B: 공통 완료 처리

Meeting Executor는 기존 `ExecutorResult`를 반환한다.

```ts
{ kind: "success", evidence: safeEvidence, result: { checkpoint, display } }
{ kind: "failure", category, evidence: safeEvidence }
```

공통 Runtime은 반환값 크기와 형식을 검사하고 operation receipt를 기록한다. Meeting adapter의 `finish()`는 기존 Builtin terminal CAS를 이용해 최종 `message.posted`와 Run 상태를 원자적으로 확정한다.

별도의 `MeetingToolAuditAdapter`와 `mcp_audit_events` 위장 기록은 만들지 않는다. Local Meeting Tool 실행은 Builtin operation evidence에 민감정보를 제거한 종류·상태·횟수만 남긴다. 실제 MCP로 이전한 뒤에는 MCP 감사 계약을 추가로 적용할 수 있다.

## 6. Messages와 Scratchpad

| 구분 | 내용 | 수명 |
|---|---|---|
| `message.posted` | 사용자 메시지와 Agent 최종 답변 | DB 영속 |
| Thread Context | 같은 Thread의 `message.posted`를 제한해 구성 | 현재 Run |
| 현재 Tool/Model 자료 | 현재 Run에서만 필요한 결과와 원문 | 현재 호출 메모리 |
| Scratchpad | 다음 Run에도 필요한 안전한 작업 요약 | Agent State Store |

중간 Tool Call·Tool Result를 최종 채팅 대화처럼 `message.posted`에 저장하지 않는다. `message.posted`와 Scratchpad의 역할도 중복하지 않는다.

## 7. HITL

```text
Tool이 hitl_required
→ Tool Repository에 후보·정합성 상세와 일회용 pendingToken 저장
→ Agent State Store에 안전한 Scratchpad·최소 HITL 참조 저장
→ Workflow Checkpoint Store에 이번 업무 턴의 완료·HITL 대기 경계 기록
→ HITL 질문 message.posted 출력, 현재 Run done

후속 사용자 메시지로 새 Run
→ 같은 conversation의 최신 이전 Checkpoint 조회
→ Tool pendingToken과 입력 검증
→ 최신 권한 재검증 후 상태 반영 또는 재질문
```

`agent_runs`에 `waiting_for_input`이나 `pendingHitlId` 열을 추가하지 않는다. 각 사용자 입력의 Run·사용량·오류·operation 기록은 독립적으로 유지한다. `/cancel`은 Tool Pending 상태를 폐기하고 새 요청을 시작할 수 있게 한다.

## 8. State 저장 경계

- Agent State Store: 공개 가능한 Scratchpad와 최소 HITL 참조
- Workflow Checkpoint Store: 사용자 요청 단위 업무 턴의 완료·HITL 대기 경계
- Local Meeting State Repository: `authorizedMeetingIds`, 후보·추가·대체·토큰 상세
- 향후 고객사 MCP: Local Tool과 해당 State 책임을 함께 이전
- 사용자 클라이언트: 없어져도 정합성이 깨지지 않는 UI 캐시만
- Recording Backend: 실제 녹화 상태

회의록 원문, API 키, 인증정보와 내부 오류 원문은 어떤 Checkpoint·Trace·operation evidence에도 저장하지 않는다.

## 9. Trace

Trace Sink는 Event를 받아 출력하는 목적지라는 뜻이다. 이번 구현은 별도 범용 `MeetingTraceSink` 인터페이스를 만들지 않고 기존 Realtime Hub의 `agent-delta`를 직접 사용한다. 두 번째 Executor에서 같은 Event 규격을 공유할 필요가 생길 때만 공통 Sink로 추출한다.

Trace는 실시간 관찰이고 operation receipt는 공식 실행 기록이다. 둘의 목적과 실패 영향은 다르다.
