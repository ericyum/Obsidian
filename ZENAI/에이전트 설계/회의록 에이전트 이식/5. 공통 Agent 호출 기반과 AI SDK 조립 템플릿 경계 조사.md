# 공통 Agent 호출 기반과 AI SDK 조립 템플릿 경계 조사

## 1. 조사 목적

이 문서는 `zen-ai`에서 다음 두 영역을 실제 코드 기준으로 구분한다.

1. 사용자가 Agent를 부른 순간부터 실행 작업을 만들고 Worker가 가져가기까지의 **공통 Agent 호출·실행 준비 기반**
2. 준비된 실행 정보를 이용해 모델·프롬프트·대화 Context·Tool을 AI SDK에 전달하고 답변을 만드는 **일반 Agent 조립·실행 템플릿**

회의록 Agent는 독립된 커스텀 Harness를 가져야 하지만, 멘션·Thread·실행 큐·권한·Streaming·최종 메시지 같은 제품 기반까지 다시 만들 필요는 없다. 어느 지점까지 재사용하고 어디부터 독립 실행부로 갈라야 하는지를 찾는 것이 이 조사의 목적이다.

## 2. 결론

현재 `zen-ai`에는 두 영역을 한 파일로 명확히 나눈 경계가 존재하지 않는다. 다만 실제 책임은 다음과 같이 구분할 수 있다.

| 구분 | 핵심 책임 | 현재 중심 코드 |
|---|---|---|
| 공통 호출·실행 준비 기반 | 메시지 접수, 멘션 해석, 사용 권한·정책 확정, `agent_runs` 생성, Worker claim, Thread Context와 답변 위치 결정 | `channels/messages.ts`, `agents/effective-config.ts`, `agents/runs.ts`, `agents/worker-runtime.ts` |
| 일반 Agent 실행 오케스트레이션 | 실행 유효성 검사, Agent 버전·개인 설정·Context·Tool·모델 준비, AI SDK 실행 요청, Streaming 수집, 최종 이벤트·사용량·실행 상태 기록 | `agents/worker.ts`의 `runAgentTurn()` |
| AI SDK 조립 템플릿 | `streamText()`에 모델, 시스템 지침, 메시지, 추론 강도, 출력 한도, Tool, 반복 종료 조건을 전달 | `agents/worker-runtime.ts`의 `startAgentStream()` |

따라서 회의록 Agent의 연결 기준은 다음과 같다.

> **공통 호출·실행 준비 기반은 재사용하되, 일반 Agent의 AI SDK 조립 템플릿을 그대로 회의록 Agent 실행부로 사용한다고 가정해서는 안 된다. Worker가 실행을 claim한 뒤 일반 Agent 실행부와 독립 회의록 Agent 실행부를 선택할 수 있는 명시적인 실행 경계가 필요하다.**

## 3. 실제 공통 호출 흐름

```text
POST /api/channels/[channelId]/messages
→ Channel Handler 인증·입력 검증
→ Channel Runtime이 Community 쓰기 범위 적용
→ postMessage()
   ├─ 채널 Agent·사용자 목록 조회
   ├─ @멘션 해석
   ├─ 사용자 메시지를 message.posted Event로 저장
   ├─ Agent 활성·부여 여부와 사용자별 유효 정책 계산
   └─ agent_runs에 pending 실행 생성 + Worker wake 알림
→ Agent Worker
   ├─ pending Run claim
   ├─ lease와 Community Worker Scope 확보
   └─ Agent 실행부 호출
```

### 3-1. 메시지 진입

API Route는 `createRuntimeChannelHandlers().postMessage()`를 호출한다. Channel Handler가 인증과 요청 Schema 검증을 맡고, Channel Runtime은 `withWriteScopeFor()`로 Community 범위를 연 뒤 `postMessage()`에 전달한다.

이 단계는 Agent 종류와 무관한 공통 채팅 기반이다.

### 3-2. 멘션 해석

`postMessage()`는 해당 채널에 실제로 들어와 있는 Agent와 사용자를 후보로 읽는다. `calledMembers()`와 `parseMentions()`가 본문의 이름 또는 slug를 식별하고, 사람 멘션과 Agent 실행 멘션을 분리한다.

후속 질문이 Thread 답글이며 새 Agent 멘션이 없으면 `inheritedMentions()`가 기존 호출 Agent를 이어받는다. 따라서 매 후속 질문마다 `@회의록 Agent`를 다시 쓸 필요는 없다.

중요한 점은 별도 Thread 테이블이나 Thread 생성 명령이 없다는 것이다. 루트 `message.posted` Event가 Thread의 루트가 되고, 답글은 `parentEventId`로 연결된다.

### 3-3. 실행 가능한 설정 확정

`loadEffectiveAgentConfigs()`는 멘션된 Agent별로 다음을 검사·계산한다.

- Agent 활성 여부
- 전체 또는 사용자별 부여 권한
- 현재 Agent 정책 버전
- 허용 모델과 기본 모델
- 사용자 모델·추론 설정 Override
- 최대 출력 Token, Context 한도, 최대 Round

계산된 유효 설정은 `enqueueRunsInTransaction()`에서 `agent_runs`에 Snapshot으로 들어간다. 즉 모델과 실행 한도는 Worker가 나중에 임의로 다시 결정하는 값이 아니라, 호출 시점의 유효 정책을 고정한 실행 계약이다.

### 3-4. 실행 원장과 Worker claim

`enqueueRunsInTransaction()`은 Agent마다 `agent_runs`의 `pending` 행을 만들고 PostgreSQL `NOTIFY`로 Worker를 깨운다. 실행 행에는 최소한 다음 식별 정보가 들어간다.

- `triggerEventId`, `triggerUserId`
- `agentId`, `channelId`, `agentVersion`
- 유효 모델·추론 정책·실행 한도 Snapshot
- 실행 상태, 시도 횟수, claim과 lease 정보

`startAgentWorker()`는 Run을 claim하고 tenant scope와 lease를 유지한 상태에서 실행부를 호출한다. 현재는 모든 Run에 대해 아래 호출이 고정되어 있다.

```ts
runAgentTurn(createWorkerDependencies(db, claim), run, { abortSignal })
```

바로 이 지점이 일반 Agent와 독립 회의록 Agent를 선택할 수 있는 가장 바깥 실행 분기 후보다. 현재 코드에는 Agent 종류에 따른 분기가 없다.

## 4. 일반 Agent 조립·실행 템플릿

### 4-1. `runAgentTurn()`이 준비하는 것

`runAgentTurn()`은 다음 순서로 일반 Agent 한 Turn을 실행한다.

1. claim과 Agent 활성·부여 상태 재검증
2. `agent_versions`에서 실행 버전의 시스템 프롬프트·기본 모델·추론 정책·한도 조회
3. 사용자 개인 지침 Snapshot 조회
4. 채널 또는 Thread Event를 AI SDK `ModelMessage[]`로 변환
5. Context 예산에 맞게 오래된 메시지 제거
6. Agent에 연결된 MCP Tool 묶음 준비
7. Provider 모델 생성
8. `startStream()` 호출
9. Text delta와 Tool call을 실시간 UI Event로 전달
10. 최종 답변을 `message.posted`로 저장하고 `agent_runs` 완료 처리

이 함수는 단순한 AI SDK 조립 함수가 아니다. 입력 준비, 실행 수명주기, Streaming, 감사, 결과 영속화까지 함께 조정하는 **일반 Agent Turn 오케스트레이터**다.

### 4-2. 실제 AI SDK 조립 지점

실제 AI SDK 호출은 `worker-runtime.ts`의 `startAgentStream()`에 있다.

```ts
streamText({
  model,
  instructions,
  messages,
  reasoning,
  maxOutputTokens,
  tools,
  prepareStep,
  stopWhen,
  abortSignal,
  onLanguageModelCallEnd,
  onToolExecutionEnd,
  onError,
})
```

여기서 AI SDK가 담당하는 일반 반복 구조는 다음과 같다.

```text
LLM 판단
→ 필요하면 등록된 Tool의 execute 실행
→ Tool 결과를 다음 Model Context에 포함
→ 같은 LLM 재판단
→ Tool을 더 호출하지 않으면 최종 Text 반환
→ stopWhen 또는 최대 Round에서 종료
```

따라서 현재 일반 Agent의 Tool Loop는 별도의 Graph 파일이 아니라 AI SDK `streamText()`의 Tool 실행과 `stopWhen`에 의해 형성된다.

### 4-3. `worker-runtime.ts`라는 이름의 의미

`src/lib/agents/runtime.ts`와 `worker-runtime.ts`는 역할이 다르다.

- `agents/runtime.ts`: Agent 생성·수정·활성화·부여·개인 설정 API에 인증과 Community Scope를 연결하는 **관리 기능 Runtime**
- `agents/worker-runtime.ts`: Worker가 사용할 DB·Provider·MCP·Realtime 구현을 조립하는 **Agent 실행 Adapter**
- `agents/worker.ts`: Adapter 계약만 받아 Agent Turn의 순서를 제어하는 **실행 오케스트레이터**

따라서 “기존 Runtime을 재사용한다”는 표현만 사용하면 관리 Runtime과 실행 Runtime을 혼동할 수 있다. 문서와 구현에서는 구체적인 함수와 책임을 함께 명시해야 한다.

## 5. 두 영역의 실제 경계

### 5-1. 호출 기반에서 실행부로 넘어오는 데이터

공통 호출 기반은 독립 Agent 실행부에 다음 정보를 넘길 수 있다.

| 데이터 | 출처 | 용도 |
|---|---|---|
| `run.id` | `agent_runs` | 실행 식별·claim·완료·실패 처리 |
| `agentId`, `agentVersion` | 멘션과 Agent 정책 | 실행부 선택과 버전 식별 |
| `triggerEventId`, `triggerUserId` | 사용자 메시지 | 입력·사용자·권한 Context |
| `channelId` | 호출 채널 | Thread Context 조회와 결과 전송 |
| 유효 모델·추론·한도 | 호출 시점 정책 Snapshot | 재현 가능한 실행 설정 |
| `AbortSignal` | Worker lease·timeout | 실행 중단과 외부 연결 취소 |

### 5-2. 실행부가 공통 기반에 돌려줘야 하는 것

독립 회의록 Agent도 제품 UI와 실행 원장에 연결되려면 다음 결과를 공통 기반으로 반환해야 한다.

- Streaming Text 또는 Tool·Trace 진행 Event
- 사용자에게 보여줄 최종 답변
- HITL 대기·재개를 표현할 실행 상태와 UI Event
- Tool 실행 감사에 필요한 비밀 없는 Metadata
- Token 사용량
- 성공·실패·중단 결과
- 답변을 붙일 Thread 루트 ID

현재 일반 `runAgentTurn()`은 이 반환 계약을 별도 타입 하나로 분리하지 않고 함수 내부에서 직접 Streaming하고 DB를 갱신한다. 따라서 독립 Agent를 추가할 때 단순히 `startAgentStream()`만 바꿔 끼우는 것으로는 충분하지 않다.

### 5-3. 현재 섞여 있는 책임

현재 `runAgentTurn()`에는 다음 두 종류의 책임이 함께 있다.

| 재사용할 공통 수명주기 | 일반 Agent에 종속된 실행 방식 |
|---|---|
| claim 유효성·lease·timeout | `agent_versions.systemPrompt`를 AI SDK instructions로 사용 |
| Thread Context와 답변 위치 결정 | 일반 Event 대화를 그대로 `ModelMessage[]`로 구성 |
| Streaming delta 발행 | MCP Tool만 동적으로 로드 |
| 최종 Event·사용량·감사·Run 상태 기록 | 하나의 `streamText()` Tool Loop로 실행 |
| tenant·권한 경계 | 커스텀 Graph·HITL·업무 Checkpoint 계약 없음 |

즉 코드상 분리 경계는 완성되어 있지 않지만, 책임상 분리 기준은 분명하다.

## 6. 회의록 Agent에 대한 적용 판단

### 6-1. 그대로 재사용할 부분

- 채널 메시지 API와 인증
- Agent 멘션 해석과 후속 Thread Agent 상속
- Agent 활성·사용 권한 확인
- `agent_runs` 생성, 중복 방지, Worker wake
- Worker claim, tenant scope, lease, timeout
- Thread Context 조회와 답변의 `parentEventId` 결정
- Realtime delta 전달 기반
- 최종 `message.posted`, 사용량, 감사, 완료·실패 기록 기반

이 영역을 독립 회의록 Agent 폴더에서 다시 구현하면 같은 제품 기능이 두 벌이 된다.

### 6-2. 그대로 사용하면 안 되는 부분

- 일반 Agent의 단일 `streamText()` Tool Loop를 회의록 Agent의 전체 Harness로 간주하는 것
- MCP Tool 목록만 바꿔 Search·Question·Recording의 커스텀 흐름이 구현된다고 가정하는 것
- 일반 Agent의 최대 Round만으로 회의록 업무 State·HITL·Checkpoint를 대신하는 것
- 녹화 Tool 결과를 다시 LLM에 넣는 일반 Tool Loop에 그대로 맡기는 것

회의록 Agent는 설계에 정의한 다음 동작을 독립 실행부가 보장해야 한다.

- Search·Question 결과를 이후 LLM 호출의 Context에 포함하고 재판단
- LLM 최종 답변이 확정된 뒤 UI 출력 직전에 업무 Checkpoint 저장
- 복수 후보와 추가·대체 선택의 HITL 중단·재개
- Recording Tool 결과는 LLM 재판단 없이 상태 갱신과 UI 반환 후 종료
- 권한 재검증과 회의록 원문 비영속성
- 설계된 Trace 경계

### 6-3. 필요한 연결 경계

현재 코드 사실에 가장 가까운 연결 형태는 다음과 같다.

```text
공통 Message·Mention·AgentRun 생성
→ 공통 Worker claim·lease·tenant scope
→ 실행부 선택 경계
   ├─ 일반 Agent → 기존 runAgentTurn() → startAgentStream() → AI SDK streamText()
   └─ 회의록 Agent → 독립 Meeting Agent Runner → 커스텀 Harness·Tool·HITL·Checkpoint
→ 공통 Streaming·최종 Event·감사·사용량·Run 완료 기반
```

여기서 `Meeting Agent Runner`의 내부 구조와 실제 분기 방식은 아직 구현안이 아니다. 먼저 다음을 추가 조사·설계해야 한다.

- 실행부를 선택할 안정적인 Agent 유형 식별자
- 일반 `runAgentTurn()` 안의 공통 마무리 기능을 중복 없이 재사용할 방법
- HITL 대기 상태를 `agent_runs`의 기존 상태로 표현할 수 있는지 여부
- 업무 Checkpoint 저장 위치와 사용자·Thread 격리 키
- 회의록 Agent 전용 Tool·Trace Event를 기존 Realtime 계약에 맞추는 방법

## 7. 경계를 판단하는 실무 기준

기능이 어느 쪽에 속하는지는 다음 질문으로 판별한다.

### 공통 호출·제품 기반에 속함

> Agent의 내부 추론 방식이 달라져도 이 기능이 그대로 필요한가?

예: 멘션, 권한, Run 원장, Worker claim, Thread 답글 위치, Realtime 전달, 최종 메시지 저장.

### Agent 실행 템플릿에 속함

> 시스템 프롬프트·모델·일반 Tool 목록만 바꾸면 동일한 실행 방식으로 처리할 수 있는가?

예: 일반 `streamText()` 기반 Tool Loop, 모델·추론 강도·출력 한도 전달.

### 독립 회의록 Agent에 속함

> 회의록 설계만의 State 전이·HITL·Checkpoint·녹화 종료 규칙을 알아야 하는가?

예: 검색 후보 선택, 허용 ID 관리, 원문 비영속 조회, Recording Tool의 LLM 미복귀, 업무 Checkpoint.
