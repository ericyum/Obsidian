# Agent 호출·구동 순서와 독립 실행부 경계 조사

## 1. 조사 목적과 결론

이 문서는 `zen-ai`에서 Agent가 호출되고 답변을 남기기까지의 전체 흐름을 간략히 정리하고, 그 안에서 **공통 제품 기반과 Agent별 실행부의 경계**를 확인한다.

회의록 Agent 이식의 기본 방향은 다음과 같다.

```text
공통 호출·실행 준비 재사용
→ Agent별 Runner 선택
→ 독립 회의록 Agent 실행
→ 공통 결과 처리 재사용
```

즉 채팅, 멘션, 실행 원장과 Worker를 새로 만드는 것이 아니다. 기존 제품 기반은 유지하고, 일반 AI SDK Tool Loop가 담당하던 가운데 실행부만 회의록 Agent의 커스텀 Harness로 교체하는 방향이다.

다만 현재 코드는 이 경계를 독립된 인터페이스로 완전히 분리해 두지 않았다. `runAgentTurn()` 안에 일반 Agent 실행과 공통 마무리 책임이 함께 있으므로, 아래의 경계 A와 B는 **현재 코드에서 확인한 책임상 경계이자 앞으로 분리해야 할 지점**이다.

## 2. 최초 호출부터 답변 완료까지

사용자가 채팅창에 다음과 같이 입력했다고 가정한다.

```text
@회의 에이전트 지난 회의를 찾아줘
```

전체 과정은 다음과 같다.

```text
① Channel Handler와 Channel Runtime이 요청 접수·검증
→ ② 사용자 메시지를 message.posted Event로 저장
→ ③ @멘션을 해석하여 회의록 Agent의 agentId 식별
→ ④ Agent DB에서 권한·버전·모델·실행 한도 조회
→ ⑤ agent_runs에 pending 실행 작업 생성
→ ⑥ Worker가 작업을 claim

──── 경계 A: 공통 준비 완료, Agent별 실행부 선택 ────

→ ⑦ 일반 Agent Runner 또는 Meeting Agent Runner 실행
→ ⑧ LLM·Tool·Harness가 이번 요청의 최종 결과 확정

──── 경계 B: Agent별 실행 완료, 공통 처리로 복귀 ────

→ ⑨ Realtime Text와 진행 Event를 UI에 전송
→ ⑩ 최종 답변을 message.posted로 같은 Thread에 저장
→ ⑪ 사용량·Tool 감사 기록 및 agent_runs 완료·실패 처리
```

최초 호출 메시지는 별도의 Thread 행을 생성하지 않는다. 해당 메시지가 Thread 루트가 되고, Agent 답변은 그 메시지의 ID를 `parentEventId`로 사용하여 연결된다.

같은 Thread의 후속 질문도 새로운 `agent_runs` 작업을 만든다. 새 멘션이 없으면 기존에 호출된 Agent를 상속하고, Worker는 Thread의 이전 `message.posted` Event를 다시 읽어 이번 Turn의 대화 Context로 구성한다. Worker 안에 조립된 Agent가 계속 살아서 다음 질문을 기다리는 구조는 아니다.

## 3. 경계 A: 공통 준비에서 Agent별 Runner로 넘어가는 지점

경계 A는 Worker가 `agent_runs` 작업을 claim한 뒤, 실제 Agent 실행을 시작하기 직전이다.

이 지점까지는 모든 Agent가 다음 제품 기반을 함께 사용한다.

- Channel 메시지 접수와 인증·입력 검증
- `message.posted` 저장과 Thread 관계
- `@` 멘션 해석과 후속 Thread의 Agent 상속
- Agent 활성 상태와 사용자 권한 확인
- Agent 버전·모델·추론 설정·실행 한도 확정
- `agent_runs` 생성, Worker claim, lease와 timeout

이후에는 안정적인 Agent 유형 식별값을 기준으로 실행부를 선택하는 구조가 필요하다.

```text
Worker가 Run claim
→ Agent 실행 유형 확인
   ├─ 일반 Agent → Standard Agent Runner
   └─ 회의록 Agent → Meeting Agent Runner
```

표시 이름이나 변경 가능한 slug보다 내부 Agent 유형처럼 안정적인 식별값을 사용하는 편이 적절하다. 실제 식별 필드와 DB 등록 범위는 구조 설계 단계에서 확정한다.

경계 A에서 Runner가 받아야 할 최소 정보는 다음과 같다.

| 입력 | 용도 |
|---|---|
| Run ID와 claim 정보 | 실행 완료·실패·중복 방지 |
| `agentId`, Agent 유형·버전 | 실행할 Runner와 정책 식별 |
| `triggerEventId`, `triggerUserId` | 현재 요청과 사용자 식별 |
| `channelId`, Thread 루트 | 대화 조회와 결과 전송 위치 |
| 확정된 실행 설정 | 모델·추론·Token·Round 한도 |
| `AbortSignal` | lease 상실·timeout 시 중단 |

## 4. Agent별 실행부의 경계

### 4-1. 일반 Agent Runner

현재 일반 Agent는 Agent DB에서 가져온 시스템 프롬프트·모델·Tool·이전 대화를 AI SDK `streamText()`에 전달한다. 이후 AI SDK의 Tool Loop가 LLM 판단, Tool 실행, Tool 결과 재입력과 최종 답변 생성을 처리한다.

```text
Agent 설정 + Messages + MCP Tool
→ AI SDK streamText()
→ 일반 Tool Loop
→ 최종 답변
```

### 4-2. Meeting Agent Runner

회의록 Agent는 독립 공간의 커스텀 Harness를 실행해야 한다. 일반 Agent와 다른 핵심 책임은 다음과 같다.

- Search·Question Tool 결과를 다음 LLM Context에 포함하고 목표를 재판단
- 복수 후보 선택과 허용 ID 추가·대체를 위한 HITL 중단·재개
- 사용자·Thread별 회의록 Agent State 사용
- 최종 사용자 답변 직전의 업무 Checkpoint
- Recording Tool 성공 여부를 반영해 녹화 상태를 갱신하고, LLM으로 돌아가지 않은 채 UI 결과를 확정하는 종료 규칙
- 회의록 접근 권한 재검증과 회의록 원문 비영속 처리
- 회의록 Agent 설계에 맞춘 안전한 Trace

```text
Meeting Agent 설정 + Messages + MeetingExecutionState
→ 커스텀 Harness
→ Search·Question·Recording Tool과 HITL
→ 최종 실행 결과
```

따라서 회의록 Agent를 기존 `streamText()` Tool Loop의 설정값만 바꾼 일반 Agent로 취급해서는 안 된다. 기존 호출 기반에 연결되지만, 내부 실행 방식은 독립적이어야 한다.

## 5. 경계 B: Agent별 결과를 공통 처리로 돌려주는 지점

경계 B는 Runner가 사용자에게 보여줄 최종 결과를 확정한 뒤, 공통 UI·DB 처리로 돌아오는 지점이다.

일반 Agent와 회의록 Agent가 내부에서 서로 다른 방식으로 실행되더라도 공통 처리부가 이해할 수 있는 계약을 가져야 한다.

개념적인 결과 계약에는 다음 내용이 필요하다.

- 실행 결과: 완료·HITL 대기·실패·중단
- 사용자에게 보여줄 최종 답변
- Token 사용량
- Tool 감사에 사용할 비밀 없는 Metadata
- 답변을 연결할 Channel과 Thread 정보
- 공통 UI가 이해할 진행 Event

Streaming은 Runner가 끝난 뒤 한꺼번에 반환할 수 없다. 실행 중 발생하는 Text와 진행 상황을 공통 Realtime 경로에 즉시 전달할 수 있도록 callback 또는 event sink 형태의 공통 출력 경계가 필요하다.

```text
Agent별 Runner
├─ 실행 중: 공통 Realtime 출력 경계로 Text·진행 Event 전달
└─ 실행 종료: 표준화된 최종 결과 반환
                    ↓
               공통 Finalizer
```

## 6. 공통 결과 처리로 재사용할 영역

경계 B 이후에는 가능한 한 다음 기존 제품 기능을 재사용한다.

- Realtime Text와 진행 Event 전송
- 최종 Agent 답변을 `message.posted`로 저장
- 호출 메시지의 Thread 루트에 답변 연결
- Token 사용량과 Tool 호출 감사 기록
- `agent_runs` 성공·실패·중단 처리
- claim·lease 유효성 확인과 중복 완료 방지

현재는 이 기능들이 독립된 Finalizer로 분리되어 있지 않고 `runAgentTurn()` 내부에 일반 AI SDK 실행 코드와 함께 있다. 따라서 Meeting Agent Runner를 추가할 때는 공통 코드를 복사하는 것이 아니라, 일반·회의록 Runner가 함께 사용할 Realtime 출력 경계와 최종 처리부를 추출하는 방향이 적절하다.

## 7. Messages와 MeetingExecutionState의 저장 책임

공통 결과 처리를 재사용한다고 해서 Worker가 Scratchpad까지 관리해 주는 것은 아니다.

### 7-1. Messages

기존 `message.posted` Event가 영속 대화 이력의 원본이다. Worker는 새 Run을 시작할 때 현재 Thread의 Event를 읽어 `ModelMessage[]`로 변환한다.

```text
기존 message.posted Event
→ Worker가 Thread 대화 조회
→ ModelMessage[] 구성
→ Meeting Agent Runner 입력
```

따라서 회의록 Agent의 State에 동일한 대화 이력을 다시 영속 저장할 필요는 없다. 다만 실행 중에는 Worker가 복원한 Messages를 Runner의 입력값으로 사용한다.

### 7-2. MeetingExecutionState와 Scratchpad

회의록 Agent 고유 상태는 공통 `message.posted` 처리로 대체되지 않는다.

```ts
type MeetingExecutionState = {
  authorizedMeetingIds: string[];
  recordingModalStatus: RecordingModalStatus;
  pendingHitl?: PendingHitl;

  scratchpad: {
    toolResults: ToolResult[];
    workingContext: WorkingContext[];
  };
};
```

- 이전 대화 이력: 기존 `message.posted`에서 복원
- 권한·녹화·HITL 기준값: `MeetingExecutionState`
- Tool 실행 중 다음 LLM 판단에 필요한 결과: `scratchpad`
- 과거 실행 관찰·감사 기록: Trace와 Tool 감사 기록

Tool 호출 감사 기록은 Tool 이름과 출처를 남기는 실행 로그이지 Scratchpad가 아니다. 현재 Turn의 Tool 결과를 후속 Node와 LLM 판단에서 사용하려면 Meeting Agent Runner가 별도로 관리해야 한다.

## 8. 현재 코드에서 확인한 위치

| 책임 | 현재 코드 위치 |
|---|---|
| 메시지 API·검증 | `src/app/api/channels/[channelId]/messages/route.ts`, `src/lib/channels/handlers.ts` |
| 메시지 저장·멘션·Run 생성 | `src/lib/channels/messages.ts` |
| Agent 권한·실행 설정 확정 | `src/lib/agents/effective-config.ts` |
| `agent_runs` 생성·claim | `src/lib/agents/runs.ts`, `src/lib/agents/worker-runtime.ts` |
| Thread Messages와 Agent 설정 조회 | `src/lib/agents/worker-runtime.ts` |
| AI SDK 조립·일반 Tool Loop | `src/lib/agents/worker-runtime.ts`의 `startAgentStream()` |
| 현재 Turn 조정과 공통 마무리 | `src/lib/agents/worker.ts`의 `runAgentTurn()` |
| Agent 관리 API | `src/lib/agents/runtime.ts` |

`src/lib/agents/runtime.ts`는 Agent 생성·수정·활성화와 같은 관리 API의 Runtime이다. Worker가 Agent Turn을 실행하고 AI SDK를 조립하는 Runtime과 혼동하면 안 된다.

## 9. 최종 정리

회의록 Agent는 기존 제품의 채팅과 실행 기반을 사용하되, 독립된 실행부를 가져야 한다.

```text
[공통]
메시지 접수 → message.posted → 멘션·Agent DB → agent_runs → Worker claim

[경계 A]
Agent 유형에 따라 Runner 선택

[독립]
Meeting Agent State → 커스텀 Harness → Tool·HITL·Checkpoint → 결과 확정

[경계 B]
Streaming Event와 표준화된 최종 결과 전달

[공통]
UI 전송 → message.posted → Thread 연결 → 사용량·감사 → Run 완료
```

핵심 경계는 두 곳이다.

1. **경계 A:** Worker가 Run을 claim한 뒤 Standard Agent Runner와 Meeting Agent Runner를 선택하는 지점
2. **경계 B:** Agent별 실행 결과를 공통 Realtime·메시지 저장·사용량·감사·Run 완료 처리에 넘기는 지점

회의록 Agent의 독립성은 제품의 공통 호출 기반을 버린다는 뜻이 아니다. 공통 기반은 재사용하고, 설계에서 검증하려는 Graph State와 커스텀 Harness가 필요한 실행 영역만 독립시키는 것이 이식 방향이다.
