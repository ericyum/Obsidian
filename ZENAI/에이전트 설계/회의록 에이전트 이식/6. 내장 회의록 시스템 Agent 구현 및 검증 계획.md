# 내장 회의록 시스템 Agent 구현 및 검증 계획

> 이 문서는 구현 순서와 검증 기준을 정한다. 별도 Branch·Worktree·Commit·PR 생성은 이 계획의 범위에 포함하지 않는다.

**목표:** POC에서 검증한 회의록 Agent 업무 로직을 zen-ai의 기존 Runtime과 AI SDK를 사용하는 내장 시스템 Agent로 구현한다.

**구조:** 회의록 Agent의 정의와 전용 로직은 `src/lib/agents/meetings`에 둔다. 기존 Runtime은 호출·대화 Context·모델 실행·Streaming을 재사용하고, 회의록 Agent 정의 로드, 녹화 명령, 공통 `follow_up` Condition과 HITL 재개에 필요한 부분만 최소 확장한다.

**기술 기반:** TypeScript, Next.js, Vercel AI SDK, Drizzle ORM, PostgreSQL, Vitest

**기준 문서:**

- `3. 회의록 Agent 이식 대상 업무 로직.md`
- `4. zen-ai 내장 시스템 Agent 실행 기반 파악.md`
- `5. POC 업무 로직의 내장 회의록 Agent 대응 방식.md`
- `회의록 에이전트 설계/1-2. 회의록 에이전트 워크플로우 Graph 상세.md`

## 1. 전체 구현 구조

```text
src/lib/agents/meetings/
├─ agent_definition.ts  # 시스템 Agent 정의와 로컬 Tool 등록
├─ search-tool.ts       # Search Tool 업무 로직
├─ question-tool.ts     # Question Tool 업무 로직
├─ recording.ts         # 녹화 명령과 기존 녹화 기능의 연결 계약
├─ session-data.ts      # 사용자·Thread별 관리 변수값
└─ hitl.ts              # Search Tool의 중단·재개 정보
```

별도의 `scratchpad.ts`, `types.ts`, `handler.ts`는 만들지 않는다.

```text
회의록 Agent 호출
→ 코드의 Agent 정의 로드
→ 녹화 명령이면 LLM 우회
→ 일반 요청이면 기존 AI SDK 실행
→ LLM이 Search·Question Tool 선택
→ AI SDK가 등록된 execute() 자동 호출
→ response + follow_up 공통 Condition
→ 반복 또는 최종 응답
```

## 2. 구현 불변 조건

- 회의록 Agent는 생성 모달로 만드는 일반 Agent가 아니라 모든 사용자가 호출하는 내장 시스템 Agent다.
- Agent의 System Prompt와 Tool 정의는 DB 설정이 아니라 코드가 원본이다.
- Search와 Question은 각각 하나의 Tool이며 내부 로직은 서로 독립적이다.
- `follow_up = true`이면 LLM 목표 판단으로 돌아가고, `false`이면 Tool의 `response`를 출력하고 종료한다.
- 녹화 명령은 LLM에 전달하지 않고 기존 녹화 모달·Backend 경로를 실행한다.
- `authorized_meeting_ids`와 Pending HITL은 사용자·Thread별로 격리한다.
- 회의록 권한은 Tool이 호출하는 Backend 경계에서 검증하고 원문 조회 직전에 다시 검증한다.
- 회의록 원문과 API Key는 DB 대화 이력, Session Data, HITL, Log, Trace와 Audit에 저장하지 않는다.
- Search·Question은 녹화 상태를 읽거나 변경하지 않는다.
- 종료 상태는 설계 용어인 `none`이며 별도 `done` 상태를 만들지 않는다.

## 3. 단계별 구현 계획

### 3.1 내장 시스템 Agent 등록과 정의

**생성 파일**

- `src/lib/agents/meetings/agent_definition.ts`
- `src/lib/agents/meetings/agent-definition.test.ts`

**수정 대상**

- `src/lib/channels/messages.ts`: 회의록 시스템 Agent 호출과 Thread 후속 요청 인식
- `src/lib/agents/effective-config.ts`: 일반 Grant와 구분되는 시스템 Agent 실행 허용
- `src/lib/agents/worker-runtime.ts`: DB Agent 정의 대신 코드 정의를 선택하는 경로
- `src/lib/agents/registry.ts`: 시스템 Agent를 일반 관리 기능으로 수정·보관하지 못하게 제한
- `scripts/platform-bootstrap-admin.ts`: 회의록 시스템 Agent의 기술적 식별 행 자동 등록
- `src/lib/db/schema.ts`: Agent를 `custom`과 `system`으로 구분하는 필드
- `drizzle/0043_meeting_agent_system.sql`: 시스템 Agent 구분과 기술적 식별 행을 위한 Schema 변경

현재 `message.posted`, `agent_runs`와 Agent 응답은 `agentId` 외래키를 사용한다. 따라서 회의록 Agent는 코드 정의만 사용하는 동시에, 기존 원장과 실행 Queue가 참조할 **기술적 Agent 식별 행**은 필요하다.

- 기술적 행은 Bootstrap에서 자동 등록한다.
- 사용자 생성 모달을 거치지 않는다.
- 모든 사용자 대상 실행 권한을 부여한다.
- 이름·Prompt·모델·Tool 정책의 원본으로 사용하지 않는다.
- 관리 화면에서 수정·비활성화·삭제할 수 없도록 시스템 Agent로 구분한다.

`agent_definition.ts`는 다음 정보를 제공한다.

```ts
export const meetingAgentDefinition = {
  name: "회의록 Agent",
  slug: "meetings",
  model: resolveTaskModel(),
  systemPrompt: MEETING_AGENT_SYSTEM_PROMPT,
  defaultReasoningEffort: null,
  maxOutputTokens: null,
  contextLimitTokens: null,
  maxRounds: 0,
  tools: {
    search_meetings: searchTool,
    question_meetings: questionTool,
  },
};
```

`null`과 `0`은 기존 Runtime 기본 동작을 사용한다는 의미다. System Prompt는 기존 회의록 Agent 설계 Prompt를 옮기고, Search·Question Tool 선택과 Tool 결과만 근거로 답하는 규칙을 포함한다.

기본 모델은 zen-ai의 내장 AI 기능이 이미 사용하는 `resolveTaskModel()`로 결정한다. 별도의 회의록 Agent 전용 모델 값을 하드코딩하지 않는다.

**검증 기준**

- 모든 사용자가 `@meetings`로 시스템 Agent를 호출할 수 있다.
- 호출 메시지를 Root로 Agent 답변과 후속 요청이 같은 Thread에 연결된다.
- Runtime이 회의록 Agent의 Prompt·Tool을 DB 정책이 아닌 코드 정의에서 읽는다.
- 일반 Agent의 기존 DB 정의 로딩과 Grant 검증은 변하지 않는다.

### 3.2 Session Data와 HITL 저장 경계

**생성 파일**

- `src/lib/agents/meetings/session-data.ts`
- `src/lib/agents/meetings/session-data.test.ts`
- `src/lib/agents/meetings/hitl.ts`
- `src/lib/agents/meetings/hitl.test.ts`

**수정 대상**

- `src/lib/db/schema.ts`
- `drizzle/0044_meeting_agent_session.sql`

Session Data는 다음 Key로 격리한다.

```text
community_id + user_id + thread_root_id
```

관리 값은 다음 두 개로 제한한다.

```ts
type MeetingAgentSessionData = {
  authorizedMeetingIds: string[];
  recordingModalStatus: string | null;
};
```

Pending HITL은 Session Data와 별도로 관리한다.

```ts
type PendingMeetingHitl = {
  kind: "meeting_selection" | "id_merge";
  candidateMeetingIds: string[];
  existingAuthorizedMeetingIds: string[];
  allowedResponses: string[];
};
```

HITL에는 회의록 원문, API Key와 전체 대화 이력을 저장하지 않는다. 사용자 응답이 유효하지 않으면 Pending 정보를 유지하고 같은 질문을 다시 출력하며, 완료·거부·취소 시 삭제한다.

**검증 기준**

- 사용자 또는 Thread가 다르면 허용 ID와 Pending HITL을 읽을 수 없다.
- 잘못된 HITL 입력 후에도 동일한 선택을 다시 받을 수 있다.
- Worker가 종료되거나 요청이 바뀌어도 다음 입력에서 HITL을 재개할 수 있다.
- HITL 완료 후 Pending 행이 남지 않는다.

### 3.3 Search Tool 구현

**생성 파일**

- `src/lib/agents/meetings/search-tool.ts`
- `src/lib/agents/meetings/search-tool.test.ts`

**재사용 대상**

- 기존 `src/lib/meetings`의 회의록 검색·조회·권한 검증 기능
- `session-data.ts`
- `hitl.ts`

AI SDK Tool 객체 안에 이름, Description, 입력 Schema와 실행 함수를 함께 정의한다.

```ts
export const searchTool = tool({
  description: "접근 가능한 회의록을 검색하고 질문에 사용할 회의록을 선택합니다.",
  inputSchema: z.object({ query: z.string().min(1) }),
  execute: executeMeetingSearch,
});
```

실행 순서는 POC Search Subgraph를 그대로 따른다.

```text
검색 조건 구성
→ 접근 가능한 후보 검색
→ 0개 / 1개 / 복수 판별
→ 복수이면 회의록 선택 HITL
→ 선택 ID와 권한 재검증
→ 필요하면 추가·대체 HITL
→ authorized_meeting_ids 갱신
→ response + follow_up 반환
```

**검증 기준**

- 후보가 0개이면 안전한 안내와 `follow_up = false`를 반환한다.
- 후보가 1개이면 불필요한 선택 HITL 없이 허용 ID를 갱신한다.
- 복수 후보이면 HITL을 만들고 임의로 첫 후보를 선택하지 않는다.
- 후보 밖 ID와 권한이 사라진 ID는 반영하지 않는다.
- 이미 허용된 동일 ID만 선택하면 추가·대체 HITL을 생략한다.
- 검색 과정에서 회의록 원문을 조회하거나 저장하지 않는다.

### 3.4 Question Tool 구현

**생성 파일**

- `src/lib/agents/meetings/question-tool.ts`
- `src/lib/agents/meetings/question-tool.test.ts`

**재사용 대상**

- 기존 `src/lib/meetings`의 상세 조회와 권한 검증 기능
- `session-data.ts`
- 기존 모델 Provider

AI SDK Tool의 모델 입력 Schema에는 질문만 노출한다.

```ts
export const questionTool = tool({
  description: "선택과 권한 검증이 완료된 회의록을 근거로 질문에 답합니다.",
  inputSchema: z.object({ question: z.string().min(1) }),
  execute: executeMeetingQuestion,
});
```

`user_id`, `thread_root_id`와 `authorized_meeting_ids`는 서버 실행 Context에서 읽으며 LLM이 생성하는 Tool 인자에 포함하지 않는다.

```text
authorized_meeting_ids 확인
→ 원문 조회 직전 권한 재검증
→ 허용된 원문만 메모리에서 조회
→ 질문 답변 Context 구성
→ response + follow_up 생성
→ 원문 참조 폐기
```

**검증 기준**

- 허용 ID가 없으면 Search가 먼저 필요하다는 결과를 반환한다.
- 다른 사용자·Thread의 허용 ID를 사용할 수 없다.
- 조회 직전에 권한이 사라진 회의록은 LLM Context에 포함하지 않는다.
- `authorized_meeting_ids` 자체는 Question LLM Prompt에 포함하지 않는다.
- 회의록 원문은 Session Data, 채팅 메시지, Log와 Audit에 남지 않는다.

### 3.5 Runtime 공통 결과 처리

**수정 대상**

- `src/lib/agents/worker.ts`
- `src/lib/agents/worker-runtime.ts`
- `src/lib/agents/worker.test.ts`
- `src/lib/agents/worker-provider.test.ts`

회의록 Tool 결과는 다음 공통 계약을 사용한다.

```ts
type MeetingToolResult = {
  response: string;
  follow_up: boolean;
};
```

```text
follow_up = true
→ 기존 AI SDK가 Tool 결과를 다음 LLM 호출에 전달

follow_up = false
→ response를 최종 Agent 메시지로 사용
→ 추가 LLM 호출 없이 실행 종료
```

Tool 이름별 Runtime 분기는 만들지 않는다. `agent_definition.ts`에 등록된 Tool 객체의 `execute()`는 AI SDK가 자동 호출한다. Runtime의 회의록 Agent 특수 처리는 정의 선택과 공통 `follow_up` 결과 계약에만 둔다.

**검증 기준**

- Search Tool 선택 시 `searchTool.execute()`가 호출된다.
- Question Tool 선택 시 `questionTool.execute()`가 호출된다.
- `follow_up = true`일 때 Tool 결과가 다음 Provider 요청의 `role: "tool"`에 포함된다.
- `follow_up = false`일 때 Provider를 다시 호출하지 않고 `response`가 최종 답변으로 저장된다.
- 일반 Agent의 기존 Tool 반복과 Streaming 동작은 변하지 않는다.

### 3.6 녹화 명령 연결

**생성 파일**

- `src/lib/agents/meetings/recording.ts`
- `src/lib/agents/meetings/recording.test.ts`

**수정 대상**

- `src/components/workspace/composer.tsx`
- `src/components/workspace/composer.test.tsx`

현재 Composer는 `isMeetingStartCommand()`와 `requestStart()`를 통해 녹화 모달을 열 수 있다. 이 경로를 재사용하되, 회의록 시스템 Agent가 호출된 Thread의 녹화 명령에만 동작하도록 제한한다.

```text
회의록 Agent Thread의 입력
→ 녹화 명령 검사
→ 일반 Agent 실행 Queue와 LLM 호출을 만들지 않음
→ 기존 requestStart()로 녹화 모달 실행
→ 모달·Backend 결과 수신
→ recording_modal_status 갱신
```

서버의 `recording.ts`는 Browser의 마이크나 모달을 직접 제어하지 않는다. 명령과 결과의 구조만 정의하고, 실제 모달 실행은 기존 Frontend Provider가 담당한다.

**검증 기준**

- 회의록 Agent Thread의 녹화 명령은 LLM Provider를 호출하지 않는다.
- 다른 Agent Thread와 일반 채널의 같은 문장은 회의록 Agent 녹화 분기로 들어가지 않는다.
- 기존 녹화 모달과 Backend 흐름이 그대로 실행된다.
- 성공·거부·실패 결과에 맞게 `recording_modal_status`가 갱신된다.
- Search·Question 실행은 녹화 상태를 읽지 않는다.

## 4. 통합 검증 시나리오

### 4.1 기본 호출

```text
@meetings 회의록을 찾아줘
→ 회의록 시스템 Agent Thread 생성
→ 코드의 System Prompt와 두 Tool 사용
```

### 4.2 Search 후 Question 연속 실행

```text
meeting-001 회의록을 찾아서 결정 사항을 설명해줘
→ Search
→ authorized_meeting_ids 갱신
→ follow_up = true
→ Question
→ follow_up = false
→ 최종 답변
```

### 4.3 복수 후보 HITL

```text
복수 후보 검색
→ 사용자 선택 요청
→ 잘못된 입력이면 같은 질문 반복
→ 올바른 선택이면 Search 재개
```

### 4.4 추가·대체 HITL

```text
기존 허용 ID 존재
→ 새로운 ID 선택
→ 추가 또는 대체 선택
→ 선택에 맞게 Session Data 갱신
```

### 4.5 권한 변경

```text
Search 당시 접근 가능
→ Question 직전 권한 제거
→ 원문 조회 거부
→ 안전한 안내
```

### 4.6 녹화 명령

```text
회의록 Agent Thread에서 /meeting-start
→ LLM 우회
→ 기존 녹화 모달 실행
→ 결과 상태 동기화
```

### 4.7 보안 확인

- DB의 Event·Agent Run·Session·HITL·Audit 행에서 회의록 원문 검색 결과가 0건이어야 한다.
- Log와 오류 응답에 회의록 원문, API Key와 내부 Stack Trace가 없어야 한다.
- 다른 사용자와 Thread의 허용 ID 및 HITL 선택지를 읽을 수 없어야 한다.

## 6. 완료 기준

- 회의록 Agent가 생성 모달 없이 내장 시스템 Agent로 호출된다.
- 모든 사용자가 호출할 수 있으며 호출 메시지를 Root로 전용 Thread가 형성된다.
- Runtime이 `agent_definition.ts`에서 Prompt·모델 정책·두 Tool을 읽어 AI SDK에 전달한다.
- Search와 Question이 각각 독립 Tool로 실행된다.
- `response + follow_up`에 따라 설계와 동일하게 반복·종료된다.
- HITL이 사용자·Thread별로 중단·검증·재개된다.
- 녹화 명령이 LLM을 거치지 않고 기존 녹화 기능을 실행한다.
- 권한 재검증과 회의록 원문 비영속성이 보장된다.
- 기존 일반 Agent와 녹화 기능의 회귀 Test가 모두 통과한다.

## 핵심 원칙

> **새로운 Agent Framework를 만드는 것이 아니라, 코드로 정의한 회의록 시스템 Agent를 기존 Runtime과 AI SDK에 연결한다. 새로 구현하는 것은 회의록 고유의 Search·Question·HITL·Session Data·녹화 연결과 설계상의 공통 `follow_up` Condition뿐이다.**
