# 독립 회의록 Agent 구조 설계

이 문서는 [[5. 공통 Agent 호출 기반과 AI SDK 조립 템플릿 경계 조사]]에서 정한 방향을 실제 구현 위치 수준으로 구체화한다.

기존 Channel·Message·Agent DB·`agent_runs`·Worker 기반은 재사용한다. Worker가 Run을 claim한 뒤 Agent 유형에 따라 실행부를 선택하고, 회의록 Agent일 때만 독립 Meeting Agent Runner와 커스텀 Harness로 진입한다.

## 1. 폴더 구조

```text
zen-ai
├─ src/lib/db/
│  └─ schema.ts                        [수정] 회의록 Agent 전용 감사 테이블 추가
│
├─ src/lib/agents/
│  ├─ worker-runtime.ts                [기존] Run claim·lease·timeout
│  ├─ worker.ts                        [수정] Runner 선택·공통 Finalizer
│  ├─ runner-contract.ts               [신규] Runner 입출력·Realtime 계약
│  ├─ standard-runner.ts               [신규] 기존 일반 Agent 실행부
│  │
│  └─ meetings/                        [신규] 독립 회의록 Agent
│     ├─ runner.ts                     Meeting Agent 진입점
│     ├─ harness.ts                    커스텀 Graph 실행
│     ├─ execution-state.ts            State 형식
│     ├─ state-client.ts               Python State 서버 Adapter
│     ├─ context.ts                    LLM Context 조립
│     ├─ pending-hitl.ts               HITL 저장·검증·재개
│     ├─ trace.ts                      MeetingTraceSink
│     ├─ audit.ts                      MeetingToolAuditAdapter
│     │
│     ├─ tools/
│     │  ├─ search-tool.ts
│     │  ├─ question-tool.ts
│     │  └─ recording-tool.ts
│     │
│     ├─ recording-skills/
│     │  ├─ start.ts
│     │  ├─ pause.ts
│     │  ├─ resume.ts
│     │  └─ stop.ts
│     │
│     └─ adapters/
│        ├─ meeting-backend.ts
│        └─ recording-backend.ts
│
└─ services/
   └─ meeting-agent-state/
      └─ server.py                      변수값·Scratchpad·HITL Snapshot 서버
```

Agent DB에는 회의록 Agent도 다음 공통 정보를 등록한다.

```text
agentId·이름·멘션 정보
+ 활성 상태·사용 권한
+ Agent 버전·시스템 프롬프트
+ 모델·추론 설정
+ Token·Context·Round 한도
```

커스텀 Harness, Tool, State 형식, HITL, Trace와 감사 Adapter는 `src/lib/agents/meetings/`에서 관리한다.

## 2. 구성요소별 책임

### 2-1. 공통 Worker 영역

| 구성요소 | 책임 |
|---|---|
| `worker-runtime.ts` | 기존 방식대로 `agent_runs` claim, lease, timeout과 동시 실행을 관리한다. 회의록 업무 로직은 넣지 않는다. |
| `worker.ts` | 공통 입력을 준비하고 Agent 유형에 맞는 Runner를 선택한 뒤 공통 Finalizer를 실행한다. |
| `runner-contract.ts` | 일반 Runner와 Meeting Runner가 사용할 입력, Realtime 출력과 최종 결과 형식을 정의한다. |
| `standard-runner.ts` | 현재 `runAgentTurn()`과 `startAgentStream()`에 섞인 일반 AI SDK Tool Loop를 옮긴다. |

현재 `Standard Agent Runner`와 공통 Finalizer가 실제로 분리되어 있는 것은 아니다. 기존 `runAgentTurn()`의 일반 Agent 실행 책임과 공통 결과 처리 책임을 나눈 뒤 사용할 구조다.

최소 Runner 계약은 다음 정보를 다룬다.

```text
Runner 입력
├─ AgentRun·Messages
├─ 시스템 프롬프트
├─ 모델·추론·Token·Context·Round 설정
├─ AbortSignal
└─ 공통 Realtime 출력 경계

Runner 결과
├─ completed | hitl_prompted | failed | cancelled
├─ 최종 답변 또는 HITL 질문
├─ Token 사용량
└─ 공개 가능한 오류 코드
```

공통 Finalizer는 다음 기존 기능을 담당한다.

- 최종 답변 또는 HITL 질문을 `message.posted`로 저장
- 호출 메시지의 Thread 루트에 연결
- Token 사용량 기록
- `agent_runs`를 `done` 또는 `failed`로 마무리
- claim·lease 유효성 확인과 중복 완료 방지

Realtime Text와 진행 Event는 Finalizer 이후가 아니라 Runner 실행 중 공통 출력 경계로 전달한다.

### 2-2. 회의록 Agent 영역

| 구성요소 | 책임 |
|---|---|
| `meetings/runner.ts` | State와 Pending HITL을 먼저 조회하고 신규 요청 또는 HITL 재개를 선택한다. 실행 종료 전 감사 기록을 저장하고 공통 결과 형식으로 반환한다. |
| `meetings/harness.ts` | LLM 판단, Search·Question 반복, Recording 종료 예외, HITL과 업무 Checkpoint를 제어한다. |
| `execution-state.ts` | Graph Engineering의 State인 `MeetingExecutionState` 형식을 정의한다. |
| `state-client.ts` | Python State 서버의 저장 방식과 HTTP 계약을 Harness에서 숨긴다. |
| `context.ts` | Messages·Scratchpad·Tool 결과에서 현재 LLM 호출에 필요한 Context만 구성한다. |
| `pending-hitl.ts` | Pending HITL 조회, 입력 검증, Snapshot 저장과 재개를 담당한다. |
| `trace.ts` | 커스텀 Harness의 실행 과정을 안전한 Trace Event로 출력한다. |
| `audit.ts` | 현재 Run의 Tool 감사 항목을 전용 감사 저장소에 기록한다. |

`MeetingExecutionState`는 다음 값을 가진다.

```ts
type MeetingExecutionState = {
  authorizedMeetingIds: string[];
  recordingModalStatus: RecordingModalStatus;

  scratchpad: {
    toolResults: ToolResult[];
    workingContext: WorkingContext[];
  };
};
```

기존 대화 이력은 Worker가 `message.posted`에서 `ModelMessage[]`로 복원하여 전달하므로 영속 State에 중복 저장하지 않는다.

### 2-3. Tool·Skill·Backend 경계

| 구성요소 | 책임 |
|---|---|
| Search Tool | 권한 범위 안에서 회의 후보를 검색하고 후보·오류·HITL 요청을 정형화해 반환한다. 선택 ID도 Backend에서 다시 검증한다. |
| Question Tool | `authorizedMeetingIds`를 확인하고 현재 권한을 재검증한 뒤 원문을 일시적인 Context로 반환한다. |
| Recording Tool | 녹화 명령에 따라 시작·일시정지·재개·종료 Skill 중 하나를 선택한다. |
| Recording Skill | 기존 녹화 모달·Backend Adapter를 호출하고 성공·실패 결과를 반환한다. |
| Meeting Backend Adapter | 기존 회의 검색·권한·원문 조회 Backend를 호출하고 오류를 공개 가능한 코드로 바꾼다. |
| Recording Backend Adapter | 기존 녹화 모달·Backend 메서드를 호출하고 결과를 정형화한다. |

Search·Question 결과는 Harness가 이후 LLM Context에 포함하여 재판단한다. Recording 결과는 `recordingModalStatus`를 갱신한 뒤 LLM에 다시 넣지 않고 UI 결과를 확정한다.

회의록 원문, API 키·인증정보, 내부 오류 원문은 State·Scratchpad·HITL Snapshot·Trace·감사 기록에 저장하지 않는다.

### 2-4. 변수값과 Pending HITL 관리

현재 우선안은 `services/meeting-agent-state/server.py`를 별도 Python 서버로 실행하는 것이다.

이 서버가 사용자·Agent·Channel·Thread별로 다음 값을 관리한다.

- `authorizedMeetingIds`
- `recordingModalStatus`
- 안전한 Scratchpad
- Pending HITL 대기 정보
- HITL 재개 위치인 `resumePoint`
- 재개에 필요한 `stateSnapshot`

격리 키는 다음 조합을 사용한다.

```text
agentId + userId + channelId + threadRootEventId
```

Pending HITL 정보와 State Snapshot을 함께 저장하므로 이 저장 기능은 **기술적인 의미의 Checkpoint 역할도 한다.**

`agent_runs`에는 `waiting_for_input`, `pendingHitlId`와 `checkpointRef`를 추가하지 않는다. HITL 질문을 안전하게 저장·출력한 현재 Run은 `done`으로 끝내고, 사용자 응답은 기존 방식대로 새로운 `message.posted`와 새로운 Run을 만든다.

Python 서버 방식은 현재 구조 설계를 위한 우선안이다. 다음 사항은 추가 조사 후 확정한다.

- 실제 영속 저장 매체와 재시작 복구
- 다중 서버 인스턴스의 상태 공유
- 동시 갱신·중복 HITL 응답 방지와 원자성
- State 서버 인증·네트워크 접근 제한
- TypeScript 서비스와 Python 서버의 운영 배포 방식

저장 기술이 변경되더라도 Harness와 Tool이 바뀌지 않도록 `state-client.ts`를 경계로 둔다. 향후에는 `/cancel`로 Pending HITL을 명시적으로 취소하고 새 일반 요청을 시작하는 기능도 고려한다.

### 2-5. Trace와 감사

`MeetingTraceSink`는 Harness 실행 중 Graph·Node·Edge·LLM·Tool·HITL·Checkpoint의 안전한 Trace Event를 실시간으로 출력한다. 초기 구현체는 서버 로그를 사용하며, 출력 실패가 Agent 업무를 실패시키지 않도록 best-effort로 처리한다.

`MeetingToolAuditAdapter`는 Tool 결과가 확정될 때 안전한 감사 항목을 메모리에 모으고, 최종 완료·HITL 질문 출력·실패 등으로 Run이 끝나기 직전에 일괄 저장한다.

회의록 내부 Tool은 MCP Tool이 아니므로 `mcp_audit_events`에 기록하지 않는다. 기존 PostgreSQL에 별도의 append-only 테이블을 추가한다.

```text
meeting_agent_tool_audit_events
├─ seq·createdAt
├─ communityId
├─ runId·agentId·actorUserId
├─ toolName·action
├─ outcome·durationMs
└─ safeMetadata
```

Trace와 감사는 목적·시점·저장 경로가 다르며, 현재는 두 기능을 묶는 Tool Wrapper를 만들지 않는다.

## 3. 실제 요청 처리 순서

### 3-1. 공통 진입과 Runner 선택

```text
사용자가 @회의 에이전트와 요청 입력
→ Channel Handler·Runtime이 요청 검증
→ 사용자 메시지를 message.posted로 저장
→ 멘션에서 회의록 Agent의 agentId 식별
→ Agent DB에서 권한 확인 및 이번 Run의
   버전·모델·추론·Token·Context·Round 한도 확정
→ agent_runs에 pending Run 생성
→ Worker가 Run claim
→ Agent 유형 확인
→ Meeting Agent Runner 호출
```

### 3-2. Meeting Agent 공통 진입

```text
Meeting Agent Runner
→ Worker가 복원한 Messages 수신
→ Python State 서버에서 MeetingExecutionState 조회
→ Pending HITL 조회
   ├─ 없음 → 신규 일반 요청으로 Harness 실행
   └─ 있음 → 현재 입력을 HITL 응답으로 검증
```

### 3-3. 일반 Search·Question 요청

```text
LLM 목표 판단
├─ Search Tool
│  → 정형화된 검색 결과 반환
│  → Harness가 다음 LLM Context에 포함
│  → LLM 재판단
│
├─ Question Tool
│  → 권한 재검증·원문 조회
│  → 필요한 원문을 해당 LLM 호출에만 포함
│  → LLM 재판단
│
└─ Tool 불필요
   → LLM 최종 답변 확정

실행 중
├─ 공통 Realtime 출력 경계로 Text·진행 Event 전달
└─ MeetingTraceSink로 안전한 Trace 출력

최종 답변 직전
→ 업무 Checkpoint 반영·안전한 State 저장
→ MeetingToolAuditAdapter로 감사 기록 저장
→ 표준 결과 반환
→ 공통 Finalizer가 message.posted·Thread·사용량·Run 완료 처리
```

### 3-4. HITL 요청과 재개

```text
Harness에서 사용자 선택 필요
→ Pending HITL·resumePoint·stateSnapshot 저장
→ 이 저장이 기술 Checkpoint 역할
→ HITL 질문 반환
→ Run 종료 직전 감사 기록 저장
→ 공통 Finalizer가 HITL 질문을 message.posted로 저장
→ 현재 agent_runs는 done
→ Worker 자원·claim·lease 해제

사용자가 같은 Thread에서 응답
→ 새로운 message.posted와 agent_runs 생성
→ Meeting Agent Runner가 Pending HITL 발견
→ HITL 입력 검증
   ├─ 유효 → Snapshot 복원·resumePoint부터 재개·Pending HITL 해결
   └─ 무효 → Pending HITL 유지·기존 질문 재안내
```

State Snapshot 저장에 실패하면 재개할 수 없으므로 HITL 질문을 먼저 출력하지 않고 현재 Run을 실패 처리한다.

### 3-5. Recording 요청

```text
LLM이 Recording Tool 호출
→ Tool이 start·pause·resume·stop Skill 중 하나 선택
→ Skill이 기존 녹화 모달·Backend Adapter 호출
→ 성공·실패 결과 반환
→ recordingModalStatus 갱신
→ 결과를 LLM에 다시 넣지 않음
→ 사용자에게 보여줄 결과 확정
→ Run 종료 직전 감사 기록 저장
→ 표준 결과 반환
→ 공통 Finalizer가 message.posted·사용량·Run 완료 처리
```

## 결론

```text
기존 Worker 공통 기반
→ 공통 Runner 계약
→ meetings/runner.ts
→ 커스텀 Harness·Tool·State·HITL·Trace·감사
→ 표준 결과
→ 기존 공통 Finalizer
```

Agent DB는 회의록 Agent의 식별·권한·버전·시스템 프롬프트·모델·실행 한도를 관리한다. `src/lib/agents/meetings/`는 회의록 Agent만의 실행 방식을 관리한다.

`authorizedMeetingIds`, `recordingModalStatus`, Scratchpad와 Pending HITL은 현재 우선안으로 별도 Python State 서버에서 관리한다. 이 방식의 영속성·동시성·다중 인스턴스·인증·배포 적합성은 추가 조사하여 최종 확정한다.
