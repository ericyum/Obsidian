# 독립 회의록 Agent 구조 설계

## 1. 폴더 구조

```text
agents/
└─ meeting/assistant/
   ├─ manifest.json
   └─ system-prompt.md

src/lib/builtin-agents/
├─ registry/executor-registry.ts     회의록 executor descriptor 등록
└─ registry/executors.server.ts      enqueue·adapter factory 등록

src/lib/meeting-agent/
├─ engine.ts                         목표와 상태 전이
├─ provider.ts                       AI SDK 모델 Adapter
├─ channel-adapter.ts                Builtin Runtime 연결과 Realtime/최종 표시
├─ thread-context.ts                 Thread 대화와 Agent State·업무 경계 조회
└─ tools/
   └─ state-repository.ts           회의 검색·원문·권한·authorizedMeetingIds·Tool HITL 상태

src/lib/ui/meeting-agent-control.ts   요청자 전용 녹화 시작 Event 계약
```

별도 `src/lib/agents/worker` 분해, `runner-contract.ts`, `harness.ts`, `context.ts`, `execution-state.ts`, `state-client.ts`, `pending-hitl.ts`, `trace.ts`, `server.py`를 먼저 만들지 않는다. 현재 필요한 책임은 위 파일 안의 작은 함수로 충분하며, 실제 중복이 생길 때만 추출한다.

## 2. 각 부분의 역할

### Definition과 Registry

Manifest는 definition identity, executor ID, handle, model allowlist와 실행 상한을 고정한다. Registry는 HTTP·DB 자유 문자열이 아니라 코드 소유 목록에서만 Executor를 선택한다.

### Channel Adapter

Builtin Worker가 claim한 Run을 회의록 Engine에 연결한다. Thread Context와 이전 Checkpoint를 읽고, 실행 중 안전한 진행 Event를 보낸 뒤 `ExecutorResult`를 반환한다. 최종 DB 처리는 기존 Builtin terminal 계약을 호출한다.

### Engine과 Provider

Engine은 다음 행동과 상태 전이만 담당하고 Provider는 AI SDK 호출과 구조화 출력 검증을 담당한다. Context 선택 규칙이 작을 때는 Provider의 함수로 두고, 독립적인 변경·테스트 필요가 생길 때 `context.ts`로 추출한다.

### Tool·State Repository

호출 사용자의 권한으로 Search와 원문 조회를 수행하고, `authorizedMeetingIds`와 Pending HITL 상태를 함께 관리한다. `authorizedMeetingIds`가 있어도 원문을 읽는 순간 다시 권한을 검사한다. 원문을 반환받은 Engine은 현재 Question 모델 호출에만 사용한다.

현재 Local Tool이 소유하는 업무 State다.

```ts
type MeetingToolState = {
  authorizedMeetingIds: string[];
  pendingHitl?: {
    pendingToken: string;
    kind: "selection" | "merge";
    candidateIds: string[];
    originalRequest: string;
    expiresAt: string;
  };
};
```

실제 DB 행은 `communityId + principalId + triggerUserId + conversationKey` Scope로 격리한다. Tool이 최신 권한·토큰·중복을 확인하고 원자적으로 갱신한다. 향후에는 이 Repository 구현을 고객사 MCP로 옮긴다.

### Agent State와 업무 Checkpoint

Agent State Store와 Workflow Checkpoint Store에는 Tool 상세를 복제하지 않는다. Tool 상세는 Tool State Repository가 소유한다.

```ts
type MeetingAgentState = {
  version: 1;
  scratchpad: SafeScratchpadEntry[];
  pendingHitlRef?: {
    tool: "search";
    pendingToken: string;
    resumePoint: "search_selection";
  };
};
```

새 Run은 Agent State Store와 Workflow Checkpoint Store를 조회한다. 최소 참조가 없거나 Tool 토큰이 소비·만료되었다면 HITL 응답으로 처리하지 않는다.

## 3. 실제 요청 흐름

### Search

```text
목표 판단 search
→ Search Tool이 Repository를 통해 사용자의 현재 접근 범위에서 후보 검색
→ 0개: 안전한 결과 안내
→ 1개: Tool State에 최초 선택 또는 기존 상태와 비교
→ 여러 개/충돌: Search Tool이 Tool State Repository에 상세 Pending 저장 + 최소 참조 반환
→ 선택 확정 뒤 남은 질문 목표가 있으면 Question으로 진행
```

### Question

```text
목표 판단 question
→ Question Tool이 Tool State Repository에서 authorizedMeetingIds 조회
→ 없으면 검색 필요 안내
→ Repository가 현재 권한 재검증 후 원문 조회
→ 원문을 현재 모델 입력에만 추가
→ 답변 생성 후 원문 참조 폐기
```

### HITL 재개

```text
새 Run 시작
→ Agent State와 업무 Checkpoint 및 Tool Pending 조회
→ /cancel이면 Pending 폐기
→ 선택 입력이면 후보·토큰·권한 재검증
→ add/replace 또는 선택 반영
→ 원래 요청의 남은 목표 실행
```

### Recording

```text
목표 판단 recording:start
→ 요청자에게만 휘발성 recording-start Event
→ 기존 Meeting Recording Provider.requestStart()
→ 전달 성공 답변으로 Run 종료
```

`recordingModalStatus`는 저장하지 않는다. 브라우저가 꺼져 Event를 받지 못하면 Agent가 실제 녹화 시작 성공으로 주장하지 않는다.

## 4. Realtime·감사·보안

- 진행 상태: 기존 `agent-delta`
- 공식 실행 기록: 기존 Builtin operation receipt/evidence
- 최종 답변과 Run terminal: 기존 Builtin DB 함수
- Local Tool은 MCP 호출인 것처럼 `mcp_audit_events`에 기록하지 않음
- Trace·evidence에는 Tool 이름, 안전한 상태, 개수만 저장
- 회의록 원문·API 키·인증정보·내부 예외 원문 저장 금지

## 5. 장기 템플릿화

사용자가 선택 가능한 커스텀 로직 서비스는 별도의 제품 기능이다. 이번 회의록 Executor에서 검증된 Engine·HITL·Tool Resolver 패턴이 두 번째 Executor에서도 반복될 때 공통 계약으로 승격한다. 지금은 미래 가능성만을 위해 일반 Agent Worker를 분해하지 않는다.
