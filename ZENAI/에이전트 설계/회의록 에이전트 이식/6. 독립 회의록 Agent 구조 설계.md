# 독립 회의록 Agent 구조 설계

이 문서는 [[5. 공통 Agent 호출 기반과 AI SDK 조립 템플릿 경계 조사]]와 이후 발표 피드백을 바탕으로 독립 회의록 Agent의 현재 구조 방향을 정리한다.

회의록 Agent는 단순한 예외 구현으로 끝나는 기능이 아니다. 최종적으로 Agent 생성 화면에서 시스템 프롬프트·모델·Tool과 함께 여러 커스텀 실행 로직을 선택할 수 있게 만드는 첫 실험작이다.

## 1. 목표 구조

```text
src/lib/agents/
├─ worker/
│  ├─ worker-runtime.ts
│  ├─ worker.ts
│  └─ runner-contract.ts
├─ standard/
│  └─ standard-runner.ts
├─ custom/
│  ├─ runner.ts
│  ├─ harness.ts
│  ├─ context.ts
│  ├─ execution-state.ts            CustomAgentState 형식
│  ├─ state-client.ts
│  ├─ pending-hitl.ts
│  └─ trace.ts
└─ tools/                         현재만 사용하는 임시 로컬 Tool
   ├─ search-tool.ts
   ├─ question-tool.ts
   └─ recording-tool.ts

services/meeting-agent-state/
└─ server.py                      현재 상태 저장 방식의 우선안
```

기존 `recording-skills/`, `meeting-backend.ts`, `recording-backend.ts`는 이 구조에서 제거한다.

## 2. 공통 호출 기반과 Runner

다음 기존 기반은 그대로 재사용한다.

```text
Channel 요청 접수
→ message.posted 저장
→ @멘션으로 agentId 식별
→ Agent DB에서 권한·모델·실행 설정 조회
→ agent_runs 생성
→ Worker claim
```

Worker는 Agent 실행 유형에 따라 Runner를 선택한다.

```text
Worker
├─ standard/standard-runner.ts    기존 AI SDK·MCP 실행
└─ custom/runner.ts               선택된 커스텀 실행 로직
```

두 Runner는 `runner-contract.ts`가 정의한 공통 입력·Realtime Event·최종 결과 규격을 따른다. 따라서 Worker와 공통 Finalizer는 내부 실행 방식과 관계없이 같은 방식으로 Runner를 호출하고 결과를 처리한다.

Realtime Text와 진행 Event는 Runner 실행 중 전달한다. Runner가 끝나면 공통 Finalizer가 최종 `message.posted`, Thread 연결, 사용량 기록과 `agent_runs` 완료·실패 처리를 담당한다.

## 3. Custom 실행 구조

### 3-1. 공통 실행 뼈대

- `custom/runner.ts`: Tool 등록, State 구성, 신규 요청·HITL 재개 구분, Harness 호출, 감사 기록 마무리와 표준 결과 반환
- `custom/harness.ts`: LLM과 Tool 사이의 실행 순서, Tool 정책에 따른 반복·종료와 HITL 발생 시점 제어
- `custom/context.ts`: 상황에 따라 필요한 대화·Tool 결과·안전한 업무 정보를 골라 LLM Context 구성
- `custom/trace.ts`: Graph·LLM·Tool·HITL 진행을 안전한 Trace Event로 출력
- `custom/pending-hitl.ts`: 표준 HITL 신호를 받아 대기 정보·Snapshot 저장, 입력 검증과 재개 처리

향후에는 Agent DB에 사용자가 선택한 커스텀 로직과 버전을 저장하고, Custom Runner가 해당 조합을 불러와 실행하도록 한다. 어떤 로직을 동시에 조합할 수 있는지와 실행 순서는 후속 설계에서 확정한다.

### 3-2. Messages와 실행 State

- 대화 원본은 기존 `message.posted`에 저장한다.
- Worker가 Thread 대화를 `ModelMessage[]`로 복원하여 Runner에 전달한다.
- 회의록 Agent가 대화 이력을 별도 저장소에 중복 저장하지 않는다.
- `execution-state.ts`는 특정 회의록 필드를 고정한 State가 아니라 Custom Harness가 실행 중 사용할 최소 공통 State 구조를 정의한다.
- `state-client.ts`는 실제 저장소의 주소·API·기술을 Harness에서 숨기는 범용 조회·갱신 경계로 사용한다.

`state-client.ts` 자체가 값을 보관하는 것은 아니다. 현재는 `server.py`가 저장 기능을 제공하고, 향후 실제 DB·Redis 등으로 바뀌더라도 Harness가 직접 저장 기술을 알지 않도록 한다.

```ts
type CustomAgentState = {
  scratchpad: Scratchpad;
  pendingHitl?: PendingHitl;
};
```

Runner는 Run 시작 시 `(agentId, userId, channelId, threadRootEventId)` Scope로 이 State를 한 번 조회해 메모리 객체로 구성한다. Harness는 Run 동안 그 객체를 읽고 갱신한다. 일반 완료 직전에는 변경된 공통 State를 저장하고, HITL 발생 시에는 질문 출력·Run 종료 전에 Pending HITL·재개 위치·안전한 Snapshot을 먼저 저장한다. HITL을 사용하지 않는 Agent에는 `pendingHitl`이 없으며 빈 HITL 레코드도 만들지 않는다.

## 4. 회의록 전용 상태 처리 방향

공통 Custom State에 회의록 전용 필드를 고정하면 다른 Agent가 같은 실행 구조를 재사용하기 어렵다. 따라서 하나의 상태 저장 기능을 사용하더라도 데이터를 논리적으로 분리한다.

```text
사용자·Agent·Channel·Thread 격리 키
├─ 공통 Custom 실행 상태
│  ├─ scratchpad
│  └─ pendingHitl·resumePoint·안전한 Snapshot
└─ Meeting 업무 상태
   └─ authorizedMeetingIds
```

- `authorizedMeetingIds`는 회의록 검색·질문 Tool이 사용하는 업무 상태다. 현재는 같은 State 서버의 Meeting 전용 영역에 저장할 수 있지만 공통 `execution-state.ts`의 고정 필드로 만들지 않는다.
- Search Tool이 선택 결과를 직접 저장하고 Question Tool이 같은 Scope로 조회한다. Tool은 회의록 접근 시 실제 Backend 권한을 다시 검증해야 한다.
- Tool별 상태 조회·저장에 필요한 Scope는 LLM Tool 인자가 아니라 Runner가 검증한 실행 Context로 주입한다.
- Harness는 Tool 전용 상태의 추가·대체 규칙을 해석하거나 `stateUpdates`를 저장하지 않는다.
- `recordingModalStatus`는 Agent State와 State 서버에 저장하지 않는다. 실제 녹화 상태는 녹화 Backend가 소유하고 Recording Tool은 Skill 트리거만 전달한다.

현재의 Python State 서버는 임시 우선안이다. 영속 저장 매체, 재시작 복구, 동시성, 다중 인스턴스 공유, 인증과 배포 방식은 추가 조사 후 확정한다.

## 5. Tool 등록과 실행 방향

### 5-1. 공통 Tool 결과 계약

```ts
type ToolResult = {
  toolCallId: string;
  toolName: string;
  status: "success" | "failed" | "hitl_required";
  output?: unknown;
  hitl?: HitlRequest;
  errorCode?: string;
};
```

- Tool은 자신의 업무 상태를 직접 저장하고 `stateUpdates`는 반환하지 않는다.
- Search·Question처럼 LLM이 알아야 하는 결과만 `output`을 반환한다.
- HITL이 필요하면 일반 `output`으로 돌리지 않고 `hitl`로 반환하여 `pending-hitl.ts`로 보낸다.
- Recording은 Skill 트리거 전달 결과만 반환하며, 실제 녹화 상태를 LLM Context에 넣지 않는다.

### 5-2. 실행 후 흐름 정책

`afterExecution`은 Tool 실행 결과가 아니라 Harness의 다음 행동을 정하는 Tool 등록 정책이다.

```ts
type ToolDefinition = {
  name: string;
  afterExecution: "return_to_llm" | "end_run";
  execute: (...) => Promise<ToolResult>;
};
```

Search·Question은 `return_to_llm`, Recording은 `end_run`을 사용한다. `hitl_required`가 반환되면 `afterExecution`보다 HITL 처리를 우선한다. Harness는 Tool 이름별 예외를 하드코딩하지 않고 Tool Resolver가 정규화한 정의만 읽으며, 외부 metadata의 정책 값은 허용된 enum인지 검증한다.

### 5-3. 현재 로컬 Tool

회의록 Tool은 아직 MCP 서버에 배포하지 않고 `src/lib/agents/tools/`에 로컬로 구현한다.

```text
Custom Runner 시작
→ Agent DB에서 회의록 Agent의 Tool 이름 확인
→ Tool 이름을 tools/의 로컬 execute 함수·afterExecution 정책과 임시 매핑
→ Harness 실행 중 로컬 Tool 호출
```

로컬 Tool에는 별도의 서버 주소가 없다. 기존 DB 스키마가 MCP 주소를 필수로 요구하는지는 구현 전에 확인해야 하며, 가짜 로컬 주소를 저장하지 않는다.

### 5-4. 향후 고객사 적용

고객사별 Tool은 고객사의 온프레미스 MCP 서버에서 실행한다.

```text
Agent DB에서 Tool·MCP 연결 정보 조회
→ MCP Tool의 스키마·호출 정보와 사용자 정의 metadata 또는 Tool manifest 조회
→ Tool Resolver가 호출용 execute Proxy·afterExecution을 공통 ToolDefinition으로 정규화
→ Harness 실행 중 MCP Tool 호출
```

따라서 현재 로컬 Tool 예외는 임시 구현이고, 향후 Tool 등록부만 MCP 연결로 교체하는 것을 목표로 한다. 정확한 DB 필드와 Resolver 규격은 현행 Tool 등록 코드를 추가 조사한 뒤 확정한다.

## 6. 녹화 명령과 Agent Tool의 구분

`/meeting-start` 같은 명령은 회의록 Agent Thread 내부 Skill이 아니다.

```text
일반 채팅창에서 /meeting-start
→ 채팅 명령 Skill
→ 회의 시작 Backend 실행
```

회의록 Agent에게 녹화를 요청한 경우에는 다음 흐름을 사용한다.

```text
회의록 Agent의 LLM 판단
→ Recording Tool 호출
→ 녹화 Skill 실행 트리거 전달
→ Tool이 트리거 전달 성공 결과 반환
→ afterExecution: end_run에 따라 LLM 재호출 없이 종료
```

여기서 Tool의 성공은 실제 녹화 완료가 아니라 Skill 트리거가 정상적으로 전달되었다는 뜻이다. 실제 녹화 실행과 UI 모달 변경은 이후 Skill·Backend가 책임진다.

따라서 기존 `recording-skills/` 폴더는 두지 않는다. 채팅 명령 Skill의 실제 파일 위치와 Agent Tool이 같은 Backend 기능을 중복 없이 호출하는 연결 방식은 기존 채팅 명령 구조를 조사한 뒤 확정한다.

## 7. Trace와 감사

- Trace는 `custom/trace.ts`가 실행 중 실시간·best-effort로 출력한다.
- Tool 감사 항목은 현재 `custom/runner.ts`가 Run 메모리에 모으고 Run 종료 직전에 전용 감사 저장소에 기록한다.
- 별도의 `audit.ts`는 두지 않는다.
- 감사 변환·보안 필터링이 복잡해지거나 여러 Agent가 재사용하게 될 때만 공용 `lib` Adapter로 분리한다.
- 회의록 원문·API 키·인증정보·내부 오류 원문은 State·Snapshot·Trace·감사에 저장하지 않는다.

## 8. 현재 확정하지 않은 사항

- Custom Runner가 여러 커스텀 로직을 조합하는 계약·순서·충돌 처리 방식
- `scratchpad`와 `pendingHitl` 내부의 상세 스키마 및 저장 주기
- `/meeting-start` 채팅 Skill의 실제 배치 위치
- 로컬 Tool과 MCP Tool을 교체하는 실제 DB 필드·Resolver 구현 규격
- Python State 서버의 최종 저장 기술과 운영 방식

## 결론

```text
기존 공통 호출 기반
→ Worker가 Standard 또는 Custom Runner 선택
→ Custom Runner가 공통 State와 선택된 Harness·Tool을 연결
→ 현재는 회의록 Tool의 execute·afterExecution을 로컬 등록
→ Harness가 Tool 결과·HITL·afterExecution에 따라 다음 흐름 결정
→ 향후 고객사 온프레미스 MCP Tool로 교체
→ 표준 결과를 기존 공통 Finalizer가 처리
```

회의록 Agent의 목적은 하나의 특수 Agent를 만드는 데서 끝나지 않는다. 회의록 Agent를 통해 검증한 Runner·Harness·Context·HITL·Trace 경계를 이후 Agent 생성 화면에서 선택 가능한 커스텀 실행 로직으로 확장하는 것이 최종 방향이다.
