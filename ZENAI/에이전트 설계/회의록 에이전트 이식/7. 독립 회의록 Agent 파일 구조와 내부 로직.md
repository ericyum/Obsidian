# 독립 회의록 Agent 파일 구조와 내부 로직

## 1. 구조 요약

```text
agents/meeting/assistant/              정적 definition
src/lib/builtin-agents/registry/       공통 Executor 등록
src/lib/meeting-agent/                 회의록 전용 실행
src/lib/meeting-agent/tools/           Local Tool·State 경계
src/lib/ui/meeting-agent-control.ts     녹화 시작 제어 Event
```

## 2. 파일·그룹별 역할

### `manifest.json` + `system-prompt.md`

회의록 Agent의 안정적인 identity, handle, model allowlist, 실행 상한과 불변 지침을 코드로 고정한다. DB의 사용자 Custom Agent 설정을 fallback으로 읽지 않는다.

### Builtin Executor Registry

`meeting-agent-v1` descriptor, channel enqueue와 adapter factory를 명시적으로 등록한다. Worker는 기존 Executor와 같은 방식으로 회의록 Executor를 호출하므로 새 `runner-contract.ts`가 필요하지 않다.

### `channel-adapter.ts`

Run·Thread·이전 Checkpoint를 Engine 입력으로 바꾸고 Realtime 진행을 발행한다. Engine 결과를 기존 `ExecutorResult`와 Builtin terminal DB 계약에 맞춘다. 별도 `runner.ts`와 `audit.ts`로 쪼개지 않는다.

### `engine.ts`

다음 순서만 명확하게 소유한다.

```text
Pending HITL 우선 확인
→ 목표 판단
→ Search | Question | Recording | direct
→ Tool 결과에 따른 계속·HITL·종료
→ 안전한 답변·Checkpoint·evidence 생성
```

권한 DB 질의, AI Provider 생성과 Realtime transport 세부 구현은 Engine 밖에 둔다.

### `provider.ts`

AI SDK `generateText()`로 목표와 최종 답변을 생성하고 JSON Schema를 검증한다. Context 예산을 넘으면 오래된 대화·안전한 Scratchpad부터 줄인다. 원문이 들어가는 Question 입력은 반환하거나 기록하지 않는다.

### `thread-context.ts`

현재 trigger 메시지와 같은 Thread의 이전 사용자·Agent `message.posted`만 순서대로 읽고 길이를 제한한다. Agent State Store와 Workflow Checkpoint Store에서 각각 Scratchpad와 업무 턴 경계를 읽는다.

### `tools/state-repository.ts`

회의 검색·원문 조회와 `authorizedMeetingIds`, Pending 후보·추가·대체·일회용 토큰을 같은 Scope에서 원자적으로 읽고 갱신한다. 사용자 권한을 SQL/Backend 경계에서 강제하며 Tool이 전달한 ID를 그대로 신뢰하지 않는다. Harness 공통 State가 아니라 Local Tool 업무 State다. 향후 Tool과 함께 MCP 서버로 이동한다.

### `meeting-agent-control.ts`

요청자 전용 휘발성 `meeting-recording-start` Frame을 검증하고 기존 Recording Provider 호출용 브라우저 Event로 바꾼다. 실제 녹화 상태는 저장하지 않는다.

## 3. Tool 결과

```ts
type MeetingToolResult = {
  status: "success" | "failed" | "hitl_required";
  output?: unknown;
  hitl?: { prompt: string; pendingToken: string };
  errorCode?: string;
};
```

- Search: 후보 제목·확정 결과처럼 다음 판단에 필요한 안전한 값만 `output`
- Question: 원문은 현재 Model 호출용 별도 메모리 값이며 저장 가능한 Tool 결과에 넣지 않음
- Recording: 제어 Event 전달 성공 여부만 반환하고 바로 Run 종료
- HITL: `hitl_required`가 다른 실행 후 정책보다 우선

이번 Executor는 일반 AI SDK 자동 Tool Loop를 사용하지 않으므로 AI SDK가 Tool Result Message를 자동 누적한다고 가정하지 않는다. Engine이 필요한 안전한 Tool 결과를 다음 Provider 입력에 명시적으로 넣는다.

## 4. State와 저장 주기

```text
Run 시작: Thread Context + Agent State + 업무 Checkpoint + Tool State 조회
Tool 실행: Tool State는 성공한 업무 전이와 함께 즉시 저장
HITL: Tool State Repository에 상세 Pending 저장, Agent State에 최소 참조 저장, 업무 Checkpoint 기록 후 질문 반환
일반 완료: Agent State의 Scratchpad 갱신, 업무 Checkpoint와 최종 답변 확정
```

Tool 상태를 Run 종료 때 한꺼번에 저장하지 않는다. Tool 성공 뒤 Worker가 중단되어도 다음 재시도가 중복 갱신하지 않도록 token/run ID 기반 멱등성을 둔다.

## 5. 캡슐화 효과

- Builtin Platform은 회의록 변수와 Tool을 모른다.
- Engine은 DB Schema·AI Provider·Realtime 연결 세부를 모른다.
- Tool Repository는 LLM 목표 판단을 모른다.
- UI Provider는 Agent State와 Tool 후보를 모른다.

이 경계는 보안과 변경 격리에 직접 필요한 만큼만 둔다. 둘 이상의 구현에서 반복되지 않은 범용 Harness·Audit Adapter·Trace Sink는 아직 만들지 않는다.
