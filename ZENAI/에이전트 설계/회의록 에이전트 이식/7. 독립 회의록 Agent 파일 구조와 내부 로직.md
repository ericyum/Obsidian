# 독립 회의록 Agent 파일 구조와 내부 로직

이 문서는 [[6. 독립 회의록 Agent 구조 설계]]의 현재 폴더 구조와 분리 이유를 간략하게 설명한다. 회의록 Agent는 선택 가능한 Custom Harness를 만들기 위한 첫 사례이며, 회의록 전용 로직을 공통 구조에 고정하지 않는 것을 원칙으로 한다.

## 1. Worker·Standard·Custom Runner

```text
src/lib/agents/
├─ worker/
│  ├─ worker-runtime.ts
│  ├─ worker.ts
│  └─ runner-contract.ts
├─ standard/
│  └─ standard-runner.ts
└─ custom/
   └─ runner.ts
```

![[Excalidraw/01_Runner_공통_계약.svg]]

- `worker/`: Run claim·lease와 Runner 선택, 공통 결과 처리를 담당한다.
- `standard/`: 기존 AI SDK·MCP 기반 Agent를 실행한다.
- `custom/runner.ts`: Custom Harness 실행, HITL 재개 구분, 감사 마무리와 표준 결과 반환을 담당한다.
- `runner-contract.ts`: 두 Runner가 따를 입력·Realtime Event·최종 결과 규격을 정의한다.

**분리 이유:** Runner 내부 구현이 달라도 Worker가 같은 방식으로 호출·처리하고, 이후 새로운 Runner도 같은 규격으로 추가하기 위해서다.

## 2. Custom Harness 내부

```text
custom/
├─ harness.ts
├─ context.ts
├─ execution-state.ts
├─ state-client.ts
├─ pending-hitl.ts
└─ trace.ts
```

![[Excalidraw/02_Harness_내부_책임_분리.svg]]

- `harness.ts`: LLM과 Tool의 실행 순서, 반복·종료와 HITL 시점을 제어한다.
- `context.ts`: 현재 LLM 호출에 필요한 대화·Tool 결과·업무 정보만 선택하여 Context를 만든다.
- `pending-hitl.ts`: 표준 HITL 신호의 저장·검증·Snapshot 복원과 재개를 처리한다.
- `trace.ts`: 실행 과정을 안전한 Trace Event로 출력한다.

**분리 이유:** Context·HITL·Trace의 세부 규칙이 바뀌어도 Harness의 핵심 실행 흐름에 미치는 영향을 줄이기 위해서다.

## 3. 실행 State와 저장소

![[Excalidraw/03_State와_저장소_경계.svg]]

- `execution-state.ts`: Custom Harness가 사용하는 최소 공통 실행 State 형식을 정의한다.
- `state-client.ts`: 값별 조회·갱신 API를 제공하고 실제 저장소의 주소와 기술을 숨긴다.
- `server.py`: 현재 우선안인 상태 저장 서비스다.

```text
사용자·Agent·Channel·Thread 격리 키
├─ 공통 상태: Scratchpad·Pending HITL·재개 Snapshot
└─ Meeting 상태: authorizedMeetingIds
```

`authorizedMeetingIds`는 Search·Question Tool이 사용하는 Meeting 업무 상태로 분리한다. `recordingModalStatus`는 실제 녹화 Backend·Modal을 기준으로 조회·갱신한다.

**분리 이유:** 회의록 전용 필드를 공통 Custom State에 고정하지 않고, 저장 기술이 바뀌어도 Harness의 변경을 최소화하기 위해서다.

## 4. 현재 로컬 Tool과 향후 MCP Tool

```text
tools/
├─ search-tool.ts
├─ question-tool.ts
└─ recording-tool.ts
```

![[Excalidraw/04_Local_Tool과_MCP_전환.svg]]

현재는 Custom Runner가 시작될 때 회의록 Tool 이름을 `tools/`의 로컬 `execute` 함수와 임시로 매핑한다. 향후에는 고객사의 온프레미스 MCP 서버 정보를 조회하여 같은 Tool을 MCP 방식으로 등록한다.

**분리 이유:** 현재 POC의 로컬 실행을 지원하면서도, Tool 등록부만 교체하여 고객사 MCP 환경으로 이전하기 위해서다.

## 5. 채팅 명령 Skill과 Recording Tool

![[Excalidraw/05_채팅_Skill과_Recording_Tool.svg]]

```text
일반 채팅창의 /meeting-start
→ 채팅 명령 Skill
→ 회의 시작 Backend

회의록 Agent의 녹화 요청
→ Recording Tool
→ 같은 회의 시작 Backend 기능
```

기존 `recording-skills/`는 Agent 내부에서 다시 나누지 않는다. 채팅 명령 Skill은 Agent 호출 전에도 작동하는 별도 채팅 명령 영역에 둔다.

**분리 이유:** 직접 채팅 명령과 Agent Tool 호출은 진입 경로만 다르고, 실제 녹화 Backend 기능은 중복 구현하지 않기 위해서다.

## 6. Trace와 감사

![[Excalidraw/06_Trace와_감사_경계.svg]]

- `trace.ts`: 실행 중 Graph·LLM·Tool·HITL 진행을 실시간으로 출력한다.
- `custom/runner.ts`: Tool 감사 항목을 모아 Run 종료 직전에 전용 저장소에 기록한다.
- 별도 `audit.ts`는 두지 않으며, 여러 Agent의 재사용 근거가 생길 때 공용 Adapter로 분리한다.

**분리 이유:** 실시간 관찰과 영속 감사를 구분하면서 현재 필요한 최소 구조만 유지하기 위해서다.

## 7. 후속 설계에서 확정할 사항

- 여러 Custom Harness 로직의 선택·조합·실행 순서
- 공통 실행 State와 Tool별 업무 State의 최종 계약
- `/meeting-start` 채팅 Skill의 실제 파일 위치
- 로컬 Tool과 MCP Tool을 전환하는 등록·Resolver 규격
- 재사용·변경 영향·보안 기준에 따라 공용 `lib`로 옮길 내부 로직
