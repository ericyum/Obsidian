# 독립 회의록 Agent 파일 구조와 내부 로직

이 문서는 [[6. 독립 회의록 Agent 구조 설계]]의 폴더별 역할과 분리 이유를 간략하게 설명한다. 회의록 Agent는 선택 가능한 Custom Harness의 첫 사례이며, 회의록 전용 상태와 업무 규칙을 공통 구조에 고정하지 않는 것을 원칙으로 한다.

## 1. Worker·Standard·Custom Runner

```text
src/lib/agents/
├─ worker/
│  ├─ worker-runtime.ts
│  ├─ worker.ts
│  └─ runner-contract.ts
├─ standard/
│  └─ standard-runner.ts
└─ custom/
   └─ runner.ts
```

![[Excalidraw/01_Runner_공통_계약.svg]]

- `worker/`: Run claim·lease, Runner 선택과 공통 Finalizer를 담당한다.
- `standard/`: 기존 AI SDK·MCP 기반 Agent를 실행한다.
- `custom/runner.ts`: Tool 등록, State 구성, HITL 재개 구분, AI SDK에 Custom Harness 규칙 적용, Tool 감사 마무리와 표준 결과 반환을 담당한다.
- `runner-contract.ts`: 모든 Runner의 입력·Realtime Event·최종 결과 규격을 정의한다.

**분리 이유:** Runner 내부 구현이 달라도 Worker가 같은 방식으로 호출·처리하고, 새 Runner도 같은 규격으로 추가하기 위해서다.

## 2. Custom Harness 내부

```text
custom/
├─ harness.ts
├─ context.ts
├─ execution-state.ts
├─ state-client.ts
├─ pending-hitl.ts
└─ trace.ts
```

![[Excalidraw/02_Harness_내부_책임_분리.svg]]

- `harness.ts`: AI SDK Tool Loop에 `afterExecution`·HITL 같은 커스텀 반복·중단 규칙을 적용한다.
- `context.ts`: AI SDK의 현재 `messages`에서 필요한 대화·Tool 결과를 선별·정렬·축약하고 안전한 Scratchpad Context를 추가한다.
- `pending-hitl.ts`: 표준 HITL 신호의 저장·입력 검증·Snapshot 복원과 재개를 처리한다.
- `trace.ts`: 실행 과정을 민감정보가 제거된 Trace Event로 출력한다.

**분리 이유:** Context·HITL·Trace의 세부 규칙을 독립적으로 변경·테스트하면서 Harness에는 공통 실행 순서만 남기기 위해서다.

Tool별 `output`을 `context.ts`가 직접 해석하거나 `toToolMessage()`로 다시 변환하지 않는다. AI SDK가 Tool 실행 결과를 공통 `tool-result` Message로 만들어 현재 Run의 `messages`에 누적하며, `context.ts`는 `prepareStep`에서 이 Messages를 받아 조립 규칙만 적용한다.

```text
Worker가 message.posted에서 복원한 초기 Messages
→ AI SDK가 현재 Run의 Tool Call·Tool Result를 임시 누적
→ context.ts가 현재 Messages와 필요한 Scratchpad를 선별·축약
→ 다음 LLM 호출
```

## 3. 실행 State와 저장소

![[Excalidraw/03_State와_저장소_경계.svg]]

- `execution-state.ts`: Harness가 사용할 최소 공통 `CustomAgentState` 형식을 정의한다.
- `state-client.ts`: 공통 State의 조회·부분 갱신 API를 제공하고 저장소 주소와 기술을 숨긴다.
- `server.py`: 현재 우선안인 상태 저장 서비스이며 공통 State와 Tool 전용 상태를 Namespace로 분리한다.

```ts
type CustomAgentState = {
  scratchpad: Scratchpad;
  pendingHitl?: PendingHitl;
};
```

```text
agentId + userId + channelId + threadRootEventId
├─ 공통 State: scratchpad·pendingHitl·resumePoint·안전한 Snapshot
└─ Meeting 상태: authorizedMeetingIds
```

Runner는 Run 시작 시 공통 State를 한 번 읽어 메모리 객체를 만들고, Harness는 Run 동안 이를 사용한다. 일반 완료 직전에는 변경 내용을 저장하고, HITL 발생 시에는 질문 출력과 Run 종료 전에 Pending HITL·재개 위치·안전한 Snapshot을 먼저 저장한다.

`authorizedMeetingIds`는 Search·Question Tool이 직접 조회·갱신하는 업무 상태다. `recordingModalStatus`는 Agent State에 저장하지 않으며 실제 녹화 상태는 녹화 Backend가 소유한다. 기존 대화는 Worker가 `message.posted`에서 `ModelMessage[]`로 복원하므로 State에 중복 저장하지 않는다.

여기서 `message.posted`에는 사용자 메시지와 Agent 최종 답변만 영속 저장된다. AI SDK의 현재 `messages`에는 여기에 더해 이번 Run의 Tool Call·Tool Result가 임시로 들어가지만, 별도로 저장하지 않는 한 Run 종료 후 사라지고 다음 Run의 초기 `ModelMessage[]`에는 포함되지 않는다.

**분리 이유:** 공통 Harness가 회의록 전용 변수와 저장 기술을 모르도록 하여 다른 Agent에서도 같은 실행 구조를 재사용하기 위해서다.

## 4. Tool 등록·결과·실행 정책

```text
tools/
├─ search-tool.ts
├─ question-tool.ts
└─ recording-tool.ts
```

![[Excalidraw/04_Local_Tool과_MCP_전환.svg]]

현재는 Tool 이름을 로컬 `execute` 함수와 `afterExecution` 정책에 매핑한다. 향후에는 고객사의 온프레미스 MCP 서버에서 Tool 호출 정보와 정책 metadata를 읽고, Tool Resolver가 호출용 `execute` Proxy와 `afterExecution`을 공통 형식으로 바꾼다.

```ts
type ToolDefinition = {
  name: string;
  afterExecution: "return_to_llm" | "end_run";
  execute: (...) => Promise<CustomToolExecutionResult>;
};
```

```ts
type CustomToolExecutionResult = {
  status: "success" | "failed" | "hitl_required";
  output?: unknown;
  hitl?: HitlRequest;
  errorCode?: string;
};
```

- `toolCallId`·`toolName`: AI SDK가 Tool Call 정보로 관리하므로 Tool 반환값에 중복하지 않는다.
- Search·Question: `return_to_llm`; LLM이 알아야 하는 결과만 `output`으로 반환한다.
- Recording: `end_run`; Skill 트리거 전달 결과만 반환한다.
- HITL: `hitl_required`가 `afterExecution`보다 먼저 처리된다.
- Tool 전용 상태는 Tool이 직접 저장하므로 `stateUpdates`는 반환하지 않는다.

Search와 Question의 `output` 내부 형태는 서로 달라도 된다. AI SDK가 각 반환값을 Tool 이름·호출 ID가 포함된 공통 Tool Result Message로 감싸기 때문이다. LLM은 AI SDK의 `tools` 설정으로 전달된 Tool Definition과 결과를 함께 보고 해석하며, `context.ts`에는 Tool별 변환 템플릿을 두지 않는다.

**분리 이유:** Harness와 Context에 Tool 이름별 예외를 넣지 않고, Tool이 늘어나거나 로컬 실행이 MCP 실행으로 바뀌어도 공통 실행 흐름을 수정하지 않기 위해서다.

## 5. 채팅 Skill과 Recording Tool

![[Excalidraw/05_채팅_Skill과_Recording_Tool.svg]]

```text
/meeting-start → 채팅 명령 Skill → 녹화 Backend

회의록 Agent의 녹화 판단
→ Recording Tool
→ 녹화 Skill 트리거 전달
→ 전달 성공 결과
→ afterExecution: end_run
```

Recording Tool의 성공은 실제 녹화 완료가 아니라 Skill 트리거 전달 성공을 뜻한다. Tool 반환 후 Harness는 LLM을 다시 호출하지 않으며, 실제 녹화 실행·상태·UI 변경은 Skill과 Backend가 담당한다.

**분리 이유:** Agent 호출 여부와 무관한 채팅 명령 진입 경로는 분리하되, 실제 녹화 기능은 같은 Backend에서 중복 없이 수행하기 위해서다.

## 6. Trace와 감사

![[Excalidraw/06_Trace와_감사_경계.svg]]

- `trace.ts`: 실행 중 Trace Sink를 통해 실시간·best-effort Event를 출력한다.
- `runner.ts`: Tool 감사 항목을 Run 메모리에 모으고 Run 종료 직전에 전용 감사 저장소에 기록한다.
- 별도의 `audit.ts`나 감사 Adapter는 두지 않는다.
- 여러 Agent에서 재사용할 근거가 생길 때만 공용 Audit Adapter로 추출한다.
- 회의록 원문·API 키·인증정보·내부 오류 원문은 State·Snapshot·Trace·감사에 저장하지 않는다.

**분리 이유:** 실행 관찰용 Trace와 공식 Tool 감사의 목적·처리 시점·실패 영향을 섞지 않기 위해서다.

## 7. 이후 확정할 사항

- 여러 Custom Harness 로직의 선택·조합 순서와 충돌 계약
- `scratchpad`·`pendingHitl`의 상세 스키마와 저장 주기
- `/meeting-start` 채팅 Skill의 실제 배치 위치
- 로컬 Tool과 MCP Tool Resolver의 실제 DB·코드 연결 규격
- Python State 서버의 최종 저장 기술·운영 방식
- 내부 로직 중 재사용·보안 목적의 공용 `lib` 추출 대상
