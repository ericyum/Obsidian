# Agent State 저장 위치 비교와 권장 방향

이 문서는 [[6. 독립 회의록 Agent 구조 설계]]과 [[7. 독립 회의록 Agent 파일 구조와 내부 로직]]에서 임시안으로 둔 별도 Python State 서버를 다시 검토한다.

비교 대상은 다음 두 방식이다.

1. **A안:** 상태를 최종 사용자의 브라우저·클라이언트 저장 공간에 두고, Tool 결과를 Harness가 해석하는 방식
2. **B안:** Tool과 상태를 고객사 MCP 서버에 함께 두고, Tool이 업무 정합성까지 검사하는 방식

여기서 A안의 “클라이언트 저장”은 `zen-ai` 서버가 접근하는 기존 DB나 운영 저장소가 아니다. Chrome의 Local Storage·IndexedDB·Origin Private File System이나 데스크톱 클라이언트 전용 파일처럼 **사용자 단말에 귀속된 공간**을 뜻한다.

결론부터 말하면 회의록 Agent의 권위 있는 업무 상태에는 **B안이 적합하다.** 다만 Agent 실행 수명과 Tool 업무 수명은 다르므로 모든 값을 한 저장소에 몰아넣지 않는다.

```text
사용자 단말
└─ 없어져도 실행 정합성이 깨지지 않는 UI 캐시만 허용

zen-ai 제품 경계
├─ message.posted와 agent_runs: 기존 영속 구조 재사용
├─ Agent State Store: 안전한 Scratchpad와 최소 HITL 참조
└─ Workflow Checkpoint Store: 사용자 요청 단위의 업무 턴 경계

현재 Local Tool / 향후 고객사 MCP 서버
└─ Tool 전용 상태와 업무 정합성
   └─ authorizedMeetingIds 등
```

별도 `server.py` 하나에 Scratchpad·HITL·Snapshot과 모든 Tool 전용 변수까지 저장하는 구조는 채택하지 않는다.

## 1. 먼저 구분할 상태

저장 위치를 정하려면 상태의 소유권부터 나눠야 한다.

| 정보 | 성격 | 권장 소유자 |
|---|---|---|
| 사용자·Agent 최종 대화 | 제품의 채팅 원장 | 기존 `message.posted` |
| 현재 Run의 Tool Call·Tool Result | AI SDK의 임시 실행 Context | 현재 Run 메모리 |
| `scratchpad` | 다음 판단에 필요한 가변 작업 Context | 필요한 최소분만 제품 실행 상태 경계 |
| 사용자 요청 단위의 완료·HITL 대기 업무 경계 | 한 턴이 어디에서 끝났는지 기록 | Workflow Checkpoint Store |
| `authorizedMeetingIds` | Search·Question Tool 전용 업무 상태 | 현재 Local Tool 저장 경계, 향후 MCP 서버 |
| 실제 녹화 상태 | 녹화 기능의 실제 상태 | 녹화 Backend |
| 화면 접힘·최근 선택 같은 편의 값 | 없어져도 정합성이 깨지지 않는 UI 상태 | 브라우저 저장소 사용 가능 |

브라우저 저장소, Agent 실행 상태와 Tool 업무 상태를 모두 “State”라고 부를 수 있지만 같은 권한과 수명을 가진 값은 아니다.

## 2. A안: 사용자 클라이언트에 State 저장

### 흐름

```text
브라우저가 Local Storage·IndexedDB 등에서 State 조회
→ 사용자 요청과 State를 zen-ai에 전달
→ Worker·Harness가 전달된 State와 Tool 결과를 해석
→ 갱신된 State를 응답에 포함
→ 브라우저가 다시 저장
```

Local Storage만 가능한 것은 아니다. IndexedDB, Origin Private File System, 데스크톱 앱 전용 파일처럼 브라우저나 클라이언트가 소유하는 다른 저장 방식도 같은 A안에 포함한다.

### 장점

- 별도 State 서버를 운영하지 않아도 된다.
- 서버 저장량을 줄일 수 있다.
- 단일 사용자의 단일 기기에서만 쓰는 임시 작업 상태는 구현이 빠르다.
- 서버로 보낼 필요가 없는 개인 UI 설정을 단말 안에 유지할 수 있다.

### 단점

- 브라우저 값은 사용자가 임의 변경할 수 있으므로 권한이나 업무 정합성의 근거가 될 수 없다.
- 새로고침, 저장 공간 정리, 시크릿 모드, 브라우저 교체와 기기 변경으로 상태가 사라질 수 있다.
- 같은 계정의 여러 탭·기기·사용자가 같은 Thread를 사용할 때 충돌 해결이 어렵다.
- Worker는 Queue에서 비동기로 실행되므로 브라우저가 닫혀 있으면 최신 State를 다시 읽을 수 없다.
- Run 재시도와 lease 회수 시 최초 요청에 실린 State가 최신인지 판단하기 어렵다.
- HITL 응답을 다른 기기에서 보냈을 때 재개 정보가 없을 수 있다.
- Harness가 Tool별 변수 의미와 추가·대체 규칙을 알아야 하므로 범용 템플릿이 회의록 업무 로직에 오염된다.
- 클라이언트가 보낸 `authorizedMeetingIds`는 신뢰할 수 없으므로 Backend에서 결국 다시 권한 검증해야 한다.

### 적합한 범위

A안은 다음처럼 **사라지거나 변조되어도 서버 실행 결과와 권한에 영향을 주지 않는 값**에만 적합하다.

- Trace 패널 열림 여부
- 임시 필터와 정렬 방식
- 작성 중인 일반 입력 초안
- 서버의 권위 있는 값을 다시 받을 수 있는 단기 캐시

`authorizedMeetingIds`, Pending HITL, Snapshot과 같이 실행·권한·재개에 영향을 주는 값의 기준 저장소로는 부적합하다.

## 3. B안: MCP 서버에 Tool과 State를 함께 배치

### 흐름

```text
Harness가 검증된 사용자·Agent·Thread Scope와 함께 Tool 호출
→ MCP Tool이 자신의 업무 State 조회
→ 권한·중복·추가·대체 조건을 Tool 경계에서 검사
→ 필요한 State를 원자적으로 갱신
→ Harness에는 표준 Tool 실행 결과만 반환
```

Search·Question Tool이 같은 회의록 MCP 서버에 있다면 두 Tool은 같은 Meeting State Namespace를 사용한다. Harness는 `authorizedMeetingIds`의 내부 의미를 알지 않는다.

### 장점

- 업무 규칙과 상태가 이를 가장 잘 아는 Tool 가까이에 모인다.
- 상태 조회·권한 재검증·갱신을 같은 서버와 트랜잭션 경계에서 처리하기 쉽다.
- Harness는 `status`, `output`, `hitl`, `afterExecution` 같은 공통 계약만 처리하므로 템플릿화하기 쉽다.
- 고객사별 업무 데이터와 상태를 고객사 온프레미스 경계 안에 둘 수 있다.
- Tool이 LLM에 필요하지 않은 내부 변수를 반환하지 않아도 된다.
- 다른 브라우저·기기에서 후속 질문하더라도 같은 MCP 상태를 조회할 수 있다.

### 단점

- MCP 서버가 상태 Schema, 동시성, idempotency, TTL, 백업과 마이그레이션을 책임져야 한다.
- Tool뿐 아니라 상태 저장소까지 장애가 나면 해당 업무 기능이 함께 중단된다.
- 여러 MCP 서버가 하나의 상태를 공유해야 한다면 명시적인 소유 서버와 계약이 필요하다.
- 중앙 `zen-ai`에서는 MCP 내부 상태를 직접 관찰할 수 없으므로 민감정보를 제외한 운영 조회·감사 경계가 필요할 수 있다.
- Agent 실행 자체와 무관한 MCP에 모든 Scratchpad·Run Snapshot을 넣으면 플랫폼 실행 수명과 Tool 수명이 결합된다.

### 적합한 범위

- `authorizedMeetingIds`
- 검색 후보와 선택 처리에 필요한 Tool 내부 상태
- Tool이 발행한 Pending HITL의 업무 세부정보와 일회용 `pendingToken`
- 고객사 Backend 권한·업무 규칙과 함께 관리되어야 하는 변수

## 4. 왜 A와 B 중 하나에 모든 State를 넣지 않는가

`authorizedMeetingIds`와 Pending HITL의 존재 여부는 모두 State이지만 소유자가 다르다.

- Tool은 “어떤 회의록을 사용할 수 있는가”와 추가·대체 정합성을 판단한다.
- Runner는 “현재 사용자 입력이 일반 요청인가, 이전 HITL에 대한 응답인가”를 구분한다.
- Worker는 Run claim·lease·timeout과 최종 상태를 관리한다.
- 브라우저는 화면을 표시하고 사용자의 다음 입력을 보낸다.

따라서 권장 구조는 다음과 같다.

```text
브라우저
└─ 비권위적 UI 캐시

Worker/Runner
├─ 현재 Run의 메모리 State
└─ 기존 제품 영속 경계에서 최소 재개 메타데이터 조회

Tool/MCP
└─ Tool 전용 State와 권한·업무 정합성
```

브라우저의 값을 서버 권한으로 승격하지 않고, MCP 내부 업무 상태를 공통 Harness 필드로 복제하지 않는 것이 핵심이다.

## 5. HITL 연결 방식

HITL은 실행 제어와 Tool 업무 판단이 만나는 지점이므로 공개 가능한 최소 정보만 제품 경계로 넘긴다.

```text
Search Tool
→ MCP 내부 후보·기존 상태·권한 확인
→ 사용자 선택이 필요하면 hitl_required 반환
   ├─ 사용자에게 보여줄 질문
   └─ 추측하기 어려운 pendingToken

Runner
→ Pending HITL 식별 정보·Tool 이름·재개 위치·안전한 Snapshot 저장
→ 질문을 UI에 출력하고 현재 Run 종료

후속 사용자 입력으로 새 Run 생성
→ Runner가 Pending HITL 조회
→ 같은 Tool에 사용자 선택·pendingToken·검증된 Scope 전달
→ Tool이 MCP의 최신 상태와 권한을 다시 검사
→ 추가·대체를 수행하거나 같은 HITL을 다시 반환
```

후보 원문, 전체 권한 정보와 Tool 내부 상태는 MCP에 남긴다. 제품 쪽 Pending HITL에는 Tool을 다시 찾는 데 필요한 최소 정보만 저장한다. `pendingToken`은 사용자·Agent·Thread Scope와 만료 시간에 결속하고 한 번만 사용할 수 있어야 한다.

브라우저 저장소에는 이 토큰을 UI 편의를 위해 캐시할 수 있지만 기준값으로 사용하지 않는다.

## 6. 현재 로컬 구현과 향후 MCP 전환

현재 Tool을 `src/lib/meeting-agent/tools/`에 임시로 둘 때도 역할 경계를 먼저 맞춘다.

```text
현재
Local Search·Question Tool
→ Local Meeting State Repository
→ 기존 회의록 Backend와 DB

향후
MCP Tool Proxy
→ 고객사 MCP 서버의 Search·Question Tool
→ 고객사 Meeting State와 Backend
```

- 별도 `services/meeting-agent-state/server.py`를 두지 않는다.
- 안전한 Scratchpad와 최소 HITL 참조는 Agent State Store에 저장한다.
- 사용자 요청 단위의 완료·HITL 대기 경계는 Workflow Checkpoint Store에 저장한다.
- 새 Run은 같은 사용자·Agent·Channel·Thread Scope에서 가장 최근 완료된 Meeting Run의 Checkpoint를 조회한다.
- `authorizedMeetingIds` 등 Tool 전용 변수는 Local Meeting State Repository가 소유하고, MCP 전환 시 서버와 함께 이동한다.
- `recordingModalStatus`는 저장하지 않는다. 실제 녹화 상태는 녹화 Backend가 소유한다.
- Local Tool과 MCP Tool은 같은 결과·HITL·실행 후 정책 계약을 사용한다.

이렇게 하면 현재 별도 Python 서버의 운영 부담을 만들지 않으면서 향후 MCP 이전 경계를 검증할 수 있다.

## 7. Tool 결과와 LLM Context

Tool이 상태를 내부에 저장하더라도 다음 LLM 판단에 필요한 결과는 `output`으로 반환한다.

```ts
type CustomToolExecutionResult = {
  status: "success" | "failed" | "hitl_required";
  output?: unknown;
  hitl?: HitlRequest;
  errorCode?: string;
};
```

- 내부 저장만 필요한 변수는 `output`에 넣지 않는다.
- Search 결과나 Question 근거처럼 LLM이 바로 판단해야 하는 값만 넣는다.
- AI SDK는 결과를 Tool Result Message로 현재 Run의 `messages`에 임시 누적한다.
- `context.ts`는 Tool별 State 저장 방식을 모르고 현재 `messages`와 필요한 Scratchpad만 선별·축약한다.
- 회의록 원문은 현재 Run의 Model Context에서만 사용하고 `message.posted`, Snapshot, Trace와 감사에는 남기지 않는다.

## 8. 최종 비교

| 기준 | A안: 사용자 클라이언트 | B안: MCP 서버 |
|---|---|---|
| 서버 운영 부담 | 낮음 | MCP 상태 운영 필요 |
| 여러 기기·탭·협업 | 충돌·유실 위험 큼 | 서버 기준으로 일관성 유지 가능 |
| 비동기 Worker·재시도 | 최신 상태 접근 어려움 | Worker와 독립적으로 조회 가능 |
| 사용자 변조 방지 | 기준 저장소로 사용 불가 | 인증·권한 경계에서 강제 가능 |
| Harness 범용화 | Tool별 해석 로직이 늘어남 | 공통 결과 계약만 처리 가능 |
| 온프레미스 데이터 경계 | 클라이언트별 분산 | 고객사 서버 안에 유지 |
| 적합한 정보 | UI 캐시·초안 | Tool 전용 업무 상태 |

## 9. 최종 결정

회의록 Agent에는 다음 원칙을 적용한다.

1. A안은 **비권위적 UI 캐시**에만 사용한다.
2. `authorizedMeetingIds`와 Tool별 변수·정합성은 **현재 Local Tool의 Meeting State Repository, 향후 고객사 MCP 서버**가 소유한다.
3. `message.posted`는 대화 저장소, Agent State는 Scratchpad·최소 HITL 참조, Workflow Checkpoint Store는 업무 턴 경계를 사용한다.
4. 별도 `server.py`에 공통 State와 모든 Tool 변수를 함께 저장하지 않는다.
5. Harness는 Tool 내부 State를 해석하지 않고 표준 Tool 결과·HITL·`afterExecution`만 처리한다.
6. 원문과 비밀정보는 클라이언트 State, 제품 State, Snapshot, Trace와 감사 어디에도 저장하지 않는다.

이 결정은 클라이언트 저장소를 중앙 DB로 오해했던 이전 비교를 정정하면서도, `zen-ai`의 비동기 Worker·Thread·온프레미스 MCP 방향과 범용 Harness 목표를 함께 지킨다.
