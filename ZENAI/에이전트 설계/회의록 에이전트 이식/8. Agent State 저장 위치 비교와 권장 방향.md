# Agent State 저장 위치 비교와 권장 방향

이 문서는 [[6. 독립 회의록 Agent 구조 설계]]와 [[7. 독립 회의록 Agent 파일 구조와 내부 로직]]에서 임시안으로 둔 별도 Python State 서버를 다시 검토한다.

비교 대상은 다음 두 가지다.

1. Agent·Web/Worker 측이 상태를 저장하고 Tool 결과를 Harness가 해석하는 방식
2. MCP 서버가 Tool 전용 상태와 업무 정합성을 책임지고 Harness에는 실행 결과만 반환하는 방식

결론부터 말하면 **공통 실행 상태는 Web/Worker 측, Tool 전용 업무 상태는 MCP 서버 측에 두는 분리안**이 가장 적절하다. 이 구조라면 별도 `server.py`를 추가로 운영하지 않으면서도 Harness를 범용 템플릿으로 유지할 수 있다.

## 1. 먼저 구분할 점: 파일 정의와 실제 저장소

`execution-state.ts`, `state-client.ts` 같은 파일을 Web 프로젝트에 둔다고 해서 값이 영속 저장되는 것은 아니다.

- TypeScript 파일: State 형식과 조회·저장 함수를 정의하는 코드
- 메모리 객체: 현재 Run 동안만 사용하는 값
- DB·Redis 등: 다음 Run에서도 값을 복원하기 위한 실제 저장소

따라서 이 문서에서 말하는 **Web/Worker 측 저장**은 브라우저 파일·메모리·Local Storage가 아니라, `zen-ai` 서버가 접근하는 기존 DB나 운영 저장소를 뜻한다. 브라우저는 사용자가 값을 변조할 수 있고 새로고침·다른 기기·동시 실행에 취약하므로 권한이나 HITL의 기준 저장소로 사용하면 안 된다.

## 2. 방식 A: Agent·Web/Worker 측이 모든 상태를 소유

### 흐름

```text
Tool 실행
→ Tool이 상세 data 반환
→ Harness가 data의 의미를 해석
→ Harness가 추가·대체·HITL 여부 판단
→ Web/Worker 측 저장소의 상태 갱신
→ 다음 LLM Context 조립
```

예를 들어 Search Tool이 후보 회의록을 반환하면 Harness가 기존 `authorizedMeetingIds`와 비교해 추가·대체 여부를 판단하고 직접 저장한다.

### 장점

- 모든 Agent State를 한 저장소에서 조회할 수 있다.
- Thread 수명·Checkpoint·HITL을 Worker의 실행 수명과 맞추기 쉽다.
- MCP Tool을 상태가 없는 단순 함수처럼 만들 수 있다.
- 중앙 운영 환경에서는 백업·관찰·장애 대응 지점을 하나로 모으기 쉽다.

### 단점

- Harness가 `authorizedMeetingIds`의 의미와 추가·대체 규칙을 알아야 한다.
- Agent 종류가 늘수록 Harness 또는 Custom 로직에 고객사별 업무 규칙이 계속 추가된다.
- Tool 내부에서 끝낼 수 있는 검증과 상태 변경이 Web 코드까지 왕복한다.
- Tool 실행과 상태 저장 사이에 실패하면 결과와 상태가 어긋날 수 있다.
- 고객사 온프레미스에 남겨야 할 업무 데이터가 중앙 Web 저장소로 이동할 수 있다.
- Tool이 반환하는 상세 데이터가 커지고 LLM Context·Trace·로그에 노출될 위험도 커진다.

### 평가

Agent 한 종류만 만들 때는 단순해 보이지만, **여러 커스텀 로직을 선택·조합하는 서비스**에서는 Harness가 업무 규칙을 계속 떠안게 된다. 현재 프로젝트의 최종 목표와는 잘 맞지 않는다.

## 3. 방식 B: MCP 서버가 Tool 전용 상태를 소유

### 흐름

```text
Harness가 Tool 호출
→ MCP Tool이 자신의 업무 상태 조회
→ MCP Tool이 권한·중복·추가·대체 조건 판단
→ 필요하면 MCP 측 상태를 직접 갱신
→ Harness에는 표준 ToolResult만 반환
→ Harness는 status·output·hitl·afterExecution만 처리
```

Search·Question Tool이 같은 회의록 MCP 서버에 있다면 두 Tool은 MCP 서버 내부의 Meeting Namespace를 함께 사용할 수 있다.

### 장점

- 업무 규칙과 업무 상태가 이를 가장 잘 아는 Tool 가까이에 모인다.
- 상태 조회·권한 검증·갱신을 하나의 서버에서 원자적으로 처리하기 쉽다.
- Harness는 회의록 변수의 의미를 모르므로 범용 템플릿으로 유지된다.
- 고객사별 상태와 데이터가 고객사의 온프레미스 경계 안에 남는다.
- Tool이 LLM에 필요하지 않은 내부 값을 반환하지 않아도 된다.
- 고객사 업무 규칙이 바뀌어도 중앙 Harness를 수정할 가능성이 작아진다.

### 단점

- MCP 서버가 상태 저장·동시성·TTL·백업·복구까지 책임져야 한다.
- Search와 Question처럼 상태를 공유하는 Tool은 같은 업무 저장소를 사용해야 한다.
- MCP 서버를 교체하거나 상태 Schema를 변경할 때 마이그레이션이 필요하다.
- 중앙 Web에서는 Tool 내부 업무 상태를 직접 관찰하기 어려우므로 안전한 상태 조회·운영 API가 필요할 수 있다.
- MCP 서버 장애 시 Tool 실행뿐 아니라 Tool 전용 상태 조회도 함께 불가능해진다.

### 평가

향후 Tool이 고객사 온프레미스 MCP 서버에서 실행되고, Harness를 공통 템플릿으로 제공하려는 방향에는 방식 B가 더 잘 맞는다. 다만 **Agent 실행 자체의 상태까지 전부 MCP 서버에 넘기는 것은 적절하지 않다.**

## 4. 왜 전부 MCP에 두면 안 되는가

다음 정보는 회의록 업무 상태가 아니라 Agent 실행 수명에 속한다.

- `scratchpad`
- `pendingHitl`
- `resumePoint`
- 안전한 실행 Snapshot

이 값들은 Runner가 중단·재개되고 Worker가 Run을 완료하는 과정에 필요하다. 특정 MCP Tool이 아니라 Custom Runner와 Harness가 소유해야 한다.

만약 이를 특정 MCP 서버에 넣으면 다음 문제가 생긴다.

- Tool을 사용하지 않는 Agent도 MCP State 서버에 의존한다.
- 여러 MCP 서버를 조합할 때 어느 서버가 실행 State의 기준인지 모호해진다.
- MCP 서버 장애가 Agent 실행 복구 전체의 장애로 확대된다.
- Worker의 `agent_runs`, Thread, HITL 수명과 MCP 상태 수명을 맞추기 어려워진다.

따라서 MCP 서버에는 **Tool 전용 업무 상태만** 두는 것이 적절하다.

## 5. 권장안: 실행 상태와 업무 상태 분리

| 정보 | 권장 소유자 | 이유 |
|---|---|---|
| 기존 대화 `messages` | `message.posted` 저장소 | 이미 Worker가 `ModelMessage[]`로 복원함 |
| `scratchpad` | Web/Worker 측 공통 State 저장소 | LLM 실행 문맥과 Harness 수명에 속함 |
| `pendingHitl`·`resumePoint`·안전한 Snapshot | Web/Worker 측 공통 State 저장소 | Run 중단·재개를 Runner가 책임짐 |
| `authorizedMeetingIds` | 회의록 Tool/MCP 서버의 Meeting 상태 저장소 | Search·Question의 업무 규칙과 함께 관리해야 함 |
| 실제 녹화 상태 | 녹화 Backend | Agent가 아니라 실제 녹화 기능이 소유함 |
| `afterExecution` | Tool 등록 metadata | Tool별 실행 후 흐름을 Harness 하드코딩 없이 지정함 |
| Trace | Runner/Harness의 Trace Sink | 실행 중 관찰용이며 업무 상태가 아님 |
| Tool 감사 | Custom Runner와 감사 저장소 | Run 종료 경계에서 영속 기록함 |

```text
zen-ai Web/Worker
├─ message.posted
├─ agent_runs
└─ 공통 Custom State
   ├─ scratchpad
   ├─ pendingHitl
   ├─ resumePoint
   └─ 안전한 Snapshot

고객사 MCP 서버
└─ Tool 전용 업무 상태
   └─ authorizedMeetingIds

녹화 Backend
└─ 실제 녹화·Modal 상태
```

이 구조에서 Harness가 아는 것은 다음뿐이다.

```text
Tool을 호출한다
→ status를 확인한다
→ output이 있으면 LLM Context에 넣는다
→ hitl_required면 공통 HITL 처리로 보낸다
→ afterExecution에 따라 LLM 복귀 또는 Run 종료
```

Harness는 `authorizedMeetingIds`의 추가·대체 방식이나 실제 녹화 상태를 알 필요가 없다.

Tool에 전달할 사용자·Agent·Thread Scope는 LLM이 Tool 인자로 만들게 하지 않고 Runner가 검증한 Runtime Context로 주입한다. 또한 저장된 `authorizedMeetingIds`는 사용자가 과거에 선택한 범위일 뿐 현재 권한의 증명이 아니므로, Question Tool은 원문 조회 시 실제 Backend 권한을 다시 검증해야 한다.

## 6. HITL에서는 양쪽 상태가 어떻게 연결되는가

HITL은 실행 제어와 업무 판단이 만나는 지점이므로 양쪽 책임을 나눠야 한다.

```text
Search Tool
→ MCP 내부 상태와 후보를 확인
→ 추가·대체 선택이 필요하다고 판단
→ hitl_required + 공개 가능한 질문 정보 + pendingToken을 hitl 필드로 반환

pending-hitl.ts
→ Tool 이름·pendingToken·resumePoint·안전한 Snapshot 저장
→ 현재 Run 종료

사용자 응답으로 새 Run 생성
→ Runner가 Pending HITL 조회
→ 같은 Tool에 사용자 선택과 pendingToken 전달
→ Tool이 MCP 내부 원본 상태를 다시 확인
→ 권한 재검증 후 추가·대체와 저장을 직접 수행
```

Web/Worker 측에는 재개에 필요한 일반 정보만 저장하고, 후보 원문·권한 상세와 같은 Tool 내부 데이터는 MCP 서버에 남긴다. `pendingToken`은 추측하기 어려운 값이어야 하며 사용자·Agent·Thread Scope, 만료 시간과 한 번만 사용할 수 있는 조건을 MCP 서버가 검증해야 한다.

## 7. 현재 구현 단계의 권장 구조

현재 로컬 `tools/` 단계에서도 별도 `server.py`를 바로 추가하지 않는다.

```text
zen-ai 기존 저장소
├─ messages와 agent_runs: 기존 구조 재사용
└─ Custom State용 최소 저장 영역
   └─ scratchpad·Pending HITL·재개 정보

로컬 회의록 Tool
└─ 기존 제품 DB의 Meeting 전용 영역 또는 Repository 사용
   └─ authorizedMeetingIds
```

- 공통 State는 기존 제품 DB에 최소 테이블 또는 JSON 필드로 저장하는 안을 우선 검토한다.
- `state-client.ts`는 별도 Python 서버 Client가 아니라 이 기존 저장 경계를 감싸는 Adapter가 된다.
- 로컬 Tool은 Meeting 상태 Repository를 직접 호출한다.
- 물리적으로 같은 DB를 사용해도 공통 Custom State와 Meeting 업무 상태의 Schema·접근 코드는 분리한다.
- 별도 서버는 다중 서비스 공유나 독립 확장이 실제로 필요해질 때만 도입한다.

이 방식은 현재 구현량을 줄이면서도 향후 MCP 이전 경계를 보존한다.

## 8. 향후 온프레미스 MCP 전환

```text
현재
Local Tool → Local Meeting Repository

향후
MCP Tool Proxy → 고객사 MCP 서버 → 고객사 Meeting State·Backend
```

이때 바뀌는 것은 Tool 등록·호출 경로와 Meeting 업무 상태의 물리적 위치다. 다음 부분은 유지한다.

- Worker와 Runner의 공통 계약
- `CustomAgentState`의 공통 필드
- Harness의 Tool Loop와 HITL 분기
- `ToolResult` 계약
- `afterExecution` 정책
- 공통 Finalizer

즉 현재부터 Tool이 자신의 업무 상태를 책임지게 설계하면, 향후 MCP 이전 때 Harness를 다시 만들 필요가 없다.

## 9. 최종 권장 결론

두 방식 중 하나를 전체 State에 일괄 적용하지 않는다.

```text
공통 실행 상태
→ zen-ai Web/Worker와 기존 제품 저장소가 소유

Tool 전용 업무 상태
→ 현재는 Local Tool의 Meeting Repository
→ 향후에는 고객사 MCP 서버가 소유
```

따라서 별도 `server.py`는 현재 필수 구성에서 제외하는 방향을 권장한다. 먼저 기존 제품 저장소로 공통 실행 상태를 저장하고, 회의록 전용 상태는 Tool 경계 뒤에 둔다. 별도 State 서비스는 실제 운영상 독립 배포·확장 요구가 확인되었을 때 도입하면 된다.

이 결정이 확정되면 6·7번 문서의 `services/meeting-agent-state/server.py` 우선안과 `state-client.ts` 설명을 기존 제품 저장소 Adapter 기준으로 수정해야 한다.
