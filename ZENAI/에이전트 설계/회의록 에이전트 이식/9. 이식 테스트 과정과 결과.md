# 회의록 Agent 이식 테스트 과정과 결과

기록 기준: 2026-09-12. 기존 9~15번의 검증 기록을 통합했다. 이번 문서 정리는 테스트 재실행이 아니다. 변경 파일별 이유는 [[10. 이식 추가·수정 파일과 근거]]를 따른다.

## 1. 코드 적용·1차 테스트와 후속 검증

사용자 설명에 따르면 기존 9·10번은 전날 직장에서 진행한 코드 적용과 1차 테스트에서 시작됐다. 이후 같은 문서에 후속 최종 결과가 반영됐다. 현재 원문만으로 전날의 실행 명령·통과 수치를 분리할 수 없으므로 추정하지 않는다.

1. 코드 이식과 1차 점검: Builtin Executor 연결, Search 중심 HITL, 세 저장소 분리 및 기존 체크포인트 호환을 확인하는 절차를 정리했다.
2. 후속 자동 검증: 타입·빌드·migration·RLS·단위/통합·전체 테스트를 실행했다. 실제 오류와 환경 문제를 구분해 수정하고 재검사했다.
3. 최종 실행 검증: 최종 의존성과 현재 소스로 Linux 전체 테스트, 실제 개발 서버 HTTP/SSE, Chromium 화면 및 standalone 실행을 확인했다.

지정된 이식 검수 범위의 미해결 항목은 없다. 아래 제외 범위까지 구현·검증 완료했다는 뜻은 아니다.

## 2. 검사 환경과 절차

검증 대상은 @MEETING 라우팅 → Builtin Executor → Engine·Provider·Tool → 공통 Worker → 최종 메시지 흐름이다.

- Agent State: 누적 Scratchpad와 최소 HITL 참조.
- Tool State: 상세 후보 Snapshot, 선택 검증과 authorizedMeetingIds.
- Workflow Checkpoint: 한 Run의 대기·완료·실패·취소 경계.
- 공통 경로: Realtime agent-delta, 최종 message.posted, operation receipt/evidence와 권한 재검증.

원본 .env와 사용자 DB를 보존하고, 별도 PostgreSQL·테스트 계정·접근 가능/불가능한 회의 자료·모의 LLM 서버를 준비했다. 실제 제품 Composer·API·Worker·Realtime·DB 경로를 사용했다.

| 단계 | 방법과 목적 |
| --- | --- |
| 의존성 | lockfile 기준 npm ci, npm audit, npm ls --all로 재설치·보안·버전 충돌 확인 |
| 정적 검사 | npm run check, npm run lint, npm run knip, 포맷 검사 |
| 빌드 | npm run build 및 postbuild 클라이언트 번들 검사 |
| DB | 빈 테스트 DB에 migration/RLS 적용, 테이블·정책·권한·트리거 검사 |
| 회의 runtime | Engine 회귀 및 5개 통합 테스트로 새 저장소 복원과 레거시 호환 검사 |
| 전체 테스트 | 일반 사용자(uid 1000), 격리 Linux와 독립 중첩 Docker로 POSIX·Docker 의존 테스트까지 실행 |
| 소스 대조 | Windows와 Linux의 1,292개 파일을 줄바꿈 정규화 후 비교 |

최종 Linux 전체 실행 명령(당시 격리 Linux 내부 기준):

~~~sh
npm test -- --maxWorkers=2 --hookTimeout=60000 \
  --reporter=default --reporter=json \
  --outputFile.json=/work/completed-tests.json
~~~

## 3. 기능·HTTP/SSE·브라우저 검사

| 시나리오 | 확인한 동작 |
| --- | --- |
| 일반 질문·단일 후보 | Builtin 연결, 자동 선택, Question 결과와 최종 답변 |
| 복수 후보 | Search에서 HITL 생성. 상세 Snapshot은 Tool State, 최소 참조는 Agent State, 경계는 hitl_waiting |
| 무효 선택 99 | 같은 token/Snapshot 유지, 재입력 안내 및 대기 경계 |
| 유효 선택 1 | Snapshot 소비, 선택 목록 갱신, pending=null, 중단 지점 이후 재개 |
| 후속 질문 | 새 저장소에서 복원하고 Scratchpad·선택 회의 연속성 유지 |
| 새 저장소 독립성 | 폐기 가능한 테스트 DB에서만 레거시 체크포인트를 제거해도 재개. 레거시 동기화 검사는 별도 유지 |
| 실패·취소 | 종료 경계 기록과 마지막 정상 Agent State 보존. 취소는 Worker 확정 이후 검사 |
| 빈 검색 | 결과 없음 안내 및 Scratchpad count=0 |
| 권한 철회 | 회의 접근 권한 철회 후 후속 질문 차단·재선택 안내 |
| Recording | 시작 이벤트, 실제 새 회의록 대화상자, 시작·취소 버튼 및 취소 동작 |
| Realtime·메시지 | agent-delta와 meeting-recording-start, 최종 메시지·경계 중복 없음 |
| 민감 정보 | 검사한 State/Checkpoint/evidence/Trace의 원문 미노출 및 민감 Snapshot 노출 경계 |
| 브라우저 | 실제 Composer의 @MEETING 자동완성부터 실행. Console/pageerror/HTTP 오류 0 |

최종 HTTP/SSE는 passed=true, agent-delta 13개, 채널 SSR 200 및 메시지 API 201이었다. 브라우저 첫 9개 Run은 최종 Assistant message.posted와 Workflow Checkpoint가 각각 1개였다.

standalone은 .next/static과 public을 생성물에 복사하고 .next/standalone/server.js로 실행했다. 빈 검색·Recording 및 추가 2개 Run의 메시지/경계 단일성, Console/HTTP 오류 0을 확인했다. 기존 Dockerfile이 같은 구성이므로 수정하지 않았다.

## 4. 중간 문제 → 원인 → 해결·재검증

| 문제 | 원인과 조치 | 재검증 |
| --- | --- | --- |
| 후속 질문 복원 실패 | pendingHitl:null 거부. 정상적인 HITL 없음으로 처리 | Engine·runtime·UI 통과 |
| 실패·취소 경계 누락 | checkpoint=null이면 트리거가 기록 생략. migration 0060 추가 | runtime 5개 통과 |
| Windows 정의 변경 오판·rename EPERM | 메타데이터 비교 차이와 일시적 파일 점유. 비교 항목 및 제한 재시도 수정 | 지원되는 컴파일 시나리오 통과 |
| 포맷 불일치 1,067개 | CRLF 차이. endOfLine:auto 진단에서 5개로 감소 | 실제 포맷만 수정 후 통과. 전역 Git 설정 유지 |
| 테스트 경로·명령 실패 | CRLF, 역슬래시, npx/npm.cmd 차이 | 실행부 호환성 수정 |
| RLS 예상값 불일치 | 새 두 테이블은 처음부터 RLS 강제 | 현재 목록으로 검증 갱신. RLS·권한 완화 없음 |
| Linux 권한·Docker 실패 | root가 쓰기 제한 우회, Docker CLI 부재 | uid 1000·독립 Docker 사용 |
| Docker/WSL 장애 | 디스크 고갈 후 테스트 이미지 node/entrypoint 0바이트 손상 | Docker/WSL 복구, 손상 테스트 이미지 재생성 |
| 컨테이너 준비 지연 | 중첩 Docker vfs의 전체 이미지 복사 | fuse-overlayfs 적용 후 생성 약 1.25초 |
| bootstrap 18개 미실행 | 준비 루프보다 짧은 beforeAll 30초 | 준비 훅만 120초. targeted 18/18 통과(41.39초), 전체 실행에서도 통과 |
| DB 정리 시간 초과 | fsync 12.43초가 훅 10초 초과 | 실행 hookTimeout=60초. DB 내구성·assertion 유지 |
| 타입 검사 실패 | .next/dev/types 중복 후행 코드 | 손상 생성물 보존 후 재생성·통과 |
| 의존성 갱신 실패 | npm 10 edgesOut 내부 오류, 부분 갱신의 peer 충돌 | .context의 별도 npm 11과 호환 버전 정렬 |
| 빈 검색 화면 문구 오류 | 모의 LLM이 빈 선택에도 같은 문구 반환 | fixture 수정 후 새 DB에서 통과. 제품 로직 변경 없음 |

중간 실행에서 bootstrap 18개가 준비 단계 오류로 실행되지 않은 것을 의도적 skip이나 통과로 계산하지 않았다. 모두 실행된 최종 결과로 판정했다. 이전 실패 로그는 해결 근거이지 현재 미해결 목록이 아니다.

Windows의 symlink 보안 fixture 2개는 링크 생성 권한 부족으로 준비 단계에서 EPERM이 났다. Windows 지원 시나리오는 3 통과·2 제외이며 전체 보안 통과로 표현하지 않는다. 실제 링크를 사용하는 원본 보안 검사는 Linux 전체 실행에 포함했다.

실제 외부 LLM 품질·OIDC 제공자 인증·마이크 녹음/저장 완료·AWS 배포는 검증하지 않았다. Recording 성공은 시작 이벤트 전달이지 녹화 완료가 아니다. MCP transport 구현·배포도 범위 밖이다.

검증 후 테스트 브라우저·서버·컨테이너를 종료하고 기존 Redis/MariaDB 실행을 확인했다. 공통 Worker/Builtin/Realtime/operation 구조, 레거시 호환, 사용자 .env와 기존 데이터를 보존했다. 검증 작업에서 staging·commit·push·merge·PR은 하지 않았다.
