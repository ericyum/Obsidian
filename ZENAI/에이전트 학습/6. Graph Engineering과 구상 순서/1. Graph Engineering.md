# Graph Engineering

> **Graph Engineering은 업무를 Node로 나누고, State에 따라 어떤 Edge를 통해 다음 Node로 이동할지 설계하는 방법이다.**

이 문서에서는 단순히 업무 흐름을 그리는 것이 아니라, **상태 머신 관점에서 Node·State·Edge를 명확히 정의하는 Graph**를 다룬다.

## 1. Node·State·Edge의 정의

### 1-1. Node란 무엇인가

일반적으로 Node는 **개발자가 하나로 묶은 워크플로우 단위**이다.

그리고 **상태 머신에 기반한**에서 Node는 다음과 같으며 다음의 정의를 사용한다.

```text
Input + 현재 State
→ Node 내부에서 로직 처리
→ State 갱신
→ Output 반환
```

즉 Node는 **Input을 받고, State를 갱신한 뒤, Output을 반환하는 단위**다.

State 변경과 Output 반환은 동시에 일어나는 하나의 작업이 아니다. **State는 Node 내부 로직에서 먼저 갱신되고, Output은 그 갱신 결과를 반영해 Node 밖으로 반환**된다. State를 어느 시점에 변경할지는 개발자가 정한다.

#### Node를 정의할 때 반드시 정의할 것

- 이 Node가 받는 **Input**은 무엇인가?
- 진입할 때의 **State**는 무엇인가?
- 이 Node는 어떤 **업무**를 처리하는가?
- Node 내부의 어느 지점에서 **State가 어떻게 갱신**되는가?
- State 갱신 후 어떤 **Output**을 반환하는가?

### 1-2. 그럼 State란 무엇인가

Node를 `Input → State 갱신 → Output`으로 정의하면 다음 질문이 자연스럽게 따라온다.

> **그럼 State는 무엇인가?**

State는 **어떤 Edge를 타고 가서 어느 Node로 들어갈 수 있는 지를 정하는 것**이다.

회의록 검색·질문 Agent Graph의 예시를 들어보자.

일단 다음과 같은 node로 나눴다고 가정한다.
```text
사용자 입력 대기 node
회의록 검색 선택 node
회의록 기반 질문 node
```

그럼 사용자 입력 대기 node에서 무엇을 기준으로 회의록 검색 선택 node 또는 회의록 기반 질문 node 중 하나도 가느냐 라는 물음이 생길 수 밖에 없고 State가 해결을 하는 것이다.

그럼 다음과 같이 작성해 볼 수 있다.

```text
State = { none, search, question }
```

- `none`: 사용자 입력을 대기 상태
- `search`: 회의록 검색·선택 상태
- `question`: 회의록 원문 기반 질문 상태

```text
none
├─ 검색이라고 판단 되면 → search
└─ 질문이라고 판단 되면 → question
```

State가 없으면 다음에 어느 Node로 이동해야 하는지를 설명할 기준이 사라진다. **따라서 상태 머신 기반 Node를 설계할 때에는 State에 대한 정의의 반드시 수반된다.**

#### State는 Graph의 스케일을 정한다

**State를 어느 수준으로 나누는 지에 따라 Graph의 각 Node 워크 플로우의 크기와 세밀함이 달라진다.**

예시를 들어보자. 회의록 기반 질문 과정에서의 state는 다음과 같은 상태라고 알고 있다.
```text
최상위 Graph의 state
State = { none, search, question }
```

여기서 개발자가 search(검색) 워크플로우 하나로만 이루어져 있는 것이 아니라 기본적으로 "검색", "검색된 회의록 처리"의 두 워크플로우라고 생각을 했을 경우에는 다음과 같이 될 수도 있는 것이다.
```text
최상위 Graph의 state
State = { none, search, meeting_process, question }
```

정말 극단적으로 다음 처럼 개발자가 처음 부터 끝까지의 모든 세밀한 분기점 하나하나를 구분하고자 한다면 다음 처럼 그래프가 그려질 수도 있는 것이다.
```text
최상위 Graph의 state
State = {
  none, 
  searching,
  no_candidates,
  one_candidate,
  multiple_candidates,
  response_ready,
  question,
  answer
}
```
실제 상황에서 최상위 Graph가 이렇게 그려질 가능성을 거의 없지만, 이럴 경우에는 이 Graph하나는 정말 많은 Node들이 이어져 있는 매우 방대하고 세밀한 구조가 될 것이다.
#### Graph들의 스케일 조절 방법: SubGraph

하지만 우리 입장에서 처음 부터 너무 세밀한 그래프를 읽으면 너무 가독성이 떨어지고 이해하기 힘들다. 따라서 권장되는 형태는 다음과 같다.

1. 일단 직관적인 업무 단위 별로 나눠서 Node, State를 정의한 그래프를 그린다.
2. 필요할 경우에 한해서 각각의 Node안의 워크플로우를 나누고 다시 한번 Node, State를 정의한 그래프를 그린다.

회의록 검색 Node에 대해서 여러 업무 워크 플로우가 나뉜 다고 판단이 되면 내부 그래프를 그릴 수 있고 그에 따라 다음과 같이 내부 State가 작성될 수 있는 것이다.
```text
최상위 Graph의 state
State = { none, search, question }

Search Subgraph
State = {
  searching,
  no_candidates,
  one_candidate,
  multiple_candidates,
  response_ready
}
```
상위 Graph에서는 `search` State일 때 검색 Node로 향하는 구조이지만,
Subgraph로 펼치면 더 세밀한 내부 Node와 State로 나뉜다.

이런 식으로 상단에서 정의한 Node 내부의 또 다른 Graph를 두고 **SubGraph**라고 한다.

**한 줄 요약**
> **개발자가 워크플로우를 개념적으로 잘 나눠서 상단 Graph를 만들고, 필요에 따라 SubGraph로 나눠서 작성하여 가독성이 있게 한다.**

### 1-3. Edge란 무엇인가

그래프 이론: **Node와 Node를 연결하는 선**
상태 머신에서: **갱신된 State에 따라 다음 Node로 이동하는 경로**다.

```text
Node A
→ [Node 내부] State = search로 갱신
→ Output 반환
→ 갱신된 State를 보고 search Edge 선택
→ Node B
```

Edge는 두 종류로 나눌 수 있다.

- **고정 Edge**: 다음 Node가 하나로 정해져 있다.
- **조건부 Edge**: Node 내부에서 갱신된 State나 반환된 판단 결과에 따라 다음 Node가 달라진다.

```text
searching
├─ no_candidates       → 결과 없음 응답 Node
├─ one_candidate       → 단일 후보 선택 Node
└─ multiple_candidates → HITL 선택 Node
```

#### 우리 팀의 원칙: Edge는 코드로 확정한다

설계를 하가 보면 LLM의 판단에 맡기는 경우들이 있다. 하지만 **LLM은 Node 내부에서 사용자 의도를 판단하고 정해진 형태의 결과를 반환하는 역할**까지만 담당한다. 그 결과에 따라 **어느 Edge로 확정하고 다음에 어떤 Node를 실행할지는 오케스트레이터의 고정 코드가 확정**한다.

예를 들어 사용자 요청이 검색인지 질문인지 구분하는 경우에는 다음과 같이 동작한다.

```text
[사용자 의도 판단 Node]
LLM이 검색 또는 질문이라는 판단 결과를 반환
→ Node 내부에서 State를 search 또는 question으로 갱신
→ Output 반환

[오케스트레이터의 Edge 선택]
State가 search이면  → 회의록 검색·선택 Node
State가 question이면 → 회의록 기반 질문 Node
```

이때 `if`문은 구현 방법의 한 가지 예시일 뿐이다. 핵심은 **LLM이 다음 Node를 임의로 직접 실행하는 것이 아니라, 개발자가 코드로 정의한 Edge 규칙이 LLM의 판단 결과를 받아 다음 Node를 선택하도록 하여 LLM에 의존하지 않도록 하는 것이다.**
