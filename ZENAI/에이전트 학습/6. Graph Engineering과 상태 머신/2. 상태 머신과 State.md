# 상태 머신과 State

> **상태 머신은 시스템의 현재 State에 따라 지금 할 수 있는 행동과 다음 State를 구분하는 구조다.**

이 문서에서는 상태 머신 전체를 다루지 않고, **Graph Engineering이 적용된 Graph와 Subgraph를 그릴 때 사용하는 State**만 설명한다.

## 1. State란 무엇인가

> **State는 현재 Graph가 어느 실행 단계에 있는지를 나타내는 상태다.**

각 Graph는 자신에게 필요한 State를 유한한 집합으로 정의할 수 있다.

```text
최상위 Graph의 State
none / recording / search / question
```

현재 State와 입력에 따라 실행할 Node가 달라지고, Node의 처리가 끝나면 다음 State로 바뀐다.

## 2. State가 변경되는 기본 구조

```text
입력 State + 입력
→ Node 실행
→ 출력 발생
→ 출력 State로 변경
→ Edge를 따라 다음 Node 실행
```

예를 들면 다음과 같다.

```text
none에서 “관련 회의록을 찾아줘”라고 요청
→ LLM 요청 판단 Node 실행
→ 출력 State: search
→ 검색 Node 실행
→ 출력 State: none
```

Graph에는 **Node에 들어오기 전 State와 Node 실행 후 State**가 구분되어야 한다.

## 3. Graph 계층마다 State가 따로 존재할 수 있다

최상위 Graph에서는 회의 녹화 전체를 하나의 State로 볼 수 있다.

```text
최상위 Graph
none → recording → none
```

그러나 `recording`에 해당하는 Node를 Subgraph로 펼치면 내부에는 더 세밀한 State가 생길 수 있다.

```text
회의 녹화 Subgraph
ready → recording ↔ paused → stopping → completed
```

이때 같은 실행 순간을 다음처럼 함께 표현할 수 있다.

```text
최상위 Graph의 State: recording
회의 녹화 Subgraph의 State: paused
```

상위 State는 큰 업무 단계이고, 내부 State는 그 업무 안의 세부 실행 단계다.

## 4. State를 나누는 범위는 설계 관점에 따라 달라진다

개발자가 **어디부터 어디까지를 하나의 업무 단위로 묶는지**에 따라 Node와 State의 범위가 달라진다.

다음 질문으로 별도 State가 필요한지 판단할 수 있다.

> **이 상태가 달라지면 다음에 실행할 Node가 달라지는가?**

- 달라진다 → 별도 State로 구분할 수 있다.
- 달라지지 않고 ID·횟수·문구 같은 값만 다르다 → State가 아니라 일반 데이터다.

```text
State
none / search / question

일반 데이터
messages / meeting_id / authorized_meeting_ids
```

State와 Node의 구분은 관점에 따라 달라질 수 있지만 완전히 임의적인 것은 아니다. 경로 분기, 재시도, Human in the Loop, Checkpoint처럼 **독립적으로 제어해야 하는 경계**가 중요한 기준이다.

## 5. 주의: 코드의 `State = {}`와 구분한다

에이전트 코드에서는 다음과 같은 데이터 객체를 `State`라고 부르기도 한다.

```text
State = {
  messages: [...],
  recording_state: "recording",
  authorized_meeting_ids: [...]
}
```

하지만 이 `State = {}`는 `messages`를 비롯한 여러 값을 Node 사이에서 전달하기 위한 **데이터 창고**다. 이 문서에서 말하는 유한한 실행 단계인 State와는 별개의 개념이므로 혼동하지 않는다.

다만 `recording_state`처럼 데이터 창고 안의 특정 변수가 `none`, `recording`, `paused`를 가진다면, 그 변수는 Graph의 State를 코드로 직접 구현한 값이 될 수 있다.

## 6. State를 표현하는 두 가지 방법

### 6-1. 코드에 직접 구현

State를 실제 변수로 저장하고 변경한다.

```text
recording_state = "recording"
```

권한 검사나 이후 요청 처리에서 현재 상태를 계속 확인해야 할 때 사용할 수 있다.

### 6-2. Graph에만 명시

별도 State 변수를 만들지 않고 **현재 실행 중인 Node와 이동 경로로 State를 표현**한다.

```text
none
→ 사용자 입력과 LLM 판단
→ search 또는 question
→ 해당 Node 실행
→ none
```

이 경우 Graph에는 `search`, `question` State가 있지만 실제 코드에는 `state = "search"`, `state = "question"` 같은 변수가 없을 수 있다. 현재 실행 중인 Node가 그 State를 대신 나타낸다.

검색·질문처럼 한 요청 안에서 잠깐 거쳐 가는 단계는 이 방식으로 표현할 수 있다.

## 7. State 전이도와 내부 순서도

Graph와 Subgraph 안에는 조건과 세부 State가 다시 생길 수 있다. 이를 자세히 나타낼 때는 목적에 따라 두 그림을 구분한다.

- **State 전이도**: State의 변화만 보여준다.
- **내부 순서도**: Node 내부의 처리 순서와 조건을 보여준다.

```text
State 전이도
recording → paused

내부 순서도
일시정지 요청 → 상태 검사 → 백엔드 실행 → 성공 여부 판단 → 결과 반환
```

내부 순서도에도 State 확인과 변경이 표시될 수 있지만, 순서도 자체가 State 전이도와 같은 것은 아니다.

## 8. Node·Edge와 State의 관계

- **State**: 현재 Graph 계층의 실행 단계
- **Node**: 현재 State에서 수행하는 작업 단위
- **Edge**: 출력 State에 따라 다음 Node로 이어지는 경로

```text
입력 State
→ Node
→ 출력 State
→ Edge
→ 다음 Node
```

## 9. 한 문장으로 정리

> **State는 각 Graph 계층의 현재 실행 단계를 나타내며, 상위 Graph와 내부 Subgraph는 각각 자신의 State를 가질 수 있다. State는 코드 변수로 구현할 수도 있고 현재 Node와 Edge로만 표현할 수도 있다.**
