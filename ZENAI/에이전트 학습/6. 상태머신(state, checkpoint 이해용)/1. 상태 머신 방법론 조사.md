# 상태 머신 방법론 조사

> 조사 목적: 특정 회의록 에이전트의 State 이름을 설명하는 데 그치지 않고, 새로운 시스템과 Agent 워크플로우를 설계할 때 State·Transition·Checkpoint를 어떤 기준으로 나눌지 판단할 수 있는 이론적·실무적 기준을 정리한다.  
> 문서 범위: 유한 상태 머신, 전이 시스템, 확장 상태 머신, Statechart, 병렬·분산 상태, 불변조건과 모델 검증, State 영속화와 Checkpoint·복구를 다룬다.  
> 문서 성격: 특정 프레임워크의 사용법이나 현재 회의록 에이전트의 확정 구현안이 아니라, 여러 Agent와 장기 실행 워크플로우에 재사용할 설계 방법론 조사 문서다.

## 1. 조사 질문

상태 머신을 설계할 때의 핵심 질문은 단순히 “State 이름을 무엇으로 정할 것인가?”가 아니다.

1. State란 정확히 무엇이며 일반 데이터와 어떻게 다른가?
2. 어떤 차이를 별도 State로 만들고, 어떤 차이는 State 내부 데이터로 남겨야 하는가?
3. Event, Command, Guard, Action과 Transition은 각각 어떤 역할을 가져야 하는가?
4. Flat FSM, 확장 상태 머신과 계층형 Statechart는 언제 선택하는가?
5. 병렬 업무는 상태 조합으로 표현할지, 독립된 상태 머신으로 나눌지 어떻게 결정하는가?
6. 도달 불가능 상태, 불법 전이, 교착, 무한 반복과 상태 폭발을 어떻게 발견하는가?
7. Checkpoint는 State와 무엇이 다르며 어느 경계에 저장해야 하는가?
8. 외부 API 호출이나 결제처럼 되돌리기 어려운 Side Effect가 있을 때 복구와 재실행을 어떻게 설계하는가?
9. 여러 서버와 Agent가 동시에 움직일 때 일관된 State를 어떻게 정의하는가?
10. 새로운 워크플로우를 받았을 때 상태 머신 설계안을 만드는 반복 가능한 절차는 무엇인가?

## 2. 핵심 결론

### 결론 1. State는 과거 전체가 아니라 미래를 결정하기 위한 충분한 요약이다

State는 시스템이 지금까지 겪은 모든 이벤트의 원문이 아니다. **앞으로 어떤 입력을 허용하고, 어떤 결과를 만들며, 어디로 이동할 수 있는지를 결정하는 데 필요한 과거의 최소 요약**이다.

```text
같은 입력을 받았을 때
허용 여부·다음 전이·출력·불변조건이 달라진다
→ 별도 State로 나눌 근거가 있음

같은 입력에 대해 행동은 같고 표시용 값만 다르다
→ 별도 State보다 State Data일 가능성이 큼
```

### 결론 2. State 이름보다 전이 계약이 먼저다

상태 머신의 본체는 상태 목록이 아니라 다음 전이 관계다.

```text
현재 State
+ Event 또는 Command
+ Guard
→ Action·Side Effect
→ 성공 또는 실패 Event
→ 다음 State
```

State 이름만 나열하면 설계가 완성되지 않는다. 각 전이의 Trigger, 조건, 성공 기준, 실패 처리와 멱등성까지 정의해야 한다.

### 결론 3. State와 Checkpoint는 같은 것이 아니다

- **State**: 현재 시스템의 논리적 조건과 다음 행동을 결정하는 값
- **Checkpoint**: 특정 실행 시점의 State와 재개 정보를 영속적으로 저장한 복구 기준점

State는 상태 머신 이론의 핵심 구성 요소다. Checkpoint는 상태 머신을 장애 이후에도 이어 실행하거나, Human in the Loop에서 중단·재개하기 위한 런타임·영속화 개념이다.

### 결론 4. Checkpoint를 저장했다고 외부 Side Effect가 되돌아가는 것은 아니다

이메일 전송, 결제, 파일 쓰기와 외부 API 호출은 Checkpoint를 과거로 돌린다고 취소되지 않는다. 재실행 가능성이 있는 모든 Side Effect에는 멱등성 키, 실행 결과 기록, 실제 상태 조회 또는 보상 동작이 필요하다.

### 결론 5. 복잡한 시스템은 하나의 거대한 State 값으로 표현하지 않는다

서로 독립적으로 변하는 축을 하나의 열거형 State로 모두 조합하면 상태 폭발이 발생한다.

```text
recording_status 4개
approval_status 3개
sharing_status 3개

단일 조합 State로 만들면 최대 4 × 3 × 3 = 36개
```

독립적인 축은 직교 Region이나 별도 상태 머신으로 분리하고, 필요한 동기화 지점만 명시한다.

### 결론 6. 상태 머신의 품질은 그림보다 검증 가능한 속성으로 판단한다

다음 질문에 답할 수 있어야 한다.

- 어떤 상태도 권한 없이 위험한 Action을 실행하지 않는가? — Safety
- 시작한 업무가 성공·실패·취소 중 하나로 끝날 수 있는가? — Liveness·Termination
- 모든 State에 실제 진입 경로가 있는가? — Reachability
- 어떤 State에서 아무 Event도 처리하지 못한 채 멈추는가? — Deadlock
- 상태만 반복하고 진전하지 않는 경로가 있는가? — Livelock
- 재시작 후 같은 이벤트를 다시 처리해도 결과가 중복되지 않는가? — Recovery·Idempotency

## 3. 상태 머신이란 무엇인가

MIT 강의 자료는 상태 머신을 단계적으로 진행되는 과정을 나타내는 추상 모델로 설명한다. 상태 머신은 현재 State와 입력을 받아 다음 State로 이동하며, 필요하면 출력을 만든다.

가장 단순한 결정적 상태 머신은 다음 요소로 표현할 수 있다.

```text
M = (S, I, O, δ, λ, s₀)

S   : 가능한 State 집합
I   : 입력 또는 Event 집합
O   : 출력 집합
δ   : 다음 State 함수, δ(State, Input) → Next State
λ   : 출력 함수
s₀  : 초기 State
```

워크플로우 관점에서는 다음 표기가 더 실용적이다.

```text
Transition:
(현재 State, Event, Guard)
→ (다음 State, Action, Output)
```

상태 머신은 “시스템이 무엇을 저장하는가”와 “그 저장된 조건에 따라 어떤 행동 차이가 생기는가”를 명시적으로 만든다.

- [MIT 6.005 — Designing State Machines](https://www.ocw.mit.edu/courses/6-005-elements-of-software-construction-fall-2008/resources/mit6_005f08_lec04/)
- [MIT 6.390 — State Machines](https://introml.mit.edu/_static/fall22/LectureNotes/6_390_lecture_notes_fall2022.pdf)

## 4. State의 정확한 의미

### 4-1. State는 시스템의 현재 조건이다

State는 특정 시점의 시스템이 어떤 조건에 있으며, 그 조건 때문에 앞으로의 반응이 어떻게 달라지는지를 나타낸다.

예를 들어 문서 승인 시스템에서 같은 `승인 요청` Command를 받아도 다음처럼 행동이 달라진다.

| 현재 State | `승인 요청`에 대한 행동 |
|---|---|
| `draft` | 검토 단계로 이동 가능 |
| `in_review` | 중복 요청으로 거부 또는 현재 상태 반환 |
| `approved` | 이미 승인되었다고 반환 |
| `rejected` | 수정 후 재요청 절차 필요 |

이처럼 미래 행동이 달라지므로 `draft`, `in_review`, `approved`, `rejected`는 State로 분리할 가치가 있다.

### 4-2. State는 과거의 충분한 요약이다

State가 필요한 이유는 미래 반응이 과거에 의존하기 때문이다. 하지만 미래를 결정하는 데 과거 전체가 필요한 것은 아니다.

```text
과거 Event 전체
DraftCreated
TitleChanged
ReviewerAssigned
ReviewRequested

현재 State 요약
workflow_state = in_review
reviewer_id = user-7
document_version = 4
```

현재 전이를 결정하는 데 충분하다면 이벤트 원문 네 개를 매번 읽지 않아도 된다. 반대로 법적 감사나 과거 State 재구성이 필요하면 Event Log는 별도로 보존할 수 있다.

### 4-3. Control State와 Extended State Data를 구분한다

실무 상태 머신은 보통 두 층으로 이루어진다.

| 구분 | 의미 | 예시 |
|---|---|---|
| Control State | 현재 행동 모드·단계 | `draft`, `review`, `approved` |
| Extended State Data | 전이 판단에 필요한 데이터 | `review_count`, `owner_id`, `deadline` |

모든 데이터 조합을 State 이름으로 만들면 State가 폭발한다.

```text
나쁜 예
review_with_owner_before_deadline
review_with_owner_after_deadline
review_without_owner_before_deadline
...

권장 예
workflow_state = review
owner_id = ...
deadline = ...
```

Guard가 `owner_id`와 `deadline`을 읽어 전이를 결정한다.

### 4-4. State와 단순 표시값을 구분하는 질문

다음 중 하나라도 참이면 별도 State 또는 State Data로 관리할 가능성이 높다.

- 허용되는 Event·Command가 달라지는가?
- 같은 Event에 대한 다음 State가 달라지는가?
- 실행해야 하는 Side Effect가 달라지는가?
- 유지해야 하는 불변조건이 달라지는가?
- Timeout, Retry 또는 권한 정책이 달라지는가?
- 장애 복구 시 반드시 구분해야 하는가?
- 운영자가 현재 업무 진행 상황을 이 값으로 판단해야 하는가?

어느 것도 달라지지 않고 UI 문구만 다르면 별도 State가 아닐 수 있다.

## 5. 상태 머신의 기본 구성 요소

### 5-1. State

시스템이 현재 머무르는 안정된 조건이다. State에 진입한 뒤 다음 Event를 기다릴 수 있어야 한다.

상태 이름은 가능하면 명사·형용사형의 안정된 조건으로 적는다.

```text
권장: pending, recording, paused, approved
주의: startMeeting, sendEmail, searchDocument
```

`sendEmail`처럼 순간적으로 실행되는 일은 State보다 Action인 경우가 많다. 다만 외부 실행이 오래 걸리고 재시작 시 진행 여부를 구분해야 한다면 `email_sending`을 State로 승격할 수 있다.

### 5-2. Event

이미 발생한 사실이다. Event는 과거형으로 표현하면 Command와 구분하기 쉽다.

```text
MeetingStartRequested  — 요청이 들어옴
MeetingStarted         — 실제 시작이 성공함
MeetingStartFailed     — 시작이 실패함
```

Microsoft의 Domain Event 가이드도 Event를 이미 발생한 사실로 보고 과거형 이름을 권장한다.

- [Microsoft — Domain events: design and implementation](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation)

### 5-3. Command

어떤 주체가 시스템에 실행을 요구하는 의도다. Command는 거부되거나 실패할 수 있다.

```text
StartMeeting
PauseRecording
ApproveDocument
ChargePayment
```

Command를 받았다는 사실과 Command가 성공했다는 사실을 같은 것으로 취급하면 안 된다.

```text
PauseRecording Command 수신
≠ 실제 녹화 일시정지 성공

PauseRecording 처리 성공
→ RecordingPaused Event
→ State를 pause로 변경
```

### 5-4. Trigger

Transition 평가를 시작하게 하는 원인이다. 사용자 입력, Timer, 외부 Event, 내부 완료 Event 등이 될 수 있다.

```text
사용자 버튼 클릭
메시지 수신
백엔드 성공 Event
Timeout 발생
하위 State 완료 Event
```

Trigger는 성공을 뜻하지 않는다. Trigger 이후 Guard와 실제 실행 결과를 확인해야 한다.

### 5-5. Guard

Transition을 허용할지 판단하는 Boolean 조건이다.

```text
event = SubmitForReview
guard = document.owner_id == actor.id
        and document.has_required_fields
```

좋은 Guard는 다음 성질을 가져야 한다.

- 같은 입력과 State에는 같은 결과를 내는 순수한 판정에 가깝다.
- Side Effect를 실행하지 않는다.
- 권한·현재 State·리소스 조건을 명시적으로 검사한다.
- 거부 시 구조화된 이유를 반환할 수 있다.

### 5-6. Action·Effect

Transition을 수행하며 발생하는 계산이나 Side Effect다.

- State Data 갱신
- DB 쓰기
- 외부 API 호출
- Event 발행
- 사용자 알림

외부 Side Effect는 실패할 수 있으므로 “전이와 완전히 같은 순간에 성공한다”고 가정해서는 안 된다. 실행 전·후 State, 성공 Event와 재시도 정책을 설계해야 한다.

### 5-7. Transition

현재 State에서 Event와 Guard를 평가해 Action을 실행하고 다음 State로 이동하는 규칙이다.

```text
draft
-- SubmitForReview [필수 항목 충족] / 검토 요청 생성 -->
in_review
```

W3C SCXML도 Transition이 Event에 의해 Trigger되고 Guard 조건으로 제한되며 실행 내용을 포함할 수 있다고 정의한다.

- [W3C — State Chart XML 1.0](https://www.w3.org/TR/scxml/)

### 5-8. Initial·Final·Error·Cancelled State

- **Initial**: 상태 머신 실행이 시작되는 진입점
- **Final**: 해당 상태 머신이나 복합 State가 정상 완료됨
- **Error**: 자동 진행이 중단된 실패 상태
- **Cancelled**: 사용자나 외부 정책에 의해 의도적으로 중단됨

`finish` 하나에 성공·실패·취소를 모두 섞으면 후속 처리와 운영 지표가 모호해진다. 업무상 행동이 다르면 `completed`, `failed`, `cancelled`처럼 분리한다.

## 6. 상태 머신의 주요 종류

### 6-1. 전이 시스템 Transition System

가장 일반적인 형태는 State 집합과 전이 관계로 시스템의 가능한 실행을 표현하는 것이다.

```text
TS = (S, S₀, A, →)

S   : State 집합
S₀  : 초기 State 집합
A   : Action 또는 Event Label
→   : State 사이의 전이 관계
```

전이 함수가 아니라 관계를 사용하면 같은 State·입력에서 여러 다음 State가 가능한 비결정적 시스템도 표현할 수 있다.

### 6-2. DFA와 NFA

고전적 유한 오토마타는 입력 문자열을 받아 Accept·Reject를 판단한다.

- **DFA**: 각 State와 입력에 다음 State가 정확히 하나
- **NFA**: 하나의 State와 입력에서 여러 전이가 가능하거나 전이가 없을 수 있음

워크플로우 설계에서는 보통 실행 결과가 재현 가능해야 하므로 Guard 우선순위와 Event 처리 규칙을 통해 관찰 가능한 동작을 결정적으로 만드는 것이 유리하다.

- [Stanford CS143 — Deterministic and Nondeterministic Automata](https://web.stanford.edu/class/cs143/lectures/lecture04.pdf)

### 6-3. Moore와 Mealy Machine

출력을 어디에 연결하는지에 따른 구분이다.

| 방식 | 출력 결정 기준 | 워크플로우 해석 |
|---|---|---|
| Moore | 현재 State | `approved` State이면 승인 완료 표시 |
| Mealy | 현재 State + 입력 | `review`에서 `Approve` Event를 받을 때 승인 알림 출력 |

실제 Agent 워크플로우는 State에 따른 UI 표시와 Transition에 따른 Tool 결과를 모두 사용하므로 두 관점이 섞인 확장 상태 머신에 가깝다.

- [MIT — Finite State Machines, Moore and Mealy Machines](https://people.csail.mit.edu/devadas/6.004/Lectures/lect6/)

### 6-4. Extended Finite State Machine

Control State 외에 변수, Guard와 Action을 사용하는 형태다. 업무 시스템과 Agent Graph 대부분은 이 유형에 해당한다.

```text
Control State: in_review
Data: review_count=2, deadline=..., owner_id=...
Guard: review_count < 3 and now < deadline
Action: review_count += 1
```

장점은 State 수를 줄일 수 있다는 점이다. 단점은 실제 가능한 전체 상태 공간이 변수 조합 속에 숨어 다이어그램만으로는 완전성을 확인하기 어렵다는 점이다.

### 6-5. Statechart와 UML State Machine

Harel의 Statechart는 복잡한 반응형 시스템에서 Flat FSM의 상태 폭발을 줄이기 위해 계층, 직교 병렬 영역과 상태 History를 도입했다. 이후 UML State Machine과 W3C SCXML에 큰 영향을 주었다.

- **계층**: 여러 하위 State의 공통 전이를 상위 State에 정의
- **직교 Region**: 서로 독립적인 여러 상태 축을 동시에 활성화
- **History**: 복합 State를 나갔다가 이전 하위 State로 복귀

- [David Harel — Statecharts: A Visual Formalism for Complex Systems](https://www.sciencedirect.com/science/article/pii/0167642387900359)
- [OMG — Unified Modeling Language Specification](https://www.omg.org/spec/UML/2.5)
- [W3C — SCXML](https://www.w3.org/TR/scxml/)

### 6-6. Workflow State Machine

업무 단계를 장기간 실행하고 외부 Task, Wait, Choice, Parallel, Success와 Failure를 조합하는 형태다. AWS Step Functions도 Workflow를 State Machine으로 정의하고 Task·Choice·Wait·Parallel·Map·Succeed·Fail 같은 State 유형을 제공한다.

- [AWS — What is Step Functions?](https://docs.aws.amazon.com/step-functions/latest/dg/welcome.html)

### 6-7. Replicated State Machine

여러 서버 복제본이 같은 초기 State에서 같은 Command를 같은 순서로 결정적으로 적용하면 같은 State와 출력을 유지할 수 있다. Raft 같은 합의 알고리즘은 복제된 로그 순서를 합의하고 각 복제본이 Commit된 Command를 로컬 상태 머신에 적용하게 한다.

- [Ongaro and Ousterhout — In Search of an Understandable Consensus Algorithm](https://raft.github.io/raft.pdf)
- [Stanford — The Raft Consensus Algorithm](https://web.stanford.edu/~ouster/cgi-bin/cs190-winter19/lecture.php?topic=raft)

## 7. 실행 의미론을 먼저 정해야 한다

상태도 모양이 같아도 Event 처리 순서와 전이 우선순위가 다르면 실제 동작은 달라진다.

### 7-1. Enabled Transition

일반적으로 다음 조건을 모두 만족할 때 Transition이 활성화된다.

```text
현재 활성 State에 해당 Transition이 존재
and Event가 Trigger와 일치
and Guard가 true
```

### 7-2. 같은 Event에 여러 Transition이 활성화될 때

다음 중 하나를 명시해야 한다.

- 우선순위가 높은 Transition 선택
- 문서 순서로 선택
- Guard가 상호 배타적이어야 한다고 강제
- 여러 Transition을 병렬 실행
- 설계 오류로 거부

비결정성을 의도하지 않았다면 Guard가 겹치지 않는지 검증해야 한다.

### 7-3. Run-to-Completion

W3C SCXML은 하나의 외부 Event 처리가 시작되면 그 Event가 만든 내부 전이와 후속 Microstep을 끝낸 뒤 다음 외부 Event를 처리하는 Run-to-Completion 의미론을 정의한다.

```text
외부 Event A 수신
→ Guard 평가
→ Transition과 Action
→ 내부 완료 Event 처리
→ 안정된 State Configuration 도달
→ 그다음 외부 Event B 처리
```

이 원칙은 중간 State가 다른 Event에 노출되어 Race Condition이 생기는 것을 줄인다. 다만 긴 외부 API 호출 전체를 하나의 잠금 구간으로 묶으라는 뜻은 아니다. 외부 작업 요청과 완료 Event 사이를 명시적인 대기 State로 모델링할 수 있다.

- [W3C SCXML — Selecting and Executing Transitions](https://www.w3.org/TR/scxml/#SelectingTransitions)

### 7-4. 처리할 수 없는 Event 정책

State마다 예상하지 못한 Event가 들어왔을 때의 정책을 정한다.

| 정책 | 적합한 상황 |
|---|---|
| 거부하고 이유 반환 | 사용자 Command, 권한·업무 State 위반 |
| 무시 | 중복된 표시용 Event, 명확히 무해한 Event |
| 지연·보류 | 상위 State를 나간 뒤 처리해야 하는 Event |
| Dead-letter 저장 | 비동기 메시지 처리 실패 분석 |
| Error State 전이 | 시스템 불변조건이 깨졌거나 수동 복구 필요 |

침묵하고 무시하는 정책은 운영자가 문제를 발견하기 어렵게 만들 수 있으므로 의도적으로 제한한다.

## 8. State를 나누는 실전 기준

### 기준 1. 미래 행동이 다르면 State를 나눈다

두 조건에서 허용 Command, Guard, Action, Timeout이나 종료 방식이 다르면 별도 State가 필요할 가능성이 높다.

### 기준 2. 업무적으로 관찰 가능한 안정된 단계인가

사용자나 운영자가 “현재 무엇을 기다리고 있는가?”라고 물었을 때 의미 있는 답이 되는가?

```text
waiting_for_user_approval
waiting_for_payment
paused
```

### 기준 3. 장애 복구 시 반드시 구분해야 하는가

재시작했을 때 외부 작업을 다시 실행할지, 결과만 조회할지 결정하려면 실행 전·후를 구분해야 한다.

```text
payment_pending
payment_requested
payment_confirmed
payment_unknown
```

### 기준 4. 불변조건이 달라지는가

```text
approved State 불변조건
→ approved_by가 반드시 존재
→ approved_at이 반드시 존재
→ 문서 내용 변경 금지
```

불변조건 집합이 달라지면 별도 State로 표현할 가치가 있다.

### 기준 5. 독립적으로 변하는 축인가

업무 단계와 연결 상태처럼 독립적으로 변하면 하나의 Enum에 합치지 않는다.

```text
workflow_state = in_review
connection_state = disconnected
```

두 축의 동기화가 필요할 때만 Guard나 Event를 정의한다.

### 기준 6. 단순 파생값인가

다른 신뢰된 필드에서 항상 계산할 수 있고 별도의 전이 의미가 없다면 저장 State로 중복 보관하지 않는다.

```text
is_finished = workflow_state in {completed, failed, cancelled}
```

`is_finished`를 별도 저장하면 `workflow_state=running, is_finished=true` 같은 모순이 생길 수 있다.

### 상태 구분 판정표

| 질문 | 예 | 설계 방향 |
|---|---|---|
| 허용 행동이 달라지는가? | pause에서만 resume 가능 | State 분리 |
| 단지 수치만 달라지는가? | retry_count 1·2·3 | Data 필드 |
| 독립 축인가? | 녹화 상태와 UI 연결 상태 | 별도 머신·Region |
| 순간 작업인가? | 알림 전송 | Action 우선 검토 |
| 오래 기다리는가? | 사용자 승인 대기 | Waiting State |
| 복구 판단에 필요한가? | 외부 결제 결과 미확인 | 별도 상태 필요 |

## 9. State 수를 줄이는 원칙

### 9-1. Boolean Flag 조합을 경계한다

```text
is_started
is_paused
is_stopped
is_shared
```

네 Boolean은 이론상 16개 조합을 만들지만 대부분은 불법이다.

```text
is_paused=true
is_stopped=true
is_started=false
```

서로 배타적인 단계라면 하나의 Enum State가 더 안전하다.

### 9-2. 행동적으로 동등한 State는 합친다

두 State가 모든 Event에 대해 같은 출력과 다음 행동을 가진다면 구분할 이유가 없는지 검토한다. 고전 FSM에서는 이러한 행동적 동등성을 이용해 State를 최소화한다.

### 9-3. 파생 상태를 중복 저장하지 않는다

원본 State에서 결정적으로 계산할 수 있는 값은 Projection으로 만든다.

### 9-4. 계층으로 공통 전이를 끌어올린다

```text
Active
├→ Recording
└→ Paused

Active -- Cancel --> Cancelled
```

`Recording`과 `Paused`에 동일한 Cancel 전이를 반복하지 않고 상위 `Active`에 둔다.

### 9-5. 독립 상태 축을 직교 Region으로 분리한다

W3C SCXML의 Parallel State에서는 여러 Child State가 동시에 활성화될 수 있다. 이는 반드시 여러 OS Thread가 동시에 실행된다는 뜻이 아니라, 하나의 State Configuration에 여러 Region의 활성 State가 함께 존재한다는 뜻이다.

```text
OrderFulfillment
├→ Payment Region: unpaid → paid
└→ Inventory Region: unreserved → reserved

두 Region 모두 Final
→ OrderReady
```

## 10. 계층·병렬·History State

### 10-1. Composite State

여러 하위 State를 하나의 상위 의미로 묶는다.

```text
MeetingActive
├→ Recording
└→ Paused
```

상위 State의 공통 Entry·Exit Action과 공통 Transition을 재사용할 수 있다.

### 10-2. Orthogonal Region

서로 독립적인 하위 상태 머신을 동시에 활성화한다.

```text
DocumentProcess
├→ Content Region: editing / locked
└→ Sync Region: synced / syncing / offline
```

독립성이 실제로 존재하는지 검토해야 한다. 모든 Transition이 서로의 State를 계속 확인한다면 Region 분리가 잘못되었거나 동기화 경계가 부족한 것이다.

### 10-3. Join과 완료 조건

병렬 Branch가 언제 상위 완료로 합쳐지는지 명시한다.

- 모두 성공해야 하는가?
- 하나만 성공하면 되는가?
- 일부 실패를 허용하는가?
- Timeout 시 부분 결과를 사용할 수 있는가?
- 결과를 덮어쓰기·이어쓰기·병합 중 어떻게 합치는가?

### 10-4. History State

복합 State를 나갔다가 다시 들어갈 때 이전 하위 State로 복귀하는 개념이다.

- **Shallow History**: 직전의 바로 아래 Child State만 기억
- **Deep History**: 전체 활성 하위 State Configuration 기억

History는 편리하지만 복귀할 State가 명시적인 데이터로 보이지 않아 디버깅이 어려울 수 있다. 업무 시스템에서는 `return_state` 같은 명시적 필드가 더 읽기 쉬운 경우도 있다.

W3C SCXML은 Initial, Final, Parallel과 Shallow·Deep History의 실행 의미를 규정한다.

- [W3C SCXML — Initial, Final, and History States](https://www.w3.org/TR/scxml/#History)

## 11. 상태 폭발과 복잡성 관리

독립 상태 머신 A가 m개 State, B가 n개 State를 가지면 두 머신의 전체 조합은 최대 `m × n`개다. 축이 늘어날수록 곱셈으로 증가한다.

### 상태 폭발의 징후

- State 이름에 여러 조건이 `and`로 붙는다.
- 거의 같은 Transition을 여러 State에 복사한다.
- Boolean Flag 조합의 불법 상태가 많다.
- State 표가 커졌지만 대부분 도달 불가능하다.
- 병렬 Branch 하나를 추가할 때 전체 다이어그램을 다시 그려야 한다.

### 완화 방법

- 계층형 State로 공통 행동 묶기
- 독립 축을 별도 머신·Region으로 분리
- Control State와 Data 분리
- Submachine으로 업무 경계 분리
- State를 행동적 동등성 기준으로 합치기
- 모델 검사 시 작은 유한 범위로 추상화
- 모든 조합을 나열하는 대신 불변조건으로 불법 조합 금지

MIT의 State Machine Invariants 자료도 병렬 머신의 Product Machine과 State Explosion을 함께 다룬다.

- [MIT 6.005 — State Machine Invariants](https://www.ocw.mit.edu/courses/6-005-elements-of-software-construction-fall-2008/resources/mit6_005f08_lec06/)

## 12. 상태 머신의 정확성을 판단하는 방법

### 12-1. Trace와 Reachable State

초기 State에서 Transition을 따라 만들어지는 State·Event의 연속을 실행 Trace라고 볼 수 있다.

```text
s₀ --e₁→ s₁ --e₂→ s₂ --e₃→ ...
```

명세에 State가 존재하더라도 초기 State에서 도달할 수 없으면 죽은 State다. 반대로 의도하지 않은 위험한 State에 도달할 수 있으면 설계 오류다.

### 12-2. Invariant

모든 도달 가능한 State에서 항상 참이어야 하는 조건이다.

```text
Invariant 예시
approved이면 approved_by가 존재한다.
paid_amount는 0보다 작을 수 없다.
동시에 두 개의 active owner가 존재할 수 없다.
finish 전에는 새로운 녹화 세션을 시작할 수 없다.
```

귀납적으로 검토할 수 있다.

1. 초기 State에서 Invariant가 참인가?
2. Invariant가 참인 State에서 가능한 모든 Transition 이후에도 참인가?

두 조건이 참이면 모든 도달 가능한 State에서 유지된다.

- [MIT 6.1200J — State Machines and Invariants](https://ocw.mit.edu/courses/6-1200j-mathematics-for-computer-science-spring-2024/mit6_1200j_s24_lec04.pdf)

### 12-3. Safety Property

“나쁜 일이 절대 발생하지 않는다”는 속성이다.

```text
권한 없는 사용자가 승인할 수 없다.
결제 전에는 배송하지 않는다.
종료된 회의를 재개할 수 없다.
```

Safety 위반은 유한한 반례 Trace로 보일 수 있다.

### 12-4. Liveness Property

“좋은 일이 언젠가 발생한다”는 속성이다.

```text
처리 가능한 요청은 언젠가 완료·실패·취소 중 하나가 된다.
재시도 가능한 작업은 서비스가 회복되면 다시 진행된다.
```

`언젠가`만으로는 실무 요구가 약할 수 있으므로 Timeout과 Deadline을 포함한 속성으로 구체화한다.

### 12-5. Termination

어떤 Transition 선택을 하더라도 유한한 단계 안에 Final State에 도달하는가를 묻는다. 반복을 허용하는 대화형 시스템 전체는 종료하지 않을 수 있지만, “질문 한 번 처리” 같은 하위 워크플로우는 종료성을 가져야 한다.

### 12-6. Deadlock과 Livelock

- **Deadlock**: Final이 아닌데 처리 가능한 Transition이 없어 멈춤
- **Livelock**: Transition은 계속 실행되지만 목표에 가까워지지 않음

```text
Livelock 예
Tool 실패 → LLM 재호출 → 같은 Tool 재호출 → 같은 실패 → ...
```

재시도 횟수, Error State와 Human in the Loop 전이를 두어 끊어야 한다.

### 12-7. Model Checking과 TLA+

Model Checking은 유한하게 추상화한 모든 도달 가능한 State와 Transition을 탐색해 Invariant, Safety와 Liveness 위반 Trace를 찾는다.

TLA+에서는 시스템을 초기 조건과 다음 단계 관계로 표현하고, TLC로 작은 모델의 State Space를 탐색할 수 있다.

```text
Spec = Init ∧ □[Next]_vars

Init : 초기 State 조건
Next : 가능한 다음 Transition 관계
□    : 항상
```

큰 시스템 전체를 그대로 넣기보다 동시성, Retry, Timeout, 승인과 권한처럼 실패 비용이 큰 핵심 규칙을 작은 모델로 검증한다.

- [Leslie Lamport — Specifying and Verifying Systems with TLA+](https://lamport.org/pubs/spec-and-verifying.pdf)
- [TLA+ High-Level View](https://lamport.azurewebsites.net/tla/high-level-view.html)

## 13. 상태 머신 테스트 방법론

### 13-1. Transition Table 테스트

각 행을 최소 한 번 검증한다.

| Source | Event | Guard | Expected Target | Expected Effect |
|---|---|---|---|---|
| draft | submit | valid | review | review request created |
| draft | submit | invalid | draft | validation error |
| review | approve | authorized | approved | approval event |

### 13-2. State·Transition Coverage

- 모든 State에 진입했는가?
- 모든 Transition을 실행했는가?
- Guard의 true·false 양쪽을 실행했는가?
- Error·Timeout·Cancel 경로를 실행했는가?

### 13-3. Property-Based 테스트

Event Sequence를 무작위 생성하고 항상 유지해야 할 Invariant를 검사한다.

```text
임의의 Command Sequence 실행 후에도
paid_amount >= refunded_amount
```

### 13-4. Recovery 테스트

각 전이의 다음 지점에서 강제로 Crash를 발생시킨다.

- Side Effect 요청 직전
- Side Effect는 성공했지만 결과 저장 전
- State 저장 후 응답 전
- Checkpoint 저장 중
- 병렬 Branch 일부 성공 후

재시작 후 중복 Side Effect, State 손실과 잘못된 다음 Node가 없는지 확인한다.

### 13-5. Concurrency 테스트

같은 State에 두 Command가 동시에 들어오는 상황을 검사한다.

```text
version = 7인 문서에
Approve와 Cancel이 동시에 도착
```

낙관적 잠금, Version 비교, Event 순서화나 명시적 우선순위가 필요하다.

## 14. Checkpoint란 무엇인가

Checkpoint는 특정 시점의 실행을 나중에 복구·재개할 수 있도록 저장한 일관된 Snapshot이다.

```text
Checkpoint
= 논리적 State 값
+ 다음에 실행할 Node·Program Counter
+ 현재 활성 Submachine·Parallel Branch
+ 완료된 작업과 Pending 작업
+ 실행 ID·Thread ID·Version
+ 복구에 필요한 최소 결과
```

LangGraph는 Thread의 특정 시점 Graph State Snapshot을 Checkpoint라고 하며 Super-step 경계마다 저장할 수 있다. Checkpoint는 Human in the Loop, Memory, Time Travel과 장애 복구에 사용된다.

- [LangGraph — Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

### State와 Checkpoint 비교

| 구분 | State | Checkpoint |
|---|---|---|
| 질문 | 지금 시스템은 어떤 조건인가? | 어디에서 어떤 값으로 재개할 것인가? |
| 성격 | 논리 모델 | 영속화된 복구 Artifact |
| 필수 여부 | 상태 머신에 필수 | 장애 복구가 필요할 때 선택 |
| 개수 | 현재 실행에 논리적 현재값 존재 | 시간에 따라 여러 Snapshot 가능 |
| 내용 | Control State와 Data | State + 실행 위치 + 메타데이터 |

### Checkpoint와 Event Log 비교

| 구분 | Checkpoint | Event Log |
|---|---|---|
| 저장 방식 | 특정 시점 Snapshot | 발생한 Event의 순서 |
| 복구 | Snapshot에서 바로 시작 | Event를 Replay해 State 재구성 |
| 장점 | 복구가 빠름 | 변경 이력과 감사에 강함 |
| 단점 | 경로 전체를 설명하지 못함 | History가 길면 Replay 비용 증가 |

둘을 조합할 수 있다.

```text
최근 Checkpoint Snapshot
+ Checkpoint 이후 Event Log Replay
→ 현재 State 복구
```

PostgreSQL도 Crash Recovery에서 최신 Checkpoint Record를 기준으로 WAL의 어느 지점부터 REDO할지 결정한다.

- [PostgreSQL — WAL Configuration and Checkpoints](https://www.postgresql.org/docs/current/wal-configuration.html)

## 15. Checkpoint를 어디에 둘 것인가

### 원칙 1. 일관된 복구 경계에 둔다

Checkpoint는 State 일부만 갱신되고 나머지는 아직 반영되지 않은 순간을 저장하면 안 된다.

```text
나쁜 경계
payment_status = paid 저장
→ 실제 결제 결과 미확인

좋은 경계
결제 성공 Event 확정
→ payment_status = paid
→ 결제 ID 저장
→ 다음 Node 확정
→ Checkpoint Commit
```

### 원칙 2. 오래 기다리기 전에 둔다

- Human in the Loop 대기
- 외부 Callback 대기
- 긴 Timer 대기
- 다음 사용자 Turn 대기

Process가 종료되어도 같은 지점에서 재개할 수 있어야 한다.

### 원칙 3. 중요한 Side Effect 결과 직후 둔다

Side Effect가 성공했다면 실행 ID와 결과를 먼저 영속화해 재시작 시 중복 실행을 방지한다.

### 원칙 4. 병렬 Branch는 일관된 Snapshot을 만든다

한 Branch의 새 State와 다른 Branch의 과거 State를 임의로 섞으면 실제로 존재하지 않았던 Global State가 될 수 있다. 분산 Snapshot에서는 Process State뿐 아니라 전송 중인 Message까지 고려해야 한다.

Chandy–Lamport 알고리즘은 실행을 완전히 멈추지 않고 분산 시스템의 일관된 Global State를 기록하는 고전적 방법을 제시한다.

- [Chandy and Lamport — Distributed Snapshots](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/12/Determining-Global-States-of-a-Distributed-System.pdf)

### 원칙 5. 모든 미세 단계에 업무 Checkpoint를 표시할 필요는 없다

런타임은 내부적으로 매 Super-step마다 Snapshot을 저장할 수 있다. 그러나 설계 문서에는 업무적으로 의미 있는 완료·대기·복구 경계만 표시할 수 있다.

```text
런타임 Checkpoint
→ 기술적 장애 복구와 Replay를 위한 세밀한 Snapshot

업무 경계 Checkpoint
→ 설계 문서에서 업무 한 단위가 확정되었음을 보여주는 지점
```

두 의미를 혼동하지 말고 이름과 목적을 분리한다.

## 16. Checkpoint에 무엇을 저장할 것인가

### 반드시 검토할 항목

- Control State와 Extended State Data
- 다음에 실행할 Node 또는 대기 중인 Event
- 실행·Thread·사용자·업무 Scope ID
- State Schema Version
- 완료된 Side Effect의 Operation ID와 결과
- Retry Count와 다음 Retry 시각
- Human in the Loop 요청과 선택 결과
- 병렬 Branch별 상태와 fan-in 대기 조건
- 이전 Checkpoint와의 인과 관계

### 저장하지 않거나 분리할 항목

- ID로 다시 가져올 수 있는 대형 원문
- 매번 달라지는 임시 Cache
- 복구에 필요하지 않은 UI 세부 데이터
- LLM이 임의로 생성한 검증되지 않은 권한 값
- 비밀키와 불필요한 민감정보

Checkpoint가 클수록 저장 비용과 지연이 증가한다. 반면 너무 작으면 복구 후 다시 계산하거나 외부 조회해야 하는 범위가 커진다.

## 17. Checkpoint 빈도의 Trade-off

| 자주 저장 | 드물게 저장 |
|---|---|
| 복구 시 재실행 범위가 작음 | 저장 I/O가 적음 |
| Human in the Loop와 Time Travel이 세밀함 | 처리 지연이 작을 수 있음 |
| 저장량과 I/O 증가 | Crash 후 더 많은 단계 재실행 |
| 중간 State Schema 관리 부담 | Side Effect 중복 위험 증가 |

데이터베이스에서도 Checkpoint 간격이 길면 정상 실행 비용은 줄 수 있지만 Crash Recovery에서 더 많은 WAL을 Replay해야 한다. 워크플로우도 같은 Trade-off를 가진다.

설계 시 다음 목표를 정한다.

- 허용 가능한 State 손실 범위
- 허용 가능한 복구 시간
- Side Effect 재실행 비용
- Checkpoint 저장 비용
- Time Travel·감사 필요 수준

## 18. 복구·Replay와 결정성

### 18-1. Replay란 무엇인가

저장된 Event History나 Checkpoint 이후의 기록을 다시 적용해 실행 State를 복원하는 것이다.

Temporal은 Workflow Event History를 Replay하여 장애 전 State를 복구한다. 같은 입력과 History에서 같은 Command Sequence를 만들어야 하므로 Workflow Code의 결정성이 중요하다.

- [Temporal — Workflow Execution and Replay](https://docs.temporal.io/workflow-execution)

### 18-2. Replay하면 안 되는 비결정적 작업

다음 값은 Replay 때 달라질 수 있다.

- 현재 시각
- 난수와 UUID
- 외부 API 응답
- 파일·DB의 현재 값
- LLM 생성 결과

이 작업들은 Durable Step이나 Activity로 격리하고 최초 성공 결과를 History·Checkpoint에 기록해야 한다. Replay 시에는 다시 호출하지 않고 기록된 결과를 사용한다.

AWS Durable Execution 문서도 외부 I/O, 현재 시각, 난수와 변경 가능한 Global State를 결정적 Workflow 본문 밖의 Durable Operation으로 분리하도록 설명한다.

- [AWS — Determinism during replay](https://docs.aws.amazon.com/durable-execution/patterns/best-practices/determinism/)

### 18-3. Agent와 LLM의 Replay

LLM 호출은 같은 Prompt에도 결과가 달라질 수 있고 모델 버전도 바뀔 수 있다. 따라서 과거 Checkpoint 복구 시 이미 완료된 LLM 판단을 무조건 다시 생성하면 다른 Branch로 갈 수 있다.

```text
최초 실행
LLM 호출 → Tool A 선택 → 결과 저장

복구 Replay
저장된 Tool A 선택과 결과 재사용
LLM을 다시 호출하지 않음
```

새로운 판단을 의도적으로 수행하는 Time Travel·Fork라면 별도 실행 ID와 새 Branch로 기록한다.

## 19. Side Effect와 정확히 한 번의 환상

### 19-1. 가장 위험한 Crash Window

```text
외부 결제 성공
→ Process Crash
→ 성공 결과를 Checkpoint에 저장하지 못함
```

재시작한 시스템은 결제가 실패했는지, 성공했지만 응답만 잃었는지 알 수 없다. 무조건 재시도하면 중복 결제가 발생할 수 있다.

### 19-2. Idempotency Key

같은 논리 작업의 재시도를 동일한 Key로 보내 외부 시스템이 중복 실행을 하나의 결과로 처리하게 한다.

```text
operation_id = workflow-42:charge-payment:1
```

AWS Builders' Library는 Retry의 부작용을 줄이기 위해 Idempotent API를 설계하는 방법을 설명한다.

- [AWS Builders' Library — Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

### 19-3. 불확실한 결과 State

외부 요청이 Timeout되었다고 실패로 단정하지 않는다.

```text
payment_status = unknown
→ operation_id로 외부 실제 상태 조회
→ confirmed 또는 failed로 전이
```

### 19-4. Compensation

이미 Commit된 외부 작업은 DB Rollback처럼 과거로 되돌릴 수 없는 경우가 많다. 이때 의미상 반대 작업을 실행한다.

```text
예약 생성 성공
후속 결제 실패
→ 예약 취소라는 새 보상 작업 실행
```

보상도 실패할 수 있으므로 별도 State, Retry와 수동 처리 경로가 필요하다. Azure의 Saga와 Compensating Transaction 패턴은 여러 Local Transaction의 성공 기록, Point of No Return과 보상 작업을 명시한다.

- [Azure — Saga distributed transactions pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)
- [Azure — Compensating Transaction pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)

## 20. Event Sourcing, Snapshot과 현재 State

Event Sourcing은 모든 State 변경을 Append-only Event Sequence로 저장하고 Replay하여 현재 State를 재구성하는 방식이다.

```text
OrderCreated
ItemAdded
PaymentConfirmed
OrderShipped
→ Replay
→ 현재 Order State
```

History가 길어지면 주기적 Snapshot을 저장하고 그 이후 Event만 Replay할 수 있다.

```text
Snapshot at version 100
+ events 101..120
→ current state at version 120
```

Event Sourcing을 사용하지 않아도 다음 원칙은 유용하다.

- Command와 성공 Event를 구분한다.
- State 변경 원인을 Event ID로 추적한다.
- Checkpoint와 Event 사이 Version을 기록한다.
- 같은 Event를 두 번 적용하지 않는다.

- [Azure — Event Sourcing pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)
- [Martin Fowler — Event Sourcing](https://www.martinfowler.com/eaaDev/EventSourcing.html)

## 21. 분산 시스템에서의 State

### 21-1. 하나의 절대적인 현재 시점이 없을 수 있다

여러 서비스가 비동기로 Event를 주고받으면 각 서비스가 관찰한 State 시점이 다를 수 있다.

```text
Service A: payment confirmed
Service B: 아직 payment pending
Message: 전송 중
```

Global State를 정의하려면 Process State뿐 아니라 전송 중 Message와 Event 순서를 고려해야 한다.

### 21-2. Version과 Optimistic Concurrency

State마다 Version을 두고 예상 Version이 맞을 때만 Transition을 Commit한다.

```text
현재 version = 7
Approve Command expects version 7 → 성공, version 8
Cancel Command expects version 7 → 충돌, 재조회 필요
```

### 21-3. State Machine Replication

복제본들이 동일한 초기 State에서 동일한 Command를 동일한 순서로 결정적으로 적용하면 같은 State를 유지한다. Consensus는 어떤 Command 순서를 Commit할지 합의하는 역할을 한다.

### 21-4. Agent fan-out·fan-in

여러 Agent가 병렬로 결과를 만들면 Parent State는 단일 값이 아니라 Branch별 부분 State와 병합 규칙을 가져야 한다.

```text
Parent State
├→ branch_A = completed
├→ branch_B = failed_retryable
├→ branch_C = completed
└→ join_policy = partial_success_allowed
```

Fan-in에서는 다음을 명시한다.

- 모든 Branch를 기다리는가?
- 일부 성공으로 진행하는가?
- Timeout 시 어떤 결과를 보존하는가?
- 같은 필드 결과를 덮어쓸지 이어쓸지 병합할지
- 충돌 시 우선순위 또는 Human in the Loop

## 22. 상태 머신이 항상 최선인 것은 아니다

### 상태 머신이 적합한 경우

- 입력 순서에 따라 허용 행동이 달라진다.
- 명확한 Lifecycle이 있다.
- 불법 전이를 막아야 한다.
- 장기 대기, Retry, Timeout과 복구가 있다.
- 현재 진행 단계를 운영자가 알아야 한다.

### 다른 모델이 더 적합할 수 있는 경우

| 문제 | 우선 검토할 모델 |
|---|---|
| 선후 의존성만 있는 일회성 계산 | DAG |
| 여러 조직·사용자 업무 절차와 메시지 흐름 | BPMN |
| 자원 Token, 동시성·동기화·교착 분석 | Petri Net |
| 입력 문자열의 패턴 인식 | DFA·NFA |
| 복제 서버의 일관된 명령 적용 | Replicated State Machine |
| 단순 CRUD와 독립 요청 | 명시적 상태 머신이 과할 수 있음 |

OMG BPMN은 비즈니스 절차를 표현하기 위한 표준 그래픽 표기이며, Petri Net은 순차·선택뿐 아니라 동시성과 동기화를 직접 표현하는 데 강하다.

- [OMG — BPMN Specification](https://www.omg.org/spec/BPMN/2.0/About-BPMN/)
- [Murata — Petri Nets: Properties, Analysis and Applications](https://disco.ethz.ch/courses/hs17/des/lectures/murata.pdf)

## 23. 상태 머신 설계 절차

### 1단계. 상태 머신의 Scope와 소유자를 정한다

```text
무엇 하나의 Lifecycle을 모델링하는가?
누가 State의 진실의 원천인가?
State ID와 Version은 무엇인가?
```

하나의 머신에 사용자 세션, 회의, 문서와 UI 상태를 모두 넣지 않는다.

### 2단계. 정상·실패 시나리오를 Event Sequence로 적는다

다이어그램 전에 실제 사례를 시간 순서로 쓴다.

```text
OrderPlaced
PaymentRequested
PaymentConfirmed
InventoryReserved
OrderCompleted
```

실패, Timeout, Cancel과 중복 Event도 함께 쓴다.

### 3단계. Command와 Event를 분리한다

```text
Command: ConfirmPayment
Event: PaymentConfirmed | PaymentFailed | PaymentUnknown
```

### 4단계. 행동적으로 구분되는 State 후보를 찾는다

각 시점에서 허용 Command, Guard, Timeout과 복구 방식이 달라지는 지점을 찾는다.

### 5단계. Control State와 Data를 분리한다

State 이름에 포함된 여러 조건 중 숫자, ID, Deadline과 독립 축을 Data로 이동한다.

### 6단계. Transition Table을 먼저 작성한다

| Source | Command·Event | Guard | Action | Success Event | Target | Failure Target |
|---|---|---|---|---|---|---|
| pending | Pay | valid | request payment | Paid | paid | payment_unknown |

다이어그램은 이 표의 시각화다.

### 7단계. Invariant를 작성한다

State별로 항상 참이어야 하는 조건과 전체 머신의 Safety Property를 적는다.

### 8단계. 계층과 병렬 Region을 검토한다

반복 Transition은 상위 State로 올리고 독립 축은 별도 Region으로 분리한다.

### 9단계. Waiting·Timeout·Retry·Cancel을 추가한다

Happy Path만 있는 상태도는 실제 운영 상태 머신이 아니다.

### 10단계. Side Effect 경계를 표시한다

각 외부 쓰기에 대해 다음을 적는다.

- Idempotency Key
- 성공 판정 기준
- Timeout 시 실제 상태 조회 방법
- Retry 상한
- Compensation 가능 여부
- Point of No Return

### 11단계. Checkpoint 정책을 정한다

- 어떤 State·Data·실행 위치를 저장하는가?
- 어느 전이 직후 저장하는가?
- Crash 후 어디서 재개하는가?
- Replay 때 다시 실행하면 안 되는 단계는 무엇인가?
- State Schema Version을 어떻게 Migration하는가?

### 12단계. 검증한다

- Reachability
- 모든 Guard 분기
- Invariant와 Safety
- Deadlock·Livelock
- Termination과 Timeout
- 동시 Command 충돌
- Crash Injection과 Replay

## 24. 전이 명세 Template

새로운 전이를 설계할 때 다음 양식을 사용할 수 있다.

```yaml
transition_id: pause_recording
source_state: recording
trigger:
  type: command
  name: PauseRecording
guard:
  allowed_roles: [meeting_owner]
  backend_condition: recording_is_active
action:
  handler: pause_recording_backend
  idempotency_key: "{workflow_id}:pause:{operation_no}"
result_events:
  success: RecordingPaused
  rejected: PauseRejected
  unknown: PauseResultUnknown
target_state:
  success: pause
  rejected: recording
  unknown: pause_unknown
checkpoint:
  on: [RecordingPaused, PauseRejected, PauseResultUnknown]
retry:
  max_attempts: 2
  retryable_errors: [TEMPORARY_FAILURE]
invariants:
  - meeting_id_is_present
  - actor_is_authenticated
```

이 Template의 핵심은 성공 경로만 적지 않고 거부·불확실·복구 경로까지 하나의 전이 계약으로 만드는 것이다.

## 26. 예제: 주문 처리 상태 머신

회의록 도메인에 한정되지 않은 예로 주문 처리 Lifecycle을 설계한다.

### State

```text
created
payment_pending
paid
fulfillment_pending
completed
payment_unknown
cancelled
failed
```

### 핵심 Transition

| Source | Event·Command | Guard | Target | 핵심 처리 |
|---|---|---|---|---|
| created | SubmitOrder | items not empty | payment_pending | 주문 확정 |
| payment_pending | PaymentConfirmed | operation ID matches | paid | 결제 ID 저장 |
| payment_pending | PaymentTimeout | result unknown | payment_unknown | 실제 결제 조회 예약 |
| payment_unknown | PaymentStatusPaid | verified | paid | 중복 결제 없이 반영 |
| paid | ReserveInventory | available | fulfillment_pending | 재고 예약 |
| fulfillment_pending | ShipmentCompleted | all items shipped | completed | 완료 |
| created | CancelOrder | allowed | cancelled | Side Effect 없음 |
| paid | CancelOrder | refundable | cancelled | 환불 보상 작업 필요 |

### Invariant

```text
completed → payment_id exists
completed → all_items_shipped
cancelled after paid → refund_operation_id exists
payment_unknown → original_payment_operation_id exists
```

### Checkpoint

- 결제 요청을 보내기 전 Operation ID 저장
- 결제 성공·실패·불확실 Event를 받은 직후 저장
- 재고 예약 성공 직후 저장
- 배송 Callback 대기 전에 저장
- 완료·취소·실패 Final State에서 저장

이 예에서 `payment_unknown`은 사용자에게 보여주기 위한 문구가 아니라 Crash·Timeout 이후 중복 결제를 막기 위한 미래 행동이 다르므로 별도 State가 된다.

## 27. Agent 워크플로우에 적용할 때의 원칙

### 원칙 1. LLM의 판단과 상태 머신의 전이를 분리한다

LLM은 Command나 Tool 호출 후보를 만들 수 있지만 State Guard, 권한과 실제 성공 판정은 결정적인 오케스트레이터·백엔드가 강제한다.

### 원칙 2. LLM 출력 자체를 성공 Event로 보지 않는다

```text
LLM: "회의를 일시정지하겠습니다"
≠ RecordingPaused
```

백엔드의 성공 결과가 있어야 State를 변경한다.

### 원칙 3. 모델 호출 결과를 Replay 가능한 실행 결과로 기록한다

이미 완료된 LLM 선택과 Tool 결과는 Checkpoint·History에서 다시 사용하고, 장애 복구만을 위해 LLM을 재호출하지 않는다.

### 원칙 4. 큰 문서와 State를 분리한다

복구에 필요한 ID·Version은 State에 두고, 다시 조회할 수 있는 원문은 Checkpoint에 반복 저장하지 않는다.

### 원칙 5. 한 사용자 Turn과 전체 대화 Lifecycle을 분리한다

전체 대화는 반복 가능하지만, 한 번의 질문 처리 Submachine은 성공·실패·사용자 입력 필요 중 하나로 안정되게 끝나야 한다.

### 원칙 6. Human in the Loop는 Waiting State와 복구 경계다

대기 중인 질문, 후보, 허용 선택지와 Resume Token을 저장한다. 사용자의 응답을 받으면 동일 실행을 재개할지 새 실행으로 시작할지 명시한다.

### 원칙 7. Tool 오류 Loop에 상한을 둔다

같은 State·같은 오류·같은 인자로 무한 재호출하지 않도록 Retry Count와 Escalation State를 둔다.

## 28. 자주 발생하는 Anti-pattern

| Anti-pattern | 문제 | 개선 방향 |
|---|---|---|
| State가 단순 화면 이름 | 실제 허용 행동과 불일치 | 업무 행동 기준으로 정의 |
| Trigger 순간 성공 State 변경 | 백엔드 실패 시 거짓 State | 성공 Event 후 갱신 |
| Boolean Flag 다수 | 불법 조합과 상태 폭발 | Enum·Region·Invariant |
| Guard 안에서 Side Effect | 평가만 해도 외부 변경 발생 | Guard와 Action 분리 |
| 모든 오류를 이전 State 유지 | 복구 불가능 상태가 숨음 | error·unknown·manual_review 분리 |
| Final State가 없음 | 업무 경계와 새 시작 조건 모호 | completed·failed·cancelled 정의 |
| Checkpoint를 State와 동일시 | 복구 위치·Pending 작업 누락 | 실행 메타데이터 포함 |
| Checkpoint Rollback으로 외부 변경 취소 기대 | 중복·불일치 | Idempotency·Compensation |
| LLM이 State 조건을 기억 | 누락·토큰 증가·비결정성 | 백엔드 Guard로 강제 |
| 병렬 결과를 도착 순으로 덮어씀 | 데이터 손실 | Reducer·Version·병합 정책 |
| 모든 세부 단계를 하나의 거대 머신에 포함 | 이해·검증 불가 | Submachine과 Scope 분리 |
| Event와 Command 이름 혼용 | 요청과 성공 사실 혼동 | 명령형·과거형 구분 |

## 29. 설계 Review 질문

### State Review

- State마다 허용 Event와 금지 Event를 설명할 수 있는가?
- 두 State의 미래 행동이 실제로 다른가?
- Control State와 Data가 섞여 있지 않은가?
- 독립 축을 하나의 조합 State로 만들지 않았는가?
- Initial, 성공·실패·취소 Final State가 있는가?
- Error와 결과 불확실 상태가 필요한가?

### Transition Review

- Trigger, Guard, Action, 성공 Event와 다음 State가 모두 있는가?
- Guard가 Side Effect 없이 결정적인가?
- 같은 State·Event에서 여러 Guard가 동시에 참일 수 있는가?
- 불법 Event의 처리 정책이 있는가?
- Retry, Timeout, Cancel 경로가 있는가?

### Correctness Review

- 핵심 Invariant를 문장과 테스트로 표현했는가?
- 모든 State가 도달 가능한가?
- Final이 아닌 Deadlock State가 있는가?
- 무한 Retry나 Livelock이 가능한가?
- 병렬 Branch의 Join 조건이 명확한가?

### Checkpoint Review

- Crash 후 어느 Node부터 재개하는가?
- Checkpoint가 일관된 State를 나타내는가?
- 완료된 Side Effect를 식별할 Operation ID가 있는가?
- Replay 시 LLM·외부 API를 중복 호출하지 않는가?
- State Schema Version과 Migration 계획이 있는가?
- 저장 주기와 복구 시간의 Trade-off를 정했는가?

## 30. 단계별 학습·실험 방향

### 실험 A. Flat FSM

작은 주문·문서 승인 Lifecycle을 State Table과 다이어그램으로 작성하고 모든 Transition 테스트를 만든다.

### 실험 B. Extended State Machine

Retry Count, Deadline, 권한을 Data와 Guard로 분리하고 State 수 변화를 비교한다.

### 실험 C. Hierarchical Statechart

공통 Cancel 전이를 상위 State로 이동하고 중복 Transition 감소를 측정한다.

### 실험 D. Orthogonal Region

독립된 두 업무 축을 Parallel Region으로 모델링하고 Product State 수와 Join 조건을 비교한다.

### 실험 E. Invariant와 Model Checking

작은 TLA+ 모델로 동시 Approve·Cancel과 Retry 순서를 탐색해 Safety 위반 Trace를 찾는다.

### 실험 F. Crash Injection

외부 Side Effect 전·후와 Checkpoint 전·후에 Crash를 발생시켜 중복 실행과 복구 위치를 검증한다.

### 실험 G. Event Log + Snapshot

Event만 Replay하는 방식과 주기적 Snapshot 이후 Replay하는 방식의 저장량·복구 시간을 비교한다.

## 핵심 정리

> 상태 머신 설계의 출발점은 State 이름을 나열하는 것이 아니라, 현재 조건에 따라 미래의 허용 행동이 어떻게 달라지는지 찾는 것이다. State는 미래 결정을 위해 필요한 과거의 최소 요약이며, Transition은 `현재 State + Event·Command + Guard → Action·성공 Event → 다음 State`라는 계약으로 정의한다. 독립적인 상태 축은 계층과 병렬 Region으로 분리하고, Invariant·Safety·Liveness·Reachability·Deadlock을 통해 정확성을 검토한다. Checkpoint는 State 그 자체가 아니라 State와 다음 실행 위치를 일관된 경계에 영속화한 복구 기준점이다. 외부 Side Effect는 Checkpoint Rollback으로 취소되지 않으므로 Idempotency, 실제 결과 조회, Event History와 Compensation을 별도로 설계해야 한다.
