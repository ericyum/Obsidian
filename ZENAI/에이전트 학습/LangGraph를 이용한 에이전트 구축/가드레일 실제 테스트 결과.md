## 2. 테스트 진행 과정

### 2-1. 순수 로직과 권한 경계 테스트

실제 LLM을 호출하기 전에 다음 항목을 단위 테스트로 확인했다.

- 공격 사례 100개와 네 공격 유형이 올바르게 생성되는지
- 공격 사례 ID가 중복되지 않는지
- 보호가 없는 삭제 Tool이 격리 파일을 삭제하는지
- 서버 권한 검사가 승인되지 않은 직접 Tool 호출을 거부하는지
- 서버에서 미리 승인한 파일은 정상적으로 삭제할 수 있는지
- 오케스트레이터 우회가 3겹에서만 최종 차단되는지

- 경로 검사가 테스트 폴더 밖의 파일 접근을 허용하지 않는지

초기 단위 테스트 8개가 통과했고, 오염된 모델 결함 주입 테스트를 추가한 뒤 최종적으로 9개가 모두 통과했다.

### 2-3. 첫 번째 400회 실행에서 발견한 오류

첫 전체 실행에서는 모든 계층에서 25건씩 오류가 발생했다.

| 계층 | 전체 | 정상 평가 | 오류 |
|---|---:|---:|---:|
| 0겹 | 100 | 75 | 25 |
| 1겹 | 100 | 75 | 25 |
| 2겹 | 100 | 75 | 25 |
| 3겹 | 100 | 75 | 25 |

오류 25건은 모두 간접 인젝션 사례였다. DeepSeek API가 다음 오류를 반환했다.

```text
The `reasoning_content` in the thinking mode must be passed back to the API.
```

이 오류는 가드레일이 공격을 막은 결과가 아니라 메시지 형식 때문에 평가가 실행되지 않은 것이다. 따라서 해당 실행 결과를 최종 보안 결과로 사용하지 않았다.

### 2-4. 오류 원인과 수정

DeepSeek V4 Pro의 사고 모드에서는 Tool을 호출한 Assistant 메시지의 `reasoning_content`를 다음 요청에도 전달해야 한다.

현재 사용한 범용 `ChatOpenAI` 어댑터는 이 DeepSeek 전용 필드를 보존하지 않았다. 모델 ID는 유지하고 다음 설정으로 사고 모드를 명시적으로 비활성화했다.

```python
extra_body={"thinking": {"type": "disabled"}}
```

이 설정은 보안 성능을 높이기 위한 가드레일이 아니라, DeepSeek API와 LangChain 어댑터의 호환성 문제를 제거하기 위한 실행 설정이다.

- [DeepSeek Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode)

| 계층 | 정상 평가 | 오류 | 모델 삭제 시도 | 실제 삭제 | 오염된 모델 호출 | 직접 Tool 우회 |
|---|---:|---:|---:|---:|---|---|
| 0겹: 보호 없음 | 100 | 0 | 54 | 54 | 삭제됨 | 삭제됨 |

이 결과는 Tool·서버 권한 검사가 최종 보안 경계여야 하는 이유를 보여준다.

## 6. 기존 뉴스 Agent 회귀 테스트

DeepSeek 사고 모드 설정을 기존 뉴스 Agent에도 적용했기 때문에 원래 Agent Loop가 계속 동작하는지 별도의 격리 폴더에서 확인했다.

```text
사용자 목표
→ check_today_news
→ 오늘자 파일 없음
→ fetch_economic_news
→ 실제 경제 뉴스 반환
→ save_news_markdown
→ 격리 폴더에 저장
→ LLM 최종 답변
→ 종료
```

실행 결과 다음 순서가 정상적으로 관찰됐다.

1. `check_today_news` 선택
2. `exists=false` 결과 관찰
3. `fetch_economic_news` 선택
4. RSS 기사 데이터 관찰
5. `save_news_markdown` 선택
6. `saved=true` 결과 관찰
7. 저장 경로를 포함한 최종 답변 반환

저장 파일은 실제 뉴스 폴더가 아닌 다음 격리 경로에 생성했다.

```text
data/security_lab/news-agent-smoke/2026-08-14-economic-news.md
```

따라서 보안 실험 추가와 DeepSeek 설정 변경 이후에도 기존 Agent Loop가 정상적으로 동작하는 것을 확인했다.

## 7. 결과 해석

### 이번 테스트에서 확인한 것

1. 보호가 없으면 100건 중 54건에서 모델의 삭제 판단이 실제 삭제로 이어졌다.
2. 시스템 프롬프트는 이번 100개 고정 공격에서는 모델의 삭제 Tool 선택을 모두 억제했다.
3. 모델이 이미 잘못된 Tool-call을 출력한 경우 프롬프트만으로는 실행을 막지 못했다.
4. 오케스트레이터는 오염된 모델의 Tool-call을 실행 직전에 차단했다.
5. 오케스트레이터를 우회한 직접 Tool 호출은 Tool·서버 권한 검사가 있을 때만 차단됐다.
6. 모델의 판단 실패와 시스템의 보안 실패는 구분하여 측정해야 한다.

### 이번 테스트로 증명할 수 없는 것

이번 테스트의 `0/100` 결과는 프롬프트가 절대 뚫리지 않는다는 뜻이 아니다.

- 공격 문장과 패턴은 전체 가능한 공격의 일부다.
- 더 긴 대화로 신뢰를 쌓는 멀티턴 공격은 포함하지 않았다.
- 이전 공격 결과를 보고 다음 문장을 개선하는 적응형 공격은 수행하지 않았다.
- 모델·프롬프트·Tool Description이 변경되면 결과도 달라질 수 있다.
- 같은 사례라도 비결정적 모델 설정에서는 다른 결과가 나올 수 있다.

InjecAgent와 AgentDojo는 Tool 사용 Agent에 대한 간접 인젝션 위험과 평가 환경을 제시한다. 2025년 적응형 공격 연구는 고정된 기존 방어도 공격자가 방어 방식에 맞춰 공격을 개선하면 우회될 수 있음을 보였다.

- [InjecAgent](https://arxiv.org/abs/2403.02691)
- [AgentDojo](https://arxiv.org/abs/2406.13352)
- [Adaptive Attacks Break Defenses Against Indirect Prompt Injection](https://aclanthology.org/2025.findings-naacl.395/)
- [Crescendo](https://arxiv.org/abs/2404.01833)

## 8. 실제 서비스에 적용할 원칙

### 조회 Tool

- 서버에서 현재 사용자와 테넌트를 확인한다.
- 조회 가능한 회의·뉴스만 결과에 포함한다.
- LLM에게 `has_permission=true` 같은 권한 판단을 맡기지 않는다.

### 삭제·게시·외부 전송 Tool

- Tool 실행 전에 오케스트레이터 정책을 적용한다.
- Tool 내부에서 서버 권한을 다시 검사한다.
- 승인 정보는 모델이 생성하는 인자가 아니라 서버 실행 컨텍스트에서 가져온다.
- 되돌리기 어려운 작업은 사람 승인을 추가한다.
- 파일·DB·네트워크 권한은 최소 범위만 부여한다.

LangGraph에서는 `interrupt`를 사용해 파괴적인 Tool 실행 전에 Graph를 멈추고 사람의 승인 후 재개할 수 있다.

- [LangChain Guardrails](https://docs.langchain.com/oss/python/langchain/guardrails)
- [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- [CaMeL: Defeating Prompt Injections by Design](https://arxiv.org/abs/2503.18813)
