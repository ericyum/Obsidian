# AI 에이전트 Tool 설계 — 발표 대사

> PPT의 발표자 노트에도 같은 흐름의 대사가 포함되어 있다. 아래 원고는 인쇄하거나 Obsidian에서 보면서 발표하기 위한 버전이다.

## 1. 표지 — AI 에이전트의 판단을 안전한 행동으로 연결하는 법

오늘 발표의 질문은 단순합니다. LLM에게 API를 몇 개 붙이면 에이전트가 되는가, 그리고 실제 프로젝트에서 그 Tool을 어떻게 설계해야 하는가입니다. 먼저 에이전트의 정의를 짧게 정리하고, Loop·Compact·Tool·Sub-agent의 관계를 본 다음, 발표의 중심인 Tool 선택과 안전한 연결 방법으로 들어가겠습니다.

## 2. 에이전트는 ‘답변’이 아니라 ‘다음 행동’을 선택한다

에이전트는 LLM의 다른 이름이 아닙니다. LLM은 문장을 이해하고 다음 행동을 제안하는 판단 엔진입니다. 에이전트는 여기에 목표, 상태, Tool, 실행 결과, 권한과 종료 조건을 결합한 시스템입니다. 따라서 좋은 모델 하나를 고르는 것만으로는 충분하지 않습니다. 무엇을 보고, 어떤 행동을 허용하며, 언제 멈추는지를 시스템 차원에서 설계해야 합니다.

## 3. LLM·챗봇·워크플로·에이전트 비교

이 네 가지를 제품 이름이 아니라 실행 방식으로 구분해야 합니다. 대화가 길다고 에이전트는 아닙니다. 워크플로에도 LLM이 들어갈 수 있지만 경로가 고정돼 있다면 여전히 워크플로입니다. 에이전트의 핵심은 관찰 결과에 따라 검색할지, 질문할지, Tool을 부를지, 멈출지를 선택하는 것입니다. 그리고 모든 문제를 에이전트로 만들 필요는 없습니다. 경로가 확정된 과정은 코드로 고정하는 편이 더 안전합니다.

## 4. 에이전트 내부의 핵심 Loop

에이전트 내부를 다섯 단계로 단순화할 수 있습니다. 목표와 제약을 확인하고, 현재 상태를 관찰하고, 다음 행동을 고릅니다. Tool이 필요하면 모델은 호출 요청과 인자를 만들지만 실제 권한과 Schema 검증은 서버가 합니다. 결과가 돌아오면 목표 달성 여부를 다시 판단합니다. 이때 반드시 반복 횟수, 비용, 시간, 중복 행동, 사람 승인과 종료 조건이 있어야 합니다. 자율성은 무한 반복이 아니라 통제된 분기입니다.

## 5. Loop·Compact·Tool·Sub-agent

네 요소를 각각 하나의 설계 질문으로 기억하면 쉽습니다. Loop는 언제 멈추는가, Compact는 무엇을 보존하는가, Tool은 무엇을 실행하게 하는가, Sub-agent는 무엇을 위임하고 누가 검증하는가입니다. 상위 에이전트에 비싼 모델, 하위 에이전트에 싼 모델을 쓰는 구조는 가능하지만 비용 배치는 두 번째 문제입니다. 먼저 역할과 권한, 결과 계약, 검증 책임이 분리돼야 합니다. 오늘은 이 중 실제 세계에 영향을 주는 Tool을 집중해서 보겠습니다.

## 6. Tool은 선택과 실행을 잇는 계약이다

Tool은 단순히 호출 가능한 함수가 아닙니다. 왼쪽은 모델이 읽는 선택 인터페이스입니다. 이름, Description, Schema를 보고 어떤 능력인지 판단합니다. 가운데에서 모델은 Tool 이름과 인자를 구조화해 요청합니다. 오른쪽은 서버의 실행 인터페이스입니다. 인증 사용자와 권한을 확인하고, 입력을 검증하고, 실제 함수를 실행하고, 오류와 로그를 남깁니다. 모델은 요청할 뿐이며, 실행 권한을 스스로 부여해서는 안 됩니다.

## 7. Toolkit은 탐색·정책 경계다

Tool 하나는 검색이나 조회처럼 한 가지 능력입니다. Toolkit은 회의, 문서, 일정처럼 관련 Tool을 묶은 그룹입니다. 사용자의 질문이 회의 영역이라면 회의 Toolkit 안에서만 후보를 비교하게 할 수 있습니다. 다만 이것을 항상 별도의 LLM 라우팅 단계로 만들 필요는 없습니다. Tool이 몇 개뿐이면 정의를 모두 제공하고 직접 선택하게 하는 것이 더 단순합니다. Tool 수가 늘어 선택 오류와 토큰 비용이 커질 때 Toolkit과 권한으로 1차 필터링합니다.

## 8. Tool 선택은 다섯 단계다

사용자의 질문과 Tool Description을 비교하는 것은 세 번째 단계입니다. 먼저 외부 정보나 행동이 필요한지 판단해야 합니다. 그다음 현재 사용자가 접근할 수 있는 도메인과 Toolkit을 좁힙니다. 이후 Description과 Schema를 바탕으로 후보를 만들고, 현재 상태에서 최종 Tool과 인자를 고릅니다. 마지막으로 서버가 인증, 권한, Schema와 정책을 검증합니다. 즉 선택 정확도와 실행 안전성은 별개의 문제이고 둘 다 필요합니다.

## 9. 임베딩은 정답이 아니라 후보를 찾는다

Tool이 많아지면 모든 Description과 Schema를 매번 프롬프트에 넣기 어렵습니다. 그래서 오프라인에서 Tool 문서를 임베딩해 벡터 인덱스를 만들고, 런타임에는 사용자 목표와 현재 계획을 임베딩해 가까운 후보 Top-K를 찾습니다. 그러나 가장 가까운 Tool이 정답이라는 보장은 없습니다. 의미가 비슷해도 권한, 현재 상태, 위험도, 필수 인자가 다를 수 있기 때문입니다. 따라서 하이브리드 검색과 재랭킹 또는 LLM의 최종 판단, 그리고 서버 검증이 필요합니다.

## 10. 좋은 Tool의 네 가지 설계 원칙

좋은 Tool의 첫 조건은 모델이 업무 단위로 이해할 수 있는 경계입니다. 기존의 범용 API를 그대로 붙이면 인자가 너무 많고 여러 목적이 섞입니다. 읽기와 쓰기는 분리하고, 쓰기는 미리보기와 승인, 멱등성 키를 둡니다. Schema는 설명을 실행 가능한 제약으로 바꾸며, 출력은 다음 판단에 필요한 구조만 제공해야 합니다. 오류도 단순 문자열이 아니라 재시도, 다른 Tool, 사용자 확인, 중단 중 무엇을 해야 하는지 구분할 수 있어야 합니다.

## 11. Description은 선택 경계를 만든다

Description은 기능을 멋지게 소개하는 마케팅 문구가 아닙니다. 모델이 언제 이 Tool을 선택하고 언제 선택하지 않을지 경계를 만드는 문장입니다. 가장 실용적인 공식은 무엇, 언제, 언제 아님, 중요 입력, 출력과 오류입니다. 특히 비슷한 Tool끼리는 금지 조건을 대칭적으로 적습니다. 회의 검색 Tool은 본문 조회에 쓰지 않는다고 쓰고, 회의록 조회 Tool은 회의 후보 찾기에 쓰지 않는다고 쓰는 방식입니다. 설명 변경은 프롬프트 변경이므로 실제 평가 세트로 버전 관리해야 합니다.

## 12. ZEN AI v1 적용안

ZEN AI의 첫 버전은 Tool Retrieval이나 Sub-agent부터 만들 필요가 없습니다. 읽기 Tool 세 개만 직접 제공합니다. 먼저 접근 가능한 회의를 찾고, 선택된 회의의 확정 회의록을 읽고, 회의록 근거가 부족할 때만 같은 회의의 전사 구간을 검색합니다. 인증 사용자와 tenant는 모델이 만들지 않고 서버 세션에서 주입합니다. 모든 조회에는 행 단위 권한과 감사 로그를 적용합니다. 게시 기능은 Q&A가 안정된 뒤 미리보기, 사람 승인, 실제 게시를 분리해 추가합니다.

## 13. 결론

마지막으로 한 문장만 기억하면 됩니다. 좋은 Tool은 모델이 쉽게 고르고, 서버가 안전하게 거부하며, 팀이 실제 결과로 개선할 수 있어야 합니다. 구현 순서는 권한이 내장된 데이터 접근 함수, 읽기 Tool 세 개, 선택과 인자와 권한 평가, 실패 데이터를 이용한 개선입니다. 처음부터 거대한 에이전트 플랫폼을 만드는 것이 아니라 작은 Tool 집합으로 정확성과 안전성을 측정한 뒤 필요한 구조만 추가하는 것이 이번 설계의 결론입니다.
