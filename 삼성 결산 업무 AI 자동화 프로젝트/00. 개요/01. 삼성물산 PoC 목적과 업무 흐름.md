# 삼성물산 PoC 목적과 업무 흐름

[[00. 프로젝트 길잡이|00 프로젝트 길잡이]] · 다음: [[02. 구현 인수인계와 SAP 시스템 이해|02 구현 인수인계와 SAP 시스템 이해]]

**핵심은 결산 담당자가 “무엇이 남았는지 파악 → 실제 실행 전에 오류 발견 → 수정 후 재검증 → 기표와 결과 확인”을 자연어와 업무 화면으로 이어서 수행하게 하는 것이다.** 기존 감가상각·외화평가 시연을 출발점으로, 고객의 결산 Activity 일부와 Custom 프로그램·권한 통제를 적용하는 방향이다.

> [!summary] 먼저 기억할 다섯 가지
> 1. 초기 합의의 중심은 **준비 모니터링·시뮬레이션·결산 수행** 세 단계다.
> 2. **Fiori와 JWD는 같은 결산 관리 테이블을 조회**한다. 화면만 두 개인 셈이며 상태의 근거가 같아야 한다.
> 3. 오류 해결 시연에서는 **AI가 AO90 확인을 제안하고 사람이 SAP에서 설정을 수정**한다.
> 4. **시뮬레이션과 실제 기표는 다른 실행**이다. 재실행은 새 RequestID, 진행 중 결과 확인은 같은 RequestID를 사용한다.
> 5. PPTX의 자동 트리거·결과 자동 반영·권한 테스트 등은 **추가 과제**이며 전부 완료된 기존 기능으로 보면 안 된다.

## 1. 두 자료는 같은 시점의 같은 PPT가 아니다

| 자료 | 담고 있는 것 | 이 문서에서의 사용 |
|---|---|---|
| `2026_11_05 17_24.mp4` | 초기 고객 합의, 데모 실행, 고객 Activity Excel, 전제조건 | 업무 목적과 시연 흐름을 설명하는 근거 |
| `[삼성건설] PoC 수행 방안_20261104.pptx` | 기존 구현 5단계, 시스템 그림, 추가 요구사항, 일정 | 후속 PoC 범위와 남은 과제를 구별하는 근거 |

짧은 영상에서 보이는 고객 시나리오에는 네 번째 **이상 변동 검증/재무 분석** 단계가 있지만, 설명자는 이 넓은 후속 분석을 당시 PoC에서 제외했다고 말한다(약 **01:40–02:40**). 이후 PPTX에는 **SAP+Non-SAP 분석형 시나리오**와 **스풀 기반 대화형 분석**이 추가 과제로 등장한다(슬라이드 9).

따라서 **“분석은 전부 제외”도, “분석까지 모두 확정”도 정확하지 않다.** 초기 제외 대상은 광범위한 결산 후 재무제표·손익/이상 변동 분석이고, 데모의 제한된 스풀 설명 및 후속 분석 요구사항은 각각 따로 판단해야 한다.

![[V1-0051-고객-시나리오.png|950]]

*영상 1, **00:50.79** 화면 일부. 고객 초기 구상은 4단계다. 화면의 네 번째 단계를 그대로 확정 PoC 범위로 받아들이면 구두 설명과 어긋난다.*

## 2. 업무 단위와 화면을 먼저 이해하기

| 용어 | 쉽게 설명하면 | 혼동하기 쉬운 것 |
|---|---|---|
| **Activity / Task** | 결산 체크리스트의 한 업무. 수동 검토 또는 Agent 실행 대상 | 목록에 있다고 모든 업무가 자동 실행되는 것은 아님 |
| **템플릿** | 반복 사용할 업무 목록·담당·의존관계 등의 정의 | 특정 월의 실행 결과 자체가 아님 |
| **결산 차수 / Cycle** | 회사·연도·기간에 해당하는 한 번의 결산 실행 묶음 | 템플릿 원본과 실제 차수 상태를 구별 |
| **Fiori App** | 필터·진행률·우선순위·일정·작업 목록을 보는 업무 화면 | SAP 표준 기능 전체를 새로 구현한 앱은 아님 |
| **JWD** | 영상에서 사용하는 Joule Work Desktop. 자연어로 현황 질의·도구 호출·결과 설명 | LLM 응답만으로 SAP 반영 결과가 증명되지는 않음 |
| **CBO / Custom 테이블** | 결산 업무 목록·실행 상태·이력 등을 저장하는 고객/사용자 정의 영역 | 표준 회계 전표 테이블과 책임이 다름 |
| **시뮬레이션** | 실제 기표 전에 TEST 모드로 조건·오류를 점검하는 작업 | 성공해도 실제 회계 전표 생성과 같지 않음 |
| **기표** | SAP 회계 처리를 실제 업데이트하는 작업 | 단순 조회 또는 시뮬레이션과 다른 영향 |
| **Job / Spool** | 백그라운드 작업과 그 작업이 남긴 출력 목록 | 대화 요약보다 상세한 근거를 제공 |
| **RequestID** | 실행 요청과 그 결과를 연결하는 추적 식별자 | **SAP 전표번호와 다르다** |

영상에서는 표준 프로그램·표준 테이블·표준 함수를 최대한 활용하고, 결산 Task와 현황 관리를 위해 커스텀 테이블을 만들었다고 설명한다(**03:28–04:25**). 제공 자료에서는 그 관리 계층을 RAP/CDS/OData로 확인할 수 있다.

### 3.1 준비 모니터링: 같은 조건으로 현황 보기

Fiori에서 **회사코드·결산 템플릿·회계연도·기간·담당자**를 선택하고, Agent 업무와 수동 업무, 우선순위, 예정 업무, 일정과 진행상태를 본다(**05:12–06:10**).

![[V1-0517-결산-대시보드.png|950]]

*영상 1, **05:17.04**. 필터와 Agent/수동 업무 구분, 완료율·우선순위·일정이 한 화면에 모인다. 시연 수치와 이름은 데모 화면의 일부다.*

이어 JWD에서 “2026년 8월 결산 현황”처럼 묻는다. 설명자는 **두 화면이 같은 테이블을 보기 때문에** 미처리 업무와 우선순위를 설명할 수 있다고 강조한다(**06:12–06:48**).

이 말은 결과를 양쪽에 수동 복사한다는 뜻이 아니다. 반대로 **JWD의 대화가 성공했더라도 SAP 관리 테이블이 갱신되지 않으면 Fiori와 상태가 달라질 수 있다.** PPTX의 결과 자동 업데이트 과제가 중요한 이유다.

### 3.2 시뮬레이션: 실행 전에 무엇을 확인하는가

데모에서는 감가상각·외화평가 등은 TEST로 실행하고, 미결 항목과 미승인 전표도 검토한다(**06:48–07:32**). 회사·기간과 사용자 담당 범위를 정확하게 넘기고, 응답에 나타난 오류·로그·스풀을 확인하는 과정이 핵심이다.

![[V1-0715-시뮬레이션-오류.png|800]]

*영상 1, **07:14.67**. 감가상각 계정 설정 오류와 검토 결과 일부. 화면의 `KTNAFG` 계정 설정 누락이 다음 보정 단계로 연결된다.*

### 3.3 오류 수정: AI 추천 다음에 사람이 하는 일

AI는 오류를 바탕으로 **AO90에서 감가상각 계정 설정을 확인**하라고 제안한다. 이어 사용자가 SAP에 직접 들어가 누락된 일반 비용 계정을 확인·보정한다(**07:32–08:21**).

![[V1-0802-AO90-사용자-보정.png|900]]

*영상 1, **08:01.54**. 사람이 SAP 설정을 수정하는 장면. 이 시연을 “AI가 AO90 설정을 자동 수정했다”로 설명하면 안 된다.*

PPTX의 **과거 오류 이력을 근거로 처리 방안을 제안**하는 요구사항은 이 추천 기능을 더 체계화하는 후속 과제다. 현재 데모의 한 번의 오류 설명이 이력 축적·검색·정확성 검증 전체의 완료를 뜻하지 않는다.

### 3.4 재실행: 이전 결과를 덮어 이해하지 않기

보정한 뒤 동일 기간에 다시 시뮬레이션한다. 영상에서는 **RequestID가 새로 발급**되었다고 설명하고, 성공 결과와 SM37 작업로그·스풀 링크를 확인한다(**08:21–09:17**).

![[V1-0824-요청ID와-진행중.png|800]]

*영상 1, **08:24.46**. RequestID·시뮬레이션 모드와 함께, 감가상각은 일부 결과가 성공이어도 전체 상태는 “실행 중”으로 보인다. **부분 성공과 최종 완료를 구별해야 하는 예**다.*

![[V1-0834-재실행.png|900]]

*영상 1, **08:34.46**. 보정 후 재실행 결과. 새 실행과 이전 실패의 식별자를 구별해 추적해야 한다.*

| 상황 | 필요한 처리 |
|---|---|
| 같은 작업이 아직 진행 중 | **같은 RequestID로 결과 조회** |
| 설정 보정 후 다시 실행 | **새 RequestID로 새 작업 요청** |
| 요청 직후 통신 타임아웃 | 이미 SAP에 접수되었는지 먼저 확인. 곧바로 새 실행을 반복하지 않음 |
| 성공 메시지만 받은 상태 | 작업 최종 상태와 로그·스풀, TEST/실제 모드를 확인 |

### 3.5 실제 기표와 결과 설명

시뮬레이션 후 실제 기표를 요청하고, 데모에서는 외화평가 **전표번호·전기일·역분개일·계정·금액·처리 건수**를 보여 준다(**09:18–10:05**).

![[V1-0939-외화평가-기표결과.png|600]]

*영상 1, **09:39.25**. 데모 외화평가의 실제 기표 결과 화면 일부. 고객 실적 자료로 쓰지 않는다.*

이어 **스풀을 근거로 환율 변화와 평가 영향**을 설명한다(**10:05–11:00**).

![[V1-1017-스풀-기반-분석.png|900]]

*영상 1, **10:17.13**. 시연 스풀 기반 설명. 환율·차익·금액은 예시이며 업무 사실로 재사용하지 않는다.*

PPTX 슬라이드 5의 발표자 메모에는 환율과 차익에 관한 초안 수치가 섞여 있다. 화면·메모 간 일관성이 충분하지 않아 이 문서에서는 숫자를 재계산하거나 확정 재무 결론으로 옮기지 않았다. 핵심은 **분석을 스풀·로그·실제 결과와 연결한다는 방식**이다.

## 4. 고객 Activity를 어떻게 PoC로 옮기는가

영상 후반에는 고객이 제공한 **결산 Activity Excel**을 보여 준다(**11:40–12:55**). 이것을 앱에서 조회하고 해당 업무를 기준으로 JWD의 시뮬레이션·수행이 흐르도록 한다는 취지다.

![[V1-1203-고객-활동목록.png|800]]

*영상 1, **12:02.88**. 고객 Activity 목록 일부. 전체 목록을 모두 구현한다는 합의는 아니다.*

| 범위 판단 | 근거와 의미 |
|---|---|
| **일부 Activity를 선별** | 영상에서 전체를 다 하지 않고 몇 가지를 뽑는다고 설명 |
| 표준 프로그램 중심 | 고객의 많은 CBO 프로그램을 SAP 내부 환경으로 그대로 옮기기 어렵다는 전제 |
| 감가상각·외화평가 | 기존 시연의 대표 예제. 전체 고객 대상이 이 두 개로 최종 확정됐다는 뜻은 아님 |
| 간단한 Custom 프로그램 | 고객은 최소 하나의 작동 예를 원한다고 설명. 구체적인 대상·난이도·스풀 제공 여부 확인 필요 |
| Excel 업로드 | PPTX에서는 **JWD → Custom 테이블 업데이트** 프로그램을 추가 과제로 명시 |

Custom 프로그램은 화면에 이름을 추가하는 것만으로 끝나지 않는다. **호출 가능한 실행 방식, 입력 조건, TEST/실제 처리 구분, 작업 상태, 로그·스풀, 결과를 다시 읽을 방법**까지 정해야 다른 Activity와 같은 흐름에 들어갈 수 있다.

## 6. 일정과 범위 관리

![[PPTX-10.png|950]]

*PPTX 슬라이드 10. 아래 일정은 문서상의 계획이며 현재 달성 여부는 확인하지 않았다.*

| PPTX 계획 | 날짜 |
|---|---|
| 추가 구현 설계서 + 고객 최종 리뷰 | **2026-11-06** |
| 기존 구현 이관 + 수정 반영 | **2026-11-27** |
| PoC 완료 보고 | **2026-12-01** |

짧은 영상의 “11월 중순~말 목표”는 초기 논의다. 이후 PPTX의 일정과 섞어 하나의 회의 확정사항으로 기록하지 않았다.

슬라이드 10이 별도로 강조하는 것은 **PoC 목적의 명확한 타깃, Custom 프로그램의 스풀 생성·커버리지 사전 확인, 범위와 분량 통제**다. Classic ABAP·Fiori·AI 관련 플랫폼·IS가 함께 걸리므로, 화면 완성도만 보고 작업량을 판단하기 어렵다.
