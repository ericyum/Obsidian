[[00. 제공 자료 전체 지도|00 제공 자료 전체 지도]] · [[01. Integration Suite 실행 구조|01 Integration Suite 실행 구조]]

**바깥 폴더의 파일명은 내보내기 ID이고, 실제 구현은 `_content` ZIP 안에 들어 있다.** 이 문서는 실제 11개 파일과 여섯 컨테이너 안의 49개 파일을 구별해 안내한다.

## 1. 바깥 파일

아래에서 `패키지/`는 `05_Integration_Suite/APL15 Business Actions/`를 뜻한다.

| 실제 경로 | 역할 |
|---|---|
| `APL15 Business Actions.zip` | 패키지 내보내기 원본. 내부 10개 파일과 현재 해제본이 동일 |
| `패키지/resources.cnt` | **base64 JSON**. 리소스 ID·종류·표시명·버전 등의 manifest |
| `패키지/contentmetadata.md` | 확장자는 Markdown이지만 실제는 **base64 인코딩된 속성 텍스트**. 패키지 메타데이터 |
| `패키지/ExportInformation.info` | 평문 내보내기 정보. 패키지명과 `Tue Oct 13 06:45:58 UTC 2026` |
| `패키지/hash` | 패키지 내보내기의 해시 관련 메타데이터. 애플리케이션 실행 코드가 아님 |
| 아래 여섯 `패키지/*_content` | 각 아티팩트의 ZIP 컨테이너 |

manifest의 resource 항목은 **7개**다. 여섯 아티팩트와 ContentPackage 메타데이터 한 개를 합친 수이며, 일곱 번째 `_content` 파일이 빠졌다는 뜻이 아니다.

## 3. 내부 폴더의 공통 의미

```text
<아티팩트 ZIP>/
├─ .project
├─ META-INF/MANIFEST.MF
└─ src/main/resources/
   ├─ parameters.prop
   ├─ parameters.propdef
   ├─ scenarioflows/integrationflow/*.iflw
   ├─ apidefinition/apidefinition.json         API/MCP에 존재
   ├─ mcpsourcemapping/mcpsourcemapping.json   MCP에 존재
   ├─ mcpspecification/mcpspecification.json   MCP에 존재
   └─ script/*.groovy                         은행 요청 iFlow에 존재
```

| 파일/경로 | 어떤 역할인가 |
|---|---|
| `.project` | 설계 도구가 프로젝트를 식별하는 메타데이터 |
| `META-INF/MANIFEST.MF` | 아티팩트 번들 식별·버전 등의 manifest |
| `parameters.prop` | 외부화 파라미터의 값/참조. 환경 값은 이 노트에 복제하지 않음 |
| `parameters.propdef` | 파라미터 정의·형식·설계 시 설명 |
| `scenarioflows/integrationflow/*.iflw` | 흐름 노드·연결·어댑터·인증·스크립트 참조 등의 XML 정의 |
| `apidefinition/apidefinition.json` | OpenAPI 계약. 세 경로·요청/응답·TEST/UPDATE 제한 |
| `mcpsourcemapping/mcpsourcemapping.json` | MCP 도구와 원본 API/operation 연결 |
| `mcpspecification/mcpspecification.json` | MCP 서버 카드·도구 이름·입력 schema·설명 |
| `script/*.groovy` | iFlow가 호출하는 요청/응답 변환·검증 코드 |

공통 파일도 각 컨테이너에 별도로 들어 있다. 하나를 고쳐 다른 아티팩트가 자동으로 함께 바뀐다고 가정하면 안 된다.

## 4. 은행 요청 스크립트: 파일 존재와 실행 참조를 구별하기

은행 iFlow에는 원본과 FIXED/HARDENED/v2/v3/v4 파일이 함께 있다. `.iflw`의 실제 `script` 속성을 확인한 결과, 활성 참조는 아래 여덟 개다. 노드 표시명과 참조 파일명이 다른 경우가 있다.

| 실제 참조 파일 | 역할 |
|---|---|
| `01_ValidateAndStoreFacadeRequest.groovy` | 필수 필드·키 길이·통화·양수 금액/소수 자릿수·날짜 검증. 정규화된 입력 보관 |
| `02_ParsePayingAccount.groovy` | 출금 계좌 조회 결과에서 유일한 매핑 해석 |
| `03_ParsePayeeAccount.groovy` | 입금 계좌 조회 결과에서 유일한 매핑 해석 |
| `04_ParsePaymentMethod.groovy` | 지급 방법 조회 결과 해석 |
| `05_BuildDraftCreateBody.groovy` | SAP 지급 요청 draft 생성 body 구성 |
| **`06_ExtractDraftKeys_FIXED_v2.groovy`** | JSON/Location에서 PaymentRequest·DraftUUID·IsActiveEntity 추출·검증. 새 draft의 빈 semantic key 허용과 활성 상태를 구별 |
| **`07_NormalizeSuccess_FIXED_v4.groovy`** | 활성화 응답의 최종 요청 ID 확인, `amount3` 기준 금액, 헤더 정리, 성공 facade 응답 |
| **`99_NormalizeError_HARDENED_v2.groovy`** | 예외 경로의 오류 facade 정규화 |

나머지 일곱 개는 현재 `.iflw`에서 script 값으로 참조되지 않는다.

| 보존된 파일 | 해석 |
|---|---|
| `06_ExtractDraftKeys.groovy` | 초기 draft 키 추출 버전 |
| `07_NormalizeSuccess.groovy` | 초기 성공 응답 버전 |
| `07_NormalizeSuccess_FIXED.groovy` | 성공 응답 보정 중간 버전 |
| `07_NormalizeSuccess_FIXED_v2.groovy` | 성공 응답 보정 중간 버전 |
| `07_NormalizeSuccess_FIXED_v3.groovy` | 성공 응답 보정 중간 버전 |
| `99_NormalizeError.groovy` | 초기 오류 응답 버전 |
| `99_NormalizeError_HARDENED.groovy` | 오류 응답 보정 중간 버전 |

소스 파일을 고쳐도 iFlow가 그 파일을 참조하지 않으면 실행 경로는 바뀌지 않는다. 반대로 오래된 파일을 이름만 보고 삭제하면 설계 도구/이력 관리에 영향이 있을 수 있어 실제 사용 확인이 필요하다. 이 정리에서는 원본을 바꾸지 않았다.

## 5. 파일명으로 판단하면 놓치기 쉬운 점

- AFAB·FCV·공통·은행 컨테이너의 `.iflw` 내부 이름은 모두 `APL15 Business Actions CSRF Gateway.iflw`다. **리소스 ID·표시명·노드 내용을 함께 본다.**
- 공통명 Gateway의 실제 노드에는 `Create Planned Order`가 있다. 결산 핵심 연계와 별도로 분류한다.
- 계좌이체 흐름은 계좌/지급방법 조회 → draft 생성 → 준비 → 활성화다. **지급 실행·release로 확대하지 않는다.**
- API 이름이 Simulation이어도 외화평가 계약은 T/U를 구별한다. 감가상각 계약은 TEST만 제공한다.
- manifest·API·MCP 카드·실제 배포의 버전은 다른 지점의 값이다.
