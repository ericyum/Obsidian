**긴 영상은 완성품 설치 교육보다, 기존 데모의 구성과 제공 자료, 접속 환경, 남은 권한·연계 작업을 설명하는 인계 회의다.** 인수자는 화면만 복사하는 것이 아니라 ABAP 관리 데이터, Fiori 화면, 조회 MCP, 실행 API, BTP 연결 설정 사이의 계약을 이어받는다.

> [!summary] 핵심 판단
> - **삼성물산 시스템을 사용한 데모가 아니다.** SAP Korea 내부 환경에서 기존 구현과 PoC용 변경을 분리한다.
> - **Kyma Insights는 주로 조회, IS Actions는 업무 실행**, Cloud Foundry는 Fiori 앱 실행을 맡는 구성이다.
> - **로그인/사용자 식별과 SAP 업무 권한 통제는 다르다.** 기술 계정 연결과 미완성 사용자 전파가 후반의 중요한 쟁점이다.
> - 빈 `06_Destination.txt`는 누락된 설명 본문이 아니라 **실제 BTP 설정을 설명하기 위해 만든 자리표시자**다.
> - 소스는 인계용으로 추린 배포본이다. **원개발자의 전체 Git 이력·개발 규칙·모든 검증 산출물은 포함하지 않는다.**

## 1. 인계할 대상과 변경 원칙

영상 초반에는 BTP 접근 권한 문제가 논의된다. 일부 참석자는 S/4 접속은 가능해도 BTP는 아직 준비가 필요했다(**00:00–02:20**). 뒤이어 기존 환경과 변경 방식을 설명한다(**02:20–06:20**).

| 구분 | 인계 설명 | 인수자가 이해할 점 |
|---|---|---|
| 환경 | SAP Korea 내부 시스템 | 삼성물산 운영/개발 환경에서 이미 검증된 결과가 아님 |
| 기존 구현 | 다른 데모·업무 영역과 함께 쓰임 | 기존 패키지를 직접 덮기보다 복제·분리하는 방향 |
| ABAP | 새 패키지·별도 Custom 테이블 등 분리 논의 | 표준 데이터는 공통으로 읽되 관리 데이터·변경 책임을 구별 |
| MCP | 결산 외 업무 영역이 혼재 | 기존 전부를 가져오기보다 결산 목적에 맞춘 서비스 분리 권고 |
| 접속·배포 | BTP, Kyma, Cloud Foundry, ABAP 각각 접근 필요 | 소스 파일 수령만으로 실환경 준비 완료가 되지 않음 |

여기서 “복제”는 삼성물산 전체 시스템을 복사한다는 말이 아니다. **공유 내부 환경에서 기존 구현에 영향을 주지 않도록 PoC용 코드·설정·관리 데이터를 구별한다는 취지**다.

## 3. 시스템 전체: 누가 무엇을 맡는가

![[삼성 결산 업무 AI 자동화 프로젝트/첨부/원본-시스템-아키텍처.png|1050]]

| 구성 | 역할 | 이것만으로 증명되지 않는 것 |

| **JWD** | 자연어 질문, Skill 지침, MCP 연결·도구 호출, 결과 설명 | LLM이 SAP의 모든 업무 권한을 자동으로 따름 |

| **Integration Suite / Actions MCP** | 선택한 API를 도구화하고 실행 연계 | 모든 SAP API가 즉시 자연어 도구로 준비되어 있음 |

| **S/4HANA PCE** | 표준 업무 데이터·Custom 결산 데이터·CDS/OData·실행 프로그램 | 제공 소스만 가져오면 서비스가 자동 활성화됨 |

> [!warning] Agent 요청과 실제 실행은 별개
> `RequestAgentExecution`은 제공 소스에서 **`AGENT_RUNNING` 상태와 `AGENT_START` 이력**을 남기며, 외부 완료 콜백은 pending으로 설명된다. 이 Action이 있다는 사실만으로 감가상각/외화평가 실행과 최종 완료 동기화 전체가 연결되어 있다고 판단하지 않는다.

권한도 동일하다. 제공된 DCL에서 회사코드 PFCG 제약은 **DashExec·DashAgent**에 확인되지만, 다른 모든 조회에 같은 통제가 걸려 있다고 확대할 수 없다. 상세 객체·상태·권한은 [[삼성 결산 업무 AI 자동화 프로젝트/03 제공 자료 구조/02 RAP/01 RAP 백엔드 구조와 데이터 흐름|01 RAP 백엔드 구조와 데이터 흐름]]에서 확인한다.

## 7. Kyma MCP: 읽기와 결과 조회를 연결한다

약 **14:00–17:00**, **25:00–29:00**에는 조회/실행 분리와 MCP 배포본을 설명한다.

| 주제 | 영상 설명 + 소스에서 읽어야 할 범위 |
|---|---|
| 조회 | Insights는 읽기 전용을 기본 경계로 삼고 POST 실행을 막는 설명 |
| 업무 영역 | 결산 외 수익성·예산·자금 영역도 함께 포함. 모두 결산 필수 기능은 아님 |
| metadata | 실제 OData가 제공하는 EntitySet/필드를 읽어 허용된 서비스 안에서 질의 |
| 결과 보조 조회 | FX/AFAB의 **정확한 RequestID로 이미 실행된 결과를 읽는 경로** |
| AI Core | 연결을 위한 준비가 있으나 기본 비활성. 가동 중인 필수 엔진으로 설명하지 않음 |
| Actions 흔적 | Kyma 소스의 비활성 Actions는 설비보전 통지 초안 기능. 재무 실행과 별개 |
| 서비스별 Destination | 이 구현이 택한 연결·거버넌스 방식. MCP 일반 규칙으로 필수라고 단정하지 않음 |

소스의 결과 보조 조회는 **`REQUEST_ID_ONLY`** 검증 수준이다. 관찰된 상태와 ID 일치를 읽어도 사용자·회사/기간·TEST/UPDATE 모드를 모두 검증했다는 뜻은 아니다. **결과 조회 성공 ≠ 올바른 사용자가 올바른 범위의 실제 기표를 했다는 완전한 증거**다.

## 9. Destination과 Security Material: 소스 밖의 설정

약 **50:00–56:00**에는 Fiori, 업무별 Insights, FX/AFAB 결과 보조 조회, IS Actions를 위한 연결 설정을 설명한다. **60:10–61:00**에는 빈 파일의 이유를 직접 확인한다.

| 대상 | 설정이 맡는 일 | 따로 확인할 것 |
|---|---|---|
| Fiori → S/4 | AppRouter의 `/sap` 요청을 해당 OData로 연결 | Destination·Connectivity 바인딩과 SAP 권한 |
| Kyma Insights → S/4 | 서비스별 조회 경로 | Transparent Proxy·서비스 루트·허용된 서비스·인증 |
| FX/AFAB 결과 조회 | RequestID 기반 기존 실행 결과 읽기 | 실행과 다른 경로이며 결과의 업무 범위 검증 필요 |
| IS → S/4 | 실행 API와 CSRF 세션 요청 | Security Material 별도 등록·참조·실행 권한 |
| Cloud Connector | 내부/PCE 시스템 연결 | 기존 설정·관리 책임과 principal propagation 준비 |

**`06_Destination.txt`는 실제 0바이트다.** 발표자는 설명을 잊지 않으려고 빈 파일만 만들었고 실제 값은 BTP Cockpit에서 확인해야 한다고 답한다. 소스 수령 후 Destination이 자동으로 복원된다고 생각하면 안 된다.

연결 값·개인 계정·client ID/secret은 문서에 복제하지 않았다. 설명과 확인 지점: [[삼성 결산 업무 AI 자동화 프로젝트/03 제공 자료 구조/06 Destination/01 Destination과 연결 설정의 역할|01 Destination과 연결 설정의 역할]]

## 10. 권한 통제: 가장 중요한 미완성 경계

영상 앞부분 **10:40–13:30**에는 SSO/IAS와 BTP Role Collection을 설명하고, 후반 **61:00–63:00**, **70:00–74:30**에서는 사용자 전파가 완료되지 않았음을 다룬다.

| 계층 | 확인하려는 것 | 현재 자료로 판단할 수 있는 범위 |
|---|---|---|
| 로그인 | 누가 접속했는가 | OAuth/SSO, IAS 연계 설명 |
| BTP 앱 접근 | 누가 앱/도구에 들어갈 수 있는가 | User·Operator·Admin 계열 역할 설명·설정 |
| `who_am_i` | MCP가 인식한 호출자는 누구인가 | 신원 식별 도구의 존재 |
| SAP 사용자 전달 | S/4가 누구로 요청을 처리하는가 | **end-user 매핑/전파 종단 간 성공은 설명되지 않음** |
| 업무 권한 | 어떤 회사·업무·데이터·실행이 허용되는가 | 일부 PFCG DCL 소스, 기술 계정 연결, 후속 테스트 필요 |

> [!warning] 로그인과 권한 완료를 연결하지 않기
> `who_am_i`가 신원을 반환하거나 BTP 역할이 부여되어도, S/4가 최종 사용자의 권한으로 실행했다는 뜻은 아니다. 영상에서는 기술 계정 Destination, S/4·Cloud Connector의 principal propagation 미완성을 명시적으로 논의한다.

발표자는 MCP 보안 규격을 근거로 사용자 전파의 제약을 해석하지만, 이 설명을 **“MCP 표준은 모든 principal propagation을 금지한다”는 일반 규칙**으로 옮기지 않았다. 이 프로젝트에서 필요한 것은 선택한 인증 방식과 토큰 사용·사용자 매핑·SAP 권한이 실제로 맞는지 검증하는 일이다.

또 “Destination만 바꾸면 된다”는 낙관적 설명도 실제 성공 증거와 구별한다. **IS MCP + propagation 설정 + 권한 통제 테스트는 회의 후반에 이번 PoC 범위로 명시된다.** ASPN이 어디까지 맡는지는 IS 전문가와 후속 R&R 회의에서 정하기로 한 상태다.
