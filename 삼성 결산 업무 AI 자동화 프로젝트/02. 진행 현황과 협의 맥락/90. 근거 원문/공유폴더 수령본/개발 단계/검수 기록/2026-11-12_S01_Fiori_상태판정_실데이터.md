# S01 Fiori 상태 판정 — 실제 8·9월 데이터 점검

## 조회 범위와 개수

회사 `1710`, 템플릿 `MONTHLY CLOSING TEMPLATE`, 회계연도 `2026`, 원장 `0L`을 공통으로 사용했다. 기간만 `008`·`009`로 구분했다. 각 기간·엔터티 응답의 CycleUuid는 1종이며, count=반환 수이고 nextLink는 없었다. 모든 연도·회사·템플릿 전체를 조사한 결과는 아니다.

| 기간 | DashboardTasks | TaskInstances | Dashboard의 `에이전트 수행 완료` | 그중 HIGH/CRITICAL |
|---|---:|---:|---:|---:|
| 2026/009 | 41 | 43 | 0 | 0 |
| 2026/008 | 41 | 43 | 1 | 1 |

8월 TaskInstances에는 한글 Agent 완료가 3건이었다. Dashboard에 없는 2건은 기존 D01의 마스터 미연결 업무이며 우선순위도 비어 있다. 이번 완료·미결 Critical 중복 대상은 마스터와 연결되는 CASH010 1건이다.

첫 TaskInstances 진단 요청에는 Dashboard 전용 `SortOrder`를 함께 select해 HTTP 400이 발생했다. TaskInstances용 공통 필드와 Dashboard 전용 필드를 분리한 뒤 HTTP 200으로 재조회했다. 해당 400은 업무 상태 변경과 관계없는 요청 필드 오류이며 최종 재현 HTTP 파일은 수정된 필드를 사용한다.

## 실제 8월 응답 한 건과 현행 계산

개인정보·업무 결과·정확한 업무 UUID는 이 문서에 기록하지 않는다.

```json
{
  "TaskCode": "CASH010",
  "Status": "에이전트 수행 완료",
  "StatusText": "에이전트 수행 완료",
  "Priority": "HIGH",
  "ExecutionMode": "AGENT",
  "IsCompleted": false,
  "IsPriorityOpen": true
}
```

| 처리 위치 | CASH010의 계산 결과 |
|---|---|
| 결산 진행 현황의 완료 집계 | COMPLETED로 변환 → 완료 +1 |
| 결산 D-Day의 미결 Critical 집계 | 원문은 COMPLETED/SKIPPED가 아님 + HIGH → 미결 +1 |
| 에이전트 팀 | COMPLETED bucket → 완료 +1, 표시용 presentationStatus도 COMPLETED |
| 타임라인 | COMPLETED → AGENT_COMPLETED lifecycle |
| 우선순위 카드 | 원문 open=true → 후보. 이번 전체 데이터 계산에서는 실제 Top 5에도 포함 |
| 예정·D-Day 주의 목록 | open 후보가 될 수 있으나, 이번 전체 데이터 계산의 Top 5에는 CASH010이 없음 |
| 공통 상태 함수의 반환값 | 원문 상태를 그대로 검사 → semantic state None, status-in-process. 우선순위 실제 아이콘은 alert 고정이며 이 아이콘 함수를 사용하지 않음 |
| 예정 전체 보기의 서버 조건 | IsCompleted=false로 필터해도 CASH010 1건 조회됨 |

계산 모듈에 41건 전체를 전달한 결과는 다음과 같다. 이는 실제 API 입력에 대한 현행 함수 결과이며 브라우저 렌더링을 새로 관찰한 수치는 아니다.

| 기간 | 전체 | 완료 | 검토·승인 필요 | 오류·차단 | 미결 Critical | 진행률(모델값) | Agent 완료/미처리/검토 필요/오류 |
|---|---:|---:|---:|---:|---:|---:|---|
| 009 | 41 | 0 | 0 | 0 | 35 | 0% | 0 / 12 / 0 / 0 |
| 008 | 41 | 1 | 3 | 1 | 35 | 2.44% | 1 / 9 / 1 / 1 |

8월 우선순위 Top 5의 업무 코드는 `CLS010, INT010, AP010, AR010, CASH010`이었다. 동일 날짜 기준의 예정·주의 Top 5는 `CLS010, CLS020, INT010, AP010, AR010`이었다. 완료와 미결 Critical은 원래도 서로 보완적인 전체 분할이 아니지만, 여기서는 **같은 업무의 완료·미완료 판정 자체가 달라 중복 반영**된다.

추가로 8월 DashboardTasks에는 `처리 완료` 상태 2건도 있다. 현재 LegacyStatusCompatibility의 네 개 매핑에 없는 값이므로 정규화 후에도 미지 상태로 남는다. 이름만 보고 최종 완료 코드로 임의 치환하지 않으며, 업무상 의미와 공식 상태 대응표를 확인해야 한다.

## 소스와 재현 자료

- 화면별 상태 처리 요약·확인 질문·주요 코드 위치는 [[01_계획단계/2026-11-12 Fiori Dashboard 분석]] 2번에 정리했다. 우선순위 실제 바인딩은 `Dashboard.view.xml` 464행(고정 alert), 479~480행(원본 Status의 문구·색상)이다. `statusIcon` 함수는 같은 파일 422행의 D-Day 주의 목록에서 사용한다.
- GET 재현: 저장소의 `03_Fiori_App/http/fiori-status-compatibility.http` S01~S06. 모두 수정된 유효 필드 요청으로 200을 확인했다.
- 로컬 계산: `03_Fiori_App/http/.local-validation/evaluate-status.cjs`. 현재 모듈을 `vm`으로 읽어 실제 응답을 계산하며 네트워크·업무 Action을 실행하지 않는다.
- 최소 필드 응답과 `status-audit-result.json`은 기존 HTTP 폴더 ignore 정책에 따라 로컬에만 둔다. 사용자 ID·접속 비밀·실행 결과 원문은 수집하지 않았다.

원본 상태를 정비할지, UI·CDS·RAP 전체에 호환 처리를 적용할지는 담당자와 결정할 사항이다. 이번에는 그 결정을 앞두고 실제 사례와 영향 경로를 확인했으며 앱·데이터를 수정하지 않았다.
