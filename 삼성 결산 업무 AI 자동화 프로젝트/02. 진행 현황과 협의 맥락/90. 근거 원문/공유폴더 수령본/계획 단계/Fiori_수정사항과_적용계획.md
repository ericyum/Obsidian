# Fiori 수정사항과 적용 계획

**현재 상태: 요구사항과 개선 계획만 관리하며, 이 문서의 추가 요구사항·리팩터링은 코드에 미적용이다.** 기존에 동작하던 기능의 보존을 전제로 한다. 소스에서 구현을 확인한 항목도 실제 SAP/BTP 환경의 검증 완료를 뜻하지 않는다.

**2026-11-11 진행:** 로컬 AppRouter·CF SSH·Destination을 통한 실제 SAP 조회 경로를 확보하고, R-01의 조회·화면 이동을 1차 점검했다. [R-01 실행 기록](<../02_개발단계/검수기록/2026-11-11_R-01_Fiori_기준동작.md>)에 정상 동작·발견 사항·미실행 범위를 구분했다. 대시보드 41건 / 전체 Task 43건 차이와 이력/Issues 조회 문제를 먼저 확인한다. ZC01_* 물리 테이블 연결, 권한·업무 Action·최종 배포 검증은 미완료다.

**D01 후속 확인:** [마스터 연결 확인 기록](<../02_개발단계/검수기록/2026-11-11_D01_Task_Master_연결확인.md>)에서 Config 서비스의 마스터 2개 미조회와 참조 업무 18건(1~9월 각 2건)을 확인했다. 활성 CDS는 기존 zcls_* 테이블을 조회하며 마스터 INNER JOIN 때문에 대시보드에서 해당 업무가 제외된다. 복구 전 원래 업무와 UUID 대응 확인이 필요하다. 원인 확인은 수행했고, 데이터 정정과 재검증은 미실시다.

**S01 후속 확인(11/12 기록 연결):** [상태 판정 기록](<../02_개발단계/검수기록/2026-11-12_S01_Fiori_상태판정_실데이터.md>)에서 실제 API 응답을 현행 계산 함수에 적용해 같은 작업의 완료·미결 Critical 이중 판정을 확인했다. 현재 호환 매핑에 없는 `처리 완료` 값도 확인했다. API 응답과 함수 결과의 확인이며 새 브라우저 렌더링 검수나 수정 완료를 뜻하지 않는다. F-06의 상태 대응과 기존 기능 보존 검수에 반영할 근거로 연결하며, 요구사항·개선 범위와 계획 상태는 유지한다.

과제 번호는 [수행과제별 확인사항과 공수](<수행과제별_확인사항과_공수.xlsx>)를 따른다. F-번호와 R-번호는 이 문서 안에서 수정사항과 내부 개선을 추적하기 위한 번호다. 엑셀의 과제 번호나 공수를 대체하지 않는다.

## 1. 착수 구분

| 구분 | 의미 | 해당 작업 |
|---|---|---|
| 바로 착수 가능 | 기존 소스와 확정된 요구로 작업 범위를 정할 수 있음. 적용 전 회귀 기준 확보 필요 | 타임라인 상단 이동, 기존 기능 테스트 구성, 단계적 코드 분리 |
| 기존 구현 검증 우선 | 관련 코드가 이미 있어 요구사항과 실제 결과를 먼저 비교 | 전월 마지막 주 시작일, 기존 필터·차트·Top 5 |
| 연계 준비 필요 | 서비스·필드·용어·업무 규칙·권한 등의 정의가 있어야 구현을 확정할 수 있음 | 신규 환경 연결, 라벨, 사용자 Value Help, 상태 대응, Dynamic Link, 권한 검증 |

## 2. 수행과제와 Fiori 작업 연결

엑셀의 과제명·위치를 기준으로 연결한다. 아래 Fiori 세부 작업은 전체 수행과제 중 화면 담당자의 작업과 협업 범위를 구체화한 것이다.

기준 시트는 **과제별 현황·공수**다. A열은 과제 ID, B열은 과제명, G~K열은 범위·판단·확인사항·완료 기준·협업, M열은 Fiori/UI5 기준 공수(MD)다. 아래 과제 번호는 읽기 편하게 끝의 마침표를 생략했으며 원본 ID와의 대응은 같다.

엑셀은 2026-11-10에 읽은 저장본 기준이다. 파일 내부 수정 시각은 2026-11-10 13:52 KST이며, Excel에서 아직 저장하지 않은 편집 내용은 포함하지 않는다.

### 3.1 신규 환경 연결과 상태 대응

Fiori는 ZC01_* 물리 테이블을 직접 읽지 않고 CDS/OData 서비스를 통해 접근한다. 기존 앱의 엔터티·필드명, 키 타입, 탐색 관계와 Action을 최대한 유지하도록 서비스 계약을 먼저 비교한다. 화면의 조회 URL만 바꾸는 것으로 이관 완료를 판정하지 않는다.

2026-11-11 활성 SAP의 서비스 정의·핵심 CDS를 ADT 읽기로 확인한 결과, 현재 TaskInstances는 zcls_taskinst, Tasks는 zcls_taskmaster, Cycle은 zcls_cycle을 사용한다. 따라서 현재 SAP 조회 경로 확보와 신규 ZC01 이관은 별도 상태다. 정확한 확인 객체와 제한은 D01 기록을 따른다.

가능하면 API의 Status에는 일관된 코드를 제공하고 한국어 표시는 StatusText로 분리한다. 현재 LegacyStatusCompatibility에는 “미처리”, “오류 발생”, “에이전트 수행 완료”, “검토 완료”의 대응이 있으나 신규 상태 전체를 처리한다고 볼 수 없다. TASKM의 AI_AGENT/AIAGENT와 TINS의 AGENT도 필드별 의미를 확인한다.

완료·검토 완료·승인 대기·SKIPPED의 의미와 진행률/자동화율 분모를 합의해야 한다. 기존 코드와 새 Code List의 계산 차이를 리팩터링 중 조용히 변경하지 않는다. 합의된 업무 변경은 별도 수정사항과 기대값으로 기록한다.

### 3.3 캘린더와 D-day

TimelineHelper.defaultStartDate는 전월 말일을 기준으로 주 시작일을 계산한다. 주 시작 요일은 UI5 로케일 설정의 영향을 받는다. 1월의 전년도 이동, 윤년, 200건 초과 시 일정 표시 제한, 날짜가 없는 데이터도 검증한다. 일반 달력 월과 다른 회계기간 체계·특별기간은 FI 기준을 확인한다.

현재 D-day는 Dashboard.controller.js의 _setCycle에서 KeyDate를 사용한다. “선택 결산 월의 말일”과 같은 기준인지 확인해야 한다. 신규 샘플에는 기간 7과 KeyDate 2026-06-30이 함께 있으므로 기간 숫자만 보고 월말로 치환하지 않는다.

### 3.4 Dynamic Link와 권한

현재 대시보드의 내부 Task List/Object Page 이동과 미결항목 업무 앱 링크를 구분한다. 전달 Skill의 예시는 GLAccount-displayGLLineItemReportingView를 대상으로 하고 sap-iapp-state 값이 고정돼 있다. 실제 대상 환경에서 지원하는 필터 전달 방식과 화면 상태 생성 방식을 먼저 확인한다.

PPT와 Skill의 계정 목록이 다르고, “최근 3개 회계기간”과 “최근 3개월 날짜 범위”의 표현도 다르다. 회사·기간·계정의 최종 기준을 맞춘 뒤 정상 링크, 연도 경계, 조건 누락, 권한 없는 사용자 진입을 검증한다.

Joule/MCP는 확정 조건으로 링크를 생성하고, Fiori/UI5는 대상 화면의 진입·조건 적용을 확인한다. FI/RAP·QA는 실제 조회 결과와 권한을 검증한다. 권한은 버튼 표시뿐 아니라 백엔드의 데이터·Action 접근 제어와 실제 실행 사용자까지 확인한다.

R-01의 1차 결과는 [[02_개발단계/검수기록/2026-11-11_R-01_Fiori_기준동작]]을 따른다. 현재 정상 조회·목록/상세 이동 기준은 일부 확보했으며, 엔터티 간 건수 차이와 백엔드 조회 문제 및 대량/실패/Action/권한 시험이 남아 있다. R-02 착수 전에 우선 추가 Task 2건의 마스터 연결과 서비스 계약을 확인한다. 이 확인은 F-03/F-06과 병행할 준비 작업이며 신규 요구사항 구현을 자동 승인한 것으로 보지 않는다.

마스터 연결 원인 확인은 D01 후속 점검으로 수행했다. 다음은 마스터 2개와 참조 업무 18건의 원래 업무 대응을 FI/RAP에서 확인하고 복구 방식을 결정하는 단계다. 화면에서 2건을 숨기거나 조인을 변경해 건수만 맞추지 않는다.

11월 11일 추가 추적에서 영향 18건 중 16건이 완료 상태임을 확인했다. 현재 마스터 41개는 활성 seed의 UUID·코드와 모두 일치하지만, 문제 두 UUID는 활성 소스·조회 가능한 seed 과거 버전·상태이력·인수 Excel에서 원래 업무로 연결하지 못했다. [[02_개발단계/검수기록/2026-11-11_D01_Task_Master_연결확인|D01 원본 추적 기록]]에 FI/RAP·원 개발사에 요청할 원본 마스터/UUID 대응과 보존 기준을 정리했다. 원본 확인 전 복구·seed 실행·구조 변경은 진행하지 않았으며 R-02는 미착수다.

현재 FE의 FPM 대시보드 + List Report + Object Page 구성을 활용한다. UI5 버전 변경, 전면 재작성, 업무 집계 규칙 변경과 구조 정리를 한 변경에 섞지 않는다. HashChanger 등 URL 처리 방식 전환은 실제 standalone/FLP 경로 검증 후 별도 판단한다.

## 7. 기존 기능 보존과 완료 판정

- 동일 데이터·시간·언어 조건에서 기존 수치, 표시, 정렬, 필터와 이동 결과를 비교한다. F-01 같은 명시적 화면 변경은 그 항목의 기대 결과만 갱신한다.
- 작업 0·1·100·101·200·201건 이상을 시험한다. 200건 초과 시 타임라인 제한, 별도 카드/요약 조회, Agent 전체 페이징을 보존한다.
- 검색 A 직후 B를 실행하고 A가 늦게 도착해도 B 결과가 유지되는지 확인한다. 부분 실패·화면 종료·재진입 시 로딩과 오류 표시도 확인한다.
- 담당자·검토자·승인자 선택, 저장, 재조회와 작업 시작·완료·검토·승인·재오픈·AI 요청의 허용/거부를 테스트 환경에서 확인한다.
- 화면 mock 성공과 실제 RAP 업무 동작을 구분한다. 확인하지 않은 항목은 NOT_RUN으로 남기며 검증 증거 없이 완료 처리하지 않는다.
- 변경을 작은 단위로 관리한다. 실패하면 해당 변경을 되돌리고, 기존 결함을 발견하면 별도 기록해 구조 정리와 기능 수정을 구분한다.
