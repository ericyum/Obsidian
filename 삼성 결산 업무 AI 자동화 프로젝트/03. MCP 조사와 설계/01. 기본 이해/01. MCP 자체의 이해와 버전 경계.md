# MCP 자체의 이해와 버전 경계

## 1. MCP는 무엇을 표준화하는가?

**AI 애플리케이션이 외부 도구·자료를 발견하고 호출하며 결과를 받는 통신 계약**이다. SAP API가 ‘업무 기능을 호출하는 계약’이라면, MCP는 그 기능을 AI 애플리케이션 쪽에 일관된 방법으로 보여주는 경계다. MCP 서버에 LLM이 반드시 들어가는 것은 아니다.

| 구성 | 역할 | 삼성물산에서의 대응 |
|---|---|---|
| Host | 대화·모델·도구 사용·사용자 경험 관리 | Joule Work/Joule 환경. 정확한 제품·버전 확인 필요 |
| MCP Client | Host 안에서 MCP 메시지를 교환 | Joule 측 커넥터 |
| MCP Server | 사용할 Tool과 입력·결과를 제공 | 우리 MCP 또는 IS가 노출하는 MCP |
| 업무 백엔드 | 권한·계산·상태 전이·실제 업무 처리 | ABAP/RAP/OData, 필요한 IS 연계 |

그림은 목표 책임 구분이다. 배포 위치를 확정하거나 현재 연결 성공을 주장하지 않는다. 편집: [[MCP-01 책임과 실행 경계.excalidraw]].

## 2. Tools·Resources·Prompts는 어떻게 다른가?

| 기능 | 제공하는 것 | 우리 적용 후보 |
|---|---|---|
| Tools | 실행 가능한 기능과 입력 스키마 | 결산 현황 조회, TEST 접수, 실행 결과 조회 |
| Resources | 식별 가능한 자료 | 긴 실행 보고서·매뉴얼의 참조 |
| Prompts | 재사용 가능한 프롬프트/작업 양식 | 지원 클라이언트에서 선택하는 안내 |

**표준에 있다는 것과 Joule이 실제 소비한다는 것은 별개**다. Resources 읽기를 지원하지 않으면 권한 검증이 있는 별도 조회 Tool로 상세 내용을 가져오는 대안을 둔다. MCP Prompt와 Joule Skill도 같은 개념으로 취급하지 않는다.

## 3. MCP가 해결해주지 않는 것은 무엇인가?

MCP를 연결해도 회계 규칙의 정확성, 고객별 권한, 장시간 실행의 영속성, 동일 업무의 중복 방지, 승인, 문맥 압축, 지식 검토가 자동으로 생기지 않는다. HTTP 성공이나 정상 Tool 응답도 **요청 접수·SAP 완료·업무 최종 완료** 중 무엇을 증명하는지 따로 정의해야 한다.

## 4. 최신 규격을 알아도 현장에 바로 적용하면 안 되는 이유

조사 당시 `latest`는 **2026-07-28**로 연결됐다. 아래는 큰 차이만 정리한 것으로 SDK 구현을 대체하는 명세가 아니다.

| 영역 | 2025-11-25 계열 | 2026-07-28 |
|---|---|---|
| 시작·상태 | initialize 기반 능력 교환; HTTP 세션 가능 | 요청별 버전/능력, 프로토콜 세션 제거, server/discover |
| 장시간 Tasks | 코어의 실험 기능 | 선택 확장 `io.modelcontextprotocol/tasks` |
| 완료 획득 | tasks/result 등 구 방식 | tasks/get polling 중심, tasks/update·tasks/cancel |
| 응답 종류 | 이전 결과 형식 | resultType으로 일반 완료·추가 입력·확장 task 구분 |

**기술 문서의 ‘MCP는 initialize로 시작한다’와 ‘MCP는 stateless다’가 모두 보일 수 있다. 버전이 다르기 때문이다.** 새 프로토콜의 무상태성은 업무 DB·실행 이력을 없애라는 뜻이 아니다. 업무 상태는 명시적 ID와 영속 저장소로 관리한다.

우리 출발점은 최신 버전을 강제하는 것이 아니라 **실제 Joule↔IS↔MCP 각 구간의 공통 지원 버전을 고정**하는 것이다. SDK 버전·transport·인증·Tool 출력 지원도 함께 기록한다. 서버가 최신 Tasks만 반환하고 Joule은 일반 결과만 기대하면 통신이 연결돼도 사용 경험이 깨질 수 있다.
