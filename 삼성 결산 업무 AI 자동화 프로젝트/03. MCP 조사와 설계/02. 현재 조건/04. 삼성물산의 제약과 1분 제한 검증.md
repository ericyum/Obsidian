# 삼성물산의 제약과 1분 제한 검증

## 1. 지금 설계의 출발점은 무엇인가?

**ABAP/RAP API 구축을 기다리는 MCP 담당자의 사전 설계**다. 기존 PoC를 그대로 복제할 계획이 아니며, 고객·SAP의 범위와 구현 방식은 아직 일부 협의 중이다. 이전 문서에 나온 CF 우선·IS 병행과 Teams의 전환 제안을 곧바로 확정 토폴로지로 합치지 않는다.

| 구분 | 현재 근거 | 설계에 주는 영향 |
|---|---|---|
| 역할 | 사용자: 우리 팀 ABAP/RAP·MCP, 본인 MCP | 계약·효율·오류·관측은 주도하고 회계 로직은 협업 |
| 데이터 | ZC01 기반 새 서비스 예정; 기존 검수는 ZCLS 경로 | 엔터티명·필드명을 현재 코드에 묶지 않음 |
| 실행 | FCV/AFAB 실행·결과 조회·Task 반영 요구 | 긴 실행과 짧은 호출을 분리할 필요 |
| 업무 기준 | 완료·승인·Agent 완료·KPI 기준 미결 | Tool 자체가 임의로 상태를 정규화해 최종 완료로 처리하지 않음 |
| 시간 | **사용자가 Teams 회의에서 약 1분 sync 제한을 들음** | 잠정 제약으로 보존. 어느 계층인지 확인 필요 |
| 최신 환경 | 제품 edition·runtime·MCP 버전 미확정 | 동작하는 공통 기능부터 사용 |

## 2. 공개 자료의 60초는 모두 같은 제한인가?

**아니다. ‘기본값’, ‘상한’, ‘한 호출’, ‘전체 turn’은 서로 다른 값이다.**

| 근거 | 설명되는 대상·값 | 확인 수준과 제한 |
|---|---|---|
| 사용자 회의 전달 | Joule sync 약 1분 | 프로젝트 입력. 녹취 위치·제품·제한 계층 미확인 |
| SAP A2A 기술 글·Architecture 색인 | 외부 code-based agent와의 동기 **A2A 60초** | 공식 검색 발췌로 확인; 직접 본문 접근 제한. 일반 MCP 호출로 확대 불가 |
| SAP Help Joule Studio classic 색인 | MCP Tool 응답 대기 **기본 200초** | 검색 색인 확인; 본문 추출 실패. JWD 환경의 설정을 증명하지 않음 |
| SAP IS 공식 GitHub 문서 | API 기반 MCP의 HTTP receiver **기본 60000ms** | 본문 확인. 백엔드 대기 설정이며 고정 최대치라는 설명 아님 |
| 로컬 Kyma Helm | Insights APIRule `timeout: 60`, Actions는 30인 인수 설정 | 정적 파일의 값. 현재 배포값·Joule 제한으로 간주하지 않음 |
| 로컬 서비스 설명 | pending은 같은 RequestID로 60초 후 읽고 재실행 금지 | 조회 간격 안내. 단일 호출을 60초 붙잡으라는 뜻 아님 |

따라서 **‘실제 한도는 200초니 회의 설명이 틀렸다’고 결론 내리지 않는다.** 제품과 계층이 다를 수 있다. 당장 설계는 짧은 호출을 지향하고, 설정·시험으로 실제 end-to-end 한도를 확정한다.

## 3. 무엇을 물어보면 한도가 확정되는가?

1. 사용하는 것은 JWD인가, Joule Studio classic인가, 다른 runtime인가? 버전·build는?
2. 약 1분은 모델을 포함한 전체 turn인가, MCP Tool 하나인가, IS receiver인가, proxy idle timeout인가?
3. 시작 시점은 요청 도착인가 실제 실행 시작인가? queue 대기도 포함하는가?
4. 진행 알림을 보내면 idle timeout이 갱신되는가? 전체 상한은 따로 있는가?
5. 시간이 끝나면 요청만 끊는가, Job 취소를 시도하는가? 에러 이후 대화는 계속되는가?
6. 다음 사용자 turn에서 기존 실행 ID를 조회할 수 있는가? 자동 재개는 어떤 기능으로 가능한가?

## 4. 60초를 잠정 예산으로 다루는 법

가정 예시: 전체 turn이 60초라면 모델 판단·최종 응답·네트워크·여유 시간을 빼야 한다. 서버 timeout을 60초로 잡으면 다른 시간은 이미 예산 밖이다. 단일 Tool 제한이라면 여러 Tool의 합계는 별도 turn 한도와 다시 대조한다.

**현재의 설계 제안:** 조회·접수·상태 확인은 수초 수준 목표로 설계하고, 긴 회계 작업은 ID를 반환해 분리한다. 실제 수치·SLA는 측정 전 미확정이다.
