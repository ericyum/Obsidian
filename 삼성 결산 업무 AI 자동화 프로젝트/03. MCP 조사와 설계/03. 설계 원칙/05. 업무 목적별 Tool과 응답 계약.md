# 업무 목적별 Tool과 응답 계약

적용 갱신: **2026-11-17** · 아래 이름·payload는 별도 표기가 없으면 **설계 제안**이다.

## 1. 좋은 Tool 경계는 무엇인가?

**사용자가 이해할 수 있는 업무 행동이면서, 서버가 범위·권한·효과·결과를 통제할 수 있는 단위**다. API 하나마다 Tool을 만들거나 모든 행동을 자유 프롬프트 하나로 받는 것을 기본안으로 삼지 않는다.

| 기준 | 삼성물산에서 확인할 것 |
| --- | --- |
| **선택 명확성** | 현황 조회·TEST 접수·결과 확인·Task 결과 반영·예금 확정을 구분 |
| **왕복 최소화** | Cycle→마스터→인스턴스를 CDS/API가 결합; 이미 받은 확정자·시각은 재조회 생략 |
| **효과 분리** | 조회가 상태를 바꾸지 않고, TEST도 Job·로그를 생성함을 명시 |
| **의미 보존** | 회사·회계기간·통화·분모·기준시각·완전성을 유지 |
| **복구 가능성** | 오류와 기존 실행 ID를 주고, 재조회와 새 실행을 구분 |

## 2. 표면 Tool 이름과 업무 계약을 나눈다

`financial_close_insights`에 `view=close_status`를 둘지 독립 현황 Tool로 나눌지는 **v0.6-Z D-11의 미결**이다. 기존 이름을 유지하면 Connector·Skill 변경이 줄고, 별도 Tool이면 효과와 필수 입력을 좁혀 설명하기 쉽다. 같은 질문으로 선택 정확도·호출 수를 비교해 결정한다. **Tool 13개나 prepare/submit 2개를 먼저 고정하지 않는다.**

어느 표면을 택해도 **읽기 / Job 접수 / 결과 반영 / 예금 확정**은 서로 다른 효과와 권한을 갖는다. 구체적인 노출 후보는 [[10. 삼성물산 MCP 설계 후보와 권장안]].

## 3. 입력은 업무 범위와 신뢰 경계를 표현한다

- **회사·회계연도·기간:** 필수 범위 또는 신뢰된 기본값을 명시한다. 회사 없는 ‘이번 결산’은 되묻는다. 회계기간을 달력 월로 단정하지 않는다.
- **필터:** 허용된 업무 필드를 OData 질의로 컴파일한다. 모델 입력으로 자유 `$filter`·URL·SQL·ABAP 실행명을 받지 않는다.
- **ID:** 백엔드가 반환한 Cycle·Task·ResultUUID·RequestID를 후속 호출에 쓴다. 임의 생성·다른 기간 재사용을 막는다.
- **금액·시각:** 백엔드 금액·통화·정밀도를 보존한다. wire 타입을 metadata로 확인하고 내부 계산 때문에 JavaScript 부동소수점으로 강제 변환하지 않는다. UTC 원시 시각과 KST 표시의 관계를 고정한다.
- **사용자:** 인증 주체와 업무 권한을 신뢰 경로로 전달한다. 모델이 보낸 `RequestedBy`나 회사 필터는 권한 증거가 아니다.

기간 `'002'` 요청에 `'2'` 응답이 오는 보통예금 사례는 **타입·표시 정규화 계약**으로 풀고 문자열 불일치 때문에 다른 기간으로 판정하지 않는다. 원래 의미를 바꾸는 범용 변환은 추가하지 않는다.

## 4. 결과는 답변에 필요한 최소 증거를 준다

S/Z 명세의 공통 `{summary, rows[], links[], request_id}`를 출발점으로 삼고 **scope·as_of·complete·경고·페이지 정보**를 어디에 둘지 D-10에서 합의한다. 아래는 **부분 결과의 업무 payload 예시**이며 실제 API·MCP wire 메시지가 아니다.

```json
{
  "summary": {"total_count": null, "completed_count": null},
  "rows": [],
  "links": [],
  "request_id": "Q-example",
  "scope": {"company_code": "4310", "fiscal_year": "2026", "fiscal_period": "008"},
  "as_of": "2026-11-17T18:00:00+09:00",
  "complete": false,
  "warnings": ["집계와 목록의 정합성을 확인하지 못했습니다."]
}
```

4310·기간·시각은 **설명용 예시**다. 위 `rows=[]`는 전체 0건을 증명하지 않으며, 미확정 전체 수를 0으로 채우지 않는다. 완전성은 **요약·목록·원천별로 필요한 범위**를 명시하고 전체 `complete`와 충돌하지 않게 정의한다.

`structuredContent`·출력 schema·짧은 설명의 실제 Joule 지원을 확인한다. JSON text 호환 복제가 필요하더라도 양쪽 결과를 모델 문맥에 중복 투입하는지 측정한다.

## 5. 같은 빈 배열이라도 의미는 다르다

| 상황 | 반환해야 할 의미와 다음 행동 |
| --- | --- |
| **Cycle 없음** | 대상 결산 차수를 찾지 못함. 정상 업무 0건과 구분 |
| **정상 0건** | 권한·조회·완전성을 확인한 조건에서 0건 |
| **권한 거절/권한으로 제외** | 존재 노출 정책 안에서 거절·범위를 표시. 전체 회사 데이터 0건이라고 답하지 않음 |
| **join 누락·소스 일부 실패** | 검출된 불일치 또는 부분 결과와 제외 범위. 확정 분모처럼 집계하지 않음 |
| **다음 페이지 존재** | 반환 건수·전체 건수의 확인 여부·cursor를 구분 |
| **진행 중/접수 불명** | 정상 조회 결과 또는 기술 오류와 업무 상태를 각각 표시. 완료 안내 금지 |
| **다건 쓰기 일부 거절** | UUID별 결과·성공·거절·확인 필요를 유지. 전체 성공/실패 한 값으로 압축하지 않음 |

MCP가 원천을 모르면 조인 누락을 자동 발견할 수 없다. **무결성 점검·집계 API의 보장·대조 fixture**가 필요하며, 한 페이지가 성공했다고 `complete=true`로 만들지 않는다.

오류는 `retryable=true` 하나보다 **허용되는 다음 행동**을 함께 정의한다. 예: `read_existing_request`, `refresh_selected_rows`, `ask_for_reason`, `contact_owner`. 이는 제안 필드이며 실행 POST 재시도를 허용하는 신호로 쓰지 않는다.

## 6. 도구 설명의 최소 항목

**언제 사용 / 필요한 범위 / 조회인지 변경인지 / 반환 의미 / 완료 판정 / 실패 뒤 할 일 / 짧은 예시**를 적는다. 설명으로 권한을 강제했다고 보지 않고 서버·백엔드에서 검사한다. 보통예금 실제 적용은 [[14. 보통예금 조회와 항목별 확정 설계]], 오류·권한의 기준은 [[09. 권한 중복 실행과 결과 불명 처리]].
