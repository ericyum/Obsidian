# 업무 목적별 Tool과 응답 계약

## 1. API를 그대로 노출하면 왜 부족한가?

개발자는 여러 API의 관계와 키를 알고 호출하지만, 에이전트는 이름·설명·현재 문맥으로 다음 행동을 고른다. 같은 업무에 비슷한 Tool이 많거나 모델이 수백 행을 직접 합쳐야 하면 잘못 고르거나 근거를 빠뜨리기 쉽다.

**좋은 경계는 ‘사용자가 의미를 이해할 수 있는 업무 행동’이면서 ‘서버가 범위·시간·권한을 통제할 수 있는 단위’다.** 하나의 거대한 `do_finance(prompt)`도, 테이블별 모든 CRUD 노출도 기본안으로 삼지 않는다.

## 2. 어떤 기준으로 경계를 정하는가?

| 기준 | 좋은 상태 | 나쁜 신호 |
|---|---|---|
| 선택 명확성 | 이름·설명만으로 언제 쓰는지 구분 | 기능이 겹치는 Tool 여러 개 |
| 호출 수 | 자주 함께 읽는 관련 정보를 제한된 크기로 반환 | task마다 master·status·history를 반복 조회 |
| 권한 경계 | 조회·TEST·실제 반영을 구분 | 읽기 Tool이 몰래 상태 변경 |
| 복구 가능성 | 오류 코드·다음 행동·ID 제공 | 모든 실패를 ‘다시 시도’로 안내 |
| 의미 보존 | 기준일·분모·통화·완전성 유지 | 한 페이지를 전체처럼 요약 |

Anthropic의 목적별 도구 설계는 참고하되, 회계의 확인·승인 경계까지 편의를 위해 하나로 합치지 않는다.

## 3. RAP와 독립적인 입력 계약부터 정하기

예: `close_get_overview(company_code, fiscal_year, fiscal_period, ledger)`는 회사·회계기간별 결산 개요를 요구한다. 실제 엔터티·서비스 URL은 RAP adapter가 연결한다.

- 기간을 달력 월로 임의 변환하지 않는다. 특별기간·템플릿·회차가 있으면 모호성을 해소한다.
- 금액은 정밀도 손실을 피하는 decimal 문자열+통화로 약속한다. 반올림·환산은 합의한 서버 규칙을 따른다.
- 자유 형식 OData `$filter`, SQL, URL, 임의 ABAP 실행명을 모델에게 입력시키지 않는다. 업무 필터를 허용 목록에 매핑한다.
- 식별자는 사람이 읽는 코드·이름과 후속 호출용 안정적 ID를 함께 준다. 모델이 UUID를 생성·추측하게 하지 않는다.
- 설명에는 사용 시점, 사용하지 않을 시점, 부작용, 필수 조건, 결과 의미, 실패 후 행동을 짧게 적는다.

## 4. 결과는 ‘답변에 필요한 최소 증거’로 구성

다음은 **업무 payload 제안**이며 확정 RAP 응답이나 완성된 MCP wire 메시지가 아니다.

```json
{
  "schema_version": "close.overview.v1",
  "scope": {"company_code": "1710", "fiscal_year": "2026", "fiscal_period": "007", "ledger": "0L"},
  "as_of": "2026-11-15T01:00:00Z",
  "completeness": "complete",
  "kpi_definition_version": "proposal-v1",
  "summary": {"total": 56, "completed": 12},
  "items": [],
  "returned_count": 0,
  "next_cursor": null,
  "warnings": [],
  "trace_id": "trace-example"
}
```

위 56·12는 **설명용 가상 수치**다. `items=[]`는 요약 전용 결과라서 빈 것이며, 목록 도구라면 빈 결과와 반환 누락을 구별해야 한다. 구현 시 `view=summary/detail` 또는 Tool별 outputSchema로 의미를 고정한다.

`structuredContent`와 사람이 읽는 짧은 설명을 활용하되, 클라이언트 호환을 위해 JSON text 복제가 필요할 수 있다. 양쪽이 같은 문맥에 들어가면 토큰이 중복되므로 **클라이언트가 모델에 실제 전달한 형식**을 확인한다. 큰 원문을 양쪽에 무조건 복제하지 않는다.

## 5. 페이지·오류가 만드는 오해를 막기

| 반환 상황 | 약속할 의미 |
|---|---|
| 정상 빈 결과 | 조회 성공, 해당 조건에서 0건 |
| 일부 소스 실패 | `partial`, 실패 범위·시간·미포함 지표 표시 |
| 다음 페이지 있음 | cursor·반환 건수·총건수의 확인 여부 표시 |
| 권한 거부 | 데이터 없음으로 위장하지 않고 허용된 오류 범위로 구분 |
| 진행 중 | `isError=false`인 정상 상태 조회 결과, 완료 아님 |
| 실행 도구 실패 | tool execution error와 업무 코드를 구분. 입력 보정 가능 여부 표시 |

목록 API의 cursor pagination과 MCP `tools/list`의 pagination은 다른 계약이다. outputSchema도 ‘LLM이 schema대로 답했다’가 아니라 **서버 결과의 구조 계약**이다.
