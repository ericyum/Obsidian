# 메모리와 컨텍스트를 나누는 설계

## 1. ‘메모리 관리’에서 무엇을 관리하는가?

**모델이 지금 읽는 문맥, 다음 대화에도 남길 지식, 업무의 실제 상태, 서버 RAM은 서로 다르다.** 이들을 하나의 memory 저장소로 다루면 오래된 지식이 현재 잔액처럼 사용되거나 프로세스 재시작에 실행 이력이 사라질 수 있다.

편집: [[MCP-03 문맥 기억 업무 상태.excalidraw]].

| 대상 | 무엇을 담는가 | 책임과 보존 |
|---|---|---|
| 모델 컨텍스트 | 현재 요청·Tool 정의·필요한 결과 | Joule 하네스. 서버는 결과 크기·참조로 간접 지원 |
| 대화 압축/노트 | 진행 요약·남은 일 | Host 기능 확인 필요. 서버는 대화 전체를 소유하지 않음 |
| 업무 실행 상태 | operation ID·RequestID·대상·모드·상태·결과 참조 | 권위 있는 영속 저장소. 대화 요약으로 대체 불가 |
| 경험 지식 | 검증된 오류 조치·적용 범위·버전·출처 | 검토 가능한 지식 관리 절차 |
| 응답 캐시 | 재사용 가능한 조회 결과 | 권한·scope·시점·무효화 조건 포함 |
| 서버 RAM | 연결·제한된 버퍼·작업 중 변수 | 크기·동시성 상한. 영속 Job 저장소로 쓰지 않음 |

## 2. 무엇을 기억하고 무엇을 다시 조회하는가?

최신 Anthropic memory 실험은 기억의 선별과 원문 대조를 다룬다. 우리에게 중요한 적용은 **변하는 현재 사실은 다시 조회하고, 재사용할 지식은 출처와 검증 상태를 붙이는 것**이다. 기억을 많이 저장하는 것 자체가 품질은 아니다.

| 내용 | 권장 취급 |
|---|---|
| 현재 잔액·Task 상태·사용자 권한 | SAP/권한 원천에서 조회. 과거 대화·벡터 검색을 정답으로 쓰지 않음 |
| 이번 실행의 ID와 TEST 모드 | 구조화 상태에 보존. scope와 함께 재확인 |
| 오류 해결 사례 | SAP 메시지 ID·조건·버전·승인자·검증 결과와 함께 검색 |
| 사용자 ‘2번으로 해결’ 피드백 | 후보 증거. 자동으로 검증된 회사 공통 지식으로 승격하지 않음 |
| 스풀 전체·긴 로그 | 제한된 저장소에 보존하고 필요한 부분만 조회 |

## 3. RAP 전에도 결정할 수 있는 기억의 계약

경험 검색 결과는 `case_id / message_id / applicable_scope / source / reviewed_status / version / evidence_ref`처럼 출처와 적용 조건을 반환하는 안을 제안한다. 초기에는 정확한 메시지 ID·키워드·검토된 소수 매뉴얼로 시작하고, 검색 실패가 확인될 때 벡터 검색을 평가한다. MCP를 쓰려면 벡터 DB가 필수인 것은 아니다.

영속 실행 기록은 **실행 ID·업무 범위·모드·접수/실행 상태·결과 참조·버전·갱신시각**을 구분한다. 기존 SAP RequestID와 기록으로 충족하면 그 원천을 사용한다. 별도 operation ID·저장소·고정 schema는 필수가 아니다. 저장 책임은 RAP 또는 별도 승인된 오케스트레이터 중 하나로 명확히 정하고, 두 곳이 동시에 정답이 되는 구조를 피한다.

## 4. 캐시는 기억과 다르다

OpenAI prompt caching은 반복 prefix 계산 재사용이고, SAP 응답 캐시는 업무 데이터 재사용이다. 전자는 조회를 대신하지 않고 후자는 모델의 사고를 저장하지 않는다.

조회 캐시 키에는 최소 tenant·권한 범위·회사·기간·원장·필터·계약 버전이 들어가야 한다. 사용자의 권한 변경을 반영할 무효화도 필요하다. Task 상태·실행 결과는 fresh read를 우선하며, 오래된 응답을 허용하면 `as_of`와 stale 표시를 반환한다. **캐시 히트 때문에 다른 사람의 데이터가 보이면 최적화 실패다.**

## 5. 새 프로젝트 자료에 적용하기

**S2 오류 검색**은 약 15건의 매뉴얼을 메시지 클래스·번호+Task → 키워드 → 벡터 보조로 찾는 방향이다. CAP 검색 입력·출력·검토 상태·로그 ID 연결은 합의할 계약이며, 벡터 DB나 사용자 피드백의 자동 지식 승격을 기본 기능으로 확정하지 않는다.

**보통예금**은 조회에 이미 있는 확정자·시각·경로를 현재 질문에 사용하되, 쓰기 전에는 현재 상태·권한과 확인 대상을 다시 대조한다. 과거 대화에 ‘일치’라고 남았다는 이유로 새 확정을 허용하지 않는다. 상세는 [[14. 보통예금 조회와 항목별 확정 설계]].

**CF 재시작** 뒤에도 실행 RequestID·결과 반영 근거를 백엔드에서 찾아야 한다. 별도 MCP DB·두 번째 operation 저장소는 기존 SAP 기록으로 해결하지 못하는 요구가 확인될 때 저장 책임과 함께 선택한다.

## 6. 우리의 우선순위

① 영속 실행 ID·상태 → ② 필요한 결과만 반환 → ③ 상세 재조회 → ④ 검토된 오류 지식 → ⑤ 측정 후 캐시·검색 고도화 순서다. 자동 dreaming·self-learning은 최신 연구로 이해하되 회계 지식의 무검토 자동 갱신으로 채택하지 않는다.
