# 토큰 지연과 서버 자원 최적화

## 1. 무엇을 줄이는 것이 목표인가?

**정확한 업무 결과를 유지하면서 모델 왕복·불필요한 데이터·서버 대기를 줄이는 것**이다. 토큰 수만 줄여 회사·기간·TEST 구분·출처가 사라지면 비용은 줄고 위험은 커진다.

설명용 비용 모델:

`turn 시간 ≈ 문맥 준비 + 각 단계(모델 판단 + Tool 대기) + 최종 응답`

`문맥 크기 ≈ 지시 + 활성 Tool 정의 + 대화 + 이번 판단에 남긴 결과`

이 식은 설계 관점의 분해다. 병렬 호출·캐시·스트리밍으로 실제 값은 달라지므로 실측을 대신하지 않는다.

## 2. 어떤 개선부터 하는가?

| 방법 | 기대 효과 | 잃지 말아야 할 것 |
|---|---|---|
| 서버 필터·projection·집계 | 불필요 행·열·LLM 합산 제거 | scope·정확한 전체 분모·계산 기준 |
| 업무별 overview | 작은 API를 여러 번 고르는 단계 감소 | 권한·부분 실패·시간 상한 |
| 요약+상세 조회 | 큰 스풀을 매번 읽는 비용 감소 | 상세 접근 권한·근거 ID |
| 결정적인 Tool 목록·버전 | 예측 가능한 discovery·캐시 | 권한별 노출과 실제 호출 검증 |
| 제한된 병렬 읽기 | 독립 조회의 대기 감소 | snapshot 일관성·부하 상한 |
| 결과 캐시 | 반복 조회 부하 감소 | 현재성·권한 분리·무효화 |

**순차 의존성이 있는 쓰기를 병렬화하지 않는다.** 회사별 업무 잠금·선행 Task·승인 단계는 속도를 위해 생략할 수 없다.

## 3. 최신 Tool Search·코드 실행은 바로 쓰면 되는가?

Anthropic의 도구 검색·코드 호출은 정의와 중간 결과의 문맥 비용을 줄이는 방법이다. 하지만 Host의 지원이 필요하고, 검색 단계가 추가돼 작은 도구 집합에서는 오히려 지연이 늘 수 있다. OpenAI의 관리형 하네스 기능도 같은 이유로 Joule 지원과 구별한다.

우리 기본안은 **작은 고정 Tool 집합과 서버의 결정적 집계**다. MCP 안에 임의 Python/SQL 실행이나 두 번째 LLM을 넣어 최신 패턴을 흉내내지 않는다. 필요가 입증되면 별도 권한·sandbox·예산·평가를 갖춘 확장으로 다룬다.

## 4. 서버 RAM·연결·대기열에도 상한이 필요하다

한 요청이 스풀 전체를 메모리에 올리거나 페이지를 무제한 순회하지 않게 한다. API 응답 byte 한도·허용 행 수·페이지 수·fan-out·연결 pool·동시 실행·대기 queue를 각각 제한한다. 소비자가 느려도 생산자가 무한히 쌓지 않게 하는 것이 backpressure다.

| 상한 후보 | 초기 시험값 예시, 승인된 운영값 아님 | 초과 시 행동 |
|---|---|---|
| 목록 page size | 기본 20, 최대 100 | 다음 cursor 제공 |
| 읽기 fan-out | 최대 3 | 나머지는 순차 또는 범위 축소 |
| overview 출력 | 약 8KiB부터 평가 | 상세 분리, completeness 유지 |
| 단일 내부 재시도 | 안전한 읽기 1회부터 평가 | 남은 시간 없으면 중단 |

byte는 token과 다르며 한국어·숫자·JSON에 따라 비율이 변한다. 토큰 수를 못 얻으면 UTF-8 bytes를 **대리 지표**로 명시한다. 이 숫자를 실제 제품 제한처럼 사용하지 않는다.

## 5. 내부 명세의 한도를 어떻게 평가하는가?

v0.6-Z §12.8/D-12의 **조회10초·pageSize200·maxPages10·p95 목표5초**와 위의 설명용 값은 서로 다른 **검토용 수치**다. 실제 Connector·범위별 데이터·CF 메모리·동시 사용자로 측정해 하나의 한도표로 확정한다. 어느 숫자도 현재 SLA·제품 제한으로 채택하지 않는다.

- **C1:** 회사·Cycle·사용자 권한을 S/4로 push-down하고 CDS의 KPI와 목록을 받는다. `$batch`의 한 HTTP 왕복은 단일 SQL·동일 snapshot 보장이 아니므로 시점 계약을 확인한다.
- **보통예금:** 현재 확정자·시각·경로는 `find_check_results`에 포함되므로 해당 질문에는 이력을 추가 호출하지 않는다. 상세 근거가 필요한 경우만 추가 조회한다.
- **Spool:** 결정적 파서·구조화 테이블의 필요한 행/금액을 반환한다. 원문 전체를 LLM에 보내 회계 합계를 맡기지 않는다.
- **초과/부분:** 페이지·byte·시간 한도에 도달하면 `complete=false`와 확인된 범위·후속 조회 방법을 유지한다. 잘린 로그·빈 응답을 오류 없음으로 바꾸지 않는다.

이 설계의 구체적 원인은 [[04. 삼성물산의 제약과 1분 제한 검증]], 보통예금의 호출 예는 [[14. 보통예금 조회와 항목별 확정 설계]].

## 6. 개선이 성공했는지 어떻게 보는가?

같은 데이터·질문·모델·권한으로 후보 A/B를 비교한다. Tool 호출 횟수, 응답 bytes/tokens, p50·p95·p99, timeout 비율, 정확한 scope·근거 유지율, 최종 업무 효과를 함께 측정한다. 평균만 개선되고 p99나 중복 실행이 악화되면 채택하지 않는다.

연쇄 단계 성공확률의 설명용 예: 각 단계가 독립적으로 98% 정확하다면 5단계는 약 90.4%, 10단계는 약 81.7%다. **독립성·98%는 가정이며 모델 실측이 아니다.** 불필요한 왕복을 줄일 동기를 설명할 뿐, 필수 승인·검증 단계를 없앨 근거는 아니다.
