# 동기 호출과 장시간 작업의 연결

## 1. ‘동기/비동기’는 어느 계층을 말하는가?

**비동기 Python 함수, HTTP 스트림, MCP Tasks, SAP 백그라운드 Job, 에이전트 중단·재개는 서로 다른 기능**이다. 서버 코드가 `async def`라고 해서 Joule이 비동기 프로토콜을 이해해야 하는 것은 아니다.

| 계층 | 의미 | 호환성 판단 |
|---|---|---|
| 서버 구현 | I/O를 비동기 처리 | 외부 응답 계약이 같으면 Host에 투명 |
| 단일 Tool 호출 | 결과가 돌아올 때까지 Host가 기다림 | 제한 안에 유효한 결과를 반환해야 함 |
| 업무 실행 | 회계 Job이 호출 뒤 계속 진행 | 짧은 접수와 후속 조회로 연결 가능 |
| MCP Tasks 확장 | 일반 결과 대신 표준 Task handle 반환 | 정확한 버전·양쪽 지원 필요 |
| Host interrupt/resume | 실행을 보존하고 이벤트로 이어감 | 하네스 기능. 서버가 단독으로 만들 수 없음 |

## 2. 사용자가 말한 비대칭은 어떤 문제인가?

동기 Host가 완료 결과만 기대하는데 서버가 지원되지 않는 Task 형식이나 나중 callback만 제공하면 처리하지 못한다. 반대로 비동기 Host도 timeout·프로토콜·스키마가 맞지 않으면 동기 Tool을 사용할 수 없다.

이를 보통 **호환성·실행 계약 불일치, capability mismatch, sync/async impedance mismatch**로 설명한다. **비가역성**은 이 문제의 일반 명칭이 아니다. 시간 제한이 있는 호출을 더 오래 기다리게 하는 wrapper만으로 장시간 실행이 해결되지 않는다.

## 3. 추천 후보: 업무는 비동기, 각 MCP 응답은 짧게 완료

![[MCP-02 짧은 호출과 긴 업무.png|1000]]

편집: [[MCP-02 짧은 호출과 긴 업무.excalidraw]]. 그림의 시간은 **설계 예시**, 자동 알림·재개는 미확인이다.

1. `prepare`가 scope·모드·정책을 검증하고 서버가 발급한 실행 의도 ID를 보존한다.
2. `submit`은 같은 의도 ID로 작업을 한 번 접수하고 **접수 상태와 operation ID**를 반환한다.
3. Joule은 “TEST 작업을 접수했다. 아직 결과는 없다”고 답할 수 있다.
4. Job은 승인된 영속 worker/SAP 실행 체계에서 계속 진행한다.
5. 다음 사용자 요청 또는 지원이 확인된 스케줄러가 `get_status`/`get_result`를 짧게 호출한다.

**일반 MCP Tool 호출의 반환 데이터 안에 operation ID를 넣는 것**과 **프로토콜의 Tasks 확장 결과를 반환하는 것**은 다르다. 전자는 일반 결과를 읽고 ID로 다른 Tool을 부르는 기본 능력만으로 구현 후보를 만들 수 있다. 실제 Joule이 ID를 유지·사용하는지는 시험해야 한다.

## 4. 진행 알림·SSE는 시간 제한을 없애지 않는다

진행 알림이 idle timeout을 갱신하는지는 구현 선택이다. 공식 규격도 별도의 최대 timeout을 권고한다. SSE 연결이 있다는 사실만으로 끊긴 뒤 자동 재개나 durable Job을 보장하지 않는다. 특히 2026-07-28은 이전의 SSE 재전송·resumability와 다르므로 버전별 동작을 시험한다.

Job 접수 후의 연결 단절은 **업무 롤백이나 취소 완료 증거가 아니다**. 수명 주기를 요청 핸들러의 RAM/background coroutine에만 묶지 말고, 영속 접수와 worker 인수를 보장해야 한다.

## 5. 시간 예산을 어떻게 나누는가?

최대 대기 예산을 `B`라고 할 때, 연결·인증·queue·백엔드·응답 직렬화·네트워크와 여유 시간을 모두 포함한다. 하위 deadline은 상위 deadline보다 짧아야 한다. 전체 turn 한도라면 모델 시간과 여러 Tool도 합산한다.

가정: 60초 turn에서 모델 판단/응답 15초, 네트워크·인증 5초, 여유 10초라면 Tool들의 **합계 예산은 30초**다. 세 번의 호출에 각각 30초를 주는 것은 같은 예산이 아니다. 이것은 실측이 아닌 예산 설명이다.

## 6. 제한된 polling과 재개 정책

- `retry_after_ms`는 다음 조회의 최소 간격 안내이며 Host가 잠들거나 자동 재개한다는 보장이 아니다.
- 같은 turn 안의 무한 polling은 금지한다. 빠른 1회 상태 확인 뒤 진행 중이면 결과를 사용자에게 돌려주는 후보부터 시험한다.
- 자동 후속 알림이 미지원이면 “나중에 자동으로 알려드리겠다”고 약속하지 않는다. 재조회할 ID·링크를 제공한다.
- 신규 Tasks 확장은 양쪽 지원과 IS 중계 보존이 확인될 때만 추가한다. 구버전 Tasks API와 혼용하지 않는다.
