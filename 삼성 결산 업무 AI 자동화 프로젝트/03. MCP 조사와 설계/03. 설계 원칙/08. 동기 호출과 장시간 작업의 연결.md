# 동기 호출과 장시간 작업의 연결

적용 갱신: **2026-11-17** · 상태: **FCV/AFAB 계약을 위한 설계 제안**

## 1. 어느 계층의 비동기인가?

**서버의 비동기 I/O, HTTP 스트림, MCP Tasks, SAP Job, Joule 중단·재개는 각각 다른 기능**이다. 긴 Job을 접수한 뒤 짧은 일반 Tool 결과로 RequestID를 반환하고, 후속 Tool로 조회하는 구조부터 검증할 수 있다.

| 계층 | 확인할 계약 |
| --- | --- |
| 한 Tool 호출 | Host가 지원하는 형식으로 시간 안에 응답 |
| SAP 실행 | 영속 접수·중복 방지·Job 실행·결과 저장 |
| 후속 대화 | 같은 RequestID를 찾아 status/result 조회 |
| MCP Tasks 확장 | 실제 client·중계·서버의 동일 버전 지원 |
| 자동 재개·메일 | 책임자·trigger·전달·실패 처리가 있는 별도 기능 |

이 불일치는 **호환성/실행 계약 불일치**로 설명한다. 단순히 기다리는 wrapper를 늘려 업무 영속성이나 Host 재개를 만들 수는 없다.

## 2. 삼성물산의 실행 흐름 후보

![[MCP-02 짧은 호출과 긴 업무.png|1000]]

[확대·검토용 SVG](../../99.%20스크린%20샷%20및%20다이어그램/03.%20MCP%20조사와%20설계/MCP-02%20짧은%20호출과%20긴%20업무.svg) · 편집: [[MCP-02 짧은 호출과 긴 업무.excalidraw]]. 그림은 **논리 흐름 제안**이며 현재 배포 경로가 아니다.

1. **대상·모드 확인:** 회사·연도·기간·업무·TEST 모드를 검증하고 실행 RequestID의 발급·보존을 약속한다.
2. **POST 접수:** 선택된 MCP 경로에서 실행 API로 한 번 전달한다. 백엔드는 같은 ID의 중복을 처리하고 영속 접수 뒤 상태를 반환한다.
3. **짧은 응답:** ‘접수됨, 실행 결과는 아직 없음’과 실제 RequestID를 돌려준다.
4. **같은 ID readback:** FCV/AFAB `RunSet('실제ID')`에서 상태·오류·결과를 조회한다. 통신 실패와 SAP Job 실패를 구분한다.
5. **업무 결과 검증:** FINISHED와 업무 성공을 구분하고 대상·모드·메시지·구조화 결과의 의미를 확인한다.
6. **결과 반영:** 합의된 호출자가 `update_close_task_result` → RAP `updateTaskResult` 계약으로 Task/HIST를 반영하고 재조회한다. 이 이름은 계획 명칭이며 현재 HE4 구현 완료를 뜻하지 않는다.

**별도 prepare Tool·intent ID·operation ID를 무조건 추가하지 않는다.** 기존 `REQUEST_ID_ONLY` readback 계약은 실제 RequestID로 조회하는 출발점이다. 새 업무의 승인·영속 접수에 추가 식별자가 꼭 필요하면 목적과 저장 책임을 합의한다. RequestID만 안다고 provenance·회사·모드·권한까지 검증됐다는 뜻은 아니다.

## 3. 실행 상태와 결과 반영 상태를 분리한다

| 마지막 확인 상태 | 허용할 다음 행동 | 금지할 오해 |
| --- | --- | --- |
| 입력 거절·미전송 확인 | 입력 보정·현재 권한 확인 | 이미 접수됐다고 안내 |
| 전달 후 접수 불명 | 기존 RequestID·접수 기록 대사 | 새 ID로 자동 재POST |
| PENDING/RUNNING | 같은 ID 조회·대기 안내 | 최종 완료 저장 |
| FINISHED, 업무 결과 미확인 | 오류·대상·모드·결과 확인 | 기술 종료만으로 기표 성공 |
| 업무 성공, Task 반영 미완료 | 해당 실행 근거로 결과 반영·재조회 | 회계 Job 전체 재실행 |
| Task/HIST 반영 완료 | 현재 관리 상태·결과 안내 | 같은 결과로 이력 무한 추가 |
| 명시적 새 실행 | 합의된 새 RequestID 발급 | 기존 조회와 새 실행을 혼용 |

결과 반영 API는 중복·늦게 도착한 옛 실행·현재 상태와의 충돌을 검증해야 한다. **조회→반영 사이 동시 변경**까지 포함한 계약은 [[11. RAP와 Joule 담당자에게 필요한 계약]].

## 4. polling·progress·timeout을 각각 검증한다

- S본 Q-16 / Z본 D-16의 **10초×12회는 잠정안**이다. 전체 turn·Tool timeout이 확인되기 전 MCP 내부 대기 루프로 구현하지 않는다.
- **같은 ID로 한 번 상태를 확인하고, 진행 중이면 결과와 재조회 방법을 돌려주는 안**부터 검증한다. 자동 후속 호출은 Joule/SAP 측 지원이 확인된 경우에만 약속한다.
- `retry_after_ms`는 조회 간격 안내다. MCP가 자동으로 poll하거나 새 Job을 시작하라는 뜻이 아니다.
- progress·SSE는 최대 시간과 업무 영속성을 보장하지 않는다. HTTP 연결 종료·취소 ACK를 SAP 중단·롤백 완료로 처리하지 않는다.
- MCP Tasks의 `completed`도 Tool 업무 성공과 동일하지 않다. Tasks를 도입하면 **프로토콜 상태→Tool 결과→SAP 업무 결과→Task 반영**을 따로 판정한다.

하위 deadline은 상위 예산 안에 둔다. 전체 turn 예산이면 모델·인증·queue·여러 Tool·응답 시간의 합계를 확인한다. 실제 시간값의 출처는 [[04. 삼성물산의 제약과 1분 제한 검증]].

## 5. 알림은 결과 반영 뒤의 별도 효과다

R&R v0.3은 **IS Mail 대신 S/4 CL_BCS/SAPconnect** 방향을 ‘11/16 결정’으로 기재한다. 결과 반영 뒤 메일을 보내며 메일 실패가 업무 결과 반영을 되돌리지 않는다는 문서 계약도 있다. 실제 합의·설정·발송은 미검증이다.

**ZEN의 발송 코드·수신자·중복 방지와 SAP Basis의 SCOT/SMTP/송신 Job/SOST**를 구분한다. 알림만 다시 보내야 할 때 회계 실행이나 결과 반영을 반복하지 않는다. 상세 담당·근거는 [[02. 확정 전달과 미결 사항]].
