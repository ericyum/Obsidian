# 권한 중복 실행과 결과 불명 처리

## 1. 왜 timeout을 실패와 동일하게 보면 안 되는가?

요청이 SAP에 도착해 실행됐지만 응답만 잃었을 수 있다. **‘응답을 못 받음’은 ‘실행 안 됨’과 다르다.** 특히 실제 기표라면 같은 요청을 다시 보내는 것이 장애보다 큰 문제를 만든다.

| 상황 | 서버가 아는 사실 | 다음 행동 |
|---|---|---|
| 입력 검증에서 거부 | 업무 요청을 보내지 않음 | 입력 보정 후 새 검증 |
| 접수 확인 | operation/backend ID 확보 | 동일 ID 상태 조회 |
| 전송 후 응답 유실 | 실행 여부 불명 | `submission_state=unknown`, 기존 ID·의도 ID로 대사 |
| 기술 Job 종료 | 실행 프로세스 종료 | 대상·모드·업무 결과·오류·Task 반영 검증 |
| 취소 요청 접수 | 취소 의사 전달 | 최종 취소 여부 재조회. 완료와 경합 가능 |

## 2. 서로 다른 ID를 구별한다

| ID | 의미 | 동일 업무 반복을 막는가? |
|---|---|---|
| JSON-RPC request ID | 한 통신 요청과 응답 매칭 | 아니오 |
| trace ID | 계층별 로그 연결 | 아니오 |
| operation ID | 영속 업무 실행 조회 | 조회·대사의 기준 |
| SAP RequestID | 백엔드 실행 식별 | 실제 백엔드 계약에 따라 확인 |
| intent/idempotency key | 같은 실행 의도를 재전송해도 중복 부작용 방지 | 저장·검증·트랜잭션 구현이 있어야 가능 |

같은 업무 키+같은 payload는 기존 실행을 조회/반환하고, 같은 키+다른 payload는 충돌로 거부하는 계약을 제안한다. tenant·인증 주체·업무 종류·scope·모드의 결합과 보관 범위를 정한다. 기존 RequestID로 이를 충족할 수 있으면 별도 intent/operation ID나 prepare Tool을 추가하지 않는다. 기존 `REQUEST_ID_ONLY`는 readback 입력 계약이며 업무 성공·권한 증명과는 별개다. 새 정당한 재실행은 명시된 새 실행으로 구분한다.

## 3. 키 하나를 넣는 것만으로 exactly-once가 되지 않는다

MCP가 key를 저장한 뒤 SAP 호출 직전에 죽거나, SAP 접수 뒤 기록 전에 죽을 수 있다. **영속 접수·unique 제약·backend correlation·상태 재조회·중복 거부**가 함께 있어야 한다. RAP/SAP가 같은 키로 조회·중복 방지를 지원하지 않으면 서버 단독으로 완벽한 exactly-once를 보장하지 못한다.

기본 약속은 ‘정해진 범위에서 중복 부작용 억제와 결과 대사’로 명시하고 장애 구간을 시험한다. 재시도 소유 계층도 하나로 정한다. Joule·MCP·IS·RAP가 각각 자동 retry하면 횟수가 곱해질 수 있다.

## 4. 승인과 권한을 모델 인자에 맡기지 않는다

- 사용자 ID·회사 권한을 모델이 입력한 문자열만으로 신뢰하지 않는다. 검증된 호출 주체와 업무 권한을 서버에서 대조한다.
- `confirmed=true`는 사용자가 실제 확인했다는 보안 증거가 아니다. 확정이 필요한 작업은 신뢰된 채널의 확인 내용과 실제 대상·모드·사유·현재 버전을 결합해야 한다. payload hash·확인 토큰은 가능한 구현 후보이며 현재의 필수 API 필드로 단정하지 않는다.
- TEST도 서버 자원을 쓰고 로그·업무 상태를 바꿀 수 있으므로 단순 read-only로 표시하지 않는다.
- 실제 기표 Tool은 별도 승인·계약이 확인되기 전 기본 집합에서 제외하는 **설계 제안**이다. 고객의 기능 범위를 임의로 삭제한다는 뜻은 아니다.
- Task 완료를 모델이 임의 저장하는 범용 `set_status(COMPLETED)`는 피한다. 실행 근거를 확인하는 서버 업무 처리로 제한한다.

## 5. MCP 특유의 경계도 지킨다

Tool description·조회 문서·오류 매뉴얼에 적힌 문장은 데이터일 수 있다. “권한을 무시하라” 같은 문서를 시스템 지시로 승격하지 않는다. 인증 token의 audience를 검증하고 downstream에 무분별하게 그대로 전달하지 않는다. 임의 URL과 resource 참조는 SSRF·외부 전송 경계를 확인한다.

operation ID를 알고 있다는 사실도 권한이 아니다. 조회·결과·취소마다 사용자/tenant 권한을 확인한다. 로그에는 token·인증 header를 남기지 않고, 업무 본문은 승인된 최소 범위·보존 기간을 정한다.

## 6. 최신 명세의 사용자·쓰기 경계를 평가한다

v0.6-Z의 **P1 사용자 전파**는 IAS↔S/4 매핑·Destination·실제 처리 사용자와 권한 시험이 필요하다. **P2 기술계정+사용자 헤더**는 대안 구상이며, 헤더가 신뢰된 인증 경로에서만 생성되고 외부 입력은 제거되는지, S/4가 허용된 대리 범위와 행위자를 검사하는지 확인해야 한다. `AUTHORITY-CHECK ... FOR USER` 문구만으로 안전한 전파가 검증된 것은 아니다.

보통예금 `RequestedBy`와 `ExecutedBySAPUser`를 구별한다. **UUID를 알고 있음·CSRF 토큰 보유·mcp.execute scope·회사 필터**는 각각 SAP 업무 권한과 사용자 확인의 대체물이 아니다. 조회/쓰기/집계의 허용·거절을 실제 사용자별로 확인한다.

**다건 확정**은 UUID별 결과를 보존하고 성공 건 재전송을 막는다. 원본 API는 GUI의 오래된 화면 검사004를 보장하지 않으므로 현재 값과 확인 대상의 일치를 별도로 계약한다. 최종 COMMIT 실패·응답 유실은 재조회/대사가 우선이다.

**CSRF 예외:** 보통예금 XLSX F10은 명시적 `403 + x-csrf-token: required` 뒤 재발급·재전송을 설명한다. 이 응답이 업무 미실행을 확실히 뜻하는지 검증한 제한된 회복과, timeout·5xx·일반403의 맹목 POST retry를 구분한다. 공통 HTTP 클라이언트의 자동 POST retry는 끄는 방향으로 합의한다. 상세는 [[14. 보통예금 조회와 항목별 확정 설계]].

## 7. 어떤 로그가 복구에 필요한가?

`trace_id, operation_id, attempt, tool/schema version, authenticated scope, backend_request_id, started/finished_at, deadline, outcome, submission_state, execution_status, error_code, output_bytes, data_as_of`를 연결한다. `not_sent / sent_unknown / accepted / terminal`은 자연어 한 줄보다 복구에 유용하다.

모델 비공개 사고 과정은 수집 대상이 아니다. 실행 시도·접수·완료·결과 반영을 확인할 관측값을 남긴다.
