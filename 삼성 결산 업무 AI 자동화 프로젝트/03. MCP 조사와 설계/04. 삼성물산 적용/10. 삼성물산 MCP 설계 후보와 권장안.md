# 삼성물산 MCP 설계 후보와 권장안

상태: **조사자가 제안하는 설계 후보. 사용자·SAP가 선정하거나 구현한 설계가 아님.**

## 1. 무엇을 목표로 삼는가?

**RAP API가 정해지면 교체 가능한 얇은 연결을 두되, Joule이 짧은 호출로 업무 상황을 정확히 이해하고 장시간 TEST 결과를 다시 찾게 한다.** 새 에이전트 하네스를 개발하는 것이 현재 목표는 아니다.

## 2. 세 후보를 비교한다

| 후보 | 장점 | 우리 조건에서의 비용·위험 | 판단 |
|---|---|---|---|
| A. RAP CRUD별 Tool | 자동 생성·초기 매핑 단순 | 모델이 키·조인·상태를 조합, 호출·문맥 증가 | 제한된 관리/진단용 후보 |
| **B. 목적별 Tool + 짧은 접수·조회** | 시간 제약에 대응, 결과 의미와 복구 계약 명확 | 업무별 계약·영속 상태 책임 합의 필요 | **우선 검증 권고** |
| C. MCP 내부 자율 AI 에이전트 | 복잡한 탐색·계획을 서버가 수행 | Joule 아래 추가 모델 루프·비용·중단/재개·timeout | 필요 입증 전 보류 |

Thin MCP는 줄 수가 적다는 뜻이 아니다. **회계 규칙과 권한·상태 변경은 백엔드가 책임지고, MCP는 사용자 행동에 맞는 도구 계약과 응답·시간 경계를 책임진다**는 뜻이다. 이름만 wrapper여도 내부에 무한 polling·상태 저장·LLM이 들어가면 역할은 두꺼워진다.

## 3. 첫 번째로 검증할 Tool 묶음

아래 이름은 **논리 계약 초안**이다. 기존 Tool 이름이나 확정 RAP Action 이름이 아니다. 실제 개수는 평가로 조정한다.

| Tool 후보 | 역할 | RAP·업무 측에 요구할 능력 |
|---|---|---|
| `close_get_overview` | 회사·회계기간·회차의 KPI·주의 업무 요약 | 일관된 집계 정의·scope·권한 |
| `close_get_task` | Task 상세·현재 단계·허용 행동·최신 결과 | 안정적 ID·이력·상태 의미 |
| `close_prepare_test` | FCV/AFAB TEST 조건 검증·실행 의도 생성 | 유효성·권한·필수 조건·만료 |
| `close_submit_test` | 준비된 의도로 TEST 접수 | 멱등 접수·RequestID·짧은 ACK |
| `close_get_execution` | 진행 상태·결과 요약·다음 조회 안내 | 정확한 ID 조회·현재성·결과 확인 |
| `close_read_evidence` | 제한된 결과표/오류 근거의 다음 페이지 | 권한 있는 artifact·row 범위 |
| `close_find_resolution` | 검토된 오류 조치 검색 | 메시지 ID·지식 출처·적용 조건 |

`close_prepare_test`에서 발급한 의도는 **승인 자체가 아니다**. 사용자 확인이 필요한 범위라면 신뢰된 Joule/UI 확인 증거와 연결한다. 확인 채널이 없으면 `submit`을 공개하지 않는 방안도 검토한다. 자동 TEST는 별도의 사전 승인 정책으로 처리하며 사용자 확인을 위조하지 않는다.

보통예금 TR006은 장부·증명서 대사와 확정 계약이 갖춰진 뒤 별도 업무 Tool을 평가한다. Excel은 validate/preview와 commit을 분리하는 후보이며, 파일 업로드·참조의 실제 Joule 지원부터 확인한다. 모든 과제를 첫 Tool 묶음에 억지로 넣지 않는다.

## 4. 결과 payload 예시

```json
{
  "schema_version": "close.execution.v1",
  "operation_id": "op-example",
  "backend_request_id": "sap-example",
  "scope": {"company_code": "1710", "fiscal_year": "2026", "fiscal_period": "007", "ledger": "0L"},
  "execution_mode": "TEST",
  "submission_state": "accepted",
  "execution_status": "running",
  "business_outcome": "not_available",
  "task_update_status": "not_started",
  "retry_after_ms": 10000,
  "as_of": "2026-11-15T01:00:00Z",
  "result_ref": null,
  "trace_id": "trace-example"
}
```

이는 일반 Tool 결과에 넣는 **업무 JSON 예시**다. 2026 MCP Tasks의 `Task` schema를 구현한 예가 아니다. `running`이면 Tool 호출은 성공했어도 회계 작업 완료는 아니다. 기술 실행 성공, 회계 검증, Task/HIST 반영을 각각 확인한다.

## 5. 배포 위치와 기능 계약은 나누어 결정

CF/CAP와 IS API 기반 MCP 중 어느 쪽이든 위 의미를 유지해야 한다. IS에서 API 자동 노출이 가능해도 필요한 timeout·출력 shaping·멱등 키·인증 전파·오류 계약을 보존하는지 확인한다. 부족한 부분은 RAP façade나 승인된 adapter 위치에서 처리한다.

**MCP 담당자가 IS 내부 구현까지 무조건 소유한다는 뜻은 아니다.** Tool 계약과 end-to-end 검증을 주도하고 IS 담당자와 경계를 합의한다. 실제 플랫폼 선택은 SAP 지원·서비스 플랜·runtime과 기존 배포 제약을 보고 정한다.

## 6. 기본안에 넣지 않는 것과 확장 조건

| 보류 대상 | 추가를 검토할 조건 |
|---|---|
| protocol Tasks | Joule·IS·서버의 동일 버전/확장 지원을 실제 확인 |
| 자동 알림·resume | 승인된 scheduler와 전달 채널·재개 계약 확보 |
| 벡터 DB·자동 기억 | 정확한 검색의 한계와 지식 검토 체계 확인 |
| 서버 내부 LLM | 결정적 조회·계산만으로 풀리지 않는 요구와 예산 입증 |
| 대량 Tool 검색 | 최소 Tool 집합으로 정확도/범위를 만족하지 못함 |
