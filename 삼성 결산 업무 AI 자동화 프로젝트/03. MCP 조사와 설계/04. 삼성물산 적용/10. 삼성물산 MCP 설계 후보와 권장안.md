# 삼성물산 MCP 설계 후보와 권장안

갱신: **2026-11-17** · 상태: **자료를 바탕으로 한 설계·착수 순서 제안. 채택·배포 전**

> [!abstract] 우선 검증할 방향
> **목적별 Tool + CDS/RAP의 공통 업무 정의 + 짧은 접수·정확한 ID 조회 + 별도 결과 반영**을 권장한다.
> 현재 내부안인 **CF Custom MCP 신규 구축**을 상세화하되, SAP 협의용 **IS MCP안**과 구분한다. 구현 스택·Tool 개수·Joule/Skill 담당 변경은 미확정이다.

## 1. 어떤 문제를 풀려는가?

**Joule이 결산의 현재 상태를 정확히 설명하고, 필요한 TEST·결과 확인·확정을 안전하게 이어가도록 한다.** 기존 Kyma 폴더를 옮기는 것보다 **업무 계약과 검증 조건을 새 RAP/OData에 맞추는 것**이 이 설계의 대상이다. 다른 재무 예제 전체·새 AI 하네스·무검토 자동 학습은 기본 범위로 추가하지 않는다.

## 2. 좋은 MCP의 기준을 현장 근거에 적용한다

| 일반 기준 | 삼성물산 근거 | 구체적인 설계 후보·이유 | 수용 증거 |
| --- | --- | --- | --- |
| **도구 선택이 분명함** | C1/S1/S1-R/S2와 예금 확정은 효과가 다름 | 조회·접수·결과 확인·반영·확정을 구분. 권한·완료 의미가 다른 효과를 한 호출에 숨기지 않음 | 같은 한국어 질문의 올바른 Tool·모드 선택 |
| **작은 문맥으로 정확히 답함** | 41/43 누락, KPI 완료 판단 차이 | CDS/API가 join·판정·집계. MCP는 scope·기준시각·완전성을 보존 | 같은 사용자·Cycle의 Fiori/Joule 수치 대조 |
| **긴 업무를 이어감** | FCV/AFAB 접수·readback·Task 반영 | 짧은 호출+RequestID, POST와 결과 반영 분리 | timeout·재시작 뒤 기존 실행 조회 |
| **사용자 통제·권한** | IAS↔S/4 매핑 미결, RequestedBy와 실행 사용자 분리 | 신뢰 사용자 전파·읽기/쓰기 권한·확인 대상 결합 | 다른 회사·타인 ID의 허용/거절 |
| **부분 실패에서 복구** | confirmMultiple 항목별 결과, COMMIT 실패, 취소 없음 | UUID별 성공·거절·불명을 유지하고 재조회 | 성공 건을 재전송하지 않는 복구 |
| **연결·운영이 지속됨** | S/Z 경로 차이, D-09 스택 미결 | Connector·인증·버전·한도·관측을 먼저 인수 | 실제 tools/list·call·오류·권한 시험 |

## 3. 기능 경계의 세 후보

| 후보 | 장점 | 비용·깨지는 조건 | 판단 |
| --- | --- | --- | --- |
| **A. OData CRUD별 Tool** | 초기 자동 노출·개별 API 진단이 쉬움 | 모델이 여러 테이블을 결합·계산하고 호출이 증가. 업무 상태·권한 경계를 놓칠 수 있음 | 제한된 관리·진단용으로 평가 |
| **B. 목적별 Tool + 짧은 호출** | 업무 효과·입력·결과·복구가 명확 | CDS/API의 집계·멱등·반영 계약이 필요. 기존 Skill과 이름을 맞춰야 함 | **우선 검증 권장** |
| **C. MCP 내부 자율 AI** | 서버가 별도 탐색·계획 가능 | Joule 아래 모델 루프·문맥·비용·재개 책임 추가 | 현재 필요를 입증할 때 재검토 |

**B를 택하는 이유:** 현재 문제는 대화 모델을 하나 더 넣는 것보다 **업무 의미·권한·실행 상태를 정확히 전달하는 계약**으로 먼저 줄일 수 있기 때문이다. Thin MCP는 입력 검증·인증·범위 검사·오류 처리를 생략한다는 뜻이 아니다. 회계 계산·업무 판정·트랜잭션의 기준을 백엔드에 두고 MCP는 AI용 인터페이스와 시간·응답 경계를 책임진다.

## 4. 업무별로 어떤 도구를 먼저 검토하는가?

아래는 **자료의 명칭을 사용하는 논리 묶음**이다. 실제 이름·노출 개수는 D-11 및 담당자 합의로 정한다.

| 업무 묶음 | 기존/명세 명칭 | 필요한 계약 | 판단 |
| --- | --- | --- | --- |
| 사용자·C1 현황 | `who_am_i`, `financial_close_insights` | 사용자 식별과 실제 권한을 구분, 공통 CDS 집계·scope·complete | **읽기 연결 우선 후보** |
| 보통예금 | `find_check_results`, `confirm_check_results`, `get_confirmation_history` | 계좌 grain·상태·UUID별 결과·신뢰 확정자 | **API 계약을 구체화할 첫 사례**. HE4 준비 후 연결 |
| S1 TEST | `post_foreign_currency_valuation_run`, `post_depreciation_simulation` | TEST 모드·RequestID·영속 접수·중복·exact readback | 실제 실행 API 계약 확보 후 |
| 결과·반영 | readback, `get_spool_summary`, `update_close_task_result` | 구조화 결과·업무 성공·Task/HIST·늦게 도착한 이전 실행 결과 차단 | 접수와 함께 계약하되 별도 효과로 노출 |
| S2 오류 검색 | `search_error_manual` / CAP 지원 | 메시지 ID→키워드→벡터 보조, 근거·적용 범위 | 검토된 소수 매뉴얼부터 평가 |
| 실제 기표·업로드·링크 | Q-17, 과제별 API/파일/링크 | 승인·대상·입력 경로·저장·실패 의미 | 고객 범위를 삭제하지 않고 **실행 준비 조건을 미결로 관리** |

보통예금은 계약이 가장 구체적인 사례지만 **HE4 API가 준비됐다는 뜻은 아니다.** C1·보통예금 중 실제 읽기 계약과 정답 fixture를 먼저 확보한 쪽으로 첫 연결을 시작한다. 현황이 준비되기 전에 예금 쓰기나 반대로 모든 과제를 기다리는 일정은 고정하지 않는다.

별도 prepare Tool·두 번째 operation 저장소·signed receipt를 현재 필수로 추가하지 않는다. 기존 결과 읽기의 `REQUEST_ID_ONLY`와 새 실행의 멱등·확인 계약을 구분한다. 상세는 [[08. 동기 호출과 장시간 작업의 연결]]·[[09. 권한 중복 실행과 결과 불명 처리]].

## 5. 배포 경로는 별도의 결정이다

| 자료별 경로 | 현재 의미 | 채택 전에 필요한 증거 |
| --- | --- | --- |
| **v0.4-S: Joule/Skill → SAP IS MCP → S/4** | 반성훈 팀장의 SAP 협의안. 신규 Custom MCP 설명 제외 | SAP의 Tool 등록·전파·오류/시간·E2E 인수 |
| **v0.6-Z: 기존 Joule Connector → 신규 CF Custom MCP → S/4·CAP** | 내부 수행 방향. Kyma 코드 미사용, §12는 검토안 | SAP Connector 수용, D-09 스택, CF Space·인증·연결·운영 |

**현재 상세화는 CF 신규안을 중심**으로 한다. 다만 S본이 폐기됐거나 CF가 이미 배포됐다고 선언하지 않는다. 같은 목적별 Tool 계약이 어느 경로에서 보존되는지 확인하고, IS를 CF 앞이나 뒤에 임의로 끼우지 않는다.

Node.js/TypeScript·CAP·MCP SDK·SAP Cloud SDK/CAP remote·validator·Streamable HTTP는 **D-09의 후보**다. 선택 기준은 실제 Connector 호환·인증·필요한 RAP 호출·운영 인수이며 예시 폴더를 복제하는 것이 아니다.

## 6. 추천을 바꾸거나 확장할 조건

| 조건 | 재검토할 선택 |
| --- | --- |
| 기존 Skill이 특정 Tool schema에 고정 | 이름 유지+view 분리와 개별 Tool을 동일 질문으로 비교 |
| 백엔드가 필요한 결합·집계·범위 조회를 제공하지 않음 | RAP API 보완을 우선 협의. MCP 무제한 전량조회·LLM 합산으로 우회하지 않음 |
| SAP가 CF Connector·인증을 수용하지 못함 | IS안의 동일 업무 계약 보존 여부와 책임 재협의 |
| 후속 polling·자동 재개가 미지원 | 일반 접수 결과와 다음 사용자 turn의 ID 조회 경로 |
| 검토된 매뉴얼 검색으로 해결되지 않는 요구가 측정됨 | 벡터·Tool 검색·별도 AI를 비용·권한·평가와 함께 검토 |

**착수 순서:** 경로·담당의 미결 확인 → API와 정답 확보 → 읽기 최소 연결 → TEST/쓰기의 실패·복구 계약 → 실제 Joule 회귀. 상세 협의는 [[11. RAP와 Joule 담당자에게 필요한 계약]], 합격 조건은 [[12. 검증 시나리오와 단계별 실행 계획]], 예금은 [[14. 보통예금 조회와 항목별 확정 설계]].

사용자의 추가 고찰 요청인 **메모리·최적화·동기식 Joule과 비동기 업무의 호환**은 [[15. 동기식 Joule을 고려한 MCP 설계 고찰]]에서 한 흐름으로 연결한다.
