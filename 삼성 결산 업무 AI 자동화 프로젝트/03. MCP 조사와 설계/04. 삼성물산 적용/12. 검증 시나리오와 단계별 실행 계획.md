# 검증 시나리오와 단계별 실행 계획

갱신: **2026-11-17** · 상태: **시험 계획. 아래 시나리오는 이번에 실행하지 않았다.**

> [!abstract] 무엇을 통과해야 좋은 설계인가?
> **연결·도구 호출·답변·업무 효과·실패 뒤 복구를 각각 확인한다.** 정답뿐 아니라 권한 밖 노출·중복 실행·잘못된 완료·부분 결과 은폐 같은 금지 행동도 검사한다. 문서 검토나 mock 통과는 실제 HE4·Joule 통과와 구분한다.

## 5. 동기 루프·메모리·최적화의 관측

| 축 | 측정·판정 |
| --- | --- |
| **시간** | 전체 turn·각 Tool·인증·queue·SAP·직렬화의 시간과 timeout 계층. 자동 progress/reset 효과를 별도 기록 |
| **문맥** | 활성 Tool 정의·결과의 tokens/UTF-8 bytes·호출 수, 필요한 scope·mode·근거 보존 |
| **기억** | 대화 재시작 뒤 실제 실행 ID 조회, 오래된 사실 재사용 차단, 미검토 지식의 확정 답변 금지 |
| **자원** | 페이지·응답 bytes·동시 호출·메모리·대기열 상한, 초과의 complete/오류 의미 |
| **효과** | 실제 Job·기표·확정·Task/HIST 수와 현재 상태. LLM judge만으로 판정하지 않음 |

같은 fixture·모델·권한·데이터로 후보를 반복 비교한다. `pass@k`와 k회 모두 성공은 다른 지표다. 성능 p50/p95/p99는 충분한 반복 수와 함께 기록하며 소수 시험의 p95를 SLA로 약속하지 않는다.

**초기 수용 제안:** 통제된 시험에서 TEST 경로 실제 기표0, 권한 밖 노출0, 중복 부작용0, running/unknown을 최종 완료로 안내0. 한 번의 통과가 운영 전반의 무결함 보장은 아니다.

## 6. 날짜보다 준비 조건으로 순서를 정한다

| 단계 | 할 일 | 다음 단계 조건 |

| **3 격리 계약 시험** | 정상·거절·부분·지연·불명·동시변경 mock | 입력·응답·금지 행동의 결정적 검사 |
| **4 백엔드 연결** | 허용된 개발환경에서 읽기·TEST/확정 효과 검증 | 실제 사용자/범위·Job/저장·이력 대조 |

| **6 측정 후 확장** | 오류 검색·추가 과제·캐시/Tasks 필요성 평가 | 효과와 비용으로 채택, 버전별 회귀 |

확정 취소가 없는 예금 쓰기는 **별도 허용 테스트 데이터·대상·정리 방법**을 정한 후 수행한다. timeout 재현을 위해 실제 기표·확정을 반복하지 않는다. 과거 11/20·25·27 일정은 이번 실행 약속으로 재사용하지 않는다.

기록 상태는 **미실행 / 환경 준비 미완료 / 통과 / 실패 / 판정 불가**를 구분하고 환경·사용자·버전·기대/실제·trace·저장 증거를 남긴다. 현재 이 문서의 모든 새 시나리오는 **미실행**이다.
