# 보통예금 조회와 항목별 확정 설계

기준: **홍종화 작성 XLSX v1.0.0, 2026-11-17** · 상태: **명세 대조 + MCP 설계 제안. 이번 직접 호출·쓰기 없음**

> [!abstract] 이 사례의 핵심
> **계좌별 대사 결과를 읽고, 사람이 선택한 항목을 사유와 함께 확정하며, 성공·거절·확인 필요를 항목별로 전달한다.**
> 이미 조회에 포함된 확정자·시각·경로를 답하려고 이력을 추가 호출하지 않는다. HTTP 200·미대사 0·실행 사용자·확정 지시자의 의미를 각각 보존한다.

## 1. 어떤 결과를 한 건으로 보는가?

**회사·회계연도·기간·House Bank 계좌의 점검 결과**가 한 건이며 안정적 키는 `ResultUUID`다. 금액 일치 여부와 담당자 확정 여부는 별개다.

| 판정 | 의미 | 확정 조건 |
| --- | --- | --- |
| **MATCHED** | 허용 오차 안에서 일치 | 미확정·권한 등 나머지 조건 확인 |
| **DIFFERENT** | 허용 오차를 넘는 차이 | **사유를 넣으면 확정 가능**. 차이를 이유로 일괄 차단하지 않음 |
| **NOT_RECON** | 외부 잔액 미수령 | 확정 불가. `ExternalValue=0`, `Difference=0`을 실제 잔액0·차이없음으로 해석하지 않음 |

회사·client·준비 상태의 기준 기록은 [[07. 보통예금 기능과 MCP 인수 기준]]. XLSX는 **HE4/client400의 RAP/OData 미반영**, 실제 펌뱅킹·G/L 미연계, 시드 데이터, 확정 취소 없음이라고 적는다. 아래 설계는 이 제한을 해소했다고 주장하지 않는다.

## 2. Tool은 업무 효과를 기준으로 나눈다

서비스 **`ZAPI_C01_CCK_DEPOSIT_O4`**, Entity **`CheckResult`·`Confirmation`**은 명세의 이름이다. 전체 URL·client·언어·metadata는 인수 환경에서 다시 맞춘다.

| Tool 명칭(명세) | 필요한 입력·효과 | 반환·호출 기준 |
| --- | --- | --- |
| `find_check_results` | 회사·연도·기간 필수, 은행·대사·확정 상태 선택. **조회** | 계좌·금액·대사/확정 상태·차단 사유·사유 필요·현재 확정자/시각/경로 |
| `confirm_check_results` | 선택 UUID·사유, 신뢰된 확정 지시자. **쓰기** | 범위 재검사→CSRF→`confirmMultiple`; UUID별 `Confirmed`·`Message` |
| `get_confirmation_history` | 실제 ResultUUID. **조회** | 확정 시점 장부/외부금액 등 추가 근거가 필요한 때 |

**작은 문맥·적은 왕복의 실제 적용:** XLSX ‘AI 예상 답안’ **AD20·AD23**은 확정자·시각·경로 질문과 기확정 재요청을 `find_check_results` **1회**로 처리한다. 이미 반환된 정보를 얻으려고 이력 Tool을 추가 호출하지 않는다. 상세 증빙·확정 시점 금액이 필요한 질문은 별도 이력을 읽는다.

단건 `confirm`은 노출되지만 명세상 실행 미검증이다. `confirmFromSapGui`는 BO 내부 GUI 전용이며 서비스에 노출되지 않는다. Action 수만큼 MCP Tool을 늘리지 않는다.

## 3. 조회부터 확정·복구까지의 흐름 제안

![[MCP-05 보통예금 항목별 확정.png|1000]]

[그림 확대](../../99.%20스크린%20샷%20및%20다이어그램/03.%20MCP%20조사와%20설계/MCP-05%20보통예금%20항목별%20확정.svg) · 편집: [[MCP-05 보통예금 항목별 확정.excalidraw]]. 그림의 사용자 확인·동시변경 방어는 **필요 계약**이며 현재 Joule/API 구현 완료가 아니다.

### 3-1. 조회와 사용자 확인

1. **필수 범위와 권한을 확인**해 대상 기간의 결과를 읽는다. 기본 회사는 인증·환경 계약으로 정하고 HE4에 ZEN1·1710을 하드코딩하지 않는다.
2. **대상·금액·통화·상태·사유 필요 여부**를 제시한다. 비교는 같은 통화·정의 안에서 하고, 회계 계산과 대사 판정은 백엔드 값을 사용한다.
3. **선택한 UUID와 항목별 사유**를 사용자의 확인 내용에 연결한다. ‘확정해 줘’가 모든 회사·새로 생긴 항목까지 포함하도록 확장하지 않는다.

### 3-2. 쓰기 직전과 백엔드 실행

1. UUID 형식·중복 입력·현재 회사/기간 범위·항목 수·사유를 검사한다. 범위 밖 또는 형식 오류 항목은 백엔드에 보내지 않고 항목별 거절로 합친다.
2. 현재 상태·권한을 다시 확인한다. **사용자가 확인한 뒤 값이 바뀌었다면 다시 확인하도록 하는 계약**이 필요하다. 단순 사전 GET은 GET과 POST 사이의 경합까지 막지 못한다.
3. 신뢰된 사용자·세션으로 CSRF를 취득하고 `confirmMultiple`을 호출한다. CSRF는 업무 권한·사용자 확인의 대체 증거가 아니다.
4. 결과는 요청/응답 순서가 아니라 **ResultUUID로 대응**한다. 누락·중복·요청 밖 UUID는 전체 성공으로 압축하지 않고 계약 오류·확인 필요로 다룬다.

**동시 변경의 실제 빈칸:** 명세의 메시지004/DisplayedChangeAt 검사는 **GUI 전용이고 API에는 해당 없음**이다. 단건 ETag 정의만으로 다건 Action까지 stale 방어가 됐다고 하지 않는다. RAP의 원자적 버전 검사·확인 snapshot 전달·Action 보완 등 가능한 방법을 홍종화/SAP와 합의하고 fixture로 검증한다.

### 3-3. 항목별 결과와 응답 불명 복구

| 결과 | 사용자 안내·허용되는 후속 행동 |
| --- | --- |
| `Confirmed=true` | 해당 UUID 성공. 확정 상태·이력과 일치하는지 인수/불명 복구 시 대조 |
| `Confirmed=false`, 사유 필요006 | 해당 항목 사유를 받고 **그 항목만** 다시 확인·요청 |
| 기확정003 | 현재 확정자·시각·경로 안내. 성공 건 재확정 금지 |
| 미수령005·권한002 | 거절 유지, 필요한 조치 안내. 다른 사용자/계정으로 자동 우회 금지 |
| Action 내부 일부 실패007 | 해당 건 거절과 나머지 저장 여부를 계약대로 전달 |
| 최종 COMMIT 실패·응답 유실·항목 결과 누락 | **상태/이력 재조회로 기존 처리 확인**. 미처리·미접수를 입증하지 못하면 결과 불명 유지 |

응답이 불명확하면 전체 `_Item`을 일괄 재POST하지 않는다. 현재 확정 사실을 찾더라도 그것만으로 이번 요청이 처리했다는 인과관계까지 증명하지 않으며, 확인된 사용자·시각·경로를 그대로 설명한다. 확정 취소가 없으므로 별도 테스트 결과와 쓰기 허용 범위를 준비한다.

### 3-4. 계좌 확정과 전체 결산 Task 완료는 별도 계약이다

R&R v0.3의 **1.1.1**은 보통예금 확정 시 해당 Cycle의 **TR006 Task 완료 반영**을 구상한다. 반면 11/17 XLSX의 관련 시트에서는 이 연결 계약을 확인하지 못했다. **구현이 없다고 단정하지 않고**, 대상 Cycle/Task 매핑·반영 주체·대상 계좌 전체/일부의 완료 조건·실패/중복 처리·HIST 근거를 추가 인수한다. 일부 계좌의 확정 성공만으로 전체 결산 업무를 완료 처리하지 않는다.

## 4. 사용자·기간·금액·시각 계약

| 항목 | 명세와 설계 판단 |
| --- | --- |
| **RequestedBy** | 확정 지시자, ExecutedBySAPUser는 실제 SAP 실행 사용자. `AI_AGENT` 문자열을 허가·대리 증거로 신뢰하지 않음 |
| **권한** | 명세는 회사별 조회 F_BKPF_BUK 03, 확정 02를 설명. 실제 사용자와 DCL/Action의 허용·거절을 각각 시험 |
| **기간** | `'002'` 요청→`'2'` 응답 사례. 정규화 규칙을 합의하고 회계기간 의미를 보존 |
| **금액** | 원천 decimal·통화를 보존. NOT_RECON의 0은 미수령/미계산으로 설명 |
| **ConfirmedAt** | 숫자형 **UTC `YYYYMMDDhhmmss.fffffff`**. epoch나 이미 KST인 값으로 읽지 않음. 0은 미확정 |
| **민감정보** | 계좌번호·확정 사유·사용자 정보는 최소 반환·로그 마스킹/제외 정책 합의. 인증 토큰·헤더는 기록하지 않음 |

## 5. 재시도에 남은 중요한 예외

XLSX API 명세 **F10**은 `403 + x-csrf-token: required`일 때 토큰 재발급 후 재전송을 설명한다. **명시적으로 미처리된 CSRF 거절**인지, HTTP 클라이언트가 임의 POST retry를 하는지 구분한다. 확인 전 보수적인 제안은 **업무 POST 자동 retry를 끄고, 거절 증거·대상·현재 권한을 대조한 제한된 회복만 합의**하는 것이다.

timeout·5xx·일반403·최종 저장 실패를 위 CSRF 예외로 확대하지 않는다. 공통 보안·결과 불명 기준은 [[09. 권한 중복 실행과 결과 불명 처리]].

| 근거 셀/절 | 확인 범위 |

| ‘API 명세’ B170~B172 | 젠데모 조회 **실제 응답으로 기재**. 이번 세션의 재호출 아님 |
| ‘API 명세’ B174~B178 | 다건 POST **요청/응답 형식 예시, 미실행**. HTTP200 항목별 결과의 계약 근거 |
| ‘AI 예상 답안’ B12·AD20·AD23 | 기준 기간 연습용 snapshot·조회 최적화·기확정 재요청 금지. **실데이터 쓰기 검증 아님** |
| ‘API 명세’ B185·B188·B198 | GUI/API stale 차이, 내부 실패/최종 COMMIT 실패, 거절 순서 |
