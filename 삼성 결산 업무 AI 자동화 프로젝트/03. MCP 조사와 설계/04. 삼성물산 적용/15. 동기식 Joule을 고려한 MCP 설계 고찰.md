# 동기식 Joule을 고려한 MCP 설계 고찰

작성: **2026-11-17** · 상태: **사용자 제약을 반영한 조사·설계 고찰. 실제 Joule 지원·timeout 실증 전**

> [!abstract] 핵심 판단
> **좋은 MCP는 에이전트의 제한된 문맥·시간·실패 가능성을 고려해, 올바른 도구 선택과 신뢰할 결과·안전한 재개를 가능하게 하는 계약이다.**
> 삼성물산은 **Joule이 동기식 루프로 동작한다는 사용자 제공 조건**을 설계 전제로 둔다. 긴 SAP 업무는 **짧은 접수 응답→같은 실행 ID 조회**로 연결하는 안을 우선 검증한다. 이 문제는 보통 **동기·비동기 실행 계약의 불일치**로 설명하며 ‘비가역성’과는 다르다.

## 1. 무엇이 오래 유지할 설계 기준인가?

모델·메모리 기법·SDK는 변해도 **지금 모델이 읽는 정보의 선택, 외부 상태의 정답, 제한된 자원, 실패 뒤 안전한 처리**는 계속 고려해야 한다. 특정 압축 알고리즘·벡터 DB·interrupt API를 변하지 않는 필수 기능으로 고정하지 않는다.

| 계속 고려할 성질 | MCP가 통제할 수 있는 설계 | Joule/백엔드와 맞출 계약 |
| --- | --- | --- |
| **모델이 읽는 문맥과 비용은 제한됨** | 필요한 요약·필드·근거만 반환, 상세는 ID로 재조회 | 실제 모델 입력·출력 노출·압축 지원 |
| **모델의 도구 선택·해석은 틀릴 수 있음** | 목적·효과·필수 조건·오류를 명확히 설명하고 서버 입력 검사 | 실제 질문의 선택·인자·답변 회귀 |
| **현재 업무 사실은 외부에서 바뀜** | scope·as_of·완전성·현재 상태 조회 | CDS/RAP 정답·권한·동시변경 검사 |
| **대화와 실행의 수명은 다름** | RequestID를 반환·다시 조회, RAM을 유일 상태로 쓰지 않음 | Job 영속 접수·결과 보관·새 turn에서 ID 전달 |
| **원격 호출은 늦거나 결과가 불명일 수 있음** | deadline·오류·재조회·POST retry 경계를 정의 | 같은 ID 중복·접수 불명 대사·실제 취소 효과 |
| **메모리·연결·동시성도 제한됨** | 페이지·bytes·fan-out·queue 상한, 부분 표시 | backend 부하·CF 자원·전체 turn 예산 |
| **행동 효과와 권한은 지켜져야 함** | 조회/TEST/쓰기 분리·신뢰 사용자 확인 | 최종 SAP 권한·확인 대상·트랜잭션 |

이는 MCP 규격 하나가 자동 제공하는 기능 목록이 아니라 **규격·에이전트 연구·현재 업무에서 도출한 설계 기준**이다. 연구와 한계는 [[03. 최신 연구와 공식 사례에서 얻는 기준]].

## 2. ‘동기식 MCP’라는 표현을 먼저 풀어야 한다

MCP에는 **통신 메시지·일반 Tool 결과·선택적 Tasks 확장**이 있고, 서버 내부는 async I/O로 구현할 수도 있다. 다음 네 개념을 한 단어로 묶지 않는다.

| 개념 | 정확히 묻는 질문 |
| --- | --- |
| **동기식 에이전트 루프** | 모델 판단→Tool 호출→유효 결과를 기다림→다음 판단 순서인가? |
| **서버의 async 함수** | I/O 대기 중 다른 요청을 처리하는 구현인가? 외부 계약은 짧은 일반 결과일 수도 있음 |
| **장시간 업무** | SAP Job이 접수 응답 뒤에도 계속 실행되는가? |
| **interrupt/resume·Tasks** | Host가 대기 상태·checkpoint·후속 이벤트를 보존해 이어가는가? 해당 protocol 형식을 이해하는가? |

interrupt는 **어디에 상태를 저장하고 어떤 신호로 어느 단계부터 재개하는지**까지 있어야 의미가 있다. HTTP 취소·사용자 확인 대기·에이전트 checkpoint는 각각의 계약이다. MCP 서버의 callback만으로 Joule의 대화가 자동 재개되지는 않는다.

## 3. 사용자가 지적한 비대칭은 언제 성립하는가?

**비동기 재개를 지원하는 Host가 일반 Tool 결과를 기다려 받는 것은 대체로 자연스럽다.** 반대로 **현재 호출에서 유효한 결과를 기다리는 Host에, 정해지지 않은 나중 callback만 제공하거나 완료까지 너무 오래 기다리는 서버**를 붙이면 timeout·미지원 형식·turn 실패가 날 수 있다.

다만 ‘동기→비동기는 항상 불가’라는 뜻은 아니다. **일반 결과를 짧게 돌려주고 후속 조회를 약속하면 호환 경로를 만들 수 있다.** 두 방향 모두 schema·transport·시간·취소·상태 계약이 맞아야 한다.

| 조합 | 판단 | 필요한 조건 |
| --- | --- | --- |
| interrupt/resume Host + 짧은 일반 Tool | 보통 가능 | 일반 결과 지원, deadline·에러 처리 |
| 동기 루프 Host + async I/O 서버의 짧은 결과 | 가능 | 서버 구현과 무관하게 유효 응답이 제때 도착 |
| 동기 루프 Host + Job 완료까지90초 대기 | 한도가 짧으면 실패 가능 | 실제 Tool/turn 한도 안에 완료하거나 계약 변경 |
| 동기 루프 Host + accepted/RequestID를2초에 반환 | **우선 검증 후보** | Host가 accepted를 최종 업무 성공으로 오해하지 않고 후속 조회 가능 |
| Tasks 미지원 Host + Tasks 전용 결과/일방 callback | 계약 불일치 | 공통 지원 기능으로 낮추거나 Host 지원 추가 |

정확한 용어는 **호환성 문제, 동기·비동기 실행 모델/완료 계약의 불일치(sync/async impedance mismatch)** 정도다. ‘비가역성’은 되돌릴 수 없는 성질을 뜻하므로 이 연결 문제의 명칭으로 사용하지 않는다. 실제 timeout이 한 Tool/turn의 실패인지 프로세스 종료인지는 제품 동작·로그로 구분하며, 현재 Joule이 실제로 ‘뻗었다’고 단정하지 않는다.

## 4. 삼성물산에 적용할 계약

### 4-1. 긴 FCV/AFAB 업무

**범위·TEST 확인→실제 RequestID로 접수→짧게 accepted 응답→같은 ID readback→업무 결과 검증→별도 Task/HIST 반영**을 후보로 삼는다. 각 Tool 호출은 동기 루프가 소비할 수 있는 일반 결과로 마친다. SAP Job의 수명은 별도 영속 실행 체계가 책임진다.

‘아직 진행 중’도 **완결된 한 번의 상태 조회 결과**다. Host가 원한 요청을 처리해 응답한 것과 SAP 업무 완료를 구분한다. 대화가 끝나도 실행 결과를 다시 찾을 수 있어야 하며, 자동 알림·resume가 없으면 지원되지 않는 약속을 하지 않는다. 원래 lifecycle은 [[08. 동기 호출과 장시간 작업의 연결]].

### 4-2. 메모리와 문맥

- **현재 사실:** 잔액·Task 상태·권한은 필요 시 원천을 다시 읽는다.
- **실행 상태:** RequestID·대상·모드·마지막 확인 상태는 영속 원천에 연결한다. 대화 압축이 실행 원장을 대체하지 않는다.
- **재사용 지식:** 오류 매뉴얼은 메시지 ID·적용 범위·출처·검토 상태로 검색한다. 사용자 피드백을 자동 정답으로 승격하지 않는다.
- **서버 RAM:** 제한된 작업 버퍼로 사용한다. 새 MCP DB·캐시·벡터 DB는 실제 부족한 계약이 확인될 때 선택한다.

이 구분의 기준 문서는 [[06. 메모리와 컨텍스트를 나누는 설계]].

### 4-3. 최적화와 정확성

**C1**은 CDS/API에서 결합·집계하고 scope·기준시각·완전성을 반환한다. **예금**은 이미 조회에 포함된 확정자·시각·경로를 활용해 이력 호출을 줄인다. **Spool**은 결정적 파싱·회계 계산 결과를 읽는다.

토큰·왕복을 줄여도 **회사·기간·TEST·권한·부분 실패·완료 근거**는 지우지 않는다. 서버 내부에서 무한 polling해 Tool 하나의 응답만 작게 만드는 것은 시간·연결 자원을 아끼는 최적화가 아니다. 자세한 측정 기준은 [[07. 토큰 지연과 서버 자원 최적화]].

## 5. 채택 전에 확인할 것

1. **실제 동기 제약:** 제품/build·선택 경로·turn/Tool/gateway deadline. 약1분과10초×12회 잠정안을 함께 검증한다.
2. **반환 계약:** accepted/running/unknown/업무성공/반영완료를 모델이 구분하고 RequestID를 유지하는가?
3. **영속·복구:** 접수 후 연결 단절·CF 재시작·늦은 결과에서도 같은 실행을 찾고 완료 작업을 반복하지 않는가?
4. **후속 동작:** 다음 turn·링크·메일·polling·Tasks·interrupt/resume 중 실제 지원하는 것과 담당자는 누구인가?
5. **효율·안전:** 같은 질문에서 지연·호출 수·문맥 크기와 정답·권한·중복·부분 결과를 함께 측정했는가?

위 질문은 [[11. RAP와 Joule 담당자에게 필요한 계약]]의 K05~K10과 연결되고, [[12. 검증 시나리오와 단계별 실행 계획]]의 E06~E20·C01~C05로 시험한다. **실제 중단/재개가 불가해도 안전한 ID 재조회까지 가능한지**를 먼저 검증하며 별도 하네스 개발을 자동 범위로 추가하지 않는다.
