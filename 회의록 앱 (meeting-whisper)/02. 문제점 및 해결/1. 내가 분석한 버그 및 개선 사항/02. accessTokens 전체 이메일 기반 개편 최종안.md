# accessTokens 전체 이메일 기반 개편 최종안

> 현재 상태: **전체 이메일 전환 및 `_` 이메일 보완 완료**  
> 이 문서의 `accessTokens`는 OAuth Bearer token이 아니라 `Meetings.accessTokens` 컬럼에 저장하는 회의 접근 식별값이다.

## 한 문장 결론

권한 판단에는 이름이나 이메일 앞부분을 쓰지 않고 **전체 이메일만** 사용한다. 다만 `_`와 `%` 같은 문자는 이메일에서 제거하지 않고, SQL `LIKE` 검색문을 만들 때만 이스케이프한다.

## 처음에 무엇이 문제였는가

기존 코드는 한 사용자를 여러 문자열로 확장했다.

```text
juyum@zenconsulting.co.kr
juyum
염정운
```

이 방식에서는 다음 두 사람이 이메일 앞부분 `juyum` 때문에 같은 사용자처럼 취급될 수 있다.

```text
juyum@zenconsulting.co.kr
juyum@gmail.co.kr
```

표시 이름도 동명이인이 있을 수 있으므로 권한 키로 적합하지 않다. 회사 내부 앱은 XSUAA 로그인을 통과한 사용자의 전체 이메일을 받을 수 있으므로, DB 구조는 유지하면서 비교 기준만 전체 이메일로 단순화했다.

## 최종 저장 형태

`Meetings.accessTokens`는 계속 `LargeString` 하나를 사용한다. 각 이메일을 줄바꿈 경계로 감싸서 저장한다.

```text
\nowner@company.co.kr
participant@company.co.kr
shared.user@company.co.kr\n
```

줄바꿈 경계를 사용하는 이유는 부분 문자열의 잘못된 일치를 막기 위해서다.

```text
kim@a.com
kim@a.com.tw

→ 서로 다른 이메일
```

## 현재 함수들이 맡는 역할

최종 구현에서는 권한 문자열 처리 로직을 `cap/srv/lib/access-tokens.js`의 순수 함수로 분리했다.

### `normalizeAccessEmail()`

한 값을 권한용 전체 이메일로 사용할 수 있는지 검사한다.

- 앞뒤 공백 제거
- 소문자로 통일
- 최대 길이 제한
- 값 내부의 공백과 개행 거부
- `@`와 도메인이 있는 전체 이메일만 허용
- 이름과 이메일 앞부분은 거부
- `_`, `.`, `-` 같은 정상 이메일 문자는 보존

중요한 점은 `_`를 제거하지 않는다는 것이다.

```text
sy_lee@zenconsulting.co.kr
→ sy_lee@zenconsulting.co.kr
```

### `normalizeAccessEmails()`

여러 후보를 `normalizeAccessEmail()`로 정리하고 중복을 제거한다.

### `userIdentityEmails()`

XSUAA 환경에 따라 이메일이 들어올 수 있는 다음 필드를 확인한다.

```text
user.attr.email
user.attr.user_name
user.id
```

필드 이름이 무엇이든 **전체 이메일 형식인 값만** 현재 사용자의 신원 후보로 남긴다. `juyum`이나 `염정운`은 남지 않는다.

### `buildAccessTokens()`

소유자·참여자·공유자의 전체 이메일을 모아 중복을 제거하고, 줄바꿈 경계가 있는 하나의 문자열로 만든다.

### `escapeLikePattern()`과 `accessTokenLikePattern()`

DB 조회용 `LIKE` 패턴을 안전하게 만든다. 여기서 이메일을 바꾸는 것이 아니라 SQL이 특별하게 해석하는 문자만 검색 패턴에서 이스케이프한다.

```text
저장된 이메일
sy_lee@company.co.kr

LIKE 검색 패턴
%\nsy\_lee@company.co.kr\n%

SQL
LIKE ... ESCAPE '\'
```

`_`는 SQL `LIKE`에서 임의의 한 글자, `%`는 임의 길이 문자열을 뜻한다. 따라서 이메일은 원형대로 저장하고 조회 조건에서만 `\_`, `\%`로 바꾸는 것이 핵심이다.

## 첫 수정에서 생긴 `_` 이메일 회귀

첫 전체 이메일 전환 커밋 `de1aa07`은 `LIKE` 와일드카드 문제를 막는 과정에서 `%`나 `_`가 들어 있는 이메일 자체를 권한 후보에서 제외했다.

```text
sy_lee@zenconsulting.co.kr
jh_hong@zenconsulting.co.kr
→ 정상 이메일인데 accessTokens에서 빠짐
→ 해당 사용자가 원래 볼 수 있던 회의를 조회하지 못함
```

이 문제는 “특수문자를 가진 이메일을 저장하지 않는다”로 해결할 문제가 아니었다. 후속 커밋 `e087c49`에서 다음처럼 바로잡았다.

```text
이메일 정규화 단계
→ `_`, `%`를 포함한 전체 이메일 보존

DB LIKE 조건 생성 단계
→ `_`, `%`, `\`만 이스케이프
```

즉, **유효한 사용자 신원은 보존하고 DB 검색 문법과 충돌하는 부분만 조회 시점에 처리**한다.

## 조회 권한과 편집 권한은 어떻게 나뉘는가

`accessTokens`는 회의를 읽을 수 있는 사용자의 합집합이다.

```text
소유자 + 참여자 + 공유자
→ accessTokens
→ 회의 조회 가능
```

하지만 읽기 권한과 편집 권한이 같다는 뜻은 아니다.

- 소유자: 소유자 규칙에 따라 조회·수정
- 참여자: 전체 이메일이 `participants`에 있으면 편집 가능
- 공유자: `accessTokens`로 조회할 수 있지만 참여자와 같은 편집 권한은 받지 않음
- `MeetingAdmin`: 전체 회의 접근 규칙 유지

따라서 전체 이메일 개편은 기존 역할 구분을 없애는 변경이 아니다.

## 아직 BTP 권한을 받지 않은 사람을 먼저 등록하면

회의에 그 사람의 전체 이메일을 참여자 또는 공유자로 먼저 저장할 수 있다. 이후 관리자가 그 사람에게 BTP 애플리케이션 권한을 부여하고, 본인이 XSUAA 로그인을 하면 JWT에서 얻은 전체 이메일이 저장된 이메일과 일치하므로 회의를 조회할 수 있다.

```text
회의 생성 시 future.user@company.co.kr 저장
→ 나중에 BTP 역할 부여
→ XSUAA 로그인
→ JWT의 전체 이메일과 accessTokens 비교
→ 일치하면 조회 허용
```

단, 이메일을 잘못 입력했거나 로그인 계정의 이메일이 다른 경우에는 일치하지 않는다.

## 기존 회의록 호환성

기존 값에 전체 이메일이 함께 들어 있다면 계속 조회할 수 있다.

```text
기존 accessTokens
juyum@zenconsulting.co.kr
juyum
염정운

현재 비교 키
juyum@zenconsulting.co.kr

→ 전체 이메일이 있으므로 조회 가능
```

과거의 `juyum`, `염정운`은 더 이상 권한 키로 사용하지 않을 뿐, 남아 있다고 해서 전체 이메일 조회를 방해하지는 않는다.

그러나 첫 수정이 적용된 동안 `_` 이메일이 accessTokens에서 누락되어 저장된 행은 코드 수정만으로 자동 복원되지 않는다. 해당 데이터는 참여자·공유자 원본을 기준으로 accessTokens를 다시 계산하는 백필이 필요하다. 팀 통합 기록에는 운영 DB 89건을 새 규칙으로 재계산한 내역이 남아 있다.

## 최종 테스트 범위

`tests/access-tokens.test.js`에서 다음 회귀를 고정한다.

- `_`가 포함된 이메일 보존
- 점·하이픈·대문자가 포함된 이메일 정규화
- 이름과 이메일 앞부분 제거
- 공백·개행이 포함된 값 거부
- 중복 제거와 줄바꿈 저장 경계
- 비슷한 이메일의 부분 일치 차단
- SQL `LIKE`에서 `_`, `%`, `\` 이스케이프
- XSUAA 사용자 객체에서 전체 이메일만 추출
- 유효한 이메일이 없을 때 빈 결과 반환

최초 HTTP 검증은 같은 앞부분을 가진 다른 계정이 더 이상 조회하지 못하는 것을 확인했고, 후속 단위 테스트는 `_` 이메일 회귀까지 포함해 검증한다.

## 관련 커밋

- `de1aa07`: 전체 이메일 기준으로 최초 변경
- `e087c49`: `_` 이메일 회귀 수정, 순수 함수 분리, 회귀 테스트 추가

## 최종 판단

현재 최종안은 다음 세 원칙으로 정리된다.

```text
사용자 신원
→ 전체 이메일만 사용

이메일 원문
→ `_`, `%`를 포함해 보존

SQL LIKE 검색
→ 특수문자를 조회 패턴에서만 이스케이프
```

DB 컬럼 구조를 바꾸지 않으면서 동명이인·동일 이메일 앞부분 충돌을 막았고, `_`가 포함된 실제 회사 이메일도 정상적으로 권한에 포함되도록 보완했다.
