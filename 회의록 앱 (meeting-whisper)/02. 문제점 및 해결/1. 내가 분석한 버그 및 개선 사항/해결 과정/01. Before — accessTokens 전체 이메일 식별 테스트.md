# Before — accessTokens 전체 이메일 식별 테스트

## 테스트 목적

현재 `accessTokens`가 전체 이메일뿐 아니라 이메일 앞부분도 권한 문자열로 저장하는지, 그 결과 전체 이메일이 일치하지 않는 사용자가 회의를 조회할 수 있는지 확인한다.

연결된 개선안: [[02. accessTokens 전체 이메일 기반 개편 최종안]]

## 테스트 환경

- 코드: `C:\Users\염정운\project\meeting-whisper-yina`
- 브랜치: `feature/juyum`
- CAP: mocked 인증, SQLite in-memory
- 회의 생성 사용자: `admin`
- 조회 사용자: `alice`
- 테스트 일시: 2026-08-06

## 테스트 데이터

관리자 계정으로 다음 참여자를 가진 회의를 생성했다.

```text
참여자 전체 이메일: alice@another-company.example
조회 사용자 ID: alice
```

두 문자열은 동일한 전체 이메일이 아니다.

## 실행 결과

생성된 회의:

```text
Meeting ID
22c85593-fa7e-4d1e-8189-f87c893e7f52
```

DB에 저장된 `accessTokens`:

```text
admin
alice@another-company.example
alice
```

그 후 `alice / alice` 계정으로 같은 회의를 조회했다.

```text
AliceCanRead = true
조회된 행 수 = 1
```

## 기대 결과와 실제 결과

| 구분 | 결과 |
|---|---|
| 기대 | 사용자의 전체 이메일이 `alice@another-company.example`과 다르면 조회되지 않아야 함 |
| 실제 | 이메일 앞부분 `alice`가 일치해 회의가 조회됨 |

## 근거 해석

`buildAccessTokens()`가 전체 이메일뿐 아니라 이메일 앞부분까지 확장해 저장하고, 사용자 신원 토큰의 `alice`와 비교한다. 따라서 같은 로컬파트를 사용하는 서로 다른 전체 이메일을 구별하지 못한다.

이번 테스트는 보안 공격을 가정한 것이 아니라 실제 권한 식별 정확성을 검증한 것이다. 회사 계정 ID와 참여자 이메일의 앞부분이 우연히 같으면 의도하지 않은 회의가 목록에 노출될 수 있다.

## Before 결론

**재현 성공.** 전체 이메일만을 기준으로 비교하도록 변경할 근거가 확인됐다.

## After 테스트 기준

같은 데이터를 사용해 수정 후 다시 조회한다.

```text
accessTokens에 alice 로컬파트가 없어야 함
alice 사용자의 조회 행 수가 0이어야 함
전체 이메일이 정확히 일치하는 사용자는 정상 조회되어야 함
```
