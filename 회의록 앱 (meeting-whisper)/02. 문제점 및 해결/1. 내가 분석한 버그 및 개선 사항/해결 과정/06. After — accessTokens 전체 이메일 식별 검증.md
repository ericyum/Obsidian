# After — accessTokens 전체 이메일 식별 검증

> 최종 결과: **전체 이메일 충돌 차단 완료, `_` 이메일 회귀 후속 보완 완료**

연결된 개선안: [[02. accessTokens 전체 이메일 기반 개편 최종안]]  
Before 기록: [[01. Before — accessTokens 전체 이메일 식별 테스트]]

## 검증 목표

```text
이메일 앞부분과 표시 이름이 권한 값에서 제거되는가?
앞부분이 같은 다른 전체 이메일이 회의를 조회하지 못하는가?
기존 회의에 저장된 전체 이메일로 계속 조회할 수 있는가?
`_`가 포함된 실제 이메일도 누락되지 않는가?
SQL LIKE에서 `_`, `%`가 와일드카드로 오해되지 않는가?
```

## 1차 수정과 HTTP 검증

첫 수정은 다음 확장을 제거했다.

```text
Before
alice@another-company.example
alice

After
alice@another-company.example
```

mocked 인증과 SQLite in-memory CAP에서 다음 충돌 시나리오를 실행했다.

```text
회의 참여자: alice@another-company.example
조회 사용자 ID: alice
```

결과:

```text
AliceVisibleCount = 0
ExpectedCount = 0
Passed = true
```

| 항목 | Before | 1차 After |
|---|---:|---:|
| 전체 이메일 저장 | 있음 | 있음 |
| 이메일 앞부분 `alice` 저장 | 있음 | 없음 |
| 다른 전체 이메일 사용자의 조회 건수 | 1 | 0 |
| 동일 앞부분 충돌 차단 | 실패 | 성공 |

## 1차 수정 후 새로 발견된 `_` 회귀

최초 커밋 `de1aa07`은 SQL `LIKE` 특수문자 문제를 피하려고 `%`와 `_`가 들어 있는 이메일 자체를 정규화 단계에서 제외했다.

```text
sy_lee@zenconsulting.co.kr
jh_hong@zenconsulting.co.kr
→ accessTokens 후보에서 제거
→ 정상 사용자가 기존 회의를 조회하지 못함
```

즉, 같은 이메일 앞부분 충돌은 해결했지만 실제 회사 이메일을 누락시키는 더 직접적인 회귀가 생겼다.

## 후속 해결 방식

후속 커밋 `e087c49`에서 이메일 정규화와 SQL 패턴 생성을 분리했다.

```text
normalizeAccessEmail()
→ sy_lee@... 원문 보존

accessTokenLikePattern()
→ sy\_lee@... 형태의 LIKE 패턴 생성

meetingAccessWhere()
→ LIKE ... ESCAPE '\' 사용
```

핵심은 `_`를 이메일에서 지우는 것이 아니라, SQL `LIKE`가 `_`를 임의 한 글자로 해석하지 못하도록 조회문에서만 `\_`로 만드는 것이다. `%`와 `\`도 같은 원칙으로 처리한다.

## 순수 함수 분리와 회귀 테스트

권한 문자열 처리를 다음 파일로 분리했다.

```text
cap/srv/lib/access-tokens.js
```

검증 파일:

```text
tests/access-tokens.test.js
```

테스트는 다음 범위를 포함한다.

- `_` 이메일 보존
- 점·하이픈·대문자 이메일 처리
- 이메일이 아닌 ID와 표시 이름 제거
- 내부 공백과 개행이 있는 값 거부
- 중복 제거와 줄바꿈 경계 저장
- 비슷한 이메일의 부분 일치 차단
- SQL `LIKE`에서 `_`, `%`, `\` 이스케이프
- XSUAA 사용자 정보에서 전체 이메일만 추출
- 유효 이메일이 없을 때 빈 결과 반환

권한 로직을 CAP 서비스 내부의 중첩 함수로만 두지 않고 순수 함수로 분리한 이유는, DB나 서버 기동 없이 입력과 결과를 직접 검증하여 같은 회귀를 막기 위해서다.

## 기존 회의록 호환성

기존 accessTokens에 전체 이메일이 함께 저장되어 있다면 현재 코드도 그 값을 사용한다.

```text
기존 값
juyum@zenconsulting.co.kr
juyum
염정운

현재 조회 신원
juyum@zenconsulting.co.kr

→ 전체 이메일 일치, 조회 유지
```

과거 별칭 문자열은 더 이상 비교에 사용되지 않지만 전체 이메일 조회를 방해하지 않는다.

예외는 1차 수정이 적용된 동안 `_` 이메일이 빠진 채 다시 저장된 행이다. 이미 없어진 값은 코드 수정만으로 복구되지 않으므로 참여자·공유자 원본을 기준으로 백필해야 한다. 팀 통합 기록에는 운영 DB 89건을 새 규칙으로 재계산해 보완한 내역이 있다.

## 권한 의미 회귀 확인

전체 이메일로 바뀌어도 기존 역할 의미는 유지한다.

```text
소유자·참여자·공유자 전체 이메일
→ accessTokens
→ 조회 권한

participants 전체 이메일
→ 별도 비교
→ 편집 권한

MeetingAdmin
→ 전체 회의 접근 유지
```

OAuth/XSUAA의 Bearer access token 구조를 수정한 것이 아니다. 변경 대상은 `Meetings.accessTokens`에 기록하는 회의별 접근 식별 문자열이다.

## 최종 Before와 After

| 상황 | Before | 최종 After |
|---|---|---|
| 같은 이메일 앞부분의 다른 사람 | 잘못 조회 가능 | 전체 이메일 불일치로 차단 |
| 표시 이름이 같은 사람 | 충돌 가능 | 표시 이름을 권한 키로 사용하지 않음 |
| `_`가 포함된 이메일 | 1차 수정에서 누락 | 이메일 보존, LIKE에서만 이스케이프 |
| 기존 전체 이메일 포함 회의 | 조회 가능 | 계속 조회 가능 |
| 1차 수정 중 `_` 값이 빠진 DB 행 | 접근 손실 가능 | 백필 필요, 운영 기록상 89건 보완 |

## 관련 커밋

- `de1aa07`: 전체 이메일 기준으로 최초 변경
- `e087c49`: `_` 이메일 회귀 수정, 순수 함수 분리, 회귀 테스트 추가

## 최종 결론

전체 이메일 전환으로 이메일 앞부분과 동명이인 충돌을 막았다. 이후 발견된 `_` 이메일 누락은 “이메일 보존”과 “SQL 패턴 이스케이프”의 책임을 분리해 해결했고, 별도 단위 테스트로 재발 조건을 고정했다.
