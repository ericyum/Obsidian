## 1. 로그아웃 관련 문제

### 문제 상황

- 화면 우상단의 계정 - 로그아웃 클릭 시 '세션 확인이 필요합니다' modal 창이 뜨는데 
	- '세션 연장' 버튼을 클릭하면 GET currentUser 401이 뜨면서 '세션 확인에 실패했습니다~'로 메시지가 바뀜. 
	- '다시 로그인' 버튼을 클릭하면 GET currentUser, GET Meetings... 가 401이 뜨면서 새로고침만 되고, 원래 modal 창 그대로인 상태임. 
- 즉, UI상으로는 modal 창에서 벗어날 방법이 없음. 
- 이 상태에서 새로고침(F5)을 하면 로그인 페이지로 보내짐.
- 시간 초과로 인한 세션 만료 시 '다시 로그인' 버튼으로 바로 로그인을 할 수 있음.

### 원인 분석

#### 왜 로그아웃 때만 갇히는가 — 핵심 차이

**타임아웃 만료와 로그아웃은 세션 쿠키 상태가 정반대입니다.**

| 구분              | 시간 초과 만료                                          | 로그아웃           |
| --------------- | ------------------------------------------------- | -------------- |
| 모달을 띄운 주체       | **클라이언트 타이머** (`session.js:98` `checkSessionAge`) | 서버 401 응답      |
| approuter 세션 쿠키 | **아직 살아 있음**                                      | **삭제됨**        |
| 재진입 시 API 호출    | 성공 → `touchSession()` → `hideExpired()` → 모달 닫힘 ✓ | 401 → 모달 재등장 ✗ |

타임아웃 모달은 `lastTouchAt`(localStorage) 기준으로 **브라우저가 혼자 판단**해서 띄웁니다. 이때 서버 세션은 멀쩡하므로, `다시 로그인`으로 페이지를 다시 띄우기만 하면 API가 성공하고 `session.js:116`의 `hideExpired()`가 모달을 닫아줍니다. **버튼이 제대로 동작해서가 아니라, 세션이 살아 있어서 우연히 해결되는 것**입니다.

로그아웃은 쿠키가 실제로 삭제되므로 이 우연이 성립하지 않고, 버튼의 결함이 그대로 드러납니다.

#### 원인 ① — `다시 로그인` 버튼이 실제로 서버에 묻지 않음

`session.js:209-211`:

```
expiredModal.querySelector("[data-session-login]")?.addEventListener("click", () => { 
 window.location.assign(window.location.href);   // ← 문제 지점
});
```

`location.assign(현재 URL)`은 **일반 내비게이션**이라 브라우저의 기본 HTTP 캐시 규칙을 따릅니다. 반면 F5는 **reload**라서 메인 문서를 강제로 재검증(revalidate)합니다. 이 차이가 사용자가 관찰한 현상을 그대로 설명합니다:

```
[다시 로그인] location.assign(same URL) 
   → 캐시된 index.html 재사용 (approuter에 도달 안 함)  
   → SPA 부팅 → GET currentUser 401, GET Meetings 401  
   → 모달 재등장 ... 무한 루프
   
[F5] reload  
   → 메인 문서 재검증 → approuter 도달  
   → 세션 없음 → 302 로그인 페이지 ✓
```

캐시가 개입할 수 있는 근거는 `xs-app.json`에 있습니다. `/user-api` 라우트에만 `cacheControl: "no-cache, no-store, must-revalidate"`가 붙어 있고(`:13`), **정적 파일을 서빙하는 catch-all 라우트(`:33-38`)에는 캐시 지시자가 없습니다.** 따라서 `index.html`이 휴리스틱 캐싱 대상이 됩니다.
- 실제 확인 : `다시 로그인` 클릭 시 DevTools Network 탭에서 `index.html` 요청이 **(from disk cache)**로 표시

#### 원인 ② — `세션 연장` 실패 시 메시지가 잘못 덮어써짐

이건 코드에서 100% 확정되는 버그입니다. `session.js:63-65`:

```
.catch((error) => {
  showExpired({ source: reason, message: error?.message || "" });  // ← status 없음
  throw error;
})
```

그런데 메시지 분기는 `status`를 봅니다 (`session.js:152`):

```
message.textContent = detail?.status === 401
  ? "로그인 세션이 만료되었습니다. ..."        // 정확한 안내
  : "세션 확인에 실패했습니다. ...";          // 항상 이쪽으로 빠짐
```

`catch`가 `status`를 전달하지 않으므로 **진짜 401이어도 항상 "세션 확인에 실패했습니다"가 됩니다.**

더 정확히는 이렇게 두 번 덮어써집니다:

1. `getCurrentUser()`가 401을 받고 `api.js:167`에서 `markSessionExpired("current-user", 401)` → **status 401이 실린 정확한 메시지**가 먼저 표시됨
2. 곧이어 같은 에러가 `refreshSession`의 catch로 올라가 `showExpired`를 **status 없이 다시 호출** → 일반 메시지로 덮어씀

즉 api.js는 이미 올바른 이벤트를 쐈는데, session.js의 중복 호출이 정보를 훼손하는 구조입니다.

#### 원인 ③ — 모달에 탈출구가 없음

`ensureExpiredModal()`이 만드는 모달에는 `세션 연장`과 `다시 로그인` 두 버튼뿐입니다. 닫기 버튼도, ESC 핸들러도, 배경 클릭 닫기도 없습니다. 두 버튼이 모두 실패하면 **설계상 빠져나올 방법이 없습니다.**

여기에 더해, 로그아웃은 사용자가 **의도한 행동**인데 앱은 이를 "세션 오류"로 취급합니다. `app.js:143-145`가 `/logout`으로 이동하는 동안 진행 중이던 API 요청이 401을 받으면 그대로 `markSessionExpired`가 발동해 모달이 뜹니다. 로그아웃 중임을 알리는 플래그가 없습니다.


### 해결 방법

우선순위 순으로 정리합니다. ①②만 고쳐도 갇히는 현상은 사라집니다.

#### 1순위 — `다시 로그인`이 반드시 서버에 도달하게 (session.js:210)

가장 작은 수정은 `location.reload()`로 바꾸는 것입니다. F5와 동일한 재검증 동작이 됩니다. 다만 프록시·중간 캐시까지 확실히 우회하려면 **캐시 버스팅 쿼리를 붙여 approuter 진입점으로 명시 이동**하는 편이 견고합니다:

```
window.location.assign(`/?_=${Date.now()}`)
```

이러면 캐시 미스가 확정되어 approuter가 반드시 응답하고, 세션이 없으면 로그인으로 리다이렉트됩니다. 부수 효과로 `?meeting=<id>` 같은 기존 쿼리가 초기화되는데, 재로그인 시나리오에서는 오히려 안전한 동작입니다.

#### 2순위 — index.html 캐시 금지 (xs-app.json)

근본 차단책입니다. 정적 라우트에 `cacheControl`을 지정해 HTML이 캐시되지 않게 하면, 어떤 방식으로 재진입하든 approuter를 거치게 됩니다.

이 프로젝트는 이미 JS 모듈을 `?v=20260708-session` 같은 **버전 쿼리로 캐시 무효화**하고 있으므로(`app.js:19`, `:22`), **index.html만 `no-store`로 두고 나머지 정적 자산은 캐시를 유지**하는 조합이 성능 손해 없이 잘 맞습니다.

#### 3순위 — 메시지 버그 수정 (session.js:64)

`refreshSession`의 catch에서 `showExpired`를 다시 호출하지 않는 것이 가장 깔끔합니다. api.js가 이미 정확한 `status`로 `EXPIRED_EVENT`를 발생시키므로 중복 호출이 불필요합니다. 굳이 유지한다면 `getCurrentUser`가 던지는 Error에 `status`를 실어 보내야 합니다 — 현재는 `"current user unavailable: 401"` 문자열뿐이라 파싱 없이는 status를 알 수 없습니다.

#### 4순위 — 로그아웃을 세션 오류로 오인하지 않기

로그아웃 클릭 시 모듈 수준 플래그(예: `signingOut = true`)를 세우고 `showExpired`에서 이를 확인해 조기 반환하면, 로그아웃 도중 뜨는 유령 모달이 사라집니다. `/logout` 내비게이션이 시작된 뒤의 401은 정상 흐름이지 오류가 아닙니다.

#### 5순위 — 모달 탈출구 추가

닫기 버튼 / ESC / 배경 클릭 중 하나는 열어두는 편이 좋습니다. 위 수정이 모두 반영돼도, 네트워크 단절 같은 예기치 못한 상황에서 사용자가 UI에 갇히지 않으려면 최후의 탈출구가 필요합니다.

### 로컬 재현과 검증

#### 관찰 — 로컬에서는 문제가 발생하지 않음

로컬에 3개 서버(CAP + Worker + Approuter)를 띄우고 XSUAA를 바인딩한 환경에서 로그아웃을 시도하면, **모달 없이 바로 IdP 로그인 페이지로 이동합니다.** 배포 환경과 정반대 동작입니다.

#### 설정 차이가 아닙니다

로컬 실행은 `approuter/dev/xs-app.json`을 사용합니다(`start:local`이 `--workingDir ./dev`로 실행). 이 파일을 배포용 `approuter/xs-app.json`과 비교하면 `logout` 블록, `/user-api` 라우트, **catch-all 라우트에 `cacheControl`이 없는 점까지 동일**합니다. 설정은 원인이 아닙니다.

#### 원인 ①의 발동 조건이 성립하지 않기 때문입니다

배포에서의 실패 사슬은 전부 "캐시된 index.html이 approuter를 우회한다"에서 출발합니다.

```
[배포] 로그아웃 → approuter가 세션 파기 → /index.html 로 리다이렉트
   → 브라우저가 디스크 캐시에서 index.html 반환 (200, 네트워크 요청 없음)
   → approuter가 요청을 못 봄 → 로그인 리다이렉트 없음
   → SPA 부팅 → 401 → 모달 → 갇힘

[로컬] 로그아웃 → approuter가 세션 파기 → /index.html 로 리다이렉트
   → 요청이 approuter에 도달 → authenticationType: xsuaa → 세션 없음
   → IdP 로그인 페이지로 302 ✓
```

모달을 띄우는 주체는 401을 받은 API 호출인데, 로컬에서는 **앱이 아예 부팅되지 않으니 API 호출도 없고 모달도 없습니다.** 버그가 고쳐진 것이 아니라 발동 조건이 성립하지 않은 것입니다.

#### 로컬에서 캐시가 개입하지 않은 이유

세 가지 가능성이 있으며, 어느 것이든 결론은 같습니다.

1. **캐시 항목이 아직 없음** — `localhost:5000`은 방금 처음 띄운 오리진입니다. 배포 도메인은 계속 사용하면서 디스크 캐시에 자리 잡았습니다. 휴리스틱 캐싱은 `Last-Modified` 기준 경과 시간에 비례하므로, 갓 받은 리소스일수록 재검증 확률이 높습니다.
2. **DevTools의 "캐시 사용 중지"** — DevTools를 열어둔 채 테스트하면 모든 요청이 캐시를 우회합니다. 이 경우 **배포 환경에서도 재현되지 않습니다.**
3. **로컬 파일 서빙의 검증자 차이** — 개발 중 `copy-web-assets.js`로 `resources/`가 갱신되면 `Last-Modified`가 바뀌어 캐시가 무효화됩니다.

#### 시사점 — 로컬 검증만으로는 불충분합니다

이 관찰은 원인 ①을 **오히려 뒷받침하는 증거**입니다. 캐시가 개입하지 않으면 문제가 사라진다는 것을 통제된 환경에서 확인한 셈입니다.

동시에 주의가 필요합니다. **로컬은 애초에 실패하지 않는 환경이므로, 수정 후 로컬에서 "잘 된다"를 확인해도 수정의 효과를 증명하지 못합니다.**

#### 로컬에서 강제로 재현하는 절차

수정 전후를 로컬에서 비교하려면 캐시가 개입하도록 조건을 만들어야 합니다.

1. DevTools의 **"캐시 사용 중지" 체크 해제**
2. `http://localhost:5000` 접속 후 로그인, 화면을 몇 번 오가며 `index.html`이 캐시에 자리 잡게 함
3. DevTools Network에서 `index.html`이 **`(from disk cache)`** 로 표시되는지 확인 — 재현의 전제 조건
4. 그 상태에서 로그아웃

3번이 나오지 않으면 재현되지 않습니다. 그때는 응답 헤더를 직접 확인합니다.

```
curl.exe -I http://localhost:5000/index.html
```

`Cache-Control`이 없고 `Last-Modified`/`ETag`만 있다면 휴리스틱 캐싱 대상이며, 시간이 지날수록 캐시 적중률이 올라갑니다.

#### 원인별 검증 가능 환경

| 원인 | 로컬 검증 | 비고 |
|---|---|---|
| ① 다시 로그인이 서버에 도달하지 않음 | 조건부 | 위 절차로 캐시 상태를 만들어야 재현. 수정 후에는 "로그인 페이지로 이동하는지"만 확인하고 실제 효과는 배포에서 확인 |
| ② 메시지가 잘못 덮어써짐 | **가능** | 단, CAP을 내리는 방법은 통하지 않는다. 아래 "적용 결과"의 검증 절차 참조 |
| ③ 모달에 탈출구 없음 | **가능** | 모달이 뜬 상태에서 ESC·배경 클릭이 동작하지 않음을 즉시 확인 |

원인 ②·③은 캐시와 무관하므로 로컬에서 바로 검증할 수 있습니다. 1순위 수정(`/?_=${Date.now()}`)은 캐시 유무와 관계없이 항상 서버에 도달하는 방식이므로, 로컬에서는 동작이 깨지지 않는지만 확인하면 충분합니다.

### 적용 결과

1·2·3순위를 적용하고 로컬에서 검증을 마쳤습니다. 4·5순위는 보류했습니다.

#### 적용한 수정

**1순위 — `session.js`**

```
- window.location.assign(window.location.href);
+ window.location.assign(`/?_=${Date.now()}`);
```

캐시 미스가 확정되어 항상 Approuter가 응답합니다.

**2순위 — `approuter/xs-app.json`, `approuter/dev/xs-app.json`**

catch-all 앞에 `index.html` 전용 라우트를 추가했습니다.

```
{
  "source": "^/(index\\.html)?$",
  "target": "/index.html",
  "localDir": "resources",
  "authenticationType": "xsuaa",
  "cacheControl": "no-store"
}
```

정규식이 `/`와 `/index.html`만 잡고 JS·CSS·폰트는 제외한다는 점을 매칭 테스트로 확인했습니다. HTML만 캐시를 끄고 정적 자산은 기존 `?v=` 방식을 유지하므로 성능 손해가 없습니다.

**3순위 — `api.js` + `session.js`**

문서에 처음 적었던 "catch에서 `showExpired`를 호출하지 않는다"는 방법은 **회귀를 만듭니다.** `api.js`는 401일 때만 `markSessionExpired`를 호출하므로, catch를 없애면 네트워크 오류나 500에서는 모달이 아예 뜨지 않습니다. 그래서 대안이었던 "에러에 status를 실어 보내는" 방식을 택했습니다.

```
# api.js getCurrentUser
+ const error = new Error(`current user unavailable: ${response.status}`);
+ error.status = response.status;
+ throw error;

# session.js refreshSession catch
- showExpired({ source: reason, message: error?.message || "" });
+ showExpired({ source: reason, status: error?.status, message: error?.message || "" });
```

**캐시 버전 갱신** — 이 프로젝트는 `?v=` 쿼리로 JS 캐시를 관리하므로, 버전을 올리지 않으면 수정 파일이 기존 사용자에게 도달하지 않습니다. 이번 버그와 같은 함정이라 함께 처리했습니다.

```
app.js       api.js?v= · session.js?v=  → 20260803-logout-fix
index.html   app.js?v=                  → 20260803-logout-fix
```

| 항목 | 결과 | 방법 |
|---|---|---|
| 1순위 재로그인 | 통과 | 모달에서 `다시 로그인` → IdP 로그인 페이지로 이동 |
| 2순위 캐시 정책 | 통과 | `index.html`에 `Cache-Control: no-store`, `app.js`에는 없음 |
| 3순위 메시지 구분 | 통과 | 아래 절차로 두 메시지가 갈리는 것을 확인 |

**3순위 검증 절차** — 이 항목은 검증 방법을 찾는 데 시행착오가 있었습니다.

처음 시도한 "CAP을 내리고 `세션 연장` 클릭"은 **통하지 않습니다.** 두 가지 이유입니다.

1. `/user-api/currentUser`는 CAP이 아니라 **Approuter가 처리**합니다. CAP이 죽어도 200을 반환합니다.
2. CAP 다운은 502를 만드는데, `markSessionExpired`는 **401에서만** 호출됩니다. 502는 세션 문제가 아니므로 모달을 띄우지 않습니다. 목록 로딩 실패 메시지만 표시되는 것이 올바른 동작입니다.

또한 로컬에서는 `useBrowserSessionKeepAlive()`가 hostname이 localhost면 `false`를 반환해 **`getCurrentUser()`를 아예 호출하지 않습니다.** 그래서 `세션 연장`이 성공한 척하며 모달만 닫히고, 실제로는 아무것도 연장되지 않습니다. 검증하려면 이 함수가 `true`를 반환하도록 임시로 바꿔야 합니다(검증 후 원복).

그 상태에서 두 경로를 확인했습니다.

| 경로 | 조건 | 기대 메시지 | 결과 |
|---|---|---|---|
| 401 | 다른 탭에서 로그아웃 후 `세션 연장` | 로그인 세션이 만료되었습니다... | 통과 |
| 비-401 | DevTools로 `/user-api/currentUser` 차단 후 `세션 연장` | 세션 확인에 실패했습니다... | 통과 |

두 메시지가 갈리므로 3순위 수정이 정확히 동작합니다. 수정 전이라면 401 경우에도 아래쪽 메시지가 나왔을 것입니다. 401일 때 모달이 닫히지 않고 유지되는 것도 올바른 동작입니다(연장이 실제로 실패했으므로).

#### 검증 과정에서 발견한 별개 문제

로컬 검증 환경을 만드는 과정에서 세 가지를 추가로 발견해 함께 처리했습니다.

**(1) Worker → CAP 콜백이 깨져 있었음**

CAP을 실제 인증으로 띄우면 Worker의 기본 Basic 인증(`CAP_WORKER_USERNAME/PASSWORD`)이 거부되어 `claimTranscription`이 401로 실패합니다. 목록 조회는 이 경로를 타지 않아 **전사 시점에야 드러나는** 문제입니다.

`cap_client.py`가 client credentials를 우선 사용하므로, `.env`에 `CAP_WORKER_TOKEN_URL` / `CLIENT_ID` / `CLIENT_SECRET`을 채우면 해결됩니다. 배포 Worker와 같은 방식이며, `xs-security.json`의 `authorities`에 Worker scope가 있어 XSUAA service key로 받은 토큰에 scope가 실립니다.

검증: 토큰에 `Worker` scope 포함 확인 → CAP `/internal/Meetings` 호출 200 → 대조로 `Basic worker:worker`는 401.

**(2) `[hybrid]` 프로파일이 db를 강제하고 있었음**

`[hybrid]`에 `"db": "hana"`를 두면 HDI 컨테이너 바인딩이 없는 환경에서 서비스가 기동조차 되지 않습니다. 이 설정은 없어도 됩니다. `cds bind`로 바인딩하면 cds가 바인딩에서 kind를 읽고, 바인딩이 없으면 SQLite로 폴백해 로컬 실행이 계속 가능합니다. 제거하는 편이 엄격하게 더 낫습니다.

**(3) `useBrowserSessionKeepAlive()`의 hostname 가드가 낡음**

이 가드는 "로컬에는 Approuter가 없다"는 전제로 만들어졌습니다. `/user-api/currentUser`가 404를 반환해 엉뚱한 모달이 뜨는 것을 막으려는 방어였습니다.

이번에 로컬에도 Approuter와 XSUAA를 붙이면서 그 전제가 깨졌습니다. 결과적으로 로컬에서 세션 기능 전체를 검증할 수 없고, "연장했는데 아무 일도 일어나지 않는" 혼란이 생깁니다. 404를 조용히 무시하도록 바꾸고 hostname 검사를 제거하면 환경을 자동으로 따라가게 됩니다. **별도 이슈로 남깁니다.**

#### 보류한 항목

**4순위(로그아웃 플래그)** — 1·2순위가 적용되면 로그아웃 후 페이지가 캐시에서 부팅되지 않으므로 이 모달은 거의 뜨지 않습니다. 남는 것은 `/logout` 내비게이션이 진행되는 짧은 순간의 401뿐입니다. 상태 플래그를 도입하면 관리 지점이 늘어나므로, **실제로 유령 모달이 관찰되는지 확인한 뒤 판단**합니다.

**5순위(모달 탈출구)** — 독립적이고 안전하지만, 모달을 닫은 뒤 사용자가 무엇을 보게 될지(빈 목록? 에러?)를 함께 설계해야 어중간한 UX가 되지 않습니다.

## 2. 요청 폭발 관련 문제

### 문제 상황

`api.js:559` `listMeetings()`가 회의 **1건당 4개의 HTTP 요청**을 발생시킵니다:

```
GET /api/Meetings                    ← 전체 목록 (페이지네이션 없음)
  회의마다 반복:
    POST getMeetingStatus            ← 상태
    GET  Transcripts?$filter=...     ← 전사문 전체
    GET  Summaries?$filter=...       ← 요약 전체
    GET  ReviewItems?$filter=...     ← 검토 후보
```

`capJobFromMeeting()`(`api.js:362-369`)이 목록 항목마다 호출되기 때문입니다. 총 요청 수는 **1 + 4N**:

|회의 수|요청 수|비고|
|---|---|---|
|20건|81|현재는 견딜 만함|
|100건|401|체감 저하 시작|
|300건|1,201|사실상 사용 불가|

더 큰 문제는 **목록 한 번 그리려고 모든 회의의 전사문 전문을 브라우저로 내려받는다**는 점입니다. 1시간 회의 전사문이 수십 KB라면 100건에서 수 MB가 됩니다. 검색이 전사 내용까지 되는 이유가 바로 이것 — `renderMeetingListView()`가 **클라이언트에서 필터링**하기 때문입니다.

같은 패턴이 상세 화면 폴링에도 있습니다. `app.js:2078`이 2초마다 `tick`을 돌리고, `getJob` → `capGetJob` → `capJobFromMeeting`이 또 4요청을 만듭니다. **회의 상세를 열어두면 2초마다 4개 요청**이 나갑니다.

#### 현재 비용 해부

목록 1회 로드 시 회의 N건에 대해:

| 호출                      | 횟수  | 실제 목록에서 쓰이는가       |
| ----------------------- | --- | ------------------ |
| `GET /api/Meetings`     | 1   | ✅                  |
| `POST getMeetingStatus` | N   | ✅ 상태·큐 정보          |
| `GET Transcripts`       | N   | ⚠️ **검색 텍스트 생성에만** |
| `GET Summaries`         | N   | ⚠️ **검색 텍스트 생성에만** |
| `GET ReviewItems`       | N   | ❌ **전혀 안 씀**       |
**총 `1 + 4N` 요청.** 여기에 서버 측 DB 쿼리가 겹칩니다. `meetingStatusFor`(`meeting-service.js:384`)는 회의당 2~4개 쿼리를 돌리는데, 그중 `transcriptionQueueInfo`(`:430`)가 특히 나쁩니다:

```
const rows = await SELECT.from(TranscriptionDispatches).where({status: {in:[...]}})  // 전체 스캔
const meetings = await SELECT.from(Meetings).where({ID: {in: meetingIds}})           // 전체 스캔
```

**큐 정보는 전역 값인데 회의마다 똑같이 다시 계산합니다.** N=100이면 동일한 전체 스캔을 200번 반복합니다.

핵심 진단 3가지:

1. `ReviewItems` N회 조회는 **순수 낭비** (목록 렌더러 어디에도 안 쓰임)
2. `Transcripts`/`Summaries` N회 조회는 **클라이언트 검색 하나 때문**
3. 큐 계산은 **1회면 될 것을 N회** 반복

### 개선 계획

#### Phase 1 — 서버에 목록 전용 action 신설 (핵심)

**목표**: `1 + 4N` 요청 → **1 요청**

#### 1-1. CDS 계약 추가 — `meeting-service.cds`

```
type MeetingListItem {
  ID, title, category, participants, ownerName,
  status, percent, durationSec, createdAt,
  dispatchStatus, queuePosition, queueAheadCount, queueSize,  
  canEdit, canDelete
}
type MeetingListResult {
  items      : array of MeetingListItem;
  total      : Integer;          // 페이지네이션용 전체 건수
  categories : array of String;  // 필터 옵션 (아래 주의사항 참조)
  people     : array of String;  // 참여자 자동완성
}
action getMeetingList(
  search: String, stage: String, category: String,
  top: Integer, skip: Integer
) returns MeetingListResult;
```

필드 목록은 `renderMeetingList`와 `queueStatusText`, `renderMeetingListView`가 실제로 참조하는 것만 추린 결과입니다. `transcript`·`note`·`transcript_review_items`는 목록에서 제외됩니다.

#### 1-2. 큐 계산을 1회로 — 가장 큰 서버 이득

`transcriptionQueueInfo(meeting, dispatch)`를 **인덱스 빌더**로 리팩터링:

```
buildQueueIndex()  →  Map<meetingId, {position, aheadCount, size}>
```

전체 스캔 2회로 전 회의의 큐 위치를 한 번에 계산합니다. 기존 `getMeetingStatus`도 이 인덱스를 쓰도록 바꾸면 상세 화면 폴링도 함께 가벼워집니다.

#### 1-3. dispatch 배치 조회

회의별 `SELECT.one.from(TranscriptionDispatches)` N회 → `WHERE meeting_ID IN (...)` 1회 후 메모리에서 매핑.

#### 1-4. 서버 사이드 검색

2단계로 나눠 각각 O(1) 쿼리:

```
① Meetings 테이블 검색: title, category, participants, sharedWith, ownerName  → LIKE
② 내용 검색: Transcripts.content / Summaries.content LIKE → meeting_ID 집합 추출
③ ① OR ② 를 meetingAccessWhere(req) 와 AND 결합
```

**권한 필터는 반드시 기존 `meetingAccessWhere()`를 재사용**해야 합니다. 새 경로에서 권한 로직을 다시 짜면 우회 취약점이 생깁니다. 이 계획에서 가장 주의할 지점입니다.

> **성능 주의**: `LIKE '%키워드%'`는 HANA에서 전체 스캔입니다. 수백 건까지는 충분하지만, 수천 건이 되면 HANA Full-Text Index를 걸거나 `accessTokens`처럼 비정규화 `searchText` 컬럼을 두는 방식으로 확장해야 합니다. Phase 1에서는 스키마 변경 없이 가고, 실측 후 판단하는 것을 권합니다.

**예상 효과**: 100건 기준 401요청 → 1요청, DB 쿼리 ~600개 → ~5개.

#### Phase 2 — 프론트 전환

#### 2-1. `api.js` `listMeetings()` 교체

새 action 하나만 호출하도록 변경. `capJobFromMeeting`은 **상세 화면 전용**으로 남깁니다(삭제하면 안 됨).

#### 2-2. 클라이언트 필터링 제거

`renderMeetingListView()`의 `meetingsCache.filter(...)`와 `buildMeetingSearchText()`를 걷어내고, 검색어·필터 변경 시 서버 재조회로 전환합니다.

- **debounce 300ms** 필수 (타이핑마다 요청 방지)
- 조회 중 스켈레톤 유지 — 이미 `loadList()`에 있는 패턴 재사용
- 기존 URL 동기화(`syncListFiltersToUrl`)는 **그대로 유지** — 상세에서 돌아왔을 때 조건 복원은 지켜야 할 UX

#### 2-3. 반드시 함께 고쳐야 할 4가지 (놓치기 쉬움)

목록 캐시에 의존하던 기능들이 페이지네이션으로 깨집니다:

|기능|현재 구현|조치|
|---|---|---|
|카테고리 필터 옵션|`knownCategories()`가 `meetingsCache`에서 수집|서버가 `categories` 반환|
|참여자 자동완성|`knownPeopleValues()`가 동일|서버가 `people` 반환|
|전체 건수 표시|`updateListCount()`가 `meetingsCache.length`|서버 `total` 사용|
|목록 캐시 재사용|`if (!meetingsCache.length)` 스켈레톤 분기|페이지 단위 캐시로 의미 재정의|

이 4개를 빠뜨리면 "카테고리 필터에 항목이 안 뜬다" 같은 버그로 돌아옵니다. Phase 1의 `MeetingListResult`에 `categories`/`people`/`total`을 넣어둔 이유입니다.

#### Phase 3 — 상세 화면 폴링 최적화 (보류)

> **정정**: 처음에는 "회의 상세를 열어두기만 해도 2초마다 4요청이 계속 나간다"고 적었으나 **사실이 아닙니다.** `openMeeting`은 처리 중인 회의에만 폴링을 시작하고(`app.js:2052`), tick 역시 `done`/`failed`에 도달하면 스스로 멈춥니다. **완료된 회의를 열면 요청은 0입니다.** 백그라운드 작업을 유발하는 액션(요약 재생성, 검토 생성, 재전사, 업로드) 뒤에는 폴링이 모두 정상적으로 재시작되며 누락된 경로는 없습니다.

따라서 이 항목은 **"처리가 진행되는 동안"에 한정된 문제**입니다. tick 1회는 `getMeetingStatus` + `Transcripts` + `Summaries` + `ReviewItems` = 4요청인데, **전사 중에는 뒤의 세 개가 아직 존재하지 않는데도 매번 조회**합니다. 4요청 중 3개가 빈 응답입니다.

1시간 회의 기준(전사 1~2분 + 요약 10초, 약 2분 처리):

| | 요청 수 | 그중 빈 응답 |
|---|---:|---:|
| 현재 | 약 240 | 약 180 |
| 개선 후 | 약 40~60 | 0 |

**개선 방향**

1. 폴링은 `getMeetingStatus` **1회만** 호출
2. `transcript`/`summary`는 **상태 전이 시점에만** 1회 로드 (`transcribing → summarizing`, `summarizing → done`)
3. 백오프 도입: 처음 30초는 2초, 이후 5초, 2분 후 10초
4. `ReviewItems`는 검토 기능을 쓸 때만 로드 — 모든 상세 진입이 4요청에서 3요청이 됩니다

**보류한 이유**

- 폴링 상태 기계를 손대는 작업이라 진행률 표시·완료 감지·재시도 흐름이 얽혀 있어 **회귀 위험이 Phase 1·2보다 큽니다.**
- 검증하려면 **실제 전사를 여러 번 돌려야** 합니다(AI Core 과금).
- Phase 1·2에서 목표의 대부분을 이미 달성했습니다.

처리 중 화면이 느리다는 체감이 실제로 생겼을 때 착수해도 늦지 않습니다.

#### 달성한 것

| 항목 | 이전 | 이후 |
|---|---|---|
| HTTP 요청 | `1 + 4N` | **1** |
| 전송 데이터 | 전 회의 전사문 전문 | 목록 카드용 필드만 |
| DB 쿼리 | 약 6N | 4~5 (건수 무관) |
| 검색 | 클라이언트 필터 | 서버 (본문 포함, 대소문자 무관) |

#### 서버 (Phase 1)

`getMeetingList` action을 신설했습니다. 계획한 4개 항목을 모두 반영했습니다.

- **큐 계산 1회** — `transcriptionQueueInfo`가 회의마다 전체 스캔 2회를 반복하던 것을 `buildQueueIndex`로 바꿔 한 번만 계산합니다. `getMeetingStatus`도 같은 함수를 쓰므로 상세 폴링도 함께 가벼워집니다.
- **dispatch 배치 조회** — 회의별 N회에서 `IN` 절 1회로.
- **서버 사이드 검색** — 전사문/요약 본문은 `meeting_ID`만 모아 오므로 회의 수와 무관하게 쿼리 2회입니다.
- **권한 필터** — 기존 `meetingAccessWhere`를 그대로 재사용했습니다.

정렬·필터·페이지네이션은 DB가 아닌 **서버 메모리**에서 처리했습니다. 회의 메타데이터 조회는 쿼리 1회로 끝나고, 없앤 것은 회의당 4회 왕복이기 때문입니다. 수천 건 규모가 되면 DB `LIMIT`과 Full-Text Index로 옮겨야 하며 해당 지점을 코드 주석에 남겼습니다.

#### 프론트 (Phase 2)

`listMeetings`가 새 action 하나만 호출합니다. `capJobFromMeeting`은 전사문/요약이 필요한 **상세 화면 전용으로 유지**했습니다.

`buildMeetingSearchText`와 클라이언트 필터링을 제거하고, 계획의 "반드시 함께 고쳐야 할 4가지"를 모두 반영했습니다. 카테고리 옵션·건수, 참여자 자동완성, 전체 건수는 서버가 **접근 가능한 전체 회의** 기준으로 계산해 주므로 페이지네이션 이후에도 후보가 사라지지 않습니다.

검색 입력 처리에 세 가지를 함께 넣었습니다.

- **debounce 300ms** — 타이핑마다 서버를 호출하지 않습니다.
- **요청 경합 방지** — `listRequestId`로 늦게 도착한 이전 응답이 최신 결과를 덮어쓰지 못하게 막습니다.
- **URL 갱신 최소화** — `replaceState`를 debounce 안으로 옮기고 값이 그대로면 생략합니다.

#### 검증 중 잡은 것 — 계획에 없던 두 가지

**(1) HANA `LIKE`의 대소문자 구분**

`STT`, `Q&A` 같은 영문이 검색되지 않았습니다. `normalizeSearchTerm`이 검색어를 소문자로 정규화하는데 본문은 원본 표기 그대로였고, **HANA의 `LIKE`는 대소문자를 구분**합니다. 한글이 잘 되던 이유도 이것입니다(대소문자 개념이 없음).

DB에 직접 질의해 확정했습니다.

| 질의 | 결과 |
|---|---|
| `LIKE '%stt%'` | 0건 |
| `LIKE '%STT%'` | 1건 |
| `lower(content) LIKE '%stt%'` | 1건 |
| `LIKE '%전사%'` | 19건 |

본문 쪽에 `lower()`를 적용해 해결했습니다. 제목·참여자 검색은 이미 JS에서 소문자로 비교하고 있어 영향이 없었습니다.

**(2) `replaceState`로 인한 favicon 반복 요청**

타이핑 한 글자마다 `favicon.svg` 요청이 발생했습니다. `syncListFiltersToUrl`이 매 입력마다 `history.replaceState`를 호출했고, 브라우저가 URL 변경 때마다 favicon을 다시 확인하기 때문입니다. 디스크 캐시에서 응답되어 비용은 거의 없지만 불필요한 노이즈였습니다.

> 이 수정을 확인하는 과정에서 **`?v=` 캐시 버전을 올리지 않아** 브라우저가 이전 `app.js`를 계속 쓰는 일이 있었습니다. 1번 문제에서 다룬 캐시 함정과 같은 계열입니다. **JS를 수정할 때마다 버전을 함께 올려야 합니다.**

#### 검증 결과

| 항목 | 결과 |
|---|---|
| 요청 수 | `getMeetingList` 1건만 발생. `Transcripts`/`Summaries`/`ReviewItems` 사라짐 |

## 3. 요약/검토가 멈추는 문제

### 문제 상황

`요약 다시 생성`을 누른 직후 CAP 서버가 종료되면 회의가 **영구히 `summarizing` 상태로 멈춥니다.**

실제로 겪은 사례: 7초짜리 회의(`20260803 인터뷰`, 평소 처리 22.5초 / 요약 6.8초)에서 요약 재생성 중 CAP을 껐더니 진행도 85%에서 멈췄고, **CAP을 다시 켜도 몇 분이 지나도록 그대로**였습니다.

### 원인 분석

```
1. '요약 다시 생성' 클릭
   -> runSummary 가 status=summarizing, percent=85 를 DB에 기록
   -> startBackgroundAiTask 로 백그라운드 요약 시작 (setImmediate, 메모리 상주)

2. CAP 종료
   -> 백그라운드 작업이 프로세스와 함께 사라짐
   -> DB에는 summarizing / 85% 만 남음

3. CAP 재시작
   -> 재개하는 코드가 없음. 백그라운드 작업은 프로세스 안에서만 산다
   -> 회의는 영원히 summarizing
```

**빠져나올 방법이 없었습니다.**

- `cleanup.js`의 `failStaleMeetings`는 `queued`·`transcribing`만 검사합니다. `summarizing`은 자동 복구 대상이 아니었습니다.
- `rejectIfMeetingBusy`가 `summarizing` 상태의 `runSummary`를 **409로 거부**해 UI 재시도도 불가능했습니다.

| 상태 | cleanup 자동 복구 | UI 재시도 |
|---|---|---|
| `queued` | O | O |
| `transcribing` | O (heartbeat 감시 포함) | O |
| **`summarizing`** | **X** | **X (409)** |
| **`reviewing`** | **X** | **X (409)** |

전사 경로는 Worker heartbeat까지 감시하며 촘촘히 방어하는데 **요약만 빠져 있었습니다.**

### 운영에서도 재현됩니다

이번에는 서버를 직접 껐지만, 같은 일이 운영에서도 일어납니다.

- CF 앱 재시작·재배포 (`cf restage`, `cf deploy`)
- 인스턴스 크래시, OOM
- 요약 중 프로세스 종료

### 해결 방법

`cleanup.js`에 `recoverStaleAiTasks`를 추가했습니다. 일정 시간(`CAP_AI_TASK_STALE_MS`, 기본 30분) 이상 `summarizing`/`reviewing`에 머문 회의를 정리합니다.

```
요약이 남아 있으면  -> done / 100% 로 복구   (보여줄 결과가 있음)
요약이 없으면       -> failed 로 표시        (사용자가 다시 시도 가능)
```

**설계에서 주의한 두 가지**

1. **staleness를 반드시 먼저 본다.** 재요약 중에도 기존 summary는 남아 있습니다. `generateSummaryForMeeting`이 LLM 응답을 받은 뒤에야 기존 요약을 교체하기 때문입니다. summary 존재만으로 완료 판정하면 **정상 진행 중인 작업을 끊게 됩니다.**
2. **임계값을 넉넉히 잡는다.** 긴 회의는 12,000자 단위 분할 요약 후 반복 결합이라 수 분이 걸립니다. 기본 30분으로 두었습니다.

### 검증

**멈춘 회의 복구** — DB를 직접 확인한 결과 transcript 1건, summary 1건(전날 성공분)이 그대로 있었고 상태 필드만 잘못돼 있었습니다. `done` / 100%로 되돌려 즉시 복구했습니다.

**자동 복구 동작** — 임계값을 1분으로 낮추고 실제 CAP에서 확인했습니다.

1. 요약 재생성 중 CAP 강제 종료
2. CAP 재시작
3. 2분 안에 회의가 `done`으로 자동 복구
4. 로그에 `recovered 1 meeting(s) left in an AI task state` 출력

> 검증 도중 배운 것: `cleanup.js`는 `cds.entities`를 쓰기 때문에 **실행 중인 CAP 밖에서는 동작하지 않습니다.** 독립 스크립트로 검증하려던 시도가 실패하면서 회의를 `summarizing` 상태로 남기는 일이 있었고 즉시 복구했습니다. 운영 DB에 직접 쓰는 스크립트는 실패 시 원상복구까지 스크립트 안에서 보장해야 합니다.

### 커밋


## 4. 테스트 신호 복구

### 문제 상황

- JS 테스트 3개(`tests/ai-core-summary.test.js`, `transcript-validation`, `transcription-dispatcher`)가 **어떤 npm 스크립트에도 물려 있지 않았습니다.**
- `npm test`는 pytest만 돌리는데, 26개 중 21개가 폐기된 `legacy/fastapi` 대상이었습니다.

CAP의 요약 chunking·transcript 검증·큐 로직을 지키는 테스트가 **있는데 안 돌고 있었고**, 통과해도 현재 코드가 안전하다는 뜻이 아니었습니다.

### 적용 결과

스크립트를 목적별로 나눴습니다.

| 스크립트 | 대상 |
|---|---|
| `npm test` | **현재 코드를 지키는 것만** (JS + worker) |
| `npm run test:js` | `node --test "tests/*.test.js"` |
| `npm run test:worker` | worker 테스트 5개 |
| `npm run test:all` | legacy 포함 pytest 전체 |

**결과: JS 18개 + worker 29개 = 47개 통과.**

#### 배선하자마자 드러난 것 — 테스트 격리 결함

worker 테스트 3개가 실패했는데, **원래 깨져 있던 것**이 실행되지 않아 드러나지 않았을 뿐이었습니다.

`Settings`가 프로젝트 루트 `.env`를 `env_file`로 읽는데, 테스트는 `monkeypatch.delenv`로 "설정되지 않은 상태"를 만들려 합니다. **`delenv`는 프로세스 환경변수만 지우고 `.env` 파일은 그대로 읽힙니다.**

| 실패한 테스트 | 읽혀버린 `.env` 값 |
|---|---|
| `test_transcribe_rejects_when_required_token_is_not_configured` | `TRANSCRIPTION_WORKER_TOKEN` |
| `test_transcribe_rejects_without_cap_base_url` | `CAP_INTERNAL_BASE_URL` |
| `test_cap_client_uses_bound_xsuaa_credentials` | `CAP_WORKER_CLIENT_ID/SECRET` |

**깨끗한 체크아웃에서는 통과하고 설정된 개발 환경에서는 실패**하는 상태라 신호를 믿을 수 없었습니다. `tests/conftest.py`를 추가해 테스트에서 `env_file`을 끄도록 했습니다.

#### 새 테스트

3번 항목에서 고친 `recoverStaleAiTasks`를 5개 케이스로 검증합니다. 특히 다음을 못박았습니다.

```
아직 오래되지 않았으면 요약이 있어도 건드리지 않는다
```

재요약 중에는 기존 요약이 남아 있으므로, staleness를 먼저 보지 않으면 정상 진행 중인 작업을 완료로 오판합니다. 이 규칙이 이제 테스트로 지켜집니다.

#### 환경 관련 참고

venv에 `pytest`가 설치되어 있지 않았습니다(`requirements.txt:9`에 선언되어 있음). 팀원도 같은 상황일 수 있으므로 로컬 준비 절차에 `pip install -r requirements.txt`가 안내되어 있는지 확인이 필요합니다.

- **Phase 3 상세 폴링 최적화** — 처리 중 화면이 느리다는 체감이 생기면
- **로그아웃 4·5순위** — 유령 모달 플래그, 모달 탈출구. 1·2순위 적용 후 실제로 관찰되는지 확인 후 판단
- **`useBrowserSessionKeepAlive()` hostname 가드** — 로컬에 Approuter가 생겨 전제가 깨졌습니다. 404를 조용히 무시하도록 바꾸고 hostname 검사를 제거하면 환경을 자동으로 따라갑니다
- **성능 실측** — 목록 개선의 before/after를 200건 규모에서 측정
