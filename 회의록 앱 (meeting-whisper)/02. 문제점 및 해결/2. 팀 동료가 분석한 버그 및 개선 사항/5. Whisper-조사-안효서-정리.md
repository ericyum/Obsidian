# Whisper 조사 — 전체 정리

한눈에

- **범위**: 공통과제 2목표 전 영역 — Whisper 구조 파악 + CI/CD 특화 + 모델 버전업 이슈까지 현재까지 조사한 전부.

- **근거 표시**: 소스코드·mta.yaml·config.yml에 직접 있는 내용은 **[근거]**, 일반 문서·지식으로 보충한 내용은 **[추정]**. [추정]은 실제 적용 전 공식 문서 확인 필요.

## A. Whisper 구조 파악 [근거: 소스 `meeting_whisper` main]

### A1. 전체 구조 한눈에

**CF 앱 4종**:

|앱|역할|
|---|---|
|`meeting-whisper-approuter`|진입점, XSUAA 인증, 정적 UI 서빙|
|`meeting-whisper-srv`|CAP 본체 (권한·대기열·요약)|
|`meeting-whisper-stt-worker`|Python FastAPI, 전사|
|`meeting-whisper-db-deployer`|HDI 스키마 배포|

**BTP 서비스**: HANA HDI(`zen-meeting-whisper`), XSUAA(`meeting-whisper-auth`), Object Store(write/read 2종), AI Core(`default_aicore`).

**CAP 서비스 2종**: `MeetingService`(`/api`, 사용자용, 권한 `MeetingUser`), `WorkerInternalService`(`/internal`, Worker 콜백용, 권한 `Worker`).

**데이터 모델**(`cap/db/schema.cds`):

- `Meetings` — `status`(`created → audio_uploaded → queued → transcribing → summarizing → done | failed`), `percent` 진행률
- `AudioObjects` — 오디오 원본. `storageKind`가 `db`이면 HANA, Object Store면 `objectKey` + signed URL
- `TranscriptionDispatches` — 사실상 대기열. `status`(`queued → dispatching → dispatched | failed`), `attempts`, `nextAttemptAt`, `workerRunId`, `workerStage`, `workerHeartbeatAt`
- `Transcripts`, `Summaries`, `ReviewItems`, `AiCoreUsageLogs`

### A2. 시나리오 A — 접속·인증·권한

```text
Browser -> Approuter(/index.html) -> XSUAA 로그인 -> /user-api/currentUser
        -> UI가 /api/Meetings 호출 -> Approuter가 xsuaa 인증으로 CAP 전달
        -> CAP before("READ","Meetings") 가 accessTokens 필터 적용
```

- Approuter 라우팅(`xs-app.json`): `/api/*`, `/api-binary/*`, `/internal/*` → `destination: srv-api`, catch-all `localDir: resources`에서 정적 UI.
- 권한 **두 층**:
    - **XSUAA 역할**(`MeetingUser`/`MeetingAdmin`/`Worker`) = "앱 접근 허용 여부"
    - **`accessTokens`** 문자열 필드 = 회의 단위 열람·편집. owner·participants·sharedWith 이름·이메일을 `\n토큰\n` 형태로 합침. 줄바꿈 감싼 건 부분 매칭 오류(`kim`이 `kim@example`에 걸림) 방지.
- `before("READ","Meetings")`에서 owner 또는 토큰 매칭 조건을 WHERE에 끼워 넣음.

### A3. 시나리오 B — 생성·업로드·대기열

```text
UI createJob()
  1. POST /api/Meetings              (회의 row 생성, accessTokens 세팅)
  2. POST /api-binary/Meetings/{id}/audio  (오디오 스트림 업로드 -> Object Store)
  3. POST /api/enqueueTranscription  (status=queued, TranscriptionDispatches row 생성)
  -> dispatcher 폴링이 dispatch row를 잡아 Worker /transcribe로 POST
```

- 오디오는 OData `LargeBinary`가 아니라 전용 스트림 라우트. `server.js` bootstrap에서 `/api-binary/Meetings/:meetingId/audio` Express 라우트 mount. **150MB 한계를 CAP body parser가 아니라 이 라우트에서 처리**.
- `enqueueTranscription` → 기존 transcript/summary/review 지우고 `status=queued, percent=10` + dispatch row 생성.
- **`req.on("succeeded", ...)`** — 사용자에게 응답 반환한 **후에** 대기열 처리 깨움. 즉시 응답, 전사는 비동기.
- dispatcher: `setInterval` 5초 폴링, `status=queued` & `nextAttemptAt` 도래 row를 5개씩 잡아 Worker로 POST. Worker 429 → `WORKER_BUSY` 마킹 → backoff 재시도.
- UI는 `queuePosition`·`queueAheadCount`로 "앞 작업 N건 처리 후 시작" 안내.

### A4. 시나리오 C — Worker 전사 (긴 오디오 분할·재시도·검증)

```text
Worker /transcribe (202 Accepted)
  1. slot 획득 (Semaphore=2) -> CAP claimTranscription (status=transcribing, 20%)
  2. background task: CAP getAudio -> (downloadUrl or base64) 임시 파일
  3. run_transcription -> aicore_stt
       - 720초 초과 or 25MB 초과 -> PyAV로 WAV chunk 분할
       - chunk별 AI Core /v2/completion 호출 (base64 file_data)
       - 응답 JSON 검증 실패 -> 같은 chunk 2회 재시도 -> 실패 시 절반으로 재분할
  4. heartbeat 30~60초 간격 + 진행률 heartbeat (30~74%)
  5. transcript 검증 -> CAP saveTranscript (content=JSON) -> Worker 종료
```

- **claim-then-202 순서**: Worker가 받아들인 줄 알고 CAP이 `dispatched`로 바꾼 뒤, 정작 Worker가 처리 안 하면 row 방치. 먼저 claim으로 `workerRunId` 검증·기록 → "이 실행이 진짜 주인" 확정. claim 실패 시 slot 반납 + 502.
- Worker→CAP 인증: XSUAA client-credentials 토큰(30초 전 미리 갱신·캐싱).
- 오디오 획득: Object Store signed URL 있으면 `httpx` 스트림 임시 파일, 없으면 `contentBase64` 디코딩.
- 분할 기준(`_should_chunk_audio`): `AICORE_STT_CHUNK_SECONDS`(720) 초과 or `AICORE_STT_INLINE_MAX_AUDIO_BYTES`(25MB) 초과. PyAV로 16kHz·mono·s16 WAV 청크.
- AI Core 호출: base64 `file_data`를 `prompt_templating` 모듈, 모델 `gemini-2.5-flash`, `/v2/inference/deployments/{deploymentId}/v2/completion` POST.
- 검증 양쪽: Worker `_normalize_segments()`(타임스탬프 단조·범위·중복), 실패 시 `AICORE_STT_MAX_ATTEMPTS`(2) 재시도 → 그래도 실패 시 chunk 절반 재분할. 저장 전 `_validate_transcript_for_storage()` 한 번 더.
- **★ Worker는 전사까지만 하고 종료. 요약 안 함.** HTTP 수명 단축 — Worker가 요약까지 붙들면 slot 늘어지고 비용 커짐.

### A5. 시나리오 D — 요약·검토 (CAP background)

```text
CAP saveTranscript (WorkerInternalService)
  -> transcript 검증 -> Transcripts 저장 -> status=summarizing, 80%
  -> startWorkerSummaryTask (setImmediate, 비동기)
     -> ai-core.summarizeMeeting (AI Core Orchestration, template 모드)
     -> 12000자 chunk 부분 요약 -> 16000자 reduce 결합
     -> Summaries(content JSON + markdown) 저장 -> status=done, 100%
     -> finally: deleteAudioForMeeting (Object Store 원본 정리)

검토는 사용자 요청 시 별도 action:
  runReview -> ai-core.reviewMeeting (direct 모드, CAP_LLM_MODEL) -> ReviewItems 저장
```

- `saveTranscript` 검증 후 transcript 저장, **즉시 응답 반환하면서** `startWorkerSummaryTask()`를 `setImmediate`로 띄움.
- 요약: `summarizeMeeting()`이 transcript를 12,000자 단위로 자르고, 청크 여러 개면 부분 요약 → 16,000자 reduce 결합. `normalizeNote()` 정규화 → `Summaries`에 JSON + Markdown 저장.
- **요약 모델 두 갈래**: 요약 = AI Core template(`meeting-whisper-summary-ko-v1`)이 모델 결정, 검토 = `CAP_LLM_MODEL=anthropic--claude-4.7-opus` direct 직접 지정.
- 요약 끝나면 `finally`에서 원본 오디오 삭제. 전사 실패로 transcript 없으면 원본 보존(재전사 가능).
- 검토: `runReview` action, summary가 입력(transcript 전체 아님) → `ReviewItems` 저장.

### A6. 시나리오 E — 권한 기반 접근 제어

```text
owner           -> 전부 가능
participants    -> 열람 + 내용 편집, 접근관리·삭제 불가
sharedWith      -> 열람만
MeetingAdmin    -> 전체 접근 (운영자)
```

- `canReadMeeting()` — owner 또는 토큰이 `accessTokens`에 있거나 참여자·공유자 토큰 겹침.
- `canEditMeeting()` — owner이거나 **참여자 토큰만** 매칭. 공유자 편집 불가.
- 삭제 — `assertDeletableMeeting()`이 owner 일치 확인.
- CRUD before 훅: `before("READ")` accessTokens 필터, `before("UPDATE")`·`before("DELETE")` `owner = currentUserId`. 자식 엔티티도 `restrictChildReadToAccessibleMeetings()`.

### A7. 정적 UI 서빙 — OTT와 다른 점

- Whisper는 **HTML5 App Repository 안 씀**. 정적 UI(`app/meeting-ui/`, plain JS)를 approuter CF 앱 안에 번들링.
- `scripts/copy-web-assets.js`가 빌드 시 `app/meeting-ui` → `approuter/resources`(운영), `approuter/dev/resources`(로컬)로 복사.
- approuter `xs-app.json` catch-all `localDir: "resources"`로 서빙. CAP srv도 로컬 `cds serve` 시 `express.static` mount.
- **프론트 배포 = approuter 재빌드·재배포 한 방**, 별도 Repo 업로드 단계 없음.

### A8. 인증 양방향

- CAP→Worker: shared Bearer token(`TRANSCRIPTION_WORKER_TOKEN`)
- Worker→CAP: XSUAA client-credentials(Worker scope)

### A9. 실시간 임시 전사 vs 최종 전사 — 통합 불가 구조 [근거]

**실시간 임시 전사 = 브라우저 `SpeechRecognition` (Web Speech API)**

- `app/meeting-ui/js/app.js:1570` — `live = new SpeechRecognition()`, `live.lang = "ko-KR"`, `live.interimResults = true`
- 브라우저 내장 음성인식. **서버 안 거침.** 결과는 메모리 변수 `liveFinalText` / `liveInterimText`만. `commitLiveInterim()`로 임시→확정 커밋.
- 녹음 중 화면에 텍스트 뿌려주는 용도. 평문. 휘발.

**최종 전사 = 서버 AI Core Gemini**

- 오디오 업로드 → CAP 대기열 → Worker → Gemini AI Core(720s 분할·검증) → `Transcripts` 엔티티에 JSON segments 저장.

**통합이 안 되는 이유 — 4축 전부 다름:**

|축|실시간 임시|최종|
|---|---|---|
|엔진|브라우저 Web Speech API (기기·브라우저 의존)|Gemini AI Core (서버)|
|저장|브라우저 메모리 (휘발, `currentDraft.liveText`)|HANA HDI `Transcripts` (영구)|
|포맷|평문 텍스트|segments JSON (타임스탬프·화자 구조)|
|타이밍|녹음 중 실시간|녹음 후 비동기 배치 (대기열·수 분)|

**결정적**: 지금 설계가 **의도적 분리**. Worker는 전사까지만 하고 종료(HTTP 수명 단축이 핵심). 실시간 결과를 서버로 스트리밍 저장하려면 Worker/CAP이 실시간 텍스트를 들고 있어야 → 이 설계와 정면 충돌.

**통합하려면 구조 변경 필요**:

1. 실시간 결과를 서버에 스트리밍/저장 (지금은 클라이언트 메모리만)
2. 포맷 통일 — 브라우저 평문 ↔ Gemini segments(JSON) 변환 레이어
3. 병합 정책 — 최종 Gemini 결과로 실시간을 "교체"할지 "병합"할지 (지금 `enqueueTranscription`은 기존 transcript를 지움 → 실시간 결과랑 충돌)
4. UI도 두 결과를 한 화면에 합치는 정합성 처리

→ 실시간은 "보여주기용 브라우저 로컬", 최종은 "저장용 서버 Gemini"로 완전히 다른 파이프라인. 둘을 같은 데이터로 통합하려면 실시간 쪽을 서버로 끌어올리는 설계 변경이 선행.

### A10. 구조 한 장 요약

```text
접속     Browser -> Approuter(XSUAA) -> CAP(/api, /api-binary, /internal)
권한     XSUAA 역할(MeetingUser/Admin/Worker) + accessTokens(회의 단위 열람/편집)
생성     createJob = POST Meetings -> /api-binary 오디오 -> enqueueTranscription
대기열   TranscriptionDispatches row -> dispatcher 5s 폴링 -> Worker /transcribe (Bearer token)
전사     Worker claim -> getAudio(signed URL) -> AI Core STT(720s 분할, 2회 재시도) -> 검증 -> saveTranscript
요약     CAP saveTranscript -> setImmediate background -> ai-core template -> Summaries 저장 -> 원본 삭제
검토     runReview -> ai-core direct(CAP_LLM_MODEL) -> ReviewItems
UI 서빙  app/meeting-ui -> copy-web-assets -> approuter/resources (Repo 없음)
실시간   브라우저 SpeechRecognition (ko-KR, interimResults) — 메모리 only, 서버 미저장
인증     CAP->Worker: shared Bearer token / Worker->CAP: XSUAA client-credentials(Worker scope)
```

## B. 현재 배포 상태 — 파이프라인 없음 [근거]

```text
pytest → cds compile → cap:build → build:mtar → cf deploy
```

- rollback도 수동 — 이전 MTAR 찾아 `cf deploy` 다시.

## C. OTT CI/CD 정석 — 참고 기준 [근거+추정]

### C1. 관리형 CI/CD

SAP CI/CD Service = Project Piper. 관리형이라 서버 설치 불필요. 레포에 `.pipeline/config.yml` 선언형으로 두면 Service가 읽어 실행.

### C2. 파이프라인 6단계

```text
Build → Additional Unit Tests → Malware Scan(자동) → Acceptance → Compliance → Release
```

- 검사 4개(2·3·4·5단계), 빌드/배포 각 1개.
- **Malware Scan**은 자동. 나머지는 config.yml에서 선택.
- **Additional Unit Tests** — 단위 테스트(`npm run test`). 로직 오류 잡음.
- **Acceptance** — 인수 테스트, E2E. 정적 분석(런타임 결함)도 여기.
- **Compliance** — 컴플라이언스 정적 분석. **SonarQube** 연동(`sonarExecuteScan`). 보안 취약점·코딩 표준·중복. 서버 따로 필요. OTT 꺼져 있음.
- OTT는 Unit Tests + Malware Scan 위주로 구성.

### C3. mta.yaml vs config.yml — 축 분리

|파일|역할|예시|
|---|---|---|
|`mta.yaml`|**뭘 배포할까**|모듈·서비스·리소스|
|`.pipeline/config.yml`|**파이프라인 어떻게 돌릴까**|credential·stage·step·트리거|

완전 별개 파일. Job이 2개여도 mta.yaml은 1개 공유.

### C4. managed vs existing

- `managed` = 새로 만듦, `path` 필요.
- `existing` = 기존 서비스 참조, `service-name`만.
- approuter 두 역할: ① managed로 XSUAA 먼저 생성 ② `xs-app.json` 라우팅 지도 마지막 배포.

### C5. 배포 함정

- **approuter `..` 경로 차단**: BTP Deploy Service가 `..` 경로 무조건 차단(MtaPathValidator, path traversal 방지).
- **HDI 스키마**: db-deployer 재배포 시 권한 시드 덮어쓰기 위험. rollback 자동 안 됨(forward-only).

## D. 운영 층 심화 — config.yml만으로 끝 아님 [추정]

### D1. Job / credential / git

- **Job** = 파이프라인 실행 단위. 보통 레포 1 = Job 1. OTT 활성 9 MTA → Job 9, Whisper 1 MTA → Job 1.
- **credential** = 비밀번호를 Service 웹 UI에 이름으로 등록. config엔 이름만(`cfCredentialsId: "cf-credentials"`). org/space도 credential에 묶음.
- **git** = `productiveBranch` 푸시 시 트리거. OTT master / Whisper main.

### D2. dev/prod 분리

CF space 2개 + credential 2개 + Job 2개 + 브랜치 매핑(dev push → dev Job, master push → prod Job) + **수동 승인 게이트**(prod).

### D3. 수동 승인 게이트

Acceptance → Release 사이. "테스트 통과했지만 운영 배포는 사람이 승인" = 운영 무승인 배포 금지 제약의 파이프라인 구현. Whisper 적용 시 Release 전 의무화.

### D4. 산물(MTAR) 관리

빌드 산물 `.mtar`를 버전별 보관. rollback 시 이전 MTAR 사용. OTT `tmsUpload: false` → TMS 안 쓰고 수동/별도 Job으로 이관.

## E. Whisper 적용 시 함정 3가지 [근거+추정]

### E1. pytest 함정

`npmExecuteScripts`는 npm 스크립트만. pytest는 Python이라 기본 단계에 안 담김.

- **(A) npm 래퍼**: `package.json`에 `"test:worker": "python -m pytest ..."` 추가. 빌드 환경에 Python 있어야 함.
- **(B) 로컬 pre-merge 땜빵**: 파이프라인엔 안 넣고 머지 전 로컬에서 pytest.

### E2. Python 빌드 환경 — 최대 기술 위험

- Worker에 `build-parameters` 없음 [근거] → CF 런타임 buildpack이 Python 설치.
- 빌드 자체는 Python 안 필요할 수도. **진짜 막히는 건 pytest 실행 시 Python 필요.**
- 빌드 환경 `MBTJ11N22`(Node 22 베이스)가 Python 포함하는지가 관건. **실제 적용 시 가장 먼저 검증**.

### E3. HDI 권한 시드 덮어쓰기

db-deployer 재배포 시 권한 시드 덮어쓰기 위험. Production 데이터 변경 금지 제약과 충돌 → 시드는 최초 1회만, 이후 보존.

### E4. 의존성 순서 자동화 안 됨

파이프라인이 "library 먼저, approuter 나중" 순서를 모름. 사람이 순서를 정하거나 체인으로 구성. Whisper는 1-MTA라 순서 문제 적음.

## F. 모델 버전업 이슈 [근거]

### F1. 핵심: 2.5 Flash shutdown 2026-06-17

Whisper가 `AICORE_STT_MODEL: gemini-2.5-flash` 사용 [근거]. **2.5 Flash가 2026-06-17 shutdown**이라 이미 종료 시점. SAP AI Core가 아직 지원하더라도 곧 중단. **교체 필수.**

### F2. 후보 모델 비교

|모델|Input($/M)|Output($/M)|회의 1시간 비용|비고|
|---|---|---|---|---|
|2.5 Flash(현행)|$1.00(오디오)|$2.50|~$0.15|종료됨|
|**3.6 Flash**|$1.50(통합)|$7.50|~$0.32|2026-07-21 출시, 비싼 만큼 전사 품질 향상 명시 아님|
|**3.5 Flash-Lite**|$0.30|$2.50|~$0.09|2.5 동일가, 가성비 최고|

- 1M tokens ≈ 오디오 11시간(audio ~25 tokens/sec) [근거].
- 3.6 개선점(coding·research·computer-use)은 STT 전사와 무관. 한국어 순수 전사는 전용 STT가 더 좋을 수 있고, Gemini는 맥락·요약 강점 [추정].
- **현실적 경로 = 3.5 Flash-Lite**: 2.5 종료 대응 + 비용 우려 동시 해결. 전사만 보면 충분.
- 3.6은 전사 후 요약/의사결정 추출 고도화할 때.
- diarization: 현재 `DIARIZE: false`. Gemini 다이어라이제이션 자체 지원 → 켜면 화자 구분 가능(모델 교체와 별개) [추정].

### F3. CI/CD와의 연결

`AICORE_STT_MODEL` 속성 변경 = mta.yaml 수정 = **배포 단위**. 모델 교체는 CI/CD 파이프라인이 잡아야 할 변경 항목. SAP AI Core에서 3.5 Flash-Lite / 3.6 지원 여부 확인이 선행.
