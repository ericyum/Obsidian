# 07. 밑줄과 퍼센트 문자를 검색하지 못하던 문제

> 현재 상태: **해결·`main` 반영 완료**

## 문제 현상

회의 목록 검색을 CAP로 옮긴 뒤 `_`나 `%`가 든 실제 제목을 검색하지 못했다.

```text
실제 제목
→ 20260805_20260805 whisper 회의

사용자 검색
→ 20260805_20260805

초기 정규화 결과
→ 20260805 20260805

결과
→ 제목의 밑줄과 공백이 달라 검색 실패
```

## 원인

초기 `normalizeSearchTerm()`은 SQL `LIKE`의 와일드카드를 막기 위해 `%`와 `_`를 공백으로 바꿔다.

```js
.replace(/[%_]+/g, " ")
```

SQL `LIKE`에서 `%`는 임의의 길이, `_`는 임의의 한 문자를 의미한다. 하지만 제목·참여자 검색은 JavaScript `includes()`로 문자 그대로 비교하므로 검색어 자체를 바꾸면 안 됐다.

## 수정 1: 검색어 원문 보존

```js
function normalizeSearchTerm(value) {
  return String(value || "")
    .trim()
    .toLowerCase()
    .replace(/\s+/g, " ")
    .slice(0, 200);
}
```

`_`와 `%`는 삭제하지 않고 앞뒤 공백·대소문자·최대 길이만 정리한다.

## 수정 2: SQL `LIKE`에서만 이스케이프

전사문·요약 본문은 HANA `LIKE`로 검색하므로 이 경로에서만 특수 의미를 없앤다.

```js
function escapeLikePattern(term) {
  return term.replace(/[\\%_]/g, (char) => `\\${char}`);
}
```

```text
원본 A_B
→ LIKE 패턴 A\_B
→ ESCAPE \
→ `_`를 와일드카드가 아닌 실제 밑줄로 처리
```

CQN의 `{ val: pattern }`으로 바인딩하므로 SQL 문장 삽입 방어와 `LIKE` 와일드카드 이스케이프는 서로 다른 문제다.

## 현재 검색 방식

```text
제목·카테고리·참여자·공유자
→ 원본 검색어로 includes()

전사문·요약 본문
→ 원본은 보존
→ SQL에 전달할 때만 `\%`, `\_`로 이스케이프
```

## 검증과 한계

실제 `20260805_20260805` 형태의 회의 제목과 HANA `LIKE ... ESCAPE` 동작을 확인했다. 다만 현재 테스트 모음에 이 검색만을 직접 고정한 전용 회귀 테스트는 보이지 않는다.
