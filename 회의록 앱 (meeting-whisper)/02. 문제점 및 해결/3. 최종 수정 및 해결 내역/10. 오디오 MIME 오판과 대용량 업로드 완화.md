# 10. 오디오 MIME 오판과 대용량 업로드 완화

> MIME 오판: **해결·`main` 반영 완료**  
> 64kbps: **파일 크기 완화책·`main` 반영**  
> request body drain: **문서에는 수정 기록이 있으나 현재 `main`에는 없음**

## 1. `.bin` 오디오의 MIME 오판

브라우저 직접 녹음은 전사되었지만 WebM 파일을 다시 첨부하면 AI Core가 다음으로 거부할 수 있었다.

```text
mimeType application/octet-stream is not supported
```

Worker가 CAP/Object Store에서 오디오를 받을 때 MIME이 `application/octet-stream`이거나 없으면 형식을 확정할 수 없어 임시 파일 확장자를 `.bin`으로 선택한다.

```text
실제 내용
→ WebM

Worker가 받은 MIME
→ octet-stream/없음

임시 파일
→ tmp12345.bin
```

오디오를 `.bin` 형식으로 변환한 것이 아니라 실제 WebM 바이트에 알 수 없는 확장자만 붙은 상태다. MIME이 어느 구간에서 최초로 유실됐는지는 완전히 특정하지 못했다.

## MIME 해결: 파일 헤더 검사

현재는 두 단계로 방어한다.

```text
1. main.py
.bin 임시 파일의 첫 32바이트 검사
→ 형식을 알면 .webm/.wav/.mp4/.mp3로 확장자 보정

2. aicore_stt.py
전송 직전에도 확장자로 MIME을 모르면 헤더 재검사
→ AI Core에 audio/webm 등으로 전달
```

현재 파악하는 매직 넘버는 WebM, WAV, MP4/M4A, MP3이다.

## 2. 대용량 로컬 업로드 중단

짧은 파일은 성공하지만 약 1MB 부근의 파일부터 `502 ECONNABORTED/ECONNRESET`이 난 사례가 있었다. 처음에는 CAP media body limit로 의심했지만 후속 조사에서 핵심 원인은 로컬 인증 응답과 전송 중인 큰 body의 충돌로 판단했다.

```text
로컬 Approuter가 인증 없이 업로드 전달
→ CAP에서 user = anonymous
→ binary route가 302/401 응답을 먼저 반환
→ 큰 오디오 request body는 아직 전송 중
→ CAP가 body를 끝까지 소비하지 않고 연결 종료
→ Approuter pipe에서 ECONNABORTED/502
```

작은 파일은 응답 전에 body 전송이 빨리 끝나 성공할 수 있어 약 1MB 제한처럼 보였다.

## 64kbps 설정의 의미

```js
new MediaRecorder(stream, {
  mimeType,
  audioBitsPerSecond: 64000
});
```

브라우저 직접 녹음을 초당 약 64,000비트로 인코딩해 파일 크기를 줄인다.

```text
이론상 1분 약 480KB
이론상 2분 약 960KB
```

이것은 업로드 부담을 줄이는 완화책이지 request body 중단의 근본 원인을 제거한 것은 아니다. 사용자가 기존 대용량 파일을 첨부하는 경우에는 64kbps 설정이 적용되지 않는다.

## `body_parser.limit = 20mb`의 의미

이 설정은 일반 JSON·text body parser에는 영향을 주지만 raw binary 오디오 업로드의 직접적인 해결책은 아니었다. 현재 코드에 남은 보조 설정으로 봐야 한다.

## request body drain의 현재 상태

문서에는 인증 실패 응답 전 `drainReq()`로 body를 끝까지 소비하는 수정이 기록되어 있다. 하지만 현재 통합 `main`의 `binary-upload-route.js`에는 해당 함수가 없다.

대신 로컬 Approuter도 XSUAA를 사용하게 되어 정상 Hybrid 경로에서 대용량 업로드가 CAP에 `anonymous`로 도달할 가능성은 줄었다.

## AI Core 사용량 로그

같은 커밋에서 각 AI Core chunk 호출의 `modelName`, `latencyMs`, `tokenUsage`, `chunkIndex`, `totalChunks`를 기록하는 진단 로그도 추가됐다. 현재 `main`에 남아 있으며 전사 결과를 바꾸지는 않는다.
