# 11. 전체 이메일 기반 accessToken과 밑줄 이메일 보완

> 현재 상태: **해결·`main` 반영 완료**

## 초기 문제

한 사람의 권한 식별자로 전체 이메일·이메일 앞부분·사용자 이름을 함께 저장했다.

```text
juyum@zenconsulting.co.kr
juyum
염정운
```

`juyum@zenconsulting.co.kr`과 `juyum@gmail.co.kr`는 다른 사람이지만 앞부분 `juyum`이 같다. 동명이인 이름도 고유 식별자가 아니다. 회사 내부 XSUAA 환경에서 전체 이메일을 권한 키로 사용하도록 단순화했다.

## 현재 함수 구조

### `normalizeAccessEmail()`

- 소문자로 정규화
- 최대 160자
- 공백·개행이 든 값 제거
- `@`와 도메인이 있는 이메일만 허용
- 이름·이메일 앞부분은 제거

### `normalizeAccessEmails()`

여러 값을 `normalizeAccessEmail()`로 정리하고 `Set`으로 중복을 제거한다.

### `userIdentityEmails()`

XSUAA 환경에 따라 이메일이 다른 필드에 들어올 수 있어 다음을 확인하되 이메일 형식인 값만 남긴다.

```text
user.attr.email
user.attr.user_name
user.id
```

### `buildAccessTokens()`

소유자·참여자·공유자의 전체 이메일을 개행으로 감싸 저장한다.

```text
\njuyum@zenconsulting.co.kr
yina@zenconsulting.co.kr\n
```

개행 경계는 `kim@a.com`이 `kim@a.com.tw`에 부분 일치하는 문제를 막는다.

## 첫 수정의 회귀: `_` 이메일 제거

전체 이메일로 좁히는 첫 커밋 `de1aa07`은 SQL `LIKE` 와일드카드 문제를 막으려고 `%`와 `_`가 든 이메일 자체를 버렸다.

```text
sy_lee@zenconsulting.co.kr
jh_hong@zenconsulting.co.kr
→ 정상 이메일이지만 accessToken에서 제거
→ 해당 사용자가 회의를 보지 못함
```

커밋 기록에 따르면 운영 DB에서 두 사용자가 각각 23건, 22건의 회의 접근을 잃은 사례가 확인됐다.

## 후속 수정: 문자는 보존하고 `LIKE`에서만 이스케이프

```text
이메일 저장
→ sy_lee@... 그대로 보존

SQL LIKE 패턴
→ sy\_lee@...
→ ESCAPE \
```

`meetingAccessWhere()`는 다음을 판단한다.

```text
회의 owner = 현재 사용자 ID
또는
현재 사용자의 전체 이메일이 accessTokens에 정확히 존재
```

공유자와 참여자는 모두 accessTokens에 들어가 읽기 권한을 받지만, 편집 권한은 `participants`와 별도 비교한다.

## 기존 회의록 호환성

기존 accessTokens에 전체 이메일이 함께 저장되어 있다면 현재 코드도 그 전체 이메일을 찾으므로 조회할 수 있다.

```text
기존
juyum@zenconsulting.co.kr
juyum
염정운

현재 조회 키
juyum@zenconsulting.co.kr

→ 전체 이메일이 있으므로 일치
```

다만 첫 수정이 `_` 이메일을 이미 제거해 저장한 DB는 코드만 고쳐서 자동 복원되지 않는다. 문서에는 운영 DB 89건을 새 규칙으로 재계산해 백필한 기록이 있다.
