# 4-2. CAP의 req.user와 MeetingUser 검사

운영 profile은 XSUAA 인증을 사용한다.

```json
"[production]": {
  "auth": "xsuaa",
  "db": "hana"
}
```

CAP Framework가 JWT의 서명과 유효성을 검증하고 사용자 ID, attribute와 scope를 `req.user` 형태로 제공한다. 이 내부 구현은 프로젝트 사용자 코드가 아니라 SAP 라이브러리 경계다.

```text
JWT
→ CAP XSUAA 인증 Adapter
→ req.user
```

`meeting-service.cds`는 서비스 입구에서 역할을 요구한다.

```cds
@path: '/api'
service MeetingService @(requires: 'MeetingUser') {
```

역할이 없으면 업무 Handler 전에 거부된다. 통과하면 `meeting-service.js`가 다음 값을 사용할 수 있다.

```text
req.user.id
req.user.attr
req.user.is("MeetingUser")
req.user.is("MeetingAdmin")
```

로컬 development profile에서는 XSUAA 대신 mocked auth가 `req.user` 자리를 채운다. 인증 공급자는 달라도 서비스 로직은 같은 `req.user` 인터페이스를 읽는다.

```text
운영: XSUAA JWT → req.user
로컬: mocked user → req.user
```

여기까지가 01 문서의 핵심 보안 종착점이다. `req.user`를 실제 DB `WHERE` 조건에 사용하는 과정은 02 문서에서 이어진다.
