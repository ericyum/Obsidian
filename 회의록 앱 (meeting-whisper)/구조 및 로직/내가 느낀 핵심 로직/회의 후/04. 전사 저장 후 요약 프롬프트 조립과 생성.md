# 전사 저장 후 요약 프롬프트 조립과 생성 — 실제 코드 워크스루

## 이 문서의 핵심 답

요약 프롬프트는 단일 문자열 상수 하나가 아니다. 저장된 전사에서 만든 text, 회의 카테고리, 카테고리별 지침, 참석자, 전체/청크 처리 지침, JSON schema가 단계별로 합쳐진다.

```text
Transcripts.content
  → parseTranscriptContent()
  → transcriptToChunks()
  → summaryMessages()
     ├─ 공통 system 지시
     ├─ 회의 category / participants
     ├─ category별 guidance
     ├─ 전체 또는 청크용 phaseInstruction
     └─ transcript text
  → SUMMARY_SCHEMA
  → AI Core template 호출
  → JSON 검증·repair
  → normalizeNote()
  → Summaries.content + Summaries.markdown
```

중요한 한계도 있다. 현재 배포는 summary에 `template` mode를 사용한다. repository에는 `config_ref`와 `user_prompt`, `json_schema` placeholder를 만드는 코드까지는 있지만, **SAP AI Core에 등록된 원격 template 본문은 없다.** 따라서 이 문서에서 로컬 조립 내용을 정확히 보여줄 수는 있지만, 원격 template의 고정 문구까지 합친 “서버 최종 최종 prompt”는 해당 AI Core 설정을 열어보지 않고는 단정할 수 없다.

## 1단계. 전사 저장 성공이 요약 background task를 시작한다

### 1. 이 단계가 하는 일

전사를 DB에 저장한 같은 CAP 프로세스가, HTTP 응답을 오래 붙잡지 않도록 `setImmediate()`로 요약 작업을 시작한다.

### 2. 실제 호출자 코드

`cap/srv/worker-internal-service.js`의 `saveTranscript` handler 끝부분:

```js
await DELETE.from(Transcripts).where({ meeting_ID: meetingId });
await INSERT.into(Transcripts).entries({
  meeting_ID: meetingId,
  language: language || "ko",
  content,
});
await UPDATE(Meetings, meetingId).set({
  status: STATUS.SUMMARIZING,
  percent: 80,
  error: null,
});
await updateWorkerHeartbeat(meetingId, workerRunId, {
  stage: "summary_queued",
  message: "Transcript saved; summary queued",
  percent: 80,
});
startWorkerSummaryTask(meetingId, workerRunId, content, meeting);
return SELECT.one.from(Meetings).where({ ID: meetingId });
```

### 3. 전달되는 값과 상태

- `meetingId`, `workerRunId`
- `content`: 저장한 transcript JSON 문자열
- `meeting`: `createdAt`, `owner`, `category`, `participants`, `durationSec` 등
- `Meetings.status = summarizing`, `percent = 80`

### 4. 실제 피호출자 코드

```js
function startWorkerSummaryTask(meetingId, workerRunId, transcriptContent, meeting) {
  setImmediate(async () => {
    const summaryStartedAt = Date.now();
    try {
      await updateWorkerHeartbeat(meetingId, workerRunId, {
        stage: "summarizing",
        message: "Generating summary",
        percent: 80,
      });
      const transcript = parseTranscriptContent(transcriptContent);
      const note = normalizeNote(await summarizeMeeting({
        transcript,
        category: meeting.category || "",
        participants: parseParticipantNames(meeting.participants),
        usageLog: {
          serviceName: "WorkerInternalService",
          actionName: "saveTranscript",
          meetingId,
          requestedBy: meeting.owner,
        },
      }));
```

### 5. 경계

DB에 저장된 것과 같은 JSON 문자열 → CAP Node 메모리의 transcript object → 비동기 요약 task 경계다. 별도의 Python Worker가 요약하는 것이 아니라 CAP 서비스 프로세스가 AI Core를 호출한다.

### 6. 반환을 받는 코드

`summarizeMeeting()` 결과가 `normalizeNote()`를 한 번 더 거쳐 `note`에 들어온다.

### 7. 다음 단계

`summarizeMeeting()`이 transcript를 요약 입력 chunks로 바꾼다.

## 2단계. transcript segments를 화자 표기가 있는 text chunks로 바꾼다

### 1. 이 단계가 하는 일

저장 JSON을 정규 transcript로 읽고, segment마다 `SPEAKER: text` 줄을 만든 뒤 글자 수 기준으로 자른다.

### 2. 실제 호출자 코드

`cap/srv/lib/ai-core.js`:

```js
async function summarizeMeeting({ transcript, participants = [], category = "", usageLog }) {
  const fallback = fallbackSummary(transcript);
  if (!hasLlmConfig()) return fallback;

  const chunks = transcriptToChunks(transcript, summaryChunkChars());
```

### 3. 전달되는 값과 상태

배포 설정의 `CAP_LLM_SUMMARY_CHUNK_CHARS: 12000`이 기본 청크 상한으로 사용된다. 토큰 수가 아니라 JavaScript 문자열 글자 수 기준이다.

### 4. 실제 피호출자 코드

`cap/srv/lib/meeting-note.js`:

```js
function transcriptToChunks(transcript, maxChars = 12000) {
  const limit = Math.max(500, Number(maxChars) || 12000);
  const chunks = [];
  let current = "";

  for (const line of transcriptLines(transcript)) {
    const parts = splitLongLine(line, limit);
    for (const part of parts) {
      const candidate = current ? `${current}\n${part}` : part;
      if (current && candidate.length > limit) {
        chunks.push(current);
        current = part;
      } else {
        current = candidate;
      }
    }
  }
  if (current) chunks.push(current);
  return chunks.length ? chunks : [""];
}

function transcriptLines(transcript) {
  const lines = [];
  for (const segment of transcript?.segments || []) {
    const speaker = segment.speaker || "UNKNOWN";
    const text = String(segment.text || "").trim();
    if (!text) continue;
    lines.push(`${speaker}: ${text}`);
  }
  return lines;
}
```

### 5. 경계

구조화된 transcript JSON → LLM 입력용 plain text 경계다. timestamp와 `words`는 요약 입력에 포함되지 않고, `speaker`와 `text`만 사용된다.

### 6. 반환을 받는 코드

`chunks.length === 1`이면 전체 요약 한 번, 둘 이상이면 각 청크의 부분 요약 후 reduce로 간다.

### 7. 다음 단계

각 chunk에 대해 `summaryMessages()`가 로컬 system/user message를 조립한다.

## 4단계. repository 안에서 확인 가능한 요약 message를 완성한다

### 1. 이 단계가 하는 일

환각 금지·JSON only 규칙을 system message로 만들고, 실제 회의별 정보와 전사를 user message로 만든다.

### 2. 실제 호출자 코드

```js
const messages = summaryMessages({ text, participants, category, phase, index, total });
```

### 3. 전달되는 값과 상태

- `phase = full`: 전사 전체 한 번 처리
- `phase = chunk`: 여러 조각 중 현재 조각 처리
- `index`, `total`: 청크 순서

### 4. 실제 피호출자 코드

```js
function summaryMessages({ text, participants, category, phase, index, total }) {
  const categoryText = String(category || "").trim();
  const guidance = categorySummaryGuidance(categoryText);
  const phaseInstruction = phase === "chunk"
    ? `전체 전사문 중 ${index + 1}/${total} 구간입니다. 이 구간의 결정 후보, 핵심 이슈, 중요한 변경 사항, 명확한 후속 조치를 우선해 중간 요약하세요. 반복 발언과 배경 설명은 압축하세요.`
    : "아래 전사문 전체를 처음부터 끝까지 검토하되, 결정, 핵심 이슈, 중요한 변경 사항, 명확한 후속 조치만 선별해 간결한 최종 회의록을 작성하세요.";
  return [
    {
      role: "system",
      content:
        "Create a concise Korean meeting note from the transcript. " +
        "Use only facts explicitly present in the transcript. " +
        "Do not invent decisions, owners, tasks, due dates, numbers, or dates. " +
        "If a decision or action item is not explicit, return an empty array for that field. " +
        "For action item due dates, use null unless the transcript states a clear due date. " +
        "Return JSON only.",
    },
    {
      role: "user",
      content:
        `[회의 정보]\n` +
        `카테고리: ${categoryText || "미지정"}\n` +
        `참석자: ${participants.join(", ") || "(미상)"}\n\n` +
        `[카테고리별 작성 지침]\n${guidance}\n\n` +
        `[요약 범위]\n${phaseInstruction}\n\n` +
        `[전사문]\n${text}`,
    },
  ];
}
```

## 5단계. 출력 JSON schema와 재시도·repair가 적용된다

### 1. 이 단계가 하는 일

요약 결과가 항상 `summary`, `decisions`, `action_items`, `topics` shape를 갖게 한다.

### 2. 실제 호출자 코드

```js
const content = await chatJson({
  schemaName: phase === "chunk" ? "meeting_note_chunk" : "meeting_note",
  schema: SUMMARY_SCHEMA,
  messages: attempt === 1 ? messages : retryMessages(messages),
  usageLog: {
    ...usageLog,
    actionName: phase === "chunk" ? "summarizeMeeting:chunk" : "summarizeMeeting",
    question: phase === "chunk"
      ? `Summarize meeting transcript chunk ${index + 1}/${total}.`
      : "Summarize meeting transcript.",
    attempt,
  },
  orchestrationPurpose: "summary",
});
return normalizeNote(content);
```

### 3. 전달되는 값과 상태

`SUMMARY_SCHEMA`의 핵심 제한:

- `summary`: 최대 600자
- `decisions`: 최대 5개, 항목 최대 240자
- `action_items`: 최대 8개, `{ owner, task, due }`
- `topics`: 최대 8개, topic별 points 최대 3개
- 추가 속성 금지, 네 최상위 필드 모두 필수

실제 schema 시작부:

```js
const SUMMARY_SCHEMA = {
  type: "object",
  additionalProperties: false,
  properties: {
    summary: { type: "string", maxLength: 600 },
    decisions: {
      type: "array",
      maxItems: 5,
      items: { type: "string", maxLength: 240 },
    },
    action_items: {
      type: "array",
      maxItems: 8,
      items: {
        type: "object",
        additionalProperties: false,
        properties: {
          owner: { type: "string", maxLength: 100 },
          task: { type: "string", maxLength: 240 },
          due: { type: ["string", "null"], maxLength: 80 },
        },
        required: ["owner", "task", "due"],
      },
    },
```

### 4. 실제 피호출자 코드

```js
async function chatJson({ messages, schemaName, schema, usageLog, orchestrationPurpose }) {
  const content = await chatJsonRaw({ messages, schemaName, schema, usageLog, orchestrationPurpose });
  try {
    return parseAndValidateChatJsonContent(content, schemaName, schema);
  } catch (error) {
    console.warn(`LLM response for ${schemaName} needs repair: ${error.message}`);
    const repaired = await repairChatJsonContent({
      content,
      error,
      schemaName,
      schema,
      usageLog,
      orchestrationPurpose,
    });
    try {
      return parseAndValidateChatJsonContent(repaired, schemaName, schema);
    } catch (repairError) {
      throw new Error(`LLM repair for ${schemaName} failed: ${repairError.message}`);
    }
  }
}
```

### 5. 경계

LLM text → JSON parse → application schema 검증 경계다. 첫 응답이 malformed/schema-invalid이면 별도 repair prompt로 한 번 고친다. 그래도 실패하면 상위 `summarizeText()`가 전체 시도 횟수 범위에서 다시 요청한다.

### 6. 반환을 받는 코드

검증된 object만 `normalizeNote()`를 거쳐 `summarizeText()`의 결과가 된다.

### 7. 다음 단계

현재 배포의 template mode에서 이 messages와 schema가 어떤 placeholder로 바뀌는지 본다.

## 6단계. 현재 배포에서는 AI Core 등록 template을 참조한다

### 1. 이 단계가 하는 일

직접 prompt template 전체를 request에 넣는 대신, AI Core에 등록된 summary template의 이름·scenario·version을 참조하고 값만 채운다.

### 2. 실제 호출자 코드

`cap/srv/lib/ai-core.js`:

```js
function aicoreCompletionBody({ messages, schemaName, schema, model, orchestrationPurpose }) {
  if (aicoreCompletionMode(orchestrationPurpose) === "template") {
    return {
      config_ref: aicoreConfigRef(orchestrationPurpose),
      placeholder_values: aicorePlaceholderValues({
        messages,
        schemaName,
        schema,
        model,
        orchestrationPurpose,
      }),
      messages_history: [],
```

### 3. 전달되는 값과 상태

### 4. 실제 피호출자 코드

```js
function aicorePlaceholderValues({ messages, schemaName, schema, model, orchestrationPurpose }) {
  const systemPrompt = messages
    .filter((message) => message.role === "system")
    .map((message) => String(message.content || ""))
    .join("\n\n");
  const userPrompt = messages
    .filter((message) => message.role === "user")
    .map((message) => String(message.content || ""))
    .join("\n\n");
  const jsonSchema = JSON.stringify(schema);
  const combinedPrompt = [
    systemPrompt ? `Instructions:\n${systemPrompt}` : "",
    userPrompt ? `Meeting transcript request:\n${userPrompt}` : "",
    `Return only a JSON object named ${schemaName} matching this JSON schema:\n${jsonSchema}`,
  ].filter(Boolean).join("\n\n");
  const values = {
    system_prompt: systemPrompt,
    user_prompt: userPrompt,
    combined_prompt: combinedPrompt,
    messages_json: JSON.stringify(messages),
    response_format_json: JSON.stringify({
      type: "json_schema",
      json_schema: { name: schemaName, schema, strict: true },
    }),
    json_schema: jsonSchema,
    model,
    extra_json: "{}",
  };
  const allowlist = clean(
    orchestrationPurposeEnv(orchestrationPurpose, "TEMPLATE_PLACEHOLDERS") ||
    process.env.CAP_AICORE_TEMPLATE_PLACEHOLDERS ||
    process.env.AICORE_TEMPLATE_PLACEHOLDERS,
  );
  if (!allowlist || allowlist === "*") return values;
  const allowed = new Set(allowlist.split(",").map((item) => item.trim()).filter(Boolean));
  return Object.fromEntries(Object.entries(values).filter(([key]) => allowed.has(key)));
}
```

### 5. 경계

CAP 코드 → AI Core 원격 registered template 경계다. 현재 allowlist 때문에 실제 request의 placeholder에는 `user_prompt`와 `json_schema`만 남는다.

이 점이 매우 중요하다.

- repository의 `summaryMessages()`는 system message도 계산한다.
- 하지만 현재 template mode allowlist는 `system_prompt`를 보내지 않는다.
- 따라서 system 규칙과 모델 선택의 최종 적용 방식은 원격 template 정의에 달려 있다.
- repository만 보고 원격 template 고정 본문을 만들어내어 적으면 추측이 된다.

### 6. 반환을 받는 코드

AI Core 응답 content가 5단계의 `chatJson()`으로 돌아와 JSON/schema 검증을 받는다.

### 7. 다음 단계

전사가 길면 부분 요약들을 reduce prompt로 다시 합치고, 최종 note를 DB에 쓴다.

## 7단계. 긴 전사는 map-reduce하고 최종 note를 저장한다

### 1. 이 단계가 하는 일

12,000자보다 긴 전사는 chunk별 부분 요약을 만들고, 부분 요약 JSON들을 16,000자 그룹으로 묶어 최종 note 하나가 될 때까지 반복 병합한다.

### 2. 실제 호출자 코드

```js
const partials = [];
for (let index = 0; index < chunks.length; index += 1) {
  partials.push(await summarizeText({
    text: chunks[index],
    participants,
    category,
    usageLog,
    phase: "chunk",
    index,
    total: chunks.length,
  }));
}
return await reducePartialSummaries(partials, { participants, category, usageLog });
```

### 3. 전달되는 값과 상태

reduce 입력은 원문 transcript가 아니라 이미 `normalizeNote()` 된 부분 요약 JSON들이다.

### 4. 실제 피호출자 코드

```js
async function reducePartialSummaries(partials, context) {
  let current = partials.map(normalizeNote);
  let round = 1;
  while (current.length > 1) {
    const groups = groupPartialSummaries(current, summaryReduceChars());
    const next = [];
    for (let index = 0; index < groups.length; index += 1) {
      next.push(await summarizePartialGroup(groups[index], {
        ...context,
        round,
        index,
        total: groups.length,
      }));
    }
    current = next;
    round += 1;
  }
  return current[0] || normalizeNote({});
}
```

reduce system prompt는 실제로 다음을 요구한다.

```js
content:
  "Combine ordered partial Korean meeting notes into one concise final meeting note. " +
  "Review every part, but keep only final decisions, blocking issues or risks, important changes, and explicit follow-up actions. " +
  "Remove background detail and duplication across summary, decisions, action items, and topics. " +
  "Do not invent content, and return JSON only.",
```

최종 결과를 받은 `startWorkerSummaryTask()`의 저장 코드:

```js
if (!hasUsefulNote(note)) throw new Error("summary response was empty");
await DELETE.from(Summaries).where({ meeting_ID: meetingId });
await INSERT.into(Summaries).entries({
  meeting_ID: meetingId,
  content: JSON.stringify(note),
  markdown: noteToMarkdown(note),
});
const finishedAt = Date.now();
const metrics = {
  status: STATUS.DONE,
  percent: 100,
  error: null,
  summarySec: elapsedSecondsFromMs(summaryStartedAt, finishedAt),
};
await UPDATE(Meetings, meetingId).set(metrics);
await updateWorkerHeartbeat(meetingId, workerRunId, {
  stage: "done",
  message: "Transcript and summary saved",
  percent: 100,
});
```

### 5. 경계

여러 AI Core 결과 → 하나의 note object → DB `Summaries.content` JSON과 `Summaries.markdown` 경계다.

### 6. 반환을 받는 코드

UI의 polling은 `Meetings.status = done`, `percent = 100`을 보고 전사와 요약을 다시 조회해 결과 화면을 채운다.

요약이 실패해도 현재 코드는 전사를 살리기 위해 `Meetings.status`를 `done`, `percent`를 100으로 두고 `error`에 정리된 오류를 기록한다. 성공·실패와 무관하게 `finally`에서 업로드 오디오를 삭제한다.

### 7. 다음 단계

사용자가 결과 화면에서 “검토 후보 생성”을 누르면, 전사가 아니라 저장된 요약 note만 별도의 review prompt에 넣는다.

## 최종 prompt를 어디까지 알 수 있는가

| 부분 | repository에서 확인 가능? | 위치 |
|---|---|---|
| transcript를 `UNKNOWN: text`로 만드는 규칙 | 가능 | `meeting-note.js` |
| 카테고리별 한국어 지침 | 가능 | `CATEGORY_SUMMARY_GUIDANCE` |
| 전체/청크용 지시 | 가능 | `summaryMessages()` |
| 로컬 system message | 가능 | `summaryMessages()` |
| JSON schema | 가능 | `SUMMARY_SCHEMA` |
| template에 보내는 placeholder | 가능 | `aicorePlaceholderValues()` |
| AI Core 등록 template의 고정 본문 | **불가능** | repository 외부 AI Core 설정 |
| template이 실제 선택하는 모델·추가 정책 | **repository만으로 확정 불가** | 원격 template 설정 |

## 다시 기억할 핵심

> 요약용 회의별 입력은 전사 text + 참석자 + 카테고리별 지침 + 전체/청크 지침으로 코드에서 조립되고, schema와 함께 AI Core 등록 template에 전달된다. 긴 전사는 부분 요약 후 재귀적인 reduce를 거친다. 다만 현재 배포는 `user_prompt,json_schema`만 원격 template에 넘기므로, 원격 template 본문까지 포함한 최종 지시 전체는 repository만 보고는 알 수 없다.
