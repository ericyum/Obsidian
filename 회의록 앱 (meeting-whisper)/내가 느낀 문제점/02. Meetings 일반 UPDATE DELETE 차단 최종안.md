# 02. Meetings 일반 UPDATE DELETE 차단 최종안

## 최종 결론

CAP 표준 `CREATE`, `READ`는 유지한다. 표준 `UPDATE`, `DELETE` 외부 요청은 명시적으로 거부한다.

회의 수정과 삭제는 이미 존재하는 커스텀 Action만 공식 쓰기 경로로 사용한다.

```text
CREATE Meetings
→ 유지

READ Meetings
→ 유지

UPDATE Meetings
→ 외부 요청 거부

DELETE Meetings
→ 외부 요청 거부
```

## 공식 쓰기 Action

```text
updateMeetingTitle
updateMeetingCategory
updateMeetingAccess
deleteMeeting
```

프론트의 `api.js`도 CAP 모드에서 이미 위 Action들을 사용한다.

## 커스텀 Action을 유지하는 이유

### 수정 종류마다 권한이 다르다

```text
제목·카테고리·전사·요약 편집
→ owner·participant·MeetingAdmin

참여자·공유자 관리
→ owner 중심

삭제
→ 회의 생성자 owner만
```

일반 UPDATE 하나로 열어두면 변경 필드별 권한을 계속 별도로 판정해야 한다. Action은 허용 입력과 권한을 명시적으로 표현한다.

### 접근 목록 수정에는 파생값 갱신이 필요하다

`updateMeetingAccess`는 participants와 sharedWith를 저장하는 것만이 아니라 다음 작업을 함께 수행한다.

```text
입력 정규화
→ 역할 중복 제거
→ participants·sharedWith 직렬화
→ accessTokens 전체 이메일로 재생성
→ 함께 UPDATE
```

### 삭제는 한 행 삭제가 아니다

`deleteMeeting`은 다음 자원을 정리한다.

```text
ReviewItems
Summaries
Transcripts
TranscriptionDispatches
Object Store 또는 DB 음성
Meetings
```

특히 외부 Object Store 삭제는 일반 `DELETE Meetings(ID)`만으로 처리할 수 없다.

## 현재 남아 있는 문제

`MeetingService`의 `Meetings` projection은 CAP 표준 OData 쓰기 경로도 제공한다. 현재 `before UPDATE`, `before DELETE`는 owner 조건을 추가할 뿐 요청을 거부하지 않는다.

```text
PATCH /api/Meetings(ID)
→ owner라면 실행 가능

DELETE /api/Meetings(ID)
→ owner라면 실행 가능
```

따라서 Action과 일반 CRUD라는 두 경로가 동시에 존재한다.

```text
Action 삭제
→ 하위 데이터와 음성 정리

일반 DELETE
→ Action의 전체 정리 로직을 거치지 않음
```

```text
Action 제목 수정
→ participant 편집 정책 적용

일반 UPDATE
→ owner 조건 정책 적용
```

## 확정 변경 계획

### 일반 UPDATE 거부

외부 OData UPDATE가 들어오면 `405 Method Not Allowed` 등으로 명시적으로 거부한다.

개념적인 형태는 다음과 같다.

```javascript
this.before("UPDATE", "Meetings", (req) => {
  return req.reject(405, "Use meeting update actions");
});
```

### 일반 DELETE 거부

```javascript
this.before("DELETE", "Meetings", (req) => {
  return req.reject(405, "Use deleteMeeting action");
});
```

### 기존 일반 UPDATE·DELETE hook 정리

일반 쓰기를 막으면 다음 hook의 외부 요청용 역할은 사라진다.

```text
일반 UPDATE에 owner WHERE 추가
일반 DELETE에 owner WHERE 추가
일반 UPDATE에서 accessTokens 재생성
```

접근 목록의 파생값 갱신은 `updateMeetingAccess` 안에서 계속 수행한다.

## 중요한 구현 주의점

Action handler 안에서는 내부 DB CQN으로 `UPDATE(Meetings...)`, `DELETE.from(Meetings)...`를 실행한다. 외부 일반 CRUD를 막는 handler가 이러한 내부 작업까지 막아서는 안 된다.

구현 전에 현재 CAP 런타임에서 다음을 확인한다.

```text
외부 PATCH /api/Meetings(ID)
→ 거부 handler 실행

updateMeetingTitle Action 내부 UPDATE
→ 정상 실행

deleteMeeting Action 내부 DELETE
→ 정상 실행
```

필요하면 서비스 projection의 외부 이벤트와 DB entity에 대한 내부 CQN을 명확히 구분한다.

## 최종 API 정책

| 업무 | 공식 경로 |
|---|---|
| 새 회의 생성 | 표준 `CREATE Meetings` |
| 회의 목록·기본 데이터 조회 | 표준 `READ Meetings` |
| 제목 수정 | `updateMeetingTitle` |
| 카테고리 수정 | `updateMeetingCategory` |
| 참여자·공유자 수정 | `updateMeetingAccess` |
| 회의 삭제 | `deleteMeeting` |

## 삭제 안정성 추가 검토

DB DELETE는 CAP transaction으로 묶을 수 있지만 Object Store 삭제는 DB transaction과 완전히 같은 방식으로 rollback할 수 없다.

```text
DB 일부 삭제 성공
→ Object Store 삭제 실패

또는

Object Store 삭제 성공
→ 마지막 DB 삭제 실패
```

이번 핵심 변경은 일반 DELETE 차단이다. 구현할 때 삭제 작업이 재호출되어도 안전한지, 실패 로그와 정리 재시도 수단이 있는지도 함께 검증한다.

## 검증 시나리오

### 표준 CRUD

```text
POST /api/Meetings
→ 성공

GET /api/Meetings
→ 사용자별 필터 적용 후 성공

PATCH /api/Meetings(ID)
→ 405 거부

DELETE /api/Meetings(ID)
→ 405 거부
```

### Action

```text
participant의 updateMeetingTitle
→ 성공

sharedWith의 updateMeetingTitle
→ 403

owner의 updateMeetingAccess
→ 성공과 accessTokens 재생성

participant의 updateMeetingAccess
→ 403

owner의 deleteMeeting
→ 모든 관련 자원 정리 후 성공

participant·sharedWith의 deleteMeeting
→ 403
```

### 정리 확인

삭제 성공 후 다음 데이터가 남지 않았는지 확인한다.

```text
Meetings
Transcripts
Summaries
ReviewItems
TranscriptionDispatches
AudioObjects 또는 Object Store object
```

## 완료 조건

- 외부 일반 UPDATE·DELETE가 항상 거부된다.
- CREATE·READ는 기존대로 작동한다.
- 모든 UI 수정·삭제가 커스텀 Action을 사용한다.
- Action별 역할 권한이 유지된다.
- `updateMeetingAccess`가 전체 이메일 accessTokens를 재생성한다.
- `deleteMeeting`이 관련 DB 데이터와 음성을 모두 정리한다.
