# 02. accessTokens 전체 이메일 기반 개편 최종안

> 수정 전 재현 결과: [[해결 과정/01. Before — accessTokens 전체 이메일 식별 테스트]]

## 최종 결론

DB 구조는 변경하지 않는다.

현재 `Meetings.accessTokens : LargeString`, `participants : LargeString`, `sharedWith : LargeString` 구조와 줄바꿈 구분 검색 방식은 유지한다. 대신 권한 신원으로 사용하는 값만 **XSUAA에서 확인한 전체 이메일**로 제한한다.

```text
현재
전체 이메일 + 이메일 앞부분 + 이름 + 표시 이름 + 이름 조합

개선
정규화한 전체 이메일만
```

## 이 정책을 선택한 전제

- 회사 내부 B2E 애플리케이션이다.
- 앱에 들어오려면 SAP 계정 인증과 BTP Role Collection이 필요하다.
- CAP는 XSUAA가 서명한 JWT에서 현재 사용자의 정보를 받는다.
- 회의 소유자가 아직 앱 권한을 받지 않은 사람의 이메일을 미리 등록할 수 있다.
- 나중에 그 사람이 BTP 역할을 받고 다시 로그인하면 JWT의 전체 이메일과 기존 `accessTokens`가 일치하여 접근할 수 있어야 한다.
- 이메일 오타는 초대하는 사용자의 책임으로 보고 별도 디렉터리 검증은 이번 범위에서 제외한다.

## 현재 구조에서 제거할 위험

현재 `expandAccessTokens()`는 다음처럼 전체 이메일에서 로컬 파트를 추가한다.

```text
kim@company.com
→ kim@company.com
→ kim
```

또한 현재 사용자 신원에는 이름과 표시 이름도 포함된다.

```text
김철수
display_name
given_name + family_name
```

이 방식은 다른 도메인의 같은 이메일 앞부분이나 동명이인을 같은 신원으로 판단할 수 있다.

```text
kim@company.com
kim@another-company.com
→ 둘 다 kim 생성

서로 다른 두 김철수
→ 같은 이름 토큰 생성
```

전체 이메일만 사용하면 이 확장 충돌을 제거할 수 있다.

## 변경하지 않는 DB와 조회 형식

다음 스키마는 유지한다.

```cds
participants : LargeString;
sharedWith   : LargeString;
accessTokens : LargeString;
```

저장 예시는 다음과 같다.

```text
participants
→ ["kim@company.com","lee@company.com"]

sharedWith
→ ["park@company.com"]

accessTokens
→ "\nkim@company.com\nlee@company.com\npark@company.com\n"
```

목록 조회의 줄바꿈 경계 검색도 유지한다.

```text
accessTokens LIKE "%\n현재사용자이메일\n%"
```

## 함수 단순화 계획

### normalizeAccessToken → normalizeAccessEmail

값 하나를 전체 이메일로 정규화한다.

```text
문자열 변환
→ 앞뒤 공백 제거
→ 소문자 변환
→ 줄바꿈과 LIKE 특수문자 제거
→ 전체 이메일 형식 확인
→ 유효한 전체 이메일 또는 빈 값 반환
```

저장 쪽과 비교 쪽에서 반드시 같은 함수를 사용한다.

```text
" Kim@Company.COM "
→ "kim@company.com"
```

### expandAccessTokens → normalizeAccessEmails

이메일 앞부분을 생성하는 확장 기능은 제거한다.

```text
여러 값 순회
→ normalizeAccessEmail()
→ 이메일이 아닌 값 제외
→ Set으로 중복 제거
→ 전체 이메일 배열 반환
```

`expand`라는 동작을 하지 않으므로 가능하면 함수 이름도 실제 역할에 맞게 바꾼다.

### userIdentityTokens → userIdentityEmails

현재 로그인 사용자의 신원 후보를 넓게 만드는 대신, XSUAA 사용자 정보에서 정상적인 전체 이메일 하나를 얻는다.

```text
1순위 attr.email
→ 전체 이메일이면 사용

fallback attr.user_name 또는 user.id
→ 값이 전체 이메일 형식일 때만 사용

name·display_name·성과 이름 조합
→ 권한 비교에서 제외
```

fallback은 다른 별칭을 권한으로 인정하는 것이 아니라 배포 환경마다 이메일 claim 위치가 다를 가능성에 대응하는 것이다. 최종 반환값은 전체 이메일만 허용한다.

### buildAccessTokens

`participants`, `sharedWith`에서 전체 이메일만 모아 줄바꿈 구분 문자열로 직렬화한다.

```text
participants 전체 이메일
+ sharedWith 전체 이메일
→ normalizeAccessEmails()
→ 중복 제거
→ "\nemail1\nemail2\n" 생성
```

owner는 현재 `Meetings.owner === currentUserId(req)`로 별도 판정하므로 accessTokens에 반드시 중복 저장할 필요는 없다. 기존 호환성을 위해 포함하려면 owner 값도 전체 이메일 형식일 때만 넣는다.

## 권한 판정 경로 변경

`buildAccessTokens()`만 바꾸면 충분하지 않다. 저장과 비교의 모든 경로가 같은 전체 이메일 정책을 사용해야 한다.

### 목록 조회 meetingAccessWhere

```text
현재 로그인 사용자의 전체 이메일
→ accessTokens LIKE "%\nemail\n%"
```

이름과 이메일 앞부분으로 WHERE 조건을 만들지 않는다.

### 상세 읽기 canReadMeeting

```text
MeetingAdmin
또는 owner
또는 accessTokens의 전체 이메일 일치
```

현재 존재하는 participants·sharedWith fallback을 제거하는 것이 가장 단순하다. 기존 데이터 호환 때문에 유지한다면 fallback에서도 전체 이메일만 정확히 비교한다. 이름과 이메일 앞부분을 다시 확장하면 안 된다.

### 편집 canEditMeeting

`accessTokens`에는 participant와 sharedWith가 합쳐져 있어 역할을 구분할 수 없다. 따라서 편집 권한은 기존처럼 `Meetings.participants`를 직접 확인하되 전체 이메일로 정확히 비교한다.

```text
MeetingAdmin 또는 owner
→ 편집 가능

그 외
→ participants의 전체 이메일과 현재 사용자 전체 이메일 비교
→ 일치하면 편집 가능

sharedWith에만 존재
→ 읽기 전용
```

### 삭제와 접근 목록 관리

기존처럼 owner ID 비교를 사용한다. 전체 이메일 전환은 참여자·공유자의 읽기와 편집 권한을 단순화하는 범위다.

## 미리 초대한 사용자의 접근 시나리오

```text
1. 아직 앱 Role Collection이 없는 사용자의 전체 이메일을 participants 또는 sharedWith에 등록
2. accessTokens에 전체 이메일 저장
3. 나중에 관리자가 BTP Role Collection 부여
4. 사용자가 로그아웃 후 다시 로그인하여 새 JWT 발급
5. MeetingUser 역할로 CAP 진입
6. JWT 전체 이메일과 accessTokens 일치
7. participant면 읽기·편집, sharedWith면 읽기 전용
```

`accessTokens`에 이메일이 있다는 것은 회의 단위 권한만 미리 준비한 것이다. `MeetingUser` 역할이 없으면 서비스 자체의 `@(requires: 'MeetingUser')`에서 차단된다.

## 기존 데이터 전환

코드만 변경해도 기존 Meetings 행의 `accessTokens`는 자동으로 바뀌지 않는다.

```text
기존 accessTokens
→ 이름·이메일 앞부분 포함

새 정책
→ 전체 이메일만 허용
```

한 번의 재생성 작업이 필요하다.

```text
모든 Meetings 조회
→ participants·sharedWith 파싱
→ 전체 이메일만 정규화
→ 참여자·공유자 구분과 무관하게 전체 이메일만 추출
→ 중복 이메일만 한 번으로 합쳐 accessTokens 재생성
→ 기존 컬럼 값 UPDATE
```

DB 스키마 migration은 아니며 기존 행의 문자열 값을 새 정책으로 정리하는 데이터 migration이다.

## 구현 대상

주요 대상은 `cap/srv/meeting-service.js`다.

```text
normalizeAccessToken
expandAccessTokens
userIdentityTokens
buildAccessTokens
meetingAccessWhere
canReadMeeting
canEditMeeting
before CREATE Meetings
updateMeetingAccess
```

프론트는 회사 전체 이메일을 입력한다는 안내를 추가할 수 있다. 실제 권한 안전성은 백엔드가 전체 이메일 외 값을 무시하거나 거부함으로써 보장한다.

## 검증 시나리오

### 정상 접근

```text
participants = ["kim@company.com"]
JWT email = "kim@company.com"
→ 목록·상세 조회 가능
→ 편집 가능
→ 삭제 불가
```

```text
sharedWith = ["lee@company.com"]
JWT email = "lee@company.com"
→ 목록·상세 조회 가능
→ 편집 불가
```

### 충돌 차단

```text
accessTokens = kim@company.com
JWT email = kim@another-company.com
→ 접근 불가
```

```text
participants 표시 이름 = 김철수
다른 사용자 display_name = 김철수
→ 이름은 권한 키가 아니므로 접근 불가
```

### 미리 초대

```text
앱 권한 없는 사용자의 이메일을 먼저 등록
→ 이후 MeetingUser 역할 부여
→ 새 JWT로 로그인
→ 기존 회의 접근 성공
```

### 기존 데이터

이관 전후 회의 수, participants, sharedWith, accessTokens를 비교하고 이름·메일 앞부분 토큰이 남아 있지 않은지 확인한다.

## 완료 조건

- `accessTokens`에 전체 이메일 이외의 이름·별칭이 저장되지 않는다.
- 로그인 사용자 권한 비교에 이름과 이메일 앞부분을 사용하지 않는다.
- 목록·상세·편집이 같은 이메일 정규화 규칙을 사용한다.
- participant와 sharedWith의 권한 차이가 유지된다.
- 기존 회의의 accessTokens가 새 정책으로 재생성된다.
- DB 스키마는 변경하지 않는다.
