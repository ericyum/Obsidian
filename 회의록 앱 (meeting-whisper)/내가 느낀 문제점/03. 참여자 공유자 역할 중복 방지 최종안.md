# 03. 참여자 공유자 역할 중복 방지 최종안

## 최종 결론

DB 구조는 변경하지 않는다. 기존 `participants`, `sharedWith` 컬럼과 프론트의 두 배열을 유지한다.

대신 한 사용자가 한 회의에서 participant와 sharedWith에 동시에 들어가지 못하도록 프론트와 백엔드 양쪽에서 강제한다.

```text
participant
→ 읽기 + 편집

sharedWith
→ 읽기 전용

양쪽에 같은 전체 이메일이 있으면
→ participant 우선
→ sharedWith에서 제거
```

## 현재 중복이 가능한 이유

프론트는 두 배열을 독립적으로 관리한다.

```javascript
participants = [];
sharedWith = [];
```

참여자 Picker의 `isSelected()`는 participants만 보고 공유자 Picker는 sharedWith만 본다.

```text
participants에 kim@company.com 존재
→ 공유자 Picker는 sharedWith만 확인
→ 아직 선택하지 않은 후보로 판단
→ sharedWith에도 추가 가능
```

백엔드의 `cleanNameList()`도 각 목록 안의 중복만 제거하고 두 컬럼 사이의 교집합은 제거하지 않는다.

## 확정 역할 정책

한 사용자는 하나의 최고 역할만 가진다.

```text
owner
> participant
> sharedWith(viewer)
```

participant는 이미 읽기 권한을 포함하므로 같은 사용자를 sharedWith에도 넣을 실익이 없다.

## 프론트엔드 변경 계획

### 비교 기준

1번 개선안의 `normalizeAccessEmail()`과 동일한 규칙으로 전체 이메일을 비교한다.

```text
" Kim@Company.COM "
"kim@company.com"
→ 같은 사용자로 판단
```

### 공유자를 참여자로 선택

역할 승격으로 처리한다.

```text
현재
participants = []
sharedWith = ["kim@company.com"]

참여자 Picker에서 kim@company.com 선택
→ sharedWith에서 제거
→ participants에 추가
→ 참여자·공유자 칩 모두 다시 렌더링
→ 후보 목록 갱신
```

UI에는 다음 의미를 보여줄 수 있다.

```text
kim@company.com
공유자에서 참여자로 변경
```

### 참여자를 공유자로 추가

일반 공유자 추가에서는 차단한다.

```text
participants에 이미 존재
→ 공유자 Picker에서 비활성화 또는 후보 제외
→ “이미 참여자” 표시
```

참여자를 읽기 전용 공유자로 낮추는 기능이 필요하다면 일반 추가가 아니라 별도의 역할 변경 동작과 확인 대화상자를 사용한다.

```text
참여자에서 공유자로 변경할까요?
→ 편집 권한이 사라집니다.
```

이번 기본 정책은 실수로 권한이 낮아지는 것을 막기 위해 공유자 Picker에서 차단하는 것이다.

### 기존 drag 이동

현재 한 목록에서 다른 목록으로 drag할 때 원본 배열에서 제거하고 대상 배열에 넣는 흐름은 상호 배타적 역할 정책과 맞는다. Picker 추가와 drag 이동이 같은 결과를 만들도록 공통 역할 이동 함수를 사용하는 것이 좋다.

## 백엔드 변경 계획

프론트 검사만으로는 직접 API 요청을 막을 수 없으므로 CREATE와 `updateMeetingAccess`에서 같은 정책을 다시 적용한다.

### 공통 접근 목록 정규화

개념적인 공통 함수는 다음 책임을 가진다.

```text
participants JSON 파싱
→ 전체 이메일 정규화·중복 제거
→ participantEmailSet 생성

sharedWith JSON 파싱
→ 전체 이메일 정규화·중복 제거
→ participantEmailSet에 있는 이메일 제거

정리된 두 배열 반환
```

```javascript
function normalizeMeetingAccess({ participants, sharedWith }) {
  const normalizedParticipants = normalizeAccessEmails(
    parseJsonArray(participants)
  );
  const participantSet = new Set(normalizedParticipants);
  const normalizedSharedWith = normalizeAccessEmails(
    parseJsonArray(sharedWith)
  ).filter((email) => !participantSet.has(email));

  return {
    participants: normalizedParticipants,
    sharedWith: normalizedSharedWith,
  };
}
```

실제 구현에서는 기존 함수 입출력과 JSON 직렬화 위치에 맞춰 조정한다.

### before CREATE Meetings

```text
새 회의 participants·sharedWith 수신
→ normalizeMeetingAccess()
→ participant 우선 중복 제거
→ 두 컬럼 직렬화
→ 전체 이메일 accessTokens 생성
```

### updateMeetingAccess

```text
변경 목록 수신
→ owner 권한 확인
→ normalizeMeetingAccess()
→ participant 우선 중복 제거
→ participants·sharedWith·accessTokens 함께 UPDATE
```

## 직접 API 요청 예시

입력:

```json
{
  "participants": ["kim@company.com"],
  "sharedWith": ["kim@company.com", "lee@company.com"]
}
```

백엔드 최종 저장:

```json
{
  "participants": ["kim@company.com"],
  "sharedWith": ["lee@company.com"]
}
```

`accessTokens`에는 두 사용자의 전체 이메일이 한 번씩 들어간다.

```text
\nkim@company.com\nlee@company.com\n
```

## 기존 데이터 정리

1번 accessTokens 데이터 migration을 수행할 때 역할 중복도 함께 정리한다.

```text
기존 Meetings 조회
→ participants 전체 이메일 정규화
→ sharedWith에서 participant 이메일 제거
→ 두 컬럼 다시 직렬화
→ accessTokens 전체 이메일로 재생성
```

DB 스키마는 바꾸지 않고 기존 문자열 값만 정리한다.

## 검증 시나리오

### 프론트

```text
공유자 kim을 참여자로 추가
→ 공유자 칩 제거
→ 참여자 칩 생성
→ 두 배열에 동시에 존재하지 않음
```

```text
참여자 kim을 공유자로 추가 시도
→ 선택 차단
→ 참여자 상태 유지
```

```text
drag로 역할 이동
→ 원본 목록에서 제거
→ 대상 목록에 한 번만 존재
```

### 백엔드

```text
CREATE 요청에서 양쪽에 같은 이메일 전달
→ participant만 유지
```

```text
updateMeetingAccess 직접 요청에서 중복 전달
→ participant만 유지
```

```text
대소문자와 공백이 다른 같은 이메일 전달
→ 정규화 후 같은 사용자로 판단
```

### 권한

```text
participant
→ 읽기와 편집 가능

sharedWith
→ 읽기 가능, 편집 불가

역할 이동 후
→ 새 역할 권한이 즉시 반영
```

## 완료 조건

- 한 전체 이메일이 participants와 sharedWith에 동시에 저장되지 않는다.
- 중복 입력 시 participant가 우선한다.
- Picker, drag, CREATE, updateMeetingAccess가 같은 역할 정책을 사용한다.
- 정리된 두 목록으로 accessTokens가 재생성된다.
- 기존 중복 데이터도 migration에서 정리된다.
- DB 스키마는 변경하지 않는다.
