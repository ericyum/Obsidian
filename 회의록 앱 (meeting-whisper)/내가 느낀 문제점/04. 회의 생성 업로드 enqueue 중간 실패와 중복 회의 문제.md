# 회의 생성 업로드 enqueue 중간 실패와 중복 회의 문제

> 수정 전 재현 결과: [[해결 과정/03. Before — 업로드 실패 후 재시도 중복 회의 테스트]]
>
> 현재 결정: **수정하지 않음 · 적용 보류**
>
> 수정 실험과 revert 기록: [[해결 과정/07. 검토 기록 — 업로드 재시도 수정 실험과 미적용 결정]]

## 최종 판단

업로드 또는 enqueue 실패 후 재시도하면 새 회의가 만들어지는 현상 자체는 실제로 재현했다. 그러나 현재 제품에는 이 수정안을 적용하지 않는다.

배포 환경의 음원은 Object Store에 저장되고, 전사와 요약 처리가 끝나면 기존 정리 로직의 대상이 된다. 재시도로 동일 음원이 일시적으로 두 번 올라가더라도 처리가 완료된 뒤 정리되므로, 현재 운영 조건에서는 저장 파일이 영구히 누적되는 문제로 보지 않는다.

반면 `pendingUpload`, `createJob()`, 음원 업로드와 enqueue의 단계 관리 방식을 바꾸면 기존 제작자가 설계한 핵심 처리 흐름 전체에 영향을 줄 수 있다. 이미 다른 사람이 만든 앱을 유지보수하는 상황에서는 확인된 운영 장애보다 변경에 따른 회귀 위험이 더 크다고 판단했다.

따라서 다음 원칙을 적용한다.

```text
현상 재현 기록은 보존
현재 제품 코드에는 적용하지 않음
실험용 수정 커밋은 revert
운영 책임자의 명시적 요청이 있을 때만 다시 검토
```

## 사용자가 겪는 증상

1. 녹음을 끝내고 업로드한다.
2. 화면에 업로드 실패와 `다시 업로드`가 표시된다.
3. 사용자는 같은 녹음을 다시 업로드한다.
4. 회의 목록에 같은 제목의 회의가 둘 이상 생기거나, 하나는 `created`·`audio_uploaded` 상태에서 멈춘다.

사용자 입장에서는 어느 회의가 정상본인지 알기 어렵고 긴 음원을 다시 전송해야 한다.

## 코드에서 확인한 원인

`app/meeting-ui/js/api.js`의 `createJob()`은 하나의 요청이 아니라 다음 세 단계를 순서대로 수행한다.

```text
Meetings 행 생성
→ 음원 업로드
→ enqueueTranscription 호출
```

첫 단계가 성공한 뒤 둘째 또는 셋째 단계가 실패해도, `app/meeting-ui/js/app.js`의 `pendingUpload`에는 이미 만든 `meetingId`와 완료 단계가 보존되지 않는다.

`retryPendingUpload()`는 기존 회의를 이어서 처리하지 않고 `createJob()` 전체를 다시 호출한다. 따라서 재시도할 때마다 새 `Meetings` 행부터 생성된다.

## 검토했던 수정 방향 — 현재 미적용

재시도 상태에 다음 정보를 보존한다.

```text
meetingId
audioUploaded
enqueued
```

- `meetingId`가 없을 때만 회의를 생성한다.
- 음원 업로드가 끝났다면 같은 음원을 다시 보내지 않는다.
- enqueue만 실패했다면 기존 `meetingId`로 enqueue만 다시 시도한다.

백엔드도 같은 회의에 대한 enqueue가 중복 호출되어도 유효한 대기표가 하나만 남도록 확인하는 방안을 검토했다.

이 내용은 구현 제안의 기록일 뿐이며 현재 코드에는 적용되어 있지 않다.

## 미적용 이유

- Object Store의 음원은 전사·요약 완료 후 기존 정리 흐름을 따른다.
- 일시적인 중복 업로드보다 업로드·enqueue 상태 머신 변경의 회귀 위험이 더 크다.
- 다른 사람이 설계한 핵심 로직을 운영상 필수 근거 없이 변경하지 않는다.
- 현재 사용자 환경에서 반드시 수정해야 하는 치명적 장애로 최종 분류하지 않았다.

향후 실제 운영에서 Object Store 정리가 되지 않거나 중복 회의가 사용자 업무를 막는 사례가 반복적으로 확인되면, 운영 책임자와 처리 정책을 먼저 합의한 뒤 다시 검토한다.

## 수행했던 Before·실험 After 검증

### 업로드 실패

1. 회의 생성 성공 직후 음원 업로드만 한 번 실패시킨다.
2. `다시 업로드`를 누른다.
3. Before에서는 `Meetings`가 두 행으로 늘어나는지 기록한다.
4. After에서는 같은 `meetingId`를 사용하고 최종 회의가 한 건인지 확인한다.

### enqueue 실패

1. 회의와 음원 업로드를 성공시킨 뒤 enqueue만 한 번 실패시킨다.
2. `다시 업로드`를 누른다.
3. After에서는 음원을 다시 보내지 않고 기존 회의의 enqueue만 성공하는지 확인한다.

비교 자료에는 화면, Network 요청 순서, `Meetings`, `AudioObjects`, `TranscriptionDispatches` 건수를 남긴다.

실험에서는 기존 `meetingId`와 업로드 완료 상태를 보존하면 중복 생성을 막을 수 있음을 확인했다. 그러나 검증 성공이 곧 운영 코드 적용을 뜻하지는 않는다. 해당 변경은 `4cb5e39` revert 커밋으로 취소했다.
