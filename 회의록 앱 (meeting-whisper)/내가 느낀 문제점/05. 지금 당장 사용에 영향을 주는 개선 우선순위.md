# 05. 지금 당장 사용에 영향을 주는 개선 우선순위

## 이 문서의 기준

코드에서 발견할 수 있는 모든 위험을 당장 고칠 필요는 없다. 이 문서는 사용자가 현재 앱으로 회의를 녹음하고 회의록을 만드는 과정에서 실제 실패·중복·데이터 손실·잘못된 화면을 경험할 가능성이 있는지를 기준으로 우선순위를 다시 정한다.

```text
회의를 정상적으로 끝까지 처리하지 못하게 하는가?
같은 회의가 중복 생성될 수 있는가?
사용자가 수정한 최신 내용이 과거 내용으로 되돌아갈 수 있는가?
처리 중이라고 표시된 채 영원히 끝나지 않을 수 있는가?
```

위 질문에 해당하면 즉시 대응 대상으로 분류한다.

## 결론

| 순위 | 문제 | 사용자에게 보이는 현상 | 판단 |
|---|---|---|---|
| 1 | 회의 생성·음원 업로드·enqueue 중간 실패 | 다시 시도할 때 같은 회의가 여러 개 생기거나 `created`, `audio_uploaded`로 남음 | 즉시 대응 |
| 2 | `summarizing`, `reviewing` 작업 중 CAP 중단 | 화면이 요약 중·검토 중에서 끝나지 않음 | 즉시 대응 |
| 3 | 요약 작업의 실행 번호 부재 | 전사문을 다시 수정했는데 과거 요약이 늦게 도착해 최신 요약을 덮음 | 즉시 대응 |
| 4 | 자동 저장 요청 순서 역전 | 최신 편집 내용이 과거 내용으로 되돌아가거나 저장 완료로 잘못 표시됨 | 즉시 대응 |
| 5 | polling 요청 중첩과 이전 회의 응답 | 다른 회의로 이동했는데 이전 회의 결과가 현재 화면을 덮음 | 빠른 대응 권장 |
| 6 | 업로드 timeout 부재 | 업로드 중 표시가 끝없이 지속될 수 있음 | 빠른 대응 권장 |

## 기존 1~4번 문서의 실제 긴급도

| 기존 문서 | 긴급도 | 이유 |
|---|---|---|
| `01. accessTokens 전체 이메일 기반 개편` | 계획 유지·배포 전 권장 | 권한 정책상 중요하지만 정상 UI 사용 도중 즉시 오류를 만들 가능성은 상대적으로 낮음 |
| `02. Meetings 일반 UPDATE DELETE 차단` | 보안 강화·배포 전 권장 | 일반 사용자는 커스텀 Action을 이용하므로 정상 UI 흐름의 직접 오류는 아님 |
| `03. 참여자 공유자 역할 중복 방지` | 단기 개선 | 정상 UI에서 역할이 중복되어 혼란과 권한 의미 불일치가 생길 수 있음 |
| `04. 일시정지 음량 분석 loop 중단` | 여유가 있을 때 | CPU·배터리 낭비 문제이며 녹음 데이터 자체가 바로 손상되는 문제는 아님 |

## 이번 즉시 대응 범위에서 제외한 것

권한 서비스의 구조 강화, Worker 내부 엔티티 `readonly`, Object Store 고아 파일 정리, 다중 CAP 인스턴스의 분산 lock, AI 사용 로그 보관 정책은 중요하다. 그러나 현재 사용자가 한 번의 회의를 정상 처리하는 과정에서 즉시 재현될 가능성은 위 세 묶음보다 낮으므로 별도 보류 문서에 둔다.
