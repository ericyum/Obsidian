# 06. 회의 생성 업로드 enqueue 중간 실패와 중복 회의 문제

## 최종 판단

이 문제는 현재 앱 사용 중 직접 발생할 수 있으므로 우선 대응해야 한다.

프론트의 `createJob()`은 이름과 달리 하나의 요청이 아니라 다음 세 작업을 차례로 수행한다.

```text
1. Meetings 행 생성
2. 음원 업로드
3. enqueueTranscription 호출
```

관련 코드:

```text
app/meeting-ui/js/api.js
createJob()

app/meeting-ui/js/app.js
retryPendingUpload()
```

## 현재 실패 시나리오

### 음원 업로드 전에 실패

```text
Meetings A 생성 성공
→ 음원 업로드 실패
→ A는 created로 남음
→ 사용자가 다시 업로드
→ Meetings B를 새로 생성
```

### enqueue에서 실패

```text
Meetings A 생성 성공
→ 음원 업로드 성공
→ enqueueTranscription 실패
→ A는 audio_uploaded로 남음
→ 사용자가 다시 업로드
→ Meetings B를 새로 생성하고 같은 음원을 다시 전송
```

사용자에게는 다음 현상으로 보일 수 있다.

- 같은 제목의 회의가 여러 개 생긴다.
- 어떤 회의는 `created` 또는 `audio_uploaded` 상태에서 진행되지 않는다.
- 긴 음원을 다시 업로드하느라 시간을 낭비한다.
- 실제 전사가 시작된 회의와 사용자가 선택한 회의가 달라 보일 수 있다.

## 원인

재시도 정보인 `pendingUpload`에는 음원과 회의 정보가 있지만 이미 생성한 `meetingId`와 어느 단계까지 성공했는지가 없다.

따라서 재시도는 실패 지점부터 이어가는 것이 아니라 `createJob()` 전체를 처음부터 반복한다.

## 권장 해결 방향

### 업로드 진행 상태를 보존한다

```text
pendingUpload.meetingId
pendingUpload.meetingCreated
pendingUpload.audioUploaded
pendingUpload.enqueued
```

정확한 필드명은 구현 때 조정할 수 있지만 의미는 유지해야 한다.

### 단계별로 재개한다

```text
meetingId 없음
→ Meetings 생성
→ 생성한 meetingId 저장

audioUploaded = false
→ 기존 meetingId에 음원 업로드

enqueued = false
→ 기존 meetingId로 enqueueTranscription만 재시도
```

### fetch에서 XHR로 넘어가는 조건을 좁힌다

현재 `uploadCapAudio()`는 fetch 경로에서 발생한 거의 모든 오류를 XHR 재업로드로 전환한다.

다음은 자동 재업로드 대상에서 제외해야 한다.

```text
400 잘못된 요청
401 세션 만료
403 권한 또는 CSRF 문제
413 파일 크기 초과
서버가 명확한 오류 JSON을 반환한 경우
```

실제 네트워크 전송 계층에서 fetch를 사용할 수 없는 경우에만 XHR fallback을 사용하는 편이 안전하다.

### 업로드 timeout을 실제로 설정한다

`xhr.ontimeout`만 등록하고 `xhr.timeout` 값은 지정하지 않은 상태다. fetch에도 `AbortController`가 없다.

```text
XHR: 충분히 긴 xhr.timeout 설정
fetch: AbortController 기반 timeout
```

긴 음원을 고려하여 짧은 고정값이 아니라 운영 환경에서 조정 가능한 설정으로 두는 것이 좋다.

## 백엔드 보완

프론트만 고치면 일반 사용자 흐름은 좋아지지만 네트워크 단절 시 서버 저장 성공 여부를 브라우저가 확신할 수 없는 상황은 남는다.

따라서 백엔드도 같은 `meetingId`의 음원 재업로드를 안전하게 교체하거나 업로드 요청 ID로 중복을 판단할 수 있어야 한다.

## 검증 시나리오

1. Meetings 생성 직후 음원 업로드를 강제로 실패시킨다.
2. 다시 시도를 누른다.
3. Meetings 행이 하나만 존재하는지 확인한다.
4. 음원 업로드 성공 후 enqueue만 실패시킨다.
5. 다시 시도를 누른다.
6. 음원을 다시 전송하지 않고 같은 회의가 queued가 되는지 확인한다.
7. 400·403·413 응답에서 XHR 재업로드가 발생하지 않는지 확인한다.
8. 네트워크가 응답하지 않을 때 무한 대기가 아니라 timeout 안내가 나타나는지 확인한다.

## 완료 기준

```text
한 번의 사용자 회의
→ Meetings 행 하나
→ AudioObjects 하나
→ 유효한 TranscriptionDispatches 하나
```

중간 실패 후 재시도해도 이 관계가 유지되어야 한다.
