# 07. AI 작업 고착과 오래된 결과 덮어쓰기 문제

## 최종 판단

요약과 검토는 사용자가 회의록 결과를 얻는 핵심 기능이다. 작업 고착과 과거 결과 덮어쓰기는 현재 사용 중 직접 발생할 수 있으므로 우선 대응해야 한다.

## 문제 1. CAP가 중간에 종료되면 상태가 복구되지 않는다

요약과 검토는 다음과 같이 상태를 먼저 변경한 뒤 백그라운드에서 실행한다.

```text
runSummary
→ Meetings.status = summarizing
→ 백그라운드 AI 호출

runReview
→ Meetings.status = reviewing
→ 백그라운드 AI 호출
```

관련 코드:

```text
cap/srv/meeting-service.js
startBackgroundAiTask()
runSummary
runReview

cap/srv/worker-internal-service.js
startWorkerSummaryTask()
```

CAP 프로세스가 작업 도중 종료되면 DB에는 `summarizing` 또는 `reviewing`만 남는다. 현재 `cleanup.js`의 장기 정체 검사는 주로 `queued`, `transcribing`을 대상으로 한다.

이 부분은 팀 동료 문서의 `recoverStaleAiTasks` 개선과 같은 대상이다. 새 로직을 중복 작성하지 말고 팀 개선을 기준으로 통합하는 것이 좋다.

## 문제 2. AI Core HTTP 요청 자체에 명시적인 timeout이 없다

`cap/srv/lib/ai-core.js`의 `fetch()`에는 `AbortController`가 연결되어 있지 않다.

AI Core payload 내부의 모델 timeout과 CAP HTTP 연결이 끝없이 대기하지 않도록 하는 client timeout은 서로 다른 문제다.

권장 구조:

```text
AI Core token 요청 timeout
AI Core completion 요청 timeout
한 요약 작업 전체 시간 상한
timeout 발생 시 오류 기록
cleanup이 상태를 복구
```

## 문제 3. 과거 AI 작업이 최신 결과를 덮을 수 있다

전사 작업에는 `workerRunId`가 있지만 요약·검토에는 현재 실행을 구분하는 번호가 없다.

가능한 시간선:

```text
요약 A 시작: 전사문 버전 1
→ 사용자가 전사문 수정
→ 요약 B 시작: 전사문 버전 2
→ B 완료 및 저장
→ A가 늦게 완료
→ A가 Summaries를 다시 교체
```

최종 화면에는 최신 전사문과 맞지 않는 과거 요약이 나타날 수 있다.

## 원인

백그라운드 작업은 결과 저장 전에 다음을 확인하지 않는다.

```text
현재 회의가 아직 이 작업을 기다리는가?
작업을 시작할 때 사용한 전사문이 아직 최신인가?
더 나중에 시작한 요약 작업이 존재하는가?
```

## 권장 해결 방향

### 요약·검토 실행 ID를 둔다

개념 예시:

```text
aiTaskRunId
summaryRunId
reviewRunId
inputRevision
```

DB 구조 변경 여부는 구현 단계에서 선택할 수 있지만 결과 저장 직전 비교는 반드시 필요하다.

```text
작업 시작
→ 현재 실행 ID 발급 및 기록

AI 결과 도착
→ DB의 현재 실행 ID와 비교

같음
→ 저장

다름
→ 오래된 결과이므로 폐기
```

### 동시에 두 작업이 시작되지 않게 원자적으로 상태를 전환한다

두 요청이 동시에 현재 상태를 읽으면 둘 다 작업을 시작할 수 있다. 단순히 먼저 SELECT하고 나중에 UPDATE하는 것보다 조건부 UPDATE가 안전하다.

```text
현재 status가 실행 가능한 상태일 때만
summarizing 또는 reviewing으로 변경
```

### 전사문 저장 중 기존 요약 작업 처리 정책을 정한다

전사문이 수정되면 이전 전사문을 기반으로 실행 중인 요약은 더 이상 유효하지 않다.

권장 정책:

```text
전사문 수정
→ 기존 요약 실행 ID 무효화
→ 새 전사문 저장
→ 새 요약 작업 시작
```

## 실패했을 때의 상태

AI 요약 실패는 전사문 자체의 실패와 다르다. 전사문은 정상적으로 존재할 수 있기 때문이다.

권장 표현:

```text
Meeting 전체: 전사문 사용 가능
Summary 작업: 실패
사용자: 요약만 다시 시도 가능
```

단일 `Meetings.status`만으로 표현하기 어렵다면 작업 상태를 분리하는 장기 개선도 고려할 수 있다.

## 검증 시나리오

1. 요약 요청을 의도적으로 오래 대기시킨다.
2. 그동안 전사문을 수정하고 새 요약을 요청한다.
3. 과거 작업을 나중에 완료시킨다.
4. 최신 요약이 과거 결과로 바뀌지 않는지 확인한다.
5. 요약 중 CAP를 재시작한다.
6. 제한 시간 후 재시도 가능 상태로 복구되는지 확인한다.
7. reviewing에서도 같은 복구가 동작하는지 확인한다.
8. AI Core가 응답하지 않을 때 client timeout이 발생하는지 확인한다.

## 팀 개선과 합칠 때 주의할 점

팀 동료의 `recoverStaleAiTasks`는 고착된 상태를 사후 복구한다. 이 문서의 실행 ID는 오래된 결과가 나중에 돌아와 복구된 상태를 다시 덮는 것을 사전에 막는다.

```text
recoverStaleAiTasks
→ 멈춘 상태 복구

AI 작업 실행 ID
→ 늦게 도착한 과거 결과 차단
```

두 개선은 중복이 아니라 함께 필요한 관계다.
