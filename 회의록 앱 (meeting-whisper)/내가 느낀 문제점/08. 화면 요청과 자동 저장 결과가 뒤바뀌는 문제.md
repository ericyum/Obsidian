# 08. 화면 요청과 자동 저장 결과가 뒤바뀌는 문제

## 최종 판단

이 문제는 사용자가 회의 상세 화면을 빠르게 이동하거나 전사문·요약을 연속 수정할 때 직접 나타날 수 있다. 특히 최신 편집 내용이 과거 내용으로 되돌아가는 경우 데이터 손실처럼 느껴지므로 빠르게 대응하는 것이 좋다.

## 기본 원인

비동기 요청은 보낸 순서대로 끝난다는 보장이 없다.

```text
요청 A 시작
→ 요청 B 시작
→ B 응답
→ A 응답
```

현재 코드는 여러 경로에서 응답이 최신 요청인지 확인하지 않고 곧바로 전역 상태와 화면에 반영한다.

## 문제 1. polling 요청이 겹칠 수 있다

`app/meeting-ui/js/app.js`의 `poll()`은 비동기 `tick()`을 `setInterval`로 2초마다 실행한다.

```text
tick A가 2초 이상 걸림
→ A가 끝나기 전에 tick B 시작
→ 응답 순서가 뒤바뀔 수 있음
```

또 `stopPolling()`은 다음 interval을 중단하지만 이미 진행 중인 fetch까지 취소하지는 않는다.

가능한 현상:

```text
회의 A 조회 중
→ 사용자가 회의 B로 이동
→ B 화면 표시
→ 늦게 도착한 A 응답이 paintResult 실행
→ 현재 화면이 A 내용으로 바뀜
```

## polling 권장 구조

```text
현재 요청 완료
→ 아직 같은 meetingId를 보고 있는지 확인
→ 결과 반영
→ 2초 후 다음 요청
```

필요한 안전장치:

- `pollGeneration` 또는 요청 번호
- 요청을 시작할 때의 `meetingId` 보존
- 결과 반영 전 현재 `currentJob`과 비교
- 화면 이동 시 `AbortController.abort()`
- `setInterval` 대신 요청 완료 후 `setTimeout`

## 문제 2. 요약 자동 저장 응답이 뒤바뀔 수 있다

요약 편집은 900ms debounce 후 `saveNoteInline()`을 실행한다.

debounce는 요청 시작 횟수를 줄일 뿐 이미 시작한 요청의 순서를 보장하지 않는다.

```text
내용 A 저장 시작
→ 사용자가 내용 B로 수정
→ B 저장 시작
→ B 저장 완료
→ A 저장이 나중에 완료
```

오래된 A 응답이 다음 값을 다시 바꿀 수 있다.

```text
currentNote
currentReviewItems
noteDirty = false
화면의 저장 완료 메시지
```

## 문제 3. 전사문 자동 저장도 같은 구조다

전사문은 250ms debounce 후 `saveTranscriptInline()`을 실행한다. 요약과 같은 응답 역전 위험이 있으며 요약 재생성까지 함께 실행하면 영향이 더 커진다.

## 자동 저장 권장 구조

### 프론트 저장 revision

```text
편집 발생
→ revision 증가

저장 요청
→ 요청에 현재 revision 기록

응답 도착
→ 응답 revision이 최신일 때만 화면 상태 반영
```

### 저장 요청 직렬화

한 요청이 진행 중이면 다음 내용을 별도 pending 상태로 기억한다.

```text
저장 A 진행 중
→ 추가 편집 발생
→ latestPending에 최신 내용 보관
→ A 완료
→ latestPending을 새 요청으로 저장
```

### 서버 낙관적 잠금

프론트 revision만으로 다른 브라우저나 탭의 동시 수정을 막을 수는 없다. 장기적으로 `modifiedAt` 또는 별도 version을 요청에 포함하고 서버가 오래된 버전의 저장을 거부하는 방법이 안전하다.

## 녹음 청크 메타데이터도 같은 유형

`onChunk`에서 여러 IndexedDB 저장이 동시에 진행될 수 있다. 늦게 끝난 과거 청크 저장이 `currentDraft` 전체를 과거 스냅샷으로 교체할 가능성이 있다.

이 부분은 실제 Blob을 잃는 문제라기보다 `chunkCount`, `durationSeconds`, `lastChunkAt`이 뒤로 가는 문제다.

권장 방식:

```text
저장 시작 때 만든 draft 전체로 교체하지 않음
→ 저장 완료 시 현재 currentDraft와 병합
→ chunkCount와 duration은 Math.max 사용
```

## 검증 시나리오

1. polling 응답 A를 지연시킨 뒤 회의 B로 이동한다.
2. A 응답이 늦게 와도 B 화면이 유지되는지 확인한다.
3. 저장 요청 A를 지연시키고 더 최신 내용 B를 저장한다.
4. A를 나중에 완료시킨다.
5. 화면과 DB 모두 B를 유지하는지 확인한다.
6. 저장 중 추가 편집이 발생하면 `dirty` 상태가 잘못 해제되지 않는지 확인한다.
7. 녹음 청크 저장 완료 순서를 인위적으로 뒤집어도 `chunkCount`가 감소하지 않는지 확인한다.

## 구현 우선순위

```text
1. 요약·전사 저장 revision
2. polling meetingId/generation 확인
3. 진행 중 요청 AbortController
4. 청크 메타데이터 병합
5. 서버 낙관적 잠금
```

1~2번은 현재 사용자 데이터와 화면 정확성에 직접 영향을 주므로 먼저 적용하는 편이 좋다.
