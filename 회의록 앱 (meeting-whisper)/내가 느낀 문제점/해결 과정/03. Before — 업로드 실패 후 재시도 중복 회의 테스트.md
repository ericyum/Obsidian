# Before — 업로드 실패 후 재시도 중복 회의 테스트

> 문서 상태: **현상 확인용 기록 · 현재 수정하지 않음**
>
> 업로드 재시도 수정은 실험 후 revert했으며 현재 제품에는 적용되어 있지 않다. 결정 근거는 [[../06. 회의 생성 업로드 enqueue 중간 실패와 중복 회의 문제]]와 [[07. 검토 기록 — 업로드 재시도 수정 실험과 미적용 결정]]을 참고한다.

## 테스트 목적

회의 행 생성 후 음원 업로드가 실패하고 사용자가 화면의 `다시 업로드`를 누르면, 기존 회의를 이어서 처리하는지 새 회의를 생성하는지 실제 Chrome에서 확인한다.

연결된 개선안: [[../06. 회의 생성 업로드 enqueue 중간 실패와 중복 회의 문제]]

## 테스트 환경

- 코드: `C:\Users\염정운\project\meeting-whisper-yina`
- Chrome: 실제 마이크 녹음 및 UI 조작
- CAP: 포트 4005, SQLite in-memory
- Worker: 포트 8010, `WORKER_MOCK_TRANSCRIPT=true`
- Network 기록 프록시: 포트 4004
- 프록시 코드: `tests/support/before-test-proxy.js`
- 테스트 일시: 2026-08-06

프록시는 첫 두 번의 바이너리 업로드를 503으로 반환했다. 두 번인 이유는 프론트가 fetch 실패 후 XHR fallback을 한 번 더 수행하기 때문이다.

## Chrome 실행 순서

```text
새 회의록
→ 제목: Before 업로드 실패 재시도
→ 실제 마이크 녹음
→ 종료
→ 저장하지 않고 계속
→ 업로드 실패 화면 확인
→ 다시 업로드 클릭
→ 전사와 결과 화면 확인
```

## 실패 직후 화면과 Console

화면:

```text
Before test injected upload failure
[다시 업로드]
```

Chrome Console:

```text
warn
fetch upload failed, retrying with XHR: Before test injected upload failure
```

## Network 근거

최초 시도:

```text
POST /api/Meetings                                      201
POST /api-binary/Meetings/edcdc53a-.../audio            503 injected upload
GET  /api/Meetings?$top=1                               200
POST /api-binary/Meetings/edcdc53a-.../audio            503 injected upload
```

재시도:

```text
POST /api/Meetings                                      201
POST /api-binary/Meetings/139912c2-.../audio            200
POST /api/enqueueTranscription                          200
POST /api/getMeetingStatus                              200
```

재시도 시 기존 ID가 아니라 새 ID로 `POST /api/Meetings`부터 다시 실행된 것이 핵심이다.

## DB 근거

실패 직후:

```text
회의 수: 1
edcdc53a-e40d-4c33-9830-e0db428fa2d3
status = created
```

재시도 완료 후:

```text
회의 수: 2

139912c2-ed65-4464-bb75-e657ea65ac19
status = done

edcdc53a-e40d-4c33-9830-e0db428fa2d3
status = created
```

## CAP·Worker 근거

- 새 회의 ID로 음원 업로드와 `enqueueTranscription`이 수행됐다.
- Worker는 새 회의에 대해 `/transcribe` 202를 반환했다.
- 기존 회의는 `created`에서 복구되지 않았다.

## Before 결론

**실제 Chrome에서 재현 성공.** 사용자가 정상적으로 `다시 업로드`를 누르면 같은 제목의 회의가 두 건 생기고 최초 회의는 `created`에 남는다.

## 추가 테스트 — enqueue만 실패하는 경우

업로드 경로 자체의 문제와 재시도 설계 문제를 구분하기 위해 다음 조건으로 다시 실행했다.

```text
Meetings 생성 성공
→ /api-binary 음원 업로드 200 성공
→ enqueueTranscription만 503 실패
→ 사용자가 다시 업로드 클릭
```

실패 직후 Network와 DB:

```text
POST /api/Meetings                                           201
POST /api-binary/Meetings/f7c7a4ea-.../audio                 200
POST /api/enqueueTranscription                               503 injected enqueue

회의 수: 1
f7c7a4ea-de94-48c4-80e4-524eb92a7eab
status = audio_uploaded
```

재시도 후:

```text
POST /api/Meetings                                           201
POST /api-binary/Meetings/61fa0c55-.../audio                 200
POST /api/enqueueTranscription                               200

회의 수: 2
61fa0c55-dd99-4940-8610-24e143ba1e1c  status = done
f7c7a4ea-de94-48c4-80e4-524eb92a7eab  status = audio_uploaded
```

**enqueue 단독 실패도 실제 Chrome에서 재현 성공했다.** 최초 음원 업로드가 정상 성공했는데도 재시도는 기존 회의의 enqueue만 이어서 실행하지 않고 새 회의 생성과 음원 업로드부터 반복했다.

## After 테스트 기준

동일한 503 조건에서 다음을 만족해야 한다.

```text
POST /api/Meetings는 한 번만 호출
재시도는 최초 meetingId 사용
최종 Meetings 행은 한 건
최초 회의가 queued → transcribing → done으로 진행
enqueue만 실패했다면 음원은 다시 업로드하지 않음
```

## 2026-08-07 현재 코드 재검증

원격 `main` 정상화와 `feature/juyum` 동기화 이후에도 동일한 문제가 남아 있는지 다시 검증했다.

```text
코드: C:\Users\염정운\project\meeting-whisper-yina
브랜치: feature/juyum
커밋: de1aa07
CAP: 4005, SQLite in-memory
실패 주입 프록시: 4004
브라우저: 실제 app/meeting-ui 화면
```

첫 번째 테스트에서는 현재 경로인 `/api/binary/Meetings/:meetingId/audio`의 첫 두 요청을 503으로 만들었다. 두 번 실패시킨 이유는 fetch 실패 후 XHR fallback이 한 번 더 실행되기 때문이다.

재시도 전:

```text
d23d04ac-d0f3-47a8-b99e-af3931de6b38
status = created
회의 수 = 1
```

재시도 후:

```text
d23d04ac-d0f3-47a8-b99e-af3931de6b38  created
fb7416a6-d2af-4a9b-b3c6-e4b889552a83  queued
회의 수 = 2
```

Network에는 `POST /api/Meetings`가 두 번 기록됐고 두 번째 회의 ID로 업로드와 enqueue가 진행됐다.

두 번째 테스트에서는 음원 업로드는 정상 처리하고 enqueue만 한 번 503으로 만들었다.

재시도 전:

```text
76400df9-f9fc-464e-86aa-68ab6c2d4cfa
status = audio_uploaded
회의 수 = 1
```

재시도 후:

```text
76400df9-f9fc-464e-86aa-68ab6c2d4cfa  audio_uploaded
43e94a8b-ee45-4754-bc9b-db3ce2f14463  queued
회의 수 = 2
```

Network에는 다음 순서가 확인됐다.

```text
POST /api/Meetings                                           201
POST /api/binary/Meetings/76400df9-.../audio                 200
POST /api/enqueueTranscription                               503

POST /api/Meetings                                           201
POST /api/binary/Meetings/43e94a8b-.../audio                 200
POST /api/enqueueTranscription                               200
```

따라서 이 문제는 과거 `/api-binary` 경로 오류를 잘못 해석한 것이 아니다. 현재 `/api/binary` 경로가 정상적으로 동작하는 상태에서도 재현됐다. 직접 원인은 `retryPendingUpload()`가 성공한 단계를 기억하지 않고 `createJob()` 전체를 다시 호출하는 것이다.

**현재 코드 재검증에서도 현상은 확인됐다. 다만 재현됐다는 사실만으로 수정 대상으로 확정하지 않는다.**

배포 환경에서는 Object Store 음원이 전사·요약 완료 후 정리된다. 중복 파일이 일시적으로 생길 수 있지만 이를 막기 위해 기존 제작자의 회의 생성·업로드·enqueue 흐름을 변경하는 것은 회귀 위험이 있다.

따라서 이 문서는 Before 근거로만 보존하며, 현재 제품에는 수정안을 적용하지 않는다. 실험용 변경은 revert했다.
