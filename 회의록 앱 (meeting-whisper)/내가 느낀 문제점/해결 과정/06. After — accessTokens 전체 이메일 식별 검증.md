## 수정 내용

기존에는 하나의 이메일에서 전체 이메일과 이메일 앞부분을 함께 만들었다.

```text
alice@another-company.example
→ alice@another-company.example
→ alice
```

수정 후에는 유효한 전체 이메일만 권한 식별값으로 사용한다.

```text
alice@another-company.example
→ alice@another-company.example
```

로그인 사용자의 `name`, `display_name`, 성과 이름의 조합도 권한 비교에서 제외했다. XSUAA 사용자 정보의 `email`, `user_name`, `user.id` 중 전체 이메일 형식으로 확인되는 값만 사용한다.

DB 구조와 줄바꿈 경계 형식은 변경하지 않았다.

```text
Meetings.accessTokens : LargeString

저장 형식
\nemail1@company.com\nemail2@company.com\n
```

## Before와 동일한 충돌 시나리오

관리자 계정으로 다음 참여자를 가진 회의를 생성했다.

```text
참여자 전체 이메일: alice@another-company.example
조회 사용자 ID: alice
```

두 값은 전체 이메일 기준으로 같은 사용자가 아니다.

## 기존 회의록 호환성

기존 회의의 `accessTokens`에 다음처럼 전체 이메일이 이미 함께 저장되어 있다.

```text
juyum@zenconsulting.co.kr
juyum
염정운
```

수정 후에는 이 중 `juyum@zenconsulting.co.kr`만 비교에 사용한다. 전체 이메일 값 자체를 삭제하거나 저장 형식을 변경한 것이 아니므로, 해당 전체 이메일로 로그인한 사용자는 기존 회의록을 계속 조회할 수 있다.

다음 권한도 기존 방식이 유지된다.

```text
회의 소유자
→ Meetings.owner와 현재 사용자 ID 비교

MeetingAdmin
→ 전체 회의 접근 권한 유지
```

단, 과거 데이터에 이름이나 이메일 앞부분만 있고 전체 이메일이 전혀 없는 회의는 이번 호환 조건에 포함되지 않는다. 현재 확인한 데이터는 전체 이메일을 함께 가지고 있으므로 별도 DB 마이그레이션은 진행하지 않았다.

## 변경 범위 확인

최종 애플리케이션 변경 파일은 다음 하나다.

```text
cap/srv/meeting-service.js
```

별도의 access token 모듈이나 DB 스키마는 추가하지 않았다. OAuth 또는 XSUAA에서 발급하는 Bearer access token을 변경한 것도 아니다. 이번 수정 대상은 `Meetings.accessTokens`에 저장하는 회의별 접근 식별 문자열이다.

## After 결론

**검증 성공.** 같은 이메일 앞부분을 가진 다른 계정이 전체 이메일 불일치 상태에서 회의를 조회하던 문제가 차단됐다.

```text
Before: alice@another-company.example → alice도 생성 → alice 조회 가능
After : alice@another-company.example만 저장 → alice 조회 불가
```

기존 회의에 저장된 전체 이메일은 그대로 비교에 사용되므로, 전체 이메일이 이미 들어 있는 기존 회의록의 접근 권한은 유지된다.
