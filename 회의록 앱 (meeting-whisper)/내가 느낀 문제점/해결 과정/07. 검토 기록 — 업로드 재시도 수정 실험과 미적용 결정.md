# 검토 기록 — 업로드 재시도 수정 실험과 미적용 결정

## 현재 상태

> **현재 제품에는 적용하지 않았다.**

업로드 실패 후 기존 회의에서 단계를 재개하는 코드를 실험하고 테스트했지만, 최종적으로 해당 커밋을 revert했다. 현재 `feature/juyum`은 기존 업로드·재시도 로직을 유지한다.

```text
af4d6f1
→ juyum: 업로드 실패 후 재시도 시 중복으로 업로드하는 문제 수정

4cb5e39
→ Revert "juyum: 업로드 실패 후 재시도 시 중복으로 업로드하는 문제 수정"
```

## 확인한 현상

기존 `createJob()`은 다음 세 단계를 순서대로 실행한다.

```text
회의 생성
→ 음원 업로드
→ 전사 enqueue
```

음원 업로드 또는 enqueue가 실패한 뒤 사용자가 `다시 업로드`를 누르면 새 회의를 만들어 처음부터 실행하는 현상을 실제 UI에서 확인했다.

### 음원 업로드 실패

```text
Before
→ 최종 Meetings 2건

실험 수정
→ 최초 meetingId 유지
→ 최종 Meetings 1건
```

### enqueue 실패

```text
Before
→ 기존 회의 audio_uploaded
→ 재시도에서 새 회의와 음원 생성

실험 수정
→ 회의 생성과 음원 업로드를 건너뜀
→ enqueue만 재시도
```

실험 수정 자체는 기대한 대로 동작했으며 JavaScript 테스트 30건도 통과했다.

## 수정 실험에서 사용한 방법

`pendingUpload`에 다음 상태를 보존했다.

```text
meetingId
audioUploaded
```

그리고 재시도할 때 이미 성공한 단계를 건너뛰도록 `createJob()`의 흐름을 변경했다.

이 내용은 기술적으로 가능함을 확인한 실험 기록이며 현재 적용 코드에 대한 설명이 아니다.

## 적용하지 않은 이유

### 1. 배포 환경의 Object Store 정리 흐름

배포 환경에서는 음원이 Object Store에 올라간다. 전사와 요약 처리가 끝나면 해당 음원은 기존 정리 로직의 대상이 된다.

따라서 재시도로 동일 음원이 일시적으로 두 번 올라가더라도 정상 처리 완료 후 정리된다. 현재 판단에서는 영구적인 저장 공간 누적으로 보지 않는다.

### 2. 핵심 처리 로직 변경 위험

실험 수정은 다음 핵심 부분을 함께 변경했다.

```text
createJob()
pendingUpload
파일 업로드
브라우저 녹음 업로드
복구 녹음 업로드
enqueue 재시도
```

이미 다른 사람이 만든 앱을 유지보수하는 상황에서 이 흐름을 변경하면 예상하지 못한 회귀가 생길 수 있다. 현재 운영상 반드시 고쳐야 하는 장애로 확정되지 않은 상태에서는 변경 위험이 더 크다.

### 3. 유지보수 원칙

```text
재현 가능하다는 이유만으로 수정하지 않는다.
운영상 치명적인 사용자 장애인지 먼저 판단한다.
기존 제작자의 핵심 로직은 최소한으로 변경한다.
수정 이득보다 회귀 위험이 크면 적용하지 않는다.
```

## 현재 코드에 남아 있는 것

실험에서 변경했던 다음 파일은 revert되어 원격 `main`과 같은 내용으로 돌아갔다.

```text
app/meeting-ui/index.html
app/meeting-ui/js/api.js
app/meeting-ui/js/app.js
```

따라서 다음 실험 상태도 현재 코드에는 없다.

```text
pendingUpload.meetingId
pendingUpload.audioUploaded
20260807-upload-resume 캐시 버전
```

현재 브랜치에서 `origin/main` 대비 남아 있던 실제 변경은 별도의 accessTokens 전체 이메일 식별 수정뿐이었다.

## 향후 다시 검토할 조건

다음과 같은 운영 근거가 확인될 때만 재검토한다.

- Object Store 음원이 전사·요약 완료 후에도 정리되지 않는다.
- 중복 회의가 실제 사용자 업무를 반복적으로 방해한다.
- 동일 음원의 중복 전사·요약 비용이 운영상 문제가 된다.
- 제품 책임자가 기존 회의에서 단계별로 재개하도록 명시적으로 요청한다.

재검토할 때에도 기존 실험 코드를 그대로 다시 적용하지 않고, 당시 최신 코드와 Object Store 정리 정책을 다시 확인한 후 Before·After 테스트를 수행한다.

## 최종 결론

**현상은 확인했지만 현재는 수정하지 않는다.**

```text
테스트 결과
→ 단계 재개 방식으로 중복 생성 방지 가능

운영 판단
→ Object Store 정리 흐름 존재
→ 기존 핵심 로직 변경 위험이 더 큼

최종 상태
→ 실험 커밋 revert
→ 현재 제품 미적용
```
