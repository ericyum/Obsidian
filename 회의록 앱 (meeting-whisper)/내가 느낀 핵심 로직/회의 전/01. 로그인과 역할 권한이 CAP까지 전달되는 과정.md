# 로그인과 역할 권한이 CAP까지 전달되는 과정 — 실제 코드 워크스루

## 이 문서가 따라가는 호출 체인

```text
브라우저 최초 요청
→ Approuter의 xsuaa 인증 route
→ XSUAA 로그인과 세션
→ /user-api/currentUser로 프로필 표시
→ /api 요청을 srv-api destination으로 전달
→ forwardAuthToken으로 JWT 전달
→ CAP production auth가 JWT를 req.user로 복원
→ MeetingService의 MeetingUser 요구 조건 검사
→ meeting-service.js가 req.user.id·attr·role 사용
```

이 문서는 각 단계마다 다음 순서를 지킨다.

1. 이 단계가 하는 일
2. 실제 호출부 코드
3. 전달되는 인자와 상태
4. 실제 피호출부 코드
5. HTTP·인증·메모리 경계
6. 반환값을 받는 코드
7. 다음 단계

---

## 단계 1. 브라우저 요청을 Approuter가 인증한다

### 1) 이 단계가 하는 일

배포 환경에서 사용자는 CAP 포트로 직접 들어가지 않고 Approuter URL을 연다. Approuter는 요청 경로를 `xs-app.json`의 위에서 아래 순서로 검사하고, 해당 route의 `authenticationType`에 따라 XSUAA 인증을 요구한다.

### 2) 실제 호출부 코드

브라우저의 최초 문서 요청은 JavaScript 함수가 아니라 주소창/navigation이 만든 HTTP 요청이다. UI가 로드된 뒤에는 다음 초기화 코드가 실행된다.

`app/meeting-ui/js/app.js` 2965~2972행:

```javascript
// ===== init =====
initSessionMonitor({ keepAlive: keepSessionAlive });
initUserProfile();
const initialRoute = routeFromLocation();
writeRoute(initialRoute, { replace: true });
applyRoute(initialRoute).catch((error) => {
  console.error("initial route failed", error);
  loadList({ replaceHistory: true });
});
```

### 3) 전달되는 인자와 상태

| 값 | 현재 상태 |
|---|---|
| 최초 URL | Approuter가 받은 HTTP 경로 |
| 브라우저 cookie/session | 로그인 전이면 없을 수 있음 |
| `initialRoute` | UI 내부에서 list/detail/new 화면을 결정하는 상태 |

### 4) 실제 피호출부 설정

`approuter/xs-app.json` 1~39행:

```json
{
  "welcomeFile": "/index.html",
  "authenticationMethod": "route",
  "logout": {
    "logoutEndpoint": "/logout",
    "logoutPage": "/index.html"
  },
  "routes": [
    {
      "source": "^/user-api(.*)",
      "target": "$1",
      "service": "sap-approuter-userapi",
      "cacheControl": "no-cache, no-store, must-revalidate"
    },
    {
      "source": "^/api/(.*)$",
      "target": "/api/$1",
      "destination": "srv-api",
      "authenticationType": "xsuaa"
    },
    {
      "source": "^/api-binary/(.*)$",
      "target": "/api-binary/$1",
      "destination": "srv-api",
      "authenticationType": "xsuaa"
    },
    {
      "source": "^/internal/(.*)$",
      "target": "/internal/$1",
      "destination": "srv-api",
      "authenticationType": "xsuaa"
    },
    {
      "source": "^/(.*)$",
      "target": "/$1",
      "localDir": "resources",
      "authenticationType": "xsuaa"
    }
  ]
}
```

### 5) 경계

여기는 **브라우저 → Approuter HTTP 경계**다. `authenticationMethod: route`이므로 route별 설정이 적용된다. 마지막 정적 리소스 route도 `xsuaa`이기 때문에 배포 UI 자체를 받기 전 로그인이 필요하다.

### 6) 반환값을 받는 코드

로그인이 끝나면 Approuter는 원래 URL 처리를 계속한다. 정적 요청이면 `resources`의 `index.html`, JS, CSS가 브라우저로 돌아가고 위의 UI 초기화 코드가 실행된다.

### 7) 다음 단계

로드된 UI의 `initUserProfile()`이 `/user-api/currentUser`를 호출하여 현재 사용자 표시 정보를 얻는다.

## 단계 2. UI가 현재 사용자 프로필을 읽는다

### 1) 이 단계가 하는 일

로그인 완료 여부를 확인하고 화면의 사용자 이름·이메일·아바타를 채운다. 이 응답은 화면 표시용이며 회의 접근 권한의 보안 원본은 아니다.

### 2) 실제 호출부 코드

`app/meeting-ui/js/app.js` 117~135행:

```javascript
async function initUserProfile() {
  const menu = $("user-menu");
  const button = $("user-button");
  const popover = $("user-popover");
  if (!menu || !button || !popover) return;

  try {
    const user = await getCurrentUser();
    const displayName = user.displayName || user.name || [user.firstname, user.lastname].filter(Boolean).join(" ") || user.email || user.userName || "User";
    const email = user.email || user.userName || "";
    $("user-name").textContent = displayName;
    $("user-avatar").textContent = userInitials(displayName, email);
    $("user-popover-name").textContent = displayName;
    $("user-popover-email").textContent = email;
    menu.classList.remove("hidden");
  } catch {
    menu.classList.add("hidden");
    return;
  }
```

### 3) 전달되는 인자와 상태

`getCurrentUser()`에는 명시적 인자가 없다. 현재 브라우저의 same-origin session cookie가 요청에 자동 포함된다.

### 4) 실제 피호출부 코드

`app/meeting-ui/js/api.js` 152~177행:

```javascript
export async function getCurrentUser() {
  let response;
  try {
    response = await fetch("/user-api/currentUser", {
      credentials: "same-origin",
      cache: "no-store",
      headers: {
        accept: "application/json",
        "X-Requested-With": "XMLHttpRequest",
      },
    });
  } catch (err) {
    throw new Error(`current user request failed: ${err.message || "Failed to fetch"}`);
  }
  if (!response.ok) {
    if (response.status === 401) markSessionExpired("current-user", response.status);
    throw new Error(`current user unavailable: ${response.status}`);
  }
  try {
    const parsed = await parseJsonResponse(response);
    markSessionTouched("current-user");
    return parsed;
  } catch (err) {
    if (isSessionHtmlError(err)) markSessionExpired("current-user");
    throw err;
  }
}
```

이 URL은 단계 1에서 본 첫 route와 연결된다.

```json
{
  "source": "^/user-api(.*)",
  "target": "$1",
  "service": "sap-approuter-userapi",
  "cacheControl": "no-cache, no-store, must-revalidate"
}
```

### 5) 경계

**UI JavaScript → Approuter 내장 User API 경계**다. CAP DB나 `meeting-service.js`를 거치지 않는다.

### 6) 반환값을 받는 코드

`initUserProfile()`이 반환 JSON의 `displayName`, `name`, `firstname`, `lastname`, `email`, `userName` 중 사용 가능한 값을 선택해 DOM에 넣는다.

### 7) 다음 단계

회의 목록 등 실제 업무 데이터는 `/api/*`로 호출한다. 이때는 Approuter가 JWT를 CAP destination으로 전달한다.

## 단계 3. Approuter가 사용자 JWT를 CAP에 전달한다

### 1) 이 단계가 하는 일

`/api/*` 요청을 CAP 서비스 URL로 reverse proxy하면서 현재 로그인 사용자의 access token을 함께 전달한다.

### 2) 실제 호출부 코드

모든 CAP JSON 요청은 결국 `requestJson()`의 fetch로 간다.

`app/meeting-ui/js/api.js` 115~130행:

```javascript
async function requestJson(url, options = {}) {
  let prepared = await prepareOptions(options);
  let response;
  try {
    response = await fetch(url, prepared);
  } catch (err) {
    throw new Error(`${url} 요청 실패: ${err.message || "Failed to fetch"}`);
  }
  if (response.status === 403 && needsCsrf(prepared)) {
    prepared = await prepareOptions(options, { refreshCsrf: true });
    try {
      response = await fetch(url, prepared);
    } catch (err) {
      throw new Error(`${url} 재요청 실패: ${err.message || "Failed to fetch"}`);
    }
  }
```

### 3) 전달되는 인자와 상태

- `url`: `/api/Meetings`, `/api/getMeetingStatus` 같은 same-origin URL
- `prepared.credentials`: 기본값 `same-origin`
- 쓰기 요청이면 CSRF token
- Approuter session이 식별한 로그인 사용자

### 4) 실제 피호출부 설정

Approuter route:

```json
{
  "source": "^/api/(.*)$",
  "target": "/api/$1",
  "destination": "srv-api",
  "authenticationType": "xsuaa"
}
```

`mta.yaml` 127~134행:

```yaml
requires:
  - name: meeting-whisper-auth
  - name: srv-api
    group: destinations
    properties:
      name: srv-api
      url: ~{srv-url}
      forwardAuthToken: true
```

### 5) 경계

**Approuter → CAP HTTP 경계**다. `forwardAuthToken: true`가 없으면 CAP가 최종 사용자 JWT 대신 익명 또는 destination 자체 문맥을 보게 될 수 있다.

### 6) 반환값을 받는 코드

CAP 응답은 Approuter를 거쳐 `requestJson()`으로 돌아온다.

`app/meeting-ui/js/api.js` 131~149행:

```javascript
  if (!response.ok) {
    let detail = "";
    if (response.status === 401) markSessionExpired(url, response.status);
    try {
      const body = await parseJsonResponse(response);
      detail = body.detail || body.error?.message || body.message || "";
    } catch (err) {
      detail = err.message || "";
    }
    throw new Error(detail || `Request failed: ${response.status}`);
  }
  try {
    const parsed = await parseJsonResponse(response);
    markSessionTouched(url);
    return parsed;
  } catch (err) {
    if (isSessionHtmlError(err)) markSessionExpired(url);
    throw err;
  }
}
```

### 7) 다음 단계

CAP의 production 인증 adapter가 JWT를 검증해 `req.user`를 만들고, 서비스-level 역할 조건을 검사한다.

## 단계 4. CAP가 `MeetingUser` 역할을 서비스 입구에서 검사한다

### 1) 이 단계가 하는 일

CAP는 운영에서 XSUAA 인증을 사용한다. JWT 검증 후 요청 사용자와 역할은 `req.user`로 노출된다. 사용자용 서비스는 `MeetingUser`가 있어야 진입할 수 있다.

### 2) 실제 호출부 설정

`package.json`의 production profile:

```json
"[production]": {
  "auth": "xsuaa",
  "db": "hana"
}
```

### 3) 전달되는 인자와 상태

Approuter가 전달한 Bearer JWT에는 사용자 ID, 사용자 attribute, XSUAA scope가 있다. CAP framework가 이를 검증해 `req.user`로 변환한다.

### 4) 실제 피호출부 선언

`cap/srv/meeting-service.cds` 1~4행:

```cds
using { meeting.whisper as db } from '../db/schema';

@path: '/api'
service MeetingService @(requires: 'MeetingUser') {
```

`xs-security.json`의 role template:

```json
{
  "name": "MeetingUser",
  "description": "Meeting Whisper user",
  "scope-references": [
    "$XSAPPNAME.MeetingUser"
  ]
},
{
  "name": "MeetingAdmin",
  "description": "Meeting Whisper administrator",
  "scope-references": [
    "$XSAPPNAME.MeetingUser",
    "$XSAPPNAME.MeetingAdmin"
  ]
}
```

### 5) 경계

여기는 **CAP framework 인증 middleware → MeetingService 경계**다. JWT 파싱 구현은 `meeting-whisper` 저장소의 사용자 코드가 아니라 `@sap/cds`와 `@sap/xssec` 라이브러리 내부에 있다. 저장소에서 직접 보여 줄 수 있는 코드 경계는 production auth 설정과 `@(requires: 'MeetingUser')` 선언까지다.

### 6) 반환값을 받는 코드

역할이 없으면 CAP framework가 서비스 handler 전에 401/403을 반환한다. 역할이 있으면 `meeting-service.js`의 hook/action이 `req.user`를 받는다.

### 7) 다음 단계

`meeting-service.js`가 `req.user.id`, `req.user.attr`, `req.user.is()`를 회의별 권한에 사용한다.

## 단계 5. 서비스 코드가 `req.user`를 회의별 권한에 사용한다

### 1) 이 단계가 하는 일

서비스 입구를 통과한 다음에는 사용자의 ID·이메일·표시 이름·관리자 역할을 회의 행 접근 판단에 사용한다.

### 2) 실제 호출부 코드

회의 서비스의 각 hook/action은 CAP가 전달한 `req`를 받는다. 공통 ID helper는 다음과 같다.

`cap/srv/meeting-service.js` 35~37행:

```javascript
function currentUserId(req) {
  return currentUserIdFromUser(req.user);
}
```

### 3) 전달되는 인자와 상태

| 값 | 출처 |
|---|---|
| `req.user.id` | JWT subject/user 식별자 |
| `req.user.attr` | email, name, given/family name 등의 JWT attribute |
| `req.user.is("MeetingAdmin")` | JWT scope를 CAP가 role로 해석한 결과 |

### 4) 실제 피호출부 코드

관리자 판정의 실제 구현은 `audio-store.js`의 helper로 이어진다.

`cap/srv/lib/audio-store.js` 20~26행:

```javascript
function currentUserId(user) {
  return user?.id || user?.attr?.email || user?.attr?.user_name || "anonymous";
}

function canAccessAllMeetings(user) {
  return Boolean(user?.is?.("MeetingAdmin") || user?.is?.("Admin"));
}
```

회의 서비스는 이 helper를 `req.user`에 적용한다.

`cap/srv/meeting-service.js` 196~198행:

```javascript
function canAccessAllMeetings(req) {
  return canAccessAllMeetingsByUser(req.user);
}
```

### 5) 경계

이 단계부터는 인증된 사용자 객체가 단순 로그인 표시가 아니라 **DB 행 접근 조건을 만드는 서버 측 보안 입력**으로 사용된다.

### 6) 반환값을 받는 코드

`currentUserId(req)`의 문자열과 `canAccessAllMeetings(req)`의 Boolean은 `READ Meetings`, 상세 action, 수정/삭제 검사에서 사용된다.

### 7) 다음 단계

구체적인 목록 WHERE 조건과 소유자·참석자·공유자별 차이는 다음 문서인 `02. 회의 목록이 사용자별로 필터링되는 과정.md`에서 실제 코드로 이어진다.

## 단계 6. 로컬 개발에서는 mocked auth가 같은 `req.user` 자리를 채운다

### 1) 이 단계가 하는 일

로컬 CAP 실행에서는 XSUAA 대신 테스트 사용자를 사용하지만 서비스 코드는 여전히 `req.user`를 읽는다.

### 2) 실제 호출부 코드

`package.json`에서 CAP 로컬 실행을 시작하는 script다.

```json
"cap:watch": "cds watch",
"cap:serve": "cds serve all",
```

`cds watch`의 기본 로컬 실행은 development profile의 설정을 읽는다.

### 3) 전달되는 인자와 상태

- 활성 profile: development
- 인증 kind: `mocked`
- mock user의 ID, tenant, roles
- 실제 password 값은 인증 흐름 설명에 필요하지 않아 이 문서에 옮기지 않는다.

### 4) 실제 피호출부 설정에서 권한에 필요한 부분

`package.json` development profile에는 로컬 mock 계정의 password 필드도 있지만, 인증 흐름 설명에 필요하지 않으므로 문서에는 값까지 복사하지 않는다. 아래는 실제 사용자별 tenant와 roles만 옮긴 발췌다.

```json
"[development]": {
  "auth": {
    "kind": "mocked",
    "users": {
      "alice": {
        "roles": [
          "MeetingUser"
        ]
      },
      "mallory": {
        "tenant": "t1",
        "roles": [
          "MeetingUser"
        ]
      },
      "worker": {
        "tenant": "t1",
        "roles": [
          "Worker"
        ]
      },
      "admin": {
        "tenant": "t1",
        "roles": [
          "MeetingUser",
          "MeetingAdmin"
        ]
      }
    }
  }
}
```

표시한 사용자명·tenant·roles는 프로젝트에 공개된 로컬 mock 설정이며 운영 XSUAA 자격 증명이 아니다.

### 5) 경계

개발에서는 CAP mocked-auth middleware가, 운영에서는 XSUAA adapter가 `req.user`를 만든다.

### 6) 반환값을 받는 코드

두 환경 모두 `meeting-service.js`에는 같은 형태의 `req.user`가 전달된다.

### 7) 다음 단계

환경별 인증 방식은 다르지만 이후 회의 목록의 행 필터 함수는 동일하다.

## 최종 연결 요약

```text
Approuter의 xsuaa route
→ XSUAA가 인증
→ forwardAuthToken이 JWT를 CAP에 전달
→ CAP production auth가 req.user 생성
→ MeetingService @(requires: MeetingUser)
→ meeting-service.js가 req.user를 회의별 필터에 사용
```

## 이 문서에서 코드로 직접 보여 줄 수 없는 경계

- XSUAA 로그인 화면 내부 구현
- JWT 서명 검증 알고리즘
- `@sap/cds`가 JWT를 `req.user`로 만드는 라이브러리 내부 코드

이 세 부분은 프로젝트 저장소 바깥의 SAP managed service/framework 구현이다. 문서에서는 그 전후의 실제 프로젝트 설정과 입력·출력 경계를 명시했다.
