# 회의 목록이 사용자별로 필터링되는 과정 — 실제 코드 워크스루

## 이 문서가 따라가는 호출 체인

```text
loadList()
→ listMeetings()
→ readEntityList("Meetings")
→ GET /api/Meetings?$orderby=createdAt+desc
→ CAP before READ Meetings
→ meetingAccessWhere(req)
→ userIdentityTokens(req.user)
→ DB가 필터된 Meetings 반환
→ getMeetingStatus(meetingId)
→ assertReadableMeeting()·canEditMeeting()
→ Transcripts/Summaries/ReviewItems 조회
→ restrictChildReadToAccessibleMeetings()
→ capJobFromMeeting()
→ meetingsCache
→ renderMeetingListView()의 검색·상태·카테고리 필터
```

## 단계 1. 홈 화면이 서버 목록 호출을 시작한다

### 1) 이 단계가 하는 일

목록 화면으로 들어오면 브라우저 초안 배너를 먼저 그린 뒤 CAP의 회의 목록을 요청한다.

### 2) 실제 호출부 코드

## 단계 2. `readEntityList()`가 OData GET을 만든다

### 1) 이 단계가 하는 일

엔터티 이름과 정렬 조건을 URL로 바꾸고 공통 `requestJson()`을 호출한다.

### 2) 실제 호출부 코드

앞 단계의 실제 한 줄이다.

```javascript
const meetings = await readEntityList("Meetings", { orderby: "createdAt desc" });
```

### 3) 전달되는 인자와 상태

| 인자 | 값 |
|---|---|
| `entity` | `Meetings` |
| `filter` | 없음 |
| `orderby` | `createdAt desc` |

UI는 owner 조건을 보내지 않는다. 사용자 필터는 CAP가 추가한다.

### 4) 실제 피호출부 코드

`app/meeting-ui/js/api.js` 307~315행:

```javascript
async function readEntityList(entity, { filter, orderby } = {}) {
  const params = new URLSearchParams();
  if (filter) params.set("$filter", filter);
  if (orderby) params.set("$orderby", orderby);
  const query = params.toString().replace(/\+/g, "%20");
  const suffix = query ? `?${query}` : "";
  const data = await requestJson(`/api/${entity}${suffix}`);
  return data.value || [];
}
```

### 5) 경계

`requestJson()`에서 **브라우저 → Approuter → CAP HTTP GET 경계**를 넘는다. URL은 `/api/Meetings?%24orderby=createdAt%20desc` 형태가 된다.

### 6) 반환값을 받는 코드

CAP OData 응답 `{ value: [...] }`에서 `data.value`를 꺼내 `listMeetings()`의 `meetings`에 반환한다.

### 7) 다음 단계

CAP가 OData `READ Meetings`를 실행하기 직전에 `before READ` hook을 호출한다.

## 단계 3. CAP가 DB 조회문에 사용자 WHERE 조건을 삽입한다

### 1) 이 단계가 하는 일

관리자는 필터 없이 통과시키고, 일반 사용자 요청에는 `owner = 현재 사용자` 또는 `accessTokens에 사용자 식별 토큰 포함` 조건을 추가한다.

### 2) 실제 호출부 코드

`cap/srv/meeting-service.js` 514~517행:

```javascript
this.before("READ", "Meetings", (req) => {
  if (canAccessAllMeetings(req)) return;
  req.query.where(meetingAccessWhere(req));
});
```

### 3) 전달되는 인자와 상태

- `req.user`: JWT 또는 mocked auth가 만든 현재 사용자
- `req.query`: CAP가 OData URL에서 만든 CQN SELECT
- `canAccessAllMeetings(req)`: MeetingAdmin/Admin 여부

### 4) 실제 피호출부 코드

`cap/srv/meeting-service.js` 164~171행:

```javascript
function meetingAccessWhere(req) {
  const clauses = ["(", { ref: ["owner"] }, "=", { val: currentUserId(req) }];
  for (const token of userIdentityTokens(req.user)) {
    clauses.push("or", { ref: ["accessTokens"] }, "like", { val: `%\n${token}\n%` });
  }
  clauses.push(")");
  return clauses;
}
```

### 5) 경계

여기는 **CAP 요청 context → DB CQN 경계**다. 브라우저가 전체 회의를 받은 뒤 숨기는 것이 아니라, SQL로 번역되기 전 query 객체 자체에 조건을 넣는다.

### 6) 반환값을 받는 코드

`meetingAccessWhere()`가 반환한 CQN expression을 `req.query.where(...)`가 현재 SELECT에 결합한다. 이후 CAP/HANA adapter가 SQL을 실행한다.

### 7) 다음 단계

WHERE의 각 token은 `userIdentityTokens(req.user)`가 만든다.

## 단계 4. 현재 사용자의 식별 토큰을 만든다

### 1) 이 단계가 하는 일

로그인 사용자 정보가 email 형식일 수도, 이름 형식일 수도 있으므로 여러 JWT attribute를 동일한 토큰 규칙으로 정규화한다.

### 2) 실제 호출부 코드

앞 단계의 loop가 직접 호출한다.

```javascript
for (const token of userIdentityTokens(req.user)) {
  clauses.push("or", { ref: ["accessTokens"] }, "like", { val: `%\n${token}\n%` });
}
```

### 3) 전달되는 인자와 상태

`req.user` 전체가 전달된다. 함수는 `user.id`와 `user.attr`을 읽는다.

### 4) 실제 피호출부 코드

`cap/srv/meeting-service.js` 65~99행:

```javascript
function userIdentityTokens(user) {
  const attr = user?.attr || {};
  const values = [
    user?.id,
    attr.email,
    attr.user_name,
    attr.name,
    attr.display_name,
    attr.given_name && attr.family_name ? `${attr.given_name} ${attr.family_name}` : null,
    attr.family_name && attr.given_name ? `${attr.family_name}${attr.given_name}` : null,
    attr.family_name && attr.given_name ? `${attr.family_name} ${attr.given_name}` : null,
  ];
  return expandAccessTokens(values);
}

function expandAccessTokens(values) {
  const tokens = new Set();
  for (const value of values || []) {
    const token = normalizeAccessToken(value);
    if (!token) continue;
    tokens.add(token);
    const at = token.indexOf("@");
    if (at > 0) tokens.add(token.slice(0, at));
  }
  return [...tokens];
}

function normalizeAccessToken(value) {
  return String(value || "")
    .trim()
    .toLowerCase()
    .replace(/[\r\n%_]+/g, " ")
    .replace(/\s+/g, " ")
    .slice(0, 160);
}
```

### 5) 경계

메모리 안의 JWT 사용자 객체가 DB 검색용 문자열 token 배열로 바뀐다. 이메일이면 `@` 앞부분도 추가된다.

### 6) 반환값을 받는 코드

토큰 배열의 각 원소가 `%\n토큰\n%` LIKE 조건 하나가 된다.

### 7) 다음 단계

HANA가 owner/accessTokens 조건을 만족하는 Meeting 행만 CAP에 반환한다.

### 4) 실제 피호출부 코드

`cap/srv/meeting-service.js` 154~162행:

```javascript
function buildAccessTokens({ owner, participants, sharedWith }) {
  const values = [
    owner,
    ...cleanNameList(participants),
    ...cleanNameList(sharedWith),
  ];
  const tokens = expandAccessTokens(values);
  return tokens.length ? `\n${tokens.join("\n")}\n` : null;
}
```

### 5) 경계

요청 JSON의 사용자 이름 배열이 HANA `Meetings.accessTokens`에 저장할 줄바꿈 경계 문자열로 바뀐다.

### 6) 반환값을 받는 코드

CAP CREATE가 `req.data.accessTokens`를 포함한 Meeting 행을 DB에 삽입한다. 참석자/공유자 변경 때도 다음 hook이 재계산한다.

```javascript
this.before("UPDATE", "Meetings", async (req) => {
  if (!("participants" in req.data) && !("sharedWith" in req.data) && !("owner" in req.data)) return;
  const id = req.data.ID || req.params?.[0]?.ID;
  if (!id) return;
  const existing = await SELECT.one.from(Meetings).where({ ID: id });

  if ("sharedWith" in req.data) req.data.sharedWith = sharedWith;

});
```

```javascript
function canReadMeeting(req, meeting) {
  if (canAccessAllMeetings(req)) return true;
  if (!meeting) return false;
  if (meeting.owner === currentUserId(req)) return true;
  const tokens = userIdentityTokens(req.user);
  const accessTokens = String(meeting.accessTokens || "");
  if (tokens.some((token) => accessTokens.includes(`\n${token}\n`))) return true;
  const fallbackTokens = expandAccessTokens([
    ...cleanNameList(meeting.participants),
    ...cleanNameList(meeting.sharedWith),
  ]);
  return tokens.some((token) => fallbackTokens.includes(token));
}

function canEditMeeting(req, meeting) {
  if (canAccessAllMeetings(req)) return true;
  if (!meeting) return false;
  if (meeting.owner === currentUserId(req)) return true;
  const tokens = userIdentityTokens(req.user);
  const participantTokens = expandAccessTokens(cleanNameList(meeting.participants));
  return tokens.some((token) => participantTokens.includes(token));
}
```

## 단계 7. 자식 엔터티도 허용된 Meeting ID로 제한한다

### 1) 이 단계가 하는 일

UI가 Transcripts, Summaries, ReviewItems를 직접 조회할 때 CAP가 회의 접근권한을 다시 WHERE로 적용한다.

### 2) 실제 호출부 코드

`app/meeting-ui/js/api.js` 362~369행:

```javascript
async function capJobFromMeeting(meeting) {
  const meetingId = meeting.ID || meeting.id;
  const meetingFilter = `meeting_ID eq ${odataString(meetingId)}`;
  const [transcriptRow, summaryRow, reviewRows] = await Promise.all([
    readFirst("Transcripts", meetingFilter),
    readFirst("Summaries", meetingFilter),
```

### 3) 전달되는 인자와 상태

브라우저가 `meeting_ID eq '...'` 필터를 보내지만, 이 필터만 신뢰하지 않고 CAP가 사용자 접근 조건을 추가한다.

### 4) 실제 피호출부 코드

hook 등록:

```javascript

```

helper 본문:

```javascript
async function accessibleMeetingIds(req) {
  if (canAccessAllMeetings(req)) return null;
  const rows = await SELECT.from(Meetings).columns("ID").where(meetingAccessWhere(req));
  return rows.map((row) => row.ID);
}

async function restrictChildReadToAccessibleMeetings(req) {
  const meetingIds = await accessibleMeetingIds(req);
  if (meetingIds === null) return;
  if (!meetingIds.length) {
    req.query.where({ meeting_ID: null });
    return;
  }
  req.query.where({ meeting_ID: { in: meetingIds } });
}
```

### 5) 경계

**자식 OData 요청 → Meetings 권한 query → 자식 DB query**의 이중 DB 경계다. 자식 ID만 알아도 권한을 우회할 수 없게 한다.

### 4) 실제 피호출부 코드

`app/meeting-ui/js/app.js` 211~235행:

```javascript
function renderMeetingListView() {
  const query = ($("meeting-search")?.value || "").trim().toLowerCase();
  const stage = $("meeting-stage-filter")?.value || "all";
  const category = $("meeting-category-filter")?.value || "all";
  const hasFilters = Boolean(query) || stage !== "all" || category !== "all";
  const filtered = meetingsCache.filter((meeting) => {
    const stageOk =
      stage === "all" ||
      (stage === "active" && !["done", "failed"].includes(meeting.stage)) ||
      meeting.stage === stage;
    const categoryOk = category === "all"
      || (category === "uncategorized" && !meeting.category)
      || meeting.category === category;
    if (!stageOk || !categoryOk) return false;
    if (!query) return true;
    if (!meeting._searchText) meeting._searchText = buildMeetingSearchText(meeting);
    return meeting._searchText.includes(query);
  });
  $("list-body").innerHTML = renderMeetingList(filtered, { filtered: hasFilters });
  updateListCount(filtered.length, hasFilters);
  $("list-body").querySelectorAll(".mtg").forEach((row) => {
    const meeting = filtered.find((item) => item.id === row.dataset.open);
    if (meeting?.can_edit === false) row.querySelector(".mtg-title-edit")?.remove();
    if (meeting?.can_delete !== true) row.querySelector(".mtg-del")?.remove();
  });
}
```

### 5) 경계

여기는 서버 보안 경계가 아니라 **브라우저 메모리 → DOM 표시 경계**다.

### 6) 반환값을 받는 코드

함수는 값을 반환하지 않고 `list-body` DOM과 목록 개수를 갱신한다.

### 7) 다음 단계

사용자가 행을 열거나 편집 버튼을 누르면 해당 CAP action이 `assertReadableMeeting()` 또는 `assertEditableMeeting()`으로 다시 검사한다.

## 최종 권한표

| 관계 | READ | action 기반 수정 | 삭제 |
|---|---:|---:|---:|
| 소유자 | 가능 | 가능 | 가능 |
| 참석자 | 가능 | 가능 | 불가 |
| 공유자 | 가능 | 불가 | 불가 |
| 관계없는 MeetingUser | 목록에서 제외 | 불가 | 불가 |
| MeetingAdmin | 모든 회의 읽기 | 대부분 가능 | `assertDeletableMeeting()` 기준 소유 회의만 가능 |

핵심은 `renderMeetingListView()`가 보안을 만드는 것이 아니라, 그보다 앞선 `before READ Meetings`와 자식 READ hook이 이미 데이터 집합을 제한한다는 점이다.
