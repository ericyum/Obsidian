# 00. 진행 상황과 다음 시작점

## 이 파일의 목적

이 파일은 다른 컴퓨터나 새 대화에서 `02. 회의 목록이 사용자별로 필터링되는 과정` 분석을 이어가기 위한 인수인계 문서다.

## 현재 완료된 범위

```text
1단계 완료: loadList()가 listMeetings()를 호출
2단계 완료: readEntityList()가 /api/Meetings OData GET 생성
3단계 완료: CAP before READ Meetings가 req.query에 사용자 WHERE 추가
4단계 완료: userIdentityTokens(req.user)가 DB 검색용 사용자 Token 생성
5단계 완료: owner·participants·sharedWith에서 accessTokens 생성 및 저장
6단계 완료: getMeetingStatus가 읽기·편집·삭제 권한 재검사
7단계 완료: Transcripts·Summaries·ReviewItems READ에 부모 Meeting 권한 적용
8단계 완료: 허용된 meetingsCache 안에서 검색·필터링·렌더링
```

이 주제의 1~8단계 코드 워크스루는 모두 완료했다.

## 전체 실행 흐름

```text
브라우저 loadList()
→ listMeetings()
→ readEntityList("Meetings")
→ GET /api/Meetings?$orderby=createdAt desc
→ Approuter가 JWT를 CAP로 전달
→ CAP before READ Meetings
→ meetingAccessWhere(req)
→ userIdentityTokens(req.user)
→ owner 또는 accessTokens LIKE 조건을 req.query에 추가
→ HANA가 허용된 Meeting 행만 반환
→ 각 Meeting에 getMeetingStatus 호출
→ assertReadableMeeting으로 읽기 권한 재검사
→ canEdit·canDelete 계산
→ Transcripts·Summaries·ReviewItems 조회
→ 허용된 Meeting ID 조건을 하위 READ에 추가
→ 완성된 UI 객체를 meetingsCache에 저장
→ 검색어·상태·카테고리로 표시 목록 필터링
→ 권한 플래그에 따라 수정·삭제 버튼 정리
→ 회의 클릭 시 getMeetingStatus부터 서버 권한 재검사
```

## 핵심 권한 모델

| 현재 사용자와 회의의 관계 | 목록·상세 읽기 | 편집 | 삭제 |
|---|---:|---:|---:|
| owner | O | O | O |
| participants에 포함 | O | O | X |
| sharedWith에만 포함 | O | X | X |
| 아무 관계 없음 | X | X | X |
| MeetingAdmin이지만 owner 아님 | O | O | X |

`accessTokens`는 `owner·participants·sharedWith`에서 만든 읽기 검색용 파생 문자열이다. 저장 형식은 `"\nTOKEN1\nTOKEN2\n"`이고, 조회는 `LIKE "%\n현재사용자TOKEN\n%"` 형식으로 수행한다.

## 완료 후 기억할 핵심

```text
브라우저는 사용자 권한 WHERE를 만들지 않는다.
CAP가 로그인 사용자의 req.user로 조회 조건을 강제로 추가한다.

accessTokens는 원본 권한 정보가 아니라 조회용 파생 문자열이다.
원본은 owner·participants·sharedWith다.

목록 조회에서 한 번 허용되었더라도 Action과 하위 데이터 조회에서 다시 검사한다.

브라우저의 meetingsCache 필터는 보안이 아니라 화면 표시 기능이다.
서버가 반환하지 않은 회의는 브라우저 필터를 조작해도 나타나지 않는다.
```

## 다음 시작점

`02. 회의 목록이 사용자별로 필터링되는 과정`은 완료 상태다. 이후 회의 전 단계의 다른 주제로 이동할 때는 해당 주제의 `00. 진행 상황과 다음 시작점` 문서를 새 인수인계 기준으로 사용한다.
