# 00. 진행 상황과 다음 시작점

## 이 파일의 목적

이 파일은 다른 컴퓨터나 새 대화에서 `02. 회의 목록이 사용자별로 필터링되는 과정` 분석을 이어가기 위한 인수인계 문서다.

## 현재 완료된 범위

```text
1단계 완료: loadList()가 listMeetings()를 호출
2단계 완료: readEntityList()가 /api/Meetings OData GET 생성
3단계 완료: CAP before READ Meetings가 req.query에 사용자 WHERE 추가
4단계 완료: userIdentityTokens(req.user)가 DB 검색용 사용자 Token 생성
```

이미 이해한 핵심은 다음과 같다.

```text
브라우저는 owner·participant 조건을 보내지 않는다.
→ CAP가 DB 조회 전에 사용자 조건을 강제로 추가한다.

MeetingAdmin
→ 사용자 WHERE 없이 전체 조회

일반 MeetingUser
→ owner = currentUserId(req)
  또는 accessTokens에 현재 사용자 Token 포함
```

`userIdentityTokens()`는 `req.user.id`, 이메일, 사용자명, 표시 이름과 성명 조합을 수집한다. `normalizeAccessToken()`이 소문자화·공백 정리·LIKE 특수 문자 정리·160자 제한을 적용하고, `expandAccessTokens()`가 이메일의 `@` 앞부분을 추가한 뒤 `Set`으로 중복을 제거한다.

## 다음에 시작할 단계

다음은 기존 02 문서 기준 **5단계**다.

```text
Meetings.accessTokens는 언제 어떻게 만들어지는가?
```

반드시 다음 실제 코드를 차례로 확인한다.

```text
cap/srv/meeting-service.js
├─ buildAccessTokens()                 154행 부근
├─ before CREATE Meetings             493행 부근
└─ before UPDATE Meetings             530행 부근
```

다음 질문에 답하면서 진행한다.

1. `owner`, `participants`, `sharedWith`는 어떤 상태로 `buildAccessTokens()`에 들어가는가?
2. `cleanNameList()`와 `expandAccessTokens()`를 거쳐 어떤 문자열이 만들어지는가?
3. 왜 반환 문자열의 앞뒤와 각 Token 사이에 줄바꿈이 들어가는가?
4. 생성 시뿐 아니라 참여자·공유자 수정 시에도 왜 다시 계산하는가?
5. 앞 단계의 `LIKE '%\n토큰\n%'` 조건과 저장 문자열이 어떻게 정확히 맞물리는가?

## 이후 남은 단계

```text
5단계. accessTokens 생성과 저장
```
