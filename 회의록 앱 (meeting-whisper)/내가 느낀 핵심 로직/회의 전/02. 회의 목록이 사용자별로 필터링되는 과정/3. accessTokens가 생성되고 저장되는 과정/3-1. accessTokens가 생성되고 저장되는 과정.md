# 3-1. accessTokens가 생성되고 저장되는 과정

이 문서는 전체 흐름 중 5단계다. 앞 단계의 `userIdentityTokens(req.user)`가 **현재 사용자를 찾기 위한 Token**을 만들었다면, 이번 단계의 `buildAccessTokens()`는 **각 Meeting 행에 저장할 접근 허용 Token**을 만든다.

```text
현재 사용자 쪽
userIdentityTokens(req.user)
→ ["user@example.com", "user", "사용자 이름", ...]

Meeting 행 쪽
buildAccessTokens({ owner, participants, sharedWith })
→ "\nowner-id\nuser@example.com\nuser\n사용자 이름\n"

두 결과를 meetingAccessWhere()의 LIKE 조건으로 비교
```

## 1. DB에는 원본 목록과 검색용 Token을 함께 저장한다

`Meetings`에는 다음 필드가 있다.

```cds
entity Meetings : cuid, managed {
  owner          : String(255);
  ownerName      : String(160);
  title          : String(160);
  category       : String(80);
  participants   : LargeString;
  sharedWith     : LargeString;
  accessTokens   : LargeString;
  // 나머지 필드 생략
}
```

각 필드의 용도는 다르다.

```text
owner
→ 회의 생성자의 실제 사용자 ID

participants
→ 편집할 수 있는 참여자 이름·이메일 목록을 JSON 문자열로 저장

sharedWith
→ 읽기만 가능한 공유 대상 목록을 JSON 문자열로 저장

accessTokens
→ owner·participants·sharedWith를 검색하기 쉽게 펼친 파생 문자열
```

`accessTokens`는 사용자가 직접 입력하는 원본 정보가 아니라, 앞의 세 필드에서 다시 만들 수 있는 **읽기 권한 검색용 파생·보조 문자열**이다. 별도의 HANA DB 인덱스를 생성한 것은 아니다.

## 2. 브라우저는 참여자와 공유 대상을 JSON 문자열로 전송한다

새 회의를 만드는 CAP 경로에서 브라우저는 다음 요청을 만든다.

```javascript
const meeting = await requestJson("/api/Meetings", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    title: title || "",
    category: category || "",
    participants: JSON.stringify(participants || []),
    sharedWith: JSON.stringify(sharedWith || []),
    durationSec: Math.round(duration || 0),
    minSpeakers: null,
    maxSpeakers: null,
    diarize,
  }),
});
```

바깥쪽 `JSON.stringify()`는 HTTP 요청 본문 전체를 JSON으로 만드는 것이고, 안쪽 두 `JSON.stringify()`는 `participants`와 `sharedWith` 필드 자체를 JSON 배열 문자열로 만드는 것이다.

개념적으로 서버가 받는 값은 다음과 같다.

```javascript
{
  title: "주간 회의",
  participants: "[\"user@example.com\",\"홍길동\"]",
  sharedWith: "[\"viewer@example.com\"]"
}
```

브라우저는 `owner`와 `accessTokens`를 신뢰 가능한 값으로 정하지 않는다. 둘은 CAP가 현재 로그인 사용자를 기준으로 정하거나 다시 계산한다.

## 3. `cleanNameList()`가 사람 목록을 정규화한다

먼저 JSON 배열 또는 JSON 배열 문자열을 실제 배열로 바꾼다.

```javascript
function parseJsonArray(value) {
  if (Array.isArray(value)) return value;
  if (!value) return [];
  try {
    const parsed = JSON.parse(value);
    return Array.isArray(parsed) ? parsed : [];
  } catch {
    return [];
  }
}
```

그 배열을 `cleanNameList()`가 정리한다.

```javascript
function cleanNameList(value) {
  const seen = new Set();
  const result = [];
  for (const item of parseJsonArray(value)) {
    const text = String(item || "").trim().replace(/\s+/g, " ");
    const key = text.toLowerCase();
    if (!text || seen.has(key)) continue;
    seen.add(key);
    result.push(text.slice(0, 160));
    if (result.length >= 80) break;
  }
  return result;
}
```

처리 내용은 다음과 같다.

```text
JSON 문자열을 배열로 변환
→ 각 값을 문자열로 변환
→ 앞뒤 공백 제거
→ 연속 공백을 하나로 축소
→ 대소문자를 무시하고 중복 제거
→ 한 항목을 최대 160자로 제한
→ 목록을 최대 80명으로 제한
```

정리한 목록은 다시 JSON 문자열로 저장한다.

```javascript
function serializeNameList(value) {
  return JSON.stringify(cleanNameList(value));
}
```

따라서 `participants`와 `sharedWith`는 DB에 임의 형식이 아니라 정리된 JSON 배열 문자열로 저장된다.

## 4. `buildAccessTokens()`가 검색용 문자열을 만든다

핵심 함수는 다음과 같다.

```javascript
function buildAccessTokens({ owner, participants, sharedWith }) {
  const values = [
    owner,
    ...cleanNameList(participants),
    ...cleanNameList(sharedWith),
  ];
  const tokens = expandAccessTokens(values);
  return tokens.length ? `\n${tokens.join("\n")}\n` : null;
}
```

실행 순서는 다음과 같다.

```text
owner 1개
+ participants의 정리된 목록
+ sharedWith의 정리된 목록
→ expandAccessTokens(values)
→ 정규화 및 이메일 ID 확장
→ 중복 제거
→ 각 Token을 줄바꿈으로 연결
→ 전체 문자열의 맨 앞과 맨 뒤에도 줄바꿈 추가
```

예를 들어 입력이 다음과 같다고 하자.

```javascript
{
  owner: "owner-id-123",
  participants: "[\"User@example.com\",\"홍길동\"]",
  sharedWith: "[\"viewer@example.com\"]"
}
```

`expandAccessTokens()`는 이메일 전체와 `@` 앞부분을 모두 만들기 때문에 결과는 개념적으로 다음과 같다.

```text
\n
owner-id-123
user@example.com
user
홍길동
viewer@example.com
viewer
\n
```

실제 문자열 표현으로 보면 다음과 같다.

```javascript
"\nowner-id-123\nuser@example.com\nuser\n홍길동\nviewer@example.com\nviewer\n"
```

## 5. 줄바꿈은 Token의 정확한 경계를 만든다

앞 단계의 조회 조건은 다음 형태였다.

```javascript
{
  ref: ["accessTokens"]
},
"like",
{
  val: `%\n${token}\n%`
}
```

저장 문자열과 조회 문자열은 다음처럼 맞물린다.

```text
저장값
\nowner-id-123\nuser\nviewer\n

user 검색 패턴
%\nuser\n%
```

바깥의 `%`는 다른 Token이 앞뒤에 있어도 전체 문자열 안에서 찾게 한다. Token 바로 앞뒤의 `\n`은 `user`가 `admin-user` 또는 `user2`의 일부로 우연히 일치하는 것을 방지하는 경계다.

## 6. CREATE 전에 서버가 owner와 accessTokens를 강제로 정한다

CAP는 새 `Meetings` 행을 INSERT하기 전에 다음 Hook을 실행한다.

```javascript
this.before("CREATE", "Meetings", (req) => {
  req.data.owner = currentUserId(req);
  req.data.ownerName = firstScalar(req.data.ownerName)
    || userDisplayName(req.user)
    || req.data.owner;
  req.data.category = firstScalar(req.data.category)
    .trim()
    .replace(/\s+/g, " ")
    .slice(0, 80);
  req.data.participants = serializeNameList(req.data.participants);
  req.data.sharedWith = serializeNameList(req.data.sharedWith);
  req.data.diarize = normalizeDiarize(req.data.diarize);
  req.data.whisperModelSize = normalizeWhisperModelSize(req.data.whisperModelSize);
  if (!req.data.diarize) {
    req.data.minSpeakers = null;
    req.data.maxSpeakers = null;
  }
  req.data.accessTokens = buildAccessTokens({
    owner: req.data.owner,
    participants: req.data.participants,
    sharedWith: req.data.sharedWith,
  });
  req.data.status = req.data.status || STATUS.CREATED;
  req.data.percent = req.data.percent ?? 0;
});
```

권한 관련 부분만 추리면 다음 순서다.

```text
브라우저의 CREATE 요청 도착
→ req.data.owner를 currentUserId(req)로 덮어씀
→ participants 정리 및 직렬화
→ sharedWith 정리 및 직렬화
→ owner·participants·sharedWith로 accessTokens 계산
→ 정리된 네 값을 한 Meeting 행에 INSERT
```

클라이언트가 `owner`나 `accessTokens`를 조작해서 보내더라도 서버가 다시 정한다는 점이 중요하다.

## 7. 참여자·공유 대상이 바뀌면 accessTokens도 다시 계산한다

일반 OData UPDATE 경로에는 다음 Hook이 있다.

```javascript
this.before("UPDATE", "Meetings", async (req) => {
  if (!("participants" in req.data)
      && !("sharedWith" in req.data)
      && !("owner" in req.data)) return;

  const id = req.data.ID || req.params?.[0]?.ID;
  if (!id) return;

  const existing = await SELECT.one
    .from(Meetings)
    .where({ ID: id });
  if (!existing) return;

  const owner = req.data.owner || existing.owner;
  const participants = "participants" in req.data
    ? serializeNameList(req.data.participants)
    : existing.participants;
  const sharedWith = "sharedWith" in req.data
    ? serializeNameList(req.data.sharedWith)
    : existing.sharedWith;

  if ("participants" in req.data) {
    req.data.participants = participants;
  }
  if ("sharedWith" in req.data) {
    req.data.sharedWith = sharedWith;
  }

  req.data.accessTokens = buildAccessTokens({
    owner,
    participants,
    sharedWith
  });
});
```

UPDATE에는 일부 필드만 들어올 수 있으므로, 변경되지 않은 값은 기존 Meeting 행에서 가져온 뒤 완전한 세 필드를 조합해서 `accessTokens`를 다시 만든다.

다시 계산하지 않으면 다음 문제가 생긴다.

```text
새 참여자를 추가했는데 accessTokens가 과거 값
→ 새 참여자가 목록을 볼 수 없음

기존 공유 대상을 제거했는데 accessTokens가 과거 값
→ 제거된 사용자가 계속 목록을 볼 수 있음
```

## 8. 실제 UI의 접근 대상 수정 Action도 같은 값을 함께 갱신한다

UI가 참여자와 공유 대상을 저장할 때 사용하는 `updateMeetingAccess` Action은 다음과 같다.

```javascript
this.on("updateMeetingAccess", async (req) => {
  const { meetingId } = req.data;
  if (!meetingId) {
    return req.error(400, "meetingId is required");
  }

  const meeting = await assertOwnedMeeting(req, meetingId);
  const participants = serializeNameList(req.data.participants);
  const sharedWith = serializeNameList(req.data.sharedWith);

  await UPDATE(Meetings, meetingId).set({
    participants,
    sharedWith,
    accessTokens: buildAccessTokens({
      owner: meeting.owner,
      participants,
      sharedWith,
    }),
  });

  return SELECT.one.from(Meetings).where({ ID: meetingId });
});
```

이 경로에서는 먼저 `assertOwnedMeeting()`으로 접근 대상을 관리할 권한을 검사한 뒤, 다음 세 필드를 한 번에 갱신한다.

```text
participants
sharedWith
accessTokens
```

## 핵심 정리

```text
원본 권한 정보
owner + participants + sharedWith
             ↓
cleanNameList()
             ↓
expandAccessTokens()
             ↓
"\nTOKEN1\nTOKEN2\n" 형식으로 accessTokens 저장
             ↓
meetingAccessWhere()가 LIKE "%\n현재사용자TOKEN\n%"로 검색
```

`accessTokens`는 별도의 사용자 권한 원장이 아니라, `owner·participants·sharedWith`를 빠르고 일관되게 조회하기 위해 Meeting 행에 함께 저장하는 파생 검색 문자열이다.
