# 4-1. getMeetingStatus가 읽기 편집 삭제 권한을 재검사하는 과정

이 문서는 전체 흐름 중 6단계다. 최초 `/api/Meetings` 목록은 `before READ Meetings`가 이미 사용자별로 제한하지만, 회의별 상태를 얻는 `getMeetingStatus`는 별도의 Action이며 `meetingId`를 직접 받는다. 따라서 이 Action 안에서 해당 ID를 현재 사용자가 실제로 읽을 수 있는지 다시 검사한다.

```text
목록 조회의 WHERE 조건
→ 어떤 Meeting 행을 처음 브라우저에 보낼지 결정

getMeetingStatus의 재검사
→ 전달받은 meetingId 하나를 현재 사용자가 읽을 수 있는지 다시 결정
```

## 1. 목록을 받은 뒤 회의마다 getMeetingStatus를 호출한다

프론트엔드의 `listMeetings()`는 먼저 허용된 `Meetings` 목록을 가져온다.

```javascript
export async function listMeetings() {
  if (useCapApi()) {
    const meetings = await readEntityList("Meetings", {
      orderby: "createdAt desc"
    });

    return Promise.all(meetings.map(async (meeting) => {
      try {
        const status = await postAction("getMeetingStatus", {
          meetingId: meeting.ID || meeting.id
        });
        return capJobFromMeeting({
          ...meeting,
          ...(status?.value || status || {})
        });
      } catch {
        return capJobFromMeeting(meeting);
      }
    }));
  }

  return requestJson("/api/meetings");
}
```

호출 흐름은 다음과 같다.

```text
GET /api/Meetings
→ before READ가 허용된 Meeting 행만 반환
→ 반환된 각 Meeting에 대해 getMeetingStatus({ meetingId }) 호출
→ 상태·대기열·canEdit·canDelete를 합침
→ capJobFromMeeting()으로 UI 객체 생성
```

## 2. Action Handler가 meetingStatusFor()로 넘긴다

CAP Action은 ID가 있는지 확인한 뒤 `meetingStatusFor()`를 호출한다.

```javascript
this.on("getMeetingStatus", async (req) => {
  const { meetingId } = req.data;
  if (!meetingId) {
    return req.error(400, "meetingId is required");
  }
  return meetingStatusFor(req, meetingId);
});
```

여기서 브라우저가 보내는 `meetingId`는 신뢰할 수 없는 입력이다. 사용자가 개발자 도구로 다른 UUID를 넣을 수 있으므로 다음 함수가 반드시 서버에서 권한을 확인한다.

## 3. assertReadableMeeting()이 행 존재와 읽기 권한을 검사한다

`meetingStatusFor()`의 첫 줄은 다음과 같다.

```javascript
async function meetingStatusFor(req, meetingId) {
  const meeting = await assertReadableMeeting(req, meetingId);
  // 이후 상태 조회와 응답 생성
}
```

`assertReadableMeeting()`의 전체 핵심은 다음과 같다.

```javascript
async function assertReadableMeeting(req, meetingId) {
  const meeting = await SELECT.one
    .from(Meetings)
    .where({ ID: meetingId });

  if (!meeting) {
    return req.reject(404, "meeting not found");
  }

  if (!canReadMeeting(req, meeting)) {
    return req.reject(
      403,
      "meeting is not shared with the current user"
    );
  }

  return meeting;
}
```

```text
meetingId로 Meeting 한 행 조회
→ 없으면 404
→ 있으면 canReadMeeting(req, meeting)
→ 읽을 수 없으면 403
→ 읽을 수 있으면 Meeting 반환
```

목록 조회의 `before READ`에만 의존하지 않기 때문에 Action URL과 ID를 직접 조작해도 같은 접근 규칙을 다시 통과해야 한다.

## 4. canReadMeeting()이 읽기 권한을 계산한다

```javascript
function canReadMeeting(req, meeting) {
  if (canAccessAllMeetings(req)) return true;
  if (!meeting) return false;
  if (meeting.owner === currentUserId(req)) return true;

  const tokens = userIdentityTokens(req.user);
  const accessTokens = String(meeting.accessTokens || "");

  if (tokens.some((token) =>
    accessTokens.includes(`\n${token}\n`))) {
    return true;
  }

  const fallbackTokens = expandAccessTokens([
    ...cleanNameList(meeting.participants),
    ...cleanNameList(meeting.sharedWith),
  ]);

  return tokens.some((token) =>
    fallbackTokens.includes(token));
}
```

판정 순서는 다음과 같다.

```text
MeetingAdmin인가?
→ 예: 읽기 허용

Meeting 행이 없는가?
→ 예: 거부

현재 사용자 ID가 owner와 같은가?
→ 예: 읽기 허용

현재 사용자의 Token이 저장된 accessTokens에 있는가?
→ 예: 읽기 허용

participants·sharedWith에서 즉석으로 만든 Token과 일치하는가?
→ 예: 읽기 허용
→ 아니오: 거부
```

마지막 `fallbackTokens`는 `accessTokens`가 없거나 과거 데이터 때문에 최신 형식이 아닐 때도 원본 `participants·sharedWith`를 이용해 한 번 더 판단하는 방어적 보완 경로로 해석할 수 있다.

## 5. canEditMeeting()은 participant까지만 편집을 허용한다

읽을 수 있는 사용자 모두가 편집할 수 있는 것은 아니다.

```javascript
function canEditMeeting(req, meeting) {
  if (canAccessAllMeetings(req)) return true;
  if (!meeting) return false;
  if (meeting.owner === currentUserId(req)) return true;

  const tokens = userIdentityTokens(req.user);
  const participantTokens = expandAccessTokens(
    cleanNameList(meeting.participants)
  );

  return tokens.some((token) =>
    participantTokens.includes(token));
}
```

`sharedWith`는 이 함수에 들어가지 않는다.

```text
owner
→ 읽기 + 편집

participants에 포함된 사용자
→ 읽기 + 편집

sharedWith에만 포함된 사용자
→ 읽기만 가능
```

실제 편집 Action은 `assertEditableMeeting()`을 사용한다.

```javascript
async function assertEditableMeeting(req, meetingId) {
  const meeting = await assertReadableMeeting(req, meetingId);
  if (!canEditMeeting(req, meeting)) {
    return req.reject(
      403,
      "meeting can only be edited by the creator or participants"
    );
  }
  return meeting;
}
```

즉 먼저 읽기 권한을 통과한 뒤 편집 권한을 한 번 더 검사한다.

## 6. 삭제 가능 여부는 owner 일치만 본다

`meetingStatusFor()`가 반환하는 삭제 플래그는 다음과 같이 계산된다.

```javascript
canDelete: meeting.owner === currentUserId(req)
```

실제 삭제 Action도 같은 원칙을 서버에서 다시 검사한다.

```javascript
async function assertDeletableMeeting(req, meetingId) {
  const meeting = await SELECT.one
    .from(Meetings)
    .where({ ID: meetingId });

  if (!meeting) {
    return req.reject(404, "meeting not found");
  }

  if (meeting.owner !== currentUserId(req)) {
    return req.reject(
      403,
      "only the meeting creator can delete this meeting"
    );
  }

  return meeting;
}
```

따라서 participant와 sharedWith 사용자는 삭제할 수 없다. 현재 코드상 `MeetingAdmin`도 해당 회의의 owner가 아니라면 `canDelete`가 `false`이고 `deleteMeeting` Action도 거부한다.

## 7. meetingStatusFor()가 권한 플래그를 응답에 포함한다

읽기 권한을 통과한 뒤 상태·대기열 정보와 함께 권한 플래그를 반환한다.

```javascript
async function meetingStatusFor(req, meetingId) {
  const meeting = await assertReadableMeeting(req, meetingId);
  const dispatch = await SELECT.one
    .from(TranscriptionDispatches)
    .where({ meeting_ID: meetingId })
    .orderBy("modifiedAt desc");

  const dispatchLastError = sanitizeOperationalError(
    dispatch?.lastError
  );
  const queueInfo = await transcriptionQueueInfo(meeting, dispatch);

  return {
    ID: meeting.ID,
    owner: meeting.owner,
    ownerName: meetingOwnerName(meeting),
    title: meeting.title,
    category: meeting.category,
    participants: meeting.participants,
    sharedWith: meeting.sharedWith,
    status: meeting.status,
    percent: meeting.percent,
    // 나머지 상태·대기열 정보 생략
    canEdit: canEditMeeting(req, meeting),
    canDelete: meeting.owner === currentUserId(req),
  };
}
```

프론트엔드는 이를 UI 이름으로 변환한다.

```javascript
return {
  // 다른 필드 생략
  can_edit: meeting.canEdit ?? meeting.can_edit ?? true,
  can_delete: meeting.canDelete ?? meeting.can_delete ?? false,
};
```

## 8. 권한 관계별 최종 결과

| 현재 사용자와 회의의 관계 | 읽기 | 편집 | 삭제 |
|---|---:|---:|---:|
| owner | O | O | O |
| participants에 포함 | O | O | X |
| sharedWith에만 포함 | O | X | X |
| 아무 관계 없음 | X | X | X |
| MeetingAdmin이지만 owner 아님 | O | O | X |

`canEdit`와 `canDelete`는 화면에서 버튼을 숨기기 위한 안내값이지만, 보안 자체는 아니다. 실제 편집·삭제 Action에서도 `assertEditableMeeting()` 또는 `assertDeletableMeeting()`을 다시 실행한다.

또한 `listMeetings()`는 `getMeetingStatus` 호출 실패 시 기본 Meeting 객체를 사용하는 fallback이 있다. 이때 `can_edit`의 기본값 때문에 버튼이 일시적으로 잘못 보일 가능성은 있지만, 실제 서버 Action의 권한 검사는 그대로 남아 있으므로 버튼 표시만으로 권한을 우회할 수는 없다.

## 핵심 정리

```text
허용된 Meetings 목록
→ 각 Meeting ID로 getMeetingStatus 호출
→ assertReadableMeeting()
   ├─ 404: Meeting 없음
   ├─ 403: 현재 사용자가 읽을 수 없음
   └─ 성공: 상태 조회 계속
→ canEditMeeting()으로 편집 가능 여부 계산
→ owner 일치로 삭제 가능 여부 계산
→ canEdit·canDelete를 브라우저에 반환
→ 실제 변경 Action에서도 다시 서버 검사
```
