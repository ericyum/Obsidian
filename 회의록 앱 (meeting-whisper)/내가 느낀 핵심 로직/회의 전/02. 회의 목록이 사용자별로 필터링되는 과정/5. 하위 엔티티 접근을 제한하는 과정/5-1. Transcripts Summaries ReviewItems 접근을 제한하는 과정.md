# 5-1. Transcripts Summaries ReviewItems 접근을 제한하는 과정

이 문서는 전체 흐름 중 7단계다. `Meetings` 목록만 사용자별로 제한해도, 하위 엔티티를 직접 조회할 수 있다면 권한 없는 전사문이나 요약문을 읽을 가능성이 생긴다. 그래서 CAP는 `Transcripts`, `Summaries`, `ReviewItems`의 READ에도 접근 가능한 Meeting ID 조건을 추가한다.

```text
Meetings 권한 필터만 존재
→ /api/Meetings에서는 다른 사람 회의가 안 보임
→ 하지만 /api/Transcripts 직접 호출 가능성이 남음

하위 엔티티 READ 필터도 적용
→ 접근 가능한 Meeting에 연결된 행만 반환
```

## 1. 하위 엔티티는 meeting Association으로 부모 회의와 연결된다

DB 모델은 다음과 같다.

```cds
entity Transcripts : cuid, managed {
  meeting        : Association to one Meetings not null;
  language       : String(16) default 'ko';
  content        : LargeString;
}

entity Summaries : cuid, managed {
  meeting        : Association to one Meetings not null;
  content        : LargeString;
  markdown       : LargeString;
}

entity ReviewItems : cuid, managed {
  meeting        : Association to one Meetings not null;
  segmentIndex   : Integer;
  text           : String(500);
  category       : ReviewCategory default 'word';
  reason         : LargeString;
  suggestion     : String(500);
  confidence     : Decimal(5, 4);
  source         : String(40);
}
```

CAP가 관리하는 외래키는 OData와 DB 조회에서 `meeting_ID`로 사용된다.

```text
Transcripts.meeting_ID
Summaries.meeting_ID
ReviewItems.meeting_ID
→ 모두 Meetings.ID를 가리킴
```

하위 행에는 별도의 `owner`나 `accessTokens`가 없다. 따라서 부모 `Meetings`의 접근 가능 여부를 이용해 권한을 상속한다.

## 2. 세 엔티티는 MeetingService의 공개 OData 엔티티다

서비스 정의에는 다음 projection이 있다.

```cds
entity Meetings as projection on db.Meetings excluding { audio };
entity Transcripts as projection on db.Transcripts;
entity Summaries as projection on db.Summaries;
entity ReviewItems as projection on db.ReviewItems;
```

따라서 브라우저는 개념적으로 다음 URL을 호출할 수 있다.

```text
GET /api/Transcripts
GET /api/Summaries
GET /api/ReviewItems
```

브라우저가 올바른 `$filter`를 보낸다는 사실만 믿으면 안 된다. 사용자는 URL을 직접 바꿀 수 있으므로 서버가 항상 접근 가능한 부모 회의 조건을 추가해야 한다.

## 3. 정상 UI는 meeting_ID 필터를 만들어 하위 데이터를 요청한다

`capJobFromMeeting()`은 회의 하나를 UI 객체로 조립할 때 다음 필터를 만든다.

```javascript
async function capJobFromMeeting(meeting) {
  const meetingId = meeting.ID || meeting.id;
  const meetingFilter = `meeting_ID eq ${odataString(meetingId)}`;

  const [transcriptRow, summaryRow, reviewRows] = await Promise.all([
    readFirst("Transcripts", meetingFilter),
    readFirst("Summaries", meetingFilter),
    readEntityList("ReviewItems", {
      filter: meetingFilter
    }),
  ]);

  // JSON 해석과 UI 객체 변환 계속
}
```

`readFirst()`도 내부적으로 `readEntityList()`를 사용한다.

```javascript
async function readFirst(entity, filter) {
  const rows = await readEntityList(entity, { filter });
  return rows[0] || null;
}
```

따라서 실제 요청은 다음과 비슷하다.

```text
GET /api/Transcripts?$filter=meeting_ID eq '회의 UUID'
GET /api/Summaries?$filter=meeting_ID eq '회의 UUID'
GET /api/ReviewItems?$filter=meeting_ID eq '회의 UUID'
```

이 `meeting_ID` 조건은 UI가 원하는 회의를 선택하기 위한 조건이다. 아직 권한을 증명하는 조건은 아니다.

## 4. accessibleMeetingIds()가 현재 사용자의 허용된 Meeting ID를 구한다

서버는 먼저 현재 사용자가 볼 수 있는 부모 Meeting ID 목록을 조회한다.

```javascript
async function accessibleMeetingIds(req) {
  if (canAccessAllMeetings(req)) return null;

  const rows = await SELECT
    .from(Meetings)
    .columns("ID")
    .where(meetingAccessWhere(req));

  return rows.map((row) => row.ID);
}
```

일반 사용자는 앞 단계와 같은 `meetingAccessWhere(req)`를 사용한다.

```text
owner = currentUserId(req)
OR accessTokens에 현재 사용자 Token 포함
```

결과는 다음처럼 Meeting ID 배열이다.

```javascript
[
  "허용된-회의-ID-1",
  "허용된-회의-ID-2"
]
```

`MeetingAdmin`이면 `null`을 반환한다. 여기서 `null`은 조회 결과가 없다는 뜻이 아니라, 모든 회의에 접근할 수 있으므로 추가 제한이 필요 없다는 특별한 표시다.

## 5. restrictChildReadToAccessibleMeetings()가 하위 조회문을 수정한다

```javascript
async function restrictChildReadToAccessibleMeetings(req) {
  const meetingIds = await accessibleMeetingIds(req);

  if (meetingIds === null) return;

  if (!meetingIds.length) {
    req.query.where({ meeting_ID: null });
    return;
  }

  req.query.where({
    meeting_ID: { in: meetingIds }
  });
}
```

경우별 동작은 다음과 같다.

```text
MeetingAdmin
→ meetingIds === null
→ 추가 WHERE 없이 전체 범위 허용

접근 가능한 Meeting이 0개인 일반 사용자
→ WHERE meeting_ID IS NULL 추가
→ meeting Association이 not null이므로 결과 0개

접근 가능한 Meeting이 있는 일반 사용자
→ WHERE meeting_ID IN (허용된 ID 목록) 추가
```

## 6. before READ Hook이 세 엔티티에 공통 적용된다

```javascript
this.before(
  "READ",
  ["Transcripts", "Summaries", "ReviewItems"],
  restrictChildReadToAccessibleMeetings
);
```

브라우저가 보낸 기존 `$filter`는 유지되고, 서버의 허용된 Meeting ID 조건이 추가된다. 개념적으로 두 조건은 AND로 결합된다.

```sql
브라우저 조건
meeting_ID = '요청한 회의 ID'

서버 조건
meeting_ID IN ('허용 ID 1', '허용 ID 2')

최종 조건
meeting_ID = '요청한 회의 ID'
AND meeting_ID IN ('허용 ID 1', '허용 ID 2')
```

요청한 ID가 허용 목록에 있으면 하위 데이터가 반환되고, 없으면 결과가 빈 배열이 된다.

## 7. 브라우저 필터를 제거하거나 ID를 조작해도 범위가 넓어지지 않는다

사용자가 다음처럼 정상 필터를 제거했다고 하자.

```text
GET /api/Transcripts
```

서버는 여전히 다음 조건을 추가한다.

```sql
WHERE meeting_ID IN (현재 사용자가 접근 가능한 Meeting ID들)
```

또는 권한 없는 회의 ID를 직접 요청해도 다음과 같이 된다.

```sql
WHERE meeting_ID = '권한 없는 ID'
  AND meeting_ID IN ('허용된 ID들')
```

두 조건을 동시에 만족하는 행이 없으므로 일반적인 OData 목록 응답은 `200`과 빈 `value` 배열이 된다. `getMeetingStatus`처럼 명시적인 `403`을 반환하는 방식과 응답 모양은 다르지만, 데이터는 반환되지 않는다.

## 8. 이 Hook은 READ 전용이다

Hook 등록은 분명히 다음과 같다.

```javascript
this.before("READ", ...)
```

따라서 이 코드 하나만 보고 `Transcripts`, `Summaries`, `ReviewItems`의 모든 CREATE·UPDATE·DELETE까지 보호된다고 결론 내리면 안 된다.

정상 UI의 쓰기 작업은 다음과 같은 별도 Action을 사용한다.

```text
saveTranscript
→ assertEditableMeeting(req, meetingId)
→ Transcripts DELETE/INSERT

saveSummary
→ assertEditableMeeting(req, meetingId)
→ Summaries·ReviewItems 갱신
```

이 Action들은 부모 Meeting의 편집 권한을 검사한다. 그러나 공개 projection에 대한 일반 OData 쓰기 전체가 어떻게 제한되는지는 READ Hook과 별개의 보안 점검 대상이다.

## 9. 현재 구조의 요청 비용

`listMeetings()`는 각 Meeting마다 다음 호출을 수행한다.

```text
getMeetingStatus 1회
Transcripts READ 1회
Summaries READ 1회
ReviewItems READ 1회
```

회의가 N개라면 주요 브라우저 HTTP 요청 수는 대략 다음과 같다.

```text
Meetings 목록 1회 + 회의마다 4회
= 1 + 4N
```

또한 세 하위 READ마다 서버는 접근 가능한 Meeting ID를 다시 조회한다. 권한상 안전하고 구조가 단순하다는 장점이 있지만, 회의 수가 커지면 성능 최적화 후보가 될 수 있다.

## 핵심 정리

```text
브라우저가 특정 meeting_ID의 하위 데이터 요청
                  ↓
before READ Transcripts/Summaries/ReviewItems
                  ↓
accessibleMeetingIds(req)
                  ↓
meetingAccessWhere(req)로 허용된 부모 Meeting ID 조회
                  ↓
req.query.where({ meeting_ID: { in: meetingIds } })
                  ↓
브라우저가 요청한 ID와 서버 허용 ID의 교집합만 반환
```

하위 데이터의 권한은 각 하위 행에 따로 저장하지 않고, `meeting_ID`를 통해 부모 `Meetings`의 접근 권한을 상속한다.
