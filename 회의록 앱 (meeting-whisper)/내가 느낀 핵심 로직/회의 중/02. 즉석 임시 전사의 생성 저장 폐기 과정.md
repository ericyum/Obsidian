# 즉석 임시 전사의 생성·저장·폐기 과정 — 실제 코드 워크스루

## 이 문서가 따라가는 두 갈래

```text
[임시 전사]
recorder.start()
→ startLiveTranscript()
→ browser SpeechRecognition
→ onresult
→ liveInterimText / liveFinalText
→ currentDraft.liveText
→ localStorage

[최종 전사]
recorder.stop()
→ 음성 Blob
→ createJob(blob, title, participants, ...)
→ CAP/Object Store
→ Worker STT
→ Transcripts
```

두 갈래는 같은 마이크에서 출발하지만 `createJob()` 인자에서 만나지 않는다. 아래 코드는 그 단절을 호출부와 피호출부 양쪽에서 확인한다.

---

## 단계 1. 녹음 시작 직후 브라우저 SpeechRecognition을 시작한다

### 1) 이 단계가 하는 일

MediaRecorder 녹음과 별개로 브라우저 음성 인식 객체를 만든다.

### 2) 실제 호출부 코드

`app/meeting-ui/js/app.js` 1338~1347행:

```javascript
show("view-recording");
paintLiveTranscript();
$("rec-title").textContent = currentDraft.title || "회의";
$("rec-chips").innerHTML = participants.map((p) => `<span class="chip"><i></i>${esc(p)}</span>`).join("");
$("timer").textContent = "00:00";
$("pause-resume").textContent = "일시정지";
setRecordingStatus(false);
recorder.start();
startLiveTranscript();
timerInt = setInterval(updateRecordingTimer, 500);
initMicGraph();
```

### 3) 전달되는 인자와 상태

명시적 인자는 없다. 함수는 전역 `recorder`, `live`, `liveWanted`, `liveProcessedResultIndex`와 DOM을 사용한다.

### 4) 실제 피호출부 코드

`app/meeting-ui/js/app.js` 1561~1574행:

```javascript
function startLiveTranscript() {
  const SpeechRecognition = window.SpeechRecognition || window.webkitSpeechRecognition;
  liveWanted = true;
  if (!SpeechRecognition) {
    $("live-state").textContent = "이 브라우저에서는 지원되지 않음";
    return;
  }
  if (live) return;
  liveProcessedResultIndex = 0;
  live = new SpeechRecognition();
  live.lang = "ko-KR";
  live.continuous = true;
  live.interimResults = true;
  live.onstart = () => $("live-state").textContent = "임시 전사 중";
```

### 5) 경계

**앱 JavaScript → 브라우저 Web Speech API 경계**다. Python Worker나 CAP 호출은 없다. 실제 인식 엔진의 로컬/원격 처리 방식은 브라우저 구현 영역이다.

### 6) 반환값을 받는 코드

`live.start()` 자체의 return을 사용하지 않는다. 결과는 비동기 `onresult`, `onerror`, `onend` event로 돌아온다.

### 7) 다음 단계

브라우저가 음성 결과 event를 내면 `live.onresult`가 interim과 final을 분리한다.

---

## 단계 2. `onresult`가 final 문장과 interim 문장을 분리한다

### 1) 이 단계가 하는 일

이전에 처리하지 않은 SpeechRecognition 결과 중 final은 확정 줄에 추가하고, 아직 final이 아닌 결과는 한 줄의 interim 문자열로 만든다.

### 2) 실제 호출부

호출자는 브라우저 Web Speech API다. 앱은 callback을 다음처럼 등록한다.

### 3) 전달되는 인자와 상태

- `event.results`: 브라우저가 누적한 인식 결과
- `event.results[i].isFinal`: 확정 여부
- `liveProcessedResultIndex`: 이미 final 처리한 마지막 위치

### 4) 실제 피호출부 코드

`app/meeting-ui/js/app.js` 1593~1611행:

```javascript
live.onresult = (event) => {
  syncLiveFinalFromEditor();
  const interimLines = [];
  for (let i = liveProcessedResultIndex; i < event.results.length; i += 1) {
    const text = (event.results[i][0]?.transcript || "").trim();
    if (!text) continue;
    if (event.results[i].isFinal) {
      appendLiveLine(text);
      liveProcessedResultIndex = i + 1;
    }
  }
  for (let i = liveProcessedResultIndex; i < event.results.length; i += 1) {
    const text = (event.results[i][0]?.transcript || "").trim();
    if (!text) continue;
    if (!event.results[i].isFinal) interimLines.push(text);
  }
  liveInterimText = interimLines.join(" ");
  paintLiveTranscript();
};
```

### 5) 경계

브라우저 event 객체가 앱 메모리의 문자열 `liveFinalText`, `liveInterimText`로 바뀐다.

### 6) 반환값을 받는 코드

callback은 return을 사용하지 않는다. `paintLiveTranscript()`가 바뀐 전역 문자열을 읽어 DOM을 갱신한다.

### 7) 다음 단계

final 결과는 `appendLiveLine()`에서 중복을 검사하고 localStorage 초안에 저장된다.

---

## 단계 3. final 문장을 `currentDraft.liveText`에 저장한다

### 1) 이 단계가 하는 일

확정 문장을 줄 단위로 누적하고 마지막 줄과 완전히 같으면 중복 추가하지 않는다.

### 2) 실제 호출부 코드

```javascript
if (event.results[i].isFinal) {
  appendLiveLine(text);
  liveProcessedResultIndex = i + 1;
}
```

### 3) 전달되는 인자와 상태

`text`는 `event.results[i][0].transcript`를 trim한 문자열이다.

### 4) 실제 피호출부 코드

`app/meeting-ui/js/app.js` 1628~1636행, 1666~1674행:

```javascript
function liveFinalLines() {
  return liveFinalText.split("\n").map((line) => line.trim()).filter(Boolean);
}

function saveLiveFinalToDraft() {
  if (!currentDraft) return;
  currentDraft.liveText = liveFinalText;
  saveDraftMeta(currentDraft);
}
```

```javascript
function appendLiveLine(text) {
  const clean = (text || "").trim();
  if (!clean) return;
  const lines = liveFinalLines();
  if (lines[lines.length - 1] === clean) return;
  lines.push(clean);
  liveFinalText = lines.join("\n");
  saveLiveFinalToDraft();
}
```

`saveDraftMeta()`가 받는다.

```javascript
export function saveDraftMeta(meta) {
  localStorage.setItem(META_KEY, JSON.stringify(meta));
}
```

### 5) 경계

`liveFinalText`는 JavaScript 메모리에서 `currentDraft.liveText`를 거쳐 localStorage JSON으로 이동한다. CAP 경계는 넘지 않는다.

### 6) 반환값을 받는 코드

다음 timer tick과 편집 UI가 같은 `liveFinalText`를 계속 읽는다.

### 7) 다음 단계

사용자가 final 줄을 직접 편집하면 DOM 내용을 다시 `liveFinalText`로 동기화한다.

## 단계 4. 사용자가 임시 전사 확정문을 편집한다

### 1) 이 단계가 하는 일

contenteditable로 표시된 final 줄의 현재 DOM 텍스트를 다시 메모리와 초안에 저장한다.

### 2) 실제 호출부 코드

`app/meeting-ui/js/app.js` 1649~1663행:

```javascript
function bindLiveFinalEditors() {
  $("live-transcript").querySelectorAll(".live-final-line").forEach((line) => {
    if (line.dataset.liveBound === "true") return;
    line.dataset.liveBound = "true";
    line.addEventListener("input", syncLiveFinalFromEditor);
    line.addEventListener("blur", () => {
      syncLiveFinalFromEditor();
      paintLiveTranscript();
    });
    line.addEventListener("keydown", (event) => {
      if (event.key !== "Enter" || event.shiftKey) return;
      event.preventDefault();
      line.blur();
    });
  });
}
```

### 3) 전달되는 인자와 상태

함수 인자는 없고 현재 `.live-final-line` DOM 전체를 읽는다.

### 4) 실제 피호출부 코드

`app/meeting-ui/js/app.js` 1638~1647행:

```javascript
function syncLiveFinalFromEditor() {
  const host = $("live-transcript");
  const finalWrap = host?.querySelector(".live-final-lines");
  if (!finalWrap) return;
  const lines = [...finalWrap.querySelectorAll(".live-final-line")]
    .map((line) => line.innerText.trim())
    .filter(Boolean);
  liveFinalText = lines.join("\n");
  saveLiveFinalToDraft();
}
```

### 5) 경계

**DOM → JavaScript 문자열 → localStorage 경계**다.

### 6) 반환값을 받는 코드

다음 `paintLiveTranscript()`가 수정된 `liveFinalText`를 다시 그린다.

### 7) 다음 단계

일시정지 또는 stop 시 남아 있는 interim까지 final에 commit한다.

## 단계 5. 일시정지·종료 시 interim을 확정하고 SpeechRecognition을 멈춘다

### 1) 이 단계가 하는 일

화면에 남아 있는 interim 문장을 final 목록에 붙이고 SpeechRecognition 재시작 의도를 끈다.

### 2) 실제 호출부 코드

중지 handler:

```javascript
const duration = recorder.elapsed();
clearInterval(timerInt);
commitLiveInterim();
stopLiveTranscript();
stopRecordingSessionKeepAlive();
const blob = await recorder.stop();
```

### 3) 전달되는 인자와 상태

함수 인자는 없고 `liveInterimText`, `liveFinalText`, `live`, `liveWanted`를 사용한다.

### 4) 실제 피호출부 코드

`app/meeting-ui/js/app.js` 1619~1626행, 1676~1684행:

```javascript
function stopLiveTranscript() {
  liveWanted = false;
  commitLiveInterim();
  if (!live) return;
  const active = live;
  live = null;
  try { active.stop(); } catch (_) {}
}
```

```javascript
function commitLiveInterim() {
  syncLiveFinalFromEditor();
  if (liveInterimText.trim()) {
    appendLiveLine(liveInterimText);
    liveInterimText = "";
  }
  paintLiveTranscript();
  saveLiveFinalToDraft();
}
```

### 5) 경계

브라우저 Web Speech session을 중단하는 경계다. MediaRecorder stop은 별도로 실행된다.

### 6) 반환값을 받는 코드

반환값은 사용하지 않는다. stop handler는 계속 `recorder.stop()`의 음성 Blob을 기다린다.

### 7) 다음 단계

음성 Blob과 회의 메타만 `createJob()`으로 전달된다.

## 단계 6. 브라우저 음성 인식이 스스로 끝나면 조건부 재시작한다

### 1) 이 단계가 하는 일

Web Speech API가 장시간 실행 중 종료되어도 실제 녹음 중이면 500ms 후 다시 시작한다.

### 2) 실제 호출부 코드

SpeechRecognition session을 실제로 시작하는 `app/meeting-ui/js/app.js` 코드다.

```javascript
try {
  live.start();
} catch (_) {
  live = null;
}
```

### 3) 전달되는 인자와 상태

`onend`는 함수 인자를 받기보다 바깥 상태를 읽는다.

- `liveWanted`: 사용자가 계속 실시간 전사를 원하고 있는가
- `recorder`: 녹음기가 아직 존재하는가
- `recorder.state()`: 실제 상태가 `recording`인가
- `liveInterimText`: 종료 직전 확정해야 할 임시 문장

### 4) 실제 피호출부 callback 코드

`app/meeting-ui/js/app.js` 1586~1592행:

```javascript
live.onend = () => {
  commitLiveInterim();
  live = null;
  if (liveWanted && recorder && recorder.state() === "recording") {
    setTimeout(startLiveTranscript, 500);
  }
};
```

### 5) 경계

브라우저 SpeechRecognition session 하나가 끝나고 새 session이 만들어지는 경계다.

### 6) 반환값을 받는 코드

새 객체의 결과도 다시 같은 `onresult` callback으로 들어온다.

### 7) 다음 단계

사용자가 pause/stop하여 `liveWanted=false`가 되기 전까지 반복된다.

## 단계 7. `createJob()` 인자에 `liveText`가 없음을 양쪽 코드에서 확인한다

### 1) 이 단계가 하는 일

임시 전사가 최종 전사의 hint나 입력으로 전달되는지 확인한다. 결론은 전달되지 않는다는 것이다.

### 2) 실제 호출부 코드

`app/meeting-ui/js/app.js` 1403~1415행:

```javascript
try {
  await ensureFreshSession("recording-upload");
  currentJob = await createJob(
    blob,
    $("title").value.trim(),
    participants,
    ext,
    duration,
    speakerBounds,
    sharedWith,
    transcriptionOptions,
    currentDraft?.category || selectedMeetingCategory(),
  );
```

### 3) 전달되는 인자와 상태

전달되는 값은 음성 Blob, 제목, 참석자, 확장자, 길이, 화자 범위, 공유자, 전사 옵션, 카테고리다. `liveFinalText`와 `currentDraft.liveText`는 없다.

### 4) 실제 피호출부 코드

`app/meeting-ui/js/api.js` 425~445행:

```javascript
export async function createJob(blob, title, participants, ext, duration, speakerBounds = {}, sharedWith = [], transcriptionOptions = {}, category = "") {
  const diarize = false;
  if (useCapApi()) {
    const meeting = await requestJson("/api/Meetings", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        title: title || "",
        category: category || "",
        participants: JSON.stringify(participants || []),
        sharedWith: JSON.stringify(sharedWith || []),
        durationSec: Math.round(duration || 0),
        minSpeakers: null,
        maxSpeakers: null,
        diarize,
      }),
    });
    const meetingId = meeting.ID;
    await uploadCapAudio(meetingId, blob, ext);
    await postAction("enqueueTranscription", { meetingId });
    return meetingId;
  }
```

### 5) 경계

**브라우저 → CAP HTTP 경계**에서 `liveText`가 payload에 포함되지 않는다. raw binary 요청에는 오직 Blob bytes가 들어간다.

### 6) 반환값을 받는 코드

CAP가 반환한 Meeting ID만 UI가 받는다. 최종 transcript는 이후 Worker 결과를 polling하여 별도로 받는다.

### 7) 다음 단계

Worker는 서버에 저장된 음성만 다운로드하여 STT를 실행한다. 임시 전사 문자열은 최종 transcript와 만나지 않는다.

## 단계 8. 복구 업로드도 `liveText`를 읽지 않는다

### 1) 이 단계가 하는 일

페이지가 중단된 뒤 복구할 때 `meta.liveText`가 최종 전사에 쓰이는지도 확인한다.

### 2) 실제 호출부 코드

복구 배너의 업로드 버튼이 `uploadRecoveredDraft(meta)`를 호출한다.

```javascript
if (canUpload) $("recover-upload").onclick = () => uploadRecoveredDraft(meta);
```

### 3) 전달되는 인자와 상태

`meta`에는 `sessionId`, MIME type, 제목, 참석자, 공유자, 녹음 길이, 화자·카테고리 설정과 `liveText`가 들어 있을 수 있다. 함수는 `sessionId`로 IndexedDB chunks를 읽지만 `liveText`는 읽지 않는다.

### 4) 실제 피호출부 복구 코드

`app/meeting-ui/js/app.js` 567~591행:

```javascript
const type = meta.mimeType || "audio/webm";
const blob = new Blob(chunks, { type });
const ext = type.includes("mp4") ? "mp4" : "webm";
resetResultView();
show("view-result");
try {
  const speakerBounds = {
    minSpeakers: meta.minSpeakers || null,
    maxSpeakers: meta.maxSpeakers || null,
  };
  const transcriptionOptions = {
    diarize: Boolean(meta.diarize),
  };
  await ensureFreshSession("recover-upload");
  currentJob = await createJob(
    blob,
    meta.title || "",
    meta.participants || [],
    ext,
    meta.durationSeconds || 0,
    speakerBounds,
    meta.sharedWith || [],
    transcriptionOptions,
    meta.category || "",
  );
```

### 5) 경계

IndexedDB Blob은 서버로 이동하지만 localStorage의 `meta.liveText`는 함수에서 읽지 않는다.

### 6) 반환값을 받는 코드

정상 녹음과 같은 Meeting ID를 받는다.

### 7) 다음 단계

복구된 음성도 동일한 Worker 최종 STT로 간다.

## 최종 결론

```text
Web Speech API 결과
→ liveFinalText
→ currentDraft.liveText
→ localStorage에서 끝

MediaRecorder 결과
→ Blob
→ createJob
→ CAP/Object Store
→ Worker STT
→ Transcripts
```

임시 전사는 화면 피드백이며 최종 STT의 초안·프롬프트·교정 사전이 아니다.
