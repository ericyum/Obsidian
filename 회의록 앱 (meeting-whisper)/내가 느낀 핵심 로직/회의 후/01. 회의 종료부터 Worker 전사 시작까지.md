# 회의 종료부터 Worker 전사 시작까지 — 실제 코드 워크스루

## 이 문서가 답하는 질문

회의 종료 버튼을 누른 뒤, 최종 녹음 Blob이 어디로 전달되고 어떤 DB 상태를 거쳐 Python Worker가 실제 전사를 시작하는가?

이 문서는 아래 한 줄을 실제 호출 코드와 반환 코드가 끊기지 않도록 따라간다.

```text
종료 버튼
  → recorder.stop()
  → createJob()
  → Meetings 생성
  → raw binary 업로드
  → enqueueTranscription
  → TranscriptionDispatches 저장
  → Worker POST /transcribe
  → CAP claimTranscription
  → Worker background task
  → getAudio
  → STT 진입
```

> 범위: 이 문서는 Worker가 STT 함수에 들어가기 직전까지를 다룬다. STT 프롬프트와 모델 호출은 다음 문서에서 이어진다.

---

## 1단계. 종료 버튼이 최종 Blob을 만들고 `createJob()`을 호출한다

### 1. 이 단계가 하는 일

브라우저의 녹음을 끝내고, 최종 Blob과 회의 메타데이터를 업로드 함수에 넘긴다.

### 2. 실제 호출자 코드

`app/meeting-ui/js/app.js`의 종료 처리 코드다.

```js
const blob = await recorder.stop();
const ext = recorder.mimeType.includes("mp4") ? "mp4" : "webm";
await promptRecordingBackup({
  blob,
  ext,
  title: currentDraft?.title || $("title").value.trim(),
});
resetResultView();
show("view-result");
const speakerBounds = {
  minSpeakers: currentDraft?.minSpeakers || null,
  maxSpeakers: currentDraft?.maxSpeakers || null,
};
const transcriptionOptions = {
  diarize: Boolean(currentDraft?.diarize),
};
try {
  await ensureFreshSession("recording-upload");
  currentJob = await createJob(
    blob,
    $("title").value.trim(),
    participants,
    ext,
    duration,
    speakerBounds,
    sharedWith,
    transcriptionOptions,
    currentDraft?.category || selectedMeetingCategory(),
  );
  syncMeetingRoute(currentJob);
  await deleteDraft(currentDraft?.sessionId);
  pendingUpload = null;
  currentDraft = null;
  recorder = null;
  poll();
```

### 3. 전달되는 값과 상태

- `blob`: 최종 녹음 바이너리
- `title`, `category`, `participants`, `sharedWith`: 회의 메타데이터
- `duration`: 녹음 길이
- `speakerBounds`, `transcriptionOptions`: 현재 UI가 넘기기는 하지만 CAP 경로에서는 뒤에서 고정·정규화된다.

### 4. 실제 피호출자 코드

`app/meeting-ui/js/api.js`의 `createJob()`이 받는다.

```js
export async function createJob(blob, title, participants, ext, duration, speakerBounds = {}, sharedWith = [], transcriptionOptions = {}, category = "") {
  const diarize = false;
  if (useCapApi()) {
    const meeting = await requestJson("/api/Meetings", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        title: title || "",
        category: category || "",
        participants: JSON.stringify(participants || []),
        sharedWith: JSON.stringify(sharedWith || []),
        durationSec: Math.round(duration || 0),
        minSpeakers: null,
        maxSpeakers: null,
        diarize,
      }),
    });
    const meetingId = meeting.ID;
    await uploadCapAudio(meetingId, blob, ext);
    await postAction("enqueueTranscription", { meetingId });
    return meetingId;
  }
```

### 5. 경계

`requestJson("/api/Meetings")`에서 브라우저 메모리 경계를 넘어 HTTP를 거쳐 CAP DB의 `Meetings` 행이 생긴다. 녹음 Blob은 아직 브라우저 메모리에 있다.

### 6. 반환을 받는 코드

`meeting.ID`를 `meetingId`로 받고, 같은 함수 안에서 오디오 업로드와 전사 큐 등록을 순서대로 기다린다. 세 호출이 모두 성공해야 `meetingId`가 UI로 반환된다.

### 7. 다음 단계

`uploadCapAudio(meetingId, blob, ext)`가 Blob 자체를 전송한다.

## 2단계. Blob을 JSON이 아닌 raw binary 경로로 올린다

### 1. 이 단계가 하는 일

회의 메타데이터와 분리하여 녹음 Blob을 HTTP body 그대로 보낸다.

### 2. 실제 호출자 코드

바로 위 `createJob()`의 다음 두 줄이다.

```js
const meetingId = meeting.ID;
await uploadCapAudio(meetingId, blob, ext);
```

### 3. 전달되는 값과 상태

- URL path: `/api-binary/Meetings/{meetingId}/audio`
- HTTP method: `POST`
- body: `Blob`
- `Content-Type`: Blob의 MIME type

### 4. 실제 피호출자 코드

`app/meeting-ui/js/api.js`:

```js
async function uploadCapAudio(meetingId, blob, ext) {
  const contentType = blob.type || `audio/${ext || "webm"}`;
  const url = `/api-binary/Meetings/${encodeURIComponent(meetingId)}/audio`;
  try {
    return await uploadBinaryWithFetch(url, blob, contentType);
  } catch (error) {
    console.warn(`fetch upload failed, retrying with XHR: ${error.message}`);
    return uploadBinaryWithXhr(url, blob, contentType);
  }
}

async function uploadBinaryWithFetch(url, body, contentType) {
  let response;
  try {
    let headers = await binaryUploadHeaders(contentType);
    response = await fetch(url, {
      method: "POST",
      credentials: "same-origin",
      headers,
      body,
    });
```

서버 쪽 Express 경로는 `cap/srv/lib/binary-upload-route.js`에 등록되어 있다.

```js
function mountBinaryUploadRoute(app, middlewares = cds.middlewares) {
  const before = (middlewares.before || []).flat().filter(Boolean);
  app.post(
    "/api-binary/Meetings/:meetingId/audio",
    ...before,
    handleBinaryAudioUpload,
  );
}
```

### 5. 경계

브라우저 `Blob` → HTTP request stream → CAP Express route → Object Store 또는 DB `LargeBinary` 경계다. 이 경로가 Base64 JSON 변환을 피하는 핵심이다.

### 6. 반환을 받는 코드

업로드 응답이 성공해야 `uploadCapAudio()`의 Promise가 끝난다. 실패하면 XHR로 한 번 더 시도하거나 오류가 `createJob()`까지 올라간다.

### 7. 다음 단계

`createJob()`은 업로드 완료 뒤에만 `enqueueTranscription` action을 호출한다.

## 3단계. UI가 CAP action으로 전사 큐 등록을 요청한다

### 1. 이 단계가 하는 일

“오디오가 있으니 이 회의를 전사하라”는 제어 요청을 JSON action으로 보낸다.

### 2. 실제 호출자 코드

`app/meeting-ui/js/api.js`:

```js
await uploadCapAudio(meetingId, blob, ext);
await postAction("enqueueTranscription", { meetingId });
return meetingId;
```

### 3. 전달되는 값과 상태

body는 `{ meetingId }` 하나다. 오디오 데이터는 이 요청에 다시 넣지 않는다.

### 4. 실제 피호출자 코드

같은 파일의 action 공통 호출 함수:

```js
async function postAction(action, body) {
  return requestJson(`/api/${action}`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(body || {}),
  });
}
```

CAP의 `cap/srv/meeting-service.js`가 action을 받는다.

```js
this.on("enqueueTranscription", async (req) => {
  const { meetingId } = req.data;
  if (!meetingId) return req.error(400, "meetingId is required");

  const meeting = await assertEditableMeeting(req, meetingId);
  return queueMeetingTranscription(req, meeting);
});
```

### 5. 경계

브라우저 → `/api/enqueueTranscription` HTTP → CAP action handler 경계다. `assertEditableMeeting()`에서 현재 사용자에게 수정 권한이 있는지도 다시 검사한다.

### 6. 반환을 받는 코드

handler는 `queueMeetingTranscription()`이 반환하는 최신 `Meetings` 행을 action 응답으로 돌려준다. UI는 응답 본문보다 action 성공 여부를 기다린 뒤 `meetingId`를 반환한다.

### 7. 다음 단계

`queueMeetingTranscription()`이 DB 상태와 dispatch 레코드를 만든다.

## 4단계. CAP가 작업 상태와 `TranscriptionDispatches`를 DB에 저장한다

### 1. 이 단계가 하는 일

오디오가 실제 존재하는지 확인하고, 이전 결과를 지운 뒤 회의를 `queued`로 만들고 내구성 있는 dispatch 행을 생성한다.

### 2. 실제 호출자 코드

```js
const meeting = await assertEditableMeeting(req, meetingId);
return queueMeetingTranscription(req, meeting);
```

### 3. 전달되는 값과 상태

- `req`: 현재 인증 사용자와 transaction lifecycle
- `meeting`: 권한 검사를 통과한 `Meetings` 행

### 4. 실제 피호출자 코드

`cap/srv/meeting-service.js`:

```js
async function queueMeetingTranscription(req, meeting) {
  const meetingId = meeting.ID;
  const audio = await SELECT.one.from(AudioObjects).where({ meeting_ID: meetingId });
  if (!audio) return req.error(409, "audio must be uploaded before transcription can be queued");

  await DELETE.from(Transcripts).where({ meeting_ID: meetingId });
  await DELETE.from(Summaries).where({ meeting_ID: meetingId });
  await DELETE.from(ReviewItems).where({ meeting_ID: meetingId });
  await UPDATE(Meetings, meetingId).set({
    status: STATUS.QUEUED,
    percent: 10,
    error: null,
  });
  await createTranscriptionDispatch(cds, {
    meetingId,
    expectedDurationSec: meeting.durationSec,
    minSpeakers: meeting.minSpeakers,
    maxSpeakers: meeting.maxSpeakers,
    diarize: normalizeDiarize(meeting.diarize),
    whisperModelSize: normalizeWhisperModelSize(meeting.whisperModelSize),
  });

  req.on("succeeded", () => {
    processTranscriptionDispatchQueue(cds, dispatchTranscription).catch((error) => {
      console.error("transcription dispatch wakeup failed", error);
    });
  });

  return SELECT.one.from(Meetings).where({ ID: meetingId });
}
```

`cap/srv/lib/transcription-dispatcher.js`의 저장 코드:

```js
async function createTranscriptionDispatch(cds, {
  meetingId,
  expectedDurationSec,
  minSpeakers,
  maxSpeakers,
  diarize,
  whisperModelSize,
}) {
  const { TranscriptionDispatches } = cds.entities("meeting.whisper");
  const payload = {
    meetingId,
    expectedDurationSec: positiveNumberOrNull(expectedDurationSec),
    minSpeakers,
    maxSpeakers,
    diarize,
    whisperModelSize,
  };
  const capInternalBaseUrl = capInternalBaseUrlForWorker();
  if (capInternalBaseUrl) payload.capInternalBaseUrl = capInternalBaseUrl;

  await DELETE.from(TranscriptionDispatches).where({ meeting_ID: meetingId });
  await INSERT.into(TranscriptionDispatches).entries({
    ID: cds.utils.uuid(),
    meeting_ID: meetingId,
    status: DISPATCH_STATUS.QUEUED,
    attempts: 0,
    maxAttempts: getMaxAttempts(),
    nextAttemptAt: nowIso(),
    workerRunId: null,
    workerStage: null,
    workerHeartbeatAt: null,
    workerMessage: null,
    payload: JSON.stringify(payload),
    lastError: null,
  });
}
```

### 5. 경계

CAP 메모리 → DB 경계다.

- `Meetings`: 사용자에게 보이는 업무 상태 (`queued`, 10%)
- `TranscriptionDispatches`: Worker 전달 재시도 상태와 payload
- `AudioObjects`: 전사할 오디오의 위치와 메타데이터

### 6. 반환을 받는 코드

DB transaction이 성공하면 `req.on("succeeded")` 콜백이 dispatch queue를 즉시 깨운다. CAP는 동시에 주기적 dispatcher도 두므로 프로세스 재시작이나 일시적 실패 뒤에도 DB의 queued 행을 다시 찾을 수 있다.

### 7. 다음 단계

`processTranscriptionDispatchQueue()`가 due 상태인 행을 `dispatchOne()`으로 넘긴다.

## 5단계. Dispatcher가 DB 행을 Worker HTTP 요청으로 바꾼다

### 1. 이 단계가 하는 일

queued 행 하나에 새로운 `workerRunId`를 부여하고 Worker의 `/transcribe`에 전달한다.

### 2. 실제 호출자 코드

`cap/srv/lib/transcription-dispatcher.js`:

```js
const dueRows = (await SELECT.from(TranscriptionDispatches)
  .where({ status: DISPATCH_STATUS.QUEUED })
  .orderBy("createdAt")
  .limit(effectiveLimit * 3))
  .filter((row) => isDue(row.nextAttemptAt))
  .slice(0, effectiveLimit);

for (const row of dueRows) {
  await dispatchOne(cds, dispatchTranscription, row);
}
```

### 3. 전달되는 값과 상태

- `row.payload`: 회의 ID, 예상 길이, STT 옵션, 내부 CAP URL
- `workerRunId`: 이번 시도만 식별하는 새 UUID
- dispatch 상태: `queued` → `dispatching`

### 4. 실제 피호출자 코드

```js
async function dispatchOne(cds, dispatchTranscription, row) {
  const { Meetings, TranscriptionDispatches } = cds.entities("meeting.whisper");
  const attempts = Number(row.attempts || 0) + 1;
  const maxAttempts = Number(row.maxAttempts || getMaxAttempts());
  const workerRunId = cds.utils.uuid();
  const dispatchStartedAt = nowIso();

  await UPDATE(TranscriptionDispatches, row.ID).set({
    status: DISPATCH_STATUS.DISPATCHING,
    attempts,
    lastAttemptAt: dispatchStartedAt,
    lockedAt: dispatchStartedAt,
    workerRunId,
    workerStage: "dispatching",
    workerHeartbeatAt: dispatchStartedAt,
    workerMessage: "Dispatching transcription job to worker",
    lastError: null,
  });

  try {
    const payload = { ...JSON.parse(row.payload || "{}"), workerRunId };
    if (!positiveNumberOrNull(payload.expectedDurationSec)) {
      const meeting = await SELECT.one.from(Meetings)
        .columns("durationSec")
        .where({ ID: row.meeting_ID });
      payload.expectedDurationSec = positiveNumberOrNull(meeting?.durationSec);
    }
    const result = await dispatchTranscription(payload);
```

실제 HTTP client인 `cap/srv/lib/worker-client.js`:

```js
async function enqueueTranscription(payload) {
  const workerUrl = process.env.TRANSCRIPTION_WORKER_URL;
  if (!workerUrl) return { ...payload, dispatched: false };

  const endpoint = new URL("/transcribe", workerUrl);
  const controller = new AbortController();
  const timeoutMs = getWorkerTimeoutMs();
  const timeout = setTimeout(() => controller.abort(), timeoutMs);

  const headers = { "content-type": "application/json" };
  const token = workerToken();
  if (token) headers.authorization = `Bearer ${token}`;

  let response;
  try {
    response = await fetch(endpoint, {
      method: "POST",
      headers,
      body: JSON.stringify(payload),
      signal: controller.signal,
    });
```

### 5. 경계

CAP DB/Node 프로세스 → 내부 HTTP → Python Worker 경계다. Worker dispatch token은 header에 붙지만 문서에는 실제 값이 아니라 코드 구조만 인용했다.

### 6. 반환을 받는 코드

Worker의 202 JSON을 받으면 client가 다음처럼 반환한다.

```js
return { ...(await response.json()), dispatched: true };
```

그 결과를 받은 dispatcher는 `TranscriptionDispatches`를 `dispatched`, stage를 `accepted`로 바꾼다. 429면 시도 횟수를 소모하지 않고 queued로 되돌리고, 다른 오류는 backoff 후 재시도하며 최대 횟수 뒤 `failed`가 된다.

### 7. 다음 단계

Python Worker의 `/transcribe` endpoint가 요청을 검증하고 CAP에 claim을 건다.

## 6단계. Worker가 먼저 CAP에 `claimTranscription`을 호출한다

### 1. 이 단계가 하는 일

Worker가 단순히 요청만 받았다는 이유로 작업을 시작하지 않고, 현재 run이 아직 유효하고 오디오도 살아 있는지 CAP에 확인받는다.

### 2. 실제 호출자 코드

`workers/transcription/app/main.py`:

```python
@app.post("/transcribe", status_code=202)
async def transcribe(
    payload: TranscriptionRequest,
    background_tasks: BackgroundTasks,
    authorization: str | None = Header(default=None),
):
    if not payload.meeting_id.strip():
        raise HTTPException(status_code=400, detail="meetingId is required")

    settings = get_settings()
    if payload.cap_internal_base_url:
        settings = settings.model_copy(update={
            "cap_internal_base_url": payload.cap_internal_base_url.rstrip("/"),
        })
    if _worker_dispatch_token_required(settings) and not _clean_token(settings.transcription_worker_token):
        raise HTTPException(status_code=503, detail="worker dispatch token is not configured")
    _verify_worker_dispatch_token(settings.transcription_worker_token, authorization)
    if not settings.cap_internal_base_url:
        raise HTTPException(status_code=503, detail="CAP_INTERNAL_BASE_URL is not configured")

    if _transcription_slots.locked():
        raise HTTPException(
            status_code=429,
            detail="worker is busy; retry transcription dispatch later",
        )
    await _transcription_slots.acquire()
    try:
        async with CAPClient(settings) as cap:
            await cap.claim_transcription(payload.meeting_id, payload.worker_run_id)
```

### 3. 전달되는 값과 상태

- `meetingId`
- `workerRunId`
- Worker→CAP 인증은 `CAPClient` 내부 토큰 방식으로 처리된다.

### 4. 실제 피호출자 코드

`workers/transcription/app/cap_client.py`:

```python
async def claim_transcription(self, meeting_id: str, worker_run_id: str | None = None) -> dict[str, Any]:
    return await self._post_action("claimTranscription", {
        "meetingId": meeting_id,
        "workerRunId": worker_run_id,
    })
```

CAP `cap/srv/worker-internal-service.js`:

```js
this.on("claimTranscription", async (req) => {
  const { meetingId, workerRunId } = req.data;
  if (!meetingId) return req.error(400, "meetingId is required");

  const meeting = await SELECT.one.from(Meetings).where({ ID: meetingId });
  if (!meeting) return req.error(404, "meeting not found");
  await assertCurrentWorkerRun(req, meetingId, workerRunId);

  const audio = await SELECT.one.from(AudioObjects)
    .columns("ID", "mimeType", "size", "storageKind", "objectKey", "expiresAt")
    .where({ meeting_ID: meetingId });
  if (!audio) return req.error(409, "audio is required before transcription can start");
  if (isExpired(audio.expiresAt)) {
    await deleteAudioForMeeting(meetingId);
    await UPDATE(Meetings, meetingId).set({
      status: STATUS.FAILED,
      error: "audio expired before transcription started",
    });
    return req.error(410, "audio expired before transcription started");
  }

  await UPDATE(Meetings, meetingId).set({
    status: STATUS.TRANSCRIBING,
    percent: 20,
    error: null,
  });
  await updateWorkerHeartbeat(meetingId, workerRunId, {
    stage: "claimed",
    message: "Worker claimed transcription job",
    percent: 20,
  });
  return SELECT.one.from(Meetings).where({ ID: meetingId });
});
```

### 5. 경계

Worker → CAP internal service HTTP → DB 경계다. `assertCurrentWorkerRun()` 덕분에 오래된 재시도 Worker가 최신 실행 결과를 덮어쓰지 못한다.

### 6. 반환을 받는 코드

claim이 성공한 뒤에만 Worker가 background task를 등록하고 202를 반환한다.

```python
background_tasks.add_task(_run_transcription_job, payload, settings)
return {
    "accepted": True,
    "meetingId": payload.meeting_id,
    "capConfigured": True,
    "transcriptQueued": True,
}
```

### 7. 다음 단계

HTTP 응답과 분리된 `_run_transcription_job()`이 `_process_transcription()`을 실행한다.

## 7단계. Background task가 오디오를 받아 STT 함수로 넘긴다

### 1. 이 단계가 하는 일

CAP에서 오디오 접근 정보를 받고, Worker의 임시 파일을 만든 뒤 전사 함수에 진입한다.

### 2. 실제 호출자 코드

`workers/transcription/app/main.py`:

```python
async def _process_transcription(payload: TranscriptionRequest, settings: Settings) -> None:
    async with CAPClient(settings) as cap:
        try:
            await _send_heartbeat(
                cap,
                payload.meeting_id,
                payload.worker_run_id,
                stage="downloading",
                message="Downloading audio for transcription",
                percent=25,
            )
            audio = await cap.get_audio(payload.meeting_id)
            await _send_heartbeat(
                cap,
                payload.meeting_id,
                payload.worker_run_id,
                stage="transcribing",
                message="Transcription is running",
                percent=30,
            )
            transcript = await _build_transcript_with_heartbeat(payload, audio, settings, cap)
```

### 3. 전달되는 값과 상태

- `payload`: meeting/run ID와 STT 옵션
- `audio`: Object Store이면 다운로드 URL, DB fallback이면 Base64 content
- heartbeat: `downloading` 25% → `transcribing` 30%

### 4. 실제 피호출자 코드

Worker client:

```python
async def get_audio(self, meeting_id: str) -> dict[str, Any]:
    return await self._post_action("getAudio", {"meetingId": meeting_id})
```

CAP `getAudio` handler:

```js
this.on("getAudio", async (req) => {
  const { meetingId } = req.data;
  if (!meetingId) return req.error(400, "meetingId is required");

  const audio = await SELECT.one.from(AudioObjects)
    .columns("ID", "mimeType", "size", "storageKind", "objectKey", "content", "expiresAt")
    .where({ meeting_ID: meetingId });
  if (!audio) return req.error(404, "audio not found");
  if (isExpired(audio.expiresAt)) {
    await deleteAudioForMeeting(meetingId);
    await UPDATE(Meetings, meetingId).set({
      status: STATUS.FAILED,
      error: "audio expired before transcription started",
    });
    return req.error(410, "audio expired before transcription started");
  }
  const payload = await audioPayloadForWorker(audio, meetingId);
  if (payload.storageKind === "db") {
    payload.contentBase64 = await toBase64Content(payload.content);
    delete payload.content;
  }
  return payload;
});
```

### 5. 경계

- 정상 배포 주 경로: Object Store → signed download URL → Worker HTTP download → 임시 파일
- DB fallback: DB `LargeBinary` → CAP Base64 응답 → Worker decode → 임시 파일

따라서 Base64는 완전히 사라진 것이 아니라, Object Store를 쓰지 못하는 fallback에서만 남아 있다.

### 6. 반환을 받는 코드

`audio = await cap.get_audio(...)`가 payload를 받고 `_build_transcript_with_heartbeat(...)`에 넘긴다. 여기서부터 실제 STT 처리가 시작된다.

## 전체 상태 변화 요약

| 시점 | `Meetings.status` | `percent` | 영속 위치 |
|---|---|---:|---|
| 메타데이터 생성 | `created` | 0 | `Meetings` |

| STT 시작 | `transcribing` | 30 이상 | Worker process |

## 다시 기억할 핵심

> 회의 종료 요청 하나 안에서 STT를 끝까지 수행하지 않는다. 브라우저는 회의 행 생성 → raw binary 업로드 → dispatch 행 생성까지만 순서대로 요청한다. CAP는 DB에 남긴 dispatch를 Worker로 전달하고, Worker는 다시 CAP에서 현재 run과 오디오를 확인한 뒤 background task로 실제 STT에 들어간다. `TranscriptionDispatches`와 `workerRunId`가 재시도와 오래된 실행 방지를 담당한다.
