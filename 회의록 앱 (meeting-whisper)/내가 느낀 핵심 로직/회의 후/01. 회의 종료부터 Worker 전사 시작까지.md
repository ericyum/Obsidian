# 회의 종료부터 Worker 전사 시작까지

## 이 문서의 질문

사용자가 회의를 끝낸 뒤 완성된 음성이 어디에 저장되고, 어떤 상태와 큐를 거쳐 STT Worker가 실제 전사를 시작하는가?

## 먼저 기억할 결론

회의 종료 후에는 “서버에 음성 하나를 올리고 곧바로 같은 요청에서 전사”하지 않는다. 세 개의 영속 상태와 별도 Worker 사이를 단계적으로 이동한다.

```text
Meetings              회의의 사용자용 상태
AudioObjects/Object Store  전사할 원본 음성
TranscriptionDispatches    Worker 전달을 재시도할 내구성 큐
```

```mermaid
flowchart LR
    UI["최종 음성 Blob"] --> M["1. Meetings 생성"]
    M --> A["2. /api-binary 원시 음성 업로드"]
    A --> Q["3. TranscriptionDispatches 생성"]
    Q --> D["CAP Dispatcher"]
    D --> W["Worker /transcribe"]
    W --> C["CAP claimTranscription"]
    C --> G["CAP getAudio"]
    G --> T["Worker 임시 파일"]
    T --> STT["STT 시작"]
```

## 1. 첫 단계: `Meetings` 행을 만든다

UI의 `createJob()`은 먼저 `POST /api/Meetings`를 호출한다. 본문에는 제목, 카테고리, 참석자, 공유자, 녹음 시간 등이 들어간다.

CAP의 `before CREATE` hook은 소유자를 현재 JWT 사용자로 강제하고, 접근 토큰과 기본 상태를 만든다. 이 시점의 상태는 `created`, 진행률은 `0`이다.

회의 행과 음성은 한 테이블의 같은 필드가 아니다. `Meetings`는 메타데이터와 처리 상태이고, 음성은 별도 `AudioObjects` 또는 Object Store에 저장된다.

## 2. 두 번째 단계: 원시 바이너리 경로로 음성을 올린다

브라우저는 다음 경로에 Blob 자체를 POST한다.

```text
/api-binary/Meetings/{meetingId}/audio
```

이 경로는 CAP 서비스 action의 JSON `LargeBinary` 경로가 아니라 `server.js`의 bootstrap 시점에 Express 앱에 등록된 원시 HTTP 경로다. `binary-upload-route.js`는 CAP의 공통 before middleware를 먼저 거쳐 인증 문맥을 만든 뒤 다음을 검사한다.

- 익명 사용자가 아닌가
- `MeetingUser` 역할이 있는가
- 해당 회의의 소유자이거나 관리자인가
- 선언된 크기와 실제 스트림이 최대 크기를 넘지 않는가

그 뒤 요청 스트림을 `saveAudioStreamForMeeting()`으로 넘긴다.

### 배포 환경의 저장

`mta.yaml`은 `OBJECT_STORE_ENABLED: true`이고 Object Store 서비스를 CAP에 연결한다. Content-Length가 있으면 요청 스트림을 64KiB 단위로 제한하면서 Object Store에 넘기므로 전체 파일을 Base64 문자열로 만들거나 CAP 메모리에 한꺼번에 펼칠 필요가 없다.

HANA의 `AudioObjects`에는 다음 메타데이터가 남는다.

- `storageKind = object_store`
- Object Store의 `objectKey`
- MIME type과 byte 크기
- 만료 시각
- `content = null`

Object Store가 꺼져 있거나 스트리밍 조건을 충족하지 못한 개발 경로에서는 최대 크기를 검사하며 Buffer로 모은 뒤 `AudioObjects.content`의 `LargeBinary`에 저장한다. 따라서 DB 바이너리 저장은 fallback이고, 현재 배포의 주 경로는 Object Store다.

업로드가 성공하면 `Meetings.status = audio_uploaded`, `percent = 5`가 된다.

## 3. 세 번째 단계: 전사 큐를 만든다

음성 업로드가 끝나면 UI는 `enqueueTranscription` action을 호출한다. CAP는 먼저 AudioObjects가 있는지 확인한다. 음성이 없으면 큐 등록을 거부한다.

정상일 때는 다음을 수행한다.

1. 이전 전사·요약·검토 후보 삭제
2. 회의 상태를 `queued`, 진행률을 `10`으로 변경
3. 기존 dispatch 행 삭제
4. 새 `TranscriptionDispatches` 행 삽입

dispatch payload에는 다음 값이 JSON으로 들어간다.

- meeting ID
- 기대 녹음 길이
- 화자 수 범위
- 화자 분리 여부
- Whisper 모델 크기
- 필요하면 Worker가 CAP 내부 API로 돌아올 base URL

이 행이 중요한 이유는 Worker HTTP 호출이 잠깐 실패해도 작업 의도를 DB에 남겨 재시도할 수 있기 때문이다.

## 4. CAP Dispatcher가 Worker를 깨운다

큐 등록 transaction이 성공하면 즉시 처리 함수를 한 번 깨운다. 동시에 서비스 시작 때 등록된 주기적 dispatcher도 기본 5초 간격으로 queued 행을 찾는다.

한 건을 보낼 때 다음이 일어난다.

1. 시도 횟수 증가
2. 새 `workerRunId` UUID 생성
3. dispatch 상태를 `dispatching`으로 바꾸고 잠금·heartbeat 기록
4. Worker의 `/transcribe`에 JSON과 Bearer dispatch token 전송
5. Worker가 202를 반환하면 `dispatched`, `accepted` 상태 기록

Worker가 429 Busy를 반환하면 시도 횟수를 소모하지 않고 queued로 되돌려 나중에 다시 보낸다. 다른 오류는 지수 backoff로 재시도하며 기본 최대 5회 이후 회의를 `failed`로 만든다.

`workerRunId`는 오래된 Worker 응답이 최신 재시도 결과를 덮어쓰지 못하게 하는 실행 세대 번호다. CAP 내부 action들은 현재 dispatch의 ID와 Worker가 보내온 ID가 다르면 `stale worker run ignored`로 거절한다.

## 5. Worker가 202를 반환하기 전에 하는 일

Worker의 `/transcribe` endpoint는 단순히 무조건 작업을 받지 않는다.

- meeting ID 확인
- Worker dispatch token 검증
- CAP 내부 base URL 확인
- 동시 실행 semaphore에 빈 자리가 있는지 확인
- CAP의 `claimTranscription` 호출

CAP의 claim은 회의, 현재 run ID, 음성 존재 여부와 만료 여부를 확인한다. 성공하면 회의 상태를 `transcribing`, 진행률을 `20`으로 바꾸고 Worker stage를 `claimed`로 남긴다. 그 뒤 Worker가 background task를 등록하고 202 Accepted를 CAP Dispatcher에 반환한다.

즉 Worker가 202를 반환했다는 것은 “전사가 완료됨”이 아니라 “실행 슬롯을 확보했고 CAP에서 이 작업을 현재 run으로 claim했음”을 뜻한다.

## 6. Worker가 음성을 받는 방법

background task가 시작되면 Worker는 heartbeat를 보내고 CAP의 `getAudio` 내부 action을 호출한다.

- Object Store 음성: CAP가 짧게 유효한 signed download URL을 반환
- DB 음성: CAP가 Base64 `contentBase64`로 변환해 반환

현재 배포 경로는 Object Store이므로 Worker가 signed URL에서 스트리밍 다운로드하여 `/tmp/meeting-whisper-worker` 아래 임시 파일로 저장한다. MIME type과 실제 파일 signature를 보고 `.webm`, `.mp4`, `.mp3`, `.wav` 등의 확장자를 정리한다.

이 임시 파일을 만든 뒤에야 `run_transcription()`을 별도 thread에서 호출한다. 전사 완료나 실패 여부와 관계없이 Worker의 임시 파일은 `finally`에서 삭제된다.

## 7. 진행률과 heartbeat의 의미

대략적인 상태 흐름은 다음과 같다.

| 진행률 | 상태/단계 | 의미 |
|---:|---|---|
| 0 | created | 회의 행만 생성 |
| 5 | audio_uploaded | 음성 저장 완료 |
| 10 | queued | dispatch 큐 등록 |
| 20 | claimed/transcribing | Worker가 현재 run을 claim |
| 25 | downloading | Worker가 음성 받는 중 |
| 30~74 | transcribing | 청크 진행률에 따라 heartbeat |
| 75 | saving | 전사문을 CAP에 저장하는 중 |
| 80 | summarizing | 전사 저장 완료, 요약 작업 시작 |
| 100 | done | 요약까지 완료 또는 요약 실패 상태 기록 |

heartbeat는 처리 중인 Worker가 살아 있음을 운영 상태에 남기는 기능이다. 작업 결과 자체는 아니며, stale 판단과 사용자 진행 메시지에 사용된다.

## 8. 음성은 영구 보관이 목적이 아니다

업로드된 음성에는 만료 시각이 있다. 전사 시작 전에 만료되면 CAP가 음성을 삭제하고 회의를 실패 처리한다.

정상 전사 후에는 CAP가 전사문을 저장하고 요약을 비동기로 생성한다. `startWorkerSummaryTask()`의 `finally`에서 요약 성공 여부와 관계없이 `deleteAudioForMeeting()`을 호출한다. UI가 중지 직후 로컬 백업 여부를 묻는 이유도 여기에 있다.

따라서 최종 산출물은 전사문과 요약이며, 서버 음성은 처리용 임시 자산에 가깝다.

## 내가 기억할 핵심

> 중지 후에는 Meetings 생성 → 원시 바이너리 음성 저장 → TranscriptionDispatches 큐 생성의 세 단계가 있고, CAP Dispatcher가 runId와 재시도 상태를 관리해 Worker를 호출한다. Worker는 claim 후 Object Store signed URL로 음성을 임시 파일에 받아야 비로소 STT를 시작한다.
