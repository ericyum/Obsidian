# STT 응답 검증·재시도·병합과 후처리

## 이 문서의 질문

STT 모델이 텍스트를 반환한 뒤 어떤 후처리가 있으며, 잘못된 JSON이나 타임스탬프는 어떻게 고치거나 거부하는가? 맞춤법·문장 교정 같은 별도 모델 후처리도 있는가?

## 먼저 기억할 결론

STT 뒤에는 상당한 **구조적 후처리와 3중 검증**이 있다. 그러나 맞춤법·고유명사·문맥 오류를 고치는 별도의 의미적 후처리 모델은 없다.

```text
모델 응답
  → Python 파싱·정규화
  → 실패 시 오류를 프롬프트에 넣어 재시도
  → 계속 실패하면 더 작은 음성 청크로 재귀 분할
  → 청크 시간 보정·병합
  → Worker 저장 직전 재검증
  → CAP 저장 직전 재검증
  → Transcripts 저장
```

이 과정의 목적은 “내용을 더 자연스럽게 고치기”보다 “저장 가능한 전사 JSON인지 보장하기”에 가깝다.

## 1. 모델 응답에서 텍스트를 꺼낸다

AI Core 응답 구조가 배포나 모델에 따라 조금 다를 수 있어 다음 후보에서 첫 message content를 찾는다.

- `final_result.choices[0].message.content`
- `choices[0].message.content`
- `module_results.llm.choices[0].message.content`

content가 문자열이면 그대로 사용하고, 멀티파트 배열이면 각 항목의 `text` 또는 `content`를 줄바꿈으로 합친다.

## 2. JSON fence를 벗기고 완전한 객체인지 확인한다

응답 전체가 다음처럼 코드 fence로 둘러싸였으면 fence만 제거한다.

````text
```json
{ ... }
```
````

그 뒤 `json.loads()`를 수행하며, 결과가 객체가 아니면 실패한다. `segments`가 배열이 아니어도 실패한다.

모델이 JSON 전체를 segment 하나의 `text` 안에 다시 문자열로 넣는 잘못된 중첩 응답도 탐지한다. `{`로 시작하고 앞부분에 `"segments"`가 보이는 raw JSON text는 거부한다.

## 3. 각 segment를 정규화한다

각 segment에 대해 다음 순서로 처리한다.

1. JSON 객체가 아니면 실패
2. `text`를 문자열로 만들고 앞뒤 공백 제거
3. 빈 text이면 그 segment는 건너뜀
4. `start`, `end`를 float로 변환
5. Boolean, NaN, Infinity, 음수는 거부
6. `end < start`이면 거부
7. 앞 segment보다 start가 0.25초 이상 뒤로 이동하면 거부
8. 시간을 소수점 3자리로 반올림
9. `speaker` 값은 보존
10. `words`는 빈 배열로 설정

AI Core STT의 출력은 segment 수준 전사이므로 단어별 timestamp를 새로 만들지 않는다.

## 4. 음성 길이를 크게 넘는 타임스탬프를 검사한다

모델에 알려 준 청크 길이가 있으면 허용 오차를 다음처럼 둔다.

```text
max(5초, 음성 길이의 2%)
```

이 범위를 넘는 시간이 있으면 일반적으로 오류다. 다만 모델이 `4분 2.5초`를 `402.5`처럼 compact MMSS 숫자로 잘못 쓴 패턴이 명확할 때만 자동 수리를 시도한다.

### compact MMSS 자동 수리 조건

예를 들어 `402.5`는 4분 2.5초, 즉 242.5초로 변환할 수 있다. 그러나 숫자 하나만 보고 항상 변환하면 실제 402.5초를 잘못 고칠 수 있다. 그래서 코드가 전체 타임라인에서 분 경계를 건너는 일관된 패턴을 최소 두 번 확인한다.

- 초 부분이 60 미만이어야 함
- 변환 후 시간 흐름이 자연스러워야 함
- 최소 2개의 강한 분 경계 증거가 있어야 함
- 변환 후에도 단조 증가하고 음성 범위 안이어야 함

조건이 모호하면 추측해 고치지 않고 응답을 거부한다. 이것은 의미 교정이 아니라 특정 숫자 형식 오류의 제한적 수리다.

## 5. 첫 검증 실패는 같은 음성을 재호출한다

정규화 중 `TranscriptionResponseError`가 발생하면 최대 2회 설정 안에서 재시도한다. 두 번째 프롬프트에는 실제 오류가 들어간다.

예:

```text
response was not a complete JSON object
segment 3 timestamp moved backwards from 14 to 9
segment 5 timestamp exceeded audio duration
```

따라서 재시도는 단순히 같은 요청을 반복하는 것이 아니라 실패 이유를 모델에 알려 형식 오류를 고치게 한다.

HTTP 4xx/5xx는 이 JSON 검증 재시도와 다르다. 현재 함수는 AI Core HTTP 오류를 즉시 RuntimeError로 올린다. 여기서 설명한 2회 재시도는 정상 HTTP 응답이지만 전사 JSON이 쓸 수 없을 때의 로직이다.

## 6. 계속 실패하면 더 작은 음성으로 재귀 분할한다

청크가 두 번의 모델 응답 후에도 유효하지 않으면 그 청크 길이의 절반으로 다시 자른다. 단 새 목표 길이는 최소 60초다.

```text
720초 실패 → 360초 두 조각
360초 조각 실패 → 180초 두 조각
180초 조각 실패 → 90초 두 조각
90초 조각 실패 → 60초 안팎 조각
60초 이하도 실패 → 최종 실패
```

새 하위 청크의 시작·끝은 부모 청크의 원본 시작 위치를 더해 보존한다. 그래서 재귀 분할되어도 최종 병합 시 원본 회의 시간축으로 되돌릴 수 있다.

## 7. 청크들을 원본 시간축으로 병합한다

각 모델 응답은 현재 청크 기준의 상대 timestamp다. 병합할 때 다음 계산을 한다.

```text
원본 start = chunk.start_sec + segment.start
원본 end   = chunk.start_sec + segment.end
```

병합 중에도 다시 다음을 확인한다.

- 빈 text 제거
- `end >= start`
- 전체 start의 단조 증가
- segment text 안의 raw transcript JSON 금지
- 3자리 반올림

완료된 객체에는 `language`, `segments`, `engine=aicore`, 모델명과 함께 `chunked=true`, `chunk_count`가 붙는다.

현재 청크는 겹치지 않게 자르며, 병합 코드에는 문장 유사도를 이용한 중복 제거가 없다. 따라서 “오버랩 청크의 중복 문장을 지우는 의미적 병합”은 현재 로직에 없다. 단순히 시간 오프셋을 더하고 순서대로 연결한다.

## 8. Worker가 저장 직전에 두 번째 검증을 한다

전체 transcript가 만들어지면 Worker의 `_validate_transcript_for_storage()`가 다시 검사한다.

- 객체와 segments 배열인지
- 실제 텍스트 segment가 하나 이상인지
- raw JSON이 text 안에 들어가지 않았는지
- 시간들이 유한한 비음수인지
- end가 start보다 빠르지 않은지
- 시간이 뒤로 움직이지 않는지
- 기대 회의 길이보다 지나치게 크지 않은지

이 단계의 길이 허용 오차는 `max(30초, 전체 길이의 5%)`로 앞의 청크 검증보다 넓다. 최종 원본 회의 시간축을 검사하는 방어선이다.

## 9. CAP가 저장 직전에 세 번째 검증을 한다

Worker는 전사 JSON을 문자열로 만들어 CAP의 내부 `saveTranscript` action에 보낸다. CAP의 `validateTranscriptContent()`는 다시 JSON 파싱, segment 구조, raw JSON text, 시간 순서와 전체 길이를 검사한다.

실패하면 422 `invalid transcript rejected`를 반환하고 DB에 넣지 않는다. 정상일 때만 기존 `Transcripts`를 지우고 새 행을 저장한다.

사용자가 나중에 UI에서 전사문을 직접 고쳐 저장할 때도 같은 CAP validator를 거친다. 즉 Worker 결과뿐 아니라 사용자 수정 결과도 최소 구조를 유지해야 한다.

## 10. 있는 후처리와 없는 후처리

### 실제로 있는 것

- Markdown JSON fence 제거
- JSON 파싱 및 schema에 가까운 구조 검사
- 공백 trim과 빈 segment 제거
- 숫자 timestamp 변환·반올림
- 제한적인 compact MMSS 수리
- 잘못된 응답에 오류 피드백을 넣은 모델 재호출
- 실패 청크 재귀 분할
- 청크 원본 시간 오프셋 복원
- Worker와 CAP의 중복 검증

### 현재 없는 것

- 별도 LLM을 이용한 맞춤법·띄어쓰기 교정
- 고유명사 사전 기반 STT 교정
- 회의 중 임시 전사와 최종 전사의 병합
- 전사 문장 유사도 기반 중복 제거
- 참석자 이름을 이용한 speaker 자동 명명
- 최종 전사 전체를 다시 읽는 “후처리 프롬프트”

요약 뒤의 검토 후보 모델은 전사 후처리가 아니다. 현재 그 모델은 전사문이 아니라 **요약본만** 보고 사람이 확인할 용어 후보를 제시한다.

## 내가 기억할 핵심

> STT 후처리는 JSON·segment·timestamp를 안전하게 만들고 실패 청크를 다시 처리하는 구조적 파이프라인이다. 제한적인 MMSS 수리는 있지만 맞춤법이나 고유명사를 자동 교정하는 별도 모델 단계는 없으며, 최종 내용 오류는 전사문 수동 수정 또는 요약 검토 후보 기능에서 사람이 다룬다.
