# 검토 후보 프롬프트와 사용자 수정 반영 — 실제 코드 워크스루

## 먼저 가장 중요한 구분

이 앱의 “검토 후보 생성”은 전체 전사를 다시 검토하지 않는다. **저장된 요약 회의록(`Summaries.content`)만 LLM에 보낸다.** 후보 적용도 transcript가 아니라 요약 note 안의 문자열을 교체한다.

```text
검토 후보 생성 버튼
  → runReview CAP action
  → Summaries.content 읽기
  → reviewMeeting({ note })
  → AI Core direct prompt
  → REVIEW_SCHEMA 검증
  → note에 실제 존재하는 짧은 text만 최대 12개 유지
  → ReviewItems 저장
  → UI에 후보 표시
  → 사용자가 제안 적용/직접 입력/이상 없음
  → note 문자열 교체 또는 후보 제거
  → saveSummary
  → Summaries + 남은 ReviewItems 저장
```

전사문 자체를 편집하는 기능은 별도다. 전사 text를 수정하면 `saveTranscript`로 저장하고 기본적으로 요약과 검토 후보를 지운 뒤 요약을 다시 생성한다.

---

## 1단계. UI의 검토 버튼이 `runReview` action을 호출한다

### 1. 이 단계가 하는 일

사용자가 검토 후보 생성을 요청하면 화면을 pending 상태로 바꾸고 CAP action을 호출한다.

### 2. 실제 호출자 코드

`app/meeting-ui/js/app.js`:

```js
async function generateReviewCandidates() {
  if (!currentJob || !currentTranscript) return;
  if (!currentCanEdit) return;
  if (summaryPending || reviewPending) return;
  try {
    reviewPending = true;
    $("tab-summary").innerHTML = renderInlineSummary(currentNote);
    bindInlineNoteEditor();
    setInlineMessage("검토 후보 생성 중", { busy: true, actionLabel: "검토 중" });
    const job = await runTranscriptReview(currentJob);
    paintResult(job);
    if (job.stage === "reviewing") {
      poll();
      return;
    }
    reviewPending = false;
    if (!job.transcript_review_items?.length) setInlineMessage("검토 완료 · 후보 없음");
  } catch (err) {
    reviewPending = false;
    showResErr(err.message);
    setInlineMessage("검토 후보 생성 실패");
  }
}
```

### 3. 전달되는 값과 상태

UI가 보내는 업무 값은 `meetingId`뿐이다. `currentTranscript` 존재 여부를 UI guard로 확인하지만 transcript 내용 자체를 action body에 넣지는 않는다.

### 4. 실제 피호출자 코드

`app/meeting-ui/js/api.js`:

```js
export async function runTranscriptReview(id) {
  if (useCapApi()) {
    await postAction("runReview", { meetingId: id });
    return capGetJob(id);
  }
  return requestJson(`/api/jobs/${id}/transcript-review`, { method: "POST" });
}
```

### 5. 경계

Browser → `/api/runReview` HTTP → CAP action 경계다.

### 6. 반환을 받는 코드

action 직후 `capGetJob(id)`로 최신 상태를 읽는다. 아직 background task 중이면 `stage === "reviewing"`이라 UI가 `poll()`을 시작한다.

### 7. 다음 단계

CAP가 권한·상태와 summary 존재 여부를 확인하고 background review를 시작한다.

## 2단계. CAP는 transcript가 아니라 `Summaries.content`를 선택한다

### 1. 이 단계가 하는 일

편집 권한을 검사하고, 회의가 다른 AI 작업 중이 아닌지 확인한 뒤 저장된 summary JSON을 review 입력으로 정한다.

### 2. 실제 호출자 코드

위 API가 `POST /api/runReview`를 보낸다.

### 3. 전달되는 값과 상태

- `meetingId`
- 현재 인증 사용자
- `Meetings.status`

### 4. 실제 피호출자 코드

`cap/srv/meeting-service.js`:

```js
this.on("runReview", async (req) => {
  const { meetingId } = req.data;
  if (!meetingId) return req.error(400, "meetingId is required");
  const meeting = await assertEditableMeeting(req, meetingId);
  if (rejectIfMeetingBusy(req, meeting)) return;

  const summaryRow = await SELECT.one.from(Summaries).where({ meeting_ID: meetingId });
  if (!summaryRow) return req.error(409, "summary is required before review can run");

  await UPDATE(Meetings, meetingId).set({
    status: STATUS.REVIEWING,
    percent: 95,
    error: null,
  });

  startBackgroundAiTask("review generation", meetingId, () =>
    generateReviewForMeeting(meetingId, summaryRow.content, {
      actionName: "runReview",
      requestedBy: currentUserId(req),
    }));
  return SELECT.one.from(Meetings).where({ ID: meetingId });
});
```

### 5. 경계

DB `Summaries.content` → CAP memory의 `summaryContent` 경계다. `Transcripts` SELECT가 이 handler에 없다는 것이 “요약만 검토한다”는 직접적인 증거다.

### 6. 반환을 받는 코드

action은 회의를 `reviewing`, 95%로 만든 뒤 바로 최신 Meeting을 반환한다. 실제 LLM 호출은 `startBackgroundAiTask()` 안에서 계속된다.

### 7. 다음 단계

`generateReviewForMeeting()`이 summary JSON을 note object로 바꾸고 `reviewMeeting()`을 호출한다.

## 3단계. note가 검토 prompt와 JSON schema로 조립된다

### 1. 이 단계가 하는 일

요약 note 안에 실제로 등장하는 이름·제품명·기술용어·숫자·날짜·어색한 전사 단어 중 수동 확인할 짧은 후보를 요청한다.

### 2. 실제 호출자 코드

`cap/srv/meeting-service.js`:

```js
async function generateReviewForMeeting(meetingId, summaryContent, usageLog = {}) {
  const note = normalizeNote(JSON.parse(summaryContent || "{}"));
  const items = await reviewMeeting({
    note,
    usageLog: {
      serviceName: "MeetingService",
      actionName: "generateReviewForMeeting",
      meetingId,
      ...usageLog,
    },
  });

  await replaceReviewItemsForMeeting(meetingId, items);

  await UPDATE(Meetings, meetingId).set({
    status: STATUS.DONE,
    percent: 100,
    error: null,
  });
}
```

### 3. 전달되는 값과 상태

여기에는 실제 코드상 주의점이 하나 있다. `reviewMeeting()`은 `participants = []` 인자를 받을 수 있지만, 위 호출은 `participants`를 넘기지 않는다. 따라서 현재 경로의 prompt에는 `Participants: (unknown)`이 들어간다.

### 4. 실제 피호출자 코드 — 검토 prompt 원문

`cap/srv/lib/ai-core.js`:

```js
async function reviewMeeting({ note, participants = [], usageLog }) {
  const fallback = fallbackReviewItems(note);
  if (!hasLlmConfig()) return fallback;

  try {
    const content = await chatJson({
      schemaName: "summary_review",
      schema: REVIEW_SCHEMA,
      messages: [
        {
          role: "system",
          content:
            "Review only the Korean meeting note, not the full transcript. " +
            "Find short terms in the note that may need manual correction: names, company/product names, English or technical terms, acronyms, numbers, dates, and awkwardly transcribed words. " +
            "Only return items whose text appears exactly in the meeting note. " +
            "Do not critique the meeting content or suggest style rewrites. Return JSON only.",
        },
        {
          role: "user",
          content:
            `Participants: ${participants.join(", ") || "(unknown)"}\n\n` +
            `[Meeting note]\n${JSON.stringify(note)}`,
        },
      ],
      usageLog: {
        actionName: "reviewMeeting",
        question: "Review meeting note terms.",
        ...usageLog,
      },
    });
```

출력 schema:

```js
const REVIEW_SCHEMA = {
  type: "object",
  additionalProperties: false,
  properties: {
    review_items: {
      type: "array",
      items: {
        type: "object",
        additionalProperties: false,
        properties: {
          segment_index: { type: "integer" },
          text: { type: "string" },
          category: { enum: ["name", "word", "sentence"] },
          reason: { type: "string" },
          suggestion: { type: ["string", "null"] },
          confidence: { type: ["number", "null"] },
        },
        required: ["segment_index", "text", "category", "reason", "suggestion", "confidence"],
      },
    },
  },
  required: ["review_items"],
};
```

### 5. 경계

note object → LLM message + schema 경계다. 이 호출에는 `orchestrationPurpose: "summary"`가 없으므로 현재 전역 `CAP_AICORE_ORCHESTRATION_MODE: direct`가 적용된다. 요약 생성의 원격 template mode와 다른 점이다.

direct mode에서는 코드가 위 messages 뒤에 다음 schema 지시 system message를 추가한다.

```js
function aicoreDirectMessages({ messages, schemaName, schema }) {
  return [
    ...messages,
    {
      role: "system",
      content:
        `Return only a JSON object named ${schemaName} that matches this JSON schema. ` +
        "Do not include markdown fences or explanatory text.\n" +
        JSON.stringify(schema),
    },
  ];
}
```

### 6. 반환을 받는 코드

`chatJson()`이 JSON parse·schema 검증·필요시 repair를 끝낸 object를 반환하고, `normalizeReviewItems(content.review_items, note)`가 받는다.

### 7. 다음 단계

모델이 만든 후보 중 note에 실제로 존재하는 것만 남긴다.

## 4단계. 후보를 note와 다시 대조하여 최대 12개만 저장한다

### 1. 이 단계가 하는 일

모델이 note에 없는 단어를 제시하거나 중복 후보를 만들지 못하게 애플리케이션 코드에서 다시 필터링한다.

### 2. 실제 호출자 코드

```js
return normalizeReviewItems(content.review_items, note);
```

### 3. 전달되는 값과 상태

- schema를 통과한 `review_items`
- `normalizeNote(note)`의 모든 text를 합친 검색 문자열

### 4. 실제 피호출자 코드

```js
function normalizeReviewItems(items, note) {
  const noteText = noteToSearchText(note);
  const seen = new Set();
  return (Array.isArray(items) ? items : [])
    .map((item) => ({
      segment_index: Number.isFinite(Number(item?.segment_index ?? item?.segmentIndex))
        ? Number(item.segment_index ?? item.segmentIndex)
        : 0,
      text: String(item?.text || "").trim(),
      category: ["name", "word", "sentence"].includes(item?.category) ? item.category : "word",
      reason: String(item?.reason || "요약본에서 확인이 필요한 후보입니다.").trim(),
      suggestion: item?.suggestion == null ? null : String(item.suggestion).trim() || null,
      confidence: Number.isFinite(Number(item?.confidence)) ? Number(item.confidence) : null,
    }))
    .filter((item) => {
      if (!item.text || seen.has(item.text) || !noteText.includes(item.text)) return false;
      seen.add(item.text);
      return true;
    })
    .slice(0, 12);
}
```

LLM 설정이 없거나 호출이 실패하면 regex 기반 `fallbackReviewItems(note)`가 영문·숫자·AI/API/LLM/CAP/BTP/GPU/CPU/Kyma/HANA/XSUAA 같은 문자열을 후보로 만들며 confidence를 0.35로 둔다.

### 5. 경계

LLM 제안 → 신뢰 가능한 애플리케이션 후보 배열 경계다. `text`가 note에 정확히 포함되어야 한다.

### 6. 반환을 받는 코드

`generateReviewForMeeting()`이 정규화된 items를 받고 `replaceReviewItemsForMeeting()`으로 넘긴다.

### 7. 다음 단계

기존 후보를 모두 교체하고 `ReviewItems` 테이블에 새 후보를 저장한다.

## 5단계. 후보가 DB에 저장되고 polling 결과로 UI에 돌아온다

### 1. 이 단계가 하는 일

검토 실행마다 이전 후보를 지우고 새 후보 snapshot으로 교체한다.

### 2. 실제 호출자 코드

```js
await replaceReviewItemsForMeeting(meetingId, items);
```

### 3. 전달되는 값과 상태

각 후보에는 text, category, reason, suggestion, confidence가 있다.

### 4. 실제 피호출자 코드

```js
async function replaceReviewItemsForMeeting(meetingId, items) {
  items = Array.isArray(items) ? items : [];
  await DELETE.from(ReviewItems).where({ meeting_ID: meetingId });
  if (items.length) {
    await INSERT.into(ReviewItems).entries(items.map((item) => ({
      ID: cds.utils.uuid(),
      meeting_ID: meetingId,
      segmentIndex: item.segment_index ?? item.segmentIndex ?? 0,
      text: String(item.text || ""),
      category: item.category || "word",
      reason: String(item.reason || ""),
      suggestion: item.suggestion == null ? null : String(item.suggestion),
      confidence: item.confidence == null ? null : Number(item.confidence),
      source: "cap",
    })).filter((item) => item.text));
  }
}
```

### 5. 경계

CAP memory → DB `ReviewItems` 경계다.

### 6. 반환을 받는 코드

작업이 끝나면 `Meetings.status = done`, `percent = 100`으로 바뀐다. UI polling의 `capGetJob()`이 `transcript_review_items`로 후보를 받아 화면에 그린다.

### 7. 다음 단계

사용자는 후보의 제안을 적용하거나 직접 교체 문구를 입력하거나 “이상 없음”으로 제거한다.

## 6단계. 후보 적용은 요약 note 전체에서 문자열을 교체한다

### 1. 이 단계가 하는 일

사용자가 입력한 replacement를 후보의 `item.text`와 정확히 일치하는 모든 요약 필드에 적용한다.

### 2. 실제 호출자 코드

`app/meeting-ui/js/app.js`:

```js
async function applyReviewItem(reviewIndex) {
  const item = currentReviewItems[reviewIndex];
  const input = $("tab-summary").querySelector(`[data-review-input="${reviewIndex}"]`);
  const replacement = (input?.value || item?.suggestion || "").trim();
  if (!item || !replacement) {
    input?.focus();
    return;
  }
  const note = collectNoteInline();
  if (!applyReviewReplacementToNote(note, item, replacement)) {
    setInlineMessage("요약본에서 해당 텍스트를 찾지 못했습니다.");
    return;
  }
  currentReviewItems = currentReviewItems.filter((_, index) => index !== reviewIndex);
  await saveReplacedNote(note, "요약본 수정됨");
}
```

### 3. 전달되는 값과 상태

- `source = item.text`
- `replacement`: 사용자가 입력한 값 우선, 없으면 LLM suggestion
- 현재 화면에서 다시 수집한 note

### 4. 실제 피호출자 코드

```js
function applyReviewReplacementToNote(note, item, replacement) {
  const source = (item.text || "").trim();
  if (!note || !source || !replacement) return false;
  let changed = false;
  const replace = (value) => {
    const text = value || "";
    if (!text.includes(source)) return text;
    changed = true;
    return text.split(source).join(replacement);
  };
  note.summary = replace(note.summary);
  note.decisions = (note.decisions || []).map(replace);
  note.action_items = (note.action_items || []).map((item) => ({
    owner: replace(item.owner),
    task: replace(item.task),
    due: item.due ? replace(item.due) : null,
  }));
  note.topics = (note.topics || []).map((topic) => ({
    title: replace(topic.title),
    points: (topic.points || []).map(replace),
  }));
  return changed;
}
```

### 5. 경계

DOM의 사용자가 입력한 text → 브라우저 memory의 note object 경계다. 이것은 segment index 기반 transcript 수정이 아니다. 동일한 source가 summary·decisions·actions·topics 여러 곳에 있으면 전부 교체한다.

### 6. 반환을 받는 코드

`changed`가 true이면 처리한 후보를 `currentReviewItems`에서 제거하고 `saveReplacedNote()`가 note와 남은 후보를 함께 저장한다. “이상 없음”은 note를 바꾸지 않고 후보만 제거하여 같은 저장 함수를 호출한다.

### 7. 다음 단계

`saveNoteInline()` → `patchNote()` → CAP `saveSummary`로 note와 남은 후보가 영속화된다.

## 7단계. 수정된 note와 남은 후보를 한 번에 저장한다

### 1. 이 단계가 하는 일

요약 수정과 후보 처리 상태가 새로고침 뒤에도 유지되도록 `Summaries`와 `ReviewItems`를 함께 교체한다.

### 2. 실제 호출자 코드

```js
async function saveReplacedNote(note, message) {
  currentNote = note;
  $("tab-summary").innerHTML = renderInlineSummary(currentNote);
  bindInlineNoteEditor();
  await saveNoteInline(message, currentReviewItems);
}
```

`saveNoteInline()`의 실제 저장 호출:

```js
const job = await patchNote(currentJob, note, reviewItemsToPersist);
noteDirty = false;
currentNote = job.note || note;
currentReviewItems = Array.isArray(reviewItemsToPersist)
  ? reviewItemsToPersist
  : (job.transcript_review_items || []);
```

### 3. 전달되는 값과 상태

- `note`: 수정된 전체 회의록 object
- `reviewItems`: 아직 처리하지 않은 후보 배열

### 4. 실제 피호출자 코드

`app/meeting-ui/js/api.js`:

```js
export async function patchNote(id, note, reviewItems) {
  if (useCapApi()) {
    const body = {
      meetingId: id,
      content: JSON.stringify(note),
    };
    if (Array.isArray(reviewItems)) body.reviewItems = JSON.stringify(reviewItems);
    await postAction("saveSummary", body);
    const job = await capGetJob(id);
    if (Array.isArray(reviewItems)) job.transcript_review_items = reviewItems;
    return job;
  }
```

CAP `cap/srv/meeting-service.js`:

```js
this.on("saveSummary", async (req) => {
  const { meetingId, content } = req.data;
  if (!meetingId) return req.error(400, "meetingId is required");
  if (!content) return req.error(400, "content is required");
  await assertEditableMeeting(req, meetingId);

  const note = normalizeNote(JSON.parse(content));
  await DELETE.from(Summaries).where({ meeting_ID: meetingId });
  await INSERT.into(Summaries).entries({
    meeting_ID: meetingId,
    content: JSON.stringify(note),
    markdown: noteToMarkdown(note),
  });
  if ("reviewItems" in req.data) {
    await replaceReviewItemsForMeeting(meetingId, parseJsonArray(req.data.reviewItems));
  }
  await UPDATE(Meetings, meetingId).set({
    status: STATUS.DONE,
    percent: 100,
    error: null,
  });
  return SELECT.one.from(Meetings).where({ ID: meetingId });
});
```

### 5. 경계

Browser memory → CAP action HTTP → DB `Summaries`, `ReviewItems`, `Meetings` 경계다.

### 6. 반환을 받는 코드

`patchNote()`가 `capGetJob()`으로 다시 읽은 job을 UI에 반환하고, UI는 note와 remaining candidates를 갱신한다.

### 7. 다음 단계

모든 후보가 처리되면 `ReviewItems`가 빈 snapshot으로 저장된다. 이후 필요하면 사용자가 검토를 다시 실행할 수 있다.

## 별도 경로. 사용자가 요약을 직접 편집하면 어떻게 저장되는가

요약의 contenteditable 필드를 입력하면 900ms debounce 뒤 같은 `saveSummary` 경로를 쓴다.

```js
function scheduleNoteSave() {
  clearTimeout(noteSaveTimer);
  noteDirty = true;
  setInlineMessage("회의록 저장 대기 중");
  noteSaveTimer = setTimeout(() => saveNoteInline(), 900);
}
```

즉 LLM 후보 적용 여부와 관계없이 직접 편집한 요약도 `collectNoteInline()` → `patchNote()` → `saveSummary`로 저장된다.

## 별도 경로. 사용자가 전사문을 직접 편집하면 어떻게 되는가

전사 text 필드는 blur 때 `scheduleTranscriptSave(true)`를 호출한다.

```js
el.addEventListener("input", () => {
```

CAP는 transcript를 검증·교체하고, `regenerateSummary`가 true이면 기존 summary와 review items를 모두 지우고 새 요약 background task를 시작한다.

```js
if (regenerateSummary) {
  await DELETE.from(Summaries).where({ meeting_ID: meetingId });
  await DELETE.from(ReviewItems).where({ meeting_ID: meetingId });
  await UPDATE(Meetings, meetingId).set({
    status: STATUS.SUMMARIZING,
    percent: 80,
    error: null,
  });
  startBackgroundAiTask("summary generation", meetingId, () =>
    generateSummaryForMeeting(meetingId, content, {
      actionName: "saveTranscript",
      requestedBy: currentUserId(req),
    }));
}
```

새 요약이 만들어진다고 검토 후보가 자동으로 다시 생성되지는 않는다. 사용자가 다시 검토 버튼을 눌러야 한다.

## 현재 코드에서 알아둘 미묘한 점

1. 함수 이름은 `runTranscriptReview`지만 실제 CAP 입력은 transcript가 아니라 summary다.
2. review prompt 자체도 “full transcript가 아니라 Korean meeting note만 검토”하라고 명시한다.
3. `generateReviewForMeeting()`이 participants를 전달하지 않아 현재 prompt의 참석자는 `(unknown)`이다.
4. `segment_index` 필드는 schema/DB에 있지만, 후보 적용 UI는 이 값을 사용하지 않고 `item.text`를 요약 note 전체에서 찾는다.
5. 후보 text는 note에 정확히 포함되어야 하며 중복 제거 후 최대 12개다.
6. 후보를 적용해도 원본 transcript는 바뀌지 않는다.
7. transcript를 수정하면 summary와 review items가 폐기되고 summary만 재생성된다.

## 다시 기억할 핵심

> 검토 후보는 전사 교정기가 아니라 “요약본 안의 수동 확인 용어 탐지기”다. LLM은 요약본에 실제 존재하는 짧은 문자열과 선택적 suggestion을 만들고, 앱은 그 존재를 다시 확인한다. 사용자가 적용하면 요약의 모든 필드에서 해당 문자열을 바꾸고, 수정된 요약과 남은 후보를 `saveSummary`로 함께 저장한다. 전사 수정은 별도의 `saveTranscript` 경로이며 요약을 다시 만든다.
