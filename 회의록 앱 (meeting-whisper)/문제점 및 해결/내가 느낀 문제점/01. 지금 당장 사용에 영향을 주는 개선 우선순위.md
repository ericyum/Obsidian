# 지금 당장 사용에 영향을 주는 개선 우선순위

## 판단 기준

보안을 이론적으로 더 단단하게 만드는가가 아니라, 회사 내부 사용자가 정상적으로 녹음·업로드·조회·편집하는 중 실제 기능 실패나 잘못된 결과를 겪는가를 기준으로 한다.

## 우선순위

| 순서 | 항목 | 사용자에게 보이는 문제 | 담당 판단 |
|---:|---|---|---|
| 1 | 회의 전환 중 늦은 이전 응답 | 회의 B를 열었는데 회의 A 화면으로 다시 바뀔 수 있음 | 우리가 수정 |
| 2 | AI 작업 고착 복구 | CAP 중단 뒤 요약·검토가 영구 진행 중으로 남고 재시도도 안 됨 | 팀 동료 변경을 합칠 때 검증 |
| 3 | accessTokens 전체 이메일 사용 | 이름·이메일 앞부분이 같은 사내 사용자를 잘못 식별할 수 있음 | 사용자가 선택한 개선 |
| 4 | 일시정지 중 음량 분석 중단 | 일시정지인데도 불필요한 분석과 화면 갱신이 계속됨 | 사용자가 선택한 개선 |

## 지금 하지 않는 것

- 일반 `UPDATE`·`DELETE` 차단
- 참여자와 공유자의 중복 지정 차단
- 자동 저장 전체 revision 체계
- AI 결과 실행 ID와 입력 revision의 DB 구조 개편
- 녹음 청크 메타데이터 저장 순서 개편
- 회의 생성 후 업로드·enqueue 재시도 단계 변경

이 항목들은 정상적인 내부 사용자에게 당장 치명적인 기능 장애로 확인되지 않았다. 재현 증거가 생기기 전에는 작업 범위를 넓히지 않는다.

업로드·enqueue 재시도 중복 현상은 실제로 재현했지만 별도로 보류했다. 배포 환경의 Object Store 음원은 전사·요약 완료 후 정리되며, 이를 피하려고 기존 제작자의 회의 생성·업로드·enqueue 흐름을 변경하는 것은 회귀 위험이 더 크다고 판단했다. 실험 수정은 revert했으며 현재 제품에는 적용하지 않았다.

## 조사 중 확인한 로컬 검증 환경 주의점

기존 `scripts/cap-browser-e2e.ps1`은 루트 `.venv`가 없으면 시스템 Python을 사용한다. 현재 클론에는 `workers\.venv`만 있으므로 그대로 실행하면 Worker의 `uvicorn`을 찾지 못한다. 이는 06~08 앱 결함의 증거가 아니라 테스트 환경 선행 조건이다.
