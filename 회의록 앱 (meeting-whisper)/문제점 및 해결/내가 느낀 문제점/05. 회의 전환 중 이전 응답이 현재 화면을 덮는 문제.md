# 회의 전환 중 이전 응답이 현재 화면을 덮는 문제

> 수정 전 재현 결과: [[해결 과정/04. Before — 늦은 이전 회의 응답의 화면 덮어쓰기 테스트]]

## 최종 판단

기존 문서는 polling, 자동 저장, 녹음 청크 저장을 한꺼번에 다뤘다. 사용자 영향과 코드 근거가 가장 분명한 “다른 회의로 이동했는데 이전 회의의 늦은 응답이 현재 화면을 덮는 문제”만 우리 수정 후보로 남긴다.

## 사용자가 겪을 수 있는 증상

```text
회의 A 상세 조회 시작
→ 응답이 늦어짐
→ 사용자가 회의 B를 엶
→ B가 먼저 표시됨
→ 뒤늦은 A 응답이 paintResult()를 실행
→ 주소나 사용자의 의도는 B인데 화면 내용은 A가 됨
```

이 상태에서 사용자가 제목·전사문·요약을 수정하면 엉뚱한 회의를 편집한다고 오해할 수 있어 데이터 정확성에 직접 영향을 준다.

## 코드에서 확인한 원인

`app/meeting-ui/js/app.js`의 `openMeeting(id)`은 `await getJob(id)`가 끝난 뒤 그 요청이 아직 최신 요청인지 확인하지 않고 `paintResult(job)`을 호출한다.

`poll()`도 2초마다 비동기 `tick()`을 시작한다. `stopPolling()`은 다음 interval만 멈추며 이미 진행 중인 `getJob()` 요청을 취소하지 않는다. 이전 회의 polling 응답이 늦게 도착해도 현재 회의와 ID를 비교하지 않고 그린다.

## 최소 수정 방향

화면 상세 조회에 generation 또는 request ID를 둔다.

```text
회의를 열 때 generation 증가
→ 요청 시작 시 generation과 meetingId 보존
→ 응답 도착 시 현재 값과 비교
→ 둘 다 같을 때만 paintResult()
```

가능하면 진행 중 요청에 `AbortController`도 연결하지만, 핵심 안전장치는 응답 반영 직전의 `meetingId`·generation 비교다. 취소는 실패할 수 있어도 비교는 오래된 화면 덮어쓰기를 막는다.

polling은 `setInterval`로 겹치게 호출하기보다 한 요청이 끝난 뒤 `setTimeout`으로 다음 요청을 예약하는 방식을 검토한다.

## 이번 범위에서 제외할 것

- 요약 자동 저장 revision 전체 도입
- 전사문 저장 queue와 서버 낙관적 잠금
- 녹음 청크 메타데이터 병합 방식 변경
- 팀 동료의 회의 목록 검색용 `listRequestId` 재구현

팀 동료의 `listRequestId`는 목록 검색 응답 경합을 막는 것이며, 이 문서의 상세 화면 `openMeeting()`·`poll()` 경합과 대상이 다르다.

## Before·After 검증

1. 회의 A의 상세 상태 응답을 의도적으로 지연시킨다.
2. 응답을 기다리는 동안 회의 B를 연다.
3. B 응답을 먼저, A 응답을 나중에 반환한다.
4. Before에서 B 화면이 A로 바뀌는지 영상·DOM·Network 순서로 기록한다.
5. After에서 늦은 A 응답이 도착해도 제목, 현재 회의 ID, 편집 대상이 모두 B인지 확인한다.
6. A polling 요청이 진행 중인 경우에도 같은 시험을 반복한다.
