# 00. 코드 수정과 Before After 검증 작업 매뉴얼

## 이 문서의 목적

이 문서는 Meeting Whisper 개선 작업을 시작하기 전에 반드시 지켜야 할 공통 작업 원칙을 정리한다.

개선안을 한꺼번에 구현하거나 코드만 고친 뒤 끝내지 않는다. 수정 계획의 한 단계마다 문제를 먼저 재현하고, 최소한의 코드를 수정하고, 같은 조건에서 다시 검증하여 실제 효과를 확인한다.

```text
Before 재현
→ 최소 수정
→ After 재검증
→ 결과 비교
→ 회귀 테스트
→ 다음 단계 판단
```

## 1. 저장소 사용 원칙

### 실제 수정 대상

```text
C:\Users\염정운\project\meeting-whisper-juyum
```

이 저장소는 개인 레포지토리와 연결된 실제 작업 공간이다. 코드·테스트·설정 변경은 이 경로에서만 수행한다.

### 절대 수정하지 않는 원본

```text
C:\Users\염정운\project\meeting-whisper
```

이 경로는 원본 코드 분석과 비교에만 사용한다.

- 파일을 추가하지 않는다.
- 테스트 파일을 만들지 않는다.
- 임시 결과 폴더를 만들지 않는다.
- 빌드 결과나 staging 문서를 만들지 않는다.
- Git 명령으로 브랜치·커밋·체크아웃 상태를 변경하지 않는다.
- 기존 파일을 수정하거나 삭제하지 않는다.

### Obsidian 기록 위치

분석·계획·검증 기록은 다음 경로에 작성한다.

```text
C:\Users\염정운\Obsidian\회의록 앱 (meeting-whisper)
```

코드 저장소 안에 Obsidian 기록용 폴더를 만들지 않는다.

## 2. 팀 동료 변경을 해석하는 원칙

팀 문서에서 `적용 완료`라고 표현한 것은 팀 동료의 개인 저장소에 적용됐다는 뜻이다.

```text
팀 동료 개인 저장소
→ 팀 동료 개선 코드가 존재할 수 있음

meeting-whisper 원본
→ 아직 반영되지 않았을 수 있음

meeting-whisper-juyum
→ 실제 파일을 확인하기 전에는 반영됐다고 가정하지 않음
```

따라서 다음 원칙을 지킨다.

1. 팀 문서만 보고 현재 코드가 이미 수정됐다고 판단하지 않는다.
2. 작업 전 `meeting-whisper-juyum`의 실제 코드를 확인한다.
3. 팀 동료가 수정할 파일·함수·코드 구간을 미리 기록한다.
4. 같은 파일을 수정해야 한다는 이유만으로 우리의 목표를 포기하지 않는다.
5. 팀 동료가 맡은 기능을 불필요하게 다시 구현하지 않는다.
6. 우리의 목표에 필요한 최소 범위만 수정한다.
7. 병합 후에는 겹친 코드 영역의 회귀 테스트를 다시 실행한다.

## 3. 한 번에 한 단계만 수정

각 개선 문서는 여러 구현 단계로 나눌 수 있다. 한 번의 작업에서는 그중 한 단계만 선택한다.

예시:

```text
06. 업로드 중간 실패 문제

1단계: pendingUpload에 meetingId 보존
2단계: 음원 업로드 성공 여부 보존
3단계: enqueue만 다시 시도
4단계: fetch/XHR fallback 조건 제한
5단계: 업로드 timeout 추가
```

위 `06. 업로드 중간 실패 문제`는 단계 분리 방법을 설명하기 위해 사용한 당시 예시다. 이후 운영 정책을 검토한 결과 Object Store 음원은 전사·요약 완료 후 정리되고, 기존 업로드 흐름을 바꾸는 위험이 더 크다고 판단해 현재는 적용하지 않는다. 예시에 있다고 해서 현재 구현 대상이라는 뜻은 아니다.

1단계 검증이 끝나기 전에 2~5단계를 함께 수정하지 않는다.

한꺼번에 수정하면 다음을 판단하기 어렵다.

- 어떤 변경이 실제 효과를 냈는가
- 어느 변경이 회귀를 만들었는가
- 실패했을 때 어디까지 되돌려야 하는가
- 팀 동료 코드와 어느 부분에서 충돌했는가

## 4. 작업 전 준비

### 저장소 상태 확인

작업 시작 전에 다음을 확인한다.

```text
현재 저장소 경로
현재 브랜치
Git 변경 파일
추적되지 않은 파일
팀 코드가 병합됐는지 여부
수정 대상 파일의 현재 내용
```

사용자가 만든 기존 변경은 임의로 되돌리거나 덮어쓰지 않는다.

### Python 실행환경

현재 프로젝트 명령과 검증 스크립트는 기본적으로 프로젝트 루트의 가상환경을 기대한다.

```text
C:\Users\염정운\project\meeting-whisper-juyum\.venv
```

`workers\.venv`는 Worker 실행용으로 사용할 수 있지만 현재 `npm test`, smoke, browser E2E 스크립트가 자동으로 사용하는 경로는 아니다.

루트 `.venv`를 준비할 때는 현재 저장소에서 새로 생성한다. 다른 저장소의 `.venv` 폴더를 복사하여 사용하지 않는다.

### 기준 테스트 확인

코드를 수정하기 전에 테스트 명령 자체가 실행되는지 확인한다.

```text
CAP JavaScript 테스트
Worker Python 테스트
필요한 Legacy 테스트
Smoke 테스트
브라우저 E2E 테스트
```

테스트가 코드 문제가 아니라 `.venv`, 패키지, `.env` 침투 등 환경 문제로 실패하면 먼저 원인을 분리한다.

## 5. Before 테스트

### 목적

수정하려는 문제가 현재 코드에서 실제로 발생한다는 것을 증명한다.

Before 테스트는 단순히 실패하는 테스트를 만드는 것이 아니다. 우리가 고치려는 정확한 현상을 재현해야 한다.

### Before 테스트 기록

다음을 반드시 기록한다.

```text
테스트 목적
재현하려는 사용자 행동
실행 환경
사용한 브랜치와 기준 커밋
실행 명령
입력 데이터
예상한 잘못된 결과
실제로 관찰한 결과
테스트 성공·실패 개수
HTTP 상태 코드와 요청 횟수
CAP 로그
Worker 로그
브라우저 콘솔과 Network 기록
DB 행과 상태
화면 캡처가 필요한 경우 이미지
```

### 재현되지 않을 때

문제가 재현되지 않으면 바로 코드를 수정하지 않는다.

다음을 먼저 확인한다.

- 문서가 다른 브랜치나 과거 코드를 기준으로 작성됐는가
- 팀 변경이 이미 병합됐는가
- 테스트 조건이 실제 장애 조건과 다른가
- mock이 실제 동작을 지나치게 단순화했는가
- 로컬과 배포 환경의 인증·캐시·라우팅이 다른가

문제를 재현하지 못한 상태에서는 개선 효과도 정확히 비교할 수 없다.

## 6. 코드 수정 원칙

### 최소 변경

이번 단계의 목표를 달성하는 코드만 수정한다.

하지 않는 것:

- 관련 없는 함수 이름 변경
- 대규모 포맷 정리
- 주변 코드 리팩터링
- 팀 동료 담당 기능 재구현
- 필요하지 않은 DB 구조 변경
- 테스트 통과를 위한 실제 검증 우회
- 오류를 숨기기 위한 catch 추가

### 팀 코드와 겹칠 때

같은 파일을 수정해야 한다면 다음을 기록한다.

```text
팀 동료가 수정할 함수
우리가 수정할 함수
같은 줄 또는 인접 구간 여부
우리 변경이 기대하는 팀 코드의 동작
병합 후 다시 실행할 테스트
```

### 수정 중 범위가 커질 때

처음 계획보다 다른 파일·DB·API 계약까지 변경해야 한다면 작업을 확장하기 전에 이유를 기록하고 사용자에게 알린다.

## 7. After 테스트

수정 후에는 Before에서 사용한 테스트를 조건을 바꾸지 않고 다시 실행한다.

```text
같은 입력
같은 사용자 역할
같은 오류 주입 지점
같은 브라우저 행동
같은 로그 수집 방법
```

After에서만 유리하도록 테스트 조건을 바꾸지 않는다.

### 완료 판정 기준

```text
[문제 재현 테스트]
Before: 문제 발생
After: 문제 해소

[기존 정상 기능]
Before: 정상
After: 계속 정상

[브라우저 사용자 흐름]
Before: 오류·중복·고착·과거 값 덮어쓰기 발생
After: 기대한 화면과 상태 유지

[로그와 DB]
Before: 잘못된 요청 수·상태·중복 행 존재
After: 기대한 요청과 데이터만 존재
```

단위 테스트 하나만 통과했다고 전체 단계를 완료로 판단하지 않는다.

## 8. 실제 로컬 실행 검증

가능하면 다음 전체 흐름을 실행한다.

```text
브라우저
→ Approuter
→ CAP 백엔드
→ 테스트 DB 또는 HANA
→ Worker
```

AI Core가 필요하지 않은 검증은 mock Worker나 제어 가능한 응답을 사용하여 반복 가능하게 만든다.

실제 AI Core 검증은 다음을 별도로 기록한다.

- 외부 API를 실제 호출했는지
- 사용한 모델
- 호출 횟수
- 처리 시간
- 토큰 또는 비용 로그
- 네트워크 상태에 따른 변동 가능성

## 9. 실제 사용자처럼 브라우저 검증

단순히 API만 호출하지 않고 가능한 경우 브라우저에서 직접 사용자 흐름을 수행한다.

```text
로그인
→ 회의 목록 확인
→ 새 회의 정보 입력
→ 참여자·공유자 선택
→ 녹음 또는 음원 파일 선택
→ 일시정지·재개
→ 녹음 종료
→ 업로드
→ 전사 진행 확인
→ 요약 결과 확인
→ 전사문·회의록 수정
→ 다른 회의로 이동
→ 다시 돌아와 저장 결과 확인
```

필요하면 다음 장애도 의도적으로 발생시킨다.

```text
음원 업로드 실패
enqueue 실패
CAP 재시작
Worker 실패
AI 응답 지연
HTTP 응답 순서 역전
polling 중 다른 회의로 이동
자동 저장 중 추가 편집
세션 만료
```

## 10. 로그와 상태 비교

Before와 After에서 가능한 한 같은 종류의 증거를 수집한다.

### 브라우저

- Console 오류
- Network 요청 순서
- URL·메서드·상태 코드
- 같은 요청의 반복 횟수
- 요청 소요 시간
- 화면 상태와 오류 문구

### CAP

- Action 진입 횟수
- 상태 전이
- 오류 stack
- cleanup 및 dispatcher 로그
- DB 변경 결과

### Worker

- `/transcribe` 접수 횟수
- `workerRunId`
- heartbeat 단계
- AI Core 요청 횟수
- 실패 및 재시도 횟수

### DB

- `Meetings` 행 개수와 status
- `AudioObjects` 개수
- `TranscriptionDispatches` 개수와 상태
- `Transcripts`, `Summaries`, `ReviewItems` 존재 여부
- 중복 행과 오래된 실행 결과 여부

## 11. Obsidian 결과 문서 작성

각 개선 사항 아래에 단계별 문서를 만든다.

예시:

```text
해결 과정
└─ 06. 회의 생성 업로드 enqueue 중간 실패
   ├─ 06-1. Before — 중간 실패 재현과 기준 결과.md
   ├─ 06-2. 수정 — meetingId와 진행 단계 보존.md
   ├─ 06-3. After — 동일 시나리오 재검증.md
   └─ 06-4. Before After 최종 비교.md
```

각 문서에는 다음을 포함한다.

```text
수정 계획의 현재 단계
수정 전 가설
Before 결과
수정 파일과 코드 범위
수정하지 않은 범위
After 결과
정량 비교
회귀 테스트 결과
브라우저 검증 결과
로그와 DB 비교
팀 코드와 충돌 예상 지점
남은 문제
다음 단계 진행 가능 여부
```

## 12. 단계 종료 조건

다음 조건을 모두 만족해야 한 단계를 완료한다.

- Before에서 문제를 재현했다.
- 이번 단계에 필요한 최소 코드만 수정했다.
- 동일 테스트의 After 결과가 개선됐다.
- 관련 기존 테스트가 계속 통과한다.
- 가능한 경우 실제 브라우저 흐름도 통과했다.
- 로그와 DB 상태가 기대와 일치한다.
- 팀 변경과 겹치는 위치를 기록했다.
- Obsidian에 Before·수정·After·비교 결과를 남겼다.

하나라도 충족하지 못하면 완료로 표시하지 않는다.

## 13. 중단하고 다시 판단해야 하는 경우

다음 상황에서는 임의로 작업 범위를 넓히지 않는다.

- Before에서 문제가 재현되지 않는다.
- 팀 동료 변경 없이는 테스트할 수 없다.
- 실제 수정 대상이 계획과 다른 DB 구조 변경을 요구한다.
- 외부 AI Core 호출로 비용이 발생해야만 검증할 수 있다.
- 운영 HANA 또는 BTP 권한 없이는 결과를 확인할 수 없다.
- 사용자 기존 변경과 같은 줄을 수정해야 한다.
- 테스트가 코드가 아니라 환경 문제로 실패한다.
- 원본 `meeting-whisper`를 수정해야만 진행할 수 있는 것처럼 보인다.

이 경우 현재 증거와 막힌 이유를 기록한 뒤 다음 행동을 사용자와 결정한다.
