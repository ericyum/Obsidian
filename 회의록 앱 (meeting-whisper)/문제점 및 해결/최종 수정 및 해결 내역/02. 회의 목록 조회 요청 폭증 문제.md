# 02. 회의 목록 조회 요청 폭증 문제

> 현재 상태: **해결·`main` 반영 완료**

## 문제 현상

초기 목록 화면은 회의 전체를 한 번 조회한 뒤, 각 회의마다 상태·전사문·요약·검토 결과를 추가로 조회했다.

```text
Meetings 목록 1회

각 회의마다
├─ getMeetingStatus
├─ Transcripts
├─ Summaries
└─ ReviewItems
```

회의가 `N`건이면 대략 `1 + 4N`개의 요청이 발생할 수 있었다. 회의 50건이면 최대 201회 수준의 요청이다.

## 원인

초기 `listMeetings()`는 `Meetings`를 읽은 뒤 `meetings.map()` 안에서 `getMeetingStatus()`를 반복했다. 이어서 `capJobFromMeeting()`을 거치며 상세 화면에서나 필요한 전사문·요약·검토 결과까지 가져왔다.

```text
목록에 필요
→ 제목, 상태, 날짜, 참여자, 카테고리

실제로 가져온 것
→ 목록 정보 + 전사문 전체 + 요약 + 검토 결과
```

HTTP 요청 개수뿐 아니라 브라우저로 전송하는 데이터 크기도 회의 수에 비례해 커졌다.

## 수정: 목록 전용 `getMeetingList` Action

CAP에 목록 전용 Action을 추가했다.

```text
이전
목록 조회
→ 회의별 추가 요청

현재
getMeetingList 한 번 호출
→ CAP가 필터·검색·페이지네이션 처리
→ 목록용 정보만 반환
```

CAP가 다음을 한 번에 처리한다.

- 현재 사용자가 접근할 수 있는 회의 조회
- 검색어·진행 단계·카테고리 필터
- 정렬과 `top`, `skip` 페이지네이션
- 편집·삭제 가능 여부
- 목록에 필요한 진행률과 큐 정보
- 필터에 필요한 카테고리·사람 후보

## 프론트엔드 변경

`listMeetings()`는 회의별 상세 요청 대신 `getMeetingList` 결과를 받는다.

```js
const raw = await postAction("getMeetingList", {
  search,
  stage,
  category,
  top,
  skip
});
```

`capListItemToJob()`은 CAP의 목록 항목을 프론트엔드 표시 형식으로만 바꾸며 전사문·요약·검토 정보를 추가 조회하지 않는다.

```text
getMeetingList
→ capListItemToJob
→ meetingsCache
→ 회의 목록 HTML
```

## 상세 화면은 필요할 때만 조회

사용자가 특정 회의를 열면 그때는 전사문·요약·검토 결과가 필요하므로 상세 조회 경로를 유지한다.

```text
목록
→ 가벼운 목록 전용 데이터

회의 클릭
→ 해당 회의의 상세 데이터
```

## 결과

| 구분 | 초기 | 현재 |
|---|---|---|
| 목록 요청 | 약 `1 + 4N` | 목록 Action 중심 1회 |
| 전사·요약 | 목록에서도 조회 | 상세 화면에서 조회 |
| 검색·필터 | 브라우저 중심 | CAP 중심 |
| 페이지 처리 | 전체 데이터 후 처리 | 서버에서 `top`, `skip` |
