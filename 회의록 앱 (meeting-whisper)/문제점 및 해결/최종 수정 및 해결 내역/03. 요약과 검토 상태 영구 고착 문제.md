# 03. 요약과 검토 상태 영구 고착 문제

> 현재 상태: **해결·`main` 반영 완료**

## 문제 현상

요약 재생성이나 AI 검토 중 CAP가 종료되면 회의가 `summarizing` 또는 `reviewing`에 영구히 멈출 수 있었다.

```text
요약 재생성
→ Meetings.status = summarizing
→ percent = 85
→ CAP 메모리의 백그라운드 AI 작업 시작
→ CAP 재시작·크래시
→ 메모리 작업은 사라짐
→ DB의 summarizing 상태는 남음
```

이 상태에서는 `rejectIfMeetingBusy` 때문에 사용자의 재시도도 409로 거부될 수 있었다.

## 원인

전사는 Worker의 Dispatch·heartbeat·`workerRunId`로 생존 여부를 감시한다. 반면 요약과 검토는 CAP 프로세스 메모리에서 실행되며 별도의 heartbeat가 없었다.

```text
사라진 것
→ CAP 메모리의 실제 AI 작업

남은 것
→ Meetings.status = summarizing/reviewing
```

기존 cleanup은 `queued`·`transcribing`은 검사했지만 `summarizing`·`reviewing`은 검사하지 않았다.

## 수정 1: `recoverStaleAiTasks()`

일정 시간 이상 상태가 변하지 않은 AI 작업을 복구한다. 기본 임계시간은 30분이며 `CAP_AI_TASK_STALE_MS`로 조정할 수 있다.

```text
summarizing/reviewing
+ modifiedAt이 30분 이상 변하지 않음
→ 유실된 AI 작업으로 판단
```

## 복구 결과

기존 요약이 남아 있으면 사용자에게 보여줄 결과가 있으므로 `done`으로 돌린다.

```js
{
  status: STATUS.DONE,
  percent: 100,
  error: "요약 생성이 중단되어 이전 요약을 유지했습니다. 다시 시도해 주세요."
}
```

기존 요약도 없으면 `failed`로 바꾸어 사용자가 다시 시도할 수 있게 한다.

```js
{
  status: STATUS.FAILED,
  error: "요약 생성이 완료되기 전에 중단되었습니다. 다시 시도해 주세요."
}
```

## 왜 30분을 기다리는가

긴 전사문은 약 12,000자 단위로 나누어 요약한 뒤 다시 결합할 수 있다. 정상 작업도 수 분이 걸릴 수 있으므로 `summarizing`이라는 이유만으로 즉시 종료하면 안 된다.

## 수정 2: CAP 기동 시 즉시 복구

CAP가 방금 새로 시작했다면 DB의 `summarizing`·`reviewing`은 이전 프로세스에서 유실된 작업이다. 현재 프로세스에서 진행 중일 수 없으므로 30분을 기다리지 않고 즉시 복구한다.

```text
CAP 시작
→ recoverAiTasksOnStartup()
→ recoverStaleAiTasks(staleMs = 0)
→ 기존 요약이 있으면 done
→ 없으면 failed
```

이 즉시 복구는 CAP가 1개 인스턴스라는 전제를 사용한다. 향후 여러 CAP 인스턴스로 확장하면 전사의 `workerRunId`처럼 AI 작업 소유권을 DB에 기록해야 한다.

## 검증

- 오래 멈춘 작업 + 기존 요약 존재 → `done`
- 오래 멈춘 작업 + 요약 없음 → `failed`
- 임계시간 전의 정상 작업 → 변경하지 않음
- `reviewing`도 같은 규칙으로 복구
- CAP 기동 시 임계시간 없이 즉시 복구
