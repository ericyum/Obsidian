# 04. 현재 코드를 검증하지 못하던 테스트 체계 문제

> 현재 상태: **해결·`main` 반영 완료**

## 문제 현상

초기 `npm test`는 Python `pytest` 전체를 실행했지만 대부분은 현재 CAP 앱이 아닌 과거 `legacy/fastapi`를 검사했다.

```json
"test": ".\\.venv\\Scripts\\python.exe -m pytest"
```

반면 CAP 요약·전사 검증·Dispatcher 테스트는 파일이 있어도 어떤 npm 기본 명령에도 연결되지 않았다.

```text
npm test 통과
→ Legacy 코드가 주로 통과했다는 뜻
→ 현재 CAP·Worker가 안전하다는 뜻이 아님
```

## 수정: 테스트 목적별 분리

```json
"test": "npm.cmd run test:js && npm.cmd run test:worker",
"test:js": "node --test \"tests/*.test.js\"",
"test:worker": ".\\.venv\\Scripts\\python.exe -m pytest ...",
"test:all": ".\\.venv\\Scripts\\python.exe -m pytest"
```

| 명령 | 목적 |
|---|---|
| `npm test` | 현재 CAP JavaScript + Worker 핵심 테스트 |
| `npm run test:js` | CAP·프론트 JavaScript 로직 |
| `npm run test:worker` | 현재 Python Worker 핵심 로직 |
| `npm run test:all` | Legacy를 포함한 Python 전체 |

## 추가로 발견한 `.env` 테스트 격리 문제

테스트는 `monkeypatch.delenv()`로 환경변수가 없는 상황을 만들었지만 Worker `Settings`가 프로젝트 루트 `.env`를 다시 읽었다.

```text
프로세스 환경변수 삭제
→ 디스크의 .env는 남아 있음
→ Settings가 .env에서 값을 다시 읽음
→ "설정이 없는 상황" 테스트가 실패
```

개발자의 `.env` 유무에 따라 결과가 달라지는 테스트는 신뢰할 수 없다. `tests/conftest.py`를 추가해 테스트에서는 로컬 `.env`를 읽지 않게 했다.

```text
일반 실행
→ .env 사용

테스트
→ 로컬 .env 무시
→ 테스트가 직접 준 값만 사용
```

## 현재 보호하는 주요 회귀 사례

- AI 요약·검토 고착 복구
- CAP 기동 시 AI 작업 즉시 복구
- `audio_uploaded` 전사 대기표 누락 복구
- 방치된 `created` 회의 정리
- 일시정지 중 RAF loop 정지
- 전체 이메일 accessToken과 밑줄 이메일
- Dispatcher·전사 결과 검증·Worker API

## 검증 의미

초기 문서에는 JavaScript 18개 + Worker 29개, 합계 47개 통과가 기록되었다. 이후 복구·RAF·accessToken 테스트가 추가되어 현재 테스트 수는 더 많다.

이 단계는 사용자 기능을 추가한 것이 아니라 `npm test`가 현재 코드의 안전성을 실제로 판단하게 만든 유지보수 개선이다.
