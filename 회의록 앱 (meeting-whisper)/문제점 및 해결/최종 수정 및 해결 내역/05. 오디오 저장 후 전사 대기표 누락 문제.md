# 05. 오디오 저장 후 전사 대기표 누락 문제

> 현재 상태: **해결·`main` 반영 완료**

## 문제 현상

오디오 업로드는 성공했지만 그다음 `enqueueTranscription` 요청이 실패하면 회의가 `audio_uploaded`, 5%에서 멈췄다.

```text
Meetings
→ status = audio_uploaded
→ percent = 5

AudioObjects/Object Store
→ 오디오 있음

TranscriptionDispatches
→ 해당 회의 행 없음
```

실제 66MB 파일 사례에서 DB에 약 68MB 오디오는 있었지만 Dispatch는 없었다.

## 원인

프론트엔드 `createJob()`은 하나의 서버 트랜잭션이 아니라 별도 HTTP 단계로 진행한다.

```text
1. Meetings 행 생성
2. 오디오 업로드
3. enqueueTranscription
```

2번이 성공한 뒤 3번 요청이 네트워크 오류나 요청 중단으로 실패하면 오디오만 남고 Worker에게 전달할 작업표가 생기지 않는다.

기존 cleanup은 `queued`·`transcribing`을 검사했지만 `audio_uploaded`는 검사하지 않았다. 재시도 버튼도 일반적으로 `failed`에서만 보였기 때문에 자동 복구와 사용자 복구 모두 없었다.

## 수정: `recoverUnqueuedUploads()`

`audio_uploaded`에서 오래 멈춘 회의를 cleanup이 검사한다. 기본 임계시간은 5분이며 `CAP_UPLOADED_STALE_MS`로 조정한다.

```text
audio_uploaded
+ modifiedAt이 5분 이상 변하지 않음
→ 복구 검사
```

### 기존 Dispatch가 있는 경우

이미 `TranscriptionDispatches`가 있는데 `Meetings.status`만 늦게 남은 경우일 수 있다. 새 Dispatch를 만들지 않고 회의 상태만 맞춘다.

```text
Dispatch 있음
→ Meetings.status = queued
→ percent = 10
```

### Dispatch는 없고 오디오는 있는 경우

```text
Dispatch 없음
+ 오디오 있음
→ createTranscriptionDispatch()
→ Meetings.status = queued
→ Dispatcher가 Worker에게 전달
```

오디오를 다시 업로드하지 않고 이미 저장된 파일을 사용한다.

### 오디오도 없는 경우

```text
Dispatch 없음
+ 오디오 없음
→ Meetings.status = failed
→ "파일을 다시 업로드" 안내
```

## 오류 안내가 사라지던 UI 문제

`enqueueTranscription` 요청이 실패한 순간 브라우저는 `showResErr()`로 오류와 조치 버튼을 표시했다. 하지만 다음 폴링에서 CAP가 `audio_uploaded`를 반환하면 `failed`가 아니라는 이유로 오류 영역을 지웠다.

```text
enqueue 실패
→ 브라우저가 오류 표시
→ 상태 폴링
→ stage = uploaded
→ failed가 아님
→ 오류 UI 삭제
```

조치 버튼이 있는 오류를 폴링이 바로 삭제하지 않도록 `stickyResErr`를 추가했다. `created`·`uploaded`에서는 안내를 유지하고 `queued` 이후로 넘어가면 문제가 해결된 것으로 보고 지운다.

## 브라우저 재시도와의 차이

`retryPendingUpload()`은 브라우저 메모리에 Blob이 남아 있을 때 사용자가 즉시 다시 업로드하는 기능이다. `recoverUnqueuedUploads()`는 브라우저 상태와 무관하게 CAP가 DB와 서버 저장소를 검사하는 사후 안전장치다.

## 검증

- 오디오가 있으면 전사 큐에 재등록
- 오디오가 없으면 `failed`
- 임계시간 전의 정상 회의는 변경하지 않음
- Dispatch가 있으면 중복 생성 없이 상태만 보정
