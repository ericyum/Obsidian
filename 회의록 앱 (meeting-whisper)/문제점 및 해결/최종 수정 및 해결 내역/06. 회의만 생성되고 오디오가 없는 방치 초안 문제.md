# 06. 회의만 생성되고 오디오가 없는 방치 초안 문제

> 현재 상태: **해결·`main` 반영 완료**

## 문제 현상

`createJob()`의 첫 단계인 `Meetings` 행 생성은 성공했지만 오디오 업로드가 실패·중단되면 회의가 `created`에 남았다.

```text
Meetings
→ 행 있음
→ status = created

AudioObjects/Object Store
→ 오디오 없음

TranscriptionDispatches
→ 없음
```

기존 cleanup은 `created`를 검사하지 않았고 회의가 `failed`도 아니어서 일반 재시도 경로도 보이지 않았다.

## 브라우저 Blob의 한계

업로드 실패 직후에는 `retryPendingUpload()`이 브라우저 메모리의 오디오 Blob을 다시 보낼 수 있다. 하지만 페이지를 새로고침하거나 브라우저를 닫으면 Blob은 사라진다.

```text
브라우저가 계속 열려 있음
→ Blob이 남아 있을 수 있음
→ 즉시 재업로드 가능

새로고침·종료
→ Blob 소멸
→ CAP이 파일을 자동으로 복원할 수 없음
```

## 수정: `recoverAbandonedDrafts()`

`created`에서 일정 시간 이상 멈춘 회의를 cleanup이 검사한다. 기본 임계시간은 30분이며 `CAP_CREATED_STALE_MS`로 조정한다.

```text
created
+ modifiedAt이 30분 이상 변하지 않음
→ 방치된 회의 검사
```

임계시간을 넓넓하게 잡은 이유는 대용량 오디오가 정상적으로 업로드 중일 수 있기 때문이다.

## 서버 저장소에 오디오가 있는 경우

`Meetings.status`만 `created`이고 오디오 저장은 이미 성공했을 수 있다. 이는 오디오를 저장한 뒤 회의 상태를 갱신하기 전에 장애가 난 경우이다.

```text
created + 오디오 있음
→ Meetings.status = audio_uploaded
→ percent = 5
→ recoverUnqueuedUploads() 단계로 전달
→ Dispatch 확인·생성
→ queued
```

## 서버 저장소에 오디오가 없는 경우

CAP은 사라진 브라우저 Blob을 다시 만들 수 없다. 따라서 자동 복구가 아니라 명확한 실패 상태로 바꾸어 사용자에게 재업로드가 필요함을 알린다.

```text
created + 오디오 없음
→ Meetings.status = failed
→ "오디오 업로드가 완료되지 않았습니다"
→ 사용자가 파일을 다시 선택
```

## 두 cleanup의 연결

```text
recoverAbandonedDrafts()
created 단계 검사
          │
          └─ 오디오 있음
             → audio_uploaded
             → recoverUnqueuedUploads()
             → Dispatch 생성
             → queued
```

`retryPendingUpload()`과 cleanup은 브라우저 Blob의 생존 여부를 서로 조회해 분기하는 구조가 아니다. 전자는 브라우저의 즉시 재시도, 후자는 CAP의 독립적인 정기 정리이다.

## 미사용 `diarizing` 상태

같은 커밋에서 `diarizing`이 과거 WhisperX 화자 분리 시절의 잔재이며 현재 설정하는 코드가 없다는 주석을 추가했다. HANA 스키마 변경 위험 때문에 enum을 실제로 삭제하지는 않았다.

## 검증

- 오디오 없이 오래 방치 → `failed`
- 오디오가 있는 상태 불일치 → `audio_uploaded`
- 임계시간 전 정상 업로드 → 변경하지 않음
- `CAP_CREATED_STALE_MS` 적용
