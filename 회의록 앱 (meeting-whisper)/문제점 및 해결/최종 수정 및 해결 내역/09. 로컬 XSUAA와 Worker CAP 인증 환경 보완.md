# 09. 로컬 XSUAA와 Worker CAP 인증 환경 보완

> 현재 상태: **해결·`main` 반영 완료**  
> 성격: 배포 기능 수정이 아닌 **로컬 검증 환경 개선**

## 문제

기존 로컬 Approuter는 `authenticationMethod: none`과 Mock 사용자를 사용했다. 배포는 XSUAA를 사용했기 때문에 로그아웃·세션 만료·`/user-api/currentUser`·재로그인 문제를 로컬에서 동일하게 재현하지 못했다.

```text
기존 로컬
→ Mock 인증
→ Approuter XSUAA 과정 생략

배포
→ Approuter
→ XSUAA
→ 사용자 세션·JWT
```

## 로컬 Approuter 수정

`approuter/dev/xs-app.json`을 라우트별 XSUAA 인증으로 맞추고 `/user-api`와 `/logout`을 추가했다.

```text
authenticationMethod = route
/user-api → sap-approuter-userapi
/api → authenticationType = xsuaa
정적 UI → authenticationType = xsuaa
```

## `default-env.json`의 역할

로컬 Approuter는 다음 명령으로 `approuter/dev`를 working directory로 사용한다.

```text
approuter.js --workingDir ./dev --port 5000
```

따라서 로컬에서는 `approuter/dev/default-env.json`의 다음 값을 읽는다.

```text
destinations.srv-api
→ http://127.0.0.1:4004
→ forwardAuthToken = true

VCAP_SERVICES.xsuaa
→ clientid, clientsecret, url 등
```

로컬 Approuter는 `mta.yaml`을 읽지 않는다. 배포 시에는 `mta.yaml`과 Cloud Foundry service binding이 같은 역할을 한다.

```text
로컬
→ dev/default-env.json

배포
→ mta.yaml
→ CF가 VCAP_SERVICES를 주입
```

`default-env.json`에 실제 XSUAA service key가 들어 있다면 UI·Approuter·CAP은 로컬에서 실행하지만 인증과 JWT 발급은 BTP의 실제 XSUAA를 사용한다.

## CAP Hybrid 프로파일

```text
npm run local:cap
→ npm run cap:serve:hana
→ cds bind --exec --profile hybrid -- cds serve all
→ [hybrid].auth = xsuaa
```

초기에는 Hybrid에 `db: hana`도 강제했지만 HDI binding이 없는 개발자의 CAP가 기동하지 못해 제거했다. 현재는 Hybrid가 XSUAA 인증을 선택하고 DB는 binding이 있으면 HANA, 없으면 로컬 DB를 사용할 수 있다.

## `.env`와 배포 설정의 차이

`.env` 파일 자체는 로컬 CAP·Worker용이다. 모델명·Orchestration template·Dispatcher 제한과 같은 동일한 값은 배포 시 `mta.yaml`에서 CAP 환경변수로 주입된다.

```text
로컬 CAP·Worker
→ .env

배포 CAP
→ mta.yaml properties

배포 서비스 자격증명
→ BTP service binding·VCAP_SERVICES
```

명령어가 직접 지정한 환경변수는 `.env`보다 우선한다. 예를 들어 `local:worker:aicore`는 `AICORE_STT_MODEL=gemini-2.5-flash`를 명령에서 직접 지정한다.

## Worker → CAP 인증

CAP을 XSUAA Hybrid로 실행하면 Mock용 Basic `worker:worker`는 401로 거부된다. Worker는 XSUAA client-credentials로 기술 사용자 토큰을 받아 CAP 내부 API를 호출해야 한다.

```text
CAP → Worker
공유 Bearer token

Worker → CAP
XSUAA client-credentials token
+ Worker 역할
+ workerRunId 작업 소유권 확인
```

Worker 인증 우선순위는 client credentials → 고정 Bearer → Basic이다.

## 검증

- XSUAA client-credentials token에 Worker scope 포함
- 해당 토큰으로 CAP `/internal` API 호출 200
- XSUAA CAP에 Basic `worker:worker` 호출 401
