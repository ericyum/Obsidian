## 2. 실험 후 되돌림: 업로드 재시도 중복 회의

문제는 실제로 재현됐다.

```text
Meetings A 생성
→ 업로드/enqueue 실패
→ 다시 업로드
→ createJob() 전체 재실행
→ Meetings B 생성
```

`af4d6f1`에서 `meetingId`, `audioUploaded`, `enqueued`를 보존해 중단된 단계부터 이어가는 실험을 했지만 `4cb5e39`에서 revert했다.

미적용 이유:

- Object Store 오디오는 처리 완료 후 cleanup 대상
- 일시적 중복보다 핵심 상태 머신 변경의 회귀 위험이 큼
- 기존 제작자의 업로드 흐름을 운영상 필수 근거 없이 바꾸지 않음

현재도 중복 Meetings 생성은 가능하지만 5·6단계 cleanup이 `created`·`audio_uploaded` 영구 고착을 사후에 완화한다.

## 3. 미해결: 늦은 상세 응답의 화면 덮어쓰기

목록 검색에는 `listRequestId`가 있어 이전 검색 응답을 무시한다. 하지만 `openMeeting()`과 `poll()`은 응답이 현재 회의의 요청인지 확인하지 않는다.

```text
회의 A 상세 요청 지연
→ 회의 B 열기
→ B 응답 먼저 표시
→ A 응답 뒤늦게 도착
→ paintResult(A)가 B 화면을 덮을 가능성
```

제안된 해결은 상세 generation/request ID와 `meetingId`를 응답 반영 직전에 비교하는 것이지만 현재 `main`에는 적용되지 않았다.

## 4. 문서에는 수정 기록, 현재 `main`에는 없음

### `displaySpeaker()` 타입 가드

문서에는 `speaker`가 숫자·객체일 때 `raw.startsWith is not a function`을 막는 다음 수정이 기록되어 있다.

```js
if (typeof raw !== "string") return "화자";
```

현재 `main`의 `ui.js`에는 이 가드가 없다. Worker가 항상 문자열로 정규화한다면 재현되지 않을 수 있지만 UI 방어 코드가 미병합인 것은 확실하다.

### 인증 실패 응답 전 `drainReq()`

큰 body를 전송하는 도중 302/401/403을 반환할 때 request body를 끝까지 소비하는 수정이 문서에 있지만 현재 `binary-upload-route.js`에는 `drainReq()`가 없다. 로컬 XSUAA로 `anonymous` 진입 가능성을 줄인 상태이며 route 자체의 body drain 방어는 미반영이다.

## 5. 미해결: 긴 오디오의 chunk 미분할과 시간 역전

약 28분 오디오의 `duration_hint`를 Worker가 얻지 못한 사례가 있었다.

```text
실제 길이 1,680초
분할 기준 720초

하지만 duration_hint = None
→ 긴 오디오인지 판단 불가
→ chunk=None/None
→ 28분 전체를 Gemini 2.5에 단일 요청
→ 일부 segment에서 end < start 시간 역전
→ Worker 검증 실패
```

`AICORE_STT_CHUNK_SECONDS=300` 강제 분할이 제안·실험됐지만 현재 `main`의 확정 해결책은 아니다. `duration_hint`가 최초로 누락된 정확한 지점도 완전히 특정되지 않았다.

## 6. 비교 후 현행 유지

### STT 모델

짧은 음성에서 새 모델이 좋은 결과를 보인 사례는 있지만 긴 음성·비용·프롬프트 재조정·SAP 요율 불확실성 때문에 현재는 다음을 유지한다.

```text
AICORE_STT_MODEL = gemini-2.5-flash
```

모델 선택·reasoning UI도 현재 배포판에 넣지 않았다.

### `diarizing`

과거 WhisperX 화자 분리 잔재로 현재 설정하는 코드가 없지만 HANA 스키마 변경 위험을 피하기 위해 enum은 삭제하지 않고 미사용 주석만 남겼다.
