# Whisper — STT 디버그 사례 (오디오 업로드·빈 응답)

> [!summary] 한눈에
>
> - 비용 비교(같은 오디오 3개 모델) 준비 중 발생한 디버그 4건. 모두 2026-08-03(일) 로컬 세션.
> - ① 빈 전사 응답(`seg_count=0`) — 묵음/인식 문제, 목소리 명확히 넣어 해결. 
> - ② 파일 업로드 `octet-stream` 400 — `.bin` 확장자 문제, `_mime_type_for_path` 매직넘버 fallback으로 해결. 
> - ③ 5분 업로드 502 ECONNRESET — CAP media stream body 한계 ~1MB, `body_parser.limit`가 media엔 안 닿음. 
> - ④ UI 업로드 실패를 "업로드 대기" 빈칸으로 표시.
> - 코드 변경: `aicore_stt.py` 매직넘버 fallback, `recorder.js` 64kbps, `package.json` body_parser.limit(부분 효과), 디버그 로그 정리.
> - 긴 오디오(2분+)는 로컬 한계로 운영 배포 후 확인.

---

## 1. 배경

- 같은 오디오로 3개 모델(2.5/3.1-lite/3.5) 비용·품질 비교가 목표. 20분 희망 → 3분 → 1분으로 점진 축소.
- 비교 준비 중 4건의 디버그 발생. 본 문서는 그 정리.

---

## 2. 이슈 ① — 빈 전사 응답 (seg_count=0)

### 증상
- 전사 후 `RuntimeError: transcript result did not contain any speech text`(`main.py:277` `_validate_transcript_for_storage`).
- raw 로그: `DEBUG raw transcript ... seg_count=0 first_seg=no-segments`. transcript dict에 keys는 다 있으나 `segments=[]`.

### 원인
- AI Core가 응답은 줬으나 세그먼트 없음(음성 인식 실패). 오디오에 묵음이거나 인식 불가 구간.
- 브라우저 임시전사(Web Speech API)는 글자가 떴으나 — 임시전사는 마이크 직접, AI Core는 업로드 파일. 엔진이 달라 AI Core 응답 정상을 보장 안 함. 단 오디오에 소리 있다는 증거는 됨.

### 해결
- 목소리 명확히 넣어 녹음 → 정상 전사. 묵음/인식 불가 구간이 원인.

### 교훈
- 빈 응답(seg_count=0) = AI Core가 음성을 못 잡은 것. 오디오 품질/묵음 확인 먼저.
- 임시전사(브라우저)와 AI Core 전사는 다른 엔진. 전자 정상이라 후자 정상 아님.

---

## 3. 이슈 ② — 파일 업로드 `octet-stream` 400

### 증상
- 웹 녹음 회의에서 다운로드한 webm 파일을 새 회의에 업로드 → AI Core 400:
  `mimeType application/octet-stream, which is not supported`.
- 웹 직접 녹음(같은 webm)은 정상. 파일 업로드만 실패.

### 원인
- `/api-binary`는 OData media stream 엔드포인트. CAP가 업로드 오디오의 mimeType을 `octet-stream`/`None`(또는 `video/webm`)으로 줌 → Worker 임시 파일이 `.bin`으로 저장.
- `_mime_type_for_path`(aicore_stt.py)는 **확장자**로만 MIME 판정(`.webm/.mp4/.m4a/.mp3/.wav`). `.bin`은 매핑 없음 → `octet-stream` → AI Core 400.
- 웹 녹음은 CAP가 `audio/webm` 명시 → `.webm` 저장 → 정상.
- raw 로그: `DEBUG _mime_type_for_path name=tmpXXX.bin suffix=.bin` 으로 확정.

### 해결
`_mime_type_for_path`에 **매직넘버 fallback** 추가 — 확장자 매핑 실패 시 파일 헤더(첫 32바이트)로 MIME 추론.
```python
# webm: \x1aE\xdf\xa3 / wav: RIFF...WAVE / mp4: ftyp / mpeg: ID3/\xff\xfb
if head.startswith(b"\x1aE\xdf\xa3"): return "audio/webm"
...
```
근본 해결 — 원인이 octet-stream이든 `video/webm`이든 매직넘버로 잡음. AI Core 400 해결.

### 교훈
- 파일 업로드 경로는 CAP mimeType 보존을 신뢰 못 함. 확장자 잃어버림.
- MIME 판정은 확장자 + 매직넘버 이중. 확장자만 쓰면 `.bin`에서 막힘.

## 4. 이슈 ③ — 5분 업로드 502 ECONNRESET (body limit)

### 증상
- 5분 webm(2MB) 업로드 → `/api-binary/.../audio` POST `502 error ... read ECONNRESET`(approuter 로그). CAP가 연결 끊음.
- 5초(수백KB) OK, 1분(900KB) OK, 1분30초(1.3MB)/2분(1.8MB)/5분(2MB) 전부 실패.

### 원인
- `/api-binary`는 **OData media stream**. media stream은 raw body라 `cds.server.body_parser.limit`(JSON/text body용)가 안 닿음.
- package.json에 `"server": {"body_parser": {"limit": "20mb"}}` 추가했으나 — media stream엔 미적용. 한계 ~1MB(cds media stream 기본).
- Worker 청크 분할(720초/25MB 초과)은 Worker 받은 후. CAP upload limit ~1MB가 청크 임계(25MB)보다 작아 Worker 청크 기능 무용지물.

### 해결(우회)
- `recorder.js` `audioBitsPerSecond: 64000` 추가 — 64kbps로 2분 녹음 ≈ 960KB(한계 내). 음성은 64kbps도 AI Core 인식 가능.
- 근본 해결(media stream limit 상향)은 로컬/운영 분리 번잡 + 운영 영향 → 보류. 긴 오디오는 운영 배포 후 확인.

### 교훈
- cds body_parser.limit = JSON/text body. media stream은 별도 한계. 설정 안 닿음 주의.
- chunk 분할은 Worker 단. CAP upload limit가 chunk 임계보다 작으면 청크 기능 무용.
- 업로드 임계 파악: 5초 OK / 1분(900KB) OK / 1분30초 fail → 한계 ~1MB.

### 적용 안 함
- `package.json` `body_parser.limit 20mb`는 JSON body엔 유효하나 media stream엔 무효. 그대로 두거나 제거 가능(번잡 방지용 남김 가능).

## 5. 이슈 ④ — UI 업로드 실패를 "업로드 대기"로 표시

### 증상
- 업로드 실패(502 등) 시 UI가 즉시 에러를 안 보여주고 "업로드 대기" 빈칸으로 멈춘 것처럼 보임. 뒤로갔다 다시 들어와야 에러 문구 표시.
- 5시간 hang으로 착각했던 3분 오디오도 사실 업로드 실패 후 빈칸 상태.

### 원인
- UI 업로드 상태 폴링/렌더가 실패 응답을 바로 반영 안 함. 화면 전환 후 에러 표시.
- "업로드 대기" = queued/transcribing 대기 상태 텍스트. 실패 시 빈칸 유지.

### 해결
- 코드 수정 안 함(UI 범위, 별세션). 원인 파악으로 착각 방지만.

### 교훈
- "업로드 대기에서 멈춤"은 hang이 아닐 수 있음. 실패 후 빈칸일 수. 뒤로갔다 들어오면 에러 표시되는지 먼저 확인.
- UI 실패 피드백 지연은 hang 오탐 원인.

## 6. 코드 변경 정리 (본 세션)

| 파일 | 변경 | 목적 | 상태 |
|---|---|---|---|
| `aicore_stt.py` `_mime_type_for_path` | 매직넘버 fallback 추가 | `.bin` → MIME 추론, octet-stream 400 해결 | 적용 |
| `recorder.js` | `audioBitsPerSecond: 64000` | 2분 녹음 960KB, 한계 내 | 적용(로컬 검증용) |
| `package.json` cds.server.body_parser.limit | 20mb 추가 | JSON body(media엔 안 닿음, 부분 효과) | 적용(무해) |
| `aicore_stt.py` `_aicore_usage_log_entry` | `DEBUG usage` 로그 추가 | 토큰·지연 비교 데이터 | 적용(비교 후 제거 가능) |

### 제거된 디버그 로그
- `main.py` `DEBUG raw transcript` — 빈 응답 원인 파악 후 제거.
- `aicore_stt.py` `DEBUG AI Core raw content` — 빈 응답 파악 후 제거.
- `aicore_stt.py` `DEBUG _mime_type_for_path` — MIME 원인 확정 후 제거.

## 7. 남은 것

- **긴 오디오(2분+) 업로드**: CAP media stream limit ~1MB. 근본 해결(상향)은 로컬/운영 분리 번잡 → 보류. 운영 배포 후 실제 회의(20분) 품질·청크 확인.
- **UI 업로드 실패 피드백**: 실패 시 즉시 에러 표시 개선(별세션).
- **`DEBUG usage` 로그**: 비교 완료 후 제거 가능(운영 전).
- **`recorder.js` 64kbps**: 로컬 검증용. 운영 품질 검증 후 기본 비트레이트 유지 여부 결정.
