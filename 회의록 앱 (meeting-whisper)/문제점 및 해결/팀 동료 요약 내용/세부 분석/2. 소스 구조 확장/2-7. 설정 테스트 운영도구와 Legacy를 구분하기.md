# 2-7. 설정·테스트·운영도구와 Legacy를 구분하기

## 루트 파일은 실행 코드의 설명서다

루트에는 여러 폴더를 연결하는 설정이 있다.

| 파일                 | 의미                                |
| ------------------ | --------------------------------- |
| `mta.yaml`         | Cloud Foundry에 배포할 프로그램·서비스·환경 변수 |
| `package.json`     | 로컬 실행, 빌드, 배포와 테스트 명령             |
| `xs-security.json` | XSUAA scope와 역할                   |
| `server.js`        | CAP 시작 시 바이너리 업로드와 로컬 정적 UI 경로 연결 |
| `.env.example`     | 필요한 환경 변수의 예시                     |
| `pytest.ini`       | Python 테스트 검색과 import 기준          |

## `scripts`는 제품 기능과 다르다

운영 스크립트는 사용자가 화면에서 실행하는 기능이 아니다.

- AI 사용량 내보내기
- 특정 회의의 상태와 지표 확인
- 남아 있는 음원으로 강제 재전사
- 전사문에서 요약만 다시 실행
- Legacy 데이터를 HANA로 옮기기
- CAP·Worker·브라우저 smoke test

스크립트를 실행하기 전에는 대상 환경과 회의 ID를 명확히 확인해야 한다. 운영 데이터를 직접 바꿀 수 있는 도구도 있기 때문이다.

## 테스트를 현재와 Legacy로 나누기

`tests` 폴더에는 현재 코드와 과거 FastAPI 코드의 테스트가 섞여 있다.

현재 경로와 직접 관련된 대표 테스트는 다음과 같다.

- Worker API와 CAP client
- AI Core Worker 전사
- faster-whisper 대체 경로
- CAP의 요약
- 전사 JSON 검증
- 전사 대기표
- 브라우저 E2E

반면 `legacy/fastapi` 모듈을 import하는 테스트는 과거 PoC를 검증한다.

`npm test`가 성공했다고 해서 현재 CAP와 Worker의 모든 경로가 검증됐다고 단정하면 안 된다. 어떤 테스트 파일이 실제로 실행됐는지를 함께 봐야 한다.

## Legacy는 왜 남아 있나

`legacy/fastapi`는 로컬 FastAPI, SQLite와 WhisperX 중심의 초기 구현이다.

현재 운영 구조는 아니지만 다음 아이디어의 과거 구현을 참고할 수 있다.

- 화자 분리
- 전사·요약·검토 파이프라인
- 로컬 데이터 저장
- 초기 UI와 API

참고 가치와 운영 가치가 같지는 않다. 버그를 고치거나 기능을 추가할 때 현재 CAP 경로와 Legacy 중 어느 쪽을 수정하는지 먼저 확인해야 한다.

## 현재 경로를 판단하는 방법

```text
mta.yaml에 모듈로 포함되는가?
현재 README의 CF 절차에서 사용하는가?
CAP 또는 Worker가 실제로 import하는가?
운영 로그 명령이 해당 앱을 가리키는가?
```

위 질문에 모두 아니라고 답하면 현재 운영 경로가 아닐 가능성이 크다.

## 핵심 정리

> 소스 저장소에는 현재 제품 코드, 개발 도구, 운영 도구와 과거 참고 코드가 함께 있으므로 “파일이 존재한다”와 “운영에서 실행된다”를 구분해야 한다.
