# Whisper — STT 디버그 사례 (업로드 임계 해소·전사 역전)

> [!summary] 한눈에
>
> - 28분/20MB 긴 오디오 비용·품질 비교(케이스 B)를 위해 로컬 업로드 한계를 풀다 발생한 디버그 3건. 모두 2026-08-04(월) 로컬 세션.
> - ① 업로드 ~960KB 임계 502 `ECONNABORTED` — `binary-upload-route`가 인증 미가용(`anonymous`) 시 body를 drain하지 않고 302 응답 → approuter가 큰 body pipe 중 abort → 세션 미생성 → 재시도도 실패. `drainReq()` 3줄 추가로 해소. 1분30초(1.3MB) 업로드 성공.
> - ② `displaySpeaker` UI 크래시 — 2.5 등 응답의 `speaker`가 number/object로 내려올 때 `raw.startsWith is not a function`. `typeof raw !== "string"` 방어 1줄.
> - ③ 2.5 긴 단일 전사 타임스탬프 역전 — 28분 단일 전사에서 `segment end before start` 역전 → Worker 검증 실패. 원인 `chunk=None/None`(분할 안 됨, duration 힌트 미잡음). 해결 방향 `AICORE_STT_CHUNK_SECONDS` 300초 강제 분할(검증 진행 중).
> - 코드 변경: `binary-upload-route.js` `drainReq`, `ui.js` `displaySpeaker` 방어 + 캐시버스터. 진단 로그(`binary-upload-route.js`·`audio-store.js`)는 제거 예정(보류).

## 1. 배경

- 1차 보고서(2026-08-03)는 CAP media stream ~1MB 한계로 1분까지만 측정. 28분(케이스 B) 비교엔 업로드 한계 해소가 선행.
- 한계 해소 과정에서 3건 발생. ①은 이전 이슈③(8/3, 64kbps 우회)의 근본 해결, ②③은 28분 전사 시도 중 노출.
- 본 문서는 그 정리. 8/3 디버그(빈 응답·MIME·body limit·UI)는 `Whisper-STT디버그-오디오업로드및빈응답-20260803.md` 참고.

## 2. 이슈 ① — 업로드 ~960KB 임계 502 ECONNABORTED

### 증상
- 로컬(approuter `:5000` → CAP `:4004`)에서 오디오 업로드가 **~960KB(1분)에서 502 `ECONNABORTED`**. 1분30초(1.3MB) 실패, 5초·1분(900KB)은 성공.
- CAP 진단 로그: `user=anonymous` 두 번 연속. 재시도해도 같음.
- approuter 로그: `write ECONNABORTED`.

### 부정된 가설 (오해 정리)

| 가설                              | 결과                                                                                                  |
| ------------------------------- | --------------------------------------------------------------------------------------------------- |
| approuter가 큰 payload를 trim/제한   | **부정** — KBA 3423929: approuter는 payload 제거·파싱 안 함, 백엔드로 pipe만                                      |
| `cds.body_parser.limit` 1mb가 원인 | **부정** — `server.js`가 `requestBodyLimit = MAX_AUDIO_BYTES×1.4+1 ≈ 211mb`로 덮어쓰기 때문 20mb 설정은 무효       |
| 모델 선택 UI 추가가 원인                 | **부정** — 업로드 파이프 4개 파일(`server.js`·`binary-upload-route.js`·`audio-store.js`·`xs-app.json`)은 일절 미변경 |

### 진짜 원인 — 인증 미가용 + body 미소비의 결합

1. 로컬 `dev/xs-app.json`은 `/api-binary`가 `authenticationType: none` → approuter가 브라우저 인증 안 함 → CAP에 토큰 미부착 → CAP mocked auth `user=anonymous`.
2. 회의 생성(`POST /api/Meetings`)은 OData 핸들이라 `anonymous`여도 동작 → owner=anonymous로 회의 생성됨(성공 로그의 원인).
3. 업로드(`/api-binary`)는 `binary-upload-route`가 직접 user 검사 → `anonymous`면 `req._login()` **302 리다이렉트 응답**.
4. 이때 CAP가 **body를 drain하지 않고** 302 보내고 연결 종료.
5. approuter는 아직 큰 body를 CAP로 pipe 중 → `write ECONNABORTED` → **502**.
6. 브라우저가 302를 못 받음 → mocked 로그인 페이지 미도달 → 세션(alice) 미생성 → 재시도도 `anonymous`.

**왜 ~960KB에서만**: 작은 파일(734KB)은 pipe가 빨리 끝나 CAP 302가 브라우저에 도달 → 로그인 → alice 세션 → 재시도 성공. 큰 파일(1.3MB)은 pipe 중 abort → 세션 미생성 → 두 번 다 실패. 임계 ≈ pipe 타이밍과 abort가 엇나가는 지점.

### 해결
`cap/srv/lib/binary-upload-route.js`에 `drainReq()` 3줄 추가. 응답 전에 요청 body를 모두 소비:
- `anonymous`(401/`_login`)·`403`(MeetingUser 아님)·`catch`(기타 에러) 3곳 모두 응답 직전 `await drainReq(req)`.
- 효과: approuter가 body를 끝까지 보낸 뒤 응답 수신 → 302가 브라우저에 도달 → 로그인 → alice 세션 → 큰 파일도 업로드 성공.
- body를 버퍼링하지 않고 `data` 이벤트를 버리므로 메모리 부담 없음.

### 검증
- 1분30초(1.3MB) 업로드 성공(`user=alice` + `INSERT done`). 임계 960KB 해소.
- 28분(20MB) 업로드 성공 → 케이스 B 3모델 측정 가능.

### 교훈
- approuter는 백엔드 응답이 빨리 오면 pipe를 끊을 수 있음(KBA 3423929). 에러 응답(302/401/403) 전에 body를 drain하지 않으면 큰 body에서 `ECONNABORTED`.
- `authenticationType: none` 로컬 우회가 인증 흐름을 건너뛰어 `anonymous` 처리 → 실환경에선 토큰 부착으로 안 일어남(로컬 특유).
- "작은 건 되고 큰 건 안 되는" 임계 현상 = pipe 타이밍·abort 엇나감. body limit 오탐 주의.

### 남은 UX 과제
- 회의 생성이 `anonymous`로 처리되어 업로드 시 매번 첫 1회는 로그인 리다이렉트를 겪음. 업로드 전 세션(alice) 사전 확보로 1회 로그인 흐름을 없애는 UX 개선은 별도.

## 3. 이슈 ② — displaySpeaker UI 크래시

### 증상
- flash-lite 전사 후 2.5로 재전사 시도 시 UI가 `raw.startsWith is not a function`으로 크래시. 전사 패널 빈 화면.
- 2.5 응답 렌더링 시에만 발생(flash-lite 응답은 정상).

### 원인
- 2.5 등 응답의 `speaker` 필드가 string이 아닌 **number/object**로 내려올 때가 있음.
- `displaySpeaker(raw, names)`(`app/meeting-ui/js/ui.js`)가 `raw.startsWith(...)`를 호출 → string 메서드가 아니라 TypeError.
- flash-lite는 `speaker`가 항상 string이라 안 났음. 모델별 응답 스키마 차이.

### 해결
`displaySpeaker` 첫 줄에 방어 1줄 추가:
```js
if (typeof raw !== "string") return "화자";
```
캐시버스터: `app.js`의 `ui.js?v=20260804-displaySpeaker` (구 버전 캐시 방지).

### 검증
- 2.5 재전사 렌더링 크래시 없음. "화자" 폴백 표시.

### 교훈
- 전사 응답 `speaker` 타입이 모델별로 다를 수 있음. string 가정하면 특정 모델에서 크래시.
- UI 진입점에 타입 가드 필수. 모델 교체·다중 모델 환경에선 응답 스키마 정규화 지점(또는 진입 방어) 필요.

## 4. 이슈 ③ — 2.5 긴 단일 전사 타임스탬프 역전

### 증상
- 28분(20MB) 오디오 2.5 전사 시 `segment 180 end timestamp 657.34 was before start 6.57.4` 역전 → Worker `_normalize_segments()` 검증 실패.
- 재시도 후에도 역전. 3.1-lite·3.5는 같은 오디오에서 발생 안 함(3.1-lite는 환각, 3.5는 정상 전사).
- 로그: `chunk=None/None` (분할 안 됨).

### 원인
- 28분(1680초) > `AICORE_STT_CHUNK_SECONDS`(720)인데도 **분할 안 됨**.
- `_should_chunk_audio`가 duration 힌트를 못 잡아 False → 단일 전사.
- 2.5가 긴 단일 전사(1680초 한 번에)에서 타임스탬프 정밀도 붕괴 → end < start 역전.
- 3.1-lite·3.5는 같은 단일 조건에서 역전 없음 → 2.5 특유의 긴 단일 전사 약점.

### 해결 방향 (진행 중)
- `AICORE_STT_CHUNK_SECONDS` 낮춤(300초=5분 시도 중)으로 강제 분할. duration 힌트 못 잡아도 시간 기반 분할이 동작하도록.
- 또는 duration 힌트 보정(오디오 헤더·길이 사전 추정).
- 정식 버전에선 2.5 긴 전사가 잘 된다는 보고 → 2.5 자체 부적합이 아니라 **단일 전사 조건 문제**, 청크 분할로 해결 가능.

### 검증 (진행 중)
- displaySpeaker 방어 후 크래시 없음(이슈②).
- 청크 분할(300초) 2.5 재전사 역전 해소 검증 진행 중. 해소 시 케이스 B 2.5 전사 정상 측정 가능.

### 교훈
- 청크 분할 로직이 duration 힌트에 의존하면 힌트 미잡음 시 분할 건너뜀. 시간 기반 fallback 필요.
- 긴 단일 전사는 모델별 타임스탬프 정밀도 차이 노출. 2.5는 긴 단일에서 역전 → 청크 분할로 회피.
- `chunk=None/None`이 분할 안 됨 신호. 긴 오디오인데 None이면 역전 위험.

## 5. 코드 변경 정리 (본 세션)

| 파일 | 변경 | 목적 | 상태 |
|---|---|---|---|
| `binary-upload-route.js` `drainReq` | 응답 전 body drain 3곳 | `anonymous`·`403`·`catch` 시 body 미소비 → ECONNABORTED 해소 | 적용 |
| `ui.js` `displaySpeaker` | `typeof raw !== "string"` 방어 | speaker 비문자열 크래시 방어 | 적용 |
| `app.js` | `ui.js?v=20260804-displaySpeaker` 캐시버스터 | 구 버전 캐시 방지 | 적용 |
| `binary-upload-route.js`·`audio-store.js` 진단 로그 | `[BIN-UPLOAD]`·`[AUDIO-STREAM]` 로그 | 업로드 임계 원인 파악용 | 제거 예정(보류) |

### 제거 예정 (보류)
- `binary-upload-route.js` `[BIN-UPLOAD]` 진단 로그 — 임계 원인 확정 후 제거.
- `audio-store.js` `[AUDIO-STREAM]` 진단 로그 — 동일.

## 6. 남은 것

- **진단 로그 제거**: `binary-upload-route.js` + `audio-store.js`의 `[BIN-UPLOAD]`/`[AUDIO-STREAM]` 로그. 임계 원인 확정됐으니 운영 전 제거.
- **2.5 청크 분할 테스트**: `AICORE_STT_CHUNK_SECONDS=300` 추가 후 28분 2.5 재전사, 역전 해소 검증.
- **UX 과제**: 업로드 전 세션(alice) 사전 확보로 첫 1회 로그인 리다이렉트 제거.
- **3.5 빈 응답 원인**: 일시 중지(별도).
- **추가 케이스**: 중간 길이(5~10분)·다양 안건·운영 환경·샘플 수 확보. 케이스 2개로 확정 불가(보고서 §6 제한).

## 7. 디버그 흐름 요약

```
28분/20MB 업로드 시도 → 1분30초(1.3MB) 502 ECONNABORTED [이슈①]
  → 부정된 가설 3개(body_parser·approuter trim·UI 변경)
  → 원인: anonymous 302 응답 전 body 미소비 → approuter pipe abort → 세션 미생성
  → drainReq 추가 → 1.3MB·20MB 업로드 성공
2.5 재전사 렌더링 → raw.startsWith TypeError [이슈②]
  → speaker number/object → displaySpeaker 방어
28분 2.5 전사 → segment end < start 역전 [이슈③]
  → chunk=None/None (duration 힌트 미잡음, 분할 안 됨)
  → AICORE_STT_CHUNK_SECONDS=300 강제 분할 시도 중
→ 케이스 B 3모델 비용·지연 측정 완료(보고서 3.3), 품질 역전 확인(보고서 4.2)
```
